🗄️ What is NoSQL?

The Problem with Traditional SQL

Before NoSQL, the world ran on relational databases (SQL) — think of them like super-organised Excel spreadsheets where every row must fit neatly into predefined columns. This worked great for decades — banking systems, HR databases, inventory management. But around 2000–2010, the internet exploded. Social media emerged. Streaming platforms launched. E-commerce went global.

Suddenly, applications were dealing with:

  • Unstructured data — a Facebook post, a tweet, a product review don't all have the same fields
  • Massive scale — millions of concurrent users worldwide
  • High speed — sub-millisecond response expectations
  • Flexible schemas — product A might have 5 attributes, product B might have 50

Traditional SQL databases struggled here. Scaling them horizontally (adding more machines) was complex and expensive. Defining rigid schemas for unpredictable data was painful. This is the problem NoSQL was invented to solve.

Figure 2: SQL vs NoSQL — how they store data differently

What "NoSQL" Actually Means

NoSQL stands for "Not Only SQL" — it refers to a broad category of database management systems that do not use the traditional relational table structure of SQL databases.

It does NOT mean "no SQL language at all" — some NoSQL databases actually support SQL-like query languages. The key difference is that NoSQL databases are designed to be horizontally scalable, schema-flexible, and optimised for specific access patterns.

💡 Real-world analogy: A SQL database is like a strictly organised filing cabinet where every folder has exactly the same number of slots and all files must fit. A NoSQL database is like a flexible digital folder where each file can be completely different — a photo, a video, a text document, or a spreadsheet — and you can add millions more folders instantly by buying more cabinets.

Core Characteristics of NoSQL

  • NoSQL databases are horizontally scalable, meaning you add more servers to handle more data rather than upgrading a single server.
  • They use a flexible or schema-less data model — no fixed columns
  • Most NoSQL databases follow the BASE model (Basically Available, Soft state, Eventually consistent) rather than the ACID model of SQL.
  • They are optimised for specific access patterns — reads, writes, or both at high speed
  • They handle unstructured and semi-structured data natively

📊 Types of NoSQL Databases

NoSQL is not one thing — it's a family of four distinct database types, each built for a different purpose. Knowing which type to use when is an exam favourite topic.

Figure 3: The four types of NoSQL databases and their AWS equivalents

1. Key-Value Stores

The simplest form of NoSQL. Data is stored as a key-value pair — like a dictionary or a hashmap. You look up a value by its unique key.

  • Examples: Redis, Amazon DynamoDB (can also act as key-value), Amazon ElastiCache
  • Best for: Session management, shopping carts, user preferences, caching, leaderboards
  • Key-value stores offer O(1) lookup time — retrieving a value by key is near-instant regardless of database size.

💡 Analogy: Think of a locker room — each locker has a number (key) and whatever is inside (value). You don't search through every locker; you go directly to locker 47 and open it.

2. Document Stores

Data is stored as semi-structured documents, usually in JSON or BSON format. Each document can have a completely different structure — no fixed schema required.

  • Examples: MongoDB, Amazon DocumentDB, CouchDB
  • Best for: Content management systems, user profiles, product catalogs, blog posts
  • Document databases store data as JSON-like documents, allowing nested structures and arrays within a single record.

💡 Analogy: Think of a filing cabinet where each file can be any shape — one file is a photo, another is a form, another is a letter. You can search inside the files, not just by their label.

3. Wide-Column Stores

Also called column-family databases. Instead of storing data row by row like SQL, they store data column by column. This is extremely efficient for queries that read many rows but only a few columns.

  • Examples: Apache Cassandra, Amazon Keyspaces (Managed Cassandra), HBase
  • Best for: Time-series data, IoT sensor readings, analytics, logging, recommendation engines
  • Wide-column stores are optimised for analytical queries that read millions of rows across a small number of columns very quickly.

4. Graph Databases

Data is stored as nodes (entities) and edges (relationships) between them. Perfect when the relationships themselves are the most important thing to query.

  • Examples: Neo4j, Amazon Neptune
  • Best for: Social networks (who follows who), fraud detection, recommendation engines (who bought this also bought that), knowledge graphs
  • Graph databases excel when queries involve traversing relationships — like "find all friends of friends who live in London."

⚡ Amazon DynamoDB

What is DynamoDB?

Amazon DynamoDB is a fully managed, serverless, NoSQL database service that provides single-digit millisecond performance at any scale.

In plain English: DynamoDB is AWS's flagship NoSQL database. You don't manage servers, you don't patch operating systems, you don't worry about scaling — AWS handles all of that. You just create a table and start storing data. It scales automatically from zero to trillion-item tables without any downtime.

Figure 5: DynamoDB internal architecture — replication, auto-scaling, and global tables

Key Features

  • DynamoDB provides single-digit millisecond latency at any scale — from 1 user to 1 billion users.
  • It is serverless — there are no EC2 instances to manage, patch, or scale.
  • Automatic replication: Data is automatically replicated across 3 Availability Zones within a Region for high availability.
  • Global Tables: Multi-region, multi-active replication — writes can happen in any Region and sync globally
  • DynamoDB Streams: Capture a time-ordered sequence of changes to items — useful for triggering Lambda functions
  • TTL (Time to Live): Automatically delete expired items from a table without consuming write capacity
  • DynamoDB supports two capacity modes: On-Demand (pay per request) and Provisioned (pre-set read/write units).

DynamoDB Data Model

DynamoDB is fundamentally a key-value store with document capabilities. Here's how data is organised:

Figure 6: DynamoDB data model — tables, items, and flexible attributes

  • Table: The top-level container (like a SQL table name, but schema-free)
  • Item: A single record in a table (like a SQL row, but attributes can vary per item)
  • Attribute: A single data field within an item (like a column, but not all items need the same attributes)
  • Every DynamoDB item must have a Primary Key, which uniquely identifies it within the table.

Primary Keys in DynamoDB

This is one of the most exam-tested topics in DynamoDB. There are two types of primary keys:

⚡ Type 1 — Simple Primary Key (Partition Key only):
A single attribute that uniquely identifies the item. DynamoDB uses the partition key value to determine which physical partition stores the item (via internal hashing). Example: UserId = "user_001"

⚡ Type 2 — Composite Primary Key (Partition Key + Sort Key):
Two attributes together form the unique identity. All items with the same Partition Key are stored together, sorted by Sort Key. Example: UserId = "user_001" + OrderDate = "2025-12-09"

When using a Composite Primary Key, multiple items can have the same Partition Key but must have different Sort Keys.

Secondary Indexes

What if you need to query by a field that isn't your primary key? That's what Secondary Indexes are for.

  • A Global Secondary Index (GSI) allows you to query using any non-primary-key attribute as the key — it can span all partition key values.
  • A Local Secondary Index (LSI) uses the same Partition Key as the base table but a different Sort Key — must be created at table creation time.
  • You can have up to 20 GSIs and 5 LSIs per table.

Capacity Modes

FeatureOn-Demand ModeProvisioned Mode
PricingPay per read/write requestPay for reserved RCUs/WCUs
ScalingInstant, automaticManual or with auto-scaling
Best forUnpredictable or new workloadsConsistent, predictable traffic
Cost at scaleHigher per-requestLower if traffic is steady

💡 RCU and WCU: In Provisioned mode, you set Read Capacity Units (RCUs) and Write Capacity Units (WCUs). One RCU = one strongly consistent read per second for items up to 4KB. One WCU = one write per second for items up to 1KB.

Consistency Models

  • Eventually Consistent Reads (default): After a write, there may be a brief delay before all copies reflect the latest data. Uses half an RCU.
  • Strongly Consistent Reads: Always returns the most up-to-date data. Uses one full RCU. Not supported for Global Tables or GSIs.

Use Cases

  • 🛒 E-commerce: Shopping cart, session data, order history
  • 🎮 Gaming: Player profiles, leaderboards, game state
  • 📱 Mobile apps: User data sync, push notification status
  • 🌐 IoT: Sensor readings, device state
  • 💼 Serverless applications: Perfect backend for Lambda-triggered workflows

🔄 AWS Database Migration Service (DMS)

What is DMS?

Imagine you've been running a business for 10 years with a huge Oracle database on-premises. Now you want to move to AWS. How do you migrate years of data without downtime, without data loss, and without breaking anything? That's exactly what AWS Database Migration Service (DMS) is designed to do.

AWS Database Migration Service (DMS) is a fully managed service that helps you migrate databases to AWS quickly and securely with minimal downtime.

Figure 8: DMS architecture — how data moves from source to target

How DMS Works

DMS uses a replication instance — an EC2-like server that AWS manages — to do all the heavy lifting. Here's the process:

  1. You create a Replication Instance — this is the DMS engine that does the data movement work
  2. Define Source Endpoint — connect DMS to your existing database (on-premises, another cloud, or AWS)
  3. Define Target Endpoint — connect DMS to your destination database on AWS
  4. Create a Migration Task — specify what to migrate: full load, CDC only, or both
  5. DMS migrates the data — reads from source, transforms if needed, writes to target

⚡ Change Data Capture (CDC): While DMS moves the initial full load of data, your source database keeps receiving new writes. CDC captures these ongoing changes and applies them to the target in real-time, ensuring your target database stays in sync right up until cutover.

Migration Task Types

  • Full Load: Migrates all existing data from source to target. Best for one-time migrations where brief downtime is acceptable.
  • Full Load + CDC: Migrates all existing data AND continuously replicates ongoing changes. Enables near-zero downtime migration.
  • CDC Only: Only replicates ongoing changes. Used when you've already seeded the target database and only need to keep it in sync.

Supported Sources and Targets

Figure 9: DMS supported source and target databases

📚 According to AWS documentation, DMS supports a wide range of source and target databases including Oracle, Microsoft SQL Server, MySQL, MariaDB, PostgreSQL, MongoDB, SAP, IBM DB2, and more — both on-premises and in other clouds. 📚 Source: AWS DMS User Guide

Homogeneous vs Heterogeneous Migration

  • A homogeneous migration is between the same database engines — such as MySQL on-premises to Amazon RDS MySQL. Schema conversion is not needed.
  • A heterogeneous migration is between different database engines — such as Oracle to Aurora PostgreSQL. Requires the AWS Schema Conversion Tool (SCT) to convert the schema first.

AWS Schema Conversion Tool (SCT)

When migrating between different database engines (heterogeneous), the table structures, stored procedures, views, and triggers must be converted. SCT automates this process:

  • Analyzes source schema and creates a migration assessment report
  • Automatically converts most schema objects
  • Flags items that need manual conversion with severity ratings
  • Generates the converted schema ready for the target database

When to Use DMS

  • Moving from on-premises databases to AWS RDS or Aurora
  • Upgrading database versions (MySQL 5.7 → MySQL 8.0)
  • Migrating from commercial databases (Oracle, SQL Server) to open-source (PostgreSQL, MySQL) to reduce costs
  • Real-time data replication for analytics pipelines (to Redshift or S3)
  • Disaster recovery — keeping a secondary database in sync with the primary

DMS Pricing

  • You pay for the replication instance (per hour, similar to EC2)
  • You pay for data transfer out of AWS (if source is on-premises)
  • Free tier: 750 hours/month of a t3.micro replication instance for the first 12 months
  • The DMS replication instance is a managed EC2 instance — you choose its size based on migration workload, but AWS handles patching and maintenance.

⚡ AWS Lambda

What is Lambda?

Think about how a light switch works. You don't need to keep the power running all the time — you flip the switch when you need light and flip it off when you don't. AWS Lambda works the same way for code.

AWS Lambda is a serverless compute service that runs your code in response to events and automatically manages the underlying compute resources.

With Lambda, you don't provision servers, you don't manage scaling, you don't pay for idle time. You simply upload your code, define the trigger (what event causes it to run), and Lambda handles everything else.

Figure 10: Lambda event-driven architecture — triggers, function execution, and outputs

Key Concepts

  • A Lambda function is your code, its dependencies, and the configuration that tells Lambda how to run it.
  • Lambda supports runtimes including Python, Node.js, Java, Go, Ruby, .NET, and custom runtimes via Lambda Layers.
  • Lambda functions have a maximum execution timeout of 15 minutes per invocation.
  • Each Lambda function gets between 128 MB and 10,240 MB (10 GB) of memory.
  • CPU is proportional to memory — more memory = more CPU allocated automatically

Lambda Triggers (Event Sources)

Lambda is event-driven — it waits for something to happen and then runs. Common triggers include:

TriggerExample Use Case
API GatewayHTTP request triggers a Lambda function (serverless API)
S3File upload triggers image resizing or data processing
DynamoDB StreamsDatabase change triggers a notification or sync
CloudWatch Events/EventBridgeScheduled task (like a cron job)
SNS / SQSMessage in queue triggers processing
CognitoUser sign-up triggers welcome email

The Serverless Concept

Serverless does NOT mean there are no servers — it means you don't see, manage, or pay for servers directly. AWS manages the infrastructure entirely.

Figure 11: Lambda (serverless) vs EC2 (traditional server) — management and cost comparison

Lambda Pricing

Lambda pricing has two components:

  • Number of requests: First 1 million requests per month are free, then $0.20 per million requests
  • Duration: Time your code runs, measured in GB-seconds (memory × duration). First 400,000 GB-seconds per month are free
  • Lambda's pricing model makes it extremely cost-effective for intermittent workloads — you pay nothing when your function isn't running.

Cold Starts

One important concept to understand is the cold start. When a Lambda function hasn't been invoked recently, AWS needs to prepare a new execution environment before running your code. This adds latency (typically 100ms–1s).

  • A cold start occurs when Lambda must initialise a new execution environment because no warm instance is available.
  • Provisioned Concurrency is a feature that pre-warms Lambda environments to eliminate cold starts for latency-sensitive applications

When to Use Lambda

  • 🔧 Serverless APIs — API Gateway + Lambda replaces a full server
  • 📁 File processing — process uploads to S3 automatically
  • ⏰ Scheduled tasks — nightly reports, cleanup jobs
  • 🔄 Real-time data processing — process DynamoDB Streams or Kinesis
  • 🤖 Automation — respond to CloudWatch alarms, resize images, send emails

📚 According to AWS documentation, Lambda automatically scales the number of concurrent executions based on the incoming event volume, up to the default concurrency limit of 1,000 concurrent executions per region (can be increased via support request). 📚 Source: AWS Lambda Developer Guide

const multer = require('multer');

const app = express();
app.use(cors());
app.use(express.json());

// Serve React build files (production)
app.use(express.static(path.join(__dirname, 'client/build')));

// Configure file upload storage

  destination: './uploads/',
  filename: (req, file, cb) => {
    cb(null, Date.now() + '.pdf');
  }
});
const upload = multer({ storage, fileFilter: (req, file, cb) => {
  if (file.mimetype === 'application/pdf') cb(null, true);

}});

// MySQL connection
const db = mysql.createConnection({
  host: 'localhost',
  user: 'root',
  password: 'YourPassword123!',
  database: 'jobappdb'
});

db.connect(err => {
  if (err) { console.error('DB Error:', err); return; }
  console.log('MySQL connected');

app.post('/api/apply', upload.single('resume'), (req, res) => {

  const resumePath = req.file ? 'uploads/' + req.file.filename : null;
  const sql = 'INSERT INTO applications (full_name, email, position, resume_path) VALUES (?, ?, ?, ?)';
  db.query(sql, [fullName, email, position, resumePath], (err) => {
    if (err) return res.status(500).json({ error: err.message });
    res.json({ message: 'Application submitted successfully' });
  });

    import React, { useState } from 'react';

function App() {

    fullName: '', email: '', position: ''
  });
  const [resume, setResume] = useState(null);
  const [message, setMessage] = useState('');

  const handleSubmit = async (e) => {
    e.preventDefault();
    const data = new FormData();
    data.append('fullName', formData.fullName);
    data.append('email', formData.email);
    data.append('position', formData.position);
    if (resume) data.append('resume', resume);

    const res = await fetch('http://YOUR_PUBLIC_IP:5000/api/apply', {
      method: 'POST', body: data
    });
    const result = await res.json();
    setMessage(result.message);
  };

  return (
    <div style={{maxWidth:600, margin:'50px auto', fontFamily:'Arial'}}>
      <h1>Job Application Form</h1>
      <form onSubmit={handleSubmit}>
        <label>Full Name:</label>
        <input type="text" required onChange={e => setFormData({...formData, fullName: e.target.value})} />
        <label>Email:</label>
        <input type="email" required onChange={e => setFormData({...formData, email: e.target.value})} />
        <label>Position:</label>
        <select onChange={e => setFormData({...formData, position: e.target.value})}>
          <option value="">Select a position</option>
          <option>Manager</option>
          <option>Designer</option>
          <option>Developer</option>
        </select>
        <label>Resume (PDF only):</label>
        <input type="file" accept=".pdf" onChange={e => setResume(e.target.files[0])} />
        <button type="submit">Submit Application</button>
      </form>
      {message && <p style={{color:'green'}}>{message}</p>}
    </div>
  );
}
export default App;

Part 4: Good vs Bad Partition Key Experiment

This is the most important part. Run the following thought experiment:

❌ Bad partition key example: Suppose you used Country = "India" as the partition key for 100 million users. All Indian users go to ONE partition. That partition gets all the reads/writes while the "USA" and "UK" partitions sit idle. This is called a hot partition and causes throttling.

✅ Good partition key example: Using UserId (a UUID or unique ID) as the partition key distributes data evenly across all partitions — no single partition is overloaded.

Create a second table to see this in practice:

aws dynamodb create-table \
  --table-name OrdersBadDesign \
  --attribute-definitions AttributeName=Status,AttributeType=S \
  --key-schema AttributeName=Status,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST

This table uses Status (values: "pending", "completed", "cancelled") as the partition key — only 3 possible values means only 3 partitions are ever used, causing severe hot-partition issues.

Verification & Cleanup

  1. Verify your CRUD operations by running a scan: aws dynamodb scan --table-name Users. Confirm 2 items remain (user_001 updated, user_002 unchanged, user_003 deleted).

  2. Delete both tables to avoid any future charges:

    aws dynamodb delete-table --table-name Users
aws dynamodb delete-table --table-name OrdersBadDesign

    import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient, PutCommand, GetCommand, DeleteCommand, ScanCommand } from "@aws-sdk/lib-dynamodb";

const client = new DynamoDBClient({});
const db = DynamoDBDocumentClient.from(client);
const TABLE = "UsersTable";

export const handler = async (event) => {
  const method = event.httpMethod || event.requestContext?.http?.method;
  const path   = event.path || event.rawPath || '';
  const userId = event.pathParameters?.id;

  try {
    // POST /users — create a user
    if (method === 'POST') {
      const body = JSON.parse(event.body || '{}');
      const newUser = {
        userId: crypto.randomUUID(),
        name:   body.name,
        email:  body.email,
        createdAt: new Date().toISOString()
      };
      await db.send(new PutCommand({ TableName: TABLE, Item: newUser }));
      return respond(201, { message: 'User created', user: newUser });
    }

    // GET /users/{id} — get a user
    if (method === 'GET' && userId) {
      const result = await db.send(new GetCommand({ TableName: TABLE, Key: { userId } }));
      if (!result.Item) return respond(404, { error: 'User not found' });
      return respond(200, result.Item);
    }

    // GET /users — list all users
    if (method === 'GET') {
      const result = await db.send(new ScanCommand({ TableName: TABLE }));
      return respond(200, { users: result.Items, count: result.Count });
    }

    // DELETE /users/{id}
    if (method === 'DELETE' && userId) {
      await db.send(new DeleteCommand({ TableName: TABLE, Key: { userId } }));
      return respond(200, { message: `User ${userId} deleted` });
    }

    return respond(405, { error: 'Method not allowed' });

  } catch (err) {
    console.error('Error:', err);
    return respond(500, { error: err.message });
  }
};

const respond = (status, body) => ({
  statusCode: status,
  headers: { 'Content-Type': 'application/json', 'Access-Control-Allow-Origin': '*' },
  body: JSON.stringify(body)
});

  console.log('S3 Event:', JSON.stringify(event, null, 2));

  3. Deploy this function code:

    import { DynamoDBClient } from "@aws-sdk/client-dynamodb";
import { DynamoDBDocumentClient, PutCommand, ScanCommand } from "@aws-sdk/lib-dynamodb";
import { S3Client, PutObjectCommand } from "@aws-sdk/client-s3";

const db  = DynamoDBDocumentClient.from(new DynamoDBClient({}));
const s3  = new S3Client({});
const TABLE  = "JobApplications";
const BUCKET = "job-resumes-YOUR-INITIALS-2025";

export const handler = async (event) => {
  const method = event.requestContext?.http?.method;

  // Handle CORS preflight
  if (method === 'OPTIONS') {
    return {
      statusCode: 200,
      headers: corsHeaders(),
      body: ''
    };
  }

  try {
    if (method === 'POST') {
      const body = JSON.parse(event.body || '{}');
      const applicationId = crypto.randomUUID();
      let resumeUrl = null;

      // If resume is provided as base64
      if (body.resumeBase64 && body.resumeFileName) {
        const fileBuffer = Buffer.from(body.resumeBase64, 'base64');
        const s3Key = `resumes/${applicationId}/${body.resumeFileName}`;
        await s3.send(new PutObjectCommand({
          Bucket: BUCKET,
          Key:    s3Key,
          Body:   fileBuffer,
          ContentType: 'application/pdf'
        }));
        resumeUrl = `s3://${BUCKET}/${s3Key}`;
      }

      const application = {
        applicationId,
        fullName:    body.fullName,
        email:       body.email,
        position:    body.position,
        resumeUrl,
        submittedAt: new Date().toISOString(),
        status:      'received'
      };

      await db.send(new PutCommand({ TableName: TABLE, Item: application }));

      return {
        statusCode: 201,
        headers: corsHeaders(),
        body: JSON.stringify({ message: 'Application submitted successfully!', applicationId })
      };
    }

    if (method === 'GET') {
      const result = await db.send(new ScanCommand({ TableName: TABLE }));
      return {
        statusCode: 200,
        headers: corsHeaders(),
        body: JSON.stringify({ applications: result.Items, total: result.Count })
      };
    }

    return { statusCode: 405, headers: corsHeaders(), body: JSON.stringify({ error: 'Method not allowed' }) };

  } catch (err) {
    console.error('Error:', err);
    return { statusCode: 500, headers: corsHeaders(), body: JSON.stringify({ error: err.message }) };
  }
};

const corsHeaders = () => ({
  'Content-Type': 'application/json',
  'Access-Control-Allow-Origin': '*',
  'Access-Control-Allow-Methods': 'GET,POST,OPTIONS',
  'Access-Control-Allow-Headers': 'Content-Type'
});

📝 Overall Summary

  • NoSQL origin: Born from the need to handle unstructured data, horizontal scale, and flexible schemas that relational SQL databases couldn't handle efficiently at internet scale.
  • 4 NoSQL types: Key-Value (simple lookups — DynamoDB/ElastiCache), Document (JSON data — DocumentDB), Wide-Column (analytics/IoT — Keyspaces), Graph (relationships — Neptune).
  • DynamoDB: AWS's fully managed, serverless NoSQL database. Single-digit millisecond latency, automatic replication across 3 AZs, infinitely scalable.
  • DynamoDB keys: Every item needs a Primary Key — either a simple Partition Key or a composite Partition Key + Sort Key. GSIs allow querying on any attribute; LSIs extend the sort key within the same partition.
  • DynamoDB capacity: On-Demand (pay per request, variable traffic) vs Provisioned (pre-set RCU/WCU, steady traffic). Strongly Consistent Reads cost twice the RCUs of Eventually Consistent Reads.
  • DMS: Fully managed service to migrate databases to AWS with minimal downtime. Uses a replication instance, source/target endpoints, and CDC to keep source and target in sync during migration.
  • DMS migration types: Full Load (one-time copy), Full Load + CDC (live migration with zero downtime), CDC Only (ongoing sync).
  • Homogeneous vs Heterogeneous: Same-engine migrations use DMS directly; different-engine migrations require AWS Schema Conversion Tool (SCT) first.
  • Lambda: Serverless compute — upload code, define a trigger, AWS runs and scales it automatically. Pay only when code executes. Maximum timeout of 15 minutes.
  • Lambda pricing: First 1 million requests/month free, then $0.20 per million. First 400,000 GB-seconds/month free for duration.
  • Hands-On Project: Deployed a 3-tier Job Application App on a single T2.medium EC2 instance: React (frontend) → Node.js/Express (backend API) → MySQL (database). Applications stored with resume PDF uploads.
