Introduction to Containerization

✅ Overview

Containerization is a lightweight alternative to traditional virtual machines for deploying applications. Instead of running applications directly on physical servers or full virtual machines, containers package applications with their dependencies into isolated, portable units.

💡 Key Concept: Containers share the host OS kernel but maintain isolated execution environments, making them more efficient than VMs.

📊 Deployment Methods Comparison

Deployment Method Resource Usage Startup Time Isolation Level Use Case
Virtual Machine (EC2) High (Full OS) Minutes Complete Traditional apps, legacy systems
Docker Container Low (Shared kernel) Seconds Process-level Microservices, cloud-native apps

🎯 Why Containerization?

  • Portability: Run anywhere - local, cloud, hybrid
  • Efficiency: No need to pre-allocate full OS or hardware
  • Speed: Fast startup and deployment
  • Consistency: "Works on my machine" problem solved
  • Scalability: Easy to replicate and scale

Docker Fundamentals

✅ What is Docker?

Docker is a containerization runtime that builds and runs containers. It is the main environment for creating containerized applications.

⚠️ Important: Docker is NOT just a tool - it's a complete platform consisting of multiple components working together.

⚙️ Docker Components

When you install Docker, you get two main components:

Component Type Purpose Who Uses It
Docker CLI Command Line Interface User interface to interact with Docker Developers, DevOps engineers
Docker Daemon Background Service Executes Docker commands, manages containers System (automatic)

🔐 Docker User Permissions

❌ Common Mistake: By default, only root user can run Docker commands. Non-root users will get "permission denied" errors.

⚙️ Practical Implementation

Method 1: AWS CLI (Adding User to Docker Group)

# Add current user to docker group
sudo usermod -aG docker $USER

# Apply group changes without logout
newgrp docker

# Verify user is in docker group
groups

# Test Docker access
docker ps

Method 2: AWS Console (EC2 Instance Setup)

  1. Launch an Ubuntu EC2 instance (t2.micro or larger)
  2. Connect via SSH or EC2 Instance Connect
  3. Install Docker: 
    sudo apt update
sudo apt install docker.io -y
sudo systemctl start docker
sudo systemctl enable docker
  4. Add ubuntu user to docker group: 
    sudo usermod -aG docker ubuntu
  5. Reconnect to session or run: newgrp docker
  6. Verify: docker --version

✅ Best Practice: Always verify Docker daemon is running before executing Docker commands using sudo systemctl status docker

🔍 Troubleshooting Docker Issues

Issue Cause Solution
Permission denied User not in docker group sudo usermod -aG docker $USER
Cannot connect to Docker daemon Docker service not running sudo systemctl start docker
Command not found Docker not installed Install Docker using package manager

Docker Components & Architecture

✅ Docker Build Process

Docker follows a three-step process to create and run containers:

Figure 1: Docker Build Process - Dockerfile to Container

📄 1. Dockerfile

A Dockerfile is a text file containing instructions to build a Docker image. It defines:

  • Base image to use
  • Application code to copy
  • Dependencies to install
  • Commands to run
  • Ports to expose

Example Dockerfile Structure:

# Base image
FROM ubuntu:22.04

# Update and install packages
RUN apt-get update && apt-get install -y python3 python3-pip

# Set working directory
WORKDIR /app

# Copy application files
COPY . /app

# Install Python dependencies
RUN pip3 install -r requirements.txt

# Expose port
EXPOSE 8000

# Run application
CMD ["python3", "app.py"]

💡 Tip: Each instruction in Dockerfile creates a new layer in the image. Optimize by combining commands with &&

🖼️ 2. Docker Image

A Docker Image is a read-only template for containers. Think of it as a blueprint.

Property Description Analogy
Read-only Cannot be modified once built Like a photo negative
Layered Built from multiple layers Like a cake with layers
Tagged Identified by name:tag Like a product with SKU
Portable Can be shared and reused Like a software installer

Building an Image:

Method 1: CLI
# Build image from Dockerfile in current directory
docker build -t myapp:v1.0 .

# Explanation:
# -t : Tag the image with name:version
# . : Use Dockerfile in current directory

# List all images
docker images

# Remove an image
docker rmi myapp:v1.0
Method 2: AWS Console (Using CodeBuild)
  1. Go to AWS CodeBuild
  2. Create a new build project
  3. Select source (GitHub, CodeCommit, S3)
  4. Choose environment: Ubuntu + Docker
  5. Add buildspec.yml: 
    version: 0.2
phases:
  build:
    commands:
      - docker build -t myapp:v1.0 .
  6. Click Start Build

📦 3. Docker Container

A Docker Container is a running instance of an image. It's a lightweight, isolated process.

⚠️ Key Difference: Image = Blueprint (static), Container = Running application (dynamic)

Running a Container:

Method 1: CLI
# Run container from image
docker run -d -p 8000:8000 --name mycontainer myapp:v1.0

# Explanation:
# -d : Run in detached mode (background)
# -p : Port mapping (host:container)
# --name : Give container a name
# myapp:v1.0 : Image to use

# List running containers
docker ps

# List all containers (including stopped)
docker ps -a

# Stop container
docker stop mycontainer

# Start stopped container
docker start mycontainer

# Remove container
docker rm mycontainer

# View container logs
docker logs mycontainer

# Execute command inside container
docker exec -it mycontainer bash
Method 2: AWS Console (Using ECS)
  1. Go to Amazon ECS
  2. Create an ECS Cluster
  3. Create a Task Definition:
    • Select Fargate or EC2 launch type
    • Define container image (from ECR or Docker Hub)
    • Set CPU/Memory limits
    • Configure port mappings
  4. Create a Service from task definition
  5. Service will maintain desired number of running containers

✅ Best Practices:

  • Always use specific image tags (avoid :latest in production)
  • Use -d flag to run containers in background
  • Always name your containers for easy management
  • Clean up stopped containers regularly: docker container prune

Docker Images & Registry

✅ Docker Hub - Public Registry

Docker Hub is the default public registry for Docker images. It functions like GitHub for Docker images.

💡 Analogy: Docker Hub is like an app store for container images - you can download official and community images.

⚙️ Working with Docker Hub

Method 1: CLI Commands

# Login to Docker Hub
docker login

# Pull image from Docker Hub
docker pull nginx:latest
docker pull ubuntu:22.04
docker pull python:3.9-slim

# Push image to Docker Hub
docker tag myapp:v1.0 username/myapp:v1.0
docker push username/myapp:v1.0

# Search for images
docker search nginx

# Logout
docker logout

Method 2: Docker Hub Web Interface

  1. Go to hub.docker.com
  2. Create a free account
  3. Search for images using search bar
  4. View official images (verified by Docker)
  5. Check image details:
    • Number of pulls
    • Available tags
    • Dockerfile source
    • Documentation
  6. Create repositories to store your images:
    • Click Create Repository
    • Set Public or Private
    • Add description and README

🔒 AWS ECR - Private Registry

Amazon ECR (Elastic Container Registry) is AWS's private Docker registry service for enterprise use.

Feature Docker Hub AWS ECR
Access Public by default Private by default
Authentication Username/Password IAM roles/policies
Integration Any platform Deep AWS integration
Cost Free (limited private repos) Pay per GB stored/transferred
Security Basic Image scanning, encryption

⚙️ Setting Up AWS ECR

Method 1: AWS CLI

# Create ECR repository
aws ecr create-repository \
    --repository-name myapp \
    --region us-east-1

# Get login password and authenticate
aws ecr get-login-password --region us-east-1 | \
docker login --username AWS --password-stdin \
123456789012.dkr.ecr.us-east-1.amazonaws.com

# Tag image for ECR
docker tag myapp:v1.0 \
123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:v1.0

# Push image to ECR
docker push \
123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:v1.0

# Pull image from ECR
docker pull \
123456789012.dkr.ecr.us-east-1.amazonaws.com/myapp:v1.0

# List images in repository
aws ecr list-images \
    --repository-name myapp \
    --region us-east-1

Method 2: AWS Console

  1. Go to Amazon ECR service
  2. Click Get Started or Create repository
  3. Configure repository:
    • Visibility: Private or Public
    • Repository name: myapp
    • Image scanning: Enable for security
    • Encryption: Enable KMS encryption
  4. Click Create repository
  5. View push commands in repository details
  6. Set up lifecycle policies:
    • Automatically delete old images
    • Keep only N most recent images
    • Save storage costs
  7. Configure repository policies (IAM-based access)

✅ Best Practices:

  • Use ECR for production workloads (security + AWS integration)
  • Use Docker Hub for public images and testing
  • Enable image scanning in ECR to detect vulnerabilities
  • Implement lifecycle policies to manage storage costs
  • Use IAM roles for EC2/ECS to access ECR (no credentials needed)

🔐 IAM Role for EC2 to Access ECR

# Attach IAM role to EC2 with this policy
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ecr:GetAuthorizationToken",
        "ecr:BatchGetImage",
        "ecr:GetDownloadUrlForLayer"
      ],
      "Resource": "*"
    }
  ]
}

With this IAM role attached, EC2 instances can pull images from ECR without storing credentials.

Docker Compose - Multi-Container Management

✅ What is Docker Compose?

Docker Compose is a tool for defining and running multi-container Docker applications using a single YAML file.

⚠️ Problem it Solves: Managing multiple containers manually is tedious. Imagine running 5+ containers with different configurations - Docker Compose automates this!

🎯 Use Cases

  • Microservices: Frontend + Backend + Database
  • Development Environment: App + Redis + PostgreSQL
  • Testing: Application + Mock services
  • Multi-tier Applications: Web + API + Cache + DB

📄 Docker Compose File Structure

# docker-compose.yml
version: '3.8'

services:
  # Frontend container
  frontend:
    image: myapp-frontend:latest
    ports:
      - "80:80"
    depends_on:
      - backend
    environment:
      - API_URL=http://backend:5000

  # Backend container
  backend:
    image: myapp-backend:latest
    ports:
      - "5000:5000"
    depends_on:
      - database
    environment:
      - DB_HOST=database
      - DB_PORT=5432

  # Database container
  database:
    image: postgres:14
    environment:
      - POSTGRES_DB=myapp
      - POSTGRES_USER=admin
      - POSTGRES_PASSWORD=secret123
    volumes:
      - db-data:/var/lib/postgresql/data

volumes:
  db-data:

⚙️ Working with Docker Compose

Method 1: CLI Commands

# Install Docker Compose (if not installed)
sudo curl -L "https://github.com/docker/compose/releases/latest/download/docker-compose-$(uname -s)-$(uname -m)" -o /usr/local/bin/docker-compose
sudo chmod +x /usr/local/bin/docker-compose
docker-compose --version

# Start all containers defined in docker-compose.yml
docker-compose up -d

# Explanation:
# up : Start services
# -d : Run in detached mode (background)

# View running services
docker-compose ps

# View logs of all services
docker-compose logs

# View logs of specific service
docker-compose logs backend

# Stop all services
docker-compose stop

# Stop and remove all containers
docker-compose down

# Stop and remove containers + volumes
docker-compose down -v

# Restart services
docker-compose restart

# Scale a service
docker-compose up -d --scale backend=3

# Rebuild images and restart
docker-compose up -d --build

Method 2: AWS Console (Using ECS with Docker Compose)

  1. Install ECS CLI: 
    sudo curl -Lo /usr/local/bin/ecs-cli https://amazon-ecs-cli.s3.amazonaws.com/ecs-cli-linux-amd64-latest
sudo chmod +x /usr/local/bin/ecs-cli
  2. Configure ECS CLI: 
    ecs-cli configure --cluster my-cluster --region us-east-1 --default-launch-type FARGATE
  3. Create docker-compose.yml (same as above)
  4. Deploy to ECS: 
    ecs-cli compose up
  5. View services in ECS Console
  6. Scale using ECS service settings

💡 Tip: AWS recently introduced Docker Compose support in ECS, making it easier to deploy multi-container apps to AWS.

🔑 Key Docker Compose Concepts

Concept Description Example
services Define containers to run frontend, backend, database
image Specify Docker image to use nginx:latest, postgres:14
build Build image from Dockerfile build: ./app
ports Port mapping (host:container) - "80:80"
environment Set environment variables DB_HOST=postgres
depends_on Start order dependency depends_on: - database
volumes Persistent data storage - db-data:/var/lib/postgresql
networks Custom networks for services networks: - frontend-net

📊 Example: WordPress with MySQL

version: '3.8'

services:
  wordpress:
    image: wordpress:latest
    ports:
      - "8080:80"
    environment:
      WORDPRESS_DB_HOST: mysql
      WORDPRESS_DB_USER: wpuser
      WORDPRESS_DB_PASSWORD: wppass
      WORDPRESS_DB_NAME: wordpress
    depends_on:
      - mysql
    volumes:
      - wordpress-data:/var/www/html

  mysql:
    image: mysql:8.0
    environment:
      MYSQL


_ROOT_PASSWORD: rootpass
      MYSQL_DATABASE: wordpress
      MYSQL_USER: wpuser
      MYSQL_PASSWORD: wppass
    volumes:
      - mysql-data:/var/lib/mysql

volumes:
  wordpress-data:
  mysql-data:

Access WordPress at: http://localhost:8080

✅ Best Practices:

  • Use depends_on to ensure correct startup order
  • Always use volumes for database data (persistence)
  • Use environment variables for configuration (never hardcode secrets)
  • Name your services clearly (frontend, backend, database)
  • Use .env files for sensitive data

Docker Networking & Volumes

✅ Docker Networking

Docker containers need to communicate with each other and the outside world. Docker provides different network types for different use cases.

🌐 Docker Network Types

Network Type Use Case Container Isolation Internet Access
bridge (default) Containers on same host communicate Yes Via host (NAT)
host Container uses host network directly No Direct
overlay Multi-host container communication Yes Via overlay network
none Complete network isolation Complete None

Figure 2: Docker Bridge Network Topology

⚙️ Working with Docker Networks

Method 1: CLI Commands

# List networks
docker network ls

# Create custom bridge network
docker network create myapp-network

# Inspect network
docker network inspect myapp-network

# Run container on specific network
docker run -d --name web --network myapp-network nginx

# Run another container on same network
docker run -d --name api --network myapp-network myapi:latest

# Containers can now communicate using container names
# From 'web' container: curl http://api:5000

# Connect existing container to network
docker network connect myapp-network database

# Disconnect container from network
docker network disconnect myapp-network database

# Remove network
docker network rm myapp-network

# Create container with host network (no isolation)
docker run -d --network host nginx

Method 2: Using Docker Compose

version: '3.8'

services:
  frontend:
    image: myapp-frontend:latest
    networks:
      - frontend-network
      - backend-network

  backend:
    image: myapp-backend:latest
    networks:
      - backend-network
      - database-network

  database:
    image: postgres:14
    networks:
      - database-network

networks:
  frontend-network:
  backend-network:
  database-network:

🗄️ Docker Volumes - Data Persistence

By default, data inside containers is ephemeral - it disappears when container is removed. Volumes solve this problem.

❌ Common Mistake: Not using volumes for databases - all data is lost when container restarts!

📦 Volume Types

Volume Type Description Use Case Managed By
Named Volumes Docker-managed volumes Database data, application state Docker
Bind Mounts Mount host directory into container Development, config files User
tmpfs Store in host memory (RAM) Temporary data, secrets Docker

⚙️ Working with Volumes

Method 1: CLI Commands

# Create named volume
docker volume create mydata

# List volumes
docker volume ls

# Inspect volume
docker volume inspect mydata

# Use volume with container
docker run -d \
  --name myapp \
  -v mydata:/app/data \
  myapp:latest

# Bind mount (host directory to container)
docker run -d \
  --name webapp \
  -v /home/user/app:/usr/share/nginx/html \
  nginx

# Read-only bind mount
docker run -d \
  -v /home/user/config:/app/config:ro \
  myapp:latest

# Remove volume
docker volume rm mydata

# Remove all unused volumes
docker volume prune

Method 2: Using Docker Compose

version: '3.8'

services:
  database:
    image: postgres:14
    volumes:
      # Named volume for database data
      - db-data:/var/lib/postgresql/data
      
      # Bind mount for init scripts
      - ./init-scripts:/docker-entrypoint-initdb.d
      
      # Bind mount for config (read-only)
      - ./postgres.conf:/etc/postgresql/postgresql.conf:ro

  application:
    image: myapp:latest
    volumes:
      # Named volume for uploads
      - app-uploads:/app/uploads
      
      # Bind mount for logs
      - ./logs:/app/logs

volumes:
  db-data:
  app-uploads:

🔌 Port Mapping

To make containers accessible from outside, you need to map container ports to host ports.

# Port mapping syntax: -p HOST_PORT:CONTAINER_PORT
docker run -d -p 8080:80 nginx

# Map to specific host IP
docker run -d -p 127.0.0.1:8080:80 nginx

# Map random host port
docker run -d -p 80 nginx

# Multiple port mappings
docker run -d \
  -p 80:80 \
  -p 443:443 \
  nginx

# View port mappings
docker port container_name

✅ Best Practices:

  • Use named volumes for all persistent data (databases, uploads)
  • Use bind mounts for development and configuration
  • Always use custom networks instead of default bridge
  • Use container names for inter-container communication
  • Avoid --network host in production (security risk)
  • Clean up unused volumes regularly with docker volume prune

Why Container Orchestration?

✅ The Problem with Docker Alone

Docker is excellent for running containers, but it lacks features needed for production environments.

⚠️ Real-World Scenario: You're running an e-commerce website with 3 containers. Suddenly, traffic increases 10x during a sale. What happens?

❌ What Docker CANNOT Do

Feature Required in Production? Docker Support? Impact Without It
Auto-Scaling ✅ Yes ❌ No Cannot handle traffic spikes
Load Balancing ✅ Yes ❌ No Single point of failure
Self-Healing ✅ Yes ❌ No Manual intervention needed
Rolling Updates ✅ Yes ❌ No Downtime during deployments
Rollback ✅ Yes ❌ No Cannot revert bad deployments
Health Checks ✅ Yes ⚠️ Basic Cannot detect app-level issues

🎯 Production Requirements

  1. High Availability: Multiple container replicas across servers
  2. Auto-Scaling: Automatically add/remove containers based on load
  3. Load Balancing: Distribute traffic across container replicas
  4. Self-Healing: Automatically restart failed containers
  5. Zero-Downtime Deployments: Update without stopping service
  6. Service Discovery: Containers find each other dynamically
  7. Resource Management: Efficient CPU/memory allocation

Figure 3: Docker Alone vs Container Orchestration

🚀 Enter Container Orchestration

Container Orchestration = Automatic management of containers in production

💡 Definition: Container orchestration tools automatically handle scheduling, scaling, load balancing, health checks, self-healing, and rolling deployments of containers.

🛠️ Container Orchestration Tools

Tool Type Complexity Best For Market Share
Docker Swarm Docker-native Low Small deployments, learning Low
Kubernetes (K8s) Open-source, CNCF High Production, enterprise ⭐ Dominant
AWS ECS AWS-managed Medium AWS-native apps Medium
AWS EKS Managed Kubernetes Medium-High Kubernetes on AWS Growing

🎯 Why Kubernetes Won

  • ✅ Open-source: No vendor lock-in
  • ✅ Cloud-agnostic: Works on AWS, Azure, GCP, on-premises
  • ✅ Industry standard: Massive community and ecosystem
  • ✅ Feature-rich: Covers all production needs
  • ✅ Extensible: Plugins and operators for any use case
  • ✅ Backed by CNCF: Google, Red Hat, Microsoft support

✅ Key Takeaway: Docker is great for running containers, but you need orchestration (Kubernetes/ECS/EKS) for production deployments with high availability, scaling, and reliability.

Kubernetes (K8s) Architecture

✅ What is Kubernetes?

Kubernetes (K8s) is an open-source container orchestration platform that automates deployment, scaling, and management of containerized applications.

💡 Name Origin: "Kubernetes" (Greek for "helmsman") → K + 8 letters + s = K8s

🏗️ Kubernetes Architecture - Cluster-Based

Kubernetes runs as a cluster with two main components:

Component Role Analogy Manages
Control Plane Brain of cluster Orchestra conductor Decisions, scheduling, state
Worker Nodes Execution units Orchestra musicians Running containers (pods)

Figure 1: Kubernetes Cluster Architecture

🧠 Control Plane Components

1. API Server

The front door of Kubernetes. All communication goes through the API Server.

  • ✅ Single entry point for all requests
  • ✅ Validates and authenticates requests
  • ✅ Routes requests to appropriate components
  • ✅ Implements RBAC (Role-Based Access Control)

2. etcd

The cluster's memory/database. Stores all cluster state and configuration.

  • ✅ Key-value store (like a database)
  • ✅ Source of truth for cluster state
  • ✅ Stores: pods, services, secrets, config maps
  • ✅ Highly available and consistent

⚠️ Critical: If etcd is lost, the entire cluster state is lost. Always back up etcd in production!

3. Scheduler

The decision engine that assigns pods to worker nodes.

  • ✅ Evaluates CPU and memory availability
  • ✅ Considers node constraints and affinity rules
  • ✅ Selects best node for each pod
  • ✅ Ensures even distribution of workload

4. Controller Manager

A collection of controllers that maintain desired state.

  • ✅ Node Controller: Monitors node health
  • ✅ Replication Controller: Maintains pod replicas
  • ✅ Endpoints Controller: Manages service endpoints
  • ✅ Service Account Controller: Manages authentication

5. Cloud Controller Manager (Optional)

Integrates with cloud provider APIs (AWS, Azure, GCP).

  • ✅ Manages load balancers
  • ✅ Provisions storage volumes
  • ✅ Manages node lifecycle in cloud

⚙️ Worker Node Components

1. Kubelet

The node agent that runs on every worker node.

  • ✅ Communicates with Control Plane
  • ✅ Ensures containers are running in pods
  • ✅ Reports node and pod status
  • ✅ Executes pod lifecycle operations

2. Container Runtime

The software that runs containers. You must choose one:

Runtime Description Status
containerd Industry standard, lightweight ✅ Recommended
CRI-O Kubernetes-native runtime ✅ Good
Docker Original runtime (deprecated) ⚠️ Being phased out

3. kube-proxy

The network proxy that manages network rules.

  • ✅ Maintains network rules on nodes
  • ✅ Enables pod-to-pod communication
  • ✅ Implements Service abstraction
  • ✅ Performs connection forwarding

📦 Pod - The Smallest Unit

A Pod is the smallest deployable unit in Kubernetes.

💡 Key Concept: A Pod is NOT a container - it's a wrapper around one or more containers that share network and storage.

Property Description
Containers Usually 1, sometimes 2+ (sidecar pattern)
Shared Network All containers share same IP address
Shared Storage Can mount same volumes
Lifecycle Ephemeral - pods die and are replaced

⚙️ Interacting with Kubernetes

kubectl - The Kubernetes CLI

# Install kubectl
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
kubectl version --client

# View cluster information
kubectl cluster-info

# View nodes
kubectl get nodes

# View pods
kubectl get pods

# View all resources
kubectl get all

# Describe a resource
kubectl describe pod my-pod

# View logs
kubectl logs my-pod

# Execute command in pod
kubectl exec -it my-pod -- /bin/bash

# Apply configuration file
kubectl apply -f deployment.yaml

# Delete resource
kubectl delete pod my-pod

✅ Key Takeaways:

  • Kubernetes is a cluster-based platform
  • Control Plane = Brain (decides what to do)
  • Worker Nodes = Execution (does the work)
  • Pods = Smallest unit (wraps containers)
  • kubectl = CLI to interact with cluster

📚 Additional Kubernetes Concepts (Advanced)

These topics require deeper study:

  • Deployments: Manage pod replicas and rolling updates
  • Services: Expose pods to network traffic
  • ConfigMaps & Secrets: Manage configuration and sensitive data
  • Namespaces: Logical cluster partitions
  • Ingress: HTTP/HTTPS routing to services
  • Persistent Volumes: Storage management
  • StatefulSets: For stateful applications
  • DaemonSets: Run pod on every node

💡 Learning Path: Kubernetes is a vast topic. Focus on basics first: Pods, Deployments, Services. Then gradually learn advanced concepts.

AWS ECS (Elastic Container Service)

✅ What is AWS ECS?

Amazon ECS is AWS's native container orchestration service that manages Docker containers without needing Kubernetes.

⚠️ AWS's Solution: "Kubernetes is complex. Use ECS - simpler AWS-native container management!"

🎯 Why Use ECS?

  • ✅ Simpler than Kubernetes: No complex cluster management
  • ✅ Deep AWS Integration: Native support for ALB, IAM, CloudWatch, Secrets Manager
  • ✅ Serverless Option: Use Fargate - no EC2 management
  • ✅ Cost-Effective: No ECS service charge - only pay for resources
  • ✅ Managed Service: AWS handles control plane

Figure 5: AWS ECS Architecture - Cluster, Tasks, and Services

🏗️ ECS Core Components

1. Cluster

A logical grouping of compute capacity (EC2 or Fargate).

Property Description
Purpose Groups resources for container deployment
Types EC2 (you manage servers) or Fargate (serverless)
Isolation Resources in one cluster don't affect another

2. Task Definition

A blueprint for your containers (like a Dockerfile but for ECS).

Defines:

  • Docker image to use
  • CPU and memory requirements
  • Port mappings
  • Environment variables
  • IAM role for task
  • Logging configuration

3. Task

A running instance of a Task Definition (like a Kubernetes Pod).

4. Service

Ensures desired number of tasks are always running.

  • ✅ Maintains task count (like Kubernetes ReplicaSet)
  • ✅ Replaces failed tasks automatically
  • ✅ Integrates with load balancers
  • ✅ Supports rolling updates

🚀 ECS Launch Types

Launch Type You Manage AWS Manages Use Case Cost Model
EC2 EC2 instances, scaling, patching Container orchestration More control, cost optimization Pay for EC2 instances
Fargate Nothing (serverless) Infrastructure + orchestration Simplicity, no ops overhead Pay per task (CPU/RAM/time)

⚙️ Creating ECS Cluster and Service

Method 1: AWS CLI

# Create ECS cluster
aws ecs create-cluster \
    --cluster-name my-app-cluster \
    --region us-east-1

# Register task definition
aws ecs register-task-definition \
    --cli-input-json file://task-definition.json

# Create service
aws ecs create-service \
    --cluster my-app-cluster \
    --service-name my-web-service \
    --task-definition my-app:1 \
    --desired-count 3 \
    --launch-type FARGATE \
    --network-configuration "awsvpcConfiguration={subnets=[subnet-12345],securityGroups=[sg-12345],assignPublicIp=ENABLED}"

# Update service (change task count)
aws ecs update-service \
    --cluster my-app-cluster \
    --service my-web-service \
    --desired-count 5

# List services
aws ecs list-services --cluster my-app-cluster

# Delete service
aws ecs delete-service \
    --cluster my-app-cluster \
    --service my-web-service \
    --force

Method 2: AWS Console

  1. Go to Amazon ECS
  2. Click Create Cluster
  3. Select Networking only (Fargate)
  4. Create Task Definition
  5. Create Service with desired task count
  6. Configure Load Balancer and Auto Scaling

✅ Best Practices:

  • Use Fargate for serverless simplicity
  • Use EC2 launch type for cost optimization at scale
  • Enable Container Insights for monitoring
  • Use Application Load Balancer for production
  • Enable Service Auto Scaling

AWS EKS (Elastic Kubernetes Service)

✅ What is AWS EKS?

Amazon EKS is AWS's managed Kubernetes service.

🎯 Why Use EKS?

  • ✅ Standard Kubernetes: No vendor lock-in
  • ✅ AWS-Managed Control Plane: HA across 3 AZs
  • ✅ AWS Integration: IAM, VPC, ALB, EBS
  • ✅ Hybrid/Multi-Cloud: Run same workloads anywhere

⚙️ Creating EKS Cluster

Method 1: CLI (eksctl)

# Create EKS cluster
eksctl create cluster \
  --name my-eks-cluster \
  --region us-east-1 \
  --nodegroup-name standard-workers \
  --node-type t3.medium \
  --nodes 3 \
  --managed

# Deploy application
kubectl create deployment nginx --image=nginx
kubectl expose deployment nginx --port=80 --type=LoadBalancer

# Delete cluster
eksctl delete cluster --name my-eks-cluster

Method 2: AWS Console

  1. Go to Amazon EKS
  2. Click Add Cluster → Create
  3. Configure cluster and networking
  4. Add Managed Node Group
  5. Configure kubectl: aws eks update-kubeconfig --name my-eks-cluster

💰 EKS Pricing

  • Control Plane: $0.10/hour (~$73/month per cluster)
  • Worker Nodes: Standard EC2 pricing
  • Fargate Pods: Per vCPU and GB-hour

🆚 ECS vs EKS Decision Guide

Scenario Choose ECS Choose EKS
New to containers ✅ ❌
AWS-only workloads ✅ ⚠️
Kubernetes experience ❌ ✅
Multi-cloud/hybrid ❌ ✅
Cost sensitivity ✅ ⚠️

Key Takeaways & Summary

🎯 Container Fundamentals

  • ✅ Containers are lightweight, isolated execution environments
  • ✅ Docker is the most popular containerization platform
  • ✅ Docker consists of CLI and Daemon
  • ✅ Images are read-only templates; Containers are running instances

🗄️ Image Storage

  • ✅ Docker Hub - Public registry
  • ✅ AWS ECR - Private registry for production

🔧 Docker Advanced Features

  • ✅ Docker Compose - Manage multi-container apps
  • ✅ Networks - Bridge, Host, Overlay
  • ✅ Volumes - Data persistence

☸️ Kubernetes

  • ✅ Cluster-based - Control Plane + Worker Nodes
  • ✅ Pod - Smallest unit
  • ✅ Industry standard for container orchestration

☁️ AWS Container Services

  • ✅ ECS - AWS-native, simpler
  • ✅ EKS - Managed Kubernetes
