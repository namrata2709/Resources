1. Introduction to Containerization

🏠 Real-Life Analogy: Shipping Containers

Imagine you're running a global shipping company. You need to transport goods - furniture, electronics, food, clothes - across the world.

💡 The Problem (Before Containers):

  • Each product needs different packaging
  • Different vehicles for different items
  • Complex loading/unloading processes
  • No standard way to transport goods
  • High chance of damage during transit

✅ The Solution (Shipping Containers):

  • Standard-sized metal boxes (20ft, 40ft)
  • Any cargo fits inside the container
  • Same container works on ships, trains, trucks
  • Easy to stack, load, and transport
  • Contents protected and isolated

Docker containers work the same way! They package your application and all its dependencies into a standard unit that can run anywhere - your laptop, a server, or the cloud.

📖 Technical Explanation

Containerization is a lightweight form of virtualization that packages an application with its dependencies (libraries, configuration files, runtime) into an isolated unit called a container.

Key Differences from Virtual Machines:

Aspect Virtual Machine (EC2) Container (Docker)
What it contains Full OS + Application Only Application + Dependencies
Size Gigabytes (5-20 GB) Megabytes (50-500 MB)
Startup Time Minutes Seconds
Resource Usage High (dedicated CPU, RAM) Low (shares host kernel)
Isolation Level Complete (hypervisor-level) Process-level (OS kernel)
Portability Limited (hardware dependencies) High (runs anywhere)

🔐 Docker User Permissions - Critical Concept

The Security Design: By default, only root user can run Docker commands. This is by design for security.

❌ Common Issue: Non-root users get "permission denied" when trying to run Docker commands.

Why is Docker root-only by default?

  1. Docker daemon runs with root privileges
  2. Containers can access host resources
  3. Security risk if any user can run containers
  4. Prevents unauthorized container deployments

The Solution: Docker Group

When Docker is installed, it creates a special group called docker. Any user added to this group can run Docker commands without sudo.

⚙️ How to Do This in Practice

Option 1: Using Command Line (CLI)

# Step 1: Install Docker (Ubuntu)
sudo apt update
sudo apt install -y docker.io

# Step 2: Start Docker service
sudo systemctl start docker
sudo systemctl enable docker

# Step 3: Verify Docker daemon is running
sudo systemctl status docker

# Step 4: Check current user
whoami
# Output: ubuntu (or ec2-user, centos, etc.)

# Step 5: Add user to docker group
sudo usermod -aG docker $USER

# Explanation:
# -aG: Add user to supplementary Group
# docker: Name of the group
# $USER: Current logged-in user

# Step 6: Apply changes (choose ONE method)
# Method A: Run newgrp (temporary, current session only)
newgrp docker

# Method B: Logout and login again (permanent)
exit
# Then reconnect via SSH

# Step 7: Verify user is in docker group
groups
# Should see: ubuntu docker

# Step 8: Test Docker without sudo
docker --version
docker ps
docker run hello-world

✅ Success Indicators:

  • docker ps works without sudo
  • No "permission denied" errors
  • groups command shows "docker" in output

3. Docker Architecture Deep Dive

🎂 Real-Life Analogy: Baking a Cake

Let's understand Docker's three-step process using a familiar activity: baking a cake!

Baking Step Docker Equivalent What It Contains Can You Eat It?
Recipe Card Dockerfile Step-by-step instructions ❌ No (it's just paper)
Cake Mold/Template Docker Image Ready-to-use template (read-only) ❌ No (it's a template)
Actual Cake Docker Container Running instance you can use ✅ Yes! (it's the real thing)

💡 The Flow:

  1. Write recipe (Dockerfile) with ingredients and steps
  2. Create mold/template (Image) using the recipe
  3. Bake actual cakes (Containers) using the mold
  4. One mold can create many cakes!

📖 Step 1: Dockerfile - The Blueprint

What is a Dockerfile?

A Dockerfile is a text file containing instructions to build a Docker image. It's like a recipe that tells Docker:

  • What base operating system to use
  • What software to install
  • What files to copy
  • What commands to run
  • What ports to expose
  • What command to execute when container starts

Dockerfile Instructions (Common Directives)

Instruction Purpose Example When to Use
FROM Specify base image FROM ubuntu:22.04 Always first line (required)
WORKDIR Set working directory WORKDIR /app When you need a specific folder
COPY Copy files from host to container COPY app.py /app/ Add your application code
ADD Copy + extract archives ADD archive.tar.gz /app/ When you need to extract files
RUN Execute commands during build RUN apt-get install -y python3 Install packages, setup environment
ENV Set environment variables ENV DB_HOST=localhost Configure application settings
EXPOSE Document port usage EXPOSE 8000 Inform which port app listens on
CMD Default command to run CMD ["python3", "app.py"] What runs when container starts
ENTRYPOINT Fixed command (not overridable) ENTRYPOINT ["nginx"] When command should never change

Example Dockerfile - Python Web Application

# Dockerfile for a Python Flask application

# 1. Start with Python base image (Alpine is lightweight)
FROM python:3.9-slim

# 2. Set working directory inside container
WORKDIR /app

# 3. Copy requirements file first (for layer caching)
COPY requirements.txt .

# 4. Install Python dependencies
RUN pip install --no-cache-dir -r requirements.txt

# 5. Copy application code
COPY . .

# 6. Set environment variables
ENV FLASK_APP=app.py
ENV FLASK_ENV=production

# 7. Expose port (documentation only)
EXPOSE 5000

# 8. Health check (optional but recommended)
HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost:5000/health || exit 1

# 9. Run application when container starts
CMD ["python3", "app.py"]

✅ Best Practices for Dockerfile:

  • Use specific base image versions (not :latest)
  • Use lightweight base images (-slim, -alpine)
  • Copy requirements file before source code (better caching)
  • Combine multiple RUN commands with && to reduce layers
  • Remove unnecessary files in same RUN layer
  • Use .dockerignore file (like .gitignore)

A Docker Image is a read-only template created from a Dockerfile. Think of it as a frozen snapshot of your application and all its dependencies.

Tagged Identified by name:tag format Like a product: brand-name:version (nike-shoes:2024)
Reusable One image can create many containers One mold makes many cakes

docker build --no-cache -t myapp:v1.0 .

docker image ls

# Remove all unused images
docker image prune -a

# Tag existing image with new name
docker tag myapp:v1.0 myapp:latest

📦 Step 3: Docker Container - The Running Instance

What is a Docker Container?

A Docker Container is a running instance of an image. It's the actual application running in an isolated environment.

Aspect Image Container
State Static (like a program file) Dynamic (like a running program)
Modifiable? ❌ No (read-only) ✅ Yes (writable layer on top)
Storage Stored on disk Running in memory
How many? 1 image Multiple containers from same image

⚙️ How to Run Docker Containers

Option 1: Using Command Line (CLI)

# Basic run command
docker run nginx

# Run in detached mode (background)
docker run -d nginx

# Run with custom name
docker run -d --name my-nginx nginx

# Run with port mapping (host:container)
docker run -d -p 8080:80 --name web nginx

# Run with environment variables
docker run -d \
  -e DB_HOST=mysql \
  -e DB_PORT=3306 \
  --name backend myapp:v1.0

# Run with volume mount
docker run -d \
  -v /host/data:/container/data \
  --name app myapp:v1.0

# Run with resource limits
docker run -d \
  --memory="512m" \
  --cpus="1.0" \
  --name limited-app myapp:v1.0

# Run interactively with terminal
docker run -it ubuntu bash

# Run and remove after exit
docker run --rm ubuntu echo "Hello Docker"

# List running containers
docker ps

# List all containers (including stopped)
docker ps -a

# View container logs
docker logs my-nginx

# Follow logs in real-time
docker logs -f my-nginx

# View last 100 lines
docker logs --tail 100 my-nginx

# Execute command inside running container
docker exec my-nginx ls /usr/share/nginx/html

# Get interactive shell inside container
docker exec -it my-nginx bash

# Stop container (graceful shutdown)
docker stop my-nginx

# Kill container (immediate shutdown)
docker kill my-nginx

# Start stopped container
docker start my-nginx

# Restart container
docker restart my-nginx

# Remove container
docker rm my-nginx

# Force remove running container
docker rm -f my-nginx

# View container resource usage
docker stats my-nginx

# View detailed container info
docker inspect my-nginx

Scenario 2: Worst Case - Image Size Nightmare

Scenario Type Context Action Outcome Key Lesson
Bloated Docker Image Worst Case Used full Ubuntu base, included development tools Image was 2.5 GB, took 10 minutes to deploy each container ❌ Couldn't scale fast, high storage costs Always use minimal base images and multi-stage builds

The Problem Dockerfile:

# BAD EXAMPLE - Don't do this!
FROM ubuntu:latest  # ❌ Full OS (500+ MB)

# Install everything including unnecessary tools
RUN apt-get update && apt-get install -y \
    python3 \
    python3-pip \
    gcc \
    g++ \
    make \
    git \
    vim \
    curl \
    wget \
    build-essential  # ❌ Not needed in production

COPY . /app
RUN pip3 install -r requirements.txt
# ❌ Didn't clean up apt cache
# Result: 2.5 GB image!

The Fixed Dockerfile:

# GOOD EXAMPLE - Optimized
FROM python:3.9-slim  # ✅ Minimal base (150 MB)

WORKDIR /app
COPY requirements.txt .

# Install only runtime dependencies
RUN pip install --no-cache-dir -r requirements.txt \
    && rm -rf /root/.cache  # ✅ Clean up cache

COPY . .

CMD ["python3", "app.py"]
# Result: 350 MB image (7x smaller!)

✅ Image Optimization Techniques:

  • Use -slim or -alpine base images
  • Multi-stage builds (build → production)
  • Clean up package manager caches
  • Combine RUN commands with &&
  • Use .dockerignore to exclude unnecessary files

Scenario 3: Edge Case - Container Data Loss

Scenario Type Context Action Outcome Key Lesson
Database Container Restart Edge Case Database container crashed, all data lost No volumes were configured for persistent storage ❌ Lost 1 week of customer data Always use volumes for stateful applications

What Happened:

  1. Team deployed MySQL container without volumes
  2. Database ran for 1 week, storing customer orders
  3. Server had a power failure
  4. Container stopped and restarted
  5. All data was gone (containers are ephemeral!)
  6. No backups configured
  7. Result: $500K in lost order data, customer complaints

❌ Critical Mistake: Running databases without volumes = guaranteed data loss!

The Correct Way:

# Always use volumes for databases
docker run -d \
  --name mysql-db \
  -v mysql-data:/var/lib/mysql \  # ✅ Persistent volume
  -e MYSQL_ROOT_PASSWORD=secret \
  mysql:8.0

# Data persists even if container is removed!
docker stop mysql-db
docker rm mysql-db

# Restart with same volume - data is still there!
docker run -d \
  --name mysql-db-new \
  -v mysql-data:/var/lib/mysql \  # ✅ Same volume
  -e MYSQL_ROOT_PASSWORD=secret \
  mysql:8.0

  • ✅ One image can create multiple containers
  • ✅ Always optimize image size (use minimal base images)
  • ✅ Use volumes for persistent data (databases, files)
  • ✅ Tag images properly for version control

🌐 Docker Hub - The Public Registry

What is Docker Hub?

Docker Hub is the default public registry for Docker images. It's like GitHub for Docker images - you can find, share, and download container images.

Docker Hub Features:

  • ✅ Official Images: Verified by Docker (nginx, ubuntu, mysql)
  • ✅ Public Repositories: Free unlimited public repos
  • ✅ Private Repositories: Limited free private repos (paid for more)
  • ✅ Automated Builds: Auto-build from GitHub/Bitbucket
  • ✅ Webhooks: Trigger actions on push
  • ✅ Team Management: Collaborate with team members

⚙️ Working with Docker Hub

# Step 1: Create Docker Hub account at hub.docker.com
# (Do this once via web browser)

# Enter username and password when prompted

docker login -u myusername -p mypassword

# Step 3: Pull images from Docker Hub

📖 What is Docker Compose?

Docker Compose is a tool for defining and running multi-container Docker applications using a single YAML file.

Why Do We Need Docker Compose?

Problem Without Compose:

# To run a 3-tier app manually:
# 1. Start database
docker run -d --name db -e MYSQL_ROOT_PASSWORD=secret mysql:8.0

# 2. Start backend (depends on db)
docker run -d --name backend --link db -e DB_HOST=db myapp-backend:v1

# 3. Start frontend (depends on backend)
docker run -d --name frontend --link backend -p 80:80 myapp-frontend:v1

# Problems:
# ❌ 3 separate commands
# ❌ Manual dependency management
# ❌ Hard to remember all flags
# ❌ Difficult to scale
# ❌ No easy way to stop all at once

Solution With Compose:

# Just one command!
docker-compose up -d

# Everything starts in correct order with dependencies
# ✅ Database starts first
# ✅ Backend waits for database
# ✅ Frontend starts after backend ready

📄 Docker Compose File Structure

Basic docker-compose.yml Example:

version: '3.8'  # Compose file format version

services:
  # Service 1: Database
  database:
    image: postgres:14
    container_name: my-postgres
    environment:
      POSTGRES_DB: myapp_db
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret123
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - backend-network
    restart: unless-stopped

  # Service 2: Backend API
  backend:
    build:
      context: ./backend
      dockerfile: Dockerfile
    container_name: my-backend
    ports:
      - "5000:5000"
    environment:
      DB_HOST: database
      DB_PORT: 5432
      DB_NAME: myapp_db
    depends_on:
      - database
    networks:
      - backend-network
      - frontend-network
    restart: unless-stopped

  # Service 3: Frontend
  frontend:
    build:
      context: ./frontend
      dockerfile: Dockerfile
    container_name: my-frontend
    ports:
      - "80:80"
    environment:
      API_URL: http://backend:5000
    depends_on:
      - backend
    networks:
      - frontend-network
    restart: unless-stopped

# Define networks
networks:
  frontend-network:
  backend-network:

# Define volumes
volumes:
  db-data:

services:
  frontend:
    image: myapp-frontend:v1
    ports:
      - "80:80"
    # ❌ No depends_on!

  backend:
    image: myapp-backend:v1
    ports:
      - "5000:5000"
    # ❌ No depends_on!

  database:
    image: postgres:14
    # Database might start last!

# What happened:
# 1. All services started simultaneously
# 2. Frontend tried to connect to backend (not ready yet)
# 3. Backend tried to connect to database (not ready yet)
# 4. All services crashed with connection errors
# 5. Had to restart multiple times manually

The Fix:

# GOOD: Proper dependency chain
version: '3.8'

services:
  frontend:
    image: myapp-frontend:v1
    ports:
      - "80:80"
    depends_on:
      - backend  # ✅ Wait for backend

  backend:
    image: myapp-backend:v1
    ports:
      - "5000:5000"
    depends_on:
      - database  # ✅ Wait for database
      - redis     # ✅ Wait for redis

  database:
    image: postgres:14
    # Starts first!

  redis:
    image: redis:7-alpine
    # Starts second

# Now startup order is correct:
# 1. database
# 2. redis
# 3. backend (waits for both)
# 4. frontend (waits for backend)

📖 Docker Network Types Explained

1. Bridge Network (Default)

When you start Docker, it creates a default bridge network. All containers connect to this by default.

Aspect Details
Purpose Containers on same host communicate with each other
How it works Creates virtual bridge (docker0) on host, containers get IP from private subnet
IP Range Typically 172.17.0.0/16
Internet Access Via NAT through host
Container-to-Container Via container name (on custom bridge) or IP
Best For Most applications on single host

2. Host Network

Container shares the host's network namespace directly - no isolation.

Aspect Details
Purpose Maximum network performance
How it works Container uses host IP address directly
Port Mapping ❌ Not needed (container binds to host ports directly)
Security ⚠️ Lower (no network isolation)
Best For High-performance apps, monitoring tools

3. Overlay Network

Enables containers on different Docker hosts to communicate securely.

Aspect Details
Purpose Multi-host container communication
Requires Docker Swarm or Kubernetes
Encryption ✅ Optional built-in encryption
Best For Distributed applications, microservices across servers

🎬 Networking Scenario 2: Worst Case - Default Bridge Confusion

Scenario Type Context Action Outcome Key Lesson
Container Communication Failure Worst Case Two containers can't find each other by name Used default bridge network (doesn't support DNS) ❌ Had to hardcode IP addresses, broke on restart Always use custom bridge networks for name resolution

The Problem:

# Started containers on default bridge
docker run -d --name backend myapi:v1
docker run -d --name frontend nginx

# From frontend container:
curl http://backend:5000
# Error: Could not resolve host: backend

# Why? Default bridge doesn't support DNS!
# Had to use IP address:
curl http://172.17.0.3:5000
# ❌ But IP changes every time container restarts!

The Solution:

# Create custom bridge network
docker network create myapp-net

# Start containers on custom network
docker run -d --name backend --network myapp-net myapi:v1
docker run -d --name frontend --network myapp-net nginx

# Now DNS works!
curl http://backend:5000
# ✅ Success! Name resolution works on custom networks

✅ Rule of Thumb: NEVER use default bridge for production. Always create custom networks!

Without Volumes:

📖 What is Kubernetes?

Kubernetes (K8s) is an open-source container orchestration platform that automates deployment, scaling, and management of containerized applications.

💡 Name Origin: "Kubernetes" is Greek for "helmsman" (ship captain). K + 8 letters + s = K8s

🏗️ Kubernetes Architecture: Cluster-Based

Kubernetes runs as a cluster with two main parts:

Component Role Analogy Quantity
Control Plane Brain of cluster Orchestra conductor 1-3 (HA)
Worker Nodes Execution units Orchestra musicians 1-1000s

🧠 Control Plane Components

1. API Server (kube-apiserver)

The front door of Kubernetes - all communication flows through here.

  • ✅ Single entry point for all cluster operations
  • ✅ Validates and processes API requests
  • ✅ Authenticates users (RBAC - Role-Based Access Control)
  • ✅ Communicates with etcd to persist cluster state

2. etcd

The cluster's memory/database - stores all cluster state.

  • ✅ Distributed key-value store
  • ✅ Source of truth for cluster state
  • ✅ Stores: pods, services, secrets, config maps, namespaces
  • ✅ Highly available (typically 3-5 replicas)

⚠️ Critical: If etcd is lost, the entire cluster state is lost! Always backup etcd in production!

3. Scheduler (kube-scheduler)

The decision engine - decides which pods run on which nodes.

  • ✅ Watches for newly created pods with no assigned node
  • ✅ Evaluates available resources (CPU, memory, disk)
  • ✅ Considers constraints (node selectors, affinity rules)
  • ✅ Selects best node for each pod

4. Controller Manager (kube-controller-manager)

A collection of controllers that maintain desired state.

  • ✅ Node Controller: Monitors node health
  • ✅ Replication Controller: Maintains correct number of pod replicas
  • ✅ Endpoints Controller: Populates service endpoints
  • ✅ Service Account Controller: Creates default accounts for new namespaces

5. Cloud Controller Manager (optional)

Integrates with cloud provider APIs (AWS, Azure, GCP).

  • ✅ Manages cloud-specific resources
  • ✅ Creates load balancers
  • ✅ Provisions storage volumes
  • ✅ Manages node lifecycle in cloud

⚙️ Worker Node Components

1. Kubelet

The node agent - runs on every worker node.

  • ✅ Communicates with Control Plane
  • ✅ Ensures containers are running in pods
  • ✅ Reports node and pod status
  • ✅ Executes pod lifecycle operations

2. Container Runtime

The software that runs containers.

Runtime Status Notes
containerd ✅ Recommended Industry standard, lightweight
CRI-O ✅ Good Kubernetes-native
Docker ⚠️ Deprecated Being phased out (use containerd instead)

3. kube-proxy

The network proxy - manages network rules on nodes.

  • ✅ Maintains network rules
  • ✅ Enables pod-to-pod communication
  • ✅ Implements Service abstraction
  • ✅ Load balances traffic to pods

📦 Pod - The Smallest Unit

A Pod is the smallest deployable unit in Kubernetes.

Property Description
What it contains 1 or more containers (usually 1)
Shared network All containers share same IP address

📖 What is AWS ECS?

Amazon ECS is AWS's native container orchestration service. AWS says: "You don't need Kubernetes - use our simpler solution!"

ECS Core Components:

  1. Cluster: Logical grouping of compute capacity
  2. Task Definition: Blueprint of your containers (like Dockerfile)
  3. Task: Running instance of Task Definition
  4. Service: Keeps desired number of tasks running

🚀 ECS Launch Types

⚙️ Creating ECS Cluster and Service

Option 1: AWS CLI


                        # Step 1: Create ECS cluster
aws ecs create-cluster \
    --cluster-name my-app-cluster \
    --region us-east-1

# Step 2: Register task definition
# First create task-definition.json:
cat > task-definition.json <<EOF
{
  "family": "my-web-app",
  "networkMode": "awsvpc",
  "requiresCompatibilities": ["FARGATE"],
  "cpu": "256",
  "memory": "512",
  "containerDefinitions": [
    {
      "name": "web-container",
      "image": "nginx:alpine",
      "portMappings": [
        {
          "containerPort": 80,
          "protocol": "tcp"
        }
      ],
      "essential": true
    }
  ]
}
EOF

aws ecs register-task-definition \
    --cli-input-json file://task-definition.json

# Step 3: Create service
aws ecs create-service \
    --cluster my-app-cluster \
    --service-name my-web-service \
    --task-definition my-web-app:1 \
    --desired-count 3 \
    --launch-type FARGATE \
    --network-configuration "awsvpcConfiguration={subnets=[subnet-abc123],securityGroups=[sg-abc123],assignPublicIp=ENABLED}"

# Step 4: View services
aws ecs list-services --cluster my-app-cluster

# Step 5: Update service (change task count)
aws ecs update-service \
    --cluster my-app-cluster \
    --service my-web-service \
    --desired-count 5

# Step 6: Delete service
aws ecs delete-service \
    --cluster my-app-cluster \
    --service my-web-service \
    --force

🟢 Basic Level (1-2 Years Experience)

Q1: What is Docker and why is it used?
Answer: Docker is a containerization platform that packages applications with their dependencies into isolated containers. It's used because containers are lightweight, portable, start quickly, and solve the "works on my machine" problem by ensuring consistent environments across development, testing, and production.
Q2: What's the difference between a Docker image and a container?
Answer: An image is a read-only template (like a blueprint) built from a Dockerfile. A container is a running instance of that image (like an actual house built from the blueprint). One image can create multiple containers.
Q3: What is a Dockerfile?
Answer: A Dockerfile is a text file containing step-by-step instructions to build a Docker image. It includes directives like FROM (base image), COPY (add files), RUN (execute commands), and CMD (what runs when container starts).
Q4: How do you build and run a Docker container?
Answer: 
# Build image from Dockerfile
docker build -t myapp:v1 .

# Run container from image
docker run -d -p 8080:80 --name mycontainer myapp:v1
Q5: What is Docker Compose used for?
Answer: Docker Compose is a tool for defining and running multi-container applications using a YAML file (docker-compose.yml). Instead of running multiple docker run commands, you define all services in one file and start everything with docker-compose up.
Q6: Why do we need Docker volumes?
Answer: Containers are ephemeral - when deleted, all data inside is lost. Volumes provide persistent storage that survives container restarts/deletions. They're essential for databases, file uploads, logs, and any data that must be preserved.
Q7: What's the difference between Docker Hub and AWS ECR?
Answer: Docker Hub is a public registry (anyone can access public images), free for public repos, has rate limits. AWS ECR is a private registry, integrated with AWS IAM, includes vulnerability scanning, no rate limits, better for production workloads.
Q8: What is container orchestration and why is it needed?
Answer: Container orchestration is automated management of containers at scale. It's needed because Docker alone can't handle production requirements like auto-scaling, load balancing, self-healing, rolling updates, and service discovery. Tools like Kubernetes and ECS provide these features.

🟠 Intermediate Level (2-4 Years Experience)

Q9: Explain the difference between CMD and ENTRYPOINT in Dockerfile.
Answer: CMD provides default arguments that can be overridden when running the container. ENTRYPOINT sets a fixed command that always runs - arguments passed to docker run are appended to ENTRYPOINT. Use ENTRYPOINT when the container should always run a specific executable, CMD for defaults that users might want to override.
Q10: You deployed a database container without volumes and it crashed. What happens to the data?
Answer (STAR Method):
  • Situation: Database container storing customer data crashed
  • Task: Need to recover data and prevent future loss
  • Action: Data is permanently lost as containers are ephemeral. Implemented volumes for data persistence going forward
  • Result: Learned critical lesson - always use volumes for stateful applications. Now all databases use named volumes.
Q11: How do you optimize Docker image size?
Answer:
  • Use minimal base images (-slim, -alpine variants)
  • Multi-stage builds (separate build and runtime stages)
  • Combine RUN commands to reduce layers
  • Remove package manager caches (apt-get clean, pip --no-cache-dir)
  • Use .dockerignore to exclude unnecessary files
  • Don't install dev dependencies in production images
Q12: Explain Docker networking types and when to use each.
Answer:
  • Bridge (default): For standalone containers on same host. Use custom bridge for DNS resolution.
  • Host: Container uses host's network directly. Use for high-performance apps, monitoring tools.
  • Overlay: Multi-host communication (requires Swarm/K8s). Use for distributed microservices.
  • None: No networking. Use for security isolation, batch jobs.
Q13: What is Kubernetes and why is it industry standard?
Answer: Kubernetes is an open-source container orchestration platform that automates deployment, scaling, and management of containerized apps. It's industry standard (88% market share) because it's cloud-agnostic, feature-rich, extensible, and backed by major tech companies. Provides auto-scaling, self-healing, rolling updates, service discovery - everything needed for production.
Q14: Explain Kubernetes architecture: Control Plane vs Worker Nodes.
Answer: K8s is cluster-based with two parts:
  • Control Plane (Brain): Makes decisions. Contains API Server (entry point), etcd (cluster state), Scheduler (assigns work), Controller Manager (maintains desired state)
  • Worker Nodes (Muscle): Run containers. Contains Kubelet (node agent), kube-proxy (networking), Container Runtime (runs containers)
Users interact with Control Plane via kubectl, which schedules work on Worker Nodes.
Q15: What is a Pod in Kubernetes?
Answer: A Pod is the smallest deployable unit in K8s - a wrapper around one or more containers that share network and storage. Containers in a pod share same IP address and can communicate via localhost. Pods are ephemeral - when they die, they're replaced (not repaired). In production, never manage pods directly - use Deployments instead.

🔴 Advanced Level (4+ Years Experience)

Q16: Describe a time when you had to scale an application under heavy load.
Answer (STAR Method):
  • Situation: E-commerce site expecting 10x traffic during Black Friday sale
  • Task: Ensure zero downtime and handle 500K concurrent users
  • Action: Deployed app on Kubernetes with Horizontal Pod Autoscaler. Configured scaling from 10 to 100 pods based on 70% CPU threshold. Set up monitoring and alerting.
  • Result: System auto-scaled to 85 pods during peak, handled all traffic with 99.99% uptime, $50M in sales. After sale, automatically scaled back down, saving costs.
Q17: How would you implement zero-downtime deployment in Kubernetes?
Answer: Use Rolling Update strategy in Deployment: 
spec:
  replicas: 10
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 2        # 2 extra pods during update
      maxUnavailable: 1  # Max 1 pod down at a time
Also configure readiness/liveness probes to ensure new pods are healthy before old ones are terminated. Use kubectl rollout status to monitor. If issues arise, rollback with kubectl rollout undo.
Q18: When would you choose ECS over EKS?
Answer: Choose ECS when:
  • AWS-only workloads (no multi-cloud needs)
  • Team is new to containers (simpler learning curve)
  • Want deep AWS integration (IAM, CloudWatch, ALB)
  • Cost-sensitive (no $73/month control plane fee)
  • Need quick setup with less operational overhead
Choose EKS when:
  • Need Kubernetes portability (multi-cloud/hybrid)
  • Team has K8s expertise
  • Want standard K8s ecosystem (Helm, Istio, operators)
  • Need to avoid vendor lock-in
Q19: How do you secure Docker containers in production?
Answer:
  • Image Security: Scan for vulnerabilities (ECR scanning, Trivy), use official images, keep updated
  • Runtime Security: Run as non-root user, use read-only filesystems, limit capabilities
  • Network Security: Use private networks, implement network policies, encrypt in transit
  • Secrets Management: Never hardcode secrets, use AWS Secrets Manager or K8s Secrets
  • Access Control: Use IAM roles (not access keys), implement RBAC, least privilege principle
  • Monitoring: Enable logging (CloudWatch, ELK), detect anomalies, audit access
Q20: Explain how you troubleshoot a failing container in production.
Answer (Systematic Approach):
  1. Check container status: docker ps or kubectl get pods
  2. View logs: docker logs container-name or kubectl logs pod-name
  3. Check events: kubectl describe pod shows why pod crashed
  4. Inspect configuration: Verify environment variables, volumes, ports
  5. Check resources: Is container OOM (out of memory)? CPU throttled?
  6. Network issues: Can container reach dependencies? DNS resolving?
  7. Execute into container: docker exec -it container bash to debug inside
  8. Review health checks: Are readiness/liveness probes configured correctly?

Exercise 1: Deploy Multi-Tier Application with Docker Compose

Objective:

Deploy a complete web application with frontend, backend, and database using Docker Compose.

Prerequisites:

  • Docker and Docker Compose installed
  • Basic understanding of YAML syntax
  • AWS EC2 instance or local machine with 4GB RAM

Step-by-Step Procedure:

  1. Create project directory: 
    mkdir webapp-project && cd webapp-project
  2. Create docker-compose.yml: 
    version: '3.8'

services:
  database:
    image: postgres:14
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret123
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - backend

  backend:
    image: node:16-alpine
    working_dir: /app
    volumes:
      - ./backend:/app
    command: sh -c "npm install && npm start"
    environment:
      DB_HOST: database
      DB_PORT: 5432
    depends_on:
      - database
    networks:
      - backend
      - frontend

  frontend:
    image: nginx:alpine
    ports:
      - "80:80"
    volumes:
      - ./frontend:/usr/share/nginx/html
    depends_on:
      - backend
    networks:
      - frontend

networks:
  frontend:
  backend:

volumes:
  db-data:
  3. Create simple HTML file (frontend/index.html): 
    <h1>My Web Application</h1>
<p>Frontend running!</p>
  4. Start all services: 
    docker-compose up -d
  5. Verify services are running: 
    docker-compose ps
  6. Access application: 
    curl http://localhost

Expected Output:

Creating network "webapp-project_frontend" with the default driver
Creating network "webapp-project_backend" with the default driver
Creating volume "webapp-project_db-data" with default driver
Creating webapp-project_database_1 ... done
Creating webapp-project_backend_1  ... done
Creating webapp-project_frontend_1 ... done

Error Cause Fix

Cannot connect to database Backend started before DB ready Add healthcheck to database service
