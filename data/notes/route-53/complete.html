📖 Introduction

Imagine you want to visit a friend's house. You know their name — "Priya's place" — but your GPS needs the actual street address to navigate. That's exactly the problem DNS solves on the internet. Your computer knows you want google.com, but to actually connect, it needs the underlying IP address like 142.250.182.46.

Figure 1: Route 53 as the world's phone book — translating human-friendly names to machine-readable IP addresses

Amazon Route 53 is AWS's highly available and scalable Domain Name System (DNS) web service and domain registrar. The name "Route 53" comes from a famous US highway — Route 66 — and port 53, the standard port DNS operates on.

💡 This session covers: How DNS works globally, what Route 53 is, hosted zones, DNS record types, and the full architecture connecting Route 53 → CloudFront → S3 for a static website.

By the end of these notes, you will understand how typing saiguda.info in a browser eventually loads a website stored quietly in a private S3 bucket — and why every piece of that puzzle matters.

🔍 What is DNS?

The internet runs on IP addresses — numbers like 192.0.2.1. But humans remember names, not numbers. DNS, the Domain Name System, is the internet's phone book: it translates human-readable domain names into machine-readable IP addresses.

The DNS Resolution Journey

When you type google.com in your browser, a behind-the-scenes conversation happens across multiple servers. Let's trace it step by step.

Figure 2: The full DNS resolution journey — from your browser to the authoritative answer

📸 From Session: DNS Record Request Sequence — the four-step journey your query takes before getting an IP address back

Here is what each player does:

1. Recursive Resolver (Caching Resolver)
The recursive resolver is managed by your Internet Service Provider (ISP) and acts as the middleman — it caches DNS results so the full lookup chain isn't repeated every time. Think of it like your browser's history, but for DNS answers. If it has the answer cached, it returns it immediately. If not, it starts the full lookup.

2. Root DNS Servers
There are 13 sets of root DNS servers globally, and they sit at the very top of the DNS hierarchy. They don't know the IP of google.com, but they know who does. They redirect the recursive resolver to the correct TLD server. For example: "You want .com? Go ask the .com TLD servers."

3. TLD (Top Level Domain) Nameservers
TLD servers manage specific domain extensions like .com, .org, .net, and .in. The .com TLD is managed by a company called VeriSign; .org is managed by PIR. The TLD server checks if the domain name exists in its list. If yes, it redirects the resolver to the authoritative nameserver that has the actual records.

4. Authoritative Nameserver (The Final Answer)
The authoritative nameserver is the final and most important server in the DNS chain — it holds the actual DNS records including the real IP address of the domain. Companies like GoDaddy, Hostinger, Namecheap, Cloudflare, and AWS Route 53 all act as authoritative nameservers. This is where the actual answer lives.

📸 From Session: How DNS Works — three phases: The Query, IP Resolution, and Connection

⚡ Key flow: Browser → Recursive Resolver (check cache) → Root DNS → TLD Server → Authoritative Nameserver → IP address returned → Website loads

TTL (Time to Live)

TTL (Time to Live) is the duration, in seconds, for which a DNS record is cached by the recursive resolver before it must be refreshed from the authoritative nameserver.

For example, if TTL is set to 600 seconds (10 minutes), the recursive resolver will serve the cached answer for up to 10 minutes. After that, it revisits the authoritative nameserver to get a fresh answer. A common TTL for Route 53 records is 3600 seconds (1 hour).

💡 Why TTL matters in practice: If you update your DNS records (e.g., point your domain to a new server), existing cached records will keep pointing to the old server until the TTL expires. Lower TTL = faster propagation but more DNS queries. Higher TTL = slower propagation but less load on DNS servers.

🛣️ What is Amazon Route 53?

Route 53 is AWS's answer to the question: "How do I give my application a friendly domain name?" It is much more than just a DNS service — it combines three powerful capabilities.

Figure 3: Route 53's three core capabilities — registration, DNS resolution, and health checking

Route 53 provides three core services: domain registration, DNS routing, and health checking.

Domain Registration: You can purchase and manage domain names directly in Route 53, just like GoDaddy or Namecheap. Route 53 supports hundreds of TLDs including .com, .info, .shop, and more.

DNS Service (Authoritative Nameserver): Route 53 acts as the authoritative nameserver for your domains, serving DNS queries with very low latency. It routes end-user requests to the appropriate AWS services or external endpoints.

Health Checking: Route 53 can monitor the health of your application endpoints and automatically route traffic away from unhealthy resources. This makes it a key component in disaster recovery and high availability architectures.

💡 Why is it called Route 53? The name is inspired by US Route 66 (famous American highway) combined with port 53 — the TCP/UDP port that DNS operates on. It's a playful but memorable name!

⚡ Route 53 is the only AWS service with a 100% availability SLA, making it one of the most reliable services in AWS.

🏷️ Domain Registration

📸 From Session: Domain Registration explained — buying the name vs. hosting the website are two separate things

Think of a domain name like a plot number in a housing society. You register (buy) the plot number to claim ownership. But the plot number is just an address identifier — what you build on it (your house/website) lives elsewhere.

When you buy a domain from a registrar like GoDaddy, Namecheap, or AWS Route 53, you are only registering ownership of the domain name — you are NOT hosting your website there.

When you register a domain, the registrar updates the TLD server (e.g., the .com TLD server) to say "this domain exists, and here is which authoritative nameserver holds its records." This is what allows the DNS resolution chain to eventually find your domain.

Registrar vs. DNS Provider

These can be the same company or different companies — and this distinction is very important in practice.

Figure 4: You can register a domain at GoDaddy but use Route 53 as the authoritative nameserver — they are separate roles

In the practical demo, the instructor purchased the domain saiguda.info on GoDaddy, but used Route 53 as the authoritative nameserver. This is a very common real-world setup. To make it work, the Route 53 hosted zone name servers had to be copied into GoDaddy's "Name Server Settings" — effectively telling GoDaddy: "Don't use your own nameservers. Forward all DNS queries for this domain to these Route 53 servers instead."

✅ Best practice: If you are using AWS services for your application, use Route 53 as both your registrar and DNS provider. This simplifies management and enables AWS-native features like alias records and latency-based routing.

How Domain Purchase Works

  1. Go to Route 53 Console → Registered Domains → Register Domain
  2. Search for your desired domain name (e.g., myapp.com)
  3. If available, add to cart and complete purchase (prices vary: .com ≈ $12–15/year, .info ≈ $12/year)
  4. Route 53 automatically creates a hosted zone for the domain
  5. The TLD server (.com, .info, etc.) is updated to point to Route 53's nameservers

💡 Domain pricing tip: Popular TLDs like .com cost around ₹1,000–1,500/year. Alternative TLDs like .info or .shop are often cheaper. You can use promo codes (e.g., GOINDIA on GoDaddy) for discounts.

📦 Hosted Zones (The DNS Container)

📸 From Session: Hosted Zone = your domain's DNS database, with 4 authoritative name servers generated automatically

Registering a domain is just step one. After that, you need somewhere to store the actual DNS records — the mappings between your domain name and your server's IP address (or AWS resource endpoint). That's what a hosted zone is for.

A hosted zone is a container in Route 53 that holds all the DNS records for a specific domain. Think of it as a DNS database for your domain.

Figure 5: A hosted zone is your DNS database — it holds all record types for your domain

Public vs. Private Hosted Zones

Route 53 supports two types of hosted zones: public hosted zones (accessible over the internet) and private hosted zones (accessible only within an AWS VPC).

Public Hosted Zone: Used for internet-facing applications. Anyone on the internet can resolve DNS names in a public hosted zone. This is what you use for a website like saiguda.info.

Private Hosted Zone: Used for internal AWS resources. DNS names are only resolvable within the VPCs you associate with the hosted zone. For example, internal microservices communicating via db.internal.myapp.com.

Name Servers in a Hosted Zone

When you create a hosted zone in Route 53, AWS automatically assigns 4 authoritative name servers to that hosted zone. These four name servers are what the rest of the internet uses to reach your DNS records.

This is the critical step that links your domain registrar to Route 53:

  1. Create hosted zone in Route 53 for saiguda.info
  2. Route 53 provides 4 name servers (e.g., ns-123.awsdns-45.com, etc.)
  3. Go to GoDaddy → Domain Settings → Name Servers
  4. Replace GoDaddy's default name servers with the 4 Route 53 name servers
  5. Now all DNS queries for saiguda.info flow through Route 53

⚡ Call Forwarding Analogy: Think of it like call forwarding on your phone. The TLD server calls GoDaddy (because that's where the domain is registered). GoDaddy sees the Route 53 name servers and says "I don't have the details, please call these 4 numbers instead" — forwarding the request to Route 53, where the actual DNS records live.

💡 Important: If you register the domain directly in Route 53 (instead of GoDaddy), Route 53 automatically sets itself as the authoritative nameserver — you don't need to manually update name server settings.

📝 DNS Record Types

📸 From Session: DNS Record Types — the actual instructions that tell the internet how to handle your domain

DNS records are the individual entries inside your hosted zone. DNS records are the actual instructions that tell the internet how to route traffic for your domain. Each record has a type that defines what kind of mapping it performs.

Figure 6: All major DNS record types and their purposes

A Record (IPv4)

An A record maps a domain name directly to an IPv4 address. This is the most common record type. Example: saiguda.info → 54.23.11.45.

AAAA Record (IPv6)

An AAAA record maps a domain name to an IPv6 address. As the internet transitions to IPv6, AAAA records become increasingly important. Example: saiguda.info → 2001:0db8::1.

CNAME Record (Alias to Another Domain)

A CNAME record maps one domain name to another domain name — it is an alias. A classic real-world example: typing fb.com redirects to facebook.com — this is a CNAME. The CNAME points to facebook.com, and separately, facebook.com has an A record pointing to an IP address.

❌ Important restriction: A CNAME record cannot be created at the zone apex (the root domain itself, e.g., saiguda.info). It can only be used for subdomains like www.saiguda.info. Use Alias records (Route 53-specific) to map root domains to AWS resources.

MX Record (Mail)

An MX record defines the mail servers responsible for accepting email for a domain. Example: To use Gmail for your custom domain email ([email protected]), you add Google's MX records to your hosted zone.

TXT Record (Text/Verification)

A TXT record stores arbitrary text data, commonly used for domain ownership verification and email security (SPF, DKIM, DMARC). When you verify ownership of a domain on Google Search Console or AWS Certificate Manager, they ask you to add a TXT record.

NS Record (Name Servers)

An NS record specifies which name servers are authoritative for a domain. Every hosted zone in Route 53 automatically gets 4 NS records — these are what you copy into your registrar's settings.

SOA Record (Start of Authority)

The SOA (Start of Authority) record contains administrative information about a domain including the primary nameserver, the email of the domain admin, and various timing parameters like TTL defaults. Route 53 creates this automatically for every hosted zone.

Alias Records (AWS-Specific Feature)

This is one of Route 53's most powerful features. When your website is hosted on an AWS service (CloudFront, ALB, S3 website endpoint), the endpoint is a domain name — not an IP address. You can't put a domain name in an A record.

An Alias record is a Route 53-specific extension that maps a domain name to an AWS resource endpoint (CloudFront distribution, ALB, S3, API Gateway, etc.) without requiring an IP address.

✅ Alias vs. CNAME: Both map a name to another name, but Alias records are free (no charge per query), can be used at the zone apex (saiguda.info), and automatically update when the underlying AWS resource's IP changes. Always prefer Alias records over CNAMEs when pointing to AWS resources.

🔑 Authoritative Nameserver Role

📸 From Session: Authoritative Nameserver — the final answer provider in the DNS chain

The authoritative nameserver is the last stop in the DNS resolution journey — and the most important one. Everything else (recursive resolver, root servers, TLD servers) is just infrastructure to find this final answer.

The authoritative nameserver's job is to store DNS records and provide the correct final answer when the internet asks for your domain's IP address.

Its four key responsibilities:

✔ Hold the real DNS records: All A, AAAA, CNAME, MX, TXT records live here. This is the single source of truth for your domain.

✔ Provide the final answer: When a recursive resolver asks "What is the IP of saiguda.info?", the authoritative server responds with the correct answer stored in its records.

✔ Maintain DNS updates: Any change you make to a DNS record propagates through the authoritative servers to the rest of the internet (subject to TTL caching).

✔ Connect domain to website hosting: Without a properly configured authoritative nameserver, your domain cannot reach your website — the DNS chain has no final answer to return.

🏗️ Full Architecture: S3 + CloudFront + Route 53

The most common use case taught in this session combines four AWS services into a production-ready static website architecture. Let's understand why each piece is needed and how they connect.

📸 From Session: High-level architecture — 4 AWS services working together for a production static website

📸 From Session: Detailed architecture with protocols — HTTPS to Route 53, HTTPS to CloudFront, HTTP to S3

Why Each Service is Needed

Figure 7: Why each service is needed — the justification for each layer in the architecture

S3 (Storage): Stores your static website files (HTML, CSS, JavaScript, images). It's cheap, durable, and supports static website hosting. However, the bucket is kept private — public access is blocked.

CloudFront (CDN): CloudFront sits in front of S3, provides HTTPS support, caches content at edge locations globally for low latency, and enables access to the private S3 bucket via Origin Access Control (OAC).

ACM (AWS Certificate Manager): Provides free SSL/TLS certificates for your custom domain, enabling HTTPS. Certificates for use with CloudFront must be created in us-east-1 (N. Virginia) region.

Route 53 (DNS): Maps your custom domain name (saiguda.info) to your CloudFront distribution endpoint. Without this, users would need to remember a long CloudFront URL like d1234abcd.cloudfront.net.

Origin Access Control (OAC)

OAC (Origin Access Control) is a CloudFront security feature that allows CloudFront to access a private S3 bucket without making the bucket public — only CloudFront can read from the bucket.

When you enable OAC on your CloudFront distribution, it automatically updates the S3 bucket policy to allow only that specific CloudFront distribution to access it. The S3 bucket remains private to everyone else on the internet.

Step-by-Step Setup

Figure 8: Complete 6-step setup process for the static website architecture

  1. Create S3 Bucket — Enable static website hosting, keep public access blocked (the bucket stays private).

  2. Create CloudFront Distribution — Set origin to your S3 bucket endpoint (bucket endpoint, NOT website endpoint). Enable OAC. CloudFront auto-updates the S3 bucket policy to allow only itself to read from it.

  3. Get ACM Certificate — Request a public certificate for your domain in us-east-1. Validate via DNS (add the provided TXT record to your hosted zone).

  4. Attach Certificate to CloudFront — In CloudFront distribution settings, configure the custom domain name (CNAME) and attach the ACM certificate to enable HTTPS.

  5. Create Route 53 Hosted Zone and Record — Create a public hosted zone for your domain. Add an A record with Alias pointing to your CloudFront distribution endpoint.

  6. Update Name Servers at Registrar — Copy the 4 Route 53 name servers from your hosted zone into GoDaddy's (or your registrar's) name server settings.

⚡ Traffic flow after setup: User types saiguda.info → DNS resolves via Route 53 → Returns CloudFront endpoint → CloudFront checks nearest edge location cache → If not cached, fetches from S3 origin → Response served back to user with HTTPS

💡 TTL and caching: Once the website is served, the recursive resolver caches the Route 53 DNS record per the TTL setting (e.g., 600s). For the next 10 minutes, subsequent lookups skip the DNS chain entirely and serve from cache. CloudFront also has its own separate caching layer at edge locations.

Routing to a Load Balancer (ALB)

The same pattern applies when your website runs on EC2 instances behind a load balancer. The Application Load Balancer (ALB) itself has a DNS endpoint (like my-alb-1234.us-east-1.elb.amazonaws.com). Customers can't remember that. Solution: Create an A record with Alias in Route 53 pointing to the ALB endpoint. Route 53 then routes traffic to the ALB, which distributes it across your EC2 instances.

🔄 Route 53 Routing Policies

Route 53 is not just a simple DNS lookup service — it can make intelligent routing decisions based on various conditions. A routing policy determines how Route 53 responds to DNS queries for a given hosted zone record.

Figure 9: Route 53 routing policies overview — from simple to intelligent traffic management

Simple Routing

The default policy. One record maps to one endpoint (or multiple IPs returned in random order). No health checks. Use for single-resource setups.

Weighted Routing

Weighted routing distributes traffic across multiple resources based on assigned weights — used for A/B testing or gradually shifting traffic to a new deployment. Example: Send 90% of traffic to v1 of your app and 10% to v2 while you test the new version.

Latency-Based Routing

Latency-based routing routes user traffic to the AWS region that provides the lowest latency for that user. Example: A user in Mumbai is routed to ap-south-1; a user in London is routed to eu-west-1. Improves user experience significantly for global applications.

Failover Routing

Failover routing automatically routes traffic to a secondary (standby) resource when the primary resource fails its health check. This is the core of active-passive disaster recovery in AWS. Route 53 health checks monitor the primary endpoint and switch traffic automatically.

Geolocation Routing

Geolocation routing routes traffic based on the geographic location of the user, not latency. Example: Users from India see an Indian version of the site (in.myapp.com); users from the US see the US version. Used for content compliance (e.g., GDPR) and localization.

Multi-Value Answer Routing

Multi-value routing returns up to 8 healthy IP addresses in response to a DNS query, functioning like a simple load balancer at the DNS level. Unlike Simple routing, Multi-value routing performs health checks on each IP and only returns healthy ones.

💡 Exam tip: Multi-value routing is NOT a substitute for a proper load balancer (ALB/NLB). The client randomly picks one of the returned IPs — there's no guarantee of even distribution or session stickiness.

Geoproximity Routing (Traffic Flow)

Routes traffic based on geographic location of users and resources, with the ability to apply a bias value to shift more or less traffic to a specific region. Requires Route 53 Traffic Flow (additional cost). Used in complex global traffic management scenarios.

📝 Overall Summary

  • DNS (Domain Name System): The internet's phone book — translates human-readable domain names (google.com) into machine-readable IP addresses.
  • DNS Resolution Chain: Browser → Recursive Resolver (ISP, caches results) → Root DNS Servers (13 sets globally) → TLD Nameservers (.com, .org, .in) → Authoritative Nameserver (final answer).
  • TTL: Time To Live — how long a DNS answer is cached by resolvers. Lower TTL = faster propagation; higher TTL = fewer DNS queries. Route 53 default is often 300s or 3600s.
  • Route 53: AWS's DNS and domain registration service. Acts as an authoritative nameserver. Name comes from Route 66 (highway) + port 53 (DNS port). Only AWS service with 100% availability SLA.
  • Domain Registration: Buying a domain name (e.g., from GoDaddy or Route 53). Only registers ownership — does NOT host the website. The registrar updates the TLD server with the authoritative nameserver details.
  • Hosted Zone: A container in Route 53 that stores all DNS records for a domain. Public hosted zones are internet-accessible; private hosted zones are VPC-only. AWS generates 4 name servers per hosted zone.
  • Name Server Update: When you buy a domain at GoDaddy but use Route 53 for DNS, you must copy Route 53's 4 name servers into GoDaddy's settings — this is the "call forwarding" step that links the two.
  • DNS Record Types: A (domain → IPv4), AAAA (domain → IPv6), CNAME (domain → domain), MX (mail servers), TXT (verification/security), NS (nameservers), SOA (administrative metadata).
  • Alias Records: Route 53-specific record type that maps domain names to AWS resource endpoints (CloudFront, ALB, S3). Free, works at zone apex, auto-updates when resource IPs change.
  • Static Website Architecture: S3 (private bucket) → OAC → CloudFront (CDN + HTTPS) ← ACM (SSL cert) ← Route 53 (DNS) ← User. Route 53 maps custom domain to CloudFront endpoint via A record with Alias.
  • Routing Policies: Simple, Weighted (A/B testing), Latency-based, Failover (DR), Geolocation (content by country), Geoproximity, Multi-value (DNS-level load balancing with health checks).

Project 1: DNS Playground — See DNS Working Live

🎯 Objective: Create a hosted zone, add DNS records, and use command-line tools to watch those records resolve in real time. No EC2, no S3 — pure DNS.

⏱️ Time: 20–30 min

💰 Cost: $0.50/month for the hosted zone (delete after practice)

🏆 Outcome: You see DNS working — not just read about it. This is the most important mindset shift.

  1. Create a Hosted Zone — Go to Route 53 → Hosted Zones → Create Hosted Zone. Enter any domain you own (or use a subdomain of one you own). Choose Public Hosted Zone. Click Create.

    📸 Screenshot: Hosted zone created — note the 4 NS records and 1 SOA auto-generated by Route 53

  2. Add an A Record → any public IP — Inside the hosted zone, click Create Record. Keep type as A. In the Value field, enter any real public IP address (e.g., 1.1.1.1 — Cloudflare's public DNS). Set TTL to 60 seconds. Click Create Records.

    📸 Screenshot: A record pointing to 1.1.1.1 with TTL 60 — low TTL so changes propagate fast during practice

  3. Add a TXT Record → verification text — Create another record. Set type to TXT. In the Value field, enter any text in double quotes: "hello-this-is-my-dns-record". TTL = 60. Click Create.

    📸 Screenshot: TXT record with custom verification text — same mechanism used by ACM and Google Search Console

  4. Verify with nslookup (Windows) or dig (Mac/Linux) — Open your terminal. Run these commands and observe the output:

    # Check the A recordnslookup yourdomain.com# Check the TXT recordnslookup -type=TXT yourdomain.com# On Mac/Linux use dig instead:dig yourdomain.com Adig yourdomain.com TXT

    📸 Screenshot: Terminal output — your records resolving live. If you see your IP and text, DNS is working.

  5. Change the A record IP — watch TTL in action — Edit your A record, change the IP to 8.8.8.8 (Google's DNS). Wait 60 seconds (your TTL). Run nslookup again. You should now see 8.8.8.8. This is TTL propagation — you just experienced it, not just read about it.

✅ Cleanup: Delete the hosted zone when done. Route 53 charges $0.50/month per hosted zone.

Project 2: Your Domain → Live EC2 Website

🎯 Objective: Point a real domain name to an EC2 instance running a web server. First real "my domain is live on a server" moment.

⏱️ Time: 30–40 min

💰 Cost: EC2 t2.micro free tier. Hosted zone $0.50/month.

🏆 Outcome: You understand the full path: domain → DNS → server. Foundation of everything else.

  1. Launch an EC2 instance — Use Amazon Linux 2, t2.micro (free tier). In User Data, paste this startup script to auto-install a web server:

    #!/bin/bashyum update -yyum install -y httpdecho "<h1>Hello from my domain!</h1>" > /var/www/html/index.htmlsystemctl start httpdsystemctl enable httpd

    Make sure the Security Group allows HTTP (port 80) inbound from 0.0.0.0/0. Note the Public IPv4 address after launch.

    📸 Screenshot: EC2 running with public IPv4 visible — copy this IP for the DNS record

  2. Verify EC2 web server is working — Paste the EC2 Public IP directly into your browser: http://<your-ec2-public-ip>. You should see "Hello from my domain!" This confirms the web server is running before you touch DNS.

  3. Create Route 53 Hosted Zone for your domain — Go to Route 53 → Hosted Zones → Create Hosted Zone. Enter your domain. If you already have a hosted zone from Project 1, you can reuse it — just add a new A record.

  4. Create an A record pointing to EC2 IP — Inside the hosted zone, create an A record. Leave the Name field blank (this sets the root domain). Set Value to your EC2 Public IPv4 address. TTL = 300. Click Create.

    📸 Screenshot: A record with EC2 public IP — leave Name blank to set the root domain

  5. Update nameservers at your registrar — If your domain is at GoDaddy, copy Route 53's 4 NS values into GoDaddy's Name Server settings. If your domain is registered in Route 53 itself, this step is automatic.

  6. Test DNS resolution — Run nslookup yourdomain.com. Once it returns your EC2 IP, open http://yourdomain.com in a browser. You should see your page.

    📸 Screenshot: Your domain loading the EC2 web page — this is the "it works" moment

❌ Common issue: If the page loads with the IP but not the domain, DNS hasn't propagated yet. Wait 5–15 minutes and try again. Use nslookup yourdomain.com 8.8.8.8 to query Google's resolver directly.

✅ Cleanup: Stop or terminate the EC2 instance when done to avoid charges. Delete the A record if you want to reuse the hosted zone for the next project.

Project 4: A/B Testing with Weighted Routing — Two Websites, One Domain

🎯 Objective: Send 80% of visitors to website v1 and 20% to website v2 using the same domain. This is how companies roll out new features safely.

⏱️ Time: 30–40 min

💰 Cost: Two S3 buckets (free). One hosted zone ($0.50/month).

🏆 Outcome: You understand traffic control — the skill behind canary deployments and blue-green releases.

⚡ Real-world use case: A company wants to test a redesigned homepage with 20% of users before full rollout. Weighted routing lets them do this at the DNS level — no code changes required.

  1. Create two S3 static websites — Create two S3 buckets. Enable static website hosting on both. In bucket 1, upload an index.html that says "Version 1 — Blue" with a blue background. In bucket 2, upload an index.html that says "Version 2 — Green" with a green background. Make both buckets public (for this lab, to keep it simple — in production you'd use CloudFront).

    📸 Screenshot: Two S3 buckets — v1 (blue) and v2 (green) — each with their own website endpoint URL

  2. Get the website endpoint URLs — For each bucket, go to Properties → Static Website Hosting → copy the Bucket Website Endpoint (format: bucket-name.s3-website-region.amazonaws.com). You'll need these for the CNAME records.

  3. Create two weighted CNAME records in Route 53 — In your hosted zone, create Record 1: Type CNAME, name test.yourdomain.com, value = S3 website endpoint of v1, TTL 60, Routing Policy: Weighted, Weight = 80, Record ID = v1-blue. Then create Record 2: same name, value = S3 endpoint of v2, Weight = 20, Record ID = v2-green.

    📸 Screenshot: Two weighted CNAME records for the same subdomain — 80/20 split visible in the records list

  4. Test by refreshing repeatedly — Open http://test.yourdomain.com in your browser. Refresh 10 times. You should land on the blue version roughly 8 times and the green version roughly 2 times. Due to DNS caching (TTL=60), you may need to wait a minute between tests or use different browsers/devices.

    📸 Screenshot: v1 (blue) loading — approximately 80% of requests should land here

  5. Simulate a full cutover — Change the v1 record weight to 0 and v2 weight to 100. Wait for TTL (60s). Now all traffic goes to v2. This is how you complete a gradual rollout.

💡 Why not 50/50? In real deployments you start with a small percentage (5–10%) on the new version. If error rates stay normal, you gradually increase. If something goes wrong, you set the new version weight to 0 — instant rollback.

✅ Cleanup: Delete both S3 buckets and their contents. Delete the weighted CNAME records from the hosted zone.

Project 5: Failover Architecture — Automatic DNS Recovery

🎯 Objective: Configure a primary and secondary endpoint. When the primary fails its health check, Route 53 automatically switches all traffic to the secondary. No manual action needed.

⏱️ Time: 40–50 min

💰 Cost: Two S3 buckets (free). Health checks: $0.50/month per health check. Hosted zone: $0.50/month.

🏆 Outcome: You understand high availability. This is what separates a hobby project from a production system.

⚡ Real-world use case: A company's primary data centre goes down. Route 53 health checks detect the failure within 30 seconds and redirect all DNS traffic to a backup region — automatically, with no on-call engineer needed.

  1. Create two S3 static websites — Primary: bucket with index.html saying "Primary Site — us-east-1". Secondary: bucket saying "Secondary Site — Backup". Enable static website hosting on both. Make both buckets public.

  2. Create a Route 53 Health Check for the primary — Go to Route 53 → Health Checks → Create Health Check. Name it primary-health-check. Set monitor type to HTTP. For the endpoint, enter the S3 website endpoint of your primary bucket (without http://). Path: /. Port: 80. Click Create.

    📸 Screenshot: Health check showing "Healthy" status — Route 53 is polling your primary endpoint every 30 seconds

  3. Create two failover CNAME records — In your hosted zone, create Record 1: Type CNAME, name failover.yourdomain.com, value = primary S3 endpoint, TTL 60, Routing Policy = Failover, Failover record type = Primary, associate with primary-health-check, Record ID = primary. Create Record 2: same name, value = secondary S3 endpoint, Failover record type = Secondary, no health check needed, Record ID = secondary.

    📸 Screenshot: Primary and Secondary failover records — Route 53 serves Primary as long as health check passes

  4. Test normal behaviour — Visit http://failover.yourdomain.com. You should see the Primary Site page. Run nslookup failover.yourdomain.com — it returns the primary S3 endpoint.

  5. Simulate primary failure — In S3, go to your primary bucket. Under Permissions → Bucket Policy — add a policy that denies all public reads. This simulates the primary going down. Wait 30–60 seconds (Route 53 health check interval). The health check status should change to Unhealthy.

    📸 Screenshot: Health check turns Unhealthy — Route 53 will now stop serving the Primary record

  6. Verify automatic failover — Refresh http://failover.yourdomain.com. You should now see the Secondary Site — Backup page. Run nslookup again — it now returns the secondary endpoint. Route 53 switched automatically.

    📸 Screenshot: Secondary site loading — failover triggered automatically by Route 53 health check

  7. Restore and verify recovery — Remove the deny bucket policy from the primary S3 bucket. The health check returns to Healthy within 30–60 seconds. Refresh the page again — you should be back on the Primary site.

✅ Cleanup: Delete both health checks ($0.50/month each). Delete failover records. Delete both S3 buckets.

Project 6: Multi-Subdomain Architecture — app, api, admin on One Domain

🎯 Objective: Route three subdomains — app, api, and admin — to three completely different AWS services using one hosted zone.

⏱️ Time: 35–45 min

💰 Cost: One hosted zone ($0.50/month). Services used are free tier.

🏆 Outcome: You understand domain architecture — how real companies structure their DNS so different parts of their product live on different services.

⚡ Real-world example: A SaaS company might have app.company.com serving the React frontend from S3+CloudFront, api.company.com going to an ALB in front of EC2 instances, and admin.company.com pointing to a separate internal tool. All managed from one Route 53 hosted zone.

  1. Prepare three endpoints — For this lab, use three different S3 static websites to simulate different services. Create three buckets: app-yourname, api-yourname, admin-yourname. Upload a different index.html to each (e.g., "App Frontend", "API Service", "Admin Panel"). Enable static website hosting on all three. Note each bucket's website endpoint URL.

    📸 Screenshot: Three S3 buckets representing three different services under one domain

  2. Create three CNAME records in one hosted zone — In your Route 53 hosted zone, create: Record 1: Type CNAME, name app, value = app bucket endpoint, TTL 300. Record 2: Type CNAME, name api, value = api bucket endpoint, TTL 300. Record 3: Type CNAME, name admin, value = admin bucket endpoint, TTL 300. All three are in the same hosted zone for yourdomain.com.

    📸 Screenshot: Three CNAME records in one hosted zone — each subdomain routes to a different service

  3. Test all three subdomains — Open each URL in your browser: http://app.yourdomain.com, http://api.yourdomain.com, http://admin.yourdomain.com. Each should load its own page. Run nslookup on each to confirm different endpoints.

    📸 Screenshot: All three subdomains live — one hosted zone, three completely different destinations

  4. Upgrade: Point api subdomain to EC2 — Launch an EC2 with a web server (from Project 2). Change the api CNAME to an A record pointing to the EC2 public IP. Now api.yourdomain.com hits a real server. app and admin still point to S3. This is a real mixed-service DNS setup.

💡 Why not use subfolders? (yourdomain.com/app, yourdomain.com/api) Subdomains are preferred for separate services because: different teams can manage them independently, they can point to completely different infrastructure, they don't share a deployment pipeline, and each can have its own SSL certificate if needed.

✅ Cleanup: Delete the three CNAME/A records. Delete the three S3 buckets and their contents.

Project 7: Domain → Load Balancer → EC2 (Industry Standard Setup)

🎯 Objective: Route a custom domain through Route 53 to an Application Load Balancer that distributes traffic across two EC2 instances. This is the most common production web architecture on AWS.

⏱️ Time: 50–60 min

💰 Cost: ALB: ~$0.008/hour. Two EC2 t2.micro (free tier). Hosted zone: $0.50/month.

🏆 Outcome: You've built the architecture that most AWS job descriptions reference. This is the setup behind thousands of production websites.

  1. Launch two EC2 instances — Use Amazon Linux 2, t2.micro. Use this User Data for instance 1:

    #!/bin/bashyum install -y httpdecho "<h1>Response from Server 1</h1>" > /var/www/html/index.htmlsystemctl start httpd

    For instance 2, change the message to "Response from Server 2". Both need HTTP (port 80) in their Security Group.

    📸 Screenshot: Two EC2 instances running — ideally in different Availability Zones for real HA

  2. Create a Target Group — Go to EC2 → Target Groups → Create. Type: Instances. Protocol: HTTP, Port: 80. Select your VPC. Health check path: /. Register both EC2 instances as targets. Click Create.

    📸 Screenshot: Target group with both EC2 instances registered as Healthy targets

  3. Create an Application Load Balancer — Go to EC2 → Load Balancers → Create → Application Load Balancer. Internet-facing. Select at least 2 AZs. Add a Security Group that allows HTTP (80) inbound. Create a listener on port 80 that forwards to your target group. Note the DNS name of the ALB (e.g., my-alb-1234.us-east-1.elb.amazonaws.com).

    📸 Screenshot: ALB in Active state with DNS name — this is what Route 53 will point to

  4. Test ALB directly — Paste the ALB DNS name into your browser. Refresh several times. You should see "Response from Server 1" and "Response from Server 2" alternating. The ALB is load-balancing correctly.

  5. Create Route 53 A Alias record → ALB — In your hosted zone, create an A record. Enable Alias. Under "Route traffic to", select Alias to Application and Classic Load Balancer. Select your region and choose your ALB from the dropdown. Click Create.

    📸 Screenshot: A Alias record pointing to the ALB — Route 53 resolves the ALB endpoint automatically

  6. Test via your domain — Open http://yourdomain.com. Refresh multiple times. You should see "Server 1" and "Server 2" alternating — load balancing is working through your custom domain.

    📸 Screenshot: Your domain load-balancing between two servers — this is the industry standard setup

⚡ Why Alias record (not CNAME) for ALB? The ALB's DNS name is a domain, not an IP. You could use a CNAME — but Route 53 Alias records are free per query, work at the zone apex, and automatically update when AWS changes the ALB's underlying IPs. Always use Alias for AWS resources.

✅ Cleanup: Delete the ALB (stops per-hour charges). Delete the target group. Terminate both EC2 instances. Delete the A Alias record.

Project 8: Zero-Downtime DNS Migration — Old DNS to Route 53

🎯 Objective: Simulate migrating a domain's DNS management from GoDaddy (or any registrar's built-in DNS) to AWS Route 53, with zero downtime. This is a real-world skill every cloud engineer needs.

⏱️ Time: 40–60 min (plus waiting for TTL to expire)

💰 Cost: One hosted zone ($0.50/month).

🏆 Outcome: You learn zero-downtime migration — one of the most anxiety-inducing tasks in DNS work, done confidently.

⚡ Why this matters: Companies migrating to AWS always need to move their DNS. Doing it wrong = website goes down for hours. This project teaches you the safe, tested approach.

  1. Check your current DNS TTL — Before touching anything, check the current TTL of your domain's A record. Run: nslookup -type=SOA yourdomain.com or dig SOA yourdomain.com. Note the TTL value. This tells you how long you need to wait during the migration.

    # Check current TTLnslookup -type=SOA yourdomain.com# Or with dig:dig SOA yourdomain.com +short

  2. Lower the TTL at the old DNS provider (GoDaddy) — Log into GoDaddy DNS management. Find your A record. Change the TTL from whatever it currently is (often 3600 = 1 hour or 86400 = 24 hours) to 300 seconds (5 minutes). Save. Now wait for the old TTL duration (e.g., 1 hour) to pass. This ensures all resolvers pick up the new low TTL before you switch.

    📸 Screenshot: Lowering TTL in GoDaddy from 3600 to 300 — this is Step 1 of every safe DNS migration

  3. Create the hosted zone in Route 53 with identical records — Create a public hosted zone in Route 53 for your domain. Recreate every DNS record that exists in GoDaddy exactly: same subdomains, same values, same record types. Do NOT miss any records (MX records for email, TXT records for verification, etc.). Set TTL to 300 on all records.

    📸 Screenshot: Route 53 hosted zone with all records recreated — verify every record before the next step

  4. Verify Route 53 is answering correctly (before switching) — Get the 4 NS values from your Route 53 hosted zone. Use nslookup to query Route 53's nameservers directly — before changing GoDaddy's settings:

    # Query Route 53 nameserver directly (replace with your actual NS)nslookup yourdomain.com ns-123.awsdns-45.com# Should return the same IP as GoDaddy currently serves

    If Route 53 returns the correct IP, you're safe to switch. If not, fix the records before proceeding.

  5. Switch nameservers at GoDaddy — Go to GoDaddy → My Domains → Name Servers → Change → Enter the 4 Route 53 NS values. Save. DNS propagation now happens in ~5 minutes (because you lowered TTL to 300 in Step 2).

    📸 Screenshot: GoDaddy nameservers updated to Route 53 — point of no return. Site should stay live.

  6. Verify propagation and raise TTL — Monitor with dig yourdomain.com every 2 minutes. Once all global resolvers are returning the Route 53 NS values, your migration is complete. Now raise the TTL on all Route 53 records back to 3600 (1 hour) for normal operation.

    # Check which NS is answering for your domaindig NS yourdomain.com# Check from multiple global resolvers via:# https://dnschecker.org

❌ Most common mistake: Skipping the TTL lowering step. If you switch nameservers while TTL is 86400 (24 hours), some users will keep hitting GoDaddy's old DNS for up to 24 hours after the switch. Always lower TTL first and wait.

✅ Migration checklist: ☑ Note current TTL ☑ Lower TTL at old provider ☑ Wait for old TTL to expire ☑ Recreate all records in Route 53 ☑ Verify Route 53 answers correctly ☑ Switch nameservers ☑ Monitor propagation ☑ Raise TTL after confirmation

🤔 Reflection Questions

1. Your website is live on an EC2 instance. A user types your domain name. Walk through every DNS server their request touches before reaching your server.

💡 Hint

Start from the user's browser, go through the recursive resolver (ISP), root DNS servers, TLD nameserver, authoritative nameserver (Route 53), and finally back to the user with the IP — which then initiates a TCP connection to EC2.

2. You bought a domain on GoDaddy but want to use Route 53 for DNS management. What exact steps do you need to take to make this work?

💡 Hint

Create a hosted zone in Route 53 → Note the 4 NS records → Go to GoDaddy → Update the Name Server settings to the 4 Route 53 NS values. This is "call forwarding" — GoDaddy redirects all DNS queries to Route 53.

3. Why can't you use a regular CNAME record to point your root domain (e.g., saiguda.info) to a CloudFront distribution? What do you use instead?

💡 Hint

CNAMEs cannot be created at the zone apex (root domain). Route 53 Alias records solve this — they work at the zone apex, are free, and can point to AWS resource endpoints.

4. Why is the S3 bucket kept private when using CloudFront? What mechanism allows CloudFront to access it?

💡 Hint

Keeping the bucket private ensures users can only access the website via CloudFront (with HTTPS, caching, and CDN benefits) — not directly via an insecure S3 URL. OAC (Origin Access Control) allows CloudFront to talk to S3 by updating the bucket policy.

5. You deployed a new version of your website but users are still seeing the old version. Name two possible caching layers that could be responsible and how to fix each.

💡 Hint

1) CloudFront cache — create an invalidation for the changed files. 2) DNS TTL cache — reduce TTL before the update, then update the record; wait for old TTL to expire.

6. A startup wants to run an A/B test where 10% of users see a new homepage design. Which Route 53 routing policy fits this and how would you configure it?

💡 Hint

Weighted routing. Create two A records with the same domain name — one pointing to the old design (weight 90) and one to the new design (weight 10). Route 53 distributes traffic proportionally.
