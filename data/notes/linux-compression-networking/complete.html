🗜️ Linux File Compression

The previous sessions covered Linux fundamentals and file permissions. This section completes the Linux module by covering file compression — a skill you will use regularly when working with log files, deployment packages, backups, and transfers on EC2 instances.

What Is Compression?

Imagine you have 100 files and you need to share them with a colleague. Sending them one by one is slow and wasteful. Compression solves two problems at once:

  1. Archiving — bundling multiple files into a single file
  2. Size reduction — making that single file smaller so it uses less storage and transfers faster

Figure 3: Compression — many files become one smaller file

Archiving means bundling multiple files into a single file. Compression means reducing the total size of that file. These are two separate operations that can be done together or independently.

The Three Main Linux Compression Tools

Linux provides three primary tools for compression. Understanding when to use each is important for both practical work and exams.

Figure 4: Three Linux compression tools and their capabilities

ToolDoes Archiving?Does Compression?File ExtensionWhen to Use
tar✅ Yes❌ No.tarBundle files together without size reduction
gzip❌ No✅ Yes.gzCompress an existing archive (used after tar)
zip✅ Yes✅ Yes.zipBundle and compress in one single step

💡 Analogy: TAR is like putting all your clothes into a suitcase (bundling). GZIP is like vacuum-sealing that suitcase to shrink it (compressing). ZIP is like a smart bag that automatically packs and shrinks everything in one action.

TAR — The Archiving Tool

TAR (Tape Archive) is the standard Linux tool for bundling multiple files and directories into a single archive. It does not reduce file size on its own.

TAR Command Flags Explained

The TAR command uses single-letter flags that you must memorise:

FlagMeaningWhen Used
cCreate a new archiveAlways used when creating
xExtract files from archiveWhen unpacking
tList/view contents of archiveWhen inspecting
vVerbose — show progress in terminalOptional, useful for debugging
fSpecify the filename of the archiveAlways — comes right before the filename

⚡ f must always come last in the flag combination because the filename argument follows immediately after it. For example: tar -cvf myarchive.tar file1.txt — the archive name myarchive.tar comes right after f.

Creating an Archive with TAR

# Create sample files first touch file1.txt file2.txt file3.txt echo "This is file one" > file1.txt echo "This is file two" > file2.txt echo "This is file three" > file3.txt # Create a directory with a file inside mkdir sample echo "This is a file in a directory" > sample/file4.txt # Create a TAR archive bundling all files and the directory tar -cvf myarchive.tar file1.txt file2.txt file3.txt sample/ # Output will show: # file1.txt # file2.txt # file3.txt # sample/ # sample/file4.txt

After running this, ls will show a new file myarchive.tar. This is your archive — all files bundled into one, but not yet compressed.

Extracting Files from a TAR Archive

# Create a new directory and copy the archive into it mkdir extract cp myarchive.tar extract/ cd extract/ # Extract all files from the archive tar -xvf myarchive.tar # ls will now show all extracted files: # file1.txt file2.txt file3.txt sample/

Viewing Archive Contents Without Extracting

# View what's inside an archive (t = list contents) tar -tvf myarchive.tar # Output shows every file and directory inside: # -rw-r--r-- user/group 17 date file1.txt # -rw-r--r-- user/group 17 date file2.txt # ...

Deleting a TAR Archive

# Simply use rm to delete the archive file rm myarchive.tar

✅ Quick memory trick for TAR flags:Create Verbose File = CVF. Extract Verbose File = XVF. Table Verbose File = TVF.

GZIP — Compressing Your Archive

GZIP does not bundle files — it only compresses a single file. The workflow is: first create a TAR archive, then compress that archive with GZIP. The result has a .tar.gz extension.

Compressing with GZIP

# First check the file size before compression ls -lh myarchive.tar # Compress the archive using gzip gzip myarchive.tar # After compression, ls shows: # myarchive.tar.gz (the .tar.gz file — smaller size) # Note: the original .tar file is REPLACED by .tar.gz

GZIP replaces the original file with a compressed version. The original .tar file is deleted and .tar.gz is created in its place.

Decompressing with GUNZIP

# Decompress a .tar.gz file gunzip myarchive.tar.gz # This restores myarchive.tar (the .gz extension is removed) # You can also use: gunzip myarchive.tar.gz # Both work

💡 Note: To compress AND archive in one TAR command, add the z flag: tar -czvf myarchive.tar.gz file1.txt file2.txt sample/. This creates a .tar.gz directly without separate steps. The z flag tells TAR to pipe through GZIP automatically.

ZIP — Archive and Compress in One Step

ZIP is the simplest tool for most use cases — it does both archiving and compression simultaneously. It is also cross-platform compatible (Windows, macOS, Linux all understand ZIP files).

# Install zip if not available (Amazon Linux / CentOS) sudo yum install zip unzip -y # Create a zip archive of files and directories zip -r myfiles.zip file1.txt file2.txt file3.txt sample/ # -r means recursive (include subdirectories) # Extract a zip file unzip myfiles.zip # View zip contents without extracting unzip -l myfiles.zip

Figure 5: TAR+GZIP workflow vs ZIP single-step workflow

Compression in Real AWS Work

On the job, you will use these tools constantly:

  • Application deployment: Package your application code as a .tar.gz and upload to S3 or EC2.
  • Log analysis: AWS stores CloudWatch logs as compressed archives. You will need to decompress them for analysis.
  • Database backups: Compress database dumps before storing to reduce S3 storage costs.
  • Lambda deployment: AWS Lambda requires function code to be uploaded as a ZIP file.

💡 According to AWS documentation, Lambda deployment packages must be a ZIP file. The uncompressed size limit is 250 MB and the compressed (zipped) limit is 50 MB. Knowing compression tools helps you stay within these limits.

🌐 AWS Networking Fundamentals

Networking is where everything in AWS connects. Before you can launch an EC2 instance with the right access controls, before you can connect a database securely, before you can build anything production-worthy — you need to understand networking. The trainer covered the first part of networking in this session using a powerful school analogy.

Figure 6: Three-part networking roadmap for this week

The Six Core Networking Components

In Part 1 of networking, you will learn these six building blocks in order. Every AWS architecture diagram you ever read will contain these components:

  1. VPC — Virtual Private Cloud (your isolated network)
  2. Subnet — Zones within the VPC (public and private)
  3. Internet Gateway — The door between your VPC and the internet
  4. Route Table — The signboard/map that directs network traffic
  5. NACL — Network Access Control List (zone-level security)
  6. Security Group — Resource-level security (per instance/service)

⚡ These six components are always deployed together. You cannot have a working AWS network without all six working in coordination. This is why the trainer teaches them as a connected system, not as isolated services.

Understanding VPC Networking — The School Analogy

The trainer used a brilliant story to explain all six networking components at once. Read this carefully — this is exactly the kind of story that gets recalled perfectly in technical interviews.

Figure 7: The school analogy — all six AWS networking components mapped to a school

The Story: Open School → Structured Campus

Imagine a big city. In this city there is a school that used to be completely open — no boundary wall, no gates, no security. Anyone could walk in. Students, teachers, outsiders, strangers — everyone had access to everything. Labs, classrooms, computers — all open.

At first it felt free and fun. But quickly, problems emerged:

  • Strangers walked into computer labs and stole equipment
  • Outsiders disturbed classrooms during lessons
  • There was no discipline or structure
  • Students did not feel safe

The school management decided: enough. We need structure, safety, and clear rules. They rebuilt the campus with a proper system. Here is what they built — and here is how it maps to AWS networking:

Figure 8: Complete mapping of school analogy to AWS networking components

VPC — Virtual Private Cloud

VPC (Virtual Private Cloud) is a logically isolated section of the AWS cloud where you can launch AWS resources in a virtual network that you define.

In the school analogy: the boundary wall of the school campus is the VPC. Once the boundary is built, the school becomes a private property — isolated from the outside world. No one can enter without permission. The boundary defines that everything inside is yours.

Key VPC facts:

  • Every AWS account gets a default VPC automatically in each region
  • A VPC is always scoped to a single AWS Region — it cannot span multiple regions.
  • You define the IP address range of your VPC using a CIDR block (e.g., 10.0.0.0/16)
  • Inside a VPC you create subnets, launch EC2 instances, RDS databases, and more
  • Resources inside the same VPC can communicate with each other by default

Figure 9: VPC structure — a private network inside AWS

Subnets — Zones Within Your VPC

A Subnet is a range of IP addresses within your VPC. You divide your VPC into subnets to separate resources with different access requirements.

In the school analogy: the school campus (VPC) is divided into Zone 1 (public area) and Zone 2 (private area). Zone 1 has the playground and admin room — accessible to outsiders with permission. Zone 2 has labs and classrooms — only for internal staff and students.

Subnet TypeSchool EquivalentWho Can AccessTypical AWS Resources
Public SubnetZone 1 — playground, admin roomInternet + internalWeb servers, load balancers, NAT gateway
Private SubnetZone 2 — labs, classroomsInternal onlyDatabases, application servers, backend services

Key subnet facts:

  • A subnet is always tied to a single Availability Zone. It cannot span multiple AZs.
  • The subnet's CIDR block must be a subset of the VPC's CIDR block
  • A public subnet has a route to the Internet Gateway; a private subnet does not
  • Best practice: deploy resources across multiple subnets in different AZs for high availability

Internet Gateway — The Main Entrance

An Internet Gateway (IGW) is a VPC component that allows communication between your VPC and the internet. Without it, nothing in your VPC can reach the internet or be reached from the internet.

In the school analogy: the main gate of the school campus is the Internet Gateway. It is the only point through which outsiders (internet traffic) can enter. And it only lets in those with permission (as defined by routing and security rules).

Key Internet Gateway facts:

  • An Internet Gateway is horizontally scaled, redundant, and highly available — you never need to worry about it becoming a bottleneck or single point of failure.
  • One VPC can have only one Internet Gateway attached at a time
  • Attaching an IGW alone is not enough — you also need a route table entry pointing to it
  • It performs NAT (Network Address Translation) for instances with public IP addresses

Route Table — The Signboard/Map

A Route Table contains a set of rules (routes) that determine where network traffic is directed within a VPC.

In the school analogy: the route table is the signboard at each zone. It tells people (network packets) where to go. Zone 1's signboard says: "Outsiders coming from the main gate → come here (Zone 1)." And: "Zone 1 people → can enter Zone 2." Zone 2's signboard says: "Zone 2 people can exit to Zone 1, but the main gate is not directly accessible."

Key Route Table facts:

  • Every subnet must be associated with a route table
  • A route table has a destination (where traffic is going) and a target (what device handles that traffic)
  • The route 0.0.0.0/0 → igw-xxxxxx means "send all internet-bound traffic to the Internet Gateway" — this is what makes a subnet public
  • Private subnets do not have a route to the IGW in their route table

Figure 10: Public vs private subnet route table comparison

NACL — Network Access Control List (Zone-Level Security)

A NACL (Network Access Control List) is a stateless firewall that controls inbound and outbound traffic at the subnet level.

In the school analogy: the NACL is the security guard at the zone entrance (S1). This guard checks everyone entering or leaving the zone — both incoming visitors and outgoing staff. The guard uses a list of rules to decide who is allowed through.

Key NACL facts:

  • NACLs are stateless, meaning return traffic is NOT automatically allowed. You must explicitly create both inbound and outbound rules.
  • Rules are evaluated in number order — lower numbers are evaluated first
  • Each rule can either ALLOW or DENY traffic
  • There is always a default deny rule (*) at the end that blocks anything not explicitly allowed
  • One NACL can be associated with multiple subnets, but one subnet can only have one NACL

Security Group — Department-Level Security

A Security Group acts as a virtual firewall at the resource level (e.g., per EC2 instance). It controls inbound and outbound traffic for individual resources.

In the school analogy: the Security Group is the security guard at each department door (S2). Even after you pass the zone guard (NACL), each individual room has its own guard who checks your permissions specifically for that room.

Key Security Group facts:

  • Security Groups are stateful, meaning if you allow inbound traffic, the return (outbound) traffic is automatically allowed.
  • Security Groups only have ALLOW rules — you cannot create explicit DENY rules
  • By default, all inbound traffic is denied and all outbound traffic is allowed
  • Multiple security groups can be applied to a single resource
  • Security groups can reference other security groups (e.g., allow traffic from any instance in SG-A)

Complete Traffic Flow — Putting It All Together

Let us trace a request from the internet to a web server in your VPC. This is the flow that appears in architecture diagrams and exams:

  1. User browser sends a request to your website (e.g., http://yoursite.com)
  2. Request hits the Internet Gateway (main school gate) — the entry point into the VPC
  3. Route Table (signboard) reads the destination and routes traffic to the public subnet (Zone 1)
  4. Traffic reaches the NACL (zone security guard) — inbound rules are checked. If allowed, traffic enters the subnet.
  5. Traffic reaches the Security Group (room guard) of the EC2 instance — inbound rules checked. If port 80 is allowed, request reaches the EC2 instance.
  6. EC2 sends a response back — Security Group (stateful) automatically allows the return traffic out. NACL (stateless) checks outbound rules before letting traffic leave the subnet.
  7. Response passes through Internet Gateway and reaches the user.

📝 Overall Summary

  • File Compression: Linux uses three main tools — TAR (archive only), GZIP (compress only), and ZIP (archive + compress). TAR is the foundation.
  • TAR flags: c = create, x = extract, t = view, v = verbose, f = filename. f must always precede the filename argument.
  • GZIP workflow: First TAR the files, then GZIP the archive. GZIP replaces the original .tar with a .tar.gz file.
  • ZIP: Does both archiving and compression in one step. Great for cross-platform use. Required for Lambda deployments.
  • VPC: Your isolated private network in AWS. Scoped to one Region. Defined by a CIDR block.
  • Subnet: A slice of your VPC, scoped to one Availability Zone. Can be public (has IGW route) or private (no IGW route).
  • Internet Gateway: The single point of connection between your VPC and the internet. One per VPC. Highly available by default.
  • Route Table: Defines traffic paths within and out of the VPC. The 0.0.0.0/0 → IGW route makes a subnet public.
  • NACL: Subnet-level stateless firewall. Evaluates rules in number order. Has both Allow and Deny rules. Return traffic must be explicitly allowed.
  • Security Group: Instance-level stateful firewall. Allow-only rules. Return traffic is automatically allowed because it is stateful.

Project 2: Automated File Backup Script

🎯 Objective: Write a bash script that automatically compresses a folder with a timestamp and saves it as a dated backup. Then schedule it with cron for daily automation.

⏱️ Time: 30–45 min

💰 Cost: Free tier

  1. Create a sample application folder to back up:

    mkdir ~/myapp echo "App config" > ~/myapp/config.txt echo "Main application file" > ~/myapp/app.py echo "Requirements" > ~/myapp/requirements.txt mkdir ~/backups

  2. Create the backup script:

    nano ~/backup.sh

    Paste this content into the file:

    #!/bin/bash # Backup script - compresses a folder with a timestamp FOLDER_TO_BACKUP="$HOME/myapp" BACKUP_DIR="$HOME/backups" TIMESTAMP=$(date +"%Y-%m-%d_%H-%M-%S") BACKUP_FILE="$BACKUP_DIR/backup_$TIMESTAMP.tar.gz" echo "Starting backup at $TIMESTAMP" tar -czvf "$BACKUP_FILE" "$FOLDER_TO_BACKUP" echo "Backup saved to: $BACKUP_FILE" echo "Size: $(du -sh $BACKUP_FILE | cut -f1)"

    📸 Screenshot: Backup script in nano editor

  3. Save with Ctrl+O, exit with Ctrl+X. Make the script executable and run it:

    chmod +x ~/backup.sh ~/backup.sh

    📸 Screenshot: Script running — observe the timestamp in the output and filename

  4. Verify the backup file was created with the correct timestamp:

    ls -lh ~/backups/

    📸 Screenshot: Backup file with timestamp in filename

  5. Schedule the script to run daily at 2 AM using cron:

    crontab -e

    Add this line at the bottom (press i in vi to insert):

    0 2 * * * /home/ec2-user/backup.sh >> /home/ec2-user/backup.log 2>&1

    📸 Screenshot: Cron job added for daily automated backup

  6. Verify the cron job was saved:

    crontab -l

✅ What you just built: A real-world backup automation pattern. Every DevOps engineer writes scripts like this. The timestamp ensures you never overwrite previous backups.

  1. Create an S3 bucket from the AWS console. Go to S3 → Create bucket.

    nano ~/log-rotate.sh

    Add this content:

    #!/bin/bash LOG_DIR="$HOME/applogs" ARCHIVE_DIR="$HOME/log-archives" BUCKET="your-bucket-name" mkdir -p "$ARCHIVE_DIR" # Compress all log files older than 1 day find "$LOG_DIR" -name "*.log" -mtime +0 | while read logfile; do BASENAME=$(basename "$logfile" .log) ARCHIVE="$ARCHIVE_DIR/${BASENAME}.tar.gz" tar -czvf "$ARCHIVE" "$logfile" rm "$logfile" echo "Archived: $ARCHIVE" # Upload to S3 aws s3 cp "$ARCHIVE" "s3://$BUCKET/logs/" echo "Uploaded: $ARCHIVE to S3" done echo "Log rotation complete."

  3. Make executable and run:

    chmod +x ~/log-rotate.sh ~/log-rotate.sh

    📸 Screenshot: Log rotation script processing each log file

  4. Verify: original logs are gone, compressed archives are in S3:

    ls ~/applogs/ aws s3 ls s3://your-bucket-name/logs/ --recursive

    📸 Screenshot: Logs compressed and moved to S3 — local directory clean

  5. Cleanup:

    aws s3 rm s3://your-bucket-name/logs/ --recursive rm -rf ~/applogs ~/log-archives

✅ What you just built: A log rotation and archiving system. Understanding log management is huge in DevOps — this pattern is used by teams monitoring production applications across all industries.

Project 5: Build Your First Custom VPC

🎯 Objective: Build a complete custom VPC from scratch with a public subnet, Internet Gateway, and route table. Launch an EC2 instance inside it and verify SSH works from the internet.

⏱️ Time: 45–60 min

💰 Cost: Free tier (t2.micro EC2)

❌ Cost alert: EC2 is free on t2.micro within free tier (750 hours/month). Stop (do not terminate) the instance when not in use to preserve your free hours.

  1. Go to VPC → Your VPCs → Create VPC. Set Name: my-custom-vpc, IPv4 CIDR: 10.0.0.0/16.

    📸 Screenshot: VPC creation with CIDR block 10.0.0.0/16

  2. Go to Subnets → Create Subnet. Select your VPC. Set Name: my-public-subnet, AZ: us-east-1a, CIDR: 10.0.1.0/24.

    📸 Screenshot: Public subnet created with /24 CIDR inside the /16 VPC

  3. Go to Internet Gateways → Create Internet Gateway. Name it my-igw. Then Attach it to your VPC.

    📸 Screenshot: Internet Gateway created and attached to VPC — state shows Attached

  4. Go to Route Tables. Find the route table for your VPC. Edit routes → Add route: Destination 0.0.0.0/0, Target: your IGW. Associate this route table with your public subnet.

    📸 Screenshot: Route table with IGW route — this is what makes the subnet public

  5. Launch an EC2 instance (t2.micro) inside your custom VPC and public subnet. Enable auto-assign public IP. Create a security group allowing SSH (port 22) from your IP only.

    📸 Screenshot: EC2 instance configured inside custom VPC and public subnet

  6. SSH into the instance using its public IP and verify connectivity:

    ssh -i your-key.pem ec2-user@YOUR_PUBLIC_IP # Once inside, test internet connectivity: ping google.com -c 3

    📸 Screenshot: SSH works + internet reachable — your custom VPC is fully functional

  7. Cleanup: Terminate EC2 → Delete subnet → Detach and delete IGW → Delete VPC.

✅ What you just built: A custom AWS VPC from scratch — the foundational skill for everything else in AWS architecture. You manually created every component that AWS auto-creates in the default VPC.

Project 6: Public + Private Architecture with Bastion Host

🎯 Objective: Build a two-tier VPC with a public subnet (bastion host) and a private subnet (backend server). SSH into the private EC2 only through the bastion. This is interview gold — every interviewer asks about this.

⏱️ Time: 60–90 min

💰 Cost: Free tier (two t2.micro instances — watch your 750 hour/month limit)

❌ Cost alert: Two EC2 instances running simultaneously use 2× the free tier hours. Stop both instances when done. Terminate when experiment is complete.

  1. Use the VPC from Project 5 or create a new one (10.0.0.0/16). Create a second subnet for private use: Name my-private-subnet, AZ us-east-1b, CIDR 10.0.2.0/24. Do NOT associate it with the IGW route table.

    📸 Screenshot: Two subnets — public and private — in the same VPC

  2. Launch the Bastion Host EC2 in the public subnet. Security Group: allow SSH (port 22) from your IP only.

    📸 Screenshot: Bastion host running in public subnet with public IP assigned

  3. Launch the Backend EC2 in the private subnet. Security Group: allow SSH (port 22) from the Bastion's Security Group only (not from the internet). Do NOT assign a public IP.

    📸 Screenshot: Backend instance in private subnet — no public IP assigned

  4. Copy your private key to the bastion host (needed to SSH from bastion to backend):

    # On your local machine: scp -i your-key.pem your-key.pem ec2-user@BASTION_PUBLIC_IP:~/.ssh/

  5. SSH into the bastion host, then SSH from bastion to the private backend:

    # Step 1: SSH to bastion ssh -i your-key.pem ec2-user@BASTION_PUBLIC_IP # Step 2: From bastion, SSH to backend using its PRIVATE IP chmod 400 ~/.ssh/your-key.pem ssh -i ~/.ssh/your-key.pem ec2-user@BACKEND_PRIVATE_IP

    📸 Screenshot: Two-hop SSH — bastion → private backend. Note the different IP in the prompt.

  6. From the private backend, try to ping the internet — it should fail (no IGW route):

    ping google.com -c 3

    📸 Screenshot: Private instance cannot reach internet — this is correct and expected

  7. Cleanup: Terminate both EC2 instances → Delete both subnets → Detach and delete IGW → Delete VPC.

✅ What you just built: The industry-standard two-tier architecture. Public subnet for the entry point (bastion), private subnet for backend servers. When an interviewer asks "how do you secure backend servers?", this is the answer.

⚡ Break it intentionally: After completing this project, try to SSH directly into the private instance's private IP from your local machine. It will fail — because there is no route from the internet to the private subnet. This is the point. Understanding why it fails teaches you more than when it succeeds.

Project 7: Traffic Control Lab — NACL + Security Groups

🎯 Objective: Deliberately configure NACL and Security Group rules. Break traffic intentionally, then fix it. This is how you truly feel the difference between stateless and stateful.

⏱️ Time: 45–60 min

💰 Cost: Free tier

  1. Use Project 5's VPC or create a fresh one. Launch an EC2 instance in the public subnet with a Security Group allowing port 22 and port 80 from anywhere.

  2. Install a simple web server to test HTTP access:

    sudo yum install httpd -y sudo systemctl start httpd sudo systemctl enable httpd echo "Hello from EC2" | sudo tee /var/www/html/index.html

    📸 Screenshot: Apache web server installed and running

  3. Test access — open a browser and visit http://YOUR_EC2_PUBLIC_IP. Confirm you see "Hello from EC2".

    📸 Screenshot: Website reachable — Security Group is allowing port 80

  4. Now go to VPC → Network ACLs → Find the NACL associated with your subnet. Add an inbound DENY rule with a low rule number to block port 80:

    Rule 50 | Type: HTTP (80) | Protocol: TCP | Port: 80 | Source: 0.0.0.0/0 | Action: DENY

    📸 Screenshot: NACL DENY rule added for port 80

  5. Refresh your browser — the website should now be unreachable. The Security Group still allows port 80, but the NACL blocked it first.

    📸 Screenshot: Website blocked — NACL denies before Security Group can allow

  6. Fix it: Delete the DENY rule from the NACL (or change it to ALLOW). Verify the website is accessible again.

    📸 Screenshot: DENY rule removed — traffic restored

  7. Now experiment with Security Groups: Remove the port 80 rule from the Security Group while keeping the NACL allowing it. Observe the result — the website is blocked again.

  8. Cleanup: Terminate EC2 instance → Delete VPC resources.

✅ What you learned: NACL evaluates BEFORE Security Groups. A DENY in NACL wins even if Security Group says ALLOW. Security Group can block even after NACL allows. Both layers must permit traffic for it to reach the instance.
