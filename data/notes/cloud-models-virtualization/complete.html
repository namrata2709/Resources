🌟 Introduction

Before you can understand any AWS service — EC2, S3, Lambda, or anything else — you need a solid foundation in how cloud computing actually works. This session covers two essential building blocks: Cloud Models (how cloud is structured and delivered) and Virtualization (the technology that makes cloud computing possible in the first place).

Figure 1: The Big Picture — Cloud Models and Virtualization as the Foundation of AWS

Think of it this way: if cloud computing is a building, then virtualization is the foundation, cloud deployment models tell you who owns the building, and cloud service types tell you how much of the building you're renting. By the end of this session, you'll be able to answer confidently: "What kind of cloud is this?" and "What exactly is a virtual machine?"

⚡ Why This Matters: Every AWS certification exam — from Cloud Practitioner to Solutions Architect — tests these fundamentals. Getting this right now means every advanced topic clicks into place faster.

🏗️ Cloud Deployment Models

The first question to ask about any cloud setup is: who owns and controls the infrastructure? That answer defines the deployment model. Think of it like housing: do you rent an apartment in a building shared by many tenants (public cloud), buy your own house (private cloud), or do both (hybrid cloud)?

Figure 2: Cloud Deployment Models — Who Owns It and Who Can Use It

☁️ Public Cloud

A Public Cloud is cloud infrastructure owned and operated by a third-party provider (like AWS, Microsoft Azure, or Google Cloud) and made available to the general public over the internet. You don't own any hardware — you simply rent what you need, when you need it.

In a public cloud, infrastructure is shared across multiple customers (called multi-tenancy), but each customer's data and workloads are logically isolated from one another.

  • Ownership: Belongs to the cloud provider (AWS, Azure, GCP).
  • Access: Available to anyone who signs up — individuals, startups, enterprises.
  • Cost: Pay-as-you-go — you only pay for what you use.
  • Maintenance: The provider handles everything: hardware, security, cooling, networking.

✅ Real-World Example: You launch a startup website on AWS. You don't buy a single server — AWS owns thousands of servers in data centers worldwide, and you rent a tiny slice of that capacity. When traffic spikes, you scale up in minutes. When it drops, you scale down and stop paying.

When to use it: Most workloads — websites, apps, development environments, data analytics. If cost efficiency and scalability matter, public cloud is almost always the answer.

🏢 Private Cloud

A Private Cloud is cloud infrastructure that is used exclusively by a single organization — it is not shared with other customers. The organization can host it in their own data center or have a provider host it for them, but the key characteristic is dedicated, exclusive access.

💡 The Bank Analogy: Imagine a major bank. It can't just dump customer financial records on a shared AWS account visible to other companies. So it builds its own cloud infrastructure inside its own secured data center — using software like VMware or OpenStack to create virtual servers, automate resource allocation, and provide self-service to internal teams. It looks and feels like AWS from the inside, but nobody else can touch it.

This is the critical distinction beginners often miss: a private cloud is still a cloud — it has on-demand provisioning, scalability, and automation — but it runs on dedicated infrastructure controlled by one organization.

  • Ownership: The organization itself (or a managed private cloud provider).
  • Access: Only internal users of that organization.
  • Cost: Higher upfront — hardware, software licenses, and IT staff required.
  • Control: Maximum — you control every layer from hardware to application.

When to use it: Highly regulated industries like banking, healthcare, and government, where data sovereignty and compliance requirements (HIPAA, PCI-DSS) make shared infrastructure risky or legally complicated.

🏢 Data Center vs. Cloud — What's the Difference?

Students often confuse "data center" and "cloud." They're related but not the same thing. Understanding the difference is critical for both exams and real-world conversations.

Figure 3: Data Center vs. Cloud — Physical Space vs. Delivery Model

AspectData CenterCloud
What it isA physical building with servers, storage, networking gearA way of delivering computing resources — flexible, on-demand, automated
Who manages itYou manage everything: hardware, OS, apps, security, power, coolingProvider manages infrastructure; you manage what runs on it
ScalingBuy more hardware, wait weeks for delivery and setupClick a button, scale in minutes
Cost modelLarge upfront CapEx (capital expenditure)Ongoing OpEx (operational expenditure) — pay-as-you-go
AnalogyBuying land and building your own houseRenting an apartment — move in today, adjust space anytime

⚡ Key Insight: A private cloud lives inside a data center but is designed to behave like a cloud — with self-service, automation, and on-demand resource allocation. The data center is the physical space; the cloud is the operating model on top of it.

🔀 Hybrid Cloud

A Hybrid Cloudcombines public and private cloud environments, allowing data and applications to move between them. Organizations use hybrid cloud when they want the control of a private cloud for sensitive workloads and the scalability of public cloud for everything else.

  • Sensitive data (patient records, financial transactions) → stays in private cloud.
  • Normal applications (website, email, analytics) → runs in public cloud.
  • Burst workloads → private cloud handles baseline; public cloud handles traffic spikes.

✅ Real-World Example: A hospital keeps patient medical records on its private cloud (HIPAA compliance), but uses AWS for its public-facing appointment booking system. During flu season, when bookings spike, AWS scales automatically while the sensitive records never leave the private environment.

When to use it: Organizations already invested in on-premises infrastructure, heavily regulated industries needing compliance, or companies wanting gradual cloud migration without abandoning existing systems.

👥 Community Cloud

A Community Cloud is the least common deployment model. In a community cloud, infrastructure is shared among organizations with common concerns — such as similar security requirements, compliance mandates, or mission objectives.

  • Ownership: Shared by participating organizations or a third party.
  • Access: Only the community of organizations involved.
  • Example: A group of universities sharing a research computing cloud, or government agencies sharing a classified cloud.

💡 Exam Note: Community cloud rarely appears as the correct answer in scenario questions. Know the definition and the example, but focus your exam prep on Public, Private, and Hybrid.

⚙️ Cloud Service Types (IaaS, PaaS, SaaS)

Once you know where cloud is hosted (deployment model), the next question is: what exactly does the cloud provider give you? That's what service types answer. Think of it like ordering food: IaaS is buying raw groceries and cooking yourself, PaaS is a meal kit (ingredients + recipe, you cook), and SaaS is ordering a fully cooked meal delivered to your door.

Figure 4: IaaS vs. PaaS vs. SaaS — The Responsibility Stack

🖥️ IaaS — Infrastructure as a Service

IaaS provides raw cloud infrastructure — servers, storage, and networking — over the internet. The customer manages the operating system, middleware, runtime, and applications.

  • Provider manages: Physical hardware, data center, networking hardware, virtualization layer.
  • You manage: OS, patches, applications, data, access control.
  • AWS Example:Amazon EC2 (virtual servers), Amazon S3 (raw storage), Amazon VPC (virtual networking).
  • Other examples: Microsoft Azure Virtual Machines, Google Compute Engine.

✅ Best for: Teams that need full control over their environment — custom OS configurations, specialized software, or migrating existing workloads ("lift and shift") to the cloud.

🛠️ PaaS — Platform as a Service

PaaS provides infrastructure plus a runtime platform — developers deploy their code without managing servers, OS, or infrastructure.

  • Provider manages: Hardware, OS, runtime, middleware, scaling, patching.
  • You manage: Your application code and data only.
  • AWS Example:AWS Elastic Beanstalk (you upload code, AWS handles deployment), AWS Lambda (serverless — you only write functions).
  • Other examples: Google App Engine, Heroku.

✅ Best for: Developers who want to focus purely on writing code and not worry about patching servers, configuring load balancers, or managing OS updates.

📱 SaaS — Software as a Service

SaaS delivers fully managed applications over the internet. The user only uses the software — they manage nothing about the underlying infrastructure, platform, or application itself.

  • Provider manages: Everything — hardware, OS, application, updates, security.
  • You manage: Your data and user access settings only.
  • Examples: Gmail, Zoom, Salesforce, Microsoft 365, Dropbox.
  • AWS Example: Amazon WorkMail, Amazon Chime.

✅ Best for: Business users who need software immediately with no setup — productivity tools, communication platforms, CRM systems.

Figure 5: IaaS vs. PaaS vs. SaaS — Real-World Examples at a Glance

⚡ Quick Memory Trick:
🖥️ IaaS = You manage most (server, OS, app)
🛠️ PaaS = You just code (app + data only)
📱 SaaS = You just use (open and go)

🔐 Shared Responsibility Model

One of the most exam-critical concepts in all of AWS is the Shared Responsibility Model. This defines exactly what AWS is responsible for securing versus what you (the customer) are responsible for securing. Many real-world cloud breaches happen because customers assumed AWS would handle something that is actually their responsibility.

Figure 6: AWS Shared Responsibility Model — Security OF the Cloud vs. IN the Cloud

The golden rule: AWS is responsible for security "of" the cloud (the infrastructure), and the customer is responsible for security "in" the cloud (everything they deploy and configure).

🏢 What AWS Is Responsible For

AWS protects and manages all the physical and foundational infrastructure that runs the cloud:

  • Physical data centers: Buildings, locks, guards, surveillance — physical security.
  • Hardware: Servers, storage devices, networking equipment.
  • Hypervisor and virtualization layer: The software that creates and isolates virtual machines.
  • Networking infrastructure: AWS global network, edge locations, routing.
  • Managed service maintenance: For services like RDS, AWS patches the underlying database engine; for Lambda, AWS manages the runtime environment.

💡 You will never be asked to patch a physical AWS server, replace a failed hard drive in an AWS data center, or manage AWS's global backbone network. That's all AWS's job — and they do it with extremely high standards.

👤 What the Customer Is Responsible For

Customers control everything they bring into the cloud:

  • Data: Encryption, backup, classification — you decide what happens to your data.
  • Identity and Access Management (IAM): Who gets access to what. If you set permissions too loosely, that's on you.
  • Operating system patching: If you run an EC2 instance (IaaS), patching the OS is your job.
  • Application security: Your code, your app's vulnerabilities, your responsibility.
  • Network configuration: Security groups, NACLs, firewalls — you configure these.

❌ Common Mistake: Assuming AWS encrypts your data by default. For many services, you must enable encryption. AWS provides the tools (KMS, S3 encryption settings), but you must turn them on. This is a frequent exam trap — and a real-world security risk.

🔄 Responsibility Shifts by Service Type

An important nuance: the division of responsibility shifts depending on whether you use IaaS, PaaS, or SaaS. The more managed the service, the more AWS takes on.

LayerIaaS (e.g., EC2)PaaS (e.g., Elastic Beanstalk)SaaS (e.g., WorkMail)
Physical hardwareAWSAWSAWS
HypervisorAWSAWSAWS
Operating SystemCustomerAWSAWS

⚡ Exam Pattern: When a question asks "who is responsible for patching the OS on an EC2 instance?" — the answer is always the customer. When the question asks "who is responsible for patching the underlying host hardware?" — always AWS.

🖥️ What is Virtualization?

You've heard about cloud computing — but have you ever wondered how AWS can give thousands of customers their own "private" servers from the same physical hardware? The answer is virtualization. It is the single most important enabling technology behind cloud computing.

Figure 7: Virtualization — One Physical Server, Many Virtual Machines

Virtualization is technology that allows multiple virtual machines to run on a single physical server by abstracting hardware resources through a hypervisor.

Without virtualization, 1 physical server = 1 operating system = 1 application. Most of the server's CPU and RAM would sit idle most of the time — wasteful and expensive. With virtualization, that same server can run 5, 10, or 20 isolated virtual machines simultaneously, each thinking it has its own dedicated hardware.

💡 Analogy: Think of a large apartment building. One building (the physical server) is divided into many apartments (virtual machines). Each tenant (customer) has their own locked space with their own furniture (OS + apps). The building's infrastructure — plumbing, electricity, elevators (CPU, RAM, network) — is shared but each apartment feels private and independent.

⚙️ How Virtualization Works

To understand virtualization, you need to know its three key components: the physical hardware, the hypervisor, and the virtual machines themselves.

Figure 8: The Three Layers of Virtualization Architecture

🔩 Layer 1: Physical Hardware (Host Machine)

This is the real, tangible server — a powerful machine with:

  • CPU: Multiple processor cores (modern servers have 32–256 cores).
  • RAM: Large memory capacity (128GB–2TB+ in enterprise servers).
  • Storage: High-speed SSDs or NVMe drives in the terabytes.
  • Network interfaces: High-speed network cards (10Gbps–100Gbps).

The physical host is the foundation. Everything virtual exists because this real hardware exists underneath it.

🧩 Layer 2: The Hypervisor

The hypervisor is the software layer that sits between the physical hardware and the virtual machines, allocating CPU, RAM, and storage to each VM.

There are two types of hypervisors:

TypeAlso CalledHow It WorksExamples
Type 1Bare-metal hypervisorRuns directly on hardware — no host OS needed. Faster and more efficient.VMware ESXi, Microsoft Hyper-V, AWS Nitro, KVM, Xen
Type 2Hosted hypervisorRuns on top of an existing OS. Slower — two OS layers. Used for development/testing.VirtualBox, VMware Workstation

⚡ AWS uses Type 1: AWS built its own hypervisor called the AWS Nitro System — a bare-metal hypervisor purpose-built for massive scale, performance, and security isolation between customer workloads.

💻 Layer 3: Virtual Machines (Guest Systems)

A Virtual Machine (VM) is a software emulation of a complete computer — it has its own OS, applications, and virtual hardware (virtual CPU, virtual RAM, virtual disk), but shares the underlying physical hardware with other VMs.

  • Each VM is completely isolated — a crash in VM1 does not affect VM2.
  • Each VM can run a different OS — you could have Windows Server, Ubuntu Linux, and Amazon Linux all running simultaneously on the same physical host.
  • VMs are portable — you can take a snapshot and move it to a different physical host without reconfiguring anything.

✅ AWS Context: When you launch an EC2 instance on AWS, you're creating a virtual machine. AWS's massive data centers run thousands of physical servers, each hosting dozens of customer EC2 instances — all thanks to virtualization.

☁️ Virtualization in Cloud Computing

Now that you understand what virtualization is, let's connect it directly to AWS and cloud computing. Virtualization is the reason cloud providers like AWS can offer the following benefits — all at massive scale:

Figure 9: How Virtualization Powers Cloud Computing Benefits

  • Multi-tenancy: Many customers share the same physical infrastructure securely and in isolation — each customer's VM is isolated from others.
  • Scalability: AWS can spin up a new EC2 instance (VM) for you in seconds — no waiting for physical hardware to be provisioned.
  • Isolation: Even though hardware is shared, your workload is isolated. A noisy neighbor on the same physical host does not see your data or crash your application.
  • Flexibility: You can run Windows, Linux, or custom AMIs (Amazon Machine Images) on the same underlying hardware.

💡 According to AWS documentation, the AWS Nitro System — a custom hypervisor — enables near bare-metal performance for EC2 instances by offloading virtualization functions to dedicated hardware. This means customers get the benefits of virtualization with minimal performance penalty.
📚 Source:AWS Nitro System Documentation

⚖️ Advantages & Disadvantages of Virtualization

Virtualization is powerful, but it's not perfect. Understanding both sides helps you make better architectural decisions — and answer exam questions that test trade-offs.

Figure 11: Virtualization Advantages vs. Disadvantages

✅ Advantages of Virtualization

  • Efficient Resource Utilization: Multiple VMs share the same physical hardware — no wastage of CPU, RAM, or storage.
  • Cost Savings: Fewer physical servers means lower hardware, power, cooling, and maintenance costs. This is the primary driver of cloud economics.
  • Scalability & Flexibility: VMs can be created, cloned, resized, or deleted in minutes — far faster than procuring physical servers.
  • Isolation & Security: Each VM is logically isolated — if one VM crashes or is compromised, the others continue operating normally.
  • Disaster Recovery & Backup: VM snapshots (a complete saved state of a VM) make backup and rapid restoration straightforward. In AWS, this is AMI snapshots and EBS snapshots.
  • Platform Independence: Run Windows, Linux, or any other OS on the same physical machine simultaneously.
  • Testing & Development: Developers can spin up and tear down isolated test environments instantly — no need for extra physical hardware.

❌ Disadvantages of Virtualization

  • Performance Overhead: VMs are slower than bare-metal servers because resources are shared and there's a hypervisor translation layer adding latency.
  • Single Point of Failure: If the physical host fails, all VMs running on it go down simultaneously.
  • Management Complexity: Operating a virtualized environment requires skilled administrators who understand hypervisors, storage virtualization, and virtual networking — a significant learning curve.
  • Licensing Costs: Hypervisor software (especially VMware) and OS licenses per VM can be expensive — potentially offsetting hardware savings.
  • Resource Contention: When too many VMs compete for the same physical CPU, RAM, or disk, performance degrades. This is called the "noisy neighbor" problem.
  • Hypervisor Vulnerabilities: A security flaw in the hypervisor could allow an attacker to escape from one VM and access another — though this is rare and cloud providers invest heavily in prevention.
  • Not Always Cost-Effective at Small Scale: For a small business with minimal workloads, the overhead of setting up and managing virtualization infrastructure may cost more than just running physical servers.

⚡ Quick Memory Trick:
✅ Advantages → Cost, Efficiency, Flexibility, Backup, Isolation
❌ Disadvantages → Performance, Complexity, Cost (software), Failure risk, Security (hypervisor)

Figure 12: Virtualization Trade-offs at a Glance

📝 Overall Summary

  • Cloud Deployment Models: Define who owns and controls cloud infrastructure — Public (anyone), Private (one org), Hybrid (both), Community (shared by similar orgs).
  • Data Center vs. Cloud: A data center is the physical building; the cloud is the delivery model on top — on-demand, automated, and scalable.
  • IaaS: Provider gives you raw infrastructure (EC2, S3). You manage OS and above. Maximum control, maximum responsibility.
  • PaaS: Provider manages infrastructure + runtime (Elastic Beanstalk). You just deploy code. Less control, less responsibility.
  • SaaS: Provider delivers the full application (Gmail, WorkMail). You just use it. Minimum management, minimum control.
  • Shared Responsibility Model: AWS secures "of the cloud" (hardware, networking, physical security). You secure "in the cloud" (data, IAM, OS patching, application code).
  • Virtualization: Technology that allows multiple virtual machines to run on one physical server using a hypervisor — the foundation of cloud computing.
  • Hypervisor: The software layer between hardware and VMs. Type 1 (bare-metal) is used in production/cloud; Type 2 (hosted) is used for development. AWS uses the Nitro hypervisor.
  • Types of Virtualization: Server, Storage, Network, and Desktop — each type enables a different AWS service category.
  • Virtualization Advantages: Efficiency, cost savings, scalability, isolation, disaster recovery, platform independence, and fast testing environments.
  • Virtualization Disadvantages: Performance overhead, single point of failure (host failure = all VMs down), management complexity, licensing costs, resource contention, and rare hypervisor security risks.

Project 1: Explore EC2 — Virtualization in Action

🎯 Objective: Launch your first EC2 instance and observe how AWS virtualization delivers a virtual machine on demand.

⏱️ Time: 20–30 min

💰 Cost: Free tier eligible (t2.micro or t3.micro)

  1. Log in to the AWS Management Console and navigate to EC2 from the Services menu.

    Figure 13: 📸 EC2 Console Home — The Launch Instance Button

  2. Click Launch Instance. Give your instance a name like my-first-vm.

  3. For Application and OS Images (AMI), select Amazon Linux 2023 (free tier). This is the operating system your virtual machine will run — proof that virtualization lets you choose any OS on shared hardware.

    Figure 14: 📸 AMI Selection — Choosing the OS for Your Virtual Machine

  4. For Instance Type, select t2.micro (1 vCPU, 1 GB RAM). Notice that "vCPU" means virtual CPU — a virtualized fraction of a real physical CPU core.

  5. For Key Pair, create a new key pair. Name it my-first-keypair, select RSA format, and .pem extension. Download and save the .pem file securely.

    Figure 15: 📸 Key Pair Creation Dialog

  6. Leave all other settings as default and click Launch Instance. Wait 1–2 minutes for the instance state to show Running.

    Figure 16: 📸 EC2 Instance in Running State

  7. Click your instance and explore the Details tab. Observe: Instance ID, Instance Type (t2.micro), Availability Zone, Public IP, and Private IP. This is your virtual machine — created in under 2 minutes, running on AWS's shared physical infrastructure.

✅ Verification: Your instance status is Running and it has a public IPv4 address assigned. You just created a virtual machine using AWS virtualization — the same concept covered in this session, now tangible.

💰 Cost Note: t2.micro is free tier eligible for up to 750 hours/month. If you use a larger instance type, charges apply (~$0.012/hour for t3.small).

🧹 Cleanup

  1. Select your instance in the EC2 console.
  2. Click Instance State → Terminate Instance.
  3. Confirm termination. The instance will move to Terminated state and stop incurring any charges.

Project 3: Multi-VM Playground — Feel Virtualization

🎯 Objective: Launch two EC2 instances with different operating systems on the same AWS hardware — making virtualization tangible.

⏱️ Time: 30–40 min

💰 Cost: Free tier eligible (2x t2.micro)

This project directly proves the theory: virtualization lets one physical server run multiple different operating systems simultaneously. You are going to feel this — not just read about it.

  1. Navigate to EC2 → Instances → Launch Instances. Name this first instance vm-amazon-linux. Under AMI, select Amazon Linux 2023. Instance type: t2.micro. Select your existing key pair.

    Figure 18: 📸 VM 1 — Amazon Linux 2023 Configuration

  2. Click Launch Instance. Then immediately launch a second one. Name it vm-ubuntu. Under AMI, click Browse more AMIs, search Ubuntu 22.04, and select the free-tier eligible Ubuntu Server 22.04 LTS AMI.

    Figure 19: 📸 VM 2 — Ubuntu 22.04 AMI Search

  3. Wait for both instances to reach Running state. Select both. Notice they each have a different AMI ID and different Platform — yet both show t2.micro and are in the same Availability Zone. Same hardware layer, completely different virtual environments.

    sudo yum update -y
    sudo yum install nginx -y

    sudo apt update
    sudo apt install apache2 -y

    Figure 21: 📸 Nginx and Apache Running Simultaneously — Two VMs, One Physical Layer

⚡ What just happened: Amazon Linux and Ubuntu running simultaneously on AWS hardware sharing the same physical layer. That is virtualization — not as a definition, but as something you just built and saw in your browser.

✅ Verification: Both public IPs load different web server pages. Both instances show Running in EC2.

Project 4: Instance Lifecycle Lab — Start, Stop, Snapshot

🎯 Objective: Observe what happens to your EC2 instance — especially its public IP — when you start, stop, reboot, and snapshot it.

⏱️ Time: 25–35 min

💰 Cost: Free tier eligible — tiny EBS snapshot storage charge

When a junior says "I stopped my instance and now I cannot connect" — a senior immediately knows why: the public IP changed. This project builds that instinct before you need it in a real environment.

  1. Launch a new instance: name it lifecycle-test, AMI Amazon Linux 2023, type t2.micro. After it reaches Running, write down its Public IPv4 address exactly.

  2. Select the instance → Instance State → Stop Instance. Confirm. Wait for Stopped state. Look at the Public IPv4 address field — it now shows a dash. When a standard EC2 instance is stopped, its public IP address is released back to AWS and a new one is assigned on next start.

    Figure 22: 📸 Stopped Instance — Public IP Released

  3. Start the instance again: Instance State → Start Instance. Once Running, check the Public IPv4 address — it is a different IP from Step 1. This is why Elastic IP addresses exist for workloads that need a fixed public address.

    Figure 23: 📸 Instance Restarted — New Public IP Assigned

  4. Create an AMI snapshot. Select the instance → Actions → Image and templates → Create Image. Name it lifecycle-test-snapshot. Click Create Image.

    Figure 24: 📸 Create AMI — Snapshotting the Instance

  5. Navigate to EC2 → Images → AMIs. Wait for your AMI to show Available. This AMI captures everything — OS, software, configuration — and can launch identical copies on any instance type, in any region.

    Figure 25: 📸 AMI Available — Portable VM Snapshot Ready

⚡ Lifecycle Cheat Sheet:
Stop then Start = new public IP (compute billing stops, EBS still billed)
Reboot = same IP retained (OS restarts, stays on same host)
Terminate = gone permanently (root EBS deleted by default)
AMI = portable snapshot, launch identical copies anywhere

✅ Verification: You observed a different IP after stop and start. Your AMI shows Available.

🧹 Cleanup

  1. Terminate lifecycle-test.
  2. EC2 → AMIs → select lifecycle-test-snapshot → Actions → Deregister AMI.
  3. EC2 → Snapshots → find the associated snapshot → Delete Snapshot.

Project 5: Break & Fix Security — Shared Responsibility in Practice

🎯 Objective: Create an over-permissive security group, observe the risk, then fix it — internalizing the customer side of the Shared Responsibility Model.

⏱️ Time: 30–40 min

💰 Cost: Free tier eligible

Security in the cloud is your job. This project makes that real. You are going to create the exact misconfiguration that causes real-world breaches — then fix it with precision.

⚠️ Note: This is a controlled exercise on your own account. The open security group will be fixed within minutes. Never leave production resources this way.

  1. Launch a new instance: name it security-test, AMI Amazon Linux 2023, type t2.micro. In Network Settings click Edit. Add two inbound rules: SSH, Source 0.0.0.0/0 and All traffic, Source 0.0.0.0/0. Every port on this server is now open to every IP on the internet.

    Figure 26: 📸 Over-Permissive Security Group — All Ports Open

  2. Once running, go to the Security tab and click the security group. Observe the rules. AWS permitted this configuration because security group rules are the customer's responsibility, not AWS's. This is the Shared Responsibility boundary in practice.

  3. Find your public IP at whatismyip.com (e.g. 203.0.113.42).

  4. Edit the security group. Delete both rules. Add back only: SSH, Source Custom, your-ip/32. The /32 means exactly one IP address — yours only. Save rules.

    Figure 27: 📸 Fixed Security Group — SSH Restricted to Your IP Only

  5. SSH from your machine — it works. Try from a different IP (VPN or a friend) — connection timeout. Correct.

✅ Verification: SSH succeeds from your IP. Any other IP gets a timeout.

⚡ Interview Answer: "Who is responsible for a breach from an open security group on EC2?" — the customer. AWS provided the tool. The customer misconfigured it. This is exactly where most cloud security incidents happen — not from AWS infrastructure failures, but from customer misconfiguration.

🧹 Cleanup

  1. Terminate security-test.
  2. EC2 → Security Groups → select the group → Delete.

Project 6: S3 Static Website — IaaS vs. Managed Service

🎯 Objective: Host a website on S3 without any EC2 instance — then compare the experience to Projects 1 and 3 where you managed servers yourself.

⏱️ Time: 20–30 min

💰 Cost: Near-zero — fractions of a cent for S3 storage and requests

In earlier projects you installed software, configured ports, and managed OS patches. Now you host a live website with zero server management. This is what the difference between IaaS and a managed service actually feels like.

  1. Create an index.html file on your local machine:

    &lt;!DOCTYPE html&gt;
&lt;html&gt;
&lt;head&gt;&lt;title&gt;My S3 Site&lt;/title&gt;&lt;/head&gt;
&lt;body&gt;
  &lt;h1&gt;Hello from S3!&lt;/h1&gt;
  &lt;p&gt;No server. No SSH. No OS to patch.&lt;/p&gt;
&lt;/body&gt;
&lt;/html&gt;

    Save this file as index.html.

  2. Navigate to S3 → Create Bucket. Give it a globally unique name like my-site-yourname-2025. Same region as your EC2 work. Uncheck Block all public access and check the acknowledgment warning — required for public website hosting.

    Figure 28: 📸 S3 Bucket — Unblocking Public Access for Static Hosting

  3. Open the bucket → Upload your index.html. Then Properties tab → scroll to Static website hosting → Edit → Enable. Set Index document to index.html. Save.

    Figure 29: 📸 Static Website Hosting Enabled — Endpoint URL Generated

  4. Permissions tab → Bucket Policy → Edit. Paste this policy and replace YOUR-BUCKET-NAME with your actual bucket name:

    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*"
  }]
}

  5. Back in Properties → Static website hosting, click the Bucket website endpoint URL. Your page loads — no EC2, no SSH, no nginx, no patch cycle, ever.

    Figure 30: 📸 Website Live on S3 — Zero Server Management

⚡ The Comparison That Matters:
EC2 path (Projects 1 and 3): Launch instance → SSH → install nginx → open port 80 → configure → manage OS patches forever.
S3 path (this project): Create bucket → upload file → enable hosting → done.
Same result. Completely different responsibility model. EC2 = IaaS. S3 static hosting = provider manages all infrastructure. This is why managed services exist.

✅ Verification: Your HTML page loads via the S3 endpoint URL. No EC2 instance was involved at any step.

🧹 Cleanup

  1. Open bucket → select all objects → Delete.
  2. Bucket list → select bucket → Delete → confirm by typing the bucket name.

🤔 Reflection Questions

1. A hospital wants to keep patient records on infrastructure it fully controls for compliance, but needs AWS for its public appointment booking website. What cloud deployment model should it use?

💡 Hint

Think about which model combines private and public cloud capabilities.

2. Your company uses Gmail and Zoom for daily work. What cloud service model are these? Who is responsible for patching the email servers?

💡 Hint

Consider how much you manage vs. how much the provider manages in this model.

3. An EC2 instance gets hacked because someone used a weak password for the OS admin account. Who is responsible — AWS or the customer? Why?

💡 Hint

Apply the Shared Responsibility Model. The OS is inside the cloud, not the physical hardware.

4. Without virtualization, AWS would need one physical server for every EC2 customer. If AWS has 1 million active EC2 customers, how many physical servers would that require? What does this tell you about why virtualization is economically necessary?

💡 Hint

Think about cost, space, power, and cooling at that scale — then contrast with the reality of many VMs per server.

5. A startup is building a web app. They want fast deployment and don't want to manage servers. Should they use EC2 (IaaS) or Elastic Beanstalk (PaaS)? What are the trade-offs?

💡 Hint

Consider control vs. convenience, and who patches the OS in each model.

6. What is the "noisy neighbor" problem in virtualization? How does AWS address it with the Nitro System?

💡 Hint

Think about resource contention between VMs on the same host and how dedicated hardware offload helps.
