📄 Static vs Dynamic Websites — Know the Difference

Before choosing where to host, you need to understand what kind of website you have. This distinction changes everything.

What is a Static Website?

A static website is made up of pre-built files — HTML, CSS, JavaScript, and images. Every user who visits the website sees the exact same content. The files are fixed; they don't change based on user data or real-time inputs.

Think of it like a printed brochure. Everyone who gets a copy sees the same thing. Examples include:

  • Company/school portfolio websites
  • Landing pages
  • Documentation sites
  • Personal blogs (when pre-built)

What is a Dynamic Website?

A dynamic website generates pages on the fly based on user data, database queries, or real-time logic. Dynamic websites require a backend — a running server with software like Node.js, Python, PHP, Java Spring, Ruby, or .NET — to construct each page at request time.

Your Amazon shopping cart, your bank account page, your Gmail inbox — all of these are dynamic. The page is different for every user and every session.

💡 Key Point: S3 can only host static websites. If your site has backend logic, user authentication, or database queries, you need EC2 (or another compute service like Lambda or Elastic Beanstalk).

🪣 S3 Static Website Hosting — How to Set It Up

Let's walk through exactly what the instructor did live in class. This is a complete step-by-step guide.

Step 1: Create an S3 Bucket

Go to the S3 console and create a new bucket. Give it a meaningful name — S3 bucket names must be globally unique across all AWS accounts and all regions.

💡 In class, the bucket was named static-67966 and created in the Mumbai (ap-south-1) region. You can use any region, but remember — this affects latency for global users (we'll fix that with CloudFront later).

📸 Screenshot: S3 bucket creation page — enter your unique bucket name and select your region

Step 2: Upload Your Static Website Files

Open your bucket and click Upload. Add all your website files — HTML pages, CSS stylesheets, JavaScript files, and images. All website files must be placed directly in the root of the bucket, not inside a subfolder — unless you're using CloudFront (covered later), which can target a specific path.

In class, a school website project was used as an example. It contained:

  • index.html — the main landing page
  • Additional .html pages for other sections
  • A css/ folder with stylesheets
  • An images/ folder with the site's images

📸 Screenshot: Uploading website files to S3 — drag and drop or use Add files/Add folder

Step 3: Enable Static Website Hosting

Go to your bucket → Properties tab → scroll all the way down to find Static website hosting. It's disabled by default.

Click Edit, then:

  1. Set to Enable
  2. Set Index document to index.html (the name of your main page — must match exactly)
  3. Set Error document to index.html as well (so any errors redirect back to the main page)
  4. Click Save changes
💡 Index Document = the default page AWS serves when someone visits your website URL. If you name your main file something other than index.html, you must enter that exact filename here.
💡 Error Document = the page served when an error occurs (like a 404). In production you'd create a custom error page; in simple setups, redirecting back to index.html is common.

📸 Screenshot: Enabling Static Website Hosting — set index document to match your main HTML filename

Step 4: Get the Website Endpoint URL

Once saved, scroll back down in the Properties tab. You'll now see a Bucket website endpoint — a URL that looks like:

http://static-67966.s3-website.ap-south-1.amazonaws.com

Copy this URL. Try opening it in a browser. What happens? You'll get a 403 Forbidden error. Why?

❌ 403 Forbidden means: The bucket is still private. The static website hosting feature only enables serving — it does NOT automatically make the bucket public. You must handle permissions separately.

Step 5: Allow Public Access (For Direct URL Method)

To let the website URL work, the bucket must be public. There are two things to do:

A) Disable Block Public Access:

  1. Go to the bucket → Permissions tab
  2. Click Edit under "Block public access"
  3. Uncheck all four checkboxes
  4. Save changes and type "confirm"

📸 Screenshot: Disabling Block Public Access — uncheck all boxes to allow public permissions

B) Add a Bucket Policy:

Disabling Block Public Access alone is not enough. You also need a bucket policy that explicitly grants public read access. Go to Permissions → Bucket policy → Edit, then add the following policy (replace YOUR-BUCKET-NAME with your actual bucket name):

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*"
    }
  ]
}

Breaking down this policy:

  • "Principal": "*" — means everyone (the entire internet)
  • "Action": "s3:GetObject" — allows reading (downloading) objects
  • "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*" — applies to all objects inside the bucket (the /* means all files)

📸 Screenshot: Bucket policy allowing public read access — Principal * means the entire internet

After saving, refresh your website URL. The website now loads with all images and pages. 🎉

⚡ Two-Step Public Access: Making an S3 bucket publicly accessible requires TWO steps: (1) disabling Block Public Access and (2) adding a bucket policy with s3:GetObject for Principal: *.

⚠️ The Problem with a Fully Public Bucket

The static website is working. But there's a catch — and it's a big one in the real world.

Problem 1: High Latency for Global Users

Your S3 bucket sits in one specific AWS region — say, Mumbai. When someone from India accesses the website, the request travels a short distance to Mumbai and comes back quickly. Low latency. Fast load.

But what about a user in Germany? Or Canada? Or Australia? Their request has to travel thousands of kilometers to Mumbai, get the data, and travel thousands of kilometers back. This distance causes high latency — the website loads slowly for users who are geographically far from the AWS region where the bucket is hosted.

Figure 4: A single-region S3 bucket creates high latency for users far away — they must wait for data to travel across the world

Problem 2: Security Risk of an Open Bucket

When you use the static website URL (.s3-website.amazonaws.com), the bucket must be public. This means:

  • Anyone on the internet can access your bucket directly using the S3 URL
  • Your organization's security team will flag this — the bucket is "open to everyone"
  • There is no way to restrict access to specific sources while still using the website endpoint URL
❌ Real-World Alert: The instructor's actual client from Singapore raised this exact issue — the bucket was publicly accessible, and the security team flagged it. The fix was CloudFront with OAC (covered next).
⚡ Two Problems, One Solution: Amazon CloudFront solves both problems simultaneously — it reduces latency by serving content from edge locations near users, and it allows the S3 bucket to remain private by using Origin Access Control (OAC).

🌍 What is a CDN? — Content Delivery Network Explained

Before we jump into CloudFront, let's understand the concept behind it. CDN is not an AWS-specific idea — it's a fundamental internet technology.

CDN Definition

A Content Delivery Network (CDN) is a globally distributed network of servers designed to deliver internet content faster to users, regardless of their geographic location.

Think of it this way: imagine you run a pizza chain. If you only have one kitchen in Mumbai, delivering pizza to someone in Germany takes too long — the pizza arrives cold. So you open mini-kitchens (not full restaurants — just small delivery hubs) in Germany, Canada, Australia, and Africa. Now everyone gets fresh pizza quickly, because it comes from the nearest kitchen, not from Mumbai.

CDN works exactly like that. Instead of one server (origin) in Mumbai, you have:

  • Mini-servers (edge locations) placed strategically around the world
  • Content is cached (temporarily stored) at these edge locations
  • When a user requests content, it comes from the nearest edge location

Figure 5: How a CDN works — mini-servers (edge locations) near users serve cached content, dramatically reducing travel distance

Caching and TTL (Time to Live)

When an edge location doesn't have a file yet (cache miss), it fetches it from the origin server (S3 in our case), serves it to the user, and keeps a copy. The next user in that region gets the cached copy — no round trip to the origin needed.

The amount of time a CDN keeps a cached copy before checking the origin for updates is called TTL (Time to Live), also referred to as cache expiry time. In class, the instructor mentioned 300 seconds as an example TTL.

💡 Why TTL matters: If you update your website content in S3, the edge locations won't immediately show the change — they'll keep showing the old cached version until TTL expires. You can also invalidate the cache manually in CloudFront to force an immediate refresh.

Edge Locations vs. Origin Servers

TermWhat it isExample
Origin ServerThe main source where your actual content livesS3 bucket in Mumbai, or an EC2-backed Load Balancer
Edge LocationA mini data center in the CDN network that caches content near users. Also called Point of Presence (PoP)CloudFront node in Frankfurt, Sydney, Toronto
Cache HitContent is already at the edge location — served instantlyUser in Germany gets a cached page from Frankfurt node
Cache MissContent is not at edge — fetched from origin, then cachedFirst request from Germany triggers a fetch from Mumbai

Figure 6: Cache hit vs cache miss — after the first request (cache miss), all subsequent requests for the same content are served instantly from the edge (cache hit)

☁️ Amazon CloudFront — AWS's CDN Service

Amazon CloudFront is AWS's managed Content Delivery Network (CDN) service. It delivers content with low latency and high transfer speeds by caching it at a global network of edge locations.

CloudFront is not just for S3. It can sit in front of:

  • S3 buckets — static files, images, websites
  • Application Load Balancers — dynamic web applications
  • EC2 instances
  • API Gateway — REST APIs
  • Any HTTP/HTTPS origin
💡 Key Term: Distribution — In CloudFront, a "distribution" is your CDN configuration. Think of it as the settings file that tells CloudFront: where is your origin, what is the root document, who can access it, and how long to cache content.

CloudFront Supports Multiple Origin Types

Figure 7: CloudFront can sit in front of many AWS origins — not just S3, but also Load Balancers, EC2, and API Gateway

How CloudFront Works — End to End

  1. You create a CloudFront distribution pointing to your S3 bucket as the origin
  2. CloudFront gives you a distribution domain name (e.g., d1234abcd.cloudfront.net)
  3. You share this CloudFront URL with your users (instead of the S3 URL)
  4. When a user makes a request, it goes to the nearest edge location
  5. If the content is cached there (cache hit) → served immediately
  6. If not (cache miss) → the edge location fetches it from S3, caches it, then serves it
  7. The next user in that region gets the cached copy instantly

Figure 8: CloudFront request flow — users always hit the nearest edge location first, not the origin

🔒 Origin Access Control (OAC) — Securing Your S3 Bucket

Here's where it gets really important — both for security and for the exam.

When you use CloudFront, you face a choice about how CloudFront should access your S3 bucket:

Option A: Use S3 Static Website Hosting URL as Origin

You can set CloudFront's origin to the S3 website endpoint URL (bucket.s3-website.amazonaws.com). But this requires the bucket to be fully public — which defeats the purpose of security.

❌ Don't do this in production: Using the website endpoint URL as origin requires the bucket to be open to the public internet. Anyone with the S3 URL can bypass CloudFront and access files directly.

Option B: Use S3 Bucket Name as Origin + Enable OAC ✅

The secure approach: set the origin to your S3 bucket name (not the website URL), and enable Origin Access Control (OAC).

Origin Access Control (OAC) is a CloudFront feature that grants CloudFront exclusive permission to access a private S3 bucket. The bucket remains completely private — only CloudFront can read the objects, not the public internet.

Figure 9: OAC security model — the S3 bucket is private; only YOUR specific CloudFront distribution can access it

How OAC Works Behind the Scenes

When you enable OAC during CloudFront distribution creation, CloudFront automatically generates a bucket policy for you. This policy is applied to your S3 bucket and contains:

  • Principal: Only the CloudFront service (cloudfront.amazonaws.com)
  • Action: s3:GetObject (read-only)
  • Resource: All objects in your bucket (arn:aws:s3:::bucket-name/*)
  • Condition: Only from YOUR AWS account AND your specific distribution ID

This means even if someone else creates a CloudFront distribution and points it at your bucket, they won't get access — OAC restricts access to only the specific CloudFront distribution in your specific AWS account.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "cloudfront.amazonaws.com"
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceAccount": "YOUR-ACCOUNT-ID",
          "AWS:SourceArn": "arn:aws:cloudfront::YOUR-ACCOUNT-ID:distribution/YOUR-DISTRIBUTION-ID"
        }
      }
    }
  ]
}
✅ Best Practice: Always use the S3 bucket name (not the static website URL) as your CloudFront origin, and always enable OAC. This keeps your bucket private while still serving content globally through CloudFront.

OAC vs. OAI (Legacy)

Older AWS documentation refers to OAI (Origin Access Identity) — the predecessor to OAC. AWS now recommends using OAC instead of OAI, as OAC offers better security and supports more S3 encryption options including SSE-KMS.

⚙️ Creating a CloudFront Distribution — Step by Step

Here's the complete walkthrough from the live session. These are the exact steps the instructor followed.

The Three Key Settings to Remember

Whenever you create a CloudFront distribution for an S3 static website, there are three things you always need to configure:

  1. Origin — your S3 bucket name (not the website URL)
  2. OAC — Origin Access Control (to keep the bucket private)
  3. Root Document — the default file to serve (e.g., index.html)
⚡ A student in class correctly recalled: "Origin, root document, and OAC" — that's the exam-ready answer for "What do you need when creating a CloudFront distribution for S3?"

Step 1: Open CloudFront Console

Search for "CloudFront" in the AWS Console. Open it. Click Create distribution.

📸 Screenshot: CloudFront console — click Create distribution to get started

Step 2: Choose a Plan

A new screen asks you to choose a pricing plan: Free, Pro, Business, or Premium. For learning and experiments, choose Free. Click Next.

💡 This plan selection page was recently added to CloudFront. Earlier versions did not have it. The Free plan is sufficient for personal projects and practice.

Step 3: Give the Distribution a Name

Enter a name for your distribution. This is just a label for you to identify it — it doesn't affect functionality. Click Next.

On this same page, you may see an option for "Domain name" — this is for Route 53 integration (custom domain). Skip it for now; the instructor mentioned it will be covered in the next session.

Step 4: Set the Origin (S3 Bucket Name)

This is the most important step. Under Origin type, select Amazon S3. Then browse and select your bucket name.

❌ Critical: Do NOT select the S3 website endpoint URL. Select only the bucket name. The console may show both — always choose the bucket name. As explained earlier, the website endpoint requires a public bucket.

📸 Screenshot: Origin selection — choose your S3 bucket name, NOT the website endpoint URL

Leave the Origin path empty (unless your content is inside a specific folder in the bucket).

Step 5: Enable Origin Access Control (OAC)

After selecting the S3 bucket as origin, the console shows a recommendation: "Allow private S3 bucket access to CloudFront." Click Enable.

This enables OAC — CloudFront will be able to talk to your private S3 bucket securely. After the distribution is created, CloudFront will automatically generate the bucket policy and display it for you to copy into your S3 bucket.

📸 Screenshot: Enable OAC — this is what keeps your S3 bucket private while CloudFront can still access it

Step 6: Skip Extra Security (WAF)

The next screen asks about Web Application Firewall (WAF) and DDoS protection. For now, skip this — extra security features cost more money. The instructor mentioned: "I'll tell you later what WAF and DDoS are. For now, don't add them." Click Next.

Step 7: Review and Create

Review your settings and click Create distribution. The distribution will take a few minutes to deploy globally (status will show "Deploying").

💡 While the distribution is deploying, go to your S3 bucket → Permissions → Bucket policy. You'll see that CloudFront has already added the OAC policy automatically! The bucket policy is now updated to allow only CloudFront from your specific account and distribution ID.

📸 Screenshot: Auto-generated OAC bucket policy — CloudFront automatically updated your S3 bucket policy after distribution creation

Step 8: Set the Default Root Object

This is the most commonly forgotten step! After creating the distribution:

  1. Open the distribution
  2. Go to the General tab
  3. Click Edit
  4. Scroll down to find Default root object
  5. Enter index.html
  6. Save changes

The default root object tells CloudFront which file to serve when a user visits the root URL of the distribution (e.g., https://d1234.cloudfront.net/). Without it, users get an access error instead of your homepage.

📸 Screenshot: Setting default root object to index.html — this is a separate step done after creating the distribution

Step 9: Verify It Works

Once the distribution status changes from "Deploying" to "Enabled," you'll see a domain name like d1234abcd.cloudfront.net.

Now test both URLs:

  • S3 website URL: http://static-67966.s3-website.ap-south-1.amazonaws.com → ❌ Access Denied (bucket is private now)
  • CloudFront URL: https://d1234abcd.cloudfront.net → ✅ Website loads fast!
✅ You've solved both problems: The S3 bucket is now private (security ✓) and users worldwide get the content from their nearest edge location (latency ✓).

🎓 Exam Tips & Common Traps

1. S3 Public Access — Two-Step Process

Exam questions often test whether you know BOTH steps to make a bucket public. Disabling Block Public Access alone is not enough — you must also add a bucket policy granting s3:GetObject to Principal: *.

2. OAC vs Website Endpoint

If a question asks how to use CloudFront with a private S3 bucket, the answer is OAC (Origin Access Control) — set the origin to the bucket name, not the website endpoint URL.

3. CloudFront Origin Types

CloudFront is not only for S3. CloudFront can have S3 buckets, Application Load Balancers, EC2 instances, and API Gateway as origin sources. Don't assume it's S3-only.

4. Edge Locations ≠ Availability Zones ≠ Regions

These three terms are frequently confused:

  • Region — A geographic area with multiple AZs (e.g., Mumbai, US-East)
  • Availability Zone (AZ) — A data center cluster within a region
  • Edge Location — A CloudFront mini data center for caching CDN content. Not a full region, not an AZ. Also called Point of Presence (PoP).

5. Static vs Dynamic

S3 can only host static websites. If the application needs server-side processing, a database, or user-specific content generation, S3 alone is not sufficient.

6. TTL and Cache Invalidation

If a question describes a scenario where users still see old content after an S3 update even though CloudFront is in front, the answer involves cache invalidation or waiting for the TTL to expire.

7. S3 Bucket Policy — Know the JSON Keys

Be able to identify the role of each field: Effect (Allow/Deny), Principal (who), Action (what operation), Resource (which S3 objects). A wildcard * in Principal means everyone; a specific service/ARN means restricted access.

💰 CloudFront Pricing — Key Facts

According to AWS documentation, CloudFront pricing is based on two main components:

1. Data Transfer Out: You are charged for the amount of data transferred from CloudFront edge locations to your users (per GB). The price varies by geographic region — data transferred to North America and Europe is cheaper than to other regions.

2. HTTP/HTTPS Requests: You are charged per 10,000 HTTP/HTTPS requests handled by CloudFront.

Free Tier: AWS CloudFront offers a free tier with 1 TB of data transfer out and 10 million HTTP/HTTPS requests per month — sufficient for most learning and small-scale projects.

📚 Source: AWS CloudFront Pricing Page

✅ Cost Saving Tip: Because CloudFront caches content at edge locations, the number of requests that reach your S3 origin is reduced. This means lower S3 data transfer costs — CloudFront can actually reduce your overall AWS bill despite adding its own charges, especially for high-traffic sites.

📝 Overall Summary

  • Static websites have pre-built HTML/CSS/JS files. Dynamic websites require backend logic and a running server.
  • S3 Static Website Hosting is the simplest, cheapest way to host a static site — no EC2, no Apache, no auto-scaling setup needed.
  • To host a static site on S3: upload files → enable static website hosting → set index document → disable Block Public Access → add bucket policy with s3:GetObject for all ("Principal": "*").
  • Problem with a public bucket: security risk (anyone can access S3 URL directly) and high latency for global users (bucket is in one region).
  • CDN (Content Delivery Network) is a globally distributed network of mini data centers (edge locations) that cache content near users to reduce latency.
  • Amazon CloudFront is AWS's CDN service. A CloudFront "distribution" is your CDN configuration.
  • OAC (Origin Access Control) lets CloudFront access a private S3 bucket. The bucket stays locked from the public; only your specific CloudFront distribution can read from it.
  • Three things needed when creating a CloudFront distribution: Origin (S3 bucket name), OAC (not website URL), and Default Root Object (index.html).
  • After enabling OAC: CloudFront auto-generates and applies the bucket policy — you don't write it manually.
  • Edge locations (also called Points of Presence/PoP) are the mini-servers that serve cached content. They are different from Regions and Availability Zones.
  • TTL (Time to Live) controls how long edge locations keep cached content before refreshing from the origin.

    📸 Screenshot: Set Default root object to index.html

  9. Once distribution status is Enabled, copy the Distribution domain name (e.g., d1234.cloudfront.net). Open it in a browser → website loads ✅. Also try the old S3 website URL → you should get 403 Access Denied ✅.

    📸 Screenshot: CloudFront URL works, direct S3 URL is blocked — mission accomplished!

🧹 Cleanup: Disable and delete the CloudFront distribution. Delete all S3 objects and the bucket. CloudFront distributions must be disabled before they can be deleted (may take ~15 minutes).

Project 3: Break It and Fix It — Debug Like an Engineer

🎯 Objective: Intentionally break a working S3 static website in three different ways, then diagnose and fix each one — building real debugging instincts

⏱️ Time: 30-40 minutes

💰 Cost: Free Tier

📋 Prerequisite: Project 1 completed — you have a working public S3 website

⚡ Why this project matters: Anyone can follow a tutorial. Engineers debug. This project forces you to understand why things break — not just how to set them up. Every break scenario here maps to a real mistake teams make in production.

Break Scenario 1 — Remove the Bucket Policy

  1. Start with your working S3 website from Project 1. Confirm it loads correctly. Note the URL.

    📸 Screenshot: Confirm the site is working before you break it — take note of the URL

  2. Go to S3 → Permissions → Bucket policy → Edit. Delete the entire policy JSON. Click Save changes (leave the editor empty).

    📸 Screenshot: Delete the bucket policy — leave the editor completely empty

  3. Refresh the website URL in the browser. What do you see? You should get a 403 Access Denied error. This is the same error students hit when they forget to add the policy during setup.

    📸 Screenshot: 403 error after deleting the bucket policy — Block Public Access alone is not enough

  4. Fix it: Re-add the public read policy (Effect Allow, Principal *, Action s3:GetObject, Resource bucket-ARN/*). Verify the website loads again.

Break Scenario 2 — Wrong Index Document Name

  1. Go to S3 → Properties → Static website hosting → Edit. Change the Index document from index.html to home.html (a file that does not exist). Save changes.

    📸 Screenshot: Set a wrong index document name — this is a common typo mistake in real deployments

  2. Visit the website URL. What do you see? A 404 Not Found or 403 error — because S3 is looking for home.html at the bucket root and it doesn't exist.

    📸 Screenshot: Error from wrong index document — S3 can't find the file it was told to serve

  3. Fix it: Change the Index document back to index.html. Verify. Then think: in a real project, what happens if a developer renames their main page and forgets to update this setting?

Break Scenario 3 — Files Uploaded Inside a Subfolder

  1. In your S3 bucket, create a new folder called site/. Move (re-upload) your index.html and all website files inside this site/ folder. Delete the files from the bucket root.

    📸 Screenshot: Files uploaded inside a subfolder — bucket root no longer has index.html directly

  2. Visit the website URL. What happens? You get a 404 — because static website hosting expects index.html at the bucket root, not inside a subfolder.

    📸 Screenshot: 404 because index.html is in a subfolder — S3 static hosting looks at the root level

  3. Fix it: Move all files back to the bucket root (re-upload them directly, not into a folder). Verify the site works again.

    📸 Screenshot: Files back at root — index.html visible directly in the bucket, not inside any folder

✅ What you built: You now have debugging instincts for the three most common S3 static website failures. When a colleague says "the site is broken," you know exactly where to look first.

🧹 Cleanup: Leave the working bucket in place — you'll use it in Project 4. Or delete all objects and the bucket to avoid charges.

Project 4: CloudFront with Public Bucket — Observe Caching Live

🎯 Objective: Put CloudFront in front of a still-public S3 bucket, then observe real cache hit and cache miss behavior, and see what happens when you update a file

⏱️ Time: 40-50 minutes (plus CloudFront deploy time ~5 min)

💰 Cost: Free Tier

📋 Prerequisite: A working public S3 static website (from Project 1)

⚡ Why this project matters: Most people create CloudFront and never actually observe how it caches. This project makes caching visible — you'll update a file and see the old version served from cache. That moment of confusion is exactly what engineers face in production.

  1. Confirm your public S3 website is working. Note the current content — for example, open index.html and remember the page title or a heading text. You'll change it later.

    📸 Screenshot: Note your current website content before adding CloudFront — you will update this later

  2. Go to CloudFront → Create distribution. This time, set the origin to the S3 static website endpoint URL (the .s3-website.region.amazonaws.com URL) — not the bucket name. Since the bucket is still public, this will work. Set Default Root Object to index.html. Do NOT enable OAC (the bucket is public). Create the distribution.

    📸 Screenshot: Using the S3 website endpoint URL as origin — only works with a public bucket

  3. Wait for the distribution status to change to Enabled. Copy the CloudFront domain name. Open it in your browser — the website should load. This is your first request: a cache miss — CloudFront fetched from S3 and cached it at the edge.

    📸 Screenshot: First load via CloudFront URL — this was a cache miss; CloudFront just cached the content

  4. Reload the page several times. Open browser DevTools (F12 → Network tab). Look at the response headers for the main HTML request. Find the X-Cache header — it should say Hit from cloudfront on subsequent loads. This is a cache hit.

    📸 Screenshot: DevTools Network tab — X-Cache: Hit from cloudfront confirms the edge location served cached content

  5. Now update your website. Open your local index.html, change the page heading to something clearly different (e.g., "UPDATED VERSION"). Re-upload it to S3, replacing the existing file.

    📸 Screenshot: Re-upload the updated index.html to S3 — the change is in S3 but CloudFront doesn't know yet

  6. Go back to your CloudFront URL and hard-refresh (Ctrl+Shift+R). What do you see? The old version — because CloudFront is still serving its cached copy. The S3 update has not propagated to the edge yet. This is the stale cache problem.

    📸 Screenshot: Stale cache — old content still showing via CloudFront even though S3 has the new version

  7. Now open the direct S3 website URL. You should see the updated version immediately — because the S3 URL bypasses CloudFront's cache entirely.

    📸 Screenshot: Direct S3 URL shows updated content — proof that S3 has the new file; CloudFront is just slow to catch up

  8. Wait for the TTL to expire (default is 86400 seconds / 24 hours — too long to wait). Instead, go to CloudFront → Your Distribution → Invalidations → Create invalidation. Enter /* to clear all cached files. Submit.

    📸 Screenshot: Create cache invalidation with /* — this forces all edge locations to fetch fresh content from S3

  9. Wait for the invalidation status to show Completed. Then reload the CloudFront URL — the updated content now appears. Cache cleared.

    📸 Screenshot: Updated content now showing via CloudFront after invalidation — edge locations fetched fresh content from S3

✅ What you learned: You now understand caching instead of just knowing it exists. You can explain cache hits, cache misses, TTL, and invalidation — with screenshots proving you've seen them in action.

🧹 Cleanup: Disable and delete the CloudFront distribution. Keep the S3 bucket for Project 5, or delete it to avoid charges.

Project 5: Cache Invalidation vs File Versioning — Two Strategies

🎯 Objective: Learn and compare the two professional strategies for deploying updates through CloudFront — cache invalidation and file versioning

⏱️ Time: 30-40 minutes

💰 Cost: Free Tier (note: CloudFront charges for invalidations beyond the free monthly allowance)

📋 Prerequisite: Project 2 completed (CloudFront + OAC setup) and Project 4 (you've seen stale cache)

⚡ Why this project matters: In production, how you handle updates is a design decision. Invalidation is simple but has limits and small costs. File versioning is what large-scale teams use — it makes caching work for you instead of against you.

Strategy A — Cache Invalidation

  1. Using your CloudFront + private S3 setup from Project 2, make a visible change to your website — update a CSS color, change a heading, anything clearly noticeable. Re-upload the changed file(s) to S3.

  2. Confirm the CloudFront URL still shows old content (stale cache). Open CloudFront → Your distribution → Invalidations → Create invalidation. Try two approaches:

    • Specific path: /index.html (only invalidates one file)
    • Wildcard: /* (invalidates everything)

    📸 Screenshot: Invalidation paths — specific file vs wildcard /* for all files

  3. After invalidation completes, confirm the updated content appears on the CloudFront URL.

    📸 Screenshot: Invalidation completed — updated content now loading via CloudFront URL

💡 Limitation of invalidation: AWS gives you 1,000 free invalidation paths per month. Beyond that, you pay per path. For large sites with hundreds of files, invalidating everything frequently can add up.

Strategy B — File Versioning (The Professional Way)

Instead of invalidating cached files, version them. The idea: when you update a CSS or JS file, you rename it with a version number (style.v2.css). Since it's a new file name, CloudFront has no cached copy — it fetches it immediately. Your HTML then references the new versioned filename.

  1. In your local project, rename your CSS file from style.css to style.v2.css. Update the <link> tag in index.html to reference style.v2.css.

    <!-- Old -->
<link rel="stylesheet" href="style.css">

<!-- New (versioned) -->
<link rel="stylesheet" href="style.v2.css">

  2. Upload both the new style.v2.css and the updated index.html to your S3 bucket. Do NOT delete style.css yet (existing cached pages may still reference it).

    📸 Screenshot: S3 bucket with versioned CSS files — both style.css and style.v2.css exist alongside the updated index.html

  3. Create an invalidation only for /index.html (not for the CSS — style.v2.css is new, so no cache exists for it). After the invalidation, reload the CloudFront URL.

    📸 Screenshot: DevTools showing index.html from CloudFront cache and style.v2.css fetched fresh — versioning means no invalidation needed for assets

✅ Best practice recommendation: Use long TTL + file versioning for CSS/JS/images (they never go stale because you version them). Use short TTL or invalidation for index.html (it's small and changes with every deployment).

🧹 Cleanup: Disable and delete the CloudFront distribution. Delete S3 objects and bucket.

Project 6: Measure Latency — S3 Direct vs CloudFront

🎯 Objective: Use browser DevTools to measure and compare actual load times between the direct S3 URL and the CloudFront URL — making the performance benefit of CDN visible and measurable

⏱️ Time: 20-30 minutes

💰 Cost: Free Tier

📋 Prerequisite: Working S3 + CloudFront setup (Project 2 or 4)

⚡ Why this project matters: You've heard "CloudFront reduces latency" many times. This project makes you measure it. When an interviewer asks "how do you know CloudFront helped?", you'll have a real answer with numbers.

  1. Open your browser. Press F12 to open DevTools. Go to the Network tab. Check the Disable cache checkbox (so browser cache doesn't interfere with measurements).

    📸 Screenshot: DevTools Network tab — check Disable cache before testing to get accurate timing

  2. Navigate to your direct S3 website URL. After the page loads, look at the bottom of the Network tab — note the total load time and the time for the first request (index.html). Record this number.

    📸 Screenshot: S3 URL load time — record this number; it represents the direct-to-origin round trip from your location

  3. Now navigate to your CloudFront URL (same website content). Note the total load time and the index.html request time. Compare with step 2.

    📸 Screenshot: CloudFront URL load time — compare with S3 direct time; CloudFront should be faster after first cache population

  4. Reload the CloudFront URL two more times. Check the X-Cache response header in the Network tab (click the index.html row → Headers tab). On subsequent loads it should show Hit from cloudfront — and the load time should drop further.

    📸 Screenshot: X-Cache header showing Hit from cloudfront — and a lower time compared to the first load or S3 direct

  5. Use the Network tab Waterfall view. Expand the index.html row timing breakdown. You'll see: DNS lookup, TCP connect, SSL, time to first byte (TTFB), and content download. Compare the TTFB (Time to First Byte) between S3 and CloudFront — this is the clearest signal of CDN impact.

    📸 Screenshot: Waterfall timing breakdown — TTFB (Time to First Byte) is the key metric showing CloudFront edge cache advantage

💡 Note: If your S3 bucket region is close to where you're testing from (e.g., you're in India and the bucket is in Mumbai), the difference may be small. The real-world difference becomes dramatic for users in distant regions. The key insight is the X-Cache: Hit from cloudfront header proving the edge is serving, not the origin.
✅ What you proved: CloudFront's benefit is measurable and visible in DevTools. You can now point to TTFB numbers and X-Cache headers as evidence — not just theory.
