🧠 What is Amazon Bedrock?

Before we build anything, let's understand what we're actually calling. Amazon Bedrock is AWS's fully managed service for accessing foundation models (FMs) — large AI models pre-trained on massive datasets that can generate text, images, code, and more.

Figure 2: Amazon Bedrock provides a single API to access multiple foundation models from different providers

Think of Bedrock as a marketplace of AI brains. You don't train the model yourself — AWS and its partners have already done that work. You just call the API with your question and get a prediction back.

How Bedrock Works Internally

A model in Bedrock is essentially a sophisticated web server. When your Python code sends it a request, the model doesn't "think" in the human sense — it predicts the most statistically likely next tokens (chunks of text) given everything you've sent. The response comes back as a JSON-formatted document, which your code then transforms into something readable.

According to AWS documentation, Amazon Bedrock provides a serverless API, meaning you don't manage any infrastructure to run the models themselves — you only pay per API call based on the number of tokens processed.
📚 Source: AWS Bedrock Docs

Models Available

Bedrock gives you access to models from multiple providers. In this session, we use Claude Sonnet 4.5 from Anthropic, accessed via a cross-region Inference Profile. The model ID used in the code is:

global.anthropic.claude-sonnet-4-5-20250929-v1:0

An Inference Profile is a Bedrock feature that routes your requests across multiple AWS regions for higher availability and throughput. For most purposes, you interact with it exactly like a regular model ID.

⚡ Not all Bedrock features are available in every AWS region. This exercise is designed to run in us-west-2 (US Oregon). If you experiment in another region, you may need to change the model ID and may encounter feature blockers.

Key Model Parameters

When calling Bedrock, you send a payload that includes several important parameters that control how the model responds:

ParameterWhat it ControlsValue Used
max_tokensMaximum length of the response500 (simple bot)
temperatureCreativity / randomness of output (0=deterministic, 1=creative)0.9
top_kNumber of top candidate tokens the model considers at each step250
top_pCumulative probability cutoff for token selection (alternative to top_k)Not used here

Todd briefly mentioned that top_k and top_p are both ways to control entropy — how diverse or focused the model's output is. Some models use one, some use both. These are parameters worth exploring as you build more sophisticated bots.

🔐 IAM Roles for Services (Not Just Users)

One of the most important concepts in this session: IAM is not only for human users logging into the AWS Console — it is also how AWS services get permission to talk to other AWS services.

Figure 3: IAM role flow — EC2 assumes the role, which carries the Bedrock permission policy, enabling it to invoke Bedrock APIs

The Hat Analogy

Todd used a memorable analogy: when you need to work in different contexts, you wear different hats. An EC2 instance that should be allowed to call Bedrock needs to put on the right hat — an IAM role that says "this service is permitted to interact with Bedrock."

Without the role, your Python code would get an AccessDeniedException when calling Bedrock, no matter how correct the code is. The permission has to exist at the infrastructure level before the code runs.

Why Not Just Embed API Keys?

You might wonder why we don't just put an AWS Access Key and Secret Key directly in the Python script. Hardcoding credentials in code is a serious security risk — they can be exposed in version control, logs, or if someone gains access to the instance. IAM roles solve this cleanly: the instance receives temporary, automatically rotating credentials via the EC2 Instance Metadata Service (IMDS), and Boto3 picks them up automatically.

✅ Best Practice: Always use IAM roles to grant EC2 instances access to AWS services. Never embed long-term access keys in your code or on the instance itself.

Principle of Least Privilege

In this demo, Todd used AmazonBedrockFullAccess — which is the widest possible permission for Bedrock. This is fine for a lab but not for production. In a real environment, you would narrow this to:

  • Only the specific Bedrock actions needed (e.g., bedrock:InvokeModel)
  • Only specific model ARNs, not a wildcard (*) resource
  • Perhaps limit by model size or cost tier to avoid unexpected large bills

Similarly, the security group allowing SSH from 0.0.0.0/0 (any IP) is fine for a lab. In production, lock SSH access to specific administrator IP ranges.

Instead of SSH with a PEM file, Todd uses EC2 Instance Connect — a browser-based terminal built into the AWS Console. EC2 Instance Connect works by generating a temporary SSH key pair that is valid for 60 seconds and injecting it into the instance. No key management required.

🔧 The Software Stack — What Gets Installed and Why

After connecting to the instance, several software packages need to be installed before any code runs. Todd walked through each one live, explaining the purpose rather than just copying and pasting blindly. Here is the full picture.

Figure 4: The software stack — each layer has a specific job in turning a user's browser request into a Bedrock API call

1. System Update

sudo yum update -y

This fetches the latest security patches and software updates for everything already on the Amazon Linux 2023 AMI. Even though the AMI is current at launch time, there's always a lag — running this ensures you have the latest patches. This is part of the shared responsibility model: AWS keeps the base AMI up to date until you launch it; after that, keeping it patched is your responsibility as the customer.

2. Apache httpd (Web Server)

sudo yum install -y httpd
sudo systemctl start httpd
sudo systemctl enable httpd

Apache is the web server — the software that listens on port 80 for incoming HTTP requests and serves back HTML pages and runs CGI scripts. In Unix/Linux parlance, it's a daemon — a background process that sits dormant until a request arrives, then springs into action.

Think of it like the hotel cleaning service: the service contract exists (enable), the cleaner is on duty (start), and they go room-to-room when called (daemon doing work). start gets it running now; enable makes it automatically restart after reboots.

3. Python 3

sudo yum install -y python3 python3-pip

Python is the language the bot is written in. Amazon Linux 2023 may have an older Python version; this installs the latest Python 3.x available in the package repo and pip3, the Python package manager needed for Boto3.

4. Boto3 — The AWS SDK

sudo pip3 install boto3

Boto3 is the AWS Software Development Kit (SDK) for Python. It is named after the boto, a pink freshwater dolphin native to the Amazon River — a clever nod to "AWS's Amazon." Boto3 provides Python functions that wrap AWS REST APIs, so you can call Bedrock, S3, DynamoDB, and other services without writing raw HTTP requests.

The "3" in Boto3 refers to compatibility with the current Python 3 ecosystem and its third-generation API structure. Without Boto3, your Python code would need to manually construct signed HTTP requests to AWS endpoints — dozens of lines of boilerplate just to authenticate one API call.

✅ Fun Fact: Boto (the dolphin) is an Amazonian animal — fitting for a library that helps you connect to Amazon Web Services. Next time you're asked in a trivia night, you'll know.

💻 The Code — HTML Front End & Python Back End

The bot consists of two files: an HTML page that presents the user interface, and a Python CGI script that handles the business logic. Together they are about 40 lines — deliberately minimal so the focus stays on understanding each part.

The HTML Front End (index.html)

The front end is a simple HTML form located at /var/www/html/index.html. It presents a text area and a submit button. When the user submits, the form POSTs to the Python script:

<!DOCTYPE html>
<html>
<head>
    <title>Bedrock Text Processing</title>
</head>
<body>
    <h1>Enter Text for Processing</h1>
    <form action="/cgi-bin/process_text.py" method="post">
        <textarea name="user_input" rows="10" cols="50"></textarea><br>
        <input type="submit" value="Process Text">
    </form>
</body>
</html>

Yes, it's plain and ugly. Todd acknowledged this with humor — one of his learners from a previous cohort rebuilt the same bot with a beautiful interface. The point is that the UI is completely separate from the AI logic. Once you understand the back end, beautifying the front end is an independent task.

The Python CGI Script (process_text.py)

The Python script lives at /var/www/cgi-bin/process_text.py. CGI (Common Gateway Interface) is a mechanism that lets a web server run an external program and return its output as the HTTP response. Apache invokes this script every time someone hits the form's submit button.

#!/usr/bin/env python3
import cgi
import cgitb; cgitb.enable()
import boto3
import json

print("Content-Type: text/html")
print()

form = cgi.FieldStorage()
user_input = form.getvalue('user_input')

if user_input:
    bedrock_client = boto3.client('bedrock-runtime', region_name='us-west-2')
    request_payload = {
        'anthropic_version': 'bedrock-2023-05-31',
        'max_tokens': 500,
        'temperature': 0.9,
        'top_k': 250,
        'messages': [
            {
                'role': 'user',
                'content': user_input
            }
        ]
    }
    response = bedrock_client.invoke_model(
            modelId='global.anthropic.claude-sonnet-4-5-20250929-v1:0',
        body=json.dumps(request_payload)
    )
    result = json.loads(response['body'].read())
    processed_text = "".join([output["text"] for output in result["content"]])
    print(f'<h2>Processed Text:</h2><p>{processed_text}</p><form action="/cgi-bin/process_text.py" method="post"><textarea name="user_input" rows="10" cols="50"></textarea><br><input type="submit" value="Process Text"></form>')
else:
    print("<h2>No input provided.</h2>")

File Permissions

sudo chmod +x /var/www/cgi-bin/process_text.py
sudo chmod 755 /var/www/cgi-bin
sudo systemctl restart httpd

Two permission steps are required. chmod +x makes the Python file executable — without this, Apache refuses to run it. chmod 755 on the directory gives Apache read and execute access to the cgi-bin folder. Finally, restarting Apache applies any configuration changes. Skipping any of these steps is a common source of "Internal Server Error" when testing.

❌ Common Mistake: Forgetting to restart Apache after changes. Always run sudo systemctl restart httpd after editing code files or changing permissions, or your changes won't take effect.

🚧 What the Simple Bot Can't Do (And How to Fix It)

After the demo, Todd asked the bot a follow-up question: "Who am I?" The bot had no idea, because it has none of the following capabilities. Understanding these gaps is the roadmap for what to build next.

Figure 5: Bot enhancement roadmap — each layer adds a new capability on top of the previous one

1. No Memory

Each time the user submits, the Python script runs fresh. It has no awareness of what was said before. The bot truly has amnesia between requests.

Fix — Chat History: Add a text file (e.g., pub.txt) that appends every exchange. Each new request reads the entire file and prepends it to the prompt. This gives the model context of the full conversation. Todd has implemented this in his enhanced bot, eventually hitting the context window limit around 800KB (approximately 120,000 words). Once near this limit, you need a summarization/archiving process to compress old history.

2. No Personality or Persona

The bot responds as a generic assistant with no defined character, name, or area of expertise.

Fix — System Instructions: Add a system prompt (a set of instructions the model reads before user messages) that defines who the bot is. For example: "You are an expert AWS support engineer who responds in a friendly but professional tone." Todd's personal bot has rich system instructions that include his preferences, name, and working style.

3. Outdated Knowledge (Training Data Cutoff)

Foundation models have a training cutoff date. When Todd told one of AWS's internal tools about Robert Duvall's death in February 2026, the bot didn't know — its training data ended in 2024. A model only knows what it was trained on; events after the training cutoff are invisible to it unless you provide that information in the prompt.

There are three main ways to address this:

  1. Wait for a new model version — providers retrain and release updated models periodically
  2. Fine-tuning / custom training — add domain-specific or new data to a base model's training
  3. Retrieval Augmented Generation (RAG) — keep the model as-is but retrieve fresh information at query time and inject it into the prompt

📚 RAG and Knowledge Bases — Grounding the Model

Retrieval Augmented Generation (RAG) is the technique Todd planned to cover in depth in the following session. Here's an introduction based on what was discussed.

Figure 6: RAG architecture — the retrieval step fetches relevant documents and adds them to the context before the model ever sees the user's question

The core idea: instead of retraining a model with new information (expensive and slow), you retrieve the relevant new information at query time and augment the prompt with it before the model generates (generates) a response. Hence: Retrieval Augmented Generation.

How RAG Works — Step by Step

  1. User submits a question
  2. A retrieval process takes the user's question and searches a curated knowledge store (e.g., an S3 bucket with PDFs, an internal database)
  3. The most relevant chunks of information are returned
  4. Those chunks are injected into the prompt alongside the user's question, chat history, and system instructions
  5. The model generates a response that is now "grounded" in current, accurate information

Amazon Bedrock Knowledge Bases

AWS provides a managed service for this — Amazon Bedrock Knowledge Bases — which handles the vector database, embedding, and retrieval pipeline for you. You provide the documents (in S3), Bedrock handles the rest.

The enhanced bot code shown by Todd uses a Bedrock Knowledge Base with the following configuration:

kb_response = bedrock_agent_client.retrieve(
    knowledgeBaseId=KNOWLEDGE_BASE_ID,
    retrievalQuery={ 'text': user_input },
    retrievalConfiguration={
        'vectorSearchConfiguration': { 'numberOfResults': 10 }
    }
)

The numberOfResults: 10 means the retrieval step finds and returns the 10 most semantically similar document chunks to the user's question. These are then appended to the prompt before calling Claude.

⚡ Why grounding matters: Without grounding, a model can "hallucinate" — confidently stating incorrect information. Todd encountered this when building the bot: the model was making up the correct JSON format for Bedrock API calls. Once the model had access to the actual AWS documentation via a knowledge base, it retrieved the correct format and linked to the source document.

Common Knowledge Base Sources

  • S3 buckets with PDF/text documentation
  • Web crawlers that continuously index public URLs
  • Internal wikis or SharePoint exports
  • CRM data exports for customer-facing bots

A Note on API Gateway Timeout

Todd originally built the enhanced bot using API Gateway as the front end instead of EC2 directly. He ran into a critical limitation: API Gateway has a hard, immutable timeout of 29 seconds — when the enhanced bot makes multiple sequential model invocations (text + image + KB retrieval), it can exceed this limit.

His solution was to switch to Lambda with a Function URL instead. This removes the 29-second constraint. The lesson: when building AI-powered applications, always check timeout limits of any intermediary services in your architecture.

📏 Context Window Management

As you add memory to a bot, you will eventually hit the model's context window limit — the maximum amount of text a model can process in a single request. Todd deliberately pushed his personal bot to this limit to understand what happens.

What Is the Context Window?

The context window is the total amount of text (measured in tokens) that a model can consider at once, including system instructions, chat history, retrieved knowledge, and the user's current question. Once you exceed this limit, you receive an error.

Todd hit errors around 800KB of history text (roughly 120,000 words). Note that token count and word count are not the same — tokens are sub-word chunks, so 120,000 words is approximately 150,000–200,000 tokens depending on vocabulary.

Strategies for Managing Context

  1. Simple truncation: Drop the oldest entries from the history when size exceeds a threshold
  2. Summarization: Periodically ask the model to summarize the conversation history, replace the full history with the summary, and archive the full version
  3. Persistent database: Store history in DynamoDB instead of a text file — easier to query, paginate, and manage at scale (this is what the production-grade version of Todd's tool uses)
  4. Sliding window: Keep only the last N exchanges in context, always dropping the oldest

✅ Todd's Simple Approach: A growing text file for history is the simplest possible memory mechanism. It works, it's transparent, and it's easy to debug. Start here. Move to DynamoDB when scale demands it.

🏗️ Architecture Evolution — From EC2 to Serverless

The simple bot runs on a single EC2 instance. Todd mentioned that a previous cohort was challenged to refactor the same code to run in a serverless environment. This is an important conceptual jump worth understanding.

Figure 8: EC2 vs Serverless architecture for the same GenAI bot — the Bedrock call is identical; what changes is where the Python code runs

EC2 Approach (What We Built)

  • Server runs 24/7 — you pay for uptime even when no one is chatting
  • Apache manages HTTP connections
  • Python script executes as a CGI process
  • Easy to debug — just SSH in and check files
  • Good for development, demos, and learning

Serverless Approach (The Challenge)

  • Lambda function runs only when invoked — pay per request
  • API Gateway or Function URL handles HTTP routing
  • Same Boto3 + Bedrock code, different execution context
  • IAM role now attached to Lambda, not EC2
  • No persistent file system — need S3 or DynamoDB for history
  • Be aware of the 29-second timeout on API Gateway

The underlying Bedrock call (the Boto3 invoke_model code) is identical in both architectures. What changes is the execution environment and how HTTP requests are routed to your code.

💡 Key Takeaways

  • Amazon Bedrock is a fully managed service that provides API access to foundation models — you don't manage any model infrastructure.
  • IAM roles give AWS services permission to call other AWS services — never embed long-term credentials in code.
  • Boto3 is the Python SDK for AWS, named after an Amazonian river dolphin. It handles authentication, request signing, and response parsing automatically.
  • A GenAI bot is just a web server + a Python script that calls an API. The "AI" part is a well-designed API call, not magic.
  • The simple bot has no memory, no personality, and no current knowledge. Each of these is one additional feature to build — independently, incrementally.
  • RAG (Retrieval Augmented Generation) is the preferred pattern for giving a model access to current or private information without retraining it.
  • API Gateway has a hard 29-second timeout — a critical constraint for multi-invocation AI workflows. Lambda Function URLs do not have this limit.
  • Always run in us-west-2 for this exercise to avoid regional feature gaps in Bedrock.
  • Start small. 40 lines of code today becomes 400 lines next week as you add features. That's not complexity — that's growth.

📝 Overall Summary

This session delivered a complete, working GenAI bot built live from scratch. The architecture is elegant in its simplicity: an EC2 instance running Apache serves an HTML form; a Python CGI script reads the form submission, calls Amazon Bedrock's Claude model via Boto3, and returns the response as HTML. An IAM role — not hardcoded credentials — gives EC2 permission to reach Bedrock.

The resulting bot deliberately has no memory, no personality, and no knowledge beyond its training data. Each of those limitations is a clearly understood, independently solvable problem. Memory means a text file (or DynamoDB). Personality means system instructions. Current knowledge means RAG with a Bedrock Knowledge Base. Todd demonstrated his own enhanced bot to show what the same codebase looks like after those layers are added: ~400 lines, multiple model invocations per request, image generation, and a rich conversational context.

The deeper lesson is architectural thinking: every sophisticated AI application is just a series of API calls orchestrated by glue code. The complexity lives in the design, not in any single line of Python.

Project 2: Add Chat Memory

🎯 Objective: Extend the bot to remember conversation history using a text file

⏱️ Time: 20–30 min (requires Project 1 complete)

💰 Cost: Minimal — same EC2 instance

  1. Connect to your running EC2 instance and open the Python script for editing:

    sudo vi /var/www/cgi-bin/process_text.py

  2. Add history file handling. Near the top of the if user_input: block, add:

    HISTORY_FILE = '/var/www/cgi-bin/history.txt'
from datetime import datetime

# Append user input to history
with open(HISTORY_FILE, 'a') as f:
    f.write(f'USER ({datetime.now()}): {user_input}\n')

# Read full history
with open(HISTORY_FILE, 'r') as f:
    history = f.read()

# Augment user input with history
augmented_input = f"{history}\nUSER: {user_input}"

  3. Change the content field in the messages payload from user_input to augmented_input.

  4. After getting the response, append it to the history file:

    with open(HISTORY_FILE, 'a') as f:
    f.write(f'ASSISTANT: {processed_text}\n')

  5. Create the history file and set permissions:

    sudo touch /var/www/cgi-bin/history.txt
sudo chmod 666 /var/www/cgi-bin/history.txt
sudo systemctl restart httpd

  6. Test by telling the bot your name in one message, then asking "Who am I?" in the next. It should now remember.

4. What is the difference between temperature, top_k, and top_p, and how would changing each one affect the bot's responses?

💡 Hint

Temperature controls overall randomness. top_k limits how many tokens the model considers at each step. top_p cuts off based on cumulative probability. Try temperature=0.1 vs temperature=0.9 with the same prompt.

6. What is RAG and why is it generally preferred over fine-tuning for keeping a model's knowledge current?

💡 Hint

Fine-tuning requires retraining the model — that's time-consuming and expensive. RAG adds information at query time without touching the model. Think about speed and cost of each approach.
