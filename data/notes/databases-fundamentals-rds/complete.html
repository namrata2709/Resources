📦 Data, Information & Metadata

What is Data?

Data is the starting point of everything in computing. Think of data as raw facts collected from the real world — facts that have no meaning on their own until they are organized and given context.

For example: Vikram, AWS Workshop, 500 rupees, Mysuru — these are all pieces of data. Seeing them in isolation, you can't tell a story. Is Vikram a student? A trainer? Did he spend 500 rupees or earn it? Where does Mysuru come in?

Data is raw facts taken from the real world that do not have meaning by themselves — they need context to become useful.

Figure 2: Data vs Information — raw facts become meaningful when organized

What is Information?

Information is what you get when data is processed, arranged, and given structure so that it starts making sense. It is meaningful data.

Take the same raw data from above and put it in a table:

NameWorkshopPriceCity
VikramAWS Kubernetes₹500Mysuru

Now the story is clear: Vikram attended an AWS Kubernetes workshop in Mysuru for ₹500. The data hasn't changed — but combining it with structure and labels turned it into information.

Information is data that has been processed or structured to give it meaning — it is meaningful data.

What is Metadata?

Metadata literally means "data about data." As your systems grow and you store more and more information, you need a way to describe and organize that stored data itself.

Think about a photo on your phone. The photo is the data. But your phone also stores: the file size, the date it was taken, who the photographer was, the GPS location, the file format (JPEG or PNG). That information about the photo is metadata.

Metadata is data that describes other data — it tells the system what the data is, where it is, and how to manage it.

Examples of metadata:

  • File size (e.g., 2.4 MB)
  • File type (e.g., .jpg, .csv, .mp4)
  • Date created / date modified
  • Who last modified it
  • Permissions (who can read or write)

💡 Why Metadata Matters: Without metadata, computers cannot understand how to organize, read, or manage files. A database without metadata is like a library where all the books have no titles, no authors, and no shelves — you can't find anything.

Figure 3: Metadata surrounds and describes data — the data's own instruction manual

🗂️ Data Classification

Now that you understand what data is, here's the next question: should all data be treated the same way? The answer is no — and that's exactly why data classification exists.

Imagine you have three things stored in a computer system: an Excel spreadsheet of student grades, a promotional banner image (PNG), and a JSON file from an API. These are all "data" — but can a computer store, organize, and search all three in the same way? Absolutely not.

Data classification is the grouping of data based on its structure and format so that a computer knows how to handle it properly.

There are three major families of data classification:

Figure 4: The three families of data classification — structured, semi-structured, and unstructured

Structured Data

Structured data is data arranged in fixed rows and columns — like an Excel spreadsheet or a database table. Every row follows the same format, every column has a defined type (name, age, city).

Structured data is organized in a fixed table format with rows and columns, making it fast to search, filter, and sort.

Examples: Excel spreadsheets, SQL database tables, CSV files

Why rows and columns? Because this structure allows:

  • Fast filtering: "Give me all students from Mysuru"
  • Fast sorting: "Sort by fee amount"
  • Fast searching: "Find student ID 247"

✅ Best for: Financial records, student data, product catalogs, order management — any data with consistent, predictable fields.

Unstructured Data

Unstructured data has no fixed format. You cannot put an image into rows and columns. You cannot put a video file into a spreadsheet. This type of data is free-form and requires different storage strategies.

Unstructured data has no fixed format and cannot be stored in rows and columns — it includes images, videos, audio files, and PDFs.

Examples: Images (PNG, JPG), Videos (MP4), Audio (MP3), PDF documents, Email bodies, Social media posts

💡 AWS Connection: Unstructured data is typically stored in object storage like Amazon S3 (covered in a previous session) — not in databases.

Semi-Structured Data

Semi-structured data sits between the two extremes. It has tags or labels to give it some structure, but it doesn't follow a fixed table format. The structure is flexible — different entries can have different fields.

Semi-structured data uses tags or key-value pairs for organization but does not follow a fixed table schema — examples include JSON and XML.

Classic example — a JSON document:

{
  "name": "Vikram",
  "workshop": "AWS Kubernetes",
  "city": "Mysuru",
  "price": 500,
  "hasDiscount": true
}

Notice: there's no fixed table, but there are labels (keys). Another JSON document might have completely different keys — that flexibility is the hallmark of semi-structured data.

Examples: JSON files, XML files, YAML files, HTML files, Email headers (not bodies)

Figure 5: Structured table (rigid, fixed columns) vs Semi-structured JSON (flexible, tagged)

🗄️ Databases & DBMS

What is a Database?

A database is an organized collection of data stored so it can be easily accessed, managed, and updated. Think of it as a highly intelligent filing cabinet — one that can find any file in milliseconds, prevent two people from overwriting each other's work, and keep your data safe even if the power goes out.

A database is an organized collection of structured data stored electronically for easy access, management, and retrieval.

Why not just use files? Great question. You could store everything in text files or Excel sheets. But as data grows, problems emerge:

  • 🔴 Speed: Searching 1 million rows in a text file is painfully slow
  • 🔴 Concurrency: Two users editing the same file simultaneously = corruption
  • 🔴 Integrity: Nothing stops you from entering "banana" in an age field
  • 🔴 Security: Files have no built-in access control per record
  • 🔴 Recovery: File crashes often mean permanent data loss

Databases solve all of these.

What is a DBMS?

A DBMS (Database Management System) is the software that manages the database. It is the layer between you and the raw data files. You never touch the database files directly — you talk to the DBMS, and it handles everything.

A DBMS (Database Management System) is software that creates, manages, and provides access to databases — it handles storage, retrieval, and security of data.

Figure 6: DBMS sits between your application and raw data files — the gatekeeper

Popular DBMS software you'll encounter:

How DBMS Works

When you install a DBMS like MySQL on a server, it runs as a service listening on a port. MySQL uses port 3306 by default. PostgreSQL uses port 5432. This is how client software connects to it — by specifying the server address and port number.

The workflow looks like this:

  1. You install MySQL on a server (your laptop, an EC2 instance, or use AWS RDS)
  2. MySQL starts and listens on port 3306
  3. You install a client tool (like MySQL Workbench or DBeaver) on your computer
  4. The client connects using: hostname + port + username + password
  5. Once connected, you can create databases, tables, and run queries

Figure 7: Client tool connects to DBMS using hostname, port number, and credentials

⚖️ Relational vs Non-Relational Databases

This is one of the most important distinctions in database technology — and it's tested heavily in AWS certifications.

Figure 8: Relational vs Non-Relational databases — structure, queries, and when to use each

Relational Databases (SQL)

Relational databases store data in tables with rows and columns. Tables are linked to each other using relationships (hence "relational"). You interact with them using SQL (Structured Query Language).

Relational databases store data in tables linked by relationships, enforce a fixed schema, and are queried using SQL.

Key characteristics:

  • Schema: The table structure (columns, data types) is defined upfront and is rigid
  • ACID compliance: Guarantees data integrity — Atomicity, Consistency, Isolation, Durability
  • Relationships: Tables connect via foreign keys (e.g., Orders table links to Customers table)
  • Best for: Financial systems, ERP, CRM, e-commerce where data integrity is critical

Example — a Students table linked to an Enrollments table:

-- Students Table
ID | Name   | City
1  | Vikram | Mysuru
2  | Priya  | Bangalore

-- Enrollments Table
ID | StudentID | Workshop          | Price
1  | 1         | AWS Kubernetes    | 500
2  | 2         | DevOps Basics     | 700

The StudentID in Enrollments links back to the ID in Students — that's a relationship.

Non-Relational Databases (NoSQL)

NoSQL databases do not use fixed table schemas or SQL. They are designed for flexibility, speed, and massive scale. The data can be stored as documents (JSON), key-value pairs, graphs, or columns.

Non-relational (NoSQL) databases have a flexible schema and are optimized for speed and scale — they do not use SQL or fixed table structures.

Key characteristics:

  • Schema-less: Each record can have different fields — no rigid structure
  • Horizontal scaling: Easily distribute across many servers
  • High speed: Optimized for specific access patterns (get by key, etc.)
  • Best for: Social media feeds, real-time apps, IoT, gaming leaderboards

Quick Comparison

📝 SQL Basics

SQL (Structured Query Language) is the language you use to talk to relational databases. Think of it as the "English" that databases understand. Whether you use MySQL, PostgreSQL, or Oracle — SQL is the universal language.

SQL (Structured Query Language) is the standard language for interacting with relational databases — used to create, read, update, and delete data.

SQL Command Categories

SQL commands are grouped into categories based on what they do:

Figure 9: SQL command categories — DDL, DML, DCL, TCL

CategoryFull NameCommandsPurpose
DDLData Definition LanguageCREATE, ALTER, DROP, TRUNCATEDefine database structure (tables, columns)
DMLData Manipulation LanguageSELECT, INSERT, UPDATE, DELETEWork with the data inside tables
DCLData Control LanguageGRANT, REVOKEControl who can access what
TCLTransaction Control LanguageCOMMIT, ROLLBACK, SAVEPOINTManage transactions and data integrity

Basic SQL Examples

Creating a table (DDL):

CREATE TABLE students (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100),
    city VARCHAR(50),
    fee DECIMAL(10,2)
);

Inserting data (DML):

INSERT INTO students (name, city, fee)
VALUES ('Vikram', 'Mysuru', 500.00);

Querying data (DML - SELECT):

-- Get all students
SELECT * FROM students;

-- Filter by city
SELECT name, fee FROM students WHERE city = 'Mysuru';

-- Sort by fee
SELECT * FROM students ORDER BY fee DESC;

Updating data (DML):

UPDATE students SET fee = 600.00 WHERE name = 'Vikram';

Deleting data (DML):

DELETE FROM students WHERE id = 1;

Database Indexes

An index is a data structure that speeds up searches on a database table. Think of it like the index at the back of a book — instead of reading every page to find "EC2", you go straight to the index, which tells you exactly which pages to look at.

A database index is a data structure that speeds up SELECT queries by allowing the DBMS to find rows without scanning the entire table.

Without an index: the database scans every row (full table scan) — slow on large tables.
With an index on a column: the database jumps directly to matching rows — much faster.

💡 Trade-off: Indexes speed up reads but slow down writes (INSERT/UPDATE/DELETE), because the index must also be updated. Add indexes on columns you search or join on frequently.

-- Create an index on the city column
CREATE INDEX idx_city ON students(city);

-- Now this query is much faster:
SELECT * FROM students WHERE city = 'Mysuru';

☁️ AWS RDS — Relational Database Service

The Problem RDS Solves

Imagine you need a MySQL database for your web application. Without AWS, here is what you'd have to do yourself:

  1. Buy or rent a server
  2. Install an operating system
  3. Install MySQL software
  4. Configure MySQL (ports, memory, character sets)
  5. Set up login credentials
  6. Create the database and tables
  7. Configure automated backups
  8. Set up monitoring and alerting
  9. Handle software patching and upgrades
  10. Plan for disaster recovery
  11. Scale when traffic grows

That's a full-time job just to run a database. AWS RDS takes all of that off your plate.

Amazon RDS (Relational Database Service) is a fully managed relational database service — AWS handles provisioning, patching, backups, and high availability automatically.

Figure 10: Self-managed database vs AWS RDS — what AWS takes off your hands

Supported Database Engines

RDS is not a database software itself — it is a managed platform that runs your choice of popular DBMS software. You pick the engine; AWS runs and maintains it.

AWS RDS supports six database engines: MySQL, PostgreSQL, MariaDB, Oracle, Microsoft SQL Server, and Amazon Aurora.

EngineBest For
MySQLWeb apps, most common open-source DB
PostgreSQLComplex queries, advanced features, GIS
MariaDBMySQL-compatible, open-source fork
OracleEnterprise, legacy enterprise apps
Microsoft SQL ServerWindows/.NET applications
Amazon AuroraAWS-native, high-performance (covered separately)

How RDS Works — Endpoints & Connections

When you create an RDS instance, AWS gives you an endpoint — a URL that acts as the address of your database. This is the key concept for connecting applications to RDS.

AWS RDS provides an endpoint URL and port number to connect your application or client tool to the managed database instance.

The endpoint looks like:

mydb.cxyzabc123.us-east-1.rds.amazonaws.com

To connect using a client tool (like MySQL Workbench):

  1. Open MySQL Workbench
  2. Create a new connection
  3. Enter the RDS endpoint as the hostname
  4. Enter port 3306 (MySQL) or 5432 (PostgreSQL)
  5. Enter the username and password you set when creating RDS
  6. Click Connect — you're now managing your cloud database from your laptop

Figure 11: RDS connection flow — both your laptop and your application connect via the endpoint URL

Your application (running on EC2 or Lambda) also uses the same endpoint. In your application's database configuration file, instead of pointing to localhost (local MySQL), you point to the RDS endpoint URL. That's the only change needed to migrate from local to cloud database.

Key RDS Features

  • Automated Backups: Daily snapshots retained for up to 35 days
  • Multi-AZ Deployment: Standby replica in another Availability Zone for automatic failover
  • Read Replicas: Up to 5 read replicas per instance for read scaling (covered in next section)
  • Storage Auto Scaling: Automatically increases storage when running low
  • Encryption: At rest (AES-256) and in transit (SSL/TLS)
  • IAM Integration: Database authentication using AWS IAM roles
  • Parameter Groups: Customize DBMS settings without SSH access

💡 According to AWS documentation, RDS automates time-consuming administration tasks such as hardware provisioning, database setup, patching, and backups, so you can focus on your applications and business.
📚 Source: AWS RDS User Guide

RDS Security

RDS does not live on the open internet by default. It lives inside your VPC (Virtual Private Cloud — covered in a previous session). You control who can reach it using Security Groups.

  • Place RDS in a private subnet — no direct internet access
  • Use Security Groups to allow only your application's EC2 instances to connect on port 3306
  • Enable encryption at rest using AWS KMS keys
  • Use SSL/TLS for all connections in transit
  • Enable IAM database authentication instead of password-only

❌ Common Mistake: Never place your RDS instance in a public subnet or allow 0.0.0.0/0 (all IP addresses) in its Security Group inbound rules. Your database should never be directly accessible from the internet.

RDS Pricing Model

RDS pricing has several components:

  • Instance hours: Charged per hour based on instance class (db.t3.micro, db.r5.large, etc.)
  • Storage: Per GB-month (General Purpose SSD, Provisioned IOPS, or Magnetic)
  • I/O requests: For Magnetic storage only
  • Backup storage: Free up to 100% of your provisioned storage size
  • Data transfer: Outbound data transfer charges apply

✅ Free Tier: AWS Free Tier includes 750 hours/month of db.t2.micro or db.t3.micro Single-AZ RDS instance, 20 GB of General Purpose storage, and 20 GB of backup storage for 12 months.

📖 Read Replicas

Imagine your application becomes wildly popular. Your database is getting thousands of read queries every second — user profiles, product listings, search results. Your single RDS instance starts struggling. What do you do?

The answer is Read Replicas — copies of your database that can handle read traffic so your main (primary) database can breathe.

A Read Replica is a read-only copy of an RDS database that receives asynchronous replication from the primary instance, used to offload read traffic and improve performance.

Figure 12: Read Replicas offload SELECT queries from the primary — writes still go to primary only

Key Facts About Read Replicas

  • Read Replicas handle SELECT (read) queries only — writes always go to the primary
  • Replication is asynchronous — there is a small lag between primary and replica data
  • RDS supports up to 5 read replicas per primary instance
  • Read Replicas can be in the same region, different region (cross-region), or same AZ
  • Each Read Replica has its own endpoint URL — your app must be coded to send reads to replicas
  • Read Replicas can be promoted to standalone databases for disaster recovery

Multi-AZ vs Read Replicas — Know the Difference

This is a very common exam trap. These two features sound similar but serve completely different purposes.

Multi-AZ is for high availability and failover — the standby is not used for reads. Read Replicas are for performance scaling — the replicas actively serve read traffic.

FeatureMulti-AZRead Replica
PurposeHigh Availability (HA)Read Performance Scaling
Standby UsageStandby is idle — only activates on failoverReplica actively serves read traffic
ReplicationSynchronousAsynchronous
FailoverAutomaticManual promotion required
Same endpoint?Yes — endpoint doesn't change on failoverNo — each replica has its own endpoint

🌟 Amazon Aurora

Amazon Aurora is AWS's own DBMS — built from the ground up at Amazon, designed specifically for the cloud. It's not a wrapper around MySQL or PostgreSQL — it's a completely reimagined database engine that happens to be compatible with MySQL and PostgreSQL syntax.

Amazon Aurora is a cloud-native relational database engine developed by AWS, available with MySQL-compatible and PostgreSQL-compatible editions.

Two Compatibility Modes

Aurora comes in two flavors:

  • Aurora MySQL-Compatible: Drop-in replacement for MySQL — your MySQL application can connect to Aurora MySQL with minimal changes
  • Aurora PostgreSQL-Compatible: Drop-in replacement for PostgreSQL

The key insight: Aurora is not MySQL or PostgreSQL. It is Aurora — but it speaks MySQL's language and PostgreSQL's language, so your existing apps work without rewriting SQL code.

Aurora Performance

Aurora delivers up to 5x the performance of MySQL and up to 3x the performance of PostgreSQL on the same hardware, at a lower cost.

How? Aurora's storage layer is completely redesigned:

  • Data is replicated 6 times across 3 Availability Zones automatically
  • Reads can happen from any of the 6 storage copies — not bottlenecked by a single disk
  • Storage grows automatically in 10 GB increments up to 128 TB
  • Aurora has up to 15 read replicas (vs 5 for standard RDS)

Figure 13: Aurora's shared distributed storage spans 3 AZs with 6 copies — readers access the same storage as the writer

Aurora vs Standard RDS

FeatureStandard RDSAmazon Aurora
Read ReplicasUp to 5Up to 15
StorageUp to 64 TB (gp2/io1)Up to 128 TB (auto-grows)
ReplicationSingle AZ or Multi-AZ6 copies across 3 AZs always
Failover~60-120 seconds (Multi-AZ)~30 seconds (faster)
CostLowerHigher (~20% more than RDS MySQL)
CompatibilityNative engineMySQL or PostgreSQL compatible

✅ When to Choose Aurora: High-traffic production applications, when you need 15 read replicas, need near-zero downtime failover, or need enterprise-level performance at a lower cost than Oracle or commercial databases.

Aurora Serverless

Aurora also offers a Serverless mode where the database automatically starts, scales, and shuts down based on actual usage. You don't provision a fixed instance size — you pay only for the database capacity used per second.

Aurora Serverless automatically starts, scales, and stops based on application demand — ideal for infrequent, intermittent, or unpredictable workloads.

💡 According to AWS documentation, Aurora Serverless v2 scales instantly to hundreds of thousands of transactions in a fraction of a second, making it ideal for variable workloads.
📚 Source: AWS Aurora Serverless v2 Docs

🏭 Amazon Redshift — Data Warehouse

So far, we've been talking about databases for operational workloads — your application reads and writes data in real time (user logins, orders, inventory). This is called OLTP (Online Transaction Processing).

But imagine the CEO wants to know: "What were our total sales by region for the last 5 years, broken down by product category and customer age group?" Running that kind of massive analytical query on your live application database would:

  • Slow down your application for all users
  • Take hours to complete on row-based storage
  • Compete for resources with thousands of active users

This is where Amazon Redshift — a data warehouse — comes in.

Amazon Redshift is a fully managed data warehouse service optimized for analytical queries (OLAP) across petabytes of data from multiple sources.

Figure 14: Redshift as a data warehouse — aggregates data from multiple sources for analytics

OLTP vs OLAP

OLTP (Online Transaction Processing) handles day-to-day operations with many small fast transactions — this is what RDS and Aurora are for.

OLAP (Online Analytical Processing) handles complex analytical queries across large historical datasets — this is what Redshift is designed for.

FeatureOLTP (RDS/Aurora)OLAP (Redshift)
PurposeDay-to-day operationsBusiness intelligence, analytics
Query TypeSimple, fast (ms)Complex, slow (seconds to minutes)
Data VolumeGB to TBTB to PB
UsersMany concurrent (app users)Few analysts and BI tools
Data AgeCurrent, live dataHistorical data (months/years)

Redshift Key Features

  • Columnar Storage: Stores data by column, not row — analytical queries that need only certain columns are dramatically faster
  • Massively Parallel Processing (MPP): Queries are distributed across many nodes simultaneously
  • Redshift Spectrum: Query data directly in S3 without loading it into Redshift
  • Data sharing: Share live data across Redshift clusters without copying
  • Integration: Works with S3, Glue, QuickSight, Tableau, Power BI

💡 According to AWS documentation, Amazon Redshift uses columnar data storage, data compression, and zone maps to reduce I/O and the amount of data required to perform queries.
📚 Source: Amazon Redshift Database Developer Guide

⚡ Amazon ElastiCache

Every time a user loads your website's homepage, your application runs the same database queries: get featured products, get top categories, get user recommendations. These queries hit your RDS database hundreds of times per second, returning the same data over and over.

What if you could save those query results in super-fast memory and serve them instantly — without touching the database at all? That's what ElastiCache does.

Amazon ElastiCache is a fully managed in-memory caching service that stores frequently accessed data in RAM for sub-millisecond response times, reducing database load.

Figure 15: Cache hit vs cache miss — ElastiCache serves from memory; RDS is only queried on cache miss

Redis vs Memcached — Two Engines

ElastiCache supports two in-memory engines:

ElastiCache offers two engines: Redis (feature-rich, supports persistence, pub/sub, and data structures) and Memcached (simple, fast, multi-threaded key-value cache).

Data StructuresStrings, lists, sets, hashes, sorted setsSimple strings only
Persistence✅ Yes (snapshots, AOF)❌ No — data lost on restart
Replication✅ Yes (Multi-AZ, read replicas)❌ No
Pub/Sub Messaging✅ Yes❌ No
Multi-threadingSingle-threaded (mostly)Multi-threaded
Use CaseSessions, leaderboards, real-time analytics, queuesSimple caching, horizontally scalable cache

Sticky Sessions with Redis

One very important use case that was covered in the session: sticky sessions.

When a user logs into your web application, a session is created (storing things like: "this user is logged in as Vikram, shopping cart has 3 items"). If your app runs on multiple EC2 instances behind a load balancer, which instance stores this session? If the load balancer sends the user to a different EC2 instance next time, that instance has no session — the user gets logged out.

ElastiCache Redis is used for centralized session storage, allowing any EC2 instance to read the user's session — solving the sticky sessions problem in load-balanced architectures.

Figure 16: Centralized session storage in ElastiCache — all EC2 instances share the same session store

ElastiCache Use Cases

  • Database query caching: Cache results of expensive DB queries
  • Session management: Centralized user session storage across multiple servers
  • Leaderboards: Redis sorted sets for real-time gaming rankings
  • Rate limiting: Count API calls per user per second
  • Pub/Sub messaging: Real-time notifications and chat
  • Real-time analytics: Fast counters and aggregations

✅ Exam Tip: If a question asks about improving database performance without changing the database → think ElastiCache. If it asks about session management across multiple EC2 instances → think ElastiCache Redis.

🚀 Amazon DynamoDB — Introduction

DynamoDB is AWS's fully managed NoSQL database — the go-to option when you need massive scale, low latency, and don't need the structure of a relational database.

Amazon DynamoDB is a fully managed serverless NoSQL key-value and document database that delivers single-digit millisecond performance at any scale.

Key DynamoDB Concepts

  • Tables: DynamoDB's equivalent of a database table (but schema-free)
  • Items: Individual records (like rows) — but each item can have different attributes
  • Attributes: Data fields (like columns) — but not fixed; each item can have unique attributes
  • Primary Key: Every item must have a unique primary key (Partition Key, or Partition Key + Sort Key)

Figure 17: DynamoDB items — each item can have different attributes, unlike rigid SQL tables

📝 Overall Summary

  • Data vs Information: Data is raw facts with no meaning; Information is processed, structured data with meaning. Metadata is data that describes other data.
  • Data Classification: Three families — Structured (tables/rows/columns), Unstructured (images/video/audio), Semi-structured (JSON/XML with tags but flexible schema).
  • Database & DBMS: A database is an organized data collection; DBMS is the software layer that manages it. MySQL uses port 3306, PostgreSQL uses 5432.
  • Relational vs NoSQL: Relational = fixed schema, SQL, ACID, best for complex relationships. NoSQL = flexible schema, horizontal scaling, best for speed and scale.
  • SQL Categories: DDL (structure), DML (data), DCL (permissions), TCL (transactions). Indexes speed up reads but slow down writes.
  • AWS RDS: Fully managed relational database — AWS handles patching, backups, HA. Supports MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Aurora. Connect via endpoint URL + port.
  • Read Replicas: Read-only async copies for scaling reads (up to 5 for RDS, up to 15 for Aurora). Different from Multi-AZ which is for failover/HA.
  • Multi-AZ vs Read Replicas: Multi-AZ = synchronous, idle standby, high availability. Read Replicas = asynchronous, active, read scaling.
  • Amazon Aurora: AWS-native DBMS, 5x faster than MySQL, 3x faster than PostgreSQL. 6 copies across 3 AZs, auto-grows to 128 TB, 15 read replicas.
  • Amazon Redshift: Data warehouse for OLAP — analytical queries on historical data from multiple sources. Columnar storage, MPP architecture.
  • Amazon ElastiCache: In-memory caching service. Redis = feature-rich, persistent, pub/sub, session storage. Memcached = simple, fast, multi-threaded.
  • DynamoDB: Serverless NoSQL, single-digit millisecond latency, schema-free, virtually unlimited scale. Full coverage in next session.

Project 1: Create & Connect to an RDS MySQL Instance

🎯 Objective: Launch a MySQL RDS instance, connect to it using MySQL Workbench, and run real CRUD operations — the foundation every backend engineer needs.

⏱️ Time: 30-45 minutes

💰 Cost: Free Tier eligible (db.t3.micro, 20GB storage)

💰 Cost Note: RDS instances incur hourly charges even when idle. A db.t3.micro runs at approximately $0.017/hour after Free Tier expires. Always stop or delete your instance when done.

  1. Sign in to the AWS Management Console and navigate to RDS under the Database section.

    Figure P1-1: 📸 RDS Console — click Create database to start

  2. Click Create database. Select Standard create and choose MySQL as the engine type.

    Figure P1-2: 📸 Select Standard create and MySQL engine

  3. Under Templates, select Free tier. This automatically sets the instance class to db.t3.micro.

  4. Under Settings, fill in: DB instance identifier (e.g., mydb-demo), Master username (admin), and a Master password. Save this password — you will need it.

    Figure P1-3: 📸 Settings section — note the instance name and credentials you set

  5. Under Connectivity, set Public access to Yes (demo only). Select your VPC and create a new Security Group.

  6. Click Create database. The instance takes 3-5 minutes to become available.

    Figure P1-4: 📸 RDS instance showing Creating status — wait for Available

  7. Once status is Available, click the instance name → Connectivity & security tab → copy the Endpoint URL.

    Figure P1-5: 📸 Copy the Endpoint URL — this is your database address

  8. Open MySQL Workbench. Click + to create a new connection. Enter: Hostname = RDS endpoint, Port = 3306, Username = admin. Click Test Connection.

    Figure P1-6: 📸 MySQL Workbench connection setup with RDS endpoint as hostname

  9. Once connected, run full CRUD operations:

    -- CREATE: Set up database and table
CREATE DATABASE workshop_db;
USE workshop_db;

CREATE TABLE students (
    id INT PRIMARY KEY AUTO_INCREMENT,
    name VARCHAR(100),
    city VARCHAR(50),
    workshop VARCHAR(100),
    fee DECIMAL(10,2)
);

-- INSERT: Add records
INSERT INTO students (name, city, workshop, fee) VALUES
('Vikram', 'Mysuru', 'AWS Fundamentals', 500.00),
('Priya', 'Bangalore', 'DevOps Basics', 700.00),
('Rahul', 'Chennai', 'Kubernetes', 800.00);

-- READ: Query the data
SELECT * FROM students;
SELECT name, fee FROM students WHERE city = 'Mysuru';
SELECT * FROM students ORDER BY fee DESC;

-- UPDATE: Modify a record
UPDATE students SET fee = 600.00 WHERE name = 'Vikram';

-- DELETE: Remove a record
DELETE FROM students WHERE id = 3;

-- Verify final state
SELECT * FROM students;

    Figure P1-7: 📸 Query result showing student rows — CRUD operations confirmed

  10. Cleanup: RDS Console → select instance → Actions → Delete. Uncheck "Create final snapshot" → confirm. This stops all charges.

Project 2: DynamoDB CRUD API — Stop Treating NoSQL Like SQL

🎯 Objective: Build a Node.js API that stores job application records in DynamoDB. You'll design access patterns (not just schemas) — the key mental shift when moving to NoSQL.

⏱️ Time: 45-60 minutes

💰 Cost: Free Tier — DynamoDB is free for first 25 GB and 200M requests/month

⚡ Why this matters: DynamoDB doesn't have "columns". It has access patterns. You design the table around how you'll query it, not how the data looks. This is the most important NoSQL mindset shift.

  1. Navigate to DynamoDB in the AWS Console. Click Create table.

    Figure P2-1: 📸 DynamoDB Create table — Partition Key: userId, Sort Key: timestamp

  2. Configure the table:
    Table name: job-applications
    Partition Key: userId (String)
    Sort Key: timestamp (String)
    Settings: Leave as default (On-demand capacity). Click Create table.

  3. Once the table is Active, click Explore table items → Create item. Add your first item manually to understand the schema-free structure:

    Figure P2-2: 📸 DynamoDB item — notice there is no fixed schema; each item can have any attributes

    {
  "userId": "user-001",
  "timestamp": "2025-12-04T10:00:00Z",
  "applicantName": "Vikram",
  "jobTitle": "AWS Cloud Engineer",
  "status": "applied",
  "resumeUrl": "s3://my-bucket/resumes/vikram.pdf"
}

  4. Now build the API. On your laptop, create a project folder and install dependencies:

    mkdir job-app-api && cd job-app-api
npm init -y
npm install express @aws-sdk/client-dynamodb @aws-sdk/lib-dynamodb

  5. Create app.js with full CRUD endpoints:

    const express = require('express');
const { DynamoDBClient } = require('@aws-sdk/client-dynamodb');
const { DynamoDBDocumentClient, PutCommand,
        GetCommand, QueryCommand, DeleteCommand,
        UpdateCommand } = require('@aws-sdk/lib-dynamodb');

const app = express();
app.use(express.json());

const client = new DynamoDBClient({ region: 'us-east-1' });
const docClient = DynamoDBDocumentClient.from(client);
const TABLE = 'job-applications';

// CREATE — POST /applications
app.post('/applications', async (req, res) => {
  const { userId, applicantName, jobTitle } = req.body;
  const item = {
    userId,
    timestamp: new Date().toISOString(),
    applicantName,
    jobTitle,
    status: 'applied'
  };
  await docClient.send(new PutCommand({ TableName: TABLE, Item: item }));
  res.json({ message: 'Application saved', item });
});

// READ — GET /applications/:userId
app.get('/applications/:userId', async (req, res) => {
  const result = await docClient.send(new QueryCommand({
    TableName: TABLE,
    KeyConditionExpression: 'userId = :uid',
    ExpressionAttributeValues: { ':uid': req.params.userId }
  }));
  res.json(result.Items);
});

// UPDATE — PATCH /applications/:userId/:timestamp
app.patch('/applications/:userId/:timestamp', async (req, res) => {
  const { status } = req.body;
  await docClient.send(new UpdateCommand({
    TableName: TABLE,
    Key: { userId: req.params.userId, timestamp: req.params.timestamp },
    UpdateExpression: 'SET #s = :status',
    ExpressionAttributeNames: { '#s': 'status' },
    ExpressionAttributeValues: { ':status': status }
  }));
  res.json({ message: 'Status updated' });
});

// DELETE — DELETE /applications/:userId/:timestamp
app.delete('/applications/:userId/:timestamp', async (req, res) => {
  await docClient.send(new DeleteCommand({
    TableName: TABLE,
    Key: { userId: req.params.userId, timestamp: req.params.timestamp }
  }));
  res.json({ message: 'Application deleted' });
});

app.listen(3000, () => console.log('API running on port 3000'));

  6. Configure AWS credentials on your laptop (aws configure) then run the API:

    node app.js

  7. Test all endpoints using curl or Postman:

    # Create a new application
curl -X POST http://localhost:3000/applications \
  -H "Content-Type: application/json" \
  -d '{"userId":"user-001","applicantName":"Vikram","jobTitle":"AWS Engineer"}'

# Read all applications for a user
curl http://localhost:3000/applications/user-001

# Update status
curl -X PATCH "http://localhost:3000/applications/user-001/2025-12-04T10:00:00Z" \
  -H "Content-Type: application/json" \
  -d '{"status":"interview_scheduled"}'

# Delete an application
curl -X DELETE "http://localhost:3000/applications/user-001/2025-12-04T10:00:00Z"

    Figure P2-3: 📸 API returning DynamoDB items — full CRUD working end-to-end

  8. Verify in the DynamoDB Console: Explore table items → confirm your items exist with updated status.

    Figure P2-4: 📸 DynamoDB table items view — API writes confirmed in the console

✅ What you've learned: DynamoDB access patterns (Query by Partition Key), the difference between SQL SELECT and DynamoDB Query, and how to build a full CRUD API against a NoSQL database.

Project 3: Event-Driven Resume Upload System (S3 + Lambda)

🎯 Objective: Build a real async pipeline — user uploads a resume to S3, S3 automatically triggers a Lambda function, Lambda renames the file and saves metadata to DynamoDB. No polling. No manual triggers. Pure event-driven architecture.

⏱️ Time: 45-60 minutes

💰 Cost: Free Tier — Lambda (1M free requests/month), S3 (5GB free)

⚡ Why this matters: This is real async architecture — the kind used in production resume parsers, image processors, and document pipelines. Events drive the system, not polling loops.

Figure P3-0: 📸 Event-driven flow — S3 event triggers Lambda which writes to DynamoDB automatically

  1. Create an S3 bucket for resumes. Navigate to S3 → Create bucket. Name it job-app-resumes-[your-account-id] (must be globally unique). Keep all defaults. Click Create bucket.

    Figure P3-1: 📸 S3 bucket created — this will receive resume uploads

  2. Create a Lambda function. Navigate to Lambda → Create function. Choose Author from scratch. Settings:
    Function name: process-resume-upload
    Runtime: Node.js 20.x
    Execution role: Create a new role with basic Lambda permissions.

    Figure P3-2: 📸 Lambda Create function — Author from scratch with Node.js 20.x runtime

  3. After creation, go to Configuration → Permissions → click the execution role link. In IAM, attach these policies to the role:
    • AmazonDynamoDBFullAccess (so Lambda can write to DynamoDB)
    • AmazonS3FullAccess (so Lambda can read the uploaded file)

    Figure P3-3: 📸 Lambda IAM role — DynamoDB and S3 permissions attached

  4. Back in the Lambda console, paste this code in the code editor:

    import { DynamoDBClient } = require('@aws-sdk/client-dynamodb');
const { DynamoDBDocumentClient, PutCommand } = require('@aws-sdk/lib-dynamodb');
const { S3Client, CopyObjectCommand, DeleteObjectCommand } = require('@aws-sdk/client-s3');

const dynamo = DynamoDBDocumentClient.from(new DynamoDBClient({}));
const s3 = new S3Client({});

exports.handler = async (event) => {
  // Extract info from the S3 event
  const bucket = event.Records[0].s3.bucket.name;
  const originalKey = decodeURIComponent(
    event.Records[0].s3.object.key.replace(/\+/g, ' ')
  );
  const fileSize = event.Records[0].s3.object.size;

  // Generate a new key with timestamp prefix (rename)
  const timestamp = new Date().toISOString();
  const userId = originalKey.split('/')[0] || 'anonymous';
  const fileName = originalKey.split('/').pop();
  const newKey = `processed/${timestamp}-${fileName}`;

  // Copy the file to new key (rename in S3)
  await s3.send(new CopyObjectCommand({
    Bucket: bucket,
    CopySource: `${bucket}/${originalKey}`,
    Key: newKey
  }));

  // Delete the original
  await s3.send(new DeleteObjectCommand({ Bucket: bucket, Key: originalKey }));

  // Store metadata in DynamoDB
  await dynamo.send(new PutCommand({
    TableName: 'job-applications',
    Item: {
      userId,
      timestamp,
      originalFileName: fileName,
      processedS3Key: newKey,
      fileSize,
      uploadStatus: 'processed'
    }
  }));

  console.log(`Processed: ${originalKey} -> ${newKey}`);
  return { statusCode: 200, body: 'Resume processed' };
};

    Click Deploy to save the function.

    Figure P3-4: 📸 Lambda code deployed — the handler processes S3 events and writes to DynamoDB

  5. Add the S3 trigger. Click Add trigger → select S3. Configure:
    Bucket: select your job-app-resumes-... bucket
    Event type: All object create events
    Prefix: uploads/ (only trigger on files in the uploads/ folder)
    Click Add.

    Figure P3-5: 📸 S3 trigger added — Lambda fires automatically on any file uploaded to uploads/ folder

  6. Test the pipeline. Go to S3 → your bucket → uploads/ folder (create it if needed) → Upload → upload any PDF file.

    Figure P3-6: 📸 Upload a PDF to S3 — this triggers Lambda automatically

  7. After a few seconds, check Lambda logs: CloudWatch → Log groups → /aws/lambda/process-resume-upload → click the latest log stream. You should see the "Processed:" message.

    Figure P3-7: 📸 CloudWatch logs — Lambda executed successfully after S3 upload

  8. Verify in DynamoDB: job-applications table → Explore table items → confirm a new item with uploadStatus: processed was created automatically.

    Figure P3-8: 📸 DynamoDB item created by Lambda — the full event-driven pipeline confirmed

✅ What you've learned: S3 events, Lambda triggers, async event-driven architecture, IAM role permissions for Lambda, and CloudWatch log inspection — the core of modern serverless pipelines.

Project 4: Serverless Job Application API — API Gateway + Lambda + DynamoDB

🎯 Objective: Replace the EC2 backend completely. Build a true serverless backend: API Gateway routes HTTP requests to Lambda, Lambda reads/writes DynamoDB. No servers to manage. Zero idle cost. Infinite scale.

⏱️ Time: 60-75 minutes

💰 Cost: Free Tier — API Gateway (1M calls/month free), Lambda (1M requests/month free)

⚡ Why this matters: This is exactly how modern startups build backends. No EC2, no patching, no capacity planning. You pay only when requests arrive. This is the architecture behind millions of production APIs.

Figure P4-0: 📸 Serverless architecture — API Gateway + Lambda + DynamoDB. No EC2 anywhere.

  1. Reuse the job-applications DynamoDB table from Project 2. Create a new Lambda function:
    Function name: serverless-job-api
    Runtime: Node.js 20.x
    Execution role: Create new role. Then attach AmazonDynamoDBFullAccess to the role (same as Project 3).

  2. Add this complete handler code to the Lambda function:

    const { DynamoDBClient } = require('@aws-sdk/client-dynamodb');
const { DynamoDBDocumentClient, PutCommand,
        QueryCommand, DeleteCommand, UpdateCommand } = require('@aws-sdk/lib-dynamodb');

const dynamo = DynamoDBDocumentClient.from(new DynamoDBClient({}));
const TABLE = 'job-applications';

exports.handler = async (event) => {
  const method = event.httpMethod;
  const path = event.path;

  try {
    // GET /applications/{userId}
    if (method === 'GET' && path.startsWith('/applications/')) {
      const userId = path.split('/')[2];
      if (!userId) throw new Error('userId is required');

      const result = await dynamo.send(new QueryCommand({
        TableName: TABLE,
        KeyConditionExpression: 'userId = :uid',
        ExpressionAttributeValues: { ':uid': userId }
      }));
      return response(200, result.Items);
    }

    // POST /applications
    if (method === 'POST' && path === '/applications') {
      const body = JSON.parse(event.body);
      const { userId, applicantName, jobTitle } = body;
      if (!userId || !applicantName || !jobTitle) {
        return response(400, { error: 'userId, applicantName, jobTitle are required' });
      }
      const item = {
        userId, applicantName, jobTitle,
        timestamp: new Date().toISOString(),
        status: 'applied'
      };
      await dynamo.send(new PutCommand({ TableName: TABLE, Item: item }));
      return response(201, { message: 'Application created', item });
    }

    // PATCH /applications/{userId}/{timestamp}
    if (method === 'PATCH') {
      const parts = path.split('/');
      const userId = parts[2];
      const timestamp = decodeURIComponent(parts[3]);
      const { status } = JSON.parse(event.body);
      await dynamo.send(new UpdateCommand({
        TableName: TABLE,
        Key: { userId, timestamp },
        UpdateExpression: 'SET #s = :status',
        ExpressionAttributeNames: { '#s': 'status' },
        ExpressionAttributeValues: { ':status': status }
      }));
      return response(200, { message: 'Status updated' });
    }

    // DELETE /applications/{userId}/{timestamp}
    if (method === 'DELETE') {
      const parts = path.split('/');
      const userId = parts[2];
      const timestamp = decodeURIComponent(parts[3]);
      await dynamo.send(new DeleteCommand({
        TableName: TABLE, Key: { userId, timestamp }
      }));
      return response(200, { message: 'Deleted' });
    }

    return response(404, { error: 'Route not found' });

  } catch (err) {
    console.error('Error:', err.message);
    return response(500, { error: err.message });
  }
};

function response(statusCode, body) {
  return {
    statusCode,
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(body)
  };
}

    Click Deploy.

  3. Create the API Gateway. Navigate to API Gateway → Create API → choose REST API → Build. Settings:
    API name: job-app-api
    Endpoint Type: Regional
    Click Create API.

    Figure P4-1: 📸 API Gateway — create a Regional REST API named job-app-api

  4. Create resources and methods. In the API Gateway console:
    Click Actions → Create Resource → Resource name: applications
    Select the /applications resource → Actions → Create Method → POST
    Integration type: Lambda Function → select serverless-job-api → Save.

    Figure P4-2: 📸 API Gateway POST method linked to Lambda function

  5. Add a proxy resource for dynamic paths (/applications/{proxy+}):
    Actions → Create Resource → check Configure as proxy resource → Resource Path: {proxy+}
    Select Lambda Proxy Integration → Lambda Function: serverless-job-api → Save.
    Enable Lambda proxy integration on the POST /applications method too.

  6. Deploy the API: Actions → Deploy API → Stage name: prod → Deploy. Copy the Invoke URL.

    Figure P4-3: 📸 API Gateway Invoke URL — this is your serverless API endpoint

  7. Test the fully serverless API:

    export API="https://YOUR_INVOKE_URL/prod"

# Create an application
curl -X POST "$API/applications" \
  -H "Content-Type: application/json" \
  -d '{"userId":"user-001","applicantName":"Vikram","jobTitle":"AWS Architect"}'

# Read applications
curl "$API/applications/user-001"

# Update status
curl -X PATCH "$API/applications/user-001/2025-12-04T10%3A00%3A00Z" \
  -H "Content-Type: application/json" \
  -d '{"status":"hired"}'

    Figure P4-4: 📸 Serverless API working — HTTP request flows through API Gateway → Lambda → DynamoDB

  8. Check CloudWatch logs to see Lambda execution logs. Navigate to CloudWatch → Log groups → /aws/lambda/serverless-job-api → open the latest stream.

    Figure P4-5: 📸 CloudWatch logs for serverless API — every request logged automatically

  9. Cleanup: Delete the API Gateway stage → delete the Lambda functions → the DynamoDB table has no charges at free tier scale. No EC2 to stop — there are no servers.

✅ What you've learned: Full serverless API architecture (API Gateway + Lambda + DynamoDB), Lambda proxy integration, validation and error handling in Lambda, CloudWatch logging — and the realization that you just built a production-grade backend without touching a single server.

🤔 Reflection Questions

1. A startup's user base grows 10x in a month. Their single RDS MySQL instance is overwhelmed with read queries from the app. What would you do first, and why?

💡 Hint

Think about what type of queries are overloading the instance. Are they reads or writes? What RDS feature is specifically designed to handle read scaling?

2. Your company runs a banking application. The CTO wants to know if DynamoDB is suitable for storing financial transactions. What's your recommendation and reasoning?

💡 Hint

Consider what banking systems require — ACID compliance, complex SQL joins, regulatory reporting. Which type of database guarantees these properties?

3. Explain the difference between ElastiCache and a Read Replica. Both seem to help with database performance — when would you use each?

💡 Hint

ElastiCache stores data in memory and never touches the database on a cache hit. Read Replicas are actual database instances that still run SQL queries. Think about data freshness, query complexity, and what type of data you're caching.

4. Your team debates whether to use Aurora or standard RDS MySQL for a new product. Aurora costs 20% more. How do you make the decision?

💡 Hint

Consider the trade-offs: read replicas count (5 vs 15), storage auto-growth, failover time, performance requirements. Is the 20% cost worth it for your traffic patterns?

5. What is the difference between structured, semi-structured, and unstructured data? Give a real-world example of each from an e-commerce platform.

💡 Hint

Think: customer orders table (structured), product review JSON (semi-structured), product images (unstructured). How would each be stored in AWS?
