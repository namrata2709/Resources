👤 What is a User in Linux?

When someone says "user" in Linux, they don't just mean a human sitting at a keyboard. A user in Linux is an account — a named identity registered in the system. With this account, someone (or something) can log into the system and use its resources: access files, run commands, and interact with processes.

Figure 2: Anatomy of a Linux User Account

Think of a user account like a flat in an apartment building. The apartment building is your Linux system. Each flat (user account) is private and belongs to one person. The flat number is the UID. The key to the flat is the password. The rooms inside the flat are the home directory where you store your files. The building's security rules control who can enter which flat — and that is the permission system.

Every user account in Linux contains the following:

  • Username — the name of the account (e.g., ec2-user, vikram)
  • Password — authentication credential (stored in encrypted form)
  • User ID (UID) — a unique number that the system uses internally to identify this user
  • Home Directory — a personal folder, usually at /home/username, where the user stores data and configuration files
  • Default Shell — the program that interprets the user's commands; most commonly /bin/bash
  • Primary Group — every user belongs to at least one group; a group with the same name as the user is created by default, and this is the primary group

⚡ Key Insight: Linux treats everything as a file — regular files, folders, processes, devices, memory. Because of this, the user and permission system controls access to absolutely everything on the system at a granular level. This is why Linux does not need antivirus software the way Windows does — the permission model itself prevents unauthorised access.

The Apartment Analogy

Imagine a large apartment building:

  • The building = the Linux system
  • Each flat = a user account
  • The flat number = UID
  • Your key = password
  • Your rooms = home directory (/home/username)
  • The building's security rules = file permissions
  • The building manager = root user (they can enter any flat)

Everyone lives independently in their own space, but the building manager has master access. That is why we do not log in as root for everyday work — it is too much power to use casually.

🗂️ Types of Users in Linux

Linux does not treat all accounts the same way. It divides users into three categories based on their roles and responsibilities. This differentiation is what makes Linux both powerful and secure.

Figure 3: Three Types of Linux Users Compared

1. Root User (Super User)

The root user is the most powerful account on any Linux system. It is also called the super user. If you are logged in as root, you have complete and unrestricted administrative privileges over everything on the machine.

What root can do:

  • Install and remove any software
  • Create, modify, or delete any user account
  • Change any system configuration file
  • Access any file — regardless of its permissions
  • Run any command — including ones that can destroy the system
The root user has UID 0 on every Linux system, without exception.

❌ Why NOT to use root for daily work: If you accidentally delete a critical configuration file, run a destructive command, or make a wrong change — as root, there is no undo. No confirmation. No second chance. The system carries out the instruction immediately. Think of it like giving a master key to everyone in the building — one careless moment and everything is at risk.

In the real world, system administrators never log into root directly. Instead, they use sudo — which temporarily borrows root privileges for just one command. This is much safer.

2. Normal User

Normal users are the accounts that humans use for day-to-day work. On AWS EC2, the default normal user accounts are:

  • Amazon Linux / Red Hat / CentOS:ec2-user
  • Ubuntu / Debian:ubuntu
  • CentOS (older):centos
Normal users have limited privileges — they can only access their own files and run permitted commands.

Normal users cannot install system-wide software or modify other users' files by default. This is the account you use in practice — safe, restricted, and controlled.

3. System User (Service Account)

System users are accounts that the Linux system creates automatically for itself — not for humans. They exist to run background services and system processes.

System users are not for login — they exist only to run background services and processes.

Examples of system users you will see on any Linux machine:

  • apache or www-data — runs the Apache web server
  • mysql — runs the MySQL database service
  • sshd — manages SSH connections
  • jenkins — automatically created when Jenkins is installed
  • docker — automatically created when Docker is installed

You cannot log into a system user account. The system manages these accounts internally. They are sometimes called service accounts.

💡 Real-world insight: When you install software like Docker or Jenkins on Linux, the installer automatically creates a system user for that service. This is a security best practice — each service runs as its own isolated account, so if one service is compromised, the attacker cannot easily access other services.

🔢 UID Ranges — How Linux Identifies Users

Every user account has a User ID (UID) — a number that the system uses internally to identify that user. When Linux checks file permissions or runs a process, it works with these numbers, not usernames. The username is just a human-friendly label.

Figure 4: UID Ranges in Linux

UID RangeUser TypeExamples
0Root user (Super user)root
1 – 999System users / Service accountssshd, apache, mysql, docker
1000+Normal users (human accounts)ec2-user, vikram, ubuntu
If a UID is 0, it is the root user. If it is between 1 and 999, it is a system/service account. If it is 1000 or above, it is a normal user.

This is why when you run cat /etc/passwd on your EC2 instance and see numbers like 72, 29, or 994, you immediately know those are system accounts — not humans. When you see 1001, 1002 — those are your normal user accounts.

⚡ Exam Tip: If asked "what UID does the root user have?" — the answer is always 0. This never changes. It is the same on every Linux distribution, every version, every system.

🗄️ Where User Information is Stored

Linux stores all user-related information in three special files inside the /etc directory. These are plain text files — but they are system configuration files with strict permission controls.

Figure 5: The Three Key User Files in /etc

/etc/passwd — Basic User Information

The /etc/passwd file stores basic information about every user account on the system.

Each line in this file represents one user and contains 7 fields separated by colons (:):

username:password:UID:GID:comment:home_directory:default_shell Example: ec2-user:x:1000:1000:EC2 Default User:/home/ec2-user:/bin/bash root:x:0:0:root:/root:/bin/bash

The fields are:

  1. username — the account name
  2. password — always shows x (actual password is in /etc/shadow)
  3. UID — unique user ID number
  4. GID — primary group ID
  5. comment — optional description (often the user's full name)
  6. home directory — path to the user's home folder
  7. default shell — the shell used when this user logs in

To view it: cat /etc/passwd (readable by all users)

/etc/shadow — Encrypted Passwords

The /etc/shadow file stores encrypted passwords and is only readable by root.

Because passwords are extremely sensitive, they are stored separately in /etc/shadow with very tight permissions. Normal users cannot read this file — only root can. This is why you need sudo to view it:

sudo cat /etc/shadow

The passwords stored here are hashed (not reversible encryption) — so even the system administrator cannot read the plain-text password, only verify it.

/etc/group — Group Information

The /etc/group file stores information about all groups, including the members of each group.

To view it: cat /etc/group

groupname:password:GID:members Example: developers:x:1002:vikram,priya wheel:x:10:ec2-user

📸 From Session: Output of cat /etc/passwd showing root (UID 0), system users (UID 1–999), and normal users (UID 1000+)

💡 Why can normal users read /etc/passwd but not /etc/shadow? In the old days, passwords were stored in /etc/passwd. As Linux evolved, passwords were moved to /etc/shadow for security, and only root can access that file. The /etc/passwd file still exists and is still readable by all users — it just no longer contains the real passwords (it shows x as a placeholder).

⚙️ Basic User Management Commands

Managing users in Linux is done from the command line. All user management commands require root privileges, so you will use sudo before each command. Let's walk through each command clearly.

Figure 6: Linux User Management Command Flow

useradd — Create a New User

The useradd command creates a new user account. Only the root user (or someone with sudo) can run it.

sudo useradd username

When you run this command, Linux automatically:

  • Creates the user account with a new UID (next available, 1000+)
  • Creates a primary group with the same name as the user
  • Creates a home directory at /home/username
  • Sets the default shell to /bin/bash

Common options:

# Create user with a custom home directory sudo useradd -d /custom/path username # Create user with a specific shell sudo useradd -s /bin/zsh username # Create user with a specific UID sudo useradd -u 1500 username # Create user and add to an existing group sudo useradd -G developers username # Create a system user (no login, no home directory) sudo useradd -r servicename

✅ Best Practice: After creating a user with useradd, always set a password immediately with passwd. A user account without a password cannot log in (which is actually fine for system users, but not for human accounts).

passwd — Set or Change a Password

# Set or change password for a specific user (requires sudo) sudo passwd username # Change your own password (no sudo needed) passwd

When you run this, Linux will prompt you to enter the new password twice. The password is then stored in encrypted form in /etc/shadow.

usermod — Modify an Existing User

The usermod command modifies an existing user account. This is one of the most important commands for day-to-day user administration.

# Add a user to an additional/secondary group (keep existing groups) sudo usermod -aG groupname username # Change a user's primary group sudo usermod -g groupname username # Change a user's home directory sudo usermod -d /new/home username # Change a user's shell sudo usermod -s /bin/zsh username # Lock a user account sudo usermod -L username # Unlock a user account sudo usermod -U username

❌ Critical Mistake: Know the difference between -G and -aG.
usermod -G groupname username — replaces all secondary groups with just this one group.
usermod -aG groupname username — appends this group to the user's existing groups.
If you forget the -a, the user loses all their other group memberships!

userdel — Delete a User

# Delete user account only (home directory is kept) sudo userdel username # Delete user account AND remove home directory sudo userdel -r username
The -r flag in userdel -r removes the user's home directory along with the account.

After running userdel -r username, the home directory is deleted. But if you use userdel username without -r, the home directory at /home/username remains. You would then need to delete it manually with:

sudo rm -rf /home/username

id — Check a User's Identity

# Check your own identity id # Check another user's identity id username

Example output:

uid=1001(vikram) gid=1001(vikram) groups=1001(vikram),1002(developers)

This shows the user's UID, primary GID, and all groups they belong to. This is your first command to verify any user management change you make.

👥 Understanding Linux Groups

Groups in Linux are a way to organise users and manage permissions collectively. Instead of setting permissions for each user individually, you can put multiple users in a group and grant permissions to the entire group at once.

Figure 7: Primary Group vs Secondary Groups

Primary Group

Every user has exactly one primary group, which is created automatically when the user account is created and has the same name as the user.

When a user creates a file, that file is automatically associated with the user's primary group. The primary group ID (GID) is stored in /etc/passwd.

Secondary Groups (Supplementary Groups)

A user can belong to multiple additional groups beyond their primary group. These are called secondary or supplementary groups. This is how you grant a user access to shared resources.

Real-world examples:

  • Add a developer to the developers group → they can access the shared codebase
  • Add an ops engineer to the docker group → they can run Docker commands without sudo
  • Add an admin to the wheel group → they can use sudo on Amazon Linux/CentOS/RHEL

Special Groups You Must Know

📸 From Session: The wheel vs sudo group comparison table shared by instructor

On Amazon Linux, CentOS, and RHEL, the group that grants sudo access to normal users is called wheel.On Ubuntu and Debian, the group that grants sudo access to normal users is called sudo.

Other important software-created groups:

  • docker — created when Docker is installed; members can run Docker without sudo
  • jenkins — created when Jenkins is installed; manages Jenkins permissions
  • www-data — created on Ubuntu for Apache/Nginx web servers

🔧 Basic Group Management Commands

Just like user management, group management is done from the command line with sudo.

groupadd — Create a New Group

sudo groupadd groupname # Example: Create a group called developers sudo groupadd developers

Viewing Groups

# View all groups on the system cat /etc/group # View groups a specific user belongs to id username groups username

Adding a User to a Group

To add a user to a secondary group without removing existing groups, use sudo usermod -aG groupname username.
# Add vikram to the developers group (keeps existing groups) sudo usermod -aG developers vikram # Verify the change id vikram # Output: uid=1001(vikram) gid=1001(vikram) groups=1001(vikram),1002(developers)

Changing a User's Primary Group

# Change vikram's primary group to QA sudo usermod -g QA vikram # Verify id vikram # Output: uid=1001(vikram) gid=1003(QA) groups=1003(QA),1002(developers)

❌ Common Mistake from Session: Using -g vs -G incorrectly.
-g groupname username → changes the primary group
-G groupname username → replaces all secondary groups
-aG groupname username → appends to secondary groups (safe)

groupmod — Modify a Group

# Rename a group sudo groupmod -n newname oldname # Change a group's GID sudo groupmod -g 2000 groupname

groupdel — Delete a Group

sudo groupdel groupname

Note: You cannot delete a group that is the primary group of any user. You must first change those users' primary groups before deleting.

🔐 sudo and the sudoers File

sudo stands for "superuser do". It lets a normal user temporarily run a command with root privileges — without actually switching to the root account. Think of it as a controlled pass to do one specific thing as the boss, then immediately give back the key.

Figure 8: How sudo Works Under the Hood

sudo allows a normal user to run a single command with root privileges without switching to the root account.

The sudoers File

The /etc/sudoers file controls who can use sudo and for what. You should never edit this file directly with a regular text editor. Instead, always use:

sudo visudo

The visudo command opens the sudoers file safely and validates the syntax before saving. A typo in /etc/sudoers can lock you out of sudo entirely.

NOPASSWD Configuration

By default, when you run sudo, Linux asks for your password as a security check. In production systems, this is important. However, in some automated or trusted environments (like EC2 instances where you connect via SSH key), you may see this line in the sudoers file:

ec2-user ALL=(ALL) NOPASSWD: ALL

This means ec2-user can run any sudo command without being asked for a password. This is why on AWS EC2 (Amazon Linux), the ec2-user can run sudo freely after SSH login.

⚡ Security Note: In real production environments, always keep password prompts enabled for sudo. NOPASSWD should only be used in very specific, controlled situations — not as a convenience shortcut.

Granting sudo Access to a User

The correct way to give a user sudo access is to add them to the appropriate group:

# Amazon Linux / CentOS / RHEL — add to wheel group sudo usermod -aG wheel username # Ubuntu / Debian — add to sudo group sudo usermod -aG sudo username

🔄 Switching Between Users

On a Linux system, you can switch from one user account to another without logging out. The command for this is su (substitute user).

The su Command

# Switch to another user (will ask for that user's password) su username # Switch to root user su - # OR su root # Switch to a user and load their full environment su - username # Run a single command as another user su -c "command" username
The su - (with hyphen) command switches to the target user and loads their full environment (home directory, PATH, shell settings), while su without hyphen only switches the user identity.

💡 su vs sudo:
su username — switches to that user entirely; needs the target user's password
sudo command — runs one command as root; needs your own password
In modern Linux administration, sudo is preferred over su for security and audit trail reasons.

Exiting Back to Previous User

exit # OR Ctrl+D

This brings you back to the original user session you were in before switching.

🌐 Logging into EC2 via SSH

When you create an EC2 instance on AWS, you do not use a password to log in. Instead, AWS uses SSH key pair authentication — a far more secure method. Understanding how this works connects all the Linux user concepts together.

Figure 9: SSH Key Authentication Flow to EC2

How SSH Key Authentication Works

When you created your EC2 key pair on AWS, two keys were generated:

  • Private key (.pem file) — downloaded to your local laptop. Never share this.
  • Public key — automatically stored in the EC2 instance at /home/ec2-user/.ssh/authorized_keys

When you try to connect via SSH:

  1. Your SSH client sends a connection request to the EC2 instance's public IP on port 22
  2. EC2's firewall (Security Group) checks: is port 22 SSH traffic allowed? (Yes, it was configured at launch)
  3. The SSH service on EC2 checks your private key against the public key in ~/.ssh/authorized_keys
  4. If the keys match — access granted! You are now logged in as ec2-user
The public key is stored at ~/.ssh/authorized_keys inside the user's home directory on the EC2 instance.

SSH Connection Steps (Command Prompt / Terminal)

# Step 1: Navigate to the folder where your .pem file is stored cd C:\Users\YourName\Downloads # Windows Command Prompt cd ~/Downloads # Mac/Linux Terminal # Step 2: (Windows only) You may need this if keys give a warning # On Mac/Linux: chmod 400 yourkey.pem # Step 3: Connect to the EC2 instance ssh -i "yourkey.pem" ec2-user@YOUR_EC2_PUBLIC_IP # Example ssh -i "inbin123.pem" [email protected]

After connecting, you will see a prompt like:

[ec2-user@ip-172-31-34-53 ~]$

This confirms you are now inside the EC2 instance, logged in as ec2-user, in the home directory (~).

Verifying Your Login

# Check current user whoami # Check working directory pwd # List hidden files (including .ssh folder) ls -la # View the authorized_keys file cat ~/.ssh/authorized_keys

✅ Security Reminder: Always make sure your Security Group on EC2 allows SSH (port 22) only from your IP address in production — not from 0.0.0.0/0 (anywhere). Allowing SSH from anywhere is convenient for practice but dangerous in production.

📝 Overall Summary

  • User in Linux: An account that allows someone or something to log into the system and use resources (files, commands, processes). Contains username, password, UID, home directory, default shell, and primary group.
  • Three User Types: Root user (UID 0, full admin), Normal user (UID 1000+, limited privileges), System user (UID 1–999, background services, no login).
  • UID Ranges: 0 = root; 1–999 = system/service accounts; 1000+ = normal users.
  • Storage Files:/etc/passwd (basic info, readable by all), /etc/shadow (encrypted passwords, root only), /etc/group (group info).
  • Key Commands:useradd (create), passwd (set password), usermod (modify), userdel (delete). All require sudo.
  • usermod -aG vs -G: Always use -aG to append to groups; -G alone replaces all secondary groups.
  • Primary vs Secondary Group: Every user has one primary group (same name as user, created automatically). Secondary groups can be added with usermod -aG.
  • Special Groups:wheel = sudo access on Amazon Linux/CentOS/RHEL; sudo = sudo access on Ubuntu/Debian.
  • sudo: Temporarily borrows root privileges for one command. Safer than logging in as root. Configuration in /etc/sudoers, edit with visudo.
  • SSH Login: Uses key pair authentication. Private key on laptop, public key in ~/.ssh/authorized_keys on EC2. Connect with ssh -i key.pem ec2-user@IP.

Project 2: Team-Based Access Control with Directory Permissions

🎯 Objective: Simulate a real company server where different teams only have access to their own project directories. You will create users, groups, directories, and set permissions so each team is isolated.

⏱️ Time: 45–60 min

💰 Cost: Free tier

⚡ Why this matters: This is the most common real-world use of Linux users and groups. Every company that runs servers needs to ensure developers cannot access QA data, QA cannot touch production configs, and so on. You are building that access control system from scratch.

  1. SSH into your EC2 instance and create two groups — one for developers, one for testers:

    sudo groupadd developers sudo groupadd testers

  2. Create four users — two developers and two testers — and assign them to the correct groups:

    sudo useradd alice sudo useradd bob sudo useradd charlie sudo useradd diana sudo passwd alice sudo passwd bob sudo passwd charlie sudo passwd diana sudo usermod -aG developers alice sudo usermod -aG developers bob sudo usermod -aG testers charlie sudo usermod -aG testers diana

    📸 Screenshot: Creating four users and assigning to groups

  3. Verify the group assignments for all four users:

    id alice id bob id charlie id diana

    📸 Screenshot: id command confirming correct group membership

  4. Create the project directory structure:

    sudo mkdir -p /project/dev sudo mkdir -p /project/test

  5. Set group ownership on each directory so it belongs to the correct team:

    sudo chown root:developers /project/dev sudo chown root:testers /project/test

  6. Set permissions so only the owning group can access each folder (no access for others):

    sudo chmod 770 /project/dev sudo chmod 770 /project/test ls -la /project/

    📸 Screenshot: Directory permissions showing 770 and group ownership

  7. Test access as alice (developer) — she should be able to enter /project/dev but NOT /project/test:

    su - alice touch /project/dev/alice-file.txt # Should work ls /project/dev # Should list files ls /project/test # Should give: Permission denied exit

    📸 Screenshot: alice can access /project/dev but is denied from /project/test

    su - charlie ls /project/test # Should work ls /project/dev # Should give: Permission denied exit

    📸 Screenshot: charlie can access /project/test but is denied from /project/dev

Project 3: Secure Server Setup (Admin Account + Hardening)

🎯 Objective: Create a dedicated admin account, grant it sudo access, disable direct root login via SSH, and lock inactive accounts. This is standard security hardening done on every production Linux server.

⏱️ Time: 45–60 min

💰 Cost: Free tier

❌ CRITICAL WARNING: In Step 5 you will disable root login in the SSH config. Before doing this, make absolutely sure you have tested that your devops-admin account can successfully SSH in, or you may lose access to the instance entirely. Never skip the verification step.

  1. Create a new admin user called devops-admin and set a strong password:

    sudo useradd devops-admin sudo passwd devops-admin

  2. Grant the user sudo access by adding them to the wheel group (Amazon Linux):

    sudo usermod -aG wheel devops-admin id devops-admin

    📸 Screenshot: devops-admin created with wheel group access

  3. Copy your SSH public key to the devops-admin account so you can SSH in as this user. Run these as ec2-user:

    sudo mkdir -p /home/devops-admin/.ssh sudo cp ~/.ssh/authorized_keys /home/devops-admin/.ssh/ sudo chown -R devops-admin:devops-admin /home/devops-admin/.ssh sudo chmod 700 /home/devops-admin/.ssh sudo chmod 600 /home/devops-admin/.ssh/authorized_keys

    📸 Screenshot: SSH key copied and permissions set for devops-admin

  4. Open a NEW terminal window and test SSH as devops-admin BEFORE touching sshd_config:

    ssh -i "yourkey.pem" devops-admin@YOUR_EC2_PUBLIC_IP

    Verify sudo works from this new session:

    sudo whoami # Should output: root

    📸 Screenshot: devops-admin SSH login confirmed, sudo whoami returns root

  5. Now — with your admin access confirmed — disable root login in the SSH config:

    sudo nano /etc/ssh/sshd_config

    Find the line PermitRootLogin and change it to:

    PermitRootLogin no

    Save the file (Ctrl+O, Enter, Ctrl+X in nano), then restart SSH:

    sudo systemctl restart sshd

    📸 Screenshot: PermitRootLogin set to no in sshd_config

  6. Create a test user to practice locking and unlocking accounts:

Project 4: User Setup Automation Script

🎯 Objective: Write a reusable bash script that automates the creation of multiple users from a CSV file. This is your first real step into DevOps thinking — instead of running commands manually, you write a script that does the work for you.

⏱️ Time: 60–90 min

💰 Cost: Free tier

⚡ Why this matters: In a real company, when 10 new developers join, no one runs useradd 10 times manually. There is a script. You are writing that script.

  1. Create the input file — a CSV listing users and their groups:

    cat > /home/ec2-user/users.csv << 'EOF' username,group,role dev1,developers,developer dev2,developers,developer qa1,testers,tester qa2,testers,tester admin1,wheel,admin EOF

    📸 Screenshot: users.csv created with five user entries

  2. Create the automation script:

    nano /home/ec2-user/setup_users.sh

    Paste this content into the file:

    #!/bin/bash # setup_users.sh - Bulk user creation from CSV # Usage: sudo bash setup_users.sh users.csv CSV_FILE="$1" LOG_FILE="/var/log/user-setup.log" echo "=== User Setup Started: $(date) ===" | sudo tee -a $LOG_FILE if [ -z "$CSV_FILE" ]; then echo "Error: No CSV file provided" echo "Usage: sudo bash setup_users.sh users.csv" exit 1 fi # Skip header line, read each row tail -n +2 "$CSV_FILE" | while IFS=',' read -r username group role; do echo "--- Processing: $username (Group: $group, Role: $role) ---" # Create group if it doesn't already exist if ! getent group "$group" > /dev/null 2>&1; then groupadd "$group" echo "Created group: $group" | tee -a $LOG_FILE fi # Create user if they don't already exist if id "$username" > /dev/null 2>&1; then echo "SKIP: User $username already exists" | tee -a $LOG_FILE else useradd -m -s /bin/bash "$username" echo "$username:TempPass@123" | chpasswd usermod -aG "$group" "$username" echo "CREATED: $username | Group: $group | Role: $role" | tee -a $LOG_FILE fi done echo "=== User Setup Complete: $(date) ===" | tee -a $LOG_FILE echo "" echo "--- Final User Summary ---" tail -n +2 "$CSV_FILE" | while IFS=',' read -r username group role; do echo "$username: $(id $username 2>/dev/null || echo 'not found')" done

  3. Make the script executable and run it:

    chmod +x /home/ec2-user/setup_users.sh sudo bash /home/ec2-user/setup_users.sh /home/ec2-user/users.csv

    📸 Screenshot: Script output showing all five users created successfully

  4. Check the log file the script created:

    sudo cat /var/log/user-setup.log

    📸 Screenshot: Log file showing timestamped audit trail of user creation

  5. Run the script a second time to test the duplicate protection — it should skip existing users:

    sudo bash /home/ec2-user/setup_users.sh /home/ec2-user/users.csv

    This time you should see SKIP: User already exists for all five users.

  6. Cleanup: Remove the created users and groups:

    for user in dev1 dev2 qa1 qa2 admin1; do sudo userdel -r $user 2>/dev/null done sudo groupdel developers 2>/dev/null sudo groupdel testers 2>/dev/null echo "Cleanup complete"

Project 5: User Activity Audit Script (Interview-Level)

🎯 Objective: Build a monitoring script that tracks login history, failed login attempts, and currently active users — then saves everything to a custom audit log. This is real production responsibility.

⏱️ Time: 60–90 min

💰 Cost: Free tier

⚡ Why this matters: Security auditing is a legal requirement in many organisations. If a breach happens, the first question is always "who logged in and when?" You are building the system that answers that question.

  1. First, explore the built-in Linux audit commands. Run each one and study the output:

    # Who is currently logged in? who # Detailed login history (last 20 entries) last -n 20 # Failed login attempts (requires sudo) sudo lastb -n 20 # System log for authentication events sudo cat /var/log/secure | tail -30

    📸 Screenshot: Output of who and last commands showing login history

  2. Check failed login attempts (this is where attackers show up):

    sudo lastb -n 20

    📸 Screenshot: lastb output showing failed login attempts with source IPs

  3. Create the audit script:

    nano /home/ec2-user/audit_users.sh

    Paste this content:

    #!/bin/bash # audit_users.sh - User activity audit report # Usage: sudo bash audit_users.sh AUDIT_LOG="/var/log/custom-user-audit.log" REPORT_DATE=$(date '+%Y-%m-%d %H:%M:%S') HOSTNAME=$(hostname) echo "========================================" | tee -a $AUDIT_LOG echo "USER AUDIT REPORT" | tee -a $AUDIT_LOG echo "Server: $HOSTNAME" | tee -a $AUDIT_LOG echo "Date: $REPORT_DATE" | tee -a $AUDIT_LOG echo "========================================" | tee -a $AUDIT_LOG echo "" | tee -a $AUDIT_LOG echo "--- CURRENTLY LOGGED IN USERS ---" | tee -a $AUDIT_LOG who | tee -a $AUDIT_LOG echo "" | tee -a $AUDIT_LOG echo "--- ALL USER ACCOUNTS (Normal Users) ---" | tee -a $AUDIT_LOG awk -F: '$3 >= 1000 && $1 != "nobody" {print "User: "$1" | UID: "$3" | Home: "$6}' /etc/passwd | tee -a $AUDIT_LOG echo "" | tee -a $AUDIT_LOG echo "--- LOGIN HISTORY (Last 10) ---" | tee -a $AUDIT_LOG last -n 10 | tee -a $AUDIT_LOG echo "" | tee -a $AUDIT_LOG echo "--- FAILED LOGIN ATTEMPTS (Last 10) ---" | tee -a $AUDIT_LOG lastb -n 10 2>/dev/null | tee -a $AUDIT_LOG echo "" | tee -a $AUDIT_LOG echo "--- USERS WITH SUDO ACCESS ---" | tee -a $AUDIT_LOG grep -Po '^sudo.+:\K.*$' /etc/group | tr ',' ' ' | sed 's/^/ sudo: /' | tee -a $AUDIT_LOG grep -Po '^wheel.+:\K.*$' /etc/group | tr ',' ' ' | sed 's/^/ wheel: /' | tee -a $AUDIT_LOG echo "" | tee -a $AUDIT_LOG echo "--- LOCKED USER ACCOUNTS ---" | tee -a $AUDIT_LOG sudo awk -F: '/^\!/{print "LOCKED: "$1}' /etc/shadow 2>/dev/null | tee -a $AUDIT_LOG || echo " (none)" | tee -a $AUDIT_LOG echo "" | tee -a $AUDIT_LOG echo "========================================" | tee -a $AUDIT_LOG echo "Report saved to: $AUDIT_LOG" echo "Report complete."

  4. Run the audit script:

    chmod +x /home/ec2-user/audit_users.sh sudo bash /home/ec2-user/audit_users.sh

    📸 Screenshot: Full audit report showing all sections of the user activity summary

  5. View the saved log file and observe how each run appends a new report:

    sudo cat /var/log/custom-user-audit.log

    📸 Screenshot: Saved audit log file showing complete report with timestamp

  6. Run the script a second time and notice it appends a new report — the log now shows two timestamped runs. This is how production audit logs work.

  7. Cleanup: Stop the EC2 instance or terminate it to avoid charges. The scripts and log files are stored on the instance only.
