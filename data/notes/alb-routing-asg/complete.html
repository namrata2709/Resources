🌐 Introduction

Imagine you run a busy shopping website. When a customer visits yourstore.com/products, they need to see the product catalog. When they go to /cart, they need the shopping cart. And when they check out, they hit /orders. Behind the scenes, these are three completely separate applications running on different servers — but to the customer, it feels like one seamless website.

This is exactly what the Application Load Balancer (ALB) does. It acts like an incredibly smart traffic cop standing at the front door of your cloud architecture, reading each incoming request and directing it to exactly the right backend service — all based on the URL path.

Figure 1: ALB as a traffic cop routing requests to the correct microservice based on URL path

In this session, we covered three interconnected topics that together form the backbone of a scalable, production-grade AWS architecture:

  • Path-based routing — how ALB reads URL paths and routes traffic to the right service
  • Auto Scaling Groups (ASG) — how AWS automatically adds or removes EC2 instances as traffic changes
  • ALB vs NLB — the key differences between Application and Network Load Balancers and when to use each

💡 Why this matters: These three concepts work together. You use ALB for intelligent routing, ASG to keep each service right-sized under load, and understanding ALB vs NLB helps you pick the correct tool for every use case. Together, they are the foundation of the microservices architecture model used by companies like Netflix, Airbnb, and Amazon itself.

⚖️ What is a Load Balancer?

Before diving into path-based routing, let's make sure the foundation is solid. A load balancer is a service that sits in front of your application and distributes incoming network traffic across multiple backend servers (called target groups).

Think of a load balancer like the front desk at a large hospital. Patients (requests) arrive, and the receptionist (load balancer) decides which doctor (server) is available and best suited to handle each patient. Without this system, all patients would flood into one room — chaos. With it, every room stays manageable.

Figure 2: A load balancer distributes traffic across multiple EC2 instances to prevent overload

A load balancer improves application availability, fault tolerance, and scalability by distributing traffic across multiple healthy targets.

AWS offers three types of load balancers under the Elastic Load Balancing (ELB) family:

  • Application Load Balancer (ALB) — Layer 7, HTTP/HTTPS, path-based routing
  • Network Load Balancer (NLB) — Layer 4, TCP/UDP, ultra-low latency
  • Gateway Load Balancer (GWLB) — Layer 3, used for third-party appliances like firewalls

📚 In this session, the focus was on ALB and NLB. Gateway Load Balancer will be covered in a later session on network security appliances.

🛣️ Path-Based Routing with ALB

Path-based routing is one of the most powerful features of the Application Load Balancer. It allows a single ALB to serve as the entry point for an entire microservices application, directing each request to a completely different backend service based solely on the URL path.

The Microservices Problem

In a traditional monolithic application, everything runs in one big codebase on one server. When traffic spikes, you can only scale everything at once — wasteful and expensive. Modern applications are built as microservices: small, independent applications where the products service, cart service, and orders service are completely separate.

But if they're separate, how does a user's browser know which server to call? They can't send three different requests to three different IP addresses. They expect one address: yourstore.com. The ALB solves this.

Figure 3: ALB path-based routing architecture for a microservices application

How Path-Based Routing Works

Here is what happens step by step when a user visits yourstore.com/products:

  1. The user's request reaches the ALB's DNS endpoint (e.g., my-alb-1234567890.us-east-1.elb.amazonaws.com)
  2. The ALB inspects the HTTP request — specifically the URL path: /products
  3. It matches the path against its configured listener rules
  4. The matching rule forwards the request to the Products Target Group
  5. The target group contains one or more EC2 instances running the Products application
  6. The response travels back through the ALB to the user

The user never knows they were talking to three different backend applications. They just see yourstore.com.

Listener Rules Explained

A listener is a process that checks for incoming connection requests, configured with a protocol (HTTP/HTTPS) and a port (typically 80 or 443).

Each listener has one or more rules. A rule has two parts:

  • Condition: A condition to match (e.g., path is /products*)
  • Action: What to do when the condition matches (e.g., forward to target group)

Rules are evaluated in priority order. Every listener must have a default rule that handles any request that doesn't match any other rule — this is the fallback action.

⚡ Path pattern matching examples:

  • /products — matches exactly /products only
  • /products* — matches /products, /products/123, /products/sale
  • *.jpg — matches any path ending in .jpg (used for static file serving)

Target Groups

A target group is a logical grouping of backend resources that receive traffic from a load balancer rule. Each target group has its own:

  • Target type: EC2 instances, IP addresses, or Lambda functions
  • Health check configuration: Which path to ping and what response code counts as healthy
  • Protocol and port: How the ALB communicates with the targets

A target group with no healthy targets will cause the ALB to return a 503 Service Unavailable error to the client.

Figure 4: Three separate target groups, each containing EC2 instances for a different microservice

Health Checks

The ALB continuously monitors the health of each target in a target group by sending HTTP requests to a configured path (e.g., /health) at regular intervals. If a target fails to respond within the threshold, it is marked as unhealthy and removed from rotation automatically.

Traffic is only sent to healthy targets. Unhealthy targets are automatically excluded until they pass health checks again.

Hands-On: What We Built

In the session, the group built a working demonstration of path-based routing:

  1. Created 3 EC2 instances — each running a simple web application for products, cart, and orders respectively
  2. Created 3 target groups — one for each service, each registering the corresponding EC2 instance
  3. Created one ALB — configured with HTTP listener on port 80
  4. Added 3 listener rules:
    • Path /products* → forward to Products Target Group
    • Path /cart* → forward to Cart Target Group
    • Path /orders* → forward to Orders Target Group
  5. Tested routing — accessed each path via the ALB DNS name and confirmed it reached the correct backend

✅ Key takeaway: One ALB, one DNS name, three completely separate backend services — all working seamlessly. This is the power of path-based routing.

📈 Auto Scaling Groups (ASG)

Path-based routing solves the direction problem — getting requests to the right service. But what happens when the products page goes viral? A single EC2 instance can only handle so many requests before it buckles. This is where Auto Scaling Groups come in.

Think of an ASG like a staffing agency for your EC2 instances. You tell the agency: "I need at least 2 servers, never more than 10, and when things get busy, hire more." The agency (ASG) watches traffic, automatically spins up new instances when needed, and terminates extras when things quiet down — all without you lifting a finger.

Figure 5: Auto Scaling Group dynamically adjusts the number of EC2 instances based on demand

Why Auto Scaling Matters

Without Auto Scaling, you have two bad choices:

  • Under-provision: Keep just enough servers for average traffic. When spikes hit, the application crashes.
  • Over-provision: Keep enough servers for peak traffic, all the time. 90% of the time you're paying for idle capacity.

Auto Scaling gives you the best of both worlds: you pay only for what you use, and you always have enough capacity to handle current demand.

ASG Key Components

Launch Template

Before you can create an Auto Scaling Group, AWS needs to know what kind of instance to create when it scales out. This blueprint is called a Launch Template.

A Launch Template defines the AMI, instance type, key pair, security groups, user data, and any other configuration needed to launch a new EC2 instance.

Think of a Launch Template like a cookie cutter. The cookie cutter (template) stays the same; every cookie (EC2 instance) it produces is identical. When ASG needs a new instance, it uses the launch template to stamp one out automatically.

💡 Launch Templates replaced the older "Launch Configurations." AWS recommends always using Launch Templates because they support versioning, mixed instance types, and Spot Instance integration.

📚 Source: AWS Auto Scaling Launch Templates Docs

Capacity Settings

Every ASG has three critical capacity numbers:

  • Minimum capacity — the ASG will never scale below this number of instances (floor)
  • Maximum capacity — the ASG will never scale above this number of instances (ceiling)
  • Desired capacity — the number of instances ASG tries to maintain right now

The desired capacity is the current target. ASG constantly works to match actual running instances to the desired count — launching instances if below, terminating if above.

Figure 6: ASG capacity settings — minimum, desired, and maximum define the scaling window

Scaling Policies

How does the ASG know when to scale? Through scaling policies tied to CloudWatch alarms.

Target Tracking Scaling (Recommended) — the simplest and most commonly used policy. You set a target metric value (e.g., keep average CPU at 50%), and ASG automatically adjusts instance count to maintain it. Think of it like a thermostat.

Step Scaling — you define specific steps: "If CPU is 60-70%, add 1 instance. If CPU is 70-90%, add 2 instances. If CPU > 90%, add 4 instances." More granular control but requires more configuration.

Scheduled Scaling — scale based on a time schedule. Useful when you know traffic patterns in advance (e.g., scale up every weekday at 9am, scale down at 7pm).

Predictive Scaling — uses machine learning to analyze historical patterns and proactively scale before demand hits. Best for workloads with consistent, recurring patterns.

⚡ Exam tip: Target Tracking is the default recommendation for most workloads. It is simpler to configure and responds faster than step scaling for gradual load changes.

ASG and Load Balancer Integration

Here is where everything ties together. When you attach an ASG to an ALB target group, something powerful happens automatically:

  • When ASG launches a new instance, it automatically registers the instance with the target group
  • The ALB immediately begins sending traffic to the new instance (once health checks pass)
  • When ASG terminates an instance, it automatically deregisters it from the target group before termination
  • The ALB stops sending traffic to that instance gracefully

This integration means traffic is never sent to an instance that isn't ready, and no traffic is lost when an instance is terminated — the process is completely seamless.

Figure 7: ASG automatically registers and deregisters instances with the ALB target group during scaling events

Per-Service Scaling: The Real Power

Going back to our microservices example — one of the most powerful things about combining ALB path-based routing with ASG is per-service scaling.

Imagine Black Friday: the products and cart services are under enormous load, but the orders service is relatively quiet. With per-service ASGs, you can scale the Products ASG from 2 to 20 instances while the Orders ASG stays at 2. You're paying only for what each service actually needs.

💡 This is why microservices + ALB + ASG is the standard architecture pattern at companies like Amazon, Netflix, and Uber. Each service scales independently based on its own traffic patterns.

Scale-In Protection and Warm-Up Periods

Instance Warm-Up Period — when a new EC2 instance starts, it needs time to initialize before it's ready to serve traffic. The warm-up period tells ASG to wait before counting the new instance's metrics in scaling decisions, preventing it from triggering another scale-out before the first new instance is even ready.

Scale-In Protection — you can mark specific instances as protected from scale-in (termination). Useful for instances running long-running jobs you don't want interrupted.

During a scale-in event, ASG uses a termination policy (default: oldest launch configuration) to decide which instance to remove first.

🔀 ALB vs Network Load Balancer (NLB)

AWS offers two main load balancers for most workloads: the Application Load Balancer (ALB) and the Network Load Balancer (NLB). They look similar on the surface — both distribute traffic, both have listeners and target groups — but they operate at completely different levels and solve different problems.

The OSI Model Context

To understand ALB vs NLB, you need to know about the OSI (Open Systems Interconnection) model — a framework that describes the seven layers of computer networking.

Figure 8: OSI model showing ALB operating at Layer 7 (Application) and NLB operating at Layer 4 (Transport)

Think of the OSI layers like different floors of a post office:

  • Layer 4 (Transport) — knows the sender's address and port number, like knowing which building and room to deliver to, but not reading the letter inside
  • Layer 7 (Application) — can actually open the envelope and read the content of the letter — understanding HTTP headers, URL paths, cookies, and more

Application Load Balancer (ALB) — Layer 7

The ALB operates at Layer 7 (Application Layer) of the OSI model, meaning it understands the full content of HTTP and HTTPS requests.

Because ALB can read the full HTTP request, it can make intelligent routing decisions based on:

  • URL path — /products, /cart, /orders
  • HTTP headers — e.g., route mobile users differently from desktop users
  • Query strings — e.g., ?version=2
  • HTTP method — e.g., route GET and POST to different targets
  • Source IP

⚡ ALB is ideal for: Web applications, microservices, REST APIs, HTTPS termination, WebSocket applications

Network Load Balancer (NLB) — Layer 4

The NLB operates at Layer 4 (Transport Layer) of the OSI model, meaning it routes traffic based only on IP addresses and TCP/UDP ports — it cannot read HTTP content.

Because NLB doesn't need to inspect packet content, it is extraordinarily fast. NLB is designed for workloads where:

  • Latency must be minimized to milliseconds
  • You need to handle millions of requests per second
  • You're using non-HTTP protocols (TCP, UDP, TLS)
  • You need a static IP address or Elastic IP for the load balancer

⚡ NLB is ideal for: Gaming servers, IoT data ingestion, real-time trading systems, DNS, VoIP, any workload using UDP or raw TCP

Can ALB and NLB Chain Together?

This came up directly in the session, and it's a very common exam topic.

An Application Load Balancer cannot directly forward traffic to a Network Load Balancer as a target.

However, a Network Load Balancer can forward traffic to an Application Load Balancer — this is used when you need a static IP (from NLB) combined with advanced HTTP routing (from ALB).

Figure 10: NLB → ALB chaining is valid and gives you static IP plus smart HTTP routing. ALB → NLB is not supported.

❌ Common mistake: Trying to put an ALB in front of an NLB. This is not supported. If you need a static IP at the edge, start with an NLB, then chain to an ALB for HTTP routing.

🎓 Exam Tips & Key Facts

⚡ High-frequency exam topics from this session:

  • ALB operates at Layer 7; NLB operates at Layer 4 of the OSI model.
  • ALB routes based on URL path, HTTP headers, query strings, and HTTP method.
  • NLB routes based on IP address and port only — it cannot inspect HTTP content.
  • NLB supports Elastic IP addresses; ALB does not — ALB uses a DNS name with dynamic IPs.
  • NLB can forward traffic to ALB, but ALB cannot forward traffic to NLB.
  • A Launch Template defines the configuration used by Auto Scaling to launch new instances.
  • ASG desired capacity is the target instance count; the ASG always works to match actual count to desired.
  • When an instance fails health checks in a target group, the ALB stops sending traffic to it automatically.
  • Health check failure returns 503 to the end user if no healthy targets exist in a target group.
  • Every ALB listener must have a default rule as a fallback for unmatched requests.

💡 Memory trick for OSI layers: "Please Do Not Throw Sausage Pizza Away" — Physical, Data Link, Network, Transport, Session, Presentation, Application. ALB = Application (Layer 7), NLB = Transport (Layer 4).

📝 Overall Summary
  • Application Load Balancer (ALB): Operates at Layer 7, reads full HTTP requests, routes based on URL path, headers, query strings, and method.
  • Path-Based Routing: A single ALB can route /products, /cart, and /orders to three completely separate target groups and backend services.
  • Listener Rules: Conditions (what to match) + Actions (what to do). Evaluated in priority order. Every listener must have a default rule.
  • Target Groups: Logical groupings of backend instances. Each group has its own health check. ALB only sends traffic to healthy targets.
  • Auto Scaling Groups (ASG): Automatically add or remove EC2 instances based on demand. Requires a Launch Template to define what to launch.
  • ASG Capacity: Minimum (floor), Maximum (ceiling), Desired (current target). ASG always reconciles actual count to desired.
  • Scaling Policies: Target Tracking (simplest, recommended), Step Scaling (granular), Scheduled (time-based), Predictive (ML-driven).
  • ASG + ALB Integration: New instances are automatically registered with the target group. Terminated instances are deregistered before shutdown. No dropped requests.
  • Network Load Balancer (NLB): Operates at Layer 4, routes based on IP + port only. Ultra-low latency, supports static/Elastic IP, ideal for TCP/UDP.
  • ALB vs NLB Chaining: NLB → ALB is valid (static IP + smart routing). ALB → NLB is not supported.

🟢 Level 1 — Foundation

Start simple. No overthinking. The goal is to touch AWS and build confidence — not to build anything complex yet.

Project 1: Static Website + ALB

🎯 Objective: Launch 2 EC2 instances serving identical HTML pages and put one ALB in front. Understand basic load balancing behavior by watching traffic switch between servers on refresh.

⏱️ Time: 30–40 min

💰 Cost: t2.micro free tier eligible. ALB ~$0.008/hr — delete after.

💰 Cost Note: Application Load Balancers are NOT free tier eligible. Delete the ALB when done to stop charges.

  1. Launch EC2 Instance A: Amazon Linux 2, t2.micro. In User Data paste:

    #!/bin/bash
yum update -y
yum install -y httpd
systemctl start httpd
systemctl enable httpd
echo "<h1>Hello from Server A</h1>" > /var/www/html/index.html

    Figure 1: 📸 User Data field for Instance A — note 'Server A' in the echo line

  2. Launch EC2 Instance B the same way, but change the echo to "<h1>Hello from Server B</h1>". Tag both instances clearly: Name = Server-A and Name = Server-B.

  3. Create a Target Group: EC2 → Load Balancing → Target Groups → Create target group. Name: basic-alb-tg, protocol HTTP, port 80. Health check path: /. Register both instances.

    Figure 2: 📸 Both instances registered and showing healthy in the target group

  4. Create an Application Load Balancer: Internet-facing, HTTP:80 listener, select 2+ AZs. Default action: forward to basic-alb-tg.

  5. Copy the ALB DNS name. Open it in your browser. Refresh 5–10 times. You should see the response alternate between "Server A" and "Server B".

    Figure 3: 📸 Browser showing Server A response — refresh to see Server B appear

✅ What you learned: The ALB distributes requests across both instances in round-robin fashion. Neither server knows about the other — the ALB is the traffic coordinator.

Project 2: Health Check Failure Simulation

🎯 Objective: Stop Apache on one instance and watch the ALB automatically stop routing traffic to it. Health checks are not theory — they actively control traffic.

⏱️ Time: 15–20 min (uses setup from Project 1)

💰 Cost: Continuation of Project 1 — ALB still running

  1. SSH into Server B. Stop the Apache web server:

    sudo systemctl stop httpd

  2. In the AWS console, navigate to your target group basic-alb-tg → Targets tab. Wait 1–2 minutes and watch Server B's health status change from healthy to unhealthy.

    Figure 4: 📸 Server B now shows unhealthy — ALB has automatically removed it from rotation

  3. Refresh the ALB URL in your browser 10 times. Every response should now say "Server A" — the ALB has completely stopped sending traffic to the unhealthy Server B.

  4. SSH back into Server B and restart Apache:

    sudo systemctl start httpd

    Watch the health status return to healthy in the console. Traffic resumes automatically.

✅ What you learned: Health checks are the mechanism that makes ALB self-healing. No human had to intervene — the ALB detected the failure and rerouted traffic automatically.

Project 3: Manual Scaling (Feel the Pain)

🎯 Objective: Manually add a third EC2 instance and register it with the target group. Feel how slow and error-prone manual scaling is — this pain is intentional. It motivates Auto Scaling Groups.

⏱️ Time: 20–25 min

💰 Cost: Third EC2 t2.micro (free tier) + ongoing ALB

  1. Launch EC2 Instance C with the same User Data as before but echo "<h1>Hello from Server C</h1>". Wait for it to reach running state.

  2. Navigate to your target group basic-alb-tg → Targets tab → Register targets. Select Instance C → Include as pending below → Register pending targets.

    Figure 5: 📸 Manually registering Instance C — note how many steps this takes compared to what ASG does automatically

  3. Wait for Instance C to pass health checks. Refresh the ALB URL — you should now see three possible responses: Server A, Server B, and Server C.

  4. Reflect: You just manually tracked down an instance, went to a separate console page, clicked through registration steps, and waited. Now imagine doing this 20 times during a traffic spike at 2am. This is why Auto Scaling Groups exist.

⚡ The lesson: Manual scaling is operationally fragile. It requires human attention, is slow, and introduces risk. ASG automates this entire process in seconds.

Cleanup: Terminate Instance C. Deregister it from the target group. Keep Instances A and B for Level 2.

Project 4: Full Path-Based Routing System

🎯 Objective: Build a microservices simulation — one ALB routing /products, /cart, and /orders to three separate EC2 instances. This is your first real microservice architecture.

⏱️ Time: 45–60 min

💰 Cost: 3x t2.micro free tier + ALB ~$0.008/hr

💰 Cost Note: Delete the ALB when done with Levels 2 experiments to avoid ongoing charges.

  1. Launch three EC2 instances with the following User Data scripts:

    Products instance:

    #!/bin/bash
yum update -y && yum install -y httpd

    Cart instance:

    #!/bin/bash

mkdir -p /var/www/html/cart
echo "<h1>Cart Service</h1><p>Managing shopping cart</p>" > /var/www/html/cart/index.html

    Orders instance:

    #!/bin/bash

mkdir -p /var/www/html/orders
echo "<h1>Orders Service</h1><p>Processing orders</p>" > /var/www/html/orders/index.html

  2. Create three target groups: products-tg (health check: /products/index.html), cart-tg (health check: /cart/index.html), orders-tg (health check: /orders/index.html). Register each instance with its respective target group.

    Figure 6: 📸 All three target groups created — each with 1 healthy target

  3. Create a new ALB named microservices-alb. Add listener rules (EC2 → Load Balancers → select ALB → Listeners → View/edit rules):

    • Priority 1: Path is /products* → Forward to products-tg
    • Priority 2: Path is /cart* → Forward to cart-tg
    • Priority 3: Path is /orders* → Forward to orders-tg

    Figure 7: 📸 Four listener rules configured — three path rules plus a 404 default

  4. Test all three paths in your browser:

    • http://[ALB-DNS]/products/index.html → Products Service
    • http://[ALB-DNS]/cart/index.html → Cart Service
    • http://[ALB-DNS]/orders/index.html → Orders Service

✅ What you learned: One ALB, one DNS name, three completely separate backend services. This is how every modern web company routes traffic to microservices.

Project 5: Break It Intentionally

🎯 Objective: Deliberately misconfigure things to understand why 503s happen and how routing fails. Most people skip this. That's why they get stuck in production.

⏱️ Time: 20–30 min (uses Project 4 setup)

💰 Cost: No additional cost

  1. Experiment A — Wrong health check path: Edit the products-tg target group. Change the health check path from /products/index.html to /wrong-path. Wait 2 minutes. The instance will become unhealthy. Try accessing /products/index.html — you'll get a 503. Fix it back and watch the instance recover.

    Figure 8: 📸 Wrong health check path causes the instance to appear unhealthy even though the app is running fine

  2. Experiment B — Misconfigured path rule: Edit listener rule Priority 1. Change the path condition from /products* to /product* (remove the 's'). Now try accessing /products/index.html — it matches the new rule and routes correctly, but /products-sale/index.html would not. Try a path like /productx/ and see what happens. Restore the rule.

  3. Experiment C — Trigger a real 503: Stop Apache on the Products instance (sudo systemctl stop httpd). Wait for unhealthy status. Access /products/index.html — you get a 503 Service Unavailable from the ALB directly.

    Figure 9: 📸 Real 503 error — the ALB returns this when no healthy targets exist in the target group

    Restart Apache and watch the 503 disappear.

✅ What you learned: 503s have specific causes — wrong health check paths, stopped services, or misconfigured rules. You now know how to diagnose each one.

Project 6: Default Rule Experiment

🎯 Objective: Hit paths that match no rule and observe exactly what the default rule does. Understand that every request gets a response — the question is what response.

⏱️ Time: 10 min (uses Project 4 setup)

💰 Cost: No additional cost

  1. Using the Project 4 ALB, visit these URLs and note the response each time:

    • http://[ALB-DNS]/random → should hit default rule (404)
    • http://[ALB-DNS]/ → default rule
    • http://[ALB-DNS]/Products (capital P) → does it match /products*? Try it.
    • http://[ALB-DNS]/products-old → does the wildcard /products* match?

    Figure 10: 📸 /random hits the default rule and returns 404 — no service handles this path

  2. Now change the default rule action: edit listener → Default rule → change from "Return fixed response 404" to "Forward to products-tg". Visit /random again — now you get the Products page as fallback.

  3. Restore: Set the default back to 404 fixed response.

⚡ Burn this in: Path matching is case-sensitive and exact prefix. /Products does NOT match /products*. Every request hits exactly one rule. The default rule is always the last resort.

Project 7: Your First Auto Scaling Group

🎯 Objective: Create a Launch Template, build an ASG with min=1 desired=2 max=4, attach it to a target group, and watch instances auto-register with the ALB. That moment matters.

⏱️ Time: 30–40 min

💰 Cost: t2.micro free tier + ALB. Delete after.

  1. Create a Launch Template: EC2 → Launch Templates → Create launch template. Name: web-launch-template. AMI: Amazon Linux 2. Instance type: t2.micro. User Data:

    #!/bin/bash
yum update -y && yum install -y httpd
systemctl start httpd && systemctl enable httpd
INSTANCE_ID=$(curl -s http://169.254.169.254/latest/meta-data/instance-id)
echo "<h1>Auto-Scaled Instance: $INSTANCE_ID</h1>" > /var/www/html/index.html

    💡 This script fetches the actual instance ID from EC2 instance metadata and puts it in the page — so you can see which instance served each request when refreshing.

    Figure 11: 📸 Launch Template User Data — the metadata URL fetches the real instance ID dynamically

  2. Create a target group asg-demo-tg: HTTP, port 80, health check path /. Do NOT register any instances manually — the ASG will do this.

  3. Create the Auto Scaling Group: EC2 → Auto Scaling Groups → Create Auto Scaling group. Name: web-asg. Select web-launch-template. Choose 2 subnets in different AZs. Attach to asg-demo-tg. Enable ELB health checks. Set: Min=1, Desired=2, Max=4.

    Figure 12: 📸 ASG capacity settings — desired of 2 means it will immediately launch 2 instances

  4. Click Create. Immediately navigate to asg-demo-tg → Targets tab. Watch instances appear and transition from initial → healthy without you doing anything.

    Figure 13: 📸 Two instances auto-registered — the ASG did this with no manual registration step

  5. Create a simple ALB with this target group. Refresh the ALB URL several times — you'll see different instance IDs, confirming both instances are serving traffic.

✅ The moment that matters: You watched instances appear in a target group without touching anything. That's ASG. This is what makes scalable architecture possible at any scale.

Project 8: Load Simulation — Watch ASG Scale Out

🎯 Objective: Simulate CPU load and watch the ASG launch new instances automatically. This is where "theory" stops and real behavior begins.

⏱️ Time: 30–40 min (uses Project 7 ASG)

💰 Cost: Extra EC2 instances will launch during test — watch the ASG max setting

  1. First, update the ASG scaling policy to Target Tracking on CPU at 30% (low threshold so it triggers easily in a demo). EC2 → Auto Scaling Groups → web-asg → Automatic scaling tab → Create dynamic scaling policy → Target tracking → CPU utilization → target 30%.

  2. SSH into one of the running instances. Install and run the stress tool to spike CPU:

    sudo yum install -y stress
stress --cpu 4 --timeout 300

    This runs 4 CPU-intensive threads for 5 minutes.

    Figure 14: 📸 Stress tool running — CPU spikes immediately. CloudWatch will detect this and trigger scaling.

  3. Navigate to: EC2 → Auto Scaling Groups → web-asg → Activity tab. Within 3–5 minutes, you'll see a new scaling activity entry: "Launching a new instance."

    Figure 15: 📸 ASG Activity tab showing the scale-out event — note the CloudWatch alarm listed as the cause

  4. Navigate to the target group — a new instance will appear and become healthy. The ALB immediately starts sending it traffic.

✅ What you learned: The ASG → CloudWatch → scale-out loop is fully automated. You triggered load, the system responded. No human intervention.

Project 9: Scale-In Behavior — Watch ASG Clean Up

🎯 Objective: Let the CPU load from Project 8 finish (or stop it manually) and watch ASG scale back in, terminating the extra instances it launched.

⏱️ Time: 15–20 min (continues Project 8)

💰 Cost: No additional — you're reducing instances

  1. Stop the stress tool on the SSH session (Ctrl+C or wait for the timeout). CPU will drop back to near 0%.

  2. Wait 10–15 minutes. CloudWatch needs to see sustained low CPU before triggering scale-in (it uses a longer cooldown to prevent oscillation).

  3. Watch the ASG Activity tab. A new entry will appear: "Terminating instance i-xxxx" — this is the scale-in event.

    Figure 16: 📸 ASG scale-in event — the extra instance is terminated, returning to desired capacity of 2

  4. Check the target group — the terminated instance disappears automatically. The ALB stops routing to it before termination (connection draining).

⚡ Key insight: ASG scale-in uses a longer cooldown than scale-out (default: 300 seconds). This prevents "thrashing" where it scales out then immediately back in. The system is deliberately conservative about removing capacity.

💰 Cost: 3x ASG (min=1, so 3 instances minimum) + ALB. This is the most expensive lab — delete promptly after.

💰 Cost Note: With 3 ASGs each at min=1, you'll be running at least 3 instances plus an ALB. Budget ~$0.05/hr total. Complete this project in one sitting and clean up immediately.

  1. Create three Launch Templates with distinct User Data (one for each service). Each template's User Data should display which service it is. Use the instance-ID metadata trick from Project 7 for each.

  2. Create three ASGs: products-asg, cart-asg, orders-asg. Each with min=1, desired=1, max=3. Each attached to its own target group. Each with a Target Tracking scaling policy (CPU target: 50%).

Project 11: Uneven Traffic Simulation

🎯 Objective: Hammer the Products service with load while leaving Cart and Orders idle. Watch only the Products ASG scale — Cart and Orders stay at min capacity. This is the "aha moment" for per-service scaling.

⏱️ Time: 30–40 min (uses Project 10 setup)

💰 Cost: Extra Products instances during test

  1. Lower the Products ASG scaling policy CPU target to 20% so it triggers quickly. Leave Cart and Orders at 50%.

  2. SSH into the Products EC2 instance. Run the stress tool:

    sudo yum install -y stress
stress --cpu 4 --timeout 300

  3. Watch the three ASGs side by side in the console. After a few minutes:

    • products-asg: desired increases from 1 → 2 or 3
    • cart-asg: stays at 1 (no load)
    • orders-asg: stays at 1 (no load)

    Figure 18: 📸 Only products-asg scaled out — cart and orders are unaffected. Per-service scaling in action.

✅ The big "aha": If this were a monolith, you'd have to scale everything together — wasting money scaling the cart server when only products is busy. With per-service ASGs, you pay only for what's actually under load.

Project 12: Multi-AZ Deployment + AZ Failure Simulation

🎯 Objective: Deploy instances across 2 Availability Zones. Then stop all instances in one AZ. System still works. This is high availability in action.

⏱️ Time: 30–40 min

💰 Cost: Slightly more instances (2 AZs × services)

  1. Update each ASG to have desired=2, min=2. Make sure each ASG is configured across two subnets in different AZs (e.g., us-east-1a and us-east-1b). ASG will place one instance in each AZ.

  2. Verify the target group shows instances from both AZs by checking the instance details (Availability Zone column in the Targets tab).

    Figure 19: 📸 Targets spread across two AZs — the ALB routes to both

  3. Simulate AZ failure: manually stop the instances in us-east-1a (select instances → Instance State → Stop). Do not terminate — just stop.

  4. Immediately refresh the ALB URL. The application still responds — traffic is now flowing only to us-east-1b.

  5. Watch the ASG Activity tab. ASG detects the unhealthy instances and launches replacements — but since us-east-1a instances are stopped (not terminated), ASG may try to replace them. Let it. You're now watching automatic failure recovery.

✅ What you learned: Multi-AZ is not just a checkbox. It's the difference between your application surviving an AZ outage and going down. ALB automatically routes around unhealthy AZ instances.

Project 13: NLB → ALB Real Use Case (Static IP + Smart Routing)

🎯 Objective: Create an NLB with a static Elastic IP in front of your ALB. Understand why this pattern exists and when ALB alone is not enough.

⏱️ Time: 30–40 min

💰 Cost: NLB ~$0.008/hr + Elastic IP (free when attached to running resource) + ALB

  1. Allocate an Elastic IP: EC2 → Network & Security → Elastic IPs → Allocate Elastic IP address. Note the IP address.

    Figure 20: 📸 Freshly allocated Elastic IP — this is the static IP that won't change

  2. Create a Network Load Balancer: EC2 → Load Balancers → Create load balancer → Network Load Balancer. Name: edge-nlb. Internet-facing. Select 1 subnet in your AZ. Under Elastic IP for that AZ, select the Elastic IP you just allocated.

  3. Create a target group for the NLB: type = Application Load Balancer (not instances). Protocol TCP, port 80. Select your existing microservices-alb as the target.

    Figure 21: 📸 NLB target group pointing to the ALB — this is the chaining configuration

  4. Complete NLB creation with the TCP:80 listener forwarding to this target group.

  5. Test: access the Elastic IP directly in your browser (http://[ELASTIC-IP]/products/index.html). The request flows: Elastic IP → NLB → ALB → products-tg → EC2 instance.

  6. The point: Your firewall team can whitelist this single Elastic IP. The ALB behind it handles all the intelligent routing. You got both static IP and smart routing.

  7. Cleanup: Delete NLB → Release Elastic IP (or you'll be charged for an unattached EIP).

Project 14: Sticky Sessions Test

🎯 Objective: Enable session stickiness on a target group and observe that every request from your browser goes to the same instance. Then disable it and see traffic distributed again. Understand when this helps and when it hurts.

⏱️ Time: 15–20 min (uses Project 7 ASG setup with 2 instances)

💰 Cost: No additional

  1. Navigate to the target group used by your ALB (with 2 instances running). Go to the Attributes tab → Edit. Enable Stickiness: type = Load balancer generated cookie, duration = 1 day.

    Figure 22: 📸 Stickiness enabled — the ALB will now set an AWSALB cookie to pin users to an instance

  2. Refresh the ALB URL many times. Notice you always see the same instance ID. Open DevTools (F12) → Application → Cookies → look for the AWSALB cookie set by the load balancer.

    Figure 23: 📸 AWSALB cookie in the browser — this cookie is how the ALB knows which instance to stick you to

  3. Open the same URL in a different browser or incognito window. You'll get a different instance — a different sticky session.

  4. Return to Target Group Attributes → disable stickiness. Refresh from your original browser — now traffic alternates again as the cookie is ignored.

⚡ Important caveat: Sticky sessions create uneven load distribution. If Instance A gets stuck with many high-traffic users, it gets overloaded while Instance B sits idle. The architectural solution is to make your application stateless and store sessions externally in ElastiCache or DynamoDB.

Project 15: Blue-Green Deployment

🎯 Objective: Deploy a new version of your application to a "green" target group while the "blue" target group serves production. Switch traffic instantly with a single listener rule change. Learn zero-downtime deployment.

⏱️ Time: 40–50 min

💰 Cost: Runs 2 sets of instances briefly. Clean up the blue group after switching.

  1. Your existing target group is Blue (current production). Create a new set of EC2 instances with updated content — change the echo line to something like "<h1>Version 2.0 — Green</h1>". Register them in a new target group called green-tg.

  2. Verify the green target group is healthy (all instances pass health checks) before touching production traffic.

    Figure 24: 📸 Green target group healthy and ready — NEVER switch traffic until this is confirmed

  3. Update the ALB listener default rule (or the relevant path rule): change the action from "Forward to blue-tg" to "Forward to green-tg". Click Save.

  4. Immediately refresh your browser. You're now on Green (v2.0). The switch took milliseconds. Zero downtime.

  5. If something goes wrong: change the listener rule back to blue-tg. Instant rollback. Blue is still running — you haven't deleted it.

  6. Once confident in Green: terminate the Blue instances and delete the blue target group. Green is now production.

✅ What you learned: Blue-green deployment is the industry standard for zero-downtime releases. The key: both environments run simultaneously until the switch. The ALB is the switch. The old version stays alive as an instant rollback option.

Project 16: Canary Deployment (Advanced Traffic Splitting)

🎯 Objective: Route 10% of traffic to a new version while 90% continues hitting the old version. Real companies use this to test new releases on a small percentage of users before full rollout.

⏱️ Time: 30–40 min

💰 Cost: Two sets of instances running simultaneously

  1. You need two target groups: stable-tg (current version, instances showing "Stable v1") and canary-tg (new version, instances showing "Canary v2"). Both should have healthy instances.

  2. In the ALB listener rules editor, create a forwarding rule with weighted target groups: select the rule → Action: Forward to → click "Add target group" → set weights: stable-tg = 90, canary-tg = 10.

    Figure 25: 📸 Weighted forwarding — 90% to stable, 10% to canary. One rule, two destinations.

  3. Refresh the ALB URL many times (try 20+). You should see approximately 1-2 out of every 10 requests return "Canary v2". The exact ratio won't be perfect at small sample sizes but the distribution is correct statistically.

  4. Experiment with different weight ratios: 50/50, then 75/25, then 100/0 (full cutover to canary). Watch the response distribution change.

  5. Rollback test: Change canary weight to 0 and stable to 100. 100% of traffic returns to stable instantly — your canary release has been pulled without any downtime.

✅ What you learned: Canary deployments let you expose a new version to a small percentage of real users to catch bugs before they affect everyone. Combined with CloudWatch monitoring, you roll forward if metrics look good, roll back if they don't — all without downtime.

🤔 Reflection Questions

1. You have a web application where the login page gets 10x more traffic than any other page. How would you use ALB and ASG together to handle this efficiently?

💡 Hint

Think about path-based routing to separate the login service into its own target group, then attach an ASG specifically for that service with aggressive scaling policies.

2. A client says "My API needs a static IP address because our enterprise firewall only whitelists specific IPs." Which load balancer would you recommend, and how would you set it up?

💡 Hint

ALB uses dynamic DNS — its IP can change. NLB supports Elastic IPs. But if you also need HTTP routing, think about chaining them.

3. Your ASG is set to min=2, desired=4, max=10. CPU spikes to 95%. What happens? Walk through the sequence of events from the CloudWatch alarm to traffic reaching the new instance.

💡 Hint

Think: CloudWatch alarm → scaling policy triggered → ASG increases desired → launch template used → instance launches → registers with target group → health check → traffic sent.

4. Why can an NLB forward to an ALB, but an ALB cannot forward to an NLB? What is the architectural reason?

💡 Hint

Think about what each layer knows about the request. An NLB at Layer 4 doesn't inspect HTTP — it just sees TCP connections. An ALB has already terminated the HTTP connection, so handing off a TCP stream to an NLB after the fact doesn't make sense architecturally.

5. If all instances in a target group fail their health checks simultaneously, what does the ALB return to end users? How would you prevent this scenario?

💡 Hint

503 Service Unavailable. Prevention: multiple AZs, ASG with minimum > 0, health check tuning to avoid false failures, circuit breaker patterns.
