🚀 Introduction

You've already learned how to create an Auto Scaling Group and how Load Balancers distribute traffic across your EC2 instances. But here's a question — how does AWS know when an instance has gone bad and needs to be replaced? And once it knows, how does it decide how many new instances to spin up?

That's exactly what today's session answers. We're going deep into two core capabilities of Auto Scaling Groups: Health Checks (how ASG detects sick instances) and Scaling Policies (how ASG decides to scale up or down).

Figure 1: How health checks and scaling policies work together inside an Auto Scaling Group

⚡ Key Idea: Auto Scaling Groups are not just about launching instances — they are about keeping the right number of healthy instances running at all times. Health checks and scaling policies are what make that possible.

What You Will Learn

  • How ASG uses EC2 health checks to detect failed instances
  • How Elastic Load Balancer health checks give ASG smarter detection
  • The difference between Simple Scaling and Step Scaling
  • When to use each scaling policy in real production environments
  • How CloudWatch alarms trigger scaling actions
  • Best practices for health check grace periods

💡 Prerequisites: This session builds on Auto Scaling Groups (ASG), Launch Templates, and Elastic Load Balancers (ELB). If you're unclear on any of these, review those sessions first before continuing here.

🏥 Health Checks — How ASG Detects Sick Instances

Imagine you have a fleet of 10 EC2 instances running your application behind a Load Balancer. What if instance #4 crashes? Or what if it's technically running but your web application on it is broken? AWS needs a way to detect this automatically — and that's what health checks do.

Think of health checks like a doctor visiting each instance periodically. The doctor asks "are you alive and doing your job?" If the answer is no, the Auto Scaling Group fires that instance and hires a replacement.

Figure 2: Two types of health checks — system-level (EC2) and application-level (ELB)

EC2 Health Checks — Always On

The first type of health check is built into every Auto Scaling Group — you cannot turn it off. EC2 health checks monitor the system status and instance status of each EC2 instance in the group.

These checks happen at the hypervisor and infrastructure level. They detect problems like:

  • The physical host machine has failed (hardware issue)
  • The network card has lost connectivity
  • The instance is stuck in a reboot loop
  • The system has run out of memory and crashed entirely

💡 Analogy: EC2 health checks are like checking whether a person has a heartbeat. They only tell you if the person is alive at a basic biological level — not whether they're doing their job properly.

When an EC2 health check fails, the ASG marks the instance as Unhealthy, terminates it, and launches a replacement automatically.

EC2 health checks check the status of the EC2 instance itself — not whether your application inside it is working. This is the key limitation of EC2-only health checks.

ELB Health Checks — Recommended

The second type is the Elastic Load Balancing health check, and it's significantly smarter. When ELB health checks are enabled, the Load Balancer periodically sends a request to a specific health check endpoint (like /health) on each instance and checks for a valid HTTP response.

Figure 3: ELB health check flow — from request to ASG replacement

This means the Load Balancer is checking:

  • Is the application actually responding to requests?
  • Is it returning the correct HTTP status code (usually 200)?
  • Is the response within the acceptable time window?

An instance can pass EC2 health checks but fail ELB health checks — this happens when the EC2 instance is running fine but the application inside it has crashed or is misbehaving. This is why ELB health checks are strongly recommended for production environments.

📸 From Session: The AWS Console showing EC2 health checks as always enabled and the option to turn on ELB health checks (recommended)

⚡ When ELB health checks are enabled, AWS shows a warning: "EC2 Auto Scaling will start to detect and act on health checks performed by Elastic Load Balancing. To avoid unexpected terminations, first verify the settings of these health checks in the Load Balancer console."

This is important — before enabling this, make sure your Load Balancer target group health check is configured correctly. Otherwise, ASG might start terminating healthy instances if the health check endpoint doesn't exist.

Health Check Grace Period

Here's an important gotcha — when ASG launches a new instance, that instance needs time to boot up, install software, and start serving traffic. If health checks fire during this startup window, the instance will fail the check and get immediately terminated — even though it was perfectly fine and just wasn't ready yet.

The health check grace period is the amount of time (in seconds) that ASG waits after launching a new instance before it starts running health checks on it.

📚 According to AWS documentation, the default grace period is 300 seconds (5 minutes). If your instances take longer to boot (e.g., they run a large startup script), you should increase this value accordingly.

📚 Source: AWS Auto Scaling Health Check Grace Period Docs

✅ Best Practice: Set the grace period to at least 60 seconds more than your typical instance startup time. If your app takes 3 minutes to start, set grace period to 240 seconds (4 minutes).

⏰ CloudWatch Alarms — The Trigger for Scaling

Before we talk about scaling policies, you need to understand the engine that drives them: Amazon CloudWatch Alarms.

Think of CloudWatch as a security camera that's always watching your metrics. You tell it: "If CPU goes above 70% for 5 minutes, alert me." When that alarm fires, it can trigger an Auto Scaling action — like "add 2 more instances."

Figure 4: How CloudWatch alarms connect to Auto Scaling Group scaling actions

Both Simple Scaling and Step Scaling policies are triggered by CloudWatch Alarms. The alarm watches a metric (like CPU utilization, network traffic, or a custom metric) and fires when it crosses a threshold you define.

CloudWatch Alarm States

A CloudWatch alarm is always in one of three states:

  • OK: The metric is within the defined threshold — no action needed.
  • ALARM: The metric has breached the threshold — triggers the scaling action.
  • INSUFFICIENT_DATA: Not enough data points yet to evaluate the alarm (common right after creation).

💡 Example: You create a CloudWatch alarm: "If average CPU utilization > 70% for 2 consecutive 5-minute periods, go to ALARM state." When your instances get busy and CPU hits 80% for 10 minutes, the alarm fires and tells the ASG to scale out.

📈 Scaling Policies — Simple vs Step Scaling

Now that you understand health checks and CloudWatch alarms, let's talk about the most important question: when an alarm fires, exactly how many instances does ASG add or remove?

The answer depends on the Scaling Policy you configure. AWS offers several types, but the two you need to understand thoroughly for both production use and exams are Simple Scaling and Step Scaling.

📸 From Session: Professor's comparison table — Simple Scaling vs Step Scaling

Simple Scaling — The Basics

Simple scaling is exactly what it sounds like — simple. With Simple Scaling, when a CloudWatch alarm fires, the ASG adds or removes a fixed number of instances, regardless of how bad the alarm condition is.

For example: "When CPU > 70%, add 2 instances." It doesn't matter if CPU is 71% or 99% — you always get exactly 2 more instances.

💡 Analogy: Simple scaling is like a thermostat that only has one setting — "too hot? Open one window." Whether it's 1 degree too hot or 20 degrees too hot, you open exactly one window. It's better than nothing, but not very smart.

After a Simple Scaling action executes, there is a cooldown period during which no further scaling actions occur, even if the alarm is still firing. The default cooldown is 300 seconds.

Figure 5: Simple Scaling — fixed response with cooldown period

When to use Simple Scaling:

  • Learning environments, demos, and proof-of-concept setups
  • Very predictable, uniform workloads where load spikes are always similar in size
  • When you want the simplest possible configuration to get started

Limitations of Simple Scaling:

  • Cannot respond proportionally to the severity of the alarm
  • Cooldown period means it can't react quickly to rapidly escalating load
  • In a real production burst, it may always be slightly under-provisioned

Step Scaling — Smarter Responses

Step Scaling solves the core problem of Simple Scaling. With Step Scaling, you define multiple step adjustments — each step triggers a different scaling amount based on how much the metric has exceeded the threshold.

Here's a real example:

  • CPU between 60%–70%: Add 1 instance (mild load)
  • CPU between 70%–85%: Add 2 instances (moderate load)
  • CPU above 85%: Add 4 instances (heavy load)

Figure 6: Step Scaling — proportional response based on metric severity

Step Scaling does not have a cooldown period — instead it uses an instance warmup period, allowing it to respond to rapidly changing load conditions much faster than Simple Scaling.

💡 Analogy: Step Scaling is like a smart air conditioner. If the room is slightly warm (1°C over), it runs at low power. If the room is very hot (10°C over), it blasts at maximum. The response matches the severity of the problem.

When to use Step Scaling:

  • Production environments with variable traffic patterns
  • Applications where load can spike sharply (e-commerce during a sale, news sites during breaking events)
  • Any scenario where you need fine-grained, proportional scaling responses

✅ Exam Tip: If a scenario asks "which scaling policy responds proportionally to the severity of the alarm?" — the answer is always Step Scaling. If it asks "which has a cooldown period?" — the answer is Simple Scaling.

🔄 Other Scaling Policy Types

Beyond Simple and Step Scaling, AWS offers three more scaling policy types. These are important to know for exams and for designing production systems.

Figure 7: All five Auto Scaling policy types and when to use each

Target Tracking Scaling — The Smartest

Target Tracking Scaling automatically adjusts the number of instances to keep a specific metric at a target value you define.

Example: "Keep average CPU at 50%." AWS figures out how many instances are needed to achieve this — you don't define the scaling amounts at all. It's like cruise control for your infrastructure.

💡 This is the most recommended policy for most production use cases. AWS manages the scale-out and scale-in logic automatically, reducing configuration complexity while providing excellent responsiveness.

Scheduled Scaling — Plan Ahead

Scheduled Scaling adjusts the minimum and maximum instance count at specific scheduled times — like a recurring calendar entry for your infrastructure.

Example: "Every Monday–Friday at 8 AM, increase to 10 instances. At 8 PM, scale back to 2 instances." This is perfect for predictable business-hours traffic patterns.

Predictive Scaling — Machine Learning

Predictive Scaling uses machine learning to analyze historical traffic patterns and proactively provision instances before demand actually arrives.

Example: If your application gets a traffic spike every Friday evening at 6 PM, Predictive Scaling recognizes this pattern and starts spinning up extra instances at 5:30 PM — before the spike hits. You're always ahead of demand, never playing catch-up.

✅ Quick Decision Guide:
Use Target Tracking as your default for most production systems.
Add Scheduled Scaling for predictable time-based patterns.
Add Predictive Scaling when you have at least 2 weeks of traffic history and recurring patterns.
Use Step Scaling when you need very specific, customized responses.
Use Simple Scaling only for demos and testing.

🗺️ Which Scaling Policy Should You Use?

Choosing the right scaling policy comes down to understanding your traffic pattern and how much control you want. Use this decision tree as your guide:

Figure 8: Decision tree for choosing the right Auto Scaling policy

Scenario Best Policy Why
Traffic spikes unpredictably Target Tracking Automatically adjusts — no manual tuning
Office hours traffic pattern Scheduled Scaling You know exactly when load will come
Daily peaks at same time Predictive Scaling ML learns and provisions ahead of time
Need proportional response to severity Step Scaling Scale more when load is worse
Learning, demo, or lab setup Simple Scaling Easiest to understand and configure

⚖️ Load Balancer Integration with ASG

Auto Scaling Groups and Load Balancers are designed to work together. Without this integration, you'd have to manually register every new instance with the Load Balancer every time ASG launches one — which defeats the whole purpose of automation.

Figure 9: How ASG integrates with Application Load Balancer through Target Groups

When you attach a Load Balancer to an Auto Scaling Group, ASG automatically registers newly launched instances with the Load Balancer's Target Group, and deregisters instances before terminating them.

Connection Draining (Deregistration Delay)

What happens to users who are already connected to an instance when ASG decides to terminate it? This is where Connection Draining (also called Deregistration Delay) becomes important.

Connection Draining allows in-flight requests to complete before the instance is removed from the Target Group. The Load Balancer stops sending new requests to the draining instance but allows existing connections to finish within a configurable timeout.

📚 According to AWS documentation, the default deregistration delay is 300 seconds. You can configure it from 0 to 3600 seconds. Setting it to 0 immediately cuts all connections (not recommended for most apps).

📚 Source: AWS ELB Target Groups Docs

Path-Based Routing — Microservices Use Case

One of the most powerful features of Application Load Balancers is path-based routing. This allows a single Load Balancer to route requests to different Target Groups based on the URL path.

Figure 10: Path-based routing — one Load Balancer routing to multiple microservice Target Groups

This is the backbone of microservices architecture. Think about Amazon.com itself:

  • amazon.com/orders → routed to the Orders service instances (their own ASG)
  • amazon.com/purchase → routed to the Purchase service instances (their own ASG)
  • amazon.com/cart → routed to the Shopping Cart service instances (their own ASG)

With path-based routing, a single Application Load Balancer can front multiple independent microservices, each with their own Target Group and Auto Scaling Group.

💡 Each microservice can scale independently. If orders traffic spikes but cart traffic is low, only the Orders ASG scales out — the Cart instances remain at their current count. This is much more cost-efficient than scaling everything together.

✅ Exam Tip: If a question mentions routing different URL paths to different backends — the answer is Application Load Balancer with path-based routing. Host-based routing (different domains → different backends) is a related concept.

🔄 Instance Lifecycle in an Auto Scaling Group

Understanding the full lifecycle of an EC2 instance inside an ASG is essential for both production troubleshooting and exam success.

Figure 11: Auto Scaling Group instance lifecycle — all states and transitions

Key Lifecycle States

  • Pending: Instance is being launched. Health check grace period starts here. No traffic yet.
  • Pending:Wait: Lifecycle hook is paused here (if configured) — allows custom startup scripts to run before instance joins the group.
  • InService: Instance is healthy and receiving traffic from the Load Balancer.
  • Terminating: Instance is being terminated (either by scaling in, health check failure, or manual action).
  • Terminating:Wait: Lifecycle hook pause before final termination — allows cleanup tasks (draining DB connections, saving state).
  • Terminated: Instance is completely gone.

Instances in the Pending state are protected from health checks during the health check grace period to allow adequate startup time.

🎯 Termination Policies — Who Gets Terminated First?

When ASG needs to scale in (remove instances), it needs to decide which instance to terminate. This is controlled by Termination Policies.

Figure 12: Default termination policy decision flow

The Default Termination Policy first identifies the Availability Zone with the most instances, then selects the instance running on the oldest launch template or configuration.

AWS provides several built-in termination policies:

  • Default: Balances AZs, then picks oldest launch template
  • OldestInstance: Always terminates the oldest instance by launch time
  • NewestInstance: Terminates the newest instance (useful for testing)
  • OldestLaunchTemplate: Terminates instances using the oldest Launch Template version
  • ClosestToNextInstanceHour: Terminates the instance closest to the end of its billing hour (saves money)
  • AllocationStrategy: Works with mixed instances to optimize cost/capacity

📚 According to AWS documentation, you can combine multiple termination policies in a priority list. AWS evaluates them in order until only one instance remains eligible, then terminates that one.

📚 Source: AWS Termination Policies Docs

✅ Auto Scaling Best Practices

✅ Always enable ELB health checks in production — EC2-only health checks will miss application crashes.

✅ Set the grace period appropriately — if your app takes 3 minutes to boot, set grace period to at least 240 seconds.

✅ Use Step Scaling or Target Tracking in production — Simple Scaling is for demos only.

✅ Define min, desired, and max carefully — minimum ensures baseline availability, maximum prevents runaway costs.

✅ Use Connection Draining to prevent dropped requests when instances are terminated.

✅ Spread instances across multiple AZs — ASG does this automatically if you configure multiple subnets in different AZs.

❌ Don't set max too low — if max is the same as desired, ASG can never scale out during spikes.

❌ Don't ignore CloudWatch alarms — if you don't configure scaling policies, alarms are created but nothing happens.

📝 Overall Summary
  • EC2 Health Checks: Always enabled, detect infrastructure-level failures (hardware, network, OS crash).
  • ELB Health Checks: Optional but strongly recommended — detect application-level failures by probing a health endpoint.
  • Health Check Grace Period: Protects new instances from premature termination during startup; default is 300 seconds.
  • Simple Scaling: Fixed response (add N instances) triggered by a CloudWatch alarm; has a cooldown period; best for demos.
  • Step Scaling: Variable response based on alarm severity (more instances when load is worse); uses instance warmup, not cooldown; best for production.
  • Target Tracking: Most automated — you set a target metric value and AWS manages the instance count to hit it.
  • Scheduled Scaling: Time-based scaling for predictable traffic patterns like office hours.
  • Predictive Scaling: Uses ML to forecast demand and provision instances ahead of spikes.
  • Path-Based Routing: One ALB routes different URL paths to different target groups (microservices pattern).
  • Connection Draining: Allows in-flight requests to complete before an instance is removed; default timeout is 300 seconds.

Project 1: Enable ELB Health Checks on an Existing ASG

🎯 Objective: Configure your Auto Scaling Group to use Elastic Load Balancer health checks instead of EC2-only health checks.

⏱️ Time: 15–20 minutes

💰 Cost: Free tier eligible (if using existing resources from prior sessions)

  1. Open the AWS Console and navigate to EC2 → Auto Scaling Groups.

    Figure P1-1: 📸 Navigate to Auto Scaling Groups in EC2 Console

  2. Select your existing Auto Scaling Group from the list and click on its name to open the details page.

  3. Click the Details tab, then scroll down to the Health checks section. Click Edit.

    Figure P1-2: 📸 Health Checks section in ASG Details tab with Edit button

  4. In the Health Checks edit panel, check the box for Turn on Elastic Load Balancing health checks. You should see the Recommended badge next to it.

  5. Read the blue info notice that appears: "EC2 Auto Scaling will start to detect and act on health checks performed by Elastic Load Balancing..." Before saving, open the Load Balancer console link in a new tab and verify your target group health check is configured correctly (protocol, path, port, thresholds).

  6. Set the Health check grace period to 180 seconds (or higher if your application takes longer to start).

  7. Click Update to save the changes.

    Figure P1-3: 📸 Updated Health Checks section showing both EC2 and ELB checks enabled

  8. Verification: Go to EC2 → Target Groups, select your target group, and open the Targets tab. Wait 1–2 minutes and confirm all instances show healthy status. If any show unhealthy, check that your health check path (e.g., / or /health) is returning HTTP 200.

Project 2: Create a Step Scaling Policy

🎯 Objective: Create a Step Scaling policy that adds 1, 2, or 4 instances depending on how high CPU utilization rises.

⏱️ Time: 20–30 minutes

💰 Cost: Free tier eligible. Note: If you actually trigger scaling and run extra instances, standard EC2 charges apply.

💰 Cost Note: When you test Step Scaling by pushing CPU high, ASG may launch additional EC2 instances. Each extra instance incurs EC2 charges. Always remember to clean up by manually setting Desired Capacity back to your baseline after testing.

  1. In the AWS Console, go to EC2 → Auto Scaling Groups and select your ASG.

  2. Click the Automatic scaling tab, then click Create dynamic scaling policy.

    Figure P2-1: 📸 Automatic scaling tab — Create dynamic scaling policy button

  3. For Policy type, select Step scaling.

  4. For Policy name, enter ScaleOut-StepPolicy-CPU.

  5. For CloudWatch alarm, click Create a CloudWatch alarm. This opens CloudWatch in a new tab. Create an alarm with these settings:

    • Metric: EC2 → Per-Instance Metrics → CPUUtilization
    • Statistic: Average
    • Period: 5 minutes
    • Threshold: Greater than 60%
    • Name: HighCPU-ASG-Alarm

  6. Return to the ASG scaling policy tab and select your newly created alarm.

  7. Under Add capacity, create step adjustments:

    • When 60 ≤ CPUUtilization < 70: Add 1 instance
    • When 70 ≤ CPUUtilization < 85: Add 2 instances
    • When CPUUtilization ≥ 85: Add 4 instances

    Figure P2-2: 📸 Step adjustments configured with three steps for mild moderate and severe CPU load

  8. Set Instance warmup to 120 seconds.

  9. Click Create to save the policy.

  10. Verification: The policy should now appear in the Automatic scaling tab. To test it, you can SSH into one of your instances and run stress --cpu 2 --timeout 600 (install with sudo yum install stress -y or sudo apt install stress -y) to push CPU above the threshold and watch ASG respond.

Cleanup Steps

  1. Set the ASG Desired Capacity back to your baseline (e.g., 1 or 2 instances).
  2. Wait for extra instances to terminate and confirm in the Instances tab.
  3. Optionally delete the HighCPU-ASG-Alarm CloudWatch alarm and the Step Scaling policy to keep your account clean.

Project 3: Multi-Step Scaling + Live Stress Testing

🎯 Objective: Configure a 3-step scaling policy and watch it respond to gradual vs sudden load — observing different instance counts added at different CPU severities.

⏱️ Time: 45–60 minutes

💰 Cost: EC2 charges apply when extra instances launch. Use Free Tier or credits. Clean up after.

⚡ What you will prove to yourself: That Step Scaling doesn't just "add instances" — it adds the right number based on how bad things are. You'll run two tests: one gradual, one sudden — and see different outcomes.

Part A — Configure the 3-Step Scaling Policy

  1. Go to EC2 → Auto Scaling Groups → select your ASG → Automatic scaling tab → click Create dynamic scaling policy.

    Figure P3-1: 📸 Automatic scaling tab — ready to create a new policy

  2. Select policy type Step scaling. Name it Step-ScaleOut-CPU.

  3. Click Create a CloudWatch alarm. In CloudWatch, create alarm:

    • Metric: EC2 → Per-Instance Metrics → CPUUtilization
    • Statistic: Average, Period: 1 minute
    • Condition: Greater than 60%
    • Name: ASG-CPU-HighAlarm

    Figure P3-2: 📸 CloudWatch alarm creation — CPUUtilization > 60% condition

  4. Back in the scaling policy, select the ASG-CPU-HighAlarm alarm. Now add step adjustments:

    • 60 ≤ CPU < 70 → Add 1 instance
    • 70 ≤ CPU < 85 → Add 2 instances
    • CPU ≥ 85 → Add 4 instances

  5. Set Instance warmup to 90 seconds. Click Create.

  6. Now create the scale-in policy. Create another dynamic policy:

    • Policy type: Step scaling, name: Step-ScaleIn-CPU
    • Create alarm: CPUUtilization less than 30% for 2 consecutive periods, name: ASG-CPU-LowAlarm
    • Step adjustment: Remove 1 instance when CPU < 30%

    Figure P3-3: 📸 Both scale-out and scale-in step policies now created and enabled

Part B — Test 1: Gradual Load

  1. SSH into one of your EC2 instances. Run a moderate stress load:

    stress --cpu 1 --timeout 300

  2. Open CloudWatch → Alarms. Watch ASG-CPU-HighAlarm. It should hit ALARM within 1–2 minutes at the 60–70% CPU step.

    Figure P3-4: 📸 CloudWatch alarm transitions to ALARM state — scaling triggered

  3. Go to ASG → Activity tab. You should see a new activity entry: "Launching a new EC2 instance" with the reason "Step adjustment: +1 instance."

    Figure P3-5: 📸 ASG Activity log — Step 1 of scaling policy fired, +1 instance launched

  4. Let the stress command finish. CPU drops. Watch ASG-CPU-LowAlarm go to ALARM. ASG removes 1 instance. Observe scale-in in Activity tab.

Part C — Test 2: Sudden Heavy Spike

  1. SSH into your instance and run a heavy load that pushes CPU above 85%:

    stress --cpu 4 --timeout 300

  2. Watch CloudWatch. CPU should exceed 85%. Observe that the Step 3 adjustment fires — ASG tries to add 4 instances (capped at your ASG max).

  3. Compare the Activity tab with Test 1. Notice the difference: same alarm, different step triggered, different number of instances launched.

    Figure P3-6: 📸 Step 3 fired — 4 instances launched for severe CPU spike above 85%

Cleanup

  1. Set ASG Desired Capacity back to 2. Wait for scale-in to complete.
  2. Delete Step-ScaleOut-CPU and Step-ScaleIn-CPU policies.
  3. Delete ASG-CPU-HighAlarm and ASG-CPU-LowAlarm from CloudWatch.

✅ What just clicked: You saw with your own eyes that Step Scaling fires different steps for different severities. One alarm, three outcomes. That's the core power of Step Scaling over Simple Scaling.

Project 4: Target Tracking — Let AWS Decide

🎯 Objective: Replace manual step policies with Target Tracking. Set a CPU target of 50% and let AWS manage instance count automatically. Experience how much simpler — and smarter — this is for production.

⏱️ Time: 30–40 minutes

💰 Cost: EC2 charges when extra instances launch. Clean up after.

⚡ The shift in mindset: With Step Scaling, you decide how many instances to add. With Target Tracking, you tell AWS what you want (keep CPU at 50%) and AWS figures out the how. You move from driver to navigator.

  1. First, go to ASG → Automatic scaling tab. Delete any existing step policies from Project 3 (if still present) so they don't conflict.

  2. Click Create dynamic scaling policy. Select policy type: Target tracking scaling.

  3. Configure the policy:

    • Policy name: Target-CPU-50
    • Metric type: Average CPU utilization
    • Target value: 50
    • Instance warmup: 120 seconds
    • Leave "Disable scale-in" unchecked — we want both scale-out and scale-in

    Figure P4-1: 📸 Target Tracking policy configuration — CPU target 50%

  4. Click Create. AWS automatically creates two CloudWatch alarms for you — one for scale-out and one for scale-in. Go to CloudWatch → Alarms and verify you can see them (they will be named with a TargetTracking prefix).

    Figure P4-2: 📸 Two CloudWatch alarms auto-created by Target Tracking — you didn't create these manually

  5. SSH into your instance. Run a moderate stress test:

    stress --cpu 2 --timeout 600

  6. Watch the ASG Instances tab every 2–3 minutes. You should see instance count rise as AWS tries to bring average CPU down to 50%.

  7. Once stress ends, watch instances terminate as CPU drops below the target. AWS handles scale-in automatically.

    Figure P4-3: 📸 ASG self-adjusting — Target Tracking adding and removing instances to hit the 50% target

✅ What just clicked: You defined a goal, not a rule. AWS watched the metric, calculated how many instances are needed, and acted — without you configuring a single step adjustment. This is how most real production teams configure scaling.

Cleanup

  1. Go to ASG → Automatic scaling. Delete the Target-CPU-50 policy.
  2. The two CloudWatch alarms it created will be auto-deleted when you delete the policy.
  3. Set Desired Capacity back to 2 if needed.

Project 5: Chaos Engineering — Break Things on Purpose

🎯 Objective: Intentionally misconfigure your ASG to produce failures. Observe what breaks, why it breaks, then fix each issue methodically. This builds real debugging instinct.

⏱️ Time: 60–90 minutes

💰 Cost: Minimal — only 2 instances running. Possible replace cycles may briefly add a 3rd. Clean up after.

⚡ Why this matters: Engineers who only build happy-path systems panic in production. Engineers who have intentionally broken things and fixed them — stay calm. That's what this project builds.

Figure P5-1: The three chaos scenarios you will deliberately create and then fix

Chaos Scenario 1 — Wrong Health Check Path

What you'll break: Point the Load Balancer health check at a path that doesn't exist. All instances will fail the ELB check. ASG will start terminating them — even though they're perfectly fine.

  1. Go to EC2 → Target Groups → select your Target Group → Health checks tab → click Edit.

  2. Change the Health check path from / to /this-does-not-exist. Save.

    Figure P5-2: 📸 Deliberately setting a wrong health check path — breaking the ELB health check

  3. Wait 2–3 minutes. Go to Target Group → Targets tab. You will see instances change from healthy to unhealthy.

    Figure P5-3: 📸 All instances marked unhealthy — ELB returning non-200 for /this-does-not-exist

  4. Watch ASG Activity tab. It begins terminating and replacing instances — which also fail and get replaced again. This is an infinite replace loop.

  5. Fix: Go back to Target Group → Health checks → Edit → change path back to /. Save. Wait for instances to show healthy again.

    Figure P5-4: 📸 Health status restored to healthy after correcting the health check path

Chaos Scenario 2 — Slow-Start App + Short Grace Period

What you'll break: Make your app take 3 minutes to start, but keep the grace period at 30 seconds. New instances will be killed before they're ready.

  1. Update your Launch Template. Add a User Data startup delay — edit the existing User Data and append:

    #!/bin/bash
# Existing commands above...
sleep 180   # Simulate 3-minute slow startup
systemctl start nginx

    Save as a new Launch Template version. Update the ASG to use the new version.

  2. Set the ASG health check grace period to 30 seconds: ASG → Details → Health checks → Edit → set grace period to 30.

    Figure P5-5: 📸 Grace period deliberately set to 30 seconds — too short for the slow-start app

  3. Terminate one instance manually so ASG launches a new one from the updated Launch Template. Watch what happens:

    • New instance launches (Pending state)
    • After 30 seconds, health checks run — but nginx hasn't started yet (still sleeping)
    • ELB health check fails → instance marked Unhealthy → terminated
    • New replacement launched — same thing happens again

    Figure P5-6: 📸 Replace loop in action — instances launched and killed repeatedly

  4. Fix: Set grace period to 240 seconds (longer than the 180s sleep). Revert Launch Template User Data to remove the sleep. Update ASG to the clean Launch Template version. Scale-in and re-launch to verify.

Chaos Scenario 3 — Kill the App Process Mid-Traffic

What you'll break: Manually stop nginx while traffic is flowing. Watch ELB detect it and ASG react.

  1. Make sure ELB health checks are enabled on your ASG (from Project 1).

  2. SSH into one of your instances. Stop nginx:

    sudo systemctl stop nginx

  3. Watch the Target Group → Targets tab. Within 30–60 seconds, that instance will show unhealthy.

  4. Watch ASG Activity tab. It will terminate the unhealthy instance and launch a replacement. The replacement will boot with nginx running (from User Data) and join the Target Group healthy.

    Figure P5-7: 📸 ASG auto-replaces the instance where nginx was stopped — self-healing in action

✅ What just clicked: You stopped thinking "happy path." You now know what wrong health check paths, short grace periods, and killed processes look like — and more importantly, how to fix each one. That's real debugging skill.

Cleanup

  1. Restore grace period to 180 seconds.
  2. Restore health check path to /.
  3. Revert Launch Template to the clean version (no sleep in User Data).
  4. Set Desired Capacity to 2 and verify both instances are healthy.

Project 6: Microservices — Two ASGs Behind One ALB

🎯 Objective: Build a real microservices-style architecture: one ALB, two Target Groups, two ASGs. Route /orders to ASG-1 and /users to ASG-2. Stress only the orders service and watch it scale independently while users stays stable.

⏱️ Time: 60–90 minutes

💰 Cost: Two ASGs + one ALB. EC2 charges for instances. Clean up after — this is the most expensive project in the list.

💰 Cost Note: This project runs two ASGs each with 2 instances (4 EC2 instances total) plus one ALB. Even on Free Tier, this can consume credits faster than other projects. Keep the runtime short — 1 hour maximum — and clean up immediately after.

Figure P6-1: Target architecture — one ALB, two Target Groups, two independent ASGs

Part A — Create the Two Launch Templates

  1. Go to EC2 → Launch Templates → Create launch template.

    Launch Template 1 — Orders Service:

    • Name: LT-Orders-Service
    • AMI: Amazon Linux 2
    • Instance type: t2.micro
    • Security Group: allows HTTP (port 80) and SSH (port 22)
    • User Data:
    #!/bin/bash
yum update -y
yum install -y nginx
echo "<h1>ORDERS SERVICE — Instance: $(hostname)</h1>" > /usr/share/nginx/html/index.html
mkdir -p /usr/share/nginx/html/orders
echo "<h1>Orders API — $(hostname)</h1>" > /usr/share/nginx/html/orders/index.html
systemctl enable nginx
systemctl start nginx

  2. Launch Template 2 — Users Service: Repeat the same process with name LT-Users-Service. Change User Data to:

    #!/bin/bash
yum update -y
yum install -y nginx
echo "<h1>USERS SERVICE — Instance: $(hostname)</h1>" > /usr/share/nginx/html/index.html
mkdir -p /usr/share/nginx/html/users
echo "<h1>Users API — $(hostname)</h1>" > /usr/share/nginx/html/users/index.html
systemctl enable nginx
systemctl start nginx

    Figure P6-2: 📸 Both Launch Templates created — one per microservice

Part B — Create Two Target Groups

  1. Go to EC2 → Target Groups → Create target group.

    Target Group 1:

    • Name: TG-Orders
    • Target type: Instances
    • Protocol: HTTP, Port: 80
    • Health check path: /orders/
    • Healthy threshold: 2, Unhealthy threshold: 2, Interval: 10s

  2. Target Group 2: Same settings with name TG-Users and health check path /users/.

    Figure P6-3: 📸 Both Target Groups created with correct health check paths per service

Part C — Create the Two ASGs

  1. Go to EC2 → Auto Scaling Groups → Create Auto Scaling group.

    ASG 1 — Orders:

    • Name: ASG-Orders
    • Launch Template: LT-Orders-Service
    • VPC + 2 Availability Zones (use existing subnets)
    • Attach to Load Balancer: select existing ALB → select TG-Orders
    • Health checks: enable ELB health checks, grace period 120s
    • Min: 1, Desired: 2, Max: 5
    • Add Target Tracking policy: Target-Orders-CPU, CPU target: 60%

  2. ASG 2 — Users: Repeat with name ASG-Users, Launch Template LT-Users-Service, Target Group TG-Users, same capacity settings and Target Tracking at 60% CPU.

    Figure P6-4: 📸 Both ASGs running with 2 instances each — 4 total EC2 instances

Part D — Configure Path-Based Routing on the ALB

  1. Go to EC2 → Load Balancers → select your ALB → Listeners tab → click on the HTTP:80 listener → View/edit rules.

  2. Add two rules above the default rule:

    • Rule 1: IF Path is /orders* → THEN Forward to TG-Orders
    • Rule 2: IF Path is /users* → THEN Forward to TG-Users

    Figure P6-5: 📸 ALB listener rules — path-based routing configured for two microservices

  3. Save the rules. Open a browser and test:

    • http://[ALB-DNS]/orders/ — should show "ORDERS SERVICE"
    • http://[ALB-DNS]/users/ — should show "USERS SERVICE"

    Figure P6-6: 📸 Path-based routing working — /orders and /users routing to separate service instances

Part E — Stress One Service, Watch the Other Stay Stable

  1. SSH into one of your ASG-Orders instances. Run heavy CPU stress:

    stress --cpu 4 --timeout 600

  2. Watch ASG-Orders scale out (new instances launching). Watch ASG-Users — it should stay at 2 instances.

    Figure P6-7: 📸 Independent scaling — Orders service scales out while Users service stays stable

✅ What just clicked: You built what real companies run. One Load Balancer. Multiple independent services. Each one scaling based on its own load. This is the architecture behind every major web platform.

Cleanup (Do This Carefully — In Order)

  1. Delete ASG-Orders and ASG-Users (this terminates all their instances).
  2. Delete TG-Orders and TG-Users Target Groups.
  3. Remove the path-based routing rules from the ALB listener (revert to default rule only).
  4. Delete LT-Orders-Service and LT-Users-Service Launch Templates.

Project 7: Cost Optimization — Min/Max/Cooldown Tuning

🎯 Objective: Start with a poorly configured ASG (too aggressive scaling, wrong cooldown, bloated max) and tune it step by step to minimize unnecessary instance launches while maintaining performance. Learn to think like someone paying the AWS bill.

⏱️ Time: 45–60 minutes

💰 Cost: Minimal — 2–4 instances. Clean up after.

⚡ The mindset shift: Every unnecessary instance launch costs money. A max of 20 instances when your app never needs more than 5 is a misconfiguration. Proper tuning saves real dollars.

Part A — Observe a Poorly Tuned ASG

  1. Configure your ASG with deliberately bad settings:

    • Min: 1, Desired: 1, Max: 20 (way too high)
    • Create a Simple Scaling policy: CPU > 50% → Add 3 instances, Cooldown: 60 seconds (too short)

  2. Run stress for 5 minutes, let it naturally end, then run again. Watch what happens:

    • Short cooldown → alarm refires quickly → more instances added rapidly
    • Max of 20 means uncapped growth
    • After stress ends, scale-in is slow — instances linger

    Figure P7-1: 📸 Over-scaling in action — too many instances launched due to short cooldown and high max

Part B — Tune the Configuration

  1. Apply proper settings based on your stress test observations:

    • Change Max from 20 to 6 (realistic for your app's peak load)
    • Change scaling policy: CPU > 60% → Add 1 instance, Cooldown: 300 seconds
    • Add a scale-in policy: CPU < 30% → Remove 1 instance, Cooldown: 300 seconds

    Figure P7-2: 📸 Tuned ASG — maximum capacity reduced from 20 to 6

  2. Run the same stress test again. Compare:

    • Fewer instances launched at each trigger
    • Cooldown prevents over-scaling during brief spikes
    • Instances scale back in when load drops

Part C — Check CloudWatch Cost Signals

  1. Go to CloudWatch → Metrics → Auto Scaling → select your ASG → view GroupInServiceInstances metric.

    Figure P7-3: 📸 CloudWatch GroupInServiceInstances metric — visualizing scaling over time

  2. Compare the graph from the badly-tuned test (many spikes, slow scale-in) vs the well-tuned test (controlled spikes, faster recovery).

  3. Use the AWS Pricing Calculator to estimate how much extra the overscaling would have cost per month.

✅ What just clicked: You started thinking about the bill. Min, Max, Cooldown, and threshold values aren't just technical settings — they're cost controls. Proper tuning means your system is both reliable and economical.

Cleanup

  1. Delete the Simple Scaling policies.
  2. Set ASG back to Min: 1, Desired: 2, Max: 6 with a Target Tracking policy at 50%.

Project 8: Flash Sale System — Production Simulation

🎯 Objective: Build and test a complete production-grade auto-scaling system simulating a flash sale scenario where traffic jumps from 100 to 10,000 users in minutes. This is a job-interview-level project.

⏱️ Time: 90–120 minutes

💰 Cost: Multiple EC2 instances + ALB. Use credits. Clean up immediately after testing.

⚡ The final boss: This isn't a tutorial. This is a system design challenge you build, test, break, and defend. After this project, you can answer: "Why did scaling fail? Why did users see errors? How do we fix it?" — which is exactly what interviewers ask.

Figure P8-1: Flash Sale system — complete architecture with all layers

Part A — Build the Foundation (ALB + ASG + Health Checks)

  1. Create a Launch Template LT-FlashSale with User Data that installs nginx and creates a simple HTML page showing hostname and timestamp:

    #!/bin/bash
yum update -y
yum install -y nginx
cat > /usr/share/nginx/html/index.html << 'EOF'
<html><body>
<h1>Flash Sale System</h1>
<p>Instance: <?php echo gethostname(); ?></p>
<p>Time: <?php echo date('Y-m-d H:i:s'); ?></p>
</body></html>
EOF
# Health check endpoint
mkdir -p /usr/share/nginx/html/health
echo "OK" > /usr/share/nginx/html/health/index.html
systemctl enable nginx
systemctl start nginx

  2. Create ASG ASG-FlashSale: Min=2, Desired=2, Max=10, attach existing ALB, enable ELB health checks, grace period=120s, Target Group health check path=/health/.

    Figure P8-2: 📸 ASG-FlashSale configured with proper health check settings and capacity bounds

Part B — Layer the Scaling Policies

  1. Layer 1 — Target Tracking (baseline): Create a Target Tracking policy named TT-CPU-50 with CPU target 50%. This handles normal day-to-day traffic.

  2. Layer 2 — Step Scaling (spike response): Create a Step Scaling policy named Step-CPU-Spike on a new alarm FlashSale-HighCPU (CPU > 80%):

    • 80–90% → Add 3 instances
    • 90%+ → Add 6 instances

    Figure P8-3: 📸 Two scaling policies active simultaneously — Target Tracking as baseline, Step Scaling for spikes

  3. Layer 3 — Scheduled Scaling (pre-warm): Create a scheduled action to pre-warm capacity before the "event" starts:

    • Name: PreWarm-FlashSale
    • Set Min/Max/Desired to: 4/10/4 (run 4 instances before the flash sale)
    • Schedule: set it 10 minutes from now (for testing purposes)

    Figure P8-4: 📸 Scheduled pre-warm action — capacity jumps to 4 at the configured time before the sale

Part C — Configure Connection Draining

  1. Go to EC2 → Target Groups → select your Target Group → Attributes tab → click Edit.

  2. Set Deregistration delay to 120 seconds. This ensures in-flight requests complete before scale-in removes instances.

    Figure P8-5: 📸 Connection draining set to 120 seconds — protecting active user sessions

Part D — Set Up a CloudWatch Dashboard

  1. Go to CloudWatch → Dashboards → Create dashboard. Name it FlashSale-Monitor.

  2. Add four widgets:

    • Widget 1: Line chart — CPUUtilization (average across all ASG instances)
    • Widget 2: Number — GroupInServiceInstances (current running count)
    • Widget 3: Line chart — RequestCountPerTarget from ALB (requests hitting each instance)
    • Widget 4: Alarm status — FlashSale-HighCPU alarm state

    Figure P8-6: 📸 CloudWatch monitoring dashboard — all key metrics visible in one place

Part E — Flash Sale Simulation

  1. Wait for the Scheduled Action to fire. Watch instance count jump to 4 on your dashboard.

  2. SSH into two instances simultaneously. On each, run:

    stress --cpu 4 --timeout 300

  3. Watch your dashboard:

    • CPU climbs above 80% → Step Scaling fires → 3 more instances launch
    • CPU stays above 90%? → 6 instances requested (capped at Max=10)
    • Dashboard shows RequestCountPerTarget dropping per instance as new capacity absorbs load

    Figure P8-7: 📸 Flash sale simulation at peak — 8 instances running, CPU alarm in ALARM state

  4. Let stress end. Watch CPU drop, instances scale in over 5–10 minutes. Verify connection draining works — check ALB access logs if available, confirm no 502/503 errors during scale-in.

🤔 Reflection Questions

1. Your application crashes silently — the EC2 instance keeps running but returns HTTP 503 errors. Which health check type detects this, and which misses it?

💡 Hint

Think about what EC2 health checks actually check (system level) vs what ELB health checks check (application response level).

2. You set a grace period of 60 seconds, but your application takes 3 minutes to start. What will happen and how do you fix it?

💡 Hint

Consider what happens when health checks run before the instance is ready. What is the consequence, and what is the correct grace period value?

3. Your e-commerce site gets a sudden traffic spike during a flash sale. CPU goes from 30% to 95% in 2 minutes. Would you use Simple Scaling or Step Scaling? Why?

💡 Hint

Think about which policy can respond proportionally to the severity of the spike. Also consider the cooldown period problem with Simple Scaling.

4. You have a news website that gets predictable traffic spikes every weekday morning at 7 AM when commuters check news. Which scaling policy would you choose?

💡 Hint

When do you know exactly when the load will arrive? What scaling policy is designed for this exact scenario?

5. Describe how path-based routing enables microservices. Give a concrete example with two different services.

💡 Hint

Think about a large application broken into services. How does a single ALB route different URL paths to the right backend? What does each backend have independently (hint: Target Group, ASG)?

💡 Hint
