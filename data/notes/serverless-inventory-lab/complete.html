📚 Background / Theory

What is Serverless Computing?

The word "serverless" is a little misleading — there are servers. You just don't manage them. AWS handles everything: provisioning, scaling, patching, availability. You provide code and a trigger. AWS does the rest.

Think of it like a food delivery app. The restaurant (your code) doesn't own delivery vehicles. When an order arrives (the trigger), a driver appears (the compute), delivers the food (runs your function), and leaves. You only pay per delivery, not to maintain a fleet of vehicles standing by.

Figure 2: Traditional vs Serverless — you pay only for what you use

In a serverless model, you do not pre-allocate servers — compute resources are automatically provided when a function is triggered and released immediately after execution.

What is AWS Lambda?

AWS Lambda is Amazon's serverless compute service. You write a function in a supported language (Python, Node.js, Java, etc.), define what triggers it, and Lambda takes care of everything else.

Internally, Lambda runs your code inside a container. AWS picks a server somewhere in the region, drops your container onto it, runs your code, and removes the container afterward. You never touch that server.

Lambda functions have a maximum execution timeout of 15 minutes per invocation.

Lambda supports event-driven invocation — it can be triggered by S3 object creation, DynamoDB Streams, API Gateway, SNS, SQS, CloudWatch Events, and more.

💡 The Cold Start Reality (Todd's War Story): When no container is running, Lambda must first spin one up — this is called a cold start. It adds a few hundred milliseconds to a few seconds of delay. Todd ran into this while testing a bot that sent a long prompt to a model: the Lambda ran fine (took 31 seconds), but API Gateway killed the response at 29 seconds because that's API Gateway's hard limit — and it cannot be changed. Bumping Lambda's timeout to 90 or 120 seconds made no difference. The lesson: always be aware of all the timeouts in your architecture, not just Lambda's.

⚡ Cold Start Chain: No container running → Init start (cold start delay) → Function runs → Container stays warm for a while → Eventually times out → Next call triggers another cold start. If your app is latency-sensitive, a cold start of even a few hundred milliseconds might be unacceptable.

Amazon S3 as an Event Source

Amazon S3 (Simple Storage Service) stores files as objects inside buckets. But beyond storage, S3 can fire events when things happen — like when a file is uploaded.

When you configure an S3 Event Notification, S3 can automatically invoke a Lambda function whenever an object is created, deleted, or modified in a bucket.

In this lab, when a store uploads a CSV inventory file to your S3 bucket, S3 immediately calls the Load-Inventory Lambda function and passes the bucket name and object key as part of the event payload. Lambda then downloads the file and processes it — all automatically, with no human action required after the initial upload.

✅ Personal Account Best Practice: In the lab environment, S3 bucket names were pre-set. In your personal account, S3 bucket names must be globally unique across all AWS accounts and regions. Use a pattern like inventory-yourname-YYYYMMDD to guarantee uniqueness.

Amazon DynamoDB

DynamoDB is AWS's fully managed NoSQL database. It's serverless too — you don't provision servers, you just create a table and start storing data. It scales automatically and offers single-digit millisecond performance.

DynamoDB is a key-value and document database — each item must have a partition key (and optionally a sort key), but other attributes can vary freely between items.

In this lab, the Inventory table uses Store as the partition key and Item as the sort key. Each row holds one item's inventory count for one store.

DynamoDB Streams is the feature that makes the second Lambda work. DynamoDB Streams captures a time-ordered sequence of item-level changes in a table, making that data available for up to 24 hours. When a new row is written, the stream fires and triggers the Check-Stock Lambda.

Amazon SNS

SNS (Simple Notification Service) is a fully managed publish/subscribe messaging service. Think of it like a newsletter — you create a topic (the newsletter), and anyone who subscribes gets notified whenever a message is published.

SNS uses a pub/sub model where publishers send messages to a topic, and SNS fans out that message to all subscribers simultaneously.

Subscribers can be: email addresses, SMS phone numbers, HTTP/HTTPS endpoints, SQS queues, Lambda functions, or mobile push notifications.

💡 Important — Email Subscription Confirmation: When you create an email subscription, SNS sends a confirmation email. You must click the confirmation link before SNS will deliver any messages to you. Todd mentioned this in class — "one of those common things that we've all done" is forgetting to confirm and then wondering why alerts aren't arriving.

Amazon Cognito (Brief Context)

The dashboard in this lab uses Amazon Cognito for authentication. You don't configure Cognito yourself in this lab, but it's worth understanding why it's there.

IAM is for AWS users and services. Cognito is for your application's users — people accessing your app through a browser or phone who should never have direct IAM credentials.

Amazon Cognito provides identity federation and allows external users to authenticate and receive temporary AWS credentials to access specific AWS resources like DynamoDB.

The dashboard uses a Cognito identity pool with anonymous authentication — it gets temporary, read-only credentials to query the Inventory DynamoDB table, without any user needing to log in or have an IAM account.

Why Two Lambda Functions? (Architecture Lesson)

You might wonder: why not just add the stock-check logic inside Load-Inventory? Todd addressed this directly in class — it's a core architectural principle.

⚡ Single Responsibility Principle: Each Lambda function should do one thing well. Load-Inventory loads data. Check-Stock checks stock levels. Combining them would make both harder to maintain, test, and debug.

The benefits of keeping them separate:

  • Simpler code — each function is shorter and easier to read
  • Independent scaling — each function scales based on its own trigger, not the other's load
  • Easy extension — want to add a "low stock warning" feature? Add a third Lambda. The existing two don't change.
  • Better debugging — when something breaks, you know exactly which function (and which responsibility) failed

IAM Roles for Lambda

Lambda functions need permission to interact with other AWS services. These permissions come from an IAM role attached to the function — called the execution role.

Every Lambda function must have an execution role — an IAM role that grants the function permission to access AWS services on your behalf.

In the lab environment, these roles were pre-created:

  • Lambda-Load-Inventory-Role — allows reading from S3 and writing to DynamoDB
  • Lambda-Check-Stock-Role — allows reading DynamoDB Streams and publishing to SNS

✅ Personal Account Best Practice: Follow the principle of least privilege. Never attach AdministratorAccess to a Lambda function. Create a custom IAM role with only the exact permissions the function needs. In this lab you'll create these roles manually — the steps are in the Personal Account Setup section.

Task 1: Create the Load-Inventory Lambda Function

This function is the workhorse of the pipeline. It gets triggered when a CSV file lands in S3, downloads the file, reads it line by line, and writes each inventory row into DynamoDB. Think of it as your automated data entry clerk — but one that processes files in seconds and never calls in sick.

Console Instructions

  1. In the AWS Console, search for Lambda and open the service.
  2. Click Create function.
  3. Select Author from scratch.
  4. Fill in the configuration:
    • Function name: Load-Inventory
    • Runtime: Python 3.12 (⚠️ Console Change: The lab instructions say Python 3.9 — that version is no longer supported. Todd flagged this: use Python 3.12 or the latest supported version shown in the console.)
  5. Expand Change default execution role.
  6. ⚠️ Console Change Alert: This section is now hidden under Additional configurations (toggle the slider button to reveal it). Todd was confused by this the first time — the console was updated to hide it since most users don't change the role at creation time.
    • Select Use an existing role
    • Choose Lambda-Load-Inventory-Role from the dropdown
  7. Click Create function.
  8. Once the function opens, scroll down to Code source.
  9. In the left file panel, click lambda_function.py.
  10. Select all the default code and delete it.
  11. Paste in the following code:
# Load-Inventory Lambda function
# Triggered by S3 object creation.
# Downloads the CSV file and inserts each row into the DynamoDB Inventory table.

import json, urllib, boto3, csv

s3 = boto3.resource('s3')
dynamodb = boto3.resource('dynamodb')
inventoryTable = dynamodb.Table('Inventory')

def lambda_handler(event, context):
    print("Event received by Lambda function: " + json.dumps(event, indent=2))

    bucket = event['Records'][0]['s3']['bucket']['name']
    key = urllib.parse.unquote_plus(event['Records'][0]['s3']['object']['key'])
    localFilename = '/tmp/inventory.txt'

    try:
        s3.meta.client.download_file(bucket, key, localFilename)
    except Exception as e:
        print(e)
        print('Error getting object {} from bucket {}.'.format(key, bucket))
        raise e

    with open(localFilename) as csvfile:
        reader = csv.DictReader(csvfile, delimiter=',')
        rowCount = 0
        for row in reader:
            rowCount += 1
            print(row['store'], row['item'], row['count'])
            try:
                inventoryTable.put_item(
                    Item={
                        'Store': row['store'],
                        'Item':  row['item'],
                        'Count': int(row['count'])
                    })
            except Exception as e:
                print(e)
                print("Unable to insert data into DynamoDB table")

    return "%d counts inserted" % rowCount
  1. Click Deploy. Wait for the banner: "Changes deployed".

  --function-name Load-Inventory \

  --action lambda:InvokeFunction \
  --principal s3.amazonaws.com \

  --bucket $BUCKET_NAME \

        \"Events\": [\"s3:ObjectCreated:*\"]
      }
    ]
  }"

# Check-Stock Lambda function
# Triggered by DynamoDB Streams when items are inserted/updated.
# Sends SNS notification for any item with Count = 0.

import json, boto3

def lambda_handler(event, context):
    print("Event received by Lambda function: " + json.dumps(event, indent=2))

    for record in event['Records']:
        newImage = record['dynamodb'].get('NewImage', None)
        if newImage:
            count = int(record['dynamodb']['NewImage']['Count']['N'])
            if count == 0:
                store = record['dynamodb']['NewImage']['Store']['S']
                item  = record['dynamodb']['NewImage']['Item']['S']

                message = store + ' is out of stock of ' + item
                print(message)

                sns = boto3.client('sns')
                alertTopic = 'NoStock'
                snsTopicArn = [t['TopicArn'] for t in sns.list_topics()['Topics']
                               if t['TopicArn'].lower().endswith(':' + alertTopic.lower())][0]

                sns.publish(
                    TopicArn=snsTopicArn,
                    Message=message,
                    Subject='Inventory Alert!',
                    MessageStructure='raw'
                )

    return 'Successfully processed {} records.'.format(len(event['Records']))

The problem: Right now both Lambda functions use plain print() statements. These appear in CloudWatch as unformatted strings — difficult to search, filter, or alert on at scale. When you have 100 uploads per day and one is failing, you're scrolling through walls of text.

    """Emit a structured JSON log line to CloudWatch."""
    entry = {

        "message":      message,

Task 10: Add Dead Letter Queue (DLQ) for Failures 🟡 Near Free

The problem: If Load-Inventory fails (bad CSV, DynamoDB permission error, timeout), the S3 event is silently lost. You have no record that a file wasn't processed and no way to retry it.

The fix: Create an SQS queue as a Dead Letter Queue. When Lambda exhausts retries, the failed event is deposited into SQS — where you can inspect it, fix the problem, and reprocess manually.

💡 How Lambda retries work: For async invocations (S3 → Lambda), Lambda automatically retries failed invocations twice before giving up. With a DLQ configured, the failed event goes to SQS instead of disappearing.

Task 11: Implement Idempotency — Duplicate Protection 🟢 Free Tier

The problem: If a store uploads the same CSV file twice (accident, retry), put_item silently overwrites the existing data. You can't tell this happened and the DynamoDB Streams will fire a second time, potentially sending duplicate SNS alerts.

The fix: Use DynamoDB's conditional write — only write the item if it doesn't already exist. If it does exist, the write fails gracefully with a ConditionalCheckFailedException, which you catch and log.

Code Change — in load_inventory.py

from botocore.exceptions import ClientError

try:
    inventoryTable.put_item(
        Item={
            'Store': row['store'],
            'Item':  row['item'],
            'Count': int(row['count'])
        },
        # Only write if this Store+Item combo does not already exist
        ConditionExpression="attribute_not_exists(#s) AND attribute_not_exists(#i)",
        ExpressionAttributeNames={"#s": "Store", "#i": "Item"}
    )
except ClientError as e:
    if e.response['Error']['Code'] == 'ConditionalCheckFailedException':
        print(f"Skipped duplicate: {row['store']} / {row['item']}")
    else:
        raise   # re-raise unexpected errors

✅ Alternative approach: If you want to allow updates (e.g., a store corrects their count), remove the ConditionExpression and instead add a LastUpdated timestamp attribute using UpdateItem with a condition that only writes if the new timestamp is newer than the stored one.

def validate_row(row):
    """Returns (is_valid, error_message)."""
    required = ['store', 'item', 'count']
    for field in required:
        if field not in row or not row[field].strip():
            return False, f"Missing or empty field: {field}"
    try:
        count = int(row['count'])
    except ValueError:
        return False, f"Count is not an integer: {row['count']}"
    if count < 0:
        return False, f"Count is negative: {count}"
    return True, None

# Inside the CSV loop:

    # ... put_item or batch.put_item as before

Task 22: Add Retry Logic for External Calls 🟢 Free Tier

The problem: DynamoDB and SNS API calls can fail with transient errors (ProvisionedThroughputExceededException, ThrottlingException, temporary network blips). The current code crashes immediately on first failure.

Option A — boto3 Built-in Retry Config (Easiest)

    retries={
        'max_attempts': 5,

Option B — Manual Retry with Backoff

import time, random

def put_item_with_retry(table, item, max_retries=3):
    for attempt in range(max_retries):
        try:
            table.put_item(Item=item)
            return
        except Exception as e:
            if attempt == max_retries - 1:
                raise
            wait = (2 ** attempt) + random.uniform(0, 1)  # exponential + jitter
            print(f"Retry {attempt+1}/{max_retries} after {wait:.1f}s: {e}")
            time.sleep(wait)

import json, boto3, os
from datetime import datetime, timezone

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table(os.environ.get('TABLE_NAME', 'Users'))

def lambda_handler(event, context):
    route = event.get('routeKey', '')
    path_params = event.get('pathParameters') or {}
    body = json.loads(event.get('body') or '{}')

    try:
        if route == 'POST /users':
            user_id = body.get('userId')
            if not user_id:
                return respond(400, {'error': 'userId is required'})
            table.put_item(Item={
                'userId': user_id,
                'name': body.get('name', ''),
                'email': body.get('email', ''),
                'createdAt': datetime.now(timezone.utc).isoformat()
            })
            return respond(201, {'message': 'User created', 'userId': user_id})

        elif route == 'GET /users/{userId}':
            result = table.get_item(Key={'userId': path_params['userId']})
            item = result.get('Item')
            if not item:
                return respond(404, {'error': 'User not found'})
            return respond(200, item)

        elif route == 'PUT /users/{userId}':
            table.update_item(
                Key={'userId': path_params['userId']},
                UpdateExpression='SET #n = :name, email = :email',
                ExpressionAttributeNames={'#n': 'name'},
                ExpressionAttributeValues={':name': body.get('name',''), ':email': body.get('email','')}
            )
            return respond(200, {'message': 'User updated'})

        elif route == 'DELETE /users/{userId}':
            table.delete_item(Key={'userId': path_params['userId']})
            return respond(200, {'message': 'User deleted'})

        else:
            return respond(404, {'error': 'Route not found'})

    except Exception as e:
        print(f"Error: {e}")
        return respond(500, {'error': str(e)})

def respond(status_code, body):
    return {
        'statusCode': status_code,
        'headers': {'Content-Type': 'application/json'},
        'body': json.dumps(body)
    }

Project 3 — Event-Driven Order Processing System 🟡 Near Free

What you're building: A simulated e-commerce order backend. A customer places an order — it goes into an SQS queue, a Lambda function processes it, stores it in DynamoDB, and SNS sends a confirmation. Failed orders go to a Dead Letter Queue for review. This is real-world event-driven architecture used by every major e-commerce platform.

Why it matters: This project introduces the SQS → Lambda pattern — different from S3 → Lambda. SQS provides buffering, retry, and backpressure that S3 triggers don't. Interviewers routinely ask "how would you handle 10,000 orders per second?" — this project gives you a real answer.

Figure P3: Event-driven order pipeline — SQS buffers orders, Lambda processes them, SNS confirms, DLQ catches failures

💡 New service — Amazon SQS: Simple Queue Service is a fully managed message queue. Producers put messages in; consumers (like Lambda) poll and process them. Unlike SNS which pushes to all subscribers, SQS holds messages until a consumer pulls them — providing a buffer between fast producers and slower processors. SQS supports a visibility timeout — while Lambda is processing a message, it's hidden from other consumers to prevent duplicate processing.

Architecture Flow

  1. Client sends POST /orders to API Gateway → Lambda writes order to SQS
  2. A second Lambda (ProcessOrder) polls SQS automatically
  3. ProcessOrder validates the order → writes to DynamoDB → publishes SNS confirmation
  4. Failures after 3 retries → go to SQS Dead Letter Queue

Lambda Code — process_order.py

import json, boto3, os

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table(os.environ.get('TABLE_NAME', 'Orders'))
sns = boto3.client('sns')
TOPIC_ARN = os.environ['SNS_TOPIC_ARN']

def lambda_handler(event, context):
    for record in event['Records']:
        order = json.loads(record['body'])
        order['status'] = 'PROCESSED'

        # Validate
        if not order.get('customerId') or not order.get('items'):
            raise ValueError(f"Invalid order: {order['orderId']}")

        # Store in DynamoDB
        table.put_item(Item=order)

        # Send confirmation
        sns.publish(
            TopicArn=TOPIC_ARN,
            Subject=f"Order Confirmed: {order['orderId']}",
            Message=f"Your order {order['orderId']} has been confirmed. Total: ${order.get('total', 0)}"
        )
        print(f"Processed order: {order['orderId']}")

    return {'statusCode': 200}

Lambda Code — submit_job.py

import json, boto3, os, uuid
from datetime import datetime, timezone

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('AsyncJobs')
sqs = boto3.client('sqs')
QUEUE_URL = os.environ['QUEUE_URL']

def lambda_handler(event, context):
    body = json.loads(event.get('body') or '{}')
    job_id = str(uuid.uuid4())
    prompt = body.get('prompt', '')

    # Write PENDING record immediately
    table.put_item(Item={
        'jobId': job_id,
        'status': 'PENDING',
        'prompt': prompt,
        'submittedAt': datetime.now(timezone.utc).isoformat()
    })

    # Queue the job for async processing
    sqs.send_message(QueueUrl=QUEUE_URL,
                     MessageBody=json.dumps({'jobId': job_id, 'prompt': prompt}))

    # Return immediately — well under 29 seconds
    return {
        'statusCode': 202,
        'body': json.dumps({
            'jobId': job_id,
            'status': 'PENDING',
            'message': 'Job submitted. Poll GET /jobs/{jobId} for result.'
        })
    }

Lambda Code — process_job.py

import json, boto3

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('AsyncJobs')
bedrock = boto3.client('bedrock-runtime', region_name='us-east-1')

def lambda_handler(event, context):
    for record in event['Records']:
        job = json.loads(record['body'])
        job_id = job['jobId']
        prompt = job['prompt']

        # Mark as processing
        table.update_item(
            Key={'jobId': job_id},
            UpdateExpression='SET #s = :s',
            ExpressionAttributeNames={'#s': 'status'},
            ExpressionAttributeValues={':s': 'PROCESSING'}
        )

        try:
            # Call Bedrock — this may take 30-60 seconds
            response = bedrock.invoke_model(
                modelId='amazon.titan-text-lite-v1',
                body=json.dumps({'inputText': prompt,
                                 'textGenerationConfig': {'maxTokenCount': 512}})
            )
            result = json.loads(response['body'].read())
            output = result['results'][0]['outputText']
            status = 'COMPLETE'
        except Exception as e:
            output = f"Error: {str(e)}"
            status = 'FAILED'

        # Write final result to DynamoDB
        table.update_item(
            Key={'jobId': job_id},
            UpdateExpression='SET #s = :s, result = :r',
            ExpressionAttributeNames={'#s': 'status'},
            ExpressionAttributeValues={':s': status, ':r': output}
        )

import json, boto3
from datetime import datetime, timezone

cloudwatch = boto3.client('cloudwatch')
sns = boto3.client('sns')

def lambda_handler(event, context):
    # Parse the CloudWatch alarm from SNS message
    message = json.loads(event['Records'][0]['Sns']['Message'])
    alarm_name = message.get('AlarmName', 'Unknown')
    alarm_state = message.get('NewStateValue', 'Unknown')
    reason = message.get('NewStateReason', 'No reason provided')

        "action": "AUTO_REMEDIATION_TRIGGERED",
        "alarm": alarm_name,
        "state": alarm_state,
        "reason": reason,
        "time": datetime.now(timezone.utc).isoformat()
    }))

    # Example remediation: if DynamoDB throttling, log and notify
    if 'Throttle' in alarm_name and alarm_state == 'ALARM':
        print("DynamoDB throttling detected — consider switching to on-demand billing")
        # In production: could call dynamodb.update_table() to increase capacity
        # For this lab: just log it so you can investigate

    # Push a remediation metric so you can track how often alarms fire
    cloudwatch.put_metric_data(
        Namespace='InventoryApp',
        MetricData=[{
            'MetricName': 'RemediationTriggered',
            'Value': 1,
            'Unit': 'Count',
            'Dimensions': [{'Name': 'AlarmName', 'Value': alarm_name}]
        }]
    )

💡 New service — AWS Step Functions: Step Functions is a serverless orchestration service. AdminAPI Lambda Code — admin_api.py

import json, boto3, os, uuid
from datetime import datetime, timezone

dynamodb = boto3.resource('dynamodb')
audit_table = dynamodb.Table('AuditLog')
sns = boto3.client('sns')
TOPIC_ARN = os.environ.get('SNS_TOPIC_ARN', '')

def write_audit(action, resource, user, result, details=''):
    audit_table.put_item(Item={
        'actionId': str(uuid.uuid4()),
        'timestamp': datetime.now(timezone.utc).isoformat(),
        'action': action,
        'resource': resource,
        'performedBy': user,
        'result': result,
        'details': details
    })

def lambda_handler(event, context):
    route = event.get('routeKey', '')
    # Extract user from Cognito JWT claims (populated by API Gateway authorizer)
    user = (event.get('requestContext', {})
                 .get('authorizer', {})
                 .get('jwt', {})
                 .get('claims', {})
                 .get('email', 'anonymous'))

    if route == 'GET /admin/resources':
        # List all Lambda functions in the account
        lam = boto3.client('lambda')
        functions = lam.list_functions()['Functions']
        resource_list = [{'name': f['FunctionName'],
                          'runtime': f['Runtime'],
                          'lastModified': f['LastModified']} for f in functions]
        write_audit('LIST_RESOURCES', 'lambda:all', user, 'SUCCESS')
        return respond(200, {'resources': resource_list, 'count': len(resource_list)})

    elif route == 'POST /admin/tag':
        body = json.loads(event.get('body') or '{}')
        resource_arn = body.get('resourceArn')
        tags = body.get('tags', {})
        # Tag the resource
        tagging = boto3.client('resourcegroupstaggingapi')
        tagging.tag_resources(ResourceARNList=[resource_arn], Tags=tags)
        write_audit('TAG_RESOURCE', resource_arn, user, 'SUCCESS',
                    details=json.dumps(tags))
        if TOPIC_ARN:
            sns.publish(TopicArn=TOPIC_ARN,
                        Subject='Admin Action: Tag Resource',
                        Message=f'{user} tagged {resource_arn} with {tags}')
        return respond(200, {'message': 'Tags applied', 'resource': resource_arn})

    return respond(404, {'error': 'Route not found'})

def respond(code, body):
    return {'statusCode': code,
            'headers': {'Content-Type': 'application/json'},
            'body': json.dumps(body, default=str)}

What you're building: A controlled chaos system that deliberately breaks your serverless inventory pipeline — injecting Lambda failures, simulating DynamoDB throttling, and introducing artificial delays — then verifies the system recovers correctly. Why it matters: Most engineers only test the happy path. Chaos engineering shows you understand failure modes, not just success paths. Figure P10: Chaos engineering — controlled failure injection with automatic recovery detection and metrics

💡 Chaos engineering principle: You inject a known failure, observe system behavior, measure recovery time, and verify your DLQ and alarms caught the event. If the system doesn't recover cleanly, you've found a real bug before your users did. The goal of chaos engineering is to build confidence in system resilience through controlled experiments, not to break things randomly.

Chaos Scenarios to Test

  • Lambda failure injection: Use an environment variable CHAOS_MODE=FAIL to make Load-Inventory throw an exception on X% of invocations — verify DLQ receives the failed event
  • Artificial latency: CHAOS_MODE=SLOW — add a random 25–35 second sleep to simulate a slow model call approaching timeouts
  • DynamoDB throttle simulation: Temporarily switch DynamoDB table to provisioned capacity with 1 WCU, upload 100 rows rapidly — observe throttle alarms from Task 19
  • Corrupted data injection: Upload a CSV with intentionally bad rows — verify validation rejects them without crashing the function

import random, time

CHAOS_MODE = os.environ.get('CHAOS_MODE', 'OFF')
CHAOS_RATE  = float(os.environ.get('CHAOS_RATE', '0.3'))  # 30% failure rate

def apply_chaos(context):
    """Inject controlled failures for chaos testing. Remove before production."""
    if CHAOS_MODE == 'OFF':
        return

    if CHAOS_MODE == 'FAIL' and random.random() < CHAOS_RATE:
        print(json.dumps({"status": "CHAOS_FAIL", "requestId": context.aws_request_id,
                          "message": "Chaos failure injected"}))
        raise RuntimeError("CHAOS: Simulated Lambda failure")

    if CHAOS_MODE == 'SLOW':
        delay = random.uniform(25, 35)
        print(json.dumps({"status": "CHAOS_SLOW", "delay_seconds": delay}))
        time.sleep(delay)  # approaches API Gateway 29s timeout

import boto3, json, os

lam = boto3.client('lambda')

def lambda_handler(event, context):
    """Toggle chaos mode on/off for a target function."""
    target_fn = event.get('function', 'Load-Inventory')
    chaos_mode = event.get('mode', 'OFF')      # OFF | FAIL | SLOW
    chaos_rate = str(event.get('rate', 0.3))   # failure probability

    # Get current env vars
    config = lam.get_function_configuration(FunctionName=target_fn)
    env_vars = config.get('Environment', {}).get('Variables', {})

    # Inject or remove chaos variables
    env_vars['CHAOS_MODE'] = chaos_mode
    env_vars['CHAOS_RATE'] = chaos_rate

    lam.update_function_configuration(
        FunctionName=target_fn,
        Environment={'Variables': env_vars}
    )
    print(f"Chaos mode set to {chaos_mode} ({chaos_rate} rate) on {target_fn}")
    return {'function': target_fn, 'chaosMode': chaos_mode, 'rate': chaos_rate}

QuizEngine Lambda Code — quiz_engine.py

import json, boto3, os, random

s3 = boto3.client('s3')
dynamodb = boto3.resource('dynamodb')
progress_table = dynamodb.Table('UserProgress')
CONTENT_BUCKET = os.environ.get('CONTENT_BUCKET', 'learning-dashboard-content')

def lambda_handler(event, context):
    route = event.get('routeKey', '')
    topic_id = (event.get('pathParameters') or {}).get('topicId', '')
    user_id = (event.get('requestContext', {})
                    .get('authorizer', {})
                    .get('jwt', {})
                    .get('claims', {})
                    .get('sub', 'anonymous'))

    if route == f'GET /quiz/{"{topicId}"}':
        # Load questions from S3
        obj = s3.get_object(
            Bucket=CONTENT_BUCKET,
            Key=f'quiz/{topic_id}/mcq.json'
        )
        all_questions = json.loads(obj['Body'].read())['questions']
        # Return 10 random questions (shuffle options too)
        selected = random.sample(all_questions, min(10, len(all_questions)))
        # Strip correct answers before sending to client
        for q in selected:
            q.pop('correctAnswer', None)
            q.pop('explanation', None)
        return respond(200, {'topicId': topic_id, 'questions': selected,
                             'total': len(selected)})

    elif route == f'POST /quiz/{"{topicId}"}/submit':
        body = json.loads(event.get('body') or '{}')
        answers = body.get('answers', {})  # {questionId: selectedLetter}

        # Load correct answers
        obj = s3.get_object(Bucket=CONTENT_BUCKET,
                            Key=f'quiz/{topic_id}/mcq.json')
        questions = {str(q['id']): q['correctAnswer']
                     for q in json.loads(obj['Body'].read())['questions']}

        score = sum(1 for qid, ans in answers.items()
                    if questions.get(qid) == ans)
        total = len(answers)
        percentage = round((score / total) * 100) if total > 0 else 0

        # Save score to DynamoDB
        progress_table.put_item(Item={
            'userId': user_id,
            'topicId': topic_id,
            'latestScore': percentage,
            'attempts': 1,
            'lastAttemptAt': __import__('datetime').datetime.utcnow().isoformat()
        })

        return respond(200, {'score': score, 'total': total,
                             'percentage': percentage,
                             'passed': percentage >= 70})

    return respond(404, {'error': 'Route not found'})

def respond(code, body):
    return {'statusCode': code,
            'headers': {'Content-Type': 'application/json',
                        'Access-Control-Allow-Origin': '*'},
            'body': json.dumps(body)}

💬 Todd's Key Highlights from This Session

These are the insights Todd shared beyond the lab steps — the real-world experience that makes this session more than just button-clicking.

  • The 29-Second Problem: API Gateway has a hard timeout of 29 seconds that cannot be changed — not by bumping Lambda's timeout, not by any configuration. This was chosen in 2015 when 29 seconds was "infinity" for database queries. Now that ML models can take 30+ seconds to respond, this architectural constraint is a real blocker. The fix isn't to increase timeouts — it's to change the architecture (async processing, WebSockets, Step Functions).
  • Cold Starts Are Real: Todd reproduced a cold start live — a bot that failed because the response took more than 29 seconds on first invocation. Always account for cold start latency in your architecture. Lambda Provisioned Concurrency is the AWS solution for latency-sensitive applications.
  • Python Version Matters: The lab said Python 3.9 — it's gone. Always use the latest supported runtime. Staying one major version behind your development version is fine for safety, but don't go two or three versions old. Check the Lambda runtimes page for what's currently supported.
  • Console Changes Constantly: "Designer" became "Function overview." The execution role moved behind a toggle. The Items tab became "Explore table items." Todd ran through the labs specifically to catch these before class. Never memorize specific button names — understand what you're trying to do and find the equivalent button.
  • CloudWatch Logs are your best friend: When a function fails silently (no error in the console), go to CloudWatch Log Insights. Todd specifically used this to discover the API Gateway timeout — the Lambda log showed 31-second execution while API Gateway was returning errors at 29 seconds.
  • Deploy Button = Easy Miss: The single most common mistake in Lambda development. Your code does not go live until you click Deploy. Todd caught himself mid-demo having forgotten to deploy. Make it a habit: code change → test → deploy → verify.
  • IAM Role: Least Privilege: The lab roles are broader than production-safe. Never attach AdminAccess to a Lambda in production. Always scope permissions to the exact actions and exact resource ARNs the function needs.

📝 Overall Summary

  • Serverless = No servers to manage: AWS Lambda runs your code in ephemeral containers, provisioned on demand, billed per millisecond of execution — not by uptime.
  • Event-driven pipeline: S3 upload → Lambda 1 (load data) → DynamoDB → Lambda 2 (check stock via Streams) → SNS → Email alert. Zero human involvement once deployed.
  • Cold starts add latency: The first invocation after a period of inactivity incurs a cold start — container initialization delay. Factor this into architectures with strict latency requirements.
  • API Gateway timeout = 29 seconds (unchangeable): Any Lambda function behind API Gateway that takes longer than 29 seconds will appear to fail — even if Lambda itself succeeds. This is a hard architectural constraint from 2015.
  • Python version: Python 3.9 is no longer supported on Lambda. Use Python 3.12 or the latest available runtime.
  • Console label changes: "Designer" → "Function overview"; "Items tab" → "Explore table items"; execution role is now under "Additional configurations" toggle.
  • SNS subscription requires email confirmation: AWS sends a confirmation link — you must click it before any messages are delivered to your email.
  • Two Lambda functions = Single Responsibility: Never add business logic (stock checking) into an already-purposeful function (data loading). Separation makes debugging, scaling, and extension dramatically easier.
  • DynamoDB Streams triggers the second Lambda: When new items are written to the table, the stream captures the change and invokes Check-Stock with the new item data as the event payload.
  • Personal account requires manual IAM setup: The lab pre-provisioned roles. In your own account, create them manually, via CLI, or via the CloudFormation template in the Personal Account Setup section.

1. What happens if the Load-Inventory Lambda takes 35 seconds to process a very large CSV file? Would this affect the DynamoDB write?

💡 Hint

2. The Check-Stock function discovers the SNS topic ARN at runtime by listing all topics. What are the downsides of this approach in production?

💡 Hint

Think about IAM permissions, the number of API calls per invocation, and what happens if you have 100 SNS topics.

3. Why does the architecture use DynamoDB Streams to trigger Check-Stock rather than just calling the Check-Stock Lambda directly from Load-Inventory?

💡 Hint

Think about coupling — if Load-Inventory calls Check-Stock, what happens if Check-Stock fails? What if you add a third function later?

4. You upload all 6 inventory CSV files simultaneously. Lambda scales to run 6 concurrent instances of Load-Inventory. All 6 try to write to the same DynamoDB table at the same time. Will this cause problems?

💡 Hint

Think about DynamoDB's write behavior — each item has a unique composite key (Store + Item). Can two functions write the same key simultaneously?

5. What changes would you need to make to this architecture to support inventory files in JSON format instead of CSV?

💡 Hint

Only the Load-Inventory function needs to change — the parser. Everything downstream (DynamoDB, Streams, SNS) is format-agnostic. This is a benefit of the decoupled design.
