🗺️ Introduction

Every machine — your laptop, your phone, your desktop — needs storage. Without it, there is nowhere to put the operating system, your files, your applications, or any data at all. The same is true in the cloud.

When you launch an EC2 instance (your virtual server in AWS), it is not complete on its own. It needs a hard disk. AWS provides two main types of storage you can attach to EC2:

  • EBS (Elastic Block Storage) — a network-attached, persistent hard disk
  • Instance Store — a physical disk directly on the host machine running your EC2 instance

Figure 1: EBS is network-attached and independent; Instance Store is physically embedded in the host machine

In today's session, we will deeply understand both of these storage types — what they are, how they work, when to use each, and how to work with them practically on a real EC2 instance.

💡 AWS Storage Services Overview: Under AWS storage, the three primary services are EBS (Elastic Block Storage), EFS (Elastic File System), and S3 (Simple Storage Service). This session covers EBS and Instance Store. EFS and S3 will be covered in upcoming sessions.

💾 Why EC2 Needs Storage

Think of your laptop. It has a CPU (processes things), RAM (temporary working memory), and a hard disk (permanent storage). Without the hard disk, your laptop cannot even boot — there is nowhere to load the operating system from.

An EC2 instance is the same. It is a virtual server with virtual CPU, virtual RAM — and it needs virtual storage. When you launch an EC2 instance, you configure two things:

  • Software configuration — this is your AMI (Amazon Machine Image): the operating system and pre-installed software
  • Hardware configuration — instance type (CPU + RAM size) and attached storage

Figure 2: EC2 is like a cloud laptop — it needs the same core components as a physical machine

When you launch an EC2 instance, attaching a storage volume is mandatory — there is no such thing as a storage-less EC2 instance.

💡 AMI Reminder: AMI stands for Amazon Machine Image. It is the "software snapshot" of your server — OS, pre-installed packages, and configuration. You select an AMI when launching EC2. This was covered in EC2 fundamentals.

⚔️ EBS vs Instance Store — The Core Difference

This is the most important concept in this entire session. Understanding the difference between EBS and Instance Store will answer exam questions, architecture decisions, and real troubleshooting scenarios.

EBS: The Network-Attached Drive

Imagine this: your laptop's hard disk is not physically inside your laptop. Instead, it is in a server room down the street, and your laptop connects to it over a very fast private network. You can read and write files just like a normal disk — but the disk itself lives somewhere else.

That is exactly what EBS is. When you attach an EBS volume to your EC2 instance:

  • The EC2 instance lives on one physical host machine in AWS's data center
  • The EBS volume lives on a separate, dedicated storage device in the same Availability Zone
  • They communicate over AWS's high-speed internal network

Figure 3: EBS lives on a separate device, connected to your EC2 instance over AWS's internal network

EBS is network-attached storage — it is physically separate from the EC2 host machine but connected via AWS's internal network.

Because EBS is independent of the EC2 instance, its data survives instance events:

  • ✅ Data persists when instance is stopped
  • ✅ Data persists when instance is rebooted
  • ✅ Data persists when instance is terminated (unless Delete on Termination is enabled)
  • ✅ Volume can be detached and re-attached to a different EC2 instance

Instance Store: The Physical Disk

Instance Store is the opposite of EBS. It is a physical disk that is directly mounted on the same host machine running your EC2 instance. There is no network hop — the disk is literally part of the same physical server.

This makes Instance Store extremely fast (no network latency), but it comes with a critical trade-off:

Instance Store is ephemeral — data is permanently lost when the EC2 instance is stopped, terminated, or if the underlying host fails.

Figure 4: Instance Store is physically inside the same host machine — fast but ephemeral

⚡ Key Exam Trap: When a question describes data loss after instance stop/termination — the answer is almost always Instance Store. EBS data survives. Instance Store does not.

📊 EBS Volume Types

Not all storage needs are equal. A gaming database that processes thousands of transactions per second needs very different storage from a backup archive that is read once a month. AWS EBS offers five volume types across two hardware categories to match different workload needs.

Figure 5: The five EBS volume types — SSDs for IOPS, HDDs for throughput

SSD Volume Types

SSDs (Solid State Drives) excel at random I/O — reading and writing many small chunks quickly. They are measured primarily in IOPS.

1. General Purpose SSD — gp2 (and gp3)

The workhorse of EBS. gp2 is a General Purpose SSD that balances price and performance for a wide variety of transactional workloads.

  • API Name: gp2
  • Volume Size: 1 GiB – 16 TiB
  • Max IOPS: 16,000 IOPS per volume
  • IOPS tied to size: 3 IOPS per GiB (e.g., 100 GiB = 300 IOPS baseline)
  • Use Cases: Most workloads — web servers, dev/test, small databases

gp3 is the newer generation — AWS now recommends gp3 over gp2 for all new volumes.

📸 From Session: gp2 vs gp3 quick comparison table — note that gp3 is 20% cheaper and decouples IOPS from storage size

⚡ gp3 Key Advantages over gp2:
• IOPS and throughput are independently configurable (not tied to disk size)
• Default 3,000 IOPS regardless of volume size
• Up to 1,000 MB/s throughput
• ~20% cheaper than gp2
• AWS recommends migrating gp2 → gp3

2. Provisioned IOPS SSD — io1

io1 is the highest-performance EBS SSD volume — designed for I/O-intensive, mission-critical applications.

  • API Name: io1
  • Volume Size: 4 GiB – 16 TiB
  • Max IOPS: 64,000 IOPS per volume
  • Max Throughput: 1,000 MB/s
  • Use Cases: Large relational databases, NoSQL databases, latency-sensitive transactional workloads

✅ When to choose io1: If your database needs more than 16,000 IOPS — io1 is your only EBS option. It is designed for Oracle, SQL Server, MongoDB, and similar enterprise databases.

HDD Volume Types

HDDs (Hard Disk Drives) excel at sequential I/O — reading or writing large streams of data from start to finish. They are measured primarily in throughput (MB/s).

3. Throughput Optimized HDD — st1

st1 is a low-cost HDD designed for frequently accessed, throughput-intensive workloads.

  • API Name: st1
  • Volume Size: 500 GiB – 16 TiB
  • Max IOPS: 500 IOPS per volume
  • Max Throughput: 500 MB/s
  • Use Cases: Big Data, data warehouses, log processing, Hadoop clusters
  • Cannot be used as a boot volume

4. Cold HDD — sc1

sc1 is the lowest-cost EBS volume type — designed for less frequently accessed workloads.

  • API Name: sc1
  • Volume Size: 500 GiB – 16 TiB
  • Max IOPS: 250 IOPS per volume
  • Max Throughput: 250 MB/s
  • Use Cases: File servers, cold archives, compliance data rarely accessed
  • Cannot be used as a boot volume

5. EBS Magnetic (Standard)

The legacy HDD type from the previous generation of EBS. Still available for workloads where data is infrequently accessed, but new workloads should use sc1 or st1 instead.

  • API Name: standard
  • Volume Size: 1 GiB – 1 TiB
  • Max IOPS: 40–200 IOPS per volume
  • Use Cases: Workloads where data is infrequently accessed

⚡ IOPS vs Throughput — Understanding the Difference

Two performance metrics come up constantly in EBS — IOPS and Throughput. Students often confuse them or use them interchangeably. They are different, and understanding the difference is critical for both the exam and real architecture decisions.

What is IOPS?

IOPS = Input/Output Operations Per Second

It counts how many individual read/write operations a disk can complete in one second — regardless of how much data each operation moves.

Think of it like a waiter at a restaurant: IOPS is how many orders the waiter can take per minute. Whether the order is a glass of water or a full 5-course meal — each order counts as one operation.

What is Throughput?

Throughput = Data transferred per second (MB/s)

It measures how much actual data moves per second. Same waiter analogy: throughput is how much food (by weight/volume) is delivered per minute — small orders contribute little; big orders contribute a lot.

📸 From Session: IOPS vs Throughput worked example — same IOPS but vastly different throughput depending on file size

How They Work Together

Here is the key insight: Throughput = IOPS × I/O size

  • 100 operations × 4 KB each = 400 KB/s throughput
  • 100 operations × 1 MB each = 100 MB/s throughput

Same IOPS. Completely different throughput.

⚡ When does each matter?
High IOPS matters for: Databases (many small random reads/writes), transactional apps
High Throughput matters for: Big Data, video streaming, data warehouses (large sequential reads)

SSDs (gp2, gp3, io1) are IOPS-dominant; HDDs (st1, sc1) are throughput-dominant.

📸 EBS Snapshots — Backups and Migration

What if your hard disk crashes? What if you accidentally delete critical data? What if you need to copy your server configuration to a new region? This is where EBS Snapshots come in.

What is an EBS Snapshot?

An EBS Snapshot is a point-in-time backup of an EBS volume, stored durably in Amazon S3.

Think of a snapshot like a photograph of your hard disk at a specific moment. The disk keeps changing after the photo is taken, but the photo preserves exactly what was there at that instant.

Figure 7: Snapshot lifecycle — first snapshot is full; subsequent snapshots save only changed blocks

Incremental Snapshots

Snapshots are incremental — but this needs careful explanation:

  • First snapshot: A complete copy of the entire EBS volume
  • Second snapshot onwards: Only the blocks (chunks of data) that changed since the last snapshot are stored

Despite being incremental, each snapshot is self-contained — you can restore the complete volume from any single snapshot.

Example: You have a 100 GB volume. You change 5 GB of data and take a second snapshot. The second snapshot stores only 5 GB — not 100 GB again. This saves significant time and cost.

What Can You Do With Snapshots?

  • 🔄 Restore: Create a new EBS volume from any snapshot at any time
  • 📦 Create AMIs: AMIs are backed by snapshots — your EC2 launch image is built from snapshots
  • 🌍 Migrate across AZs: Take a snapshot, create a new volume from it in a different AZ
  • 🗺️ Migrate across Regions: Copy a snapshot to another Region, then create a volume from it
  • 🔒 Share: Share snapshots with other AWS accounts

📸 From Session: AWS storage relationship diagram — EBS snapshots are stored in S3, and multiple EC2 instances can share EFS

⚡ Cross-AZ Migration via Snapshot:
EBS volumes are tied to one Availability Zone. To move a volume:
1. Take a snapshot of the volume
2. Create a new volume from the snapshot in the target AZ
3. Attach the new volume to the EC2 instance in that AZ

💡 According to AWS documentation: Snapshots are stored in S3 internally but managed through the EC2 console — you will not see them in the S3 console. They are billed at the S3 rate for the data stored.
📚 Source: AWS EBS Snapshots Docs

🗂️ Formatting a Disk — Why New Volumes Need Prep

When you create a brand-new EBS volume and attach it to an EC2 instance, you cannot use it immediately. It is raw storage — like a brand new, completely blank notebook with no lines, no sections, no page numbers. You can't write meaningfully on it yet because there is no structure.

Formatting is the process of adding that structure — drawing the lines and creating the organization system that allows an operating system to write files, folders, metadata, and permissions.

📸 From Session: Disk formatting analogy — a raw EBS volume is a blank notebook; formatting draws the structure needed to write files

Linux Filesystem Types

A filesystem is the system of rules for how data is organized on the disk. Common Linux filesystems:

  • XFS — High-performance filesystem, default on Amazon Linux 2. Handles large files well. Command: mkfs.xfs
  • ext4 — Fourth extended filesystem, common on many Linux distros. Command: mkfs.ext4

XFS is the default filesystem on Amazon Linux 2.

XFS stands for nothing in particular — it is simply the name of the filesystem. There is no official expansion. The "FS" stands for File System.

Mount Points

After formatting, you need to mount the volume — tell Linux where to make it accessible. A mount point is just a directory.

Linux treats everything as a file, starting from the root directory /. Under it: /home, /dev, /tmp, /proc. When you mount a volume to /data, Linux makes the volume's contents accessible at that path.

# Format a new EBS volume with XFS
sudo mkfs.xfs /dev/nvme1n1

# Create a mount point directory
sudo mkdir /data

# Mount the volume
sudo mount /dev/nvme1n1 /data

# Verify the mount
df -h

💡 Permanent mounting: The above mount is temporary — it disappears on reboot. To make it permanent, add an entry to /etc/fstab. This ensures the volume auto-mounts every time the instance starts.

📈 EBS Scaling — Growing Your Storage

As your application grows, your storage needs grow too. AWS gives you two ways to scale EBS storage — you can scale up (make the existing volume bigger) or scale out (add more volumes).

📸 From Session: EBS modifiable parameters — gp3 gives you independent control of size, IOPS, and throughput; gp2 only allows size changes

Scale Up — Vertical Scaling

Vertical scaling means increasing the size or performance of your existing EBS volume — without replacing it or losing data.

Example scenario: Your EC2 root volume is 8 GB and is filling up. You scale it up to 20 GB.

⚡ Important: EBS volumes can only be increased in size — you cannot shrink a volume once it has been expanded.

The process (two parts):

Part 1 — Resize in AWS Console:

  1. Go to EC2 Console → Volumes
  2. Select the volume → Actions → Modify Volume
  3. Change the size (e.g., 8 GB → 20 GB)
  4. Click Modify — the console reflects the new size immediately

Part 2 — Grow the filesystem on the instance (required!):

The OS does not automatically know the disk got bigger. You must explicitly tell it:

# Step 1: Check current disk state
lsblk

# Step 2: Grow the partition (replace nvme0n1 and 1 with your device/partition)
sudo growpart /dev/nvme0n1 1

# Step 3: Grow the XFS filesystem to fill new space
sudo xfs_growfs -d /

# Step 4: Verify the filesystem now shows new size
df -h

❌ Common Mistake: Students resize the EBS volume in the console and assume it is done. The OS still shows the old size. You MUST run growpart and xfs_growfs (or resize2fs for ext4) to claim the new space.

Scale Out — Horizontal Scaling

Horizontal scaling means attaching additional EBS volumes to your EC2 instance and combining them into a larger logical storage unit — without modifying the existing volume.

This is useful when:

  • You have hit the maximum size of a single volume
  • You need more storage without disrupting the existing setup
  • You want to combine volumes for a larger pool

The scale-out process:

  1. Create a new EBS volume in the same Availability Zone as your EC2 instance
  2. Attach it to your running EC2 instance via the console
  3. SSH into the instance
  4. Run lsblk — the new device appears (e.g., /dev/nvme1n1)
  5. Format the new volume: sudo mkfs.xfs /dev/nvme1n1
  6. Mount it: sudo mount /dev/nvme1n1 /newdata
  7. Optionally use LVM (Logical Volume Manager) to combine volumes into one pool

Figure 8: Scale-out — attaching a second EBS volume without touching the original

💡 According to AWS documentation: You can attach multiple EBS volumes to a single EC2 instance. The maximum number of attachable volumes depends on the instance type.
📚 Source: AWS EBS Multiple Volumes Docs

🔑 EBS Key Features & Important Facts

Availability Zone Constraint

An EBS volume is scoped to a single Availability Zone — it can only be attached to EC2 instances in the same AZ.

If your EC2 instance is in ap-south-1a, your EBS volume must also be in ap-south-1a. To use a volume in a different AZ, you must take a snapshot and create a new volume in the target AZ.

Delete on Termination

When you launch an EC2 instance, there is a setting for each attached EBS volume called Delete on Termination:

  • Root volume: Delete on Termination is enabled by default
  • Additional volumes: Delete on Termination is disabled by default

If you terminate an EC2 instance without enabling Delete on Termination on additional volumes, those volumes persist and continue to incur charges.

EBS Pricing

EBS charges for the storage you provision — not what you use:

Volume TypePrice (ap-south-1 approx)
io1$0.125/GB-month + $0.065/provisioned IOPS
gp2$0.10/GB-month
st1$0.045/GB-month
sc1$0.025/GB-month

❌ Cost Trap: Even a 1 GB unattached EBS volume costs money. Always delete volumes you no longer need. Check the EC2 console → Volumes → filter by "Available" state to find orphaned volumes.

Important EBS Limits

  • Max IOPS per instance (across all attached volumes): 80,000 IOPS
  • Max Throughput per instance: 1,750 MB/s
  • Max IOPS per io1 volume: 64,000 IOPS
  • Max IOPS per gp2/gp3 volume: 16,000 IOPS

📝 Overall Summary

  • EBS is mandatory for EC2: Every EC2 instance must have at least one attached storage volume — just like a laptop needs a hard disk.
  • EBS vs Instance Store: EBS is network-attached and persistent; Instance Store is physically attached and ephemeral (lost on stop/termination).
  • Five EBS volume types: gp2/gp3 (general purpose SSD), io1 (high-performance SSD), st1 (throughput HDD), sc1 (cold HDD), EBS Magnetic (legacy).
  • gp3 is preferred over gp2: gp3 decouples IOPS from size, is ~20% cheaper, and AWS recommends migrating gp2 → gp3.
  • io1 for maximum IOPS: Up to 64,000 IOPS — for mission-critical databases needing more than gp2's 16,000 IOPS ceiling.
  • st1 and sc1 cannot boot: HDD types cannot be used as root/boot volumes — only SSDs can.
  • IOPS vs Throughput: IOPS = operations per second (small random I/O); Throughput = MB/s (large sequential I/O). Same IOPS, different throughput depending on file size.
  • Snapshots are point-in-time backups: Stored in S3, incremental after first full backup, used for DR, cross-AZ/Region migration, and AMI creation.
  • AZ constraint: EBS volumes are AZ-specific — must be in the same AZ as the EC2 instance.
  • Scaling: Scale-up (vertical) = resize existing volume. Scale-out (horizontal) = attach additional volumes. Both require Linux filesystem steps after the AWS console action.

🧱 Project 1: My First Cloud Disk (Attach, Format, Mount)

🎯 Objective: Create a new EBS volume, attach it to a running EC2 instance, format it with XFS, write files, reboot — and prove that data survives. This builds the core EBS muscle memory.

⏱️ Time: 20–30 minutes

💰 Cost: ~$0.01 (free tier: first 30 GB free)

  1. Navigate to EC2 → Elastic Block Store → Volumes. Click Create Volume.

    📸 Screenshot: EC2 console — Volumes in the left panel

  2. Set type to gp3, size to 10 GiB. Select the same Availability Zone as your EC2 instance — this is critical.

    📸 Screenshot: Create Volume form — AZ must match EC2 instance AZ

  3. Select the new volume → Actions → Attach Volume → choose your EC2 instance.

    📸 Screenshot: Attach Volume — select your running EC2 instance

  4. SSH into the instance. Run lsblk — confirm the new volume appears (e.g., nvme1n1, 10 GB, no mount point).

    lsblk

    📸 Screenshot: lsblk — new 10 GB volume visible but not yet mounted

  5. Format with XFS, create mount point, mount:

    sudo mkfs.xfs /dev/nvme1n1
sudo mkdir /data
sudo mount /dev/nvme1n1 /data

  6. Write a test file and verify:

    echo "EBS persists!" | sudo tee /data/test.txt
cat /data/test.txt
df -h

    📸 Screenshot: df -h confirms /data mounted with 10 GB, test file written

  7. Reboot the instance:

    sudo reboot

  8. After reboot, SSH back in. Run ls /data — the file is gone from the mount, but the data on the volume is safe. The volume needs to be remounted (because we did not add it to /etc/fstab yet). Mount it again and verify the file is intact:

    sudo mount /dev/nvme1n1 /data
cat /data/test.txt

    📸 Screenshot: After reboot — data survived. EBS is persistent.

Make the mount permanent (fstab)

Add to /etc/fstab so the volume auto-mounts on every reboot:

# Get the UUID of the device
sudo blkid /dev/nvme1n1

# Add to /etc/fstab (replace UUID-HERE with your actual UUID)
echo "UUID=UUID-HERE  /data  xfs  defaults,nofail  0  2" | sudo tee -a /etc/fstab

# Test fstab without rebooting
sudo mount -a

Cleanup

  1. Unmount: sudo umount /data
  2. Console: Volumes → select → Detach → then Delete (to avoid charges)

🧱 Project 2: Instance Store vs EBS — Reality Check

🎯 Objective: Write data to both an EBS volume (/data-ebs) and an Instance Store volume (/data-instance-store), then stop the instance. Observe that EBS data survives and Instance Store data is permanently gone. This locks the concept in permanently.

⏱️ Time: 30–40 minutes

💰 Cost: Requires an instance type with Instance Store (e.g., m5d.large or c5d.large). These are NOT free tier. Run for 30 min only — cost ~$0.03.

❌ Important: Standard t2.micro / t3.micro do NOT have Instance Store. You must launch an instance type with the "d" suffix (e.g., m5d.large, i3.large) or check the instance type details for "Instance Storage" in the launch wizard.

  1. Launch a new EC2 instance with Instance Store. In the launch wizard, choose instance type m5d.large (or similar with local NVMe storage). Also attach a separate EBS gp3 volume (10 GB).

    📸 Screenshot: Launch with m5d.large — notice Instance Storage listed in the storage details

  2. SSH in. Run lsblk — you should see both the Instance Store NVMe disk and the EBS volume.

    lsblk

    📸 Screenshot: lsblk showing all three disks — root EBS, additional EBS, and Instance Store

  3. Set up the EBS volume at /data-ebs:

    sudo mkfs.xfs /dev/nvme1n1
sudo mkdir /data-ebs
sudo mount /dev/nvme1n1 /data-ebs
echo "I am on EBS - I will survive!" | sudo tee /data-ebs/ebs-test.txt

  4. Set up the Instance Store at /data-instance-store:

    sudo mkfs.xfs /dev/nvme2n1
sudo mkdir /data-instance-store
sudo mount /dev/nvme2n1 /data-instance-store
echo "I am on Instance Store - I will NOT survive!" | sudo tee /data-instance-store/instance-test.txt

  5. Confirm both files exist:

    cat /data-ebs/ebs-test.txt
cat /data-instance-store/instance-test.txt

    📸 Screenshot: Both files exist before stopping the instance

  6. Stop the instance from the AWS console (Actions → Stop Instance). Wait until it is fully stopped.

    📸 Screenshot: Instance in Stopped state in EC2 console

  7. Start the instance again. SSH back in. Now check both locations:

    # Try to mount EBS - it works
sudo mount /dev/nvme1n1 /data-ebs
cat /data-ebs/ebs-test.txt   # ✅ Still there!

# Try to access Instance Store
ls /data-instance-store       # ❌ Empty or inaccessible
# Even if you can mount it, the data is gone - Instance Store was wiped

    📸 Screenshot: EBS data intact. Instance Store empty. The difference is real.

⚡ What just happened? When the instance stopped, AWS moved it off the physical host machine. The Instance Store — which was physically on that host — was wiped. The EBS volume, stored on a separate device connected via network, remained completely untouched.

Cleanup

  1. Terminate the m5d instance (Stop first, then Terminate)
  2. Delete the standalone EBS volume (check Volumes → Available)

⚙️ Project 3: Right Volume for the Right Workload

🎯 Objective: Attach gp3, io1, and st1 volumes to one EC2 instance. Simulate different workloads on each. Use iostat and dd to observe IOPS vs throughput behaviour in practice — not just theory.

⏱️ Time: 45–60 minutes

💰 Cost: io1 costs more — run tests in under 1 hour. Estimated ~$0.05–0.10 total.

  1. Create three volumes in the same AZ:

    • 10 GiB gp3 (API name: gp3) — simulates web app
    • 10 GiB io1 with 3000 provisioned IOPS — simulates database
    • 500 GiB st1 (minimum size for st1) — simulates log storage

    📸 Screenshot: Three volumes created — gp3, io1, st1 — all in Available state

  2. Attach all three to the same EC2 instance. Run lsblk to identify device names.

    lsblk

  3. Format and mount each:

    sudo mkfs.xfs /dev/nvme1n1 && sudo mkdir /web-app && sudo mount /dev/nvme1n1 /web-app
sudo mkfs.xfs /dev/nvme2n1 && sudo mkdir /database && sudo mount /dev/nvme2n1 /database
sudo mkfs.xfs /dev/nvme3n1 && sudo mkdir /logs && sudo mount /dev/nvme3n1 /logs

  4. Install sysstat for iostat:

    sudo yum install sysstat -y

  5. Simulate small random writes (database workload) on the io1 volume. Open a second terminal and run iostat while the write runs:

    # Terminal 1: simulate random small-file writes (database-like)
sudo dd if=/dev/urandom of=/database/testfile bs=4K count=10000 oflag=direct

# Terminal 2: watch IO stats live
iostat -x 2

    📸 Screenshot: iostat during io1 write — high IOPS, small block size pattern

  6. Simulate large sequential writes (log/data warehouse workload) on the st1 volume:

    # Terminal 1: simulate large sequential writes (log-like)
sudo dd if=/dev/urandom of=/logs/bigfile bs=1M count=1000 oflag=direct

# Terminal 2: iostat again
iostat -x 2

    📸 Screenshot: iostat during st1 write — high throughput MB/s, low IOPS count

⚡ What to observe: The io1 test (4K block, many operations) shows high IOPS with lower MB/s. The st1 test (1M block, sequential) shows high MB/s with much lower IOPS. Same machine, same instance — completely different storage behaviour because the volumes are designed for different workloads.

Cleanup

  1. Unmount all three: sudo umount /web-app /database /logs
  2. Detach and delete all three volumes from the console

📈 Project 5: Zero Downtime Resize (Scale Up)

🎯 Objective: Expand a running EC2 root volume from 8 GB to 20 GB using the AWS console, then grow the filesystem using growpart and xfs_growfs — without stopping or rebooting the instance. This is one of the most common interview questions for cloud engineers.

⏱️ Time: 20–30 minutes

💰 Cost: ~$0.02/month difference (free tier: first 30 GB free)

  1. SSH into your EC2. Record the current state:

    lsblk
df -h

    📸 Screenshot: Baseline state — 8 GB volume before resize

  2. In AWS console → EC2 → Volumes → select root volume → Actions → Modify Volume. Change size to 20 GiB. Click Modify.

    📸 Screenshot: Modify Volume — changing from 8 to 20 GiB

  3. Back in the terminal, run lsblk again — the disk now shows 20 GB but the filesystem partition still shows 8 GB. The OS has not caught up yet.

    lsblk

    📸 Screenshot: lsblk shows disk = 20 GB but partition = 8 GB. The gap to fill.

  4. Grow the partition to fill the new disk space:

    sudo growpart /dev/nvme0n1 1

  5. Grow the XFS filesystem to fill the partition:

    sudo xfs_growfs -d /

  6. Verify — df -h should now show ~20 GB:

    df -h

    📸 Screenshot: df -h after xfs_growfs — filesystem now shows 20 GB. Instance never stopped.

❌ Most common mistake: Resizing in the console and assuming it is done. The OS still shows the old size until you run growpart + xfs_growfs. This is exactly what interviewers test.

Cleanup

No cleanup needed (volume size cannot be reduced). If cost is a concern, terminate the instance.

📈 Project 6: Scale Out Storage (Attach Multiple Volumes)

🎯 Objective: Attach two additional EBS volumes, mount them at /data1 and /data2, verify independence, and then use LVM to combine them into a single logical volume. This is how production infrastructure engineers think about storage.

⏱️ Time: 40–50 minutes

💰 Cost: ~$0.02 for two 10 GiB gp3 volumes (free tier eligible)

  1. Create two gp3 volumes (10 GiB each) in the same AZ. Attach both to your running EC2 instance.

    📸 Screenshot: Two volumes attached to the same instance — in-use state

  2. Format and mount each independently:

    sudo mkfs.xfs /dev/nvme1n1
sudo mkfs.xfs /dev/nvme2n1
sudo mkdir /data1 /data2
sudo mount /dev/nvme1n1 /data1
sudo mount /dev/nvme2n1 /data2
df -h

    📸 Screenshot: df -h showing /data1 and /data2 as separate 10 GB volumes

  3. Write files to each and verify they are independent:

    echo "Volume 1 data" | sudo tee /data1/vol1.txt
echo "Volume 2 data" | sudo tee /data2/vol2.txt
ls /data1
ls /data2

  4. Bonus: Combine with LVM — Unmount, then use LVM to merge them into one 20 GB logical volume.

    # Install LVM tools
sudo yum install lvm2 -y

# Unmount first
sudo umount /data1 /data2

# Initialize physical volumes
sudo pvcreate /dev/nvme1n1 /dev/nvme2n1

# Create volume group
sudo vgcreate data-vg /dev/nvme1n1 /dev/nvme2n1

# Create logical volume using all space
sudo lvcreate -l 100%FREE -n data-lv data-vg

# Format and mount the logical volume
sudo mkfs.xfs /dev/data-vg/data-lv
sudo mkdir /combined-data
sudo mount /dev/data-vg/data-lv /combined-data

# Verify — should show ~20 GB
df -h /combined-data

    📸 Screenshot: /combined-data shows ~20 GB — two volumes combined via LVM

⚡ Why LVM matters in production: LVM lets you add storage without changing application paths. Your app keeps writing to /combined-data — you just add more physical volumes and extend the group. No downtime, no reconfiguration.

Cleanup

  1. Unmount: sudo umount /combined-data
  2. Deactivate LVM: sudo vgchange -an data-vg
  3. Detach and delete both volumes from the console

🎯 Objective: Take a manual EBS snapshot of a volume containing data, delete the volume, then restore from the snapshot and verify the data is perfectly intact. This is the backbone of all disaster recovery on AWS.

⏱️ Time: 30–40 minutes

💰 Cost: Snapshots billed by data stored at S3 rates (~$0.05/GB-month). Delete after the project.

  1. Prepare a volume with meaningful data. Create and mount a 5 GiB gp3 volume, write several files:

sudo mkdir /backup-test
sudo mount /dev/nvme1n1 /backup-test
echo "Critical config file" | sudo tee /backup-test/config.txt
echo "Important database dump" | sudo tee /backup-test/db-dump.sql

ls -la /backup-test/

    📸 Screenshot: Files written to the volume before taking snapshot

  2. Unmount cleanly before snapshotting (best practice for data consistency):

    sudo umount /backup-test

  3. In the AWS console → EC2 → Volumes → select the volume → Actions → Create Snapshot. Add description: "Project 7 backup test".

    📸 Screenshot: Create Snapshot dialog — description helps identify snapshots later

  4. Navigate to EC2 → Snapshots and wait for status to change to completed.

    📸 Screenshot: Snapshot status = completed

  5. Now — the scary step — detach and delete the original volume from the console. The data is "gone".

    📸 Screenshot: Volume deleted — only the snapshot remains

  6. Navigate back to Snapshots → select your snapshot → Actions → Create Volume from Snapshot. Choose the same AZ as your EC2 instance.

📸 Project 8: Cross-AZ Migration via Snapshot

🎯 Objective: Take a snapshot of a volume in AZ-A (e.g., ap-south-1a), create a new volume from it in AZ-B (e.g., ap-south-1b), attach to a new EC2 instance in that AZ, and verify data integrity. This is exactly how real production migrations work.

⏱️ Time: 40–50 minutes

💰 Cost: Two small instances + snapshot storage — ~$0.05 total

  1. In AZ-A: Launch EC2-A. Create a 5 GiB volume in AZ-A, attach, mount, write data:

    sudo mkfs.xfs /dev/nvme1n1
sudo mkdir /migration-source
sudo mount /dev/nvme1n1 /migration-source
echo "Source AZ data — migrating to AZ-B" | sudo tee /migration-source/migration.txt
hostname >> /migration-source/migration.txt
date >> /migration-source/migration.txt

  2. Unmount, then take a snapshot of the volume. Wait for completed status.

    sudo umount /migration-source

    📸 Screenshot: Snapshot completed from AZ-A source volume

  3. Create a new volume from the snapshot — this time, select AZ-B (a different AZ in the same region).

    📸 Screenshot: Creating volume in AZ-B from the AZ-A snapshot

  4. Launch EC2-B in AZ-B. Attach the new volume to EC2-B.

  5. SSH into EC2-B. Mount and verify the migrated data:

    sudo mkdir /migration-dest
sudo mount /dev/nvme1n1 /migration-dest
cat /migration-dest/migration.txt

    📸 Screenshot: Data from AZ-A is accessible on EC2-B in AZ-B — migration successful

⚡ Key insight: EBS volumes are AZ-locked — you cannot directly move them. Snapshots are the bridge. The snapshot itself is region-scoped (not AZ-locked), which is why you can create a new volume from it in any AZ within the same region.   2. Delete both volumes and the snapshot

🧠 Project 10: Database Storage Architecture Design

🎯 Objective: Design and implement a multi-volume storage architecture for a production-grade application server: gp3 for the OS, io1 for the database, st1 for logs. Explain the reasoning behind each choice. This is direct interview preparation.

⏱️ Time: 45–60 minutes

💰 Cost: io1 is charged at $0.125/GB + $0.065/provisioned IOPS. Run for under 1 hour — ~$0.10.

⚡ The Architecture:
• EC2 instance — the application server
• gp3 (root, 8 GB) — operating system
• io1 (10 GB, 3000 IOPS) — database files
• st1 (500 GB) — application logs and audit data

  1. Launch an EC2 instance with a standard 8 GiB gp3 root volume. Create and attach:

    • 10 GiB io1 volume with 3000 provisioned IOPS
    • 500 GiB st1 volume

    📸 Screenshot: Three-volume architecture — gp3 OS, io1 database, st1 logs all attached

  2. Set up the database volume:

    sudo mkfs.xfs /dev/nvme1n1
sudo mkdir /var/lib/database
sudo mount /dev/nvme1n1 /var/lib/database
echo "Simulated DB data" | sudo tee /var/lib/database/data.db

  3. Set up the log volume:

    sudo mkfs.xfs /dev/nvme2n1
sudo mkdir /var/log/app
sudo mount /dev/nvme2n1 /var/log/app
echo "$(date): Application started on $(hostname)" | sudo tee /var/log/app/app.log

  4. Verify the complete architecture:

    lsblk
df -h

    📸 Screenshot: lsblk showing the complete three-tier storage architecture

  5. Write your architecture justification — this is what you say in an interview:

    cat << 'EOF' | sudo tee /var/log/app/architecture-notes.txt
Storage Design Justification:
- Root (gp3): OS and application binaries. gp3 balances price and performance.
  No need for io1 here — OS does not do high-frequency random I/O.
- Database (io1): PostgreSQL/MySQL data files. Databases need consistent,
  low-latency IOPS for random reads/writes. io1 with 3000 provisioned IOPS

  need random I/O performance.

🚀 Project 11: Automated Backup with AWS CLI + Cron

🎯 Objective: Write a shell script that creates an EBS snapshot using the AWS CLI, then schedule it with cron to run nightly. This is real production automation — the difference between manual backups and a robust backup strategy.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier CLI usage. Snapshot storage at S3 rates. Delete test snapshots after.

  1. Install and configure AWS CLI on the EC2 instance (requires an IAM role with EC2 permissions attached to the instance):

    # Verify CLI is installed
aws --version

# Verify the instance has permissions (should return instance metadata)
aws ec2 describe-instances --query 'Reservations[0].Instances[0].InstanceId' --output text

    📸 Screenshot: AWS CLI working — version shown and instance ID returned successfully

  2. Get your volume ID (replace nvme1n1 with your data volume device):

    # Get volume ID from the block device
VOLUME_ID=$(aws ec2 describe-volumes   --filters Name=attachment.instance-id,Values=$(curl -s http://169.254.169.254/latest/meta-data/instance-id)             Name=attachment.device,Values=/dev/sdf   --query 'Volumes[0].VolumeId' --output text)
echo "Volume ID: $VOLUME_ID"

  3. Create the backup script:

    sudo tee /usr/local/bin/ebs-backup.sh << 'SCRIPT'
#!/bin/bash
# EBS Automated Backup Script
VOLUME_ID="vol-XXXXXXXXXXXXXXXXX"   # Replace with your volume ID
DATE=$(date +%Y-%m-%d-%H%M)
DESCRIPTION="auto-backup-${DATE}"
LOG_FILE="/var/log/ebs-backup.log"

echo "[$(date)] Starting backup of ${VOLUME_ID}" >> $LOG_FILE

SNAPSHOT_ID=$(aws ec2 create-snapshot   --volume-id $VOLUME_ID   --description "$DESCRIPTION"   --query 'SnapshotId' --output text)

if [ $? -eq 0 ]; then
  echo "[$(date)] Snapshot created: ${SNAPSHOT_ID}" >> $LOG_FILE
else
  echo "[$(date)] ERROR: Snapshot creation failed" >> $LOG_FILE
  exit 1
fi

# Optional: delete snapshots older than 7 days
aws ec2 describe-snapshots   --filters Name=volume-id,Values=$VOLUME_ID             Name=description,Values="auto-backup-*"   --query 'Snapshots[?StartTime<=`'"$(date -d '7 days ago' --utc +%Y-%m-%dT%H:%M:%S)"'`].SnapshotId'   --output text | xargs -r aws ec2 delete-snapshot --snapshot-id

echo "[$(date)] Backup complete" >> $LOG_FILE
SCRIPT

sudo chmod +x /usr/local/bin/ebs-backup.sh

  4. Test the script manually:

    sudo /usr/local/bin/ebs-backup.sh
cat /var/log/ebs-backup.log

    📸 Screenshot: Backup script ran successfully — snapshot ID logged to /var/log/ebs-backup.log

  5. Verify the snapshot was created in the AWS console:

    📸 Screenshot: Snapshot visible in console — created automatically by the CLI script

  6. Schedule the script with cron to run every night at 2 AM:

    sudo crontab -e
# Add this line:
# 0 2 * * * /usr/local/bin/ebs-backup.sh
    # Verify the cron job was added
sudo crontab -l

    📸 Screenshot: crontab -l confirms the nightly backup is scheduled at 2 AM

✅ What you just built: A real production backup system — the same pattern used in companies before they adopt AWS Backup or DLM. Knowing this demonstrates you understand both the what (snapshots) and the how (automation via CLI + cron).

Cleanup

  1. Remove cron job: sudo crontab -e (delete the line)
  2. Delete test snapshots from the console
  3. Terminate the instance
