🚀 Introduction

In Windows, installing software feels familiar — you open a browser, download a .exe or .msi file, click through a wizard, and you're done. Linux is completely different, and honestly, much smarter once you understand how it works.

Linux uses a system called package management — a centralized, automated way to install, update, and remove software. Instead of hunting the internet for downloads, you simply tell Linux what you want, and it fetches everything from a trusted central location called a repository. No browser, no wizard, no manual dependency hunting.

Figure 1: Linux Software Management — How packages flow from repository to your system

This session also sets the stage for understanding web application architecture — you'll learn how a frontend, backend, and database all work together, and why web server software like Apache and Nginx is the critical piece that makes frontend applications accessible on the internet.

⚡ Why this matters for AWS: Every EC2 instance you launch runs Linux. Managing software on those servers — installing, updating, patching — is a daily task for every cloud engineer. This is not optional knowledge.

🌐 How Web Applications Work (3-Tier Architecture)

Before you can understand why you need to install web server software, you need to understand how a real-world web application is built. Every major application — Facebook, Netflix, Flipkart, Amazon Prime — follows the same pattern: three tiers.

Think of it like a restaurant. The menu and dining room is the frontend (what customers see). The kitchen is the backend (where the actual work happens). The storage room and pantry is the database (where all the ingredients/data live).

Figure 2: Three-Tier Web Application Architecture — Frontend, Backend, and Database

Tier 1 — Frontend (What the User Sees)

The frontend is the face of the application — what you see in your browser. When you open Facebook and see the login page with input fields for username and password, that's the frontend. It handles everything the user interacts with directly: buttons, forms, images, layouts.

The frontend is also called the client-side and is responsible for handling HTTP requests and sending responses back to the user's browser.

The software that powers the frontend tier — that serves your HTML, CSS, and JavaScript files to browsers — is called a web server. The two most popular web server softwares are:

  • Apache HTTP Server — the most widely used web server in the world, known for flexibility and broad compatibility
  • Nginx — known for high performance, low memory usage, and excellent handling of concurrent connections

💡 Real example: When you open amazon.com, your browser sends an HTTP request. The web server (Nginx/Apache) running on Amazon's servers receives that request and sends back the HTML page you see. The web server is the gatekeeper between the internet and the rest of the application.

Tier 2 — Backend (The Business Logic)

The backend is where the actual processing happens. When you type your username and password into Facebook and hit Login, the frontend sends that data to the backend. The backend's job is to process that request — check if your account exists, validate your password, decide what to show you next.

The backend is also called the server-side and is responsible for generating dynamic responses by processing requests and interacting with the database.

Popular backend technologies include:

  • Node.js — JavaScript runtime for building fast, scalable server-side applications
  • Flask — lightweight Python web framework, popular for APIs and microservices
  • Django, Spring Boot, Laravel — other popular backend frameworks

Tier 3 — Database (Where Data Lives)

The database is where all persistent data is stored — user accounts, orders, messages, product listings, everything. When the backend needs to check if your login credentials are valid, it queries the database.

The most common database software in Linux environments is MySQL, which stores and retrieves data for the backend application.

How All Three Tiers Talk to Each Other

Let's trace a complete login flow to make this concrete:

  1. You open flipkart.com — your browser makes an HTTP request
  2. The web server (Apache/Nginx) receives the request and serves the login page HTML
  3. You type your email and password and click Login
  4. The frontend sends your credentials to the backend (Node.js/Flask)
  5. The backend queries the database (MySQL): "Does this account exist? Is the password correct?"
  6. The database confirms: "Yes, valid credentials"
  7. The backend tells the frontend: "Access granted"
  8. The frontend logs you in and shows your dashboard

⚡ Key insight: Today's focus is on Tier 1 — the Frontend. To serve a frontend application on Linux, you need to install and configure a web server (Apache or Nginx). That's exactly why software management is the first thing to learn — you can't deploy anything without knowing how to install software.

📦 Types of Linux Software

In Linux, all the software you interact with falls into one of three categories. Understanding this helps you know what you're installing and why it matters.

Figure 3: Three Types of Linux Software — System, Application, and Utility

1. System Software

System software consists of the core programs that run and manage the operating system itself — without them, Linux wouldn't function.

Examples include:

  • Kernel — the heart of Linux, manages hardware resources
  • Bash — the shell (command line interpreter) you type commands into
  • systemd — the service manager (covered in service management)

You generally don't install or remove system software manually — it comes with the OS and is managed carefully during OS updates.

2. Application Software

Application software provides specific functionality to end users or services — these are the programs that actually do the work you care about.

Examples include:

  • Apache HTTP / Nginx — web server software for serving frontend applications
  • MySQL / PostgreSQL — database servers for storing data
  • Git — version control system for managing code
  • Python — programming language runtime

This is the software you'll install most often as a cloud engineer — setting up servers, databases, and tools on EC2 instances.

3. Utility Software

Utility software consists of supporting tools that help you manage, maintain, and work with the system — they are helper programs, not end-user applications.

Examples include:

  • vim / nano — text editors for editing config files
  • chmod — file permission manager
  • ls, cat, echo — basic file and output tools
  • tar, zip — compression utilities

📦 What is a Software Package?

Think of a software package like an IKEA box. When you buy an IKEA wardrobe, the box contains the actual wardrobe parts, the assembly instructions, the list of required tools, and all the small hardware (nuts, bolts, dowels). You don't need to source anything separately — everything is bundled together.

A Linux software package works exactly the same way.

Figure 4: Inside a Linux Software Package — The Four Components

A Linux package is a compressed archive (like a zip file) that contains:

  • Program Files — the actual executable software and libraries
  • Dependencies — other software libraries this package needs to function (a single app often relies on dozens of shared libraries)
  • Configuration Files — default settings files that go into /etc/
  • Metadata — information about the software: its name, version number, license, description, author

📸 From Session: Where RPM package files get placed after installation in system directories

💡 After installation, where do files go? When you install an RPM package (used on Amazon Linux/Red Hat), its files are unpacked and placed in standard system directories:

• Executables → /usr/bin/, /usr/local/bin/, /bin/
• Configuration files → /etc/
• Libraries → /usr/lib/, /lib64/
• Logs → /var/log/
• Temporary files → /tmp/
• Package metadata → /var/lib/rpm/

Package formats differ by Linux distribution: RPM (.rpm) is used by Red Hat, CentOS, and Amazon Linux, while DEB (.deb) is used by Ubuntu and Debian.

Why Dependencies Matter

Almost no software runs completely alone. Your web server (Apache) depends on OpenSSL for HTTPS. Git depends on several cryptography libraries. In Windows, you'd have to hunt down and install each of these manually. In Linux, the package manager handles all of this automatically — it reads the dependency list from the package metadata and installs everything required.

✅ This is the biggest advantage of package management: You install one package and the system automatically resolves and installs all required dependencies. No more "DLL not found" errors.

🗄️ What is a Repository?

Imagine a giant, officially maintained app store — but for your Linux server, accessible directly from the command line. That's a repository.

A repository is a central storage location of verified, pre-built software packages that a Linux system can install from and update against.

Figure 5: Repository Architecture — How packages flow from central storage to your system

Who Maintains Repositories?

Repositories are maintained by two types of members:

  • Official maintainers — for Amazon Linux, Amazon itself maintains the official repositories and updates them with security patches and new software versions. For Ubuntu, a company called Canonical Limited maintains the official repos.
  • Third-party maintainers — organizations like Google, Docker, and MongoDB maintain their own repositories for their specific software. When you install Docker on Linux, you add Docker's official repository and install from there.

Where Repository Configuration Lives on Your System

Your system knows which repositories to talk to because of configuration files stored locally. On Amazon Linux, repository configuration files are located at:

/etc/yum.repos.d/

You can explore this directory to see what repositories your system is configured to use:

cd /etc/yum.repos.d/ ls

You'll see files like amazonlinux.repo — these are the core repository files that define where Amazon Linux looks for packages. Each .repo file contains the URL of the remote repository, the GPG key for verification, and settings for whether the repo is enabled.

💡 Repository = Trust + Convenience: Every package in an official repository has been tested, verified, and signed. When you install from a repo, you know the software hasn't been tampered with. This is fundamentally more secure than downloading random executables from the internet.

🔧 Package Managers — The Bridge Between You and the Repository

The repository is the store, but you can't just walk into a store and grab items off the shelf yourself — you need someone to help you find things, check if you have what's needed, and carry everything back. That's the job of the package manager.

A package manager is a tool that automates the process of installing, updating, configuring, and removing software packages, including resolving all dependencies automatically.

Figure 6: Package Manager Workflow — From command to installed software

YUM vs APT — Which Package Manager Do You Use?

The package manager you use depends on your Linux distribution:

Linux DistributionPackage ManagerPackage Format
Amazon Linux, Red Hat (RHEL), CentOS, Fedorayum / dnf.rpm
Ubuntu, Debian, Linux Mintapt / apt-get.deb
Arch Linuxpacman.pkg.tar
SUSE Linuxzypper.rpm

For Amazon Linux (used in AWS EC2), the package manager is YUM (Yellowdog Updater, Modified), and it is pre-installed by default.

💡 Note: Newer versions of Amazon Linux (AL2023) and Fedora use dnf (Dandified YUM) as the default, but yum still works as an alias. In practice, both commands work identically for everyday tasks.

What the Package Manager Does for You

When you run yum install git, the package manager:

  1. Searches the configured repositories for a package named git
  2. Finds it and reads its dependency list
  3. Checks what's already installed on your system
  4. Downloads git and all missing dependencies
  5. Installs everything in the correct order
  6. Updates the package database to track what's installed

Compare this to Windows where you'd need to manually download Git from git-scm.com, run the installer, click through options, and then separately manage updates. The package manager does all of this in a single command.

⚙️ Installing Software with YUM

Now let's get practical. Here are the essential YUM commands you'll use every day as a Linux administrator on AWS EC2.

Checking if Software is Already Installed

Before installing, check if the software already exists:

git --version

If git is not installed, you'll see: bash: git: command not found. If it is installed, you'll see its version number.

You can also use YUM to check detailed package information:

yum info git

This shows the name, version, release, size, repository source, summary, and description of the git package — whether it's installed or just available in the repository.

Installing a Package

sudo yum install git

YUM will show you exactly what it's about to do — which packages it will download, from which repository, and how much disk space it needs. It then asks for confirmation: Is this ok [y/d/N]:

To skip the confirmation prompt and automatically say yes (useful in scripts):

sudo yum install git -y

The -y flag tells YUM to automatically answer yes to all prompts, allowing non-interactive (scriptable) installations.

Real Examples from Class

🔄 Update vs Upgrade — What's the Difference?

This is one of the most commonly confused concepts in Linux, and it comes up in every AWS interview. Let's clear it up once and for all.

Figure 8: Update vs Upgrade — Two different operations, often confused

CommandWhat it DoesAnalogy
sudo yum update -yRefreshes the local list of available packages from the repository — tells the system which versions are currently availableChecking the store's latest catalogue — you're just reading what's available, not buying anything
sudo yum upgrade -yActually downloads and installs newer versions of all currently installed packagesActually going to the store and replacing your old items with the new versions from the catalogue

You must always run yum update before yum upgrade — update refreshes the repository metadata, then upgrade uses that metadata to find and install the latest versions.

Daily Workflow: The Correct Order

# Step 1: Refresh repository metadata sudo yum update -y # Step 2: Upgrade all installed software to latest versions sudo yum upgrade -y

❌ Warning: Running sudo yum upgrade -y blindly in a production environment can break running applications. If an application is running on Python 3.8 and you upgrade Python to 3.11, the app might break due to version incompatibilities. Always confirm with your team before upgrading in production.

💡 Linux vs Windows for updates: On Windows, the OS automatically notifies you when updates are available with a pop-up notification. Linux servers have no such pop-up — there's no GUI notification system. As a Linux admin, you must proactively check for updates and run them manually (or automate it with a script).

🛡️ OS Patching — Why It's Critical

You've heard the word "patching" in Windows — those annoying "Restart to update" notifications. On Linux servers, patching is equally important but completely manual. Let's understand what it actually means and how to do it.

OS patching is the process of applying small code updates to fix or improve existing software without replacing it completely — addressing security vulnerabilities, resolving bugs, improving performance, and adding minor enhancements.

Figure 9: Why OS Patching Matters — Four Key Reasons

Why Patching is Non-Negotiable

  • Fix security vulnerabilities — unpatched servers are the #1 target for hackers. Vulnerabilities like Shellshock and Heartbleed affected millions of unpatched Linux servers.
  • Resolve bugs — software bugs cause crashes, incorrect behavior, and data corruption. Patches fix these without requiring a full reinstall.
  • Improve performance — patches often include optimizations that make software run faster or use fewer resources.
  • Minor feature enhancements — small improvements that don't justify a full version upgrade but add useful capabilities.

Step-by-Step: How to Patch a Specific Package

Here's the exact process to check for and apply a patch for a specific piece of software (e.g., Git):

# Step 1: Check the currently installed version git --version # or yum info git
# Step 2: Check if any patch/update is available sudo yum check-update git
# Step 3: Review the update details (what version, from which repo) # Output will show the new version available # Step 4: Apply the patch (after confirming with your team in production) sudo yum update git -y
# Step 5: Verify the update was applied git --version

⚡ Real output you'll see: When you run sudo yum check-update git on Amazon Linux 2023, you may see a warning: "New release of Amazon Linux is available." This means you're already on the latest version of Amazon Linux 2023 but Amazon Linux has a newer major release available. This is not a problem — it means your current OS is up to date.

Automating Patch Checks

Since Linux doesn't show pop-up notifications like Windows, you can automate patch checking using a shell script that runs when a user logs in, or on a schedule using cron. For example, a simple script that runs yum check-update every day and emails the admin if patches are available.

💡 In AWS environments, you can automate patching at scale using AWS Systems Manager Patch Manager — it lets you define patching schedules and automatically apply approved patches to all your EC2 instances without logging into each one individually.

📝 Overall Summary

  • 3-Tier Architecture: Every major web application has three layers — Frontend (what users see), Backend (processing logic), and Database (data storage). Web server software like Apache/Nginx powers the frontend tier.
  • Three types of Linux software: System software (OS core programs like kernel and bash), Application software (end-user programs like Apache and MySQL), and Utility software (supporting tools like vim and chmod).
  • Packages: A Linux software package is a compressed bundle containing the program files, dependencies, configuration files, and metadata — everything needed to install the software in one shot.
  • Repositories: Central, verified storage locations from which Linux systems fetch software packages. On Amazon Linux, repository configs live in /etc/yum.repos.d/. Amazon and Canonical are examples of official repository maintainers.
  • Package Managers: YUM is used on Amazon Linux and Red Hat; APT is used on Ubuntu and Debian. Package managers automate installation, dependency resolution, and updates.
  • yum install <package> -y: The core command to install software. The -y flag skips confirmation prompts — essential for automation scripts.
  • Update vs Upgrade:yum update refreshes the repository metadata (catalogue); yum upgrade actually installs newer versions of installed software. Always run update before upgrade.
  • OS Patching: Applying small code updates to fix security vulnerabilities, resolve bugs, improve performance, and add minor enhancements — without replacing the software entirely. Critical for server security.
  • No GUI notifications: Unlike Windows, Linux servers don't show pop-ups for available updates. Admins must proactively check and apply patches, or automate with scripts or AWS Systems Manager Patch Manager.
  • Production caution: Never run yum upgrade blindly in production — always check with the team first, as upgrades can break existing applications that depend on specific software versions.

Project 1: Install and Deploy a Web Server on EC2

🎯 Objective: Install Apache HTTP Server on an Amazon Linux EC2 instance, deploy a sample HTML page, and access it from a browser.

⏱️ Time: 30-45 min

💰 Cost: Free tier (t2.micro or t3.micro)

💰 Cost Note: EC2 instances outside the free tier (t2.micro) will incur charges. Ensure you're using a free-tier eligible instance type and remember to stop/terminate after completing the project.

  1. SSH into your Amazon Linux EC2 instance using your key pair.

    ssh -i your-key.pem ec2-user@your-ec2-public-ip

    Figure N: 📸 Successful SSH login — you should see the Amazon Linux welcome banner and ec2-user prompt

  2. Update the repository metadata to ensure you get the latest package information.

    sudo yum update -y

    Figure N: 📸 Repository update — look for the Complete! message at the end

  3. Install Apache HTTP Server using YUM.

    sudo yum install httpd -y

    Figure N: 📸 Apache install — note the package name is httpd (not apache), and the dependency packages installed automatically

  4. Start the Apache service and enable it to start automatically on reboot.

    sudo systemctl start httpd sudo systemctl enable httpd

  5. Verify Apache is running.

    sudo systemctl status httpd

    Figure N: 📸 Apache status — look for the green 'active (running)' text to confirm the service is running

  6. Create a simple HTML page to test your deployment. Apache serves files from /var/www/html/.

    sudo nano /var/www/html/index.html

    Add this content:

    <html> <body> <h1>Hello from my EC2 instance!</h1> <p>Apache web server is running on Amazon Linux.</p> </body> </html>

    Save with Ctrl+X, Y, Enter.

  7. Open your browser and navigate to your EC2 instance's public IP address: http://your-ec2-public-ip. Make sure port 80 is open in your EC2 security group.

    Figure N: 📸 Browser confirmation — your HTML page should appear at the EC2 public IP address on port 80

Verification

# Confirm Apache is running sudo systemctl status httpd # Check the web root directory ls /var/www/html/ # Check Apache version httpd -v

Cleanup

# Stop the service sudo systemctl stop httpd # Optionally uninstall sudo yum remove httpd -y

If you no longer need the EC2 instance, stop or terminate it from the AWS Console to avoid charges.

Project 3: Package Deep Dive — Where Does Software Actually Go?

🎯 Objective: Install Nginx and trace exactly where every file lands on the filesystem. Build mental clarity on Linux directory structure — this is what separates beginners from engineers.

⏱️ Time: 20-30 min

💰 Cost: Free tier (using existing EC2 instance)

Most beginners install software and never think about where it goes. In DevOps, you need to know exactly where the binary is, where the config lives, and where logs are written. This project makes that instinct automatic.

  1. Install Nginx.

    sudo yum install nginx -y

  2. Find the Nginx binary — the actual executable file.

    which nginx

    Figure N: 📸 which nginx — shows the exact path of the installed binary (/usr/sbin/nginx)

  3. List every single file that the Nginx RPM package installed on your system.

    rpm -ql nginx

    Figure N: 📸 rpm -ql nginx — every file the package placed on your system. Note the pattern: binary in /usr/sbin/, config in /etc/nginx/, logs in /var/log/nginx/

  4. Explore the three key locations and verify they exist.

    # Config files ls /etc/nginx/ # Default web root ls /usr/share/nginx/html/ # Log directory (empty until Nginx starts) ls /var/log/nginx/

    Figure N: 📸 Three key directories — config in /etc/, web content in /usr/share/, logs in /var/log/

  5. Start Nginx and check the log directory again — watch how logs appear once the service is running.

    sudo systemctl start nginx ls /var/log/nginx/ cat /var/log/nginx/access.log

    Figure N: 📸 Log files appear after the service starts — access.log and error.log are now present

  6. View the main Nginx configuration file to understand its structure.

    cat /etc/nginx/nginx.conf

    Figure N: 📸 nginx.conf — note the root directive pointing to /usr/share/nginx/html/ and listen 80 for HTTP traffic

✅ The pattern you just learned applies to every package: Binary in /usr/bin/ or /usr/sbin/, config in /etc/, logs in /var/log/, data in /var/. This is the Linux Filesystem Hierarchy Standard (FHS) — it never changes.

Cleanup

sudo systemctl stop nginx sudo yum remove nginx -y

Project 4: Break It and Fix It — Service Lifecycle Mastery

🎯 Objective: Intentionally break Apache in different ways, diagnose the problem using logs and status commands, and fix it. Real DevOps is mostly debugging — this builds that muscle.

⏱️ Time: 30-45 min

💰 Cost: Free tier

💰 Cost Note: You need an EC2 instance running. Use a t2.micro or t3.micro (free tier eligible). Remember to stop the instance when done.

  1. Install Apache and deploy a working page first.

    sudo yum install httpd -y sudo systemctl start httpd sudo systemctl enable httpd echo "<h1>Working!</h1>" | sudo tee /var/www/html/index.html

    Verify it works in your browser at the EC2 public IP.

    Figure N: 📸 Working baseline — confirm the page loads before you start breaking things

  2. Break #1 — Stop the service. Stop Apache and try to load the page in your browser. What error do you see?

    sudo systemctl stop httpd sudo systemctl status httpd

    Figure N: 📸 Service stopped — note the red 'inactive (dead)' status. Your browser will now show 'Connection refused'

    Fix it:

    sudo systemctl start httpd

  3. Break #2 — Delete the HTML file. Remove the index page and reload your browser.

    sudo rm /var/www/html/index.html

    The service is still running but you'll get a 403 Forbidden error — Apache has nothing to serve. Check the error log:

    sudo cat /var/log/httpd/error_log

    Figure N: 📸 403 Forbidden — the service runs but the content file is missing. The error_log tells you exactly what happened

    Fix it by recreating the file:

    echo "<h1>Fixed!</h1>" | sudo tee /var/www/html/index.html

  4. Break #3 — Introduce a config error. Edit the Apache config and add invalid syntax, then try to restart.

    sudo nano /etc/httpd/conf/httpd.conf

    Add a line with invalid syntax anywhere: INVALID_DIRECTIVE yes. Save and exit. Now try to restart:

    sudo systemctl restart httpd

    Figure N: 📸 Config error restart failure — always check 'sudo systemctl status httpd' and 'sudo journalctl -xe' to find the exact line causing the error

    Diagnose using Apache's built-in config tester:

    sudo httpd -t

    This shows exactly which line has the error. Fix it by removing the invalid line, then:

    sudo httpd -t # Confirm config is valid sudo systemctl start httpd

⚡ Interview gold: "Walk me through how you'd debug a web server that's not responding." Answer: (1) Check service status with systemctl status, (2) Check logs in /var/log/httpd/error_log, (3) Validate config with httpd -t, (4) Check if the port is open with ss -tlnp.

Cleanup

sudo systemctl stop httpd sudo yum remove httpd -y

Project 5: Patch Management Workflow — The DevOps Daily Routine

  3. Step 2: Refresh repository metadata to get the latest available versions.

  4. Step 3: Check specifically if git has any updates available.

  5. Step 4: Check ALL available updates across the entire system (not just git).

    sudo yum check-update

    Figure N: 📸 Full system check-update — this is your patch review list. A DevOps engineer reviews this before deciding what to apply

  6. Step 5: Apply the git patch specifically (not a blanket upgrade of everything).

    sudo yum update git -y

  7. Step 6: Verify the version changed after patching.

    git --version yum info git

    Figure N: 📸 After patching — compare to the before screenshot. The version should be the same or newer (if an update was available)

Project 6: Auto Patch Checker — Your First Automation Script

🎯 Objective: Write a real bash script that checks for available updates and logs the results. Then schedule it to run automatically every day using cron. This is the exact type of automation script DevOps engineers write in their first month on the job.

⏱️ Time: 30-40 min

💰 Cost: Free tier

  1. Create the patch check script.

    sudo nano /usr/local/bin/patch-check.sh

    Paste this content exactly:

    #!/bin/bash # Patch Check Script # Runs daily to log available updates on this server LOG_FILE="/var/log/patch-check.log" DATE=$(date '+%Y-%m-%d %H:%M:%S') HOSTNAME=$(hostname) echo "========================================" >> $LOG_FILE echo "Patch Check — $DATE" >> $LOG_FILE echo "Server: $HOSTNAME" >> $LOG_FILE echo "========================================" >> $LOG_FILE # Refresh repo metadata sudo yum update -y >> /dev/null 2>&1 # Check for available updates UPDATE_COUNT=$(sudo yum check-update --quiet 2>/dev/null | grep -v "^$" | grep -v "Loaded" | wc -l) if [ "$UPDATE_COUNT" -gt 0 ]; then echo "STATUS: $UPDATE_COUNT package(s) have updates available" >> $LOG_FILE sudo yum check-update --quiet 2>/dev/null | grep -v "^$" | grep -v "Loaded" >> $LOG_FILE else echo "STATUS: All packages are up to date" >> $LOG_FILE fi echo "" >> $LOG_FILE

    Save with Ctrl+X, Y, Enter.

  2. Make the script executable.

    sudo chmod +x /usr/local/bin/patch-check.sh

    Figure N: 📸 Script created and made executable — note the 'x' permission bits in ls -la output confirming it can be executed

  3. Run the script manually once to test it.

    sudo /usr/local/bin/patch-check.sh

  4. Check the log file output.

    cat /var/log/patch-check.log

    Figure N: 📸 patch-check.log — your script's output. This is exactly what an admin would check each morning to know if servers need patching

  5. Schedule the script to run every day at 6 AM using cron.

    crontab -e

    Add this line at the bottom of the cron file (press i to insert if using vi, or just type in nano):

    0 6 * * * /usr/local/bin/patch-check.sh

    Save and exit.

    Figure N: 📸 Crontab entry — '0 6 * * *' means at minute 0, hour 6, every day. Your patch check is now fully automated

  6. Verify the cron job was saved correctly.

    crontab -l

⚡ What you just built: A real-world patch monitoring system. Every morning at 6 AM, this script silently checks your server for available updates and writes the results to a log file. An admin (or another script) can read that log to decide whether patching is needed — no manual SSH required.

Cleanup

# Remove the cron job crontab -r # Remove the script sudo rm /usr/local/bin/patch-check.sh # Remove the log sudo rm /var/log/patch-check.log

Project 7: 3-Tier Architecture — Lite Version (Apache + Flask)

🎯 Objective: Build the first two tiers of a real 3-tier application: Apache as the frontend web server, and a Python Flask app as the backend. See how a browser request travels through both tiers.

⏱️ Time: 45-60 min

💰 Cost: Free tier (t2.micro or t3.micro)

💰 Cost Note: Ensure your EC2 security group has port 80 (HTTP) and port 5000 (Flask) open for testing. Remove port 5000 access when done for security.

  1. Install all required software in one command.

    sudo yum install httpd python3 python3-pip -y

  2. Install Flask using pip (Python's package manager).

    pip3 install flask

    Figure N: 📸 Flask installed via pip — note this is Python's package manager (pip), separate from YUM which handles system packages

  3. Create the Flask backend application.

    mkdir ~/myapp nano ~/myapp/app.py

    Paste this content:

    from flask import Flask app = Flask(__name__) @app.route('/api/hello') def hello(): return {"message": "Hello from the Backend!", "tier": "Backend (Flask)", "server": "Amazon Linux EC2"} @app.route('/api/status') def status(): return {"status": "running", "backend": "Flask 3.x", "database": "Not connected yet"} if __name__ == '__main__': app.run(host='0.0.0.0', port=5000)

    Save and exit.

  4. Start the Flask backend in the background.

    cd ~/myapp python3 app.py &

    Figure N: 📸 Flask backend running on port 5000 — the '&' at the end runs it as a background process so you can continue using the terminal

  5. Test the Flask backend directly first (before Apache is involved).

    curl http://localhost:5000/api/hello curl http://localhost:5000/api/status

    Figure N: 📸 Flask API responding to curl — this confirms the backend is working before the frontend connects to it

  6. Now create the Apache frontend. Start Apache and create an HTML page that calls the Flask API.

    sudo systemctl start httpd sudo nano /var/www/html/index.html

    Paste this content:

    <!DOCTYPE html> <html> <head><title>My 3-Tier App</title></head> <body> <h1>Frontend (Apache) — Tier 1</h1> <p>This page is served by Apache on Amazon Linux EC2.</p> <button onclick="callBackend()">Call Backend API</button> <div id="result"></div> <script> function callBackend() { fetch('http://' + window.location.hostname + ':5000/api/hello') .then(r => r.json()) .then(data => { document.getElementById('result').innerHTML = '<p><strong>Backend says:</strong> ' + data.message + '</p>'; }); } </script> </body> </html>

    Save and exit.

  7. Open your browser and navigate to your EC2 public IP. Click the "Call Backend API" button and watch the frontend call the Flask backend.

    Figure N: 📸 3-Tier architecture working — Apache (Tier 1) serves the HTML, the button click calls Flask (Tier 2) which returns data. Two tiers communicating live in your browser

✅ What you just built: A working 2-tier system (Frontend + Backend). You can now say in any interview: "I've deployed a multi-tier web application on EC2 with Apache as the web server and Flask as the backend API, and verified end-to-end communication between tiers."

Cleanup

# Stop Flask background process kill $(lsof -t -i:5000) # Stop Apache sudo systemctl stop httpd sudo yum remove httpd python3-pip -y

Project 8: Automated Server Setup Script — Job-Level DevOps Work

🎯 Objective: Write a single bash script that completely sets up a fresh server — installs all required software, starts all services, and produces a status report. This is what a DevOps engineer delivers as a "server bootstrap script" and is directly discussable in interviews.

⏱️ Time: 40-50 min

💰 Cost: Free tier — ideally use a fresh EC2 instance to test the full flow

  1. Create the server setup script.

    nano ~/server-setup.sh

    Paste this complete script:

    #!/bin/bash # ============================================ # Server Setup Script — Amazon Linux 2023 # Sets up: Nginx, Git, Python3 # Starts all services and verifies installation # ============================================ set -e # Exit on any error LOG="/var/log/server-setup.log" DATE=$(date '+%Y-%m-%d %H:%M:%S') echo "[$DATE] Starting server setup..." | sudo tee -a $LOG # --- Step 1: Update repositories --- echo "[INFO] Refreshing package repositories..." | sudo tee -a $LOG sudo yum update -y >> $LOG 2>&1 echo "[OK] Repositories refreshed" | sudo tee -a $LOG # --- Step 2: Install packages --- PACKAGES="nginx git python3" echo "[INFO] Installing: $PACKAGES" | sudo tee -a $LOG sudo yum install $PACKAGES -y >> $LOG 2>&1 echo "[OK] Packages installed" | sudo tee -a $LOG # --- Step 3: Start and enable Nginx --- echo "[INFO] Starting Nginx..." | sudo tee -a $LOG sudo systemctl start nginx sudo systemctl enable nginx echo "[OK] Nginx started and enabled" | sudo tee -a $LOG # --- Step 4: Verify installations --- echo "" | sudo tee -a $LOG echo "=== Installation Summary ===" | sudo tee -a $LOG nginx -v 2>&1 | sudo tee -a $LOG git --version | sudo tee -a $LOG python3 --version | sudo tee -a $LOG # --- Step 5: Service status --- echo "" | sudo tee -a $LOG echo "=== Service Status ===" | sudo tee -a $LOG sudo systemctl is-active nginx | sudo tee -a $LOG echo "" | sudo tee -a $LOG echo "[$DATE] Setup complete! Check $LOG for full details." | sudo tee -a $LOG echo "Server is ready." | sudo tee -a $LOG

    Save with Ctrl+X, Y, Enter.

  2. Make it executable.

    chmod +x ~/server-setup.sh

  3. Run the script.

    sudo ~/server-setup.sh

    Figure N: 📸 Setup script running — each step is logged. The [OK] messages confirm each step completed. The [INFO] lines show what's happening at each stage

  4. Review the complete setup log.

    cat /var/log/server-setup.log

    Figure N: 📸 Setup log — a complete audit trail of everything the script did. In a real environment, this log is evidence that the server was configured correctly

  5. Verify all services and software are working as expected.

    sudo systemctl status nginx nginx -v git --version python3 --version

    Figure N: 📸 All systems verified — nginx running, git and python3 installed. The automated script set up a production-ready server without a single manual install command

⚡ What you can say in interviews: "I wrote a server bootstrap script that automates the complete setup of a fresh EC2 instance — package installation, service configuration, and verification — all logged for audit purposes. A new server can be fully configured in under 2 minutes."

Cleanup

sudo systemctl stop nginx sudo yum remove nginx git python3 -y sudo rm /var/log/server-setup.log

🤔 Reflection Questions

1. You're setting up a new EC2 instance for a production web application. Walk through every step of installing and configuring Apache, from the first command to verifying the site is live in a browser. What would you check at each stage?

💡 Hint

Think about the order: update repos → install httpd → start and enable service → check status → open security group → create content → verify in browser.

2. A junior engineer asks: "Why can't I just download Apache's .exe from the website and install it like on Windows?" How would you explain the Linux package management philosophy and why it's actually better?

💡 Hint

Think about: dependency resolution, security (signed packages), centralized updates, speed, and repeatability.

3. Your manager asks you to "patch all the servers tonight." What exact commands would you run, and what precaution would you take before running yum upgrade on a production server?

💡 Hint

Consider: checking for updates first, confirming with the team about version compatibility, testing on a staging environment before production, and having a rollback plan.

4. What's the difference between a repository and a package manager? Could you use one without the other?

💡 Hint

Repository = the store (where packages live). Package manager = the tool that talks to the store. Technically you could manually download .rpm files and install them, but you'd lose automatic dependency resolution.

5. You're building a 3-tier web application. A user reports they can access the site but their login isn't working even though they're sure the password is correct. Which tier do you investigate first, and why?

💡 Hint

If the site loads (frontend works), the issue is in Tier 2 (backend processing login logic) or Tier 3 (database storing credentials). Start with the backend logs.

6. How would you automate daily patch checks on a Linux server so that the admin receives a notification if updates are available, without manually running commands every day?

💡 Hint

Think about cron jobs to schedule yum check-update, shell scripts to parse the output and send an email/notification, or AWS Systems Manager Patch Manager for large-scale automation.
