🌐 Background: What Is a Checksum?

A checksum is like a unique seal on an envelope. An algorithm reads every single byte of your file in sequence and produces a fixed-length string. If even one byte changes — due to network packet corruption, hard drive failure, a cosmic ray, or any other reason — the checksum changes completely. This makes it impossible for corruption to go undetected.

Figure 2: One byte changed — completely different checksum. Corruption cannot hide.

Amazon S3 supports four additional checksum algorithms beyond its default MD5/ETag mechanism: SHA-1, SHA-256, CRC32, and CRC32-C. The checksum is calculated at upload time and preserved for the entire lifespan of the object, then validated again at download — providing true end-to-end data integrity.

Figure 3: Choosing the right algorithm — security vs. performance trade-off

Algorithm Output Speed Cryptographic Best For
SHA-256 256 bits Moderate ✅ Yes Healthcare, finance, compliance, archival
SHA-1 160 bits Moderate ⚠️ Weak Legacy compatibility only
CRC32 32 bits Fast ❌ No High-throughput media uploads
CRC32-C 32 bits Fastest ❌ No Large migrations, hardware-accelerated envs

✅ Key Rule: Regulated data → SHA-256. Maximum throughput → CRC32-C. Legacy systems → SHA-1. General media → CRC32.

🔧 Extended Task 1: Upload with AWS CLI Checksum Verification

Instead of clicking in the console, engineers upload via CLI. The --checksum-algorithm flag tells the CLI to calculate a checksum and send it with the upload request. S3 verifies this server-side before storing the object. 

aws s3api put-object \
  --bucket your-name-checksum-extended-lab \
  --key photo1.txt \
  --body photo1.txt \
  --checksum-algorithm SHA256

If the upload succeeds, the checksum matched. If not, S3 rejected it. This is the exact integrity validation used in production data pipelines.

Verify the upload worked

aws s3api list-objects-v2 \
  --bucket your-name-checksum-extended-lab \
  --query "Contents[].{Key:Key,Size:Size}" \
  --output table

✅ You should see your file listed with its key name and size in bytes.

💡 Try the other algorithm flags too:
--checksum-algorithm CRC32 — fastest, use for high-volume media
--checksum-algorithm CRC32C — hardware accelerated, use for large migrations
--checksum-algorithm SHA1 — legacy compatibility only

Re-run the upload command with each flag and note that all succeed — then use head-object in Task 2 to see which checksum field S3 stored for each.

🔍 Extended Task 2: Retrieve Object Metadata and Checksum

After uploading, you will query S3 metadata programmatically to confirm the stored checksum. The head-object command retrieves metadata without downloading the file — critical at scale when files are gigabytes.

aws s3api head-object \
  --bucket your-name-checksum-extended-lab \
  --key photo1.txt

Look for the ChecksumSHA256 field in the JSON response. It will look something like:

{
  "ContentLength": 19,
  "ContentType": "binary/octet-stream",
  "ETag": "\"d41d8cd98f00b204e9800998ecf8427e\"",
  "ChecksumSHA256": "abc123XYZ+base64value==",
  "ServerSideEncryption": "AES256"
}

Extract just the checksum value

aws s3api head-object \
  --bucket your-name-checksum-extended-lab \
  --key photo1.txt \
  --query "ChecksumSHA256" \
  --output text

Copy this value — you will compare it against your local calculation in the next task.

💡 Why use head-object instead of get-object?
head-object fetches metadata only — no data transfer, no egress cost. For a bucket with 100,000 files, you can verify checksums without downloading a single byte. This is how automated integrity monitoring scripts work.

⚡ Hands-on challenge: Upload contract.txt using --checksum-algorithm CRC32 and then run head-object on it. Notice that S3 stores ChecksumCRC32 instead of ChecksumSHA256 — the field name matches the algorithm used at upload.

✅ Extended Task 3: Compare Checksums Locally

Now compare what S3 stored against what your local file produces. These values must be identical for the transfer to be considered intact.

macOS / Linux

shasum -a 256 photo1.txt

This outputs a hex value. To convert to base64 (the format S3 uses):

shasum -a 256 photo1.txt | cut -f1 -d\ | xxd -r -p | base64

Windows (PowerShell)

$hash = (Get-FileHash -Algorithm SHA256 photo1.txt).Hash.ToLower()
$bytes = [byte[]]::new($hash.Length / 2)
for ($i = 0; $i -lt $hash.Length; $i += 2) {
    $bytes[$i / 2] = [Convert]::ToByte($hash.Substring($i, 2), 16)
}
[Convert]::ToBase64String($bytes)

Windows (certutil — simpler, hex only)

certutil -hashfile photo1.txt SHA256

💡 Note: certutil outputs hex, not base64. Use the PowerShell method above to get base64 for a direct comparison with the S3 value from Task 2.

✅ Local base64 value = S3 ChecksumSHA256 value → Integrity confirmed, file intact.

❌ Values differ → The file was corrupted during transfer. Re-upload and verify again.

Use the cleaner openssl method (macOS/Linux)

A shorter, single-pipeline alternative that skips the hex step entirely:

openssl dgst -sha256 -binary photo1.txt | base64

The -binary flag outputs raw bytes directly — no hex conversion needed. Both produce identical results; use whichever feels more readable.

🤖 Extended Task 4: Automate — Batch Upload and Validation Script

Instead of checking files one at a time, you will write a script that uploads an entire folder, retrieves checksums, compares them, and logs PASS or FAIL for each file. Save this as validate.sh:

#!/bin/bash
BUCKET="your-name-checksum-extended-lab"
PASS=0
FAIL=0

echo "================================================"
echo " S3 Checksum Validation Pipeline"
echo " Bucket: $BUCKET"
echo "================================================"

for file in *.txt *.csv *.jpg 2>/dev/null; do
  [ -f "$file" ] || continue

  echo ""
  echo "Processing: $file"

  # Upload with SHA-256 checksum
  aws s3api put-object \
    --bucket "$BUCKET" \
    --key "$file" \
    --body "$file" \
    --checksum-algorithm SHA256 \
    --output text > /dev/null

  # Calculate local checksum in base64
  LOCAL=$(shasum -a 256 "$file" | cut -f1 -d\  | xxd -r -p | base64)

  # Retrieve S3 stored checksum
  S3=$(aws s3api head-object \
    --bucket "$BUCKET" \
    --key "$file" \
    --query "ChecksumSHA256" \
    --output text)

  echo "  Local : $LOCAL"
  echo "  S3    : $S3"

  if [ "$LOCAL" = "$S3" ]; then
    echo "  Status: ✅ PASS — Integrity Confirmed"
    ((PASS++))
  else
    echo "  Status: ❌ FAIL — Mismatch Detected"
    ((FAIL++))
  fi
done

echo ""
echo "================================================"
echo " Results: $PASS PASS | $FAIL FAIL"
echo "================================================"

Run the script

chmod +x validate.sh
./validate.sh

✅ You should see PASS for each file. A PASS for every file means every byte transferred correctly.

💥 Extended Task 5: Simulate File Corruption

This task makes the concept concrete. You will intentionally corrupt a file and prove that the checksum catches it immediately.

Step 1 — Record the original checksum

shasum -a 256 photo1.txt

Copy the hex value. This is your baseline.

Step 2 — Corrupt the file

# Append junk bytes to simulate corruption
echo "corruption-test-byte-injection" >> photo1.txt

Step 3 — Recalculate and compare

shasum -a 256 photo1.txt

The new value will be completely different from the original — even though you only added a few bytes to the end. This is the avalanche effect of cryptographic hash functions.

❌ Result: Original checksum ≠ Corrupted file checksum. Any script or system comparing these values will know instantly that something changed.

Step 4 — Attempt upload with old checksum (rejection test)

Try uploading the corrupted file with the original (now wrong) checksum — S3 should reject it:

# First get the original S3 checksum
ORIGINAL_S3=$(aws s3api head-object \
  --bucket your-name-checksum-extended-lab \
  --key photo1.txt \
  --query "ChecksumSHA256" \
  --output text)

# Attempt to upload corrupted file with old checksum — this should FAIL
aws s3api put-object \
  --bucket your-name-checksum-extended-lab \
  --key photo1.txt \
  --body photo1.txt \
  --checksum-algorithm SHA256 \
  --checksum-sha256 "$ORIGINAL_S3"

✅ Expected result: S3 returns an error: InvalidChecksum or BadDigest. The corrupted file was rejected. The original uncorrupted version remains safely in S3.

⚡ Now run the batch script again: Re-run ./validate.sh from Task 4. The corrupted photo1.txt will now show ❌ FAIL in the batch output — because the local copy no longer matches what S3 has stored.

Download the object

Verify checksum of the downloaded file

🔴 Scenario C: Checksum mismatch — BadDigest error

# Create a file and calculate its checksum
echo "Original content for mismatch test" > mismatch-test.txt
CORRECT=$(shasum -a 256 mismatch-test.txt | cut -f1 -d\  | xxd -r -p | base64)
echo "Correct checksum: $CORRECT"

  --body mismatch-test.txt \
  --checksum-algorithm SHA256 \
  --checksum-sha256 "$FRESH"

🔴 Scenario D: CRLF line ending mismatch (cross-platform)

# Simulate a Windows file with CRLF line endings
printf "Line 1\r\nLine 2\r\nLine 3\r\n" > windows-file.txt

# Calculate checksum on this CRLF file
CRLF_HASH=$(shasum -a 256 windows-file.txt | cut -f1 -d\  | xxd -r -p | base64)
echo "CRLF hash: $CRLF_HASH"

# Now convert to Unix LF line endings
sed 's/\r//' windows-file.txt > unix-file.txt

# Calculate checksum on LF file
LF_HASH=$(shasum -a 256 unix-file.txt | cut -f1 -d\  | xxd -r -p | base64)
echo "LF hash:   $LF_HASH"

# Are they the same?
[ "$CRLF_HASH" = "$LF_HASH" ] && echo "MATCH" || echo "DIFFERENT — line endings affect checksums!"

Lesson: These will be different. In cross-platform pipelines, always normalize line endings before checksumming. Use file windows-file.txt to detect line ending type.

file yourfile.txt — shows if file has CRLF
cat -A yourfile.txt | head -3 — shows ^M$ at line ends (the CRLF carriage return)
sed -i 's/\r//' yourfile.txt — convert CRLF to LF in-place

🧪 Extended Task 9: Testing Checksums Across File Types and Sizes

Checksums work identically regardless of file type — but behavior around large files, binary data, and empty files has some interesting edge cases worth knowing. Run each test and observe the results.

Test 1 — Binary vs text files

# Create a text file
echo "Hello, this is text content." > test-text.txt

# Create a binary file (random bytes)
dd if=/dev/urandom bs=1024 count=10 of=test-binary.bin 2>/dev/null

# Create a CSV file
printf "name,age,city\nAlice,30,Mumbai\nBob,25,Delhi\n" > test-data.csv

import json
import time

verify_artifact() {

    return 1

}

💰 Cost Note: Cross-Region Replication incurs data transfer charges between regions (typically $0.02–$0.09/GB depending on regions). Use small files (under 1 MB each) to keep costs under $0.01.

done

📝 Overall Summary
  • Checksum = byte-level fingerprint: Every byte processed sequentially produces a fixed-length output. A single changed byte produces a completely different hash — avalanche effect ensures corruption cannot go undetected.
  • Two use cases, four algorithms: SHA-256 gives cryptographic proof required for HIPAA, PCI-DSS, and FINRA compliance. CRC32-C is hardware-accelerated — fastest for high-throughput pipelines. SHA-1 is legacy only. CRC32 suits general media. Benchmarked: CRC32-C is typically 3-10x faster than SHA-256 for the same file (ET20).
  • End-to-end protection: S3 calculates at upload, stores as metadata, re-validates at download. Neither direction is trusted without verification. All three values — local, stored, downloaded — must match (ET6).
  • Two ways to convert: shasum pipeline vs openssl: Both produce identical base64 SHA-256 output. shasum -a 256 | cut | xxd -r -p | base64 vs openssl dgst -sha256 -binary | base64. openssl skips the hex-to-binary step. Use whichever is available on your system (ET3).
  • Precalculated checksums = rejection at the gate: Providing your checksum makes S3 compare it against its own. BadDigest/InvalidChecksum = upload rejected before corrupt data touches storage (ET5, ET21).
  • aws s3api put-object, not aws s3 cp: The high-level aws s3 cp does not support --checksum-algorithm. Use aws s3api put-object for all checksum-verified production uploads. CLI command reference table covers all 10 essential S3 commands (ET7).
  • Checksums are file-type and size agnostic: SHA-256 treats every file as raw bytes regardless of extension. Text, binary, CSV, empty files — all produce valid, consistent checksums. The empty file always produces 47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU= (ET9).
  • Debugging path: AccessDenied → sts get-caller-identity then simulate-principal-policy. BadDigest → recalculate immediately before re-uploading. Missing ChecksumSHA256 → re-upload with --checksum-algorithm. CRLF mismatch → sed to normalize (ET8).
  • IAM is two-layer: Bucket actions need bucket ARN. Object actions need object ARN (bucket/*). ImplicitDeny = never granted. ExplicitDeny = overrides all allows. simulate-principal-policy tests both without making real API calls (ET10).
  • Multipart composite checksum: NOT the SHA-256 of the assembled file — it is SHA-256 of the concatenated part checksums. Only part-level validation gives you a checksum you can independently reproduce locally. A single failed part is rejected without restarting the upload (ET12, ET21).
  • HIPAA pattern — four layers: Pre-calculate SHA-256 at source → upload with precalculated value (BadDigest rejects corruption) → Object Lock WORM prevents deletion → independent audit log (QLDB) proves neither was tampered (ET11).
  • Interview simulation — narrate while typing: The strongest interview answers combine real CLI commands with clear narration — "I never guess at IAM errors, I always start with sts get-caller-identity." Practicing the live walkthrough format matters as much as knowing the answer (ET13).
  • Checksums survive all storage class transitions: head-object returns ChecksumSHA256 whether an object is in Standard, Standard-IA, Glacier, or Deep Archive — no restore needed for metadata access (ET16).
  • CloudTrail for audit compliance: Management events logged by default. Data Events (PutObject, GetObject) must be explicitly enabled. CloudTrail records which checksum algorithm was used in every upload (ET15).
  • Pre-signed URLs enforce checksums: Generate with ChecksumAlgorithm=SHA256 in presign params. Files go directly browser→S3 — your credentials never leave your backend. S3 rejects the upload if checksum header is missing or wrong (ET19).
  • Scale with Inventory + Athena: For millions of objects, S3 Inventory + Athena finds all objects missing checksums in seconds at pennies of cost vs $50+ with head-object per object (ET17).
  • Event-driven monitoring replaces batch: S3 Event Notifications → Lambda → headObject → DynamoDB → SNS. Failures detected within 60 seconds. DynamoDB provides a queryable audit trail (ET18).
  • Linux integrity toolkit: sha256sum --check validates a batch against a baseline. xargs -P 8 parallelises upload/validate across CPU cores. Process substitution (diff <(cmd1) <(cmd2)) compares without temp files. tar + .sha256 manifest is standard release packaging (ET14, ET22).
  • CI/CD and supply chain integrity: Record artifact checksum at build time, verify at deploy time. A mismatched checksum halts the deployment — this is the pattern that catches software supply chain attacks before they reach production (ET22).

🤔 Reflection Questions

1. What is the difference between S3 detecting a network error and a checksum mismatch? Why does one require checksums and the other does not?

💡 Hint

A network error means the TCP connection itself failed — reported automatically. A checksum mismatch means the connection succeeded but the bytes that arrived are different from the bytes that were sent. TCP does not detect silent byte corruption. Only a checksum catches this — which is why a successful HTTP 200 response does not prove the data arrived intact.

2. In Extended Task 8 you reproduced a CRLF mismatch. Why does it happen and what is the single-line fix?

💡 Hint

Windows uses CRLF (2 bytes per line: 0x0D 0x0A). Linux uses LF (1 byte: 0x0A). A file edited on Windows has different byte content than its Linux counterpart — SHA-256 sees the extra 0x0D and produces a completely different hash. Fix: sed -i s/\r// yourfile.txt before checksumming. Detect with file yourfile.txt — it reports "CRLF line terminators" when present.

3. In Extended Task 10, simulate-principal-policy returned implicitDeny. What does that mean and how is it different from explicitDeny?

💡 Hint

AWS defaults to deny everything. ImplicitDeny means no ALLOW statement exists — the action was never granted. ExplicitDeny means a DENY statement exists and overrides all ALLOW statements. The fix for implicitDeny is adding an ALLOW. The fix for explicitDeny is removing the DENY — adding an ALLOW alone is not enough because explicit denies always win.

4. You used Governance mode Object Lock in Extended Task 11. What is the difference between Governance and Compliance mode — and when would you use each?

💡 Hint

Governance mode: users with s3:BypassGovernanceRetention permission can delete objects before retention expires. Use for dev and testing — mistakes are recoverable. Compliance mode: nobody can delete the object until retention expires — not even the root account. Use for actual regulated records (HIPAA, SEC 17a-4, FINRA) where auditability requires deletion to be genuinely impossible.

5. In Extended Task 12, the composite checksum for your 50 MB multipart upload was NOT the SHA-256 of the assembled file. Why does this matter for validation scripts?

💡 Hint

The composite checksum is SHA-256 of the concatenated part checksums, base64-encoded — not the hash of the full assembled file. Running sha256sum large-file.bin locally produces a different value and your script would always report FAIL for multipart objects even when the data is perfectly intact. For multipart uploads, validate at the part level using --checksum-sha256 per part during upload-part.

6. The batch script in ET4 runs sequentially. If you needed to validate 50,000 files overnight, what is one Linux-native approach and one AWS-native approach?

💡 Hint

Linux-native: xargs -P 8 or GNU parallel — runs multiple upload/verify cycles simultaneously using all CPU cores. AWS-native: Lambda triggered by S3 Event Notifications validates each file the moment it uploads — no batch window, failures caught within seconds. For truly large datasets, AWS DataSync handles checksums, retries, and parallel transfers as a fully managed service.

7. From Extended Task 14 — what is the sha256sum --check baseline pattern and where does it appear in real security systems?

💡 Hint

Generate a baseline: sha256sum *.txt > checksums.sha256. Later verify: sha256sum --check checksums.sha256 — any file modified since baseline shows FAILED. Enterprise IDS tools like AIDE and Tripwire use exactly this pattern on system binaries and config files. This is also how CI/CD pipelines verify deployment artifacts have not been tampered with between build and deploy (Extended Task 22).

8. Across all three projects — what does each layer protect against that the others cannot?

💡 Hint

SHA-256 checksums detect silent data corruption — bit rot, network errors, disk failures. S3 Versioning protects against accidental overwrites and deletions — any previous version is restorable. S3 Object Lock (ET11) prevents deletion even by administrators — mandatory for compliance. Cross-Region Replication (Project 3) protects against an entire AWS region outage. Each layer defends a different threat. A production backup system needs all four working together.

9. In Extended Task 15, why does CloudTrail NOT capture S3 PutObject events by default, and what is the exact configuration change required?

💡 Hint

CloudTrail records management events (bucket creation, policy changes) by default because those are low-volume operations. Data events (PutObject, GetObject) can generate millions of log entries per day for a busy bucket — AWS makes you opt in to control costs and storage. The fix: aws cloudtrail put-event-selectors with DataResources type AWS::S3::Object. Without this, object-level API calls — including which checksum algorithm was used — are completely invisible to audit.

10. In Extended Task 17, why is S3 Inventory + Athena more efficient than calling head-object for every object in a 10-million-object bucket?

💡 Hint

10 million head-object API calls costs $50 (at $0.005 per 1,000 requests) and takes hours sequentially. S3 Inventory delivers a flat file with all 10 million objects and their metadata in one batch — costing $0.0025 per million objects listed. Athena queries the flat file in seconds — the SQL runs in parallel across all rows. Total cost: under $0.50. The pattern also works offline — Inventory is asynchronous, Athena runs when you choose.

11. In Extended Task 19, what is the key security advantage of the pre-signed URL pattern over having a backend proxy receive all uploads first?

💡 Hint

With a backend proxy, every byte of every uploaded file flows through your server — doubling bandwidth cost, adding latency, and making your backend a bottleneck. With pre-signed URLs, the file goes directly browser→S3. Your backend credentials are never exposed to the client. With ChecksumAlgorithm in the presign params, S3 enforces integrity without the file ever touching your infrastructure. This is both cheaper (no egress from your server) and more secure (reduced attack surface).

12. In Extended Task 22, what is a "software supply chain attack" and how does checksum verification at deploy time prevent it?

💡 Hint

A supply chain attack inserts malicious code into a software artifact after it leaves the build system — during storage, transfer, or at a dependency registry. In 2020, the SolarWinds attack modified a build artifact after the legitimate build step. If the deploy pipeline had compared the SHA-256 of the artifact at deploy time against a checksum recorded at build time, the modification would have been detected immediately. Checksum verification at deploy is the single most important defense against this class of attack.

13. In Extended Task 3, both shasum and openssl produce the same base64 SHA-256 output for the same file. Describe the internal pipeline each uses and explain why the intermediate steps differ even though the result is identical.

💡 Hint

shasum -a 256 outputs: hex-text + space + filename. You need cut to strip the filename, xxd -r -p to convert hex text to raw binary bytes, then base64 to encode — four pipeline stages. openssl dgst -sha256 -binary outputs raw binary bytes directly (the -binary flag skips hex text entirely), so only one pipe to base64 is needed. Both compute exactly the same SHA-256 digest — they differ only in the intermediate representation of that digest. The key insight is that -binary bypasses the hex encoding step, making the pipeline shorter and less error-prone.

14. Extended Task 6 proves "end-to-end" integrity by checking three values: local original, S3 stored, and downloaded copy. Which two of these three comparisons detect which specific failure types?

💡 Hint

Local vs S3 stored: detects transit corruption on upload — the bytes changed between your machine and S3's storage. S3 stored vs downloaded: detects corruption on retrieval — the bytes changed between S3's storage and your machine on download. If all three match, both directions of the transfer were clean. If local ≠ S3 stored, the upload was corrupted. If S3 stored ≠ downloaded, the download was corrupted. S3 stored is the trusted reference — it is what S3 actually has, proven by the checksum stored at upload time.

15. In Extended Task 7 (CLI Reference), you see that aws s3 ls and aws s3api list-objects-v2 both list bucket contents. When would you use s3api over s3 and what additional information does it expose?

💡 Hint

aws s3 ls is a convenience wrapper — human-readable, easy to scan, but returns only key, size, and modification date. aws s3api list-objects-v2 maps to the raw REST API — it returns JSON including ETag, StorageClass, Owner, and supports --query for JMESPath filtering, --output table for structured display, and pagination tokens for large buckets. The s3api version is necessary when you need to script against output (variable assignment, conditional logic) or when you need fields the s3 convenience command doesn't expose. Rule: for scripting and automation, always use s3api; for quick human inspection, s3 is fine.

16. Extended Task 9 shows that an empty file always produces the same SHA-256 checksum. Why does this matter for integrity monitoring systems, and what false-positive risk does it create?

💡 Hint

The SHA-256 of an empty file (zero bytes) is always 47DEQpj8HBSa+/TImW+5JCeuQeRkm5NMpJWZG3hSuFU= — universally known and deterministic. The risk: an integrity monitoring system comparing against a baseline would correctly report PASS for an empty file — which means a system that accidentally truncates a file to zero bytes would show as "intact" if the baseline checksum was also recorded against an empty file. In production, add a size check alongside the checksum: if ContentLength == 0 AND the expected size is > 0, flag it as suspicious even if the checksum matches.

Technical interviews assess both knowledge and communication. The practice of saying "First I always run sts get-caller-identity to confirm which profile is active — the wrong profile causes 80% of AccessDenied errors I've seen" while typing the command demonstrates both technical depth and the mental model behind the decision. Interviewers are evaluating whether they would trust you to debug a 3 AM production incident alone. Narrating while doing is the closest simulation of that scenario.
