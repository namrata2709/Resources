🏫 Why Do We Need Databases?

Before jumping into technical definitions, let's build intuition through a story that makes databases click permanently.

The College Story

Imagine a college — let's call it ABC College. When it first opens with 200 students, managing everything in Excel and paper registers works just fine. The admin can search manually, one person handles data at a time, and the files are small. Life is good.

But the college grows. Five years later — 8,000 students, 300 teachers, 15 departments, daily attendance records, fee payments, library transactions, exam marks. Now the same Excel approach that worked before starts exploding with problems.

Figure 2: Excel vs Database — what breaks at scale

❌ Problem 1: No Security

With Excel or paper registers, anyone who can open the file can change anything — marks, attendance, fee records. There's no concept of "only the accounts team can see fees" or "only teachers can update marks." Anyone can delete data, modify records, or corrupt the entire file — and you'd never know who did it.

A DBMS provides user accounts, role-based access control, audit logs (who changed what and when), and encryption — none of which Excel can offer.

❌ Problem 2: No Multi-User Access

In Excel, if two people open the same file and edit it at the same time, one person's changes overwrite the other's. Versions mismatch. Files get locked. The accounts team can't update fees while the academic team is updating marks.

A DBMS supports concurrency control — hundreds of users can read and write simultaneously without corrupting data. The DBMS manages conflicts automatically behind the scenes.

❌ Problem 3: Searching Is Slow

Finding one student's record in a 10,000-row Excel sheet means scrolling, using Ctrl+F, and hoping the filters don't break. As the file grows heavier, searches take longer, formulas fail, and the file itself starts freezing.

With SQL: SELECT * FROM students WHERE roll_no = 2023; — result in 0.01 seconds, regardless of how many millions of records exist.

❌ Problem 4: No Relationships Between Data

A college has multiple data areas: students, courses, attendance, marks, fees, library. In Excel, these are separate files with no connection. A student might appear in the attendance sheet under a slightly different name spelling than in the marks sheet. Inconsistency creeps in everywhere.

A database creates relationships — a single student_id links the student to their attendance, marks, fees, and library records, ensuring data consistency across all areas.

❌ Problem 5: No Automation

Excel cannot automatically calculate if a student has fallen below the attendance threshold, trigger a fee reminder, prevent duplicate roll numbers from being entered, or auto-update related records when a student changes department. Every such task is manual and error-prone.

With DBMS, you can create stored procedures, triggers, and views — for example: if a student pays fees, their attendance portal gets activated automatically.

❌ Problem 6: Excel Breaks With Big Data

A college with 10,000 students generates roughly 30,000 attendance rows daily, 50,000 library transactions per semester, and millions of exam result records over the years. Excel will freeze, crash, and eventually lose data. It simply wasn't built for this volume.

Databases handle millions of records efficiently through indexing and query optimization — performance stays fast regardless of data volume.

❌ Problem 7: No Backup and Recovery

If your Excel file is accidentally deleted, your laptop crashes, or the hard drive fails — the data is gone forever. Paper registers can be lost in a fire or flood. There is no undo for these disasters.

A DBMS supports automatic daily backups, point-in-time recovery (restore to any specific minute), and replication across multiple servers. AWS RDS even replicates across Multiple Availability Zones — so even if an entire data center fails, your data survives.

❌ Problem 8: Reporting Is a Nightmare

Generating a merit list, identifying fee defaulters, or producing a monthly academic report from Excel takes hours of manual work — pulling data from multiple sheets, sorting, filtering, and cross-referencing. One mistake and the report is wrong.

With SQL, one query produces any report instantly — sorted, filtered, and accurate.

✅ The Conclusion: Registers and Excel work fine for small, simple, single-user data. But a real organization needs security, consistency, speed, automation, scalability, and multi-user access. Only a database + DBMS combination can provide all of this.

📦 Three Families of Data

Before choosing a database, you need to know what kind of data you're storing. All data in the world falls into one of three families, and understanding this determines which database technology you pick.

Figure 3: The three families of data and where each is stored

1. Structured Data

Structured data is organized in a fixed, predefined format — rows and columns in a table. Every record follows the exact same structure. If a student table has 4 columns (id, name, age, department), every single student record must fill all 4 columns in that exact order.

Structured data is stored in Relational Databases (RDBMS) like MySQL, PostgreSQL, Oracle, and SQL Server. It is queried using SQL.

Real examples: Student records, bank transactions, employee payroll, product inventory, e-commerce orders.

2. Semi-Structured Data

Semi-structured data does not use a fixed table format, but it still has internal structure using tags or key-value pairs — like JSON or XML.

Think of it as data that carries its own labels. A JSON object {"name": "Amit", "age": 20, "hobbies": ["cricket", "coding"]} is not a fixed table row — different records can have different fields. But it's not fully unstructured either — the key-value pairs give it meaning.

Semi-structured data is stored in NoSQL document databases (MongoDB, DynamoDB) or managed using AWS services. It's the format most APIs and modern web applications use.

3. Unstructured Data

Unstructured data has no predefined format — it cannot fit neatly into rows and columns.

Examples: images, videos, audio recordings, raw log files, PDF documents, social media posts. You can store them, but you can't easily query their content with SQL. Unstructured data is stored in object storage (Amazon S3, Azure Blob) or processed with specialized tools (Elasticsearch for log search).

💡 Why this matters: The type of data determines your database choice. Before building any system, ask: "Is my data structured, semi-structured, or unstructured?" The answer drives your architecture decision.

SQL Data Types

Inside a relational database, each column has a specific data type that defines what kind of value it holds:

  • INT / INTEGER — Whole numbers (age, count, quantity). Example: age INT
  • VARCHAR(n) — Variable-length text up to n characters. Example: name VARCHAR(50) — most commonly used string type
  • CHAR(n) — Fixed-length text. Always stores exactly n characters regardless of actual length
  • TEXT / LONGTEXT — Large text content (descriptions, content). No length limit specified
  • BOOLEAN — True or False values only. Example: is_active BOOLEAN
  • DATE / DATETIME / TIMESTAMP — Date and time values
  • DECIMAL / FLOAT — Numbers with decimal points (salary, price)
⚡ VARCHAR is the most commonly used string data type — it stores variable-length text efficiently and is the standard choice for names, emails, and other text fields.

🗄️ Database vs DBMS — Understanding the Difference

This is one of the most common interview questions and one of the most commonly confused concepts. Let's nail it with an analogy first.

Figure 4: Library analogy — the library is the database, the management system is the DBMS

Think of a physical library. The library building with all its books is the database — it's the place where everything is stored. The system the librarian uses to manage who can borrow books, track returns, search the catalog, enforce rules, and run reports — that is the DBMS.

A database is the digital storage system where data is kept. A DBMS is the software that creates, manages, secures, and optimizes that database.

Types of Databases

Databases come in several flavors, each optimized for a specific type of data:

  • Relational Databases (RDBMS) — Structured data in tables with relationships. Examples: MySQL, PostgreSQL, Oracle, SQL Server, MariaDB, SQLite
  • NoSQL Databases — Four subtypes for flexible data: Document (MongoDB, DynamoDB), Key-Value (Redis), Column (Cassandra), Graph (Neo4j)
  • In-Memory Databases — Data stored in RAM for ultra-fast access. Examples: Redis, Memcached. Used for caching and session management
  • Time-Series Databases — Optimized for time-stamped data. Examples: InfluxDB, Amazon Timestream. Used for IoT data, metrics, monitoring
  • Object Storage — Stores large files (images, videos, backups). Examples: Amazon S3, Azure Blob Storage

Types of DBMS Software

  • RDBMS — Manages relational databases using SQL: MySQL, PostgreSQL, Oracle, SQL Server, MariaDB
  • NoSQL DBMS — Manages NoSQL databases: MongoDB server, DynamoDB, Redis, Cassandra
  • NewSQL — Combines relational structure with NoSQL horizontal scalability: CockroachDB, Google Spanner
  • Cloud-Native DBMS — Fully managed database services where the cloud handles everything: AWS RDS, AWS DynamoDB, Azure CosmosDB, Google Firestore

💡 Cloud-Native DBMS: With services like AWS RDS, you don't install or manage MySQL yourself — Amazon handles installation, patching, automatic backups, scaling, and Multi-AZ failover. You just use it. This is the real-world production approach.

📚 Source: AWS RDS Documentation

AWS Database Services Overview

  • AWS Aurora — Cloud-native RDBMS with MySQL and PostgreSQL compatibility. 5x faster than standard MySQL
  • AWS RDS — Managed relational database service supporting MySQL, PostgreSQL, Oracle, SQL Server, MariaDB
  • AWS DynamoDB — Fully managed NoSQL key-value and document database
  • AWS Redshift — Data warehouse service that collects and analyzes data from multiple sources for analytics at scale
  • AWS ElastiCache — Managed in-memory caching using Redis or Memcached

📝 SQL Fundamentals

SQL (Structured Query Language) is the universal language for talking to relational databases. Whether you use MySQL, PostgreSQL, Oracle, or SQL Server — you use SQL to communicate with all of them. Learning SQL once means you can work with any RDBMS.

Figure 5: The four SQL command categories and their commands

The Four SQL Command Categories

SQL commands are divided into four categories: DDL (Data Definition Language), DML (Data Manipulation Language), DQL (Data Query Language), and DCL/TCL (Data Control / Transaction Control Language).

DDL — Data Definition Language

Used to define or modify the structure of tables and databases. DDL commands don't touch the data itself — they define the containers.

  • CREATE — Create a new database or table
  • ALTER — Modify an existing table structure (add/remove/rename columns)
  • DROP — Permanently delete a table or database (including all data)
  • TRUNCATE — Remove all rows from a table instantly (structure remains)

DML — Data Manipulation Language

Used to add, modify, or delete the actual data inside tables.

  • INSERT — Add new rows/records to a table
  • UPDATE — Modify existing data in a table
  • DELETE — Remove specific rows from a table

DQL — Data Query Language

Used to retrieve or fetch data from tables. This is the most frequently used category in day-to-day work.

  • SELECT — The only DQL command. Retrieves data based on specified conditions

DCL & TCL — Control Languages

DCL (Data Control Language) manages permissions. TCL (Transaction Control Language) manages safe, multi-step operations.

  • GRANT — Give a user specific permissions on a database or table
  • REVOKE — Remove permissions from a user
  • COMMIT — Permanently save all changes made in the current transaction
  • ROLLBACK — Undo all changes made since the last commit
  • SAVEPOINT — Create a named checkpoint within a transaction

💡 The Statement Terminator: Every SQL query must end with a semicolon (;) — it is the statement terminator that tells the SQL engine the command is complete and should be executed. Without it in CLI, the engine waits thinking you're still typing.

🔧 SQL End-to-End: From Database to Query

Theory is good. But seeing SQL work end-to-end — creating a database, a table, inserting data, then reading and filtering it — is what makes it stick. Let's walk through the complete workflow using a college students example.

Figure 6: The complete SQL workflow from database creation to advanced queries

Step 1: Create a Database

The very first thing is creating a database — a named container where all your tables will live.

CREATE DATABASE college;

Step 2: Select (Use) the Database

Before writing any table queries, you must tell MySQL which database to work in.

USE college;

Step 3: Create a Table

Now we define the structure — what columns exist and what type of data each holds.

CREATE TABLE students (
  id          INT PRIMARY KEY,
  name        VARCHAR(50),
  age         INT,
  department  VARCHAR(50)
);

The PRIMARY KEY constraint on the id column ensures every student has a unique identifier that can never be NULL.

Step 4: Insert Data

Adding a single record:

INSERT INTO students (id, name, age, department)
VALUES (1, 'Amit', 20, 'CSE');

Adding multiple records at once (more efficient):

INSERT INTO students VALUES
  (2, 'Priya', 21, 'ECE'),
  (3, 'Rahul', 22, 'ME'),
  (4, 'John',  20, 'CSE'),
  (5, 'Neha',  19, 'CIVIL');

Step 5: Read Data with SELECT

Retrieve all columns and all rows:

SELECT * FROM students;

Retrieve only specific columns:

SELECT name, department FROM students;

Step 6: Filter with WHERE

WHERE narrows down which rows are returned.

-- Students older than 20
SELECT * FROM students WHERE age > 20;

-- Students in CSE department
SELECT name FROM students WHERE department = 'CSE';

-- Names starting with 'A'
SELECT * FROM students WHERE name LIKE 'A%';

-- Age between 18 and 22
SELECT * FROM students WHERE age BETWEEN 18 AND 22;

-- Department is CSE or ECE
SELECT * FROM students WHERE department IN ('CSE', 'ECE');

Step 7: Sort with ORDER BY

-- Youngest to oldest
SELECT * FROM students ORDER BY age ASC;

-- Oldest to youngest
SELECT * FROM students ORDER BY age DESC;

Step 8: Update Existing Data

UPDATE students
SET age = 23
WHERE id = 2;
❌ Never run UPDATE without a WHERE clause. Without WHERE, every single row in the table gets updated to the new value.

Step 9: Delete Rows

DELETE FROM students WHERE id = 3;
❌ Never run DELETE without a WHERE clause. DELETE FROM students; without WHERE wipes every row in the table — the table structure stays, but all data is gone.

Step 10: Advanced Features

DISTINCT — Remove Duplicates

When a column has repeating values and you only want unique entries:

SELECT DISTINCT department FROM students;

SQL scans the department column, removes all duplicates, and returns only unique department names (CSE, ECE, ME, CIVIL).

LIMIT — Restrict Rows

Useful for pagination, testing, and avoiding loading thousands of records:

SELECT * FROM students LIMIT 5;

Aggregate Functions

Functions that perform calculations across multiple rows and return a single summary value:

SELECT COUNT(*) FROM students;     -- Total number of students
SELECT AVG(age)  FROM students;     -- Average age
SELECT MAX(age)  FROM students;     -- Oldest student
SELECT MIN(age)  FROM students;     -- Youngest student

GROUP BY — Group and Aggregate

GROUP BY groups rows that share the same value in a specified column, allowing aggregate functions to be applied per group.

SELECT department, COUNT(*)
FROM students
GROUP BY department;

This gives one row per department showing how many students are in each.

HAVING — Filter After Grouping

⚡ Use WHERE to filter rows before grouping. Use HAVING to filter groups after GROUP BY. HAVING can use aggregate functions; WHERE cannot.
-- Only departments with more than 10 students
SELECT department, COUNT(*)
FROM students
GROUP BY department
HAVING COUNT(*) > 10;

Figure 7: WHERE vs HAVING — when each filter is applied in the execution order

🔗 SQL JOINs — Combining Data from Multiple Tables

In the real world, data doesn't live in a single table. A college database has separate tables for students, departments, courses, fees, and marks. JOINs are the SQL mechanism that connects related tables and retrieves combined data.

Understanding Our Base Tables

To understand JOINs visually, we use two tables:

students table:

id | name  | department
 1 | Amit  | CSE
 2 | Priya | ECE
 3 | Rahul | ME
 4 | John  | CSE
 5 | Neha  | CIVIL      ← CIVIL has NO entry in departments table

departments table:

dept_name | hod_name
CSE       | Dr. Sharma
ECE       | Dr. Raghavan
ME        | Dr. Sundar
IT        | Dr. Kiran    ← IT has NO students

💡 Notice: Neha (CIVIL student) has no match in departments. IT department has no students. These two mismatches are what make each JOIN type behave differently.

Figure 8: All six SQL JOIN types visualized with Venn diagrams

1. INNER JOIN — Only Matching Rows

INNER JOIN returns only rows where both tables have a matching value on the JOIN condition. Rows with no match on either side are excluded.

SELECT s.name, s.department, d.hod_name
FROM students s
INNER JOIN departments d
ON s.department = d.dept_name;

Result: Amit, Priya, Rahul, John — all with their HOD names. Neha (CIVIL, no match) is excluded. IT department (no students) is excluded.

2. LEFT JOIN — All Left Table Rows

LEFT JOIN returns all rows from the left table and matching rows from the right table. If no match exists, right-table columns show NULL.

SELECT s.name, s.department, d.hod_name
FROM students s
LEFT JOIN departments d
ON s.department = d.dept_name;

Result: All 5 students appear. Neha's row shows NULL for hod_name (CIVIL not in departments).

3. RIGHT JOIN — All Right Table Rows

RIGHT JOIN returns all rows from the right table and matching rows from the left table. If no match exists, left-table columns show NULL.

SELECT s.name, s.department, d.hod_name
FROM students s
RIGHT JOIN departments d
ON s.department = d.dept_name;

Result: All 4 departments appear. IT department row shows NULL for name and department (no IT students).

4. FULL OUTER JOIN — Everything from Both Tables

FULL OUTER JOIN returns all rows from both tables. Unmatched rows on either side show NULL for the missing columns.

MySQL does not natively support FULL JOIN — simulate using UNION:

SELECT s.name, s.department, d.hod_name
FROM students s
LEFT JOIN departments d ON s.department = d.dept_name
UNION
SELECT s.name, s.department, d.hod_name
FROM students s
RIGHT JOIN departments d ON s.department = d.dept_name;

Result: All 5 students + all 4 departments. Neha shows NULL HOD. IT shows NULL student.

5. CROSS JOIN — Every Combination

CROSS JOIN produces a Cartesian product — every row from the left table paired with every row from the right table. No matching condition required.

SELECT s.name, d.hod_name
FROM students s
CROSS JOIN departments d;

Result: 5 students × 4 departments = 20 rows. Every student is paired with every department. Use with caution — can produce enormous result sets.

6. SELF JOIN — Join a Table With Itself

A SELF JOIN joins a table with itself using two different aliases to compare rows within the same dataset.

SELECT a.name AS student1, b.name AS student2, a.department
FROM students a
JOIN students b
ON a.department = b.department
AND a.id <> b.id;

Result: Finds all pairs of students in the same department — Amit & John are both in CSE.

Figure 9: JOIN type comparison summary using the students/departments example

⚡ Quick Memory Rule: INNER = intersection only | LEFT = keep all left | RIGHT = keep all right | FULL = keep everything | CROSS = every × every | SELF = table meets itself

⚙️ MySQL Setup on Ubuntu EC2

Knowing SQL theory is one thing. Setting up a real MySQL database server on AWS EC2 is where the knowledge becomes a practical skill. This section walks through the complete setup — installation, security hardening, remote access configuration, and user management.

Figure 10: Complete MySQL setup flow on Ubuntu EC2

Step 1: Install MySQL Server

sudo apt update
sudo apt install mysql-server -y

This installs the MySQL server and client on your EC2 Ubuntu machine, starts the MySQL service, and creates an initial root user (root@localhost).

Step 2: Secure MySQL (Critical)

sudo mysql_secure_installation

mysql_secure_installation is a post-install security script that sets the root password, removes anonymous accounts, disables remote root login, and deletes the test database. Never skip this on a production server.

Step 3: Fix the Ubuntu Auth Socket Issue

Ubuntu installs MySQL with a plugin called auth_socket by default. This means you can only log in as root using sudo mysql — you cannot use a password. This breaks tools like MySQL Workbench, Node.js MySQL clients, and phpMyAdmin.

-- Login first using auth_socket
sudo mysql

-- Then switch to password-based authentication
ALTER USER 'root'@'localhost'
IDENTIFIED WITH mysql_native_password
BY 'RootPass123!';

FLUSH PRIVILEGES;

Now you can log in normally with mysql -u root -p.

Step 4: Create a Database

mysql -u root -p

CREATE DATABASE myapp;

Always create a dedicated database for each application — never use the system databases.

Step 5: Create a Dedicated App User

❌ Never use the root user for application database connections. Root has full system access — if the application is ever compromised, an attacker gains full control of every database on the server.
-- Create user accessible from any IP (use specific IP in production)
CREATE USER 'appuser'@'%' IDENTIFIED BY 'AppPass123!';

-- Grant access only to the specific app database
GRANT ALL PRIVILEGES ON myapp.* TO 'appuser'@'%';

FLUSH PRIVILEGES;

The % wildcard in MySQL means the user can connect from any IP address. For production, replace % with the specific private IP of your application server for tighter security.

Step 6: Enable Remote Connections

By default, MySQL's bind-address is set to 127.0.0.1 — it only accepts connections from the local machine itself. To allow external tools (Workbench, app servers) to connect, change this.

sudo nano /etc/mysql/mysql.conf.d/mysqld.cnf

Find the line:

bind-address = 127.0.0.1

Change to:

bind-address = 0.0.0.0
sudo systemctl restart mysql

Figure 11: bind-address 127.0.0.1 vs 0.0.0.0 — what each setting allows

Step 7: Open Port 3306 in Security Group

Even if MySQL is configured to accept remote connections, AWS Security Groups act as a firewall and will block all traffic on port 3306 unless an explicit inbound rule allows it.

In the AWS Console: EC2 → Security Groups → Select your instance's security group → Edit Inbound Rules → Add Rule: Type: MySQL/Aurora | Port: 3306 | Source: your laptop IP or app server IP

❌ Never set Source to 0.0.0.0/0 (Anywhere) for port 3306 in production. This exposes your database to the entire internet. Always restrict to specific IPs.

Step 8: Test the Connection

From the EC2 server itself (local test):

mysql -u appuser -p

From a remote machine or another EC2 instance:

mysql -h <EC2-private-IP> -u appuser -p

From MySQL Workbench on your laptop: Host = EC2 Public IP | Port = 3306 | Username = appuser | Password = AppPass123!

Useful ALTER USER Commands

-- Change a user's password
ALTER USER 'appuser'@'%' IDENTIFIED BY 'NewSecurePass!';

-- Force password change on next login
ALTER USER 'appuser'@'%' PASSWORD EXPIRE;

-- Lock an account (temporarily disable access)
ALTER USER 'appuser'@'%' ACCOUNT LOCK;

-- Unlock an account
ALTER USER 'appuser'@'%' ACCOUNT UNLOCK;

Common Error: Host Not Allowed

Host 'X.X.X.X' is not allowed to connect to this MySQL server

This means the MySQL user was not created with that host allowed. Fix by creating the user with the correct host:

CREATE USER 'appuser'@'X.X.X.X' IDENTIFIED BY 'pass';
-- OR use % to allow any IP:
CREATE USER 'appuser'@'%' IDENTIFIED BY 'pass';

📝 Overall Summary

  • Why Databases: Excel and registers fail at scale — they lack security, multi-user access, fast search, data relationships, automation, scalability, backup, and reporting. Databases + DBMS solve all 8 problems.
  • Three Data Families: Structured (tables/RDBMS), Semi-Structured (JSON/XML/NoSQL), Unstructured (images/videos/Object Storage). The data type determines the database technology.
  • Database vs DBMS: A database is where data is stored. DBMS (like MySQL) is the software that creates, manages, secures, and optimizes that storage. They are different things that work together.
  • SQL Categories: DDL (CREATE/ALTER/DROP/TRUNCATE — structure), DML (INSERT/UPDATE/DELETE — data), DQL (SELECT — retrieval), DCL (GRANT/REVOKE — permissions), TCL (COMMIT/ROLLBACK — transactions).
  • Statement Terminator: Every SQL query in CLI must end with a semicolon (;) — it signals execution.
  • WHERE vs HAVING: WHERE filters individual rows before GROUP BY. HAVING filters group results after GROUP BY. HAVING can use aggregate functions; WHERE cannot.
  • JOINs: INNER = matching rows only | LEFT = all left + matching right (NULLs for unmatched) | RIGHT = all right + matching left | FULL = everything | CROSS = Cartesian product | SELF = table joins itself.
  • MySQL on EC2: Install → secure with mysql_secure_installation → fix auth_socket → create DB → create dedicated app user → configure bind-address → open port 3306 in Security Group → test.
  • Security Rule: Never use root for application connections. Always create a dedicated user with privileges restricted to only the application's database.
  • DELETE/UPDATE Warning: Always use WHERE with DELETE and UPDATE. Without WHERE, the entire table's data is affected.

SELECT s.name, s.department, d.hod_name
FROM students s
LEFT JOIN departments d ON s.department = d.dept_name;

    📸 Screenshot: Neha's row showing NULL for hod_name is the key result — LEFT JOIN kept her even though CIVIL has no matching department record

  8. Update and delete safely using WHERE:

    UPDATE students SET age = 23 WHERE id = 2;
DELETE FROM students WHERE id = 5;
SELECT * FROM students;

Project 2: Configure MySQL for Remote Access on EC2

🎯 Objective: Set up MySQL on EC2 to accept remote connections from MySQL Workbench on your laptop — the real-world setup used by every development team.

⏱️ Time: 30–45 min

💰 Cost: Free tier

📚 Skills: MySQL user management, bind-address configuration, EC2 Security Groups, remote connection

  1. Install MySQL and run the security hardening script:

    sudo apt update && sudo apt install mysql-server -y
sudo mysql_secure_installation

    📸 Screenshot: Successful installation ends with 'Setting up mysql-server' — no errors in red

  2. Fix Ubuntu's auth_socket issue so password login works:

    sudo mysql
ALTER USER 'root'@'localhost' IDENTIFIED WITH mysql_native_password BY 'RootPass123!';
FLUSH PRIVILEGES;
EXIT;

  3. Create an application database and a dedicated app user (never use root for apps):

    mysql -u root -p
CREATE DATABASE myapp;
CREATE USER 'appuser'@'%' IDENTIFIED BY 'AppPass123!';
GRANT ALL PRIVILEGES ON myapp.* TO 'appuser'@'%';
FLUSH PRIVILEGES;
EXIT;

    📸 Screenshot: Query OK after both CREATE USER and GRANT confirms the app user is ready — this is the correct pattern for every production setup

  4. Edit MySQL configuration to allow remote connections:

    sudo nano /etc/mysql/mysql.conf.d/mysqld.cnf

    Find bind-address = 127.0.0.1 and change to bind-address = 0.0.0.0, then save (Ctrl+O, Enter, Ctrl+X).

    📸 Screenshot: The bind-address line changed to 0.0.0.0 — this single change allows MySQL to accept connections from any network interface

  5. Restart MySQL and confirm it is running:

    sudo systemctl restart mysql
sudo systemctl status mysql

    📸 Screenshot: 'active (running)' in green confirms the restart succeeded with the new config — if you see 'failed', check the config file for typos

  6. Open port 3306 in the EC2 Security Group: AWS Console → EC2 → Security Groups → Edit Inbound Rules → Add Rule: Type: MySQL/Aurora | Port: 3306 | Source: Your laptop's IP address (not 0.0.0.0/0).

    📸 Screenshot: Port 3306 rule with a specific source IP — never use 0.0.0.0/0 (Anywhere) for database ports in production

  7. Test the remote connection:

    mysql -h <EC2-public-IP> -u appuser -p

    Run SHOW DATABASES; — you should see myapp in the list.

Verification

A successful connection shows the mysql> prompt from your remote machine.

Cleanup (if testing only)

DROP USER 'appuser'@'%';
DROP DATABASE myapp;

Also remove the port 3306 inbound rule from the Security Group.

Project 3: Build a Relational Schema — Students, Courses & Enrollments

🎯 Objective: Extend the college database with a many-to-many relationship between students and courses. Write multi-table JOIN queries that reflect real application data models.

⏱️ Time: 45–60 min

💰 Cost: Free tier

📚 Skills: Schema design, composite primary keys, many-to-many relationships, 3-table JOINs

⚡ Why this matters: Real applications never have just one table. An e-commerce site has orders, products, and users — all linked. A hospital has patients, doctors, and appointments. This project teaches you how those links work.

  1. Start fresh with the college database from Project 1 (or recreate it):

    CREATE DATABASE college;
USE college;

CREATE TABLE students (
  id         INT PRIMARY KEY,
  name       VARCHAR(50),
  age        INT,
  department VARCHAR(50)
);

INSERT INTO students VALUES
  (1, 'Amit',  20, 'CSE'),
  (2, 'Priya', 21, 'ECE'),
  (3, 'Rahul', 22, 'ME'),
  (4, 'John',  20, 'CSE'),
  (5, 'Neha',  19, 'ECE');

  2. Add the courses table:

    CREATE TABLE courses (
  course_id   INT PRIMARY KEY,
  course_name VARCHAR(100),
  credits     INT
);

INSERT INTO courses VALUES
  (101, 'Database Systems',    3),
  (102, 'Cloud Computing',     3),
  (103, 'Python Programming',  2),
  (104, 'Linux Administration',2);

  3. Add the enrollments table — this is the many-to-many bridge. One student can take many courses; one course can have many students.

    CREATE TABLE enrollments (
  student_id INT,
  course_id  INT,
  PRIMARY KEY (student_id, course_id)
);

INSERT INTO enrollments VALUES
  (1, 101), (1, 102), (1, 103),
  (2, 101), (2, 104),
  (3, 102),
  (4, 101), (4, 103),
  (5, 102), (5, 103), (5, 104);

    📸 Screenshot: The enrollments table with a composite PRIMARY KEY — notice two columns together form the key, preventing any student from enrolling in the same course twice

  4. Query: Show each student's name alongside the courses they are enrolled in (3-table JOIN):

    SELECT s.name, c.course_name
FROM students s
JOIN enrollments e ON s.id = e.student_id
JOIN courses c    ON e.course_id = c.course_id
ORDER BY s.name, c.course_name;

    📸 Screenshot: Each student appears once per enrolled course — this is the power of JOINs across a many-to-many relationship

  5. Query: How many courses is each student taking? Sort by most courses first:

    SELECT s.name, COUNT(e.course_id) AS courses_enrolled
FROM students s
JOIN enrollments e ON s.id = e.student_id
GROUP BY s.name
ORDER BY courses_enrolled DESC;

  6. Query: Students taking more than 2 courses (HAVING with multi-table JOIN):

    SELECT s.name, COUNT(e.course_id) AS total_courses
FROM students s
JOIN enrollments e ON s.id = e.student_id
GROUP BY s.name
HAVING COUNT(e.course_id) > 2;

    📸 Screenshot: HAVING filters after grouping — only students with more than 2 courses appear. This is a real report a college admin would run.

  7. Query: Which courses have no enrolled students? (LEFT JOIN to find missing relationships):

    SELECT c.course_name
FROM courses c
LEFT JOIN enrollments e ON c.course_id = e.course_id
WHERE e.student_id IS NULL;

Verification

The 3-table JOIN should return multiple rows per student (one per enrolled course). The HAVING query should show only Amit (3 courses) and Neha (3 courses).

Cleanup

DROP DATABASE college;

Project 4: Debug & Fix a Broken Database

🎯 Objective: Intentionally break a database, read the error messages, understand what went wrong, and fix it using constraints. This is exactly what happens in real companies every day.

⏱️ Time: 30–40 min

💰 Cost: Free tier

📚 Skills: Reading SQL errors, PRIMARY KEY constraints, UNIQUE constraints, ALTER TABLE

⚡ Why this matters: Debugging broken SQL is an interview favourite — "Tell me about a time you fixed a database issue." After this project, you'll have a real answer.

  1. Set up a fresh students table:

    CREATE DATABASE debugtest;
USE debugtest;

CREATE TABLE students (
  id         INT PRIMARY KEY,
  name       VARCHAR(50),
  age        INT,
  department VARCHAR(50)
);

INSERT INTO students VALUES (1, 'Amit', 20, 'CSE');

  2. Trigger Error 1 — duplicate PRIMARY KEY. Try inserting a student with id=1 again:

    INSERT INTO students VALUES (1, 'Duplicate', 22, 'ECE');

    📸 Screenshot: ERROR 1062 — Duplicate entry. The PRIMARY KEY constraint is working exactly as designed — it rejected the duplicate and protected data integrity.

    This error means: the PRIMARY KEY constraint rejected the duplicate. This is the constraint doing its job. Fix by using a unique id:

    INSERT INTO students VALUES (2, 'Duplicate', 22, 'ECE');

  3. Trigger Error 2 — NULL in a NOT NULL column. Add a NOT NULL constraint and test it:

    ALTER TABLE students MODIFY name VARCHAR(50) NOT NULL;

-- Now try inserting a student with no name:
INSERT INTO students (id, age, department) VALUES (3, 21, 'ME');

    📸 Screenshot: ERROR 1364 — Field 'name' doesn't have a default value. The NOT NULL constraint prevents incomplete records from entering the database.

    Fix by providing the required name field:

    INSERT INTO students VALUES (3, 'Rahul', 21, 'ME');

  4. Add a UNIQUE constraint to prevent duplicate names:

    ALTER TABLE students ADD UNIQUE(name);

    Test the constraint:

    INSERT INTO students VALUES (4, 'Amit', 25, 'IT');

    📸 Screenshot: ERROR 1062 again — but this time for the UNIQUE constraint on name. Now both id AND name are protected from duplicates.

    Fix by using a different name:

    INSERT INTO students VALUES (4, 'Sunita', 25, 'IT');

  5. Verify that all constraints are in place and check your final table:

    DESCRIBE students;
SELECT * FROM students;

    📸 Screenshot: DESCRIBE shows the full constraint profile — PRI for primary key, UNI for unique, NO in the Null column for NOT NULL. This is how you verify your table structure at any time.

Verification

The DESCRIBE output should show: id as PRI key, name as NOT NULL and UNI, and 4 clean rows in the SELECT result.

Cleanup

DROP DATABASE debugtest;

Project 5: Backup, Recovery & Query Performance

🎯 Objective: Simulate a real production incident — accidental data loss — then recover from backup. Then use EXPLAIN and indexing to make a slow query fast.

⏱️ Time: 40–50 min

💰 Cost: Free tier

📚 Skills: mysqldump, database restore, EXPLAIN, CREATE INDEX, query optimization

⚡ Why this matters: Every production DBA and backend developer needs to know backup/restore and basic query optimization. These are senior-level skills that set you apart.

Part A — Backup & Recovery

  1. Build a sample database to protect:

    CREATE DATABASE production_sim;
USE production_sim;

CREATE TABLE orders (
  order_id   INT PRIMARY KEY,
  customer   VARCHAR(100),
  product    VARCHAR(100),
  amount     DECIMAL(10,2),
  order_date DATE
);

INSERT INTO orders VALUES
  (1, 'Alice',   'Laptop',   75000.00, '2024-01-15'),
  (2, 'Bob',     'Phone',    25000.00, '2024-01-18'),
  (3, 'Priya',   'Tablet',   35000.00, '2024-02-01'),
  (4, 'Rahul',   'Monitor',  15000.00, '2024-02-10'),
  (5, 'Sunita',  'Keyboard',  3000.00, '2024-02-14');

  2. Create a backup using mysqldump (run this in the Ubuntu terminal, not inside MySQL):

    exit   -- exit MySQL first if you are inside it
mysqldump -u root -p production_sim > ~/production_sim_backup.sql

    📸 Screenshot: The backup file created — run ls -lh ~/production_sim_backup.sql immediately after to confirm the file exists and is not empty (size should be a few KB)

    Verify the backup file was created:

    ls -lh ~/production_sim_backup.sql

  3. Simulate a disaster — drop the entire database:

    mysql -u root -p -e "DROP DATABASE production_sim;"

    Verify it is gone:

    mysql -u root -p -e "SHOW DATABASES;"

  4. Restore from backup — recreate the database and import the dump:

    mysql -u root -p -e "CREATE DATABASE production_sim;"
mysql -u root -p production_sim < ~/production_sim_backup.sql

    📸 Screenshot: Run SELECT COUNT(*) FROM orders after restore — seeing 5 rows confirms 100% data recovery. No error messages means the restore was clean.

    Verify all data is back:

    mysql -u root -p production_sim -e "SELECT * FROM orders;"

Part B — Query Performance with EXPLAIN and Indexing

  1. Run a search query and check how MySQL executes it:

    mysql -u root -p production_sim

EXPLAIN SELECT * FROM orders WHERE customer = 'Priya';

    📸 Screenshot: EXPLAIN output showing type=ALL and key=NULL — MySQL scanned every row to find Priya. This is a full table scan. On millions of rows, this is dangerously slow.

    The key things to read in EXPLAIN output:

    • type: ALL → full table scan (bad for large tables)
    • key: NULL → no index used
    • rows → how many rows MySQL examined

  2. Add an index on the customer column to speed up searches by customer name:

    CREATE INDEX idx_customer ON orders(customer);

  3. Run EXPLAIN again on the same query and compare:

    EXPLAIN SELECT * FROM orders WHERE customer = 'Priya';

    📸 Screenshot: After adding the index — type changes from ALL to ref, and key shows idx_customer. MySQL now jumps directly to Priya's row instead of scanning everything. This is the difference between a fast and a slow application.

    With the index: type: ref, key: idx_customer — MySQL uses the index to find rows instantly instead of scanning the whole table.

  4. Check all indexes on the table:

    SHOW INDEXES FROM orders;
✅ What you just proved: Adding an index on a searched column changes query execution from a full table scan (slow) to a direct index lookup (fast). On a table with millions of rows, this difference is the gap between a 30-second query and a 0.001-second query.

Verification

EXPLAIN before index: type=ALL, key=NULL. EXPLAIN after index: type=ref, key=idx_customer. Backup/restore: 5 rows returned after recovery.

Cleanup

DROP DATABASE production_sim;
rm ~/production_sim_backup.sql

💡 Hint

You need to COUNT orders per customer. Think about when WHERE runs (before grouping) vs when HAVING runs (after grouping). The count doesn't exist before grouping.

💡 Hint

Think of two independent barriers: the MySQL application layer (bind-address controls which interface it listens on) and the AWS network layer (Security Group controls what traffic reaches the EC2 instance at all).
