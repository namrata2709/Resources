🔒 S3 Object Lock

What is Object Lock?

Imagine you have a critically important document — a signed legal contract, audit-grade log file, or a financial transaction record. You need to guarantee that nobody — not even a developer with admin access, not even the AWS root user — can delete or change that file for the next seven years. Object Lock is exactly the feature designed for this guarantee.

S3 Object Lock permanently allows objects in a bucket to be locked, preventing them from being deleted or overwritten for a fixed time period or indefinitely.

Figure 2: Object Lock enforces the WORM model — Write Once, Read Many

Once locked, an object becomes WORM storage — WORM stands for Write Once, Read Many, meaning you can upload the object once, read it as many times as you like, but you cannot re-edit, overwrite, or delete it during the lock period.

⚠️ Critical Prerequisite

❌ Object Lock requires versioning to be enabled.Object Lock works only on versioning-enabled buckets — you cannot enable Object Lock on a bucket that does not have versioning turned on. This is a very common exam and interview question.

When Do You Actually Need This?

Object Lock is not for everyday use. It is specifically designed for situations where data integrity is legally or operationally non-negotiable:

  • Financial records — Transaction logs, audit trails that must be retained for regulatory periods (e.g., 7 years under SOX compliance).
  • Healthcare data — Patient records subject to HIPAA that cannot be altered once written.
  • Ransomware protection — Even if attackers compromise credentials, locked objects cannot be encrypted or deleted by ransomware.
  • Accidental deletion prevention — Protects critical data from developer mistakes or scripts running with overly broad permissions.
  • Legal hold — Preserving evidence during litigation proceedings.

Figure 3: Real-world use cases for S3 Object Lock

The Two Modes of Object Lock

Object Lock has two enforcement modes, and choosing between them matters a great deal in production. Think of them on a spectrum from "flexible protection" to "absolute protection":

Figure 4: Governance Mode vs Compliance Mode comparison

Governance Mode

In Governance Mode, the object is protected from deletion, but authorised users with special IAM permissions (such as the root user or a designated admin) can still overwrite or modify the object. No user — not even admins — can delete it during the lock period, but modification is possible for privileged users.

Think of it like a safe that most staff cannot open, but the bank manager has a master key. Use this for internal production environments where you want to protect data from the broader team but still need a senior administrator to make corrections when genuinely necessary.

Compliance Mode

In Compliance Mode, no one can delete or modify the object for the entire retention period — not authorised users, not the root user, and not AWS itself. It is completely immutable for the locked duration. This is the strictest level of protection available in AWS.

⚡ Interview tip: When asked "who can bypass compliance mode?" — the answer is nobody. Not even AWS. This is by design for regulatory frameworks like SEC Rule 17a-4 that legally require immutable storage.

Retention Period vs Legal Hold

Object Lock has two mechanisms for locking objects:

  • Retention Period — You specify an exact date until which the object cannot be modified or deleted. When the date passes, the object lock is automatically released.
  • Legal Hold — There is no time limit. The object remains locked until an authorised user explicitly removes the legal hold. Used during active litigation where you cannot predict how long the hold will last.

According to AWS documentation, you can apply Object Lock at the bucket level (default settings for all new objects) or at the individual object level. Both retention period and legal hold can be applied to the same object simultaneously.

📚 Source:AWS S3 Object Lock Docs

Enabling Object Lock — Step by Step

Object Lock must be enabled at bucket creation time — you cannot enable it on an existing bucket that was created without it. Here is the process:

  1. Open the S3 console and click Create bucket.
  2. Scroll to the Advanced settings section.
  3. Enable Object Lock and acknowledge the checkbox warning. Versioning is automatically enabled when you do this.
  4. After creating the bucket, go to the bucket → Properties → scroll to Object Lock to configure default retention settings.
  5. When uploading individual objects, you can also set per-object retention under the Properties tab during the upload wizard.

🔐 S3 Encryption

The Basics: What Is Encryption?

Before diving into S3-specific encryption options, it helps to understand what encryption actually is — because once you grasp the concept, all the AWS options become obvious.

Think of your data as a letter written in plain English. You want to send it through the postal system, but you are worried someone might intercept it. So you use a special code (a key) to scramble the letter into gibberish before you post it. Only someone with the same key (or a paired key) can unscramble it back into readable English.

Figure 5: Encryption converts readable data into ciphertext; decryption reverses the process

Encryption is the process of converting readable data (plaintext) into unreadable data (ciphertext) using a cryptographic key and algorithm, so that only authorised parties with the correct key can decrypt it back to its original form.

Symmetric vs Asymmetric Keys

A symmetric key uses the same key for both encryption and decryption, while an asymmetric key pair uses a public key to encrypt and a private key to decrypt.

  • Symmetric: Faster, simpler — one key does everything. Used by S3 server-side encryption under the hood.
  • Asymmetric: More secure for sharing — you give everyone your public key to encrypt messages to you, but only your private key (which you never share) can decrypt them. Used in SSL/TLS certificates.

Server-Side vs Client-Side Encryption

AWS S3 gives you two high-level choices for where encryption happens:

Figure 6: Client-Side Encryption (you encrypt before upload) vs Server-Side Encryption (AWS encrypts on arrival)

Server-Side Encryption (SSE): You upload your data as normal. AWS takes responsibility for encrypting it before writing it to disk. When you retrieve the object, AWS decrypts it transparently before delivering it to you. This is the most common approach because you do not have to do anything special — it just works.

Client-Side Encryption: You encrypt the data yourself, on your own machine or server, before uploading it to S3. S3 stores the already-encrypted blob. AWS never sees your plaintext data. This gives you the maximum control but requires you to manage keys and encryption logic yourself.

The Three Types of Server-Side Encryption

Figure 7: Three SSE types — from fully managed to customer-provided keys

SSE-S3 — S3 Managed Keys (Default)

SSE-S3 is the default encryption for all new S3 objects — Amazon S3 automatically manages the encryption keys, and every new upload is encrypted transparently using AES-256 with no additional configuration required.

This is like using a safe deposit box at a bank where the bank keeps the spare key. You do not have to remember any key, but you are trusting the bank completely. SSE-S3 is perfect for most non-sensitive workloads because it is completely free and automatic.

✅ Best practice for beginners: If you are unsure which encryption to use, SSE-S3 is always enabled by default and costs nothing extra. It is solid enough for most use cases.

SSE-KMS — AWS KMS Managed Keys (Most Common in Production)

SSE-KMS uses AWS Key Management Service (KMS) to manage the encryption keys, giving you full control over key policies, key rotation, access auditing via CloudTrail, and the ability to grant or revoke key access to specific IAM users or roles.

In the real world, SSE-KMS is the standard choice for production financial, healthcare, and regulated data workloads. It is used because it adds a critical capability: auditability. Every single time an object is encrypted or decrypted using a KMS key, that event is logged in AWS CloudTrail. You know exactly who accessed what, and when.

The professor's client encountered this first-hand — users uploading to S3 were getting errors. The bucket policy required all uploads to include a KMS Key ID in a specific ARN format. Without the correct key, uploads were rejected — exactly the kind of strict access control that protects financial data.

SSE-C — Customer-Provided Keys

SSE-C allows you to provide your own encryption key with each upload request; AWS uses your key to encrypt the data but does not store the key — you must send the same key again for each download request.

❌ Important: SSE-C is being blocked for all new S3 buckets from April 2026 due to AWS security concerns. AWS does not want customers to manage their own key delivery over the API. Use SSE-KMS instead for customer key control.

AWS Key Management Service (KMS)

KMS is a fully managed AWS service dedicated to creating, storing, and controlling cryptographic keys. Think of it as a highly secure key vault for your cloud environment.

Figure 8: KMS architecture — keys stored in tamper-proof HSMs with full policy and audit controls

Customer Managed Keys vs AWS Managed Keys

Within KMS, there are two key ownership models:

  • AWS Managed Keys are created and rotated automatically by AWS on your behalf — you cannot view, manage, or change their policies, but they are free to use.
  • Customer Managed Keys (CMK) are keys that you create yourself in KMS — you control the key policies (who can use them), the rotation schedule, and you can grant or revoke access to specific IAM principals.

In real projects, CMKs are used because they allow you to say: "Only IAM Role X in Account 123456 can use this key to encrypt or decrypt objects in bucket Y." This is how you enforce strict data access boundaries in large organisations.

Where Are Keys Actually Stored?

KMS stores all keys in Hardware Security Modules (HSMs) — tamper-proof physical devices that are designed so that even AWS employees cannot extract the raw key material from them.

An HSM is like a physical vault that destroys its contents if it detects tampering. The key never leaves the HSM in plaintext form — it only performs encryption/decryption operations inside the hardware itself.

Key Rotation

Key rotation is the practice of automatically replacing an old cryptographic key with a new one on a regular schedule (typically every 90–365 days), so that even if a key is somehow compromised, the window of exposure is limited.

Think of it like how some systems force you to change your password every 90 days. For KMS Customer Managed Keys, you can enable automatic annual rotation from the key's settings page. AWS Managed Keys are rotated automatically every year.

Data Encryption Keys (DEK) — The Critical Concept

This is the most important internals concept that interviewers love to ask about. Understanding how DEKs work shows you truly understand KMS, not just the surface-level configuration.

Figure 9: How DEK (Data Encryption Key) works — S3 never uses your KMS key directly

Here is the key insight: S3 does not directly use your KMS key to encrypt your data. Instead:

  1. When you upload an object to an SSE-KMS bucket, S3 calls KMS with your Key ID.
  2. KMS generates a short-lived DEK (Data Encryption Key) — a temporary key derived from your KMS master key.
  3. S3 uses the DEK to actually encrypt the object data.
  4. The encrypted DEK is stored alongside the encrypted object in S3.
  5. When you retrieve the object, S3 sends the encrypted DEK back to KMS to decrypt it, then uses the resulting DEK to decrypt the object and deliver it to you.

A DEK (Data Encryption Key) is a temporary cryptographic key generated by KMS to actually encrypt your S3 object data — your KMS master key never directly touches the raw data, preserving the security of the master key inside the HSM.

⚡ Interview answer: If asked "what actually encrypts your S3 data when using SSE-KMS?" — the correct answer is the DEK (Data Encryption Key). The KMS master key generates and wraps the DEK, but the DEK does the actual encryption work.

S3 Bucket Key — Cost Optimisation

Here is a problem: with standard SSE-KMS, every single object upload AND every single object download triggers a separate KMS API call. KMS is a charged service — you pay per API call. If you have millions of objects being read and written daily, the KMS costs can balloon.

Figure 10: Bucket Key reduces KMS API calls by reusing a single bucket-level DEK

An S3 Bucket Key is a long-lived, bucket-level Data Encryption Key generated by KMS once, and then reused by S3 to encrypt and decrypt many objects without making a new KMS API call for each one — reducing KMS costs by up to 99%.

Instead of calling KMS for every object, S3 calls KMS once per bucket to get a bucket-level DEK. This bucket key is cached inside S3 and reused for all objects in that bucket. The result: dramatically fewer KMS API calls, dramatically lower bills, with no reduction in security because the bucket key itself is still derived from and protected by your KMS master key.

✅ Bucket Key is enabled by default on all new SSE-KMS buckets. AWS enabled this by default because they want S3 to remain cost-competitive — charging customers heavily for KMS calls would have driven customers away from SSE-KMS encryption.

Enforcing KMS Encryption via Bucket Policy

In production, it is common to use a bucket policy to enforce that nobody can upload objects without using a specific KMS key. This prevents accidental uploads using SSE-S3 or no encryption at all.

The policy uses a Deny statement with a condition: if the upload does not include the KMS key in the correct ARN format, the upload is rejected. The KMS key ARN format looks like this:

arn:aws:kms:[region]:[account-id]:key/[key-id]

The professor shared a real story: a client was unable to upload files to their financial data bucket. The error was caused by a bucket policy that required uploads to reference the company's CMK Key ARN. Once the client obtained the Key ARN from their management and included it in the upload properties, the uploads succeeded immediately.

♻️ S3 Lifecycle Rules

What Are Lifecycle Rules?

Imagine you are a company storing server logs in S3. Your DevOps team needs instant access to logs from the past 30 days to debug issues. Logs from 30–90 days ago are rarely accessed but might be needed occasionally. Logs older than 90 days almost never need to be retrieved quickly. And logs older than one year can probably be deleted entirely.

Without lifecycle rules, you would need someone to manually move or delete files every month. That is tedious, error-prone, and expensive. Lifecycle Rules automate this entire process.

S3 Lifecycle Rules are automated policies that transition objects to cheaper storage classes or permanently delete them based on the age of the object, reducing storage costs without any manual intervention.

Figure 11: A typical lifecycle rule for log files — objects automatically move to cheaper storage as they age

The Two Types of Lifecycle Actions

Every lifecycle rule performs one of two actions:

  • Transition actions move objects from one storage class to another after a specified number of days — for example, moving from S3 Standard to S3 Standard-IA after 30 days.
  • Expiration actions permanently delete objects (or delete specific object versions if versioning is enabled) after a specified number of days.

Which Storage Classes Can Objects Transition Between?

Transitions always flow in one direction — from more expensive to cheaper storage. You cannot transition objects back up to a more expensive class using lifecycle rules (you would need to copy them manually). The valid downward transition flow is:

Figure 12: S3 storage class transition waterfall — lifecycle rules always move objects to cheaper classes

Key constraints to remember for the exam:

  • Objects must stay in S3 Standard for at least 30 days before they can be transitioned to Standard-IA or One Zone-IA.
  • Objects in Standard-IA or One Zone-IA must stay for at least 30 days before transitioning to Glacier.
  • S3 Intelligent-Tiering can be a destination for any object and manages sub-transitions automatically.

Scope: Entire Bucket vs Prefix Filter

Lifecycle rules can apply to an entire bucket or be narrowed to specific prefixes (folder paths) or object tags. This is what makes them flexible in real projects:

  • logs/ prefix → transition logs to Glacier after 90 days
  • images/thumbnails/ prefix → delete thumbnails after 365 days
  • Tag: environment=dev → delete development objects after 7 days

Lifecycle Rules with Versioning

When versioning is enabled, lifecycle rules gain extra power. You can create separate actions for:

  • Current versions — the active, latest copy of each object.
  • Non-current versions — older versions created by overwrites or deletes.
  • Expired delete markers — clean up tombstone markers left after versioned deletions.

With versioning enabled, a best practice lifecycle rule is to move non-current versions to Glacier after 30 days and permanently delete them after 90 days, preventing version history from accumulating unbounded storage costs.

Creating a Lifecycle Rule — Step by Step

  1. Go to your S3 bucket → click the Management tab.
  2. Click Create lifecycle rule.
  3. Give the rule a name (e.g., log-archival-rule).
  4. Choose the scope — apply to all objects, or filter by prefix/tag.
  5. Under Lifecycle rule actions, check "Transition current versions of objects between storage classes."
  6. Add transition: after 30 days → Standard-IA.
  7. Add transition: after 90 days → Glacier Flexible Retrieval.
  8. Optionally, check "Expire current versions of objects" and set after 365 days → permanent deletion.
  9. Review and save.

According to AWS documentation, lifecycle transitions to Glacier Flexible Retrieval or Deep Archive are the most cost-effective for data that rarely needs to be accessed. Glacier Deep Archive costs as little as $0.00099 per GB per month — roughly 23x cheaper than S3 Standard.

🔄 S3 Replication Rules

What Is Replication?

Picture a bank that keeps an exact backup copy of all its records in a vault in a different city. If a disaster strikes the main office, the backup city has everything needed to keep operating. S3 Replication is the AWS equivalent — automatically keeping a real-time copy of your objects in another bucket.

S3 Replication is a feature that automatically and asynchronously copies new and updated objects from a source bucket to one or more destination buckets, either within the same AWS account or across different accounts.

Figure 13: S3 supports two replication types — Same-Region (SRR) and Cross-Region (CRR)

Two Types: CRR and SRR

Cross-Region Replication (CRR) copies objects to a destination bucket in a different AWS region, while Same-Region Replication (SRR) copies objects to a destination bucket within the same region.

Cross-Region Replication (CRR)

Used for:

  • Disaster recovery — If the Mumbai region goes down, your Singapore replica is unaffected and can serve as a failover.
  • Latency improvement — Replicate content to a region closer to your end users for faster downloads.
  • Compliance — Some regulations require data to be stored in multiple geographic locations.
  • Cross-account backup — A security team in Account B can receive read-only copies of production data from Account A.

Same-Region Replication (SRR)

Used for:

  • Log aggregation — Consolidate logs from multiple buckets into one central analytics bucket.
  • Dev/prod sync — Keep a staging bucket in sync with production for testing.
  • Data sovereignty within a region — Maintain a second copy for internal audit without leaving the region.

Prerequisites for Replication

❌ Replication requires versioning to be enabled on BOTH the source and destination buckets. This is a mandatory prerequisite — replication will fail to configure if versioning is not on for both.

Other requirements:

  • The S3 service needs an IAM role with permission to read from the source and write to the destination.
  • For cross-account replication, the destination bucket policy must explicitly grant the source account permission to replicate into it.
  • KMS-encrypted objects can be replicated, but you must specify a KMS key for the destination region separately.

What Gets Replicated?

Once replication is enabled, it applies to new objects going forward. Objects that existed in the bucket before replication was turned on are NOT automatically replicated. To replicate existing objects, you use S3 Batch Replication — a separate operation that backfills existing objects.

⚡ Exam tip: "Replication only applies to new objects uploaded after the rule is created" is a frequently tested fact. Existing objects require S3 Batch Replication separately.

What is replicated by default:

  • Objects and their metadata
  • Object tags
  • ACLs (if configured)
  • Object versions

What is NOT replicated by default (requires additional configuration):

  • Delete markers (can be optionally enabled)
  • Replicated objects from another replication rule (no chaining by default)
  • Objects stored in Glacier or Glacier Deep Archive (until restored)

Replication Time Control (RTC)

S3 Replication Time Control (RTC) is an optional add-on that provides an SLA guaranteeing that 99.99% of objects will be replicated within 15 minutes of upload, with real-time monitoring via CloudWatch metrics.

Standard replication is asynchronous with no time guarantee — it usually completes within seconds to minutes, but there is no official SLA. Use RTC when your business requires a guaranteed RPO (Recovery Point Objective) for disaster recovery.

Setting Up CRR — Step by Step

  1. Enable versioning on the source bucket (Properties → Versioning → Edit → Enable).
  2. Create the destination bucket in a different region with versioning also enabled.
  3. On the source bucket → Management tab → Replication rules → Create replication rule.
  4. Give the rule a name and set the status to Enabled.
  5. For scope, choose all objects or a prefix/tag filter.
  6. Select the destination bucket (specify bucket name and region).
  7. Under IAM role, choose "Create new role" — S3 will auto-create a role with the necessary permissions.
  8. Optionally enable Replication Time Control and configure KMS encryption for the destination.
  9. Save. A prompt asks if you want to replicate existing objects via Batch Replication — choose Yes if needed.

According to AWS documentation, you can have up to 1,000 replication rules per bucket and replicate to multiple destination buckets simultaneously, including cross-account destinations.

📚 Source:AWS S3 Replication Docs

🌐 S3 Static Website Hosting

What Is Static Website Hosting?

Normally, to serve a website, you need a server — an EC2 instance, a container, a Lambda function — something running 24/7 to respond to requests. But for many websites (personal portfolios, documentation sites, landing pages, frontend apps), the content never changes based on who is viewing it. These are "static" sites.

S3 Static Website Hosting allows you to serve a static website (HTML, CSS, JavaScript, images) directly from an S3 bucket over HTTP, without any backend servers, with near-zero cost and automatic scalability.

Figure 14: S3 static website architecture — with and without CloudFront for HTTPS and custom domains

When to Use It

  • Personal portfolio or blog
  • Product landing pages
  • Documentation sites (like AWS docs themselves use similar principles)
  • React / Angular / Vue.js Single Page Applications (SPAs) after building
  • Error pages (custom 404 pages hosted in S3)
  • Pre-launch "coming soon" pages

Key Limitation: HTTP Only

S3 static website hosting serves content over HTTP only — it does not natively support HTTPS. To serve your static site over HTTPS with a custom domain, you must place a CloudFront distribution in front of your S3 bucket.

This is why the professor mentioned that the next session covers CloudFront and ACM (AWS Certificate Manager) together with static website hosting — they form an integration stack. The standard production pattern is: S3 (content storage) + CloudFront (CDN + HTTPS) + ACM (SSL/TLS certificate) + Route53 (custom domain).

Figure 15: Full production static website stack: S3 + CloudFront + ACM + Route53

Index Document and Error Document

When enabling static website hosting, you must specify:

  • Index document — The default page S3 serves when someone visits the root URL (e.g., index.html).
  • Error document — The page S3 serves when an object is not found or access is denied (e.g., error.html). This gives you a friendly custom 404 page.

The Website Endpoint URL

Once enabled, S3 generates a website endpoint in this format:

http://[bucket-name].s3-website-[region].amazonaws.com

For example: http://my-portfolio.s3-website-ap-southeast-1.amazonaws.com

Note: The S3 REST API endpoint and the S3 website endpoint are different. The website endpoint supports redirects, custom index/error documents, and serving directory-style URLs. The REST endpoint does not.

Making Content Publicly Accessible

For a public website, all objects need to be readable by anyone. You must:

  1. Disable Block Public Access on the bucket (specifically the "Block public access via new bucket policies" setting).
  2. Add a bucket policy granting s3:GetObject to Principal: "*" for all objects in the bucket.
{ "Version": "2012-10-17", "Statement": [{ "Sid": "PublicReadGetObject", "Effect": "Allow", "Principal": "*", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::your-bucket-name/*" }] }

❌ Security note: Only make objects public this way for genuinely public-facing website content. Never use this pattern for buckets containing sensitive data. For private content delivery, use CloudFront with Origin Access Control (OAC) instead — this keeps the S3 bucket private while still allowing CloudFront to serve its content.

Enabling Static Website Hosting — Step by Step

  1. Open your S3 bucket → click the Properties tab.
  2. Scroll to Static website hosting → click Edit.
  3. Select Enable.
  4. Set the Index document to index.html.
  5. Set the Error document to error.html (optional but recommended).
  6. Click Save changes.
  7. Copy the Bucket website endpoint URL shown — this is your website URL.
  8. Upload your index.html and all other website files to the bucket.
  9. Configure a bucket policy (above) to allow public read.
  10. Visit the endpoint URL in your browser — your website is live!

✅ Cost note: Hosting a static website in S3 is extremely cheap. You only pay for storage (typically a few cents per GB per month) and data transfer out (first 100 GB per month is free via CloudFront free tier). A small personal website costs less than $1/month total.

📝 Overall Summary

  • Object Lock (WORM): Prevents objects from being deleted or overwritten. Requires versioning. Governance mode allows authorised users to modify (not delete). Compliance mode blocks everyone — including AWS — from any changes during the retention period.
  • Encryption Basics: Encryption converts plaintext to ciphertext using a key. Symmetric encryption uses one key for both operations; asymmetric uses a key pair. Two high-level options: Server-Side Encryption (AWS encrypts on arrival) and Client-Side Encryption (you encrypt before upload).
  • SSE-S3: Default encryption. AWS S3 manages all keys automatically using AES-256. Free, zero-configuration. Best for non-sensitive workloads.
  • SSE-KMS: AWS KMS manages keys. You control key policies, rotation, and access via IAM. Every KMS call is logged in CloudTrail. The standard choice for regulated production environments.
  • KMS + DEK: S3 never directly uses your KMS master key to encrypt data. Instead, KMS generates a temporary DEK per object. The DEK encrypts the object. The encrypted DEK is stored alongside the object. On retrieval, KMS decrypts the DEK, which then decrypts the object.
  • Bucket Key: Reduces SSE-KMS costs by up to 99%. S3 generates one long-lived bucket-level DEK via a single KMS call and reuses it for many objects, dramatically reducing per-call charges.
  • Lifecycle Rules: Automate storage class transitions and deletions based on object age. Transition actions move objects down the storage class waterfall; expiration actions delete them. Supports prefix/tag scoping and per-version controls.
  • Replication — CRR: Cross-Region Replication copies objects to a different AWS region. Used for disaster recovery, compliance, and latency improvements. Requires versioning on both buckets. Only new objects are replicated; use S3 Batch Replication for existing objects.
  • Replication — SRR: Same-Region Replication copies objects to another bucket in the same region. Used for log aggregation, dev/prod sync, or internal backup without leaving the region.
  • Static Website Hosting: Serve HTML/CSS/JS directly from S3 over HTTP. No servers needed. Must add a public bucket policy for s3:GetObject. HTTPS and custom domains require CloudFront + ACM in front.

Project 4: Secure Upload System — Enforce KMS via Bucket Policy

🎯 Objective: Create an S3 bucket where uploads fail unless the uploader uses a specific KMS key. Reproduce the real-world scenario from the lecture.

⏱️ Time: 30–40 min

💰 Cost: KMS CMK costs $1/month — schedule deletion after the project.

📚 Topics Combined: SSE-KMS + Bucket Policy + KMS Key ARN format

📋 Before You Start

  • ✅ You have a Customer Managed Key in KMS (from Project 2, or create a new one)
  • ✅ You have your KMS Key ARN ready in Notepad: arn:aws:kms:region:account-id:key/key-id

  1. Create a new S3 bucket named secure-upload-lab-[yourname]. Keep Block Public Access on (default).

    📸 Screenshot: Creating the secure upload bucket with default settings

  2. Go to the bucket → Permissions → Bucket policy → Edit. Add this policy (replace YOUR-BUCKET-NAME and YOUR-KMS-KEY-ARN):

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyNonKMSUploads",
      "Effect": "Deny",
      "Principal": "*",
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption-aws-kms-key-id": "YOUR-KMS-KEY-ARN"

      }
    }
  ]
}

    📸 Screenshot: Bucket policy with Deny condition for non-KMS uploads

  4. Test 2 — Upload with the correct KMS key: Click Upload → choose the same file → expand Properties → under Server-side encryption, select Specify an encryption key → paste your KMS Key ARN → Upload. Confirm it succeeds.

    📸 Screenshot: Upload succeeding when the correct KMS Key ARN is provided

  5. Click the uploaded object → Properties → scroll to Server-side encryption and confirm it shows your KMS Key ARN. This proves the object is encrypted with your specific CMK.

  6. Cleanup: Delete all objects → delete the bucket → go to KMS → schedule key deletion (7-day minimum).

🤔 Reflection Questions

1. Your company stores financial audit logs in S3. A junior developer accidentally ran a script that deleted last quarter's logs. How could Object Lock have prevented this, and which mode would you have chosen?

💡 Hint

Think about Compliance Mode vs Governance Mode. Compliance Mode means even root cannot delete. What would stop even an accidental root-level deletion?

2. A colleague says "We use SSE-S3 by default, so we don't need KMS." What is the key difference in control and auditability that KMS provides that SSE-S3 does not?

💡 Hint

Think about CloudTrail logging, key rotation control, and the ability to grant/revoke access per IAM principal.

3. You have 10 million objects in S3 encrypted with SSE-KMS. Your AWS bill shows unexpectedly high KMS charges. What feature should you enable, and how does it work?

💡 Hint

S3 Bucket Key reduces KMS API calls. Think about how it replaces per-object KMS calls with a single bucket-level DEK.

4. You have 3 years of server logs in S3 Standard. You need to keep them for legal reasons but they are never accessed after 60 days. Design a lifecycle rule policy to optimise costs.

💡 Hint

Use two transition actions (e.g., to Standard-IA at day 30, then Glacier Deep Archive at day 90) and no expiration since you need to retain them.

5. Your Mumbai-region production bucket needs to be replicated to Singapore for disaster recovery. You need a guarantee that replication completes within 15 minutes. What feature do you enable?

💡 Hint

Standard CRR has no SLA. Think about Replication Time Control (RTC).

6. You enable CRR on your production bucket but notice old objects are not appearing in the replica bucket. Why? What do you need to do to replicate those objects?

💡 Hint

Replication only applies to new objects. S3 Batch Replication handles existing objects.
