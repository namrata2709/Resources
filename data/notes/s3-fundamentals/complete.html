🌟 Introduction

Think about this: where do you store your files on your computer? In folders, right? Now imagine a storage system so big that it can hold millions of files, accessible from anywhere in the world, never loses your data, and automatically handles all the hardware so you never have to worry about disk space running out. That is exactly what AWS S3 is.

Figure 1: S3 high-level architecture — objects stored in buckets, distributed across availability zones

Amazon S3, or Simple Storage Service, is a fully managed, scalable object storage service provided by AWS. Unlike EBS (block storage attached to EC2) or EFS (file system storage over a network), S3 stores data as objects inside containers called buckets. You do not need to manage any servers, disks, or hardware — AWS handles everything for you.

In this session, we covered three foundational S3 topics: how buckets and objects work, the different storage classes you can choose from, and how versioning protects your data from accidental changes or deletions. These are among the most exam-heavy topics in all of AWS, so understanding them deeply matters both for certification and for real-world cloud work.

⚡ Why S3 matters: Nearly every AWS architecture uses S3 — for storing application files, hosting static websites, backing up databases, delivering content globally, and archiving years of historical data. It is the backbone of cloud storage.

☁️ What is S3?

Before diving into the details, let us understand what kind of storage S3 is and how it differs from the other storage systems you have already learned about.

Figure 2: Three AWS storage types compared — EBS, EFS, and S3

Storage Types Recap

You have already seen two types of AWS storage:

  • EBS (Elastic Block Store): Block storage attached directly to an EC2 instance. Like a hard drive plugged into your computer — only that one computer can use it.
  • EFS (Elastic File System): Network-based file system storage that multiple EC2 instances can share — like a shared drive on a company network.
  • S3 (Simple Storage Service): Object storage — files are stored as independent objects with a unique URL. Any application, user, or service can access them from anywhere over the internet (with the right permissions).

Key Characteristics of S3

S3 is a fully managed service, meaning AWS handles all underlying infrastructure — no servers to provision, no disks to manage.

S3 provides 11 nines of durability (99.999999999%), meaning even if you store data and come back after 100 years, your data will still be there. This is not just marketing — AWS achieves this by automatically replicating your objects across multiple physical locations.

S3 is also virtually unlimited in capacity. You can store as many objects as you want — from a single file to billions of files — without ever needing to request more space.

💡 Durability vs Availability: Durability means your data will not be lost. Availability means you can access it when you need it. S3 Standard offers both — 11 nines durability and 99.99% availability. According to AWS documentation, this durability is achieved by redundantly storing data across multiple devices and multiple facilities.

📚 Source:AWS S3 Data Durability Docs

🪣 Buckets and Objects

Everything in S3 starts with two concepts: buckets and objects. Think of it like this — if S3 is a filing cabinet, then a bucket is a drawer in that cabinet, and objects are the individual files inside that drawer.

Figure 3: S3 bucket and object hierarchy — buckets contain objects, each object has a unique URL

What is a Bucket?

A bucket is the top-level container for storing objects in S3. You create a bucket in a specific AWS region, and all objects inside that bucket are stored within that region.

S3 bucket names must be globally unique across all AWS accounts worldwide — no two buckets anywhere on AWS can share the same name. This is because the bucket name becomes part of the object's URL, which must be globally resolvable.

A bucket is region-specific — when you create a bucket, you choose one AWS region where the data physically lives, and S3 stores your objects there.

✅ Bucket naming rules: 3–63 characters, lowercase letters, numbers, and hyphens only. Cannot start or end with a hyphen. Must not look like an IP address (e.g., 192.168.1.1 is not allowed).

What is an Object?

An object is any file you store in S3 — an image, a video, a text document, a ZIP archive, a database backup, anything. Each object consists of the actual data (the file content) plus metadata (information about the file — who owns it, when it was created, its size, its storage class, etc.).

Every object has a key, which is simply the name of the object (including any folder-like path). The key is what uniquely identifies the object within a bucket.

Object URL Structure

Every object in S3 automatically gets a unique URL that follows this pattern:

https://[bucket-name].s3.[region].amazonaws.com/[key-name]

For example, if your bucket is called saiguda966 in the ap-south-1 region and you uploaded a file called tctprice.txt, the URL would be:

https://saiguda966.s3.ap-south-1.amazonaws.com/tctprice.txt

This URL is how S3 knows exactly which account, which bucket, and which file you are requesting. By default, this URL returns "Access Denied" because objects are private. You must explicitly grant permissions to make them publicly accessible.

Figure 4: Anatomy of an S3 object URL — each segment has a specific meaning

Upload Limits — Important Exam Facts

S3 has specific size limits that come up frequently in exams and interviews.

The maximum object size in S3 is 5 TB (5 terabytes) — this is the largest single file S3 can store.

The maximum single PUT upload size is 5 GB — you cannot upload a file larger than 5 GB in a single upload operation.

For objects larger than 5 GB, you must use Multipart Upload — S3 does not allow a single PUT for files above this size. In practice, AWS recommends using Multipart Upload for any file larger than 100 MB for better performance.

Figure 5: Multipart upload process — large files are split, uploaded in parallel, and reassembled

How Multipart Upload Works

Imagine you have a 10 GB file. You cannot upload it directly to S3 in one go (5 GB limit). Multipart Upload solves this:

  1. S3 automatically (or you manually) splits the large file into smaller chunks.
  2. Each chunk is uploaded independently and in parallel — this makes uploads much faster.
  3. Once all parts arrive, S3 reassembles them into the original complete file.
  4. If one part fails, only that part needs to be retried — not the entire file.

💡 Console vs CLI upload limits: Through the AWS Console, the practical limit for a single upload session is around 160 GB — above that you must use the AWS CLI or SDK. For files over 5 GB, multipart upload happens automatically regardless of the method you use.

📚 Source:AWS S3 Multipart Upload Docs

⚡ Quick Reference — S3 Size Limits:

  • Max object size: 5 TB
  • Max single PUT upload: 5 GB
  • Multipart required for: files > 5 GB
  • Multipart recommended for: files > 100 MB

📦 S3 Storage Classes

Here is a question: Would you pay the same rent for a luxury penthouse and a storage unit in a warehouse? Of course not — the penthouse gives you instant access and premium comfort, while the warehouse is slow to access but much cheaper. S3 storage classes work the same way.

Not all data needs the same performance. Some files you open every day. Others you back up once a month. And some are ancient archives you might look at once a year for auditing. S3 storage classes allow you to choose how quickly you can access data, how durable it is, and how much you pay — based on how frequently you need it.

Figure 6: S3 storage classes arranged by access speed and cost — faster access costs more

What Does a Storage Class Decide?

When you upload an object to S3, you choose a storage class for it. That choice determines:

  • Cost: How much AWS charges you per GB per month to store the object.
  • Access speed: Whether you get the data in milliseconds or have to wait minutes or hours.
  • Availability zones: Whether the object is spread across multiple AZs (fault-tolerant) or stored in just one AZ (cheaper, but less resilient).
  • Retrieval cost: Whether there is an extra charge each time you download or access the data.
  • Minimum storage duration: Some classes charge you for a minimum number of days even if you delete the object earlier.
  • Minimum billable object size: Some classes charge a minimum size per object even if your file is smaller.

Figure 7: Decision tree for choosing the right S3 storage class based on access patterns

S3 Standard — For Frequent Access

This is the default storage class. If you do not choose anything specific, S3 uses Standard.

S3 Standard is designed for frequently accessed data, offering millisecond access with objects stored across a minimum of 3 Availability Zones.

  • Use case: Active websites, mobile applications, gaming data, content distribution — anything your users touch daily.
  • Durability: 99.999999999% (11 nines)
  • Availability: 99.99%
  • Retrieval fee: None
  • Minimum storage duration: None
  • Cost: Highest per GB — you pay for premium performance

S3 Standard-IA — For Infrequent Access (Multi-AZ)

IA stands for Infrequent Access. Think of this as the backup drive you pull out once a month.

S3 Standard-IA is designed for data accessed infrequently but requiring millisecond retrieval when needed, stored across multiple Availability Zones.

  • Use case: Disaster recovery backups, monthly reports, older log files you rarely query.
  • Durability: 99.999999999% (11 nines)
  • Availability: 99.9%
  • Retrieval fee: Yes — you pay per GB retrieved
  • Minimum storage duration: 30 days
  • Minimum billable object size: 128 KB — even if you store a 10 KB file, you are billed for 128 KB.

S3 One Zone-IA — For Infrequent Access (Single AZ)

Same as Standard-IA, but S3 only stores the object in one Availability Zone instead of three. This makes it cheaper — but if that AZ goes down, your data is temporarily (or permanently, in a disaster) unavailable.

S3 One Zone-IA stores data in a single Availability Zone, making it 20% cheaper than Standard-IA but with lower resilience.

  • Use case: Secondary backups, data that can be recreated if lost (e.g., thumbnail images generated from originals).
  • Retrieval fee: Yes
  • Minimum storage duration: 30 days
  • Minimum billable object size: 128 KB

❌ Do not use One Zone-IA for primary backups or data that cannot be recreated. If the single AZ experiences a failure, you could lose that data permanently. Use Standard-IA or Standard for critical, irreplaceable data.

Glacier Storage Classes — For Archive Data

Glacier classes are designed for cold storage — data you almost never touch. Think of your 10-year-old bank statements you are legally required to keep, or medical records from 2015. You need to keep them, but you almost never open them.

Figure 8: Three Glacier classes compared by retrieval speed and cost

Glacier Instant Retrieval:

Glacier Instant Retrieval provides millisecond access for archive data accessed once per quarter, with a minimum storage duration of 90 days.

  • Use case: Medical images, news media archives accessed occasionally but urgently when needed.
  • Retrieval fee: Yes

Glacier Flexible Retrieval (formerly Glacier):

Glacier Flexible Retrieval offers retrieval times of minutes to hours (1–12 hours standard, or expedited 1–5 minutes at higher cost), with a minimum duration of 90 days.

  • Use case: Backup and disaster recovery data where retrieval SLAs are flexible. Like asking a bank for your 2020 statement — they will get back to you in a few hours.
  • Retrieval fee: Yes

S3 Glacier Deep Archive:

S3 Glacier Deep Archive is the lowest-cost S3 storage class, designed for data retained for 7–10 years, with retrieval times of up to 12 hours (standard) or 48 hours (bulk).

  • Use case: Regulatory compliance archives, financial records, healthcare data required by law to be retained long-term.
  • Minimum storage duration: 180 days
  • Retrieval fee: Yes

S3 Intelligent-Tiering — Let AWS Decide

Not sure which storage class fits your data? That is exactly what Intelligent-Tiering is for. It monitors how often each object is accessed and automatically moves it to the most cost-efficient tier.

S3 Intelligent-Tiering automatically moves objects between access tiers based on changing access patterns, with no retrieval fees and a small monthly monitoring and automation fee per object.

  • Tiers inside Intelligent-Tiering: Frequent Access → Infrequent Access (after 30 days of no access) → Archive Instant Access (after 90 days) → Archive Access (optional, after 90–180 days) → Deep Archive Access (optional, after 180+ days)
  • Use case: Data lakes, user-generated content, unpredictable workloads where access patterns change.
  • Minimum storage duration: 30 days

💡 Train analogy from class: Think of S3 storage classes like train compartments. First AC is expensive but ultra-comfortable and fast (S3 Standard). General class is cheap but slow (Glacier Deep Archive). You choose based on your actual need — not on what is fanciest. Why pay First AC prices for a 30-minute local ride?

🔄 S3 Versioning

Here is a common real-world problem: You upload a file to S3, then someone edits it and uploads a new version with the same name. The old version is gone. Or worse — someone accidentally deletes the file entirely. How do you get it back? This is exactly what versioning solves.

Figure 10: S3 versioning keeps all versions of an object — each upload creates a new version, not a replacement

What is Versioning?

S3 Versioning is a feature that keeps multiple versions of the same object in a bucket, allowing you to retrieve, restore, or delete specific versions at any time.

Without versioning enabled, uploading a file with the same key (name) as an existing object simply overwrites it. The old version is gone forever. With versioning enabled, S3 preserves every version — each upload creates a new version with a unique Version ID, and all previous versions remain accessible.

Enabling Versioning

Versioning is disabled by default. You enable it at the bucket level:

  1. Go to your S3 bucket in the AWS Console.
  2. Click the Properties tab.
  3. Find Bucket Versioning and click Edit.
  4. Select Enable and click Save changes.

💡 Important: Once you enable versioning on a bucket, you cannot fully disable it — you can only suspend it. Suspended versioning stops creating new versions but keeps all existing versions intact. According to AWS documentation, versioning-enabled buckets can also be used with MFA Delete for additional protection.

📚 Source:AWS S3 Versioning Docs

How Versions Work

Let us walk through a practical example (the same one demonstrated in class):

  1. You create a file tctprice.txt with "On-demand pricing: $0.0071/hour"
  2. You upload it to S3. S3 stores it as Version 1. No version ID yet (versioning was not enabled).
  3. You enable versioning on the bucket.
  4. You edit the file: "On-demand pricing: $0.005/hour" and upload it again with the same name.
  5. S3 now has two versions — the old one is preserved, and the new one is marked as "Latest".
  6. You add another line and upload again — now three versions exist simultaneously.

On the main S3 page you see only the latest version. To see all versions, click Show versions in the console — each version appears with its unique Version ID and timestamp.

Figure 11: S3 versioning console — all versions listed with unique IDs, latest marked at top

Versioning and Deletion — Delete Markers

Versioning handles deletions in a clever way that protects you from accidental loss.

When you delete an object from a versioning-enabled bucket, S3 does not permanently delete it — instead, it inserts a delete marker, which hides the object from the main view.

Figure 12: Delete marker flow — deletion hides the object, removing the marker restores it

Here is how the full delete and restore process works:

  1. User deletes the file from the main S3 page → S3 places a Delete Marker on the object. The file disappears from the main view.
  2. Switch to "Show versions" in the console → You can see the Delete Marker and all previous versions underneath it.
  3. To restore the file, select the Delete Marker and delete it. This removes the marker, and the object reappears in the main view — fully restored.
  4. To permanently delete a specific version, go to the versions view, select that version directly, and permanently delete it. Once a specific version is permanently deleted, it cannot be recovered.

⚡ Key insight: Deleting from the main page = safe (only adds a delete marker). Deleting from the versions page (selecting a specific version or marker) = permanent. This is a favourite exam scenario question — always think about which view you are deleting from.

Why Use Versioning?

  • Accidental overwrite protection: Someone uploads wrong data with the same filename — retrieve the previous version.
  • Accidental deletion protection: Someone deletes a critical file — remove the delete marker to restore it instantly.
  • Audit trail: Keep a history of all changes to important documents or configuration files.
  • Compliance: Some regulations require organizations to maintain historical versions of records.

✅ Best practice: Enable versioning on any bucket that stores important or irreplaceable data. Combine it with S3 Lifecycle Policies (future topic) to automatically move or expire old versions so storage costs stay manageable.

Cost Impact of Versioning

Every version of an object takes up storage and is billed accordingly. If you upload a 1 GB file 10 times with the same name, you are storing 10 GB total (each version is preserved). Use lifecycle policies to expire old versions after a set number of days — this controls costs while still keeping recent history.

🔒 S3 Object Lock (Introduction)

Object Lock was introduced at the very end of this session. It will be covered in full in the next session — this section provides complete coverage so you have everything you need to understand it.

What is Object Lock?

S3 Object Lock allows you to store objects using a write-once-read-many (WORM) model, preventing objects from being deleted or overwritten for a fixed amount of time or indefinitely.

Think of Object Lock like a sealed vault. Once you put a document inside and lock it, nobody — not even an administrator — can modify or delete it until the lock period expires. This is critical for regulatory compliance where data integrity must be guaranteed.

Figure 13: S3 Object Lock WORM model — locked objects cannot be modified or deleted during retention period

Object Lock Modes

Object Lock has two retention modes:

Compliance Mode:

In Compliance mode, no user — including the AWS root account — can delete or alter the object until the retention period expires. This is the strictest mode, used when regulations demand absolute immutability.

Governance Mode:

In Governance mode, most users cannot delete or alter objects, but users with special s3:BypassGovernanceRetention permissions can override the lock. This gives flexibility for administrative corrections while still protecting data from accidental changes.

Legal Hold

A Legal Hold prevents an object from being deleted or overwritten without a retention period — it stays locked until the legal hold is explicitly removed by a user with s3:PutObjectLegalHold permission.

Legal Hold is used when an organization is under litigation and must preserve specific records until the case is resolved — regardless of when a set retention period might otherwise expire.

Object Lock Requirements

  • Object Lock must be enabled at bucket creation — you cannot enable it on an existing bucket after it is created.
  • Versioning is automatically enabled and cannot be disabled on Object Lock buckets.
  • Object Lock applies at the object version level — a specific version of an object is what gets locked.

💡 Real-world use cases for Object Lock: Financial institutions storing trade records (SEC Rule 17a-4), healthcare organizations retaining patient records (HIPAA), media companies archiving original content, and any organization subject to GDPR or similar data retention regulations.

📚 Source:AWS S3 Object Lock Docs

🎓 Exam Tips
  • Storage class with NO retrieval fee: S3 Standard and S3 Intelligent-Tiering. All Glacier and IA classes have retrieval fees.
  • Single AZ storage class: Only S3 One Zone-IA. All other classes use multiple AZs (or let you choose for Intelligent-Tiering archive tiers).
  • 5 TB vs 5 GB: Max object size = 5 TB. Max single PUT upload = 5 GB. Above 5 GB = must use Multipart Upload. This distinction appears in exam questions frequently.
  • Delete marker behaviour: Deleting from main view = adds delete marker (recoverable). Deleting a specific version from the versions view = permanent.
  • Versioning once enabled: Can only be suspended, not fully disabled. All existing versions are preserved on suspension.
  • Compliance vs Governance mode: Compliance = absolute lock (even root cannot delete). Governance = most users locked but bypass permission exists.
  • Intelligent-Tiering monitoring fee: The only class that charges a per-object monitoring fee. No retrieval fee though.
  • Minimum 128 KB billing: Applies to Standard-IA and One Zone-IA. A 10 KB file stored in Standard-IA is still billed as 128 KB.
  • Minimum storage durations: Standard-IA and One Zone-IA = 30 days. Glacier Instant and Flexible = 90 days. Deep Archive = 180 days.
  • 11 nines durability: Applies to all S3 storage classes EXCEPT One Zone-IA (which still has 11 nines durability but lower availability because it is in one AZ).

📝 Overall Summary
  • S3 is object storage: Files (objects) are stored in buckets — unlike EBS (block) or EFS (file system). It is fully managed, serverless, and virtually unlimited.
  • Bucket names are globally unique: Because the bucket name is part of every object's URL, no two buckets anywhere on AWS can share a name.
  • Upload limits matter: Max object size = 5 TB. Max single PUT = 5 GB. Files above 5 GB require Multipart Upload, which splits the file into parallel chunks and reassembles them.
  • 11 nines durability: S3 guarantees 99.999999999% data durability — your data is replicated across multiple AZs and facilities automatically.
  • Storage classes optimize cost: Choose Standard for frequent access, Standard-IA or One Zone-IA for infrequent, Glacier classes for archive, and Intelligent-Tiering when access patterns are unpredictable.
  • Retrieval fees exist on IA and Glacier classes: Only Standard and Intelligent-Tiering have no retrieval fee. Every other class charges you to get data back out.
  • Versioning preserves history: With versioning enabled, every upload of the same key name creates a new version — old versions are kept. This allows rollback to any point in time.
  • Delete markers protect from accidental loss: Deleting from the main view only adds a delete marker. To truly restore the object, delete the marker. To permanently remove a version, delete it from the versions view directly.
  • Object Lock enforces WORM: Objects cannot be overwritten or deleted during a retention period. Compliance mode is absolute (even root is blocked). Governance mode allows bypass for privileged users.
  • Legal Hold adds flexibility: Blocks deletion without a fixed time period — stays active until explicitly removed by authorized users.

Project 1: Create a Bucket and Upload Objects

🎯 Objective: Create an S3 bucket, upload objects with different storage classes, and explore object properties and URLs.

⏱️ Time: 20–30 minutes

💰 Cost: Free tier (5 GB S3 Standard storage free per month)

  1. Sign in to the AWS Console and navigate to S3 using the search bar.

  2. Click Create bucket. Enter a globally unique bucket name (e.g., yourname-awstraining-2025). Select your preferred region (e.g., ap-south-1). Leave all other settings as default. Click Create bucket.

    Figure 14: 📸 Create bucket page — bucket name and region selection

  3. Click your newly created bucket to open it. Click Upload. Click Add files and select a file from your computer (e.g., a text file). Under Properties, scroll down to see the default storage class (Standard). Click Upload.

    Figure 15: 📸 S3 upload page — file selected with Standard storage class visible

  4. After the upload succeeds, click the uploaded object. Scroll down to see the Object URL. Copy and paste the URL into a browser — you should see Access Denied. This confirms the default private setting.

    Figure 16: 📸 S3 object properties page — note the Object URL and storage class

  5. Upload a second object. This time, before clicking Upload, scroll to Storage class under Properties and change it to S3 Standard-IA. Upload the file and compare the two objects' storage classes in the bucket view.

Verification

You should see two objects in your bucket with different storage class labels — one Standard, one Standard-IA. Both should return "Access Denied" when their URLs are opened in a browser.

Cleanup

  1. Select all objects in the bucket and click Delete. Type permanently delete to confirm.
  2. Return to the S3 bucket list. Select the bucket and click Delete. Type the bucket name to confirm deletion.

Project 2: Enable Versioning and Practice Delete Markers

🎯 Objective: Enable versioning on a bucket, upload multiple versions of the same file, practice deletion and restoration using delete markers.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier (note: each version counts as a separate object for billing)

  1. Create a new bucket (or use the one from Project 1 if not deleted). Go to the bucket's Properties tab. Scroll to Bucket Versioning and click Edit. Select Enable and click Save changes.

    Figure 17: 📸 Enabling bucket versioning from the Properties tab

  2. Create a text file on your computer named pricing.txt. Add the text: T3 Micro On-Demand: $0.0071/hour. Save it. Upload this file to your bucket.

  3. Edit the same file on your computer — change the price to $0.005/hour. Save it with the same filename (pricing.txt). Upload it again to the same bucket. You have now created Version 2.

  4. In the bucket, click Show versions (toggle at the top right of the objects list). You should see two entries for pricing.txt — each with a different Version ID and timestamp. The latest is marked.

    Figure 18: 📸 Show versions toggle reveals all versions with unique Version IDs

  5. Toggle back to the main view (hide versions). Select pricing.txt and click Delete. Type delete to confirm. The file disappears from the main view.

  6. Click Show versions again. You will see a Delete Marker listed at the top — this is the "deletion" S3 recorded. Your original versions are still there underneath.

    Figure 19: 📸 Delete marker appears at top of versions list — actual data is still present below

  7. To restore the file: In the versions view, select the Delete Marker only. Click Delete. Type permanently delete in the confirmation box. Confirm. Toggle back to main view — pricing.txt is restored.

Verification

After removing the delete marker, pricing.txt should reappear in the main bucket view showing the most recent version's content. Both historical versions should still be visible in the versions view.

Cleanup

💰 Cost Note: Every version stored in S3 is billed as a separate object. Delete all versions to avoid ongoing charges.

  1. Click Show versions. Select ALL versions of every object (including all historical versions and any delete markers).
  2. Click Delete. Type permanently delete to confirm. All versions are now gone.
  3. Return to the bucket list. Select and delete the bucket itself.

Project 3: Host a Static Website on S3

🎯 Objective: Host a real static HTML website directly from an S3 bucket — no servers, no EC2, no cost beyond storage.

⏱️ Time: 30–45 minutes

💰 Cost: Essentially free — a few KB of storage and minimal data transfer

S3 can serve HTML files directly to browsers over HTTP. This is how many landing pages, documentation sites, and error pages are hosted at near-zero cost. No web server software needed — S3 acts as the server.

Figure 1: S3 static website hosting — bucket acts as web server, serving HTML directly to browsers

  1. Create a new S3 bucket named yourname-static-site-2025 (replace yourname with something unique). Choose any region. Leave all defaults for now — you will configure website hosting separately.

    Figure 2: 📸 New static site bucket visible in the S3 bucket list

  2. Create two files on your local machine:

    index.html

    <!DOCTYPE html> <html> <head><title>My AWS S3 Site</title></head> <body> <h1>🚀 Hello from Amazon S3!</h1> <p>This page is hosted entirely on S3 — no server required.</p> <p>Storage class: Standard | Region: ap-south-1</p> </body> </html>

    error.html

    <!DOCTYPE html> <html> <head><title>Page Not Found</title></head> <body> <h1>404 — Page Not Found</h1> <p>Sorry, the page you requested does not exist.</p> <a href="index.html">Go back home</a> </body> </html>

  3. Upload both files to your bucket. In the S3 console, open the bucket, click Upload, add both files, and click Upload. Keep storage class as Standard.

  4. Go to the bucket's Properties tab. Scroll to Static website hosting. Click Edit. Select Enable. Set Index document to index.html. Set Error document to error.html. Click Save changes.

    Figure 3: 📸 Static website hosting enabled — note the website endpoint URL at the bottom of the section

  5. Copy the Bucket website endpoint URL (shown at the bottom of the static hosting section). Open it in a browser — you will see 403 Forbidden. This is expected because the bucket is still private.

  6. Now make the bucket publicly readable. Go to the Permissions tab. Click Edit on Block Public Access. Uncheck all four boxes. Click Save changes. Type confirm in the confirmation box.

    💰 Cost Note: Making a bucket public allows anyone on the internet to access your files and incur data transfer charges. For this training bucket with a tiny HTML file, the cost is negligible (fractions of a cent). Never make buckets containing sensitive data public.

    Figure 4: 📸 Block Public Access disabled — all four checkboxes must be unchecked to allow public access

  7. Now add a Bucket Policy to allow public read access to all objects. Still in the Permissions tab, scroll to Bucket policy. Click Edit. Paste this policy (replace yourname-static-site-2025 with your actual bucket name):

    { "Version": "2012-10-17", "Statement": [ { "Sid": "PublicReadGetObject", "Effect": "Allow", "Principal": "*", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::yourname-static-site-2025/*" } ] }

    Click Save changes.

    Figure 5: 📸 Bucket policy saved — the policy grants s3:GetObject to all principals (*)

  8. Return to the Properties tab and copy the bucket website endpoint again. Open it in your browser. You should now see your Hello from Amazon S3! page.

    Figure 6: 📸 Static website live in browser — served directly from S3 with no server

  9. Test the error page: Add a random path to the URL (e.g., http://...amazonaws.com/doesnotexist) and press Enter. You should see your custom 404 — Page Not Found page.

What you just built

A live website with zero server infrastructure. The same technique powers AWS documentation, many startup landing pages, and error pages for large web applications. The next natural step (taught later in the course) is adding CloudFront in front of this bucket for HTTPS, caching, and global delivery.

Cleanup

💰 Cost Note: A public bucket with tiny HTML files costs nearly nothing, but it is good practice to clean up after every project.

  1. Go to the bucket. Select all objects and click Delete. Type permanently delete to confirm.
  2. Return to the bucket list. Select the bucket and click Delete. Type the bucket name to confirm deletion.

Project 4: Smart Storage with Lifecycle Policies

🎯 Objective: Create a lifecycle policy that automatically moves objects from Standard → Standard-IA → Glacier as they age, simulating real cost optimization used in production systems.

⏱️ Time: 25–35 minutes

💰 Cost: Free tier — lifecycle rules themselves have no cost. Storage transitions take effect after the configured number of days.

In production, no one manually moves files between storage classes. You set a rule once and S3 handles it forever. This is how companies save thousands of dollars monthly on storage — by automatically moving ageing data to cheaper tiers.

Figure 7: S3 lifecycle policy — files automatically transition between storage classes based on age

  1. Create a new bucket called yourname-lifecycle-demo-2025. Leave all settings as default. Do NOT enable versioning for this project.

  2. Upload five sample files to the bucket. You can use any small files from your computer — text files, images, anything. The content does not matter; you are learning lifecycle rule behavior.

  3. In the bucket, go to the Management tab. Click Create lifecycle rule.

    Figure 8: 📸 Management tab — Lifecycle rules section with Create lifecycle rule button

  4. Configure the rule:

    • Rule name:auto-archive-rule
    • Filter type: Apply to all objects in the bucket (leave prefix empty)
    • Rule actions: Check Transition current versions of objects between storage classes

  5. Add three transitions in order:

    • Transition 1: Storage class = Standard-IA, Days after creation = 30
    • Transition 2: Storage class = Glacier Flexible Retrieval, Days after creation = 90

    Then also check Expire current versions of objects and set Days = 365 to auto-delete after one year.

    Figure 9: 📸 Lifecycle rule with three transitions configured — Standard-IA at 30 days, Glacier at 90, expire at 365

  6. Click Create rule. The rule is now active. S3 will evaluate all objects nightly and transition any that have passed the age threshold.

  7. Return to the Management tab and confirm your rule appears in the list with status Enabled.

What you just built

A fully automated storage cost optimizer. In a real system, this rule would automatically save money as data ages — paying Standard prices only for fresh data, IA prices for monthly-accessed data, and Glacier prices for old archives. Many companies combine this with versioning to also expire old versions on a separate rule.

✅ Production tip: Use separate lifecycle rules for current versions and non-current versions. Example: keep current versions in Standard for 30 days, then move to IA. Expire non-current (old) versions after 7 days to control versioning storage costs.

Cleanup

  1. In the Management tab, select the lifecycle rule and click Delete. Confirm deletion.
  2. Select and permanently delete all objects in the bucket.
  3. Delete the bucket.

Project 5: Secure File Sharing with Pre-Signed URLs

🎯 Objective: Generate time-limited pre-signed URLs using the AWS CLI and Python (boto3) that allow temporary access to private S3 objects without making them public.

⏱️ Time: 30–40 minutes

💰 Cost: Free — S3 standard storage, no data transfer charges for tiny test files

Pre-signed URLs are how real applications handle secure file sharing. When a user wants to download their invoice from an app, the backend generates a URL that expires in 15 minutes — not a permanent public link, just a temporary one. The file stays private. This is production-level S3 usage.

Figure 10: Pre-signed URL flow — backend generates a temporary URL, user downloads directly from S3

Part A — Using the AWS CLI

  1. Make sure the AWS CLI is installed and configured (aws configure with your access key, secret, and default region). Then create a private bucket: 

    aws s3 mb s3://yourname-presigned-demo-2025 --region ap-south-1

  2. Create a test file and upload it to the private bucket:

    echo "This is a confidential invoice - Invoice #2025-001" > invoice.txt aws s3 cp invoice.txt s3://yourname-presigned-demo-2025/invoices/invoice.txt

  3. Verify the file is private — try opening its object URL in a browser. You should see Access Denied.

  4. Generate a pre-signed URL that expires in 5 minutes (300 seconds):

    aws s3 presign s3://yourname-presigned-demo-2025/invoices/invoice.txt \ --expires-in 300

    The command prints a very long URL with a signature embedded in it. Copy the full URL.

    Figure 11: 📸 Pre-signed URL generated by AWS CLI — note X-Amz-Expires=300 (5 minutes)

  5. Paste the pre-signed URL into your browser. The file downloads successfully — no AWS credentials needed by the browser. Wait 5 minutes and try the same URL again — you should now see Access Denied because the link has expired.

Part B — Using Python (boto3)

  1. Create a Python file called generate_presigned.py and paste this code:

    import boto3 from botocore.exceptions import ClientError def generate_presigned_url(bucket_name, object_key, expiry_seconds=900): """ Generate a pre-signed URL to download a private S3 object. Default expiry: 900 seconds (15 minutes) """ s3_client = boto3.client('s3', region_name='ap-south-1') try: url = s3_client.generate_presigned_url( 'get_object', Params={ 'Bucket': bucket_name, 'Key': object_key }, ExpiresIn=expiry_seconds ) print(f"\n✅ Pre-signed URL generated successfully!") print(f"Expires in: {expiry_seconds} seconds ({expiry_seconds // 60} minutes)") print(f"\nURL:\n{url}\n") return url except ClientError as e: print(f"❌ Error generating URL: {e}") return None # --- Run it --- BUCKET = 'yourname-presigned-demo-2025' # Replace with your bucket name KEY = 'invoices/invoice.txt' EXPIRY = 900 # 15 minutes generate_presigned_url(BUCKET, KEY, EXPIRY)

  2. Install boto3 if not already installed:

    pip install boto3

  3. Run the script:

    python generate_presigned.py

    Copy the output URL and test it in your browser — the file should download.

    Figure 12: 📸 Python boto3 output — pre-signed URL generated with 15 minute expiry

  4. Now generate an upload pre-signed URL (so someone can upload to your private bucket without AWS credentials). Add this function to your script: 

    def generate_presigned_upload_url(bucket_name, object_key, expiry_seconds=300): """ Generate a pre-signed URL to allow upload to a private S3 bucket. The uploader needs no AWS credentials. """ s3_client = boto3.client('s3', region_name='ap-south-1') try: url = s3_client.generate_presigned_url( 'put_object', Params={ 'Bucket': bucket_name, 'Key': object_key, 'ContentType': 'text/plain' }, ExpiresIn=expiry_seconds ) print(f"\n✅ Upload pre-signed URL generated!") print(f"Upload to key: {object_key}") print(f"Expires in: {expiry_seconds} seconds") print(f"\nURL:\n{url}\n") print("Use this curl command to test upload:") print(f'curl -X PUT -H "Content-Type: text/plain" --data "test upload content" "{url}"') return url except ClientError as e: print(f"❌ Error: {e}") return None generate_presigned_upload_url(BUCKET, 'uploads/test-upload.txt')

  5. Run the script and use the printed curl command to test the upload pre-signed URL. Then check your S3 bucket — you should see the uploaded file.

What you just built

The core of any file-sharing feature in production apps. Every time a user clicks "Download" in a real application — on a bank statement, a medical report, a shared document — the backend runs code like this to generate a temporary URL. The file stays private in S3. The URL works just once, for a short time, for that specific user.

Cleanup

  1. Delete all objects from the bucket:

    aws s3 rm s3://yourname-presigned-demo-2025 --recursive

  2. Delete the bucket:

    aws s3 rb s3://yourname-presigned-demo-2025

Project 6: File Upload API Using Python SDK (boto3)

🎯 Objective: Build a Python script that uploads files to S3 with validation (file size and type checks), assigns unique keys using UUID, and stores metadata — simulating a real backend file upload service.

⏱️ Time: 40–60 minutes

💰 Cost: Free tier — standard S3 storage for small test files

This is Level 5 of the skill ladder: S3 becomes part of an application. In real apps (Instagram, Dropbox, any file-sharing tool), files are never uploaded through the console — a backend service handles it, validates the file, generates a unique key, and stores metadata alongside the upload.

Figure 13: SDK upload architecture — backend validates, assigns UUID key, uploads to S3, stores metadata

  1. Create a private bucket called yourname-upload-service-2025. No versioning needed for this project.

  2. Create a Python file called s3_uploader.py. This is a complete upload service with validation:

    import boto3 import uuid import os from datetime import datetime from botocore.exceptions import ClientError # --- Configuration --- BUCKET_NAME = 'yourname-upload-service-2025' # Replace with your bucket name REGION = 'ap-south-1' MAX_FILE_SIZE_MB = 10 ALLOWED_EXTENSIONS = {'.jpg', '.jpeg', '.png', '.gif', '.pdf', '.txt', '.docx'} s3_client = boto3.client('s3', region_name=REGION) def validate_file(file_path): """Check file size and extension before uploading.""" if not os.path.exists(file_path): return False, f"File not found: {file_path}" file_size_bytes = os.path.getsize(file_path) file_size_mb = file_size_bytes / (1024 * 1024) if file_size_mb > MAX_FILE_SIZE_MB: return False, f"File too large: {file_size_mb:.2f} MB (max {MAX_FILE_SIZE_MB} MB)" _, extension = os.path.splitext(file_path) if extension.lower() not in ALLOWED_EXTENSIONS: return False, f"File type not allowed: {extension}. Allowed: {ALLOWED_EXTENSIONS}" return True, "Valid" def generate_unique_key(file_path, folder='uploads'): """ Create a unique S3 key using UUID. Format: uploads/2025-11-21/uuid-filename.ext """ _, extension = os.path.splitext(file_path) filename = os.path.basename(file_path) unique_id = str(uuid.uuid4())[:8] # short UUID prefix date_prefix = datetime.now().strftime('%Y-%m-%d') unique_key = f"{folder}/{date_prefix}/{unique_id}-{filename}" return unique_key def upload_file(file_path): """Main upload function with validation, unique key, and metadata tagging.""" print(f"\n📂 Uploading: {file_path}") # Step 1: Validate is_valid, message = validate_file(file_path) if not is_valid: print(f"❌ Validation failed: {message}") return None file_size_bytes = os.path.getsize(file_path) _, extension = os.path.splitext(file_path) # Step 2: Generate unique key s3_key = generate_unique_key(file_path) print(f"🔑 S3 Key: {s3_key}") # Step 3: Upload with metadata tags try: s3_client.upload_file( file_path, BUCKET_NAME, s3_key, ExtraArgs={ 'Tagging': ( f"uploader=python-sdk&" f"original_filename={os.path.basename(file_path)}&" f"upload_date={datetime.now().strftime('%Y-%m-%d')}&" f"file_type={extension.lstrip('.')}" ), 'StorageClass': 'STANDARD' } ) # Build the object URL object_url = f"https://{BUCKET_NAME}.s3.{REGION}.amazonaws.com/{s3_key}" print(f"✅ Upload successful!") print(f"📦 Size: {file_size_bytes / 1024:.1f} KB") print(f"🔗 URL: {object_url}") print(f"🏷️ Tags: original_filename, upload_date, file_type stored as S3 tags") return object_url except ClientError as e: print(f"❌ Upload failed: {e}") return None def list_uploaded_files(): """List all files in the uploads folder with their metadata.""" print(f"\n📋 Files in s3://{BUCKET_NAME}/uploads/") print("-" * 60) try: response = s3_client.list_objects_v2( Bucket=BUCKET_NAME, Prefix='uploads/' ) objects = response.get('Contents', []) if not objects: print("No files found.") return for obj in objects: print(f" Key: {obj['Key']}") print(f" Size: {obj['Size'] / 1024:.1f} KB") print(f" Date: {obj['LastModified'].strftime('%Y-%m-%d %H:%M')}") print() except ClientError as e: print(f"❌ Error listing files: {e}") # --- Run the uploader --- if __name__ == '__main__': # Create test files test_files = [] # Valid text file with open('test_invoice.txt', 'w') as f: f.write("Invoice #2025-001\nAmount: $500\nDate: 2025-11-21") test_files.append('test_invoice.txt') # Try an invalid extension (will be rejected) with open('test_script.sh', 'w') as f: f.write("#!/bin/bash\necho hello") test_files.append('test_script.sh') print("=" * 60) print("S3 Upload Service — boto3 Demo") print("=" * 60) # Upload each file for file_path in test_files: upload_file(file_path) # List what was uploaded list_uploaded_files() # Clean up local test files for f in test_files: os.remove(f) print("\n🧹 Local test files cleaned up.")

  3. Run the script:

    python s3_uploader.py

    You should see the text file upload succeed and the shell script rejected by validation.

    Figure 14: 📸 SDK upload script output — text file succeeds, .sh file rejected by validation

  4. Go to the AWS S3 console, open your bucket, and find the uploaded file under uploads/YYYY-MM-DD/. Click on the object. Click the Tags tab to see the metadata tags stored alongside the file.

    Figure 15: 📸 S3 object tags — metadata stored alongside the uploaded file, visible in the console

What you just built

The core of any file upload feature in production software. The pattern here — validate → generate unique key → upload with metadata → return URL — is used in virtually every SaaS application that handles user files. Add a database to store the URL and key, add user authentication, and you have the storage layer of a full product.

  1. Delete all objects:

    aws s3 rm s3://yourname-upload-service-2025 --recursive

Project 7 (Challenge): Secure Compliance Document Vault

🎯 Objective: Build a document vault where legal documents are locked for a retention period using S3 Object Lock — no deletion or modification possible, even by admins.

⏱️ Time: 45–60 minutes

💰 Cost: Free tier storage. Object Lock has no additional charge beyond storage.

💰 Cost Note: Object Lock must be enabled at bucket creation. You cannot delete a bucket that still has locked objects — you must wait for the retention period to expire. Use short retention periods (1–2 days) for testing to avoid getting stuck.

  1. Create a new bucket called yourname-vault-2025. During creation — at the bucket creation screen only — expand Advanced settings and enable Object Lock. This also enables versioning automatically. You cannot add Object Lock to an existing bucket.

    Figure 16: 📸 Object Lock enabled during bucket creation — this is the only time it can be set

  2. Upload a test document — create a file called legal-contract-2025.txt with any content.

    echo "LEGAL CONTRACT - Document ID: LC-2025-001 - Do not delete or modify" > legal-contract-2025.txt aws s3 cp legal-contract-2025.txt s3://yourname-vault-2025/contracts/legal-contract-2025.txt

  3. Apply a Governance retention lock to this specific object for 2 days (for testing — in production you would use years):

    aws s3api put-object-retention \ --bucket yourname-vault-2025 \ --key contracts/legal-contract-2025.txt \ --retention '{"Mode":"GOVERNANCE","RetainUntilDate":"2025-11-23T00:00:00Z"}'

    Replace the date with 2 days from today's date in the same format.

  4. Try to delete the locked object — this should fail:

    aws s3 rm s3://yourname-vault-2025/contracts/legal-contract-2025.txt

    You should see an error: An error occurred (AccessDenied)... — the lock prevented deletion.

    Figure 17: 📸 Deletion blocked by Object Lock — AccessDenied error confirms the lock is active

  5. View the lock details on the object in the S3 console: open the bucket, find the object, click on it, and scroll to the Object Lock section in the Properties tab. You should see the retention mode and retain-until date.

  6. Apply a Legal Hold as well (simulating litigation hold):

    aws s3api put-object-legal-hold \ --bucket yourname-vault-2025 \ --key contracts/legal-contract-2025.txt \ --legal-hold Status=ON

  7. Remove the Legal Hold (simulating case resolution) and then wait for the retention period to expire before cleanup:

    aws s3api put-object-legal-hold \ --bucket yourname-vault-2025 \ --key contracts/legal-contract-2025.txt \ --legal-hold Status=OFF

Cleanup

Wait until the 2-day retention period expires. Then delete all object versions (Object Lock buckets have versioning — you must delete all versions, not just the current object), then delete the bucket. If the retention has not expired, you cannot delete the objects — this is by design.

1. A company stores 10 million user-uploaded images. Users access recent uploads daily but rarely view images older than 6 months. What storage strategy would you design?

💡 Hint

Think about combining storage classes with lifecycle policies. What class fits daily access? What class fits 6-month-old data? What about data that is 2+ years old?

💡 Hint

With versioning: think about what "deleting" actually does in S3 when versioning is on. Without versioning: think about whether any recovery is possible at all.

💡 Hint

Think about which S3 feature is specifically designed to prevent deletion and overwriting. Between Compliance and Governance mode, which one blocks even the root user?

💡 Hint
