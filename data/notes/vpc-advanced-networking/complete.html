🌐 Introduction

Imagine you just moved into a new apartment building. You have your own private floor — no one else can enter without your permission. That's your VPC (Virtual Private Cloud) in AWS. It's your own isolated section of the AWS cloud where you launch your servers, databases, and applications.

But here's where it gets interesting. Once your apartment is set up, you need to answer three important questions:

  • Who is visiting and what are they carrying? → VPC Flow Logs — a security camera system that records all network traffic moving in and out of your VPC.
  • Can my apartment talk privately to my friend's apartment? → VPC Peering — a private tunnel connecting two VPCs so they communicate without going through the public internet.
  • Can I order room service without opening my front door to the public? → VPC Endpoints — a private backdoor that lets your VPC talk directly to AWS services (like S3) without using the internet.

These three features — Flow Logs, Peering, and Endpoints — are the foundation of advanced VPC networking. Together they give you visibility, connectivity, and security. This guide covers all three from scratch, assuming no prior AWS knowledge.

⚡ What you'll learn: By the end of these notes, you'll understand how AWS networks are monitored, connected, and secured — skills directly tested in the AWS Solutions Architect and Cloud Practitioner exams.

☁️ AWS Cloud & VPC Basics (Start Here)

Before diving into advanced topics, let's make sure the foundation is solid. If you've never used AWS before, this section is for you.

What is AWS?

AWS (Amazon Web Services) is a cloud computing platform that provides on-demand IT resources — servers, storage, databases, networking — over the internet, on a pay-as-you-go basis. Instead of buying physical hardware, you rent it from Amazon. You pay only for what you use, and you can scale up or down in minutes.

What is a Server?

A server is just a powerful computer that runs 24/7 and responds to requests. When you visit a website, a server somewhere is sending you that webpage. In AWS, these servers are called EC2 instances (Elastic Compute Cloud). You can launch as many EC2 instances as you need, choose their size (how powerful), and pay only while they're running.

What is a Region and Availability Zone?

AWS has data centers all over the world, organized into Regions. A Region is a geographic area — like US East (Virginia), Asia Pacific (Mumbai), or Europe (Ireland). Each Region contains multiple Availability Zones (AZs), which are physically separate data centers within that Region, designed so a failure in one doesn't affect the others.

Figure 2: AWS Regions contain multiple Availability Zones; your VPC lives within one Region

What is a VPC?

A VPC (Virtual Private Cloud) is your own logically isolated network within AWS, where you have complete control over IP addressing, routing, and security. Think of it like this: AWS is a massive city. A VPC is the private gated community you build inside that city. You decide who can enter, who can leave, and what routes they take.

Every AWS account gets a default VPC automatically created in each Region. You can also create custom VPCs for more control.

CIDR Blocks — Your VPC's Address Range

When you create a VPC, you must define an IP address range for it. This is written in CIDR notation (Classless Inter-Domain Routing). For example: 10.0.0.0/16.

Think of a CIDR block like a zip code area. 10.0.0.0/16 means "all addresses that start with 10.0" — that gives you 65,536 addresses. The /16 is the prefix length — the smaller the number after the slash, the bigger the network (more addresses).

💡 Quick CIDR Reference:

  • /16 = 65,536 addresses (typical VPC size)
  • /24 = 256 addresses (typical subnet size)
  • /32 = exactly 1 address (a single IP)

Subnets — Dividing Your VPC

A subnet is a smaller network carved out of your VPC. A public subnet has a route to the internet via an Internet Gateway; a private subnet has no direct internet access and is used for internal resources like databases.

Internet Gateway

An Internet Gateway (IGW) is a horizontally scaled, redundant VPC component that allows communication between resources in your VPC and the internet. Without an IGW, nothing in your VPC can reach the outside world, and nothing from outside can reach in.

Route Tables

A route table is like a GPS for your VPC. It contains rules (routes) that tell network traffic where to go. Every subnet must be associated with a route table, which controls the routing for that subnet. If a route table has an entry pointing to an Internet Gateway, traffic can reach the internet — making that subnet public.

Security Groups and NACLs

These are the two security layers that control traffic in a VPC:

  • Security Groups: Security Groups are stateful firewalls that operate at the instance (EC2) level — if you allow inbound traffic, the return traffic is automatically allowed.
  • NACLs (Network Access Control Lists): NACLs are stateless firewalls that operate at the subnet level — you must explicitly allow both inbound AND outbound traffic.

Figure 3: NACLs protect subnets; Security Groups protect individual EC2 instances

✅ Remember the layers: Traffic entering your VPC hits the NACL first (subnet level), then the Security Group (instance level). Both must allow the traffic for it to reach your EC2.

📋 VPC Flow Logs

What Are VPC Flow Logs?

Imagine you run a busy office building. You install security cameras at every entrance and exit to record who comes in, who goes out, and whether their access was granted or denied. You don't record what they said or what they carried — just the metadata: who, when, allowed or rejected.

VPC Flow Logs is an AWS feature that captures metadata about the IP traffic flowing to and from network interfaces within your VPC. It does NOT capture the actual content of the traffic — just the details about the connection: source, destination, port, protocol, and whether it was accepted or rejected.

Figure 4: VPC Flow Logs captures network metadata and stores it in CloudWatch Logs or S3

Why Use VPC Flow Logs?

Flow Logs are your network's audit trail. Here's what they're used for:

  • Debugging connectivity issues: If an EC2 instance can't be reached, Flow Logs show whether the traffic was rejected — and by what rule.
  • Security monitoring: Detect unusual traffic patterns, port scanning, or unauthorized access attempts.
  • Compliance: Many regulations require network activity logs to be retained for audit purposes.
  • Troubleshooting Security Groups and NACLs: If you can't connect to a server, Flow Logs tell you exactly where the traffic is being dropped.

What Data Does a Flow Log Record?

Each flow log record captures the following fields for a network connection:

  • Source IP address — where the request originated
  • Destination IP address — where the request is going
  • Source port number — the port used by the sender
  • Destination port number — the port being contacted (e.g., port 80 for HTTP, port 22 for SSH)
  • Protocol — TCP, UDP, or ICMP
  • Action — ACCEPT (traffic was allowed) or REJECT (traffic was blocked)
  • Log status — whether the log was captured successfully

💡 Important: Flow Logs capture metadata only — not the actual packet contents. Think of it like a phone bill: it shows who called whom and for how long, but not what was said.

Three Levels of Flow Log Creation

VPC Flow Logs can be created at three levels: VPC level, subnet level, and network interface level.

  • VPC level: Captures traffic for ALL resources inside the entire VPC. Broadest scope.
  • Subnet level: Captures traffic for all resources within a specific subnet.
  • Network interface level: Captures traffic for one specific resource (e.g., a single EC2 instance, a Load Balancer, or a Lambda function).

Figure 5: Flow Logs can be scoped to a VPC, a subnet, or a single network interface

Where Are Flow Logs Stored?

Flow Logs can be stored in Amazon CloudWatch Logs, Amazon S3, or Amazon Data Firehose.

  • CloudWatch Logs: Best for real-time monitoring and alerting. You can set up alarms on specific patterns (e.g., alert when traffic is repeatedly rejected).
  • S3: Best for long-term storage and cost-efficiency. Use Athena to query the logs later.
  • Amazon Data Firehose: Best for streaming logs to third-party analytics tools in real time.

IAM Permissions for Flow Logs

When you configure Flow Logs to send data to CloudWatch Logs, the Flow Logs service needs permission to write to CloudWatch. You must attach an IAM role to the Flow Log that grants it permission to create log groups and publish log events to CloudWatch Logs. AWS can create this role automatically for you during setup.

This is a key AWS concept: when one AWS service talks to another AWS service, it needs an IAM role to authorize that communication. Flow Logs → CloudWatch: needs IAM role. EC2 → S3: needs IAM role. This pattern repeats across all of AWS.

Using Flow Logs to Debug Connectivity Issues

Here's a practical scenario: Your EC2 instance is running, but you can't SSH into it. How do Flow Logs help?

  1. Check the Flow Log for your EC2's network interface
  2. Look for your connection attempt (your IP → EC2 IP, port 22)
  3. Check the Action column: is it ACCEPT or REJECT?
  4. If REJECT: the Security Group or NACL is blocking port 22 — add an inbound rule allowing SSH
  5. If ACCEPT: traffic reached EC2 but something inside the OS is blocking it — check the firewall inside the instance

✅ Exam Tip: If a flow log shows REJECT, check the Security Group (instance level) and NACL (subnet level). Both must allow the traffic. NACLs are stateless — you need both inbound AND outbound rules.

Capture Interval

Flow Logs have a configurable aggregation interval of either 1 minute or 10 minutes. The 1-minute interval gives more granular visibility but generates more data (and cost). The 10-minute interval is cheaper and sufficient for most use cases.

What Flow Logs Do NOT Capture

Flow Logs have some important limitations to remember for the exam:

  • Traffic to 169.254.169.254 (EC2 instance metadata service) is NOT logged
  • Traffic to 169.254.169.123 (Amazon Time Sync Service) is NOT logged
  • DHCP traffic is NOT logged
  • Traffic to the default VPC router's reserved IP is NOT logged
  • DNS queries resolved by Route 53 Resolver are NOT logged by Flow Logs

❌ Common Mistake: Flow Logs do NOT capture packet contents. They only capture connection metadata. If you need the actual data being transmitted, you need a different tool (e.g., packet capture at the OS level).

🔗 VPC Peering

What is VPC Peering?

Picture two neighboring houses on the same street. Normally, if you want to visit your neighbor, you walk out your front gate, down the public road, and through their front gate. The entire neighborhood can see you walking. That's how VPCs communicate by default — through the public internet.

Now imagine you and your neighbor build a private gate between your two backyards — a direct connection that only you two can use. No one else sees you moving between the houses. That's VPC Peering.

VPC Peering is a private networking connection between two VPCs that allows them to communicate using private IP addresses, without routing traffic through the public internet.

Figure 6: VPC Peering creates a private network path between two VPCs — no internet required

Why Use VPC Peering?

  • Security: Traffic never leaves the AWS network — no exposure to the public internet
  • Low latency: Direct private connection is faster than routing through internet gateways
  • Cost: No data transfer charges for traffic within the same Availability Zone via peering
  • Isolation: You can connect specific VPCs without merging them — they remain separate environments

Same Account vs Different Account, Same Region vs Different Region

VPC Peering is flexible: you can peer VPCs within the same AWS account, across different AWS accounts, within the same Region, or across different Regions (inter-region peering). This makes it useful for multi-account architectures and disaster recovery setups.

💡 Inter-Region Peering: Traffic between VPCs in different regions is encrypted. This is a common exam point — VPC peering across regions provides encrypted private connectivity between your AWS infrastructure in different parts of the world.

Critical Rules for VPC Peering

There are three rules you MUST know for the exam:

Rule 1: No Overlapping CIDR Blocks

The CIDR blocks of the two VPCs being peered must not overlap. If they do, peering will fail.

Think about it this way: if both VPCs have the address range 10.0.0.0/16, AWS can't know which VPC a packet destined for 10.0.1.5 should go to. Ambiguous addresses = no connection possible.

❌ Will Fail: VPC-A = 10.0.0.0/16, VPC-B = 10.0.0.0/16 — overlapping, peering rejected

✅ Will Work: VPC-A = 10.0.0.0/16, VPC-B = 10.1.0.0/16 — different network portions, peering allowed

Rule 2: Route Tables Must Be Updated Manually

Creating a peering connection alone is not enough — you must manually update the route tables in both VPCs to direct traffic toward the peering connection.

Here's what this means: after you create the peering connection, each VPC's subnet route table needs a new entry saying "if traffic is destined for the other VPC's CIDR range, send it through the peering connection." Without this, the two VPCs have a tunnel but no GPS directions to use it.

Figure 7: Both route tables must have entries pointing to the peering connection for traffic to flow

Rule 3: Security Groups and NACLs Still Apply

VPC Peering does not bypass Security Groups or NACLs — all existing security rules still apply to peered traffic.

This means even after peering, if EC2-B's Security Group doesn't allow inbound traffic on port 22 from EC2-A's IP, the SSH connection will still be rejected. Peering changes the route, not the permissions.

The Request-Accept Workflow

Setting up a peering connection follows a two-step handshake process, similar to sending a friend request on social media:

  1. Requester: The owner of VPC-A sends a peering request to VPC-B, specifying the VPC ID of the target
  2. Acceptor: The owner of VPC-B logs into the VPC dashboard and accepts the peering request
  3. Once accepted, the peering connection status changes to Active
  4. Both owners then update their respective route tables

If the VPCs are in different AWS accounts, the acceptor must log into the second account to accept. If they're in different regions, the acceptor must switch to the correct region in their console.

VPC Peering is NOT Transitive

This is one of the most commonly tested VPC peering concepts.

VPC Peering is non-transitive: if VPC-A is peered with VPC-B, and VPC-B is peered with VPC-C, VPC-A cannot communicate with VPC-C through VPC-B.

Think of it like roads: if Road A connects Town A to Town B, and Road B connects Town B to Town C, you cannot drive from Town A to Town C using just these roads — there's no through-passage. You'd need a direct Road C connecting Town A and Town C.

Figure 8: Peering is non-transitive — A→B and B→C does NOT give A→C. Direct peering required for every pair.

❌ Common Exam Trap: If the question says "VPC-A is peered with VPC-B, and VPC-B is peered with VPC-C — can VPC-A reach VPC-C?" The answer is NO — not without a direct peering connection between A and C.

When VPC Peering Falls Short: Transit Gateway

Peering works great for a few VPCs, but if you have 10 or 20 VPCs that all need to talk to each other, you'd need to create peering connections between every pair (this is called a mesh topology) — which becomes complex quickly.

For connecting many VPCs at scale, AWS recommends Transit Gateway instead of VPC Peering — it acts as a central hub that all VPCs connect to, supporting transitive routing. Transit Gateway is a more advanced topic covered in a future session.

✅ Exam Rule of Thumb: For connecting 2–3 VPCs → use VPC Peering. For connecting 4+ VPCs → consider Transit Gateway.

🔌 VPC Endpoints

What Are VPC Endpoints?

Here's a scenario: your EC2 instance is in a private subnet with no internet access — good for security. But now you need that EC2 to upload files to Amazon S3. Normally, traffic to S3 would go through the internet gateway, which means your private server must be made public. That defeats the purpose of a private subnet.

VPC Endpoints solve this elegantly. Imagine a private staff entrance at a shopping mall. Regular customers enter through the main public entrance. But mall employees use a private back door that goes directly to the storage room — no need to walk through the public entrance at all.

A VPC Endpoint is a private connection between your VPC and supported AWS services (like S3 and DynamoDB) that does not require an internet gateway, NAT device, VPN connection, or AWS Direct Connect. Traffic between your VPC and the AWS service stays entirely within the AWS network.

Figure 9: VPC Endpoint routes traffic to S3 privately — no internet gateway needed

Two Types of VPC Endpoints

There are two types of VPC Endpoints: Gateway Endpoints and Interface Endpoints. Knowing which to use for which service is a common exam question.

1. Gateway Endpoint

A Gateway Endpoint is a route table entry that directs traffic destined for a specific AWS service through a private gateway, without using the internet. It is supported only for S3 and DynamoDB.

How it works: when you create a Gateway Endpoint, AWS automatically adds a special route to your route table. Any traffic destined for the S3 or DynamoDB service is redirected through the endpoint instead of the internet gateway. You don't need to modify your application code — it's transparent.

Key characteristics:

  • Available only for S3 and DynamoDB
  • Free — no hourly charges
  • Implemented as a route table entry
  • Does NOT require a private IP address in your subnet
  • Does NOT use AWS PrivateLink

2. Interface Endpoint

An Interface Endpoint is an elastic network interface with a private IP address that serves as an entry point for traffic destined for a supported AWS service. It is powered by AWS PrivateLink.

Interface Endpoints work with a much broader range of services: EC2 API, Systems Manager (SSM), CloudWatch, Secrets Manager, SNS, SQS, Kinesis, and hundreds more.

Key characteristics:

  • Works with most AWS services (not just S3 and DynamoDB)
  • Costs money — charged per hour and per GB processed
  • Creates an ENI (Elastic Network Interface) with a private IP in your subnet
  • Powered by AWS PrivateLink
  • Supports security groups to control access

Figure 10: Gateway Endpoint vs Interface Endpoint — key differences for the exam

Endpoint Policies

You can attach an endpoint policy to a VPC Endpoint to control which AWS resources, principals, and actions are allowed through the endpoint. For example, you could restrict an S3 Gateway Endpoint to only allow access to a specific S3 bucket — even if your EC2 has full S3 permissions, it can only reach that one bucket through the endpoint.

When to Use VPC Endpoints

  • Regulatory compliance: Data must never leave the AWS network — use endpoints to ensure S3/DynamoDB traffic stays private
  • Security: Private subnets with no internet access still need to reach AWS services (SSM, CloudWatch, S3)
  • Cost optimization: Avoid NAT Gateway data processing charges for S3 and DynamoDB traffic (use Gateway Endpoints, which are free)
  • Performance: Lower latency for S3/DynamoDB access compared to routing through NAT and internet gateways

✅ Cost-Saving Tip: If your EC2 instances frequently access S3 and currently route through a NAT Gateway, switching to a Gateway Endpoint is free and eliminates NAT Gateway data processing charges ($0.045/GB). This is a common cost optimization question in the exam.

Connecting to Private EC2 Using SSM (Without Bastion Host)

This is a practical topic that comes up in hands-on labs. When your EC2 is in a private subnet (no internet, no public IP), how do you connect to it for management? Options:

  1. Bastion Host: A public EC2 instance you SSH into first, then SSH from there to your private EC2. Works but adds cost and complexity.
  2. AWS Systems Manager Session Manager (SSM): A service that lets you open a browser-based shell directly to your EC2 — no SSH keys, no bastion host, no port 22 needed.

For SSM to work on a private EC2, you need:

  • An IAM role on the EC2 with AmazonSSMManagedInstanceCore policy
  • The SSM agent installed (pre-installed on Amazon Linux 2, Ubuntu 20.04+, and Windows AMIs)
  • Either internet access OR an Interface Endpoint for SSM (com.amazonaws.region.ssm) in the same VPC

💡 In the Session: The instructor demonstrated creating a private EC2 with an SSM IAM role and connecting via Session Manager instead of SSH. If SSM isn't working, the most common fixes are: (1) check the IAM role has the correct policy, (2) reboot the instance, (3) verify the SSM agent is running.

🏗️ How Flow Logs, Peering, and Endpoints Work Together

These three features aren't independent — they're designed to be used together in real architectures. Here's a typical enterprise scenario:

A company has two VPCs: a Production VPC (where applications run) and a Logging VPC (where all monitoring and security tools live). Here's how all three features are used:

  1. VPC Peering: The Production and Logging VPCs are peered so they can communicate privately. Security tools in the Logging VPC can monitor resources in Production without using the internet.
  2. VPC Flow Logs: Enabled at the VPC level on the Production VPC, with logs stored in CloudWatch Logs. The security team in the Logging VPC monitors for suspicious traffic patterns.
  3. VPC Endpoint: Both VPCs use Gateway Endpoints for S3 and DynamoDB access, ensuring application data and logs never traverse the public internet.

Figure 11: Real-world architecture combining VPC Peering, Flow Logs, and VPC Endpoints

⚡ Architecture Pattern: This three-layer approach (visibility + connectivity + private access) is the foundation of AWS's Well-Architected Framework security pillar. Expect exam questions that test whether you know which tool to use for which problem.

🎯 Exam Cheat Sheet

VPC Flow Logs — Key Exam Facts

  • Flow Logs capture network metadata only — not packet contents
  • Three levels: VPC, subnet, network interface
  • Storage: CloudWatch Logs, S3, or Amazon Data Firehose
  • Capture interval: 1 minute or 10 minutes
  • Requires IAM role when sending to CloudWatch Logs
  • Does NOT log: metadata service (169.254.169.254), DHCP, DNS via Route 53 Resolver
  • Use case: debug Security Group/NACL issues, security monitoring, compliance

VPC Peering — Key Exam Facts

  • CIDR blocks of peered VPCs must not overlap
  • Works: same account, different accounts, same region, different regions
  • Route tables must be manually updated in BOTH VPCs
  • Security Groups and NACLs still apply
  • Peering is non-transitive — A↔B and B↔C does NOT give A↔C
  • Two-step setup: Request → Accept → Update route tables
  • Status must be Active for traffic to flow

VPC Endpoints — Key Exam Facts

  • Gateway Endpoint: S3 and DynamoDB only, free, uses route table
  • Interface Endpoint: most AWS services, uses ENI, powered by PrivateLink, has cost
  • Both allow private connectivity without internet, NAT, or VPN
  • Endpoint policies can restrict access to specific resources
  • Gateway Endpoint = free alternative to NAT Gateway for S3/DynamoDB

📝 Overall Summary

  • VPC: Your private isolated network in AWS, with full control over IP ranges, subnets, routing, and security.
  • Public vs Private Subnet: Public subnets have internet access via an Internet Gateway; private subnets are isolated from the internet.
  • Security Groups (stateful) vs NACLs (stateless): Both control traffic but at different levels — instance vs subnet. NACLs require explicit rules for both inbound and outbound.
  • VPC Flow Logs: Network traffic metadata recorder. Captures source/destination IP, port, protocol, and ACCEPT/REJECT status. Stored in CloudWatch Logs, S3, or Firehose. Does NOT capture packet contents.
  • Flow Log Levels: Can be created at VPC, subnet, or network interface level. Use for debugging connectivity, security auditing, and compliance.
  • VPC Peering: Private tunnel between two VPCs using private IPs. No internet required. Works across accounts and regions. Non-transitive — every pair needs its own connection.
  • Peering Rules: No overlapping CIDRs. Must manually update route tables. Security Groups and NACLs still apply.
  • VPC Endpoints: Private backdoor from your VPC to AWS services — no internet, NAT, or VPN needed.
  • Gateway Endpoint: Free, for S3 and DynamoDB only. Implemented as a route table entry.
  • Interface Endpoint: Paid, for most AWS services. Creates an ENI with private IP. Powered by PrivateLink.
  • Combined use: Flow Logs (visibility) + Peering (connectivity) + Endpoints (private access) = secure, well-architected AWS network.

Project 1: Set Up VPC Flow Logs and Analyze Traffic

🎯 Objective: Enable VPC Flow Logs on your default VPC, generate some traffic, and read the logs in CloudWatch.

⏱️ Time: 30–45 min

💰 Cost: Free tier (CloudWatch Logs may incur minor charges after free tier)

  1. Open the AWS Console and navigate to VPC using the search bar at the top.

    📸 Screenshot: Search for VPC in the AWS Console

  2. In the left sidebar, click Your VPCs. Select your default VPC by clicking its checkbox.

    📸 Screenshot: Select the default VPC from the list

  3. Scroll down and click the Flow logs tab. Click Create flow log.

    📸 Screenshot: Flow logs tab on the VPC details page

  4. Fill in the form: Name = my-vpc-flow-log, Filter = All, Maximum aggregation interval = 1 minute, Destination = Send to CloudWatch Logs.

  5. For Destination log group, go to CloudWatch in a new tab: CloudWatch → Log groups → Create log group. Name it vpc-flow-logs-group. Return and select this group.

  6. For IAM role, select Create new role — AWS will auto-create a role with the correct permissions.

  7. Click Create flow log. You should see a success message.

    📸 Screenshot: Flow log created successfully with Active status

  8. Launch a small EC2 instance (t3.micro, Amazon Linux 2, in the default VPC). Wait 2–3 minutes after launch.

  9. Go to CloudWatch → Log groups → vpc-flow-logs-group. Click on the latest log stream. You should see flow log records showing traffic to and from your EC2 instance.

    📸 Screenshot: Flow log records in CloudWatch showing ACCEPT and REJECT entries

  10. Cleanup: Delete the flow log (VPC → select VPC → Flow logs tab → select log → Actions → Delete), terminate the EC2 instance, and optionally delete the CloudWatch log group.

Project 2: Connect Two VPCs with VPC Peering

🎯 Objective: Create a custom VPC, peer it with the default VPC, and verify that EC2 instances in both VPCs can ping each other using private IP addresses.

⏱️ Time: 45–60 min

💰 Cost: Free tier (EC2 instances — stop/terminate after the project)

💰 Cost Note: Two running EC2 instances consume free tier hours. Terminate both instances immediately after completing the project to avoid charges.

  1. Create a new custom VPC: VPC → Create VPC. Set IPv4 CIDR to 10.1.0.0/16 (must be different from default VPC's 172.31.0.0/16).

  2. Create a subnet in the new VPC: Subnets → Create subnet. VPC = your new VPC. CIDR = 10.1.1.0/24.

  3. Create an Internet Gateway, attach it to your new VPC, and update the route table for the new subnet to route 0.0.0.0/0 to the IGW (this makes it a public subnet so you can connect to test).

  4. Create the peering connection: Peering connections → Create peering connection. Name = default-to-custom. Requester VPC = your custom VPC. Acceptor VPC = default VPC.

    📸 Screenshot: Creating a peering connection between two VPCs

  5. Accept the request: stay on the Peering connections page, select the pending connection, click Actions → Accept request. Status changes to Active.

    📸 Screenshot: Peering connection status is Active after acceptance

  6. Update route table for the custom VPC subnet: add a route with Destination = 172.31.0.0/16 (default VPC CIDR), Target = peering connection ID.

  7. Update route table for the default VPC: add a route with Destination = 10.1.0.0/16 (custom VPC CIDR), Target = same peering connection ID.

  8. Launch EC2-A in the default VPC and EC2-B in the custom VPC. Ensure both Security Groups allow ICMP (ping) from each other's CIDR range.

  9. SSH or Session Manager into EC2-A. Run: ping [private IP of EC2-B]. You should see replies — proving private communication via peering.

    📸 Screenshot: Successful ping between peered VPCs using private IP addresses

  10. Cleanup: Terminate both EC2 instances → delete peering connection → delete custom VPC (this also deletes the subnet, route table, IGW).

Project 3: Access S3 from a Private EC2 Using Gateway Endpoint

🎯 Objective: Launch an EC2 in a private subnet (no internet access), create an S3 Gateway Endpoint, and confirm the EC2 can list S3 buckets without an internet connection.

⏱️ Time: 40–50 min

💰 Cost: Gateway Endpoint is free. EC2 uses free tier. Stop instance after the project.

  1. Launch an EC2 instance in a private subnet of your default VPC. Give it an IAM role with AmazonSSMManagedInstanceCore and AmazonS3ReadOnlyAccess policies. Do NOT assign a public IP.

  2. In the VPC route table for that subnet, remove the Internet Gateway route if present (to simulate a true private subnet).

  3. Try to connect to the EC2 via Session Manager. Then try running aws s3 ls — it should time out because there's no internet path.

  4. Create the Gateway Endpoint: VPC → Endpoints → Create endpoint. Name = s3-gateway-endpoint. Service category = AWS services. Search for S3 and select the Gateway type endpoint.

    📸 Screenshot: Creating an S3 Gateway Endpoint

  5. Select your VPC and the route table for the private subnet. Click Create endpoint. AWS automatically adds a route to the route table.

    📸 Screenshot: Route table updated automatically with S3 endpoint route after creation

  6. Return to Session Manager and run aws s3 ls again. This time it should succeed and list your S3 buckets — all without internet access!

    📸 Screenshot: aws s3 ls succeeds from private EC2 using VPC Endpoint

  7. Cleanup: Delete the endpoint → terminate the EC2 instance → restore route table if needed.

Project 4 — Level 2: Break the Network Lab (Cause & Effect)

🎯 Objective: Deliberately break network rules one at a time and use Flow Logs to diagnose exactly what failed and why. This is how real cloud engineers debug connectivity issues.

⏱️ Time: 60–75 min

💰 Cost: Free tier (2 EC2 instances — stop after the project)

⚡ Mindset shift: You're not following steps anymore. You're running experiments. Each experiment has a prediction → action → observation → explanation. Write down your prediction before each test.

📋 Setup (do this first)

  • ✅ Create one VPC: CIDR 10.10.0.0/16
  • ✅ Create a public subnet: 10.10.1.0/24 with Internet Gateway and route table
  • ✅ Create a private subnet: 10.10.2.0/24 with no IGW route
  • ✅ Launch EC2-Public in public subnet — Amazon Linux 2, t3.micro, assign public IP, Security Group allows SSH (port 22) inbound from your IP and all outbound
  • ✅ Launch EC2-Private in private subnet — Amazon Linux 2, t3.micro, no public IP, Security Group allows ICMP (ping) and SSH inbound from 10.10.0.0/16
  • ✅ Enable VPC Flow Logs on the VPC, sending to CloudWatch Logs (from Project 1 steps)

Experiment 1: Remove NACL Outbound Rule

🔬 What we're testing: NACLs are stateless — removing the outbound rule breaks return traffic even for allowed inbound connections.

  1. SSH into EC2-Public from your laptop. Then from EC2-Public, try to ping EC2-Private:

    ping 10.10.2.X   # replace X with EC2-Private's private IP

    Expected: ping succeeds. Note this in your observations.

    📸 Screenshot: Baseline ping succeeds before NACL change

  2. Go to VPC → Subnets → Private Subnet → Network ACL → Edit inbound rules. Remove the rule that allows ICMP (All ICMP - IPv4). Keep everything else. Save.

  3. Prediction: What do you think will happen to the ping? Write it down before testing.

  4. Run the ping again from EC2-Public to EC2-Private. Observe the result.

  5. Wait 1–2 minutes, then go to CloudWatch Logs and find the flow log for this traffic. What action does it show?

    📸 Screenshot: Flow Log showing REJECT after removing NACL rule

  6. Answer these questions:

    • Was the action ACCEPT or REJECT?
    • Was it the NACL or the Security Group that caused it? How do you know?
    • If NACL is stateless, what happens if you only remove the OUTBOUND rule but keep inbound — does ping still work?

  7. Restore the NACL rule before the next experiment.

Experiment 2: Remove Security Group Inbound Rule

🔬 What we're testing: Security Groups are stateful — removing inbound blocks the connection but the Flow Log action tells you exactly which layer said REJECT.

  1. From EC2-Public, SSH into EC2-Private (Security Group allows it from 10.10.0.0/16). Confirm the connection works:

    ssh -i your-key.pem ec2-user@10.10.2.X

  2. Now go to EC2-Private's Security Group → Edit inbound rules → Remove the SSH (port 22) rule. Save.

  3. Prediction: Will the SSH attempt now be ACCEPT or REJECT in Flow Logs? Will it be caught by SG or NACL?

  4. Try to SSH from EC2-Public to EC2-Private again. It should hang or fail.

  5. Check Flow Logs in CloudWatch. Look for the SSH attempt (port 22) — is the action ACCEPT or REJECT?

    📸 Screenshot: Flow Log REJECT on port 22 after removing SG rule

  6. Key insight to note: Flow Logs show REJECT for both NACL and SG blocks. The only way to tell which one caused it is by checking BOTH — process of elimination. If NACL allows it but SG rejects it, the log shows REJECT. Remove the SG and it's ACCEPT.

  7. Restore the Security Group rule.

Experiment 3: Break the Route Table

🔬 What we're testing: Route tables are the GPS of the VPC. Remove a route and traffic has no path — it doesn't even reach the security layers to be rejected.

  1. From EC2-Public, confirm you can reach EC2-Private by ping (after restoring rules from Experiments 1 & 2).

  2. Go to VPC → Route Tables → Public Subnet Route Table → Routes → Edit routes. Remove the 0.0.0.0/0 → Internet Gateway route. Save.

  3. Prediction: Will Flow Logs show a REJECT? Or will there be no log entry at all?

  4. Try to SSH from your laptop to EC2-Public. What happens?

  5. Check Flow Logs. Do you see any log entries for your failed SSH attempt?

    📸 Screenshot: No flow log entry when route is missing — traffic never enters VPC

  6. Critical learning: No Flow Log entry ≠ traffic reached and was rejected. It means traffic never arrived. A missing route is invisible to Flow Logs because there's no network interface capturing it. This is a key debugging distinction.

  7. Cleanup: Restore the route, then terminate both EC2 instances.

Project 5 — Level 3: Two-VPC Communication Debug Lab

🎯 Objective: Set up an App server in VPC-A and a DB server in VPC-B connected via peering. Simulate a failed database connection and debug it using only Flow Logs, route tables, and Security Groups — exactly like a real interview scenario or production incident.

⏱️ Time: 75–90 min

💰 Cost: Free tier (2 EC2 instances — stop after the project)

💰 Cost Note: Two running EC2 instances use free tier hours. Stop both immediately after completing the project.

📋 Setup

  • ✅ VPC-A (App): CIDR 10.0.0.0/16, one public subnet 10.0.1.0/24, Internet Gateway attached
  • ✅ VPC-B (DB): CIDR 10.1.0.0/16, one private subnet 10.1.1.0/24, no IGW
  • ✅ EC2-App in VPC-A public subnet — Amazon Linux 2, SSM role, Security Group allows all outbound
  • ✅ EC2-DB in VPC-B private subnet — Amazon Linux 2, SSM role, Security Group allows MySQL port 3306 inbound from 10.0.0.0/16
  • ✅ VPC Peering established between VPC-A and VPC-B (status: Active)
  • ✅ Flow Logs enabled on both VPCs, sending to CloudWatch Logs
  • ✅ Install netcat on EC2-App for port testing: sudo yum install -y nc

Debug Scenario 1: Missing Route Table Entry

  1. Connect to EC2-App via Session Manager. Try to reach EC2-DB on port 3306:

    nc -zv 10.1.1.X 3306   # replace X with EC2-DB private IP

    It should fail. Your job: figure out why using only the three tools (Flow Logs, route tables, SG).

  2. Step 1 — Check Flow Logs: Go to CloudWatch Logs for VPC-A. Do you see any log entries for traffic from EC2-App to 10.1.1.X on port 3306?

    📸 Screenshot: No flow log entry from VPC-A — missing route, traffic never left the subnet

  3. Step 2 — Check Route Tables: Go to VPC-A's route table. Is there a route for 10.1.0.0/16 pointing to the peering connection? If not — that's your bug. The traffic never left VPC-A's subnet.

  4. Fix: Add the missing route: Destination = 10.1.0.0/16, Target = peering connection ID. Also add the reverse route in VPC-B: Destination = 10.0.0.0/16, Target = same peering connection.

  5. Run the netcat test again. Does it work now?

Debug Scenario 2: Security Group Blocking Port 3306

  1. Now with routes in place, try again:

    nc -zv 10.1.1.X 3306

  2. If it still fails — check Flow Logs in VPC-B. Do you see the traffic arriving at EC2-DB's ENI? What is the action — ACCEPT or REJECT?

    📸 Screenshot: Flow Log in VPC-B shows traffic arriving but REJECT on port 3306 — SG is blocking

  3. If you see REJECT in VPC-B's Flow Logs, the traffic IS arriving (routing works) but is being blocked. Check EC2-DB's Security Group inbound rules. Is port 3306 allowed from 10.0.0.0/16?

  4. Fix: Add inbound rule to EC2-DB's Security Group: Type = MySQL/Aurora (port 3306), Source = 10.0.0.0/16. Test again.

  5. Now the netcat test should show: Connection to 10.1.1.X 3306 port [tcp/mysql] succeeded!

    📸 Screenshot: Successful port 3306 connection and ACCEPT in Flow Logs

Debug Scenario 3: Wrong CIDR in Route (Advanced)

  1. Edit VPC-A's route table: change the route for VPC-B from 10.1.0.0/16 to 10.2.0.0/16 (intentionally wrong CIDR). Save.

  2. Run the netcat test again. It will fail.

  3. Check Flow Logs. Are there any entries? What does the absence of logs tell you about where the failure is?

  4. Debugging logic: No log in VPC-A = traffic never left VPC-A's subnet. That points to routing. No log in VPC-B = traffic never arrived. Again routing. If you see logs in VPC-A but not VPC-B = traffic left but didn't arrive = wrong destination route.

  5. Fix the route back to 10.1.0.0/16. Confirm connectivity.

  6. Cleanup: Delete peering connection → terminate EC2 instances → delete both custom VPCs.

Project 7 — Level 5: Security Monitoring with Athena

🎯 Objective: Send Flow Logs to S3, query them with Amazon Athena, simulate suspicious traffic, and identify the attacker's IP — exactly like a cloud security analyst would.

⏱️ Time: 75–90 min

💰 Cost: S3 storage (minimal), Athena per-query charges (~$0.005 per query), EC2 free tier. Stay under $1 total.

  1. Create an S3 bucket for logs: e.g. my-vpc-flowlogs-YYYY. Go to VPC → Flow Logs → Create. Destination = S3, enter the bucket ARN. Enable for your VPC.

    📸 Screenshot: Flow Log configured to deliver to S3 bucket

  2. Launch a public EC2 instance. Generate diverse traffic patterns:

    • SSH from your laptop (this will be ACCEPT)
    • Try connecting to port 8080 from your browser — it should be rejected (port not open in SG)
    • Try connecting to port 3389 (RDP) — rejected
    • From the EC2, run: curl http://checkip.amazonaws.com (outbound HTTP)

  3. Wait 10–15 minutes for logs to land in S3. They appear under the bucket in a partition path like AWSLogs/ACCOUNT-ID/vpcflowlogs/REGION/YYYY/MM/DD/.

  4. Set up Athena: Go to Athena → Query editor. Create a database and table mapped to your S3 flow log data. Use this DDL:

    CREATE EXTERNAL TABLE IF NOT EXISTS vpc_flow_logs (
  version int,
  account_id string,
  interface_id string,
  srcaddr string,
  dstaddr string,
  srcport int,
  dstport int,
  protocol bigint,
  packets bigint,
  bytes bigint,
  start bigint,
  end bigint,
  action string,
  log_status string
)
ROW FORMAT DELIMITED FIELDS TERMINATED BY ' '
LOCATION 's3://YOUR-BUCKET/AWSLogs/ACCOUNT-ID/vpcflowlogs/REGION/'
TBLPROPERTIES ("skip.header.line.count"="1");

    📸 Screenshot: Athena table created for VPC Flow Logs in S3

  5. Run these queries and record the results:

    All rejected traffic:

    SELECT srcaddr, dstaddr, dstport, action, count(*) as attempts
FROM vpc_flow_logs
WHERE action = 'REJECT'
GROUP BY srcaddr, dstaddr, dstport, action
ORDER BY attempts DESC
LIMIT 20;

    Identify any IP with more than 5 rejected attempts (potential port scanner):

    SELECT srcaddr, count(*) as reject_count
FROM vpc_flow_logs
WHERE action = 'REJECT'
GROUP BY srcaddr
HAVING count(*) > 5
ORDER BY reject_count DESC;

    📸 Screenshot: Athena query results showing REJECT patterns by source IP

  6. From the results, answer:

    • Which ports are most frequently targeted by REJECT?
    • Is any external IP hitting multiple ports? (That's port scanning behaviour.)
    • What would your next step be if you found a suspicious IP?

  7. Cleanup: Drop the Athena table, delete Flow Logs, delete S3 bucket contents and bucket, terminate EC2.

Project 8 — Level 6: Auto-Remediation System (Preview)

🎯 Objective: Understand the architecture of a self-defending network — one that automatically blocks a suspicious IP address when Flow Logs detect repeated rejected connections. This project gives you the full picture; some components (Lambda, CloudWatch Metric Filters) are advanced topics covered in future sessions.

⚡ What you'll build conceptually: Flow Logs → CloudWatch → Metric Filter (count REJECTs per IP) → CloudWatch Alarm (threshold crossed) → Lambda function (auto-adds NACL deny rule for that IP). This is real cloud security automation used in production.

Figure 12: Auto-remediation pipeline — from Flow Log detection to automatic IP block

Here is what each component does in this pipeline:

  • Flow Logs → CloudWatch Logs: All network rejections are captured in real time (you've already done this)
  • CloudWatch Metric Filter: A filter pattern that counts how many REJECT events come from each unique source IP per minute. You define the pattern: [version, accountId, interfaceId, srcAddr, dstAddr, srcPort, dstPort, protocol, packets, bytes, start, end, action="REJECT", logStatus]
  • CloudWatch Alarm: Fires when the REJECT count from a single IP exceeds your threshold (e.g., 10 rejects in 1 minute)
  • Lambda Function: Triggered by the alarm. Reads the offending IP from the alarm context, then calls the AWS API to add a DENY rule to your VPC NACL for that IP address

Part you CAN do right now — create the Metric Filter:

  1. Go to CloudWatch → Log groups → your flow log group → Metric filters → Create metric filter.

  2. Filter pattern:

    [version, accountId, interfaceId, srcAddr, dstAddr, srcPort, dstPort, protocol, packets, bytes, start, end, action="REJECT", logStatus]

  3. Metric namespace: VPCFlowLogs. Metric name: RejectedConnections. Metric value: 1.

    📸 Screenshot: CloudWatch Metric Filter for counting REJECT events

  4. Create a CloudWatch Alarm on this metric: threshold = 10 rejections in 1 minute. Action = SNS notification to your email for now (Lambda trigger comes in a future session).

    📸 Screenshot: CloudWatch Alarm configured to alert on REJECT spike

  5. Generate rejected traffic (try connecting on blocked ports from your laptop). Verify the alarm transitions to IN ALARM state and you receive an email.

💡 Complete the Lambda auto-block portion after covering Lambda in a future session. Full implementation guide: AWS Automated Security Response and CloudWatch Alarms with Lambda.

Cleanup: Delete metric filter → delete alarm → delete SNS topic → delete Flow Log.

Project 9 — Level 7: Chaos Networking Lab (Failure Testing)

🎯 Objective: Intentionally break a running multi-VPC setup by disabling components one at a time, observe the impact through Flow Logs, and practice the recovery procedure. This is how SRE (Site Reliability Engineering) teams build resilience.

⏱️ Time: 60–75 min

💰 Cost: Free tier (2 EC2 instances — stop immediately after)

⚡ SRE mindset: In real jobs, things break in production. The engineer who stays calm, follows a systematic detection-and-recovery process, and can explain what happened is the one who gets promoted. This project trains exactly that.

📋 Setup

  • ✅ Use the two-VPC setup from Project 5 (VPC-A App + VPC-B DB) with peering active and both EC2s running
  • ✅ Flow Logs enabled on both VPCs
  • ✅ Confirm baseline: nc -zv 10.1.1.X 3306 succeeds from EC2-App before starting

Chaos 1: Delete Route Table Entry Mid-Traffic

  1. Start a continuous ping from EC2-App to EC2-DB: ping -i 0.5 10.1.1.X (ping every 0.5 seconds).

  5. Recovery: Re-add the route. How long until ping resumes? Is it instant or delayed?

  1. From EC2 with S3 endpoint active, start a continuous S3 list in a loop:

    while true; do aws s3 ls; sleep 2; done

  3. Check Flow Logs — do you see a REJECT, or no entry at all? Why?

  6. Cleanup: Terminate all EC2 instances → delete peering → delete custom VPCs.

🤔 Reflection Questions

1. Your EC2 instance can't connect to an RDS database in the same VPC. You check the Flow Logs and see the traffic action is REJECT. What are the two things you should check first?

💡 Hint

Think about the two layers of network security in a VPC — one at the instance level, one at the subnet level. One is stateful, one is stateless.

2. A company has three VPCs — Dev, Staging, and Production. They want all three to communicate with each other privately. How many peering connections do they need? Draw the connections mentally.

💡 Hint

Remember: peering is non-transitive. Every pair that needs to communicate requires its own connection. Count the pairs: Dev-Staging, Dev-Prod, Staging-Prod.

3. You want your private EC2 instance to access both S3 and the SSM service without internet access. What type of endpoint do you need for each, and why?

💡 Hint

S3 has a special type of endpoint that's free. SSM is not S3 or DynamoDB, so it needs a different type of endpoint that creates a network interface.

4. VPC-A (CIDR: 10.0.0.0/16) and VPC-B (CIDR: 10.0.0.0/16) — can you create a peering connection between them? Why or why not?

💡 Hint

Think about what happens when a packet arrives destined for 10.0.1.5 — which VPC should it go to? AWS can't know, so it refuses the ambiguity at the start.

5. A colleague says "We created the VPC peering connection and it shows Active, but the two EC2 instances still can't talk to each other." What step did they most likely miss?

💡 Hint

The peering connection is the tunnel, but you also need GPS directions telling traffic to use that tunnel. Look at what controls traffic routing in a VPC.

6. You are designing an architecture where a Lambda function in a private VPC needs to call DynamoDB. What's the most cost-effective solution to avoid using the internet?

💡 Hint

DynamoDB is one of only two services that have a free type of endpoint. Which type is it?

7. What is the difference between VPC Flow Logs capturing traffic at the VPC level vs the network interface level? When would you choose each?

💡 Hint

Think about scope and volume. VPC level captures everything — all resources. Network interface level is surgical — just one specific resource. When debugging a specific server vs. auditing the entire network.
