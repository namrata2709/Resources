🚀 Introduction

Imagine you've just finished writing an application. It works perfectly on your laptop. But when your colleague runs it, it crashes — different operating system, different libraries, different environment. This is known as the classic "works on my machine" problem, and it has haunted software teams for decades.

This is exactly the problem that containerization solves. And to manage those containers at scale, we use an orchestration tool called Kubernetes, which automates deployment, scaling, and management of containerized applications.

Figure 1: Evolution from Physical Servers → Virtualization → Containers → Kubernetes

In this session, we also explore CI/CD pipelines — the backbone of modern software delivery — and how Docker containers plug into that pipeline to enable fast, reliable, automated deployments.

💡 Why this matters: Docker and Kubernetes are among the most in-demand skills in cloud and DevOps roles. Understanding these concepts makes you immediately more hireable and better equipped to work in any modern software team.

⚙️ DevOps & Agile — Quick Recap

Before we dive into containers, it helps to remember why DevOps exists. In a traditional software team, developers would write code for weeks, then hand it to a testing team, who would test for more weeks, then hand it to operations to deploy. By the time a bug was found, the developer had already forgotten the code they wrote. Feedback was slow, expensive, and painful.

DevOps combines development and operations into a single continuous workflow, with the goal of automation, collaboration, and efficiency.

Figure 2: The Three Core Principles of DevOps

When combined with Agile methodology, something powerful happens: developers make small code changes daily, those changes are tested automatically within hours, and the entire team gets rapid feedback. The developer pushes code, CI/CD triggers automatically, the code is compiled, tested, and made ready for deployment — all within the same day.

✅ Key Principle: Agile + DevOps = small, frequent releases with automated testing. This dramatically reduces the risk of shipping broken software.

🗂️ Git & GitHub — Version Control

Before we can understand CI/CD pipelines, we need to understand where the code lives and how it's managed. Think of it like Google Docs version history — but for code, and far more powerful.

What is Git?

Git is a distributed version control system (DVCS) that tracks changes to files over time, allowing developers to maintain a complete history of all code modifications. You install Git on your local machine, and it watches a folder called a repository.

Think of a Git repository like a filing cabinet with a perfect memory. Every time you make changes, you can create a labelled snapshot (a "version") of the entire cabinet. You can always go back to any previous snapshot.

Figure 3: Git Workflow — Working Directory → Staging → Local Repo → Remote Repo

Branching Strategy

Developers never push code directly to the main branch. They create a feature branch for their work and raise a Pull Request (PR) to merge changes into main.

Here's why: the main branch is like a production environment. If everyone pushed directly to it, a single developer's mistake could break the entire application for the whole team. Feature branches give each developer a safe sandbox to work in.

💡 Source Code Management (SCM) Tools: Git is the local tool. The remote platform can be GitHub, GitLab, BitBucket, or in AWS — AWS CodeCommit. They all work with Git commands.

⚡ Pull Request (PR): A formal request to merge a feature branch into main. A code reviewer (team lead) reviews the code, checks CI test results, and approves or rejects the merge. Only after approval does the code enter the main branch.

🔄 CI/CD Pipeline — Continuous Integration & Delivery

Imagine an assembly line in a car factory. Each station has a specific job — attach the wheels, paint the body, test the brakes. Every car goes through every station automatically. No car reaches the showroom without passing every quality check.

A CI/CD pipeline is the software equivalent of that assembly line. Every code change goes through a series of automated stages before it is allowed to deploy.

Figure 4: Complete CI/CD Pipeline — From Code Push to Deployment

What is CI — Continuous Integration?

Continuous Integration (CI) is the practice of automatically building and testing code every time a developer pushes a change, ensuring that the codebase remains stable and integration bugs are caught early.

The CI pipeline triggers automatically in two situations: when code is pushed to main, or when a Pull Request is created or updated.

CI Pipeline Stages

Stage 1 — Checkout

The CI tool (e.g., Jenkins) uses webhooks to detect that code has changed in GitHub. It then pulls (checks out) the latest code from the relevant branch.

Stage 2 — Compile / Build

Compiling converts your source code into an executable format that the system can understand and run. Computers cannot directly run Python, Java, or JavaScript files — they need a compiled or built version.

LanguageBuild Tool
JavaMaven
Node.js / JavaScriptNPM
PythonPIP

Stage 3 — Static Code Analysis (Optional)

Static code analysis examines code without running it, looking for bugs, code smells, security vulnerabilities, and poor coding practices. The most popular tool for this is SonarQube.

  • Bugs: Logic errors in code
  • Code smells: Poor syntax, bad structure, not following conventions
  • Security issues: Hardcoded passwords, access keys exposed in code

❌ Common Mistake: Never hardcode passwords or AWS access keys directly in your source code. Static code analysis tools like SonarQube will flag this as a critical security issue.

Stage 4 — Unit Testing (Optional)

Unit tests test small, individual units of code — such as individual functions or methods — in isolation, without running the entire application.

LanguageUnit Test Tool
JavaJUnit
PythonPyTest

Developers write test scripts alongside their code — not just to satisfy a process, but as their own safety net. If a test fails, they know immediately that their code broke something.

Stage 5 — Code Coverage (Optional)

Code coverage measures what percentage of the code is actually tested by the unit tests, ensuring there are no untested paths that could hide bugs.

LanguageCoverage Tool
JavaJaCoCo
JavaScriptIstanbul
PythonCoverage.py

Stage 6 — Build Artifact / Package

After all tests pass, the CI pipeline produces a final packaged build — a build artifact. This is the deployable version of the application, ready to be handed to the CD pipeline.

CI Orchestration Tools

A CI orchestration tool manages and connects all the above stages into a pipeline. Popular options include:

  • Jenkins — most popular, open source, highly configurable
  • GitHub Actions — built into GitHub, no separate server needed
  • GitLab CI — built into GitLab
  • AWS CodeBuild — AWS-native CI tool
  • CircleCI — cloud-based CI/CD platform

What is CD — Continuous Delivery / Deployment?

The CD pipeline takes the verified build artifact from CI and safely deploys it to the target environment — dev, QA, or production.

💡 Continuous Delivery vs Continuous Deployment:
Continuous Delivery = code is always ready to deploy, but a human approves the final push to production.
Continuous Deployment = deployment to production happens automatically after all tests pass, with no manual approval.

Infrastructure as Code (IaC)

The CD pipeline doesn't create servers manually. It uses Infrastructure as Code (IaC) tools to provision identical environments automatically:

  • Terraform — for infrastructure provisioning (creating EC2, VPCs, databases)
  • Ansible — for software configuration management (installing software, deploying applications on servers)

Using IaC tools ensures that dev, QA, and production environments are identical, eliminating environment-specific bugs.

Figure 5: CD Pipeline — Deploying to Dev, QA, and Production Environments

🖥️ Virtualization — The Foundation

To understand why containers exist, we first need to understand what came before them: virtualization. And to understand why virtualization was invented, we need to understand the problem it solved.

The Problem — Resource Contention

Imagine a powerful physical server with 12-core CPU, 100 GB RAM, and 1 TB disk. You run five applications on it. Application 1 is a busy e-commerce website — it grabs most of the CPU and RAM. By the time Application 5 tries to run, the resources are exhausted. It's slow, crashing, and unreliable.

This is called resource contention — applications fighting each other for the same hardware.

Figure 6: Resource Contention — Applications Fighting for the Same Hardware

The Solution — Virtualization

Virtualization is the process of creating multiple Virtual Machines (VMs) on a single physical server by partitioning hardware resources using a software layer called a hypervisor.

Think of it like an apartment building. One large building (physical server) is divided into separate apartments (VMs). Each apartment has its own front door, its own kitchen, its own bathroom. What one tenant does doesn't affect another tenant.

How Virtualization Works

A hypervisor sits between the physical hardware and the virtual machines. It pre-allocates hardware resources — CPU, RAM, and disk — to each VM before the VM starts. Popular hypervisors include VMware, Oracle VirtualBox, Xen, and KVM.

Figure 7: Virtualization Architecture — Hypervisor Partitions Physical Resources into VMs

Each virtual machine contains:

  • Its own Guest OS (Linux, Windows, etc.) — a full operating system
  • Pre-allocated CPU, RAM, and disk
  • Its own applications and libraries

Advantages of Virtualization

  • Better hardware utilization — resources are shared rather than idle
  • Isolation — one VM crashing doesn't affect others
  • Easier server management — multiple environments on one machine
  • Snapshot and rollback — can save VM state and restore it

Disadvantages of Virtualization

Here is where the problem becomes clear. Each VM includes a full operating system, which means every VM consumes significant CPU, RAM, and disk just for the OS — before your application even starts.

A Linux OS with all its kernel, utilities, libraries, and shell can consume gigabytes of RAM. If you have 10 VMs, you're paying 10x the OS overhead. This makes VMs:

  • Slow to start — booting an OS takes minutes
  • Heavy — each VM can be gigabytes in size
  • Resource-inefficient — OS overhead wastes capacity

⚡ This is exactly the gap that containers fill. A container does NOT include a full OS — only the bare minimum needed to run the application.

📦 Containerization — Lightweight Isolation

If a VM is an entire apartment with a full kitchen, bathroom, and bedroom, a container is more like a hotel room — you get what you need to stay, nothing more. No construction of an entire building required.

What is a Container?

A container is a lightweight, isolated process that packages an application together with only its required libraries and dependencies, sharing the host OS kernel rather than running a full OS of its own.

Figure 8: VMs vs Containers — Key Architectural Difference

No Resource Reservation

Unlike VMs, containers do not pre-allocate CPU or RAM. They dynamically take resources from the host machine as needed, releasing them when not in use. This makes containerized environments far more efficient.

Microservices and Containers

Modern applications are not one big program — they are a collection of small, independent services called microservices. Think of an e-commerce site: it has a login service, a product catalogue, a shopping cart, a payment service, and a delivery tracker. Each is a separate piece of software.

Each microservice runs in its own container, isolated from the others. If the cart service crashes, the product catalogue and login service continue to function normally.

Figure 9: Microservices Architecture — Each Service in Its Own Container

VMs and Containers — Better Together

VMs and containers are not competing technologies — they are complementary. In practice, you create an EC2 instance (a VM), install a container runtime like Docker inside it, and run multiple containers within that VM.

This gives you the security of VM-level isolation between your EC2 and other customers' EC2s in AWS, while also getting the efficiency of containers within your EC2.

✅ Best Practice: Use VMs (EC2) for environment-level isolation and infrastructure provisioning. Use containers within VMs for running individual microservices efficiently.

Containerization Tools

Several tools can create and manage containers:

  • Docker — the most popular containerization tool, industry standard
  • containerd — lightweight container runtime, used by Kubernetes internally
  • Podman — daemonless container tool, alternative to Docker
  • CRI-O — lightweight runtime for Kubernetes

🐳 Docker — Architecture & Workflow

Docker is the most widely used containerization platform. Understanding how Docker works internally helps you use it effectively and troubleshoot issues when they arise.

Docker's Two Components

When you install Docker, it installs two components: the Docker Client (CLI) and the Docker Daemon (background service).

  • Docker Client: The command-line interface you interact with. When you type docker build or docker run, the client receives your command.
  • Docker Daemon: The background service (dockerd) that actually does the work — building images, creating containers, managing networks and volumes.

The client and daemon communicate via a REST API, usually over a Unix socket. The Docker Client never does the actual work — it translates your command and sends it to the Docker Daemon, which executes it.

Figure 10: Docker Client-Daemon Architecture

Dockerfile — The Blueprint

A Dockerfile is a plain text file containing step-by-step instructions that tell Docker exactly how to build a container image. Think of it as a recipe: the ingredients are your application code and libraries, the steps are the Dockerfile instructions, and the final dish is the Docker image.

A Dockerfile is always named Dockerfile (with a capital D, no extension) by default. Here is a typical example:

# Start from a base image
FROM nginx:latest

# Set the working directory inside the container
WORKDIR /app

# Copy source code from current directory into container
COPY . /app

# Run a command to install dependencies
RUN npm install

# Tell Docker what command to run when container starts
CMD ["npm", "start"]

Key Dockerfile Instructions

InstructionPurposeExample
FROMBase image to start from (OS + runtime)FROM python:3.11
WORKDIRSets working directory inside containerWORKDIR /app
COPYCopies files from host into containerCOPY . /app
RUNExecutes a command during image buildRUN pip install -r requirements.txt
CMDDefault command to run when container startsCMD ["python", "app.py"]
EXPOSEDocuments which port the container listens onEXPOSE 8080
ENVSets environment variablesENV APP_ENV=production

💡 The FROM instruction is critical. Every container starts from a base image. This base provides the OS layer and runtime environment. Common bases: ubuntu, python:3.11, node:18, nginx, alpine (minimal Linux, under 5MB).

Docker Image — The Template

A Docker image is a read-only template created from a Dockerfile that contains everything needed to run an application: the base OS layer, application code, runtime, libraries, and configuration.

An image is like an installer (.exe or .dmg file for your application). It does nothing on its own — but from it, you can create and run containers.

To build an image from a Dockerfile, you use:

docker build -t my-app:v1 .

The -t flag gives the image a name and tag. The . tells Docker to look for the Dockerfile in the current directory.

Figure 11: From Dockerfile → Docker Image → Running Container

Docker Registry — Image Storage

A Docker registry is a remote storage location for Docker images, similar to GitHub for source code. The most popular public registry is Docker Hub (hub.docker.com).

  • docker push my-app:v1 — uploads your image to the registry
  • docker pull nginx — downloads an image from the registry to your machine

AWS also has its own private registry: Amazon ECR (Elastic Container Registry). According to AWS documentation, ECR is a fully managed container image registry that integrates with Amazon ECS and EKS.

💡 📚 Source: Amazon ECR Documentation

Docker Container — The Running Instance

A Docker container is a running instance of a Docker image — a live, isolated process executing your application with its own filesystem, network, and process space.

To run a container from an image:

docker run -d -p 8080:80 my-app:v1
  • -d: run in detached (background) mode
  • -p 8080:80: map port 8080 on the host to port 80 in the container

What happens internally when you run this command:

  1. Docker Client receives the command and sends it to Docker Daemon
  2. Docker Daemon checks if the image my-app:v1 exists locally
  3. If not found locally, it pulls from Docker Hub automatically
  4. Docker Daemon creates a new container from the image
  5. The application starts running inside the isolated container

Docker Image Layers

Docker images are built in layers. Each instruction in the Dockerfile creates a new layer. Docker caches each layer, so if only the application code changes, only that layer is rebuilt — not the entire image. This makes builds dramatically faster in CI/CD pipelines.

☸️ Kubernetes — Container Orchestration

Docker is excellent for running containers. But imagine you have 50 microservices, each running 3 copies of their container for high availability. That's 150 containers to manage. How do you restart failed containers? How do you scale up when traffic spikes? How do you update one service without downtime?

That's where Kubernetes comes in.

What is Kubernetes?

Kubernetes (K8s) is an open-source container orchestration platform that automates the deployment, scaling, load balancing, and self-healing of containerized applications.

Think of Kubernetes as the conductor of an orchestra. Every musician (container) knows their part. The conductor (Kubernetes) ensures everyone plays at the right time, at the right volume, and brings in a substitute if someone misses their cue.

Figure 12: Kubernetes Architecture — Control Plane and Worker Nodes

What Kubernetes Does For You

  • Self-healing: If a container crashes, Kubernetes automatically restarts it
  • Auto-scaling: Scales the number of pods up or down based on traffic
  • Rolling updates: Updates containers with zero downtime
  • Load balancing: Distributes traffic evenly across running pods
  • Service discovery: Containers find each other automatically by name

Kubernetes on AWS — Amazon EKS

According to AWS documentation, Amazon EKS (Elastic Kubernetes Service) is a fully managed Kubernetes service that removes the complexity of setting up and maintaining the Kubernetes control plane. You focus on your applications; AWS manages the cluster infrastructure.

💡 📚 Source: Amazon EKS Documentation

🔗 Docker in the CI/CD Pipeline

Now that we understand Docker and CI/CD separately, let's see how they work together — because in real-world projects, they are inseparable.

Figure 13: Docker Integrated into a Complete CI/CD Pipeline

Here is the full end-to-end flow when Docker is part of the pipeline:

  1. Developer pushes code to a feature branch in GitHub
  2. CI pipeline (Jenkins / GitHub Actions) is triggered by a webhook
  3. Code is checked out, compiled, and tested
  4. docker build is run — a new Docker image is created from the Dockerfile
  5. docker push — the image is pushed to Amazon ECR or Docker Hub
  6. CD pipeline is triggered — it pulls the image and deploys it to the target environment
  7. New containers replace old ones, with zero downtime rolling update

✅ Why Docker in CI/CD is powerful: The same Docker image that was tested in the CI stage is the exact same image deployed in production. There are no "it worked in test but failed in prod" surprises — the environment is identical.

Where Containers Can Be Deployed

  • EC2 with Docker installed — simplest setup, full control
  • Amazon ECS (Elastic Container Service) — AWS-managed container service
  • Amazon EKS (Elastic Kubernetes Service) — AWS-managed Kubernetes
  • AWS Fargate — serverless container execution (no EC2 management needed)

🎤 Interview Strategy — STAR Methodology

Technical interviews don't just ask technical questions. They also ask behavioural questions to understand how you handle real-world situations. The most effective framework for answering these is the STAR methodology.

Figure 14: STAR Methodology — Answering Behavioural Interview Questions

STAR Example — Real-World Cloud Scenario

⚡ Question: "Tell me about a challenge you faced in a cloud role."

S (Situation): While working as a cloud engineer, our EC2 instance was stopped by an IAM user, causing the public IP address to change.

T (Task): My responsibility was to restore the application within 30 minutes without affecting end users.

A (Action): I allocated an Elastic IP address, attached it to the EC2 instance, and updated the application configuration files with the new IP.

R (Result): The application was restored in 8 minutes, users experienced no prolonged downtime, and we implemented an Elastic IP as standard practice going forward.

Common Behavioural Questions to Prepare

  • Tell me about a time you faced a challenge at work
  • Tell me about a recent failure and what you learned
  • Describe a time you worked with a difficult team member
  • Tell me about a project you're proud of
  • How do you handle a tight deadline?

✅ Key Tip: Keep STAR answers concise. One minute is ideal. More talking often leads to contradictions and confusion. Practice your answers out loud before interviews.

📝 Overall Summary

  • DevOps Core Principles: Collaboration, Automation, and Efficiency — enabling small, frequent releases with automated testing and deployment.
  • Git Workflow: Developers push to feature branches → raise Pull Requests → team lead reviews → merges to main. Git tracks all versions; GitHub/GitLab stores them remotely.
  • CI Pipeline: Automatically triggered on code push or PR. Stages include: checkout, compile/build (Maven/NPM/PIP), static code analysis (SonarQube), unit testing (JUnit/PyTest), code coverage (JaCoCo), and building the final artifact.
  • CD Pipeline: Takes the CI artifact and deploys it to dev, QA, and production environments using IaC tools — Terraform for infrastructure, Ansible for software configuration.
  • Virtualization: Hypervisors (VMware, VirtualBox) partition a physical server into multiple VMs. Each VM has a full OS, pre-allocated resources, and strong isolation — but is heavy and slow to start.
  • Containerization: Containers are lightweight isolated processes that share the host OS kernel. No resource pre-allocation. Start in seconds. Ideal for microservices.
  • Docker Architecture: Docker Client (CLI) sends commands to Docker Daemon (background service). Workflow: Dockerfile → docker build → Docker Image → docker push to registry → docker run → Container.
  • Dockerfile: A plain text blueprint with instructions (FROM, WORKDIR, COPY, RUN, CMD) that Docker uses to build an image.
  • Docker Image: A read-only, layered template containing everything needed to run an application. Stored in Docker Hub or Amazon ECR.
  • Docker + CI/CD: In the CI pipeline, docker build creates an image; docker push stores it. In the CD pipeline, the same image is pulled and deployed — ensuring identical environments from test to production.

Project 1: Dockerize a Static Website on EC2 (Level 1 — Foundations)

🎯 Objective: Install Docker on an EC2 instance, write a Dockerfile for a simple HTML website, build an image, run a container, and access it from a browser. Then rebuild with a content change to observe layer caching in action.

⏱️ Time: 45–60 minutes

💰 Cost: Free tier eligible (t2.micro EC2)

  1. Launch a new EC2 instance (Amazon Linux 2 or Ubuntu 22.04), open port 22 (SSH) and port 80 (HTTP) in the Security Group, and connect via SSH.

    📸 Screenshot: EC2 launch wizard showing AMI, instance type, and security group rules

  2. Install Docker on the EC2 instance and start the service:

    sudo yum update -y
sudo yum install docker -y
sudo systemctl start docker
sudo systemctl enable docker
sudo usermod -aG docker ec2-user

    Log out and log back in via SSH so the group change takes effect, then verify:

    docker --version
docker ps

    📸 Screenshot: Terminal confirming Docker version and empty container list

  3. Create a project directory and a simple HTML page:

    mkdir my-web-app && cd my-web-app
cat > index.html <<'EOF'
<!DOCTYPE html>
<html><body>
<h1>Hello from Docker on EC2! — v1</h1>
<p>This page is served by an Nginx container.</p>
</body></html>
EOF

  4. Create a Dockerfile in the same directory:

    nano Dockerfile

    Add this content exactly:

    FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

    📸 Screenshot: Dockerfile content in nano editor on EC2

  5. Build the Docker image and tag it as version 1:

    docker build -t my-web-app:v1 .

    📸 Screenshot: Docker build output showing all steps completing successfully

  6. Run a container from your image, mapping host port 80 to container port 80:

    docker run -d -p 80:80 --name web-v1 my-web-app:v1

    Verify the container is running:

    docker ps

    📸 Screenshot: docker ps showing the container running with port 80 mapped

  7. Open a browser and navigate to http://<your-ec2-public-ip>. You should see your web page.

    📸 Screenshot: Browser showing the v1 web page served by the Docker container on EC2

  8. Observe layer caching: Edit index.html to say "v2", then rebuild and observe that only the COPY layer rebuilds — the base nginx layer is cached:

    sed -i 's/v1/v2/' index.html
docker build -t my-web-app:v2 .

    📸 Screenshot: Second docker build showing Step 1 as CACHED and only Step 2 rebuilding

  9. Run a second container on a different port to serve v2 simultaneously:

    docker run -d -p 8080:80 --name web-v2 my-web-app:v2

    Now :80 serves v1 and :8080 serves v2. Verify with docker ps and access both URLs in your browser.

  10. Cleanup: Stop and remove containers and images:

    docker stop web-v1 web-v2
docker rm web-v1 web-v2
docker rmi my-web-app:v1 my-web-app:v2

✅ What you practised: Dockerfile instructions, image build, port mapping, layer caching, running multiple containers simultaneously, and image versioning (v1/v2 tags).

Project 2: Git + Docker Workflow — Version-Controlled Containers (Level 2)

🎯 Objective: Store a Dockerfile inside a Git repository. Practice the feature branch → commit → merge workflow and use version tags to tie image versions to Git commits. Add a .dockerignore file and observe the difference in build context size.

⏱️ Time: 30–40 minutes

💰 Cost: Free (GitHub account only, no AWS needed)

  1. Create a new GitHub repository called docker-git-practice, clone it to your local machine, and enter the directory:

    git clone https://github.com/your-username/docker-git-practice.git
cd docker-git-practice
git branch

  2. Create a feature branch for your first feature:

    git checkout -b feature/add-homepage

    📸 Screenshot: Terminal confirming feature branch creation and current active branch

  3. Create the application file and a Dockerfile:

    echo "<h1>Home Page — v1.0</h1>" > index.html

cat > Dockerfile <<'EOF'
FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]
EOF

  4. Create a .dockerignore file to exclude unnecessary files from the Docker build context:

    cat > .dockerignore <<'EOF'
.git
*.md
node_modules
.env
EOF

    💡 Why .dockerignore matters: Without it, Docker sends the entire .git folder (which can be hundreds of MB) to the daemon as build context. With .dockerignore, only the files Docker actually needs are sent — making builds significantly faster.

  5. Stage all files and commit with a descriptive message:

    git add .
git commit -m "feat: add homepage with nginx Dockerfile"

    📸 Screenshot: Terminal showing staged files committed with a descriptive message

  6. Push the feature branch to GitHub:

    git push origin feature/add-homepage

  7. Go to GitHub and open a Pull Request from feature/add-homepage → main. Add a brief description, then merge it.

    📸 Screenshot: GitHub PR showing changed files and the Merge button

  8. Pull the merged code locally and build a versioned image from it:

    git checkout main
git pull origin main
docker build -t docker-git-practice:v1.0 .

  9. Run the container and verify it works:

    docker run -d -p 80:80 --name homepage-v1 docker-git-practice:v1.0
docker ps

  10. Cleanup:

    docker stop homepage-v1
docker rm homepage-v1
docker rmi docker-git-practice:v1.0

✅ What you practised: Storing a Dockerfile in Git, the full feature branch → PR → merge workflow, .dockerignore for build optimization, and image versioning that matches Git history.

Project 3: Automated CI Pipeline with GitHub Actions (Level 4)

🎯 Objective: Set up a real CI pipeline using GitHub Actions. Every time you push code, GitHub automatically checks out your code, runs a basic test, and builds a Docker image — no manual steps needed.

⏱️ Time: 40–50 minutes

💰 Cost: Free (GitHub Actions has a free tier — 2,000 minutes/month)

  1. Use the docker-git-practice repository from Project 2, or create a new one. Inside the repo, create the GitHub Actions workflow directory:

    mkdir -p .github/workflows

  2. Create the CI workflow file:

    nano .github/workflows/ci.yml

    Add the following content:

    name: CI Pipeline

on:
  push:
    branches: [ main, 'feature/**' ]
  pull_request:
    branches: [ main ]

jobs:
  build-and-test:

Project 4: Push to Docker Hub Registry — Image as Artifact (Level 5)

🎯 Objective: Build a Docker image locally, push it to Docker Hub (your remote image registry), then pull it on a separate EC2 instance and run it — proving the image is truly portable.

⏱️ Time: 30–40 minutes

💰 Cost: Free (Docker Hub free tier; free-tier EC2)

  1. Create a free account at hub.docker.com if you don't have one. Then log in from your terminal (local machine or EC2):

    docker login

    📸 Screenshot: Terminal showing successful Docker Hub login

  2. Build your image and tag it with your Docker Hub username so it can be pushed:

    docker build -t <your-dockerhub-username>/my-web-app:v1 .

    The format username/image-name:tag is required for Docker Hub. Replace <your-dockerhub-username> with your actual username.

  3. Push the image to Docker Hub:

    docker push <your-dockerhub-username>/my-web-app:v1

    📸 Screenshot: docker push output showing each layer pushed to Docker Hub

  4. Verify the image is visible in Docker Hub by opening https://hub.docker.com/r/<your-username>/my-web-app in your browser.

    📸 Screenshot: Docker Hub repository page showing the v1 tag published

  5. On a second EC2 instance (or after removing the image locally), pull and run the image directly from Docker Hub — no Dockerfile or source code needed:

    # Remove the local image first to simulate a fresh machine
docker rmi <your-dockerhub-username>/my-web-app:v1

# Pull from Docker Hub and run
docker run -d -p 80:80 <your-dockerhub-username>/my-web-app:v1

    📸 Screenshot: Docker automatically pulling the image from Docker Hub and starting the container

  6. Access the running app via the second EC2's public IP. The same container you built locally now runs identically in the cloud.

  7. Cleanup: Stop the container and optionally delete the Docker Hub repository from the web UI.

    docker stop $(docker ps -q)
docker rm $(docker ps -aq)
docker rmi <your-dockerhub-username>/my-web-app:v1

✅ What you practised: The full artifact concept — a Docker image IS the deployable artifact. Once pushed to a registry, any machine with Docker can pull and run it identically. This is exactly what CI/CD pipelines do in production.

Project 5: Multi-Service App with Docker Compose (Level 6 — Microservices)

🎯 Objective: Run a two-service application — a frontend (Nginx) and a backend (a simple Python API) — using Docker Compose. The frontend and backend communicate over a Docker network. Add a persistent volume for the backend to demonstrate stateful vs stateless containers.

⏱️ Time: 60–75 minutes

💰 Cost: Free (runs locally or on free-tier EC2)

💡 What is Docker Compose? Docker Compose is a tool that lets you define and run multiple containers from a single docker-compose.yml file. Instead of running separate docker run commands for each service, one command (docker compose up) starts everything. According to AWS documentation, Docker Compose is commonly used for local development before deploying to ECS or EKS.

  1. Install Docker Compose on your EC2 (it is included with Docker Desktop on Mac/Windows):

    sudo curl -L "https://github.com/docker/compose/releases/latest/download/docker-compose-$(uname -s)-$(uname -m)" -o /usr/local/bin/docker-compose
sudo chmod +x /usr/local/bin/docker-compose
docker-compose --version

  2. Create a project directory and set up the structure:

    mkdir multi-service-app && cd multi-service-app
mkdir frontend backend

  3. Create the backend Python API. First, add the Python file:

    cat > backend/app.py <<'EOF'
from http.server import HTTPServer, BaseHTTPRequestHandler
import json

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header('Content-Type', 'application/json')
        self.send_header('Access-Control-Allow-Origin', '*')
        self.end_headers()
        response = {"message": "Hello from the Backend API!", "service": "backend"}
        self.wfile.write(json.dumps(response).encode())

HTTPServer(('0.0.0.0', 5000), Handler).serve_forever()
EOF

    Then create the backend Dockerfile:

    cat > backend/Dockerfile <<'EOF'
FROM python:3.11-alpine
WORKDIR /app
COPY app.py .
EXPOSE 5000
CMD ["python", "app.py"]
EOF

  4. Create the frontend HTML page that calls the backend API:

    cat > frontend/index.html <<'EOF'
<!DOCTYPE html>
<html><body>
<h1>Frontend Service</h1>
<button onclick="callBackend()">Call Backend API</button>
<pre id="result">Click the button</pre>
<script>
function callBackend() {
  fetch('http://localhost:5000')
    .then(r => r.json())
    .then(d => document.getElementById('result').innerText = JSON.stringify(d, null, 2));
}
</script>
</body></html>
EOF

cat > frontend/Dockerfile <<'EOF'
FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
EOF

  5. Create the docker-compose.yml file in the project root:

    cat > docker-compose.yml <<'EOF'
version: '3.8'

services:
  frontend:
    build: ./frontend
    ports:
      - "80:80"
    networks:
      - app-network
    depends_on:
      - backend

  backend:
    build: ./backend
    ports:
      - "5000:5000"
    networks:
      - app-network
    volumes:
      - backend-data:/app/data

networks:
  app-network:
    driver: bridge

volumes:
  backend-data:
EOF

    📸 Screenshot: docker-compose.yml file showing both services, shared network, and volume

  6. Build and start both services with one command:

    docker-compose up -d --build

    📸 Screenshot: docker-compose up output showing both services built and started

  7. Verify both containers are running:

    docker-compose ps

    📸 Screenshot: docker-compose ps showing both frontend and backend containers running

  8. Test the backend API directly:

    curl http://localhost:5000

    You should see: {"message": "Hello from the Backend API!", "service": "backend"}

    Access the frontend at http://<your-ec2-public-ip> in a browser and click the button to call the backend.

  9. View real-time logs from both services:

    docker-compose logs -f

  10. Cleanup: Stop and remove all containers, networks, and volumes created by Compose:

    docker-compose down -v

✅ What you practised: Defining a multi-service architecture in a single file, automatic Docker networking between services, persistent volumes for stateful data, and managing the full lifecycle of multiple containers with single commands. This is the foundation of microservices deployment.

🤔 Reflection Questions

1. Your team is running five applications on one physical server and Application 3 keeps crashing due to memory pressure. What architectural change would you recommend and why?

💡 Hint

Think about resource isolation. Both virtualization and containerization solve this problem — which is more appropriate depends on whether the applications share dependencies and how much overhead you can afford.

2. A developer says "it works on my machine but breaks in production." What technology directly solves this problem, and how?

💡 Hint

The problem is environment inconsistency. Think about which technology packages the application with its exact environment, so the same package runs identically everywhere.

3. Why do developers push to a feature branch rather than directly to the main branch? What would go wrong if they pushed directly to main?

💡 Hint

Think about what the main branch represents and what happens if broken code enters it. Consider what the CI pipeline checks and when it triggers.

4. A new team member asks: "Why do we need both CI and CD? Can't we just deploy manually after testing?" How would you respond?

💡 Hint

Think about speed, consistency, human error in manual deployments, and how often modern teams release. What risk does manual deployment introduce?

5. You need to deploy 20 microservices, each needing to scale independently during peak traffic. Would you use VMs, Docker alone, or Kubernetes? Justify your choice.

💡 Hint

Consider the overhead of 20 VMs. Consider whether Docker alone gives you automatic scaling and self-healing. What is the role of an orchestration tool?

6. Describe what happens — step by step — from the moment a developer runs git push to the moment a container is running in production.

💡 Hint

Walk through: Git push → webhook → CI pipeline stages → docker build → docker push → CD pipeline → docker pull → container run. Each step has a specific tool involved.

7. A SonarQube report shows a "critical security issue" in the latest build. What kind of issue might this be, and what should the team do before proceeding with deployment?

💡 Hint

Think about what SonarQube looks for — especially hardcoded credentials or keys. What is the correct way to handle secrets in a containerized application?
