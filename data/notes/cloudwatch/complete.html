🌟 Introduction

Imagine you're running a restaurant. You have a kitchen, waitstaff, a cashier, and maybe a delivery service. If something goes wrong — a dish is taking too long, the cashier keeps making errors, or deliveries keep failing — you need to know what went wrong, when it happened, and why. Amazon CloudWatch is exactly that for your AWS infrastructure: it's your all-seeing eye that watches over your services, collects evidence of problems, and helps you figure out what to fix.

Amazon CloudWatch is AWS's native monitoring and observability service that collects metrics, logs, and events from virtually every AWS service. It is the first place you go when something in your cloud environment behaves unexpectedly.

1. 🔍 What Is CloudWatch?

Let's start with the big picture. When you run applications on AWS, dozens of services are working together — EC2 instances running your code, S3 storing your files, Lambda functions responding to events, AI models answering user queries. All of these services produce data about their own health and behavior. CloudWatch is the place where all of that data flows.

CloudWatch collects monitoring data in two main forms: Metrics (numerical data points over time) and Logs (text-based records of events).

What Does CloudWatch Monitor?

Almost everything! Here are common examples:

  • CPU Utilization on EC2 instances — if your processor is at 80%+, that's effectively at capacity and you need to act
  • Network traffic in and out — unusual spikes can indicate attacks or bugs
  • Application latency — how long users wait for a response (5 seconds = normal for AI apps; 4.5 minutes = disaster)
  • Error rates — how many requests are failing (HTTP 500 errors, timeouts, etc.)
  • Custom application logs — anything your code writes to a log file
💡 The 80% CPU Rule: 80% CPU utilization is effectively full capacity. At that level, the system can't efficiently schedule and move tasks around. Best practice is to set an alarm well below 100% and trigger auto-scaling before things go critical.

How Does CloudWatch Get Its Data?

Some AWS services send data to CloudWatch automatically — you don't have to do anything. Others require you to explicitly enable logging. Some AWS services automatically send logs to CloudWatch, while others require manual configuration to enable logging. Additionally, many services store logs in both CloudWatch and Amazon S3, giving you flexibility in how you analyze them.

Figure 2: Data flows from multiple AWS services into CloudWatch automatically or with configuration

✅ Pro Tip: If you have your own AWS console account, explore CloudWatch to see what data is already being collected. Even a basic setup will have more data than you expect. It's a great place to understand your environment's baseline behavior.

2. 📊 Metrics vs. Logs — What's the Difference?

People often confuse metrics and logs, but they serve very different purposes. Think of it this way: metrics are your car's dashboard (speed, fuel, temperature as numbers), while logs are the car's black box recorder (a detailed story of everything that happened).

Figure 3: Metrics give you the "what number" at a glance; Logs give you the "what happened" in detail

CloudWatch Metrics

CloudWatch Metrics are numerical data points collected over time, used to track the performance and health of AWS resources. They are:

  • Great for graphs and dashboards
  • Easy to set alarms on (e.g., "alert me when latency exceeds 10 seconds")
  • Show you trends over time (was the problem all day, or just at 8:40 AM?)
  • Support comparison across time periods

In the real-world demo we saw, looking at latency metrics on a dashboard immediately revealed three anomalies on March 24th: one response took 18.5 seconds, one took 45 seconds, and another over 10 seconds — all clustered around 8:40 AM. Without metrics, you'd have no idea these spikes happened.

CloudWatch Logs

Logs are the detailed records. They contain things like error messages, request/response details, timestamps, user actions, and status codes. CloudWatch Logs stores text-based records of events from applications and AWS services, organized into Log Groups and Log Streams.

  • More verbose and harder to read at scale (thousands of entries)
  • Contain the "why" behind a problem that metrics only hint at
  • Require querying tools (like Log Insights) to be useful
  • Can be searched, filtered, and analyzed with SQL-like queries
⚡ The Detective Analogy: Metrics show you that a crime happened. Logs show you what happened. CloudTrail shows you who did it and how. You often need all three.

HTTP Status Codes — What Logs Are Full Of

When working with web services and AI models (which are essentially web applications), your logs will be full of HTTP status codes. Here's a quick cheat sheet:

Code RangeMeaningExample
200Success ✅Request processed, got a response
4xxClient error — you did something wrong400 Bad Request, 403 Forbidden
500Server error — the service has a problem502 Gateway Error, 503 Service Unavailable

In our demo, the instructor saw 500-family errors appearing in logs during the outage periods — which is a strong signal that the problem was on the infrastructure/service side, not in the user's code.

3. 📁 CloudWatch Logs Deep Dive

CloudWatch Logs is where most of your troubleshooting will happen. When an application behaves strangely, you go to its logs and ask: "What were you doing when this happened?"

Log Groups and Log Streams

Logs are organized hierarchically. CloudWatch organizes logs into Log Groups (one per application or service) and Log Streams (one per instance or deployment) for structured organization.

  • Log Group: A container for all logs from a particular application or AWS service (e.g., all logs from your SageMaker model endpoint)
  • Log Stream: A sequence of log events from a specific source within that group (e.g., logs from one particular model variant)

What's Actually In a Log?

When you look at a raw CloudWatch log for an AI model endpoint (like a SageMaker deployment), you'll see:

  • Keep-alive / health check pings — the system constantly asking "are you still there?" These are the majority of entries and mostly noise
  • Invocation records — actual user requests (HTTP POST to invoke the model)
  • Response codes — 200 for success, 500 for failure
  • Timestamps — in Unix epoch format (more on this in section 8)
  • Request/response metadata — region, model ID, request size, duration
❌ The Noise Problem: When a model is "always on" (not serverless), it generates constant keep-alive pings. A model running for hours can have hundreds of these pings for every real user request. This is one reason why AI-powered log summarization is so valuable — you don't want to read through 714 keep-alive entries to find 3 actual errors.

Navigating to the Right Logs

One practical tip from the demo: when you're working in services like SageMaker or Bedrock, you often get a direct link to CloudWatch logs from within the service console. This saves you from having to navigate CloudWatch manually and figure out which log group belongs to your specific application or model variant.

✅ Real-World Workflow: See an error in your app → click the CloudWatch logs link in SageMaker/Bedrock console → jump directly to that model's log group → use Log Insights to query for errors → identify the timestamp → correlate with other monitoring tools.

Figure 4: Direct log navigation from service consoles saves significant troubleshooting time

4. 🔎 Log Insights — Querying Your Logs

Raw logs are overwhelming. Thousands of lines of text, most of it routine noise. CloudWatch Log Insights is your search engine for logs — it lets you run queries to extract exactly the information you need.

CloudWatch Log Insights is an interactive query tool that lets you search, filter, and analyze log data using a SQL-like query language.

How Log Insights Works

  • You select one or more log groups to query
  • You choose a time range (relative like "last hour," or absolute like "March 24th, all day")
  • You write (or generate with AI) a query
  • Results appear almost instantly, even across millions of log entries

The Log Insights Query Language

The query language has SQL-like syntax but is purpose-built for logs. CloudWatch Log Insights uses its own query language with commands like fields, filter, stats, sort, and limit to analyze log data. Here are common patterns:

# Get all log entries (basic)
fields @timestamp, @message
| sort @timestamp desc
| limit 20

# Filter for errors
fields @timestamp, @message
| filter @message like /500/
| sort @timestamp desc

# Count events by type
stats count(*) as eventCount by statusCode
| sort eventCount desc

The good news: you don't have to learn this syntax deeply if you use the AI query generator (covered in the next section). But understanding the structure helps you interpret and modify generated queries.

Saving Queries

If you find yourself running the same query over and over (e.g., "show me all 500 errors"), CloudWatch Log Insights allows you to save frequently used queries for quick reuse. This is especially valuable in a team environment where multiple people monitor the same application.

💡 Practical Use Case: Imagine you have multiple AI model variants deployed (maybe testing Model A vs Model B). You can query log groups from both simultaneously in Log Insights and compare their error rates, response times, and failure patterns side by side.

5. 🤖 AI-Powered Features in CloudWatch

This is one of the most exciting recent additions to CloudWatch. AWS recognized that logs are overwhelming for humans and added AI capabilities to help. AWS launched AI-powered log summarization in CloudWatch Log Insights globally in August 2024, following a trial in select regions in June 2024.

Feature 1: AI Summarize Results

After running a Log Insights query, you can click "Summarize Results" and AI will analyze all the results and give you a plain-English summary of what it found.

In the demo, after running a query that returned 717 log events (mostly keep-alive pings), clicking AI Summarize instantly told us:

  • There's a SageMaker endpoint receiving two types of requests (POST for model invocations, GET for health checks)
  • Most POST requests return 200 (success)
  • Two requests failed — and here's why
  • Possible mitigations for the failures

Without this, you'd have to manually scan 717 log lines. The AI summarize feature in CloudWatch can analyze hundreds of log entries and identify patterns, anomalies, and potential root causes automatically.

✅ Time Savings: Finding 3 error events among 717 log entries manually could take 20-30 minutes. AI summarization does it in seconds and also suggests what might be causing the problems — something a raw log scan can't do.

Feature 2: Natural Language Query Generation

Don't know the CloudWatch query syntax? Just describe what you want in plain English. CloudWatch Log Insights includes an AI-powered natural language query generator that converts plain English descriptions into valid Log Insights queries.

Examples of queries you can type in plain English:

  • "Show all 500 code errors"
  • "Find all errors"
  • "Show me requests that took more than 10 seconds"
  • "Count failures by hour for the last 24 hours"

The AI will:

  1. Show you what it interpreted from your request (with markup)
  2. Generate the actual query code
  3. Remove the markup and run the query
💡 Honest Limitation: The AI query generator is not perfect. It sometimes produces queries that don't run on the first try, or that interpret your request differently than intended. But it handles most common requests well, especially straightforward filter and count operations. You can iterate — if the first result isn't right, refine your description.

How AI Features Compare to Building Your Own

In the demo, the instructor had actually built a custom log analysis tool using Bedrock before discovering CloudWatch's built-in AI features. The experience revealed an important lesson: build things yourself to learn, but use managed services in production.

The custom-built tool worked, but had issues like:

  • Poor Unix timestamp conversion (the AI would guess dates incorrectly)
  • Limited query flexibility
  • Required significant development effort

The built-in CloudWatch AI features handle most of this correctly out of the box. Generative AI is not reliable for tasks requiring mathematical precision, such as converting Unix timestamps — use deterministic code (like Python) for such calculations instead.

❌ Critical Lesson on AI Limitations: LLMs cannot reliably convert Unix epoch timestamps to human-readable dates. When asked to do so, they will fabricate plausible-sounding dates. If you need accurate timestamps, use a programming language's date library — not an AI model. This is a fundamental limitation of language models: they predict likely text, not calculate correct math.

6. 🛠️ Real-World Demo: Troubleshooting an AI App

Let's walk through the exact troubleshooting scenario demonstrated in class. This gives you a concrete mental model for how CloudWatch fits into real-world problem-solving.

The Setup

The application stack being monitored:

  • A SageMaker endpoint hosting a custom image classification model (pizza vs. not pizza)
  • An EC2 instance running test scripts and a conversational AI app
  • A Bedrock-based chatbot using Claude models via inference profiles
  • All generating logs in CloudWatch

Step 1: Noticing the Problem via Metrics

On March 24th, the instructor noticed something strange — some requests were taking much longer than usual. Normal latency for the AI app was around 5 seconds. But three incidents showed:

  • One response at ~18.5 seconds
  • One at ~45 seconds
  • One at just over 10 seconds

On March 17th, it was even worse: latency jumped to 30 seconds, then 2 minutes, then nearly 4.5 minutes. Some requests timed out entirely with no response at all.

Monitoring metrics dashboards can surface latency anomalies and error patterns that would be invisible to someone only looking at whether the service is "up" or "down."

Step 2: Looking at Logs for Context

The metrics told the instructor when and how bad the problem was. Next step: go to CloudWatch Logs for the specific models and applications experiencing issues.

In the SageMaker logs, most entries were health-check keep-alives (noise). Using Log Insights + AI Summarize quickly surfaced the meaningful events.

Step 3: Finding the Errors

Using the natural language query "find all errors" on the Bedrock logs for March 24th, the query returned exactly 3 results — all around 8:39–9:05 AM. These were Service Unavailable exceptions — the service itself was reporting it couldn't handle requests.

Figure 6: The 5-step troubleshooting workflow using CloudWatch for AI application monitoring

Step 4: Connecting the Dots

Timestamps from logs: 8:39, 8:42, 9:05 AM (Pacific time). Correlating with AWS's own service health dashboard confirmed: there was an AWS infrastructure incident during those exact windows. The problem wasn't in the app's code — it was in the underlying infrastructure.

The root cause: the app was using a global inference profile for Claude Sonnet. Global profiles route requests to whichever Claude endpoint has the best availability worldwide. But when data centers in the Middle East region were experiencing severe disruptions (caused by real-world geopolitical events), the global routing was overwhelmed. Too many requests, too few available endpoints — causing massive delays and timeouts.

Step 5: The Fix

The solution was to switch from a global inference profile to a US regional inference profile. This limits routing to US data centers only, which still load-balances between multiple regions (Oregon, Virginia, etc.) but avoids the impacted Middle East endpoints entirely.

💡 Inference Profiles Explained: When using large models like Claude Sonnet on Bedrock, you cannot invoke the model directly by ID. You must use an inference profile — essentially a smart load balancer that distributes your requests across multiple instances of the model. Global profiles route worldwide; regional profiles stay within a geography. For models like Claude Sonnet on Amazon Bedrock, direct model invocation is not supported — you must use a cross-region inference profile instead.

7. 🔍 CloudWatch vs. CloudTrail — Know the Difference

This is a very common source of confusion — and a very common exam question. CloudWatch and CloudTrail both help you monitor your AWS environment, but they watch very different things.

CloudWatch monitors operational metrics and application logs, while CloudTrail records API calls and tracks who did what in your AWS account.

Figure 7: CloudWatch watches HOW services perform; CloudTrail watches WHO is doing WHAT in your account

Amazon CloudWatch

  • Focus: Operational performance and application behavior
  • What it captures: CPU usage, network traffic, latency, application log messages, custom metrics
  • Good for: "Why is my app slow?" "Which requests are failing?" "When did the error spike happen?"
  • Think of it as: A hospital patient monitor — tracking vitals in real time

Amazon CloudTrail

  • Focus: API activity and account governance
  • What it captures: Every API call made in your AWS account — who called it, when, from where, and whether it succeeded
  • Good for: "Who deleted this S3 bucket?" "Did someone try to log in and fail?" "When was this security group modified?"
  • Think of it as: A security camera system — recording who comes and goes and what they touch
AspectCloudWatchCloudTrail
Primary usePerformance monitoringAudit and compliance
Data typeMetrics, logs, eventsAPI call records
Who cares?DevOps, developersSecurity, compliance, auditors
Real-time?Yes (near real-time)Slight delay (minutes)
Retention defaultConfigurable (never expires by default for logs)90 days in event history; S3 for longer
💡 Real-World Example: You notice your application is slow (CloudWatch shows latency spike). You then check CloudTrail and see that someone modified a security group rule 10 minutes before the slowdown started. CloudWatch told you the symptom; CloudTrail told you the possible cause. Together, they solve the mystery.
✅ Exam Tip: When a question asks about performance, logs, or application health → think CloudWatch. When a question asks about API calls, who changed what, or compliance → think CloudTrail.

8. ⏱️ Unix Timestamps — The Secret Language of Logs

Every log entry in CloudWatch (and most logging systems in the world) has a timestamp. But it won't look like "March 24th, 8:39 AM." It'll look like this: 1711269540000

This is called a Unix epoch timestamp, and once you understand it, reading logs becomes much less confusing.

What Is Unix Epoch Time?

Unix epoch time counts the number of seconds (or milliseconds) that have elapsed since January 1st, 1970 at 00:00:00 UTC — the "Unix epoch."

When you see a 10-digit number in a log, it's seconds since 1970. When you see a 13-digit number (like in CloudWatch), it's milliseconds since 1970 — giving you precision down to one-thousandth of a second.

Why Do We Use This Format?

  • Language-neutral: Every programming language and operating system understands this number
  • Sortable: Higher number = later time, always. No timezone confusion.
  • Precision: Millisecond-level accuracy for sequencing events
  • Simple comparison: Subtract two timestamps to get exact duration

How to Convert Unix Timestamps

You need a converter tool — don't do it in your head, and definitely don't ask an AI to do it.

  • Online: epochconverter.com or unixtimestamp.com
  • Linux/Mac terminal: date -d @1711269540 (seconds) or date -d @1711269540000 (milliseconds)
  • Python: from datetime import datetime; datetime.fromtimestamp(1711269540)
# Python conversion example
from datetime import datetime, timezone

# CloudWatch millisecond timestamp
ms_timestamp = 1711269540000

# Convert to human-readable UTC
dt = datetime.fromtimestamp(ms_timestamp / 1000, tz=timezone.utc)
print(dt)  # 2024-03-24 08:39:00+00:00
❌ Critical Warning: Generative AI models cannot reliably convert Unix timestamps and will fabricate plausible but incorrect dates. Always use a deterministic tool (Python, JavaScript date library, or an online converter) for timestamp conversion. This is not a limitation that can be "prompted away" — it's fundamental to how LLMs work. They predict likely output, not perform arithmetic.

UTC vs. Local Time in CloudWatch

CloudWatch stores and displays all timestamps in UTC (Coordinated Universal Time). If you're in Pacific Time (UTC-7 or UTC-8), you'll need to subtract 7 or 8 hours from what you see. In the demo, an error logged at 15:39 UTC was actually 8:39 AM Pacific — which matched exactly when the instructor noticed problems in their application. CloudWatch often gives you an option to adjust for local time, but the underlying storage is always UTC.

9. 🌍 When Infrastructure Itself Fails — Real-World Context

One of the most important lessons from this session went beyond CloudWatch itself: sometimes the problem you're monitoring isn't in your code or your configuration. Sometimes, the cloud itself experiences failures — and the failures can be caused by events far outside anyone's control.

The Incident: What Actually Happened

During the period covered in class (March 2025), AWS experienced disruptions affecting data centers in the Middle East region. Unlike typical cloud incidents (hardware failure, software bug, power issue), this one was tied to real-world geopolitical events. Multiple AWS data centers within 300 miles of each other experienced damage severe enough that they could not be brought back online quickly, unlike typical hardware replacement scenarios.

The impact was felt by many users as:

  • Timeout errors from Claude and other AI services
  • Dramatically increased latency (minutes instead of seconds)
  • "Service Unavailable" errors that weren't caused by user code
  • Applications that appeared redundant were no longer redundant

The "Fake Redundancy" Problem

Many customers had designed their applications to use both a European region and the Bahrain (Middle East) region for redundancy — believing they were protected against failure. But when Bahrain became unavailable, they discovered they effectively had single-region deployments. If a secondary region becomes completely unavailable, applications designed for multi-region redundancy may effectively be running in a single region, eliminating the intended failover protection.

⚡ Werner Vogels' Law (Chief Technology Officer, Amazon): "Everything fails all the time." Even infrastructure designed to handle hurricanes and earthquakes can face scenarios beyond original design parameters. Cloud architecture must account for cascading, multi-point failures, not just single component failures.

Inference Profiles: Global vs. Regional

This infrastructure issue directly impacted anyone using global inference profiles on Amazon Bedrock (the managed AI service). Here's the breakdown:

Profile TypeRouting BehaviorImpact During Incident
Global ProfileRoutes to best-available model endpoint worldwide❌ Severely impacted — trying to route through unavailable Middle East capacity
US Regional ProfileRoutes only within US data centers (Oregon, Virginia, etc.)✅ Mostly unaffected — stayed within functioning US capacity
EU Regional ProfileRoutes only within European data centers⚠️ Partially impacted depending on specific regions
💡 The Air Traffic Control Analogy: Think of AWS routing as air traffic control. During the Middle East incident, it was like losing multiple major airports simultaneously. The global "control tower" was overwhelmed trying to reroute all that traffic. Switching to a regional profile is like telling the system "I only fly domestic — don't even try to route me through international airports right now."

Regulatory Constraints on Failover

One important caveat: you can't always just switch regions. Regulatory requirements like GDPR in Europe or HIPAA in healthcare may restrict which AWS regions you can use to store and process data, limiting your failover options during outages.

  • Healthcare data (HIPAA) may need to stay in specific US regions
  • European user data (GDPR) may need to stay within EU regions
  • Some government data must stay within national borders

This means your disaster recovery plan must account for legal constraints, not just technical ones. You can't just "move everything to the US" if your users' data has EU residency requirements.

How AWS Communicates Incidents

AWS proactively communicates outages through:

  • AWS Service Health Dashboard — public page showing current status of all services by region
  • Personal Health Dashboard — shows incidents affecting your specific account and resources
  • Email notifications — sent to customers with resources in affected regions, including specific guidance on what to move and where
  • Account teams — enterprise customers receive direct support; individual developers must rely on self-service tools
✅ Actionable Takeaway: Bookmark the AWS Service Health Dashboard. When you're experiencing weird errors and CloudWatch shows you it's not your code, check the health dashboard. If there's a known incident, you'll see it there — which saves hours of fruitless debugging.

10. ✅ Best Practices for CloudWatch Monitoring

Structuring Your Monitoring Strategy

Good monitoring isn't about watching everything — it's about watching the right things and getting alerted when they cross meaningful thresholds.

  1. Know your baseline first — Before you can spot anomalies, you need to know what "normal" looks like. For an AI app, 5-second response time might be normal. For a database query, 200ms might be the baseline.
  2. Set alarms with buffer — If 80% CPU is your concern point, set the alarm at 70%. You want to react before things go critical, not during a crisis.
  3. Layer your monitoring tools — CloudWatch for operational data, CloudTrail for API audit, AWS Security Hub for security posture, application-level logging for code-level debugging
  4. Enable logging explicitly where needed — Not all services log to CloudWatch by default. When you deploy a new service, verify its logs are flowing where you expect
  5. Use Log Insights' AI features — Don't manually scan hundreds of log entries when AI summarization can surface the key patterns in seconds

For AI Applications Specifically

Monitoring AI applications on AWS has some unique considerations:

  • AI model endpoints on SageMaker generate high volumes of keep-alive health check logs that constitute the majority of log entries and must be filtered to find meaningful events.
  • Track latency carefully — AI model inference is inherently slower than traditional API calls, and latency spikes are often the first sign of infrastructure problems
  • Monitor token usage for Bedrock models — costs are per-token, and unexpected spikes in usage can indicate bugs or abuse
  • Use regional inference profiles when global reliability is uncertain; use global profiles when you prioritize availability and have regulatory flexibility

Privacy Considerations

When building apps that log user interactions, think carefully about what gets captured. Application logs may capture user inputs and AI responses; always review vendor privacy policies to understand whether logged data is used for model training.

  • Some AI vendors use conversation logs for training — opt out if privacy matters
  • Design apps to encrypt sensitive content before logging if full transparency isn't needed
  • Treat user-generated content in logs as sensitive data with appropriate retention policies

📝 Overall Summary

  • CloudWatch is your monitoring hub: It collects metrics (numbers over time) and logs (text events) from virtually every AWS service, and is the first place to look when something goes wrong.
  • Metrics vs. Logs: Metrics show performance trends (great for dashboards and alarms); logs show event details (great for root cause analysis). You need both.
  • 80% CPU rule: Treat 80% processor utilization as effectively full capacity — set alarms and auto-scaling triggers before reaching this threshold.
  • Log Insights: A built-in query tool that lets you search and analyze millions of log entries using a SQL-like language, without manually scanning raw logs.
  • AI-powered summarization: Available globally in CloudWatch since August 2024 — it analyzes hundreds of log entries, surfaces patterns and anomalies, and suggests mitigations in plain English.
  • Natural language queries: CloudWatch Log Insights can generate query code from plain-English descriptions, making log analysis accessible even without knowing the query syntax.
  • CloudWatch ≠ CloudTrail: CloudWatch monitors operational performance; CloudTrail audits API calls and tracks who did what. Use both for complete visibility.
  • Unix timestamps: Logs use millisecond epoch timestamps (counting from Jan 1, 1970). Always use code or tools to convert them — AI models will fabricate incorrect dates.
  • Inference profiles matter: Large Bedrock models like Claude Sonnet require inference profiles (not direct invocation). Global profiles offer wider reach but more exposure to regional outages; regional profiles provide more isolation.
  • CloudWatch is a starting point: It tells you when and what failed, but not always why. Combine it with CloudTrail, application logs, and the AWS Health Dashboard to complete your investigation.

🔴 Level 7: Auto-Remediation — System Fixes Itself

🎯 Objective: Create a Lambda function that automatically reboots your EC2 instance when CPU stays above 80% — letting the system heal itself

Step 1: Create the Auto-Remediation Lambda

  1. Lambda Console → Create function → Name: auto-remediate-ec2
  2. Runtime: Python 3.12
  3. Paste this code (replace YOUR_INSTANCE_ID):
import boto3

ec2 = boto3.client('ec2', region_name='us-east-1')

def lambda_handler(event, context):
    instance_id = "i-YOUR_INSTANCE_ID"  # Replace this
    
    print(f"Auto-remediation triggered for {instance_id}")

sudo systemctl stop amazon-cloudwatch-agent

In CloudWatch → Metrics → EC2 → CPUUtilization for your instance. After 5 minutes, observe that the metric line shows no data (gaps in the graph). In production, this pattern tells you either the instance is gone or the agent crashed.

# Create a 2GB file to pressure disk space
fallocate -l 2G /tmp/bigfile2
df -h  # Check disk usage

Watch CloudWatch → EC2 → DiskSpaceUtilization (if disk metrics are enabled). Clean up immediately after: rm /tmp/bigfile2

Chaos Test 4: Restart Everything

# Restart the agent
sudo systemctl start amazon-cloudwatch-agent

# Restart log generator
nohup ~/log-generator.sh &

Observe in CloudWatch how the metrics resume — the gap in the graph shows exactly the downtime window.
