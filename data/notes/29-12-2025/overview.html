🎯 Executive Summary

This document covers three critical AWS concepts tested in the AWS Certified Cloud Practitioner exam:

  • Well-Architected Framework (WAF): Best practices for building and reviewing cloud workloads
  • Cloud Adoption Framework (CAF): Organizational readiness for cloud migration
  • Security Hardening: Network and system-level security implementations

⚠️ Exam Note: These topics typically appear as 1-2 questions in the AWS Cloud Practitioner exam. Focus on understanding the six pillars of WAF and six perspectives of CAF.

🏛️ AWS Well-Architected Framework (WAF)

📖 Definition

The AWS Well-Architected Framework is a set of best practices designed to help cloud architects build secure, high-performing, resilient, and efficient infrastructure for applications and workloads.

💡 Key Purpose: WAF answers the question: "Is your application deployed and built the right way on AWS?"

🎯 The Six Pillars of WAF

Figure 1: The Six Pillars of AWS Well-Architected Framework

Pillar Focus Area Key Question Example AWS Services
1. Operational Excellence Running and monitoring systems How do you run and monitor systems to deliver business value? CloudWatch, CloudTrail, Systems Manager
2. Security Protecting information and systems How do you protect data, systems, and assets? IAM, GuardDuty, Shield, WAF
3. Reliability Ensuring consistent performance How do you ensure workloads perform their intended function? Multi-AZ, Auto Scaling, Backup
4. Performance Efficiency Using resources efficiently How do you use computing resources efficiently? Lambda, ECS, Elastic Beanstalk
5. Cost Optimization Avoiding unnecessary costs How do you avoid or eliminate unneeded cost? Cost Explorer, Budgets, Reserved Instances
6. Sustainability Minimizing environmental impact How do you minimize environmental impacts? EC2 right-sizing, S3 Intelligent-Tiering

🔍 Why WAF Exists

Problem Statement: When organizations first migrate to AWS, they often face:

  • Applications that work initially but suddenly go down
  • Unexpectedly high costs
  • Security vulnerabilities and gaps
  • Poor performance under load

❌ Common Misconception: "Cloud failures are due to technology issues." Reality: People fail in the cloud because of poor planning and poor design, not because AWS services don't work.

⚙️ Practical Implementation

Method 1: AWS CLI - Well-Architected Tool

# Create a workload review
aws wellarchitected create-workload \
    --workload-name "MyApplication" \
    --description "Production web application" \
    --environment PRODUCTION \
    --region us-east-1

# List available lenses
aws wellarchitected list-lenses --region us-east-1

# Get workload details
aws wellarchitected get-workload \
    --workload-id  \
    --region us-east-1

Method 2: AWS Console (GUI)

  1. Open AWS Management Console and search for "Well-Architected Tool"
  2. Click Define workload
  3. Enter workload details:
    • Name: Your application name
    • Description: Application purpose
    • Environment: Production/Pre-production
    • Regions: Where deployed
  4. Click Start reviewing
  5. Answer questions for each pillar
  6. Review High-risk issues (HRI) and Medium-risk issues (MRI)
  7. Download improvement plan

✅ Best Practice: Conduct Well-Architected Reviews quarterly for production workloads and before major architectural changes.

📊 WAF Review Process

Step Action Duration Output
1. Define Identify workload and stakeholders 30 minutes Workload profile
2. Review Answer pillar-specific questions 2-4 hours Risk assessment
3. Analyze Identify high and medium risks 1 hour Risk report
4. Improve Implement recommendations Ongoing Remediation plan

Figure 2: AWS Well-Architected Framework Review Process

🎯 Key Takeaways

  • WAF provides technical correctness after migration
  • Focuses on continuous improvement of existing workloads
  • Six pillars must be balanced - optimizing one shouldn't compromise others
  • Regular reviews prevent architectural debt
  • Use the Well-Architected Tool in AWS Console for guided assessments

🚀 AWS Cloud Adoption Framework (CAF)

📖 Definition

The AWS Cloud Adoption Framework (CAF) provides guidance to help organizations prepare for successful cloud migration. It addresses organizational readiness across six perspectives.

💡 Key Purpose: CAF answers: "Are we ready to move to the cloud?" It focuses on organizational readiness BEFORE migration.

⚖️ WAF vs CAF: Understanding the Difference

Aspect Cloud Adoption Framework (CAF) Well-Architected Framework (WAF)
Timing BEFORE migration AFTER migration
Focus Organizational readiness Technical correctness
Scope People, processes, culture Architecture, workloads
Question "Are we ready to migrate?" "Is our application optimized?"
Components 6 Perspectives 6 Pillars

⚠️ Remember: CAF = Organization preparation | WAF = Continuous workload optimization

🔒 Security: System & Network Hardening

🎯 Core Security Principle

⚠️ Core Truth: Security is about controlling access. There are two places where access can be controlled:
1. BEFORE reaching the system (Network Hardening)
2. AFTER reaching the system (System Hardening)

📚 Real-Life Analogy: Protecting Valuables

Imagine protecting a valuable gold ornament:

  • Layer 1: House entrance with gate (Network Hardening)
  • Layer 2: Bedroom door (Network Hardening)
  • Layer 3: Almirah/Cupboard (Network Hardening)
  • Layer 4: Locker inside cupboard (System Hardening)
  • Layer 5: Only authorized person has key (System Hardening)
  • Monitoring: CCTV cameras throughout (Both)

💡 Key Insight: Multiple layers of security (defense in depth) protect against different threat vectors.

🌐 Network Hardening

📖 Definition

Network Hardening controls access BEFORE someone reaches the system. It answers: "Who can connect? From where? On which port?"

Figure 3: Network Hardening Components

🔧 Network Hardening Components

Component Purpose AWS Implementation Example Rule
Firewall Filter incoming/outgoing traffic Security Groups, Network ACLs Allow HTTP (80) from anywhere
Port Control Allow only necessary ports Security Group Rules SSH (22) only from admin IP
IP Filtering Block/allow specific IPs NACL, WAF IP sets Block suspicious IP ranges
Network Segmentation Isolate resources VPC, Subnets Public vs Private subnets
IDPS Detect intrusions GuardDuty, IDS solutions Alert on port scans

⚙️ Practical Implementation: Network Hardening

Method 1: AWS CLI - Security Group Configuration
# Create a security group with strict rules
aws ec2 create-security-group \
    --group-name "WebServer-SG" \
    --description "Hardened security group for web servers" \
    --vpc-id vpc-xxxxx

# Allow HTTP from anywhere (port 80)
aws ec2 authorize-security-group-ingress \
    --group-id sg-xxxxx \
    --protocol tcp \
    --port 80 \
    --cidr 0.0.0.0/0

# Allow SSH ONLY from admin IP (port 22)
aws ec2 authorize-security-group-ingress \
    --group-id sg-xxxxx \
    --protocol tcp \
    --port 22 \
    --cidr 203.0.113.25/32  # Replace with your IP

# Deny all other inbound traffic (implicit in AWS)
# All outbound traffic allowed by default

# Create Network ACL for subnet-level control
aws ec2 create-network-acl \
    --vpc-id vpc-xxxxx

# Add NACL rule to block specific IP range
aws ec2 create-network-acl-entry \
    --network-acl-id acl-xxxxx \
    --ingress \
    --rule-number 100 \
    --protocol -1 \
    --cidr-block 198.51.100.0/24 \
    --rule-action deny
Method 2: AWS Console - Network Hardening Setup
  1. Configure Security Groups:
    • Go to EC2 Dashboard → Security Groups
    • Click Create security group
    • Name: "Hardened-WebServer-SG"
    • Add Inbound Rules:
      • Type: HTTP | Port: 80 | Source: 0.0.0.0/0
      • Type: HTTPS | Port: 443 | Source: 0.0.0.0/0
      • Type: SSH | Port: 22 | Source: Your IP/32
    • Outbound Rules: Keep default (all traffic allowed)
    • Click Create
  2. Configure Network ACLs:
    • Go to VPC Dashboard → Network ACLs
    • Select your VPC's NACL
    • Add Inbound Rules (evaluated in order):
      • Rule 100: Block malicious IP | Deny
      • Rule 110: Allow HTTP | Port 80 | Allow
      • Rule 120: Allow HTTPS | Port 443 | Allow
      • Rule 130: Allow SSH | Port 22 | Allow
      • Rule *: Deny all (default)
    • Click Save changes
  3. Enable VPC Flow Logs:
    • Select your VPC → Actions → Create flow log
    • Filter: Accept, Reject, or All
    • Destination: CloudWatch Logs or S3
    • This monitors all network traffic

✅ Best Practice: Use Security Groups for instance-level control (stateful) and NACLs for subnet-level control (stateless). Security Groups should be your primary defense.

⚙️ Practical Implementation: System Hardening

Method 1: AWS CLI - System Hardening
# 1. Enable CloudWatch Logs for EC2
aws logs create-log-group \
    --log-group-name "/aws/ec2/system-logs"

# 2. Apply security patches using Systems Manager
aws ssm send-command \
    --document-name "AWS-RunPatchBaseline" \
    --targets "Key=instanceids,Values=i-xxxxx" \
    --parameters "Operation=Install"

# 3. Create IAM role with least privilege
aws iam create-role \
    --role-name "EC2-LimitedAccess" \
    --assume-role-policy-document file://trust-policy.json

aws iam attach-role-policy \
    --role-name "EC2-LimitedAccess" \
    --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess

# 4. Enable GuardDuty for threat detection
aws guardduty create-detector \
    --enable \
    --finding-publishing-frequency FIFTEEN_MINUTES

# 5. Run security assessment with Inspector
aws inspector2 enable \
    --resource-types EC2 ECR

# 6. Configure file integrity monitoring (example user data script)
# This would be in EC2 user data or Systems Manager document
#!/bin/bash
# Install AIDE (Advanced Intrusion Detection Environment)
yum install aide -y
aide --init
cp /var/lib/aide/aide.db.new.gz /var/lib/aide/aide.db.gz
# Schedule daily integrity checks
echo "0 5 * * * /usr/sbin/aide --check" | crontab -
Method 2: AWS Console - System Hardening Setup
  1. Configure IAM for Least Privilege:
    • Go to IAM Dashboard → Roles
    • Click Create role
    • Select: AWS service → EC2
    • Attach policies:
      • For web servers: AmazonS3ReadOnlyAccess
      • For logging: CloudWatchAgentServerPolicy
      • Avoid: AdministratorAccess
    • Name role: "EC2-WebServer-Role"
    • Attach to EC2 instance during launch
  2. Enable Systems Manager for Patch Management:
    • Go to Systems Manager → Patch Manager
    • Click Configure patching
    • Select: Scan and install
    • Schedule: Daily at 2 AM
    • Targets: Tag-based (e.g., Environment=Production)
    • Reboot option: Reboot if needed
  3. Set Up CloudWatch Logs:
    • SSH into EC2 instance
    • Install CloudWatch Agent: 
      wget https://s3.amazonaws.com/amazoncloudwatch-agent/linux/amd64/latest/amazon-cloudwatch-agent.rpm
sudo rpm -U ./amazon-cloudwatch-agent.rpm
    • Configure agent to collect:
      • /var/log/secure (authentication logs)
      • /var/log/messages (system logs)
      • /var/log/httpd/access_log (web logs)
    • Start agent: sudo systemctl start amazon-cloudwatch-agent
  4. Enable GuardDuty for Threat Detection:
    • Go to GuardDuty → Get Started
    • Click Enable GuardDuty
    • Configure findings:
      • Export to S3 for long-term storage
      • Send to SNS for email alerts
      • Integrate with Security Hub
  5. Harden OS Configuration (SSH to instance): 
    # Disable root login
sudo sed -i 's/PermitRootLogin yes/PermitRootLogin no/' /etc/ssh/sshd_config

# Disable password authentication (use key-based only)
sudo sed -i 's/PasswordAuthentication yes/PasswordAuthentication no/' /etc/ssh/sshd_config

# Restart SSH service
sudo systemctl restart sshd

# Set strict file permissions
chmod 600 ~/.ssh/authorized_keys
chmod 700 ~/.ssh

# Remove unnecessary packages
sudo yum remove telnet -y

# Enable automatic security updates
sudo yum install yum-cron -y
sudo systemctl enable yum-cron
sudo systemctl start yum-cron

❌ Common Mistake: Opening systems first and then trying to secure them. Always harden BEFORE exposing to network.

⚖️ Network vs System Hardening Comparison

Aspect Network Hardening System Hardening
Control Point BEFORE reaching system AFTER reaching system
Question "Can you reach the system?" "What can you do inside?"
Focus Network traffic control System configuration
AWS Services Security Groups, NACLs, WAF, VPC IAM, Systems Manager, Inspector
Analogy House gate, door locks Safe inside the house
First Line ✅ Yes - first defense ❌ No - second defense
Prevents Unauthorized connection attempts Unauthorized actions on system

🔄 Complete Security Implementation Workflow

Step Action Type Tools
1 Design VPC with public/private subnets Network VPC, Subnets, Route Tables
2 Configure NACLs for subnet-level filtering Network Network ACLs
3 Create restrictive Security Groups Network Security Groups
4 Launch hardened AMI System EC2 Image Builder
5 Attach IAM role with least privilege System IAM
6 Configure OS security settings System Systems Manager, User Data
7 Install and configure monitoring Both CloudWatch, GuardDuty
8 Enable logging and auditing Both CloudTrail, VPC Flow Logs
9 Regular security assessments Both Inspector, Security Hub
10 Continuous patch management System Patch Manager

🎯 Key Takeaways

  • Defense in Depth: Use both network and system hardening
  • Network Hardening: First line of defense - prevents unauthorized connections
  • System Hardening: Second line of defense - limits what can be done after access
  • Default Insecure: Fresh OS installations are open by default - must be hardened
  • Continuous Process: Hardening is not one-time - requires ongoing maintenance
  • If you can't reach it, you can't attack it - Network hardening principle

🔐 Online Exam Check-In Process (30 Minutes Before)

Phase 1: System Test (Do this NOW + on exam day)

  1. Visit: Pearson VUE OnVUE System Test
  2. Click Run System Test
  3. Download OnVUE application
  4. System test checks:
    • ✅ Internet speed (minimum 1 Mbps upload/download)
    • ✅ Webcam functionality
    • ✅ Microphone functionality
    • ✅ Screen sharing capability
  5. If all checks pass → System is ready

Phase 2: Check-In (30 Minutes Before Exam)

  1. Launch OnVUE application (installed during system test)
  2. Enter Access Code (from confirmation email)
  3. Wait for Proctor (usually 5-15 minutes)

Phase 3: Testing Space Verification

Proctor will ask you to:

  1. Show your room: Lift laptop and pan 360° slowly
    • Show all four walls
    • Show desk area (must be clear)
    • Show under desk
    • Confirm door is closed
  2. Show your hands: Front and back of both hands
    • Confirm no watches
    • Confirm no rings with cameras/devices
  3. Show your ears: No earphones/hearing devices
  4. Show area around laptop: No papers, books, phones

Phase 4: Photo ID Verification

  1. Proctor will send a link to your mobile phone
  2. Open link on phone and upload:
    • Photo of government ID: Passport, Driver's License, or Aadhaar Card
      • Must be clear and readable
      • Name must match certification account
    • 4 Photos of your testing space:
      • Front of your laptop
      • Right side of laptop
      • Back of laptop
      • Left side of laptop
  3. After uploading, keep phone away from testing area

Phase 5: Exam Begins

Once proctor confirms everything:

  • Exam will be released on your screen
  • Proctor monitors you throughout via webcam
  • Do NOT:
    • Look away from screen for extended time
    • Talk or move lips (even silently)
    • Stand up or leave seat
    • Cover your face
  • Allowed to:
    • Use on-screen whiteboard for calculations
    • Flag questions for review
    • Take brief breaks (timer continues)

⚠️ Real Incident - Learn from Instructor's Experience:
The instructor failed twice due to technical issues:
Attempt 1: Laptop battery died mid-exam (not plugged in) → Moving to plug charger = violation → Exam cancelled
Attempt 2: Power outage = Wi-Fi disconnected → Exam failed
Attempt 3 (SUCCESS): Laptop fully charged + plugged in + 5G mobile hotspot → Passed!

Lesson: Use mobile hotspot instead of home Wi-Fi to avoid power outage issues.

🔒 Security Hardening Best Practices

Network Hardening

  • Least Privilege Network Access: Open only required ports
  • Source IP Restriction: Limit SSH to specific IPs
  • Use Security Groups First: Primary defense mechanism
  • Network Segmentation: Separate public and private subnets
  • Enable VPC Flow Logs: Monitor all network traffic

System Hardening

  • Patch Management: Automate security updates
  • Disable Root Login: Use sudo with regular accounts
  • Remove Unnecessary Services: Stop unused daemons
  • Strong Password Policies: Or better, use key-based authentication
  • Enable Logging: Track all system activities
  • Use IAM Roles: Never hardcode credentials
