🏛️ AWS Well-Architected Framework (WAF) - Complete Guide

📖 Story Time: The Restaurant That Kept Breaking Down

The Problem: A restaurant moved from a small kitchen to a large cloud-based food delivery platform. Initially, everything worked great! Orders came in, food went out. But soon:

  • 🔴 The app crashed during dinner rush (reliability issue)
  • 💰 Cloud bills skyrocketed to $10,000/month (cost issue)
  • 🐌 Food took 2 hours to deliver (performance issue)

The Solution: The restaurant used AWS Well-Architected Framework to identify and fix these problems. They realized: "Technology isn't the problem—poor planning and design are!"

🎯 What is WAF? (In Simple Words)

The AWS Well-Architected Framework is like a quality checklist that asks:

  1. "Is your cloud application built correctly?"
  2. "Are you following best practices?"
  3. "Where can you improve?"

✅ Think of it as: A health checkup for your cloud applications. Just like doctors check blood pressure, heart rate, etc., WAF checks six important "health indicators" of your cloud setup.

🎨 The Six Pillars: Explained with Everyday Examples

1️⃣ Operational Excellence: "Running Smoothly"

Simple Definition: How well do you run and monitor your systems?

Analogy Technical Meaning Real Example
🚗 Car Dashboard: Speedometer, fuel gauge, warning lights help you drive safely Monitoring systems, automated responses, continuous improvement Netflix monitors video streaming quality 24/7 and auto-scales servers during peak times

Key Questions WAF Asks:

  • Can you automatically fix problems? (Lambda, Systems Manager)
  • Do you learn from failures? (Post-incident reviews)

⚠️ Common Mistake: Deploying applications without monitoring. It's like driving a car with no dashboard—you won't know there's a problem until you break down!

2️⃣ Security: "Protecting Your Assets"

Simple Definition: How do you protect data, systems, and users?

Analogy Technical Meaning Real Example
🏦 Bank Vault: Multiple locks, guards, cameras, and access logs Encryption, IAM, security groups, logging Banking apps encrypt your data, require multi-factor authentication, and log every transaction

Key Questions WAF Asks:

  • Is data encrypted? (KMS, SSL/TLS)
  • Who can access what? (IAM policies)
  • Are you tracking access? (CloudTrail)
  • Do you have network controls? (Security Groups, NACLs)

❌ Horror Story: A company left their S3 bucket public by mistake. Result? 100 million customer records leaked. Cost? $50 million in fines and lost reputation.

3️⃣ Reliability: "Always Available"

Simple Definition: Does your application work consistently when needed?

Analogy Technical Meaning Real Example
🚰 Water Supply: Backup water tanks, multiple pipelines, automatic switching Multi-AZ deployment, auto-scaling, backups, disaster recovery Amazon.com runs in multiple data centers. If one fails, traffic automatically goes to another

Key Questions WAF Asks:

  • What happens if a server fails? (Auto Scaling)
  • Are you using multiple locations? (Multi-AZ, Multi-Region)
  • Can you recover from disasters? (Backups, snapshots)

💡 Pro Tip: Netflix famously runs "Chaos Monkey"—a tool that randomly shuts down servers to test if the system can survive failures!

4️⃣ Performance Efficiency: "Fast and Optimized"

Simple Definition: Are you using resources efficiently for best performance?

Analogy Technical Meaning Real Example
🏎️ Race Car: Right engine size, right fuel, proper tires for the race track Right-sized instances, CDN, caching, serverless where appropriate YouTube uses CDN (CloudFront) to deliver videos from servers closest to you—faster and cheaper!

Key Questions WAF Asks:

  • Are you using the right instance types? (t3.micro vs c5.xlarge)
  • Can you use serverless? (Lambda instead of EC2)
  • Are you caching content? (CloudFront, ElastiCache)

⚠️ Waste Alert: Using a Ferrari to deliver groceries = Using c5.24xlarge for a simple blog. Right tool for the job!

5️⃣ Cost Optimization: "Don't Waste Money"

Simple Definition: How do you avoid paying for things you don't need?

Analogy Technical Meaning Real Example
💡 Electricity Bill: Turn off lights in empty rooms, use energy-efficient bulbs, compare electricity providers Stop unused instances, use Reserved Instances, right-sizing, S3 lifecycle policies Pinterest saved $20 million/year by identifying and stopping unused EC2 instances and old snapshots

Key Questions WAF Asks:

  • Are you paying for idle resources? (EC2 instances running 24/7 but only used 2 hours/day)
  • Can you use Reserved Instances? (Up to 75% savings)
  • Are you storing unnecessary data? (Old logs, unused snapshots)

❌ Real Incident: A startup left test servers running over the weekend. Monday morning: $15,000 AWS bill! Always use auto-shutdown!

6️⃣ Sustainability: "Eco-Friendly Cloud"

Simple Definition: How do you minimize environmental impact?

Analogy Technical Meaning Real Example

Key Questions WAF Asks:

  • Are you using efficient instance types? (Graviton2 uses 60% less energy)
  • Do you scale down when not needed? (Turn off dev/test environments at night)
  • Are you in green regions? (AWS regions powered by renewable energy)

  • 🤯 Management blamed IT, IT blamed management

The Learning: They realized: "We had the technology but not the organizational readiness. Cloud migration is not just about technology—it's about people, processes, and culture!"

The Solution: They started over using AWS Cloud Adoption Framework. This time, they prepared the organization BEFORE moving.

🎯 What is CAF? (In Simple Words)

The AWS Cloud Adoption Framework is like a wedding planner's checklist that ensures:

  1. "Is everyone ready for the big change?"
  2. "Do we have all the people, skills, and plans in place?"
  3. "What gaps need to be filled before we start?"

✅ Think of it as: A pre-flight checklist for pilots. Before takeoff (migration), you must check fuel (budget), crew training (skills), weather (risks), and flight plan (strategy).

⚖️ WAF vs CAF: The Ultimate Comparison

Aspect CAF (Cloud Adoption Framework) WAF (Well-Architected Framework)
Analogy 🏠 Moving Company Checklist: Pack boxes, hire movers, update address, transfer utilities 🔍 Home Inspector: After moving in, check if plumbing works, electricity is safe, foundation is solid
When BEFORE migration (preparation phase) AFTER migration (optimization phase)
Focus Organizational readiness (people, skills, culture) Technical correctness (architecture, best practices)
Main Question "Are we ready to move to cloud?" "Is our cloud setup optimized?"

⚠️ Key Insight: CAF = "Are we organizationally ready?" | WAF = "Are we technically correct?"
Both are essential! CAF prepares your organization, WAF optimizes your applications.

🔒 Security Hardening - Complete Guide

📖 Story Time: The Hotel Analogy

Imagine a luxury hotel protecting its guests and valuables:

  • 🚧 Main Gate: Security guard checks who enters (Network Hardening)
  • 🏢 Building Entrance: Reception checks guest IDs (Network Hardening)
  • 🚪 Room Door: Key card access (System Hardening)
  • 🔒 Room Safe: Only guest knows the code (System Hardening)
  • 📹 CCTV Everywhere: 24/7 monitoring (Both)

The Principle: Multiple layers of security. If one fails, others protect you. This is called "Defense in Depth"

🎯 Core Security Truth

⚠️ Golden Rule of Security: Security is about controlling access. There are TWO control points:

  1. BEFORE someone reaches the system → Network Hardening
  2. AFTER someone reaches the system → System Hardening

If attackers can't reach you, they can't attack you!

🌐 Network Hardening: "The Outer Shield"

📖 Simple Definition

Network Hardening = Controlling who can connect to your system, from where, and on which ports.

🏰 Medieval Castle Analogy

Medieval Defense Network Hardening Equivalent AWS Service
🏔️ Natural Moat: Water around castle VPC isolation - separate networks Virtual Private Cloud (VPC)
🚧 Main Gate: Only one entrance with guards Internet Gateway - controlled entry point Internet Gateway, NAT Gateway
🛡️ Castle Walls: Block unauthorized entry Firewall rules - block bad traffic Security Groups, NACLs
🔭 Watchtowers: Scouts watching for enemies Intrusion detection GuardDuty, VPC Flow Logs
📜 Guest List: Who's allowed in? IP whitelisting/blacklisting Security Group rules, WAF

⚙️ How to Implement Network Hardening

Step-by-Step: Security Group Setup

Method 1: AWS CLI

# Create Security Group for Web Server
aws ec2 create-security-group \
    --group-name "WebServer-Hardened" \
    --description "Secure web server with minimal ports" \
    --vpc-id vpc-12345678

# Allow HTTPS from anywhere (port 443)
aws ec2 authorize-security-group-ingress \
    --group-id sg-12345678 \
    --protocol tcp \
    --port 443 \
    --cidr 0.0.0.0/0

# Allow HTTP from anywhere (port 80)
aws ec2 authorize-security-group-ingress \
    --group-id sg-12345678 \
    --protocol tcp \
    --port 80 \
    --cidr 0.0.0.0/0

# Allow SSH ONLY from your office (replace with YOUR IP)
aws ec2 authorize-security-group-ingress \
    --group-id sg-12345678 \
    --protocol tcp \
    --port 22 \
    --cidr 203.0.113.25/32

# Note: All other ports are automatically DENIED

Method 2: AWS Console (Step-by-Step for Absolute Beginners)

  1. Login to AWS Console
    • Go to https://console.aws.amazon.com
    • Enter your credentials
  2. Navigate to EC2
    • Search bar at top: Type "EC2"
    • Click "EC2" service
  3. Go to Security Groups
    • Left sidebar: Scroll down to "Network & Security"
    • Click "Security Groups"
  4. Create New Security Group
    • Orange button top-right: "Create security group"
    • Name: WebServer-Hardened
    • Description: Secure configuration for web server
    • VPC: Select your VPC (usually one default)
  5. Add Inbound Rules (Who can connect TO your server)
    • Click "Add rule" button
    • Rule 1: HTTPS
      • Type: HTTPS
      • Protocol: TCP (auto-filled)
      • Port: 443 (auto-filled)
      • Source: 0.0.0.0/0 (means "from anywhere")
      • Description: "Allow HTTPS from internet"
    • Rule 2: HTTP
      • Type: HTTP
      • Port: 80 (auto-filled)
      • Source: 0.0.0.0/0
      • Description: "Allow HTTP from internet"
    • Rule 3: SSH (Admin Access)
      • Type: SSH
      • Port: 22 (auto-filled)
      • Source: My IP (click dropdown, select "My IP")
      • Description: "Admin access from office only"
  6. Outbound Rules (What your server can access)
    • Leave default: "All traffic" to "0.0.0.0/0"
    • This allows your server to make any outbound connections
    • (You can restrict this later for paranoid security)
  7. Review and Create
    • Scroll down
    • Orange button: "Create security group"
    • Success! ✅
  8. Apply to EC2 Instance
    • Go back to EC2 → Instances
    • Select your instance
    • Actions → Security → Change security groups
    • Select "WebServer-Hardened"
    • Click "Add security group"
    • Remove old insecure ones
    • Save!

✅ Congratulations! You've just implemented network hardening. Your server now only accepts connections on ports you explicitly allowed!

💻 System Hardening: "The Inner Safe"

📖 Simple Definition

System Hardening = Controlling what users can do AFTER they've accessed the system.

🏦 Bank Vault Analogy

Imagine you passed the security guard and entered the bank (network hardening worked). But:

  • 🚫 Can you enter the vault? → User Access Control (IAM)
  • 🔐 Can you open safe deposit boxes? → File Permissions
  • 👀 Are your actions being recorded? → Logging & Monitoring
  • 🔧 Can you access bank systems? → Service Hardening

💡 Key Insight: Network Hardening asks "Can you reach me?" System Hardening asks "What can you do once you're in?"

🔧 Five Pillars of System Hardening

1️⃣ User Access Control (IAM)

Principle: Who can access what? Give minimum necessary permissions.

Real-Life Example Technical Implementation AWS Service
👤 Hotel staff: Janitor can clean rooms but can't access safe Create IAM roles with specific permissions
Example: ReadOnlyAccess for interns		 IAM (Identity and Access Management)

Bad Example:

❌ Give everyone AdministratorAccess
Result: Junior developer accidentally deleted production database

Good Example:

✅ Developers get: EC2 read/write, RDS read-only
✅ Admins get: Full access with MFA required
✅ Interns get: Read-only access to logs
2️⃣ Operating System Hardening

Principle: Keep OS secure and updated

Action Why Important How to Do It
Apply security patches Fix known vulnerabilities AWS Systems Manager Patch Manager
Disable root login Prevent highest-privilege access Edit /etc/ssh/sshd_config
Remove unnecessary software Fewer attack surfaces yum remove telnet
Enable firewall Additional layer of defense systemctl enable firewalld
3️⃣ Service Hardening

Principle: Stop unnecessary services, secure necessary ones

Think of it like: Why leave all appliances running when you're not home? Turn off what you don't need!

Service Risk if Unsecured Hardening Action
SSH Brute force attacks • Disable password auth (use keys only)
• Change default port from 22
• Fail2ban for auto-blocking
Web Server (Apache/Nginx) Information disclosure • Hide version numbers
• Disable directory listing
• Enable HTTPS only
Database SQL injection, unauthorized access • Bind to localhost only
• Use strong passwords
• Enable SSL connections
4️⃣ File & Permission Security

Principle: Control who can read, write, or execute files

Common Secure Permissions:

# SSH Private Key (only you can read)

Q1: What is the AWS Well-Architected Framework?

Answer: The AWS Well-Architected Framework is a set of best practices and guidelines that helps you design, build, and review cloud workloads on AWS. It consists of six pillars: Operational Excellence, Security, Reliability, Performance Efficiency, Cost Optimization, and Sustainability. It's like a quality checklist to ensure your applications are built correctly.

Q2: What are the six pillars of the Well-Architected Framework?

Answer:

  1. Operational Excellence - Running and monitoring systems effectively
  2. Security - Protecting information and systems
  3. Reliability - Ensuring consistent performance
  4. Performance Efficiency - Using resources efficiently
  5. Cost Optimization - Avoiding unnecessary expenses
  6. Sustainability - Minimizing environmental impact

Memory trick: "Our Smart Robot Paints Colorful Sunsets" (O-S-R-P-C-S)

Q3: What is the difference between WAF and CAF?

Answer:

  • CAF (Cloud Adoption Framework) is used BEFORE migration to ensure organizational readiness. It has 6 perspectives (Business, People, Governance, Platform, Security, Operations).
  • WAF (Well-Architected Framework) is used AFTER migration for technical optimization. It has 6 pillars focused on application architecture.

Simple analogy: CAF = Wedding planner (preparation), WAF = Home inspector (quality check after moving in)

Q4: What is the difference between Network Hardening and System Hardening?

Answer:

  • Network Hardening: Security controls BEFORE reaching the system (e.g., Security Groups, firewalls, port restrictions). It answers "Can you connect?"
  • System Hardening: Security controls AFTER reaching the system (e.g., IAM, file permissions, patching). It answers "What can you do inside?"

Analogy: Network = Castle walls, System = Safe inside the castle

Q5: What is a Security Group in AWS?

Answer: A Security Group is a virtual firewall that controls inbound and outbound traffic for EC2 instances. It works at the instance level and is stateful (if you allow inbound traffic, the response is automatically allowed out). You specify which ports are open and from which IP addresses traffic is allowed.

Example: Allow port 80 (HTTP) from anywhere, but port 22 (SSH) only from your office IP.

Q6: What does "Defense in Depth" mean?

Answer: Defense in Depth is a security strategy that uses multiple layers of security controls. If one layer fails, other layers still protect the system. Like an onion with multiple layers, or a castle with moat, walls, guards, and locked rooms.

AWS Example: VPC isolation → Security Groups → System firewalls → File permissions → Encryption

Q8: Your EC2 instance is running but you can't SSH into it. What could be wrong?

  1. Security Group: Port 22 might not be open or not allowed from your IP
  2. NACL: Subnet-level blocking
  3. Key Pair: Using wrong .pem file
  4. Username: Wrong username (should be ec2-user for Amazon Linux, ubuntu for Ubuntu)
  5. Instance State: Instance might be stopped or terminated

Troubleshooting steps: Check Security Group first, then verify key pair and username.

Q9: How would you secure a database server in AWS?

Answer: Use both network and system hardening:

Network Hardening:

  • Place database in private subnet (no internet access)
  • Security Group: Allow port 3306/5432 ONLY from web server security group
  • No public IP address

System Hardening:

  • Enable encryption at rest (KMS)
  • Enable encryption in transit (SSL/TLS)
  • Strong passwords or IAM authentication
  • Regular backups with automated snapshots
  • Enable CloudWatch monitoring and alarms

Q10: What is the principle of Least Privilege and why is it important?

Answer: The Principle of Least Privilege means giving users/services only the minimum permissions they need to do their job, nothing more.

Why important:

  • Limits damage from compromised accounts
  • Prevents accidental mistakes (junior dev can't delete production DB)
  • Meets compliance requirements
  • Easier to audit and track actions

Example: Intern gets ReadOnlyAccess, not AdministratorAccess

Q14: Your production server was compromised. Walk me through your incident response using system hardening principles.

Answer:

Immediate Response (0-30 minutes):

  1. Isolate: Change Security Group to deny all traffic (except your forensic IP)
  2. Snapshot: Take EBS snapshot immediately (preserve evidence)
  3. Alert: Notify security team, management

Investigation (30 min - 2 hours):

  1. Check CloudTrail: What API calls were made? Who accessed what?
  2. Check VPC Flow Logs: Where did traffic come from? What connections were made?
  3. Check System Logs: SSH access logs (/var/log/auth.log), command history
  4. Check GuardDuty findings: Any threat detections?

Remediation (2-4 hours):

  1. Launch new instance from clean AMI (don't try to clean compromised one)
  2. Apply hardening:
    • Disable root login
    • New SSH keys
    • Restrictive Security Groups
    • Latest patches
    • Enhanced monitoring
  3. Restore data from last known good backup
  4. Update WAF rules if web application was exploited

Post-Incident (Next week):

  1. Root cause analysis: How did they get in?
  2. Fix vulnerabilities: Patch systems, close security gaps
  3. Update runbooks: Document lessons learned
  4. Implement preventive controls: Better monitoring, stricter access controls
  5. Terminate compromised instance after forensics complete

Section 3: Security Hardening

  1. What is the primary purpose of network hardening?
    • A) To improve application performance
    • B) To control access before reaching the system
    • C) To encrypt data at rest
    • D) To monitor user activities

    ✅ Answer: B) To control access before reaching the system

    Explanation: Network hardening controls who can connect to your system, from where, and on which ports. It's the first line of defense that prevents unauthorized connection attempts.

    Examples: Security Groups, NACLs, firewalls, VPC isolation

    Key principle: "If you can't reach it, you can't attack it"

  2. Which of the following is an example of system hardening?
    • A) Configuring Security Groups to allow only port 443
    • B) Disabling root login on a Linux server
    • C) Placing database in a private subnet
    • D) Using a Web Application Firewall

    ✅ Answer: B) Disabling root login on a Linux server

    Explanation: System hardening controls what users can do AFTER reaching the system. Disabling root login is an operating system configuration that limits access.

    Why others are wrong:

    • A) Security Groups = Network hardening
    • C) Private subnet = Network hardening
    • D) WAF = Network hardening

    Other system hardening examples: File permissions, patching, IAM roles, removing unnecessary services

  3. A Security Group operates at which layer?
    • A) Region level
    • B) VPC level
    • C) Subnet level
    • D) Instance level

    ✅ Answer: D) Instance level

    Explanation: Security Groups are virtual firewalls that control traffic at the instance (EC2) level. They are stateful, meaning return traffic is automatically allowed.

    Comparison:

    • Security Group: Instance level, stateful, allow rules only
    • NACL: Subnet level, stateless, allow AND deny rules
  4. What does "Defense in Depth" mean in cloud security?
    • A) Using only the strongest single security control
    • B) Implementing multiple layers of security controls
    • C) Focusing only on perimeter security
    • D) Encrypting everything with the longest possible keys

    ✅ Answer: B) Implementing multiple layers of security controls

    Explanation: Defense in Depth means using multiple layers of security so if one layer fails, others still protect the system.

    Example layers:

    1. VPC isolation (network layer)
    2. Security Groups (instance firewall)
    3. OS firewall (system level)
    4. File permissions (access control)
    5. Encryption (data protection)

    Analogy: Like an onion with multiple layers, or a castle with moat, walls, guards, and locked rooms

  5. Which AWS service should you enable to detect threats and malicious activity in your account?
    • A) CloudWatch
    • B) CloudTrail
    • C) GuardDuty
    • D) Inspector

    ✅ Answer: C) GuardDuty

    Explanation: GuardDuty is a threat detection service that uses machine learning to identify malicious activity like cryptocurrency mining, unusual API calls, compromised instances, and reconnaissance attacks.

    Service comparison:

    • GuardDuty: Threat detection (finds bad guys)
    • CloudWatch: Monitoring metrics (CPU, memory, etc.)
    • CloudTrail: Audit logging (who did what)
    • Inspector: Vulnerability scanning (finds security holes)
  6. What is the Principle of Least Privilege?
    • A) Give all users administrator access for convenience
    • B) Give users only the minimum permissions they need
    • C) Remove all privileges from users
    • D) Give privileges based on seniority

    ✅ Answer: B) Give users only the minimum permissions they need

    Explanation: Least Privilege means granting only the permissions necessary to perform a job, nothing more. This limits damage from compromised accounts and prevents accidental mistakes.

    Example:

    • ❌ Bad: Give intern AdministratorAccess
    • ✅ Good: Give intern ReadOnlyAccess to specific resources

    Real incident: Junior developer with full access accidentally deleted production database

  7. You want to restrict SSH access to your EC2 instance to only your office IP. Which service should you configure?
    • A) IAM
    • B) Security Group
    • C) KMS
    • D) CloudWatch

    ✅ Answer: B) Security Group

    Explanation: Security Groups control network traffic to EC2 instances. To restrict SSH (port 22) to your office:

    Type: SSH
Port: 22
Source: 203.0.113.25/32 (your office IP)

    Why others are wrong:

    • A) IAM controls AWS API access, not network traffic
    • C) KMS manages encryption keys
    • D) CloudWatch monitors resources
  8. Which is NOT a component of system hardening?
    • A) Applying security patches
    • B) Configuring firewall rules
    • C) Setting file permissions
    • D) Disabling unnecessary services

    ✅ Answer: B) Configuring firewall rules

    Explanation: Configuring firewall rules is NETWORK hardening (controls before reaching system), not system hardening.

    System hardening includes:

    • ✅ OS patching
    • ✅ File permissions (chmod, chown)
    • ✅ User access control (IAM)
    • ✅ Disabling unnecessary services
    • ✅ Strong password policies
    • ✅ Logging and monitoring
  9. What is the best practice for placing a database in AWS?
    • A) Public subnet with public IP
    • B) Private subnet with no internet access
    • C) Public subnet with firewall
    • D) Any subnet with strong password

    ✅ Answer: B) Private subnet with no internet access

    Explanation: Databases should NEVER be directly accessible from the internet. Place them in private subnets where they can only be accessed by application servers in public subnets.

    Architecture:

    • Public Subnet: Web servers (need internet access)
    • Private Subnet: Databases, application servers
    • Security Group: Database port (3306/5432) only from web server SG

    Real incident: Coffee shop left database public → hacked in 2 hours → $200K lawsuit

  10. Which command disables root login on a Linux server?
    • A) passwd -l root
    • B) Edit /etc/ssh/sshd_config and set PermitRootLogin no
    • C) userdel root
    • D) chmod 000 /root

    ✅ Answer: B) Edit /etc/ssh/sshd_config and set PermitRootLogin no

    Explanation: To disable root SSH login:

    sudo vi /etc/ssh/sshd_config
# Change: PermitRootLogin yes
# To: PermitRootLogin no
sudo systemctl restart sshd

    Why others are wrong:

    • A) Only locks password, doesn't disable SSH with keys
    • C) Deleting root user breaks the system!
    • D) Doesn't affect SSH login

    Why disable root: Prevents accidental destruction (like rm -rf /) and limits damage from compromised accounts

🛠️ Hands-On Practical Exercise

Exercise: Secure a Web Application on AWS

🎯 Objective

Deploy a simple web application and implement both network and system hardening following WAF principles.

📋 Prerequisites

  • AWS Account with EC2 access
  • Basic understanding of Linux commands
  • SSH client (Terminal on Mac/Linux, PuTTY on Windows)
  • Time needed: 1-2 hours

🚀 Step-by-Step Implementation

Phase 1: Launch EC2 Instance (Unsecured)
  1. Go to EC2 Dashboard → Launch Instance
  2. Settings:
    • Name: WebServer-Unsecured
    • AMI: Amazon Linux 2023
    • Instance Type: t2.micro (free tier)
    • Key Pair: Create new or use existing
    • Network: Default VPC, Public subnet
    • Security Group: Create new - Allow ALL traffic from anywhere (0.0.0.0/0)
  3. Launch instance
  4. Note the Public IP address
Phase 2: Install Web Server
# SSH into instance
ssh -i your-key.pem ec2-user@YOUR_PUBLIC_IP

# Update system
sudo yum update -y

# Install Apache web server
sudo yum install httpd -y

# Create simple webpage
echo "<h1>Welcome to My Insecure Website!</h1>" | sudo tee /var/www/html/index.html

# Start web server
sudo systemctl start httpd
sudo systemctl enable httpd

# Test: Open browser and go to http://YOUR_PUBLIC_IP
Phase 3: Identify Security Issues (Current State)

Check what's open:

# Check listening ports
sudo netstat -tuln

# Check running services
sudo systemctl list-units --type=service --state=running

# Check users
cat /etc/passwd

# Check if root login is enabled
grep PermitRootLogin /etc/ssh/sshd_config

❌ Current Problems:

  • All ports open to internet
  • Root login enabled via SSH
  • No monitoring
  • No backups
  • System not patched
  • Unnecessary services running
Phase 4: Implement Network Hardening

4.1: Create Restrictive Security Group (AWS Console)

  1. EC2 → Security Groups → Create security group
  2. Name: WebServer-Hardened-SG
  3. Inbound Rules:
    • Type: HTTP, Port: 80, Source: 0.0.0.0/0 (anywhere)
    • Type: HTTPS, Port: 443, Source: 0.0.0.0/0
    • Type: SSH, Port: 22, Source: My IP (click dropdown)
  4. Outbound Rules: Keep default (all traffic allowed)
  5. Create security group

4.2: Apply to Instance

  1. Select your instance
  2. Actions → Security → Change security groups
  3. Remove old security group
  4. Add WebServer-Hardened-SG
  5. Save

4.3: Test (Network Hardening Complete)

# From your computer, test:
# ✅ This should work (HTTP allowed from anywhere)
curl http://YOUR_PUBLIC_IP

# ✅ This should work (SSH allowed from your IP)
ssh -i your-key.pem ec2-user@YOUR_PUBLIC_IP

# From a DIFFERENT IP (friend's computer or mobile network):
# ❌ SSH should be blocked
# ✅ HTTP should still work
Phase 5: Implement System Hardening

5.1: Disable Root Login

# SSH into server
ssh -i your-key.pem ec2-user@YOUR_PUBLIC_IP

# Disable root login
sudo sed -i 's/PermitRootLogin yes/PermitRootLogin no/' /etc/ssh/sshd_config
sudo sed -i 's/#PermitRootLogin yes/PermitRootLogin no/' /etc/ssh/sshd_config

# Disable password authentication (use keys only)
sudo sed -i 's/PasswordAuthentication yes/PasswordAuthentication no/' /etc/ssh/sshd_config

# Restart SSH
sudo systemctl restart sshd

# Verify
grep PermitRootLogin /etc/ssh/sshd_config
# Should show: PermitRootLogin no

5.2: Install and Configure Automatic Security Updates

# Install automatic update tool
sudo yum install yum-cron -y

# Configure for automatic security updates
sudo sed -i 's/update_cmd = default/update_cmd = security/' /etc/yum/yum-cron.conf
sudo sed -i 's/apply_updates = no/apply_updates = yes/' /etc/yum/yum-cron.conf

# Enable and start
sudo systemctl enable yum-cron
sudo systemctl start yum-cron

# Verify
sudo systemctl status yum-cron

5.3: Set Strict File Permissions

# Secure SSH directory
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys

# Secure web files (owned by apache user)
sudo chown -R apache:apache /var/www/html
sudo chmod 755 /var/www/html
sudo chmod 644 /var/www/html/index.html

# Verify
ls -la ~/.ssh
ls -la /var/www/html

5.4: Remove Unnecessary Services

# List all services
sudo systemctl list-units --type=service

# Remove telnet (if installed - insecure)
sudo yum remove telnet -y

# Disable unnecessary services (example)
# sudo systemctl disable bluetooth  # if server has it

5.5: Install and Configure Fail2Ban (Auto-ban brute force)

# Install EPEL repository
sudo yum install epel-release -y

# Install fail2ban
sudo yum install fail2ban -y

# Configure fail2ban for SSH
sudo cat > /etc/fail2ban/jail.local << 'EOF'
[sshd]
enabled = true
port = ssh
logpath = /var/log/secure
maxretry = 3
bantime = 3600
EOF

# Enable and start
sudo systemctl enable fail2ban
sudo systemctl start fail2ban

# Check status
sudo fail2ban-client status sshd

5.6: Enable System Logging

# Install CloudWatch Logs agent
wget https://s3.amazonaws.com/amazoncloudwatch-agent/amazon_linux/amd64/latest/amazon-cloudwatch-agent.rpm
sudo rpm -U ./amazon-cloudwatch-agent.rpm

# Note: Full CloudWatch configuration requires IAM role
# For this exercise, just verify local logging

# Check system logs are enabled
sudo systemctl status rsyslog

# View recent security logs
sudo tail -f /var/log/secure
