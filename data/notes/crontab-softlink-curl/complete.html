⏰ Crontab — Scheduling Tasks in Linux

What is Crontab?

Think of crontab as your mom who wakes you up every morning — except she's a program that never forgets, never oversleeps, and never makes a mistake. Crontab is a Linux utility that allows you to schedule commands or shell scripts to run automatically at specified times or intervals.

The word "cron" comes from the Greek word Chronos, meaning time. The cron daemon is a background process that wakes up every minute, checks the crontab file for scheduled jobs, and executes any jobs whose time matches the current time.

💡 The Alarm Clock Analogy: You want to wake up every day at 6 AM. You could ask your mom, but she might forget or be busy. Instead, you set an alarm clock — you give it one instruction and it repeats forever. Crontab is that alarm clock for your Linux server. You define a schedule once; cron runs it automatically.

Figure 2: How cron works — every minute it wakes up, checks the schedule, and runs matching jobs.

Why Use Crontab?

Manual tasks that are repetitive are a recipe for human error. The more times you do the same thing, the more likely you are to make a mistake — maybe because you're tired, or distracted, or simply forget. Crontab eliminates this risk entirely.

  • Repetitive tasks: Running the same script every hour, day, or month.
  • Non-business hours automation: Backups at 2 AM when no users are active.
  • Maintenance tasks: Cleaning log files, rotating certificates, sending reports.
  • Cost optimisation: Automatically starting and stopping EC2 instances based on business hours.

✅ Real AWS Use Case: A crontab job on an EC2 instance can automatically back up data to S3 every night at midnight — no human intervention needed, no risk of forgetting.

Crontab Syntax — The 5-Star Expression

Every crontab entry follows a fixed format. It looks intimidating at first, but once you understand it, it becomes second nature.

Figure 3: The five-field crontab expression — each position controls a different unit of time.

The format is:

* * * * * /path/to/command
│ │ │ │ │
│ │ │ │ └── Day of week  (0–7, where 0 and 7 = Sunday)
│ │ │ └──── Month        (1–12)
│ │ └────── Day of month (1–31)
│ └──────── Hour         (0–23)
└────────── Minute       (0–59)

A * (asterisk) in any field means "every" — so * * * * * means "every minute of every hour of every day."

📚 According to AWS documentation, cron expressions are also used directly in Amazon EventBridge (formerly CloudWatch Events) to schedule Lambda functions, EC2 operations, and other AWS automations — making this syntax doubly important for cloud work.
📚 Source: Amazon EventBridge Schedule Expressions

Essential Crontab Commands

The command crontab -e opens the crontab file for the current user in the default editor, allowing you to add or edit scheduled jobs.

CommandPurpose
crontab -eEdit (create/modify) the current user's crontab
crontab -lList all scheduled cron jobs for the current user
crontab -rRemove (delete) the current user's entire crontab
crontab -u username -lList crontab for a specific user (requires root)

❌ Common Mistake: crontab -r deletes ALL your cron jobs immediately with no confirmation — be very careful. There is no undo.

Setting the Default Editor for Crontab

By default, crontab may try to open in the vi/vim editor, which can be confusing for beginners. You can force it to use nano instead by setting an environment variable:

export EDITOR=nano

The export command creates an environment variable and makes it available to all programs that run in the current terminal session. In this case, it tells the system to use nano as the editor whenever any program needs to open a text editor.

💡 Remember: This export only lasts for the current terminal session. To make it permanent, add it to your ~/.bashrc or ~/.bash_profile file.

Hands-On: Creating Your First Crontab Job

Here's exactly what was done in the session to create a crontab that runs a shell script every minute:

Step 1: Create a shell script:

nano script.sh

Inside the file, write:

#!/bin/bash
echo "$(date): Cron job ran!" >> /home/ec2-user/cron-demo.log

Step 2: Give execution permissions:

chmod +x script.sh

Step 3: Set nano as the default editor:

export EDITOR=nano

Step 4: Open the crontab editor:

crontab -e

Step 5: Add this line to run the script every minute:

* * * * * /home/ec2-user/script.sh

Save with Ctrl+X, then Y, then Enter.

Step 6: Verify the job was saved:

crontab -l

Step 7: After 2 minutes, check the output file:

cat /home/ec2-user/cron-demo.log

You should see two lines — one per minute — because the script uses >> (append) not > (overwrite).

✅ Why append (>>) and not overwrite (>)? Using >> adds each new output to the end of the file. Using > would delete the previous output every time. For log files, you always want to preserve history — always use >>.

Figure 5: Append vs. overwrite — why cron jobs always use >> to preserve log history.

Installing Cron (If Not Already Installed)

On some minimal Linux systems (like a fresh AWS EC2 instance), cron may not be installed. You'll see "command not found" when you try to run crontab. Here's how to install it:

# On Amazon Linux / CentOS / RHEL:
sudo yum install cronie -y
sudo systemctl enable crond
sudo systemctl start crond

# On Ubuntu / Debian:
sudo apt-get install cron -y
sudo systemctl enable cron
sudo systemctl start cron

Exam Tips — Crontab

⚡ The cron expression 0 2 * * * means 2:00 AM every day — minute 0 of hour 2, every day of every month.

⚡ In AWS, Amazon EventBridge uses the same cron syntax to schedule automated AWS actions like triggering Lambda functions or stopping EC2 instances.

🔗 Soft Links and Hard Links

Before we can understand soft and hard links, we need to understand how Linux actually stores files — because the difference between these two link types is rooted in Linux's file storage architecture.

What is an Inode?

When you create a file in Linux, the file system stores two separate things: the file name (which you see), and the actual file data (stored elsewhere on disk). The bridge between them is called an inode.

An inode (index node) is a data structure in Linux that stores metadata about a file — such as its size, permissions, owner, and the disk location of its data — but NOT its name.

Figure 6: Inodes — Linux separates the file name from the actual data. The inode is the bridge.

Think of it like a library system: the book title (file name) points to a catalog card (inode), which tells you exactly which shelf the book is on (actual data location on disk).

To see inode numbers, use:

ls -li

The command ls -li shows files with their inode numbers — if two files have the same inode number, they point to the exact same data on disk.

What is a Hard Link?

A hard link is an additional directory entry that points to the same inode as the original file — meaning both names refer to the exact same data on disk.

Figure 7: Hard links — two doors leading into the exact same room. Delete one door, the room still exists.

The professor used a great analogy: imagine a room with two doors. Both doors lead into the same room. If you remove one door, the room still exists and is fully accessible through the other door. Hard links work the same way.

⚡ If you delete the original file, the hard link still works because the data (inode) is still present on disk — hard links are true backup references.

To create a hard link:

ln original.txt hardlink.txt

To verify they share the same inode:

ls -li

You will see both files have the same inode number — proof they share the same data.

What is a Soft Link (Symbolic Link)?

A soft link (also called a symbolic link or symlink) is a special file that contains only the path to another file — it is a shortcut, like a Windows desktop shortcut.

Figure 8: Soft links store only the path — if the original file is deleted, the soft link breaks.

Think of a soft link as a sticky note on your desk that says "the file you want is at /home/ec2-user/vig.txt." If someone moves or deletes that file, the sticky note is now pointing at nothing.

To create a soft link:

ln -s /home/ec2-user/original.txt /root/short.txt

The -s flag is what makes it a soft link. Without -s, Linux creates a hard link.

When you do ls -l, a soft link shows up starting with l (for link):

lrwxrwxrwx 1 root root 30 Oct 31 short.txt -> /home/ec2-user/original.txt

❌ If you delete the original file that a soft link points to, the soft link breaks. You'll get "No such file or directory" when you try to access it. In ls -l output, broken soft links turn red.

Practical Demo from Class

Creating a soft link:

# Create original file
echo "Welcome to WinSys" > original.txt

# Create a soft link in the root directory
ln -s /home/ec2-user/original.txt /root/short.txt

# Check it exists and shows as a link (starts with 'l')
ls -l /root/short.txt

# Read through the soft link (works fine while original exists)
cat /root/short.txt

# Delete the original
rm /home/ec2-user/original.txt

# Try to read the soft link now
cat /root/short.txt   # ERROR: No such file or directory

Creating a hard link:

# Create original file
echo "Welcome to WinSys" > original.txt

# Create a hard link
ln original.txt hardlink.txt

# Verify same inode number (they should be identical)
ls -li

# Delete the original
rm original.txt

# Hard link still works!
cat hardlink.txt   # Output: Welcome to WinSys

✅ Quick Memory Trick: Soft link = Shortcut (breaks if target removed). Hard link = Backup (survives original deletion).

🌐 curl and wget — Network Command-Line Tools

Until now, everything we've done in Linux has been about managing files and processes on the machine. But what if you need to get something from the internet — download a file, call an API, check if a website is up? That's where curl and wget come in.

⚡ Both curl and wget are network command-line tools — they allow you to interact with URLs and transfer data over the internet directly from the Linux terminal.

Figure 10: curl and wget — your terminal's connection to the internet.

What is wget?

wget stands for Web GET — it is a non-interactive file downloader that retrieves files from the internet and saves them to disk.

Think of wget like a download manager that works entirely in the terminal. You give it a URL, it downloads the file, and saves it to your current directory. It's that simple.

Basic syntax:

wget [URL]

Example — download a file from the internet:

wget https://example.com/archive.tar.gz

Key wget features:

  • Resumable downloads: If a download is interrupted, wget can pick up where it left off using wget -c [URL].
  • Background downloads: Run in the background with wget -b [URL].
  • Mirror entire websites: wget --mirror [URL] recursively downloads a site.
  • No interactivity required: Works in scripts and cron jobs without needing a user present.

📚 According to AWS documentation, wget is commonly used on EC2 instances to download installer packages, application binaries, and configuration files directly from S3 or the internet — a fundamental DevOps skill.
📚 Source: AWS EC2 User Guide — Installing Software

What is curl?

curl stands for Client URL — it is a data transfer tool that supports many protocols (HTTP, HTTPS, FTP, SFTP, and more) and is primarily used for sending requests to and receiving responses from servers.

curl is more powerful and flexible than wget. While wget is focused on downloading files, curl can do much more — it can send data, set headers, authenticate, and interact with REST APIs. This is why it is the tool of choice for DevOps engineers testing API endpoints.

Figure 11: curl vs wget — curl is a Swiss Army knife; wget is a precision file downloader.

Basic syntax:

curl [URL]

Example — fetch a webpage:

curl https://example.com

Example — call a REST API:

curl https://api.github.com/users/octocat

Example — download a file and save it:

curl -O https://example.com/file.tar.gz

Example — send a POST request with data:

curl -X POST -H "Content-Type: application/json" \
  -d '{"name": "test"}' https://api.example.com/items

Key curl flags you must know:

FlagMeaningExample
-OSave with original filenamecurl -O https://example.com/file.zip

-X METHODSpecify HTTP methodcurl -X POST https://api.example.com
-H "Header: Value"Set a request headercurl -H "Authorization: Bearer token" URL

📝 Overall Summary

  • Crontab: Linux's built-in task scheduler. Uses a 5-field time expression (minute, hour, day-of-month, month, day-of-week) followed by a command. The cron daemon checks every minute and runs matching jobs automatically.
  • Crontab syntax: * * * * * /path/to/script.sh — asterisks mean "every." Use 0 2 * * * for 2 AM daily, 0 1 * * 0 for every Sunday at 1 AM, 0 */6 * * * for every 6 hours.
  • Key crontab commands: crontab -e to edit, crontab -l to list, crontab -r to remove all (dangerous). Set export EDITOR=nano to use nano instead of vim.
  • Inodes: Linux stores file data at inode addresses. File names point to inodes. Two links with the same inode number share the same data.
  • Hard links: Additional names for the same inode. Survive deletion of the original file. Cannot cross file systems. Created with ln original.txt hardlink.txt.
  • Soft links (symlinks): Shortcuts storing only the path to the original file. Break if the original is deleted. Can cross file systems. Created with ln -s /path/original /path/shortcut. Identified by l in ls -l output.
  • wget: Web GET — a file downloader. Downloads files from URLs and saves to disk. Supports resumable downloads. Best for non-interactive file downloading in scripts.
  • curl: Client URL — a versatile data transfer tool supporting HTTP, HTTPS, FTP, and more. Can send POST/PUT/DELETE requests, set headers, and interact with REST APIs. Best for API testing and complex HTTP interactions.
  • AWS relevance: Crontab expressions power EventBridge scheduling. curl is used to query EC2 instance metadata. wget is used to install packages on EC2 instances. Hard/soft links are used in Linux system administration on EC2.
  • Key exam trap: Deleting the original file breaks a soft link but NOT a hard link — because hard links share the inode (data), while soft links only store the path.

Project 1: Automated Log Backup with Crontab

🎯 Objective: Create a shell script that backs up a log file and schedule it to run automatically every 5 minutes using crontab.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier (EC2 t2.micro)

  1. SSH into your EC2 instance and create a logs directory with a sample log file:

    mkdir -p /home/ec2-user/logs
echo "App started at $(date)" >> /home/ec2-user/logs/app.log

    Figure: 📸 Screenshot: Terminal output after creating the logs directory and initial log file.

  2. Create a backup shell script:

    nano /home/ec2-user/backup-logs.sh

    Enter this content:

    #!/bin/bash

cp /home/ec2-user/logs/app.log /home/ec2-user/logs/backup-$TIMESTAMP.log
echo "Backup created at $TIMESTAMP" >> /home/ec2-user/cron-run.log

    Figure: 📸 Screenshot: Nano editor open with the backup script content visible.

    chmod +x /home/ec2-user/backup-logs.sh

  4. Set nano as the default crontab editor and open crontab:

    export EDITOR=nano
crontab -e

    Figure: 📸 Screenshot: Nano editor open for crontab editing.

    */5 * * * * /home/ec2-user/backup-logs.sh

  6. Verify the cron job is saved:

    crontab -l

    Figure: 📸 Screenshot: crontab -l output confirming the job is scheduled.

  7. Wait 5–10 minutes, then check results:

    Figure: 📸 Screenshot: Backup files created and cron-run.log showing multiple entries.

  8. Cleanup: Remove the cron job and files when done:

    crontab -r

Project 4: Automated Backup System with Log Rotation

🎯 Objective: Upgrade the basic backup from Project 1 into a real system — compress backups as .tar.gz, keep only the last 5 backups, and automatically delete older ones. This is how production servers manage disk space.

⏱️ Time: 40–50 minutes

💰 Cost: Free tier

⚡ Why this matters: A backup script that never deletes old files will eventually fill your disk and crash your server. Real DevOps engineers always implement log rotation alongside backups.

  1. Create the project directory and a sample app log to back up:

    mkdir -p /home/ec2-user/app-logs /home/ec2-user/backups
for i in {1..20}; do echo "$(date): Request $i processed OK" >> /home/ec2-user/app-logs/app.log; done
cat /home/ec2-user/app-logs/app.log

    Figure: 📸 Screenshot: Initial app.log created with 20 sample entries.

  2. Create the backup-with-rotation script:

    nano /home/ec2-user/smart-backup.sh

    Enter this complete script:

    #!/bin/bash

# Configuration
LOG_FILE="/home/ec2-user/app-logs/app.log"
BACKUP_DIR="/home/ec2-user/backups"
KEEP=5
SCRIPT_LOG="/home/ec2-user/backup-history.log"

# Create backup with timestamp
TIMESTAMP=$(date +%Y-%m-%d_%H-%M-%S)
BACKUP_NAME="backup-$TIMESTAMP.tar.gz"

# Compress the log file into a .tar.gz archive
tar -czf "$BACKUP_DIR/$BACKUP_NAME" "$LOG_FILE"

echo "$(date): Created $BACKUP_NAME" >> "$SCRIPT_LOG"

# Count existing backups
BACKUP_COUNT=$(ls "$BACKUP_DIR"/backup-*.tar.gz 2>/dev/null | wc -l)
echo "$(date): Total backups: $BACKUP_COUNT" >> "$SCRIPT_LOG"

# If more than KEEP backups exist, delete the oldest ones
if [ "$BACKUP_COUNT" -gt "$KEEP" ]; then
    DELETE_COUNT=$((BACKUP_COUNT - KEEP))
    ls -t "$BACKUP_DIR"/backup-*.tar.gz | tail -"$DELETE_COUNT" | xargs rm -f
    echo "$(date): Deleted $DELETE_COUNT old backup(s). Kept last $KEEP." >> "$SCRIPT_LOG"
fi

    Figure: 📸 Screenshot: smart-backup.sh open in nano showing the full rotation logic.

  3. Make it executable and do a manual test run first:

    chmod +x /home/ec2-user/smart-backup.sh
/home/ec2-user/smart-backup.sh
ls -lh /home/ec2-user/backups/
cat /home/ec2-user/backup-history.log

    Figure: 📸 Screenshot: First manual run — compressed backup file created, history log updated.

  4. Schedule it with crontab to run every minute (for testing purposes):

    export EDITOR=nano
crontab -e

    Add this line:

    * * * * * /home/ec2-user/smart-backup.sh

    Save and exit.

  5. Wait 7–8 minutes, then check that rotation is working — you should see exactly 5 backups:

    ls -lt /home/ec2-user/backups/
cat /home/ec2-user/backup-history.log

    Figure: 📸 Screenshot: Exactly 5 backups remain — rotation deleted the older ones automatically.

  6. Verify a backup can actually be restored (extract it):

    mkdir -p /home/ec2-user/restore-test
LATEST=$(ls -t /home/ec2-user/backups/backup-*.tar.gz | head -1)
tar -xzf "$LATEST" -C /home/ec2-user/restore-test/
cat /home/ec2-user/restore-test/home/ec2-user/app-logs/app.log

    Figure: 📸 Screenshot: Backup successfully extracted and original log content restored.

  7. Cleanup:

    crontab -r
rm -rf /home/ec2-user/app-logs /home/ec2-user/backups /home/ec2-user/restore-test /home/ec2-user/backup-history.log /home/ec2-user/smart-backup.sh

Project 5: Broken Soft Link Detector

🎯 Objective: Write a script that scans a directory, finds all soft links, detects which ones are broken (dangling), and logs a report. This is a real sysadmin task — broken symlinks on servers cause silent failures that are hard to debug manually.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier

  1. Create a test directory with working and broken soft links:

    mkdir -p /home/ec2-user/link-test

# Create real files
echo "Config A" > /home/ec2-user/link-test/config-a.txt
echo "Config B" > /home/ec2-user/link-test/config-b.txt

# Create working soft links

Project 6: API Health Checker with cron

🎯 Objective: Build a monitoring script that uses curl to check an API every minute, logs the HTTP status code and response time, and alerts when the API is down. This is the foundation of every production monitoring system.

⏱️ Time: 35–45 minutes

💰 Cost: Free tier

⚡ Why this matters: Monitoring APIs for health is one of the most common DevOps responsibilities. This project uses curl's built-in timing to measure response time — the same approach used by tools like Nagios and Datadog at their core.

  1. Create the health checker script:

    nano /home/ec2-user/api-health-check.sh

    Enter this script:

    #!/bin/bash

# API to monitor (uses a public test endpoint)
API_URL="https://httpbin.org/get"
LOG_FILE="/home/ec2-user/api-health.log"
ALERT_LOG="/home/ec2-user/api-alerts.log"
TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')

# Use curl to get HTTP status code and response time
HTTP_STATUS=$(curl -o /dev/null -s -w "%{http_code}" --max-time 10 "$API_URL")
RESPONSE_TIME=$(curl -o /dev/null -s -w "%{time_total}" --max-time 10 "$API_URL")

# Log the result
echo "$TIMESTAMP | Status: $HTTP_STATUS | Response time: ${RESPONSE_TIME}s" >> "$LOG_FILE"

# Alert if status is not 200 (OK)
if [ "$HTTP_STATUS" != "200" ]; then
    echo "$TIMESTAMP | ALERT: $API_URL returned HTTP $HTTP_STATUS" >> "$ALERT_LOG"
    echo "$TIMESTAMP | ALERT: API DOWN — HTTP $HTTP_STATUS"
else
    echo "$TIMESTAMP | OK: API is healthy (${RESPONSE_TIME}s)"
fi

Project 7: Auto Downloader with Retry Logic (wget)

🎯 Objective: Build a download script that automatically retries on failure, logs each attempt, and reports success or permanent failure. This is a real production pattern used in CI/CD pipelines and server provisioning scripts.

⏱️ Time: 25–35 minutes

💰 Cost: Free tier

  1. Create the retry downloader script:

    nano /home/ec2-user/smart-download.sh

    Enter this script:

    #!/bin/bash

# Configuration
DOWNLOAD_URL="${1}"
OUTPUT_DIR="/home/ec2-user/downloads"
MAX_RETRIES=3
RETRY_DELAY=5
DOWNLOAD_LOG="/home/ec2-user/download-history.log"

if [ -z "$DOWNLOAD_URL" ]; then
    echo "Usage: $0 "
    exit 1
fi

mkdir -p "$OUTPUT_DIR"
FILENAME=$(basename "$DOWNLOAD_URL")
TIMESTAMP=$(date '+%Y-%m-%d %H:%M:%S')

echo "==============================" >> "$DOWNLOAD_LOG"
echo "Download started: $TIMESTAMP" >> "$DOWNLOAD_LOG"
echo "URL: $DOWNLOAD_URL" >> "$DOWNLOAD_LOG"

ATTEMPT=0
SUCCESS=false

while [ $ATTEMPT -lt $MAX_RETRIES ]; do
    ATTEMPT=$((ATTEMPT + 1))
    echo "$(date '+%H:%M:%S') Attempt $ATTEMPT of $MAX_RETRIES..." | tee -a "$DOWNLOAD_LOG"

    # Try download; exit code 0 = success
    if wget -q --tries=1 --timeout=30 -O "$OUTPUT_DIR/$FILENAME" "$DOWNLOAD_URL"; then
        SUCCESS=true
        FILE_SIZE=$(ls -lh "$OUTPUT_DIR/$FILENAME" | awk '{print $5}')
        echo "$(date '+%H:%M:%S') SUCCESS: Downloaded $FILENAME ($FILE_SIZE)" | tee -a "$DOWNLOAD_LOG"
        break
    else
        echo "$(date '+%H:%M:%S') FAILED on attempt $ATTEMPT. Retrying in ${RETRY_DELAY}s..." | tee -a "$DOWNLOAD_LOG"
        sleep $RETRY_DELAY
    fi
done

if [ "$SUCCESS" = false ]; then
    echo "$(date '+%H:%M:%S') PERMANENT FAILURE: Could not download after $MAX_RETRIES attempts." | tee -a "$DOWNLOAD_LOG"
    rm -f "$OUTPUT_DIR/$FILENAME"
    exit 1
fi

🤔 Reflection Questions

1. Your EC2 instance needs to send a daily report to S3 at 3:30 AM every weekday (Monday–Friday). What crontab expression would you use?

💡 Hint

The fields are: minute, hour, day-of-month, month, day-of-week. Weekdays are 1–5. "Every" is asterisk. 3:30 AM means minute 30, hour 3.

2. You create a soft link to a config file. A teammate deletes the original config file. What happens when you try to open the soft link? How would using a hard link have changed this outcome?

💡 Hint

Soft links store the path. Hard links share the inode. Think about what happens when the path target disappears versus when a name pointing to an inode is removed.

3. You need to call a REST API endpoint with a POST request, pass a JSON body, and include an Authorization header. Would you use curl or wget? Write the command.

💡 Hint

One of these tools supports setting custom headers with -H and sending request bodies with -d. The other is primarily for downloading files.

4. Two files show the same inode number in ls -li. What does this tell you? Which type of link was used to create the second file?

💡 Hint

Inode numbers identify data blocks on disk. Same inode = same data. Only one type of link shares the inode with the original.

5. You want to create a cron job that runs every 15 minutes but only between 9 AM and 5 PM, Monday to Friday. How would you approach writing this expression?

💡 Hint

Use step values (*/15) for minutes, a range (9-17) for hours, and a range (1-5) for day-of-week. The day-of-month and month fields should be wildcards.

6. A colleague says "I'll just use wget for everything — it downloads files and that's all I ever need." What scenarios would prove their approach insufficient?

💡 Hint

Think about REST APIs, PUT/DELETE requests, custom headers, authentication tokens, and reading responses programmatically in scripts.
