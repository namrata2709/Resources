🌐 1. What is Amazon EFS?

Imagine a USB drive that every computer in a building can plug into at the same time — everyone reads and writes simultaneously, the drive grows automatically, and no one manages the hardware. That is Amazon EFS, but in the cloud for EC2 instances.

Amazon Elastic File System (EFS) is a fully managed, serverless, elastic network file system that allows multiple EC2 instances to share the same storage simultaneously using the NFSv4.1 protocol.

Figure 1: Production EFS architecture — an ALB distributes user traffic across multiple EC2 instances in an Auto Scaling Group, all reading from the same EFS file system. This is the project you'll build.

💡 "Elastic" means EFS grows and shrinks automatically. You never provision a fixed size. Linux sees it as 8 exabytes (effectively unlimited), and you pay only for what you actually store. Real-world uses: shared web content, CMS user uploads, data analytics, centralized logs, user home directories in a fleet.

Why not just use EBS?

EBS (Elastic Block Store) is like a hard drive attached to one computer — only that one computer can use it at a time. If you have 10 EC2 instances in an Auto Scaling Group and one user uploads a file, the other 9 instances can't see it without complex syncing solutions. EFS solves this: all 10 instances mount the same file system and see the same files instantly.

⚙️ 2. Core Concepts — NFS, Mount Targets, Security Groups

What is NFS?

EFS uses the Network File System protocol version 4.1 (NFSv4.1) which runs over TCP port 2049. NFS is an industry-standard protocol from the 1980s that lets computers access files stored on another computer over a network — as if those files were local. Your application just writes to /efs/myfile.txt and NFS handles all network communication invisibly. No SDK, no API calls — standard file I/O.

What is a Mount Target?

EFS does not connect directly to EC2 instances. Instead it places mount targets inside your VPC — one per Availability Zone. A mount target is an ENI (Elastic Network Interface) — a virtual network card — sitting in a subnet, assigned a private IP, and listening on TCP port 2049.

Figure 2: Mount targets sit inside your VPC — one per AZ. EC2 instances connect to the mount target in their own AZ for low latency and no cross-AZ data charges. Both AZs see the same data.

💡 Why one mount target per AZ? When EC2 and mount target are in the same AZ, NFS traffic stays local — fast and free. Crossing AZs adds latency (~1ms) and inter-AZ data transfer charges. In an Auto Scaling Group across 3 AZs, you want mount targets in all 3 AZs so every instance gets a local connection.

Security Group Chaining

EFS uses two linked security groups. The EFSClient SG (or EC2 SG) is attached to your EC2 instances. The EFS Mount Target SG is attached to mount targets, with one inbound rule: NFS (TCP 2049) sourced from the EFSClient SG ID. Any instance in EFSClient gets automatic NFS access — even as instances scale, fail, or change IPs.

Figure 3: Security group chaining — the mount target SG allows NFS from any EC2 in the EFSClient SG, regardless of IP. New Auto Scaling instances automatically get access just by being in the EFSClient SG.

✅ Mental model: EFSClient SG = the membership card. EFS Mount Target SG = the door policy. The door allows anyone holding an EFSClient card to enter on port 2049. No IP address management needed — essential for Auto Scaling.

❌ Common interview trap: "Can I use EFS for my database?" Technically possible but never recommended. Databases need sub-millisecond block I/O. EFS network latency adds up with thousands of random reads per second. Always use EBS (io2/gp3) for databases.
❌ Why not S3 for this project? S3 stores objects accessed via HTTPS API. In this project the web server expects a traditional Linux file path — it reads files with open() system calls. EFS behaves like a mounted drive, S3 doesn't. EFS fits; S3 doesn't without rewriting the application.
⚡ The one-sentence rule: Multiple EC2 instances needing to share the same files simultaneously → EFS. One instance needing fast local block storage → EBS. Global object storage or API-accessed assets → S3.

🔒 Task 1 — Create the EFS Security Group

EFS uses a chained security group model. The EC2 instance uses the EFSClient security group (already created for you in the lab). You create a new SG for the EFS mount targets.

  1. Go to EC2 → Security Groups.
  2. Find EFSClient — copy its Security Group ID (format: sg-0xxxxxxxxxxxxxxxxx). Paste it in a text editor — you need it in the next step.
  3. Click Create security group:
    • Name: EFS Mount Target
    • Description: Inbound NFS access from EFS clients
    • VPC: Lab VPC
  4. Under Inbound rules → Add rule: Type = NFS (auto-fills port 2049) | Source = Custom → paste EFSClient SG ID.
  5. Click Create security group.
✅ After creation: one inbound rule — NFS | TCP | 2049 | Source: EFSClient SG ID. That's all it needs.
💡 Why reference an SG instead of an IP? In Auto Scaling environments, EC2 instances launch and terminate constantly with changing IPs. By referencing the EFSClient SG ID, any instance that belongs to that group automatically gets NFS access — no manual IP updates ever needed. This is how production systems work.

🔌 Task 4 — Mount the EFS File System

Step 1 — Create the mount directory

sudo mkdir efs
💡 What is a mount point? In Linux, storage doesn't appear as drive letters. It attaches to directories. After mounting EFS to efs/, anything you write inside that directory is physically stored on EFS — not on the EC2's local disk. The directory is the doorway; EFS is the room behind it.

Step 2 — Get your real mount command from the console

Don't use the placeholder command in the lab PDF. Get the FS-specific command from EFS:

  1. EFS → File Systems → your file system → click Attach (top right).
  2. Copy the command from the "Using the NFS client" section.
sudo mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport fs-XXXXXXXX.efs.us-west-2.amazonaws.com:/ efs
💡 NFS options explained:
nfsvers=4.1 — force NFSv4.1
rsize/wsize=1048576 — 1 MB read/write buffer (optimal for EFS large transfers)
hard — retry indefinitely on connection drop (don't silently fail)
timeo=600 — 60-second timeout (value is in tenths of seconds)
retrans=2 — retry each operation 2 times
noresvport — don't use privileged source ports (required by EFS)

Step 3 — Verify the mount

sudo df -hT

Expected EFS line in output:

fs-531babfa.efs.us-west-2.amazonaws.com:/  nfs4  8.0E  0  8.0E  0%  /home/ec2-user/efs
⚡ The 8.0E (8 exabytes) is EFS's way of saying "effectively unlimited." Linux requires a size — EFS reports its theoretical maximum. You pay only for bytes actually stored, not the 8E displayed.
❌ Mount command hangs with no output? Press Ctrl+C. Almost always = wrong SG on mount target (left the default). EFS → Network → Edit → replace default SG with EFS Mount Target SG → retry.

🔑 Ext. Task 1 — Fix File System Permissions

After mounting, the EFS root directory is owned by root. Try writing a file:

touch efs/test.txt
# Output: touch: cannot touch 'efs/test.txt': Permission denied

Fix ownership so ec2-user can write:

sudo chown ec2-user:ec2-user efs/
ls -ld efs/

Verify ec2-user is now the owner, then write again:

touch efs/test.txt
ls -la efs/
✅ The file appears. This chown step is almost always required after a fresh EFS mount. In production you would create subdirectories with appropriate ownership immediately after setup, per application requirements.

🔁 Ext. Task 6 — Configure Automatic Mount After Reboot

The current mount disappears on reboot. To make it permanent, add an entry to /etc/fstab:

sudo nano /etc/fstab

Add this line at the bottom (replace fs-XXXXXXXX with your actual FS ID):

fs-XXXXXXXX:/  /home/ec2-user/efs  nfs4  defaults,_netdev  0  0

Save and exit: Ctrl+X → Y → Enter

Test the entry without rebooting:

sudo umount efs/
sudo mount -a
df -hT | grep efs
❌ The _netdev option is not optional. Without it, Linux tries to mount EFS during early boot before the network interface and DNS are ready. The mount fails silently, the instance boots with an empty /efs directory, and if it's in an Auto Scaling Group, it fails its health check and gets terminated — triggering a cascade. Always include _netdev for any network file system in fstab.

🔎 Ext. Task 9 — Investigate File System Activity

# Show all NFS mounts with their applied options
mount | grep nfs

# Show NFS client statistics — ops, retransmissions, timeouts
nfsstat -c

# Show which processes have files open on EFS (for debugging "device busy" errors)

🔌 Ext. Task 10 — Try the EFS Helper Mount Method

The professor encourages comparing both mount methods. Unmount the current NFS client mount and try the EFS helper:

# Unmount current
sudo umount efs/

# Mount using EFS helper (much simpler command)
sudo mount -t efs fs-XXXXXXXX:/ efs

# Verify

Notice the filesystem source in df output is now 127.0.0.1:/ instead of the EFS DNS name. The EFS helper starts a local stunnel proxy that wraps NFS traffic in TLS encryption before forwarding to EFS. The loopback address (127.0.0.1) is the local proxy — this is expected, not an error.

🔑 Ext. Task 18 — Create and Use an EFS Access Point

⚡ Real-world context: Access Points are one of the most important EFS production features. They let you give different applications a different isolated view of the same EFS — each sees only its own directory, with enforced POSIX ownership, even if the container runs as root. Used heavily in ECS, EKS, and Lambda.

What is an Access Point?

An Access Point is a named entry into EFS that enforces three things: a root directory (the app sees / but is actually inside /app1 on the real EFS), a POSIX user identity (all writes appear to come from a specific UID/GID regardless of who wrote them), and automatic directory creation (the directory is created if it does not exist).

Create an Access Point via CLI

aws efs create-access-point \
  --file-system-id fs-XXXXXXXX \
  --posix-user Uid=1000,Gid=1000 \
  --root-directory "Path=/app1,CreationInfo={OwnerUid=1000,OwnerGid=1000,Permissions=755}" \
  --tags Key=Name,Value=app1-access-point

# Note the AccessPointId in the output: fsap-XXXXXXXXX

Mount using the Access Point

sudo mkdir /efs-app1

# Requires EFS helper (mount -t efs)
sudo mount -t efs \
  -o tls,accesspoint=fsap-XXXXXXXXX \
  fs-XXXXXXXX:/ /efs-app1

ls -la /efs-app1/
df -hT | grep efs
💡 What you will notice: The /efs-app1 mount looks like the root of a file system but is actually just the /app1 subdirectory of your EFS. You cannot navigate above it with cd .. This isolation is the key security benefit — a compromised container cannot read files belonging to other applications on the same EFS.

Test POSIX user enforcement

echo "written via access point" > /efs-app1/test.txt
ls -lan /efs-app1/test.txt
# Shows UID 1000 regardless of who you are

Clean up

sudo umount /efs-app1
aws efs delete-access-point --access-point-id fsap-XXXXXXXXX
✅ Interview answer — "How do you isolate multiple apps on a shared EFS?" Create one Access Point per application, each pointing to a different subdirectory with its own POSIX UID/GID. Mount each Access Point in its container via the EFS CSI driver (Kubernetes) or ECS task definition volume. Each app sees its own isolated file system root and ownership is enforced at the storage layer.

🌍 Ext. Task 20 — Real-World Pattern: Atomic Config File Propagation

⚡ Real-world context: A fleet of 20 web servers all need to pick up a config change without restarting. EFS makes this simple — update one file and every server reading it sees the new version on the next read cycle. This task builds that pattern and shows the correct atomic update technique.

Step 4 — Atomic config update (the correct production pattern)

❌ Never write directly to the live config file in production. Direct writes create a race condition — a server might read a half-written file mid-write and crash. The correct pattern is write-then-rename.

debug=false

log_level=info

echo "Atomic update to v3.0 complete"
✅ mv (rename) is atomic on POSIX file systems including EFS. A reader either gets the old version or the new version, never a half-written file. This is the correct pattern for all production config updates via shared storage.

🔧 Guided Failure Exercise — Break and Fix EFS

⚡ Understanding how things break is more valuable than knowing how they work when everything is fine. Each failure below is something you will encounter in real cloud environments.

💥 Failure 1 — Wrong Security Group (the silent hang)

In EFS console → Network tab → Edit → remove EFS Mount Target SG from one AZ, add the default SG → Save. Then:

sudo umount efs/
sudo mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport fs-XXXXXXXX.efs.us-west-2.amazonaws.com:/ efs

What you observe: The command hangs with no output. No error, no progress — Linux retries the TCP SYN indefinitely because the SG drops the packet instead of returning RST.

Fix: Ctrl+C → EFS → Network → Edit → restore EFS Mount Target SG → wait 30s → retry.

❌ A hanging mount = security group problem first, always. Never blame the NFS config before checking the SG.

💥 Failure 2 — Missing Mount Directory

sudo rmdir efs/
sudo mount -t nfs4 -o nfsvers=4.1 fs-XXXXXXXX.efs.us-west-2.amazonaws.com:/ efs

What you observe: mount: mount point efs does not exist — immediate, clear error.

Fix: sudo mkdir efs && sudo mount ...

💥 Failure 3 — fstab Without _netdev

sudo nano /etc/fstab
# Edit: remove _netdev from your EFS entry → save

What you observe: sudo mount -a works (network is already up). The real failure only appears on cold boot — Linux tries to mount EFS before DNS resolves, fails silently, and you log into an empty efs/ directory with no error in the console. In an ASG, the instance fails health checks and gets terminated.

Fix: Always include _netdev. Put it back.

💥 Failure 4 — Permission Denied Writing

sudo chown root:root efs/
touch efs/newfile.txt

What you observe: Permission denied

Fix: sudo chown ec2-user:ec2-user efs/

💥 Failure 5 — Wrong File System ID

sudo mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport fs-00000000.efs.us-west-2.amazonaws.com:/ efs

What you observe: DNS lookup failure or long hang. No file system with that ID exists.

Fix: Always get the mount command directly from EFS → Attach in the console. Never type the FS ID manually.

✅ Failure exercise summary — key lessons:
  • Hanging mount with no error = security group problem (SG dropped the TCP SYN)
  • Immediate error = missing directory or wrong DNS name
  • Files gone after reboot = missing fstab entry or missing _netdev
  • Permission denied on write = EFS root owned by root — chown fix
  • Always get mount commands from EFS → Attach, never from memory

🔊 The Noisy Neighbor Problem

AWS data centers are multi-tenant — thousands of customers share the same physical hardware. AWS implements fairness controls to prevent any one tenant from consuming all shared I/O capacity. This is the noisy neighbor problem in cloud environments.

Think of an apartment building: if your neighbor blasts music at 2am it affects you, even though you're paying for your own space. AWS is building management — it enforces "quiet hours" on I/O to protect all tenants.

For EFS in the lab this means:

  • First fio run: 85 seconds. Second run (same command): 18 minutes. Burst credits depleted + fairness throttling both active.
  • Small instances (t2.micro, t3.micro) are more affected — AWS packs more small instances per physical host, increasing contention.
  • Time of day matters: weekday afternoons = heavy contention; weekend nights = much faster.
  • Always wait 5–10 minutes between intensive I/O tests to let credits partially replenish and throttling to reset.
💡 Watch the BurstCreditBalance CloudWatch metric — when it hits 0, throughput drops to baseline (50 MiB/s per TiB of storage). Credits replenish at 1 MiB/s per TiB of storage — so a small lab file system takes overnight to fully replenish.

📝 Overall Summary

  • EFS = shared NFS storage: Multiple EC2 instances mount the same file system simultaneously. Fundamental difference from EBS (one-to-one exclusive) and S3 (object API, no POSIX).
  • NFSv4.1 on TCP 2049: Industry-standard protocol. EFS helper adds TLS (stunnel) on top. NFS client mount shows EFS DNS; EFS helper shows 127.0.0.1 in df.
  • Mount targets = ENIs in your VPC: One per AZ. Verify Status: Available and correct SG before mounting. Two mount targets = high availability across AZs.
  • Security group chaining: EFSClient SG on EC2 → referenced as source in EFS Mount Target SG (port 2049). No IP management — scales automatically with Auto Scaling.
  • Task 0 (trainer fix): Install packages first, then wait 3–5 min (do Tasks 1–2 in console). Never mount immediately after install — NFS daemons need time.
  • 8 exabytes in df: Elastic — not provisioned capacity. Pay for bytes stored, not the display value. No pre-allocation needed.
  • Permissions: EFS root owned by root after mount. Always sudo chown ec2-user:ec2-user /efs before writing (Ext. Task 1).
  • fstab with _netdev: Required for persistent mounts. Prevents boot failure when network is not ready — critical for Auto Scaling launch templates.
  • Burst credits: Enable throughput above baseline. Deplete with heavy I/O, replenish overnight at 1 MiB/s per TiB. Watch BurstCreditBalance in CloudWatch.
  • CloudWatch metrics: PermittedThroughput (allowed max) | DataWriteIOBytes Sum÷60 (actual MB/s) | BurstCreditBalance (remaining credits).
  • File locking (POSIX): EFS supports flock and fcntl advisory locks across instances — proven in Ext. Task 13. Databases and CMS tools work correctly.
  • tcpdump insight: Every file operation generates multiple NFS protocol calls (LOOKUP, GETATTR, WRITE, SETATTR). A single ls -la on 100 files = 100+ NFS ops (Ext. Task 12).
  • strace insight: Applications use identical syscalls (write, open, close) for local disk and EFS. The kernel NFS client handles all translation — zero application changes needed.
  • Access Points: Enforce a root directory and POSIX UID/GID per application. Each app sees its own isolated root. Used in ECS, EKS, Lambda for multi-tenant EFS (Ext. Task 18).
  • Lifecycle Management: Automatically moves files not accessed in N days to IA storage (~$0.025/GB vs ~$0.30/GB). Can cut EFS costs 80%+ for archive workloads (Ext. Task 22).
  • Atomic config updates: Always use write-to-temp + mv (rename) pattern. Direct writes to live files risk serving half-written config during write operations (Ext. Task 20).
  • rsync for migration: Initial full sync + incremental delta syncs = zero-downtime migration from local disk to EFS. AWS DataSync for terabyte-scale migrations (Ext. Task 17).
  • Debugging hanging mount: Check in order — SG on mount target → iptables port 2049 → DNS resolution → mount target status → NFS daemons. Covers 95% of incidents.
  • Lab Project: ALB → Auto Scaling Group → multiple EC2 instances → single EFS. Proves compute can scale independently while storage stays consistent across all instances.
  • EFS vs EBS vs S3 (exam): Multiple instances need same files → EFS. Single instance needs fast block I/O → EBS. Global object access via API → S3.
