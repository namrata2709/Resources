🌐 Introduction

Imagine you just built a beautiful website. You stored all the files in an Amazon S3 bucket, made it public, and gave your customers the S3 URL. It works! But then the complaints start rolling in — "Your website is so slow!" from users in Australia, and your security team is saying, "Why is our S3 bucket open to the entire internet?"

This session solves both of those problems at once. You will learn how Amazon CloudFront acts like a global delivery network — caching your website content at hundreds of edge locations around the world so every user gets lightning-fast load times, no matter where they are. And you will see how Origin Access Control (OAC) lets you keep your S3 bucket completely private, allowing only CloudFront to read from it.

Then, because a long CloudFront URL is not exactly customer-friendly, you will learn how Amazon Route 53 maps your human-readable domain name (like www.mycompany.com) to your CloudFront distribution — so customers never have to see or remember a raw AWS URL.

Finally, you will learn about the AWS SDK — specifically Boto3 for Python — which lets developers talk to AWS programmatically. Instead of clicking through the console, a developer can write a script that launches EC2 instances, uploads files to S3, and much more, all from code.

Figure 1: Full architecture — S3 (private) → CloudFront (CDN) → Route 53 (DNS) → Global Users

⚡ This session covers three deeply connected services: CloudFront for global content delivery, Route 53 for DNS routing, and the AWS SDK (Boto3) for developer-level automation. Together, they represent how real production websites are built and managed on AWS.

🔴 The Problem We Are Solving

Before diving into CloudFront, it helps to understand exactly what problem it solves. This section walks through the complete journey of a static website on AWS, and the two critical issues that push teams toward CloudFront.

Step 1: S3 Static Website Hosting

Amazon S3 can host static websites — pages made of HTML, CSS, JavaScript, and images with no server-side processing. You simply upload your files to an S3 bucket, enable static website hosting in the bucket properties, and AWS gives you a URL like:

http://my-bucket.s3-website.ap-south-1.amazonaws.com

For customers to access this URL, the bucket must be public. That means removing the "Block all public access" setting and adding a bucket policy like this:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*"
    }
  ]
}

The Principal: "*" means anyone on the internet can read your files. The action s3:GetObject is read-only — nobody can modify or delete your content — but the bucket is still wide open to the world, which makes security teams nervous.

Figure 2: S3 public website — works, but has latency and security problems

Problem 1: High Latency

Your S3 bucket lives in one AWS region — for example, Mumbai (ap-south-1). Every time a customer from Australia, Canada, or Europe requests your website, their request must travel all the way to Mumbai and back. The physical distance creates high latency, meaning the website loads slowly for international users.

❌ The Distance Problem: A user in Sydney making a request to a server in Mumbai is physically routing data roughly 10,000 km each way. Even at the speed of light through fiber, this adds hundreds of milliseconds of delay — which users notice instantly.

Problem 2: Security Concerns

Opening your S3 bucket to Principal: "*" means the bucket is publicly accessible to anyone who knows the S3 URL. Even though they can only read files (not modify them), many organizations have compliance policies that forbid exposing storage buckets directly to the internet. You want to serve your content publicly — but through a controlled gateway, not by exposing the raw storage layer.

⚡ The Goal: Keep the S3 bucket completely private — no public access, no bucket policy for the internet — while still serving its content to users worldwide with low latency. CloudFront solves both problems simultaneously.

☁️ Amazon CloudFront

Think of CloudFront like a chain of mini warehouses spread around the world. Imagine you run a warehouse in Mumbai (your S3 bucket). Every time someone in Australia wants a package, they order it from Mumbai — slow and expensive. Now imagine you open small local depots in Sydney, London, Toronto, and Tokyo. You stock those depots with copies of your most popular products. Now when someone in Sydney orders, the depot in Sydney delivers it in minutes. That is CloudFront. Your S3 bucket is the central warehouse, and CloudFront's edge locations are the local depots.

What is CloudFront?

Amazon CloudFront is a Content Delivery Network (CDN) service that distributes content to end users with low latency by caching it at geographically distributed edge locations.

As of 2024, CloudFront has over 600+ Points of Presence (PoPs) including edge locations and regional edge caches across more than 90 cities in 48 countries.

Figure 3: CloudFront edge locations globally — content cached close to every user

How CloudFront Works — Step by Step

Here is exactly what happens when a user visits your CloudFront-fronted website for the first time:

  1. The user's browser requests www.mycompany.com.

  2. DNS routes the request to the nearest CloudFront edge location.

  3. CloudFront checks its local cache — is a copy of this file already stored here?

  4. Cache miss: The file is not cached yet. CloudFront fetches it from the origin (your S3 bucket), stores a copy locally, and delivers it to the user.

  5. Cache hit: The file is already cached. CloudFront delivers it directly from the edge location — no round trip to S3 needed.

  6. All subsequent users in that region get the cached copy — fast delivery, no load on S3.

Figure 4: Cache hit vs cache miss flow in CloudFront

💡 Cache TTL (Time-To-Live): Cached files are not stored forever. Each file has a TTL, which defaults to 24 hours (86,400 seconds). After the TTL expires, CloudFront re-fetches the file from the origin on the next request. You can customize TTL per file type or invalidate the cache manually.

Creating a CloudFront Distribution

A distribution is CloudFront's term for a deployment configuration. When you create a distribution, you are defining how CloudFront should behave for your content. Creating a distribution requires three key pieces of information:

Three Required Inputs

Every CloudFront distribution requires: Origin (where the content lives), Default Root Object (the landing page), and permissions (how CloudFront is allowed to access the origin).

1. Origin — The source of your content. For static websites, this is usually an S3 bucket. For dynamic web apps, it might be an Application Load Balancer or a custom HTTP server.

2. Default Root Object — When a user visits the root URL of your distribution (e.g., https://abc123.cloudfront.net/), CloudFront needs to know which file to serve. For most websites this is index.html.

3. Origin Access Control (OAC) — This is the permission mechanism that lets you keep S3 private while allowing CloudFront to read from it.

Figure 5: Three required inputs when creating a CloudFront distribution

Origin Access Control (OAC)

Origin Access Control (OAC) is a CloudFront feature that allows only a specific CloudFront distribution to access a private S3 bucket, replacing the older Origin Access Identity (OAI).

Here is how it works:

  1. You create an OAC and attach it to your CloudFront distribution.
  2. CloudFront receives a unique distribution ID (e.g., E2QWRUHEXAMPLE).
  3. You add a bucket policy to your S3 bucket that says: "Allow s3:GetObject only from this specific CloudFront distribution." You reference the distribution ARN in the policy condition.
  4. All other access to S3 — including direct S3 URLs — is denied.
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "cloudfront.amazonaws.com"
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-bucket/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::123456789:distribution/E2QWRUHEXAMPLE"
        }
      }
    }
  ]
}

✅ OAC vs OAI: Origin Access Identity (OAI) was the older method for locking down S3 origins. OAC is the recommended replacement for OAI as it supports all S3 regions, supports SSE-KMS encryption, and supports dynamic requests (POST, PUT, DELETE) to S3.

CloudFront URL and Custom Domain

Once your distribution is deployed (which can take 5–20 minutes), CloudFront gives you a distribution domain name that looks like:

d1234abcdef8.cloudfront.net

Users can now access your website at this URL. The S3 bucket URL no longer works (because you removed public access), but the CloudFront URL does. However, this CloudFront URL is not user-friendly. Nobody is going to remember d1234abcdef8.cloudfront.net. That is where Route 53 comes in — to map a friendly domain name to this CloudFront endpoint.

CloudFront Pricing

CloudFront uses a pay-as-you-go model with no upfront fees.

According to AWS documentation, CloudFront pricing is based on three dimensions: data transfer out to the internet (per GB), HTTP/HTTPS request count (per 10,000 requests), and the price class (which regions you serve from). The free tier includes 1 TB of data transfer out and 10 million HTTP/HTTPS requests per month for the first year.

📚 Source: AWS CloudFront Pricing

When to Use CloudFront

CloudFront is the right choice when you need any of the following:

  • Serve a static website globally with low latency
  • Keep your S3 bucket private while still delivering its content to users
  • Accelerate API responses by caching at the edge
  • Stream video content to global audiences (CloudFront supports HLS and MPEG-DASH)
  • Protect your application from DDoS attacks using AWS Shield integration
  • Add SSL/TLS (HTTPS) to content stored in S3 (S3 static website endpoints do not support HTTPS natively)

❌ When NOT to use CloudFront: CloudFront is not suitable for highly dynamic content that changes every request (like real-time stock prices or personalized dashboards), since caching would serve stale data. For those cases, use CloudFront with caching disabled or use other solutions like API Gateway.

🌍 Amazon Route 53

You now have a CloudFront distribution with a URL like d1234abcdef8.cloudfront.net. Your website is fast and secure. But imagine telling your customers, "Just visit d1234abcdef8.cloudfront.net!" That is not going to work. People need a friendly domain name — like www.myshop.com. That is exactly what Route 53 does.

What is Route 53?

Amazon Route 53 is a highly available and scalable Domain Name System (DNS) web service that translates human-readable domain names into IP addresses.

The name "Route 53" refers to port 53, the standard network port used by DNS.

💡 DNS Analogy: DNS is like the contact list on your phone. You don't remember your friend's phone number — you just search "Raj" and your phone finds the number. DNS works the same way: you type www.amazon.com, and DNS looks up the actual IP address behind it (like 54.239.28.85).

Figure 6: DNS resolution flow — how Route 53 maps domain names to CloudFront

Route 53 Key Concepts

Hosted Zone

A hosted zone is a container for DNS records for a specific domain (e.g., myshop.com). It tells Route 53 how to route traffic for that domain and its subdomains.

There are two types:

  • Public hosted zone: Routes traffic over the public internet (e.g., www.myshop.com → CloudFront)
  • Private hosted zone: Routes traffic within an Amazon VPC only (e.g., internal services that should not be publicly accessible)

Name Servers

When you create a hosted zone, Route 53 automatically assigns four name servers to it. These are the authoritative servers that hold the DNS records for your domain. You must update your domain registrar (wherever you bought your domain) to point to these four Route 53 name servers. After this update propagates, Route 53 becomes the authority for your domain's DNS.

✅ Domain Registration in Route 53: Route 53 can also act as your domain registrar — you can buy a domain directly through Route 53. In that case, Route 53 automatically sets its own name servers for that domain, and you skip the manual name server update step.

DNS Record Types

Once your hosted zone is set up, you create records inside it that define how traffic is routed:

Figure 7: Common DNS record types in Route 53

  • A Record: Maps a domain name to an IPv4 address (e.g., myshop.com → 54.239.28.85)
  • AAAA Record: Maps a domain name to an IPv6 address
  • CNAME Record: Maps one domain name to another domain name (alias). CNAME records cannot be used for the root domain (apex domain) — for example, you cannot create a CNAME for myshop.com, only for subdomains like www.myshop.com.
  • Alias Record: AWS-specific record type. Alias records can point directly to AWS resources like CloudFront distributions, S3 websites, ELBs, and other Route 53 records — and unlike CNAMEs, alias records can be used at the apex domain.
  • MX Record: Specifies mail servers for the domain
  • TXT Record: Stores text information (often used for domain ownership verification)

Connecting Route 53 to CloudFront

In the session, the instructor created an Alias A record in Route 53 pointing the domain to the CloudFront distribution. Here is the complete process:

  1. In Route 53, open (or create) a hosted zone for your domain.
  2. Click Create Record.
  3. Set the record name to your subdomain (e.g., www) or leave blank for the root domain.
  4. Set the record type to A.
  5. Enable the Alias toggle.
  6. In the alias target, choose CloudFront distribution and select your distribution from the dropdown.
  7. Save the record.

After DNS propagation (usually within a few minutes to 48 hours), users can visit www.myshop.com and it will route through CloudFront to serve your S3-hosted static website.

Route 53 Routing Policies

Route 53 is not just a simple DNS server — it supports intelligent routing policies that can route traffic based on geography, health, latency, and more:

Figure 8: Route 53 routing policies overview

  • Simple: One record, one destination. Simplest policy.
  • Weighted: Split traffic between multiple resources by percentage (e.g., 90% to v1, 10% to v2). Useful for blue/green deployments and A/B testing.
  • Latency-based: Routes users to the AWS region with the lowest latency. Useful for globally distributed applications.
  • Geolocation: Routes users based on their geographic location (country or continent).
  • Failover: Active-passive setup. Traffic goes to the primary resource; if the health check fails, it automatically switches to the secondary.
  • Multivalue Answer: Returns multiple IP addresses and lets the client choose. Not a replacement for a load balancer, but adds basic redundancy.

Route 53 Pricing

According to AWS documentation, Route 53 charges $0.50 per hosted zone per month (for the first 25 hosted zones) and a per-query fee that starts at $0.40 per million queries for standard queries. Alias queries to AWS resources (CloudFront, ELB, S3) are free of charge.

🏗️ Complete Architecture: S3 + CloudFront + Route 53

Let us now put all three services together and walk through the complete flow of a production static website on AWS — from storing the files to a customer visiting the site with a custom domain name.

Figure 9: Complete static website architecture — S3 + CloudFront + Route 53

Step-by-Step Setup

  1. Create an S3 bucket in your preferred region (e.g., ap-south-1). Upload all website files. Enable static website hosting and set index.html as the index document.

  2. Block all public access on the S3 bucket. Remove any open bucket policy. The bucket is now completely private.

  3. Create a CloudFront distribution. Set the origin to your S3 bucket. Set the default root object to index.html. Create and attach an OAC.

  4. Update the S3 bucket policy to allow only your new CloudFront distribution (using its ARN) to call s3:GetObject. CloudFront will generate the exact policy for you to copy-paste — you just need to go to the S3 bucket and paste it.

  5. Test using the CloudFront domain name (e.g., d1234abcdef8.cloudfront.net). Your website should load.

  6. Request an SSL certificate via AWS Certificate Manager (ACM) for your domain. ACM certificates for CloudFront must be requested in us-east-1 (N. Virginia) regardless of where your users are.

  7. Attach your custom domain and certificate to the CloudFront distribution under "Alternate Domain Names (CNAMEs)".

  8. Create a Route 53 hosted zone for your domain. Create an Alias A record pointing to the CloudFront distribution.

  9. Update your domain registrar's name servers to Route 53's name servers (if you bought the domain outside of Route 53).

  10. Test with your custom domain. Users can now visit www.myshop.com over HTTPS, served from the nearest CloudFront edge location, backed by a private S3 bucket.

✅ Result: Your S3 bucket is private (no public access), your content is cached globally (fast for all users), your domain is friendly and HTTPS-secured (professional and trustworthy), and everything runs on AWS managed infrastructure with zero servers to maintain.

🐍 AWS SDK — Boto3 (Python)

So far, every AWS action we have discussed has been done through the AWS Management Console — clicking buttons, filling forms, configuring services through a web interface. But what if you need to create 100 EC2 instances? Or automatically process every file uploaded to S3? Clicking through the console is not practical. That is where the AWS SDK comes in.

What is the AWS SDK?

An SDK (Software Development Kit) is a collection of tools, libraries, and code examples that developers use to interact with AWS services programmatically from within their application code.

AWS provides SDKs for many programming languages, including Python, JavaScript/Node.js, Java, .NET, Go, Ruby, PHP, and more. In this session, the instructor used Boto3 — the AWS SDK for Python.

Three Ways to Interact with AWS

Figure 10: Three ways to interact with AWS — Console, CLI, and SDK

In the session, the instructor asked the class which interface developers prefer most. The answer: CLI and SDK, because DevOps engineers and developers rarely use the console for repetitive tasks. The console is great for learning and one-off configurations, but automation always wins in production.

Boto3 — Python AWS SDK

Boto3 is the official AWS SDK for Python, allowing Python developers to create, configure, and manage AWS services using Python code.

Installing Boto3 is a single pip command:

pip install boto3

Boto3 has two primary interfaces:

  • Client: Low-level interface. Provides 1-to-1 mapping with AWS API operations. Returns raw Python dictionaries.
  • Resource: High-level, object-oriented interface. More Pythonic, easier to use for simple tasks. Not available for all AWS services.

Boto3 Example: Launching an EC2 Instance

In the session, the instructor wrote a Python script to programmatically launch an EC2 instance in Mumbai, wait for it to be running, and print its public and private IP addresses. Here is an expanded and annotated version of that script:

import boto3

# Configuration
REGION = "ap-south-1"         # Mumbai region
AMI_ID = "ami-0c55b159cbfafe1f5"  # Ubuntu Server AMI (changes by region!)
INSTANCE_TYPE = "t3.micro"

def launch_ec2_instance():
    """Launch an EC2 instance and return its details."""
    try:
        # Create an EC2 resource using boto3
        ec2_resource = boto3.resource("ec2", region_name=REGION)

        print("Launching EC2 instance...")

        # Create the instance
        instances = ec2_resource.create_instances(
            ImageId=AMI_ID,
            InstanceType=INSTANCE_TYPE,
            MinCount=1,
            MaxCount=1,
            TagSpecifications=[
                {
                    "ResourceType": "instance",
                    "Tags": [{"Key": "Name", "Value": "my-python-server"}]
                }
            ]
        )

        instance = instances[0]
        print(f"Instance created with ID: {instance.id}")

        # Wait until the instance is in the 'running' state
        print("Waiting for instance to enter running state...")
        instance.wait_until_running()

        # Reload to get the latest attributes
        instance.reload()

        print(f"Instance is running!")
        print(f"Public IP:  {instance.public_ip_address}")
        print(f"Private IP: {instance.private_ip_address}")
        print(f"EC2 instance launched successfully: {instance.id}")

    except Exception as e:
        print(f"Error: {e}")

if __name__ == "__main__":
    launch_ec2_instance()

Figure 11: Boto3 script flow — Python code calls AWS API to launch EC2 instance

AMI ID: Region Dependency

AMI IDs are region-specific — the same operating system image has a different AMI ID in every AWS region.

To find the correct AMI ID for your region:

  1. Go to EC2 in the AWS Console.
  2. Click Launch Instances.
  3. Browse or search for the OS you want (e.g., Ubuntu Server 22.04).
  4. Copy the AMI ID shown — this is the correct ID for your current region.

❌ Common Mistake: Copying an AMI ID from a tutorial written for a different region. The script will fail with an "InvalidAMIID.NotFound" error. Always find the AMI ID in your own console in the same region you are deploying to.

AWS Configuration and Credentials

Before running any Boto3 script, you must configure your AWS credentials on your local machine. This is done using the AWS CLI:

aws configure

This command prompts you for:

  • AWS Access Key ID — from your IAM user
  • AWS Secret Access Key — from your IAM user (shown only once at creation)
  • Default region name — e.g., ap-south-1
  • Default output format — e.g., json

Credentials configured with aws configure are stored in ~/.aws/credentials and ~/.aws/config files on your local machine.

✅ Best Practice: Never hardcode AWS credentials (Access Key ID, Secret Access Key) inside your Python scripts or application code. Always use aws configure, IAM roles (for EC2 and Lambda), or environment variables. Hardcoded credentials are a serious security risk and can lead to credential leaks if code is shared or pushed to GitHub.

Common Boto3 Use Cases

Boto3 is not just for launching EC2 instances. Developers use it for virtually every AWS service:

  • Upload or download files from S3 buckets
  • Process SQS messages in a queue
  • Create or query DynamoDB tables
  • Trigger Lambda functions
  • Send emails via SES
  • Manage IAM users and roles
  • Query CloudWatch logs and metrics

According to AWS documentation, Boto3 is the most widely used AWS SDK among backend developers. It supports virtually all AWS services through the same consistent client/resource pattern.

Why DevOps Engineers Prefer CLI and SDK

In real-world DevOps environments, almost nobody uses the AWS Console for repetitive tasks. The reasons are practical:

  • Speed: A CLI command takes seconds; clicking through the console takes minutes.
  • Consistency: Scripts run the same way every time. Console clicks are error-prone.
  • CI/CD integration: Automated pipelines (GitHub Actions, Jenkins) use CLI and SDK commands, not console clicks.
  • Infrastructure as Code: Tools like AWS CloudFormation, Terraform, and AWS CDK use the SDK internally.

✅ Study Tip: As you prepare for AWS certifications and job interviews, practice using both the console (to understand the services visually) AND the CLI (to develop practical operational skills). Many real-world AWS roles expect fluency in both.

🎓 Exam Tips & Key Facts

CloudFront Exam Tips

  • CloudFront uses edge locations to cache content. Edge locations are separate from AWS Regions and Availability Zones.
  • CloudFront supports both static and dynamic content — dynamic content bypasses the cache and goes directly to the origin.
  • ACM certificates for use with CloudFront must be created in us-east-1 (N. Virginia), regardless of where users are.
  • OAC is the current recommended method to restrict S3 origin access; OAI is the legacy method.
  • CloudFront integrates with AWS WAF (Web Application Firewall) to block malicious traffic at the edge.
  • CloudFront cache invalidation removes files from edge caches before the TTL expires. Invalidations cost money (first 1,000 paths per month are free).

Route 53 Exam Tips

  • Route 53 is the only AWS service with a 100% availability SLA — it is designed to always resolve DNS queries.
  • Alias records are free for AWS resource targets (CloudFront, ELB, S3); CNAME records are charged per query.
  • Alias records work at the apex/root domain; CNAME records do not.
  • Route 53 health checks can monitor endpoints and automatically route traffic away from unhealthy resources.
  • Route 53 Resolver supports DNS resolution between on-premises networks and VPCs using inbound and outbound endpoints.

SDK/Boto3 Exam Tips

  • SDK, CLI, and Console all use the same underlying AWS APIs — they are different interfaces to the same service.
  • SDK credentials follow a strict precedence order: environment variables → AWS config file → IAM instance profile (for EC2).
  • For EC2 instances or Lambda functions accessing AWS services, always use IAM roles instead of access keys — roles are temporary, automatically rotated, and more secure.

Project 2: Static Infra with CloudFormation (EC2 + S3)

🎯 Objective: Write your first CloudFormation template that creates one EC2 instance and one S3 bucket using hardcoded values. Understand the template → stack → resources lifecycle.

⏱️ Time: 30–40 min

Project 10: Parameter Store — No Hardcoded Secrets

🎯 Objective: Store a database password as a SecureString in SSM Parameter Store, then fetch it in a Python script using Boto3 — without ever writing the password in code.

⏱️ Time: 25–30 min

💰 Cost: Free (Parameter Store standard tier is free)

  1. Go to Systems Manager → Parameter Store → Create parameter. Set name to /myapp/prod/db-password. Type: SecureString. KMS key: default (aws/ssm). Value: MySecretDBPass123! → Create parameter.

    📸 Screenshot: Parameter Store — creating a SecureString parameter

  2. Create a Python script fetch_secret.py that retrieves the parameter:

    import boto3

def get_db_password():
    ssm = boto3.client('ssm', region_name='ap-south-1')

    response = ssm.get_parameter(
        Name='/myapp/prod/db-password',
        WithDecryption=True   # Decrypts SecureString automatically
    )

    password = response['Parameter']['Value']
    print(f"Retrieved password: {password}")
    return password

if __name__ == "__main__":
    get_db_password()

  3. Run the script:

    python fetch_secret.py

    📸 Screenshot: Python script output — secret fetched from Parameter Store

  4. Notice: the password never appears in the Python code. The script only knows the parameter name. The actual secret lives in Parameter Store, encrypted with KMS.

✅ Key insight: Never hardcode secrets in application code or config files. This is a top interview question. Parameter Store (free) or Secrets Manager (paid, with auto-rotation) is the AWS answer.

    When to use which:
    Parameter Store — Free, simple key-value storage, manual rotation. Good for config values, feature flags, non-sensitive strings, and simple secrets without rotation.
