🚀 Introduction

Imagine you walk up to an ATM. You don't need to open the machine, touch the internal wiring, or understand how money flows through bank networks. You just press a button — and you get what you want. That button press is you sending a request. The ATM's display is the API Gateway. The bank's backend system is the backend service.

Figure 1: API Gateway as the front door between clients and backend services

That is exactly what AWS API Gateway does in the cloud. It sits between your users (the clients) and your application logic (the backend), acting as a smart front door — receiving requests, checking them, and routing them to the right backend service.

In this session, you also learned about VPC Endpoints — a way for your AWS resources inside a private network to talk to other AWS services without ever going out to the public internet. Together, these two services form a critical part of how real-world AWS applications are built securely and efficiently.

💡 Why this matters: Almost every modern web application — whether it is a food delivery app, a banking portal, or a shopping site — uses an API Gateway pattern. Understanding this is essential for cloud roles, DevOps, and backend development.

🔌 What Is an API?

Before diving into API Gateway, you need to understand what an API actually is, because the word gets thrown around everywhere.

API stands for Application Programming Interface — it is a set of rules and definitions that allows two software systems to communicate with each other.

Think of it this way: when you use a food delivery app on your phone, the app itself does not store all the restaurant menus or process your payment. It talks to other systems — the restaurant's inventory system, the payment gateway, the delivery tracking system. The language those systems use to talk to each other? That's the API.

Figure 2: The waiter analogy — API as a messenger between client and server

A classic real-world analogy: imagine you are at a restaurant. You (the client) cannot walk directly into the kitchen and cook your food. Instead, you tell the waiter (the API) what you want. The waiter goes to the kitchen (the server/backend), places your order, and brings back the food (the response). The API is the waiter — a messenger between two systems.

⚡ Key insight: APIs are everywhere — when you log into Google using your Facebook account ("Login with Facebook"), Facebook's API is handling that. When a weather widget on a website shows live data, it is calling a weather API.

🏛️ What Is AWS API Gateway?

AWS API Gateway is a fully managed service that allows you to create, publish, maintain, monitor, and secure APIs at any scale.

In simpler words: API Gateway is the single front door for all client requests to your backend. Think of it as a smart security guard at the entrance of a large office building — every visitor (request) must go through the guard, get checked, and be directed to the right floor (backend service).

Figure 3: API Gateway as the single entry point routing to multiple backend services

Without API Gateway, every user would need to know the exact internal address of every backend service. That would be like publishing the internal phone numbers of every department in a company — chaotic and insecure. Instead, API Gateway gives everyone one public URL, and internally routes them to the right place.

✅ Key benefit: API Gateway is serverless — you do not manage any servers. AWS handles all the infrastructure, scaling, patching, and availability automatically.

What API Gateway Does

API Gateway collects the request from the client, applies authentication, validation, throttling, and monitoring, then routes the request to the backend service using HTTP methods.

  • Authentication: Is this user allowed to access this resource? (Is the person at the door on the guest list?)
  • Validation: Is the request properly formatted? (Is the visitor carrying the right ID?)
  • Throttling: Is this user sending too many requests too fast? (Is the door being rushed by a crowd?)
  • Monitoring: Logs and tracks all requests using CloudWatch for debugging and analytics.

Figure 4: The complete request-response flow through API Gateway

📦 Anatomy of an HTTP Request

Every time a user clicks a button in an application — Login, Submit Order, Pay Now — the application sends an HTTP request to the server. Understanding the parts of this request is fundamental to understanding how API Gateway works.

Every HTTP request has four basic parts: Method, URL, Headers, and Body.

Figure 5: The four parts of every HTTP request

PartWhat It IsReal-World Analogy
MethodWhat action do you want to perform?The verb — "get", "create", "update", "delete"
URLWhere do you want to do it?The address of the specific resource
HeadersExtra information — token, content typeYour ID card and the language you speak
BodyThe data you are sending (only for POST, PUT, PATCH)The parcel you hand over at the counter

💡 Example — Login Request:

Method: POST
URL: https://api.myapp.com/login
Headers: { "Content-Type": "application/json" }
Body: { "username": "abc", "password": "xyz" }

The Body only exists when you are sending data — for login (POST), creating a user (POST), or updating a record (PUT/PATCH). For GET and DELETE requests, there is usually no body — you are just asking for or removing something.

⚙️ HTTP Methods — The Four Core Actions

HTTP methods tell the server what action you want to perform on a resource. They are the verbs of the web. There are four methods you absolutely must know for both exams and interviews.

The four primary HTTP methods are GET (read), POST (create), PUT (update/replace), and DELETE (remove).

Figure 6: HTTP methods mapped to CRUD operations

MethodActionReal-World ExampleHas Body?
GETRead / Retrieve dataViewing your order history❌ No
POSTCreate new dataPlacing a new order✅ Yes
PUTUpdate / Replace existing dataEditing your delivery address✅ Yes
DELETERemove dataCancelling your order❌ Usually not
PATCHPartial updateUpdating just one field (e.g., email)✅ Yes

⚡ CRUD Mapping (must memorize): These methods map directly to the four database operations — Create → POST, Read → GET, Update → PUT/PATCH, Delete → DELETE. You will see "CRUD" in every backend development and API design question.

Path + Method = One API Operation

In API Gateway, a path and a method together define one unique API operation. They always work as a combination — never alone.

The combination of URL path and HTTP method uniquely identifies one API operation.

💡 Example — Same path, different actions:

GET  /users        → Get list of all users
POST /users        → Create a new user
GET  /users/123    → Get details of user with ID 123
PUT  /users/123    → Update user 123
DELETE /users/123  → Delete user 123

Notice: /users is the same path in all cases, but the method changes what happens. This is how RESTful APIs are designed.

🗂️ Resources and Paths in API Gateway

When you build an API Gateway in AWS, you define resources — which are really just the paths (URLs) your API will respond to.

A resource in API Gateway is the path in the URL that defines which backend component you are accessing.

Think of it like the floors in a building. The building's address is the base URL (your API Gateway endpoint). The floor number is the path (the resource). The action you want to do on that floor is the method.

Figure 7: Resources (paths) in API Gateway routing to different backends

For example, if your e-commerce application has an API Gateway endpoint at https://api.myshop.com:

  • /users → routes to the user management service
  • /orders → routes to the order processing service
  • /orders/{orderId} → routes to a specific order by ID
  • /payments → routes to the payment service
  • /shipping → routes to the shipping/logistics service

Each of these paths is a resource you define inside API Gateway. Once defined, API Gateway knows exactly where to send the incoming request based on the path.

📚 According to AWS documentation, resources in API Gateway represent logical components of your application. Path parameters enclosed in curly braces (like {orderId}) are dynamic path parameters — they capture values from the actual URL at runtime. 📚 Source: AWS API Gateway Concepts

🏗️ API Gateway with Microservices

One of the most powerful use cases for API Gateway is in a microservices architecture — where your application is split into multiple small, independent services, each handling one specific job.

Imagine an e-commerce application broken into separate services:

  • Orders service — running on an EC2 instance
  • Payments service — running on another EC2 instance
  • Shipping service — running as a Lambda function

Figure 8: API Gateway as single entry point for a microservices application

Without API Gateway, the client would need to know three different URLs, three different IP addresses, three different authentication systems. That is messy and insecure. With API Gateway:

  • Clients always talk to one URL: https://api.myshop.com
  • API Gateway routes /orders → EC2 Orders service
  • API Gateway routes /payments → EC2 Payments service
  • API Gateway routes /shipping → Lambda Shipping function

API Gateway provides a single entry point for clients in a microservices architecture, routing requests to the appropriate backend based on the URL path.

📊 HTTP Status Codes — Reading the Response

When the backend finishes processing a request, it sends back a response — which always includes a status code. Status codes tell you whether the request succeeded or failed, and if it failed, whose fault it is.

HTTP status codes are grouped by their first digit: 2xx means success, 4xx means client-side error, and 5xx means server-side error.

Figure 9: HTTP status code families — success, client error, server error

2xx — Success Codes

CodeMeaningWhen You See It
200 OKRequest succeededGET request returned data successfully
201 CreatedResource created successfullyPOST request created a new user/order
204 No ContentSuccess, no data returnedDELETE request completed

4xx — Client Error Codes (Your Mistake)

If you get a 4xx error, the problem is with the request you sent, not the server.

CodeMeaningCommon Cause
400 Bad RequestInvalid input / malformed requestSending wrong data format in the body
401 UnauthorizedNot authenticatedMissing or invalid authentication token
403 ForbiddenAuthenticated but not permittedUser logged in but does not have permission
404 Not FoundResource or path does not existWrong URL path — not defined in API Gateway

❌ Common Confusion — 401 vs 403: Both feel like "access denied" but they are different. 401 means "I don't know who you are — please log in." 403 means "I know who you are, but you are not allowed here." Example: 401 = no ticket, 403 = ticket for economy, trying to enter business class.

5xx — Server Error Codes (Server's Mistake)

If you get a 5xx error, the problem is on the server side — your request was fine, but something broke in the backend.

CodeMeaningCommon Cause
500 Internal Server ErrorServer crashed or threw an errorBug in backend code
502 Bad GatewayInvalid response from upstreamLambda returned malformed output
503 Service UnavailableServer overloaded or downBackend is not running

⚡ Quick memory trick: 4xx = You messed up. 5xx = They messed up. In interviews: "404 is the developer's most recognizable error — the resource was not found, usually because of a wrong URL path."

🔧 Types of API Gateway in AWS

AWS API Gateway offers three distinct types. Choosing the right type depends on your use case, performance requirements, and whether you need real-time two-way communication.

Figure 10: Three types of AWS API Gateway

REST API

The REST API type is the most feature-rich option in API Gateway, supporting advanced features like usage plans, API keys, request/response transformation, and AWS WAF integration.

Use REST API when you need full control and advanced capabilities: fine-grained authorization, caching at the API Gateway level, request throttling per client, and detailed usage reporting. It is more expensive but far more powerful.

HTTP API

The HTTP API type is a lightweight, lower-cost alternative to REST API, designed for simple proxy integrations to Lambda or HTTP backends with lower latency.

Use HTTP API when you want speed and simplicity. It is up to 71% cheaper than REST API and has lower latency, but it lacks some advanced features like request transformation and API-level caching.

WebSocket API

The WebSocket API type enables real-time, full-duplex (two-way) communication between clients and servers — the connection stays open continuously.

Use WebSocket API for real-time applications: live chat, multiplayer games, live stock tickers, collaborative tools. Normal REST APIs are like postal mail (send, wait, receive). WebSocket is like a phone call — both sides can talk at any time.

FeatureREST APIHTTP APIWebSocket API
Use CaseFull-featured appsSimple, fast proxyReal-time apps
CostHigherLower (~71% cheaper)Based on messages
LatencySlightly higherLowerPersistent connection
Caching✅ Yes❌ No❌ No
WAF Support✅ Yes✅ Yes❌ No

📚 According to AWS documentation, HTTP API is recommended for most use cases unless you specifically need REST API features like API-level caching, request transformation, or usage plans. 📚 Source: HTTP API vs REST API — AWS Docs

🛠️ Creating an API Gateway — Step by Step

When you create an API Gateway in AWS, you follow a simple pattern: Create the API → Define Resources (paths) → Attach Methods → Integrate with Backend → Deploy.

Figure 11: Five-step process to create an API Gateway

  1. Choose API type: REST API, HTTP API, or WebSocket API.
  2. Create Resources (paths): Define your paths like /users, /orders, /login. Each path is a resource that represents a backend component.
  3. Add Methods to each resource: For /users, you might add GET (list all users), POST (create user), and DELETE (remove user).
  4. Integrate with Backend: For each method, tell API Gateway where to send the request — a Lambda function, an EC2 instance, another HTTP endpoint, or even another AWS service directly.
  5. Deploy the API: Deploy to a stage (e.g., dev, prod). After deployment, AWS gives you a public URL (endpoint) that you can use in your frontend application.

✅ After deployment: You get a URL like https://abc123.execute-api.us-east-1.amazonaws.com/prod. This is your API's public address. Every button click in your frontend application that calls the backend will use this URL with the appropriate path and method.

Stages in API Gateway

A stage in API Gateway is a named reference to a specific deployment of your API — allowing you to maintain separate environments like dev, staging, and prod.

Think of stages as different versions of your API running simultaneously. You test in dev, validate in staging, and serve real users from prod — all from the same API Gateway configuration.

⭐ Key Features of API Gateway

Figure 12: Core features of AWS API Gateway

Authentication and Authorization

API Gateway supports three main authorization mechanisms: IAM authorization, Lambda Authorizers (custom auth), and Amazon Cognito (user pools).

  • IAM authorization: Uses AWS IAM roles and policies — good for internal service-to-service calls.
  • Lambda Authorizer: A custom Lambda function that validates a token (e.g., JWT) and returns an IAM policy — flexible for custom auth logic.
  • Cognito: Integrates with Amazon Cognito User Pools for managing end-user sign-in and authentication — ideal for consumer apps.

Throttling

API Gateway applies throttling to protect your backend from being overwhelmed by too many requests — by default, it allows 10,000 requests per second with a burst limit of 5,000 requests.

Throttling is like a bouncer at a club — only a limited number of people can enter per minute, preventing the backend from crashing under load.

Caching (REST API only)

API Gateway can cache responses for a specified TTL (Time to Live) between 0 to 3600 seconds, reducing repeated calls to your backend.

Caching is like a librarian who memorises the answer to a frequently asked question — instead of looking it up every time, they just tell you immediately.

CORS Support

CORS (Cross-Origin Resource Sharing) can be enabled in API Gateway to allow web browsers to make requests to your API from a different domain.

Without CORS enabled, a web app at myapp.com cannot call an API at api.myapp.com — browsers block this for security. API Gateway lets you configure exactly which origins are allowed.

Monitoring and Logging

API Gateway integrates natively with Amazon CloudWatch to log all requests, track latency, monitor error rates, and set alarms. You can see exactly how many requests are failing, how fast your API responds, and where bottlenecks occur.

🔒 VPC Endpoints — Staying Private

Imagine your company's office building (your VPC) is on a private road. Normally, to send mail to the post office (S3), you would have to go out to the public road, drive through town, and come back. That's slow, visible to everyone, and costs extra toll fees.

A VPC Endpoint is like building a private tunnel directly from your office to the post office — no public road needed, no tolls, completely private.

A VPC Endpoint is a private connection between your VPC and supported AWS services that does not require internet access, a NAT Gateway, or a VPN connection.

Figure 13: VPC Endpoint vs public internet path to S3

The Problem VPC Endpoints Solve

When you have an EC2 instance in a private subnet (no internet access), and it needs to talk to S3, DynamoDB, or any other AWS service — by default, it has to:

  1. Go through the NAT Gateway (costly, chargeable)
  2. Exit the AWS network through the Internet Gateway
  3. Travel across the public internet
  4. Come back into AWS to reach S3

This is not just slow — it is also expensive and a security concern. Traffic going over the public internet can potentially be intercepted. VPC Endpoints eliminate all of this.

💰 Cost Note: NAT Gateways are charged by the hour AND by the GB of data processed. For EC2 instances that frequently access S3 or DynamoDB, using VPC Endpoints instead of NAT Gateways can result in significant cost savings.

🔀 Types of VPC Endpoints

There are two types of VPC Endpoints: Gateway Endpoints and Interface Endpoints.

Figure 14: Gateway Endpoint vs Interface Endpoint

Gateway Endpoints

Gateway Endpoints are available only for Amazon S3 and Amazon DynamoDB, and they work by adding an entry to your route table to direct traffic through the AWS network.

Gateway Endpoints are free of charge. They work at the route table level — when traffic is destined for S3 or DynamoDB, the route table redirects it through the endpoint instead of through the internet. No interface is created inside your subnet.

  • ✅ Free of charge
  • ✅ Works for S3 and DynamoDB only
  • ✅ Uses AWS backbone network — no internet exposure
  • ✅ Configured via route table modification

Interface Endpoints (AWS PrivateLink)

Interface Endpoints use AWS PrivateLink to create an Elastic Network Interface (ENI) with a private IP address inside your subnet, enabling private connectivity to a wide range of AWS services.

Unlike Gateway Endpoints, Interface Endpoints create an actual network interface inside your subnet — with a private IP address. Any service call that would normally go over the internet now goes through this private interface. Interface Endpoints support far more services than Gateway Endpoints.

  • ✅ Supports most AWS services (EC2 API, CloudWatch, SNS, SQS, Secrets Manager, etc.)
  • ✅ Also supports S3 and DynamoDB (but costs money, unlike Gateway)
  • ⚠️ Charged per hour and per GB processed
  • ✅ Creates ENI inside your subnet with a private IP
FeatureGateway EndpointInterface Endpoint
Services SupportedS3, DynamoDB onlyMost AWS services
CostFreeCharged (per hour + per GB)
How It WorksRoute table entryENI with private IP in subnet
Powered ByAWS network routingAWS PrivateLink
ScopeRegionalAZ-specific (per subnet)

✅ Exam tip: If a question asks which VPC Endpoint type to use for S3 or DynamoDB and mentions cost optimization — choose Gateway Endpoint (free). If a question asks about connecting to services like SNS, SQS, CloudWatch, or any non-S3/DynamoDB service — choose Interface Endpoint.

💰 Benefits of VPC Endpoints

VPC Endpoints offer three major benefits that are frequently tested in AWS exams:

Figure 15: Three key benefits of VPC Endpoints

1. Enhanced Security

With VPC Endpoints, traffic never leaves the AWS network, eliminating exposure to the public internet and reducing the attack surface.

Your data travels entirely within AWS's private backbone network. No eavesdropping, no interception risk from the public internet.

2. Cost Savings

NAT Gateways are expensive — they charge per hour AND per GB of data transferred. For EC2 instances that make frequent API calls to S3 or DynamoDB, removing the NAT Gateway dependency and using a (free) Gateway Endpoint can cut costs dramatically.

3. Improved Performance

Since traffic stays within the AWS network, VPC Endpoints provide lower latency compared to routing through the public internet.

The AWS backbone network is optimised for speed and reliability — far better than taking the long way around through the public internet.

📚 According to AWS documentation, VPC Endpoints enable resources in a private VPC to communicate with AWS services without requiring an internet gateway, NAT device, VPN connection, or AWS Direct Connect connection. The instances in the VPC do not require public IP addresses to communicate with the service. 📚 Source: AWS VPC Endpoints Documentation

📝 Overall Summary

  • API (Application Programming Interface): A set of rules allowing two software systems to communicate — like a waiter between the customer (client) and kitchen (server).
  • API Gateway: A fully managed AWS service acting as the single front door for all client requests to backend services — it handles auth, validation, throttling, routing, and monitoring.
  • HTTP Request Parts: Every request has four parts — Method (what to do), URL (where), Headers (extra info like token), and Body (data, only for POST/PUT/PATCH).
  • HTTP Methods: GET (read), POST (create), PUT (update), DELETE (remove), PATCH (partial update). Path + Method = one unique API operation.
  • Resources and Paths: Defined in API Gateway to represent backend components — e.g., /users, /orders, /payments. Each path routes to a specific backend.
  • Status Codes: 2xx = success, 4xx = client error (wrong request), 5xx = server error (backend issue). Key codes: 200, 201, 400, 401, 403, 404, 500, 503.
  • API Gateway Types: REST API (full-featured), HTTP API (lightweight/cheaper), WebSocket API (real-time two-way communication).
  • Microservices: API Gateway provides a single entry point for microservice architectures, routing based on URL path to different backend services.
  • VPC Endpoint: A private connection between a VPC and AWS services — traffic stays within the AWS network, no internet required.
  • Gateway Endpoint: Free, works only for S3 and DynamoDB, operates via route table entry.
  • Interface Endpoint: Paid, works for most AWS services, creates an ENI with a private IP inside the subnet (uses AWS PrivateLink).
  • VPC Endpoint Benefits: Enhanced security (traffic never leaves AWS), cost savings (eliminates NAT Gateway charges), and improved performance (lower latency).

Project 0.1 — Multi-Method CRUD API (No Database Yet)

🎯 Objective: Extend your hello-world Lambda into a full CRUD API with four operations on a /users resource — using hardcoded in-memory data. This locks in the path + method = operation concept before adding a real database.

⏱️ Time: 30–45 minutes

💰 Cost: Free tier

🧱 Builds on: Project 1 (hello-world Lambda + API Gateway)

⚡ What you are learning: Method routing, status code discipline, and response formatting — the three things every backend developer must get right before touching a database.

  1. Open your existing hello-api-function Lambda (or create a new one named users-api-function). Replace the entire code with the following multi-method handler:

    import json

# Simulated in-memory "database"
USERS = {
    "1": {"id": "1", "name": "Alice", "email": "alice@example.com"},
    "2": {"id": "2", "name": "Bob",   "email": "bob@example.com"},
}

def lambda_handler(event, context):
    method     = event["httpMethod"]
    path       = event.get("path", "")
    path_params = event.get("pathParameters") or {}
    body_raw   = event.get("body") or "{}"

    try:
        body = json.loads(body_raw)
    except Exception:
        return respond(400, {"error": "Invalid JSON body"})

    # GET /users
    if method == "GET" and path == "/users":
        return respond(200, {"users": list(USERS.values())})

    # POST /users
    if method == "POST" and path == "/users":
        user_id = str(len(USERS) + 1)
        name  = body.get("name")
        email = body.get("email")
        if not name or not email:
            return respond(400, {"error": "name and email are required"})
        USERS[user_id] = {"id": user_id, "name": name, "email": email}
        return respond(201, {"message": "User created", "user": USERS[user_id]})

    # GET /users/{id}
    if method == "GET" and path_params.get("id"):
        user = USERS.get(path_params["id"])
        if not user:
            return respond(404, {"error": "User not found"})
        return respond(200, {"user": user})

    # PUT /users/{id}
    if method == "PUT" and path_params.get("id"):
        uid = path_params["id"]
        if uid not in USERS:
            return respond(404, {"error": "User not found"})
        USERS[uid].update(body)
        return respond(200, {"message": "User updated", "user": USERS[uid]})

    # DELETE /users/{id}
    if method == "DELETE" and path_params.get("id"):
        uid = path_params["id"]
        if uid not in USERS:
            return respond(404, {"error": "User not found"})
        del USERS[uid]
        return respond(200, {"message": "User deleted"})

    return respond(404, {"error": "Route not found"})

def respond(status, body):
    return {
        "statusCode": status,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps(body)
    }

    Click Deploy after pasting.

    Figure 29: 📸 Multi-method Lambda — full CRUD handler deployed

  2. Go to API Gateway → Create API → REST API → Build. Name it users-crud-api. Create a resource at path /users. Under /users, create a child resource with path {id} — this captures the dynamic user ID from the URL.

    Figure 30: 📸 Resource tree — /users with /{id} child resource

  3. On the /users resource, add two methods: GET and POST. On the /{id} child resource, add three methods: GET, PUT, DELETE. For every method, choose Lambda Proxy Integration and point to users-api-function.

    Figure 31: 📸 All five methods configured across both resources

  4. Deploy to a new stage called dev. Copy the Invoke URL. Now test every operation using Postman or curl:

    # List all users
curl [invoke-url]/dev/users

# Create a new user
curl -X POST [invoke-url]/dev/users   -H "Content-Type: application/json"   -d '{"name": "Carol", "email": "carol@example.com"}'

# Get one user
curl [invoke-url]/dev/users/1

# Update a user
curl -X PUT [invoke-url]/dev/users/1   -H "Content-Type: application/json"   -d '{"email": "alice-new@example.com"}'

# Delete a user
curl -X DELETE [invoke-url]/dev/users/2

# Trigger a 404 (user that does not exist)
curl [invoke-url]/dev/users/999

# Trigger a 400 (missing required fields)
curl -X POST [invoke-url]/dev/users   -H "Content-Type: application/json"   -d '{"name": "NoEmail"}'

    Figure 32: 📸 Postman — POST /users returning 201 Created with user data

✅ You know this is working when: Every method returns the correct status code — 200 for reads, 201 for create, 404 for missing users, 400 for bad input. If your 404 and 400 cases work, your debugging instinct is already forming.

Project 0.2 — API Testing and Debugging (Break Things on Purpose)

🎯 Objective: Use Postman to deliberately send bad requests to your API and observe how errors surface. Build the muscle of reading API responses, not just happy-path testing.

⏱️ Time: 20–30 minutes

💰 Cost: Free tier

🧱 Builds on: Project 0.1 — your users-crud-api must be deployed

  1. In Postman, create a new Collection called API Debug Tests. Add the following requests, each as a separate saved request so you can run them repeatedly:

    # Test 1: Wrong content-type header (should break JSON parsing)
curl -X POST [invoke-url]/dev/users   -H "Content-Type: text/plain"   -d "not json at all"

# Test 2: Empty body on POST (missing required fields)
curl -X POST [invoke-url]/dev/users   -H "Content-Type: application/json"   -d '{}'

# Test 3: Wrong path (undefined route)
curl [invoke-url]/dev/nonexistent

# Test 4: DELETE on a user that does not exist
curl -X DELETE [invoke-url]/dev/users/9999

# Test 5: PUT on a user that does not exist

    import json
import boto3
import uuid

dynamodb = boto3.resource("dynamodb")
table    = dynamodb.Table("users-table")

def lambda_handler(event, context):
    print("Event:", json.dumps(event))
    method      = event["httpMethod"]
    path        = event.get("path", "")
    path_params = event.get("pathParameters") or {}
    body_raw    = event.get("body") or "{}"

    try:
        body = json.loads(body_raw)
    except Exception:
        return respond(400, {"error": "Invalid JSON body"})

    # GET /users — scan all users
    if method == "GET" and path == "/users":
        result = table.scan()
        return respond(200, {"users": result["Items"]})

    # POST /users — create a new user
    if method == "POST" and path == "/users":
        name  = body.get("name")
        email = body.get("email")
        if not name or not email:
            return respond(400, {"error": "name and email are required"})
        user_id = str(uuid.uuid4())
        item = {"userId": user_id, "name": name, "email": email}
        table.put_item(Item=item)
        return respond(201, {"message": "User created", "user": item})

    # GET /users/{id}
    if method == "GET" and path_params.get("id"):
        result = table.get_item(Key={"userId": path_params["id"]})
        user   = result.get("Item")
        if not user:
            return respond(404, {"error": "User not found"})
        return respond(200, {"user": user})

    # PUT /users/{id}
    if method == "PUT" and path_params.get("id"):
        uid  = path_params["id"]
        name = body.get("name")
        if not name:
            return respond(400, {"error": "name is required"})
        table.update_item(
            Key={"userId": uid},
            UpdateExpression="SET #n = :name",
            ExpressionAttributeNames={"#n": "name"},
            ExpressionAttributeValues={":name": name},
        )
        return respond(200, {"message": "User updated"})

    # DELETE /users/{id}
    if method == "DELETE" and path_params.get("id"):
        table.delete_item(Key={"userId": path_params["id"]})
        return respond(200, {"message": "User deleted"})

    return respond(404, {"error": "Route not found"})

def respond(status, body):
    return {
        "statusCode": status,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps(body)
    }

import boto3
import uuid

Project 2.2 — Multi-Service Routing (True Microservices Split)

🎯 Objective: Split the single ecommerce-api Lambda into three independent Lambda functions — one per service. API Gateway routes to each separately. This is the microservices pattern your notes describe.

⏱️ Time: 45–60 minutes

💰 Cost: Free tier

🧱 Builds on: Project 2.1 — ecommerce-api structure

⚡ Why split? In production, separate Lambda functions mean: independent deployments (fix orders without touching users), independent scaling (payments can handle 10x traffic without scaling users), and independent permissions (payments Lambda only has access to the payments table).

  1. Create three new Lambda functions: users-service, orders-service, payments-service. Copy the relevant section of your ecommerce-api Lambda code into each one. Each function only handles its own resource.

    # users-service Lambda — handles only /users routes
import json, boto3, uuid
dynamodb = boto3.resource("dynamodb")
table    = dynamodb.Table("users-table")

def lambda_handler(event, context):
    method = event["httpMethod"]
    body   = json.loads(event.get("body") or "{}")
    params = event.get("pathParameters") or {}

    if method == "GET" and not params.get("id"):
        return respond(200, {"users": table.scan()["Items"]})
    if method == "POST":
        uid  = str(uuid.uuid4())
        item = {"userId": uid, "name": body["name"], "email": body["email"]}
        table.put_item(Item=item)
        return respond(201, {"user": item})
    if method == "GET" and params.get("id"):
        res = table.get_item(Key={"userId": params["id"]})
        return respond(200, {"user": res["Item"]}) if "Item" in res else respond(404, {"error": "Not found"})

    return respond(404, {"error": "Not found"})

def respond(status, body):
    return {"statusCode": status, "headers": {"Content-Type": "application/json"}, "body": json.dumps(body)}

Project 3.2 — Secure File Upload API (Pre-Signed URLs + S3 + Gateway Endpoint)

🎯 Objective: Build a two-step file upload API — client requests a pre-signed URL from API Gateway, then uploads directly to S3 using that URL. Lambda generates the URL from inside a private VPC using an S3 Gateway Endpoint. No public Lambda-to-S3 traffic.

⏱️ Time: 45–60 minutes

💰 Cost: Free tier (S3: first 5GB free; Gateway Endpoint: free)

🧱 Builds on: Project 3.1 — backend-vpc and VPC Endpoint pattern

⚡ This is a real production pattern used by every company that lets users upload files — profile photos, documents, product images. The client never gets direct Lambda access to S3, and the URL expires after a short time window.

  1. Create an S3 bucket named secure-uploads-[your-account-id]. Block all public access. No static website hosting. Under Permissions → CORS, add this configuration to allow browser uploads:

    [
  {
    "AllowedHeaders": ["*"],
    "AllowedMethods": ["PUT", "POST"],
    "AllowedOrigins": ["*"],
    "ExposeHeaders": ["ETag"],
    "MaxAgeSeconds": 3000
  }
]

    Figure 50: 📸 S3 bucket — public access blocked, CORS configured for uploads

  2. Create a Lambda function named upload-url-generator. Attach an IAM policy allowing s3:PutObject on your bucket. Place it in your backend-vpc private subnet. Paste this code:

    import json
import boto3

s3_client = boto3.client("s3")
BUCKET    = "secure-uploads-[your-account-id]"

def lambda_handler(event, context):
    body     = json.loads(event.get("body") or "{}")
    filename = body.get("filename")
    filetype = body.get("contentType", "application/octet-stream")

    if not filename:
        return respond(400, {"error": "filename is required"})

    # Generate a pre-signed URL valid for 5 minutes
    presigned_url = s3_client.generate_presigned_url(
        "put_object",
        Params={
            "Bucket":      BUCKET,
            "Key":         f"uploads/{filename}",
            "ContentType": filetype,
        },
        ExpiresIn=300,  # 300 seconds = 5 minutes
    )

    return respond(200, {
        "uploadUrl": presigned_url,
        "expiresIn": "5 minutes",
        "instructions": "PUT your file directly to this URL"
    })

def respond(status, body):
    return {
        "statusCode": status,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps(body)
    }

# Users

# Restaurants
GET  /v1/restaurants    → list all (public)

# Orders (auth required for all)
POST /v1/orders         → place order
GET  /v1/orders         → list my orders
GET  /v1/orders/{id}    → get one order

# Image Upload (auth required)
POST /v1/upload         → get pre-signed S3 URL

Build Steps

  1. Create all DynamoDB tables: fd-users (userId), fd-restaurants (restaurantId), fd-menus (menuItemId, sort: restaurantId), fd-orders (orderId, sort: userId).

  2. Create the Cognito user pool food-delivery-pool with email sign-in. Create an app client with no client secret. Note the pool ID and client ID.

  3. Create four Lambda functions: fd-users-service, fd-restaurant-service, fd-order-service, fd-upload-service. Each handles only its own routes. Attach DynamoDB and S3 permissions as needed.

  4. Place all Lambda functions in a fd-backend-vpc private subnet. Create Gateway Endpoints for DynamoDB and S3.

  5. Create a REST API named food-delivery-api. Create the resource tree as shown in the API design above. Attach the Cognito authorizer to all protected routes. Set throttling on the prod stage (5000 RPS, 2000 burst). Enable CloudWatch logging.

  6. Create a usage plan standard-plan (1000 req/day) and generate an API key for testing. Enable API Key Required on all authenticated endpoints.

  7. Deploy to dev stage. Run through the complete user journey:

🤔 Reflection Questions

1. Your company's mobile app needs to call three different backend services (user auth, product catalog, order management). How would you design the API layer using API Gateway? What resources and methods would you create?

💡 Hint

Think about what paths (/users, /products, /orders) and what HTTP methods (GET, POST, PUT, DELETE) make sense for each service. Consider using one API Gateway with multiple resources routing to different Lambda functions or EC2 services.

2. A junior developer gets a 403 error when calling your API. They say "I'm logged in so I should have access!" How would you explain the difference between authentication and authorization, and what API Gateway setting might be misconfigured?

💡 Hint

401 = not logged in, 403 = logged in but not allowed. The authorizer might have them authenticated but their IAM policy or Cognito user group doesn't permit that specific API resource and method.

3. An EC2 instance in a private subnet needs to access S3 to store and retrieve files. You want to avoid any NAT Gateway costs. What would you implement, and what type would you choose?

💡 Hint

VPC Endpoint — specifically a Gateway Endpoint for S3 (free). You would create the endpoint, attach it to the private subnet's route table, and traffic would route privately through the AWS network.

4. Your API is getting flooded by one client making 50,000 requests per second, causing other clients to time out. What API Gateway feature addresses this, and how does it work?

💡 Hint

Throttling. API Gateway has default limits (10,000 RPS, 5,000 burst) and you can set per-client limits using usage plans and API keys. Requests beyond the limit return a 429 Too Many Requests status code.

5. A team wants to build a live collaborative document editor where multiple users need to send and receive updates simultaneously without polling the server constantly. Which API Gateway type would you recommend and why?

💡 Hint

WebSocket API — it maintains a persistent, open connection between client and server, allowing real-time bidirectional communication. REST/HTTP APIs require the client to repeatedly poll the server, which is inefficient for live collaboration.

6. Your application needs an ENI with a private IP inside the subnet to privately access CloudWatch and Secrets Manager. Which VPC Endpoint type would you create, and why can't you use a Gateway Endpoint here?

💡 Hint

Interface Endpoint — Gateway Endpoints only support S3 and DynamoDB. For CloudWatch, Secrets Manager, SNS, SQS, and other services, Interface Endpoints (AWS PrivateLink) are required. They create an ENI with a private IP in your subnet.
