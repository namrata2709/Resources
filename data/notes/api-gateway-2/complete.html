🚪 Introduction

Imagine you're building an e-commerce website. You have a team of specialists behind the scenes: one person handles orders, another handles payments, and a third manages user accounts. Each specialist knows their job perfectly. But customers can't walk into the back office and talk to each specialist directly — that would be chaotic, insecure, and hard to manage.

So you set up a reception desk. Every customer request comes to the reception desk first. The receptionist looks at the request — "you want to place an order? I'll route you to the orders team" — and forwards it to the right specialist. The customer never needs to know who's in the back office, what technology they use, or even how many people are there.

That reception desk is exactly what AWS API Gateway does for your cloud application.

Figure 1: API Gateway is the single front door to all your backend services

⚡ What you'll learn: By the end of these notes you'll understand what an API is, why API Gateway exists, how to build one from scratch with Lambda, and the key concepts tested in the AWS Solutions Architect exam.

🤝 What is an API? (Start Here)

The Plain-English Definition

An API (Application Programming Interface) is a set of rules and protocols that allows one software application to communicate with another. Think of it as a waiter in a restaurant — you (the frontend) tell the waiter what you want, the waiter takes your order to the kitchen (the backend), and returns with the food (the response). You never need to go into the kitchen yourself.

Figure 2: The restaurant analogy — API is the waiter between your frontend and backend

HTTP Methods — The Language of APIs

When your frontend talks to an API, it uses HTTP methods to express what it wants to do. These four methods map to the four basic operations on data, commonly called CRUD (Create, Read, Update, Delete):

  • GET — Read data. "Give me the list of orders." No changes made to the server.
  • POST — Create new data. "Place a new order." Sends data in the request body.
  • PUT — Update existing data. "Update order #42." Replaces the entire resource.
  • DELETE — Delete data. "Cancel order #42." Removes the resource.

💡 Real example: When you open your banking app and see your balance, the app made a GET request. When you transfer money, it made a POST request. APIs are everywhere — every mobile app, every website, every connected device uses them.

What is a REST API?

A REST API (Representational State Transfer) is a style of API design that uses standard HTTP methods and organizes data around resources identified by URLs. For example:

  • GET /orders — get all orders
  • GET /orders/42 — get order number 42 specifically
  • POST /orders — create a new order
  • DELETE /orders/42 — delete order number 42

The URL (/orders) identifies what resource you're working with, and the HTTP method (GET, POST) says what action to take on it. This combination is clean, predictable, and universally understood — which is why REST is the most popular API style in the world.

What is an Endpoint?

An endpoint is the specific URL where an API can be accessed. Every API has a base URL plus a path. For example, an API Gateway endpoint looks like:

https://abc123.execute-api.us-east-1.amazonaws.com/dev/orders

Breaking this down: abc123.execute-api.us-east-1.amazonaws.com is the API Gateway's auto-generated domain, /dev is the stage (environment), and /orders is the resource path.

🔑 What is AWS API Gateway?

Definition

Amazon API Gateway is a fully managed service that makes it easy to create, publish, maintain, monitor, and secure APIs at any scale. It acts as the single entry point — the front door — for all your backend services, whether those are Lambda functions, EC2 instances, or any HTTP endpoint.

The key word is fully managed. AWS handles all the infrastructure — the servers running API Gateway, their availability, auto-scaling, and patching. You only define the API: what URLs exist, what HTTP methods they support, and where the traffic goes.

Why Use API Gateway?

Without API Gateway, you'd need to run your own web server just to receive HTTP requests, write code to route them to different backends, build your own authentication layer, handle rate limiting, set up HTTPS certificates, and build monitoring from scratch. API Gateway handles traffic management, authorization, access control, monitoring, and API version management — all out of the box.

Figure 3: Everything API Gateway handles for you — zero servers required

Three Types of API Gateway

AWS API Gateway offers three types: REST API, HTTP API, and WebSocket API.

  • REST API: The most feature-rich option. Supports usage plans, API keys, request validation, response transformation, caching, WAF integration, and private endpoints. More expensive. Best for enterprise-grade public APIs.
  • HTTP API: Simpler and about 70% cheaper than REST API. Supports Lambda and JWT authorizers but lacks advanced features like usage plans, caching, and WAF. Best for most modern serverless applications.
  • WebSocket API: For real-time two-way communication — like a chat app or live dashboard. The connection stays open continuously.

💡 Exam tip: Questions about usage plans, API keys per client, request/response transformation, response caching, or WAF integration → answer is REST API. Questions about cheapest option for simple Lambda routing → answer is HTTP API.

API Gateway + Lambda = Fully Serverless

The combination of API Gateway + Lambda + DynamoDB forms the foundation of serverless architecture on AWS — you pay only for actual requests, not for idle servers. No EC2, no patching, no capacity planning. Everything scales automatically.

✅ Cost advantage: A serverless app handling 1 million requests/month costs a fraction of what an EC2-based equivalent would cost. EC2 charges even when idle; Lambda and API Gateway charge per request.

🧱 Core Concepts of API Gateway

Building an API Gateway is like designing a building: resources are the floors, methods are the doors, integrations are what's inside each room, stages are separate copies of the building (dev, prod), and deployment is the act of opening the building to visitors.

1. Resources — What You're Working With

A resource in API Gateway represents a logical entity identified by a URL path, forming a tree structure starting from the root (/).

For an e-commerce API the resource tree looks like this:

  • / — root (always exists)
  • /orders — the orders collection
  • /orders/{orderId} — a specific order ({orderId} is a path parameter — a variable that takes a real value at runtime)
  • /users — the users collection
  • /payments — the payments collection

Figure 4: Resource tree — every URL path is a resource; path parameters use curly braces

2. Methods — What Action to Take

A method is an HTTP verb (GET, POST, PUT, DELETE, PATCH) attached to a resource that defines what action a client can perform on it.

Example: the /orders resource has GET (list all orders) and POST (create new order). The /orders/{orderId} resource has GET (fetch one order) and DELETE (cancel that order). You define exactly which methods are allowed — any method not defined gets a 404 response automatically.

3. Integrations — Where Requests Go

An integration defines what backend service API Gateway forwards a request to after receiving it from a client.

The four main integration types:

  • Lambda Function: The most common. API Gateway calls a Lambda function with the request data and returns its response.
  • HTTP Integration: Forwards requests to any external HTTP/HTTPS URL — another service, a third-party API, or your EC2-based backend.
  • AWS Service Integration: Directly calls AWS services like DynamoDB, SQS, or S3 without Lambda in the middle.
  • Mock Integration: Returns a hardcoded response without calling any backend. Useful for testing API structure before the backend is built.

💡 Lambda Proxy Integration: When enabled (the default and recommended choice), API Gateway passes the entire HTTP request as a single JSON event to Lambda — headers, query parameters, path parameters, body, all in one object. Lambda returns JSON with statusCode, headers, and body, which API Gateway converts back to an HTTP response.

4. Stages — Your Environments

A stage is a named reference to a deployment of your API, representing an environment such as development, staging, or production — each with its own invoke URL.

Common stages: dev, staging, prod. Each gets a unique URL:

https://abc123.execute-api.us-east-1.amazonaws.com/dev/orders   ← dev
https://abc123.execute-api.us-east-1.amazonaws.com/prod/orders  ← prod

Stage variables let you configure different Lambda function aliases per stage — so prod always points to stable, tested Lambda code and dev always points to the latest version.

5. Deployment — Publishing Your Changes

Creating or modifying resources and methods in API Gateway does NOT automatically make those changes visible to clients. You must explicitly deploy your API to a stage before any changes take effect. This is the most common gotcha for beginners — updating Lambda or changing a method and wondering why clients still see old behaviour.

Figure 5: Changes are not live until deployed — deployment is the explicit publish step

🔄 The Complete Request-Response Flow

Let's trace exactly what happens when a customer clicks "Place Order". Understanding this full flow is what the exam tests.

Figure 6: The 7-step request-response lifecycle through API Gateway and Lambda

  1. Client sends request: The frontend sends POST https://abc123.execute-api.us-east-1.amazonaws.com/prod/orders with a JSON body.

  2. Authentication check: API Gateway checks for a valid API key, Lambda Authorizer result, or Cognito JWT. If any check fails, API Gateway returns 401/403 immediately — Lambda never runs.

  3. Request validation: If a validator is configured, API Gateway checks required headers, query parameters, or body schema.

  4. Integration request: API Gateway converts the HTTP request into a JSON event object for Lambda. With Proxy Integration, this includes all headers, query params, path params, and body.

  5. Lambda executes: Your function runs, processes the order, saves to DynamoDB, and returns JSON with a statusCode and body.

  6. Integration response: API Gateway receives Lambda's JSON and maps it back to an HTTP response structure.

  7. Response returned: The client receives an HTTP 201 Created with the order confirmation JSON.

✅ Key insight: With Lambda Proxy Integration, steps 3 and 6 are pass-through — no transformation needed. Your Lambda code controls the exact response. This is the recommended approach for new APIs.

⚡ Lambda Basics (Required for API Gateway)

What is AWS Lambda?

AWS Lambda is a serverless compute service that runs your code in response to events, automatically managing all underlying infrastructure. You upload a function, define what triggers it, and Lambda handles server provisioning, scaling, and availability. You pay only for compute time in milliseconds — nothing when code isn't running.

Lambda Key Facts for the Exam

  • Maximum execution timeout: 15 minutes per invocation.
  • Default timeout: 3 seconds. Configure up to 15 minutes.
  • Default concurrent execution limit: 1,000 per region (soft limit, can be increased).
  • Each simultaneous call creates a separate execution — 1,000 users hitting your API = 1,000 parallel Lambda executions.
  • Supported runtimes: Python, Node.js, Java, Go, Ruby, .NET, and custom runtimes.

How Lambda Receives API Gateway Requests

With Lambda Proxy Integration, API Gateway passes an event object to your function:

{
  "httpMethod": "POST",
  "path": "/orders",
  "headers": { "Content-Type": "application/json" },
  "queryStringParameters": { "userId": "123" },
  "body": "{\"item\": \"laptop\", \"quantity\": 1}",
  "requestContext": { "stage": "prod" }
}

Lambda processes this, then returns:

{
  "statusCode": 201,
  "headers": { "Content-Type": "application/json" },
  "body": "{\"message\": \"Order placed!\", \"orderId\": \"ORD-789\"}"
}

Lambda IAM Execution Role

Every Lambda function must have an IAM execution role that grants it permission to interact with other AWS services. To write to DynamoDB, the role needs dynamodb:PutItem. To log to CloudWatch (which all functions do), it needs logs:CreateLogGroup and logs:PutLogEvents. The AWSLambdaBasicExecutionRole managed policy covers CloudWatch logging and is the minimum baseline for every Lambda function.

Figure 7: Lambda's IAM execution role controls which AWS services the function can access

🌐 CORS — Cross-Origin Resource Sharing

What is CORS and Why Does It Matter?

Your website is at https://myshop.com. Your JavaScript calls your API at https://abc123.execute-api.amazonaws.com/prod/orders. The browser sees two different domains and, by default, blocks the request. This is the Same-Origin Policy — a browser security rule that prevents JavaScript from calling APIs on different domains without explicit permission.

CORS (Cross-Origin Resource Sharing) is a mechanism that lets a server tell browsers which other origins are allowed to make requests to it — overriding the Same-Origin Policy for trusted domains.

When you enable CORS on an API Gateway resource, it adds these headers to responses:

Access-Control-Allow-Origin: *
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization

Enabling CORS also creates an OPTIONS method (preflight) on the resource. Before a browser sends a POST or PUT, it first sends OPTIONS to check if the server allows the cross-origin request. API Gateway handles this automatically when CORS is enabled.

❌ Most common beginner mistake: API works perfectly in Postman (not a browser, doesn't enforce CORS) but fails in the browser with "CORS error." Fix: enable CORS on the API Gateway resource, then re-deploy the API to the stage.

⚙️ Advanced API Gateway Features

Authentication and Authorization

API Gateway offers three built-in authorization mechanisms:

1. API Keys + Usage Plans

API Keys are alphanumeric strings distributed to clients who must include them via the x-api-key header. Usage Plans attach throttle and quota limits to each key — e.g., 1,000 requests/day at max 10 RPS. This is how you offer tiered access to different partners or developers.

2. Lambda Authorizer (Custom Authorizer)

A Lambda Authorizer is a Lambda function that API Gateway calls before the backend — it validates a token and returns an IAM policy (allow or deny). Use this for custom token formats, proprietary auth systems, or database-backed permission checks.

3. Cognito Authorizer

A Cognito Authorizer validates JWT tokens from Amazon Cognito User Pools — managed user authentication without custom code. Users log in through Cognito, get a JWT, and include it in API calls. API Gateway validates it automatically.

Figure 8: Three authorization options — choose based on who is calling your API

Throttling and Rate Limiting

API Gateway enforces throttling at account, stage, and method levels. The default account-level limit is 10,000 requests per second (RPS) with a burst of 5,000 requests. When exceeded, clients receive 429 Too Many Requests. You can set lower limits on specific stages or individual methods to protect expensive operations.

Response Caching

REST API supports response caching so identical requests don't invoke Lambda every time. The TTL is configurable up to a maximum of 3,600 seconds (1 hour). Caching is configured per stage and only applies to GET requests — POST/PUT/DELETE always pass through to the backend. Useful for read-heavy endpoints returning data that doesn't change frequently.

WAF Integration

REST API can be associated with AWS WAF (Web Application Firewall) to block SQL injection, XSS, and DDoS attacks before they reach your backend. WAF rules are evaluated at the API Gateway perimeter — malicious requests are dropped immediately.

Private API

A Private API endpoint is only accessible from within a VPC via a VPC Interface Endpoint — it cannot be reached from the public internet. Used for internal microservices that should never be exposed externally.

API Gateway vs ALB

Both can route HTTP traffic to Lambda, but serve different purposes. API Gateway is designed for API management — authentication, throttling, caching, versioning. Best for public or partner-facing APIs. ALB is designed for load balancing traffic across a fleet of EC2s or containers with health checks. Best for web applications with multiple backend servers. No API management features.

💡 Rule of thumb: Building an API for developers/apps to call? Use API Gateway. Distributing web traffic to a server fleet? Use ALB.

📝 Overall Summary

  • API: Rules for software-to-software communication. REST APIs use HTTP methods (GET/POST/PUT/DELETE) on resource URLs to represent CRUD operations.
  • API Gateway: AWS's fully managed front door for backend services. Handles routing, auth, throttling, caching, and monitoring with no servers.
  • Three types: REST API (all features, higher cost), HTTP API (simpler, 70% cheaper), WebSocket API (real-time). Pick REST for enterprise features; HTTP for most serverless apps.
  • Resources: URL path segments in your API (/orders, /users). Form a tree from root /. Path parameters use curly braces: {orderId}.
  • Methods: HTTP verbs attached to resources (GET, POST, PUT, DELETE). Define which actions are allowed.
  • Integration: Where requests go — Lambda (most common), HTTP endpoint, AWS service directly, or Mock.
  • Lambda Proxy Integration: Full HTTP request passed as JSON event to Lambda. Lambda returns JSON with statusCode and body. Recommended default.
  • Stages: Named environments (dev/prod). Each has its own URL. Stage variables enable pointing to different Lambda versions per stage.
  • Deploy: Changes are invisible to clients until explicitly deployed to a stage. This is the most common beginner mistake.
  • CORS: Enable on resources accessed by browser-based frontends from a different domain. Creates OPTIONS method automatically.
  • Throttling: Default 10,000 RPS / burst 5,000. Returns 429 when exceeded.
  • Caching: REST API only. Max 1 hour. Reduces Lambda invocations for read-heavy GET endpoints.
  • Auth: API Keys + Usage Plans (developer/partner tiers), Lambda Authorizer (custom tokens), Cognito (user JWT).

Project 1: Your First API — Hello World

🎯 Objective: Create a Lambda function, connect it to API Gateway, and call it from your browser and curl. Understand the complete end-to-end request cycle.

⏱️ Time: 30–40 min

💰 Cost: Free tier (Lambda: first 1M requests free; API Gateway: first 1M requests free)

    📸 Screenshot: Lambda function creation — Author from scratch with Python 3.12

  2. Replace the default code in the editor with:

    import json

def lambda_handler(event, context):
    return {
        "statusCode": 200,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps({
            "message": "Hello from Lambda!",
            "path": event.get("path", "/"),

Project 4: Full Serverless App — API Gateway + Lambda + DynamoDB

🎯 Objective: Build a real end-to-end serverless application where data is actually stored and retrieved from DynamoDB. This is the complete CRUD cycle used in production serverless apps.

⏱️ Time: 75–90 min

💰 Cost: Free tier for all three services. Delete DynamoDB table after the project.

💰 Cost Note: DynamoDB On-Demand mode charges per read/write request. The free tier covers 25 WCUs and 25 RCUs per month — far more than this lab uses. Still, delete the table when done.

  1. Create a DynamoDB table: DynamoDB → Create table. Name: Orders. Partition key: orderId (String). Leave all other settings as default. Click Create table.

    📸 Screenshot: DynamoDB Orders table with orderId as the partition key

  2. Create Lambda function orders-crud (Python 3.12). After creation, attach AmazonDynamoDBFullAccess to its IAM role.

  3. Paste this code into the Lambda editor and click Deploy:

    import json, boto3, uuid
from datetime import datetime

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table('Orders')

def lambda_handler(event, context):
    method = event['httpMethod']
    
    if method == 'GET':
        result = table.scan()
        return {
            'statusCode': 200,
            'headers': {'Content-Type': 'application/json'},
            'body': json.dumps(result['Items'])
        }
    
    elif method == 'POST':
        body = json.loads(event['body'])
        order = {
            'orderId': str(uuid.uuid4()),
            'item': body['item'],
            'quantity': body.get('quantity', 1),
            'status': 'Pending',
            'createdAt': datetime.utcnow().isoformat()
        }
        table.put_item(Item=order)
        return {
            'statusCode': 201,
            'headers': {'Content-Type': 'application/json'},
            'body': json.dumps({'message': 'Order created', 'orderId': order['orderId']})
        }
    
    return {'statusCode': 405, 'body': json.dumps({'message': 'Method not allowed'})}

  4. Create REST API orders-api. Resource /orders with CORS. GET method (→ orders-crud) and POST method (→ orders-crud). Deploy to stage prod.

  5. Create your first order:

    curl -X POST https://YOUR-URL/prod/orders \
  -H "Content-Type: application/json" \
  -d '{"item": "AWS Certification Book", "quantity": 1}'

  6. Create another order, then retrieve all:

    curl https://YOUR-URL/prod/orders

    You'll see both orders in the response — data is persisted in DynamoDB.

  7. Verify in the DynamoDB console: DynamoDB → Tables → Orders → Explore table items.

    📸 Screenshot: DynamoDB showing orders stored via the API

  8. Cleanup: Delete DynamoDB table → delete Lambda → delete API Gateway.

Project 5: Dev vs Prod — Stage Variables and Environment Separation

🎯 Objective: Deploy the same API to dev and prod stages, each pointing to a different Lambda version. Understand how stage variables give you true environment isolation.

⏱️ Time: 40–50 min

💰 Cost: Free tier

  1. Using orders-crud Lambda: publish a version. Actions → Publish new version. Description: "stable v1". Note the version number. Create alias prod pointing to version 1.

  2. Update the Lambda code — add "env": "dev" to the GET response body. Deploy but do NOT publish a new version. Create alias dev pointing to $LATEST.

    import json

ORDERS = {
    "ORD-001": {"orderId": "ORD-001", "item": "Laptop", "status": "shipped", "qty": 1},
    "ORD-002": {"orderId": "ORD-002", "item": "Mouse",  "status": "pending", "qty": 2},
    "ORD-003": {"orderId": "ORD-003", "item": "Keyboard","status": "shipped", "qty": 1},
}

def lambda_handler(event, context):
    method = event["httpMethod"]
    path_params = event.get("pathParameters") or {}
    query_params = event.get("queryStringParameters") or {}

    # GET /orders/{orderId}
    if method == "GET" and path_params.get("orderId"):
        order_id = path_params["orderId"]
        order = ORDERS.get(order_id)
        if not order:
            return respond(404, {"error": f"Order {order_id} not found"})
        return respond(200, order)

    # GET /orders?status=shipped
    if method == "GET":
        status_filter = query_params.get("status")
        results = list(ORDERS.values())
        if status_filter:
            results = [o for o in results if o["status"] == status_filter]
        return respond(200, {"orders": results, "count": len(results)})

    # POST /orders
    if method == "POST":
        body = event.get("body")
        if not body:
            return respond(400, {"error": "Request body is required"})
        data = json.loads(body)
        if not data.get("item"):
            return respond(400, {"error": "Field 'item' is required"})
        new_id = f"ORD-{len(ORDERS)+1:03}"
        ORDERS[new_id] = {"orderId": new_id, "item": data["item"],
                          "status": "pending", "qty": data.get("qty", 1)}
        return respond(201, {"message": "Order created", "orderId": new_id})

    return respond(405, {"error": "Method not allowed"})

def respond(status_code, body):
    return {
        "statusCode": status_code,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps(body)
    }

Project 7 — Level 2: Notes API (Clean Code Structure)

🎯 Objective: Build a complete Notes API with proper code structure (handler / service / validation layers), UUIDs, timestamps, error handling, and clean JSON responses. This is what a real junior cloud engineer produces.

⏱️ Time: 60–75 min

💰 Cost: Free tier (DynamoDB + Lambda + API Gateway)

logger = logging.getLogger()
logger.setLevel(logging.INFO)

# ── Validation layer ────────────────────────────────────────
def validate_note(data):
    if not data.get("title"):
        return "Field 'title' is required"
    if len(data.get("title", "")) > 200:
        return "Title must be 200 characters or fewer"
    if not data.get("content"):
        return "Field 'content' is required"
    return None

# ── Service layer ───────────────────────────────────────────
def create_note(data):
    note = {
        "noteId":    str(uuid.uuid4()),
        "title":     data["title"],
        "content":   data["content"],
        "createdAt": datetime.now(timezone.utc).isoformat(),
        "updatedAt": datetime.now(timezone.utc).isoformat(),
    }
    table.put_item(Item=note)
    return note

def get_all_notes():
    result = table.scan()
    return sorted(result.get("Items", []),
                  key=lambda n: n["createdAt"], reverse=True)

def delete_note(note_id):
    existing = table.get_item(Key={"noteId": note_id}).get("Item")
    if not existing:
        return None
    table.delete_item(Key={"noteId": note_id})
    return existing

# ── Handler layer ───────────────────────────────────────────
def lambda_handler(event, context):
    method      = event["httpMethod"]
    path_params = event.get("pathParameters") or {}
    note_id     = path_params.get("noteId")

    logger.info(json.dumps({"method": method, "path": event.get("path"),
                             "noteId": note_id}))
    try:
        if method == "GET" and not note_id:
            return ok(get_all_notes())

        if method == "POST":
            body = event.get("body")
            if not body:
                return bad_request("Request body is required")
            data = json.loads(body)
            error = validate_note(data)
            if error:
                return bad_request(error)
            return created(create_note(data))

        if method == "DELETE" and note_id:
            deleted = delete_note(note_id)
            if not deleted:
                return not_found(f"Note {note_id} not found")
            return ok({"message": "Note deleted", "noteId": note_id})

        return respond(405, {"error": "Method not allowed"})

    except Exception as e:
        logger.error(f"Unhandled error: {str(e)}")
        return respond(500, {"error": "Internal server error"})

# ── Response helpers ────────────────────────────────────────
def respond(code, body):
    return {"statusCode": code,
            "headers": {"Content-Type": "application/json"},
            "body": json.dumps(body, default=str)}

def ok(body):      return respond(200, body)
def created(body): return respond(201, body)
def bad_request(msg): return respond(400, {"error": msg})
def not_found(msg):   return respond(404, {"error": msg})

Part B: Async Processing with SQS (Future Topic — Architecture Preview)

💡 This section is a conceptual preview. SQS (Simple Queue Service) is an AWS messaging service covered in a future session. Read through the architecture now so you understand why it's used — come back and build it after covering SQS. AWS SQS Developer Guide

The problem with synchronous APIs: when a customer places an order, do they really need to wait for the payment to be processed, the inventory to be updated, and the confirmation email to be sent — all in one HTTP response? In production, the answer is no. Orders are placed instantly; the downstream processing happens asynchronously.

Here's how the async architecture works:

  1. POST /orders → Lambda immediately saves the order to DynamoDB with status pending and returns 202 Accepted to the customer. Fast.
  2. Lambda also sends a message to an SQS queue with the order details.
  3. A separate Payments Lambda is triggered by the SQS queue, processes payment, and updates the order status to confirmed or failed.
  4. The customer polls GET /orders/{id} to check the final status.

Figure 11: Async order processing — customer gets instant 202, payment happens in background

This pattern decouples your API from downstream processing, makes the system more resilient (if the payment service is slow or down, orders still get accepted), and enables retry logic (SQS automatically retries failed messages).

Chaos 2: Lambda Concurrency Limit

  1. Add a 2-second sleep to your Lambda handler (import time; time.sleep(2)). Deploy. This makes each invocation hold a concurrency slot for 2 seconds.

  2. Set reserved concurrency to 1: Lambda → orders-smart → Configuration → Concurrency → Reserve concurrency = 1. This means only 1 request can be processed at a time.

    📸 Screenshot: Reserved concurrency set to 1 on the Lambda function

  3. Send two simultaneous requests (open two terminal tabs, run curl at the same time). One gets 200; the other gets 429 (Lambda throttled).

  4. Reset: remove reserved concurrency → remove the sleep.

Chaos 3: Observe Caching Behavior

  1. Enable API Gateway response caching on GET /orders: Stages → dev → Settings → Enable API Cache. Cache capacity: 0.5 GB. Method override on GET /orders: enable caching, TTL = 30 seconds.

  2. Add a timestamp to your Lambda response so you can see when the data was generated:

    "generatedAt": datetime.utcnow().isoformat()

  3. Make 5 requests to GET /orders in rapid succession:

done

    📸 Screenshot: Same timestamp across 5 requests — all served from cache, Lambda invoked once

  5. Wait 30 seconds (TTL expires). Make another request — you'll see a new timestamp. Cache miss → Lambda invoked.

  6. Cleanup: Disable caching → reset all throttle overrides → remove sleep from Lambda.

🤔 Reflection Questions

1. Your frontend (at myshop.com) calls your API and gets a CORS error. It works perfectly in Postman. What is the problem and exact fix?

💡 Hint

Postman is not a browser and doesn't enforce the Same-Origin Policy. The fix requires two steps: one on the resource, one after.

2. You updated your Lambda code and deployed it, but API clients still see the old response. What did you forget?

💡 Hint

Lambda deployment and API Gateway deployment are separate actions. Updating Lambda code doesn't automatically update what clients receive.

3. A company wants three partners with different daily API limits — 1K, 10K, and 100K requests. How do you implement this?

💡 Hint

You need a way to identify each partner and a mechanism to enforce per-partner limits. Two API Gateway features work together here.

4. When would you choose HTTP API over REST API? Give a concrete scenario for each.

💡 Hint

Think about the features REST API has that HTTP API doesn't. If you need any of those features, you must use REST. Otherwise, HTTP saves money.

5. Your API is receiving 50,000 requests per second — far above the default limit. What response do clients get, and what are two options to handle the load?

💡 Hint

There's a specific HTTP status code for throttle exceeded. One solution is an AWS Support request; another reduces backend load without hitting Lambda every time.

6. You're building a mobile app where end users log in and then make API calls. Which authorizer type should you use — Lambda Authorizer or Cognito? Why?

💡 Hint

Lambda Authorizer is for custom/proprietary tokens. Cognito is for managed user pools with standard JWT. Who are the callers — users or developers?

7. An internal API should never be reachable from the internet — only from EC2 instances in your VPC. How do you configure this?

💡 Hint

There's a specific API Gateway endpoint type for this. It pairs with a VPC feature you know from the VPC Networking notes — a specific type of VPC Endpoint.
