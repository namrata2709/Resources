📦 S3 Static Website Hosting — Quick Recap

Before we dive into CloudFront, let's understand the starting point: S3 Static Website Hosting. S3 (Simple Storage Service) is AWS's object storage — think of it like a giant file cabinet in the cloud where you store files, images, HTML pages, and videos.

What Is Static Website Hosting?

A static website has no server-side processing — it's just HTML, CSS, JavaScript, and image files. S3 can serve these files directly to a browser without you needing a web server like Apache or Nginx.

To enable it, you go to your S3 bucket → Properties → Static website hosting → Enable, and specify your index document (usually index.html). AWS then gives you an endpoint URL like:

http://my-bucket.s3-website.ap-south-1.amazonaws.com

Figure 2: S3 static website hosting — bucket with public access and direct endpoint

The Two Problems With This Approach

❌ Problem 1 — High Latency: Your bucket is in one region (e.g., Mumbai). Users in Canada or Australia must travel thousands of miles over the internet to reach it, causing slow load times.

❌ Problem 2 — Security Risk: To make the website accessible, you must make the bucket public and add a bucket policy granting GetObject permission to everyone (Principal: "*"). This means your S3 bucket is exposed to the entire internet — a security concern.

The solution to both problems? CloudFront.

☁️ What Is Amazon CloudFront?

Amazon CloudFront is AWS's Content Delivery Network (CDN) service. A CDN is a globally distributed network of servers that caches copies of your content close to your users, so they don't have to reach all the way back to your origin server every time.

Think of it like a chai stall network. Instead of everyone in Delhi, Chennai, and Kolkata driving to a single factory in Mumbai to get their tea, CloudFront sets up local chai stalls (called edge locations) in every city. The tea is prepared once at the factory (your S3 bucket), distributed to all stalls, and from then on, locals get it instantly from the nearest stall.

Figure 3: CloudFront edge locations worldwide — content is cached near every user

Key Concepts

  • Origin: The source of truth for your content — this is your S3 bucket (or an EC2 server, or an ALB).
  • Distribution: The CloudFront "delivery network" you create. It has a unique endpoint like d111111abcdef8.cloudfront.net.
  • Edge Locations: Mini data centers spread across the globe (400+ worldwide). CloudFront caches your content here.
  • Cache Hit: When a user requests content and CloudFront already has it cached at the nearest edge location — served instantly.
  • Cache Miss: When CloudFront doesn't have the content yet — it fetches from the origin (S3), caches it, and then serves it. Subsequent requests for the same content are cache hits.
  • TTL (Time to Live): How long CloudFront keeps content cached before fetching a fresh copy from origin. Default is 24 hours.

According to AWS documentation, CloudFront integrates natively with S3, EC2, Elastic Load Balancing, Route 53, AWS Shield, and AWS WAF — making it a core piece of a secure, high-performance web architecture.

🔧 Creating a CloudFront Distribution

When you create a CloudFront distribution, you provide three essential things. Think of these as filling out an order form for a delivery service.

Figure 4: Three required inputs when creating a CloudFront distribution

Step 1: Specify the Origin

The origin is where CloudFront fetches content from when it doesn't have it cached. In our case, the origin is an S3 bucket. You select the bucket from a dropdown in the CloudFront console.

The origin is the source of truth — CloudFront always fetches fresh or uncached content from here.

Step 2: Specify the Default Root Object

This is the file CloudFront should serve when a user visits the root URL (e.g., https://d111abc.cloudfront.net/ with no file path). You set this to index.html — your website's main landing page.

Step 3: Origin Access Control (OAC)

This is the security magic. Origin Access Control (OAC) is a CloudFront permission mechanism that tells AWS: "Only this specific CloudFront distribution is allowed to access this S3 bucket — block everyone else."

OAC (Origin Access Control) allows CloudFront to access a private S3 bucket on behalf of users, so the bucket never needs to be made public.

Here's how it works in practice:

  1. You create the distribution with OAC enabled.
  2. AWS gives the distribution a unique ID.
  3. You update your S3 bucket policy to say: "Allow GetObject only from this specific CloudFront distribution ID."
  4. All direct access to the S3 endpoint is blocked — only CloudFront can read your files.

💡 OAC is the modern replacement for the older OAI (Origin Access Identity) method. AWS recommends OAC for all new distributions as it supports additional S3 features like server-side encryption with AWS KMS.

Figure 5: OAC flow — CloudFront is the only allowed reader of the private S3 bucket

After Creation: Your Distribution Endpoint

Once the distribution is deployed (takes 5–10 minutes to propagate), you get a URL like:

https://d111111abcdef8.cloudfront.net

Users access your website using this URL. The old S3 static website endpoint will no longer work (because the bucket is now private). This is intentional — you want all traffic through CloudFront, not directly to S3.

⚡ Key Exam Fact: After enabling OAC and making the bucket private, the direct S3 static website endpoint returns a 403 Forbidden or Access Denied error. Users must use the CloudFront distribution URL.

🛡️ Updating the S3 Bucket Policy for OAC

When you create a CloudFront distribution with OAC, the console will actually generate the bucket policy for you and offer to copy it or apply it automatically. This policy restricts S3 access to only your CloudFront distribution.

The generated policy looks like this:

{ "Version": "2012-10-17", "Statement": [ { "Sid": "AllowCloudFrontServicePrincipal", "Effect": "Allow", "Principal": { "Service": "cloudfront.amazonaws.com" }, "Action": "s3:GetObject", "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*", "Condition": { "StringEquals": { "AWS:SourceArn": "arn:aws:cloudfront::YOUR-ACCOUNT-ID:distribution/YOUR-DISTRIBUTION-ID" } } } ]
}

Notice the key difference from the old public bucket policy: the Principal is cloudfront.amazonaws.com (not "*"), and there's a Condition locking it down to your specific distribution ID. This means even other CloudFront distributions cannot access your bucket — only yours.

✅ Best Practice: Always use OAC with a private S3 bucket. Never leave your S3 bucket public when CloudFront is in front of it. This gives you both global performance and strong security.

🌍 Amazon Route 53 — DNS & Domain Management

Now your website is on CloudFront with a URL like d111abc.cloudfront.net. But try remembering that. Your customers certainly can't. That's where Route 53 comes in.

Route 53 is AWS's Domain Name System (DNS) service. DNS is the internet's phone book — it translates human-friendly names like www.myshop.com into the machine addresses (IP addresses or distribution endpoints) that computers use to connect.

Figure 6: Route 53 DNS resolution flow — custom domain → CloudFront → cached content → user

Key Route 53 Concepts

  • Authoritative Name Server:Route 53 is an authoritative name server, meaning it has the final, definitive answer for the domain names it manages.
  • Hosted Zone: A container in Route 53 that holds DNS records for a domain. When you register or transfer a domain, you create a hosted zone for it. A hosted zone is a container for DNS records for a specific domain.
  • Name Servers (NS Records): When you create a hosted zone, Route 53 assigns you 4 name servers (e.g., ns-123.awsdns-45.com). You point your domain registrar to these name servers so Route 53 becomes authoritative for your domain.
  • A Record: Maps a domain name to an IP address — or in AWS, to an alias endpoint like a CloudFront distribution.
  • Alias Record: A Route 53-specific extension of an A record that can point to AWS resources (CloudFront, ELB, S3) by their DNS name rather than a fixed IP. It's free and updates automatically when the resource's IP changes.

Setting Up Route 53 for Your CloudFront Site

  1. Register or Transfer Your Domain: Buy a domain (e.g., myshop.com) from Route 53 or any registrar like GoDaddy. If using an external registrar, update the domain's NS records to point to Route 53 name servers.

  2. Create a Hosted Zone: In Route 53, create a hosted zone for your domain. Route 53 provides 4 name servers — update your domain registrar to use these.

  3. Create an A Record (Alias): Inside the hosted zone, create an A record:
    — Name: www (for www.myshop.com) or leave blank for the root domain
    — Type: A — Alias
    — Alias target: Your CloudFront distribution (d111abc.cloudfront.net)

  4. Add the Domain to CloudFront: In your CloudFront distribution settings, add the custom domain under Alternate domain names (CNAMEs). You also need an SSL certificate from AWS Certificate Manager (ACM) — in the us-east-1 region — for HTTPS to work.

💡 DNS Propagation: After making DNS changes, it can take up to 48 hours for the changes to propagate across the globe — though it's usually much faster (minutes to a few hours). This is because DNS servers cache results for a period defined by the TTL (Time to Live) value on each record.

Figure 7: Route 53 hosted zone with NS records and A alias record pointing to CloudFront

Route 53 Routing Policies

Route 53 is much more than simple DNS. It offers intelligent traffic routing policies:

  • Simple Routing: Standard DNS — returns a single value (or multiple values in random order).
  • Weighted Routing: Split traffic between resources by percentage — great for A/B testing or gradual deployments. E.g., 90% to v1, 10% to v2.
  • Latency-Based Routing: Routes users to the AWS region that gives them the lowest latency — ideal for multi-region setups.
  • Failover Routing: Routes traffic to a primary resource and automatically switches to a secondary (backup) if health checks fail.
  • Geolocation Routing: Routes traffic based on where the user is physically located — e.g., users in India go to Mumbai, users in Germany go to Frankfurt.
  • Geoproximity Routing: Routes based on geographic proximity and lets you bias traffic toward certain regions.
  • Multi-Value Answer Routing: Like Simple, but performs health checks and only returns healthy records.
Route 53 Failover Routing uses health checks to automatically redirect traffic to a backup resource when the primary becomes unhealthy.

According to AWS documentation, Route 53 can also perform health checks on your resources and, based on health, stop routing traffic to unhealthy endpoints — making it a key tool for high availability architectures.

🔄 Full Architecture: S3 + CloudFront + Route 53

Let's walk through the complete flow from the moment a user types your domain name to when they see your website:

Figure 8: Complete architecture flow — custom domain to cached content delivery

  1. User types www.myshop.com in their browser.
  2. The browser queries DNS → Route 53 returns the CloudFront distribution endpoint.
  3. The browser connects to the nearest CloudFront edge location to the user.
  4. CloudFront checks its cache:
    • ✅ Cache Hit: Serves content immediately from the edge location — super fast.
    • ❌ Cache Miss: CloudFront makes a request to the origin (private S3 bucket) using OAC credentials, fetches the content, caches it at the edge, and serves it to the user.
  5. Subsequent users from the same region get a cache hit — content never leaves the edge location again until TTL expires.

⚡ Result: The S3 bucket remains private and secure. Users get content from the nearest edge location — low latency globally. The domain name is human-friendly. All three problems solved in one architecture.

🐍 AWS SDK — Boto3 & Python Automation

So far we've been using the AWS Console (the website you click around in) to create and configure resources. But what if you need to create 50 EC2 instances? Or automate a deployment every time code is pushed? That's where the AWS SDK comes in.

What Is the AWS SDK?

SDK stands for Software Development Kit. The AWS SDK is a set of libraries that lets developers interact with AWS services directly from their code, without opening a browser. Instead of clicking "Launch Instance" in the console, you write a function that does it programmatically.

The AWS SDK allows developers to interact with AWS services programmatically from within their application code.

AWS provides SDKs for many languages:

  • Python → Boto3
  • JavaScript/Node.js → AWS SDK for JavaScript
  • Java → AWS SDK for Java
  • Go, Ruby, .NET, PHP, and more

What Is Boto3?

Boto3 is the official AWS SDK for Python. It allows Python developers to create, configure, and manage AWS services — S3, EC2, Lambda, DynamoDB, and hundreds more — using clean Python code.

Boto3 is the AWS SDK for Python, used to automate AWS resource management programmatically.

SDK vs Console vs CLI

Figure 9: Three ways to interact with AWS — Console, CLI, and SDK

All three interact with the same underlying AWS APIs. The choice depends on your use case:

  • Console: Best for beginners, visual exploration, and one-time tasks. Not scriptable.
  • CLI: Best for quick commands, shell scripts, and DevOps pipelines. Highly loved by developers and DevOps engineers.
  • SDK: Best for embedding AWS calls inside application code, complex logic, and production automation.

💻 Boto3 in Action — Launching an EC2 Instance with Python

In the session, the instructor walked through a complete Python script that uses Boto3 to launch an EC2 instance automatically. Let's break it down step by step.

Installing Boto3

Boto3 is a Python package. Install it with pip:

pip install boto3

Configuring AWS Credentials

Before running any Boto3 script, you must authenticate. Boto3 needs to know who you are (which AWS account) and what permissions you have.

Run this command in your terminal and provide your credentials:

aws configure

You'll be prompted for:

AWS Access Key ID: [your access key]
AWS Secret Access Key: [your secret key]
Default region name: ap-south-1
Default output format: json

💡 You create Access Keys in the IAM console: IAM → Users → Your User → Security credentials → Create access key. Never share or commit access keys to GitHub.

The Python Script

Here is the complete Python script to launch an EC2 instance, wait for it to be running, and print its IP addresses:

import boto3 # Configuration
REGION = "ap-south-1" # Mumbai region
AMI_ID = "ami-0c55b159cbfafe1f0" # Ubuntu Server AMI (changes per region!)
INSTANCE_TYPE = "t3.micro" def launch_ec2_instance(): try: # Create a boto3 EC2 resource client ec2 = boto3.resource("ec2", region_name=REGION) # Launch the instance instances = ec2.create_instances( ImageId=AMI_ID, InstanceType=INSTANCE_TYPE, MinCount=1, MaxCount=1, TagSpecifications=[ { "ResourceType": "instance", "Tags": [{"Key": "Name", "Value": "MyPythonInstance"}] } ] ) instance = instances[0] print(f"Launching EC2 instance... Instance ID: {instance.id}") # Wait until the instance is running print("Waiting for instance to enter running state...") instance.wait_until_running() # Reload to get updated attributes (public/private IP) instance.reload() print(f"Instance created: {instance.id}") print(f"Public IP: {instance.public_ip_address}") print(f"Private IP: {instance.private_ip_address}") print(f"EC2 instance launched successfully: {instance.id}") except Exception as e: print(f"Launch failed: {e}") if __name__ == "__main__": launch_ec2_instance()

Script Breakdown

Figure 10: Boto3 script execution flow — from import to running instance

  • import boto3: Imports the Boto3 library — gives Python access to all AWS services.
  • boto3.resource("ec2", region_name=REGION): Creates a high-level EC2 resource object for a specific region. Boto3 has two interfaces: resource (high-level, Pythonic) and client (low-level, closer to raw API).
  • create_instances(): The function that actually launches EC2 instances. Key parameters:
    • ImageId: The AMI ID — the blueprint for your server. AMI IDs are region-specific, so the same Ubuntu AMI has a different ID in Mumbai vs us-east-1.
    • InstanceType: The hardware size — t3.micro is Free Tier eligible.
    • MinCount / MaxCount: Number of instances to launch.
    • TagSpecifications: Adds a name tag to find the instance easily in the console.
  • instance.wait_until_running(): A built-in waiter — the script pauses here until the instance reaches the running state. No need to manually poll.
  • instance.reload(): Refreshes the instance object from AWS — necessary because attributes like public IP are not available immediately after launch.
  • try/except: Error handling — if anything fails (wrong AMI, insufficient permissions), the exception is caught and printed cleanly.
AMI IDs are region-specific — the same operating system image has a different AMI ID in each AWS region.

How to Find the Correct AMI ID

  1. Go to the EC2 console in the target region.
  2. Click Launch Instances.
  3. Choose your OS (e.g., Ubuntu Server).
  4. Copy the AMI ID shown — e.g., ami-0c55b159cbfafe1f0.
  5. Use that ID in your script for that region.

✅ Pro Tip: In production, use the Systems Manager Parameter Store to dynamically fetch the latest AMI ID for a given OS — so your script always uses the most current, patched image without hardcoding.

Running the Script

# Save the file as launch_ec2.py
# Then run:
python launch_ec2.py

Expected output:

Launching EC2 instance... Instance ID: i-0abcd1234ef567890
Waiting for instance to enter running state...
Instance created: i-0abcd1234ef567890
Public IP: 13.234.45.67
Private IP: 172.31.5.22
EC2 instance launched successfully: i-0abcd1234ef567890

You can then go to the EC2 console, refresh, and see your newly launched instance with the tag name, public IP, and private IP all matching the script output.

📂 Boto3 with S3 — Real-World Developer Use Case

Boto3 is not just for EC2. Developers use it constantly with S3. A very common real-world pattern: a web application accepts resume uploads from job applicants, stores them in S3, and processes them.

import boto3 def upload_resume_to_s3(file_path, bucket_name, applicant_name): """Upload a resume file to S3 with a structured key.""" s3 = boto3.client("s3", region_name="ap-south-1") s3_key = f"resumes/{applicant_name}/resume.pdf" try: s3.upload_file(file_path, bucket_name, s3_key) print(f"Resume uploaded: s3://{bucket_name}/{s3_key}") except Exception as e: print(f"Upload failed: {e}") # Usage
upload_resume_to_s3("resume.pdf", "my-company-bucket", "Rohan_Sharma")

This is exactly the kind of code a developer writes in the backend of a job portal. The same principles apply — import Boto3, create a client or resource, call the appropriate API method, handle errors.

🔬 CloudFront — Advanced Features & Exam Facts

Cache Behaviors

CloudFront allows you to set different caching rules for different URL patterns. For example:

  • /images/* → cache for 7 days (images rarely change)
  • /api/* → don't cache (dynamic API responses)
  • / default → cache for 24 hours

Cache Invalidation

What if you update your website and want CloudFront to serve the new version immediately (before TTL expires)? You create an invalidation. This tells CloudFront to remove specific files (or all files with /*) from all edge caches immediately.

# CLI to invalidate all files in a distribution
aws cloudfront create-invalidation \ --distribution-id E1234567890ABC \ --paths "/*"
CloudFront cache invalidation removes objects from edge caches before the TTL expires — first 1,000 invalidation paths per month are free.

HTTPS and SSL/TLS

CloudFront can serve your content over HTTPS. When using a custom domain, you need an SSL certificate from AWS Certificate Manager (ACM). The certificate must be created in the us-east-1 (N. Virginia) region — this is a hard requirement regardless of where your origin is located.

SSL certificates used with CloudFront must be in the us-east-1 region in AWS Certificate Manager — even if your origin is in another region.

Signed URLs and Signed Cookies

For premium or private content (like paid video courses), CloudFront supports Signed URLs and Signed Cookies to ensure only authorized users can access content.

  • Signed URL: Grants access to a single specific file — good for individual downloads.
  • Signed Cookie: Grants access to multiple files — good for streaming video with multiple segments.

CloudFront Pricing

CloudFront pricing is based on:

  • Data Transfer Out (to users) — price varies by region (lower in US/Europe, higher in South America/Australia).
  • HTTP/HTTPS Requests — per 10,000 requests.
  • Invalidation Requests — first 1,000 paths/month are free.
  • Free Tier: 1 TB data transfer + 10 million HTTP/HTTPS requests per month — for the first 12 months.

There are three price classes to control cost: All regions, Only US/Europe/Asia, or Only US/Europe. Using a lower price class means you skip some edge locations but pay less.

According to AWS documentation, CloudFront has no upfront fees and no minimum commitments. You pay only for what you use, billed at the end of each month.

🚀 Project 13: CI/CD — Auto-Deploy to S3 + Invalidate CloudFront on Push

🎯 Objective: Set up a GitHub Actions workflow that automatically deploys your website to S3 and invalidates CloudFront every time you push to the main branch. This is core DevOps thinking.

⏱️ Time: 30–45 min

💰 Cost: GitHub Actions free for public repos. AWS costs: S3 + CloudFront Free Tier.

📊 Level: Job-Level / DevOps

  1. Create a GitHub repository. Push your website files (index.html, about.html, etc.) to the main branch.

  2. Create an IAM user for GitHub Actions with limited permissions. In IAM → Users → Create user. Attach an inline policy:

    { "Version": "2012-10-17", "Statement": [ { "Effect": "Allow", "Action": ["s3:PutObject", "s3:DeleteObject", "s3:ListBucket"], "Resource": [ "arn:aws:s3:::YOUR-BUCKET-NAME", "arn:aws:s3:::YOUR-BUCKET-NAME/*" ] }, { "Effect": "Allow", "Action": "cloudfront:CreateInvalidation", "Resource": "arn:aws:cloudfront::YOUR-ACCOUNT-ID:distribution/YOUR-DIST-ID" } ]
}

    📸 Screenshot: IAM policy for GitHub Actions with minimal S3 and CloudFront permissions

  3. Generate Access Key + Secret Key for this IAM user. Add them to GitHub: Repository → Settings → Secrets and variables → Actions → New repository secret. Create two secrets: AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY.

    📸 Screenshot: GitHub Actions secrets with AWS credentials added

  4. Create the workflow file in your repo at .github/workflows/deploy.yml:

    name: Deploy to AWS S3 + CloudFront on: push: branches: [main] jobs: deploy: runs-on: ubuntu-latest steps: - name: Checkout code uses: actions/checkout@v3 - name: Configure AWS credentials uses: aws-actions/configure-aws-credentials@v2 with: aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }} aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }} aws-region: ap-south-1 - name: Sync files to S3 run: | aws s3 sync . s3://YOUR-BUCKET-NAME \ --exclude ".git/*" \ --exclude ".github/*" \ --delete - name: Invalidate CloudFront cache run: | aws cloudfront create-invalidation \ --distribution-id YOUR-DISTRIBUTION-ID \ --paths "/*" echo "Invalidation submitted — cache will clear in ~30 seconds"

  5. Commit and push this file to main. Go to GitHub → Actions tab — watch the workflow run automatically.

    📸 Screenshot: GitHub Actions workflow run showing all steps completed successfully

  6. Make a change to index.html, commit, and push. Watch the workflow auto-run and the website update live within ~30 seconds.

✅ Verification: Push to main → GitHub Actions auto-runs → S3 synced → CloudFront invalidated → website updated. No manual steps needed after initial setup.

🚀 Project 15: Fault-Tolerant Architecture — Failover Routing

🎯 Objective: Set up Route 53 Failover Routing with a primary CloudFront distribution and a backup S3 static page. Configure health checks so Route 53 automatically redirects on failure.

⏱️ Time: 45–60 min

💰 Cost: Route 53 health checks: $0.50/month each. CloudFront Free Tier.

📊 Level: Job-Level / Reliability

💰 Cost Note: Each Route 53 health check costs $0.50/month. Delete them after the project to avoid charges.

  1. You need two CloudFront distributions: your primary (from Project 4/14) and a secondary "failover" distribution pointing to a minimal S3 page that says "Site temporarily unavailable — please try again shortly."

  2. Create a Route 53 health check: Route 53 → Health checks → Create health check. Configure:

    • What to monitor: Endpoint
    • Protocol: HTTPS
    • Domain name: your primary CloudFront distribution domain
    • Path: /index.html
    • Request interval: 30 seconds
    • Failure threshold: 3

    📸 Screenshot: Route 53 health check configured for primary CloudFront distribution

  3. Update the www A record in Route 53 to use Failover routing:

    • Edit the existing record: Routing policy → Failover. Record type → Primary. Associate with the health check you created.
    • Create a second www A record: Routing policy → Failover. Record type → Secondary. Alias to the secondary (failover) CloudFront distribution. No health check.

    📸 Screenshot: Route 53 failover routing — Primary and Secondary A records

  4. Verify health check is Healthy (green): Route 53 → Health checks → [health check]. Your primary distribution should report healthy within 1–2 minutes.

    📸 Screenshot: Route 53 health check showing Healthy status

  5. Simulate a failure (optional, careful): temporarily disable the primary CloudFront distribution. Within 90 seconds, Route 53 detects the health check failure and routes traffic to the secondary. Re-enable primary to restore normal routing.
