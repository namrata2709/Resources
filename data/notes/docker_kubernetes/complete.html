🚀 Introduction: Containers vs Virtual Machines

Imagine you've built a Python web app on your laptop. It works perfectly. You push it to a server — and it breaks. Missing libraries, wrong Python version, different OS. Sound familiar? This is the classic "works on my machine" problem.

⚡ Containers solve this: A container packages your application and everything it needs to run — libraries, dependencies, configs — into one portable unit that runs the same everywhere.

Figure 1: Containers share the host OS kernel — no need for a full OS per app like VMs

With a Virtual Machine, you're renting an entire house — full OS, its own memory, its own CPU allocation. With a container, you're renting a furnished room in a shared building — lightweight, isolated, but sharing the plumbing (the host OS kernel).

FeatureVirtual MachineContainer
Startup timeMinutesSeconds
SizeGBs (full OS)MBs (app + deps)
IsolationFull hardware isolationProcess-level isolation
PortabilityModerateVery high
Resource usageHeavyLightweight
Use caseFull OS neededMicroservices, CI/CD

Containers are lightweight, isolated processes that share the host OS kernel — unlike VMs which each require a full operating system.

🐳 Docker Fundamentals

Docker is the most popular containerization tool. When you install Docker, you're not just getting one thing — you get two components that work together:

Figure 2: Docker's two-component architecture — CLI talks to the Daemon

Component 1: Docker CLI (Command Line Interface)

This is what you interact with. When you type docker run, you're talking to the CLI. It's your control panel — the interface where you give instructions.

Component 2: Docker Daemon (dockerd)

This runs silently in the background as a service. It's the engine that actually builds and runs containers. The CLI sends your requests to the Daemon, and the Daemon does the work.

💡 Think of it like a restaurant: You (the user) talk to the waiter (Docker CLI), who takes your order to the kitchen (Docker Daemon), which prepares your food (the container).

⚠️ Two Troubleshooting Rules You Must Remember

Whenever Docker commands aren't working, check these two things first:

❌ Rule 1: Is the Docker Daemon (service) running in the background? If the daemon is stopped, nothing works. Check with: sudo systemctl status docker
❌ Rule 2: Is your user in the docker group? By default, only the root user can run Docker commands. If you're logged in as ubuntu on an EC2 instance and run docker ps, you'll get a permission error.

Fix Rule 2 by adding your user to the docker group:

sudo usermod -aG docker ubuntu
newgrp docker   # Apply immediately without restarting

By default, only the root user can run Docker commands — non-root users must be added to the docker group using usermod -aG docker username.

📄 Dockerfile & Images

To create a container, Docker needs a recipe. That recipe is called a Dockerfile. Think of it like a blueprint — just as an architect's blueprint tells builders exactly how to construct a house, a Dockerfile tells Docker exactly how to build your container image.

Figure 3: The build pipeline — Dockerfile → Image → Container

Understanding the Pipeline

A Dockerfile is a text file with instructions to build an image. An image is a read-only template. A container is a running instance of that image.

The analogy to EC2: AMI → EC2 Instance is the same as Docker Image → Container. The image is the template; the container is what's actually running.

Sample Dockerfile (Python App)

# Step 1: Choose your base image (pre-built OS + runtime)
FROM python:3.11-slim

# Step 2: Set the working directory inside the container
WORKDIR /app

# Step 3: Copy your files into the container
COPY . .

# Step 4: Install Python dependencies
RUN pip install -r requirements.txt

# Step 5: Tell Docker which port your app uses
EXPOSE 5000

# Step 6: Command to run when container starts
CMD ["python", "app.py"]
💡 What is a Base Image? FROM python:3.11-slim pulls a pre-built image from Docker Hub that already has Python installed. You're building on top of someone else's work — no need to install Python from scratch.

Building and Running

# Build an image from the Dockerfile in current directory
# -t gives it a name (tag)
docker build -t my-python-app:v1 .

# Run a container from that image
# -d = detached (background)
# -p = port mapping (host:container)
# --name = give the container a name
docker run -d -p 5000:5000 --name myapp my-python-app:v1

Dockerfile Instructions Reference

InstructionPurposeExample
FROMBase image to start fromFROM ubuntu:22.04
WORKDIRSet working directoryWORKDIR /app
COPYCopy files from host to containerCOPY . .
RUNExecute command during buildRUN apt-get update
ENVSet environment variablesENV PORT=3000
EXPOSEDocument which port app usesEXPOSE 8080
CMDDefault command when container startsCMD ["node", "app.js"]
ENTRYPOINTFixed command (CMD becomes args)ENTRYPOINT ["python"]

Docker images are read-only templates — every time you run a container, Docker adds a thin writable layer on top of the image. The image itself never changes.

🗄️ Container Registries

Once you build an image, where do you store it? Just like GitHub stores your code, container registries store your Docker images. You can then pull these images from anywhere — your laptop, an EC2 instance, a CI/CD pipeline.

Figure 4: Public vs Private registries — Docker Hub for public, ECR for private/enterprise use

Public Registry: Docker Hub

Docker Hub (hub.docker.com) is the default registry. When you run docker pull ubuntu, Docker fetches it from Docker Hub automatically. It's like GitHub but for container images.

# Pull an official image from Docker Hub
docker pull ubuntu:22.04

# Pull your own image (username/repo:tag)
docker pull yourname/myapp:v1

# Push your image to Docker Hub
docker tag my-python-app:v1 yourname/my-python-app:v1
docker push yourname/my-python-app:v1
✅ When to use Docker Hub: Open-source projects, learning, sharing images with the community, pulling official base images like ubuntu, python, node.

Private Registry: AWS ECR (Elastic Container Registry)

ECR (Elastic Container Registry) is AWS's private container image registry — like a private Docker Hub for your organization's images.

Why private? In a company, you don't want your proprietary application images visible to the public. ECR keeps them inside your AWS account, protected by IAM policies.

# Authenticate Docker to ECR (run this first)
aws ecr get-login-password --region us-east-1 | \
  docker login --username AWS --password-stdin \
  123456789.dkr.ecr.us-east-1.amazonaws.com

# Tag your image for ECR
docker tag my-app:v1 \
  123456789.dkr.ecr.us-east-1.amazonaws.com/my-app:v1

# Push to ECR
docker push \
  123456789.dkr.ecr.us-east-1.amazonaws.com/my-app:v1
💡 EC2 + ECR Integration: Attach an IAM Role to your EC2 instance with ECR read permissions. Now your EC2 can pull private images without storing credentials. This is the AWS-recommended approach.

🔧 Docker Compose

Real applications are never just one container. A typical web app has: a frontend container, a backend API container, and a database container. Running and wiring them together manually with docker run commands is tedious and error-prone.

Docker Compose lets you define all your containers in a single docker-compose.yml file and launch them all with one command.

Figure 5: Docker Compose manages multiple containers as a single application stack

Sample docker-compose.yml (E-commerce App)

version: '3.8'

services:
  # Frontend container
  frontend:
    image: my-frontend:v1
    ports:
      - "80:80"
    depends_on:
      - backend
    networks:
      - app-network

  # Backend API container
  backend:
    image: my-backend:v1
    ports:
      - "3000:3000"
    environment:
      - DB_HOST=database
      - DB_PORT=27017
    depends_on:
      - database
    networks:
      - app-network

  # Database container
  database:
    image: mongo:6.0
    volumes:
      - mongo-data:/data/db
    networks:
      - app-network

# Named volume for data persistence
volumes:
  mongo-data:

# Custom network for inter-container communication
networks:
  app-network:
    driver: bridge

Docker Compose Commands

# Start all containers (detached mode)
docker-compose up -d

# Stop all containers (keeps containers)
docker-compose stop

# Stop and remove containers + networks
docker-compose down

# View logs from all containers
docker-compose logs -f

# Check running services
docker-compose ps

Docker Compose uses a docker-compose.yml file to define and run multi-container applications — one command (docker-compose up) starts all services together.

🌐 Docker Networking & Volumes

Docker Networks

Containers are isolated by default — they can't see each other unless connected to the same network. Docker provides different network types for different scenarios.

Figure 6: Docker network types — Bridge (default), Host, and port mapping for external access

Network TypeDescriptionUse Case
Bridge (default)Private internal network for containers on same hostMulti-container apps on one machine
HostContainer shares host machine's network directlyPerformance-critical apps, no isolation needed
OverlaySpans multiple Docker hosts (used in Swarm/K8s)Distributed multi-host setups
NoneNo networking — fully isolatedBatch jobs, security-sensitive workloads

By default, all Docker containers on the same host are connected to the bridge network and can communicate with each other using container names as hostnames.

Port Mapping — Exposing Containers to the World

Your container might run a web server on port 80 inside the container. But to make it accessible from the internet (via EC2 public IP), you need to map a host port to the container port.

# Map host port 8080 to container port 80
docker run -d -p 8080:80 --name website nginx

# Now accessible at: http://EC2-public-IP:8080
# (Remember to open port 8080 in Security Group!)

Docker Volumes — Persistent Data

Containers are ephemeral — when you delete a container, all data inside it is lost. This is a problem for databases! If your MongoDB container is deleted, all your data disappears.

Docker Volumes solve this by storing data on the host machine, outside the container.

# Named volume (Docker manages location)
docker run -d \
  -v mongo-data:/data/db \
  --name mydb mongo:6.0

# Bind mount (you specify the path on host)
docker run -d \
  -v /home/ubuntu/mydata:/app/data \
  --name myapp my-app:v1
✅ Best Practice: Always use volumes for databases and any stateful data. Even if you destroy and recreate your container, your data survives because it lives on the host.

Docker volumes persist data beyond the container lifecycle — data stored in volumes survives container deletion and restarts.

🤔 Why Do We Need Container Orchestration?

You now know Docker. You can build images, run containers, network them, compose them. But here's the problem — Docker alone is not enough for production.

Figure 7: Docker alone cannot handle production requirements — orchestration fills the gaps

Imagine you're running an e-commerce site with 10 containers (frontend, cart, payments, inventory...). What happens when:

  • Traffic spikes on a sale — your single container is overwhelmed
  • A container crashes at 2 AM — no one restarts it until morning
  • Your EC2 instance goes down — all 10 containers die with it
  • You deploy a new version — users experience downtime
❌ Docker alone cannot: Auto-scale containers when traffic increases, auto-restart failed containers (self-healing), load balance traffic across multiple containers, perform zero-downtime rolling deployments, spread containers across multiple servers for high availability.

Container orchestration tools automatically manage containers in production — handling scaling, load balancing, self-healing, and zero-downtime deployments that Docker alone cannot provide.

☸️ Kubernetes (K8s) Deep Dive

Kubernetes (K8s — because there are 8 letters between K and s) is the industry-standard container orchestration platform. Open-source, free, and works on any cloud — AWS, Azure, GCP, or on-premises.

💡 The Orchestra Analogy: An orchestra has many musicians (containers). Left alone, they'd each play at their own pace — chaos. The conductor (Kubernetes) stands in the middle, tells everyone when to start, when to stop, how fast to play, and brings in new musicians when needed. Kubernetes is your container conductor.

Figure 8: Kubernetes cluster — Control Plane (brain) + Worker Nodes (execution)

📸 From Session: Kubernetes cluster architecture shared during the lecture — Master Node with Control Plane on the left, Worker Nodes on the right handling actual container execution

The Kubernetes Cluster

A Kubernetes cluster has two main parts: the Control Plane (the brain that makes decisions) and Worker Nodes (the machines that run your containers).

Control Plane Components

1. API Server (kube-apiserver)

The API Server is the single entry point for all communication with the cluster. Every request — from you, from other components, from external tools — goes through the API Server. It validates and authenticates every request using RBAC (Role-Based Access Control).

You talk to the API Server using kubectl (pronounced "kube-control") — the CLI tool for Kubernetes.

# Talk to cluster through API server using kubectl
kubectl get pods                    # List all pods
kubectl apply -f deployment.yaml    # Deploy from file
kubectl describe pod mypod          # Get pod details
kubectl logs mypod                  # View pod logs

2. etcd

etcd is the cluster's source of truth — a distributed key-value store that holds the entire cluster state including configurations, secrets, and current status of all resources.

Think of etcd as the cluster's memory — everything the cluster knows lives here. If etcd is lost without a backup, your cluster state is gone.

3. Scheduler (kube-scheduler)

When you request a new Pod, the Scheduler decides which Worker Node it should run on. It evaluates CPU and memory available on each node, checks constraints you've set, and picks the best fit. It's the decision engine for pod placement.

4. Controller Manager (kube-controller-manager)

A collection of controllers that continuously watch the cluster state and ensure the actual state matches the desired state you declared. If you say "I want 3 replicas," but only 2 are running, the Deployment Controller creates a 3rd. Controllers include: Node Controller, ReplicaSet Controller, Deployment Controller, and more.

5. Cloud Controller Manager

Integrates Kubernetes with cloud provider APIs (AWS, Azure, GCP) — manages cloud-specific resources like Load Balancers, Volumes, and Node lifecycle.

Worker Node Components

Kubelet

Kubelet is an agent running on every Worker Node — it acts as the bridge between the Control Plane and the container runtime, ensuring containers described in PodSpecs are running and healthy.

The Control Plane doesn't talk directly to Worker Nodes — it talks to the Kubelet, which carries out instructions locally.

Kube-proxy

Manages network rules on each Worker Node. It ensures that Pods can communicate with each other and with services, implementing Kubernetes' networking model — any Pod can reach any other Pod by IP.

Container Runtime

The software that actually runs containers. Options include containerd, CRI-O, or Docker. Kubernetes doesn't care which you use — it talks to the runtime via the Container Runtime Interface (CRI).

Key Kubernetes Objects

Pod

The smallest deployable unit in Kubernetes. A Pod wraps one or more containers that share network and storage. You don't run containers directly in Kubernetes — you run Pods.

💡 Pod vs Container: A Pod is like a shared apartment. Containers inside share the same IP address and can communicate via localhost. Usually one container per pod, but sidecar patterns use multiple.

Deployment

Manages replica sets of Pods. You tell Kubernetes: "I want 3 replicas of my web app running at all times." The Deployment controller ensures this — if one crashes, it creates a replacement. It also handles rolling updates.

# deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-web-app
spec:
  replicas: 3          # Always keep 3 pods running
  selector:
    matchLabels:
      app: my-web-app
  template:
    metadata:
      labels:
        app: my-web-app
    spec:
      containers:
      - name: web
        image: my-web-app:v2
        ports:
        - containerPort: 80

Service

Pods are temporary — they come and go, and their IP addresses change. A Service provides a stable endpoint (IP + DNS name) that always routes to the correct Pods, even as pods are replaced. Think of it as a load balancer in front of your pods.

Namespace

Virtual clusters within a physical cluster. Used to separate environments (dev, staging, prod) or teams within the same cluster.

Self-Healing in Action

Kubernetes self-healing means that if a container or Pod crashes, Kubernetes automatically detects it and creates a replacement — zero manual intervention required.

☁️ AWS Container Services: ECS, EKS & Fargate

AWS provides managed container services so you don't have to set up Kubernetes or orchestration infrastructure yourself. Three key services:

Figure 10: AWS Container Services — choose based on your control vs simplicity tradeoff

ECS — Elastic Container Service

ECS is AWS's native container orchestration service — it manages Docker containers without requiring Kubernetes knowledge, deeply integrated with AWS services like IAM, ALB, and CloudWatch.

ECS is like Kubernetes, but AWS-only and simpler. If you're all-in on AWS and don't need Kubernetes, ECS is often the right choice.

ECS Core Concepts

ConceptWhat it isAnalogy
ClusterLogical grouping of compute capacityThe datacenter
Task DefinitionBlueprint for your container (like a Dockerfile for ECS)Recipe card
TaskA running instance of a Task DefinitionThe actual dish
ServiceKeeps desired number of Tasks running, handles load balancingRestaurant manager

Fargate — Serverless Containers

AWS Fargate is a serverless compute engine for containers — you don't provision or manage EC2 instances; AWS manages the underlying infrastructure, and you only pay for the CPU and memory your containers actually use.

⚡ ECS on EC2 vs ECS on Fargate:
EC2 launch type: You manage EC2 instances, more control, lower cost at scale.
Fargate launch type: AWS manages servers, no EC2 to manage, pay per task, great for variable workloads.

EKS — Elastic Kubernetes Service

EKS is AWS-managed Kubernetes — AWS runs and maintains the Control Plane (API server, etcd, controllers) for you, so you only manage the Worker Nodes (EC2 or Fargate) and your application workloads.

Why EKS over plain Kubernetes?

  • AWS patches and upgrades the Control Plane automatically
  • High availability Control Plane across multiple AZs
  • Seamless integration with IAM, VPC, ALB, ECR, CloudWatch
  • Same kubectl commands — portable skills across clouds

Choosing the Right AWS Container Service

Figure 11: How to choose between ECS, EKS, and Fargate

ScenarioRecommended Service
Already using Kubernetes, want it on AWSEKS
AWS-only, want simplicity, don't need K8sECS
Don't want to manage servers at allFargate (with ECS or EKS)
Need maximum control and cost optimization at scaleECS or EKS on EC2
Variable workloads, pay-per-useFargate

CI/CD Integration — The Full Picture

In production, containers don't get deployed manually. A CI/CD pipeline automates the entire flow:

  1. Developer pushes code to GitHub feature branch
  2. Pull Request triggers CI pipeline (Jenkins, GitHub Actions)
  3. Pipeline runs: tests → docker build → docker push to ECR
  4. CD pipeline: updates ECS/EKS with new image tag
  5. Rolling update deploys new containers with zero downtime

In a DevOps pipeline, Docker images are built automatically by CI tools like Jenkins, pushed to ECR, and then deployed to ECS or EKS — enabling fully automated zero-downtime deployments.

📝 Overall Summary

  • Containers vs VMs: Containers are lightweight isolated processes sharing the host OS kernel — faster, smaller, and more portable than full Virtual Machines.
  • Docker Architecture: Two components — Docker CLI (user interface) and Docker Daemon (background service). Non-root users must be added to the docker group to run commands.
  • Dockerfile → Image → Container: Write a Dockerfile (recipe), build an Image (read-only template), run a Container (running instance). Same as AMI → EC2 Instance in AWS.
  • Registries: Docker Hub for public images, AWS ECR for private organizational images. EC2 instances use IAM Roles to pull from ECR without stored credentials.
  • Docker Compose: Manages multi-container applications via a single docker-compose.yml file — one command to start/stop the entire stack.
  • Docker Networking: Bridge network (default) lets containers on the same host communicate. Port mapping exposes containers to external traffic.
  • Docker Volumes: Persist data beyond the container lifecycle — critical for databases. Without volumes, data is lost when a container is deleted.
  • Why Orchestration: Docker alone can't auto-scale, self-heal, load balance, or do zero-downtime deployments. Container orchestration tools provide these production requirements.
  • Kubernetes (K8s): Industry-standard open-source orchestration. Cluster = Control Plane (API Server, etcd, Scheduler, Controller Manager) + Worker Nodes (Kubelet, kube-proxy, container runtime, Pods).
  • AWS ECS: AWS-native orchestration — Cluster, Task Definition, Task, Service. Simpler than Kubernetes for AWS-only workloads.
  • AWS Fargate: Serverless containers — no EC2 to manage, AWS handles infrastructure, pay per task. Works with both ECS and EKS.
  • AWS EKS: AWS-managed Kubernetes Control Plane. Use when you need Kubernetes and want AWS to manage the Control Plane.

Project 1: Containerize a Python Flask App

🎯 Objective: Write a Dockerfile, build an image, run a container on EC2

⏱️ Time: 30-45 min

💰 Cost: Free tier (t2.micro)

Create these three files in a folder called flask-app/:

# app.py
from flask import Flask
app = Flask(__name__)

@app.route("/")
def home():
    return "<h1>Hello from Docker Container!</h1>"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
# requirements.txt
flask==3.0.0
# Dockerfile
FROM python:3.11-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
EXPOSE 5000
CMD ["python", "app.py"]
  1. Launch Ubuntu EC2 (t2.micro), SSH in
  2. Install Docker: sudo apt update && sudo apt install docker.io -y
  3. Enable Docker: sudo systemctl enable --now docker
  4. Add user to docker group: sudo usermod -aG docker ubuntu && newgrp docker
  5. Build image: docker build -t my-flask-app:v1 .
  6. Run container: docker run -d -p 5000:5000 --name flask-app my-flask-app:v1
  7. Open port 5000 in Security Group
  8. Visit: http://[EC2-public-IP]:5000

Project 2: Break Your Container — Then Fix It

🎯 Objective: Learn real debugging skills — the most valuable skill in production

⏱️ Time: 30-45 min

💰 Cost: Free tier

Real work is mostly fixing broken things. This project teaches you to debug containers systematically.

Step 1 — Break it intentionally (3 ways):

# Break 1: Remove requirements.txt before building
rm requirements.txt
docker build -t broken-app:v1 .
# What error do you see?
# Break 2: Wrong port in docker run
docker run -d -p 9999:5000 --name broken-app my-flask-app:v1
# App runs but cant access it — why?
# Break 3: Wrong CMD in Dockerfile
# Change CMD to: CMD ["python", "wrong-file.py"]

docker run --name broken-app2 broken-app:v2

Step 2 — Debug using these commands:

# Check container logs (most important command)
docker logs flask-app
docker logs --tail 50 flask-app

# Get inside a running container
docker exec -it flask-app bash

# Check why a container exited
docker inspect flask-app | grep -A 5 "ExitCode"

# Check all containers including stopped ones
docker ps -a

Project 4: Volume Data Loss Test

🎯 Objective: Feel exactly why volumes matter — this sticks permanently once you lose data

> db.users.insertOne({name: "Alice", role: "DevOps"})
> exit
docker rm -f mongo-with-vol
docker run -d --name mongo-with-vol -v mongo-data:/data/db mongo:6.0
docker exec -it mongo-with-vol mongosh
> use testdb
> db.users.find()
# Alice is still there ✅

  - DB_HOST=wrong-hostname

docker-compose up -d
docker-compose logs backend
# You will see: MongoServerError: connect ECONNREFUSED

# Fix: change back to DB_HOST=database
# Then verify:
docker exec -it backend ping database

📸 Screenshot: Connection refused error from wrong DB_HOST vs successful connection after fix

✅ Key Takeaway: Containers on the same Docker Compose network communicate using the service name as hostname — not IP address, not localhost.

Project 10: Rolling Update — Zero Downtime

🎯 Objective: Deploy a new version with zero downtime — this is how production deployments work

⏱️ Time: 20-30 min

💰 Cost: Free

# Update deployment.yaml: change image tag to v2
# Then apply:
kubectl apply -f deployment.yaml

# Watch rolling update in real time
kubectl get pods --watch
# Old pods terminate ONE AT A TIME
# New v2 pods come up before old ones die

# Check rollout status
kubectl rollout status deployment/flask-app

# If v2 is broken, rollback instantly:
kubectl rollout undo deployment/flask-app

📸 Screenshot: Rolling update — old pods terminate one at a time as new pods come up, maintaining availability

✅ Key Takeaway: Rolling updates mean users never see downtime. If v2 is broken, kubectl rollout undo reverts in seconds.

# Authenticate Docker to ECR

  [ACCOUNT-ID].dkr.ecr.us-east-1.amazonaws.com/my-flask-app:v1

docker pull [ACCOUNT-ID].dkr.ecr.us-east-1.amazonaws.com/my-flask-app:v1
docker run -d -p 5000:5000 \
  [ACCOUNT-ID].dkr.ecr.us-east-1.amazonaws.com/my-flask-app:v1

✅ Key Takeaway: ECR + IAM Role = secure image distribution without storing credentials anywhere. This is the AWS-recommended pattern.

Project 12: ECS Deployment

🎯 Objective: Deploy your containerized app using AWS ECS — no Kubernetes needed

⏱️ Time: 45-60 min

💰 Cost: ~$0.01/hour for Fargate tasks

  1. AWS Console → ECS → Create Cluster → Name: my-cluster
  2. Create Task Definition → Container: use your ECR image URI, port 5000
  3. Create Service → Desired count: 2 → Launch type: Fargate
  4. Wait for tasks to reach RUNNING state
  5. Get public IP from task details and visit port 5000

📸 Screenshot: ECS Service showing 2 running Fargate tasks — desired count matches running count

✅ Compare with Kubernetes: ECS is simpler — no kubectl, no YAML manifests. Best choice for AWS-only teams who don't need Kubernetes portability.

Project 13: Fargate Serverless Container

🎯 Objective: Run a container with zero server management — the modern cloud pattern

⏱️ Time: 20-30 min

💰 Cost: Pay per task second only

  1. Edit your ECS Service → Change launch type to Fargate
  2. Set CPU: 0.25 vCPU, Memory: 0.5 GB
  3. No EC2 instances to manage — AWS handles all servers
  4. Tasks start within 30-60 seconds
  5. Verify: no EC2 instances visible in your account — only running tasks

📸 Screenshot: Fargate task running — no EC2 instances, AWS manages all infrastructure

✅ Key Takeaway: With Fargate you never SSH into a server, never patch an OS. You just define what to run — AWS handles the how.
