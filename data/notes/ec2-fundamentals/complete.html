📖 Introduction

Imagine you're building a website for your school project. You've written all the code on your laptop — but your laptop can't be "on the internet" 24/7, and it's definitely not powerful enough to handle thousands of visitors at once. What do you do? You rent a server from someone who has the infrastructure to handle it.

That's exactly what Amazon EC2 is — a service that lets you rent virtual servers in the cloud, on demand, and pay only for what you use. Instead of buying and maintaining expensive physical hardware, you go to AWS, pick the server configuration you need, and have it running in minutes.

Figure 1: EC2 at a Glance — your virtual server in the AWS cloud

In this session, we'll cover everything from scratch — what EC2 is, how to configure it, how to connect to it, and how to deploy a real project on it. By the end, you'll understand not just what EC2 is, but why every component exists and how they all fit together.

⚡ Key Idea: EC2 allows you to create and manage virtual servers in the AWS cloud — no physical hardware required. You pay only for the time your server is running.

🖥️ Shell, CLI, and GUI — The Basics

Before we dive into EC2, we need to talk about how humans communicate with computers — because on the servers you'll be managing in AWS, you will almost always be using a CLI, not a graphical interface.

What is a Shell?

Your operating system (Windows, Linux, macOS) manages all the hardware resources — CPU, memory, disk. But you can't talk to the OS directly. There's a translator in the middle called a shell.

A shell is a program that acts as an interface between the user and the operating system. It accepts your commands, interprets them, and passes them to the OS for execution.

Figure 2: Shell Architecture — your request flows through the shell to the OS

When you type a command like mkdir vinsys, here's what actually happens:

  1. You type the command in the terminal
  2. The shell receives your command
  3. The shell invokes a utility — a small, ready-made program (like mkdir) designed to perform a specific action
  4. The utility, through the shell, sends the request to the OS
  5. The OS interacts with the hardware to create the directory

💡 Utilities are pre-built programs that perform specific operations — like mkdir (make directory), ls (list files), cd (change directory). They are part of your OS installation and are used by the shell on your behalf.

GUI vs CLI

There are two ways to interact with your computer — graphical (GUI) or text-based (CLI).

A GUI (Graphical User Interface) uses visual elements like icons, windows, and menus. A CLI (Command Line Interface) uses text commands typed into a terminal.

Figure 3: GUI vs CLI — two ways to create a folder

In GUI (Windows Explorer), to create a folder you: open a window → navigate to a location → right-click → select "New Folder." In CLI, you simply type mkdir foldername — one line, done instantly.

FeatureGUICLI
SpeedSlower (navigation required)Fast (one command)
Learning curveLow — intuitiveHigher — must memorize commands
AutomationDifficultEasy — scripts run commands automatically
Remote accessRequires special toolsNative — SSH works natively
Resource usageHigh — renders graphicsVery low — text only

✅ Why CLI is preferred in cloud: When you connect to an AWS server over the internet, you don't need (or want) a full graphical interface. CLI is lightweight, fast, scriptable, and works perfectly over SSH connections with low bandwidth.

Shells on Different Operating Systems

Different operating systems come with different default shells:

  • Windows:PowerShell (modern) and Command Prompt (legacy) — both support CLI
  • Linux/Unix:Bash (Bourne Again Shell) — the most widely used shell in the Linux world
  • macOS: Zsh (default since macOS Catalina), also supports Bash

Windows is primarily GUI-first with CLI support added; Linux and Unix are CLI-first by default, with optional GUI support. This is why Linux is preferred for cloud servers — it's efficient, uses fewer resources, and is purpose-built for CLI-driven management.

💡 Terminology Note: In GUI, you work with folders. In CLI, the same concept is called a directory. mkdir stands for "make directory." Both are the same thing — just different terminology depending on your context.

☁️ What is EC2?

Now that you understand how to communicate with servers, let's talk about the servers themselves. In AWS, the service you use to create and manage virtual servers is called EC2.

Amazon EC2 (Elastic Compute Cloud) is an AWS service that allows you to create, launch, and manage virtual machines (called instances) in the AWS cloud.

Figure 4: EC2 as IaaS — you control the software, AWS manages the hardware

EC2 is an example of IaaS (Infrastructure as a Service) — meaning you are responsible for managing your own infrastructure (OS, software, configuration), while AWS manages the physical hardware underneath.

⚡ IaaS means more control, more responsibility. With EC2, you decide the OS, install your own software, configure security rules, and manage scaling. AWS just provides the physical machine and network.

Why Would You Use EC2?

Think of it this way: your laptop is a great personal computer, but it's not designed to host a website that thousands of people visit. It's not always on, it's not in a data center, and it can't scale up when traffic spikes. EC2 solves all of these problems.

  • Host websites and web apps — Deploy your project on a server that's always online
  • Run backend servers — APIs, databases, microservices
  • Development and testing — Spin up a clean environment in minutes, destroy it when done
  • Big data processing — Temporarily create powerful instances for data crunching
  • Machine learning — Use GPU-optimized instances for model training

EC2 vs Owning a Physical Server

The instructor demonstrated this perfectly: if you run out of storage on a physical server in your office, you need to physically go buy a new hard drive, install it, and configure it — that could take days. With EC2 and EBS (Elastic Block Storage), you can increase your server's storage in seconds from the AWS console. Same goes for CPU and RAM — stop the instance, change the instance type, restart. Done.

✅ Pay-as-you-go: With EC2, you only pay for the time your instance is running. If you stop it, you stop paying for compute (though EBS storage still incurs cost). This makes it ideal for projects with variable traffic or temporary workloads.

🚀 Launching an EC2 Instance — Step by Step

Creating an EC2 instance is like filling out a form to describe exactly what kind of computer you want. AWS then builds that machine virtually, pulling resources from its physical data centers. Let's walk through each component you configure when launching an instance.

Figure 5: The Five Core Components of an EC2 Instance Configuration

Step 0: Select Your Region

Before you even open EC2, you must select your AWS region. A region is a geographic area containing multiple data centers. Resources you create are tied to the region you select — if you switch regions, your instances won't appear.

The instructor selected Asia Pacific (Mumbai) — ap-south-1 — which contains three availability zones (A, B, C). When you don't explicitly select an availability zone, AWS picks one for you automatically within your chosen region.

Step 1: Name and Tags

Every EC2 instance should have a human-readable name. AWS uses a tagging system — key-value pairs you attach to resources to organize and identify them. For example: Name = "demo-linux-server", Batch = "Invent129". You can add up to 50 tags per resource. This becomes very important when you have dozens of servers running in production.

Step 2: AMI — Your Software Configuration

The first major choice when creating an EC2 instance is the software configuration — and that's done through the AMI.

An AMI (Amazon Machine Image) is a software configuration template that contains the operating system, application servers, and any pre-installed applications needed to launch your instance.

Figure 6: What an AMI Contains — your complete software blueprint

Think of an AMI like a DVD image for your computer. When you buy a new laptop, you choose an OS (Windows, macOS, Linux). When you create an EC2 instance, you choose an AMI. AWS provides many ready-made AMIs — called Quick Start AMIs — covering different OS options.

Common free-tier eligible AMIs include:

  • Amazon Linux 2023 — AWS's own Linux distribution, optimized for AWS; standard user is ec2-user
  • Amazon Linux 2 — Previous version, still widely used
  • Ubuntu 22.04 LTS / 24.04 LTS — First one or two versions are free tier eligible
  • Windows Server 2019 / 2022 — Free tier eligible versions available

💡 Free Tier Tip: When selecting AMIs, always check the "Free tier eligible" label. Some AMIs come bundled with additional software (like NVIDIA drivers or deep learning tools) — these are typically not free tier and will incur charges.

The default username for Amazon Linux instances is ec2-user. For Ubuntu, it is ubuntu. For Windows, it is Administrator.

Step 3: Instance Type — Your Hardware Configuration

Once you've picked your OS, AWS asks: what hardware do you want? That's the instance type.

An instance type defines the hardware configuration of your EC2 instance — specifically the virtual CPU (vCPU), RAM, and supported storage options.

Just like a shopkeeper recommends a laptop based on your usage (gaming needs high CPU, databases need high RAM), AWS provides 5 categories of instance types based on workload requirements:

Figure 7: EC2 Instance Type Categories — choose based on your workload

General PurposeBalanced CPU, RAM, network — all workloadst2.micro, t3.small, m5.large
Compute OptimizedHigh CPU-intensive workloads — video encoding, HPCc5.large, c6i.xlarge
Memory OptimizedHigh RAM workloads — databases, caching, analyticsr5.large, x1e.xlarge

How to Read Instance Type Names

Instance type names follow a consistent format: family + generation + size. For example, t2.micro means:

  • t — Instance family (t = general purpose)
  • 2 — Generation (second generation)
  • micro — Size (the smallest, after nano)

Sizes range from nano → micro → small → medium → large → xlarge → 2xlarge etc. As size increases, CPU and RAM increase — and so does the cost.

💡 Free Tier:t2.micro (1 vCPU, 1 GB RAM) and t3.micro (2 vCPU, 1 GB RAM) are free tier eligible. You get 750 hours/month free for the first 12 months.

Step 4: Storage — EBS

Every EC2 instance needs a disk to store the OS and your application files. In AWS, this disk is not called a "hard drive" — it's called EBS.

EBS (Elastic Block Storage) is AWS's block storage service — it acts as the hard drive for your EC2 instance. By default, a new instance comes with 8 GB of EBS storage.

The key advantage: if 8 GB isn't enough, you can increase it immediately — no physical hardware changes needed. You can also attach multiple EBS volumes to a single EC2 instance.

⚡ Important: When you stop an EC2 instance to change its hardware configuration (instance type), your data on EBS is safe. You're only changing the CPU/RAM layer — the storage layer and its contents remain intact. When you restart, everything is exactly as you left it.

Step 5: Security Group — Your Firewall

Your server is running on the internet — without protection, anyone could send any kind of traffic to it. That's where Security Groups come in.

A Security Group is a virtual firewall that controls incoming (inbound) and outgoing (outbound) traffic to your EC2 instance. It acts like a watchman — checking every request against the rules before letting it in.

Figure 8: Security Group — your instance's gatekeeper

Security Group rules define what traffic is allowed. Each rule specifies:

  • Protocol — SSH, HTTP, HTTPS, etc.
  • Port number — e.g., port 22 for SSH, port 80 for HTTP, port 443 for HTTPS
  • Source — where the traffic is coming from (anywhere, a specific IP, etc.)

When you create an Amazon Linux instance with default settings, AWS automatically adds one inbound rule: Allow SSH (port 22) from anywhere (0.0.0.0/0). This allows you to log in remotely from any location using SSH.

❌ Security Note: Allowing SSH from "anywhere" is fine for learning, but in production you should restrict SSH access to your specific IP address. Exposing port 22 to the entire internet increases the risk of brute-force attacks.

Security Groups are stateful — meaning if you allow an inbound connection, the response traffic is automatically allowed outbound without needing an explicit outbound rule.

🔑 Key Pairs — Secure Login Without Passwords

You've configured your virtual server. Now you need a way to log into it. But EC2 doesn't use traditional username/password authentication — and there's a very good reason for that.

By default, EC2 does not support password-based authentication for SSH logins, because if someone discovers your password, they can access your server from anywhere in the world.

Instead, AWS uses a much more secure mechanism: key pairs.

What is a Key Pair?

A key pair consists of two cryptographically linked keys: a public key stored on your EC2 instance, and a private key downloaded and kept only on your local computer.

Think of it like a padlock and key analogy: the public key is the lock installed on your front door (the server), and the private key is the physical key you carry in your pocket. Only the person with the matching key can open that lock.

Figure 9: Key Pair Authentication — how your laptop connects to EC2 securely

How Key Pairs Work

  1. In the EC2 launch wizard, you create a new key pair (or select an existing one)
  2. AWS generates two keys — the public key is automatically stored inside your EC2 instance
  3. The private key file is immediately downloaded to your laptop (only happens once — never again)
  4. When you SSH into your EC2, you provide your private key file as part of the login command
  5. EC2 checks: does this private key match the public key stored inside? If yes — access granted

💡 Encryption: Both keys are encrypted files using RSA encryption (or ED25519 as an alternative). They are not plain text — they are mathematically linked so that what one key encrypts, only the other can decrypt.

Private Key File Formats

The private key can be downloaded in two formats: .pem (used with Linux/macOS and OpenSSH on Windows) and .ppk (used with PuTTY on Windows).

  • .pem — Works with the native ssh command in Terminal, PowerShell, or Command Prompt
  • .ppk — Required for PuTTY (a third-party SSH client for Windows)

❌ Critical Warning:Once the private key file is downloaded, AWS never shows it again. If you lose your private key, you cannot SSH into your instance using that key pair. Store it safely.

✅ Best Practice: Name your key pair something meaningful (e.g., invent129.pem). Store it in a secure folder on your laptop. Never share it, never upload it to GitHub, and never leave it in your Downloads folder permanently — move it somewhere safe.

🔗 Connecting to EC2 via SSH

Your EC2 instance is running. You have your private key file. Now how do you actually connect to and control this remote server? Through SSH.

SSH (Secure Shell) is a network protocol that allows you to securely log into and control a remote computer over an encrypted connection. For Linux-based EC2 instances, SSH runs on port 22.

The SSH Connection Flow

Figure 10: SSH Connection Flow — step by step from your laptop to EC2

Here's what happens when you SSH into your EC2 instance:

  1. From your laptop, you open a terminal (Command Prompt, PowerShell, or MobaXterm)
  2. You run the SSH command with: your private key file + the EC2 user name + the EC2 public IP address
  3. Your request travels over the internet to the EC2's public IP address
  4. The Security Group checks the incoming request — is SSH on port 22 allowed? If yes, it passes through
  5. Inside the EC2, a service called SSHD (SSH Daemon) is running continuously in the background, listening on port 22
  6. SSHD receives your request and asks: "Please provide your username and private key"
  7. Your SSH client sends the private key; SSHD compares it against the stored public key
  8. If they match — you're in! You now have a terminal session on your remote server

SSH Command Syntax

The full SSH command format for connecting to Amazon Linux is:

ssh -i "your-key-name.pem" ec2-user@your-public-ip-address

Breaking this down:

  • ssh — the SSH client command
  • -i "your-key-name.pem" — specifies the identity file (your private key); -i stands for "identity"
  • ec2-user — the default username for Amazon Linux instances
  • @your-public-ip-address — the public IP address of your EC2 instance

💡 Finding the SSH command: AWS makes this easy. Select your instance in the EC2 console → click Connect → choose SSH client tab. AWS displays the exact command you need to copy and paste. The command uses the Public DNS or public IP address interchangeably.

SSHing from Windows

On modern Windows (10+), you can SSH directly from Command Prompt or PowerShell — no extra software needed. Just navigate to the folder containing your .pem file first (very important!), then run the SSH command.

cd C:\Users\YourName\Downloads
ssh -i "invent129.pem" [email protected]

❌ Common Mistake: If you run the SSH command from a folder where your .pem file doesn't exist, you'll get a "No such file or directory" error. Always cd into the folder containing your key file first, or provide the full path to the key file.

Alternative SSH clients for Windows:

  • MobaXterm — A popular third-party tool that provides a GUI for SSH connections alongside a terminal. Useful for file transfers using SFTP
  • PuTTY — A classic, lightweight SSH client; requires the .ppk key format
  • FileZilla / WinSCP — Good for drag-and-drop file transfers to/from your server

Public IP vs Private IP

When you look at a running EC2 instance, you'll see two IP addresses:

The public IP address is accessible from the internet and is used to connect to your instance from outside AWS. The private IP address is only accessible within the AWS network and is used for communication between resources inside the same VPC.

💡 Note: By default, a public IP is assigned to your EC2 instance when launched and changes every time you stop and start the instance. For a permanent public IP, you would use an Elastic IP — a topic for a future session.

🌐 Deploying a Project on EC2

Once you're logged into your EC2 instance via SSH, you have a full Linux environment at your fingertips. Let's walk through how to deploy a web project on it.

Installing Software — Package Manager

On Amazon Linux, software is installed using the yum (or dnf on Amazon Linux 2023) package manager. For example, to install Git:

sudo yum install git -y

To install Apache HTTP Server (a web server that serves your HTML/website files to visitors):

sudo yum install httpd -y

Then start the web server service:

sudo systemctl start httpd

💡 sudo: When you SSH in as ec2-user, you're a regular user — not root. The sudo prefix lets you run commands with administrator (root) privileges. To permanently switch to root: sudo su -i.

Transferring Files to EC2

After logging in, you need to get your project files onto the server. There are two main ways:

Method 1 — SFTP with MobaXterm / FileZilla: Connect to your EC2 via SFTP, then simply drag and drop your project files from your laptop into the server's directory. The instructor demonstrated uploading a school website project to the EC2 using MobaXterm's file manager — just like copying files between folders on your desktop.

Method 2 — Git clone: If your project is on GitHub, clone it directly onto the server:

git clone https://github.com/yourusername/your-project.git

Serving Your Web Content

Apache serves web content from a specific directory: /var/www/html/. Copy your project files there:

sudo cp -r * /var/www/html/

Now, open your browser and navigate to your EC2's public IP address using HTTP:

http://your-ec2-public-ip

Your website is live! Anyone on the internet can access it using that IP address. (In a real production setup, you'd attach a domain name — but for learning, the IP works perfectly.)

✅ What you just did: You rented a server from AWS, installed a web server, uploaded your project, configured the firewall to allow HTTP traffic, and made your website publicly accessible on the internet — all in minutes, with no physical hardware.

Scaling Your EC2 Instance

One of the most powerful things about EC2 is how easy it is to scale:

  • Vertical scaling (scale up): Stop your instance → change the instance type to a more powerful one (more CPU, more RAM) → start it again. Your data and OS remain intact.
  • Storage scaling: Increase EBS volume size from the console — no downtime required in most cases.
  • Horizontal scaling: Launch multiple EC2 instances and distribute traffic between them (using a Load Balancer — a future topic).

Important Ports to Remember

For Linux SSH access, always open port 22 (SSH protocol) in your Security Group inbound rules.

For serving websites, open port 80 (HTTP) and/or port 443 (HTTPS) in your Security Group inbound rules.

  • An AMI is a software configuration template; an instance type is a hardware configuration — never confuse the two.

📝 Overall Summary

In this session, we covered a lot of ground — from how computers communicate using shells and CLIs, all the way to deploying a real web project on a virtual server in the AWS cloud. Here's the big picture.

The shell is the layer between you and the operating system. Whether you use PowerShell on Windows or Bash on Linux, the shell interprets your commands and makes them happen. CLI is faster, more powerful for automation, and essential for cloud work — Linux servers on AWS come CLI-first by default.

EC2 (Elastic Compute Cloud) is AWS's virtual server service and a prime example of IaaS. When you launch an EC2 instance, you configure five things: the AMI (what software/OS runs on it), the instance type (how much CPU and RAM it has), the EBS storage (its disk space), the key pair (how you'll log in securely), and the security group (what network traffic is allowed in and out).

Key pairs replace passwords with cryptographic security. The public key lives on the server; you keep the private key. When you SSH using your private key, the server verifies it against its public key. If they match, you're in — no password needed, no risk of password theft.

Once inside, you have a full Linux terminal. You can install software, transfer files, configure services, and deploy projects — all the same things you'd do on a physical server, but faster, cheaper, and scalable on demand.

Project 1: Launch and Connect to Your First EC2 Linux Server

🎯 Objective: Launch an Amazon Linux EC2 instance and SSH into it from your local Windows machine.

⏱️ Time: 20–30 min

💰 Cost: Free tier (t2.micro or t3.micro)

  1. Log in to your AWS account as root user. Select region: Asia Pacific (Mumbai) — ap-south-1.

    📸 Screenshot: AWS region selector showing Mumbai selected

  2. In the search bar, type EC2 and open the EC2 service. Click Instances in the left sidebar, then click Launch instances.

    📸 Screenshot: EC2 Instances page with Launch instances button visible

  3. Enter a name for your instance, e.g., demo-linux-server. Add an additional tag: Key = Batch, Value = your batch name.

  4. Under Application and OS Images (AMI), select Amazon Linux 2023 AMI (Free tier eligible).

    📸 Screenshot: AMI selection with Amazon Linux 2023 and Free tier eligible badge

  5. Under Instance type, select t2.micro or t3.micro (Free tier eligible — 1 vCPU, 1 GB RAM).

  6. Under Key pair (login), click Create new key pair. Enter a name (e.g., invent129), select RSA type, select .pem format, then click Create key pair. The file downloads automatically.

    📸 Screenshot: Create key pair dialog with .pem format selected

  7. In Network settings, verify that the default Security Group allows SSH (port 22) from anywhere. Leave other settings as default.

    📸 Screenshot: Security group settings with SSH port 22 from anywhere enabled

  8. Review the storage: 8 GB gp3 EBS volume (default). Click Launch instance.

    📸 Screenshot: Success page showing instance launched with instance ID

  9. Click View all instances. Wait until Instance State shows running and Status checks show 2/2 checks passed. Note the Public IPv4 address.

    📸 Screenshot: Instance in running state with Public IP visible

  10. Open Command Prompt on Windows. Navigate to your Downloads folder where the key file was saved:

    cd C:\Users\YourName\Downloads

  11. Run the SSH command (replace with your actual public IP):

    ssh -i "invent129.pem" ec2-user@YOUR_PUBLIC_IP

    When prompted "Are you sure you want to continue connecting?" type yes and press Enter.

    📸 Screenshot: Successful SSH login showing Amazon Linux 2023 welcome message

  12. Verification: You should see the Amazon Linux welcome banner. Type whoami — it should return ec2-user. Type pwd — you should be in /home/ec2-user.

  13. Cleanup: When done, type exit to disconnect from SSH. In the EC2 console, select your instance → Instance state → Terminate instance. Confirm termination. This stops all charges.

    💰 Cost Note: A running t2.micro instance is free tier eligible (750 hours/month). However, if you leave it running past free tier limits or forget to terminate it, you will incur charges. Always terminate instances when you are done with a lab.

Project 2: Deploy a Static Website on Your EC2 Server

🎯 Objective: Install Apache, deploy an HTML website, and make it publicly accessible via the EC2 public IP.

⏱️ Time: 20–30 min

💰 Cost: Free tier

  2. SSH into the instance as in Project 1.

  3. Update the package list and install Apache web server:

sudo yum install httpd -y

    sudo systemctl start httpd
sudo systemctl enable httpd

  5. Create a simple HTML page to test:

    echo "<h1>Hello from my AWS EC2 Server!</h1>" | sudo tee /var/www/html/index.html

  6. Copy your public IP address from the EC2 console. Open a browser and go to: http://YOUR_PUBLIC_IP

    📸 Screenshot: Browser showing live website served from EC2

  7. Cleanup: Terminate your EC2 instance when done to avoid charges.

    💰 Cost Note: The EC2 instance itself is free tier, but leaving it running counts toward your 750 hours/month limit. Terminate when finished.

Project 3: Clone a Real GitHub Project and Deploy It

🎯 Objective: Clone a real project from GitHub directly onto your server and serve it via Apache — the real-world dev → server → live workflow.

⏱️ Time: 25–35 min

💰 Cost: Free tier

  1. Launch an EC2 instance (Amazon Linux 2023, t2.micro). In Security Group, allow SSH (22) and HTTP (80). SSH in.

  2. Install Git and Apache:

    sudo yum install git httpd -y
sudo systemctl start httpd
sudo systemctl enable httpd

  3. Navigate to the web root and clone your project from GitHub:

    cd /var/www/html
sudo git clone https://github.com/YOUR_USERNAME/YOUR_REPO.git .

    💡 The . at the end clones directly into the current folder (no subfolder created). Make sure your repo contains index.html at the root level.

    📸 Screenshot: git clone running on EC2 inside /var/www/html

  4. Check the files are in place:

    ls -la /var/www/html

    📸 Screenshot: Project files visible inside /var/www/html

  5. Open a browser and go to http://YOUR_EC2_PUBLIC_IP. Your full project should be live.

    📸 Screenshot: GitHub project live on EC2 via browser

  6. Now simulate a code change. Edit a file directly on the server to see the live output loop:

    sudo nano /var/www/html/index.html

    Change something visible (e.g., a heading), save with Ctrl+O, exit with Ctrl+X, then refresh your browser.

    📸 Screenshot: nano editor open on index.html — make a visible change

  7. Cleanup: Terminate the instance when done.

    💰 Cost Note: Free tier eligible as long as you stay within 750 hours/month.

Project 4: Secure Your Server — Lock Down SSH Access

🎯 Objective: Harden your EC2 Security Group by restricting SSH access to your specific IP only — no more "open to the world".

⏱️ Time: 15–20 min

💰 Cost: Free tier

⚡ Why this matters: Leaving SSH open to 0.0.0.0/0 (the whole internet) means bots scan your server constantly attempting to break in. Restricting to your IP is Security Group best practice #1.

  1. Find your current public IP. Open a browser and visit whatismyip.com. Note your IP (e.g., 103.21.45.67).

  2. Launch an EC2 instance. When configuring the Security Group, instead of "Anywhere (0.0.0.0/0)" for SSH, select My IP from the dropdown — AWS auto-fills your current IP.

    📸 Screenshot: Security Group SSH rule with My IP selected (not Anywhere)

  3. Launch and SSH into the instance normally — it should work because you're connecting from the allowed IP.

  4. View your live Security Group rules: Select the instance → Security tab → click the Security Group link → Inbound rules. Confirm only your IP is listed for SSH.

    📸 Screenshot: Inbound rules showing SSH restricted to your specific IP only

  5. Edit a live rule (no restart needed): Click Edit inbound rules. Change the SSH source to 0.0.0.0/0 and save — then change it back to My IP and save again. Notice the change applies instantly.

    ✅ Key insight: Security Group rule changes apply to running instances immediately — no reboot required. This is critical knowledge for production incidents.

  6. Cleanup: Terminate the instance when done.

Project 5: Automate Server Setup with EC2 User Data

🎯 Objective: Use EC2 User Data to automatically install Apache and deploy a webpage at launch — zero manual SSH setup required.

⏱️ Time: 20–25 min

💰 Cost: Free tier

⚡ What is User Data? User Data is a shell script you attach to an EC2 instance at launch time. It runs automatically when the instance first boots — before you ever SSH in. This is the foundation of cloud automation and Auto Scaling.

  1. Go to EC2 → Launch instance. Configure AMI (Amazon Linux 2023), instance type (t2.micro), key pair, and Security Group (allow SSH 22 + HTTP 80).

  2. Scroll to the bottom of the launch wizard. Expand Advanced details. Scroll to find the User data text box.

    📸 Screenshot: User data text box in Advanced details section

  3. Paste the following script into the User data field:

    #!/bin/bash
yum update -y
yum install -y httpd
systemctl start httpd
systemctl enable httpd
echo "<html><body>
<h1>Automated Server Setup!</h1>
<p>This page was deployed automatically via EC2 User Data.</p>
<p>No SSH required!</p>
</body></html>" > /var/www/html/index.html

    📸 Screenshot: User data field with automation script pasted in

  4. Click Launch instance. Wait 1–2 minutes for the instance to start and the bootstrap script to complete.

  5. Get the public IP from the EC2 console. Open a browser and go to http://YOUR_PUBLIC_IP — without ever SSHing in, your website is already live.

    📸 Screenshot: Website live from User Data script — no manual setup needed

  6. Verify via SSH (optional): SSH in and check the Apache service and the deployed file:

    sudo systemctl status httpd
cat /var/www/html/index.html

  7. Cleanup: Terminate the instance when done.

    💰 Cost Note: Free tier eligible. Terminate immediately after verifying the deployment.

Project 6: Create an AMI Backup and Restore Your Server

🎯 Objective: Create a custom AMI from a configured server, terminate the original, then restore it perfectly by launching from the saved AMI — simulating real disaster recovery.

⏱️ Time: 30–40 min

💰 Cost: Free tier (small EBS snapshot storage charge may apply)

⚡ Why this matters: If your server crashes or gets compromised, you can spin up a new identical server in minutes from a saved AMI. This is the basis of backup and disaster recovery in AWS.

  1. Launch an EC2 instance. SSH in, install Apache, and deploy a custom webpage (Project 2 steps). This is the server you will "back up".

  2. In the EC2 console, select your running instance. Go to Actions → Image and templates → Create image.

    📸 Screenshot: Actions → Image and templates → Create image

  3. Fill in the form: Image name = my-web-server-backup, add a description. Click Create image.

    📸 Screenshot: Create image form with name and description filled in

  4. Go to EC2 → AMIs in the left sidebar. Wait until your AMI status changes from pending to available.

    📸 Screenshot: Custom AMI showing available status in AMIs list

  5. Simulate a disaster: Terminate your original EC2 instance. It's gone.

  6. Restore from your AMI: In the AMIs list, select your AMI → click Launch instance from AMI. Configure same instance type, key pair, and security group. Launch.

    📸 Screenshot: Launch instance from AMI — restoring your server

  7. Get the new instance's public IP. SSH in and navigate to the public IP in a browser. Your Apache setup and webpage are fully restored.

  8. Cleanup: Terminate the new instance. Go to AMIs → select your AMI → Actions → Deregister AMI. Then go to Snapshots → select the associated snapshot → Delete snapshot.

    💰 Cost Note: AMIs stored in your account create EBS snapshots that incur a small storage charge (~$0.05/GB/month). Always deregister test AMIs and delete their snapshots after the exercise.

Project 8: Deploy a Full Multi-Page Website (HTML + CSS + JS)

🎯 Objective: Deploy a complete frontend project with multiple pages, stylesheets, and JavaScript — and fix the real permission and path issues that trip up most beginners.

⏱️ Time: 30–40 min

💰 Cost: Free tier

⚡ Why this is harder than it looks: Single-file HTML is easy. Real projects have files across multiple folders. Understanding the /var/www/html/ structure and file permissions is where most beginners get stuck.

  1. Launch EC2 (Amazon Linux 2023, t2.micro). Allow SSH (22) + HTTP (80). SSH in. Install Apache and Git:

    sudo yum install httpd git -y
sudo systemctl start httpd
sudo systemctl enable httpd

  2. Clone to /tmp first (avoids permission issues), then copy to the web root:

    cd /tmp
git clone https://github.com/YOUR_USERNAME/YOUR_REPO.git project
sudo cp -r project/* /var/www/html/

    💡 Always clone to /tmp first, then copy with sudo. The /var/www/html/ directory requires root permissions to write — cloning directly there fails without sudo.

    📸 Screenshot: Project folders (css, js, images) copied into /var/www/html

  3. Set correct file permissions:

    sudo chmod -R 755 /var/www/html/
sudo chown -R apache:apache /var/www/html/

    💡 chmod 755 allows Apache to read all files. chown apache:apache makes the Apache service the owner of all files — required for it to serve them correctly.

    📸 Screenshot: Permissions and ownership set — no errors means success

  4. Restart Apache:

    sudo systemctl restart httpd

  5. Open http://YOUR_PUBLIC_IP in your browser. The full site — CSS styles, JavaScript, and all internal links — should render correctly.

    📸 Screenshot: Full styled multi-page site live on EC2 with CSS applied

  6. Troubleshoot broken CSS/JS: If the site looks unstyled, open browser DevTools (F12) → Console. Look for 404 errors. These usually mean Windows absolute paths like C:\Users\...\css\style.css were used instead of relative paths like css/style.css.

    ❌ Common Issue — Path errors: Your HTML file must reference assets with relative paths (e.g., css/style.css), not absolute Windows paths. Fix in your code locally and re-deploy.

  7. Cleanup: Terminate the instance when done.

🤔 Reflection Questions

1. Why does AWS use key pairs instead of passwords for SSH? What security problem does this solve?

💡 Hint

Think about what happens if someone discovers your password — compared to what would need to happen for someone to misuse a private key file.

2. You've launched an EC2 instance but can't SSH into it. The SSH command gives a "Connection timed out" error. What is the most likely cause?

💡 Hint

Your request is reaching the internet fine — but it's not reaching the server. What sits between the internet and your EC2 instance?

3. What is the difference between an AMI and an instance type? If you wanted a server running Ubuntu with 4 vCPUs and 16 GB RAM, which component determines each?

💡 Hint

One is about software. One is about hardware. Ubuntu is software. 4 vCPUs is hardware.

4. You stop your EC2 instance, change its instance type from t2.micro to t3.large, and restart it. What happens to your application files on the EBS volume? Why?

💡 Hint

Think about which layer you changed and which layer stores your data. Are they the same layer?

5. What happens to your EC2 instance's public IP address when you stop and restart it? Why might this be a problem in production?

💡 Hint

If your website is pointing to an IP address and that IP changes, what happens to people trying to visit your site?

6. Why is Linux preferred over Windows for cloud servers, even though Windows is more popular for desktops?

💡 Hint

Think about GUI vs CLI, resource usage, cost, and how servers are managed compared to personal computers.

7. A colleague says "I'll just share my private key file with the team so everyone can SSH into the server." What would you tell them?

💡 Hint

Think about what the private key represents and what happens if it falls into the wrong hands. What's the right approach for team access?
