🏢 AWS Organizations

Think of a large university. It has a main administration office, and under it there are separate departments — Engineering, Medical, Arts. Each department manages its own students, but the central admin sets the overall rules for everyone. AWS Organizations works exactly like this for AWS accounts.

Figure 2: AWS Organizations — Master Account, OUs, and Member Accounts

What is AWS Organizations?

AWS Organizations is a service that lets you centrally manage and govern multiple AWS accounts from a single management account (also called master account). Instead of logging into 10 different AWS accounts to apply security rules, you do it once from the top.

Key Concepts

Management Account (Master Account)

This is your main AWS account — the one you use to create or invite all other accounts. The management account has full control over all member accounts and cannot itself be controlled by SCPs.

Member Accounts

These are the individual AWS accounts that join your organization. A team in your company might use one account for development, another for testing, another for production. Each member account can have its own root user and IAM users.

Organizational Units (OUs)

An Organizational Unit (OU) is a logical grouping of accounts within AWS Organizations, similar to a folder in a file system. In class, the instructor created three OUs: Dev OU (for development accounts), QA OU (for quality assurance accounts), and Prod OU (for production accounts).

💡 Analogy: Think of OUs like folders on Google Drive. You group related files (accounts) into folders (OUs) to keep things organized. A policy applied to a folder automatically applies to everything inside it.

How to Add Accounts to an Organization

There are two ways to add accounts to your organization from the AWS console under AWS Organizations → Add an AWS Account:

  1. Invite an Existing Account: Enter the existing AWS account ID and send an invitation. When the account owner accepts, they join your organization as a member account.
  2. Create a New AWS Account: Provide a name and a unique email address. AWS automatically creates a new member account inside your organization within a few minutes.

Figure 3: Two Ways to Add Member Accounts to Your Organization

Service Control Policies (SCPs)

A Service Control Policy (SCP) is a JSON policy document that controls what actions AWS accounts in your organization can or cannot perform.

Remember in IAM sessions we covered: AWS Managed Policies, Customer Managed Policies, Inline Policies, and Permission Boundaries. SCPs are the next level — they work at the organizational level, sitting above all IAM policies.

⚡ Critical Difference: IAM policies control what individual users/roles can do within an account. SCPs control what the entire account (including its root user) can do.

SCPs apply to all users and roles in a member account, including the root user of that account. This is a very important exam fact — even the root user of a member account cannot do something if an SCP denies it.

How SCPs Work — Example

Imagine you create an SCP that says: "Deny all EC2 actions." You attach this SCP to the Dev OU. Now, every account inside Dev OU — and every user (including root) in those accounts — cannot launch or manage EC2 instances. In class, a student's screen shared the error: "API error" when trying to access EC2, confirming the SCP was working.

Figure 4: SCP Attached to OU Blocks All Accounts Inside It

Attaching SCPs

  • Attach to an OU: All accounts inside the OU inherit the SCP automatically. The recommended approach — change one OU rule, all accounts update instantly.
  • Attach to an individual account: Only that specific account is affected. Useful for exceptions.

💡 Default SCP: By default, AWS attaches a policy called FullAWSAccess to all accounts in an organization. This allows all actions — it's a starting point, not a security feature. You remove or restrict it by creating your own SCPs.

✅ Best Practice: Use SCPs with a deny-list strategy: start from FullAWSAccess and add explicit deny policies for what you want to block. This is safer than an allow-list approach for large teams.

Consolidated Billing

Consolidated Billing combines the AWS usage charges across all accounts in an organization into a single invoice paid by the management account.

Think of it like a family mobile plan — each family member uses their phone independently, but the bill comes as one combined invoice. Benefits of consolidated billing:

  • Simplified cost tracking: View all account expenses in one billing dashboard.
  • Volume discounts: AWS gives discounts for high usage. When all accounts' usage is combined, you're more likely to hit discount thresholds — AWS calls these volume pricing tiers.
  • Single payment: The management account pays all bills for all member accounts.

Figure 5: Consolidated Billing — All Account Bills Flow to One Invoice

📚 According to AWS documentation, you can also enable consolidated billing without using the full Organizations governance features. But using both together gives you maximum cost visibility and control.

📚 Source:AWS Organizations SCP Docs

Why Use AWS Organizations?

  • Centralized governance: One place to manage security policies across all accounts.
  • Cost management: Combined billing + volume discounts + cost tracking per account.
  • Security and compliance: SCPs enforce rules even root users can't override.
  • Isolation: Each team/environment gets its own account — a security breach in Dev won't automatically affect Prod.

🛡️ AWS WAF (Web Application Firewall)

Picture a college that releases a hackathon registration website. Suddenly, the site gets 10,000 fake form submissions per second — not from real students, but from automated bots created by hackers trying to inject malicious code and crash the server. How do you stop them? With AWS WAF.

Figure 6: AWS WAF Filters Bad Traffic Before It Reaches Your Application

What is AWS WAF?

AWS WAF (Web Application Firewall) is a security service that monitors and filters HTTP/HTTPS requests to protect your web applications from common web exploits and OWASP Top 10 attacks. It sits in front of your application and inspects every incoming request before it reaches your servers.

What Does WAF Protect Against?

  • SQL Injection: Hackers try to inject malicious SQL code through form fields to steal or corrupt your database.
  • Cross-Site Scripting (XSS): Attackers embed malicious scripts into web pages viewed by other users.
  • Bot attacks: Automated scripts send thousands of fake requests to overload your server or scrape data.
  • Bad IP addresses: Requests coming from known malicious IP addresses.
  • Geographic threats: Requests from countries where your service doesn't operate.
  • Rate-based attacks: A single IP sending too many requests in a short period.

How WAF Works — Rules and Rule Groups

WAF works by defining rules. Each rule specifies a condition and an action (Allow, Block, Count, CAPTCHA):

Figure 7: WAF Rule Types — IP-Based, Geo-Based, and Rate-Based Rules

Rule Types

  • IP-Based Rules: Block or allow requests from specific IP addresses. If you know an attacker's IP, blacklist it.
  • Geo-Based Rules (Location Rules): Allow only traffic from certain countries. Example: "Allow only from India, block all other countries."
  • Rate-Based Rules: Limit how many requests a single IP can make. Example: "Block any IP sending more than 1,000 requests per 5 minutes." This kills bot attacks automatically.
  • Managed Rule Groups: Pre-built rule sets by AWS or AWS Marketplace sellers — for example, AWS Core Rule Set covers OWASP Top 10 threats out of the box.

CAPTCHA Challenges

WAF can be configured to serve a CAPTCHA challenge ("Select all traffic lights") to suspicious requests instead of immediately blocking them. This allows real humans who triggered a rate limit to prove they're not bots, while bots fail and get blocked.

Where Can You Attach WAF?

AWS WAF can be attached to Amazon CloudFront, Application Load Balancer (ALB), Amazon API Gateway, and AWS AppSync.

WAF Logging

WAF can log every request it sees (allowed or blocked) to Amazon S3, CloudWatch Logs, or Kinesis Data Firehose. From these logs you can see: how many requests came in, how many were blocked, which IPs triggered rules, and what the attack patterns look like.

❌ Common Mistake: WAF is not free. You pay per Web ACL (Web Access Control List), per rule, and per million requests inspected. Always review costs before enabling in production.

✅ Best Practice: Start with AWS Managed Rule Groups (free baseline rules), then add custom rules as you understand your traffic patterns better.

WAF vs Shield — Important Distinction

Students often confuse WAF and Shield. Here's the key difference:

  • WAF: Protects at the application layer (Layer 7) — inspects request content, blocks bad patterns like SQL injection or bots.
  • Shield: Protects at the network/transport layer (Layers 3/4) — absorbs volumetric DDoS floods of traffic. Covered next.

🔰 AWS Shield

Imagine hackers controlling thousands of computers worldwide (a botnet) and directing all of them to flood your website with millions of fake requests per second. Your server can't tell fake from real — it gets overwhelmed and crashes. This is a DDoS attack, and AWS Shield is your protection.

What is a DDoS Attack?

A DDoS (Distributed Denial of Service) attack is when attackers use many compromised computers to flood a target with so much fake traffic that it becomes unavailable to legitimate users.

The key word is distributed — the attack comes from thousands of sources simultaneously, making it impossible to block just one IP address. Real-world impact: your 500 daily users can't reach your site because 5 million fake requests per second have crashed your servers. You lose customers, revenue, and trust.

Figure 8: DDoS Attack — Botnet Overwhelms Your Server, Blocking Real Users

What is AWS Shield?

AWS Shield is a DDoS protection service that safeguards your AWS applications against distributed denial of service attacks.

Think of it as a giant umbrella over your infrastructure. When the flood of fake traffic arrives, Shield absorbs and deflects it before it ever reaches your servers. Your real users keep getting through normally.

AWS Shield Tiers

Figure 9: AWS Shield Standard vs Advanced Comparison

Shield Standard — Free for Everyone

AWS Shield Standard is automatically enabled for all AWS customers at no cost and protects against the most common network and transport layer DDoS attacks.

  • Protects against SYN/UDP floods, reflection attacks, and other Layer 3/4 attacks.
  • Works automatically with CloudFront, Route 53, Elastic Load Balancing — no configuration needed.
  • No visibility into attack details.

Shield Advanced — Paid Tier

Shield Advanced adds enterprise-grade protection on top of Standard:

  • Always-on detection: Continuously monitors your traffic for unusual patterns.
  • Layer 7 protection: Works with WAF to block sophisticated application-layer attacks.
  • 24/7 DRT access: Direct access to AWS's DDoS Response Team for help during active attacks.
  • Cost protection: AWS reimburses scaling costs (EC2, CloudFront, etc.) incurred because of a DDoS attack.
  • Real-time visibility: Detailed attack dashboards in CloudWatch.
  • Cost: Approximately $3,000/month plus data transfer fees.

💡 WAF + Shield = Best Combo: The instructor emphasized using WAF and Shield together. Shield handles the volumetric flood at the network level. WAF handles application-layer attacks (bots, SQL injection) at the request level. Together they cover all threat layers.

📚 According to AWS documentation, Shield Advanced also provides global threat visibility and integrates with AWS Firewall Manager to centrally manage WAF rules and Shield protections across all accounts in your organization.

📚 Source:AWS Shield Documentation

🔍 AWS Inspector

A doctor doesn't wait for you to get sick before checking your health — they run regular check-ups, find warning signs early, and recommend treatment. AWS Inspector is the security doctor for your AWS environment: it regularly scans your resources for vulnerabilities before attackers find them.

What is AWS Inspector?

Amazon Inspector is an automated security assessment service that continuously scans AWS resources (like EC2 instances and container images) for software vulnerabilities and unintended network exposure.

The key word is automated — you don't have to manually check anything. Inspector runs continuously in the background and reports what it finds.

Figure 10: AWS Inspector — Scan, Find, Report, Remediate

What Does Inspector Scan?

  • EC2 instances: Scans the operating system and installed software packages for known CVEs (Common Vulnerabilities and Exposures).
  • Amazon ECR container images: Scans Docker container images for vulnerable software packages before they're deployed.
  • AWS Lambda functions: Scans function code and dependencies for vulnerabilities.

What Does Inspector Find and Report?

  • Software packages that are outdated or have known security vulnerabilities (CVEs).
  • Network reachability issues — for example, an EC2 instance with port 22 (SSH) open to the entire internet (0.0.0.0/0).
  • Misconfigurations that could expose your resources.
  • Severity ratings: Critical, High, Medium, Low, Informational — so you know what to fix first.

❌ Critical Distinction: Inspector does not block attacks. It finds and reports weaknesses. You take the action based on its findings report. Think of it as "find the problem before the hacker does."

Inspector Pricing

Inspector is not free. Pricing is based on the number of EC2 instances scanned and the number of container images scanned per month. You can try it with a 15-day free trial when you first enable it.

✅ Best Practice: Enable Inspector in all accounts in your organization using AWS Organizations. Use Security Hub to centralize all Inspector findings from all accounts into one dashboard.

⚙️ AWS Config

Imagine your office has a rule: "The front door must always be locked after 6 PM." Now imagine someone unlocks it at 7 PM and nobody notices for days. AWS Config is the security camera and audit log that catches exactly this — configuration changes that violate your defined rules.

What is AWS Config?

AWS Config is a service that records every configuration change made to your AWS resources and evaluates those changes against your defined compliance rules.

It answers questions like: "Was this S3 bucket always public, or did it change? When? Who changed it?" Config keeps a complete timeline of your resource configurations.

Figure 11: AWS Config Timeline — Detecting When Configurations Drift from Rules

Config Rules

You define rules in Config that describe your desired configuration state. Config continuously evaluates your resources against these rules and flags any violations:

  • s3-bucket-public-read-prohibited — No S3 bucket should allow public read access.
  • restricted-ssh — No security group should allow SSH (port 22) from 0.0.0.0/0 (everywhere).
  • ec2-instance-no-public-ip — EC2 instances should not have public IP addresses directly assigned.
  • required-tags — All EC2 instances must have specific tags (like "Environment" and "Owner").

When a resource deviates from a rule, Config marks it as NON_COMPLIANT and can trigger alerts via SNS, trigger an AWS Lambda function to auto-remediate, or log to Security Hub.

Config vs Inspector vs GuardDuty — Clearing Confusion

  • Config: "Did the configuration change? Is it still compliant with our rules?"
  • Inspector: "Does this EC2 instance have known software vulnerabilities?"
  • GuardDuty: "Is something suspicious happening right now in my account?" (Covered next)

💡 Example Config Rule in Action: A developer in Dev OU accidentally changes a security group to allow SSH from everywhere (0.0.0.0/0). Config detects the change within minutes, marks the security group as NON_COMPLIANT, and sends an SNS alert to the security team.

❌ Config is NOT free. You pay per configuration item recorded and per Config rule evaluation per month. Enable only the rules relevant to your compliance needs.

🕵️ Amazon GuardDuty

Your company runs normally all day. But at 3 AM, a compromised IAM key starts making API calls from an unusual IP address in another country — someone is trying to exfiltrate data. How do you catch this in real time? Amazon GuardDuty.

What is Amazon GuardDuty?

Amazon GuardDuty is a threat detection service that continuously monitors your AWS account for malicious activity and unauthorized behavior using machine learning and AWS log analysis.

Think of GuardDuty as a security guard watching all the security camera feeds at once — not just one door, but everything happening across your entire AWS account, 24/7, without fatigue.

Figure 12: GuardDuty — Analyzes Multiple Log Sources with Machine Learning

What Does GuardDuty Analyze?

GuardDuty automatically consumes and analyzes these AWS data sources (you don't need to configure log collection manually):

  • AWS CloudTrail logs: Records every API call made in your account. GuardDuty looks for suspicious API patterns — like an IAM user suddenly calling DeleteTrail or creating many IAM users.
  • VPC Flow Logs: Records network traffic in your VPC. GuardDuty detects unusual traffic patterns — like an EC2 instance communicating with a known malicious IP (cryptocurrency mining C2 server).
  • DNS logs: Looks for queries to known malicious domains — a sign that an EC2 instance may be compromised.
  • S3 data events: Detects suspicious S3 access patterns like large data downloads or unusual geographic access.

GuardDuty Findings

When GuardDuty detects suspicious activity, it generates a finding. Findings are categorized by type and severity:

  • UnauthorizedAccess:EC2/SSHBruteForce — Someone is trying many SSH passwords on your EC2 instance.
  • Recon:IAMUser/MaliciousIPCaller — An IAM user is calling APIs from a known malicious IP address.
  • CryptoCurrency:EC2/BitcoinTool — An EC2 instance appears to be mining cryptocurrency (a sign of compromise).
  • Exfiltration:S3/MaliciousIPCaller — S3 data is being accessed from a known malicious IP.

💡 Important: GuardDuty detects and alerts — it does not automatically block threats. After receiving a finding, you investigate and remediate (possibly using Lambda to auto-respond, or manually via the console).

❌ GuardDuty is NOT free. Pricing is based on the volume of CloudTrail events, VPC Flow Logs, and DNS query logs analyzed per month. There is a 30-day free trial when first enabled.

🎛️ AWS Security Hub

You now have GuardDuty alerting on suspicious behavior, Inspector reporting vulnerabilities, Config flagging misconfigurations, and Macie detecting sensitive data exposure. Each tool sends alerts — but where do you go to see everything in one place? AWS Security Hub.

What is AWS Security Hub?

AWS Security Hub is a centralized security dashboard that aggregates, organizes, and prioritizes security findings from multiple AWS security services and third-party tools in one place.

Think of it as the main control room with all the camera feeds: GuardDuty sends its alerts here, Inspector sends its vulnerability reports here, Config sends its compliance violations here, and Macie sends its sensitive data alerts here — all visible on one dashboard.

Figure 13: Security Hub — One Dashboard for All Security Findings

Key Features

  • Aggregated findings: All findings from all security services displayed with normalized severity scores.
  • Security standards: Automated checks against frameworks like CIS AWS Foundations Benchmark, AWS Foundational Security Best Practices, and PCI DSS.
  • Compliance score: A percentage score showing how compliant your environment is right now.
  • Multi-account support: Aggregate findings from all accounts in your AWS Organization into one Security Hub administrator account.
  • Automated responses: Integrate with EventBridge and Lambda to auto-remediate findings.

✅ Best Practice: Enable Security Hub in all accounts in your organization and designate one account as the Security Hub administrator. All findings from all accounts flow into this one account for centralized visibility.

🔑 IAM Access Analyzer

You carefully set up your S3 bucket policies — but six months later a developer edits a bucket policy and accidentally makes it public. Nobody notices because nobody checked. IAM Access Analyzer is the automated watcher that detects exactly these accidental exposures.

What is IAM Access Analyzer?

IAM Access Analyzer is a tool that continuously analyzes resource policies to identify any resources that are accessible from outside your AWS account or organization — such as S3 buckets, IAM roles, KMS keys, Lambda functions, and SQS queues.

It answers the question: "Have I accidentally given strangers access to something they shouldn't have?"

Figure 14: IAM Access Analyzer — Detecting Externally Accessible Resources

What It Finds

  • S3 bucket accessible to public: Bucket policy or ACL allows read/write by anyone (public internet).
  • IAM role assumable by external account: A role's trust policy allows an external AWS account to assume it.
  • KMS key accessible to external accounts: Your encryption key can be used by another account — potential data access risk.
  • Lambda function with public resource policy: Lambda can be invoked by anyone without authentication.
  • SQS queue open to external accounts: Messages in your queue can be read or sent by outside accounts.

Zone of Trust

You configure a zone of trust — either your AWS account or your entire AWS Organization. Access Analyzer flags any resource accessible from outside your zone of trust as a potential finding. Intentional external access (like a public S3 website) can be archived once reviewed.

💡 Access Analyzer is free! Unlike most security services, IAM Access Analyzer for S3 and IAM is available at no additional charge. Access Analyzer for S3 Policy Checks and custom policy generation do have costs — check the pricing page.

🔎 Amazon Macie

Your S3 buckets might contain hundreds of thousands of files — spreadsheets, logs, exports, backups. Hidden in there could be credit card numbers, social security numbers, or API keys. Could you manually check every file? Of course not. Amazon Macie does it automatically.

What is Amazon Macie?

Amazon Macie is a data security service that uses machine learning to automatically discover, classify, and protect sensitive data stored in Amazon S3.

Macie knows what sensitive data looks like — it has patterns for credit card numbers, passport numbers, social security numbers, AWS access keys, passwords, and more. It scans your S3 objects and flags anything that looks sensitive, especially if that data is publicly accessible.

Figure 15: Amazon Macie — Scanning S3 for Sensitive Data with Machine Learning

What Sensitive Data Does Macie Detect?

  • Personally Identifiable Information (PII): Names, addresses, dates of birth, social security numbers, passport numbers, driver's license numbers.
  • Financial data: Credit card numbers, bank account numbers, financial records.
  • Credentials: AWS access keys, private keys, API tokens, passwords embedded in files.
  • Healthcare data: Medical record numbers, health insurance IDs (HIPAA-sensitive data).

Macie Findings

Macie produces two types of findings:

  • Policy findings: A bucket's settings changed to allow public access or sharing — the configuration has become risky.
  • Sensitive data findings: Macie found specific sensitive data (credit cards, SSNs, etc.) in a specific S3 object — and if that object is in a publicly accessible bucket, it's a critical finding.

✅ Use Case: Macie is especially valuable for compliance with regulations like GDPR, HIPAA, and PCI-DSS, which require you to know exactly where sensitive data lives and ensure it's properly protected.

❌ Macie is NOT free. Pricing is based on the number of S3 buckets evaluated per month (for bucket inventory) and the amount of data scanned in bytes (for sensitive data discovery).

🔬 Amazon Detective

GuardDuty just fired an alert: "Suspicious API calls from an unusual IP." Now what? You need to investigate — when did this start? What exactly did the attacker do? Which resources were touched? How did they get in? Amazon Detective is your forensic investigation officer.

What is Amazon Detective?

Amazon Detective is a security investigation service that automatically collects log data and uses machine learning to help you quickly analyze, investigate, and identify the root cause of security incidents.

Think of it as the detective who arrives after a crime. GuardDuty is the alarm that went off; Detective is the expert who pieces together exactly what happened, how, and who did it.

Figure 16: Amazon Detective — Forensic Investigation After a Security Incident

What Does Detective Analyze?

Detective automatically ingests and analyzes data from:

  • AWS CloudTrail: Shows every API call — who called what, when, from where.
  • VPC Flow Logs: Shows network traffic patterns — what connected to what, how much data was transferred.
  • Amazon GuardDuty findings: The alerts that triggered the investigation in the first place.
  • EKS audit logs: If you use Kubernetes, Detective can analyze Kubernetes API activity.

Detective vs GuardDuty — Key Distinction

  • GuardDuty: Detects threats in real time and fires alerts. "Something bad is happening."
  • Detective: Investigates after an alert to explain what happened. "Here's exactly what the attacker did."

💡 Analogy: GuardDuty is the smoke alarm. Detective is the fire investigator who comes afterward to determine the cause, timeline, and damage. Both are essential — one for detection, one for understanding.

❌ Detective is NOT free. Pricing is based on the volume of data ingested (CloudTrail events, VPC flow log bytes, GuardDuty findings) per month. 30-day free trial on first enable.

🌐 Route 53 + CloudFront + ACM Practical (From Class)

In the second half of the session, the class worked through a practical: hosting a static website on S3, distributing it via CloudFront, and connecting a custom domain using Route 53. Here's a clean walkthrough:

💡 This topic (Route 53, CloudFront, ACM, S3 static website) was covered in previous sessions. This section summarizes what was demonstrated in class for revision. Refer to the Route 53 and CloudFront session notes for full details.

Static Website: S3 + CloudFront + Route 53 Architecture

Figure 18: Static Website Architecture — S3 + CloudFront + Route 53 + ACM

Steps Demonstrated in Class

  1. Create an S3 bucket (keep it private — block all public access). Upload your website files (HTML, CSS, images).
  2. Create a CloudFront distribution pointing to the S3 bucket as origin. Use Origin Access Control (OAC) — CloudFront automatically updates the bucket policy to allow CloudFront access without making the bucket public.
  3. Set Default Root Object to index.html in CloudFront distribution settings (General → Edit).
  4. Access via CloudFront domain — copy the distribution domain name (e.g., d1abc123.cloudfront.net) and open it in a browser. Your website loads.
  5. Create Route 53 Hosted Zone with your domain name (e.g., www.yourdomain.com). This creates a container for DNS records.
  6. Create an Alias Record in Route 53 pointing to the CloudFront distribution. Switch to Alias → select CloudFront as the endpoint type → select your distribution.
  7. Update Name Servers at your domain registrar (GoDaddy, etc.) with the name servers from your Route 53 hosted zone. This delegates DNS control to Route 53.

❌ Key Mistake from Class: A student tried to use their S3 bucket endpoint directly in Route 53, but it didn't work because the bucket name must exactly match the domain name for direct S3 + Route 53 integration. The correct approach is to use CloudFront as the intermediary (bucket name does not need to match domain name when using CloudFront).

💡 SSL/HTTPS: To enable HTTPS on your CloudFront distribution, attach an SSL certificate from AWS Certificate Manager (ACM). ACM SSL certificates for CloudFront must be created in us-east-1 (N. Virginia) region — this is an important exam fact.

💼 AWS Trusted Advisor — Quick Review

Students raised questions about Trusted Advisor status indicators, so here's a clear clarification:

Trusted Advisor Status Colors

  • 🟢 Green (OK): No issues found — your configuration is fine.
  • 🟡 Yellow — Action Recommended: Potential issues detected. AWS recommends you review and take action, but it's not critical.
  • 🔴 Red — Action Recommended (Critical): This was the class discussion point. Even for red status, Trusted Advisor says "action recommended" — NOT "action required." This is because AWS never enforces actions — it only recommends. You always retain control over your resources. The instructor confirmed: "Red = Action Recommended" (not "Action Required") — Trusted Advisor is advisory only, never mandatory.

💡 Exam Trap: If a question asks what "red status in Trusted Advisor" means, the answer is "Action Recommended" — not "Action Required." AWS advises, never mandates.

📝 Overall Summary
  • AWS Organizations: Centrally manage multiple AWS accounts using OUs (logical account groups), SCPs (JSON policies that restrict what accounts can do, including root user), and Consolidated Billing (single invoice + volume discounts).
  • SCPs vs IAM Policies: IAM policies control individual users/roles within an account. SCPs control what the entire account (including root) can do — they sit above IAM policies in the permission hierarchy.
  • AWS WAF: Application-layer (L7) firewall that filters HTTP/HTTPS requests using IP-based, geo-based, rate-based, and managed rules. Attach to CloudFront, ALB, API Gateway, or AppSync.
  • AWS Shield: DDoS protection. Standard is free and automatic for all customers (L3/L4 protection). Advanced ($3K/month) adds L7 protection, DRT access, and cost reimbursement for DDoS scaling costs.
  • WAF + Shield combo: Best practice — Shield handles volumetric floods, WAF handles application-layer attacks. Use together for full protection.
  • AWS Inspector: Automated vulnerability scanner for EC2, ECR, and Lambda. Finds CVEs, outdated packages, network exposure issues. Does NOT block — only reports findings for you to act on.
  • AWS Config: Records every configuration change to AWS resources. Evaluates against compliance rules. Flags NON_COMPLIANT resources when configurations drift (e.g., S3 bucket goes public).
  • Amazon GuardDuty: Threat detection using machine learning on CloudTrail, VPC Flow Logs, and DNS logs. Detects suspicious activity like compromised credentials, unusual API calls, crypto mining. Alerts only — does not block.
  • AWS Security Hub: Centralized security dashboard. Aggregates findings from GuardDuty, Inspector, Config, Macie, Access Analyzer, and third-party tools. Shows compliance scores against frameworks like CIS and PCI-DSS.
  • IAM Access Analyzer: Detects resources (S3, IAM roles, KMS, Lambda, SQS) accidentally exposed to external accounts or public internet. Defines zone of trust (account or organization). Mostly free.
  • Amazon Macie: Uses machine learning to discover and classify sensitive data (PII, financial, credentials) in S3 buckets. Alerts when sensitive data is in publicly accessible buckets.
  • Amazon Detective: Forensic investigation tool. Used AFTER an incident to analyze what happened, using CloudTrail + VPC Flow Logs + GuardDuty findings. Produces timeline and root cause analysis.

Project 1: Set Up AWS Organizations with SCPs (Level 1)

🎯 Objective: Create an AWS Organization, add a member account, create an OU, move the account into the OU, and test an SCP that denies EC2 access.

⏱️ Time: 30-45 min

💰 Cost: Free (AWS Organizations is free)

  1. Sign in to your main AWS account. In the console, search for AWS Organizations and open the service.

    📸 Screenshot: AWS Organizations dashboard with management account details

  2. Click Add an AWS account. Select Create an AWS account. Enter an account name (e.g., "Dev Team") and a unique email address not used for any other AWS account. Click Create AWS account. Wait a few minutes for the account to be provisioned.

    📸 Screenshot: Create member account form with name and email filled in

  3. Once created, click AWS accounts in the left nav. Click Actions → Create new → Organizational unit. Name it Dev-OU and confirm.

    📸 Screenshot: Create Organizational Unit dialog with Dev-OU name

  4. Select the Dev Team account → Actions → Move → choose Dev-OU → confirm.

  5. Navigate to Policies → Service control policies → enable if needed → click Create policy. Name it DenyEC2Access. Write a JSON policy with Effect: Deny, Action: ec2:*, Resource: *. Save.

    📸 Screenshot: SCP policy editor showing DenyEC2Access policy JSON

  6. Click on Dev-OU → Policies tab → Attach → select DenyEC2Access.

  7. Sign in to the Dev Team member account (reset password via Forgot Password). Navigate to EC2 → Instances. You should see an API error confirming the SCP is working.

    📸 Screenshot: EC2 access denied in member account due to SCP

  8. Cleanup: Detach the SCP from Dev-OU. Go to the member account → Actions → Close account. Then delete Dev-OU. This avoids any lingering configurations.

🚧 Challenge Mode: After the basic setup, try attaching a SECOND SCP that denies S3 DeleteBucket actions at the root OU level (applies to ALL accounts). Then verify from the member account that you cannot delete an S3 bucket. Can you think of why you'd want this rule in production?

🔥 Real Scenario: A financial company has 40 AWS accounts. One junior developer accidentally deleted a production S3 bucket that stored transaction logs. After this incident, the security team asked: "How could we prevent root users in ANY account from deleting critical buckets?" — SCPs at the root OU level are the answer. IAM policies alone cannot restrict the root user.

🎤 Interview Thinking: If asked "Why use SCPs instead of IAM policies for account-level governance?" — say: IAM policies cannot restrict root users. SCPs can. Also, IAM policies require changes in every account individually. SCPs apply once at the OU level and cascade to all accounts automatically. This is the only scalable approach for large organizations.

Project 2: Host Static Website on S3 + CloudFront (Level 1)

🎯 Objective: Upload a static HTML website to a private S3 bucket, create a CloudFront distribution, and access the site via the CloudFront domain.

⏱️ Time: 20-30 min

💰 Cost: Free Tier eligible (CloudFront: 1TB data transfer/month free; S3: 5GB storage free)

  1. Create an S3 bucket (keep Block all public access ON). Upload your HTML, CSS, and image files.

    📸 Screenshot: S3 bucket with Block All Public Access enabled (private)

  2. Go to CloudFront → Create distribution. Select your S3 bucket as origin. Under Origin Access, choose Origin access control settings (recommended). Create a new OAC. Copy and apply the generated bucket policy to your S3 bucket's Permissions → Bucket policy.

  3. Skip WAF (to avoid cost). Click Create distribution. While deploying, go to the distribution's General tab → Edit → Default root object → enter index.html → Save.

    📸 Screenshot: CloudFront distribution settings with index.html as default root object

  4. Once status shows Enabled, copy the distribution domain name and open it in a new browser tab. Your website should load.

    📸 Screenshot: Static website loading via CloudFront domain

  5. Cleanup: Disable and delete the CloudFront distribution. Empty and delete the S3 bucket.

🚧 Challenge Mode: After the site is live, try accessing the S3 bucket URL directly (not the CloudFront URL). You should get "Access Denied." Then try disabling the CloudFront distribution while the site is being accessed — observe what happens to the user experience. This illustrates why CloudFront's edge caching matters for availability.

🔥 Real Scenario: A startup's marketing team needed their landing page hosted with global performance and zero server management. S3 + CloudFront delivers this: content is cached at 400+ AWS edge locations, the bucket stays private (never directly accessible), and the setup costs near zero. This is the real-world pattern behind many static marketing sites.

🎤 Interview Thinking: If asked "Why not just enable S3 static website hosting and make the bucket public?" — say: Public S3 buckets expose your origin directly. Anyone can see your bucket name and hit it with traffic, bypassing caching. CloudFront gives you: SSL termination, caching (faster load), origin protection (bucket stays private), and WAF attachment. It's production-grade vs. a quick demo.

Project 3: WAF + GuardDuty Security Monitoring Pipeline (Level 2)

🎯 Objective: Connect WAF to an existing CloudFront distribution, enable GuardDuty, generate sample findings, and see how threats surface. This is your first "connected services" project — two services working together.

⏱️ Time: 45-60 min

💰 Cost: GuardDuty: 30-day free trial; WAF: ~$5-10 for this exercise — disable after

Part A — WAF Setup

  1. Search for WAF & Shield in the console. Click Create web ACL. Name it my-security-waf. Resource type: Amazon CloudFront distributions (must select this to attach to CloudFront). Region will auto-set to Global (CloudFront).

    📸 Screenshot: WAF Create web ACL — name and resource type configuration

  2. On the Add rules step, click Add rules → Add managed rule groups. Expand AWS managed rule groups. Enable Amazon IP reputation list (blocks known malicious IPs — free). Click Add to web ACL.

    📸 Screenshot: WAF managed rule groups — enabling Amazon IP reputation list

  3. Still on Add rules, click Add rules → Add my own rules → Rate-based rule. Name it rate-limit-1000. Set rate limit to 1000 requests, evaluation window 5 minutes. Action: Block. Save.

    📸 Screenshot: WAF rate-based rule — 1000 req/5min block configuration

  4. Set Default action to Allow (allow all traffic that doesn't match a block rule). Complete the wizard and create the Web ACL. Now go to your CloudFront distribution → Security tab → associate this Web ACL.

    📸 Screenshot: WAF successfully attached to CloudFront distribution

Part B — GuardDuty Sample Findings

  1. Search for GuardDuty in the console. Click Get started → Enable GuardDuty. GuardDuty starts monitoring immediately (30-day free trial).

    📸 Screenshot: GuardDuty enabled and active with monitoring status

  2. Click Settings → Generate sample findings. GuardDuty will create one sample finding for every finding type it knows about (~80 findings). Go back to Findings. Browse the list — notice severity levels (Critical, High, Medium, Low) and finding types.

    📸 Screenshot: GuardDuty sample findings list showing severity levels and finding types

  3. Click on a Critical finding to open its detail panel. Read the Action, Actor, Resource, and Additional information sections. Notice how GuardDuty tells you exactly: what happened, what resource was affected, and from which IP.

    📸 Screenshot: GuardDuty finding detail — action, resource, actor, and severity breakdown

  4. Cleanup: In GuardDuty, go to Settings → Suspend GuardDuty (or Disable if you don't want to resume). Delete the sample findings. Detach the WAF from CloudFront if no longer needed. Delete the Web ACL (note: WAF charges per ACL per month).

🚧 Challenge Mode: After seeing GuardDuty findings, go to Settings → Suppression rules. Create a rule that suppresses LOW severity findings of type Recon:EC2/PortProbeUnprotectedPort — these are often noisy and expected. Real security teams spend significant time tuning suppression rules to reduce alert fatigue. How would you decide which findings to suppress vs. investigate?

🔥 Real Scenario: A company's GuardDuty fired a finding at 3 AM: UnauthorizedAccess:IAMUser/InstanceCredentialExfiltration.OutsideAWS. This meant an IAM key from an EC2 instance was being used from an IP outside AWS — a classic sign of credential theft via the instance metadata endpoint. The security team used GuardDuty's finding details to immediately identify the affected instance, rotated credentials, and patched the application within 90 minutes. Without GuardDuty, this could have gone undetected for days.

🎤 Interview Thinking: If asked "WAF or Shield — which one first?" — say: They solve different problems, not competing ones. But if budget is limited, WAF first if you have a web application (most attacks are L7). Shield Standard is free and automatic anyway. Add Shield Advanced only if you're a high-value DDoS target (banks, gaming, media) or if a DDoS would cause significant business loss through AWS scaling costs.

Project 4: Data Leak Detection — Macie + Access Analyzer (Level 3)

🎯 Objective: Simulate a data leak scenario — create an S3 bucket with fake sensitive data, make it public, and watch two services (Macie and Access Analyzer) detect the exposure from different angles. This teaches you how real data security monitoring works.

⏱️ Time: 45-60 min

💰 Cost: Macie: 30-day free trial for new accounts; Access Analyzer: free

  1. Create an S3 bucket named test-sensitive-data-[yourname]. Keep it private for now. Create a simple text file called customer-data.txt on your computer with this content (fake PII — safe for testing):

    Name,Email,CreditCard,SSN
John Smith,john@example.com,4111111111111111,123-45-6789
Jane Doe,jane@example.com,5500005555555559,987-65-4321
Bob Lee,bob@example.com,340000000000009,456-78-9012

    Upload this file to your S3 bucket.

    📸 Screenshot: Fake sensitive data file uploaded to private S3 bucket

  2. Enable Amazon Macie: Search for Macie → Get started → Enable Macie. Once enabled, click S3 buckets in the left nav. Find your bucket — check its classification status (may show "Not classified" until a scan job runs).

    📸 Screenshot: Amazon Macie S3 buckets inventory view

  3. Create a Macie scan job: Click Jobs → Create job. Select your bucket. Job type: One-time job. Leave other settings as default. Submit the job. Wait 5-10 minutes for it to complete.

    📸 Screenshot: Macie scan job running on the test bucket

  4. While Macie scans, enable IAM Access Analyzer: Search for IAM → click Access Analyzer in the left panel → Create analyzer. Zone of trust: Current account. Name: account-analyzer. Create it. Findings list will be empty initially.

  5. Now simulate the leak: Go to your S3 bucket → Permissions tab → Block public access → Edit → uncheck all four checkboxes → Save. Confirm the warning. Then go to Bucket policy and add a policy that allows s3:GetObject for Principal * (everyone).

    📸 Screenshot: S3 bucket made public — Block Public Access Off and bucket policy allowing all

  6. Wait 2-5 minutes. Check IAM Access Analyzer → Findings. You should see a new finding for your S3 bucket showing it is publicly accessible. Click it to see the full details — resource ARN, access level, and the policy clause that caused the exposure.

    📸 Screenshot: Access Analyzer finding — S3 bucket detected as publicly accessible

  7. Check Macie → Findings after the scan completes. Macie should report a sensitive data finding showing credit card numbers and SSN patterns detected in customer-data.txt. Combined with the bucket now being public — Macie will flag this as a critical data exposure.

    📸 Screenshot: Macie finding — credit card and SSN patterns detected in S3 object

  8. Cleanup: Re-enable Block public access on the bucket. Delete the bucket policy. Delete the customer-data.txt file. Archive the Access Analyzer finding. In Macie, disable the service if no longer needed (Settings → Disable Macie). Delete the analyzer in Access Analyzer.

🚧 Challenge Mode: After seeing both findings, try answering: (1) Which service detected the exposure FASTER — Macie or Access Analyzer? (2) If the bucket were still private but contained the credit card data, which service would still alert and which would not? (3) Can you think of a situation where Macie alerts but Access Analyzer does NOT?

🔥 Real Scenario: A healthcare startup stored patient intake forms (containing names, DOBs, and insurance IDs) in an S3 bucket. A developer temporarily made the bucket public during a debugging session and forgot to revert it. Three weeks later, a GDPR audit flagged the exposure. Macie would have detected the PII in the files and Access Analyzer would have detected the public bucket policy — together, the security team would have been alerted within minutes instead of weeks. HIPAA violations carry fines up to $1.9 million per violation category.

🎤 Interview Thinking: "When would you NOT use Macie?" — Macie is S3-specific and scans data at rest. It is NOT suitable for: real-time data in transit, database content in RDS/DynamoDB, or files stored outside S3. It also has costs based on data volume — for very large data lakes (petabytes), scanning everything continuously is expensive. In practice, you'd scope Macie to specific high-risk buckets rather than all buckets in the account.

Project 5: AWS Config Compliance + Auto-Remediation (Level 3)

🎯 Objective: Enable AWS Config, add compliance rules for common security misconfigurations, intentionally break the rules, and watch Config detect and auto-remediate the violations. This is the "system that fixes itself" pattern used in production environments.

⏱️ Time: 60-90 min

💰 Cost: Config: ~$0.003 per configuration item recorded + $1 per active rule per month — keep it short

  1. Search for AWS Config → Get started. On setup: select Record all resources supported in this region. Create a new S3 bucket for Config to store its history (name it config-history-[yourname]). Enable SNS notifications (optional — creates an email alert for each violation). Complete setup and click Confirm.

    📸 Screenshot: AWS Config initial setup — resource recording and delivery configuration

  2. Click Rules → Add rule. Search for s3-bucket-public-read-prohibited. Select it. Leave all defaults. Click Save. This rule flags any S3 bucket that allows public read access.

    📸 Screenshot: Adding the s3-bucket-public-read-prohibited Config rule

  3. Add a second rule: search for restricted-ssh. Select it. Save. This rule flags any security group allowing SSH (port 22) from anywhere (0.0.0.0/0).

  4. Wait 2-5 minutes for Config to evaluate your current resources. Click Rules → check compliance status. Resources that already comply show green; violations show red. Click on a rule to see which specific resources are NON_COMPLIANT.

    📸 Screenshot: Config rules compliance dashboard showing compliant vs NON_COMPLIANT resources

  5. Now break a rule intentionally: Go to a Security Group in EC2 → Inbound rules → Edit → Add rule: Type SSH, Source 0.0.0.0/0 (anywhere) → Save. Wait 2-5 minutes, then check Config → the security group should now appear as NON_COMPLIANT under the restricted-ssh rule.

    📸 Screenshot: Security group flagged NON_COMPLIANT by Config after SSH rule added

  6. Click on the NON_COMPLIANT resource → view the Configuration timeline. You can see the exact moment the configuration changed from COMPLIANT to NON_COMPLIANT — with a timestamp. This is your audit trail.

    📸 Screenshot: Config configuration timeline showing compliance state change with timestamp

  7. Now set up auto-remediation: On the restricted-ssh rule page, click Actions → Manage remediation. Select Automatic remediation. Choose SSM Automation document: AWS-DisablePublicAccessForSecurityGroup. Map the GroupId parameter to RESOURCE_ID. Save. Now if Config finds the rule violated, it will automatically trigger the SSM document to remove the bad SSH rule — no human needed.

    📸 Screenshot: Config auto-remediation setup using SSM Automation document

  8. Cleanup: Delete the Config rules. Go to Settings → Turn off recording to stop Config from recording (this stops charges). Delete the config-history S3 bucket. Remove the SSH-from-anywhere inbound rule from the security group you modified.

🚧 Challenge Mode: After auto-remediation is set up, break the rule again (re-add SSH from 0.0.0.0/0). Watch Config detect it, then watch the SSM Automation trigger and remove it automatically. Check CloudTrail → Event history and search for the SSM automation event — you'll see the exact API call that removed the bad rule. Can you trace the full chain: Config detection → Remediation trigger → SSM action → CloudTrail record?

🔥 Real Scenario: A retail company ran an e-commerce platform on AWS with 200+ EC2 instances across 5 accounts. Their Config rules included restricted-ssh with auto-remediation. One night, a developer in the staging account added an SSH-from-anywhere rule for a quick debugging session and forgot to remove it before the weekend. Config detected it within 3 minutes and auto-remediated. The developer returned Monday to find a Config NON_COMPLIANT email — and the security team confirmed the rule had been automatically removed. Zero manual intervention, zero weekend on-call escalation.

🎤 Interview Thinking: "Config + auto-remediation sounds perfect — why not auto-remediate everything?" — In production, blind auto-remediation can cause outages. Example: auto-removing a security group rule might break a running application that depends on that network path. Best practice: in Dev/Staging, use full auto-remediation. In Production, use SNS alerts for human review and approval. For truly critical policies (like "no public S3"), auto-remediation makes sense everywhere. For nuanced network rules, human judgment is safer.
