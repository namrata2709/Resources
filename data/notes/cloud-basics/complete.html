🔄 Software Development Life Cycle (SDLC)

When your friend approached an IT company to build his app, the first thing they told him was: "We don't write code randomly. We follow a structured process called the Software Development Life Cycle."

Figure 2: The six phases of SDLC — a continuous cycle, not a one-time process

📋 The 6 Phases of SDLC

Each phase has a specific purpose. Skipping a phase is like building a house without laying the foundation first:

PhaseWhat HappensReal Example
1. Requirement AnalysisUnderstand what the client/business needsWhat features does the import-export app need? Product catalog? Order tracking? Payments?
2. DesignPlan the architecture, database, and UIHow many screens? Which database? How will data flow between screens?
3. DevelopmentEngineers write the actual codeDevelopers build the frontend, backend, and APIs
4. TestingCheck for bugs, performance issues, security holesQA team verifies every feature works under load and without crashes
5. DeploymentMake the application live and accessibleDevOps team pushes the app to cloud servers so users can access it globally
6. MaintenanceRelease updates, fix bugs, handle new requestsAdd new features, patch security issues, improve performance over time

⚙️ SDLC Models: Waterfall vs Agile

Once you understand the phases, the next question is: in what order and style do you execute them? That's where models come in.

Figure 3: Waterfall (linear, rigid) vs Agile (iterative, flexible)

Waterfall Model: A sequential, phase-by-phase approach where you complete one phase fully before moving to the next. Once a phase is done, going back is difficult and expensive.

  • ✅ Good for: Projects with well-defined, stable requirements (e.g., government systems, construction software)
  • ❌ Bad for: Projects where requirements change frequently

Agile Methodology: An iterative, sprint-based approach where the app is developed in small cycles (sprints), with feedback and improvements at each stage.

  • ✅ Good for: Dynamic projects, startups, modern apps — requirements evolve with user feedback
  • ✅ Faster delivery — working software ships early and often
  • ❌ Requires: Close collaboration, flexible teams, and clear communication

✅ Today's standard: Most modern companies, including all major cloud providers, use Agile. When you work on AWS projects, expect sprints, standups, and iterative delivery.

💻 Computers, Programs, Software & Applications

Before you can understand cloud computing, you need to understand what's actually running inside those cloud data centers. Let's break this down from first principles.

🖥️ What Is a Computer?

A computer is a machine that can receive instructions, process them, and produce results. Every server in AWS is, at its core, just a very powerful computer.

Figure 4: Core components of a computer — the same components exist in cloud servers

ComponentRoleCloud Equivalent
CPUExecutes instructions — the brainEC2 vCPUs in AWS
RAM (Memory)Temporary workspace while programs runInstance memory (e.g., 8 GB, 16 GB on EC2)
StoragePermanent storage for files and programsEBS volumes, S3 buckets
Network InterfaceConnects to other computersVPC, ENI, Internet Gateway in AWS
Input/OutputReceive commands, show resultsAPIs (input) and HTTP responses (output)

📦 Program vs Software vs Application

These three terms are often used interchangeably, but they have precise meanings:

Figure 5: Program → Software → Application — each builds on the previous

A program is a set of instructions written in a programming language that a computer can execute. For example:

print("Hello, World!")

This one-line Python program tells the CPU to display text. Simple. But programs grow — and when many programs are packaged together to solve a larger problem, we call it software.

Software is one or more programs packaged together to solve a specific problem. Software runs on a computer — it is not the end user. Example: Microsoft Office = Word + Excel + PowerPoint + tools.

An application (app) is software designed specifically for an end user to perform a task. Examples: WhatsApp, Gmail, Amazon Shopping app.

🚗 Car Analogy:

TermCar Analogy
SoftwareThe engine and internal parts (makes it run)
ApplicationThe complete car, ready to drive
End UserThe driver — the person actually using it

The engine doesn't drive itself. It needs a driver (end user). Similarly, software needs an application layer for users to interact with.

⚡ How Programs Run on a Computer

This five-step process happens billions of times per second inside cloud servers:

  1. Developer writes the program in a language (Python, Java, Node.js)
  2. Program is saved to storage (SSD, HDD, or cloud storage)
  3. Program is loaded into RAM when it needs to execute
  4. CPU reads instructions from RAM and performs the actual computation
  5. Output is sent — to a screen, a network response, a database, or a file

✅ Why this matters for cloud: When you launch an EC2 instance on AWS and run your app on it, this exact process happens — your code runs in RAM, the CPU processes requests, and responses go back to clients over the network.

🔗 The Client-Server Model

Your friend's app needs to serve customers globally. Those customers (clients) send requests, and the app (server) responds. This is the foundation of every web application, API, and cloud service ever built.

Figure 6: The client-server request-response cycle — the backbone of every app

👤 What Is a Client?

A client is a device or software that requests resources or services from a server.

There are two dimensions to a client:

  • Client as a machine: Your laptop, phone, or tablet — the physical hardware making the request. Example: Your iPhone opening instagram.com.
  • Client as software: The browser (Chrome, Safari) or app (WhatsApp, Swiggy) running on that device that actually sends the request. The device is the machine; the app is the software client.

🖥️ What Is a Server?

A server is a powerful computer or program that provides resources, data, or services to clients.

  • Server as a machine: A powerful computer in a data center (or cloud) that "serves" requests. Example: An EC2 instance running in AWS's data center in Mumbai.
  • Server as software: The programs running on that server machine that do the actual work.

🗂️ Types of Servers

Server TypeWhat It DoesExamples
Web ServerSends HTML/CSS/JS pages to browsersApache, Nginx
Application ServerHandles business logic and app processingNode.js, Tomcat, Django
Database ServerStores and retrieves structured dataMySQL, PostgreSQL, MongoDB
File ServerStores and shares files (PDFs, images, videos)Samba, FTP, AWS S3

🔄 The Request-Response Cycle

Every time a user clicks something in your friend's app, this happens:

  1. Client (browser/app) sends a request with: destination IP address + port number + protocol (HTTP/HTTPS)
  2. Request travels over the internet to the server
  3. Server receives the request, processes it (looks up database, runs logic)
  4. Server sends a response back to the client
  5. Client renders the response (shows the page, displays data)

⚡ Example: User clicks "View Products" → browser sends GET request to https://yourapp.com/products → app server queries the database server → database returns product list → app server formats it → sends HTML/JSON back → browser displays the products.

🌐 Networking Basics for Applications

When your friend's app gets requests from clients all over the world, how do those requests know where to go? Networking. Three concepts are essential: IP addresses, ports, and protocols.

Figure 7: IP address, port, and protocol — the three pillars of network communication

📍 IP Address

An IP address is a unique numerical identifier assigned to every device on a network, used to locate and communicate with that device.

Think of it like a home address. Just like a courier needs your street address to deliver a package, data packets need an IP address to reach the right server.

  • IPv4: 4 numbers separated by dots — e.g., 192.168.1.1 (most common today)
  • IPv6: Newer format for more addresses — e.g., 2001:0db8:85a3::8a2e:0370:7334

🚪 Port Numbers

A port is a numbered "door" on a server that identifies which specific service or application should receive incoming network traffic.

Think of it like an apartment building: the IP address is the building address, the port is the apartment number. Multiple services can run on the same server using different ports:

PortProtocol / ServiceUse Case
80HTTPUnencrypted web traffic
443HTTPSEncrypted web traffic (SSL/TLS)
22SSHSecure remote login to servers
3306MySQLDatabase connections
5432PostgreSQLDatabase connections

📜 Protocols

A protocol is a set of rules governing how data is formatted and transmitted between devices on a network. Without agreed protocols, different computers couldn't communicate — it would be like two people speaking completely different languages.

  • HTTP (HyperText Transfer Protocol): Standard web communication — unencrypted
  • HTTPS: Encrypted version of HTTP using SSL/TLS — always use this for production apps
  • FTP: File Transfer Protocol — transferring files between machines
  • SSH: Secure Shell — encrypted remote terminal access to servers

✅ AWS Security note: When you configure Security Groups on AWS EC2 instances later in this course, you will explicitly specify which ports and protocols are allowed. Port 22 (SSH) and port 443 (HTTPS) will be the most common ones you configure.

💰 CapEx vs OpEx: The IT Cost Problem

When your friend decided to build his app on traditional IT infrastructure, the IT company explained the real cost problem — and it's what makes cloud computing so compelling.

Figure 9: CapEx (big upfront cost) vs OpEx (pay-as-you-go) — the fundamental financial argument for cloud

🏗️ Capital Expenditure (CapEx)

CapEx refers to upfront, one-time investments in physical assets that a company owns and uses long-term.

For traditional IT, CapEx includes:

  • Buying physical servers (can cost $5,000–$50,000+ each)
  • Purchasing storage devices (SANs, HDDs, SSDs)
  • Networking equipment (routers, switches, load balancers)
  • Security appliances (firewalls, intrusion detection systems)
  • Building or renting a data center space
  • Power and cooling infrastructure
  • Software licenses

❌ The CapEx problem: You pay for everything upfront. If your app never takes off, you've wasted millions. If it grows faster than expected, you need weeks to buy and install new hardware — by which time you've lost users.

💳 Operational Expenditure (OpEx)

OpEx refers to ongoing, recurring costs to run day-to-day operations — you pay as you consume.

Traditional IT OpEx includes: electricity bills, cooling systems, maintenance contracts, IT staff salaries, and software subscriptions.

Cloud computing converts CapEx to OpEx: Instead of buying a server for $20,000, you pay $0.10/hour only when you use a cloud server. Use it for 1 hour → pay $0.10. Stop it → pay nothing.

⚠️ The Utilization Problem

Even if a company can afford the CapEx, traditional infrastructure creates an efficiency nightmare:

Figure 10: The utilization problem — traditional servers are either idle or overwhelmed

  • Underutilization: Most servers run at 10–20% capacity on average. You're paying for 100% of the hardware, but using only a fraction.
  • Traffic spikes: When a product launch or sale causes sudden traffic, traditional servers can't scale fast enough. The site crashes. Sales lost.
  • Scaling takes weeks: Ordering, shipping, installing, and configuring new servers takes weeks. By then, the opportunity is gone.

☁️ What Is Cloud Computing?

After seeing all those IT challenges, the company had one suggestion for your friend: "Why not use a Cloud Computing Service Provider?"

Figure 11: Cloud computing — infrastructure over the internet, on-demand, pay-as-you-go

📖 Definition

Cloud computing is the delivery of IT resources — servers, storage, databases, networking, software, and analytics — over the internet on a pay-as-you-go basis.

Instead of owning the infrastructure (CapEx), you rent it from a cloud provider (OpEx). You use it when you need it, scale it to any size, and stop paying when you don't need it anymore.

✅ Key Benefits of Cloud Computing

BenefitWhat It MeansTraditional vs Cloud

🏢 Cloud Computing Service Providers (CCSPs)

A Cloud Computing Service Provider (CCSP) is a company that delivers computing resources — servers, storage, databases, networking, and software — over the internet on a pay-as-you-go or subscription basis.

🎯 The Key Insight

Your friend's final realization says it all:

⚡ "I should focus on my business goals. Let the cloud provider handle the IT infrastructure."

This is the entire value proposition of cloud computing: businesses build products, cloud providers manage the plumbing.

📝 Overall Summary

  • SDLC: Every software project follows six phases — Requirement Analysis, Design, Development, Testing, Deployment, and Maintenance. Skipping phases causes expensive failures.
  • Waterfall vs Agile: Waterfall is sequential and rigid; Agile is iterative and flexible. Modern teams use Agile for faster delivery and adaptability.
  • Computers: Every server is fundamentally a CPU + RAM + Storage + Network. Cloud servers are the same hardware — just rented, not owned.
  • Program → Software → Application: A program is instructions; software is programs packaged together; an application is software designed for an end user.
  • Client-Server: Clients request resources; servers provide them. The request-response cycle is the foundation of every web app and API.
  • Networking: IP addresses identify devices; ports identify services; protocols define communication rules. HTTP=80, HTTPS=443, SSH=22 are the most important.
  • CapEx vs OpEx: Traditional IT requires heavy upfront CapEx (buying hardware). Cloud converts this to OpEx — pay only for what you use, when you use it.
  • The Utilization Problem: Traditional servers are either idle (wasting money) or overwhelmed (crashing). Cloud solves this with on-demand scaling.
  • Cloud Computing: Delivery of IT resources over the internet on a pay-as-you-go basis — scalable, globally available, cost-efficient, and managed by the provider.
  • Major CCSPs: AWS (market leader), Azure (enterprise), GCP (AI/data). This course focuses on AWS — the most widely used and certified platform.

Project 2: Run a Local Web Server (Feel the Client-Server Model)

🎯 Objective: Build and run a real web server on your own laptop. Send requests from your browser (client) and see responses come back from your server — exactly like the client-server model from the notes.

⏱️ Time: 20–30 min

💰 Cost: Free — runs entirely on your laptop, no AWS needed

Before you can appreciate what EC2 does, you need to feel what a server actually is. In this project, your laptop becomes the server. Your browser becomes the client. You'll see the request-response cycle happen live.

⚡ Concept check: Right now, every time you open a website, a server somewhere is running a program like the one you're about to create. AWS EC2 is just that server — but in the cloud instead of on your desk.

Option A — Python (Recommended, usually pre-installed)

  1. Open your Terminal (Mac/Linux) or Command Prompt (Windows). Check if Python is installed:

    python3 --version

    You should see something like Python 3.11.0. If not, download it from python.org.

    📸 Screenshot: Python version confirmed in terminal — you're ready to build a server

  2. Create a new file on your Desktop called server.py. Open it in any text editor (Notepad, VS Code, TextEdit) and paste this code:

    from http.server import HTTPServer, BaseHTTPRequestHandler

class MyServer(BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200)
        self.send_header("Content-type", "text/html")
        self.end_headers()

        if self.path == "/":
            message = "<h1>Welcome! Server is running.</h1><p>You are the CLIENT. This Python script is the SERVER.</p>"
        elif self.path == "/products":
            message = "<h1>Products</h1><ul><li>Product A - ₹500</li><li>Product B - ₹1200</li></ul>"
        elif self.path == "/users":
            message = "<h1>Users</h1><p>User: Rahul, City: Mumbai</p>"
        else:
            self.send_response(404)
            message = "<h1>404 - Page Not Found</h1>"

        self.wfile.write(bytes(message, "utf-8"))

    def log_message(self, format, *args):
        print(f"REQUEST: {self.client_address[0]} → {self.path}")

server = HTTPServer(("localhost", 3000), MyServer)
print("Server running at http://localhost:3000")
print("Try: /products and /users routes")
server.serve_forever()

  3. In your terminal, navigate to your Desktop and run the server:

    cd ~/Desktop
python3 server.py

    You should see: Server running at http://localhost:3000

    📸 Screenshot: Your server is live — notice the terminal is now waiting, listening for requests

  4. Open your browser (client). Visit these URLs one by one and observe what comes back from your server:

    • http://localhost:3000 — Home route
    • http://localhost:3000/products — Products route
    • http://localhost:3000/users — Users route
    • http://localhost:3000/xyz — Non-existent route (watch for 404)

    📸 Screenshot: Browser (client) receiving the /products response from your Python server

  5. Now look back at your terminal. You'll see every request logged — this is what every web server does in production:

    📸 Screenshot: Server logs — every browser request shows up here. This is what real server logs look like.

Option B — Node.js

If you prefer Node.js, install it from nodejs.org, then create server.js:

const http = require('http');

const server = http.createServer((req, res) => {
    console.log(`REQUEST: ${req.method} ${req.url}`);
    res.writeHead(200, {'Content-Type': 'text/html'});

    if (req.url === '/') {
        res.end('<h1>Hello! Your Node.js server is running.</h1>');
    } else if (req.url === '/products') {
        res.end('<h1>Products</h1><p>Product A, Product B</p>');
    } else {
        res.writeHead(404);
        res.end('<h1>404 Not Found</h1>');
    }
});

server.listen(3000, () => console.log('Server at http://localhost:3000'));

Run with: node server.js

✅ What you just proved: The client-server model is real and tangible. Your browser (client) sent HTTP requests → your Python/Node script (server) processed them → sent back HTML responses. Port 3000 was your server's "door". When we move this to EC2, the only difference is the server lives in AWS's data center instead of your laptop.

❌ Common mistake: Forgetting to stop the old server before starting a new one. If you see "Address already in use", press Ctrl+C to stop the running server first. This is the port conflict you learned about in the Networking section.
