🔍 VPC Flow Logs

📖 Detailed Explanation

VPC Flow Logs is a feature that captures network traffic metadata flowing to and from network interfaces within your VPC. It provides visibility into network traffic patterns, helping you monitor, troubleshoot, and analyze network connectivity issues.

Flow logs capture information about IP traffic going to and from network interfaces in your VPC. They record allowed and rejected traffic, helping you diagnose overly restrictive security group rules, monitor traffic reaching your instances, and determine the direction of traffic to and from network interfaces.

Unlike packet capture tools, VPC Flow Logs capture metadata about the traffic, not the actual packet contents. This makes them efficient for large-scale monitoring without impacting network performance.

🔑 Key Concepts

  • Capture Scope: Flow logs can be created at VPC level (all resources), subnet level (subnet resources), or network interface level (specific resource)
  • Traffic Types: Configure to capture accepted traffic, rejected traffic, or all traffic
  • Aggregation Interval: Data captured at 1-minute or 10-minute intervals
  • Destination Options: Logs stored in CloudWatch Logs, S3 buckets, or Amazon Kinesis Data Firehose
  • Log Format: Includes source/destination IP, ports, protocol, packets, bytes, action (ACCEPT/REJECT)
  • No Performance Impact: Flow logs run outside the path of network traffic and don't affect network throughput or latency

🔗 VPC Peering Connection

📖 Detailed Explanation

VPC Peering is a networking connection between two VPCs that enables you to route traffic between them using private IPv4 or IPv6 addresses. Instances in either VPC can communicate with each other as if they were within the same network, without requiring an internet gateway, VPN connection, or separate network appliance.

VPC Peering connections work across AWS accounts and regions, enabling you to create private network connections between VPCs regardless of where they reside. Traffic between peered VPCs stays on the AWS private network and never traverses the public internet, providing enhanced security and lower latency.

The peering connection is a one-to-one relationship - you cannot create transitive peering. If VPC-A peers with VPC-B, and VPC-B peers with VPC-C, VPC-A cannot communicate with VPC-C through VPC-B. Each peering relationship must be explicitly established.

🔑 Key Concepts

  • Requester and Accepter: One VPC initiates the peering request, the other accepts it
  • Non-overlapping CIDR Blocks: VPCs must have different IP address ranges to peer successfully
  • Route Table Updates: Manual route entries required in both VPC route tables to enable traffic flow
  • Security Group References: Can reference security groups from peered VPC (same region only)
  • No Transitive Peering: Traffic cannot route through an intermediate VPC
  • Cross-Region Support: Peering connections work across AWS regions with data transfer charges
  • Cross-Account Support: VPCs in different AWS accounts can be peered

🔌 VPC Endpoints

📖 Detailed Explanation

VPC Endpoints enable you to privately connect your VPC to supported AWS services without requiring an internet gateway, NAT device, VPN connection, or AWS Direct Connect. Traffic between your VPC and AWS services does not leave the Amazon network, providing enhanced security and lower latency.

There are two types of VPC endpoints: Gateway Endpoints (for S3 and DynamoDB) and Interface Endpoints (powered by AWS PrivateLink for other services). Gateway endpoints are free and use route table entries, while interface endpoints create elastic network interfaces in your subnets and incur hourly charges plus data transfer costs.

VPC endpoints eliminate the need for public IP addresses and internet connectivity for resources accessing AWS services. This is particularly valuable for resources in private subnets that need to access services like S3, DynamoDB, or other AWS services without exposing them to the internet.

🔑 Key Concepts

  • Gateway Endpoints: Free endpoints for S3 and DynamoDB using route table entries
  • Interface Endpoints: Powered by AWS PrivateLink, create ENIs in subnets for most AWS services
  • Private Connectivity: Traffic stays on AWS private network, never traverses public internet
  • Endpoint Policies: IAM policies to control access to services through the endpoint
  • No Internet Gateway Required: Resources in private subnets can access AWS services
  • Security Group Support: Interface endpoints support security groups for access control
  • DNS Resolution: Interface endpoints provide private DNS names for service access

🚪 API Gateway

📖 Detailed Explanation

Amazon API Gateway is a fully managed service that makes it easy to create, publish, maintain, monitor, and secure APIs at any scale. It acts as a "front door" for applications to access data, business logic, or functionality from backend services such as Lambda functions, EC2 instances, or any HTTP endpoint.

API Gateway handles all the tasks involved in accepting and processing up to hundreds of thousands of concurrent API calls, including traffic management, authorization and access control, monitoring, and API version management. It supports RESTful APIs, WebSocket APIs, and HTTP APIs for real-time two-way communication applications.

In serverless architectures, API Gateway is commonly used as the entry point that triggers Lambda functions. The API Gateway receives HTTP requests, invokes the appropriate Lambda function with the request data, and returns the Lambda response to the client. This pattern enables building scalable, pay-per-use backend services without managing servers.

🔑 Key Concepts

  • REST API: RESTful API with full feature set including caching, request/response transformations
  • HTTP API: Simplified, lower-cost option for HTTP proxy integrations with Lambda
  • WebSocket API: For real-time two-way communication (chat apps, streaming dashboards)
  • Resources: URL paths like /orders, /payment representing different endpoints
  • Methods: HTTP verbs (GET, POST, PUT, DELETE) allowed on each resource
  • Integration: Backend service the API Gateway connects to (Lambda, HTTP endpoint, AWS service)
  • Stages: Different deployment environments (dev, staging, prod) with unique URLs
  • CORS: Cross-Origin Resource Sharing enabling web applications to call your API from different domains

Practice Why It Matters How to Implement
