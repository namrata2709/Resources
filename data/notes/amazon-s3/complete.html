🌟 Introduction

Imagine you need to store a billion photos. You can't put them on a single hard drive — it would fill up instantly. You can't put them on a local server — what if it crashes? You need something that stores any amount of data, is accessible from anywhere in the world, never loses a file, and costs only for what you actually store.

That is Amazon S3.

Amazon S3 (Simple Storage Service) is an object storage service that offers industry-leading scalability, data availability, security, and performance. It is one of the oldest AWS services (launched in 2006) and one of the most widely used — powering everything from individual file backups to Netflix's video streaming infrastructure.

Figure 1: Amazon S3 — global object storage accessible from anywhere via HTTPS

In today's class, after completing EFS, we moved on to S3 and started with the two most fundamental concepts: buckets and objects. We also saw a live demo of creating a bucket and the globally unique naming constraint in action — when a bucket name was already taken by someone else, the console immediately rejected it.

⚡ Key fact from class: "S3 is a global service — unlike EC2, you see ALL your S3 buckets from a single dashboard regardless of which region you're in."

🔍 What is Amazon S3?

Object Storage vs Block Storage — The Fundamental Difference

Before understanding S3, you need to understand what "object storage" means — because it is different from EBS (block storage) and EFS (file storage) in a fundamental way.

Figure 2: Block vs File vs Object storage — three fundamentally different storage models

ConceptBlock (EBS)File (EFS)Object (S3)
How data is organizedRaw blocks (like hard drive sectors)Files in a directory treeObjects with a flat key (filename) + data + metadata
Access methodDirectly attached to OSNFS mount over networkHTTP/HTTPS API (REST)
MutabilityEditable in-placeEditable in-placeReplace entire object (not editable in-place)
Best forOS boot volumes, databasesShared Linux file systemsStatic files, backups, media, data lakes

S3 in One Sentence

Amazon S3 stores data as objects inside buckets — every object consists of the data itself, a unique key (filename), and metadata.

Think of it this way: a bucket is like a folder or container, and an object is the file you put inside it. But unlike a regular folder on your computer, an S3 bucket can hold an unlimited amount of data and is accessible from anywhere in the world via a URL.

🪣 Buckets — The S3 Container

What is a Bucket?

A bucket is a container for objects stored in Amazon S3. Every object in S3 must be stored inside a bucket.

The class used the analogy perfectly: "a bucket is a container." You do not upload files directly to S3 — you first create a bucket, then upload files (objects) into that bucket.

Figure 3: S3 bucket and object structure — buckets contain objects, objects have keys and metadata

Globally Unique Bucket Names

S3 bucket names must be globally unique — across ALL AWS accounts and ALL regions worldwide. No two buckets anywhere on AWS can have the same name.

This is why in class, when we tried to create a bucket named "saiguda", it was rejected — someone else (in any account, any region) had already taken that name. We then successfully created "saiguda654".

Why globally unique? Because every S3 bucket gets a public DNS name in the format bucket-name.s3.amazonaws.com. If two buckets had the same name, the DNS system would break. Think of bucket names like domain names on the internet — only one person can own "google.com".

Bucket Naming Rules

  • Between 3 and 63 characters long
  • Lowercase letters, numbers, and hyphens only
  • Must start with a letter or number (not a hyphen)
  • Cannot be formatted as an IP address (e.g., 192.168.1.1)
  • Cannot have underscores or uppercase letters

Buckets Are Created in a Region

When you create an S3 bucket, you choose a specific AWS region where it is created. The data in that bucket physically resides in that region.

In class today, we created a bucket in the Asia Pacific (Mumbai) ap-south-1 region. But as we saw — even if you switch the console to Singapore, you can still see all buckets from all regions in the same S3 dashboard. This is because of S3's global nature.

Bucket Size

In class, we asked: "What is the size of the bucket you are creating?" — The answer: unlimited. A single S3 bucket has no maximum storage limit. You can store as little as 0 bytes or as many petabytes as you need in a single bucket. AWS handles the underlying storage infrastructure automatically.

Bucket Types

When creating a bucket, you choose the bucket type:

  • General Purpose: The standard bucket — stores objects across multiple Availability Zones within the region. This is what we used in class.
  • Directory bucket: A high-performance bucket for specific use cases requiring single-AZ storage with faster processing. Used for the S3 Express One Zone storage class only.

💡 From class: "If you are creating a directory means it is for a different purpose — only for the S3 Express One Zone storage class, for faster processing within a single availability zone." For the SAA exam, General Purpose is the default and most commonly tested.

📦 Objects — The S3 Data Unit

What is an Object?

An object is any file or data stored in S3 — it consists of the object data (the actual content), a key (the object's name/path), and metadata (information about the object).

In class, we discussed the analogy of objective (fixed) vs subjective (varies per person). An object in S3 is "objective" — it has a fixed, definitive value. A key is "subjective" — it varies (it's the unique name you give). This is a memorable way to think about the distinction.

Object Keys

The key is the full path and name of the object within the bucket. Examples:

  • photo.jpg — a simple file at the root level
  • 2024/january/invoice-001.pdf — a "path" using the / separator
  • users/sai/profile-picture.png — appears to be in subdirectories

S3 has no actual directory structure — it is a flat namespace. The slashes in keys are just part of the key name and give the visual appearance of folders in the console. Underneath, every object is at the same level with just different key names.

Object Size Limits

A single S3 object can be up to 5 TB in size. For objects larger than 5 GB, you must use the Multipart Upload API, which breaks the upload into parts that are uploaded in parallel and then assembled.

📚 According to AWS documentation, for objects 100MB or larger, AWS recommends using Multipart Upload even though it is only required for objects over 5GB. The parallel upload provides faster completion and the ability to resume failed uploads.
📚 Source: S3 Multipart Upload Docs

Object Metadata

Every S3 object carries metadata — information about the object:

  • System metadata: Content-Type, Content-Length, Last-Modified, ETag (checksum), version ID — set by S3
  • User-defined metadata: Custom key-value pairs you attach — e.g., x-amz-meta-uploaded-by: john

🌍 S3 as a Global Service

In class today we observed a critical behavior — when you switch the AWS console region to Singapore, you still see ALL S3 buckets (including the one we created in Mumbai). The instructor pointed out this is different from EC2.

Figure 4: S3 global dashboard — all buckets visible in one view, regardless of console region setting

Amazon S3 is a global service — all buckets in an account are visible from a single S3 dashboard, regardless of which region the console is currently set to.

However — and this is important — although S3 has a global dashboard, each bucket's data is stored in a specific region. Data does NOT automatically replicate across regions unless you configure Cross-Region Replication (CRR).

⚡ The contrast:
EC2 console → switch region → see only that region's instances.
S3 console → switch region → still see ALL buckets from all regions.

🛠️ Creating Your First Bucket — Walkthrough

Here is the exact process we followed in class today to create an S3 bucket:

  1. Open the S3 Console (search "S3" or "Scalable Storage in the Cloud").
  2. Click Create bucket.
  3. Under Bucket type, select General purpose (default).
  4. Enter a Bucket name — it must be globally unique. If you see "The specified bucket name is already taken," someone else owns that name. Try adding numbers or your identifier (we used "saiguda654").
  5. Select the AWS Region where the bucket should be created (we used ap-south-1 Mumbai).
  6. Leave all other settings as default for now. Click Create bucket.

📸 Screenshot: S3 bucket creation — general purpose type, globally unique name, region selected

  1. The bucket appears in the S3 dashboard. Notice the region column — it confirms where the bucket lives.
  2. Click the bucket name to open it. You will see it is empty. Click Upload to add your first object.
  3. Click Add files, select a file from your computer, and click Upload. The file appears as an object in your bucket.

🗄️ S3 Storage Classes

S3 offers multiple storage classes so you can optimize cost vs availability vs retrieval speed based on how frequently you access different types of data.

Figure 5: S3 storage classes — from instant-access Standard to long-term archive Deep Archive

S3 Standard

S3 Standard stores data across a minimum of 3 Availability Zones, providing 11 nines (99.999999999%) of durability and 99.99% availability. This is the default storage class and is best for frequently accessed data.

S3 Intelligent-Tiering

S3 Intelligent-Tiering automatically moves objects between access tiers based on usage patterns — no retrieval fees apply regardless of which tier the object is in. Best for data with unpredictable access patterns.

S3 Standard-IA (Infrequent Access)

S3 Standard-IA stores data across multiple AZs for infrequently accessed data — lower storage cost than Standard but with a per-GB retrieval fee. Minimum storage duration: 30 days.

S3 One Zone-IA

S3 One Zone-IA stores data in a single AZ — lowest cost for infrequent access, but data is lost if the AZ is destroyed. Use only for data that can be recreated or is already replicated elsewhere.

S3 Glacier Classes (Archive Storage)

Glacier classes are for data you rarely need but must keep — think compliance archives or disaster recovery backups.

ClassRetrieval TimeUse Case
S3 Glacier Instant RetrievalMillisecondsArchive that needs occasional instant access (e.g., medical images)
S3 Glacier Flexible Retrieval1-12 hoursBackup archives where retrieval isn't urgent
S3 Glacier Deep Archive12-48 hoursLong-term compliance storage — cheapest option on AWS

✅ Cost optimization rule of thumb:
Accessed daily → Standard
Accessed weekly/monthly → Standard-IA
Accessed rarely but must keep → Glacier
Unknown pattern → Intelligent-Tiering

🛡️ Durability and Availability

The Famous 11 Nines

Amazon S3 Standard provides 99.999999999% durability (11 nines) — this means if you store 10 million objects, you can expect to lose at most one object every 10,000 years.

How does S3 achieve this? Every object is automatically stored across a minimum of 3 Availability Zones within a region. If one data center catches fire or floods, your data is still intact in two other locations.

Figure 6: S3 durability — automatic replication across 3 AZs within a region

💡 Durability vs Availability:
Durability = will your data still exist? (S3 Standard: 11 nines — near permanent)
Availability = can you access your data right now? (S3 Standard: 99.99% — roughly 53 minutes downtime per year max)

📜 S3 Versioning

S3 Versioning keeps all versions of an object — including overwrites and deletes — allowing you to restore any previous version at any time.

Without versioning: if you upload a new file with the same key, the old one is permanently overwritten. With versioning enabled, every upload is preserved as a new version. A delete creates a "delete marker" — the object isn't actually gone; you can restore it by removing the delete marker.

⚡ Versioning is a must for: any bucket where accidental deletion or overwrite would cause data loss — website assets, code repositories, database backups.

🔒 S3 Security

Public vs Private Buckets

By default, all S3 buckets and objects are private — only the bucket owner can access them.

To make objects publicly accessible (e.g., for a static website), you must explicitly disable the "Block Public Access" settings and apply a bucket policy or object ACL. Public access should only be enabled intentionally for specific use cases.

Bucket Policies

Bucket policies are JSON-based IAM policies attached to the bucket that control who can access it and what they can do. You can grant access to specific AWS accounts, IAM roles, or the public.

Encryption

S3 supports multiple encryption options:

  • SSE-S3: Server-side encryption with S3-managed keys (default since 2023)
  • SSE-KMS: Server-side encryption with AWS KMS keys (customer-controlled)
  • SSE-C: Server-side encryption with customer-provided keys
  • Client-side encryption: You encrypt before uploading

Since January 2023, all new S3 objects are encrypted by default with SSE-S3 — no configuration required.

📊 Key S3 Facts for the Exam

  • S3 is an object storage service — not block (EBS) or file (EFS) storage.
  • S3 Standard durability: 99.999999999% (11 nines).
  • S3 Standard availability: 99.99%.
  • Bucket names must be globally unique across all AWS accounts worldwide.
  • Bucket names: 3–63 characters, lowercase only, no underscores.
  • Single object max size: 5 TB. Multipart Upload required for objects > 5 GB.
  • S3 is a global service — all buckets visible from one dashboard, but data is stored in a specific region.
  • Default encryption on all new objects since January 2023 (SSE-S3).
  • S3 One Zone-IA = single AZ = lowest cost but no AZ redundancy.
  • S3 Glacier Deep Archive = cheapest storage on AWS for long-term archiving.

📝 Overall Summary

  • What is S3: AWS's scalable, durable object storage service — store and retrieve any amount of data from anywhere via HTTP/HTTPS.
  • Core components: Buckets (containers) and Objects (files). Every object lives in a bucket.
  • Global service: All buckets visible from one dashboard. But each bucket's data lives in a specific region.
  • Globally unique names: Bucket names must be unique across ALL AWS accounts worldwide — like domain names on the internet.
  • Unlimited size: A single S3 bucket has no storage size limit.
  • 11 nines durability: S3 Standard stores objects across 3 AZs — 99.999999999% durability.
  • Object size: Up to 5TB per object. Multipart Upload required for objects over 5GB.
  • Flat namespace: No real directories — slashes in object keys simulate folder structure visually.
  • Storage classes: Standard → Intelligent-Tiering → Standard-IA → One Zone-IA → Glacier (Instant → Flexible → Deep Archive). Match class to access frequency for cost optimization.
  • Security: Private by default. Bucket policies and ACLs control access. Default encryption since 2023.

Project 2: Host a Static Website on S3

🎯 Objective: Configure an S3 bucket as a static website host, add a bucket policy for public access, and serve a real HTML page via a public URL.

⏱️ Time: 20-30 min

💰 Cost: Free Tier for storage; minimal GET request costs if accessed publicly

  1. Create a new bucket (unique name, e.g., yourname-static-site-nov2025). Create an index.html file locally and upload it.

  2. Bucket → Properties → Static website hosting → Edit → Enable → Index document = index.html → Save.

    📸 Screenshot: Static website hosting enabled — index.html set as index document

  3. Bucket → Permissions → Block Public Access → Edit → uncheck all → Save → type "confirm". Then add a bucket policy allowing public GetObject.

    📸 Screenshot: Bucket policy editor — public read GetObject policy added

  4. Copy the bucket website endpoint URL from Properties → Static website hosting. Open it in a browser.

    📸 Screenshot: S3-hosted website live in browser via the bucket endpoint URL

✅ What you proved: S3 can serve a fully functional public website with no servers. Zero infrastructure to manage — just objects in a bucket.

🧹 Cleanup: Re-enable Block Public Access → delete bucket policy → delete objects → delete bucket.

Project 3: Versioning + Accidental Deletion Recovery

🎯 Objective: Enable S3 Versioning, simulate accidental overwrites and deletions, then recover the original data using version history and delete markers. This is one of the most asked-about S3 topics in interviews.

⏱️ Time: 25-35 min

💰 Cost: Free Tier — old versions consume storage, delete after testing

  1. Create a new bucket. Bucket → Properties → Bucket Versioning → Edit → Enable → Save.

    📸 Screenshot: Bucket Versioning enabled — status shows Enabled

  2. Create a file locally: echo "Version 1 — original content" > config.txt. Upload it to the bucket.

  3. Create a new version: echo "Version 2 — accidental overwrite" > config.txt. Upload the same filename again. In the bucket, toggle Show versions — you now see two versions of config.txt.

    📸 Screenshot: Show versions toggle — two versions of config.txt with different Version IDs

  4. Restore Version 1: Click the older version (Version 1) → Download → verify content says "Version 1 — original content". To restore: download the old version and re-upload it — it becomes Version 3 (the latest). Or copy the version ID and use it directly.

  5. Now delete the object (without specifying version ID). Toggle Show versions — notice a Delete marker appeared. The object looks deleted from the normal view but all versions are preserved.

    📸 Screenshot: Delete marker visible — object appears deleted but versions preserved

  6. Recover from delete: Select the Delete marker → Delete (you are deleting the marker, not the file). Toggle Show versions off — config.txt reappears as if nothing happened.

✅ What you proved: Versioning turns every overwrite and delete into a reversible operation. A "deleted" file with versioning is just hidden by a delete marker — removing the marker resurrects it instantly. This is the most important data protection feature in S3.

🧹 Cleanup: Delete all versions explicitly (not just the latest) → delete the bucket. With versioning, you must delete each version separately — the bucket won't allow deletion otherwise.

Project 4: Lifecycle Policies — Automate Storage Class Transitions

🎯 Objective: Create S3 Lifecycle rules that automatically move objects through storage classes over time. Build a cost-optimized tiered storage system with zero manual work after initial setup.

⏱️ Time: 30-40 min

💰 Cost: Free to configure. Storage charges apply for what you store — use small test files.

  1. Create a new bucket. Create three "folders" (key prefixes) to simulate different data categories: upload files with keys starting with hot/, warm/, and archive/.

    # Using AWS CLI
aws s3 cp test.txt s3://your-bucket-name/hot/active-report.txt
aws s3 cp test.txt s3://your-bucket-name/warm/monthly-log.txt
aws s3 cp test.txt s3://your-bucket-name/archive/old-records.txt

    📸 Screenshot: S3 bucket with hot/, warm/, archive/ prefix structure

  2. Bucket → Management tab → Lifecycle rules → Create lifecycle rule.

  3. Create Rule 1 — Warm data tiering:
    Rule name = warm-to-ia | Prefix = warm/ | Action: Transition to Standard-IA after 30 days.

    📸 Screenshot: Lifecycle Rule 1 — warm/ prefix transitions to Standard-IA at 30 days

  4. Create Rule 2 — Archive tiering:
    Rule name = archive-to-glacier | Prefix = archive/ | Two transitions:
    → Transition to Standard-IA after 30 days
    → Transition to Glacier Flexible Retrieval after 90 days
    → Expire (delete) after 365 days.

    📸 Screenshot: Lifecycle Rule 2 — archive/ prefix has 3 tiers: IA → Glacier → expire

  5. View the Lifecycle rules list to see both rules active on the same bucket.

    📸 Screenshot: Two lifecycle rules active — warm-to-ia and archive-to-glacier

✅ What you proved: S3 Lifecycle is a fully automatic cost optimisation engine. Once configured, objects flow through tiers without any human involvement. The hot/ prefix stays in Standard forever; warm/ saves money after 30 days; archive/ eventually costs almost nothing and deletes itself after a year.

🧹 Cleanup: Delete all objects → delete lifecycle rules → delete the bucket.

Project 5: Secure File Sharing with Pre-Signed URLs

🎯 Objective: Generate time-limited pre-signed URLs that grant temporary access to private S3 objects — without making the bucket public and without sharing AWS credentials. This is how real applications let users download private files securely.

⏱️ Time: 20-30 min

💰 Cost: Free — S3 GET requests within Free Tier

  1. Create a private bucket (Block Public Access ON — leave default). Upload a file (e.g., a PDF or image). Confirm the object is private: click the object URL — you should see Access Denied.

    📸 Screenshot: Direct object URL returns Access Denied — object is private

  2. Generate a pre-signed URL using the AWS CLI (valid for 3600 seconds = 1 hour):

    aws s3 presign s3://your-bucket-name/your-file.pdf   --expires-in 3600

    📸 Screenshot: AWS CLI presign output — time-limited signed URL generated

  3. Open the pre-signed URL in a browser. The private file downloads successfully — no login, no credentials, just the signed URL.

    📸 Screenshot: Pre-signed URL works — private file accessible via the time-limited link

  4. Wait for the URL to expire (or generate one with --expires-in 10 for a 10-second URL). Try accessing it after expiry — you will see Request has expired.

    📸 Screenshot: Expired pre-signed URL returns Request has expired error

✅ What you proved: Pre-signed URLs are the correct solution for sharing private S3 content securely and temporarily. No bucket policy changes, no credentials sharing, no public access. The URL itself is the time-limited key.

⚡ Real-world usage: Almost every application that serves user-uploaded files (profile photos, invoices, reports) uses pre-signed URLs behind the scenes. When you click "Download your invoice" on any SaaS platform, there is a very high chance a Lambda function just generated a pre-signed S3 URL for you.

🧹 Cleanup: Delete all objects → delete the bucket.
