🌟 Introduction

Imagine you work in a big office building. Not everyone can walk into every room — the CEO has a master key, employees have keys to their own floors, and the security system has its own automated access. Linux works exactly the same way. Every person or process that interacts with the system does so through a user account, and every file, folder, and resource has rules about who can access it and what they can do.

This session dives into the three pillars that make Linux one of the most secure operating systems in the world: Users (who you are), Groups (the team you belong to), and File Permissions (what you're allowed to do). These concepts are the absolute core of Linux — understanding them is non-negotiable for interviews, day-to-day DevOps work, and managing cloud servers on AWS.

Figure 1: The three types of Linux users and their access levels

⚡ Why this matters for AWS: Every EC2 instance runs Linux. When you SSH into a server, you log in as a user (like ec2-user). Understanding users and permissions means you can control exactly who can access your server, which files they can read, and which commands they can run — essential for cloud security.

👤 What is a Linux User?

In Linux, a user is not just a person sitting at a keyboard. It is an account — an identity that the operating system recognises and uses to control access to the system. Think of it like a hotel key card: each card is programmed with its own level of access, and the hotel's system checks the card before letting anyone through any door.

In Linux, a user is an account that allows a person or a process to log into the system and use system resources such as files, commands, processes, and devices.

When you work with Amazon Linux on an EC2 instance, the first thing you do is log in as the ec2-user account. That is a user. Because of that account, you are allowed to connect to the server and start running commands. Without it, the operating system simply would not let you in.

What Every User Account Has

Every user account in Linux comes with a fixed set of attributes. Think of these like your employee badge — each badge has your name, ID number, department, and office location. In Linux, those details look like this:

Figure 2: The six attributes every Linux user account carries

  • Username: The human-readable name for the account (e.g., ec2-user, sai, alice).
  • Password: Stored in encrypted form in /etc/shadow. You can assign a password to any user.
  • Every user has a UID (User ID) — a unique numeric identifier that the kernel uses internally to identify the account.
  • Home Directory: A private folder allocated to the user (e.g., /home/alice). This is the user's working space on the filesystem.
  • Default Shell: The program that interprets the commands you type (e.g., /bin/bash). Without a shell, you cannot interact with the OS.
  • Primary Group: When a user is created, Linux automatically creates a group with the same name as the username, and the user becomes a member of that group.

💡 Real-world analogy: Think of a user account like a Netflix profile. Each profile has a name, its own watch history, its own settings, and its own restrictions. Linux user accounts work the same way — each has its own identity, its own home folder, and its own set of permissions.

🏷️ Types of Linux Users

Just like a Windows machine has an Administrator and a Guest, Linux has three distinct types of users. Each type has a different level of power over the system. Understanding these is critical — both for interviews and for working securely in the real world.

Figure 3: Detailed comparison of root, normal, and system users with their UID ranges

1. Root User (Super User)

The root user is the all-powerful administrator of the Linux system — equivalent to the Administrator in Windows, but with even more power. There is nothing the root user cannot do.

The root user has full administrative privileges and can install software, manage other users, change system configuration files, and access any file on the system.
  • The root user's username is always root.
  • The root user always has a UID of 0 — this is how Linux identifies the root account regardless of the username.
  • The root user's home directory is /root (not /home/root).
  • Using root for everyday tasks is considered a serious security risk — even system administrators avoid it.

❌ Security Warning: Never run your daily work as root. If a malicious script runs as root, it can delete every file, expose every password, and destroy the entire system. Always use a normal user and escalate only when absolutely necessary.

2. Normal User

Normal users are accounts created by the system administrator (root) for real human beings who need to use the system. Think of them like employees with a key card to their own floor but not to the server room.

Normal users have limited privileges and can only read, write, or execute files they own or have been explicitly granted access to by the system administrator.
  • Created by root using the useradd command.
  • Normal users have UIDs starting from 1000 on most modern Linux distributions.
  • Each normal user has their own home directory under /home/username.
  • They can use the sudo command to temporarily elevate their privileges — but only if the administrator has granted them that permission.

3. System User

System users are not humans — they are accounts created by the operating system or application software to run background services and processes. You will never log in interactively as a system user.

System users are service accounts used to run background processes like web servers, databases, and SSH daemons — they typically have no home directory and no login shell.
  • Examples: www-data (web server), mysql (database), sshd (SSH daemon).
  • System users have UIDs in the range 1–999 on most Linux distributions.
  • They exist purely so that services can run with the minimum necessary permissions — a principle called least privilege.

⚡ Interview Tip: If asked "What are the three types of Linux users?" — answer: Root (UID 0), Normal (UID 1000+), and System (UID 1–999). Memorise the UID ranges — they frequently appear in exams and interviews.

👥 Linux Groups

A group in Linux is exactly what it sounds like — a collection of user accounts that share the same access permissions. Think of it like a department in a company. Everyone in the Finance department can access the Finance shared drive. You do not need to give each person individual access — you just add them to the Finance group.

A Linux group is a collection of user accounts that share a common set of permissions, allowing administrators to manage access for multiple users at once instead of individually.

Figure 4: How groups allow shared access to resources without individual permission assignments

What Every Group Has

  • Group Name: Human-readable name (e.g., developers, sudo, ec2-user).
  • Every group has a GID (Group ID) — a unique numeric identifier used internally by the Linux kernel.
  • Member List: The users who belong to that group.
  • Group Password: Rarely used, but groups can have passwords stored in /etc/gshadow.

Primary vs. Secondary Groups

Every user in Linux belongs to at least one group — their primary group. But users can also be added to additional groups called secondary groups.

A user's primary group is automatically created when the user is created and shares the same name as the username; secondary groups are additional groups the user is added to for shared access.

💡 Real-world example on AWS: On an EC2 instance running Amazon Linux, the ec2-user account is a member of the ec2-user group (primary) and also the sudo group (secondary) — that is why ec2-user can run sudo commands.

📂 Important Configuration Files

Linux stores all user, group, and password information in plain-text configuration files located in the /etc directory. These files are the source of truth for the entire authentication system. Knowing these files inside out is critical for interviews — you will almost certainly be asked about them.

Figure 5: The three critical Linux configuration files and how they relate to each other

/etc/passwd — User Database

/etc/passwd is the main user database file that stores basic information about every user account on the system — it is readable by all users.

Each line in this file represents one user, with fields separated by colons (:). Here is what a typical line looks like:

ec2-user:x:1000:1000:EC2 Default User:/home/ec2-user:/bin/bash

Breaking that down field by field:

  • ec2-user — Username
  • x — Password placeholder (actual password is in /etc/shadow)
  • 1000 — UID (User ID)
  • 1000 — GID (Primary Group ID)
  • EC2 Default User — Comment / Full Name (GECOS field)
  • /home/ec2-user — Home directory
  • /bin/bash — Default login shell

💡 View this file: Run cat /etc/passwd on any Linux system. Because it is world-readable (anyone can read it), the actual passwords are NOT stored here — just an x as a placeholder.

/etc/shadow — Encrypted Passwords

/etc/shadow stores the encrypted (hashed) passwords for all user accounts and is readable only by the root user for security reasons.

This file was created because storing passwords in /etc/passwd (which is world-readable) was a major security vulnerability. By moving passwords to /etc/shadow and restricting access, Linux prevents normal users from even reading the encrypted password hashes.

ec2-user:$6$randomsalt$hashedpassword...:19000:0:99999:7:::
  • The password is stored using a strong hashing algorithm (like SHA-512, indicated by $6$).
  • Even if someone reads this file, they see only the hash — not the actual password.
  • Only the root user can read /etc/shadow — a normal user receives Permission denied when trying to open it.

✅ Demo from class: Running cat /etc/shadow as a normal user returns "Permission denied". Running sudo cat /etc/shadow shows the file because sudo elevates you to root privileges temporarily.

/etc/group — Group Database

/etc/group is the group database file that lists all groups on the system, their GIDs, and the members of each group.

Each line represents one group:

developers:x:1001:alice,bob,carol
  • developers — Group name
  • x — Group password (rarely used)
  • 1001 — GID (Group ID)
  • alice,bob,carol — Comma-separated list of group members

💡 View this file: Run cat /etc/group to see all groups. You will see a group for every user (their primary group), plus system groups like sudo, docker, and wheel.

🛠️ User Management Commands

Now that you understand what users and groups are, let's look at how to manage them. All user management commands require root privileges — either by running as root or using sudo.

Figure 6: Linux user and group management commands organised by function

Creating Users

# Create a new user (basic)
useradd username

# Create a user with a home directory, shell, and comment
useradd -m -s /bin/bash -c "Full Name" username

# Set a password for the user
passwd username

# Create a new group
groupadd groupname

Flags explained:

  • -m — Create the home directory at /home/username
  • -s /bin/bash — Set the default shell
  • -c "Full Name" — Add a comment (usually the full name)

Modifying Users

# Add a user to a secondary group
usermod -aG groupname username

# Change a user's shell
usermod -s /bin/zsh username

# Lock a user account (disable login)
usermod -L username

# Unlock a user account
usermod -U username

⚡ Critical flag: Always use -aG (append to Group) with usermod. If you use just -G without -a, you will replace all existing secondary groups — potentially removing the user from important groups like sudo.

Deleting Users

# Delete a user (keeps their home directory)
userdel username

# Delete a user AND their home directory
userdel -r username

# Delete a group
groupdel groupname

Viewing User Information

# Show the current user's UID, GID, and groups
id

# Show just the current username
whoami

# Show all groups the current user belongs to
groups

# Show groups for a specific user
groups username

# Switch to a different user
su - username

# Switch to root
sudo -i

✅ Tip from class: id is one of the most useful commands in Linux. It shows you your UID, GID, and every group you belong to — all in one line. Always run it after adding yourself to a new group to confirm the change took effect (you may need to log out and log back in first).

🔐 sudo — Privilege Escalation

Here is a real-world problem: you are logged in as a normal user, but you need to install software, edit a system config file, or restart a service — actions that require root privileges. You do not want to log out and log back in as root. You just need a temporary, controlled boost of power. That is exactly what sudo does.

sudo (short for superuser do) allows an authorised normal user to run a specific command with root-level privileges temporarily, without switching to the root account.

Figure 7: How the sudo privilege escalation flow works — from user request to /etc/sudoers check to execution

How sudo Works

  1. A normal user types sudo command.
  2. Linux checks the /etc/sudoers file to see if that user is listed.
  3. If the user is listed: the command runs with root privileges. If not: access is denied and the attempt is logged.
  4. The user may be prompted for their own password (not root's password) to confirm identity.
The /etc/sudoers file is the configuration file that controls which users and groups are allowed to use sudo and which commands they can run.

The /etc/sudoers File

You must never edit /etc/sudoers directly with a normal text editor. A syntax error in this file can lock you out of sudo permanently. Always use the safe editor:

# Correct way to edit sudoers
sudo visudo

# Or with nano (as shown in class)
sudo nano /etc/sudoers

A typical sudoers entry looks like this:

# Allow ec2-user to run all commands as root without a password
ec2-user ALL=(ALL) NOPASSWD: ALL

# Allow alice to run only the apt command as root
alice ALL=(ALL) /usr/bin/apt

💡 From class demo: The ec2-user on Amazon Linux can use sudo because its name is listed in /etc/sudoers with NOPASSWD: ALL. The user ayushi created in class could NOT use sudo because her account was not listed there — Linux said "ayushi is not in the sudoers file."

Adding a User to sudo

The most common method is to add the user to the sudo group (on Ubuntu/Debian) or the wheel group (on RHEL/CentOS/Amazon Linux):

# Add user to sudo group (Ubuntu/Debian)
sudo usermod -aG sudo username

# Add user to wheel group (Amazon Linux / RHEL / CentOS)
sudo usermod -aG wheel username
On Amazon Linux, members of the wheel group are granted sudo privileges by default because the sudoers file contains a rule allowing all wheel group members to run any command.

Switching to Root

# Switch to root user (loads root's environment)
sudo -i

# Switch to root user (stays in current directory)
sudo su

# Exit root and return to normal user
exit

💰 Security Best Practice: On production AWS EC2 instances, direct root login via SSH is disabled by default. This is intentional — it forces all access through named user accounts with sudo, creating an audit trail of exactly who did what and when.

🔄 Switching Between Users

Linux is a multi-user operating system — you can have multiple user sessions and switch between them without logging out. This is a daily task for system administrators.

# Switch to another user (prompts for that user's password)
su - username

# Switch to root (prompts for root's password, or current user's password if using sudo)
su -
sudo -i

# Exit the current user session and return to previous
exit

The - flag after su is important. It means "load the full environment of the target user" — including their home directory, shell settings, and environment variables. Without -, you switch to the user but stay in the current directory with your old environment, which can cause confusing behaviour.

⚡ From class: When the trainer switched to user ayushi (su - ayushi), she was inside ayushi's session and could not use sudo. After typing exit, she returned to ec2-user, who could use sudo. This demonstrates that sudo access is tied to the user account, not the terminal.

🔒 Linux File Permissions

Every single file and directory in Linux has a set of permissions attached to it. These permissions answer three questions: Who can read this? Who can write to this? Who can execute this? And they answer those questions for three different groups of people: the owner, the owner's group, and everyone else.

This is the core of Linux security — and understanding it deeply will set you apart in any DevOps or cloud interview.

Figure 8: Anatomy of a Linux permission string — every character explained

Viewing Permissions with ls -l

Run ls -l in any directory to see file permissions:

-rwxr-xr--  1  alice  developers  4096  Oct 16 10:00  script.sh
drwxr-xr-x  2  root   root        4096  Oct 16 09:00  config/

The first column is the permission string. Let's decode it character by character:

PositionCharacterMeaning
1- or d or lFile type: -=regular file, d=directory, l=symbolic link
2–4rwxOwner permissions (read, write, execute)
5–7r-xGroup permissions (read, write, execute)
8–10r--Others permissions (read, write, execute)

The Three Permission Types

Linux has three permission types: read (r) allows viewing file content or listing a directory; write (w) allows modifying a file or creating/deleting files in a directory; execute (x) allows running a file as a program or entering a directory.

Figure 9: What r, w, x mean differently for files versus directories

💡 Beginner gotcha: Execute on a directory does not mean "run the directory" — it means you can cd into it. If you remove execute permission from a directory, even if you can read it, you cannot enter it or access any files inside it.

The Three Permission Groups

  • Owner (u): The user who created or owns the file. They have the first set of rwx bits.
  • Group (g): The group assigned to the file. All members of that group share the second set of rwx bits.
  • Others (o): Everyone else on the system — any user who is neither the owner nor in the file's group.

⚙️ chmod — Changing Permissions

chmod (change mode) is the command you use to set or change file permissions. There are two ways to use it: symbolic mode (human-readable) and numeric (octal) mode. Both are important — exams and interviews test both.

Symbolic Mode

Symbolic mode uses letters and operators to modify permissions:

# Give the owner execute permission
chmod u+x script.sh

# Remove write permission from group
chmod g-w file.txt

# Give others read permission
chmod o+r file.txt

# Give everyone read and execute
chmod a+rx script.sh

# Set exact permissions for owner: rwx, group: r-x, others: ---
chmod u=rwx,g=rx,o= file.txt

The operators are: + (add), - (remove), = (set exactly). The targets are: u (owner/user), g (group), o (others), a (all).

Numeric (Octal) Mode

Numeric mode uses numbers to represent permissions. Each permission type has a numeric value:

In octal notation, read = 4, write = 2, and execute = 1 — you add these values together to express the permission for each group.

Figure 10: The octal permissions table — all 8 possible combinations from 0 to 7

NumberPermissionCalculation
7rwx4+2+1
6rw-4+2+0
5r-x4+0+1
4r--4+0+0
3-wx0+2+1
2-w-0+2+0
1--x0+0+1
0---0+0+0

You use three digits together — one for owner, one for group, one for others:

# rwxr-xr-- = 754
chmod 754 script.sh

# rw-r--r-- = 644 (typical for regular files)
chmod 644 file.txt

# rwxr-xr-x = 755 (typical for directories and scripts)
chmod 755 script.sh

# rwx------ = 700 (owner only — maximum privacy)
chmod 700 private.sh

⚡ Common permission patterns to memorise:
644 — Standard file (owner can edit, others can read)
755 — Standard directory or script (owner full access, others can read/execute)
600 — Private file like SSH keys (owner only)
777 — Full access for everyone (dangerous — avoid in production)

❌ Never use 777 in production. Setting chmod 777 on a file means anyone on the system — including compromised accounts and malicious scripts — can read, modify, or execute it. This is a critical security mistake.

👑 chown & chgrp — Changing Ownership

Permissions control what you can do with a file. Ownership determines who the permissions apply to. Every file has an owner (a user) and an associated group. You can change both using chown and chgrp.

chown (change owner) changes the user and/or group ownership of a file or directory, and requires root or sudo privileges to execute.
# Change the owner of a file
chown alice file.txt

# Change owner and group in one command
chown alice:developers file.txt

# Change ownership recursively (entire directory tree)
chown -R alice:developers /var/www/project/

# Change only the group (alternative to chgrp)
chown :developers file.txt
# Change the group using chgrp
chgrp developers file.txt

# Recursively change group
chgrp -R developers /var/www/

💡 When do you use chown? A common scenario: you upload files to a web server as root, but the web server process runs as www-data. The server cannot read those files because the owner is root and permissions are set to owner-only. You run chown -R www-data:www-data /var/www/html to fix it.

⭐ Special Permissions (SUID, SGID, Sticky Bit)

Beyond the standard read/write/execute, Linux has three special permission bits. These come up frequently in advanced interviews and AWS security discussions.

Figure 11: The three special permission bits — SUID, SGID, and Sticky Bit explained with real examples

SUID (Set User ID) — 4xxx

The SUID bit, when set on an executable file, causes that file to run with the permissions of the file's owner rather than the permissions of the user running it.

Classic example: /usr/bin/passwd. Any user can change their own password using this command. But the password is stored in /etc/shadow, which only root can write to. SUID allows passwd to run as root (its owner) regardless of who calls it.

# Set SUID
chmod u+s file
chmod 4755 file

# Identify SUID files (shows 's' in owner execute position)
ls -l /usr/bin/passwd
# Output: -rwsr-xr-x ... /usr/bin/passwd

SGID (Set Group ID) — 2xxx

The SGID bit on a directory ensures that all files created inside that directory inherit the directory's group ownership rather than the creating user's primary group.

This is extremely useful for shared project directories where multiple team members need all new files to automatically belong to the project group.

# Set SGID on a directory
chmod g+s /shared/project
chmod 2755 /shared/project

Sticky Bit — 1xxx

The sticky bit on a directory ensures that only the file's owner, the directory's owner, or root can delete or rename files within it — even if others have write permission to the directory.

The classic example is /tmp — everyone can create files in /tmp, but no one can delete someone else's files.

# Set sticky bit
chmod +t /tmp
chmod 1777 /tmp

# Identify sticky bit (shows 't' in others execute position)
ls -ld /tmp
# Output: drwxrwxrwt ... /tmp

🎭 umask — Default Permission Mask

When you create a new file or directory, it does not start with open permissions. Linux applies a umask (user file creation mask) that subtracts permissions from the maximum defaults. Think of umask as a filter — it tells Linux which permissions to remove from newly created files.

The umask is a value subtracted from the default maximum permissions (666 for files, 777 for directories) to determine the actual permissions of newly created files and directories.
# View the current umask
umask
# Common output: 0022

# Calculate effective permissions:
# Files:       666 - 022 = 644 (rw-r--r--)
# Directories: 777 - 022 = 755 (rwxr-xr-x)

# Change umask temporarily (for current session only)
umask 027

# With umask 027:
# Files:       666 - 027 = 640 (rw-r-----)
# Directories: 777 - 027 = 750 (rwxr-x---)

📚 According to AWS documentation, correct umask configuration is a key hardening step for EC2 Linux instances. A umask of 027 or 077 is recommended for sensitive environments where files should not be world-readable by default. 📚 Source: AWS EC2 OS Security Docs

💡 Putting It All Together — Real-World Scenarios

The best way to understand users and permissions is through real scenarios. Here are three practical examples that combine everything from this session.

Scenario 1: Setting Up a Secure Web Server

# Create a web developer group
sudo groupadd webdevs

# Create a developer user and add to group
sudo useradd -m -s /bin/bash -G webdevs alice
sudo passwd alice

# Set up the web root directory with proper ownership
sudo chown -R root:webdevs /var/www/html
sudo chmod -R 755 /var/www/html

# Enable SGID so new files inherit the webdevs group
sudo chmod g+s /var/www/html

# Result: alice can create/edit files in /var/www/html
# All files automatically belong to webdevs group

Scenario 2: Protecting an SSH Private Key

# SSH private key must be readable ONLY by the owner
chmod 600 ~/.ssh/id_rsa

# SSH config directory permissions
chmod 700 ~/.ssh/

# If permissions are too open, SSH will refuse to use the key:
# Warning: UNPROTECTED PRIVATE KEY FILE!

Scenario 3: Creating a Team Shared Folder

# Create the shared team directory
sudo mkdir /shared/team
sudo groupadd teamgroup
sudo usermod -aG teamgroup alice
sudo usermod -aG teamgroup bob

# Set ownership and permissions
sudo chown root:teamgroup /shared/team
sudo chmod 2770 /shared/team
# 2 = SGID (new files inherit group)
# 7 = owner rwx
# 7 = group rwx
# 0 = others no access

# Result: alice and bob can collaborate freely
# No one outside teamgroup can even see the files

📝 Overall Summary

  • Users: A Linux user is an account (person or process) that logs in and uses system resources. Every user has a username, UID, home directory, shell, password, and primary group.
  • Three User Types: Root (UID 0, full power), Normal (UID 1000+, limited, created by admin), and System (UID 1–999, for background services).
  • Groups: A collection of users sharing the same permissions. Every user has a primary group (same name as username) and can belong to secondary groups.
  • Config Files: /etc/passwd (user details, world-readable), /etc/shadow (encrypted passwords, root-only), /etc/group (group memberships).
  • sudo: Allows authorised normal users to run commands with root privileges temporarily. Controlled by /etc/sudoers. On Amazon Linux, members of the wheel group can use sudo.
  • Permissions: Every file/directory has rwx permissions for Owner, Group, and Others. Viewed with ls -l.
  • chmod: Changes permissions using symbolic (u+x) or octal (755) notation. Key values: r=4, w=2, x=1.
  • chown / chgrp: Changes file ownership and group. Requires root/sudo.
  • Special Permissions: SUID (run as file owner), SGID (inherit group in directory), Sticky Bit (only owner can delete). Set with 4xxx, 2xxx, 1xxx.
  • umask: Filters default permissions for newly created files. Default 022 gives files 644 and directories 755.

Project 1: User and Group Management on EC2

🎯 Objective: Create users and groups, configure sudo access, and switch between user accounts on a live EC2 instance. You will feel what it means to be a normal user versus a privileged one.

⏱️ Time: 30–45 min

💰 Cost: Free tier eligible (t2.micro or t3.micro)

  1. SSH into your EC2 instance using the key pair from your earlier session.

    Figure 12: 📸 Successful SSH login — terminal showing ec2-user@ip-address prompt

  2. Run id and whoami to see your current user details. Note the UID, GID, and all group memberships — especially the wheel group that gives ec2-user sudo access.

    Figure 13: 📸 Output of the id command showing ec2-user's UID, GID, and group memberships

  3. Create a new group called devteam: sudo groupadd devteam. Verify it was created: cat /etc/group | grep devteam.

  4. Create two new users — alice and bob — with home directories and bash shells:

    sudo useradd -m -s /bin/bash alice
sudo useradd -m -s /bin/bash bob

    Figure 14: 📸 useradd commands for alice and bob, with /etc/passwd confirmation showing new entries

  5. Set passwords for both users:

    sudo passwd alice
sudo passwd bob

  6. Add both users to devteam:

    sudo usermod -aG devteam alice
sudo usermod -aG devteam bob

    Verify alice's group memberships: groups alice. You should see both alice (primary) and devteam (secondary).

  7. Switch to alice's account and try a privileged command:

    su - alice
sudo cat /etc/shadow

    This should fail — alice is not in sudoers yet.

    Figure 15: 📸 alice's sudo attempt failing — the sudoers denial message confirms she has no elevated access

  8. Exit back to ec2-user and add alice to the wheel group:

    exit
sudo usermod -aG wheel alice

    Switch back to alice and try again:

    su - alice
sudo cat /etc/shadow

    This time it should succeed — alice can now use sudo because wheel group members are authorised in /etc/sudoers.

    Figure 16: 📸 alice's successful sudo command after wheel group membership — /etc/shadow contents now visible

  9. Cleanup — exit to ec2-user and remove test accounts:

    exit
sudo userdel -r alice
sudo userdel -r bob
sudo groupdel devteam

    Verify: cat /etc/passwd | grep alice should return nothing.

Project 2: File Permissions Playground

🎯 Objective: Feel permissions rather than memorise them. You will break permissions intentionally, observe the exact error, and recover — building the muscle memory that turns theory into instinct.

⏱️ Time: 20–30 min

💰 Cost: Free tier eligible

  1. SSH into your EC2 instance. Create a working directory:

    mkdir ~/permissions-lab && cd ~/permissions-lab

  2. Create test files and observe default permissions:

    touch file1.txt file2.sh
ls -l

    Figure 17: 📸 Default file permissions — both files start with 644 (rw-r--r--) because of the system's default umask 022

  3. Add execute permission to the script using symbolic mode, then verify:

    chmod u+x file2.sh
ls -l

    You should now see -rwxr--r-- for file2.sh — the x appeared in the owner section.

  4. Set exact octal permissions on both files:

    chmod 644 file1.txt
chmod 755 file2.sh
ls -l

    Decode each digit yourself before looking at the output. 755 = owner rwx (7), group r-x (5), others r-x (5).

  5. Break it intentionally — remove ALL permissions from file1.txt:

    chmod 000 file1.txt
ls -l
cat file1.txt

    Figure 18: 📸 chmod 000 in action — the owner is denied too, because permissions override ownership checks

  6. Restore and write a real script:

    chmod 644 file1.txt
echo '#!/bin/bash' > file2.sh
echo 'echo Hello from file2' >> file2.sh
./file2.sh

    It should print the message. This confirms execute permission is working correctly.

  7. Test ownership control — change file1.txt to root and try to write as ec2-user:

    sudo chown root:root file1.txt
ls -l
echo "test" >> file1.txt

    Figure 19: 📸 Ownership change to root — ec2-user is now in the 'others' category and has read-only access

  8. Cleanup:

    cd ~
rm -rf permissions-lab

Project 4: Secure Shared Folder with SGID

🎯 Objective: Build a proper team collaboration directory using SGID so that every file created inside automatically inherits the team's group — no manual chown needed. This is how real DevOps teams set up shared codebases.

⏱️ Time: 25–35 min

💰 Cost: Free tier eligible

  1. Create users and group:

    sudo groupadd webdevs
sudo useradd -m -s /bin/bash dev1
sudo useradd -m -s /bin/bash dev2
sudo passwd dev1
sudo passwd dev2
sudo usermod -aG webdevs dev1
sudo usermod -aG webdevs dev2

  2. Create the project directory WITHOUT SGID first:

    sudo mkdir /project
sudo chown root:webdevs /project
sudo chmod 770 /project

  3. Switch to dev1 and create a file — note its group:

    su - dev1
echo "code by dev1" > /project/app.py
ls -l /project/app.py
exit

    Figure 23: 📸 Without SGID — new files inherit the creator's primary group (dev1), not the directory's group (webdevs)

  4. Now enable SGID on the directory:

    sudo chmod g+s /project
ls -ld /project

    Notice the s in the group execute position: drwxrws---. That is SGID active.

    Figure 24: 📸 SGID enabled — the 's' flag in the group execute position confirms group inheritance is now active

  5. Switch to dev2 and create a new file — observe its group:

    su - dev2
echo "code by dev2" > /project/utils.py
ls -l /project/
exit

    Figure 25: 📸 SGID inheritance — utils.py automatically belongs to webdevs, meaning dev1 can also read and write it

  6. Cleanup:

    sudo rm -rf /project
sudo userdel -r dev1
sudo userdel -r dev2
sudo groupdel webdevs

Project 5: Broken System — Debug and Fix

🎯 Objective: Intentionally break file permissions and ownership, then diagnose and fix each issue using only chmod, chown, and your understanding of Linux permissions. This is what interviews and real on-call situations look like.

⏱️ Time: 30–40 min

💰 Cost: Free tier eligible

  1. Set up the broken environment:

    sudo mkdir -p /broken/app /broken/scripts
sudo useradd -m -s /bin/bash appuser
echo "app config" | sudo tee /broken/app/config.txt
echo '#!/bin/bash' | sudo tee /broken/scripts/deploy.sh
echo 'echo Deploying...' | sudo tee -a /broken/scripts/deploy.sh

  2. Now break everything intentionally:

    # Wrong ownership — root owns everything but appuser needs it
sudo chown -R root:root /broken/
# Wrong permissions — no execute on directory, no read on config
sudo chmod 000 /broken/app/
sudo chmod 333 /broken/scripts/deploy.sh

  3. Switch to appuser and try to use the broken system:

    su - appuser
ls /broken/app/
cat /broken/app/config.txt
/broken/scripts/deploy.sh
exit

    Figure 26: 📸 Three permission failures at once — each has a different root cause that you must diagnose separately

  4. As ec2-user, diagnose the problems:

    ls -ld /broken/app/
ls -l /broken/scripts/deploy.sh

    Work out each issue before applying the fix: What is wrong with /broken/app/? What is wrong with deploy.sh?

  5. Fix each issue:

    # Fix 1: Give appuser ownership of the app directory
sudo chown -R appuser:appuser /broken/app/
# Fix 2: Restore correct permissions on the directory (needs x to enter)
sudo chmod 750 /broken/app/
# Fix 3: Fix the script — needs read + execute, not just write
sudo chown appuser:appuser /broken/scripts/deploy.sh
sudo chmod 750 /broken/scripts/deploy.sh

  6. Switch back to appuser and verify everything works now:

    su - appuser
ls /broken/app/
cat /broken/app/config.txt
/broken/scripts/deploy.sh
exit

    Figure 27: 📸 System fixed — all three operations now succeed. This debugging workflow is exactly what interviewers want to see.

  7. Cleanup:

    sudo rm -rf /broken
sudo userdel -r appuser

Project 6: Multi-User Production System Setup

🎯 Objective: This is the job-level project. You are a DevOps engineer. Build a complete system from scratch where developers can deploy code, a web server can serve files, and unauthorised users cannot access anything. Every decision you make here mirrors a real production environment.

⏱️ Time: 45–60 min

💰 Cost: Free tier eligible. Install nginx (no extra charge — software only).

💰 Cost Note: This project installs nginx on the EC2 instance using yum. There is no additional AWS cost — only the EC2 instance itself is billed, which is free tier eligible on t2.micro or t3.micro. Terminate the instance after the project to avoid ongoing charges.

  1. Install nginx (the web server):

    sudo yum install -y nginx
sudo systemctl start nginx
sudo systemctl enable nginx

    Verify it is running: sudo systemctl status nginx. You should see active (running).

    Figure 28: 📸 nginx running — the green 'active (running)' status confirms the web server is ready

  2. Check what user nginx runs as — this is the system user you will configure permissions for:

    ps aux | grep nginx
grep 'user' /etc/nginx/nginx.conf

    On Amazon Linux, nginx typically runs as nginx. Note this — it is the system user you will grant access to.

  3. Create the development team:

    sudo groupadd webdevs
sudo useradd -m -s /bin/bash dev1
sudo useradd -m -s /bin/bash dev2
sudo passwd dev1
sudo passwd dev2
sudo usermod -aG webdevs dev1
sudo usermod -aG webdevs dev2
# Also add the nginx system user to webdevs so it can read files
sudo usermod -aG webdevs nginx

  4. Set up the application directory with correct ownership and SGID:

    sudo mkdir -p /var/www/app
sudo chown root:webdevs /var/www/app
sudo chmod 2775 /var/www/app
ls -ld /var/www/app

    Decode 2775: the leading 2 is SGID, 7 gives owner full access, 7 gives webdevs full access, 5 gives others read+execute (so nginx can serve files).

    Figure 29: 📸 /var/www/app directory — SGID active, webdevs has full access, nginx can read and execute

  5. Deploy a simple web page as dev1:

    su - dev1
echo "<h1>Deployed by dev1</h1>" > /var/www/app/index.html
ls -l /var/www/app/
exit

    Verify the file's group inherited webdevs automatically because of SGID.

  6. Configure nginx to serve from your app directory. Edit the nginx config:

    sudo nano /etc/nginx/conf.d/app.conf

    Add this content:

    server {
    listen 80;
    root /var/www/app;
    index index.html;
}

    Save and reload nginx:

    sudo nginx -t
sudo systemctl reload nginx

  7. Configure sudo for deploy task only — dev1 can restart nginx, nothing else:

    sudo visudo

    Add this line at the bottom:

    dev1 ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx

    Test it:

    su - dev1
sudo systemctl restart nginx
sudo cat /etc/shadow  # This should still be DENIED
exit

    Figure 30: 📸 Targeted sudo — dev1 can restart nginx but nothing else. This is least-privilege sudo in practice.

  8. Verify an outsider cannot access the app directory. Create a test user outside the group:

    sudo useradd -m outsider
su - outsider
cat /var/www/app/index.html
ls /var/www/app/
exit

    The outsider can read the files because others have read+execute (5) — this is correct for a public web server. If you wanted a private app, you would set 2770 instead of 2775.

  9. Cleanup:

    sudo userdel -r dev1
sudo userdel -r dev2
sudo userdel -r outsider
sudo groupdel webdevs
sudo rm -rf /var/www/app
sudo systemctl stop nginx
sudo yum remove -y nginx
