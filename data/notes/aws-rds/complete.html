🗄️ Introduction

Every application needs somewhere to store data. Whether it's a job portal storing resumes, an e-commerce site storing orders, or a bank storing transactions — data has to live somewhere, be protected, and be accessible fast. Managing your own database server is like owning a car: you're responsible for maintenance, oil changes, repairs, insurance — everything. AWS RDS is like switching to a taxi service: you just tell it where you want to go, and it handles everything else.

Figure 1: AWS RDS — the managed database service that takes the burden of DB administration off your hands

In this session, we cover the full AWS database ecosystem: RDS (managed relational databases), Read Replicas (scaling reads), Aurora (AWS's cloud-native engine), Redshift (data warehousing), ElastiCache (in-memory caching), and an introduction to DMS (Database Migration Service).

⚡ The Real-World Context: In this session, we build a 3-part project: a full-stack job portal on EC2 → automating resume movement to S3 → hosting the frontend on S3 with CloudFront + Route 53, while the backend talks to AWS RDS for the database layer.

🗄️ What is AWS RDS?

Before AWS RDS existed, every developer had to do the same tedious work: rent a server, SSH into it, manually install MySQL or PostgreSQL, configure it, secure it, back it up on a schedule, patch it when vulnerabilities appeared, and pray it didn't crash. That's a lot of undifferentiated heavy lifting — work that doesn't make your application better, just keeps the lights on.

AWS RDS (Relational Database Service) is a fully managed relational database service that automates database administration tasks including provisioning, patching, backups, recovery, and scaling.

Figure 2: Inside AWS RDS — automated backups, Multi-AZ standby, and managed storage, all invisible to you

Supported Database Engines

RDS is not a database itself — it's a platform that runs your chosen database engine on managed infrastructure. Think of it like an app store for database engines. You pick the one you know, and AWS hosts it for you. RDS supports six database engines: MySQL, PostgreSQL, MariaDB, Oracle, Microsoft SQL Server, and Amazon Aurora.

💡 PaaS, not IaaS: RDS is a Platform as a Service. You don't get SSH access to the underlying OS. You only interact with the database engine itself. AWS owns and manages the server, OS, and DBMS installation.

What AWS Manages For You

Here's the part that makes RDS worth it. AWS takes the following off your plate entirely:

  • Automated backups: RDS automatically takes daily snapshots of your database and captures transaction logs. The default backup retention period is 7 days, configurable up to 35 days.
  • Automated patching: OS and database engine patches are applied automatically during your defined maintenance window.
  • Storage auto-scaling: When your database storage runs low, RDS can automatically increase it without downtime.
  • High availability with Multi-AZ: RDS can create a synchronous standby replica in another Availability Zone for automatic failover.
  • Monitoring: Built-in CloudWatch metrics for CPU, storage, connections, and query performance.

✅ The Rule of Thumb: If a task is about keeping the database alive (patches, backups, failover), AWS does it. If a task is about what's inside the database (schema design, queries, indexes), that's still your job.

DB Instance Types

Just like EC2 instances, RDS uses instance types that determine the compute and memory available to your database. RDS instance classes include db.t (burstable, for dev/test), db.m (general purpose), and db.r (memory-optimized for large databases).

Storage Types

RDS uses EBS (Elastic Block Store) volumes for storage. Three types are available, each suited to different workloads:

Storage TypeBest ForIOPS

Multi-AZ Deployments

Imagine your database is in one data center and that data center loses power. Without Multi-AZ, your application goes down. With Multi-AZ, AWS automatically maintains a synchronized standby replica in a different Availability Zone.

In a Multi-AZ deployment, AWS synchronously replicates data to a standby instance. If the primary fails, RDS automatically fails over to the standby in under 60-120 seconds — no manual intervention required.

💡 Multi-AZ vs Read Replicas — The Classic Exam Trap: Multi-AZ is for availability and disaster recovery. The standby cannot serve read traffic. Read Replicas (covered next) are for performance and read scaling. Know the difference — it appears on every AWS exam.

Figure 3: Multi-AZ — your application always connects to the same endpoint; AWS changes where that endpoint points during failover

RDS Pricing Model

RDS pricing has several dimensions. Understanding them helps you design cost-efficient architectures:

  • Instance hours: You pay per hour the DB instance is running, based on instance type.
  • Storage: Per GB/month of allocated storage.
  • I/O requests: For Magnetic storage (not SSD).
  • Backup storage: Free up to the size of your provisioned database storage; charged beyond that.
  • Data transfer: Data transferred out of RDS to the internet is charged; in-region transfer to EC2 in same VPC is free.

📚 According to AWS documentation, RDS Free Tier includes 750 hours per month of db.t2.micro or db.t3.micro Single-AZ instance usage, 20 GB of SSD storage, and 20 GB of backup storage for up to 12 months. 📚 Source: AWS RDS Free Tier

📖 Read Replicas

Your app has grown. A thousand users are hitting your database every second — reading product listings, searching orders, pulling dashboards. The database is struggling. Adding more CPU to the primary database helps a little, but reads are the real bottleneck. This is where Read Replicas come in.

A Read Replica is an asynchronously replicated copy of the primary RDS instance, used to offload read traffic and improve application performance.

Figure 4: Read Replicas — writes go to primary, reads scale across multiple replicas

How Read Replicas Work

When you create a Read Replica, RDS creates a snapshot of the primary, launches it as a new instance, and then continuously applies all changes from the primary to the replica using asynchronous replication. Asynchronous means there's a tiny lag — the replica might be a few milliseconds behind the primary.

💡 Asynchronous vs Synchronous: Multi-AZ uses synchronous replication — every write must be confirmed by both primary and standby before success. Read Replicas use asynchronous — the primary confirms writes immediately, and replicas catch up shortly after. This is why Multi-AZ has zero data loss risk, while Read Replicas have replication lag.

Read Replica Limits and Features

  • You can create up to 5 Read Replicas per primary RDS instance (MySQL, MariaDB, PostgreSQL).
  • Read Replicas can be in a different AZ, or even a different AWS Region (Cross-Region Read Replicas).
  • A Read Replica can be promoted to become a standalone database — it breaks replication and becomes an independent writable instance.
  • Read Replicas of Read Replicas are possible (chaining), but replication lag increases with each level.
  • You connect to each Read Replica using its own unique endpoint.

When to Use Read Replicas

ScenarioUse Read Replica?Why
Reporting/analytics queries✅ YesHeavy reads won't slow primary
Dashboard for many users✅ YesDistribute read load
Disaster recovery❌ NoUse Multi-AZ instead
High-availability failover❌ NoUse Multi-AZ instead
Write scaling❌ NoReplicas are read-only

⚡ Exam Trap: Read Replicas require automatic backups to be enabled on the primary. You cannot create a Read Replica if backups are turned off.

☁️ Amazon Aurora

Aurora is Amazon's own database engine, purpose-built for the cloud. It didn't come from Oracle or the open-source community — AWS engineers designed it from scratch to fix the limitations of traditional database engines when running on cloud infrastructure.

Amazon Aurora is a cloud-native relational database engine that is compatible with both MySQL and PostgreSQL, offering up to 5x the performance of standard MySQL and 3x the performance of standard PostgreSQL.

Figure 5: Aurora's shared distributed storage — all instances read from and write to the same underlying storage layer

Aurora's Distributed Storage

Traditional databases like MySQL store data on a disk attached to the server. If the server dies, the disk might go with it, or failover takes time while the replacement attaches to the disk. Aurora works completely differently.

Aurora stores data across 3 Availability Zones with 6 copies of your data automatically — 2 copies per AZ. The storage layer is fully separate from the compute layer.

This means Aurora can tolerate losing up to 2 copies without affecting write availability and up to 3 copies without affecting read availability. It also means failover is near-instant — the new primary just starts reading from the same shared storage without needing to re-synchronize.

Aurora vs RDS MySQL/PostgreSQL

Aurora Read Replicas

Aurora supports up to 15 Read Replicas, compared to 5 for standard RDS. Aurora replicas share the same underlying storage, so they have near-zero replication lag.

Because all Aurora instances share the same distributed storage volume, a Read Replica doesn't need to copy data — it simply reads from the same storage. This is fundamentally different from RDS Read Replicas, which maintain separate data copies and have real replication lag.

Aurora Serverless

Aurora also offers a serverless mode, where the database capacity automatically adjusts based on application demand. You pay per second for the capacity you use, and it can scale to zero when idle.

💡 Aurora Serverless is ideal for: Applications with infrequent, unpredictable, or intermittent workloads — like a test environment, a dev database, or a multi-tenant SaaS that has very variable load.

Aurora Global Database

Aurora Global Database allows a single Aurora database to span multiple AWS Regions, with replication latency of under 1 second. This is used for disaster recovery with a very low Recovery Time Objective (RTO) and for low-latency global reads.

When to Choose Aurora

✅ Choose Aurora when: You need MySQL or PostgreSQL compatibility but want significantly better performance, faster failover, more read replicas, or automatic storage management. Aurora is the recommended choice for production workloads on AWS when performance and availability matter.

❌ Don't choose Aurora when: You're on a tight budget, running a dev/test environment, or need a database engine not supported by Aurora (Oracle, SQL Server, MariaDB).

📊 Amazon Redshift

RDS and Aurora are excellent for transactional databases — storing and retrieving individual records quickly. But what about analytics? What if you want to ask: "What were our total sales by region last year, broken down by product category and customer age group?" That query might scan billions of rows. A transactional database would crawl.

Amazon Redshift is a fully managed, petabyte-scale data warehouse designed for OLAP (Online Analytical Processing) workloads — complex queries over very large datasets.

Figure 6: Redshift's MPP architecture — one leader node coordinates many compute nodes working in parallel

OLTP vs OLAP — The Core Distinction

This distinction is absolutely critical for the exam. Many candidates confuse RDS and Redshift because both are "databases."

AspectOLTP (RDS/Aurora)OLAP (Redshift)
Full formOnline Transaction ProcessingOnline Analytical Processing
Query typeInsert, update, delete, simple readsComplex aggregations, joins, analytics
Data volumeGigabytes to terabytesTerabytes to petabytes
UsersApplication users (thousands)Analysts, BI tools (dozens)
Speed neededMilliseconds per transactionSeconds to minutes per query
ExampleProcess a bank transactionAnalyze 5 years of transactions

MPP Architecture

Redshift uses Massively Parallel Processing (MPP) — queries are automatically broken into smaller pieces and distributed across all compute nodes simultaneously.

Think of it like a research team. Instead of one person reading 10,000 pages of reports, you assign 100 researchers, each reading 100 pages. They work in parallel, then report findings to the lead researcher. That's MPP. Redshift's leader node receives your SQL query, breaks it up, sends slices to each compute node, collects results, and returns the final answer.

Columnar Storage

Traditional row-based databases (like MySQL) store entire rows together. If you want to sum one column across 1 billion rows, you have to read all 1 billion full rows — including all the columns you don't need.

Redshift uses columnar storage — each column is stored separately on disk, so analytics queries only read the specific columns needed, dramatically reducing I/O.

💡 Analogy: Row-based storage is like a filing cabinet where each drawer has one person's complete file. Columnar storage is like having separate drawers for each type of information — one drawer with all "ages", one with all "salaries". If you want the average salary, you only open the salary drawer.

Redshift Spectrum

Redshift Spectrum allows you to run SQL queries directly against data stored in Amazon S3 without loading it into Redshift first. This is powerful for querying historical data cheaply — keep cold data in S3, query it with Spectrum, and only load hot data into Redshift proper.

Redshift Use Cases

  • Business Intelligence (BI): Connecting Tableau, QuickSight, Power BI to query massive datasets
  • Data lakes: Querying structured data on S3 via Spectrum
  • Financial reporting: Aggregating years of transaction data for regulatory reports
  • Log analysis: Analyzing application and access logs at scale

⚡ Redshift is NOT a replacement for RDS. Use RDS/Aurora for your application's live database (reads/writes from your app). Use Redshift for analytics and reporting on historical or aggregated data. They serve completely different purposes.

Loading Data Into Redshift

The recommended way to load large amounts of data into Redshift is using the COPY command from S3. It loads data in parallel across all compute nodes, making it much faster than row-by-row INSERT statements. Redshift also integrates with AWS Glue for ETL (Extract, Transform, Load) pipelines.

Redshift Pricing

Redshift offers two pricing models: On-Demand (pay per hour per node) and Reserved Instances (1 or 3-year commitment for up to 75% savings). Redshift Serverless is also available, where you pay per RPU (Redshift Processing Unit) second consumed.

⚡ Amazon ElastiCache

Imagine you run a popular news website. Every visitor who loads the homepage triggers a database query: "Get the latest 10 articles with their thumbnails and author names." That same query is run thousands of times per minute, and the answer barely changes. Why go to the database for the same data over and over?

This is exactly the problem ElastiCache solves. Instead of hitting the database, you store the query result in ultra-fast RAM. The next request gets the answer in microseconds instead of milliseconds.

Amazon ElastiCache is a fully managed, in-memory caching service that stores frequently accessed data in RAM to reduce database load and dramatically speed up application response times.

Figure 7: Cache hit vs cache miss — when data is in cache, the database is bypassed entirely

How ElastiCache Works

The logic is simple and elegant:

  1. Application requests data (e.g., "Get user profile for user #12345")
  2. ElastiCache is checked first — cache hit? Return data immediately from RAM. Done.
  3. If cache miss (data not in cache): Fetch from the database (RDS/Aurora)
  4. Store the result in ElastiCache for next time
  5. Return the data to the application

Over time, frequently requested data lives permanently in cache, and the database handles only new or infrequent queries.

Redis vs Memcached

ElastiCache supports two engines: Redis and Memcached. Understanding the difference is an exam staple:

FeatureRedisMemcached
Data structuresStrings, lists, sets, sorted sets, hashes, bitmapsStrings only
Persistence✅ Yes — can persist to disk❌ No — memory only
Backup/Restore✅ Supported❌ Not supported
Replication✅ Primary/Replica support❌ No replication
Multi-AZ✅ Supported❌ Not supported
Pub/Sub messaging✅ Supported❌ Not supported
ComplexityMore features, more configurationSimple and fast
Use whenNeed persistence, complex data, HASimple caching, horizontal scaling

⚡ Professor's Recommendation: In practice, use Redis. It has far more features — backup, replication, complex data types, pub/sub — and is the industry standard. Memcached is simpler but lacks persistence and replication, making it unsuitable for most production scenarios.

Figure 8: Redis vs Memcached — Redis wins on features; Memcached wins only on pure simplicity

ElastiCache Use Cases

  • Session management: Store user sessions in Redis instead of a database — fast reads, automatic expiry
  • Database query caching: Cache results of expensive or frequent queries
  • Leaderboards: Redis sorted sets are perfect for real-time leaderboards (gaming, rankings)
  • Rate limiting: Track API call counts per user per second in Redis
  • Real-time analytics: Count events, track metrics in memory before writing to permanent storage

TTL and Cache Invalidation

One important concept: cached data becomes stale if the underlying database changes. You manage this with TTL (Time To Live) — a setting that automatically expires cached entries after a defined time period.

💡 Cache invalidation is one of the hardest problems in computer science. You need to decide: How long can stale data be shown? For product prices (show max 5 min stale), that's different from user profile pictures (show max 24 hours stale). Set TTL based on how much "freshness" your use case requires.

ElastiCache Pricing

ElastiCache is priced per node hour based on node type and size. Redis replication groups are priced per node. There's no Free Tier for ElastiCache, so be mindful of running cache nodes in your personal AWS account.

🔄 AWS Database Migration Service (DMS)

You have an application running on an on-premises Oracle database. You want to move to Aurora PostgreSQL on AWS. How do you get the data there without weeks of downtime? That's where DMS comes in.

AWS Database Migration Service (DMS) helps you migrate databases to AWS quickly and securely, with the source database remaining fully operational during migration, minimizing downtime.

Figure 9: DMS — a replication instance sits between source and target, continuously syncing data

Migration Types

Homogeneous migration is when source and target databases use the same engine (e.g., MySQL → MySQL, Oracle → Oracle). Heterogeneous migration is when engines differ (e.g., Oracle → Aurora PostgreSQL, SQL Server → MySQL).

Heterogeneous migrations require an additional step: schema conversion. AWS provides the Schema Conversion Tool (SCT) to automatically convert the database schema and most of the stored procedures from the source engine format to the target.

The Three Steps of Redshift Data Loading (mentioned in class)

The professor also covered Redshift data loading workflow:

  1. Create a cluster: Set up your Redshift cluster with appropriate node type and count
  2. Data dump / load: Use the COPY command to load data from S3 (or other sources) into Redshift in parallel
  3. Query and analyze: Connect BI tools (QuickSight, Tableau) and run analytical SQL queries

💡 DMS creates an EC2 replication instance: When you create a DMS task, AWS launches a managed EC2 instance (the replication instance) that handles reading from the source, transforming, and writing to the target. You don't manage this instance directly.

DMS Use Cases

  • Migrating on-premises databases to AWS RDS or Aurora
  • Moving between RDS engine types (Oracle → PostgreSQL)
  • Continuous replication for ongoing synchronization between databases
  • Database consolidation (multiple databases into one)

🏗️ Full-Stack Architecture with RDS

The professor walked through a real architecture that ties together EC2, S3, RDS, CloudFront, and Route 53 into a production-grade deployment. This is how real companies build their applications on AWS.

Figure 10: Production-grade full-stack architecture — frontend on S3/CloudFront, backend on EC2, database on RDS, all in a VPC

The Three Layers

The architecture follows a classic three-tier pattern:

  • Presentation Layer (Frontend): A static website (HTML/CSS/JS) hosted on S3 with static website hosting enabled. CloudFront sits in front for low-latency global delivery. Route 53 handles the custom domain with an ACM SSL certificate for HTTPS.
  • Application Layer (Backend): A Node.js/Python/Java application running on EC2 (Ubuntu). This is your business logic — validating form submissions, processing resume uploads, querying the database. It requires a server, so it stays on EC2.
  • Data Layer (Database): AWS RDS (MySQL/PostgreSQL). The application connects to RDS using the endpoint URL, database name, username, and password. RDS and EC2 should be in the same VPC so they can communicate privately without going over the internet.

VPC Placement — Why It Matters

EC2 and RDS placed in the same VPC can communicate using private IP addresses — no internet gateway needed, no data transfer charges, lower latency, and better security.

✅ Best Practice: Place your EC2 instances in public subnets (so they can receive traffic from CloudFront or users) and your RDS instances in private subnets (so they are never directly accessible from the internet). Only EC2 can talk to RDS from within the VPC.

Cron Job for Resume Management

As resumes accumulate on the EC2 instance's local filesystem, disk space fills up. The solution: a scheduled cron job that moves uploaded resumes from EC2's local storage to S3, then deletes the local copies.

💡 Cron Job Pattern: This is a fundamental DevOps pattern — use scheduled jobs to automate housekeeping tasks. In Linux, cron jobs are defined in the crontab file. A job like 0 * * * * /scripts/move-resumes.sh runs every hour and moves new resumes to S3, freeing EC2 disk space automatically.

📝 Overall Summary

  • AWS RDS: Fully managed relational database service supporting 6 engines (MySQL, PostgreSQL, MariaDB, Oracle, SQL Server, Aurora). AWS handles backups, patches, failover, and scaling.
  • Multi-AZ: Synchronous standby replica in another AZ for high availability and automatic failover. Used for disaster recovery, NOT for read scaling.
  • Read Replicas: Asynchronously replicated copies of the primary. Up to 5 for RDS (MySQL/PostgreSQL). Used for read scaling, NOT for HA. Can be promoted to standalone DB.
  • Aurora: AWS's cloud-native MySQL/PostgreSQL-compatible engine. 3–5× faster, up to 15 read replicas, storage spread across 3 AZs with 6 copies, failover under 30 seconds. More expensive but worth it for production.
  • Redshift: Managed data warehouse for OLAP workloads. Uses MPP (Massively Parallel Processing) and columnar storage. Designed for terabyte to petabyte analytics, not for OLTP applications.
  • ElastiCache: Managed in-memory caching with Redis or Memcached engines. Reduces database load, speeds up reads. Redis is preferred — it supports persistence, backup, replication, and complex data types.
  • DMS: Database Migration Service for moving databases to AWS. Supports homogeneous (same engine) and heterogeneous (different engine, requires SCT) migrations with minimal downtime.
  • Full-Stack Architecture: Frontend on S3 + CloudFront, backend on EC2, database on RDS — all within a VPC. Use private subnets for RDS, public subnets for EC2.
  • OLTP vs OLAP: RDS/Aurora = OLTP (live app transactions). Redshift = OLAP (analytical queries on large historical datasets). Never use one where the other is appropriate.
  • Cache hit vs miss: ElastiCache checks cache first. Hit = return from RAM instantly. Miss = fetch from DB, store in cache, return. Over time, hot data stays in cache permanently.

🎯 Objective: Upgrade the Level 1 app into a proper REST API. Add structured routes, environment variables, database connection pooling, and real error handling — the way production backends are actually written.

⏱️ Time: 45–60 minutes (builds on Level 1 EC2 + RDS setup)

💰 Cost: Free Tier eligible (same EC2 + RDS from Level 1)

✅ What You Will Learn: REST API structure, the difference between a demo and a real backend, why .env files matter for security, and how to handle errors gracefully so your app doesn't crash on bad input.

  1. Create a .env file on the EC2 instance to store all sensitive config outside of code:

    nano .env

  queueLimit: 0

// GET all applications (with pagination)
app.get('/applications', async (req, res) => {
  const limit = parseInt(req.query.limit) || 10;

⚡ Level 3 — High-Traffic Scaling (Read Replicas + ElastiCache Redis)

🎯 Objective: Add a Read Replica to separate read and write traffic, then layer in ElastiCache Redis to cache frequent query results. This is how real apps handle traffic spikes without upgrading their database instance.

⏱️ Time: 60–75 minutes

💰 Cost: Read Replica ~$0.017/hr (not Free Tier). ElastiCache cache.t3.micro ~$0.017/hr. Delete both when done.

💰 Cost Warning: Read Replicas and ElastiCache nodes are NOT Free Tier. Each costs approximately $0.017/hour. Complete this project in one session and delete resources immediately.

✅ What You Will Learn: How to route reads vs writes to different DB endpoints, how Redis cache reduces database load, and the cache hit/miss flow in a real application.

  1. Create a Read Replica of your existing RDS MySQL instance. In the AWS console: RDS → select your DB → Actions → Create read replica. Use the same region, db.t3.micro.

    Figure 📸 Screenshot: Create Read Replica — same region, db.t3.micro, replica of primary DB

  2. Once the replica is available (status: Available), note its endpoint. Update your .env to include both endpoints:

    DB_HOST=mydb-primary.abc123.us-east-1.rds.amazonaws.com
DB_READ_HOST=mydb-replica.def456.us-east-1.rds.amazonaws.com
DB_USER=admin
DB_PASSWORD=yourpassword
DB_NAME=jobportal

  3. Update server.js to use two connection pools — write pool points to primary, read pool points to replica:

    const writePool = mysql.createPool({
  host: process.env.DB_HOST,      // Primary — all writes
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  connectionLimit: 10
});

const readPool = mysql.createPool({
  host: process.env.DB_READ_HOST, // Replica — all reads
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  database: process.env.DB_NAME,
  connectionLimit: 10
});

// GET uses readPool
app.get('/applications', async (req, res) => {
  const [rows] = await readPool.query('SELECT * FROM applications ORDER BY applied_at DESC LIMIT 10');
  res.json({ success: true, data: rows });
});

// POST uses writePool
app.post('/applications', async (req, res) => {
  const { name, email, position } = req.body;
  const [result] = await writePool.query(
    'INSERT INTO applications (name, email, position) VALUES (?, ?, ?)', [name, email, position]
  );
  res.status(201).json({ success: true, id: result.insertId });
});

    Figure 📸 Screenshot: Two pools in code — writePool to primary, readPool to replica

  4. Create an ElastiCache Redis cluster. Navigate to ElastiCache → Create cluster → Redis OSS → Cluster Mode off → cache.t3.micro, 1 node. Place it in the same VPC as your EC2.

    Figure 📸 Screenshot: ElastiCache cluster — Redis, cache.t3.micro, same VPC as EC2

  5. Add Redis inbound rule: ElastiCache security group must allow port 6379 from the EC2 security group. Install Redis client on EC2:

    npm install redis

  6. Add cache-aside logic to the GET route — check Redis first, fall back to DB on miss:

    const redis = require('redis');
const redisClient = redis.createClient({
  socket: { host: process.env.REDIS_HOST, port: 6379 }
});
await redisClient.connect();

app.get('/applications', async (req, res) => {
  const cacheKey = 'applications:recent';
  try {
    // Check cache first
    const cached = await redisClient.get(cacheKey);
    if (cached) {
      return res.json({ success: true, source: 'cache', data: JSON.parse(cached) });
    }
    // Cache miss — query read replica
    const [rows] = await readPool.query(
      'SELECT * FROM applications ORDER BY applied_at DESC LIMIT 10'
    );
    // Store in cache for 60 seconds (TTL)
    await redisClient.setEx(cacheKey, 60, JSON.stringify(rows));
    res.json({ success: true, source: 'database', data: rows });
  } catch (err) {
    res.status(500).json({ success: false, error: err.message });
  }
});

  7. Test cache behavior — call GET twice. First call: "source": "database". Second call within 60 seconds: "source": "cache".

    Figure 📸 Screenshot: Cache miss (first call) vs cache hit (second call) — same data, different source

✅ What You Just Built: A horizontally scaled read path. Writes go to the primary. Reads go to the replica. Repeated reads of hot data don't touch the database at all — they come from Redis RAM. This is how high-traffic apps serve millions of requests without upgrading their database instance.

💡 What to notice: When you POST a new application, the Redis cache still holds the old list for up to 60 seconds. This is cache staleness in action. In production you'd add cache invalidation — explicitly deleting the cache key on every write so the next read fetches fresh data.

🧹 Cleanup: Delete the ElastiCache cluster (ElastiCache → Clusters → Delete). Delete the Read Replica (RDS → select replica → Actions → Delete). Both continue charging until deleted.

🧠 Level 4 — Secure Multi-Tier VPC Architecture

🎯 Objective: Rebuild the architecture properly — public subnet for EC2, private subnet for RDS, locked security groups, IAM roles instead of access keys. This is what "production-ready" actually means from a security perspective.

⏱️ Time: 60–90 minutes

💰 Cost: Free Tier eligible (same instance types, just restructured)

✅ What You Will Learn: Why network isolation matters, how to use IAM roles instead of storing credentials, how to properly lock down security groups, and how to explain your architecture's security posture in an interview.

  1. Create a custom VPC with CIDR 10.0.0.0/16. Navigate to VPC → Create VPC.

    Figure 📸 Screenshot: Create VPC — 10.0.0.0/16 CIDR block

  2. Create two subnets inside the VPC:

    • Public subnet: 10.0.1.0/24 — this is where EC2 will live
    • Private subnet: 10.0.2.0/24 — this is where RDS will live

    Attach an Internet Gateway to the VPC and add a route 0.0.0.0/0 → IGW in the public subnet's route table only. The private subnet has no IGW route — RDS cannot reach the internet.

    Figure 📸 Screenshot: Two subnets — public for EC2, private for RDS

  3. Create two security groups:

    • sg-ec2: Inbound: port 22 from your IP only, port 80 from 0.0.0.0/0, port 3000 from 0.0.0.0/0. Outbound: all.
    • sg-rds: Inbound: port 3306 from sg-ec2 only (source = security group ID). Outbound: none.

    Figure 📸 Screenshot: RDS security group — only EC2 security group can reach port 3306

  4. Create an RDS Subnet Group using the private subnet. Navigate to RDS → Subnet groups → Create DB subnet group. Add the private subnet.

  5. Launch a new RDS MySQL instance inside the private subnet with Public Access: No. Attach sg-rds.

  6. Create an IAM role for EC2 with the AmazonS3FullAccess policy (for resume uploads). Attach it to your EC2 instance via Actions → Security → Modify IAM role. No access keys stored anywhere — the role provides temporary credentials automatically.

    Figure 📸 Screenshot: EC2 IAM role — attached role provides S3 access without storing any keys

  7. Launch EC2 in the public subnet, attach sg-ec2. SSH in and verify it can connect to RDS (in private subnet) using the endpoint:

    mysql -h <rds-private-endpoint> -u admin -p

    This should succeed — EC2 (sg-ec2) is allowed through sg-rds on port 3306. Now try connecting to the RDS endpoint from your local machine — it should time out (no public access, private subnet).

✅ What You Just Built: A properly isolated two-tier network. The database is unreachable from the internet by design — only your application server can talk to it, and only on port 3306, and only because it belongs to a specific security group. This is what "secure by design" means. IAM roles eliminate the most common credential leak vectors.

⚡ Interview Answer Unlocked: "Where do you put RDS — public or private subnet, and why?" → Private subnet. No internet route, no public IP. Only the application server in the same VPC can reach it, controlled by security group rules. If the EC2 is compromised, the attacker still can't reach the DB from outside the VPC.

✅ What You Will Learn: The practical difference between OLTP and OLAP, how to move data from RDS to Redshift via S3, how to run columnar analytical queries, and why Redshift is 10-100× faster than RDS for these workloads.

  1. Export application data from RDS to S3 as CSV (this becomes the Redshift load source):

    # From EC2, export applications table as CSV
mysql -h $DB_HOST -u $DB_USER -p$DB_PASSWORD jobportal \
  -e "SELECT id, name, email, position, applied_at FROM applications" \
  | sed 's/\t/,/g' > /tmp/applications.csv

# Upload to S3
aws s3 cp /tmp/applications.csv s3://jobportal-ops-yourname/redshift-load/applications.csv

    Figure 📸 Screenshot: RDS data exported as CSV and uploaded to S3 for Redshift loading

  2. Create a Redshift cluster (or Serverless workgroup). Navigate to Amazon Redshift → Clusters → Create cluster. Choose dc2.large (1 node), create database analytics.

    Figure 📸 Screenshot: Redshift cluster — dc2.large, 1 node, analytics database

  3. Connect to Redshift using the Query Editor v2 (in the console) and create the analytics table:

    CREATE TABLE applications_analytics (
  id INTEGER,
  name VARCHAR(100),
  email VARCHAR(100),
  position VARCHAR(100),
  applied_date DATE,
  applied_week INTEGER,
  applied_month INTEGER,
  applied_year INTEGER
)
DISTKEY(position)
SORTKEY(applied_date);

    💡 DISTKEY and SORTKEY: These are Redshift-specific optimizations. DISTKEY(position) distributes rows with the same position to the same compute node — queries filtering by position run on less data. SORTKEY(applied_date) stores rows physically sorted by date — range queries on date skip huge chunks of data. You don't need these in RDS; they only matter in columnar analytics engines.

  4. Load data from S3 into Redshift using the COPY command (much faster than INSERT):

    COPY applications_analytics (id, name, email, position, applied_date)
FROM 's3://jobportal-ops-yourname/redshift-load/applications.csv'
IAM_ROLE 'arn:aws:iam::YOUR_ACCOUNT_ID:role/RedshiftS3ReadRole'
FORMAT AS CSV
IGNOREHEADER 1
DATEFORMAT 'YYYY-MM-DD';

  5. Run analytical queries that would be slow on RDS but fast on Redshift:

    -- Applications per day (last 30 days)
SELECT applied_date, COUNT(*) AS applications
FROM applications_analytics
WHERE applied_date >= CURRENT_DATE - 30
GROUP BY applied_date
ORDER BY applied_date;

-- Top 5 most applied-for positions
SELECT position, COUNT(*) AS total_applications
FROM applications_analytics
GROUP BY position
ORDER BY total_applications DESC
LIMIT 5;

-- Weekly application trend
SELECT applied_week, applied_year, COUNT(*) AS weekly_total
FROM applications_analytics
GROUP BY applied_week, applied_year
ORDER BY applied_year, applied_week;

✅ What You Just Built: A real data pipeline. Data originates in RDS (OLTP — transactional), gets exported to S3, loaded into Redshift (OLAP — analytical), and queried for business insights. This RDS → S3 → Redshift pattern is used by real data engineering teams everywhere.
