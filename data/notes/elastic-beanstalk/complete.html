🌱 Introduction

Imagine you have built a brilliant web application. You've written the code, tested it locally, and now you want to put it on the internet so people can actually use it. But wait — suddenly there's a mountain of infrastructure to manage: you need a server (EC2), a load balancer to handle traffic, auto-scaling rules, a database, security configurations, monitoring dashboards... it feels like you need to be a DevOps expert just to deploy one app.

That's exactly the problem AWS Elastic Beanstalk was built to solve.

Figure 1: Elastic Beanstalk — you bring the code, AWS handles the infrastructure

AWS Elastic Beanstalk is a Platform as a Service (PaaS) that automatically handles the deployment, capacity provisioning, load balancing, auto-scaling, and health monitoring of your application. You simply upload your application code and Elastic Beanstalk takes care of the rest — all the underlying AWS resources are provisioned and managed on your behalf.

⚡ Key Insight: Elastic Beanstalk is not a new AWS service that replaces EC2 or RDS. It is an orchestration layer — it uses existing AWS services (EC2, RDS, ELB, Auto Scaling, CloudWatch) but creates and manages them automatically for you.

The professor demonstrated this live in class: the instructor navigated to Elastic Beanstalk, created an application, uploaded code, and within minutes a fully working website with its own EC2 instance, public URL, and monitoring was live — without manually configuring a single EC2 instance or touching a VPC setting directly.

🤔 What Is Elastic Beanstalk?

Think of Elastic Beanstalk like a smart apartment building manager. You are the tenant (the developer). You move in with your belongings (your application code). The building manager (Elastic Beanstalk) handles electricity, plumbing, security, maintenance, and everything else. You just live there (run your app). If you need more space because you have guests (traffic spikes), the manager handles that too — automatically.

Figure 2: The "building manager" analogy — you focus on your app, Beanstalk manages the building

Elastic Beanstalk is part of the Compute category of AWS services and supports multiple programming languages and platforms.

Supported platforms include:

  • Java (Tomcat)
  • Python (with Django, Flask)
  • .NET (on Windows Server)
  • Node.js
  • PHP
  • Ruby
  • Go
  • Docker (containerized apps)
  • Multi-container Docker (ECS-based)

💡 Note: During the session, the instructor used a Java-based web application on Amazon Linux 2 as the platform. The steps are the same regardless of which platform you choose — only the runtime environment differs.

💡 Why Use Elastic Beanstalk?

Before Elastic Beanstalk, a developer who wanted to deploy an app on AWS had to manually do all of the following:

  1. Launch an EC2 instance with the right AMI and instance type
  2. Install the runtime (Java, Node.js, etc.) manually
  3. Configure a Security Group to allow HTTP/HTTPS traffic
  4. Set up an Elastic Load Balancer if needed
  5. Configure Auto Scaling policies
  6. Connect an RDS database and pass credentials securely
  7. Set up CloudWatch alarms for monitoring
  8. Configure S3 for log storage

That is a huge amount of work before your application is even running. And if you need a second environment (say, for testing), you repeat all of it.

⚡ With Elastic Beanstalk, all infrastructure provisioning is automated — you only need to upload your code and choose basic configuration options. AWS handles the rest.

Figure 3: Manual deployment vs Elastic Beanstalk — same result, drastically fewer steps

Key reasons to use Elastic Beanstalk:

  • ✅ Speed: Go from code to live application in minutes
  • ✅ Simplicity: No infrastructure expertise required
  • ✅ Full control retained: You can still customize every resource Beanstalk creates
  • ✅ Multiple environments: Create Dev, Test, and Production environments in the same application
  • ✅ Free to use: You only pay for the underlying AWS resources (EC2, RDS, etc.) — Elastic Beanstalk itself has no additional charge

✅ Elastic Beanstalk is free — you pay only for the AWS resources it creates, such as EC2 instances, RDS databases, and load balancers.

🧱 Core Concepts: Applications and Environments

To work effectively with Elastic Beanstalk, you need to understand two key building blocks: Applications and Environments.

Figure 4: Application → Environments hierarchy in Elastic Beanstalk

Application

An Application in Elastic Beanstalk is a logical container — it holds all the versions of your code and all the environments that run those versions. Think of it like a GitHub repository: the repository itself just holds things — the actual running code lives in environments.

In the class demo, the instructor created an application and then created environments inside it.

Environment

An Environment is the actual running instance of your application — it contains the EC2 instances, load balancer, auto scaling group, and all other AWS resources needed to run your app.

One application can have multiple environments running simultaneously. For example:

Environment NamePurposeWho Uses It
MyApp-DevActive developmentDevelopment team
MyApp-TestQA testingTesting team
MyApp-ProdLive for usersEnd users

💡 Real-world use: During the session, the professor explained that after creating the initial environment (Environment 1), you can create another environment in the same application for the testing team — they test against that environment without ever touching production.

Environment Types

Elastic Beanstalk supports two environment types: Web Server Environment and Worker Environment.

TypePurposeTypical Use Case
Web ServerHandles HTTP/HTTPS requests from usersWebsites, REST APIs, web applications
WorkerProcesses background tasks from an SQS queueImage processing, sending emails, data pipelines

The class demo used a Web Server environment — a single instance (free tier eligible) running the pet caretaker web application.

⚙️ How Elastic Beanstalk Works Internally

When you create an Elastic Beanstalk environment, you are essentially giving AWS a detailed set of instructions. Behind the scenes, Elastic Beanstalk uses AWS CloudFormation to provision all the resources — it creates a CloudFormation stack under the hood, and every resource in that stack is what your environment consists of.

Figure 5: Inside Elastic Beanstalk — all the AWS resources it creates automatically

Here is what happens step by step when you create an environment:

  1. You choose a platform — e.g., Java on Amazon Linux 2. Beanstalk picks the right AMI.
  2. You upload your code — as a ZIP or WAR file. Beanstalk stores this in S3 automatically.
  3. Beanstalk provisions resources — it calls CloudFormation to create: EC2 instance(s), security group, elastic IP (if needed), and routing rules.
  4. Your code is deployed — Beanstalk installs the runtime, copies your code, and starts the application on the EC2 instance.
  5. Health monitoring begins — CloudWatch metrics are enabled (by default, every 5 minutes). Beanstalk reports environment health as Green, Yellow, Red, or Grey.
  6. A domain is assigned — a public URL like my-app.us-east-1.elasticbeanstalk.com is generated and you can access the app immediately.

⚡ From the session: The professor showed how the Events tab in Elastic Beanstalk tracks every step in real time — you can see "Creating environment", "Added instance to environment", "Deployment completed successfully" — all happening automatically without any manual action.

The environment's health status transitions through Pending → Launching → Updating → Ready states during creation, and then shows Ok (Green) once everything is healthy.

🚀 Creating an Application and Environment (Step-by-Step)

The professor walked through the entire creation process live. Here is the exact sequence:

Step 1 — Navigate to Elastic Beanstalk

  1. Log in to the AWS Management Console
  2. Search for Elastic Beanstalk in the top search bar
  3. Click Create Application

Step 2 — Configure the Application and Environment

Elastic Beanstalk organizes setup into numbered steps:

  1. Step 1 — Configure environment:

    • Choose environment tier: Web server environment
    • Give your application a name
    • Choose a Platform — e.g., Java on Amazon Linux 2
    • Upload your code: choose Local file and upload your ZIP/WAR file
    • Instance type: choose Single instance (Free tier eligible)

  2. Step 2 — Configure service access:

    • Elastic Beanstalk needs permissions to create resources on your behalf
    • Select an existing IAM role or create a new one

  3. Step 3 — Set up networking, database, and tags:

    • Choose your VPC (use Default VPC)
    • Enable Public IP address so the app is accessible from the internet
    • Choose a Subnet and Availability Zone
    • If your app needs a database, configure Amazon RDS here — Beanstalk will create and attach it automatically

  4. Step 4 — Configure instance traffic and scaling:

    • Root volume type: General Purpose SSD (gp2), minimum 10 GB
    • Auto Scaling: choose between Single instance (no scaling) or Load balanced (with auto scaling)
    • Security Group: use the default security group

  5. Step 5 — Configure updates, monitoring, and logging:

    • CloudWatch monitoring: default is every 5 minutes
    • Log streaming: can store logs in S3 (optional)
    • Email notifications: can set up SNS alerts (optional)

  6. Step 6 — Review and create:

    • Review all settings
    • Click Submit — Elastic Beanstalk begins creating the environment

💡 Important from the session: Elastic Beanstalk said the minimum root volume should be 10 GB (the instructor initially entered 8 GB and the system required upgrading). Always use at least 10 GB for the EBS root volume.

Step 3 — Monitor the Creation Events

After clicking Submit, navigate to the Events tab. You will see a real-time log of everything Beanstalk is doing. Read the events from bottom (oldest) to top (newest). Key events to watch for:

  • Environment creation started
  • Created security group with name: ...
  • Created Elastic IP address
  • Added 1 instance(s) to your environment
  • Waiting for EC2 instance to launch
  • Application deployment completed

Once you see Environment health has transitioned to Ok, your application is live.

Step 4 — Access Your Application

Elastic Beanstalk generates a unique domain name for your environment. You can find it on the environment's overview page. Copy the URL and open it in any browser — your application should be live and accessible.

In the session demo, the students accessed a pet caretaker web application — they could view owners, add new owners, and see the database working. This entire app was deployed by Beanstalk without the instructor manually launching a single EC2 instance or configuring RDS.

🔁 Multiple Environments in One Application

One of Elastic Beanstalk's most powerful features for teams is the ability to run multiple environments inside a single application. The professor explained this clearly with an example:

"You can create Environment 1 for development. Environment 2 for testing. Environment 3 for production. All inside the same application. Each environment is independent — it has its own EC2, its own URL, its own configuration."

Figure 7: Multiple environments in one application — each environment is fully independent

Here is a typical real-world multi-environment workflow:

  1. Development team deploys to MyApp-Dev (single instance, low cost)
  2. Features are tested against MyApp-Test by the QA team (separate instance, no risk to dev)
  3. Once approved, code is promoted to MyApp-Prod (load balanced, production-grade)
  4. If something breaks in prod, you can instantly swap back using environment swap (blue/green deployment)

⚡ Elastic Beanstalk supports Blue/Green deployment — you can swap the CNAME URLs of two environments with zero downtime, allowing safe production releases.

🔄 Deploying Application Updates

Once your application is running, you will eventually need to update it — fix bugs, add features, change configurations. Elastic Beanstalk makes this simple.

Deployment Methods

Elastic Beanstalk supports multiple deployment policies that control how and when traffic is shifted during updates.

Figure 8: Deployment strategies — trade-off between speed, cost, and downtime

StrategyDowntime?CostRollback SpeedBest For

Rolling❌ No downtimeNo extraManual re-deployNon-critical prod

To deploy an update, simply go to your environment in the Elastic Beanstalk console, click Upload and deploy, and upload your new code. Beanstalk handles the rest using your chosen deployment policy.

📊 Monitoring and Health

Elastic Beanstalk provides built-in monitoring so you can see how your application is performing without setting up anything manually. The professor mentioned that CloudWatch monitoring is enabled by default every 5 minutes.

Health Status Colors

Elastic Beanstalk uses a color-coded health system to indicate the state of your environment at a glance.

ColorStatusMeaning
🟢 Green (Ok)HealthyAll resources are functioning correctly
🟡 Yellow (Warning)DegradedSome health checks failing; investigate
🔴 Red (Degraded)SevereApplication is unavailable or critical errors
⚫ Grey (No data)Pending / UnknownEnvironment is launching or health data not yet available

💡 From the session: When the professor created the environment, the health showed as Pending (grey) for several minutes while EC2 launched and the application deployed. Once the deployment completed, it turned Green (Ok). Students who opened the URL during the Pending phase saw no website yet — which is expected.

What Is Monitored

Elastic Beanstalk automatically monitors and displays:

  • CPU Utilization — how busy your EC2 instance is
  • Request Count — number of HTTP requests received
  • Latency — response time of your application
  • HTTP 5xx errors — server-side errors (your code crashing)
  • HTTP 4xx errors — client-side errors (bad requests)
  • Instance health — EC2 status checks

All of these metrics are pulled from CloudWatch and displayed on the Elastic Beanstalk Monitoring tab. You can also set up CloudWatch Alarms to notify you (via SNS email) when a metric crosses a threshold.

⚖️ Elastic Beanstalk vs Alternatives

Elastic Beanstalk is not the only way to deploy applications on AWS. Understanding when to use it versus alternatives is critical for both real-world use and exam questions.

⚡ Exam Tip: Choose Elastic Beanstalk when the question mentions "developers who want to deploy without managing infrastructure" and the app is a traditional web application. Choose Lambda for event-driven or short-lived tasks. Choose ECS/EKS for container workloads.

🔧 Elastic Beanstalk and CloudFormation

When Elastic Beanstalk creates an environment, it secretly uses AWS CloudFormation behind the scenes. CloudFormation is AWS's infrastructure-as-code service — it takes a template (a list of resources and configurations) and creates all the resources defined in that template.

You can actually see this in the AWS Console: navigate to CloudFormation and you will find a stack named something like awseb-e-XXXXXXXXXX-stack. That stack contains all the EC2 instances, security groups, and other resources for your Beanstalk environment.

💡 Important: Do NOT manually delete CloudFormation stacks created by Elastic Beanstalk. Always use the Elastic Beanstalk console to terminate environments — this ensures proper cleanup in the right order.

This also means that Elastic Beanstalk environments are 100% reproducible. You can export the environment configuration and recreate the exact same setup in a different region or account.

💰 Pricing and Free Tier

Elastic Beanstalk itself has no additional charge — you only pay for the underlying AWS resources it creates.

Figure 10: Elastic Beanstalk pricing — the service is free, you pay for underlying resources

Here is what you will pay for in a typical free-tier-eligible setup:

  • EC2 (t2.micro or t3.micro): Free tier — 750 hours/month for 12 months
  • EBS Storage (10 GB gp2): Free tier — 30 GB/month for 12 months
  • RDS (db.t2.micro, 20 GB): Free tier — 750 hours/month for 12 months
  • S3: Free tier — 5 GB standard storage
  • Data transfer: First 1 GB outbound free, then ~$0.09/GB

❌ Not Free Tier: An Elastic Load Balancer is charged at approximately $0.008 per hour (~$5.76/month). If you choose the Load Balanced environment type, charges begin immediately. Stick to Single Instance for free tier.

🎓 Exam Tips and Key Facts

Elastic Beanstalk is a popular topic in the AWS Cloud Practitioner and Solutions Architect exams. Here are the most commonly tested facts:

  • Elastic Beanstalk is a PaaS (Platform as a Service) — you manage the application, AWS manages the platform.
  • Elastic Beanstalk is free to use — you only pay for the resources it creates (EC2, RDS, etc.).
  • Supported languages: Java, Python, .NET, Node.js, PHP, Ruby, Go, Docker
  • An Application is a logical container; an Environment is the actual running deployment.
  • One application can have multiple environments (Dev, Test, Prod)
  • Elastic Beanstalk uses CloudFormation internally to provision all resources.
  • Deployment strategies: All at once, Rolling, Rolling with additional batch, Immutable, Blue/Green
  • Health colors: Green = Ok, Yellow = Warning, Red = Degraded, Grey = No data
  • CloudWatch metrics are enabled by default every 5 minutes for Elastic Beanstalk environments.
  • Do NOT delete the CloudFormation stack manually — always terminate through Beanstalk console
  • S3 buckets are NOT auto-deleted when you terminate an environment — delete them manually

✅ Analogy for the exam: Elastic Beanstalk is like Heroku on AWS — you push code, it handles the infrastructure. The difference is that with Beanstalk you still have full access to the underlying AWS resources if you need to customize them.

📝 Overall Summary

  • What it is: AWS Elastic Beanstalk is a PaaS service that deploys and manages web applications automatically — no infrastructure expertise required.
  • What it solves: Eliminates the manual effort of provisioning EC2, load balancers, auto scaling, security groups, and monitoring for every new application.
  • Core structure: An Application is a logical container; Environments are the actual running deployments (one application can have Dev, Test, and Prod environments simultaneously).
  • Resources it creates: EC2, Security Group, Elastic IP, S3 (for code/logs), CloudWatch metrics, and optionally ELB, Auto Scaling, and RDS — all billed at normal AWS rates.
  • Pricing: Elastic Beanstalk itself is free — you pay only for the underlying AWS resources; single-instance environments are free-tier eligible.
  • Deployment strategies: All at once (fastest, brief downtime), Rolling (no downtime), Immutable (safest), and Blue/Green (zero downtime with instant rollback).
  • Under the hood: Elastic Beanstalk uses CloudFormation to provision all resources — never delete the CloudFormation stack manually.
  • Health monitoring: Built-in color-coded health (Green/Yellow/Red/Grey) backed by CloudWatch metrics collected every 5 minutes by default.
  • Multiple environments: Create Dev, Test, and Prod environments in one application; support Blue/Green deployment with CNAME swap for zero-downtime releases.
  • Cleanup: Terminate environments via the Beanstalk console; manually delete S3 buckets to avoid ongoing storage charges.

🎯 Objective: Deploy a working Java web application on Elastic Beanstalk using a single-instance environment, verify it is live, and clean up all resources.

💰 Cost: Free tier (single instance, no ELB)

🟢 Project 3: Break & Fix — Learn to Debug Deployments

🎯 Objective: Intentionally break a working deployment and use Elastic Beanstalk's debugging tools — Events tab, logs, and health monitor — to find and fix the problem. This is the skill most beginners skip and most interviewers test.

⏱️ Time: 30–45 minutes

💰 Cost: Free tier (single instance)

⚡ Why this matters: Knowing how to deploy is table stakes. Knowing how to debug a failed deployment is what separates a junior from someone ready for production systems.

  1. Start with your working single-instance environment from Project 1. Confirm it is Green before proceeding.

  2. Break it — Method A: Wrong port. Modify your application code (or its configuration file) so it listens on port 9000 instead of port 8080 (the port Elastic Beanstalk expects for Java/Tomcat). Package and upload the broken version via Upload and deploy.

    Figure P3-1: 📸 Health turns Red — the environment is degraded after the bad deploy

  3. Watch the health indicator turn Red (Degraded). Now click the Events tab and read the events from the bottom. You should see messages like Health of instance [id] changed from Ok to Severe and Deployment failed.

    Figure P3-2: 📸 Events tab shows the exact failure sequence — always read bottom to top

  4. Click the Logs tab → Request last 100 lines. Download the log bundle and open the file. Look for lines containing ERROR, WARN, or Connection refused — these tell you exactly what the application tried and failed to do.

    Figure P3-3: 📸 Logs tab — request and download logs to read the actual error

  5. Fix the port back to 8080, repackage, and redeploy the corrected version. Watch the Events tab as the deployment succeeds and health returns to Green.

  6. Break it — Method B: Crash on startup. Add a line in your application startup code that throws an intentional exception (e.g., throw new RuntimeException("intentional crash");). Deploy it and repeat the debug process using Events and Logs.

  7. Fix and confirm: Deploy the working version again. Confirm Green health and that the application is accessible via its URL.

    Figure P3-4: 📸 Health recovers to Green after fixing and redeploying — mission accomplished

  8. Cleanup: Keep the environment running for Project 4, or terminate and clean up S3 if done for today.

✅ What you just learned: How to use the Events tab, Logs tab, and health status to diagnose a failed deployment — a skill you will use constantly in real AWS environments.

🟢 Project 4: Custom Environment Variables — Config Without Code Changes

🎯 Objective: Configure real environment variables (DB_HOST, API_KEY, APP_MODE) in Elastic Beanstalk and update your application to read them at runtime. Understand why this is the correct way to manage configuration across environments.

⏱️ Time: 20–30 minutes

💰 Cost: Free tier (single instance)

  1. Go to your Elastic Beanstalk environment → Configuration → Software → Edit.

    Figure P4-1: 📸 Configuration → Software → Edit to add environment variables

  2. Scroll down to the Environment properties section. Add the following three variables using the Add environment property button:

    • DB_HOST → mydb.us-east-1.rds.amazonaws.com (a fake value for now)
    • API_KEY → demo-key-abc123
    • APP_MODE → development

    Figure P4-2: 📸 Environment properties — three variables added with name and value

  3. Click Apply. Elastic Beanstalk will restart the environment to apply the new configuration. Watch the Events tab — you will see Applying configuration changes and then Environment update completed.

  4. Update your application code to read and display these environment variables. For example in Java:
    String dbHost = System.getenv("DB_HOST");
    Add a simple page or log entry that prints the values of these variables.

  5. Upload and deploy the updated app version. Access the application URL and confirm the variable values appear correctly.

  6. Key insight to internalize: The same application code can behave differently in each environment just by changing these variables. Dev environment gets APP_MODE=development and a dev DB. Prod gets APP_MODE=production and the real DB — without touching a single line of code.

  7. Cleanup: Remove the env variables or terminate the environment when done.

✅ What you just learned: Environment variables are the correct way to manage per-environment configuration. Never hard-code credentials or config in source code — it creates security risks and makes multi-environment setups fragile.

🟡 Project 5: Attach RDS — Build a Real Stateful Backend

🎯 Objective: Connect your Elastic Beanstalk application to an Amazon RDS database, store real data through the app, restart the environment, and confirm that data persists. Understand the difference between stateless compute and stateful data.

⏱️ Time: 45–60 minutes

💰 Cost: Free tier — RDS db.t2.micro, 20 GB SSD, 750 hrs/month

💰 Cost Note: RDS will use your free tier 750 hours/month allowance. Always stop or delete your RDS instance when done with the project to avoid charges after free tier expires.

  1. Go to Amazon RDS in the AWS Console → Create database. Choose Standard Create, engine MySQL, template Free tier. Set a DB instance identifier, master username, and master password. Note these down — you will pass them as environment variables.

    Figure P5-1: 📸 RDS Create database — MySQL, Free tier template selected

  2. Under Connectivity: select the same VPC as your Beanstalk environment. Enable Public access: Yes for now (so the app can reach it). Leave the default security group or create one that allows port 3306 from your Beanstalk environment's security group.

  3. Click Create database and wait for Status to show Available (3–5 minutes). Copy the Endpoint URL (e.g., mydb.abc123.us-east-1.rds.amazonaws.com).

    Figure P5-2: 📸 RDS status Available — copy the Endpoint URL

  4. In Elastic Beanstalk → Configuration → Software → Edit, add environment variables:
    DB_HOST → your RDS endpoint
    DB_USER → your master username
    DB_PASSWORD → your master password
    DB_NAME → your database name

  5. Update your application code to connect to MySQL using these environment variables, create a simple table (e.g., visitors), and insert a row each time the home page is visited. Display the total visitor count on the page.

  6. Deploy the updated application. Visit the URL several times. Each visit should increment the counter — data is being written to RDS.

    Figure P5-3: 📸 App showing visitor count — data is stored in RDS, not in EC2

  7. Restart test: Go to Elastic Beanstalk → Actions → Restart app server(s). Wait for the environment to return to Green. Visit the URL again — the counter should continue from where it left off. This proves data lives in RDS, not in the EC2 instance.

    Figure P5-4: 📸 Restart app servers — data survives because it lives in RDS, not EC2

  8. Cleanup: Delete the RDS instance (create a final snapshot if you want to keep the data). Terminate the Beanstalk environment. Delete S3 bucket.

✅ What you just learned: EC2 instances are stateless — data stored on them disappears when the instance is replaced. RDS is stateful — data persists independently of the compute layer. This distinction is fundamental to cloud architecture.

🟡 Project 6: Enable Auto Scaling — Your First Real Cloud Moment

🎯 Objective: Switch to a Load Balanced environment, configure Auto Scaling (min 1, max 3 instances), simulate traffic, and watch instances scale out automatically. This is the "cloud moment" that makes everything click.

⏱️ Time: 45–60 minutes

💰 Cost: ⚠️ NOT free tier — ELB charges ~$0.008/hr. Run for 1 hour max then clean up (~$0.01 total)

💰 Cost Note: A Load Balanced environment creates an Elastic Load Balancer which is NOT free tier eligible. Charges start immediately at ~$0.008/hr. Keep this environment running for 1 hour maximum during this project, then terminate it.

  1. In your existing Beanstalk application, create a new environment (do not modify your free-tier single instance one). Choose Load balanced as the environment type. Deploy the same application code.

    Figure P6-1: 📸 Choose Load balanced environment type — this enables Auto Scaling

  2. In the Capacity section, set Auto Scaling Group: Min instances: 1, Max instances: 3. Set the scaling trigger to scale out when CPUUtilization > 60% for 1 minute.

    Figure P6-2: 📸 Auto Scaling configured — min 1, max 3, scale out at 60% CPU

  3. Wait for the environment to reach Green. Verify that only 1 EC2 instance exists right now by checking EC2 → Instances or the Beanstalk environment's Health tab.

  4. Simulate traffic: Open a terminal and run a simple load script. For example using ab (Apache Bench): 

    ab -n 10000 -c 100 http://your-beanstalk-url.elasticbeanstalk.com/
    Or open the application URL in multiple browser tabs and keep refreshing. The goal is to push CPU above 60% on the current instance.

  5. Watch the Monitoring tab in Elastic Beanstalk. You should see CPUUtilization climbing. After a minute above 60%, Auto Scaling will launch a second instance.

    Figure P6-3: 📸 Monitoring tab showing CPU spike above 60% — Auto Scaling trigger reached

  6. Go to EC2 → Instances or Beanstalk → Health tab. You should now see 2 instances running — Auto Scaling launched a new one to handle the load.

    Figure P6-4: 📸 Two instances running — Auto Scaling worked! Cloud moment achieved.

  7. Stop the load test. Wait several minutes (scale-in cooldown). Confirm Auto Scaling terminates the extra instance and returns to 1 — cost optimization in action.

  8. Cleanup immediately: Terminate this environment as soon as the experiment is done. The ELB charges by the hour. Delete the S3 bucket.

✅ What you just learned: Auto Scaling adds capacity automatically when needed and removes it when load drops — you pay only for what you use, when you use it. This is one of the most powerful cloud concepts in practice.

🟠 Project 7: Deployment Strategies Lab — Feel the Difference

🎯 Objective: Try All at Once, Rolling, and Immutable deployment strategies on a real environment. Intentionally break one deployment mid-way to understand rollback behavior. You will feel the difference instead of just memorizing it.

⏱️ Time: 60–90 minutes

💰 Cost: Free tier for All at Once and Rolling (single instance). Immutable requires 2x instances briefly — minimal extra cost.

  1. Start with a working Load Balanced environment (minimum 2 instances for Rolling to be meaningful). Go to Configuration → Deployment preferences → Edit.

    Figure P7-1: 📸 Configuration → Deployment preferences → Edit to change strategy

  2. All at Once: Set policy to All at once. Prepare a v2 of your app (change a visible UI element — e.g., background color, or a heading). Deploy it. Watch the Events tab — all instances update simultaneously. The app may be briefly unreachable during this window. This is the downtime.

  3. Rolling: Change policy to Rolling with batch size 1. Deploy a v3. Watch Events carefully — you will see one instance updated while others still serve the old version. During the rollout, open the app URL in two tabs and keep refreshing — you may catch both versions serving traffic simultaneously.

    Figure P7-2: 📸 Rolling deployment in progress — one instance updating while others serve old version

  4. Immutable: Change policy to Immutable. Deploy a v4. Watch EC2 Instances — you will see new instances launch in a temporary Auto Scaling Group. Only after they pass health checks are the old instances terminated. This is the safest strategy.

    Figure P7-3: 📸 Immutable deployment — old and new instances run in parallel until health checks pass

  5. Break one intentionally: Deploy a broken version using Immutable. The new instances will fail health checks. Observe that the old instances are never touched — traffic continues uninterrupted. Elastic Beanstalk terminates the failed new instances automatically.

  6. Cleanup: Terminate the environment. Delete S3.

✅ What you just learned: The deployment strategy choice has real consequences on downtime, cost, and rollback speed. Immutable is the safest for production — old instances are untouched until the new ones prove they work.

🟠 Project 8: Blue/Green Deployment — Zero Downtime with Instant Rollback

🎯 Objective: Set up two environments (Blue = current, Green = new version), swap their CNAME URLs to shift traffic instantly, then roll back by swapping again. This pattern is heavily tested in AWS interviews.

⏱️ Time: 45–60 minutes

💰 Cost: Two single-instance environments = free tier. If using Load Balanced = two ELBs (watch costs)

  1. In your Elastic Beanstalk application, create two environments:
    Blue: MyApp-Blue — deploy version 1 of your app (current stable version)
    Green: MyApp-Green — deploy version 2 (new feature or visible change)

    Both should be Green health status before proceeding.

    Figure P8-1: 📸 Both Blue and Green environments healthy and running different versions

  2. Test the Green environment at its own URL. Confirm it works correctly before swapping. This is the validation step — you never send users to untested code.

  3. Go to the Blue environment → Actions → Swap environment URLs. Select MyApp-Green as the target environment. Click Swap.

    Figure P8-2: 📸 Swap environment URLs — the CNAME switch that makes Blue/Green work

  4. After the swap completes (takes about 15–30 seconds for DNS propagation), visit the original Blue URL. It now serves the Green (v2) application. Users have been silently moved to the new version with zero downtime.

  5. Simulate a problem: Pretend v2 has a critical bug. Go back to Actions → Swap environment URLs again. Swap back. Within seconds, traffic returns to v1. That is your rollback — no re-deploy, no waiting, just a DNS swap.

    Figure P8-3: 📸 Rollback complete — original URL pointing back to v1 in seconds

  6. Cleanup: Terminate both environments. Delete the S3 bucket.

✅ What you just learned: Blue/Green is not just a theory concept — it is a real operational technique. The CNAME swap takes seconds. Rollback takes seconds. No users experience downtime. This is why it is used by companies deploying hundreds of times per day.

🔴 Project 9: Logging & Monitoring — Build Your Observability System

🎯 Objective: Set up CloudWatch alarms for CPU utilization and 5xx error rate. Trigger the alarms intentionally. Receive email notifications. Understand observability — the skill most beginners completely ignore.

⏱️ Time: 45–60 minutes

💰 Cost: CloudWatch: first 10 alarms free. SNS email notifications: free. EC2: free tier.

  1. In your Elastic Beanstalk environment, go to Configuration → Monitoring → Edit. Enable Health event streaming to CloudWatch Logs. Set log retention to 7 days. Click Apply.

    Figure P9-1: 📸 Enable CloudWatch log streaming in Monitoring configuration

  2. Navigate to Amazon CloudWatch → Alarms → Create alarm. Select metric: EC2 → Per-Instance Metrics → CPUUtilization. Choose your Beanstalk EC2 instance. Set threshold: Greater than 60% for 1 datapoint in 1 minute.

    Figure P9-2: 📸 CloudWatch alarm creation — CPUUtilization metric, 60% threshold

  3. On the next screen, set the alarm action: Send notification to an SNS topic. Create a new topic and enter your email address. Click Create topic. Check your email and confirm the SNS subscription.

    Figure P9-3: 📸 SNS subscription email — confirm it or you will not receive alarm notifications

  4. Create a second alarm: go back to CloudWatch → Create alarm. Search for metric ApplicationRequests5xx under ElasticBeanstalk → Per-Environment Metrics. Threshold: Greater than 5 per minute. Same SNS topic.

  5. Trigger the CPU alarm: Run a load test against your environment (use ab or repeat browser refreshes). Watch CloudWatch → Alarms — the alarm state should change from OK → In alarm. Within 1–2 minutes, you should receive an alert email.

    Figure P9-4: 📸 Alarm triggered — CPU alarm shows In alarm state in red

  6. Trigger the 5xx alarm: Deploy a version of your app that intentionally returns HTTP 500 errors (e.g., throw an exception on every request). Hit the URL several times. Watch the 5xx alarm trigger.

  7. Redeploy the working version and watch both alarms return to OK state.

  8. Cleanup: Delete the CloudWatch alarms. Delete the SNS topic. Terminate the Beanstalk environment.

✅ What you just learned: Observability means you know when something breaks before users report it. CloudWatch + SNS is the foundational monitoring stack in AWS. Setting up alarms is one of the first things a DevOps engineer does for every production environment.
