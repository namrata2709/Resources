🌟 Introduction

Imagine you're the CEO of a busy company. You can't personally monitor every system — the water pressure, the air conditioning, the server rooms — all at once. So you hire a watchman and set up an intercom system. The watchman monitors everything, sounds an alarm when something goes wrong, and the intercom broadcasts the alert to whoever needs to know.

That's exactly what today's three AWS services do together. SNS is your intercom — it broadcasts messages to the right people. CloudWatch is your watchman — it monitors everything silently in the background. Lambda is your automated response team — it springs into action the moment something happens, handles the task, and disappears when done.

These three services are the backbone of modern, automated cloud operations. By the end of these notes, you'll understand not just what each service does, but how they work together to build systems that monitor themselves, alert the right people, and even fix problems automatically.

Figure 1: How SNS, CloudWatch, and Lambda work together in a real-world monitoring and automation pipeline

⚡ Why these three matter: Together, SNS + CloudWatch + Lambda enable you to build self-healing infrastructure that monitors itself, notifies your team, and takes corrective action — all without human intervention.

📢 Amazon SNS — Simple Notification Service

What Is SNS?

Think about how YouTube works. A content creator makes a video and uploads it to their channel. Within minutes, millions of subscribers get a notification on their phones. The creator didn't call each subscriber individually — they published once, and YouTube handled the delivery to everyone.

That's exactly how Amazon SNS works in the cloud.

Amazon SNS is a fully managed publish-subscribe messaging service that enables you to send notifications or messages to multiple subscribers simultaneously. You publish a message once, and SNS delivers it to everyone who has subscribed — regardless of whether they're checking email, reading SMS, or running an automated Lambda function.

Figure 2: SNS publish-subscribe model — one message, multiple simultaneous deliveries

The Three Key Players

Every SNS interaction involves three roles working together:

  • Topic: The communication channel — like a YouTube channel. Publishers send messages to it, and subscribers receive from it. A Topic is a logical access point and communication channel in SNS.
  • Publisher: Anyone or anything that sends a message to a topic. This could be you (publishing manually from the console), your application code, or another AWS service like CloudWatch, Auto Scaling, or S3.
  • Subscriber: An endpoint that receives messages from the topic. SNS subscribers can receive messages via email, SMS, HTTP/HTTPS, SQS, Lambda, and mobile push protocols.

💡 Subscription Confirmation: Email subscriptions require the subscriber to confirm by clicking a link in a confirmation email. SQS and Lambda subscriptions are confirmed automatically. This prevents unauthorized email subscriptions.

Standard vs. FIFO Topics

When creating an SNS topic, you choose between two types:

FeatureStandard TopicFIFO Topic
Message OrderingBest-effort (usually in order)Strictly preserved
Supported ProtocolsEmail, SMS, SQS, Lambda, HTTP/S, MobileSQS FIFO only
Duplicate DeliveryPossible (at-least-once)Exactly-once
Use CaseGeneral notifications, fan-outFinancial transactions, ordered events

SNS FIFO topics only support SQS FIFO queues as subscribers and strictly preserve message ordering. Standard topics support all protocols with best-effort ordering.

Figure 3: SNS Standard vs FIFO — choosing the right topic type for your use case

The Fan-Out Pattern

One of SNS's most powerful capabilities is the fan-out pattern. When you publish a single message to a topic, SNS simultaneously delivers it to all subscribers — each receiving its own independent copy.

Real-world example: A customer places an order on your e-commerce site. Your application publishes one "order-placed" event to an SNS topic. Simultaneously: the billing service (via SQS) processes the payment, the shipping service (via Lambda) reserves the inventory, and the customer (via email) receives a confirmation. One publish call, three independent parallel actions.

Figure 4: SNS Fan-out — one message triggers multiple independent consumers in parallel

SNS Integration with AWS Services

SNS doesn't just work with human subscribers. It's deeply integrated with other AWS services as both publishers and subscribers:

  • Auto Scaling → SNS: When your Auto Scaling Group scales out or in, it can notify an SNS topic. Your operations team gets an email whenever capacity changes.
  • CloudWatch → SNS: When a CloudWatch Alarm fires (CPU too high, error rate too high), it publishes to an SNS topic.
  • S3 → SNS: When objects are created or deleted in S3, S3 event notifications can publish to SNS.
  • SNS → Lambda: An SNS topic can trigger a Lambda function, enabling fully automated, serverless responses to notifications.

💡 According to AWS documentation, SNS supports delivery to more than 10 billion messages per day and can fan out to thousands of subscribers simultaneously with sub-second latency.

📊 Amazon CloudWatch — Monitoring & Observability

What Is CloudWatch?

Imagine you're driving a car with no dashboard. No speedometer, no fuel gauge, no temperature warning light. You're essentially flying blind — you won't know you're speeding until you crash, you won't know you're low on fuel until the engine dies, you won't know the engine is overheating until it seizes. The dashboard doesn't make the car go faster. It gives you the information you need to make smart decisions and catch problems before they become disasters.

Amazon CloudWatch is a fully managed monitoring and observability service that collects metrics, stores logs, and enables alarms for your AWS resources and applications.

Every AWS service you use — EC2, RDS, S3, Lambda, Auto Scaling — automatically sends data to CloudWatch. You don't configure anything to start collecting basic metrics. CloudWatch is always watching, always recording.

Figure 5: CloudWatch sits at the center of AWS observability — every service feeds into it

The Four Golden Signals

Before diving into CloudWatch's components, it's worth understanding what to monitor. The four Golden Signals (a concept from Google's Site Reliability Engineering, widely adopted in AWS) give you a complete picture of any system's health:

  • Latency: How long does it take to serve a request? Example: API response time in milliseconds. High latency = slow system.
  • Traffic: How much demand is the system handling? Example: requests per second, active connections. Use this to understand scale.
  • Errors: What percentage of requests are failing? Example: HTTP 500 error rate. Even low percentages matter at scale.
  • Saturation: How full is the resource? Example: CPU at 95%, disk at 90%. Saturation predicts future failure.

The four Golden Signals — Latency, Traffic, Errors, and Saturation — are the foundation for setting up effective CloudWatch alarms in production.

CloudWatch Metrics

A metric is a time-series measurement of something over time — for example, CPU utilization at 75% over the last 5 minutes. Metrics are numerical values sampled at regular intervals and stored in CloudWatch for analysis.

AWS services automatically emit standard metrics. For EC2, these include:

  • CPU Utilization (percentage of CPU consumed)
  • Network In / Network Out (bytes transferred)
  • Disk Read / Write operations
  • Status Check Failed (0 = healthy, 1 = failed)

❌ Common Misconception: CloudWatch does NOT automatically collect memory utilization or disk space used (in GB) from EC2. These require the CloudWatch Agent to be installed on the instance. Only the metrics above are collected by default.

Metric Collection Frequency:

By default, EC2 instances send metrics to CloudWatch every 5 minutes (Basic Monitoring). Enabling Detailed Monitoring reduces this to every 1 minute — additional charges apply.

Figure 6: Basic vs Detailed Monitoring — trading cost for granularity

CloudWatch Logs

While metrics are numerical (CPU at 75%), logs are textual — they record what actually happened. Think of logs as the detailed diary of your system's activity: every request, every error, every event, with timestamps.

CloudWatch Logs stores log data in Log Groups, which are containers that hold related log streams.

  • Log Group: A named container for related logs. Example: /aws/lambda/my-function holds all logs from a Lambda function named "my-function".
  • Log Stream: A sequence of log events from a single source within a log group. Each Lambda invocation creates its own log stream.
  • Retention: By default, logs are kept indefinitely. You can set retention periods from 1 day to 10 years to control storage costs.

Lambda automatically creates a Log Group and streams all execution output (print statements, errors, duration, memory used) to it. EC2 does NOT automatically send logs — you need the CloudWatch Agent or custom code to push logs from EC2.

CloudWatch Alarms

Alarms are where CloudWatch transforms from passive monitoring to active response. An alarm watches a single metric and performs actions when that metric crosses a threshold you define.

CloudWatch Alarms have three states: OK (metric within threshold), In Alarm (threshold breached), and Insufficient Data (not enough data to evaluate).

A newly created alarm always starts in Insufficient Data — it needs time to collect enough metric data points before it can evaluate whether the metric is within or above the threshold.

Figure 7: CloudWatch Alarm state transitions — a new alarm always starts in Insufficient Data

Alarm Actions: When an alarm transitions to In Alarm, it can trigger:

  • SNS Notification: Send a message to an SNS topic (which delivers to all subscribers)
  • EC2 Actions: Stop, Start, Reboot, or Terminate the specific EC2 instance being monitored
  • Auto Scaling Actions: Add or remove instances from an Auto Scaling Group
  • Systems Manager Actions: Run automation documents

✅ Best Practice: Always configure both a notification action (SNS email) AND an automated remediation action (EC2 stop, Auto Scaling) on production alarms. Notifications alert humans; automated actions prevent downtime while humans respond.

CloudWatch Dashboards

Dashboards let you create a custom view of your CloudWatch data — combining metrics from multiple services and regions into a single screen. Think of it as building your own car dashboard, where you choose which gauges to display and how to display them.

  • Display metrics as line charts, numbers, gauges, or tables
  • Combine metrics from different services (EC2, RDS, Lambda) on one screen
  • Share dashboards across your organization
  • Auto-refresh at configurable intervals

💡 Billing Alarms — Regional Restriction: CloudWatch Billing Alarms are only available in us-east-1 (N. Virginia). This is because AWS billing data is aggregated in N. Virginia. If you're in ap-south-1 (Mumbai), you will NOT see the Billing Alarms section in CloudWatch — you must switch regions.

Figure 8: A CloudWatch custom dashboard — build your operational control center

⚡ AWS Lambda — Serverless Compute

The Evolution of Compute

To understand why Lambda exists, you need to understand the journey of compute resources. Let's use a car analogy:

  • Traditional Servers (Own Car): You buy the car, pay for insurance, maintenance, and parking — whether you drive it or not. This is on-premises infrastructure: you own the hardware, manage everything, and pay continuously regardless of usage.
  • Cloud EC2 (Rental Car): You rent a car for a trip. You specify what you want (5-seater, AC), pay only for the rental period, and return it when done. This is EC2 — you choose the instance type, pay while it's running, and stop paying when you terminate it.
  • Lambda (Taxi): You don't think about the car at all. You just tell the taxi where to go, pay for that trip, and you're done. This is Lambda — you just write code, and AWS handles everything else. You pay only for the milliseconds your code runs.

AWS Lambda is a serverless, event-driven compute service that runs code without requiring you to provision or manage servers.

Figure 9: The compute evolution — Lambda is the final step toward zero infrastructure management

How Lambda Works

When you use Lambda, here's what happens under the hood:

  1. You create a Function: A function is a named container for your code. You specify the runtime (Python, Node.js, Java, Go, Ruby, .NET), upload your code, set the timeout and memory, and attach an IAM execution role.
  2. You attach a Trigger: A trigger is an AWS service that invokes your function when something happens. Triggers can be S3 (file uploaded), API Gateway (HTTP request received), CloudWatch/EventBridge (scheduled time or alarm), SNS (notification received), DynamoDB Streams (record changed), and many more.
  3. The trigger fires: Someone uploads a file to S3. S3 sends an event to Lambda.
  4. Lambda provisions compute: AWS automatically allocates a container with your chosen runtime. This happens in milliseconds.
  5. Your code runs: Lambda executes your function with the event data as input. Your code can read files from S3, write to DynamoDB, call other APIs — anything boto3 can do.
  6. Lambda shuts down: When your code finishes (or times out), the execution environment is released. You pay only for the execution duration.

Figure 10: Lambda execution flow — from trigger to code execution to shutdown

Key Limits and Specifications

Lambda has specific limits you must know for both the exam and real-world design decisions:

ParameterDefault / LimitNotes

Lambda's maximum execution timeout is 15 minutes. For workloads that run longer, use EC2, ECS, or AWS Batch instead.

Lambda Billing — Pay Only When Code Runs

This is the most important differentiator of Lambda from EC2. With EC2:

  • Instance runs for 24 hours a day, 7 days a week
  • You pay for 24 hours regardless of whether any code runs
  • Even idle, it costs money

With Lambda:

  • Function only runs when triggered
  • You pay only for actual execution duration in milliseconds
  • Between invocations, there is zero cost

Lambda charges based on the number of requests and the duration of compute time in milliseconds — you pay only when your code executes.

💡 Free Tier: AWS Lambda includes 1 million free requests and 400,000 GB-seconds of compute per month in the free tier — permanently, not just the first 12 months. For most learning and small projects, Lambda is effectively free.

IAM Execution Role

Every Lambda function has an attached IAM role called the Execution Role. This role defines what AWS resources the function is allowed to interact with.

When you create a Lambda function, AWS automatically creates a basic execution role with one permission: the ability to write logs to CloudWatch Logs. If your function needs to read from S3, write to DynamoDB, or send to SNS, you must add those permissions to the execution role.

✅ Principle of Least Privilege: Only grant the specific permissions your Lambda function actually needs. Don't attach AdministratorAccess to a function that only needs to read one S3 bucket. Use resource-specific policies like s3:GetObject on arn:aws:s3:::my-bucket/uploads/*.

Lambda Layers — Managing Dependencies

By default, Lambda's runtime includes only the standard library for your chosen language. If your Python code imports Pillow (for image processing), pandas (for data analysis), or requests (for HTTP calls), you must bundle those packages separately.

A Lambda Layer is a reusable ZIP archive containing libraries, dependencies, or custom runtimes that can be shared and attached across multiple Lambda functions.

The workflow for creating and using a Layer:

  1. On an EC2 instance or your local machine, install the required packages into a directory: pip install Pillow -t python/
  2. Zip the directory: zip -r pillow-layer.zip python/
  3. Upload the zip to S3 or directly to Lambda as a Layer
  4. Attach the Layer to your function via the Console or CLI
  5. Your function code can now import Pillow as if it were natively installed

A single function can have up to 5 layers attached, and the total unzipped size of all layers combined with the deployment package cannot exceed 250 MB.

Figure 11: Lambda Layers — separate your code from its dependencies for cleaner deployments

Event-Driven Architecture with Lambda

Lambda is the engine of event-driven architecture in AWS. Instead of services calling each other directly (tight coupling), they communicate through events (loose coupling). Lambda sits in the middle, reacting to events from any source.

Common Lambda trigger patterns:

  • S3 → Lambda: Process files when they land in a bucket (resize images, validate CSVs, extract text from PDFs)
  • API Gateway → Lambda: Serve REST API endpoints without any servers
  • CloudWatch Events/EventBridge → Lambda: Run scheduled tasks (cron jobs), enforce policies, start/stop instances
  • SNS → Lambda: Process notifications and take action (update database, send to another system)
  • DynamoDB Streams → Lambda: React to database changes in real time

❌ Recursive Invocation Warning: If your Lambda function reads from and writes to the same S3 bucket/prefix, the output file triggers the function again — creating an infinite loop. AWS warns about this during trigger configuration. Always use separate input and output folders (e.g., uploads/ for input, processed/ for output) to prevent recursive invocation.

Automatic Scaling

Lambda scales automatically and concurrently. If 1000 requests arrive simultaneously, Lambda creates up to 1000 parallel execution environments — each handling one request. You never configure scaling policies, launch templates, or warm-up times.

This is fundamentally different from EC2 Auto Scaling, which requires configuration, takes minutes to add new instances, and can only scale to the defined maximum.

💡 Cold Starts: The first time a Lambda function is invoked (or when scaling up to a new environment), AWS must provision a new container. This takes 100ms to several seconds and is called a "cold start." Subsequent invocations reuse the same container (warm start) and are much faster. For latency-sensitive applications, use Provisioned Concurrency to pre-warm environments.

🔗 How SNS, CloudWatch, and Lambda Work Together

These three services become exponentially more powerful when combined. Here's the most common real-world pattern — the automated monitoring and response pipeline:

  1. CloudWatch monitors your EC2 instance, collecting CPU metrics every 5 minutes
  2. You set a CloudWatch Alarm: "If CPU ≥ 80% for 1 minute, trigger actions"
  3. CloudWatch Alarm triggers two actions: Send SNS notification (emails team) + Stop EC2 instance
  4. SNS delivers an email to all subscribers explaining the issue and action taken
  5. Lambda automates complex responses (via SNS trigger or direct CloudWatch trigger) — launches a new instance, updates a load balancer, sends a Slack message

Figure 12: The complete automated monitoring pipeline — detect, notify, remediate

Real-World Lambda Automation Examples

Lambda automation in real production environments goes far beyond simple file renaming. Here are patterns discussed in class that represent actual use cases:

1. EBS Volume Compliance Enforcement
Company policy requires GP3 volumes, but interns sometimes create GP2. Solution: Lambda function triggered by EventBridge (captures CloudTrail "CreateVolume" API call). Lambda checks if the new volume is GP2, converts it to GP3 using boto3, and sends an SNS notification documenting the automatic conversion. Zero manual remediation needed.

2. Scheduled EC2 Start/Stop for Cost Savings
Development instances only needed 9 AM–6 PM weekdays. Solution: Two Lambda functions (start-instances and stop-instances) triggered by EventBridge cron schedules. Instances tagged Environment=Development are started at 9 AM and stopped at 6 PM automatically. Result: ~73% reduction in development compute costs.

3. Image Processing Pipeline
Photo app needs thumbnails generated for every uploaded image. Solution: S3 PUT event triggers Lambda. Lambda uses Pillow library (in a Layer) to resize the image, saves thumbnail to processed/ prefix, writes metadata to DynamoDB, sends success notification to SNS. Scales to thousands of uploads per day with zero server management.

📝 Overall Summary

  • SNS (Simple Notification Service): A fully managed publish-subscribe messaging service. Publishers send to a Topic; all subscribers receive simultaneously. Supports email, SMS, SQS, Lambda, HTTP/S, and mobile push protocols.
  • SNS Topic Types: Standard topics support all protocols with best-effort ordering. FIFO topics strictly preserve order but only support SQS FIFO as subscriber.
  • SNS Fan-out: One message published to a topic is delivered to all subscribers simultaneously — enabling parallel, decoupled processing by multiple consumers.
  • CloudWatch: AWS's monitoring and observability service. Collects metrics automatically from all AWS services, stores logs in Log Groups, enables Alarms, and supports custom Dashboards.
  • CloudWatch Metrics: Numerical time-series measurements. EC2 sends metrics every 5 minutes by default; Detailed Monitoring enables 1-minute intervals at additional cost.
  • CloudWatch Alarms: Watch a single metric and trigger actions (SNS notifications, EC2 actions, Auto Scaling) when a threshold is breached. Three states: OK, In Alarm, Insufficient Data.
  • Billing Alarms: Only available in us-east-1 (N. Virginia) — a critical exam fact. Billing data is aggregated in this region.
  • Lambda: Serverless, event-driven compute. Write code, attach a trigger, and pay only for milliseconds of actual execution. AWS manages all infrastructure.
  • Lambda Timeout: Default 3 seconds, maximum 15 minutes. Not suitable for workloads exceeding 15 minutes.
  • Lambda Layers: Reusable packages of third-party libraries shared across functions. Up to 5 layers per function.
  • Integration Pattern: CloudWatch Alarm → SNS (notify team) + Lambda (automate remediation) is the standard self-healing infrastructure pattern in AWS.

Project 2: Smart S3 File Processor with Filtering and Structured Logs

🎯 Objective: Upgrade the basic file renamer into a smarter Lambda that only processes .jpg and .png files, skips everything else, and writes structured log entries for every decision — processed, skipped, or error.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier

🧠 What you'll learn: Conditional logic in Lambda, structured logging, thinking in outcomes not just steps

  1. Reuse your S3 bucket from Session Project 2 (or create a new one with uploads/ and processed/ folders). If creating new: S3 → Create bucket → name it smart-processor-[suffix] → create two folders: uploads/ and processed/.

    📸 Screenshot: S3 bucket with uploads and processed folders — starting clean

  2. Create the Lambda function. Lambda → Create function → Author from scratch. Name: smart-file-processor. Runtime: Python 3.12. Create function. Attach S3 full access to the execution role (same as Session Project 2 — IAM → role → Add permissions → AmazonS3FullAccess).

    📸 Screenshot: Lambda execution role with both CloudWatch Logs and S3FullAccess permissions

  3. Deploy the smart processing code. In the Lambda Code tab, paste the following and click Deploy:

    import boto3
import json
from datetime import datetime

s3 = boto3.client('s3')

ALLOWED_EXTENSIONS = {'.jpg', '.jpeg', '.png'}

def lambda_handler(event, context):
    results = []

    for record in event['Records']:
        bucket = record['s3']['bucket']['name']
        source_key = record['s3']['object']['key']
        filename = source_key.split('/')[-1]

        # Get extension (lowercase for comparison)
        ext = ''
        if '.' in filename:
            ext = '.' + filename.rsplit('.', 1)[1].lower()

        # Decision: skip or process
        if ext not in ALLOWED_EXTENSIONS:
            log_entry = {
                "action": "SKIPPED",
                "file": source_key,
                "reason": f"Extension '{ext}' not in allowed list {list(ALLOWED_EXTENSIONS)}",
                "timestamp": datetime.utcnow().isoformat()
            }
            print(json.dumps(log_entry))
            results.append(log_entry)
            continue

        # Process: rename with timestamp and move
        try:
            name = filename.rsplit('.', 1)[0]
            timestamp = datetime.utcnow().strftime('%Y%m%d_%H%M%S')
            new_filename = f"{name}_{timestamp}{ext}"
            destination_key = f"processed/{new_filename}"

            s3.copy_object(
                Bucket=bucket,
                CopySource={'Bucket': bucket, 'Key': source_key},
                Key=destination_key
            )
            s3.delete_object(Bucket=bucket, Key=source_key)

            log_entry = {
                "action": "PROCESSED",
                "source": source_key,
                "destination": destination_key,
                "timestamp": datetime.utcnow().isoformat()
            }
            print(json.dumps(log_entry))
            results.append(log_entry)

        except Exception as e:
            log_entry = {
                "action": "ERROR",
                "file": source_key,
                "error": str(e),
                "timestamp": datetime.utcnow().isoformat()
            }
            print(json.dumps(log_entry))
            results.append(log_entry)

    return {'statusCode': 200, 'body': json.dumps(results)}

    📸 Screenshot: Smart processor code deployed — ALLOWED_EXTENSIONS and structured log entries visible

  4. Add the S3 trigger. Lambda → Add trigger → S3 → your bucket → Event type: PUT → Prefix: uploads/ → Acknowledge recursive warning → Add.

    📸 Screenshot: S3 trigger attached — uploads/ prefix prevents recursion

import json
from datetime import datetime

ec2 = boto3.client('ec2')
s3 = boto3.client('s3')

AUDIT_BUCKET = 'ec2-audit-logs-[suffix]'  # replace with your bucket name

def lambda_handler(event, context):
    timestamp = datetime.utcnow().isoformat()

    # Parse the SNS message
    for record in event['Records']:
        sns_message = json.loads(record['Sns']['Message'])

        instance_id = extract_instance_id(sns_message)

            "alarm": alarm_name,
            "state": new_state,
            "instance_id": instance_id,
            "timestamp": timestamp
        }))

        if instance_id:
            # Tag the instance
            ec2.create_tags(
                Resources=[instance_id],
                Tags=[
                    {'Key': 'HighCPU', 'Value': 'true'},
                    {'Key': 'LastAlarm', 'Value': alarm_name},

                ]

        # Write audit log to S3
        audit_record = {
            "event_type": "CPU_ALARM",
            "alarm_name": alarm_name,
            "alarm_state": new_state,
            "instance_id": instance_id,
            "action_taken": "ec2_tagged",
            "timestamp": timestamp,
            "raw_message": sns_message
        }

        s3_key = f"alarms/{alarm_name}/{timestamp.replace(':', '-')}.json"
        s3.put_object(
            Bucket=AUDIT_BUCKET,
            Key=s3_key,
            Body=json.dumps(audit_record, indent=2),
            ContentType='application/json'
        )
        print(json.dumps({"step": "audit_written", "s3_key": s3_key}))

    return {'statusCode': 200}

def extract_instance_id(message):
    """Extract EC2 instance ID from CloudWatch alarm dimensions."""
    try:
        dimensions = message['Trigger']['Dimensions']
        for dim in dimensions:
            if dim['name'] == 'InstanceId':
                return dim['value']
    except (KeyError, TypeError):
        pass
    return None

Project 5: Idempotent Auto-Remediation System

🎯 Objective: Build a CloudWatch → SNS → Lambda remediation system where Lambda checks an EC2 tag before acting. If the instance is already tagged as handled, Lambda exits without repeating the action. This prevents duplicate remediation when alarms fire multiple times for the same event.

⏱️ Time: 60–75 minutes

💰 Cost: Free tier

🧠 What you'll learn: Idempotency — "what if this Lambda runs twice?" — the most important production engineering concept for event-driven systems

⚡ Why idempotency matters: CloudWatch Alarms can fire multiple times for a sustained threshold breach. If your Lambda isn't idempotent, it might stop 3 EC2 instances, send 10 emails, or create 5 duplicate records — one for each alarm firing. Idempotency means the second (and third, and fourth) run produces the same result as the first, with no side effects.

  1. Launch an EC2 instance. Name: remediation-test. t2.micro. Amazon Linux 2023. Launch and wait for Running state. Note the instance ID.

    📸 Screenshot: Instance running with no custom tags — clean baseline before the system runs

  2. Create SNS topic and email subscription. SNS → Create topic: remediation-alerts → Standard. Add email subscription. Confirm in inbox.

  3. Create the Lambda remediation function. Lambda → Create function. Name: idempotent-remediator. Python 3.12. Create function. Attach an inline IAM policy with these permissions (same pattern as Project 3 — go to the execution role in IAM → inline policy):

  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ec2:DescribeInstances",
        "ec2:CreateTags",
        "ec2:DescribeTags",
        "ec2:StopInstances"
      ],
      "Resource": "*"
    }
  ]
}

    📸 Screenshot: Least-privilege IAM policy — only EC2 describe and stop actions, no broad access

  4. Deploy the idempotent remediation code. In the Lambda Code tab, paste the following and click Deploy:

    import boto3
import json
from datetime import datetime

ec2 = boto3.client('ec2')

HANDLED_TAG_KEY = 'RemediationHandled'
HANDLED_TAG_VALUE = 'true'

def lambda_handler(event, context):
    timestamp = datetime.utcnow().isoformat()

    for record in event['Records']:
        sns_message = json.loads(record['Sns']['Message'])
        instance_id = extract_instance_id(sns_message)
        alarm_name = sns_message.get('AlarmName', 'unknown')

        if not instance_id:
            print(json.dumps({"step": "no_instance_id", "alarm": alarm_name}))
            continue

        # IDEMPOTENCY CHECK: Has this instance already been handled?
        if already_handled(instance_id):
            print(json.dumps({
                "step": "SKIPPED_DUPLICATE",
                "reason": f"Instance {instance_id} already has tag {HANDLED_TAG_KEY}={HANDLED_TAG_VALUE}",
                "timestamp": timestamp
            }))
            return {'statusCode': 200, 'body': 'Already handled — skipping'}

        # First time: take action
        print(json.dumps({"step": "REMEDIATING", "instance_id": instance_id, "alarm": alarm_name}))

        # Tag first — mark as handled BEFORE stopping
        # (if stop fails, the tag prevents infinite retry loops)
        ec2.create_tags(
            Resources=[instance_id],
            Tags=[
                {'Key': HANDLED_TAG_KEY, 'Value': HANDLED_TAG_VALUE},
                {'Key': 'RemediatedAt', 'Value': timestamp},
                {'Key': 'RemediatedBy', 'Value': 'idempotent-remediator-lambda'}
            ]
        )
        print(json.dumps({"step": "TAGGED", "instance_id": instance_id}))

        # Stop the instance
        ec2.stop_instances(InstanceIds=[instance_id])
        print(json.dumps({"step": "STOPPED", "instance_id": instance_id, "timestamp": timestamp}))

    return {'statusCode': 200, 'body': 'Remediation complete'}

def already_handled(instance_id):
    """Check if instance already has the remediation tag."""
    response = ec2.describe_instances(InstanceIds=[instance_id])
    for reservation in response['Reservations']:
        for instance in reservation['Instances']:
            for tag in instance.get('Tags', []):
                if tag['Key'] == HANDLED_TAG_KEY and tag['Value'] == HANDLED_TAG_VALUE:
                    return True
    return False

def extract_instance_id(message):
    try:
        dimensions = message['Trigger']['Dimensions']
        for dim in dimensions:
            if dim['name'] == 'InstanceId':
                return dim['value']
    except (KeyError, TypeError):
        return None

import json
from datetime import datetime
