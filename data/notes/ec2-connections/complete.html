🚀 Introduction

In the previous sessions you launched your first EC2 instance and explored the AWS Console. Now it is time to actually use that server — log in to it, manage it like a real cloud engineer, and understand what happens to it over its lifetime.

Think of your EC2 instance like a computer you rented from AWS. Before you can use a computer, you need a way to sit in front of it and type commands. Because this computer is sitting inside an AWS data center thousands of kilometres away, you cannot physically walk up to it — you need a remote connection. That is exactly what this session is about.

By the end of these notes you will know how to connect to a Linux server three different ways, how to connect to a Windows server using RDP, how to resize your instance, how AWS protects you from accidental shutdowns and deletions, how EC2 moves through its lifecycle states, and how AWS charges you for all of this.

🔑 SSH Connection Methods (Linux / Amazon Linux / Ubuntu)

SSH stands for Secure Shell — it is a network protocol that lets you log into a remote Linux server and run commands securely over an encrypted connection. Think of it like a secret telephone line between your laptop and your server: everything you type is scrambled so nobody in between can read it.

For Linux-based EC2 instances, there are three practical methods to connect. Understanding all three matters for the exam and for real-world work.

Figure 2: Comparison of the three SSH connection methods for EC2 Linux instances

Method 1: EC2 Instance Connect (Browser-Based)

This is the simplest method — no software to install, no key file to manage. AWS opens a terminal right inside your browser window.

✅ Best for: Quick access, beginners, situations where you do not have your key pair file handy.

How it works behind the scenes: AWS temporarily pushes a one-time SSH key to your instance for 60 seconds, then removes it. You never see the key — the whole process is invisible.

Steps to connect

  1. Open the EC2 Console → go to Instances.

  2. Select your running instance and click the Connect button at the top.

    📸 Screenshot: The Connect button in the EC2 instances list

  3. The Connect to instance page appears. Make sure the EC2 Instance Connect tab is selected (it usually is by default).

    📸 Screenshot: EC2 Instance Connect tab selected on the Connect to instance page

  4. Leave the username as ec2-user (for Amazon Linux) or ubuntu (for Ubuntu). Click Connect.

  5. A new browser tab opens with a black terminal window — you are now inside your server!

    📸 Screenshot: Successful EC2 Instance Connect terminal session in the browser

💡 Prerequisite: EC2 Instance Connect requires port 22 (SSH) to be open in the instance's Security Group inbound rules. If it is blocked, the connection will fail.

Method 2: SSH with Key Pair (Linux / Mac Terminal)

If you are on a Mac or Linux machine, your operating system already has an SSH client built in. You open your Terminal app and type a single command — no extra software needed.

💡 What is a key pair? When you launched your EC2 instance, AWS asked you to create or choose a key pair and download a .pem file. That file is your private key — think of it as the physical key to a padlock. AWS keeps the padlock (public key) on your server. You must have the private key file to unlock the door.

Steps to connect

  1. Open your Terminal application.

  2. Navigate to the folder where your .pem file is saved. For example: cd ~/Downloads

  3. Set the correct permissions on your key file. The .pem file must have permissions set to chmod 400 — otherwise SSH will refuse to use it.

    chmod 400 your-key-name.pem

  4. Run the SSH command using your instance's Public IPv4 DNS or IP address (find this on the EC2 console instance details page):

    ssh -i "your-key-name.pem" ec2-user@<your-public-ip>

    For Ubuntu instances, replace ec2-user with ubuntu.

  5. The first time you connect, SSH asks "Are you sure you want to continue connecting?" — type yes and press Enter.

  6. You are now inside your server.

❌ Common Error — Unprotected Private Key File: If you see WARNING: UNPROTECTED PRIVATE KEY FILE!, it means you forgot step 3. Run chmod 400 your-key-name.pem and try again.

Method 3: PuTTY (Windows Users)

Windows does not have a built-in SSH client (older versions). PuTTY is a free, lightweight SSH client for Windows that has been the industry standard for decades.

💡 Note: Windows 10 and Windows 11 now include a built-in OpenSSH client, so you can also use the regular Command Prompt or PowerShell with the same ssh command as Linux/Mac. PuTTY is still widely used and worth knowing.

PuTTY does NOT accept .pem files directly — you must first convert your key to .ppk format using a tool called PuTTYgen.

Steps to connect with PuTTY

  1. Download and install PuTTY from putty.org (it also installs PuTTYgen automatically).

  2. Convert .pem to .ppk using PuTTYgen:

    • Open PuTTYgen → click Load
    • Change file type filter to "All Files" → select your .pem file → Open
    • Click Save private key → save it as your-key-name.ppk

  3. Open PuTTY. In the Host Name field, type: ec2-user@<your-public-ip>

  4. In the left panel go to Connection → SSH → Auth → Credentials. Browse to your .ppk file and select it.

  5. Go back to Session, give it a name under Saved Sessions, click Save (so you do not have to redo this each time), then click Open.

  6. A terminal window opens — type yes on first connection and you are in.

Figure 3: PuTTY connection flow — from .pem download to terminal access

⚡ FileZilla tip: FileZilla is another popular Windows tool that uses the same PuTTY key format (.ppk) to transfer files between your PC and your EC2 instance over SFTP. You will use this when we start the Linux module.

🖥️ RDP Connection to Windows EC2

When your EC2 instance runs a Windows Server operating system, SSH does not apply. Windows uses a completely different protocol called RDP — Remote Desktop Protocol — which runs on port 3389 and gives you a full graphical desktop, just like sitting in front of a Windows computer.

Think of it this way: SSH is a text-only phone call (you type commands). RDP is a video call (you see the entire desktop with windows, icons, and a mouse pointer).

Figure 5: SSH (port 22, text) for Linux vs RDP (port 3389, graphical) for Windows

Steps to connect via RDP

  1. Make sure your Windows EC2 instance is in the Running state.

  2. In the EC2 console, select the instance → click Connect → choose the RDP client tab.

    📸 Screenshot: RDP client tab on the Connect to instance page

  3. Click Get password. You will be prompted to upload your .pem key file. AWS uses it to decrypt and reveal the administrator password for your Windows instance.

    📸 Screenshot: Retrieving the Windows administrator password using the .pem key file

  4. Copy the revealed password. Then click Download remote desktop file — this downloads a small .rdp file pre-configured with your instance's IP address.

  5. Open the .rdp file. A Windows Remote Desktop dialog opens. Enter the username Administrator and the password you copied. Click Connect.

  6. Accept the certificate warning (expected on first connect) and you will see the full Windows Server desktop.

💡 On Mac: Download Microsoft Remote Desktop from the Mac App Store — it is free and works perfectly with AWS Windows instances.

On Linux: Use Remmina or FreeRDP as your RDP client.

❌ Common Mistake: For RDP to work, port 3389 (RDP) must be open in the Security Group inbound rules — just like port 22 is needed for SSH. Forgetting this is the most common reason RDP connections fail.
⚡ Windows EC2 instances take longer to boot than Linux — typically 2–3 minutes before the password is available and RDP is ready. If you try to connect immediately after launch and it fails, wait a couple of minutes and try again.

⚙️ Changing Instance Type (Vertical Scaling)

Imagine you bought a laptop with 8 GB of RAM but your workload grew and now it is slow. With a physical machine you would need to buy a new computer. With EC2, you can simply upgrade — this is called vertical scaling or changing the instance type.

For example, you might start with a t2.micro (1 vCPU, 1 GB RAM) and later change to a t3.medium (2 vCPU, 4 GB RAM) when your application grows.

💡 According to AWS documentation, you can change the instance type of an instance that is in a stopped state. The new instance type must be compatible with the instance's current configuration (e.g., same virtualization type for most instance families).

📚 Source: AWS EC2 Change Instance Type Docs

Figure 6: Vertical scaling — upgrading instance type requires a stop/start cycle

Steps to change instance type

  1. First, stop the instance (you cannot change the type while it is running). Go to EC2 → Instances → select instance → Instance state → Stop instance.

    📸 Screenshot: Stopping an instance via the Instance state dropdown

  2. Wait for the instance state to show Stopped.

  3. With the stopped instance selected, go to Actions → Instance settings → Change instance type.

    📸 Screenshot: Accessing Change instance type from the Actions menu

  4. Choose your new instance type from the dropdown (e.g., t3.medium) and click Apply.

  5. Start the instance again — it will boot up with the new hardware configuration.

❌ Common Mistake: You cannot change the instance type while the instance is in a running state — it must be stopped first.
⚡ Cost note: When you change instance type, you are charged at the new rate from the moment the instance starts with the new type. Stopping an instance stops compute charges — but EBS (storage) charges continue while stopped.

🛡️ Stop Protection & Termination Protection

Imagine you are running a critical production server — an e-commerce website that processes payments 24/7. If someone accidentally clicks "Stop" or "Terminate" on that instance, your business goes down and data may be lost. AWS provides two safety features to prevent this.

Figure 7: Stop protection and termination protection — two independent safety shields for your instance

Stop Protection

Stop protection prevents an instance from being accidentally stopped via the console, CLI, or API.

Why does this matter? When you stop an instance, all background processes and services running on it are killed. If you have a database or web server running on that instance, stopping it abruptly could disrupt users or corrupt in-progress operations.

💡 Use case: Enable stop protection on any instance running a production application — a web server, a database, or a batch processing job — to prevent accidental interruption.

Termination Protection

Termination protection prevents an instance from being permanently deleted (terminated) via the console, CLI, or API.

This is even more critical than stop protection. Once an EC2 instance is terminated, it cannot be recovered — it is permanently deleted. The instance disappears from your dashboard after a short delay (AWS cleans it up in the background).

❌ Critical fact for the exam: Termination is irreversible — unlike stopping, there is no way to undo a termination. Always enable termination protection on production instances.

💡 IAM connection: In an upcoming session you will learn about IAM (Identity and Access Management) users and permissions. IAM lets you control who has permission to stop or terminate instances — this is a more powerful approach for large teams. Termination protection adds a second layer on top of IAM.

How to enable Stop / Termination Protection

  1. Select your instance in the EC2 console.
  2. Go to Actions → Instance settings → Change termination protection (or Change stop protection).
  3. Check the Enable box and click Save.

📸 Screenshot: Enabling termination protection from Instance settings

⚡ Shutdown behaviour setting: There is also a related setting called Instance initiated shutdown behavior. This controls what happens when the OS inside the instance runs a shutdown command: either the instance stops (default) or it terminates. For production servers, always verify this is set to Stop, not Terminate.

🔄 EC2 Instance States & Lifecycle

Your EC2 instance is not just "on" or "off" — it moves through a series of states during its lifetime, just like a real computer going from being powered on, to running applications, to being shut down or decommissioned.

Understanding these states is critical because AWS charges you differently depending on the state, and certain operations (like changing instance type) are only possible in specific states.

📸 From Session: EC2 instance lifecycle diagram shown during the October 8 session — this is the same diagram you need to memorise for the exam.

State 1: Pending

The Pending state is the brief startup phase after you launch or start an instance — AWS is preparing the hardware, booting the OS, and running startup scripts.

Think of it like your laptop powering on before Windows or macOS finishes loading. You cannot log in yet.

  • Trigger: Launched for the first time, or started after being stopped
  • What AWS does: Allocates hardware, assigns public IP, boots the OS
  • Billing: You are not billed during the Pending state — billing starts only once the instance reaches Running
  • Duration: Usually 30–90 seconds for Linux; 2–3 minutes for Windows

State 2: Running

The Running state means the instance is fully booted and available — AWS is actively charging you.

This is the state where your server is alive and doing work. You can SSH/RDP into it, run applications, serve traffic, and process data.

  • Trigger: Automatically follows Pending
  • Billing: ✅ You are billed per second (Linux) or per hour (Windows) while Running
  • Actions available: Connect, stop, reboot, terminate, create AMI
⚡ Key exam fact: AWS charges for EC2 in the Running state regardless of whether any application is actively running on the instance. An idle running server still costs money — just like paying for a rented car whether you drive it or not.

States: Stopping → Stopped

When you click Stop on a running instance, it first moves to Stopping (a brief transition state while the OS gracefully shuts down) and then to Stopped.

  • In the Stopped state, compute charges stop but EBS storage charges continue.
  • The instance retains its configuration, AMI, security groups, and attached EBS volumes
  • The public IP address is released when an instance is stopped — it will get a different public IP when started again. Use an Elastic IP if you need a permanent address.
  • You can change the instance type, modify settings, and restart the instance from Stopped

💡 Stop-hibernate: There is also a Stop-hibernate option which saves the contents of RAM to the EBS root volume before stopping. When the instance starts again, it resumes exactly where it left off — like putting your laptop to sleep. The instance must have hibernation enabled at launch time to use this feature.

State 3: Rebooting

Rebooting is equivalent to restarting your laptop. The OS shuts down and comes back up — but the instance stays on the same physical hardware.

  • During a Reboot, the instance retains its public IP address — unlike a Stop/Start cycle.
  • Running services will stop momentarily and restart
  • Billing: continues uninterrupted (instance is still "yours" on that hardware)
  • Use case: Applying OS patches or configuration changes that require a restart
⚡ Reboot vs Stop/Start — exam trap: Reboot = same host, same IP. Stop → Start = new host possible, new public IP. This distinction is frequently tested.

States: Shutting-down → Terminated

When you click Terminate, the instance moves to Shutting-down briefly and then to Terminated.

  • A Terminated instance is permanently deleted and cannot be recovered.
  • The instance remains visible in the console for a short period with "terminated" status, then disappears completely as AWS cleans it up
  • By default, the root EBS volume is deleted when the instance is terminated (this can be changed)
  • Billing stops immediately
❌ Do not confuse: Stopped = off but recoverable. Terminated = gone forever. Enable termination protection on any instance you cannot afford to lose.

💰 EC2 Pricing Models

AWS does not have just one price for EC2 — it offers five pricing models so you can match your spending to your actual usage patterns. Choosing the right model can save you up to 90% compared to the default pricing.

Think of it like buying a flight ticket: last-minute full-price (on-demand), advance booking discount (reserved), bidding for an unsold seat (spot), subscription bundle (savings plans), or renting the entire plane (dedicated host).

Figure 9: Overview of the five EC2 pricing models — choose based on workload predictability and commitment level

On-Demand

On-Demand pricing means you pay for compute capacity by the second (Linux) or by the hour (Windows) with no long-term commitments or upfront payments.

  • Best for: Unpredictable workloads, short-term projects, new applications you are testing, development and test environments
  • Flexibility: Start and stop any time — you only pay while the instance is running
  • Cost: Highest per-unit cost of all pricing models — you pay a premium for the flexibility
  • Free Tier: New AWS accounts get 750 hours/month of t2.micro or t3.micro On-Demand for 12 months

💡 Real-world example: You build a demo application to show a client next week. You launch an On-Demand EC2, run it for 3 days during the demo period, then terminate it. You pay only for those 3 days.

Spot Instances

Spot Instances let you use spare AWS capacity at discounts of up to 90% compared to On-Demand prices.

AWS has data centres full of servers. At any given moment, not all of them are being used by customers. Spot lets you bid for this unused capacity at a huge discount — but there is a catch: AWS can interrupt and reclaim your Spot Instance with 2 minutes notice when they need the capacity back.

  • Best for: Batch processing, data analysis, machine learning training, video rendering — any work that can tolerate interruptions or be restarted
  • Not suitable for: Web servers, databases, or any application where sudden termination would cause problems
  • Savings: Up to 90% vs On-Demand
❌ Critical rule: Never run mission-critical applications on Spot Instances — they can be terminated without warning if AWS needs the capacity.

Reserved Instances

Reserved Instances offer discounts of up to 72% compared to On-Demand in exchange for a 1-year or 3-year commitment.

If you know you are going to run a particular instance type in a specific region for at least a year, Reserved Instances make a lot of sense financially.

  • Payment options: All upfront (maximum discount), partial upfront, or no upfront (minimum discount)
  • Types: Standard RI (highest discount, least flexible), Convertible RI (can change instance family, lower discount)
  • Best for: Steady-state workloads — a database server, a web application that runs 24/7

💡 Analogy: Reserved Instances are like signing a 1-year apartment lease. You get a lower monthly rate but you are committed. On-Demand is like a hotel — pay as you go, more expensive, but no commitment.

Savings Plans

Savings Plans offer discounts of up to 66% in exchange for committing to a specific dollar amount of usage per hour for 1 or 3 years.

Unlike Reserved Instances which lock you to a specific instance type and region, Savings Plans are more flexible — your committed spend can apply to any instance type or size within the plan's scope.

  • Types: Compute Savings Plans (most flexible — apply to any EC2, Lambda, Fargate), EC2 Instance Savings Plans (highest discount, less flexible)
  • Best for: Organisations that want Reserved Instance-level savings but need flexibility to change instance types as their architecture evolves

Dedicated Hosts

A Dedicated Host is a physical server in an AWS data centre that is exclusively yours — no other AWS customer shares the underlying hardware.

  • Best for: Compliance requirements (some regulations require dedicated hardware), software licensing tied to physical cores or sockets (e.g., Oracle, SQL Server)
  • Cost: Most expensive option — you pay for the entire physical host
  • Flexibility: You choose how to slice the host into instances

💡 Dedicated Instances vs Dedicated Hosts: Dedicated Instances run on hardware dedicated to your account but AWS manages the physical host placement. Dedicated Hosts give you visibility and control over the specific physical server — needed for certain licensing audits.

Figure 10: EC2 pricing model decision tree — use this to pick the right model for each workload

⚡ Pricing comparison summary:
On-Demand (baseline 100%) → Reserved Instances (save ~72%) → Savings Plans (save ~66%) → Spot Instances (save ~90%, interruptible) → Dedicated Host (most expensive)

📝 Overall Summary

  • SSH (port 22): Used to connect to Linux EC2 instances — three methods: EC2 Instance Connect (browser, easiest), SSH terminal with .pem key (Linux/Mac), PuTTY with .ppk key (Windows).
  • RDP (port 3389): Used to connect to Windows EC2 instances — provides a full graphical desktop; requires decrypting the Windows password with your .pem key file.
  • Changing instance type: Requires stopping the instance first — cannot be done while running; enables vertical scaling (upgrade/downgrade CPU and RAM).
  • Stop protection: Prevents accidental stop actions; protects running background processes and services from unexpected interruption.
  • Termination protection: Prevents permanent deletion of an EC2 instance; termination is irreversible — always enable on production instances.
  • Shutdown behaviour: Controls whether an OS-initiated shutdown stops or terminates the instance — set to Stop for production servers.
  • EC2 instance states: Pending → Running → Stopping → Stopped → (can restart); Running → Rebooting → Running; Running → Shutting-down → Terminated (permanent).
  • Billing by state: Charged only while Running; Stopped state still incurs EBS storage costs; Terminated incurs no charges.
  • Reboot vs Stop/Start: Reboot keeps the same host and public IP; Stop/Start may move to different host and always assigns a new public IP.
  • Five pricing models: On-Demand (flexible, most expensive), Spot (cheapest, interruptible), Reserved (committed term, up to 72% off), Savings Plans (flexible commitment), Dedicated Host (physical server, compliance/licensing).

⏱️ Time: 30–40 minutes

💰 Cost: Free tier eligible (t2.micro)

⭐ Level 1 — Project 2: Break & Fix SSH

🎯 Objective: Deliberately remove the SSH rule from your Security Group, watch the connection fail, then fix it yourself.

⏱️ Time: 15–20 minutes

💰 Cost: Free tier eligible

💡 Outcome: You stop being scared of errors — you know what causes them and how to fix them. This is the #1 troubleshooting question in cloud interviews.

  1. Go to EC2 → Security Groups. Select the Security Group attached to your instance. Click Edit inbound rules.

  2. Delete the SSH rule (port 22). Click Save rules.

    📸 Screenshot: Deleting the SSH inbound rule from the Security Group

  3. Now try to SSH into the instance (via EC2 Instance Connect or terminal). It will hang and time out.

    📸 Screenshot: SSH connection timeout — the expected failure after removing port 22

  4. Go back to the Security Group → Edit inbound rules → Add rule → Type: SSH, Source: My IP → Save rules.

    📸 Screenshot: SSH inbound rule restored — source set to My IP for better security

  5. Connect again — it works. This time you changed the source to My IP instead of 0.0.0.0/0 — that is a security improvement you made yourself.

⚡ Interview story ready: "I was testing SSH connectivity to an EC2 instance. I intentionally removed port 22 from the Security Group to understand what happens, then restored it. This hands-on experiment helped me build a systematic troubleshooting approach for SSH issues."

⭐⭐⭐ Level 3 — Project 5: Linux Web Server Setup

🎯 Objective: Install Nginx, create a custom HTML page, and serve it from your EC2 — your first real deployed website on a cloud server.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier eligible

⭐⭐⭐⭐ Level 4 — Project 8: Backup Mindset — AMI Create & Recover

🎯 Objective: Create an AMI (Amazon Machine Image) of your running server, terminate the original instance, then launch a fresh one from your backup — the complete disaster recovery cycle.

⏱️ Time: 20–30 minutes

💰 Cost: Small EBS snapshot cost (~$0.05/GB/month) — terminate the new instance after the exercise

💡 Outcome: You understand recovery — "I deleted it but I can get it back from my AMI."

  1. With your Nginx web server running from Project 5, create an AMI: select instance → Actions → Image and templates → Create image. Give it a name like my-nginx-server-backup. Click Create image.

    📸 Screenshot: Create image dialog — naming the AMI before creation

  2. Go to EC2 → Images → AMIs. Wait for the AMI status to change from Pending to Available.

    📸 Screenshot: AMI status showing Available in the AMIs list

  3. Disable termination protection on the original instance (if enabled), then Terminate it. Confirm the termination — it is gone.

  4. Now recover: go to your AMI → Launch instance from AMI. Use the same key pair and Security Group. Launch it.

    📸 Screenshot: Launching a new instance from the custom AMI backup

  5. Once running, get the new Public IP. Open it in a browser — your Nginx page loads. The backup worked.

    📸 Screenshot: Nginx page loading from the recovered instance — backup and restore confirmed

  6. Cleanup: Stop the new instance. Delete the AMI (EC2 → AMIs → Deregister) and the associated EBS snapshot (EC2 → Snapshots → Delete) to avoid ongoing storage charges.

⭐⭐⭐⭐⭐ Level 5 — Project 9: Vertical Scaling Performance Test

🎯 Objective: Observe the performance difference between a t2.micro and a t3.medium by running a CPU stress test on both, then document why scaling matters — not just how to do it.

⏱️ Time: 30–40 minutes

💰 Cost: t3.medium is not free-tier eligible — stop immediately after exercise. Expected cost: under $0.05.

💡 Outcome: You understand why scaling matters, not just how to click the button.

  1. Start with your t2.micro. Connect via SSH. Install the stress tool:

    sudo yum install stress -y

  2. Run a CPU stress test for 30 seconds and observe the load:

    stress --cpu 1 --timeout 30

    While stress is running, open a second terminal window and watch CPU usage:

    top

    📸 Screenshot: CPU at 100% on t2.micro during stress test — the instance is overwhelmed

  3. Stop the instance. Change the instance type to t3.medium (Actions → Instance settings → Change instance type). Start it again.

    📸 Screenshot: Changing instance type to t3.medium after stopping

  4. Connect again. Install stress again (sudo yum install stress -y). Run the same test:

    stress --cpu 1 --timeout 30

    Watch top again. The load average stays much lower because the t3.medium has more CPU capacity.

    📸 Screenshot: Same stress test on t3.medium — lower CPU % showing better capacity

  5. Cleanup: Stop the instance immediately after comparing. Change back to t2.micro if you want to keep it within free tier for future projects.

⚡ What you just proved: Vertical scaling is not just "making the number bigger" — it directly changes how your server handles load. This is the foundation of capacity planning in every cloud role.

⭐⭐⭐⭐⭐⭐ Level 6 — Project 10: "Website Down" Incident Simulation

🎯 Objective: Simulate a production outage — stop an EC2 instance, watch the website fail, then diagnose and restore it step by step using a real incident checklist.

⏱️ Time: 25–35 minutes

💰 Cost: Free tier eligible

💡 Outcome: This becomes a perfect STAR interview story about incident diagnosis and resolution.

  1. Make sure your Nginx web server instance is running and your custom page loads in a browser. Note the URL (public IP).

  2. Simulate the crash: Stop the instance via Instance state → Stop instance.

  3. Try to load the website in your browser. It will fail — timeout or "This site can't be reached."

    📸 Screenshot: Browser error confirming the website is down after instance was stopped

  4. Diagnose step by step — work through this checklist as a real engineer would:
    Check 1: Go to EC2 → Instances. What is the instance state? (It shows Stopped.)
    Check 2: Is the Security Group still correct? (Yes — we did not change it.)
    Check 3: What changed? (We stopped the instance — that is the root cause.)

    📸 Screenshot: EC2 console showing instance in Stopped state — root cause identified

  5. Fix: Start the instance. Wait for Running state. Note the new Public IP (it changed!). Update your browser to use the new IP.

    📸 Screenshot: Website restored and loading from the new public IP after restarting the instance

⚡ Your STAR story: S — Our EC2 web server went down. T — Restore service and identify root cause. A — Checked instance state (stopped), checked Security Group (unchanged), confirmed root cause was instance state, started the instance, updated client with new IP. R — Service restored in under 5 minutes, documented the IP change behaviour and proposed Elastic IP as prevention.

⭐⭐⭐⭐⭐⭐⭐ Level 7 — Project 12: Production-Ready EC2 Setup

🎯 Objective: Build a full production-style EC2 deployment from scratch — web server, custom site, locked-down security, protection features, correct sizing, AMI backup, and a simulated failure recovery. Document everything.

⏱️ Time: 60–90 minutes

💰 Cost: Free tier eligible (use t2.micro or t3.micro)

💡 Outcome: You can say in an interview: "I deployed and managed a production-style EC2 server — handled access control, cost decisions, and failure recovery." That is job-level.

Figure: Project 12 target architecture — a production-style EC2 deployment

Phase 1: Launch with production-grade settings

  1. Launch a fresh Amazon Linux 2 EC2 instance (t3.micro). Name it prod-web-server-01.

  2. Security Group — set it up with exactly two rules:
    — HTTP port 80: Source 0.0.0.0/0 (website must be public)
    — SSH port 22: Source My IP only (only you can SSH in — nobody else)

    📸 Screenshot: Locked-down Security Group — HTTP open to world, SSH restricted to My IP only

Phase 2: Configure the web server

  1. Connect via EC2 Instance Connect. Install Nginx and create your custom site:

    sudo amazon-linux-extras install nginx1 -y
sudo systemctl start nginx
sudo systemctl enable nginx
sudo bash -c 'cat > /usr/share/nginx/html/index.html <<EOF
<html>
<head><title>Production Server</title></head>
<body>
  <h1>Production Web Server</h1>
  <p>Deployed on EC2 — Server: prod-web-server-01</p>
</body>
</html>
EOF'

  2. Open the public IP in a browser — confirm your page loads.

    📸 Screenshot: Production site live and loading from the EC2 public IP

Phase 3: Apply production protections

  1. Enable termination protection: Actions → Instance settings → Change termination protection → Enable → Save.

  2. Enable stop protection: Actions → Instance settings → Change stop protection → Enable → Save.

    📸 Screenshot: Instance details showing both protections enabled

Phase 4: Create backup

  1. Create an AMI: Actions → Image and templates → Create image → name it prod-web-server-01-backup-v1 → Create image. Wait for it to be Available.

    📸 Screenshot: Production AMI backup showing Available status

Phase 5: Simulate failure and recover

  1. Disable both protections (so you can simulate a failure). Stop the instance. Your website is now "down."

  2. Launch a new instance from your AMI backup. Use the same Security Group. Start it.

  3. Get the new public IP. Confirm your website loads from the recovered instance.

    📸 Screenshot: Website recovered and live from AMI-restored instance

Phase 6: Document your work

  1. Write a brief incident + recovery report in a text file covering: what you built, security decisions made (why SSH is restricted to My IP), what failure you simulated, how you recovered, and what you would do differently in a real environment (Elastic IP, auto-scaling, load balancer).

I documented the full process including what I would improve in a real production environment."

💡 Hint

Can you change instance type while it is running? What state must it be in first?

3. A junior team member accidentally terminated the production database server. How could this have been prevented?

💡 Hint

There are at least two AWS features that could have prevented this — one at the instance level and one at the user permissions level (coming in a future session).

💡 Hint

Think about the two components of an EC2 instance: the compute (CPU/RAM) and the storage (EBS disk). Which one continues even when the instance is stopped?

Think about the public IP address and which physical host the instance runs on after each operation.
