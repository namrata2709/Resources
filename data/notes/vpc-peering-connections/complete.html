📖 Introduction

This lab covers VPC Peering Connections — one of the most important AWS networking concepts for real-world architecture and certification exams. You will connect two isolated VPCs privately, configure route tables on both sides, and troubleshoot connectivity failures using a structured diagnostic approach.

The lab uses a real-world scenario: a web application in one VPC must reach a MySQL database in a completely isolated VPC that has no internet gateway. Peering is the only path.

📚 Background / Theory

🌐 What is VPC Peering?

Figure 1: Before peering (left) and after peering (right) – two isolated VPCs connected privately

Imagine you have two completely separate houses (VPCs) in the same neighbourhood (AWS). Each house has its own walls, its own locks, and its own private world inside. Normally, to send something from one house to the other, you'd have to go out onto the public street (the internet) — which is risky and slow.

A VPC Peering Connection is a private, direct network link between two VPCs that lets instances communicate as if they were in the same network, without ever touching the public internet.

💡 Key Insight: VPC Peering works completely within the AWS backbone network. The traffic never leaves AWS infrastructure, which means lower latency, no data transfer costs to the internet, and far better security.

🤔 Why Do We Need VPC Peering?

Figure 2: Common VPC Peering use cases in real-world architectures

By default, every VPC is its own island. Traffic cannot flow between VPCs unless you explicitly connect them. This is actually a great security feature — you don't want random VPCs talking to your production database. But sometimes you do want controlled communication between VPCs. Common real-world reasons include:

  • Centralized database: One VPC holds a shared MySQL/PostgreSQL database; multiple application VPCs need access.
  • Cross-account sharing: Partner companies or internal teams in different AWS accounts need to exchange data securely.
  • Cross-region architectures: Services in different AWS regions need a private link.
  • Microservices isolation: Each service lives in its own VPC for blast-radius control, but they still need to communicate.

In the lab, we have exactly this scenario: a Lab VPC (containing a web application / inventory app in a public subnet) and a Shared VPC (containing a MySQL database in a completely private subnet with no internet gateway). The app needs to talk to the database — and peering is how we make that happen safely.

⚡ The Golden Rule:The Shared VPC has NO internet gateway — the only way to reach its database is through the VPC peering connection. This is intentional, and it's exactly the kind of secure architecture you'd build for a production database tier.

⚙️ How VPC Peering Works

Figure 3: Route tables after peering – each VPC learns the other's CIDR via the peering connection (pcx-id)

Think of a VPC peering connection like a two-key safe. Both people need to turn their keys before the safe opens. Neither side can force a connection — both must agree.

There are three phases to getting a peering connection working:

  1. Request: One VPC (the requester) sends a peering request to another VPC (the accepter).
  2. Accept: The target VPC owner must explicitly accept the request. This is a critical security step — you can't just start sending traffic to someone else's VPC.
  3. Route: Both VPCs must update their route tables to know how to forward traffic over the peering link. Without this step, even an accepted peering connection won't carry traffic.
✅ Important:VPC peering is non-transitive — if VPC A peers with VPC B, and VPC B peers with VPC C, VPC A cannot reach VPC C through VPC B. Each pairing needs its own direct peering connection.

  • Shared VPC: CIDR 10.5.0.0/16 — has only private subnets and NO internet gateway. The MySQL RDS database lives here, completely isolated.

Step-by-Step: Creating the Peering Connection

  1. In the AWS Console, navigate to VPC → Peering Connections.
  2. Click Create Peering Connection.
  3. Fill in:
    • Name tag:Lab-Peer
    • VPC (Requester): Lab VPC
    • VPC (Accepter): Shared VPC
  4. Click Create Peering Connection, then OK.
💡 Why do we need to "Accept"? Even when both VPCs are in the same account, the acceptance step exists for safety. In real life, the accepter VPC may belong to a different team, department, or even company. Acceptance means that owner consciously approves the connection.
  1. Select the newly created Lab-Peer peering connection.
  2. Choose Actions → Accept Request → Yes, Accept.
  3. Close the pop-up.
✅ Status Check: After acceptance, the peering connection status should change from Pending Acceptance to Active. If you misclick and the pop-up disappears, go to Peering Connections and look for pending approvals.
⚡ Requester and Accepter — both sides must agree. The connection will show as Pending Acceptance until the accepter approves.

🗺️ Task 2 – Configuring Route Tables

📸 Screenshot: Lab VPC route table showing the new peering route to 10.5.0.0/16

📸 Screenshot: Shared VPC route table showing the return peering route to 10.0.0.0/16

Accepting the peering connection only tells AWS the two VPCs want to talk. The route tables tell the network how to actually send packets there. Without updated routes, traffic will never find its way across.

Think of it like this: the peering connection builds the bridge, but the route table is the road sign that says "To Shared VPC → take the bridge."

Updating the Lab VPC Route Table

  1. Go to VPC → Route Tables.
  2. Select Lab Public Route Table (the one associated with Lab VPC).
  3. Click the Routes tab → Edit routes → Add route.
  4. Set:
    • Destination:10.5.0.0/16 (Shared VPC's CIDR range)
    • Target: Peering Connection → Lab-Peer
  5. Click Save routes → Close.
💡 What does this route say? "Any packet destined for an IP in the 10.5.x.x range — send it through the Lab-Peer peering connection." Without this, the Lab VPC would drop or misroute packets headed to the Shared VPC.

Updating the Shared VPC Route Table

  1. Now select Shared-VPC Route Table.
  2. Click Edit routes → Add route.
  3. Set:
    • Destination:10.0.0.0/16 (Lab VPC's CIDR range)
    • Target: Peering Connection → Lab-Peer
  4. Click Save routes → Close.
✅ Why both directions?Route tables must be updated on BOTH sides of a VPC peering connection — traffic needs a path to go AND a path to return. Forgetting one side is the #1 mistake in this lab.

Figure 6: Both route tables must have entries pointing to the peering connection for two-way communication

❌ Common Mistake: Selecting the private route table instead of the correct one. Always double-check the route table name before editing. The Lab VPC has both a public and private route table — only the Lab Public Route Table needs the peering route for this lab.

📡 ICMP & the Ping Test (Bonus Lab Demonstration)

📸 Screenshot: AWS CLI output confirming peering connection status is active

📸 Screenshot: OS-level routing table on the EC2 instance showing VPC CIDR entries

The professor added a clever bonus demonstration to prove the peering works even before the database step. This used ICMP (Internet Control Message Protocol) — the protocol behind the ping command.

What is ICMP / Ping?

ICMP is a network diagnostic protocol used for error reporting and reachability testing. The ping command sends ICMP echo requests to check if a host is alive and reachable.

The name "ping" actually comes from sonar — like a submarine sending out a sound pulse and listening for an echo back. You send a packet, and if the device is there and reachable, it pings back. It's also sometimes said to stand for "Packet Internet Groper" — you're groping in the dark looking for another device.

ICMP is also the foundation of traceroute, which lets you see every "hop" a packet takes through the network on its way to a destination — incredibly useful for diagnosing where traffic is getting stuck.

The Bonus Test Setup

Before creating the peering connection, the professor launched a second EC2 instance ("target") in the Shared VPC (the isolated one). This instance:

  • Was placed in the Shared VPC's private subnet
  • Had a security group rule allowing ICMP (IPv4) from any source
  • Had only a private IP address — no public IP

Then, from the App Server (in Lab VPC), they tried to ping the target instance's private IP. Before peering — silence. No response. After peering and adding routes — pings succeed, proving the private connection works at the network level.

💡 Why allow ICMP from "any"? In a lab context, this is fine. In production, you'd restrict ICMP to known IP ranges. But since we don't know exactly which IP might be pinging (could come from various places within the VPC), setting the source to 0.0.0.0/0 makes the demo straightforward.

🔍 Troubleshooting: When the Lab Breaks

Figure 7: VPC Peering troubleshooting checklist — work through each layer in order

This particular lab encountered a real-world failure between November 2025 and February 2026 — not because the lab instructions were wrong, but because AWS upgraded its default database engine version, breaking compatibility with the client software on the EC2 instance. This is an amazing real-world lesson in version management.

❌ The Symptom: The Inventory application shows a database connection error even after the peering connection is correctly set up. The peering works — but the application layer can't communicate with the database.

What Actually Went Wrong

The CloudFormation template that built the lab specified a MySQL database engine but did not pin the version. When AWS updated its default MySQL version from 8.0.x to 8.4.7, the lab broke because:

  1. Authentication method changed: MySQL 8.4.x defaults to caching_sha2_password — a more secure but newer auth method. The EC2 client software is old and doesn't support it.
  2. DNS reverse lookup requirement: MySQL 8.4.x by default requires a reverse DNS lookup on connecting clients. The EC2 app server's IP couldn't be resolved, so MySQL refused the connection entirely.
⚡ Pinning database engine versions in CloudFormation templates is critical — failing to do so means AWS may automatically provision a newer, incompatible version when the template runs.

How to Check What's Wrong

You can inspect the RDS logs in the AWS Console (RDS → Databases → your DB → Logs & Events). Look for messages about:

  • "Could not be resolved" — this is the DNS reverse lookup failure
  • Authentication-related errors about caching_sha2_password

The Fix (If You Had Permissions)

The simplest fix would be adding two lines to the CloudFormation template under the database resource to specify an older, compatible engine version:

EngineVersion: "8.0"
AutoMinorVersionUpgrade: true

This tells AWS to use MySQL 8.0.x (which is backward-compatible with the old EC2 client) and to auto-apply minor version upgrades within that family. This would give the lab compatibility for several more years.

🗄️ Database Version Mismatch – A Real-World Lesson

The lab failure illustrates something every cloud engineer encounters in the real world: version drift. Systems that worked perfectly for years suddenly break when one component gets upgraded.

According to AWS documentation, MySQL 8.4 introduced significant changes to default authentication and parameter groups compared to MySQL 8.0. Existing applications relying on older client libraries may need updates before migrating to 8.4.

📚 Source:AWS RDS MySQL Version Management

What Is a Parameter Group?

MySQL (and other RDS engines) use parameter groups to control hundreds of configuration settings — think of it as a settings file for the database. The default parameter group for MySQL 8.4 includes settings like authentication_policy set to require the new SHA2 method.

Changing the parameter group could allow old clients to connect again, but it requires database-level permissions in the lab environment.

Lessons for Production Environments

  • Always pin versions: Specify the exact engine version in CloudFormation/Terraform so upgrades happen on your schedule, not AWS's.
  • Test upgrades in staging first: Never upgrade production databases without testing compatibility in a staging environment.
  • Upgrade client software together: When you upgrade a database engine, also update the client libraries on applications that connect to it.
  • Plan maintenance windows: Database upgrades require downtime. Communicate to users in advance and choose low-traffic windows.
  • Stay current (but not bleeding edge): Being 18 months behind on patches leaves you vulnerable. But jumping to the absolute latest immediately carries its own risks — let others discover the bugs first, then upgrade.
✅ The Balance: A practical approach is to stay 1-2 minor versions behind the latest, apply security patches promptly, and do major version upgrades quarterly with proper testing.

🛡️ Security & Best Practices for VPC Peering

CIDR Overlap Prevention

VPC peering requires non-overlapping CIDR blocks — two VPCs cannot peer if their IP ranges conflict. In the lab, this is deliberately set up: Lab VPC uses 10.0.0.0/16 and Shared VPC uses 10.5.0.0/16. Plan your IP addressing carefully from the start.

Least-Privilege Security Groups

Even with a peering connection, Security Groups act as the final gatekeeper. Just because two VPCs can route to each other doesn't mean all instances can talk to all other instances. You still need to explicitly allow traffic in Security Groups:

  • Allow only the specific port needed (e.g., port 3306 for MySQL)
  • Set the source to the CIDR of the other VPC, not 0.0.0.0/0
  • Use separate Security Groups for different tiers (web, app, database)

ACLs vs Security Groups

Network ACLs (NACLs) are stateless and operate at the subnet level. Security Groups are stateful and operate at the instance level. Security Groups are stateful — return traffic is automatically allowed without needing a separate outbound rule. NACLs require explicit rules for both directions.

For most peering setups, Security Group changes are sufficient. NACLs usually don't need changes unless they've been hardened with specific deny rules.

Monitoring Peering Traffic

Enable VPC Flow Logs to capture information about IP traffic going to/from network interfaces. This helps with troubleshooting and security auditing across peered VPCs.

🌐 Other AWS Network Connection Options

Figure 8: VPC Peering vs Transit Gateway — when to choose each option

VPC Peering is one tool in the networking toolbox — choose Transit Gateway when you have many VPCs to connect, as full-mesh peering requires N*(N-1)/2 connections. Here's when to use what:

Connection TypeUse CaseInternet Involved?
VPC PeeringTwo VPCs that need private communicationNo
AWS Transit GatewayHub-and-spoke for many VPCs (avoids peering mesh complexity)No
AWS Direct ConnectOn-premises data center to AWS (dedicated private line)No
Site-to-Site VPNOn-premises to AWS over encrypted internet tunnelYes (encrypted)
Internet GatewayVPC resources to/from the public internetYes
NAT GatewayPrivate subnet resources initiating outbound internet connectionsYes (outbound only)
💡 When to use Transit Gateway instead of Peering: If you have more than 3-4 VPCs that need to communicate with each other, VPC peering creates a complex mesh (N*(N-1)/2 connections). Transit Gateway acts as a central router — all VPCs connect to it and can reach each other without individual peering connections.

🔍 Ext. Task 1 — Inspect CIDR Ranges and Validate No Overlap

VPC peering fails silently if CIDR blocks overlap — always verify with aws ec2 describe-vpcs before creating a connection. Before creating any peering connection, always verify the ranges are distinct.

  1. Go to VPC → Your VPCs. Note the IPv4 CIDR of each VPC.
  2. Open CloudShell (top nav → CloudShell icon) and run:
aws ec2 describe-vpcs --query 'Vpcs[*].{ID:VpcId,CIDR:CidrBlock,Name:Tags[?Key==`Name`].Value|[0]}' --output table
  1. Verify CIDRs don't overlap with Python:
python3 -c "
import ipaddress
lab = ipaddress.IPv4Network('10.0.0.0/16')
shared = ipaddress.IPv4Network('10.5.0.0/16')
print('Overlaps:', lab.overlaps(shared))
print('Lab range:', list(lab.hosts())[0], '-', list(lab.hosts())[-1])
print('Shared range:', list(shared.hosts())[0], '-', list(shared.hosts())[-1])
"
✅ Expected: Overlaps: False — the two CIDRs are completely distinct. If they overlapped, the peering connection creation would fail.

🖧 Ext. Task 2 — Inspect Routing Tables Before and After Peering

This task teaches you to read route tables as a network engineer — understanding exactly what each route entry means and how traffic flows.

  1. Before peering: note the routes in both VPC route tables (Lab VPC and Shared VPC).
  2. After completing Task 2 (adding routes), view the updated route table via CLI:
aws ec2 describe-route-tables \
  --query 'RouteTables[*].{ID:RouteTableId,VPC:VpcId,Routes:Routes}' \
  --output json | python3 -m json.tool
  1. Identify the entry with GatewayId starting with pcx- — that is the peering route.
  2. Confirm both VPCs have a route pointing to the same pcx- ID.
💡 Reading route priority: AWS uses longest-prefix matching. A route for 10.5.0.0/16 is more specific than 0.0.0.0/0 and will win when a packet targets that range — the packet goes over peering, not out to the internet.

🔬 Ext. Task 3 — Test Connectivity with netcat and ping

Before the Inventory app test, prove the network layer is working using basic Linux tools.

  1. SSH into App-Server (Lab VPC). Get the private IP of the database server from the EC2 console.
  2. Test ICMP (ping):
ping -c 4 <database-private-ip>
  1. Test TCP port reachability:
nc -zv <database-private-ip> 3306
  1. Test with verbose output:
nc -zvw 5 <database-private-ip> 3306 2>&1
✅ Connection to <ip> 3306 port [tcp/mysql] succeeded! means the route table AND security group are both correct. If ping succeeds but nc fails, the security group is blocking port 3306 specifically.
❌ Timeout vs Refused: "Connection timed out" = dropped by security group or NACL (silent drop). "Connection refused" = packet arrived but the port isn't listening. These tell you very different things about where the problem is.

🔐 Ext. Task 4 — SSH Tunneling Through App Server to Database Server

The database server has no public IP — you can only reach it from inside the Lab VPC. This is called a bastion host pattern: the App Server acts as a jump host.

scp -i vpc-lab-key.pem vpc-lab-key.pem ec2-user@<app-server-public-ip>:~/

# Expected: curl: (28) Connection timed out

✅ You can now inspect the full peering metadata programmatically — exactly how DevOps engineers audit network configurations in production.

💥 Ext. Task 6 — Simulate and Recover from a Routing Failure

This task teaches the most common VPC peering mistake: A peering connection can be Active while traffic still fails — missing route table entries are the most common cause of VPC peering connectivity issues.

  1. Confirm the application works — open it in a browser and verify data loads.
  2. Go to VPC → Route Tables → Lab VPC Public Route Table → Routes → Edit routes.
  3. Delete the route: Destination 10.5.0.0/16. Save.
  4. Refresh the application page.
❌ Expected result: Database connection failed — the application can no longer reach the database even though the peering connection is still Active.
  1. Run nc -zv <database-endpoint> 3306 from the EC2 terminal to confirm the TCP connection also fails.
  2. Restore the route (Destination: 10.5.0.0/16, Target: the peering connection).
  3. Verify the application recovers within 10–30 seconds.
💡 The lesson: Peering connection = Active means the connection exists. It does NOT mean traffic flows. Traffic only flows when both VPCs have the correct route table entries pointing to the peering connection ID. This is the #1 mistake in VPC peering setups.

🔐 Ext. Task 7 — Break and Fix Security Group Rules

Security groups are stateful firewalls that work independently of routing — a correct route table with a wrong security group still blocks traffic.

  1. Go to EC2 → Security Groups. Find the database security group.
  2. Note the current inbound rule: Type=MySQL, Port=3306, Source=10.0.0.0/16.
  3. Delete this rule. Save.
  4. Try nc -zv <database-endpoint> 3306 — connection refused or timeout.
  5. Try mysql -h <database-endpoint> -u admin -p — hangs indefinitely.
❌ The TCP connection fails even though the route table is correct. Security groups block traffic at the instance level.
  1. Restore the rule: Add inbound rule — Type: MySQL/Aurora | Port: 3306 | Source: 10.0.0.0/16.
  2. Confirm nc -zv <database-endpoint> 3306 succeeds within 30 seconds.
✅ Security group changes take effect immediately — no reboot needed.
💡 Debugging order for production incidents: (1) Is the peering connection Active? (2) Are routes present in both VPCs? (3) Does the security group allow the traffic? (4) Do Network ACLs block it? Run through these in order every time.

🌐 Ext. Task 8 — Network ACL Investigation

📸 Screenshot: Network ACL showing both inbound and outbound rules — both required for stateless NACL

Network ACLs are stateless — you must explicitly allow both inbound AND outbound traffic, including ephemeral ports for return traffic. They operate at the subnet level — they can block traffic even when security groups allow it.

  1. Find the Network ACL associated with the Shared VPC private subnet:
aws ec2 describe-network-acls \
  --query 'NetworkAcls[*].{ID:NetworkAclId,VPC:VpcId,InboundRules:Entries[?Egress==`false`]}' \
  --output json | python3 -m json.tool
  1. In the AWS console: VPC → Network ACLs → select the ACL for the Shared VPC subnet.
  2. View Inbound rules — confirm there is an ALLOW rule for TCP port 3306 or ALL traffic from 10.0.0.0/16.
  3. To test the impact: add a DENY rule with rule number 50 for port 3306 from 10.0.0.0/16. (Lower number = higher priority — this DENY fires before the ALLOW.)
❌ Connection fails — NACL DENY overrides security group ALLOW. Remember: NACLs are stateless. You also need an outbound ALLOW for return traffic (ephemeral ports 1024–65535).
  1. Delete the DENY rule to restore access.
💡 SG vs NACL: Security groups are stateful (return traffic is automatically allowed). NACLs are stateless (you must explicitly allow inbound AND outbound). NACL rules are evaluated in number order — first match wins.

📊 Ext. Task 9 — Enable and Read VPC Flow Logs

📸 Screenshot: VPC Flow Log entries in CloudWatch showing ACCEPT and REJECT records with key fields annotated

VPC Flow Logs capture ACCEPT and REJECT decisions for every network flow — essential for diagnosing connectivity failures. They record metadata about every network connection attempt — accepted and rejected. Essential for production debugging.

  1. Go to VPC → Your VPCs → Lab VPC → Flow Logs tab → Create flow log.
  2. Settings:
    • Filter: All (captures accepted and rejected)
    • Destination: CloudWatch Logs
    • Log group: create /vpc/efs-lab-flows
    • IAM role: create new or use existing VPC flow logs role
  3. Generate some traffic: run nc -zv <database-endpoint> 3306 a few times.
  4. Go to CloudWatch → Log Groups → /vpc/efs-lab-flows. Wait 2–5 minutes for logs to appear.
  5. Each log entry contains: srcaddr dstaddr srcport dstport protocol packets bytes action
# Filter for accepted MySQL connections
aws logs filter-log-events \
  --log-group-name /vpc/efs-lab-flows \
  --filter-pattern "3306 ACCEPT" \
  --query 'events[*].message' \
  --output text
💡 In production incidents, Flow Logs are the first place to look when traffic mysteriously fails. An ACCEPT log with no response suggests a security group problem. A REJECT log confirms a NACL or SG is dropping the traffic.

💰 Cost Note: Flow logs to CloudWatch incur a small ingestion charge. Delete the flow log and log group after this task to avoid unexpected costs.

🏗️ Ext. Task 10 — Compare VPC Peering vs Transit Gateway

Figure 9: Full-mesh VPC Peering vs Transit Gateway hub-and-spoke topology

VPC Peering is not always the right tool. VPC Peering requires N*(N-1)/2 connections for a full mesh; Transit Gateway requires only 1 attachment per VPC — use Transit Gateway when connecting 4 or more VPCs. Understanding when to switch to Transit Gateway is a common interview topic.

FactorVPC PeeringTransit Gateway
CostNo hourly charge — pay data transfer only$0.05/hr per attachment + data transfer
Connections requiredN*(N−1)/2 for full mesh (10 VPCs = 45 connections)1 attachment per VPC
Transitive routing❌ Not supported✅ Supported
Cross-region✅ Supported (Inter-Region Peering)✅ Supported (TGW Peering)
Cross-account✅ Supported✅ Supported
BandwidthNo limit — uses full instance bandwidthUp to 50 Gbps per VPC attachment
Best for2–3 VPCs, simple topology, cost-sensitive4+ VPCs, hub-and-spoke, shared services
💡 Formula to memorise: For N VPCs in a full mesh, you need N×(N−1)÷2 peering connections. For 5 VPCs: 10 connections. For 10 VPCs: 45 connections. Past 3–4 VPCs, Transit Gateway is almost always simpler to manage.
  1. Draw the topology for 4 VPCs connected with full peering — how many connections?
  2. Now draw the same 4 VPCs connected through a single Transit Gateway hub — how many attachments?
✅ 4 VPCs full mesh = 6 peering connections. 4 VPCs via TGW = 4 attachments + 1 TGW. At scale, TGW wins every time on operational complexity.

💬 Ext. Task 12 — Architecture Discussion: Why Separate VPCs?

This task prepares you for system design and behavioural interview questions.

💡 Question: "Why would a company put the application and database in separate VPCs instead of one VPC?"

Strong answers include all of these points:

ReasonExplanation
Security isolationA breach in the application VPC cannot directly access the database network — the peering connection is the only path and it's controlled by security groups.
Team separationDifferent teams own different VPCs. The database team controls the Shared VPC; the application team controls the App VPC. Neither needs console access to the other's VPC
Blast radiusA misconfiguration in the app VPC (e.g., an overly permissive security group) cannot affect the database VPC's security posture
ComplianceRegulators often require database resources to be in isolated network segments — separate VPCs satisfy this cleanly
Shared servicesOne Shared VPC (DNS, logging, monitoring) can be peered to many application VPCs — centralises operations without merging networks
Multi-account strategyAWS recommends separate accounts per environment. VPC peering works cross-account — each account maintains its own network perimeter
✅ In your interview answer, always mention at least 3 of these. Lead with security isolation — it's the most common reason and interviewers look for it first.

🧹 Ext. Task 13 — Clean Up Resources Correctly

Deleting resources in the wrong order leaves orphaned blackhole routes — always delete the peering connection before removing route table entries. Deleting resources in the wrong order can leave orphaned items that generate unexpected charges. Follow this order.

  1. Delete VPC Flow Logs (if created in Ext. Task 9) — CloudWatch → Log Groups → delete the flow log group.
  2. Delete the Peering Connection — VPC → Peering Connections → select Lab-Peer → Actions → Delete.
  3. Remove peering routes from both route tables — after the peering connection is deleted, any routes pointing to it become blackholes. Delete them:
    • Lab VPC route table: remove the 10.5.0.0/16 route
    • Shared VPC route table: remove the 10.0.0.0/16 route
  4. Terminate EC2 instances (if created for extended tasks).
  5. Delete Security Groups created for extended tasks.
💰 Cost reminder: VPC peering data transfer inside the same region costs ~$0.01/GB. The lab generates negligible traffic. The main cost risk is EC2 instances left running — always terminate them after the lab.

📝 Overall Summary

  • VPC Peering: A private, direct network connection between two VPCs that keeps traffic within the AWS backbone — no internet required.
  • Three-step setup: Request → Accept → Route. Skipping the route table step is the #1 mistake — the connection shows Active but traffic still fails.
  • Route tables are mandatory on BOTH sides: Each VPC must have a route pointing the other's CIDR to the peering connection ID. One missing route breaks connectivity in one direction.
  • Non-transitive by design: A → B → C does NOT give A access to C. Each pair of VPCs that needs to communicate requires its own dedicated peering connection.
  • No overlapping CIDRs: Peered VPCs must have non-conflicting CIDR ranges. Always verify with python3 -c "import ipaddress; print(a.overlaps(b))" before creating a connection.
  • Security groups still apply: Peering enables the routing path. Security groups control which traffic is actually allowed between specific instances. Both must be correct.
  • Network ACLs are stateless: Unlike security groups, NACLs require explicit inbound AND outbound rules. A DENY rule in a NACL overrides any security group ALLOW.
  • Diagnostic order: Peering status → route tables (both VPCs) → security groups → NACLs → DNS → nc port test → MySQL client. Always work from layer 3 to layer 7.
  • VPC Flow Logs: Enable on either VPC to capture ACCEPT/REJECT metadata for every connection attempt. Essential for debugging non-obvious failures.
  • Peering vs Transit Gateway: N×(N−1)÷2 connections for full mesh peering. Past 3–4 VPCs, Transit Gateway is operationally simpler — one attachment per VPC, supports transitive routing.
  • Real-world pattern: Companies separate Application VPCs from Database VPCs to enforce security boundaries, comply with regulations, and allow different teams to own their own networks.
  • Lab debugging lesson: The lab's database connectivity broke due to a MySQL 8.0→8.4 authentication method change — a real-world example of version drift breaking network-layer-correct configurations.

🤔 Reflection Questions

1. You create a VPC peering connection and the status shows Active. The application still cannot reach the database. What do you check first?

💡 Hint

Active means the connection exists — not that traffic flows. Check the route tables in both VPCs. Is there a route for the other VPC's CIDR pointing to the peering connection? If either route is missing, traffic fails in that direction.

2. You run nc -zv <database-endpoint> 3306 and get "Connection timed out." Your route table has the correct peering route. What are the next two things to check?

💡 Hint

Timeout (not refused) typically means the packet is being silently dropped. Check: (1) The database security group — does it allow TCP 3306 from the application VPC's CIDR range? (2) The Network ACL on the database subnet — is there a DENY rule for port 3306 or is there no ALLOW rule for the source IP range?

3. Your company has 6 VPCs that all need to communicate with each other. How many VPC peering connections would a full mesh require? Is there a better approach?

💡 Hint

Full mesh: 6×(6−1)÷2 = 15 connections. Each connection also needs route table entries in both VPCs — so 30 route table updates, 15 peering connections to manage. At 6 VPCs, Transit Gateway (6 attachments, 1 central hub) is significantly simpler to manage and supports transitive routing.

4. A developer says "the application and database are in the same AWS account — why do they need to be in separate VPCs?" Give three strong answers.

💡 Hint

Key answers: (1) Security isolation — a compromise in the app layer cannot directly reach the database network without a separately controlled path. (2) Blast radius reduction — misconfigured security groups in the app VPC don't expose the database. (3) Team/ownership separation — different teams manage different VPCs independently. Also valid: compliance requirements, future multi-account strategy.

5. You need to let VPC A communicate with VPC C, but VPC B is already peered with both. Why can't you just use the existing peering connections?

💡 Hint

VPC peering is non-transitive. Even if A↔B and B↔C exist, traffic from A cannot traverse B to reach C. AWS does not route packets between peering connections. You must create a direct A↔C peering connection — or use Transit Gateway which does support transitive routing.

6. You enable VPC Flow Logs and see REJECT entries for traffic on port 3306 coming from 10.0.1.84. What does this tell you, and what do you fix?

💡 Hint

REJECT in flow logs means a NACL or security group is dropping the packet. 10.0.1.84 is a private IP in the Application VPC subnet (10.0.1.0/24). The database SG inbound rule likely doesn't include this IP range, or a NACL DENY rule is firing first. Check the database security group for a CIDR-based allow of 10.0.0.0/16 on port 3306.
