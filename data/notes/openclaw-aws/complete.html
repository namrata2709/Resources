🧭 Introduction

Picture this: it's 2am, your phone is blowing up, and production is down. You pry open your laptop, squint at CloudWatch dashboards, click through the ECS console, and try to figure out what broke — all while barely awake.

Now imagine instead: you type one WhatsApp message — "check aws" — and within seconds your phone shows you exactly which EC2 instances are stopped, which ECS tasks have failed, and which services have spiked CPU. No browser. No dashboard navigation. Just an answer.

That's the problem OpenClaw solves. It's an open-source AI agent that runs on your own machine, connects to your messaging apps, and executes structured "skills" when you ask in natural language. This session — delivered by Yash Garudkar, a 5-year AWS Community Builder and tech lead, at the AWS User Group Mumbai meetup — walks through building a real AWS health monitoring skill from scratch.

Figure 1: OpenClaw overview — WhatsApp message in, AWS health report out

⚡ The core idea: AI agents become useful for DevOps not by being trained on your infrastructure, but by being given well-defined tools (skills) that call real AWS APIs on demand.

By the end of these notes you will understand how OpenClaw works, how to build and install a skill, how to set up IAM correctly, and how the aws-health skill queries EC2, ECS, and CloudWatch to give you a conversational window into your production environment.

🦀 What is OpenClaw?

OpenClaw is an open-source AI agent that runs locally on your machine (not in the cloud). It acts as a bridge between your messaging apps and executable skills you define. When you send a message, OpenClaw reads it, figures out which skill to run, executes it, and sends the result back — all automatically.

Figure 2: OpenClaw as the router between messaging channels and skills

Why Not Just Use CloudWatch?

CloudWatch dashboards are powerful but have friction: you need a browser, AWS credentials loaded, and the mental overhead of navigating multiple service consoles. At 2am during an incident, that friction costs minutes — and minutes cost money and SLA points.

OpenClaw removes that friction by letting you query your infra state in plain English from any device where you already have WhatsApp or Slack open.

💡 Analogy: Think of OpenClaw as Jarvis from Iron Man — Tony Stark doesn't open dashboards, he just says "Jarvis, what's wrong with the reactor?" and gets an instant answer. OpenClaw is your personal Jarvis for AWS infrastructure.

Key Characteristics

  • OpenClaw runs locally — it is not a SaaS product or hosted in AWS. You control your credentials and data.
  • It connects to WhatsApp, Slack, and Telegram as messaging channels.
  • It executes skills — structured folders of scripts — when triggered by natural language.
  • It is LLM-agnostic: you can use Claude, GPT-4, or any other model with an API (the speaker uses Claude).
  • It is free and open-source at openclaw.ai — with 300,000+ GitHub stars.

🗂️ Skill Architecture

A skill is the fundamental unit of OpenClaw. Every capability the agent has lives inside a skill. Understanding the skill structure is the most important thing to grasp before building anything.

Figure 3: Anatomy of an OpenClaw skill folder

Skill Folder Structure

aws-health/             ← skill folder (one skill per folder)
├── SKILL.md            ← AI reads this to know when/how to use the skill
├── package.json        ← Node.js dependencies
├── iam-policy.json     ← Minimal IAM policy for AWS access
└── scripts/
    └── aws.ts          ← The actual TypeScript script that runs

SKILL.md — The Brain

SKILL.md is not documentation for humans — it is instruction for the AI agent about when to invoke the skill and how. The agent reads SKILL.md at startup and uses the description to match user messages to skills.

According to the session slides, a SKILL.md contains five sections:

  1. Metadata — name, version, author
  2. Statements that invoke the skill — example phrases that trigger it
  3. How to invoke — which script to run and with what arguments
  4. Output — how the script's output should be formatted and presented
  5. Error handling — what to do if the script fails or returns unexpected results
name: aws-health
description: |
  Check health of AWS EC2 instances and ECS clusters/services.
  Reports running/stopped counts, CPU/memory metrics, and unhealthy tasks.
  Use when the user asks about AWS instance health, ECS status, or infra monitoring.

⚡ Key insight: The more precise your description, the better the agent routes messages. Vague descriptions cause the agent to call the wrong skill or miss valid triggers.

How the Agent Executes a Skill

  1. User sends a message: "how are my EC2 instances?"
  2. OpenClaw passes the message to the LLM with all SKILL.md descriptions in context.
  3. LLM identifies the aws-health skill as the best match.
  4. OpenClaw executes the script: npx tsx scripts/aws.ts ec2
  5. Script calls AWS APIs, formats a structured report.
  6. OpenClaw sends the report back to the user on WhatsApp.

Figure 4: Complete execution flow from message to AWS API to response

💡 Analogy: Think of each skill as an employee with a job description. The LLM is the manager reading resumes (SKILL.md) to decide who to assign the task to. Once assigned, the employee (script) runs the task independently.

🏥 The aws-health Skill

The aws-health skill monitors your AWS compute infrastructure — EC2 instances, ECS clusters, and CloudWatch metrics — and returns a human-readable status report. It was built by Yash Garudkar and is available at github.com/yashgkar/aws-health.

Dependencies

npm install
# Installs:
@aws-sdk/client-ec2      ← Query EC2 instance state and metadata
@aws-sdk/client-ecs      ← Query ECS cluster and service state
@aws-sdk/client-cloudwatch  ← Pull CPU utilization metrics
tsx                      ← Run TypeScript directly, no build step

The skill uses AWS SDK v3 — the modular JavaScript SDK where each service is a separate package. You only install what you need, keeping the skill lightweight.

What the Skill Reports

From the session slides, here is exactly what each section of the report contains:

ServiceData Returned
EC2Instance name, type, Availability Zone (AZ), state, system status check (hardware failures), CPU — 15-minute average via CloudWatch
ECSAll clusters and services, running vs desired task count, deployment rollout state, last 5 stopped tasks + stop reason

CLI Arguments

CommandWhat it does
npx tsx scripts/aws.tsChecks both EC2 and ECS
npx tsx scripts/aws.ts ec2Checks EC2 only
npx tsx scripts/aws.ts ecsChecks ECS only

Environment Variables

ACCESS_KEY=AKIA...          ← IAM Access Key ID
SECRET_KEY=...              ← IAM Secret Access Key
REGION=us-east-1            ← AWS region to query
SESSION_TOKEN=...           ← Optional: only for temporary credentials

❌ Never hardcode credentials in the script. Always read them from environment variables. Never commit .env files to git.

🔬 AWS APIs Deep Dive

Understanding exactly which AWS API calls the skill makes — and what they return — is important for both debugging and extending the skill.

EC2 APIs

DescribeInstances returns a nested structure:

response.Reservations[].Instances[].{
  InstanceId,     // e.g. i-0abc123
  InstanceType,   // e.g. t3.micro
  Tags[],         // includes the 'Name' tag
  State.Name      // running | stopped | terminated | pending
}

💡 What is a Reservation? A "Reservation" in the EC2 API is a legacy grouping — it wraps one or more instances that were launched in the same RunInstances API call. The word "reservation" here has nothing to do with Reserved Instances pricing — it is a common source of confusion. Your code must iterate through Reservations → then through Instances inside each Reservation.

DescribeInstanceStatus returns per-instance health:

response.InstanceStatuses[].{
  InstanceId,
  InstanceState.Name,    // running | stopped
  SystemStatus.Status,   // ok | impaired | not-applicable
  InstanceStatus.Status  // ok | impaired | not-applicable
}

Figure 6: EC2 DescribeInstances response structure — must iterate reservations first

CloudWatch API

GetMetricStatistics fetches time-series data for a named metric:

GetMetricStatistics({
  Namespace: 'AWS/EC2',
  MetricName: 'CPUUtilization',
  Dimensions: [{ Name: 'InstanceId', Value: 'i-0abc123' }],
  StartTime: /* now - 15min */,
  EndTime: /* now */,
  Period: 900,               // 15-minute average (as shown in session slides)
  Statistics: ['Average']
})

ECS APIs

ListClusters()              → list of cluster ARNs
DescribeServices(cluster)   → services with runningCount vs desiredCount
ListTasks(cluster, service) → task ARNs
DescribeTasks(cluster, tasks) → task status, container health, CPU/memory

Figure 7: ECS API call chain to get cluster health

🔒 IAM Security Setup

This is the most critical part of the setup. Getting IAM wrong can expose your entire AWS account. The session emphasised this repeatedly.

❌ NEVER use your root AWS credentials for OpenClaw. Root credentials have unrestricted access to every AWS service — if they leak, an attacker can destroy your entire account.

Create a Dedicated IAM User

  1. Go to AWS IAM → Users → Create user
  2. Name it something like openclaw-health-reader
  3. Select Programmatic access (no console access needed)
  4. Attach the minimal custom policy (see below)
  5. Save the Access Key ID and Secret Access Key securely

Minimal IAM Policy

The IAM user must have read-only access to specific services only — no wildcards, no write permissions.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ec2:DescribeInstances",
        "ec2:DescribeInstanceStatus",
        "ecs:ListClusters",
        "ecs:DescribeServices",
        "ecs:ListTasks",
        "ecs:DescribeTasks",
        "cloudwatch:GetMetricStatistics"
      ],
      "Resource": "*"
    }
  ]
}

This exact policy is in iam-policy.json in the repo — no need to write it from scratch.

Figure 8: Least privilege IAM — only the exact 7 actions needed, nothing more

Key Security Rules

  • Create a new IAM user specifically for OpenClaw — never reuse credentials from another tool or service.
  • Never commit credentials to git — use environment variables or a secrets manager.
  • Rotate access keys regularly (every 90 days is a reasonable baseline).
  • Enable CloudTrail to audit all API calls made by the OpenClaw IAM user.
  • If sharing OpenClaw across a team, be aware that a shared instance means all users share the same file system — there is no user isolation.

✅ Best practice: Each engineer should run their own local OpenClaw instance with their own IAM credentials. This gives you per-user auditability and eliminates the shared file system risk.

  2. WhatsApp delivers the message to OpenClaw via the WhatsApp Business API
  3. OpenClaw passes the message + all SKILL.md descriptions to the LLM
  4. LLM responds: "use aws-health skill, run both ec2 and ecs"
  5. OpenClaw executes: npx tsx scripts/aws.ts

  8. Script formats a structured plain-text report
  9. OpenClaw sends the report back to your WhatsApp

⚖️ OpenClaw vs Alternatives

OpenClaw is not the only way to get conversational access to your infra. Here's how it compares.

Figure 10: When to choose OpenClaw vs alternatives

ToolBest forLimitation
OpenClawPersonal DevOps, rapid skill development, full controlRequires local machine running, no native multi-user support
CloudWatch DashboardsRich visualisations, built-in AWS integrationRequires browser, no natural language, manual navigation
AWS Health APIService-level event monitoring, account healthService-level only — no per-instance granularity
PagerDuty / OpsgenieEnterprise on-call management, SLA trackingExpensive, heavy, not conversational in the same way

AWS Health API vs OpenClaw Skill

This came up as a question from the audience and is worth understanding clearly:

  • AWS Health API reports service-level events: outages, maintenance, and scheduled changes that affect your account. Example: "EC2 is experiencing elevated API error rates in us-east-1."
  • The aws-health skill reports per-instance/per-task data: specific instance IDs, states, CPU utilisation, ECS running vs desired task counts.
  • They are complementary. AWS Health tells you if AWS is having an outage; OpenClaw tells you the exact state of your specific resources.

⚙️ Setup Guide

Prerequisites

  • OpenClaw installed and running locally (openclaw.ai)
  • Node.js 18+ installed
  • AWS account with programmatic access
  • WhatsApp linked to OpenClaw (or Slack/Telegram)

Step 1: Clone the Skill

git clone https://github.com/yashgkar/aws-health
cd aws-health
npm install

Step 2: Create IAM User

  1. Go to AWS Console → IAM → Users → Create user
  2. Enable programmatic access
  3. Create a new policy using the contents of iam-policy.json
  4. Attach the policy to the user
  5. Copy the Access Key ID and Secret Access Key

Step 3: Configure Environment

ACCESS_KEY=your-access-key-id
SECRET_KEY=your-secret-access-key
REGION=us-east-1
# SESSION_TOKEN=optional-if-using-temp-credentials

Step 4: Test the Skill Manually

# Check both EC2 and ECS
npx tsx scripts/aws.ts

# Check EC2 only
npx tsx scripts/aws.ts ec2

# Check ECS only
npx tsx scripts/aws.ts ecs

Step 5: Install in OpenClaw

Copy the skill folder into your OpenClaw skills directory (check OpenClaw docs for the exact path). OpenClaw will detect the new skill automatically on next start and the agent will begin routing relevant WhatsApp messages to it.

✅ Test trigger messages: "check aws", "how are my EC2 instances?", "is production healthy?", "check ECS", "how are my instances?"

🔧 Extending the Skill

The aws-health skill is intentionally minimal — a starting point for your own extensions. The speaker mentioned plans to add RDS and other services. Here's how to think about extending it.

Adding RDS Monitoring

// 1. Add dependency
npm install @aws-sdk/client-rds

// 2. Add the client
import { RDSClient, DescribeDBInstancesCommand } from '@aws-sdk/client-rds';
const rdsClient = new RDSClient({ region, credentials });

// 3. Query instances
const rdsResponse = await rdsClient.send(new DescribeDBInstancesCommand({}));
const instances = rdsResponse.DBInstances || [];

// 4. Add to IAM policy
// "rds:DescribeDBInstances"

Adding Parallel Execution (Audience Suggestion)

An audience member noted that querying EC2 and ECS sequentially is slow for large environments. The fix: run checks in parallel using Promise.all:

const [ec2Report, ecsReport, rdsReport] = await Promise.all([
  checkEC2(),
  checkECS(),
  checkRDS()
]);
// Total time = slowest check, not sum of all checks

Adding Proactive Alerts

The current model is reactive (user asks → agent responds). You can make it proactive by adding a scheduler:

// Run health check every 5 minutes
setInterval(async () => {
  const report = await runHealthCheck();
  if (report.hasAlerts) {
    await sendWhatsAppMessage(report.summary);
  }
}, 5 * 60 * 1000);

💡 This transforms OpenClaw from a query tool into an alerting system — similar to PagerDuty but self-hosted and conversational.

OpenClaw and MCP

An audience member connected OpenClaw skills to MCP (Model Context Protocol) — the emerging standard for giving AI agents access to external tools. The connection is direct:

  • OpenClaw SKILL.md = MCP tool schema definition
  • OpenClaw script execution = MCP tool invocation
  • Both patterns: describe the capability → AI picks the right one → execute → return result

As MCP matures, OpenClaw-style skills may migrate to MCP-native implementations — but the design principle is identical.

🐛 Debugging and Troubleshooting

Skill Not Triggering

  • Check your SKILL.md description — is it specific enough to match the messages you're sending?
  • Try exact phrases from the description as test messages
  • Check OpenClaw logs to see which skill (if any) was selected for your message

AWS API Errors

  • AccessDenied: The IAM user is missing a required permission. Check against iam-policy.json and verify all 7 actions are granted.
  • AuthFailure: Access key or secret is wrong. Double-check environment variables.
  • NoCredentialProviders: Environment variables not loaded. Verify ACCESS_KEY and SECRET_KEY are set in the process environment.
  • InvalidClientTokenId: Access key has been deactivated or deleted in IAM.

Empty Results (No Instances / No Clusters)

  • Verify you're querying the correct region — EC2 instances in us-east-1 won't appear if REGION=eu-west-1
  • EC2: check AWS console for instances in the configured region
  • ECS: if no clusters exist, the skill returns zero results — this is expected, not an error (as the speaker demonstrated live)

Unexpected Agent Responses

If the agent produces an unexpected response, check the OpenClaw gateway logs to trace exactly what was executed. The logs show: which message triggered the skill, which skill was called, what the script output was, and how the LLM formatted the response.

📝 Overall Summary

OpenClaw is an open-source local AI agent that gives you conversational access to your infrastructure via WhatsApp, Slack, or Telegram. Instead of navigating dashboards at 2am, you ask in plain English and get a structured AWS health report back in seconds.

The aws-health skill demonstrates the pattern: a SKILL.md tells the AI agent when to invoke the skill, and a TypeScript script uses AWS SDK v3 to query EC2 (via DescribeInstances and DescribeInstanceStatus), ECS (via ListClusters, DescribeServices, ListTasks), and CloudWatch (via GetMetricStatistics) to build the report.

Security is non-negotiable: create a dedicated IAM user with read-only permissions to only the 7 specific API actions needed. Never use root credentials or wildcard policies. Use the iam-policy.json from the repo as your starting point.

The architecture is intentionally simple: everything runs locally, there is no AWS hosting cost, and skills are plain folders with TypeScript files — easy to read, modify, and extend. The speaker plans to add RDS monitoring and parallel execution as next steps.

OpenClaw skills are conceptually identical to MCP tools — both are the emerging pattern for giving AI agents structured, safe access to real-world systems.
