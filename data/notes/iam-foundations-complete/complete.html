🔐 Introduction

Every single API call in AWS — whether it comes from a developer's terminal, a Lambda function, or an EC2 instance — passes through one gate: IAM, Identity and Access Management. It doesn't matter which service you're using, what region you're in, or how long you've been using AWS. Every request is checked here first.

Figure 1: IAM is the single gate every AWS API call passes through

These notes are a deep-dive written at SAA-C03 level, based on lectures by Chandra Dunn (session details). They cover the five pillars of IAM that appear most heavily on the Solutions Architect Associate exam: Identities & Principals, Root User Protection, Policy Structure & Least Privilege, Policy Evaluation Logic, and MFA & Security Baselines — plus the all-important topic of Cross-Account Access.

⚡ IAM is exam-heavy: a large portion of SAA-C03 scenario questions reduce to correctly applying IAM evaluation logic, even when the question appears to be about S3, EC2, or KMS.

By the end of these notes, you should be able to read any IAM policy JSON aloud like a senior cloud engineer, identify least-privilege violations at a glance, trace a cross-account access flow end-to-end, and answer evaluation-logic questions confidently under exam pressure.

🏛️ What IAM Actually Does — The Three Pillars

Before jumping into policies and roles, you need to nail three concepts. Every IAM question on the exam — no matter how long the scenario — is really asking about one of these three things:

Figure 2: The three pillars of IAM — Authentication, Authorization, and Audibility

🔑 Authentication — Who is Making the Call?

Authentication answers the question: who are you? It is established by the credential type used in the API call. AWS recognises four credential types:

  • Password — used by human IAM users signing into the console.
  • Access Key (Access Key ID + Secret Access Key) — long-lived credentials used by programmatic workloads. These are the ones you must rotate and never embed in code.
  • Temporary STS Token — short-lived credentials issued by AWS Security Token Service. Used when a role is assumed. These expire automatically.
  • Federated Identity Assertion (SAML/OIDC) — used when an external identity provider (Active Directory, Google, Okta) vouches for a user. IAM Identity Center uses this mechanism.

🔒 Authorization — Is This Caller Allowed?

Authorization answers: can you do this action on this resource? It is established entirely by IAM policy evaluation. AWS evaluates every applicable policy — identity-based, resource-based, permission boundaries, SCPs, session policies — and produces a single binary answer: allow or deny.

📋 Audibility — Who Did What, When, and From Where?

Audibility is established by AWS CloudTrail. CloudTrail logs every API call with the calling identity, source IP, timestamp, and request parameters attached. It is the forensic record that security teams use after an incident. An account without CloudTrail enabled is an account in which incident response is nearly impossible.

💡 Exam tip: When a question describes a security incident and asks which AWS service would have prevented or detected it, map the missing concept: missing authentication → MFA or Identity Center; missing authorization → least-privilege policies or SCPs; missing audibility → CloudTrail.
✅ The Grandmother Test: Think of a hotel. Authentication is showing your ID at reception. Authorization is whether your key card opens a specific door. Audibility is the CCTV log showing which doors you actually opened.

👥 IAM Principal Types — The Four Identities

IAM recognises exactly four principal types. Getting these right is critical — especially the difference between a group (a container, not an identity) and a role (a temporary costume, not a person).

Figure 3: The four IAM principal types and their key characteristics

👑 Root User

The root user is created when you open an AWS account. It uses the email address you registered with. The root user is unconstrained by any IAM policy, service control policy, or permission boundary — it has 100% blast radius if compromised. You cannot delete it. You cannot restrict it with policies.

The root user should only be used for a tiny set of tasks: closing the account, changing the root email or password, restoring IAM permissions if accidentally revoked, activating IAM access to billing, registering as a Reserved Instance Marketplace seller, and enabling AWS GovCloud regions. Outside of these, lock it away.

❌ On the exam: Any scenario that proposes regular root user use is almost always the wrong answer — regardless of what other protections are layered on top. AWS Trusted Advisor flags daily root use as a high-priority finding.

🧑‍💻 IAM User

An IAM user is a long-lived identity. It has a username, a password for console access, and optional access keys for programmatic access. One IAM user per human. Never share IAM user credentials across team members — this destroys auditability because you can no longer tell which person took which action.

A common anti-pattern (that you'll see in wrong exam answers) is creating one IAM user per environment: dev-user, staging-user, prod-user, shared across the team. This is bad because it conflates identity with environment and makes incident response impossible.

🫙 IAM Group

Think of a group as a Tupperware bowl. You put IAM users into it, and the bowl holds permissions. When a user is in the bowl, they inherit those permissions. When they leave, those permissions are gone. IAM groups are permission management containers — they are NOT identities. A group cannot make API calls. Only the users inside the group can.

⚡ IAM groups cannot be principals in a resource-based policy. When you write an S3 bucket policy, you must reference the underlying users or roles, not the group they belong to. This is a direct exam trap.

Groups shine when teams grow. Migrating from per-user policy attachments to a group-based model typically reduces the number of policy attachments by around 80%, and makes permission changes a one-line edit instead of touching 40 individual users.

🎭 IAM Role

Think of a role as a costume. A principal puts it on (assumes it), has whatever superpowers it grants for a limited time, and then takes it off and returns to normal. IAM roles are temporary identities assumed through AWS Security Token Service (STS), which issues short-lived credentials that expire automatically. They are used for cross-account access, workload access (EC2, Lambda, ECS), and federation.

✅ Quick exam decision tree:
• Scenario involves a workload (Lambda, EC2, ECS, EKS, Fargate) → IAM Role
• Scenario involves a human → IAM User (or federated identity via IAM Identity Center)
• Scenario involves a set of humans with the same permissions → IAM Group
• Scenario involves cross-account access → IAM Role with cross-account trust policy
• Scenario mentions Active Directory, SAML, SSO, multi-account → IAM Identity Center

Figure 4: Principal-type decision tree used by senior cloud engineers on the job

🔒 Root User Protection — Locking It Away

Because the root user is unconstrained, a compromised root credential is the worst possible AWS security incident. There is no recovery path other than full account closure. The root user has the authority to reverse any defensive measure you could possibly set up. So AWS's guidance is simple: use it once, lock it away forever.

Figure 5: The four-step root user lockdown process

The Four-Step Lockdown Pattern

  1. Complete the initial setup tasks that genuinely require root: set up the account name, configure billing alerts, enable MFA on root, activate IAM access to billing.
  2. Create an IAM administrative user (or set up IAM Identity Center) for daily work. Grant it the permissions your project actually needs — not everything. Apply least privilege even to the admin user.
  3. Enable MFA on both the root user and the new admin IAM user. This is non-negotiable.
  4. Store the root credential and MFA recovery codes offline — in a physical safe, a sealed envelope, or somewhere that no single individual can access alone. The goal is to make root credential recovery a deliberate, witnessed event — not something one person can do at 2am.
💡 The operational cost of locking away the root user is about five to ten minutes per year. The cost of a compromised root credential is potentially the entire account and all customer data it contains.

IAM User vs IAM Identity Center for Daily Admin Work

AWS now recommends IAM Identity Center over direct IAM users for human identities, especially in multi-account environments.

✅ Exam rule: When a scenario mentions corporate Active Directory, SAML federation, or access across multiple AWS accounts, the answer involves IAM Identity Center.

📄 Policy Anatomy — Reading IAM JSON Like a Pro

Every IAM policy is a JSON document with a small, fixed vocabulary. Once you get used to this structure, you can read any policy aloud like a senior cloud engineer reads a balance sheet — fluently and quickly. Don't let it intimidate you. It's just four mandatory elements.

Figure 6: The four mandatory elements of every IAM policy

The Four Elements

1. Effect

Either Allow or Deny. That's it. It states whether the actions listed are permitted or prohibited.

2. Action

One or more API calls in the format service:operation. For example: s3:GetObject, ec2:RunInstances, kms:Decrypt. Wildcards in the Action element are the most common least-privilege violation — s3:* grants every S3 action including Delete, PutBucketPolicy, and ACL changes.

3. Resource

One or more ARNs (Amazon Resource Names). This is the specific resource the action applies to. Wildcards here are equally dangerous. "Resource": "*" means the action applies to every resource in your account.

4. Condition

Optional key-value tests that constrain when the policy applies. Conditions can check source IP, MFA presence, MFA age, time of day, encryption requirements, request tags, and more. This is where fine-grained access control lives.

Identity-Based vs Resource-Based Policies

There are two families of IAM policies, and the exam loves to test you on their differences.

FeatureIdentity-Based PolicyResource-Based Policy
Attached toIAM principals (users, groups, roles)AWS resources (S3 buckets, KMS keys, SQS queues…)
AnswersWhat can this principal do?Who can do what to this resource?
Principal elementImplicit (policy is on the identity)Explicit (must name the identity)
Cross-account access❌ Cannot grant cross-account by itself✅ Can grant cross-account access
Absolute deny enforcementLimited✅ Explicit deny applies to everyone, including root
⚡ Not every AWS service supports resource-based policies. The services that do are: S3, KMS, SQS, SNS, Lambda, ECR, EFS, API Gateway, and Secrets Manager. All other services rely on identity-based policies only.

How to Spot the Policy Type

The exam sometimes shows you a policy and asks whether it's identity-based or resource-based without explicitly labeling it. The rule: if the policy has an explicit Principal element naming an identity, it's resource-based — because the policy lives on a resource and must say who is allowed. If the Principal element is absent, it's identity-based — because the policy is attached to the identity, making the principal implicit.

// Resource-based policy (bucket policy) — explicit Principal {
    "Effect": "Allow",
    "Principal": {
        "AWS": "arn:aws:iam::123456789012:role/DataAnalystRole"},
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::acme-reports/quarterly/*" }
// Identity-based policy — no Principal element {
    "Effect": "Allow",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::acme-reports/quarterly/*",
    "Condition": {
      "Bool": {"aws:MultiFactorAuthPresent": "true"}} }

🏷️ ARNs and Resource Scope

An ARN — Amazon Resource Name — is the globally unique address for every resource in AWS. Every resource: every S3 object, every EC2 instance, every KMS key, every Lambda function. ARNs follow a predictable structure, and the exam tests that structure directly in the form: "which ARN matches this resource scope?"

ARN Structure

arn:aws:<service>:<region>:<account-id>:<resource-type>/<resource-name>

For most services, all five segments are present. Examples:

arn:aws:ec2:us-east-1:123456789012:instance/i-1234567890abcdef0
arn:aws:iam::123456789012:role/DataAnalystRole
arn:aws:kms:us-east-1:123456789012:key/1234abcd-12ab-34cd-56ef-1234567890ab
⚡ S3 is the only AWS service where the region and account ID are omitted from the ARN. An S3 ARN looks like: arn:aws:s3:::acme-reports (bucket) or arn:aws:s3:::acme-reports/quarterly/* (objects under a prefix). Memorize this — it appears on the exam frequently.

Figure 7: Standard ARN structure vs S3 ARN — note the missing region and account-id in S3

Resource Scope Ladder

The resource element in an IAM policy defines the blast radius of any action. Think of it as a ladder from narrowest (safest) to widest (most dangerous):

Scope LevelExampleWhat it covers
Specific object (narrowest)arn:aws:s3:::acme-reports/quarterly/2025-Q4.csvOne specific file
Prefixarn:aws:s3:::acme-reports/quarterly/*Every object under one prefix
Bucketarn:aws:s3:::acme-reportsBucket-level operations (ListBucket)
All objects in bucketarn:aws:s3:::acme-reports/*Every object in the bucket
All resources (widest)*Every resource in the account
❌ Real-world lesson from the lecture: A production incident occurred where an application policy used "Resource": "*" as a "let me just get this working" shortcut. A junior engineer's typo accidentally deleted a production bucket. The fix was a one-line ARN scope that took five minutes. The incident cost three days of lost data and a customer escalation. The moral: never leave wildcard resources in production policies.

Object Level vs Bucket Level — A Critical Distinction

S3 actions operate on two different types of resources: the bucket itself and the objects inside it. These require different ARNs and are a very common exam trap.

// Bucket-level actions (ListBucket, GetBucketPolicy...) use the bucket ARN:
    "Resource": "arn:aws:s3:::acme-reports"
// Object-level actions (GetObject, PutObject, DeleteObject...) use the object ARN:
    "Resource": "arn:aws:s3:::acme-reports/*"

If a policy grants s3:GetObject on arn:aws:s3:::acme-reports/* but the user tries to call s3:ListBucket, the call fails with Access Denied — because ListBucket is a bucket-level action and needs arn:aws:s3:::acme-reports (without the slash and asterisk). S3 bucket-level ARNs and object-level ARNs are different — the action must be applied to the correct ARN type.

⚖️ Least Privilege — The Two-Axis Grading Rubric

Least privilege is not just a concept — it's a measurable, gradeable property. Every IAM policy can be scored on two independent axes: the action scope and the resource scope. A senior cloud engineer or security tool grades each axis independently. The exam asks you to do the same.

Figure 8: The two-axis least-privilege grading grid — aim for the top-left corner

Action Scope

GradeExampleMeaning
Narrow ✅s3:GetObjectSpecific API only — the recommended answer
Medium ⚠️s3:Get*All S3 read actions — sometimes acceptable
Wide ❌s3:*Every S3 action including Delete and PutBucketPolicy

Resource Scope

GradeExampleMeaning
Narrow ✅Specific ARN with prefixOne prefix in one bucket
Medium ⚠️One bucket ARNAll objects in one bucket
Wide ❌* or arn:aws:s3:::*All S3 buckets in the account
⚡ A well-formed least-privilege policy is narrow on both action and resource. A policy that is wide on either axis is almost never the right answer on the SAA exam. When four policy options are presented, eliminate any option with a wildcard on either axis — unless the question explicitly justifies it.

The Least-Privilege Rule in One Sentence

Grant the smallest action scope and the smallest resource scope that satisfies the functional requirement — nothing more.

💡 How to grade in 30 seconds: Look at the Action element first. Is it s3:*? Reject. Is it s3:Get*? Flag for review. Is it s3:GetObject? Good. Then look at the Resource. Is it *? Reject. Is it a specific bucket? Review. Is it a specific prefix ARN? Good. If both axes are narrow, the policy passes.

⚙️ IAM Evaluation Logic — The Three-Step Rule

This is the single most important thing to memorize for IAM questions. Every IAM authorization decision — regardless of which service, how many policies, which account — follows the same three-step rule. This rule does not change. It is invariant.

Figure 9: The IAM three-step evaluation flowchart — memorize this

The Three Steps

  1. Step 1 — Explicit Deny: Is there an explicit Deny anywhere in the evaluated policies? If yes, the request is denied and evaluation stops immediately. No Allow, no condition, no other policy can override an explicit Deny.

  2. Step 2 — Explicit Allow: Is there an explicit Allow? If yes (and there was no Deny in Step 1), the request is allowed.

  3. Step 3 — Implicit Deny (Default): If neither an explicit Deny nor an explicit Allow applies, the request is denied by default. AWS is deny-by-default. The absence of a permission means no permission.

⚡ Explicit deny wins. Explicit allow grants. Implicit deny is the default. Memorize this phrase. It answers the majority of IAM scenario questions on the SAA-C03 exam.

Where This Rule Applies

The rule is invariant — it applies across all policy types: identity-based policies, resource-based policies, permission boundaries, service control policies (SCPs), session policies, and cross-account combinations. No policy type overrides this rule.

✅ Production debugging tip: A developer has an identity-based policy that allows s3:GetObject, but the API call returns Access Denied. The cause is almost always an explicit Deny somewhere — in an SCP, a permission boundary, a bucket policy, or a session policy. When an Allow does not work, look for the Deny — it is in there somewhere.

Same-Account Evaluation

When the principal and the resource are in the same AWS account, an explicit Allow in either the identity-based or resource-based policy is usually sufficient (as long as there is no Deny blocking it). For example: a bucket policy that grants access to a role in the same account is enough — the role does not also need an identity-based policy allowing S3 access (though best practice is to have both explicit).

❌ Common wrong answer on the exam: "The call succeeds because identity-based policies and resource-based policies are evaluated independently, so the identity-based allow grants access regardless of the bucket policy." This is wrong. An explicit Deny in the bucket policy wins over any Allow anywhere — same account or cross-account.

🛡️ The Complete IAM Security Stack — Four Mechanisms

Real-world IAM security is not just one type of policy. It is a layered stack of four mechanisms, each with a distinct job. The exam often presents multi-requirement scenarios where the right answer is a combination of two or more of these mechanisms matched to the correct requirements.

Figure 10: The four-layer IAM security stack — each mechanism has a distinct role

Mechanism 1: Identity-Based Policies — The Floor

These grant the baseline permissions the principal (user, group, or role) needs to do its job. They are the floor — they establish the minimum permissions. Add condition keys to constrain when the permissions apply. This is the most common policy type.

Mechanism 2: Resource-Based Policies — The Gate

These are the gate. They apply absolute prohibitions on the resource itself, and they enable cross-account access without role assumption. Use resource-based policies when you need an explicit Deny that no identity-based Allow can override — for example, blocking public access to an S3 bucket or restricting access to requests from a specific VPC.

Mechanism 3: Permission Boundaries — The Ceiling

Permission boundaries are ceilings. They cap the maximum effective permissions an IAM user or role can gain through any other mechanism. If a developer writes their own policies, the boundary ensures they cannot grant themselves more than the boundary allows — even if they attach a policy that says Allow: *. Used to limit blast radius in developer-managed accounts.

Mechanism 4: Condition Keys — The Contextual Gate

Condition keys are contextual gates. They apply constraints that depend on request context, not identity or resource: source IP, MFA presence, MFA age, time of day, request tags, region of origin. Condition keys are where fine-grained access control lives — they are the mechanism for enforcing MFA requirements on specific actions.

💡 Mental model: Policies grant. Conditions constrain. Boundaries cap. Resource policies guard. When a question describes multiple security requirements, the answer is the right combination of these four mechanisms matched to the right requirements.

🔑 MFA and Security Baselines

Multi-factor authentication is not just a checkbox. AWS supports four MFA mechanisms, each with different operational characteristics and attack resistance. And there are two distinct IAM condition keys for MFA — they look similar but solve very different problems. Getting these mixed up is a direct exam trap.

The Four MFA Mechanisms

Figure 11: The four AWS MFA mechanisms and their key trade-offs

MechanismTypeStrengthsWeaknesses
Virtual MFATOTP app (Google Authenticator, Authy, Duo)Fast, free, low frictionRelies on phone security; not phishing-resistant
Hardware MFAPhysical TOTP device (SafeID, AWS ship tokens)No phone dependency; tamper-resistantHardware procurement; lost token = problem
FIDO Security KeyHardware key with public-key cryptography (Google Titan)Phishing-resistant; credential cannot be replayedHardware procurement; user training needed
PasskeyFIDO2 device-bound or syncable (Touch ID, Windows Hello)Phishing-resistant; smooth UX; supported by IAM Identity CenterNewer pattern; sync model varies; some legacy SAML flows unsupported
💡 2026 production recommendation: Virtual MFA for general engineering staff. FIDO security keys or passkeys for high-privilege identities like root users and security administrators. SMS MFA was deprecated by AWS in 2019 — existing configurations remain functional but new ones cannot be created.

MFA Condition Keys — The Critical Distinction

This is one of the most-tested IAM distinctions on the SAA-C03 exam. Two condition keys, two very different behaviors:

Figure 12: MultiFactorAuthPresent (boolean, session-wide) vs MultiFactorAuthAge (numeric, per-action)

Condition KeyTypeValue BehaviorProtects AgainstUse For
aws:MultiFactorAuthPresentBooleanSet at session start, does not change for session lifetimeUnauthenticated access onlyRead-only operations, general access
aws:MultiFactorAuthAgeNumeric (seconds)Increases as the session ages; compare with NumericLessThanSession hijacking; stale sessionsDestructive operations (Delete, PutBucketPolicy)
⚡ aws:MultiFactorAuthPresent is for the session. aws:MultiFactorAuthAge is for the action. Present stays true for the whole session — a hijacked session would still pass the Present check. Age requires fresh MFA within a threshold (e.g., 900 seconds = 15 minutes) before a specific action.
// Require MFA to be present anywhere in the session (read operations):
    "Condition": {
      "Bool": {"aws:MultiFactorAuthPresent": "true"}}
// Require MFA issued within the last 15 minutes (destructive operations):
    "Condition": {
      "NumericLessThan": {"aws:MultiFactorAuthAge": "900"}}
✅ Production architecture pattern: Enforce MultiFactorAuthPresent for read-only operations (user signs in with MFA once, reads work all day). Enforce MultiFactorAuthAge: 900 for destructive operations (user must re-authenticate with MFA within 15 minutes before deletion of production resources). This balances usability with strong protection for high-risk actions.
💡 Exam keyword mapping: When a question mentions "session hijacking," "fresh MFA recency," or "ensure MFA was performed in the last X seconds" → the answer involves aws:MultiFactorAuthAge. When the question only requires that MFA was used somewhere during the session → aws:MultiFactorAuthPresent is sufficient.

🔄 Cross-Account Access — The Highest-Frequency Exam Pattern

Cross-account access is where most candidates lose points — not because the concept is impossibly hard, but because under exam pressure, the source account vs destination account distinction trips people up. Get this clear now and you will nail these questions.

The Two-Pronged Rule

When the principal and the resource are in different AWS accounts, AWS requires an explicit Allow on both sides. This tightens the allow-side rule compared to same-account evaluation.

Figure 13: Cross-account access flow — Account B (source) assumes a role in Account A (destination)

Source Account vs Destination Account

⚡ The source account is the account making the call. The destination account is the account holding the resource. In a cross-account scenario where EC2 in Account B accesses S3 in Account A: Account B is the source, Account A is the destination. The call originates from B and travels to A.

Full Cross-Account Walkthrough

The scenario: Account A holds an S3 bucket with encrypted videos (KMS customer-managed key). Account B runs EC2 transcoding jobs that need to read those videos. No long-lived credentials on the instances. CloudTrail must capture every read.

Account A side (destination, resource owner):

  • An IAM role in Account A has a trust policy that allows Account B to assume it.
  • The role's permission policy allows s3:GetObject on the bucket AND kms:Decrypt on the KMS key.
  • The KMS key policy independently allows kms:Decrypt for that role. (Two-pronged KMS rule — both must permit.)
  • CloudTrail data events are enabled on the bucket.

Account B side (source, caller):

  • EC2 instances have an instance profile attached.
  • The instance profile's permission policy allows sts:AssumeRole on the Account A role.
  • The instances call AssumeRole via AWS STS, receive short-lived temporary credentials, and use them to call s3:GetObject and kms:Decrypt.
  • No long-lived access keys sit on the instances.
💡 Once the EC2 in Account B has assumed the role in Account A, from IAM's perspective the call is no longer cross-account. It is treated as a same-account call by the assumed role identity in Account A.

The KMS Two-Pronged Rule

KMS is special. When a cross-account caller decrypts data, both the IAM role policy AND the KMS key resource policy must independently permit kms:Decrypt. Having only one is not enough. Exam answer options that mention only one of the two authorizations are distractors — they are incomplete.

// Debugging cross-account KMS+S3 access denied — four places to check in order:
1. Principal's IAM policy in the SOURCE account (Account B)
2. Role's trust policy in the DESTINATION account (Account A)
3. Bucket policy in the DESTINATION account (Account A)
4. KMS key policy in the DESTINATION account (Account A)

Common Wrong Answers

  • Creating IAM users with access keys in Account A — wrong because the security team requires no long-lived credentials.
  • Storing access keys in Secrets Manager — wrong because Secrets Manager mitigates exposure risk but the credentials are still long-lived.
  • AWS PrivateLink / VPC endpoint — wrong because PrivateLink solves a network-path problem, not an identity-based access control problem.
  • S3 Cross-Region Replication — wrong because replication is a data durability feature, not an access control mechanism.
✅ The correct cross-account pattern for workloads: IAM Role in the destination account, instance profile in the source account, STS AssumeRole, temporary credentials, KMS key policy updated to allow the role. This satisfies: no long-lived credentials, no access keys on instances, CloudTrail captures everything.

🎯 Six Exam Takeaways — Cover ~80% of IAM Questions

Chandra Dunn distilled the IAM exam content into six takeaways. Together they cover roughly 80% of the IAM-related questions you will encounter on the SAA-C03. If you can internalize all six, you are in excellent shape for the IAM domain.

  1. Use IAM Groups for sets of users with identical permissions. Attach policies to the group, not to each user individually. Add and remove users without touching policies. Groups cannot be principals in resource-based policies.

  2. Lock the root user away after initial account setup. Enable MFA on root, create an IAM user or use IAM Identity Center for daily work, store the root credential offline. Any exam scenario proposing regular root use is almost always wrong.

  3. Least privilege requires both narrow actions AND narrow resources. A wildcard action with a narrow resource is as bad as a narrow action with a wildcard resource. Audit both axes independently. On the exam, the correct answer is almost always narrow on both.

  4. Explicit Deny anywhere wins — across identity-based policies, resource-based policies, permission boundaries, and SCPs — same account or cross-account. The rule is invariant.

  5. aws:MultiFactorAuthPresent is a Boolean true for the entire session lifetime. aws:MultiFactorAuthAge is numeric seconds since MFA was issued. Use Age to enforce fresh MFA on high-impact actions. Use Age for anything that could be session-hijacked.

  6. Cross-account access to a KMS-encrypted S3 bucket requires two-pronged authorization. Both the IAM role policy AND the KMS key resource policy must independently permit kms:Decrypt. Exam options mentioning only one are distractors.

Project 1: ACME Media Platform — Multi-Team IAM Architecture

🎯 Objective: Build a complete, production-realistic IAM architecture for a fictional company, ACME Media, that stores customer video uploads in S3, processes them with EC2 transcoding jobs in a separate account, enforces MFA on data deletion, and audits everything with CloudTrail. You will create all the IAM roles, groups, policies, and bucket policies described in the lectures — and see exactly why each design decision was made.

⏱️ Estimated Time: 60–90 minutes

💰 Cost: Free tier eligible (IAM, S3, KMS key ~$1/month if left running — clean up after)

Business Requirements

ACME Media has the following security requirements (these come straight from the lecture's exam-style scenario):

  1. Only data analyst staff may read customer video data.
  2. Data analysts must never be able to delete the data under any circumstance.
  3. Every read must require a fresh MFA credential issued within the last 15 minutes.
  4. Developers who need temporary data analyst access during testing must not have their broader developer permissions extended by gaining that access.
  5. A separate analytics team in Account B must run EC2 transcoding jobs against the videos — without long-lived IAM users or access keys on instances.
  6. Every cross-account read must be captured in CloudTrail data events.

  3. Enable Server-Side Encryption with a customer-managed KMS key (we will create the key next). Leave default encryption as SSE-S3 for now; we will switch to SSE-KMS after key creation.

Step 2: Create the Customer-Managed KMS Key (Account A)

  1. Navigate to KMS → Customer managed keys → Create key. Key type: Symmetric. Usage: Encrypt and decrypt. Alias: acme-videos-key.

    📸 Screenshot: KMS key creation — symmetric, encrypt/decrypt, alias set

  2. In the key policy, note the key policy JSON. It will include the account root as a key administrator by default. We will add additional principals later.

  3. Go back to your S3 bucket → Properties → Default encryption → Edit. Change to SSE-KMS and select the acme-videos-key you just created.

    📸 Screenshot: S3 bucket encryption updated to SSE-KMS with customer-managed key

Step 3: Create the IAM Groups (Account A)

Groups represent the bowl analogy from the lecture. We create two groups with different permission needs:

  1. Navigate to IAM → User groups → Create group. Name: DataAnalystGroup. Do not attach policies yet.

  2. Create a second group: DeveloperGroup. Do not attach policies yet.

    📸 Screenshot: Two IAM groups created — DataAnalystGroup and DeveloperGroup

Step 4: Create the DataAnalystRole (Account A)

This is the IAM role that data analysts and cross-account EC2 instances will assume. It must grant read access with an MFA age condition and must have no delete permissions.

  1. Navigate to IAM → Roles → Create role. Trusted entity: AWS account → This account (we will add cross-account trust later). Role name: DataAnalystRole.

  2. Do not attach a managed policy. Create a custom inline policy. Click Create inline policy and paste the following JSON:

    {
  "Version": "2012-10-17",
  "Statement": [ {
    "Sid": "ReadVideosWithFreshMFA",
    "Effect": "Allow",
    "Action": [ "s3:GetObject" ],
    "Resource": "arn:aws:s3:::acme-videos-[your-account-id]/*",
    "Condition": {
      "NumericLessThan": { "aws:MultiFactorAuthAge": "900" } } }, {
    "Sid": "AllowKMSDecrypt",
    "Action": "kms:Decrypt",
    "Effect": "Allow",
    "Resource": "arn:aws:kms:us-east-1:[your-account-id]:key/[key-id]" } ] }

    📸 Screenshot: DataAnalystRole inline policy — GetObject with MFA age condition + KMS decrypt

  3. Why no s3:ListBucket here? The application receives the exact object keys from an upstream queue and does not enumerate the bucket. Adding ListBucket would violate least privilege. This is exactly the lecture's exam scenario — the question tests whether you add ListBucket or not.

Step 5: Create the S3 Bucket Policy — Absolute Deny on Delete (Account A)

This is the resource-based policy (the Gate) that enforces the no-deletion requirement absolutely. Because it is a resource-based explicit deny, no identity-based allow can override it — not even one attached to a future admin role.

  1. Navigate to your S3 bucket → Permissions → Bucket policy → Edit. Paste the following:

    {
  "Version": "2012-10-17",
  "Statement": [ {
    "Sid": "AbsolutelyNoDeletionForDataAnalysts",
    "Effect": "Deny",
    "Principal": {
        "AWS": "arn:aws:iam::[your-account-id]:role/DataAnalystRole" },
    "Action": [ "s3:DeleteObject", "s3:DeleteObjectVersion" ],
    "Resource": "arn:aws:s3:::acme-videos-[your-account-id]/*" } ] }

    📸 Screenshot: S3 bucket policy — explicit Deny on delete for DataAnalystRole

  2. Why does this satisfy Requirement 2? The explicit Deny in the bucket policy overrides any Allow anywhere — including any future identity-based policy that might accidentally grant delete. This is the lecture's evaluation-logic lesson in action: explicit deny wins.

Step 6: Create IAM Users and Add to Groups

  1. Create two IAM users: alice-analyst (data analyst) and bob-developer (developer). Enable console access and MFA for both.

    📸 Screenshot: IAM users created with MFA enabled for both

  2. Add alice-analyst to DataAnalystGroup. Add bob-developer to DeveloperGroup.

  3. Attach an inline policy to DataAnalystGroup that allows sts:AssumeRole on DataAnalystRole. This allows data analysts to assume the role and gain temporary access.

  4. Attach a permission boundary to bob-developer that caps his maximum permissions to developer-scope services (EC2, S3 read, CloudWatch) — explicitly excluding s3:DeleteObject and any admin-level permissions. This satisfies Requirement 4: even if Bob assumes DataAnalystRole, his effective permissions cannot exceed the intersection of the role's permissions and his boundary.

Step 7: Enable Cross-Account Trust (Account A Role — Account B Access)

  1. Open the DataAnalystRole in IAM. Edit the Trust policy to add Account B as a trusted principal:

    {
  "Version": "2012-10-17",
  "Statement": [ {
    "Effect": "Allow",
    "Principal": {
        "AWS": [ "arn:aws:iam::[account-a-id]:root", "arn:aws:iam::[account-b-id]:root" ] },
    "Action": "sts:AssumeRole" } ] }

  2. Update the KMS key policy to also allow DataAnalystRole to use kms:Decrypt. Navigate to KMS → Your key → Key policy → Edit. Add a statement granting the role Decrypt permission. This is the two-pronged KMS requirement — without this the cross-account call will fail even if the role policy allows it.

    📸 Screenshot: KMS key policy updated — DataAnalystRole explicitly allowed kms:Decrypt

Step 8: Set Up Account B (EC2 Instance Profile)

  1. In Account B, create an IAM role named TranscoderRole. Trusted entity: EC2 (for instance profile use).

  2. Attach an inline policy to TranscoderRole that allows sts:AssumeRole on the Account A DataAnalystRole ARN:

    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "sts:AssumeRole",
    "Resource": "arn:aws:iam::[account-a-id]:role/DataAnalystRole"
  }] }

  3. Launch an EC2 instance in Account B. Attach the TranscoderRole as the instance profile. This gives the instance temporary credentials to assume the Account A role — with no access keys stored on the instance.

    📸 Screenshot: EC2 instance launch — TranscoderRole attached as instance profile

Step 9: Enable CloudTrail Data Events (Account A)

  1. Navigate to CloudTrail → Trails → Create trail (or use an existing trail). Enable Data events → S3 → All current and future buckets (or specifically acme-videos-*).

    📸 Screenshot: CloudTrail data events enabled for S3 — every object read will be logged

  2. This satisfies Requirement 6. Every cross-account read by the EC2 transcoding jobs will now appear in CloudTrail with the assumed role identity (DataAnalystRole), source IP of the EC2 instance, and exact object key accessed.

Verification: Testing the Architecture

  1. From the EC2 instance in Account B, run: aws sts assume-role --role-arn arn:aws:iam::[account-a-id]:role/DataAnalystRole --role-session-name TranscoderSession. You should receive temporary credentials.

  2. Use the temporary credentials to call: aws s3 cp s3://acme-videos-[account-a-id]/test-video.mp4 /tmp/test-video.mp4. This should succeed (GetObject allowed).

  3. Try: aws s3 rm s3://acme-videos-[account-a-id]/test-video.mp4. This should fail with Access Denied — the bucket policy's explicit Deny on DeleteObject is working.

  4. Check CloudTrail in Account A — the GetObject call should appear with the DataAnalystRole identity attached.

Cleanup

  1. Terminate the EC2 instance in Account B.
  2. Delete the KMS key (schedule deletion — minimum 7-day waiting period).
  3. Empty and delete the S3 bucket in Account A.
  4. Delete the IAM roles, users, and groups created in both accounts.
  5. Delete the CloudTrail trail if created specifically for this project.

📝 Overall Summary

  • IAM is the gate: Every AWS API call passes through IAM. It handles Authentication (who), Authorization (can they), and Audibility (CloudTrail records everything).
  • Four principal types: Root user (unconstrained, lock it away), IAM user (long-lived, one per human), IAM group (permission container, not an identity), IAM role (temporary costume via STS).
  • Policy anatomy has four elements: Effect (Allow/Deny), Action (service:operation), Resource (ARN), Condition (contextual constraints). Only Effect, Action, Resource are mandatory.
  • Identity-based vs resource-based: Identity-based attaches to principals. Resource-based attaches to the resource and requires an explicit Principal. Only 9 services support resource-based policies: S3, KMS, SQS, SNS, Lambda, ECR, EFS, API Gateway, Secrets Manager.
  • Three-step evaluation rule: Explicit Deny wins → Explicit Allow grants → Implicit Deny by default. This rule is invariant across all policy types and account boundaries.
  • Least privilege = narrow on both axes: Narrow action scope AND narrow resource scope. Wildcards on either axis fail the audit.
  • S3 ARN has no region or account ID — the only service where this is true. Memorize this for ARN-matching exam questions.
  • MFA Present vs MFA Age: Present is a boolean for the session lifetime. Age is numeric seconds since MFA was issued. Use Age (NumericLessThan: 900) for destructive operations to defend against session hijacking.
  • Cross-account requires explicit allow on both sides. Source account (caller) and destination account (resource owner) must both authorize the access.
  • KMS cross-account is two-pronged: Both the IAM role policy AND the KMS key resource policy must permit kms:Decrypt independently. One side is not enough.

🤔 Reflection Questions

1. A colleague argues that adding s3:* to a developer's policy is fine because "the bucket policy will protect us." Why is this reasoning flawed from an IAM security perspective?

💡 Hint

Think about which policy would need to have an explicit Deny, and whether that's always guaranteed to be present. Also consider future bucket creation.

2. You receive an Access Denied error even though the IAM role has an explicit Allow for s3:GetObject. Walk through the four most likely causes in priority order.

💡 Hint

Think about all the policy types that can override an Allow: SCPs, permission boundaries, bucket policies, session policies.

3. A company is moving from 30 individual IAM users (each with their own policies) to a group-based model. What is the operational benefit beyond just fewer policy attachments?

💡 Hint

Think about what happens when permissions need to change for the whole group, and what happens when someone joins or leaves.

4. Why can't you solve the cross-account EC2-to-S3 scenario by simply creating an IAM user in Account A and putting the access keys on the EC2 instances in Account B?

💡 Hint

Think about key rotation, key exposure risk, what happens when the instance is compromised, and what the security team's explicit requirement was.

5. A data analyst's session was established this morning with MFA. It is now 5 hours later. They attempt to delete a production S3 object. The bucket policy has an explicit Deny on DeleteObject for their role, and the identity-based policy uses MultiFactorAuthPresent: true. Will the deletion succeed? Why or why not?

💡 Hint

Apply the three-step rule. Step 1: is there an explicit Deny anywhere? What does the bucket policy say?

6. Explain why the statement "Once you assume a role, IAM no longer treats the call as cross-account" is important for debugging access denied errors.

💡 Hint

Once you assume a role in Account A, you ARE the role in Account A. The same-account rules apply from that point forward.
