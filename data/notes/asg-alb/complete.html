🌟 Introduction

Imagine you open a coffee shop. It fits 100 customers. Business is slow at first — one shop, one kitchen, life is simple. Then your coffee goes viral. Suddenly 500 people are showing up. One shop can't handle it. You open a second shop with the exact same layout. Now 1,000 people are coming on weekends and only 50 on Tuesdays. You're wasting money keeping both shops fully staffed on quiet days.

This is exactly the problem that AWS Auto Scaling Group (ASG) and Application Load Balancer (ALB) solve — automatically. ASG adds or removes EC2 servers based on real traffic demand. ALB acts like the person at the door who decides which shop (server) each customer goes to. Together, they make your AWS application highly available, fault-tolerant, and cost-efficient — without you touching anything manually.

Figure 1: How ASG and ALB work together — the load balancer distributes traffic to a fleet of auto-scaling EC2 instances

⚡ Why this matters in real life: On every real project you'll work on, someone will raise a Jira ticket asking you to set up Auto Scaling and a Load Balancer. It's not optional — it's standard practice for any production system on AWS.

☕ The Problem: Why Scaling Exists

Before we touch AWS, let's make sure we fully understand the problem. If you don't understand the problem, the solution won't stick.

Option 1: Scale Up (Vertical Scaling)

Going back to our coffee shop — your first instinct might be to expand the shop. Add more tables, a bigger kitchen, more staff. In AWS terms, this means upgrading your EC2 instance to a more powerful one (more CPU, more RAM).

Figure 2: Vertical scaling (scale up) vs Horizontal scaling (scale out) — AWS recommends horizontal for resilience

The problem with vertical scaling: If anything goes wrong with that one big server — the kitchen breaks, the power cuts — your entire business stops. This is called a Single Point of Failure (SPOF). No matter how big you make one machine, it's still just one machine.

Option 2: Scale Out (Horizontal Scaling)

The smarter approach: open a second shop (add a second EC2 instance) with the exact same setup. Now if one goes down, the other keeps serving customers. Horizontal scaling is the AWS-recommended approach because it eliminates single points of failure and allows near-infinite scale.

But horizontal scaling creates a new question: which shop should each customer go to? That's where the load balancer comes in.

The Traffic Director

You hire a person to stand at the entrance of your coffee complex. Their job: greet every customer, check which shop has available tables, and point the customer to the right one. In AWS, this person is the Load Balancer. It performs health checks on each server and only sends traffic to healthy ones.

💡 The Real-Time Problem: Traffic isn't constant. 6–9 AM is rush hour. 2–4 PM is quiet. Should you keep 10 servers running at 2 AM just because you might need them at 9 AM? No — that wastes money. Auto Scaling solves this by dynamically adjusting the number of servers based on current demand.

🔄 What is Auto Scaling Group (ASG)?

An Auto Scaling Group (ASG) is a collection of Amazon EC2 instances that are managed together, allowing automatic addition or removal of instances based on defined conditions.

Think of ASG as a smart fleet manager. You tell it: "I need at least 2 servers, aim for 3, but never go beyond 6." ASG watches the traffic, and when servers get overwhelmed, it automatically adds more. When traffic drops, it removes them to save cost. It also continuously monitors instance health — if one crashes, it replaces it automatically.

Figure 3: ASG automatically maintains your fleet between minimum and maximum limits, targeting desired capacity

Key Benefits of ASG

  • High Availability: If an instance fails health checks, ASG automatically replaces it — no manual intervention needed.
  • Cost Optimization: You only pay for instances that are actually running. During low traffic, ASG scales in (removes instances).
  • Elasticity: Handles traffic spikes automatically — no more 3 AM emergency logins to add servers.
  • Integration: Works natively with Elastic Load Balancers, CloudWatch, and EC2.

✅ Best Practice: Always integrate your ASG with a Load Balancer. Without a load balancer, traffic won't be distributed to new instances as they're added.

1️⃣ Configuration Details — Using a Launch Template

ASG creates EC2 instances automatically, but it needs a Launch Template to know what kind of instance to create — the AMI, instance type, key pair, security groups, and user data.

A Launch Template is like a blueprint or recipe. Just as a coffee shop franchise uses a standard kitchen setup manual so every new branch has the same equipment, your Launch Template ensures every new EC2 instance that ASG creates is identical and ready to serve traffic immediately.

💡 Step 2 of ASG creation also asks: Which VPC and subnets should new instances be deployed in? You specify this so ASG knows where to place new instances (which Availability Zones).

2️⃣ Size Limits — Minimum, Desired, Maximum

This is where you define the boundaries of your fleet:

Using the example from class: If desired capacity is 3, maximum size is 6, and minimum size is 2, ASG starts with 3 instances, can scale out to 6 during high traffic, and will never scale in below 2 even if traffic drops to zero.

3️⃣ Scaling Policy — When to Scale

Even though scaling is automatic, ASG still needs to know when to act. The scaling policy defines the conditions that trigger a scaling action (adding or removing instances). Without a policy, ASG just maintains desired capacity — it won't automatically react to traffic changes.

⚡ Key Exam Point: There are 4 types of scaling policies in ASG. You need to know all of them and when to use each.

📈 Types of Scaling Policies

ASG supports four types of scaling policies. The professor covered all four, plus the three sub-types of Dynamic Scaling. These are frequently tested in AWS exams.

Figure 5: All ASG scaling policy types — Dynamic Scaling has 3 sub-types that are commonly tested

1. Manual Scaling

You manually change the desired capacity. ASG then adds or removes instances to match. Simple, but not "smart" — it's just you clicking a number in the console.

Use when: You know in advance that you need a specific number (e.g., you have a maintenance window and want exactly 1 instance running).

❌ Not recommended for production: Manual scaling requires constant human monitoring and intervention. It defeats the purpose of automation.

2. Dynamic Scaling

Dynamic Scaling automatically adjusts capacity in real time based on CloudWatch metrics such as CPU utilization or request count. This is the most commonly used type and has three sub-types:

🔹 Step Scaling

Step Scaling adds or removes instances in steps based on how much a metric exceeds a threshold. For example: if CPU is 60–70%, add 1 instance; if CPU is 70–90%, add 2 instances; if CPU > 90%, add 3 instances. The response size scales with the severity of the demand.

Best for: Applications with variable and unpredictable load spikes where a proportional response is needed.

🔹 Simple Scaling

Simple Scaling triggers a single scaling action when a CloudWatch alarm fires, then waits for a cooldown period before taking another action.

Limitation: During the cooldown period, even if CPU keeps rising, no additional scaling happens. This makes it less responsive than Step or Target Tracking scaling.

💡 According to AWS documentation, Simple Scaling is the older policy type. AWS recommends Step Scaling or Target Tracking instead for most use cases. 📚 Source:AWS EC2 Auto Scaling Step and Simple Scaling Docs

🔹 Target Tracking Scaling

Target Tracking Scaling automatically adjusts capacity to keep a specific metric at a target value — similar to how a thermostat maintains room temperature.

You set a target (e.g., "keep average CPU at 50%"). ASG continuously watches the metric and adds or removes instances to stay near that target. It calculates the required capacity change automatically — you don't define steps.

Best for: Most production workloads. It's the simplest to configure and most intelligent in response. AWS recommends this as the preferred policy.

Figure 6: How the three Dynamic Scaling sub-types respond differently to a sudden CPU spike

3. Predictive Scaling

Predictive Scaling uses machine learning to analyze historical traffic patterns and proactively scales capacity before anticipated demand spikes.

For example: if every Monday at 9 AM your CPU spikes (because employees log in), Predictive Scaling will automatically add instances at 8:45 AM — before the spike even happens. This eliminates the lag time between "traffic increases" and "instances are ready."

Best for: Workloads with predictable, recurring patterns (business hours, weekly cycles, end-of-month processing).

💡 According to AWS documentation, Predictive Scaling requires at least 24 hours of historical data to generate forecasts, and works best with at least 2 weeks of history. 📚 Source:AWS Predictive Scaling Docs

4. Scheduled Scaling

Scheduled Scaling lets you define exact times when ASG should scale in or scale out, using a fixed schedule.

For example: "Every Friday at 5 PM, scale up to 10 instances for the weekend sale. Every Monday at 6 AM, scale back down to 3 instances." You know the pattern in advance — you just schedule it.

Best for: Known, planned events — flash sales, batch jobs, scheduled maintenance, end-of-day processing.

⚖️ What is a Load Balancer?

A Load Balancer is a managed AWS service that automatically distributes incoming application traffic across multiple targets (EC2 instances, containers, Lambda functions) in one or more Availability Zones.

Without a load balancer, all your users would hit one server, even if you have ten running. The load balancer acts as the single entry point. Users never talk to your EC2 instances directly — they always go through the load balancer. This also means your instances can stay private (no public IP needed).

Figure 7: A two-tier architecture with public and internal load balancers distributing traffic across subnets

Types of AWS Load Balancers

AWS offers four load balancer types under the Elastic Load Balancing (ELB) service:

TypeLayerProtocolBest For
Application Load Balancer (ALB)Layer 7 (HTTP/HTTPS)HTTP, HTTPS, WebSocketWeb applications, path-based routing, microservices
Network Load Balancer (NLB)Layer 4 (TCP/UDP)TCP, UDP, TLSUltra-high performance, gaming, IoT
Gateway Load Balancer (GWLB)Layer 3IP packetsFirewall appliances, security inspection

⚡ Exam Trap: The question will almost always be about ALB for web workloads. If the scenario mentions HTTP/HTTPS traffic, path-based routing, or host-based routing → ALB. If it mentions millions of requests per second or TCP/UDP → NLB.

🌐 Application Load Balancer (ALB) — Deep Dive

The Application Load Balancer (ALB) is a Layer 7 load balancer, meaning it understands HTTP and HTTPS. This is what makes it powerful — it can make routing decisions based on the content of the request, not just the IP address.

ALB Core Components

Figure 8: ALB component flow — Listener catches traffic, Rules route it, Target Group holds the destination EC2 instances

🔊 Listeners

A Listener is a process that checks for incoming connection requests on a specific port and protocol. Think of it as the reception desk — it sits at a specific port (like port 80 for HTTP) and waits for incoming connections.

You can configure multiple listeners on one ALB. For example: one listener on port 80 (HTTP) and another on port 443 (HTTPS). Each listener has at least one rule that tells it what to do with the traffic it receives.

📋 Rules

Rules are conditions and actions defined on a Listener. When a request matches a rule's condition, the action is executed — typically forwarding traffic to a specific Target Group.

Rules are evaluated in priority order. The last rule is always the default rule (catch-all). This is where path-based routing lives — you can say: "If the URL contains /api, send to the API Target Group. If it contains /images, send to the Media Target Group."

🎯 Target Groups

A Target Group is a logical grouping of targets (EC2 instances, Lambda functions, IP addresses, or containers) that the ALB routes traffic to.

Each Target Group has its own health check settings. ALB continuously sends health check requests to every target. If a target fails health checks, the ALB stops sending traffic to it until it recovers.

💡 Target Group and ASG connection: When you create an ASG and attach it to a Target Group, any new instances that ASG spins up are automatically registered with the Target Group — the load balancer immediately starts sending them traffic. When ASG removes an instance, it's deregistered first (connection draining), then terminated.

Figure 9: ALB routing to multiple Target Groups — enables blue/green deployments and canary releases

🗺️ Path-Based Routing

Path-based routing allows ALB to forward requests to different Target Groups based on the URL path in the HTTP request.

Real-world example: Your e-commerce site has different backend teams for different services:

  • https://shop.com/products/* → Product service (Target Group A)
  • https://shop.com/cart/* → Cart service (Target Group B)
  • https://shop.com/checkout/* → Payment service (Target Group C)

All three can be hosted on different EC2 instances, but users only see one URL. This is how modern microservices architectures work behind a single load balancer.

🏠 Host-Based Routing

Host-based routing forwards requests to different Target Groups based on the Host header in the HTTP request — the domain name.

Example: api.mycompany.com → API Target Group, www.mycompany.com → Web Target Group, admin.mycompany.com → Admin Target Group. One ALB handles all subdomains.

🗺️ ALB and Availability Zones

ALB spans multiple Availability Zones — it deploys an ALB Node in each AZ you enable. Each node handles traffic for targets in its AZ.

📸 From Session: ALB nodes in each AZ — both nodes share the same Target Group

💡 According to AWS documentation, enabling Cross-Zone Load Balancing allows each ALB node to distribute traffic evenly to all registered targets across all enabled AZs — not just the targets in its own AZ. This is enabled by default on ALB. 📚 Source:AWS ALB Target Groups Docs

🔒 Security Groups on ALB

ALB needs two security groups configured:

  1. ALB Security Group: Allows inbound traffic from the internet (e.g., TCP port 80 and 443 from 0.0.0.0/0)
  2. EC2 Instance Security Group: Allows inbound traffic only from the ALB security group — not from the internet directly. This keeps your instances private.

✅ Security Best Practice:EC2 instances behind an ALB should have their security group configured to allow traffic only from the ALB's security group, not from 0.0.0.0/0. This ensures no one can bypass the load balancer.

🛠️ Creating an ASG — 6 Steps in the Console

When you go to EC2 → Auto Scaling Groups → Create Auto Scaling Group, you'll see 6 steps. Here's what each step does:

  1. Step 1 — Name & Launch Template: Give your ASG a name. Attach an existing Launch Template (which defines the instance type, AMI, key pair, security groups, and user data for instances ASG creates).

  2. Step 2 — Instance Launch Options: Choose which VPC and which subnets (Availability Zones) ASG should deploy instances into. Selecting subnets in multiple AZs ensures high availability.

  3. Step 3 — Load Balancing (optional but recommended): Attach the ASG to an existing Load Balancer Target Group. New instances are automatically registered, removed instances are deregistered.

  4. Step 4 — Group Size & Scaling: Set your Minimum, Desired, and Maximum capacity. Choose your scaling policy type (None, Target Tracking, Step Scaling, or Scheduled).

  5. Step 5 — Notifications (optional): Configure SNS notifications for scale-in/scale-out events. Useful for monitoring and alerting.

  6. Step 6 — Tags (optional): Add tags to identify resources created by this ASG. Tags propagate to instances.

  7. Step 7 — Review: Review all settings before creating. ASG begins with Desired Capacity instances immediately.

💡 The professor noted: Steps 5 and 6 are not required for basic setup. Focus on Steps 1, 2, and 4 when getting started.

🤝 How ASG and ALB Work Together

ASG and ALB are designed to be used together. Here's the complete picture of how they interact:

  1. User sends a request to your app's domain name (e.g., www.myapp.com)
  2. DNS resolves to the ALB's public DNS name
  3. The ALB Listener receives the request on port 80 or 443
  4. ALB checks its rules and forwards to the appropriate Target Group
  5. ALB performs health checks and only routes to healthy instances
  6. ASG monitors CloudWatch metrics across all instances
  7. If CPU spikes, ASG launches new instances using the Launch Template
  8. New instances automatically register with the Target Group
  9. ALB starts sending traffic to the new instances within seconds
  10. When traffic drops, ASG terminates excess instances (after deregistering from ALB)

Figure 11: Complete ASG + ALB integration — traffic flows in, CloudWatch watches, ASG reacts, new instances join the Target Group automatically

⚡ Key Insight:ASG handles the quantity of instances. ALB handles the distribution of traffic. Together they provide both elasticity and high availability.

Health Checks — The Most Important Concept

ALB health checks periodically send an HTTP request to a specified path on each target. If a target returns anything other than a 2xx or 3xx HTTP status, it is marked unhealthy and removed from rotation.

ASG also has its own health checks (EC2 system status checks). When you enable ELB health checks on your ASG, ASG treats any instance that the ALB marks unhealthy as a failed instance — and will automatically terminate and replace it.

✅ Best Practice: Always enable ELB health checks on your ASG (not just EC2 health checks). EC2 health checks only detect hardware/OS failures. ELB health checks detect application-level failures too.

🎓 Exam Tips & Common Scenarios

Scenario-Based Exam Traps

❌ Trap 1: "A company needs to handle sudden, unpredictable traffic spikes. Which scaling policy?" → Target Tracking (not Scheduled — that requires known patterns)

❌ Trap 2: "A company runs batch jobs every Sunday at 2 AM. Which scaling policy?" → Scheduled Scaling (not Dynamic — the pattern is known and predictable)

❌ Trap 3: "What ensures users always go to healthy instances?" → ALB health checks (not ASG health checks alone)

❌ Trap 4: "ALB vs NLB?" → HTTP/HTTPS/WebSocket traffic = ALB. Millions of requests per second / TCP/UDP = NLB

Key Numbers to Remember

  • ALB operates at Layer 7 (Application Layer)
  • NLB operates at Layer 4 (Transport Layer)
  • Default health check interval: 30 seconds
  • Default healthy threshold: 5 consecutive successes
  • Default unhealthy threshold: 2 consecutive failures
  • Predictive Scaling needs minimum 24 hours of data, best with 2 weeks

📝 Overall Summary

  • Auto Scaling Group (ASG): Automatically manages a fleet of EC2 instances, scaling out when demand rises and scaling in when demand drops, within your defined minimum/desired/maximum limits.
  • Three things ASG needs: Launch Template (what to launch), Size Limits (min/desired/max), Scaling Policy (when to scale).
  • Scaling Types: Manual (human action), Dynamic (reactive — Step, Simple, Target Tracking), Predictive (ML-based, proactive), Scheduled (time-based).
  • Target Tracking: AWS-recommended scaling policy — works like a thermostat, maintains a target metric value automatically.
  • Load Balancer: Distributes incoming traffic across multiple healthy EC2 instances. Users never talk to instances directly.
  • ALB: Layer 7 (HTTP/HTTPS) load balancer that supports path-based routing, host-based routing, and content-based routing.
  • ALB Components: Listener (receives traffic on port/protocol), Rules (routing conditions), Target Group (destination instances).
  • Target Groups: Logical grouping of targets with their own health checks. ALB only routes to healthy targets.
  • ASG + ALB Integration: New instances from ASG auto-register with the Target Group; terminated instances deregister first.
  • Health Checks: Enable ELB health checks on ASG (not just EC2) so application-level failures also trigger instance replacement.

Project 4: Trigger Real Scaling with the Stress Tool

🎯 Objective: Use the stress tool to artificially spike CPU on running instances and watch the ASG automatically add new instances in real time via the AWS console.

⏱️ Time: 30–45 min (keep Project 3 running, or rebuild it)

💰 Cost: Small — same as Project 3

📚 What you learn: Full ASG scale-out lifecycle in action, reading CloudWatch metrics, watching health checks, understanding the scaling cooldown period

⚡ Why this matters: Reading about auto scaling is one thing. Watching it happen — instances appearing in the console while you caused the trigger — makes it stick forever. This is the project most students remember years later.

Part A — Prepare SSH Access

  1. In the ASG Instance Management tab, note the Private IP (or Public IP if you gave instances public IPs) of any one running instance. You'll SSH into it to run the stress command.

    📸 Screenshot: ASG Instance management — selecting an instance IP to SSH into

  2. SSH into the instance. From your terminal (Linux/Mac) or PuTTY (Windows):

    chmod 400 your-key.pem ssh -i your-key.pem ec2-user@<PUBLIC-IP>

  3. Install the stress tool on the instance:

    sudo amazon-linux-extras install epel -y sudo yum install stress -y

Part B — Spike the CPU

  1. Run the stress command to max out 4 CPU cores for 5 minutes:

    stress --cpu 4 --timeout 300

    Keep this terminal open and running.

  2. In a second browser tab, go to your ASG → Monitoring tab → EC2 section. Watch the CPU Utilization metric climb in the graph. It may take 1–2 minutes to update.

    📸 Screenshot: ASG Monitoring — CPU spike visible in CloudWatch graph

  3. Go to the ASG → Activity tab. Within 3–5 minutes of the spike, you should see a new entry showing ASG launching a new instance because CPU exceeded the target.

    📸 Screenshot: ASG Activity tab — new instance launch triggered by CPU spike

  4. Go to ASG → Instance management. You should now see a 4th instance appearing, starting in Pending state, then transitioning to InService.

    📸 Screenshot: New instance in Pending state — ASG scale-out in progress

Part C — Watch the Scale-In

  1. Let the stress command finish (or stop it with Ctrl+C on the SSH terminal). CPU will drop back. Within 10–15 minutes (Target Tracking scales in conservatively), ASG will remove the extra instance.

  2. In the ASG Activity tab, you'll see a scale-in event — an instance being terminated.

    📸 Screenshot: ASG Activity — scale-in event after CPU dropped back to normal

Cleanup

  1. Delete ASG → Delete ALB → Delete Target Group → Delete Launch Template

Project 5: Path-Based Routing — Microservices Style

🎯 Objective: Create two separate sets of EC2 instances and configure ALB to route /api traffic to one group and /web traffic to another — simulating a real microservices architecture.

⏱️ Time: 45–60 min

💰 Cost: Small (~$0.50–1.00 if cleaned up in 1 hour)

📚 What you learn: ALB listener rules, path-based routing, multiple Target Groups, real microservice routing pattern

Figure 12: Path-based routing — one ALB, two Target Groups, URL path decides which backend receives the request

Part A — Launch 4 EC2 Instances (2 per role)

  1. Launch 2 instances for the API backend. User data:

    #!/bin/bash yum update -y && yum install -y httpd systemctl start httpd && systemctl enable httpd mkdir -p /var/www/html/api echo "<h1 style='color:#E65100'>🔧 API Server — $(hostname -f)</h1><p>This is the API backend</p>" > /var/www/html/api/index.html

  2. Launch 2 more instances for the Web frontend. User data:

    #!/bin/bash yum update -y && yum install -y httpd systemctl start httpd && systemctl enable httpd mkdir -p /var/www/html/web echo "<h1 style='color:#1565C0'>🌐 Web Server — $(hostname -f)</h1><p>This is the web frontend</p>" > /var/www/html/web/index.html

Part B — Create Two Target Groups

  1. Create Target Group 1: Name tg-api. Register the 2 API instances. Health check path: /api/index.html.

  2. Create Target Group 2: Name tg-web. Register the 2 Web instances. Health check path: /web/index.html.

    📸 Screenshot: Two Target Groups (tg-api and tg-web) both showing healthy targets

Part C — Create ALB with Path-Based Rules

  1. Create an ALB (Internet-facing, 2 AZs). For the listener, set the default action to forward to tg-web.

  2. After the ALB is created, go to the Listener → View/edit rules. Click the + to add a new rule.

    📸 Screenshot: ALB Listener rules — path /api/* → tg-api, default → tg-web

  3. Add Rule: IF Path is /api/* THEN Forward to tg-api. Save.

Part D — Test Path-Based Routing

  1. Copy the ALB DNS name. In your browser, test three URLs:

    • http://<ALB-DNS>/web/index.html → should show the blue "🌐 Web Server" page
    • http://<ALB-DNS>/api/index.html → should show the orange "🔧 API Server" page
    • http://<ALB-DNS>/ → should show the Web server (default rule)

    📸 Screenshot: Path-based routing — same ALB DNS, different paths → different servers

Cleanup

  1. Delete ALB → Delete both Target Groups → Terminate all 4 EC2 instances

🤔 Reflection Questions

1. You have a web app that gets hit hard every Friday at 5 PM when employees submit weekly reports, and is quiet all weekend. Which ASG scaling type is the best fit, and why?

💡 Hint

Think about whether this is a predictable, time-based pattern or a reactive, metric-based one. Does the spike happen at a known time?

2. A developer asks why they can't SSH directly to the EC2 instances even though they have the key pair. The instances are behind an ALB. What's likely wrong, and what's the correct solution?

💡 Hint

Think about what the security group on the EC2 instances is allowing. Remember best practices around instances behind a load balancer.

3. Your ASG has Minimum 2, Desired 3, Maximum 6 with Target Tracking at 50% CPU. Current CPU across all 3 instances is 85%. What will ASG do, and how many instances will it likely add?

💡 Hint

Target Tracking wants to get CPU back to 50%. If 3 instances running at 85% CPU... how many instances would distribute that load to bring the average back to ~50%?

4. An exam question says: "An e-commerce company needs to route /api requests to one backend and /static requests to another. Which load balancer feature enables this?" What's the answer?

💡 Hint

This is about routing based on the URL path — a Layer 7 ALB feature you covered in class.

5. What is the difference between EC2 health checks and ELB health checks in the context of an ASG? Which should you use in production?

💡 Hint

EC2 health checks detect hardware/OS level issues. ELB health checks detect something different — think about what level they operate at.
