🚀 Introduction

You have already launched EC2 instances, chosen instance types, set up key pairs, and connected via SSH and RDP. Now it is time to go deeper — understanding what actually happens to your instance over its full lifetime.

Think of your EC2 instance like a rented hotel room. You can check in (start), sleep (stop or hibernate), change to a bigger room (scale up), add another room for your group (scale out), and eventually check out permanently (terminate). AWS charges you only while you are actively using the room — not while you are sleeping or have checked out.

In this session we cover six interconnected topics that every cloud engineer must know cold: the EC2 instance lifecycle, vertical and horizontal scaling, how to change instance types, termination and stop protection, shutdown behavior, hibernation, and the fundamentals of EC2 pricing.

Figure 1: EC2 Instance Lifecycle — all possible states and transitions

⚡ Why this matters: On the job, a developer might accidentally terminate a production server. You might need to resize a VM at 2 AM without downtime. AWS might charge you even when your instance is stopped. These are real scenarios that happen every week in real companies — and this session teaches you exactly how to handle them.

🔄 EC2 Instance Lifecycle

Every EC2 instance follows a defined journey from the moment you launch it to the moment it is permanently removed. Understanding each state — and what AWS charges in each — is one of the most tested topics in AWS certifications and the most practical skill you will use every day on the job.

The Seven States

Figure 2: EC2 States — what happens in each and when AWS charges

StateWhat Is HappeningAWS Charges?
PendingInstance is booting up. AWS is allocating hardware, loading the OS.❌ No charge
RunningInstance is fully active. CPU and RAM are allocated and working.✅ Yes — per second/hour
StoppingTransition state — OS is shutting down services before full stop.❌ No charge
StoppedInstance is off. CPU and RAM deallocated. EBS storage still attached.✅ EBS storage only
RebootingLike restarting a computer — instance stays on the same physical host.✅ Yes — charged throughout
HibernatingRAM contents saved to EBS. Instance paused mid-work.✅ EBS storage only
Shutting-downTransition to termination. OS cleaning up before permanent deletion.❌ No charge
TerminatedInstance deleted permanently. Cannot be restarted or recovered.❌ No charge

The Key Insight About Billing

AWS only charges EC2 compute costs while the instance is in the running state. The moment you stop an instance, compute charges stop. But here is the part that surprises many beginners: even in the stopped state, AWS continues to charge for EBS storage because the hard disk remains allocated to your instance.

💡 Real-World Tip: When you are done working for the day, stop your instance to pause compute charges. Only terminate it when you are completely done with the project and want to save storage costs too. Never leave instances running overnight unless your application requires it.

Stop vs. Terminate — The Critical Difference

Students often confuse these two. Think of it this way:

  • Stop is like turning off your laptop — everything is saved on the hard disk. You can start it back up anytime and pick up where you left off.
  • Terminate is like throwing your laptop in a shredder — it is gone forever. The instance disappears from your account and cannot be undone.

Termination is permanent and irreversible — the EC2 instance and its root EBS volume are deleted and cannot be recovered.

Reboot vs. Stop/Start

When you reboot, the instance restarts on the same physical host in the same Availability Zone. Your public IP address remains the same. It is just like pressing restart on your computer.

When you stop and then start, the instance may be placed on a different physical host. This means: after a stop-start cycle, the public IP address of your instance changes unless you have assigned an Elastic IP.

💡 According to AWS documentation, if you need a consistent public IP that survives stop-start cycles, use an Elastic IP address — a static IP you can associate with your instance. Without one, your public IP changes every time you stop and start.

📐 Scaling — Vertical and Horizontal

Scaling is one of those concepts that sounds technical but is incredibly intuitive once you see a real example. It is simply the ability of a system to handle increasing workloads — by either growing bigger or growing in number.

Figure 3: Vertical vs Horizontal Scaling — the two fundamental approaches

Vertical Scaling — Growing Bigger

Imagine you are using Google Drive and you have filled up your 15 GB. You have two choices: upgrade your existing account to 30 GB, or create a brand new account. The first choice — upgrading within the same account — is vertical scaling.

Vertical scaling means increasing or decreasing the resources of a single existing instance — changing its CPU, RAM, or both.

DirectionWhat You Are DoingAWS TermExample
⬆️ UpwardIncreasing resourcesScale UpT3 micro → T3 large
⬇️ DownwardDecreasing resourcesScale DownT3 large → T3 micro

⚡ Exam Tip: "Scale up" and "scale down" always refer to vertical scaling. "Scale out" and "scale in" always refer to horizontal scaling. Do not mix these up.

Horizontal Scaling — Growing in Numbers

Back to Google Drive — the second choice was creating an entirely new account and using its 15 GB. That is horizontal scaling. You are not making one thing bigger; you are adding more of the same thing.

Horizontal scaling means adding or removing instances to handle load — rather than making an existing instance bigger.

DirectionWhat You Are DoingAWS TermExample
➡️ OutwardAdding more instancesScale Out1 EC2 → 3 EC2 instances
⬅️ InwardRemoving instancesScale In3 EC2 → 1 EC2 instance

Which Scaling to Choose?

Figure 4: Scaling Decision Tree — choosing the right approach

CriteriaVertical ScalingHorizontal Scaling
ApproachMake one server biggerAdd more servers
DowntimeYes — must stop instanceNo — new instances launch while existing ones run
LimitYes — max instance type is the ceilingNo hard limit — can scale to hundreds of servers
Auto-scale?Typically manual/plannedCan be fully automated (Auto Scaling Groups)
CostOne larger instanceMultiple smaller instances
Best forDev/test servers, databasesProduction web apps, high-availability systems

💡 Real-World Note: In production systems, engineers almost never use vertical scaling alone. The standard approach is horizontal scaling combined with a load balancer and Auto Scaling Group — so that traffic is distributed across multiple instances and the system can expand or shrink automatically based on demand. We will cover load balancers and Auto Scaling Groups in a future session.

🔧 Changing Instance Type (Vertical Scaling in Practice)

Your development team raised a ticket: "The T3 micro server is too slow. Please upgrade it." This is the moment vertical scaling becomes real. Here is exactly how you do it on the AWS Console — step by step.

Step-by-Step: Change Instance Type

⚠️ Important: This process requires stopping the instance. There will be downtime — your applications will be unreachable while the instance is stopped. Plan this during a maintenance window in production environments.

  1. Navigate to EC2 → Instances in the AWS Console. Select your instance.

  2. Click Instance State → Stop instance. Confirm the stop. Wait for the instance state to show Stopped.

  3. With the instance still selected, click Actions → Instance Settings → Change instance type.

  4. In the Change Instance Type dialog, you will see your current type (e.g., T3 micro) and its specs. Select the new instance type from the dropdown — for example, T3 medium or T2 large.

  5. Review the new configuration — CPU count, RAM, and whether it is Free Tier eligible. Click Apply.

  6. Go back to Instances, select your instance, and click Instance State → Start instance. The instance moves through Pending → Running with the new hardware configuration.

Figure 5: 📸 Change Instance Type dialog in the AWS Console

✅ What stays the same after a type change: Your EBS storage, your files, your applications, your security groups, and your instance ID — all remain intact. Only the CPU and RAM configuration changes.

Understanding Instance Families

Instance types follow a naming convention that tells you a lot: T3.micro means Family = T (burstable general purpose), Generation = 3, Size = micro.

The Downtime Problem and Solutions

The major drawback of vertical scaling is that you must stop the instance, causing downtime. In production, no one wants their website going down for 10–15 minutes. Here are the real-world strategies:

  • Schedule a maintenance window: Inform users in advance (e.g., "Scheduled maintenance 2–3 AM Sunday"), gracefully shut down applications, perform the resize, restart.
  • Blue-Green Deployment: Launch a new, already-resized instance in parallel. Route traffic to the new instance (via a load balancer), verify everything works, then decommission the old one — zero downtime.
  • Auto Scaling Groups + Load Balancers: Instead of resizing one server, automatically add more capacity and distribute load. We will cover this in a dedicated session.

💡 In production, you rarely resize a single server. Instead you use Auto Scaling Groups to add capacity automatically. Vertical scaling is most commonly used in development and test environments, or for databases that cannot be easily horizontally scaled.

AWS Nitro System — Live Resizing (Advanced)

AWS has been rolling out a capability called live resizing (also called "hot change") for EC2 instances built on the AWS Nitro System — AWS's modern virtualization platform.

On Nitro-based instances, AWS is enabling CPU and memory resize without stopping the instance — eliminating downtime for supported configurations.

💡 Condition: At the time of writing, live resizing is supported only when changing within the same instance family and generation (e.g., T3.micro to T3.large). Changing families (e.g., T3 to C5) still requires a stop. Check the AWS EC2 Instance Resize Docs for the latest supported configurations as this technology is evolving.

🔒 Termination Protection

Picture this: you are a pilot flying an aircraft. Mid-flight, someone accidentally hits the engine shutdown switch. Catastrophe. The same logic applies to your production EC2 instances — an accidental termination by a developer, a teammate, or even a script can wipe out your server and all its data. Forever.

Termination Protection is a safeguard that prevents an EC2 instance from being terminated — whether accidentally or intentionally — until the protection is explicitly disabled.

Figure 7: Termination Protection Flow — how it blocks accidental deletion

Enabling Termination Protection

You can enable it at two points:

Option 1 — During launch: In the EC2 launch wizard, scroll to Advanced Details at the bottom. Find Termination protection and set it to Enable.

Option 2 — After launch: Select the running or stopped instance → Actions → Instance Settings → Change Termination Protection → Set to Enable → Save.

What Happens When You Try to Terminate a Protected Instance?

If you attempt to terminate an instance with protection enabled, AWS will return an error: "Failed to terminate the instance — it has termination protection enabled." The instance remains completely unaffected.

⚡ To terminate a protected instance, you must first disable termination protection, then terminate. You cannot terminate directly.

When to Enable Termination Protection

  • ✅ Any production server
  • ✅ Instances running live customer-facing applications
  • ✅ Database servers or servers with critical data
  • ✅ Instances shared in a team where others have IAM access
  • ❌ Temporary dev/test instances you plan to delete frequently

✅ Best Practice: Enable termination protection on any instance that would cause a major incident if accidentally deleted. This is a one-click safeguard that takes seconds to set up and has saved companies from serious outages.

🛑 Stop Protection

Similar to Termination Protection, Stop Protection prevents an instance from being stopped. This is useful when you have an application that must never be interrupted — even by a well-meaning team member who thinks they are just "stopping it temporarily."

Stop Protection prevents an EC2 instance from being stopped — it will remain in the running state even if a stop command is issued.

Enable it the same way as Termination Protection: Actions → Instance Settings → Change Stop Protection → Enable.

Stop Protection vs. Termination Protection

Stop ProtectionTermination Protection
PreventsStopping the instanceTerminating (deleting) the instance
After protectionInstance stays runningInstance stays running/stopped
To overrideDisable stop protection firstDisable termination protection first

⚙️ Shutdown Behavior

Here is a scenario that catches engineers off guard: a developer is SSH'd into your Linux EC2 and types sudo shutdown now. Or a Windows user clicks Start → Power → Shut Down from inside the virtual machine. What does AWS do? Stop the instance? Or delete it entirely?

That is exactly what Shutdown Behavior controls.

Shutdown Behavior defines what happens to an EC2 instance when the OS-level shutdown command is executed from within the virtual machine.

Figure 8: Shutdown Behavior — Stop vs. Terminate path

The Two Options

OptionWhat HappensDefault?
StopInstance enters stopped state — data preserved, can be restarted✅ Yes
TerminateInstance is permanently deleted — all data on root volume lost❌ No

The default shutdown behavior is Stop — this is the safe default that preserves your instance.

How to View or Change Shutdown Behavior

Go to Actions → Instance Settings → Change Shutdown Behavior. You will see the current setting and can change it.

Alternatively, set it during launch under Advanced Details → Shutdown Behavior.

Performing OS-Level Shutdown (Linux Example)

When connected via SSH to a Linux instance, the shutdown command is:

sudo shutdown now

For Windows instances, it is the standard Start → Power → Shut Down from within the Remote Desktop session.

Critical Interaction: Shutdown Behavior + Protections

This is an important scenario that appears in AWS exams. What happens when protection settings conflict with shutdown behavior?

Figure 9: Shutdown Behavior × Protection Settings — all four combinations

Shutdown BehaviorProtection EnabledResult
StopStop Protection ONInstance remains running — protection wins
StopNo protectionInstance stops normally
TerminateTermination Protection ONInstance remains running — protection wins
TerminateNo protectionInstance terminated permanently

When protection settings conflict with shutdown behavior, protection always takes the upper hand — the instance remains running.

❌ Common Mistake: Setting Shutdown Behavior to "Terminate" without enabling Termination Protection. If a developer runs sudo shutdown now from inside the server, the whole instance gets deleted. Always pair Terminate shutdown behavior with Termination Protection if you need that configuration for a specific reason.

💤 Hibernation

You know the difference between turning off your laptop (Stop) and putting it into sleep mode (Hibernate). EC2 offers the same distinction. Hibernation is like pressing "sleep" on your laptop — work pauses mid-task and resumes exactly where it left off when you wake it up.

EC2 Hibernation saves the contents of RAM to the EBS root volume, then stops the instance — allowing it to resume from exactly the same state when started again.

Figure 10: Hibernation vs. Stop — what happens to RAM contents

What Happens During Hibernation

  1. You trigger hibernate on the running instance.
  2. The OS receives a hibernate signal and begins saving the entire contents of RAM to the EBS root volume (this is called a RAM dump).
  3. The instance stops — no CPU activity, no networking, no memory usage.
  4. When you start the instance again, the OS reads the RAM dump from EBS and restores it into memory.
  5. All applications, processes, and connections resume from the exact point they were paused.

Billing During Hibernation

During hibernation, there are no EC2 compute charges — but AWS charges for the EBS storage because the RAM dump is stored on disk.

Charge TypeStoppedHibernating
EC2 Compute❌ No charge❌ No charge
EBS Storage✅ Charged✅ Charged (extra: RAM dump)
Elastic IP✅ Charged if not associated✅ Charged if not associated

Hibernation Requirements

💡 According to AWS documentation, EC2 hibernation has specific requirements: the instance must be configured for hibernation at launch time (you cannot enable it after launch), the root EBS volume must be encrypted, and the EBS volume must be large enough to hold the RAM contents. Not all instance types support hibernation.

💰 EC2 Pricing Fundamentals

Before we dive into the five EC2 pricing models (which we will cover in the next session), let us make sure the fundamentals are crystal clear. Every cloud engineer needs to understand not just what AWS charges, but when and why.

What AWS Charges You For

When working with EC2, AWS charges across three dimensions:

Figure 11: EC2 Pricing Components — the three things AWS charges for

  1. Compute (EC2 Instance Charge): AWS charges for EC2 compute only when the instance is in the running state — billed per second (Linux) or per hour (Windows) based on instance type and region.

  2. EBS Storage: AWS charges for EBS storage based on the amount of storage provisioned (in GB-months) — regardless of whether the instance is running, stopped, or hibernating.

  3. Data Transfer Out: AWS charges for data transfer out (from AWS to the internet) but does NOT charge for data transfer in (uploads to AWS).

Pricing Varies by Region

The same T3.micro instance type costs different amounts in different AWS regions. Think of it like hotel pricing — a room at the Taj Hotel in Hyderabad costs less than the same room at the Taj in Mumbai, because land costs, operational costs, and demand differ by location.

EC2 pricing varies by instance type, operating system (Linux costs less than Windows), and AWS region.

💡 Free Tier: AWS provides 750 hours/month of T2.micro or T3.micro (depending on region) at no cost for the first 12 months. Plus 30 GB of EBS storage. This is enough to run a small instance 24/7 for free during your first year.

Billing by Instance State — Summary

StateCompute Charge?EBS Charge?
Running✅ Yes✅ Yes
Stopped❌ No✅ Yes
Hibernating❌ No✅ Yes (+ RAM dump)
Terminated❌ No❌ No (EBS deleted)

How to View Your Bills

Go to AWS Console → Billing and Cost Management → Bills. You will see charges broken down by service and region. For EC2, you will typically see:

  • EC2 running hours (e.g., T3.micro — X hours in Asia Pacific Mumbai)
  • EBS volume storage (e.g., 8 GB-month at $0.10/GB)
  • Data transfer out (if any outbound traffic occurred)

✅ Cost-Saving Tip: Always delete EC2 instances you are no longer using — not just stop them. A stopped instance still incurs EBS charges. If you are done with a project entirely, terminate the instance to stop all charges. If you might need the server again, stop it (compute charges pause but storage continues).

Unexpected AWS Bills — What to Do

If you receive an unexpected AWS bill (for example, because you forgot to delete resources), you can raise a support ticket explaining that you are a student and were unaware. AWS has historically waived charges for first-time incidents. This is a one-time goodwill waiver — do not rely on it repeatedly.

🎯 Study Tips and Career Advice

The instructor shared several practical pieces of advice during this session that apply to everyone learning cloud from scratch — especially those returning to study after a career break or managing study alongside household responsibilities.

Practice from Day One

Reading notes and watching sessions is not enough. The only way to truly learn cloud is to do it. Every concept you read — launch it, break it, fix it. When you experiment hands-on, mistakes become lessons that stick far longer than any text.

⚡ Aim for at least 30 minutes of hands-on AWS practice every day, separate from the live sessions. Open the console. Try to recreate what was taught. Make a mistake. Figure out why.

Focus Strategies for Returning Learners

Returning to technical study after a career break is genuinely challenging — your mind carries the weight of household tasks, family commitments, and self-doubt simultaneously. Here are strategies that help:

  • Time-blocking: Reserve a fixed daily window — even 30–45 minutes — that is non-negotiable study time. Treat it like a meeting you cannot cancel.
  • Break tasks into micro-steps: Instead of "practice EC2 today," set a specific goal: "Stop, start, and reboot one instance." Tiny wins build momentum.
  • Creative breaks help: Activities like walking, art, or cooking genuinely restore focus. They are not wasted time — they are productivity infrastructure.
  • Study groups and breakout rooms: Solving a lab with three or four people reduces frustration and builds accountability. When you explain something to a peer, your own understanding deepens.
  • It is okay to not remember everything: Cloud is vast. No one memorizes everything. What matters is knowing where to look and having hands-on muscle memory.

Handling AWS Billing Mistakes

If you accidentally leave resources running and receive an unexpected bill, do not panic and do not pay immediately. Contact AWS Support, explain that you are a student in training, and describe the situation honestly. AWS has a history of granting one-time billing credits for genuine mistakes by learners. Wait up to three months before considering payment — the support team will respond.

✅ Prevention is better than cure: After every lab session, go to EC2 → Instances and confirm all instances that are no longer needed are terminated. Set a reminder on your phone. This 30-second habit prevents surprise bills entirely.

📝 Overall Summary

  • Instance Lifecycle: EC2 instances move through states: Pending → Running → Stopping → Stopped → (Terminated). AWS charges compute only in the Running state.
  • EBS Always Charges: Even in the Stopped or Hibernating state, AWS charges for EBS storage because the disk remains allocated to your instance.
  • Vertical Scaling: Changing the instance type (CPU/RAM) of an existing instance. Scale Up = bigger, Scale Down = smaller. Requires stopping the instance (causes downtime).
  • Horizontal Scaling: Adding or removing instances. Scale Out = more instances, Scale In = fewer instances. No downtime — preferred for production.
  • Changing Instance Type: Stop → Actions → Instance Settings → Change Instance Type → Select new type → Save → Start. All files and settings are preserved.
  • Termination Protection: Blocks accidental permanent deletion. Enable for any production or critical instance. Instance stays running even if terminate is clicked.
  • Stop Protection: Blocks accidental stopping. Both protections take priority over shutdown behavior settings.
  • Shutdown Behavior: Controls what happens when OS-level shutdown is performed inside the VM. Default = Stop. Can be changed to Terminate (use with caution).
  • Hibernation: Saves RAM to EBS and pauses the instance mid-work. On restart, applications resume from the same state. Charges EBS only (no compute charge).
  • EC2 Pricing: Billed per second (Linux) or per hour (Windows) for compute while running, plus EBS storage always, plus data transfer out. Rates vary by region and instance type.

Project 1: EC2 Playground — Feel How It Behaves

🎯 Objective: Launch an instance, cycle through all lifecycle states hands-on, and observe the public IP change on stop/start. Then attach an Elastic IP to fix it.

⏱️ Time: 30–40 minutes

💰 Cost: Free Tier — T3.micro. Elastic IP: free while associated with a running instance.

Reading about lifecycle states is one thing. Watching them change in real time is something entirely different. This project is your first hands-on proof that you understand how EC2 actually behaves.

  1. Go to EC2 → Instances → Launch Instances. Set Name: playground-01. OS: Amazon Linux 2023. Type: T3.micro. Key pair: your existing key pair. Security group: allow SSH (port 22). Click Launch Instance.

    📸 Launch wizard filled out — name, AMI, type, key pair all set

    📸 Instance running — note the Public IPv4 address shown here

    📸 Back in Running — Public IP has changed after stop/start

    📸 Release the Elastic IP — unassociated IPs cost money

✅ What you proved: Stop/start changes the public IP. Reboot does not. Elastic IP gives you a permanent address. You now feel this — not just know it.

    📸 Creating a 10 GB gp3 volume for the billing experiment

  4. Attach it to billing-stopped: Select volume → Actions → Attach Volume → select billing-stopped → device /dev/sdf → Attach Volume.

    📸 Attaching the extra volume to the stopped instance

  5. After 1–2 hours: Billing and Cost Management → Bills → Current month → Elastic Compute Cloud → expand your region. Identify: the compute hours line (running instance only) and the EBS lines (both instances — the stopped one still has storage charges).

    📸 Billing breakdown — compute for running only, EBS for both instances

  6. Cleanup: Detach the extra volume (Volumes → Actions → Detach Volume). Delete it (Actions → Delete Volume). Terminate both instances.

    📸 Delete the volume — Available volumes still incur charges

✅ What you proved: A stopped instance still costs money (EBS). An extra volume costs money even when detached. You now read your bill like an engineer, not a student.

Project 5: Blue-Green Deployment — How Real Companies Avoid Downtime

🎯 Objective: Simulate a production resize with zero downtime. Deploy an app on Blue, launch Green, switch traffic by reassigning an Elastic IP, then terminate the old instance.

⏱️ Time: 45–60 minutes

💰 Cost: Two T3.micro instances for ~1 hour = within Free Tier. One Elastic IP: free while associated.

In Project 3 you measured the downtime from a vertical scaling resize. In production that downtime is unacceptable. This project shows you the exact strategy real companies use to resize without any customer-visible outage.

  1. Launch blue-server: Amazon Linux 2023, T3.micro, your key pair, allow SSH and HTTP. SSH in and set up a labelled page:

    sudo yum install -y nginx
sudo systemctl start nginx
echo "<h1>This is BLUE - T3.micro</h1>" | sudo tee /usr/share/nginx/html/index.html

    📸 Blue server live — this is your current production app

  2. Allocate an Elastic IP and associate it with blue-server. This is your stable production endpoint.

    📸 Elastic IP associated with blue-server — stable production address

  3. Access the app via the Elastic IP in your browser — confirm "This is BLUE".

  4. Launch green-server: Amazon Linux 2023, T3.micro, your key pair, allow SSH and HTTP. SSH in and deploy the upgraded version:

    sudo yum install -y nginx
sudo systemctl start nginx
echo "<h1>This is GREEN - Upgraded Server</h1>" | sudo tee /usr/share/nginx/html/index.html

    📸 Green server verified — ready for traffic, not yet receiving it

  5. Switch traffic: Elastic IPs → select the IP → Actions → Associate Elastic IP Address. Change instance from blue-server to green-server. Tick "Allow this Elastic IP to be reassociated". Click Associate.

    📸 Reassociating Elastic IP from Blue to Green — this IS the traffic switch

  6. Immediately refresh the Elastic IP in your browser. It now shows "This is GREEN". Traffic switched. Blue still running — zero downtime.

    📸 Same Elastic IP, now serving Green — zero downtime achieved

  7. Terminate blue-server. Green is the new production server — users never saw an outage.

  8. Cleanup: Disassociate and release the Elastic IP. Terminate green-server.

✅ What you proved: You switched production traffic without stopping anything. Zero downtime. Old server terminated cleanly. This is the pattern real companies use every time they resize or redeploy.
