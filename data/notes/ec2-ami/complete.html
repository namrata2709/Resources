🌟 Introduction

If EC2 is a virtual server in the cloud, then an AMI is the blueprint for that server — a saved snapshot of everything your server needs to run: the operating system, installed software, configuration settings, and even your files. Think of it as a master copy you can use to stamp out identical servers instantly, wherever you need them.

🖼️ What Is an AMI (Amazon Machine Image)?

An AMI (Amazon Machine Image) is a template that contains everything needed to launch an EC2 instance. You can think of it as a complete "system image" or a server blueprint.

Figure 2: What an AMI contains — OS, software, and configuration packaged together

An AMI contains the operating system, application software, and configuration settings needed to launch an EC2 instance. When you launch an EC2 instance, you must always select an AMI — it is a required parameter.

The Blueprint Analogy

Imagine a hotel chain. Every time they open a new hotel, they do not design the rooms from scratch — they follow a standard room blueprint: same furniture layout, same fixtures, same amenities. An AMI is exactly like that blueprint. You design your server once, save it as an AMI, and use it to "open" identical servers wherever you need them.

💡 Another way to think of it: AMI is to EC2 what a cookie cutter is to cookies. The cutter (AMI) defines the shape; the cookies (instances) are what you bake.

What an AMI Contains

  • Operating System: e.g., Amazon Linux 2, Ubuntu 22.04, Windows Server 2022
  • Installed Software: e.g., Apache HTTP server, Node.js, Python packages, databases
  • Configuration Settings: e.g., environment variables, system configs, file structure
  • One or more EBS Snapshots: The actual storage data (disk contents) that back the AMI

An AMI is backed by one or more EBS snapshots — backups of the root volume and any additional volumes attached to the instance.

AMI Scope — Region-Specific

AMIs are region-specific — an AMI created in one AWS region is not automatically available in another region. If you need to use the same AMI in a different region, you must explicitly copy it there using the Copy AMI action.

📚 Source: AWS EC2 AMI Docs

📦 Types of AMIs

When you launch an EC2 instance in the AWS Console, you are presented with an AMI selection screen. There are three main sources of AMIs:

Figure 3: The three AMI sources — Quick Start (AWS), My AMIs (custom), and Marketplace (third-party)

1. Quick Start AMIs (AWS-Provided)

These are AMIs maintained and published by AWS itself. They contain a clean operating system installation with no additional software. Examples:

  • Amazon Linux 2023
  • Ubuntu Server 22.04 LTS
  • Windows Server 2022 Base
  • Red Hat Enterprise Linux 9

Quick Start AMIs are maintained by AWS and always contain the latest security patches at the time of launch.

2. My AMIs (Custom / Your Own)

These are AMIs you have created yourself — either from a running EC2 instance (as demonstrated in this session) or imported from your own environment. The trainer referred to these as "Custom AMIs" or "My AMI".

Use My AMIs when you want to pre-install software so every new instance starts ready to work — no manual setup needed after launch.

3. AWS Marketplace AMIs

These are AMIs published by third-party vendors on the AWS Marketplace. They often come pre-installed with commercial software (e.g., a hardened security appliance, a pre-configured database, a licensed application). Many are free; some have an additional hourly cost on top of the EC2 instance price.

💡 Tip for Interviews: Be ready to explain the difference between Quick Start AMIs (AWS-managed, clean OS) and My AMIs (custom, pre-configured by you). This is a common interview question.

💽 EBS Snapshots and AMIs — How They Are Related

To understand AMIs fully, you need to understand their relationship with EBS (Elastic Block Store). EBS is the hard disk of your EC2 instance — it is the persistent storage where the OS, software, and files actually live.

Figure 4: When you create an AMI, AWS also creates an EBS Snapshot — the actual backup of your disk

The trainer made this relationship very clear in the session:

  • EBS Volume: The actual attached hard disk of your EC2 instance — e.g., 8 GB storage. This is where everything lives while the instance is running.
  • EBS Snapshot: A point-in-time backup of that EBS volume. An EBS snapshot is a backup of your hard disk — it captures the actual contents of your EBS volume at the moment you take the snapshot.
  • AMI: A higher-level template that references the EBS snapshot and adds launch configuration (instance type recommendations, architecture, block device mappings). When you create a custom AMI from an EC2 instance, AWS automatically creates an EBS snapshot of the root volume in the background.

⚡ Session Example: The trainer's instance had an 8 GB EBS volume attached. When they created a custom AMI, AWS took an EBS snapshot — which came out to only 1.6 GB because the snapshot only captures the used portion of the disk, not the entire allocated size.

The trainer summarized it perfectly: "EBS is your hard disk. The snapshot is the backup of your hard disk. The AMI is the backup of your entire server configuration — and it uses the snapshot as its storage."

📚 Source: AWS EBS Snapshots Docs

🛠️ Creating a Custom AMI — Step by Step

The trainer demonstrated creating a custom AMI live in the AWS Console. Here is the complete process, from a running EC2 instance to a reusable AMI.

Figure 5: The custom AMI creation process — from running instance to reusable blueprint

When Do You Need a Custom AMI?

You need a custom AMI when you want to replicate a configured server — not just a blank OS. The classic scenario the trainer described:

"I need to create more EC2 instances, but with the same software configuration as this one. Which AMI do I use?"

The answer: your Custom AMI (My AMI). Instead of launching a blank server and re-installing Apache, PHP, your application, and all your settings from scratch, you just pick your custom AMI and everything is already there.

Steps to Create a Custom AMI

  1. Go to EC2 → Instances in the AWS Console. Select the running instance you want to capture.

  2. Click Actions → Image and Templates → Create Image.

  3. Fill in the Image name (e.g., "my-webserver-ami") and an optional description. You can also adjust the storage configuration if needed — or leave it as is.

  4. Click Create Image. AWS will now create the AMI. The instance continues running during this process (no reboot needed for most cases, though AWS may reboot it to ensure a consistent state unless you disable that option).

  5. Go to EC2 → AMIs in the left menu. You will see your new AMI with a status of pending. Wait for it to change to available — this means it is ready to use.

  6. Go to EC2 → Snapshots to confirm the EBS snapshot was also created automatically in the background.

✅ Verification: Under AMIs, your new image should show Status: available. Under Snapshots, you should see a corresponding snapshot — this is the actual disk backup that powers your AMI.

Launching an EC2 Instance from Your Custom AMI

  1. Go to EC2 → Instances → Launch Instances.

  2. In the AMI selection step, instead of choosing Quick Start, click My AMIs.

  3. Select your custom AMI from the list.

  4. Complete the rest of the launch wizard as normal — choose instance type, network settings, key pair, security group, etc.

  5. Launch the instance. Once it starts, connect to it — you will find all your original software already installed and configured.

⚡ Session Demo Result: The trainer launched a new EC2 instance from their custom AMI, copied the public IP, opened it in a browser, and the web page (Apache + file system) was already running — with zero manual setup after launch.

🌍 Copying an AMI Across AWS Regions

This was one of the key practical demonstrations of the session. The trainer explained a common real-world scenario:

"A team member says: Sai, can you please create the same server in North Virginia? Will the AMI be available there?"

An AMI created in one region is NOT available in another region by default — you must explicitly copy it to the target region.

Figure 6: Copying an AMI from Mumbai to North Virginia — enabling multi-region deployment

Steps to Copy an AMI to Another Region

  1. Go to EC2 → AMIs. Select your custom AMI.

  2. Click Actions → Copy AMI.

  3. In the dialog, select the Destination Region — e.g., us-east-1 (US East / North Virginia).

  4. Optionally, add a new name or description for the copied AMI. Click Copy AMI.

  5. Switch your AWS Console to the destination region (North Virginia). Go to EC2 → AMIs. You will see your AMI appearing there with a status of pending.

  6. Once the status changes to available, you can launch EC2 instances from it in the new region — under My AMIs.

💡 Why This Matters: Imagine you have built a fully configured web application server in Mumbai and you need to expand to serve users in the US. Instead of manually setting up a server from scratch in North Virginia, you just copy the AMI and launch an identical server. This is how real-world multi-region deployments work.

Deleting an AMI

If you no longer need an AMI, you can remove it through a two-step process:

  1. Go to EC2 → AMIs, select the AMI, and click Actions → Deregister AMI. This removes the AMI template itself.
  2. Go to EC2 → Snapshots, find the corresponding snapshot, and click Delete Snapshot. This removes the actual stored data.

❌ Common Mistake: Deregistering an AMI does NOT automatically delete the underlying EBS snapshot. You must delete the snapshot separately to stop incurring storage charges.

📚 Source: AWS Copy AMI Docs

🚀 Why AMIs Matter — Real-World Use Cases

AMIs are one of the most practically useful features of EC2. Here are the real-world scenarios where they shine:

Figure 7: Four key real-world use cases for custom AMIs

1. Auto Scaling (Launch Identical Servers Fast)

When traffic spikes, you need more servers — fast. If those servers need Apache, Node.js, your application code, and 30 minutes of setup each, you cannot scale in time. With a custom AMI containing all of that pre-installed, a new server can be launched and ready in under 2 minutes.

2. Disaster Recovery

If your production server crashes or gets corrupted, a custom AMI lets you rebuild it from a known-good state in minutes. Creating regular AMIs of your production servers is a key disaster recovery best practice.

3. Multi-Region Deployment

As demonstrated in class — copy your AMI to another region and launch there. Users in the US or Europe can be served from servers close to them, reducing latency.

4. Golden Image Management

Large teams maintain a "golden AMI" — a standard, approved, hardened base image. All team members launch servers from this image, ensuring consistency across development, testing, and production environments. A golden AMI is a standardized, pre-approved AMI that enforces consistent configuration across all environments.

5. Cost Optimization via Spot Fleet (Mentioned, Coming Soon)

The trainer briefly touched on Spot Fleet — a feature that lets you define a set of instance type preferences (T2, T3, M5, etc.) and AWS automatically selects the cheapest available option to launch from. You provide an AMI and a fleet configuration; AWS handles the rest. This topic will be covered in more depth in a future session.

What Is DNS? (Brief Preview)

DNS is the internet's phone book. When you type www.google.com into a browser, your computer does not know where Google's server is — it asks a DNS system to translate that human-readable name into an IP address (like 142.250.80.46). Without DNS, you would need to memorize IP addresses for every website.

Amazon Route 53 (Brief Preview)

Amazon Route 53 is AWS's managed DNS service — it translates domain names into IP addresses and routes user requests to the correct AWS resources.

🎓 Exam Tips — AMI
  • AMIs are region-specific — they must be copied to be used in another region.
  • When you create a custom AMI, AWS automatically creates an EBS snapshot of the root volume.
  • Deregistering an AMI does NOT delete the EBS snapshot — you must delete it separately.
  • AMI IDs are unique — the same OS on two different AMIs will have different AMI IDs across regions.
  • To share an AMI with another AWS account, you can modify the AMI's permissions to make it private-shared or public.
  • An AMI must have a status of available before it can be used to launch instances.
  • AMIs support both HVM (Hardware Virtual Machine) and PV (Paravirtual) virtualization types — modern instances use HVM.
  • You are charged for EBS snapshot storage used by your AMIs. There are no charges for the AMI registration itself.

Project 1: Create a Custom AMI and Launch a Clone Instance

🎯 Objective: Create a custom AMI from a running EC2 instance with Apache installed, then launch a new instance from it and verify the software is pre-installed.

⏱️ Time: 20–30 minutes

💰 Cost: Free tier eligible (t2.micro / t3.micro instances)

  1. Log in to the AWS Console and navigate to EC2 → Instances. Confirm your base instance (with Apache installed) is in Running state.

    Figure 📸 Screenshot: Confirm instance is running before creating AMI

  2. Select the instance. Click Actions → Image and Templates → Create Image.

    Figure 📸 Screenshot: Actions → Image and Templates → Create Image menu path

  3. In the Create Image dialog, enter a name such as my-apache-ami. Leave storage settings as default. Click Create Image.

    Figure 📸 Screenshot: The Create Image dialog — enter name and click Create Image

  4. Navigate to EC2 → AMIs in the left sidebar. You will see your new AMI with status pending. Wait for it to change to available (usually 1–5 minutes).

    Figure 📸 Screenshot: AMI status showing 'available' — ready to use

  5. Navigate to EC2 → Snapshots. Confirm a snapshot was automatically created. Note its size — it should be smaller than the total EBS volume size.

  6. Go to Launch Instances. In the AMI selection, click My AMIs. Select my-apache-ami. Choose t2.micro. Use your existing key pair and security group (with port 80 and 22 open). Launch the instance.

    Figure 📸 Screenshot: My AMIs tab — select your custom AMI for launch

  7. Once the new instance reaches Running state, copy its Public IPv4 address and open it in a browser with http://<public-ip>. You should see the Apache default page — confirming the software was pre-installed from the AMI.

    Figure 📸 Screenshot: Apache page loading from cloned instance — AMI worked correctly

✅ Verification: Apache runs on the new instance without any manual installation. This confirms your custom AMI correctly captured the software configuration.

⚠️ Cleanup: Terminate both EC2 instances when done. Deregister the AMI (EC2 → AMIs → Actions → Deregister AMI) and delete the EBS snapshot (EC2 → Snapshots → Delete Snapshot) to avoid ongoing storage charges.

  4. Switch your AWS Console region to US East (N. Virginia). Navigate to EC2 → AMIs. You will see the copied AMI with status pending — wait for it to become available.

    Figure 📸 Screenshot: Copied AMI now available in N. Virginia region

  5. Launch a new EC2 instance in N. Virginia using this AMI (My AMIs tab). Verify Apache loads from the new instance's public IP.

Project 3: Versioned AMIs — Build and Compare v1 / v2 / v3

🎯 Objective: Create three progressively richer AMIs — Apache only, Apache + Node.js, and Apache + Node.js + a custom app page. Launch one instance from each and compare them side by side. Think and act like a dev team maintaining software versions.

⏱️ Time: 45–60 minutes

💰 Cost: Free tier eligible. Run all three instances briefly, then terminate.

Real teams never overwrite AMIs — they maintain versions. If v3 breaks in production, you roll back to v2 in minutes. This project teaches that discipline from day one.

Part A — Create v1: Apache Only

  1. Launch a fresh EC2 instance from a Quick Start AMI (Amazon Linux 2023). SSH into it and run:

    sudo yum update -y
sudo yum install httpd -y
sudo systemctl start httpd
sudo systemctl enable httpd
echo "<h1>Server v1 — Apache Only</h1>" | sudo tee /var/www/html/index.html

    Figure 📸 Screenshot: v1 Apache page loading in browser — confirm before creating AMI

  2. Confirm Apache serves the page, then create an AMI. Name it exactly: webserver-v1. Wait for status available.

    Figure 📸 Screenshot: webserver-v1 AMI available

Part B — Create v2: Apache + Node.js

  1. On the same running instance (do not launch a new one — build on top of v1's state), install Node.js:

    curl -fsSL https://rpm.nodesource.com/setup_18.x | sudo bash -
sudo yum install nodejs -y
node --version
echo "<h1>Server v2 — Apache + Node.js $(node --version)</h1>" | sudo tee /var/www/html/index.html

  2. Create another AMI from this same instance. Name it: webserver-v2. Wait for available.

Part C — Create v3: Full App

  1. Still on the same instance, create a small Node.js app file and update the page: 

    mkdir -p /home/ec2-user/myapp
cat > /home/ec2-user/myapp/app.js << 'EOF'
const http = require('http');
const server = http.createServer((req, res) => {
  res.end('Hello from Node.js App on Port 3000!');
});
server.listen(3000, () => console.log('App running on port 3000'));
EOF
echo "<h1>Server v3 — Apache + Node.js + App</h1><p>Node app on port 3000</p>" | sudo tee /var/www/html/index.html

  2. Create AMI. Name it: webserver-v3. Wait for available.

Part D — Launch and Compare All Three

  1. Launch one instance each from webserver-v1, webserver-v2, and webserver-v3 (three separate launches, My AMIs tab each time). Use the same security group and key pair.

    Figure 📸 Screenshot: Three instances running — one from each versioned AMI

  2. Open all three public IPs in your browser. Each should show its version-specific page — proving the AMIs captured different software states independently.

  3. SSH into the v3 instance. Confirm Node.js is installed with node --version. SSH into the v1 instance — run node --version. It will return command not found. This proves AMI isolation.

    Figure 📸 Screenshot: v1 instance — Node.js not present, confirming AMI version isolation

✅ Key Insight: Each AMI is a frozen snapshot of that exact moment. Changes made after creating an AMI do not affect earlier versions — and earlier AMIs do not include later software. This is version control for servers.

⚠️ Cleanup: Terminate all three instances. You can keep the three AMIs for reference, or deregister them and delete snapshots to avoid charges.

Project 4: Crash & Recover — AMI as Disaster Recovery

🎯 Objective: Simulate a server failure by terminating a running instance, then recover it from an AMI in under 5 minutes. Understand the critical distinction: AMI captures system state, but dynamic data must be stored externally.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier eligible

This is one of the most interview-relevant projects in this list. When an interviewer asks "how would you handle an EC2 instance failure?" — you need to be able to walk through exactly this scenario.

Part A — Set Up a "Production" Server

  1. Launch an EC2 instance from webserver-v2 (Project 3's AMI) or your my-apache-ami. Name it production-server.

  2. SSH in and add some "runtime data" to simulate the server being in active use: 

    # Simulate some log files and runtime content
sudo mkdir -p /var/app/logs
echo "App started at $(date)" | sudo tee /var/app/logs/app.log
echo "User session: user123 logged in" | sudo tee -a /var/app/logs/app.log
echo "<h1>Production Server</h1><p>All systems running</p>" | sudo tee /var/www/html/index.html

  3. Confirm the page loads and check your log file exists. Note the instance's public IP and instance ID.

    Figure 📸 Screenshot: Production server running and serving traffic

Part B — Simulate the Crash

  1. Go to EC2 → Instances. Select production-server. Click Instance State → Terminate instance. Confirm termination.

    Figure 📸 Screenshot: Terminating the production server — simulating a crash

  2. Try opening the old IP in your browser. It will time out — the server is gone.

Part C — Recover from AMI

  1. Go to Launch Instances. Under My AMIs, select the AMI you used for production-server. Use the same instance type, key pair, and security group. Name the new instance production-server-recovered. Launch it.

  2. Once running, open the new public IP in your browser. Apache loads — the system is recovered.

    Figure 📸 Screenshot: Recovered server serving traffic from the new instance — AMI recovery worked

  3. SSH into the recovered instance. Check for your log file:

    cat /var/app/logs/app.log

    The log file is gone. The AMI captured the system software and config — but the runtime data you wrote after the AMI was created was not included. This is expected and important.

    Figure 📸 Screenshot: Log file missing after recovery — AMI only captures state at creation time

❌ Critical Lesson: An AMI captures the system at the moment it was created — not live runtime data. Files written after the AMI was made are lost on termination. This is why production architectures separate system state (AMI) from data state (EBS volumes or S3).

✅ Real-World Pattern: In production, application logs go to Amazon CloudWatch Logs, user data goes to S3 or RDS, and the EC2 instance itself is treated as disposable. The AMI just provides the system template — it is never the data store.

⚠️ Cleanup: Terminate production-server-recovered. The original instance was already terminated in the simulation.

Project 5: The Stamp Test — Prove AMI Creates Truly Identical Instances

🎯 Objective: Launch 3 instances from the same AMI. Manually modify one of them. Then stop and restart all three — confirming that AMI behavior is identical at launch, and that changes on one instance do not affect others.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier. Three t2.micro instances for ~30 minutes = well within limits.

This project answers a question many beginners have: "If I change something on one instance, does it affect others launched from the same AMI?" The answer is no — and this project makes you feel that, not just read it.

  1. Launch 3 instances from the same AMI (use my-apache-ami or webserver-v2). Name them: stamp-1, stamp-2, stamp-3. Same key pair, same security group.

    Figure 📸 Screenshot: Three identical instances launched from the same AMI

  2. Open all three public IPs in the browser. All three should show the same Apache page — proving identical starting state.

  3. SSH into stamp-2 only. Change its page content:

    echo "<h1>I am stamp-2 — I was modified!</h1>" | sudo tee /var/www/html/index.html

  4. Now open all three IPs again. stamp-1 and stamp-3 still show the original AMI page. stamp-2 shows the modified page. This proves instances are independent after launch — modifying one has zero effect on others.

    Figure 📸 Screenshot: stamp-1 unchanged, stamp-2 modified — instances are independent

  5. Stop all three instances (not terminate — stop). Wait for status Stopped.

  6. Start all three instances. Get their new public IPs (stop/start changes the public IP). Open them in the browser.

    • stamp-1: still shows the original AMI page ✅
    • stamp-2: still shows the modified page ✅ (changes persist through stop/start — EBS root volume is persistent)
    • stamp-3: still shows the original AMI page ✅

    Figure 📸 Screenshot: All three instances running again after stop/start — note new public IPs

✅ Two things confirmed in one project:
1. AMI creates truly identical, independent instances — changes on one do not affect others.
2. Changes within a running instance persist through stop/start (EBS is persistent storage).

💡 Exam Tip: Stop/Start changes the public IP of an instance. The private IP and EBS volume data are preserved. To keep a fixed public IP, use an Elastic IP.

⚠️ Cleanup: Terminate all three stamp instances.

Project 6: Golden AMI Pipeline — Base → Web → Production

🎯 Objective: Build a layered AMI structure: a base hardened OS image, a web-tier image built on top of it, and a production-tagged AMI derived from the web tier. Document what each layer adds. This is how real engineering teams manage server standardization.

⏱️ Time: 60–90 minutes

💰 Cost: Free tier eligible. You only need one running instance at a time throughout this project.

In real companies, a "golden AMI" is a controlled, versioned base image that the entire team builds from. Nobody starts from a raw OS — they start from the golden AMI. This project teaches you to think in layers.

Figure: The Golden AMI Pipeline — each layer builds on the previous one

Layer 1 — Base AMI (OS + Hardening)

  1. Launch a fresh EC2 instance from Amazon Linux 2023 Quick Start AMI. SSH in and run the following to simulate OS hardening:

    # Apply all OS updates (security patches)
sudo yum update -y

# Install the AWS Systems Manager agent (standard in all golden AMIs)
sudo yum install -y amazon-ssm-agent
sudo systemctl enable amazon-ssm-agent
sudo systemctl start amazon-ssm-agent

# Install CloudWatch agent (for monitoring — standard in enterprise)
sudo yum install -y amazon-cloudwatch-agent

# Harden: disable root SSH login
sudo sed -i 's/PermitRootLogin yes/PermitRootLogin no/' /etc/ssh/sshd_config
sudo systemctl restart sshd

echo "Base hardening complete at $(date)"

  2. Create AMI. Name it: base-ami-v1. Tag it: Key = Layer, Value = base. Wait for available.

    Figure 📸 Screenshot: base-ami-v1 available with Layer tag applied

Layer 2 — Web AMI (Apache + Node.js on top of Base)

  1. Do not launch a new instance from scratch. Stay on the same instance (or launch from base-ami-v1 if you stopped it). Install the web layer on top:

    sudo yum install httpd -y
sudo systemctl start httpd
sudo systemctl enable httpd

curl -fsSL https://rpm.nodesource.com/setup_18.x | sudo bash -
sudo yum install nodejs -y

Project 7: Automate AMI Creation with AWS CLI

🎯 Objective: Move beyond clicking in the console. Use AWS CLI commands to create an AMI, check its status, and launch a new instance from it — all from the terminal. This is how real DevOps engineers work.

⏱️ Time: 30–45 minutes

💰 Cost: Free tier eligible

Nobody at a real company sits clicking "Create Image" in the console every time. AMI creation is automated — triggered by deployment pipelines, cron jobs, or scripts. This project is your first step into that world.

Prerequisites

  • AWS CLI installed and configured (aws configure with your access key, secret key, and region set to ap-south-1)
  • A running EC2 instance with Apache installed (use any from earlier projects)
  • The instance's Instance ID (format: i-0abc1234def56789) — copy it from the console

Step 1 — Create an AMI via CLI

  1. Run the following command, replacing YOUR_INSTANCE_ID with your actual instance ID:

    aws ec2 create-image \
  --instance-id YOUR_INSTANCE_ID \
  --name "cli-created-ami-$(date +%Y%m%d)" \
  --description "AMI created via AWS CLI on $(date)" \
  --no-reboot \
  --region ap-south-1

    This returns a JSON response containing the new ImageId. Copy it — you will use it in the next steps.

    Figure 📸 Screenshot: CLI output showing the new AMI ID after running create-image

Step 2 — Poll AMI Status Until Available

  1. Replace YOUR_AMI_ID with the ID from Step 1:

    aws ec2 describe-images \
  --image-ids YOUR_AMI_ID \
  --query 'Images[0].State' \
  --output text \
  --region ap-south-1

    Run this every 30 seconds. It returns pending while creating, then available when ready. Or use the built-in waiter:

    aws ec2 wait image-available --image-ids YOUR_AMI_ID --region ap-south-1
echo "AMI is now available!"

    Figure 📸 Screenshot: CLI confirm AMI state is 'available'

Step 3 — Launch an Instance from the CLI-Created AMI

  1. First, get your security group ID and subnet ID from the console, then run (replace all placeholder values):

    aws ec2 run-instances \
  --image-id YOUR_AMI_ID \
  --instance-type t2.micro \
  --key-name YOUR_KEY_PAIR_NAME \
  --security-group-ids YOUR_SG_ID \
  --subnet-id YOUR_SUBNET_ID \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=cli-launched-instance}]' \
  --region ap-south-1

    This returns detailed JSON. Look for InstanceId in the output to track your new instance.

    Figure 📸 Screenshot: CLI output from run-instances — note the InstanceId in the response

  2. Check instance status via CLI:

    aws ec2 describe-instances \
  --instance-ids YOUR_NEW_INSTANCE_ID \
  --query 'Reservations[0].Instances[0].State.Name' \
  --output text \
  --region ap-south-1

  3. Once running, go to the console to get the public IP, or query it via CLI:

    aws ec2 describe-instances \
  --instance-ids YOUR_NEW_INSTANCE_ID \
  --query 'Reservations[0].Instances[0].PublicIpAddress' \
  --output text \
  --region ap-south-1

    Open the IP in your browser — Apache should load, confirming the CLI-created AMI works exactly like a console-created one.

Step 4 — CLI Cleanup

  1. Terminate the instance:

    aws ec2 terminate-instances --instance-ids YOUR_NEW_INSTANCE_ID --region ap-south-1

  2. Get the snapshot ID backing your AMI:

    aws ec2 describe-images \
  --image-ids YOUR_AMI_ID \
  --query 'Images[0].BlockDeviceMappings[0].Ebs.SnapshotId' \
  --output text \
  --region ap-south-1

  3. Deregister the AMI:

    aws ec2 deregister-image --image-id YOUR_AMI_ID --region ap-south-1

  4. Delete the snapshot:

    aws ec2 delete-snapshot --snapshot-id YOUR_SNAPSHOT_ID --region ap-south-1

✅ What You Proved: Every action you have done in the console — create AMI, wait for available, launch instance, clean up — can be scripted. This is the foundation of infrastructure automation. The next step from here is wrapping these commands in a shell script or a Terraform configuration.

💡 What Real Companies Do: A CI/CD pipeline (e.g., GitHub Actions or Jenkins) runs these exact CLI commands automatically after every successful build — creating a fresh AMI with the latest code baked in, then updating Auto Scaling Groups to use the new AMI. You do not need to click anything.
