📖 Introduction

Imagine you are a school parent who invested a lot of money in your child's education. At the end of the year, the school hands you results — and only 60% of students passed. You are frustrated. You don't know where the problem was, when it happened, or who is to blame. Sound familiar?

This is exactly the problem software teams faced before DevOps. Developers would write code for months, hand it to operations, and only then discover nothing worked properly in production. DevOps was born to fix this — through better coordination, automation, and continuous feedback between development and operations teams.

🔄 Software Development Lifecycle (SDLC)

Every software product goes through a series of phases before it reaches the end user. This series of phases is called the Software Development Lifecycle, or SDLC.

Figure 2: SDLC Phases — a never-ending lifecycle

The Six SDLC Phases

Here are the phases in order, along with what happens in each:

  • Requirements: Gather what the client needs. What features? What problems to solve?
  • Design: Architect the solution. How will it look? How will components connect?
  • Development: Developers write the actual code.
  • Testing: QA teams verify the software works correctly and securely.
  • Deployment: Release the software to end users or customers.
  • Monitoring: Watch for bugs, performance issues, and gather user feedback to feed back into requirements.

SDLC is a never-ending lifecycle — monitoring feeds back into requirements, making it a continuous loop.

💡 Key Insight: The phases of SDLC are fixed. What changes is how you move between them — that is where methodology choices like Waterfall vs Agile make all the difference.

🌊 Waterfall Methodology

The Waterfall model is the oldest and most traditional approach to SDLC. Think of water flowing down a waterfall — it only moves in one direction and can never go back up.

Figure 3: Waterfall Model — each phase must fully complete before the next begins

What is the Waterfall Model?

Waterfall is a linear software development model where each phase must fully complete before the next phase starts — with no overlap and no going back.

In the Waterfall model, the sequence is strict: Requirements → Design → Development → Testing → Deployment → Maintenance. Once requirements are gathered at the start, they are frozen. No changes can be made without restarting the entire process — which is extremely expensive and time-consuming.

Real-World Waterfall Timeline

Here is what a typical 7-month Waterfall project looks like:

  • Month 1: Requirements gathering
  • Month 2: Design
  • Months 3–5: Development
  • Month 6: Testing
  • Month 7: Deployment — customers finally see the product

❌ The Problem: Customers see the product only after 7 months. If they don't like it — or requirements changed during those months — the entire effort may be wasted.

Why Waterfall Failed

Three major problems caused teams to abandon the Waterfall model in modern software development:

Problem 1 — Requirements Change in Real Life: In Waterfall, requirements are frozen at the start, but software requirements in real life keep evolving. Going back to change requirements means restarting the design, development, and testing phases — massive cost and delay.

Problem 2 — Late Feedback: Users see the software only at the very end, meaning feedback arrives too late to make meaningful changes without enormous effort. If users say "this feature doesn't work for us," months of work may be wasted.

Problem 3 — Very Slow Delivery: Waterfall provides no partial releases — the complete product is delivered only at the end. There is no way to get incremental value to users while development continues. Think of it like building an entire car, including engine, seats, tires, steering — and only then asking the customer if they like it.

⚡ Car Analogy: Imagine manufacturing a car completely — gathering requirements, designing, building all parts together, testing — and only then letting the customer drive it. If the engine vibrates, the seats are uncomfortable, and the steering is stiff, you have to redo the entire car. That is Waterfall.

🏃 Agile Methodology

Agile emerged as a direct response to Waterfall's failures. Instead of working for months in isolation, Agile breaks work into small, time-boxed cycles called sprints and continuously involves the customer.

Figure 4: Agile Sprint Cycle — small, repeating loops with continuous feedback

What is Agile?

Agile is an iterative software development methodology where work is divided into short cycles called sprints (typically 1–2 weeks), with working software delivered at the end of each sprint.

Going back to the school analogy: instead of one exam at the end of the year (Waterfall), Agile is like having module exams every 3 months. Students and teachers get feedback regularly, can correct course, and the final exam results are much better.

Core Agile Principles

  • Flexible: Requirements can change between sprints — nothing is frozen permanently.
  • Fast: Working software is delivered every sprint, not after many months.
  • Feedback-Driven: After every sprint, the team sits with the client to review the work, gather feedback, and plan the next sprint.
  • Customer Collaboration: The client is continuously involved, not just at the beginning and end.

In Agile, teams are regularly in touch with clients — gathering feedback after every sprint and adjusting requirements for the next one.

Agile Planning Tools

Two tools are central to day-to-day Agile work:

Jira: Jira is used to plan, assign, track, and report work in Agile projects — breaking big features into stories and tasks, organizing them into sprints, and tracking progress (To Do / In Progress / Done). It is not a coding or deployment tool — it is purely for organizing work.

Slack: A team communication tool used instead of email for instant coordination during sprints. Teams create channels for specific projects, sprints, or topics. Because many tools generate updates simultaneously and email is too slow, Slack provides real-time communication between developers, QA, operations, and product owners.

💡 Remember: Jira = plan and track work. Slack = communicate and get updates. These are two different purposes, two different tools.

🤔 Why DevOps? The Gap Agile Couldn't Fill

Agile was a massive improvement over Waterfall, but it introduced its own set of problems — specifically between the Development team and the Operations/Production team. DevOps emerged to fill the gap that Agile left behind.

Figure 5: The Dev-Ops Gap — the core problem DevOps solves

Problem 1: The "Works on My Laptop" Problem

The developer builds and tests code on their local Windows laptop running Node.js version 18. Everything works perfectly. They hand the code to the production team, who run it on a Linux server with Node.js version 14. The application crashes.

This is the environment mismatch problem — code works in the development environment but fails in production because configurations, OS versions, or dependency versions differ.

❌ The core issue: Developer says "It works on my laptop." Operations says "It doesn't work on production." Both are telling the truth — but for different environments. This blame game stalls deployment.

Problem 2: Manual Deployment Fear

In Agile, every sprint ends with new code that must be deployed to production. Without DevOps, this is done manually by the operations team:

  1. Log into production servers
  2. Stop the running application
  3. Copy new files to the server
  4. Change configuration files
  5. Restart the application

During manual deployment, the website is taken offline — users are affected every time a new version is released. With Agile sprints every 1–2 weeks, this becomes a constant disruption.

Naturally, the operations team starts resisting deployments: "Deploying this feature might be risky. Let's wait." The development team says the sprint is ready. Operations says it's unsafe to deploy. The sprint sits undeployed — the gap widens.

The Core Gap: Ready vs. Live

The sprint is ready but the software is not live — because deploying feels unsafe to the operations team. This is the exact gap DevOps was created to bridge.

⚡ Key Insight: Agile improved how we plan and build software. DevOps improves how we deploy and operate it. Together, Agile tells what to build in each sprint. DevOps tells how to build, test, and deploy it safely and automatically.

⚙️ What is DevOps?

DevOps is not a tool, a team title, or a product. It is a culture and set of practices that bridges the gap between development and operations by automating deployment, standardizing environments, and building shared responsibility.

Figure 6: How DevOps Solves Agile's Gaps

DevOps Solutions to Agile Problems

Agile ProblemDevOps Solution
Environment mismatchStandardized environments (Docker containers)
Manual deploymentAutomated deployment via CI/CD pipelines
Blame game between teamsShared responsibility model
Slow releases (ready but not live)CI/CD enables fast, frequent releases
Deployment failures with no recoveryAutomated rollback to previous version

DevOps Core Goals

The three core goals of DevOps are: Deploy Fast, Deploy Safely, and Operate Reliably.

DevOps achieves this by making development and operations teams work together as one unified team with shared tools, shared visibility, and shared accountability — rather than throwing code over a wall from one team to the other.

According to AWS documentation, DevOps represents a combination of cultural philosophies, practices, and tools that increases an organization's ability to deliver applications at high velocity — evolving and improving products faster than traditional software development processes.

🔁 CI/CD Explained

CI/CD stands for Continuous Integration and either Continuous Delivery or Continuous Deployment. It is the automation pipeline that makes DevOps real — automatically testing, building, packaging, and deploying code every time a developer makes a change.

Figure 7: A Complete CI/CD Pipeline — from code commit to production deployment

What is Continuous Integration (CI)?

Continuous Integration (CI) is the practice of automatically testing and building code every time a developer commits a change to the shared repository.

Here is what happens step-by-step when a developer commits code:

  1. Developer writes code in their own feature branch (not directly in main)
  2. Developer opens a pull request to merge into the main branch
  3. The CI system automatically detects the new commit
  4. Unit tests run against the new code
  5. The application is built (compiled/packaged)
  6. Code quality and security vulnerabilities are scanned
  7. A final deployable artifact (package) is created

If any step fails, the pipeline stops automatically and notifies the development team so they can fix the issue before it reaches production.

What is Continuous Delivery (CD — Delivery)?

Continuous Delivery means the application package is always ready to deploy to production, but a manual approval is required before the final push to live servers.

Think of it this way: the car is built, tested, and sitting in the showroom — fully ready. But someone must press the "release" button to hand the keys to the customer. The team reviews test reports and decides when to release (e.g., "we'll push to production tonight at midnight").

What is Continuous Deployment (CD — Deployment)?

Continuous Deployment means if all automated tests pass, the code is automatically deployed to production with no manual approval step.

Every code change that passes all tests goes directly to live users — no human in the loop. This is the fastest possible release cycle and is used by companies that deploy dozens or hundreds of times per day.

⚡ Key Difference to Remember:

  • Continuous Delivery = Always ready to deploy. Waits for manual approval.
  • Continuous Deployment = Always ready to deploy. Deploys automatically if tests pass.

CI/CD Across Environments

A full DevOps setup runs the same pipeline across multiple environments:

  • Development (Dev): Small instances (e.g., t2.micro). Used by developers to verify features work.
  • Staging / Pre-production: Medium instances (e.g., t2.medium). Mirrors production for final QA.
  • Production: Large instances (e.g., m5.large). Where real users interact with the software.

All environments use the same pipeline and same configuration — only instance sizes and resource capacities differ, eliminating environment mismatch.

🛠️ CI/CD Tools Deep Dive

A CI/CD pipeline is built by connecting multiple specialized tools together. Here are the key tools used in a real DevOps pipeline:

Figure 8: CI/CD Tool Chain — each tool plays a specific role

Jenkins — CI/CD Orchestration

Jenkins is a CI/CD orchestration tool that connects all other tools in the pipeline, creating automated workflows triggered by code commits.

Jenkins does not build, test, or deploy by itself — it acts as the conductor, telling each tool when to run and passing results between them. Jenkins has its own dashboard where you can see every pipeline run, which steps passed or failed, and detailed reports.

✅ Jenkins Alternatives: GitHub Actions (built into GitHub), CircleCI, GitLab CI/CD, AWS CodePipeline. All serve the same purpose — orchestrating CI/CD pipelines.

Maven — Build Tool

Maven is a build tool used primarily for Java applications. Its job is to compile your source code into a format the computer can execute, and bundle all dependencies into a final package. Without Maven (or a similar tool), your source code is just text — it cannot run on a server.

JUnit — Unit Testing

JUnit runs automated unit tests — small tests that verify individual functions or components of your code work correctly in isolation. If a unit test fails, Jenkins stops the pipeline immediately and notifies the team.

SonarQube — Code Quality & Security

SonarQube performs static code analysis — scanning source code for security vulnerabilities, code quality issues, and test coverage without actually running the code.

SonarQube grades the code (A, B, C, D) and produces a report. A Quality Gate is configured in Jenkins: if the code does not meet the minimum grade (e.g., 90% coverage, grade A), the pipeline stops and the code is not deployed.

JaCoCo — Code Coverage

JaCoCo (Java Code Coverage) measures what percentage of your code is actually tested by your unit tests. If you wrote 1,000 lines of code but your tests only exercise 500 of them, that is 50% coverage. Low coverage means bugs can hide in untested code.

JFrog Artifactory — Artifact Storage

JFrog Artifactory is an artifact repository where built deployment packages are stored and versioned. Every successful build produces a versioned artifact that can be deployed to any environment. If a deployment fails, you can roll back to a previous artifact version instantly.

GitHub — Source Control

All code lives in GitHub. Developers work in their own feature branches, and when ready, create a pull request to merge into the main branch. This merge event triggers the entire CI/CD pipeline automatically.

🏗️ Infrastructure as Code (IaC)

Creating servers manually in the AWS Console is fine for a single server — but imagine needing to create 50 identical servers across Dev, Staging, and Production environments. Doing this by hand is slow, error-prone, and inconsistent. This is the problem Infrastructure as Code (IaC) solves.

What is IaC?

Infrastructure as Code (IaC) is the practice of managing and provisioning cloud infrastructure — servers, networks, databases — using code files rather than manual clicks in a console.

With IaC, you write code once, and that same code can spin up identical infrastructure in Dev, Staging, and Production — with only minor configuration differences (like instance size). No more "works in Dev but not in Production" because of manual setup mistakes.

Terraform — Infrastructure Management

Terraform is an IaC tool used to provision and manage cloud infrastructure — VPCs, EC2 instances, databases, and networking — using declarative code files.

With Terraform, you write: "I want a VPC with these subnets, 3 EC2 instances of this type, and an RDS database." Terraform reads that code and creates exactly what you described in AWS.

Ansible — Configuration Management

Ansible is a configuration management tool used to manage software packages and configurations across many servers simultaneously.

If you need to install Node.js version 18 on 100 servers — or push a software update across all of them — Ansible does this automatically with a single playbook (configuration file), instead of logging into each server manually.

💡 Terraform vs Ansible in One Line:
Terraform creates the infrastructure (the server). Ansible configures what's on the server (the software).

🔬 Full DevOps Pipeline: End-to-End Walkthrough

Let's walk through exactly what happens in a real DevOps pipeline from the moment a developer writes code to the moment a customer uses the feature.

Figure 10: Complete DevOps Pipeline — from developer laptop to production

Step 1: Developer Commits Code

Developer writes code in their feature branch. Once ready, they merge into the main branch via a pull request. This merge event automatically triggers the Jenkins pipeline.

Step 2: Build (Maven)

Jenkins instructs Maven to compile the source code and bundle it with all dependencies. If the build fails (e.g., compilation error), the pipeline stops immediately.

Step 3: Unit Testing (JUnit)

JUnit runs all automated unit tests. Tests verify that individual functions behave correctly. Coverage is measured with JaCoCo. Failures stop the pipeline.

Step 4: Quality Gate (SonarQube)

SonarQube scans for vulnerabilities, code smells, and coverage. If the code fails the quality gate (e.g., coverage below 80%, critical security issue found), the pipeline halts and the developer is notified.

Step 5: Package & Store Artifact (JFrog)

The verified, tested, scanned code is packaged into a deployable artifact and stored in JFrog Artifactory with a version number. This artifact can be deployed to any environment.

Step 6: Deploy to Development Environment

The artifact is automatically deployed to Dev servers. Developers can test the feature end-to-end in an environment close to production.

Step 7: Deploy to Production (Delivery or Deployment)

There are two options at this stage:

  • Continuous Delivery: Pipeline pauses and waits for a human to click "Approve." The team reviews test reports and decides when to go live.
  • Continuous Deployment: If all tests passed the quality gate automatically, the artifact is deployed directly to production with no human approval needed.

Step 8: Monitor and Rollback if Needed

After deployment, monitoring tools watch for errors, performance degradation, or crashes. If a deployment causes issues, rollback to the previous artifact version in JFrog takes seconds — avoiding prolonged outages.

📝 Overall Summary

  • SDLC: The software development lifecycle has six phases — Requirements, Design, Development, Testing, Deployment, Monitoring — and is a never-ending loop.
  • Waterfall: A linear, sequential model where requirements are frozen and each phase must complete before the next begins. Problems: frozen requirements, late feedback, no partial releases, very slow delivery.
  • Agile: An iterative model using 1-2 week sprints with regular customer feedback. Improvements: flexible requirements, fast feedback, frequent releases. Tools: Jira (planning), Slack (communication).
  • DevOps Gap: Agile improved planning and development, but left two problems — environment mismatch ("works on my laptop") and manual deployment fear causing delays between sprint-ready and going-live.
  • DevOps: A culture and set of practices that automates deployment, standardizes environments, and creates shared responsibility between Dev and Ops teams. Goals: Deploy Fast, Deploy Safely, Operate Reliably.
  • CI (Continuous Integration): Automatically test, build, and package code every time a developer commits — stopping the pipeline if anything fails so bugs are found immediately.
  • Continuous Delivery: Code is always ready to deploy to production, but requires a manual approval before going live. Humans control the release timing.
  • Continuous Deployment: If all automated tests pass, code goes directly to production with no manual step. Maximum automation.
  • Key CI/CD Tools: Jenkins/GitHub Actions (orchestration), Maven (build), JUnit (unit tests), SonarQube (quality gate), JaCoCo (coverage), JFrog Artifactory (artifact storage), GitHub (source control).
  • IaC Tools: Terraform provisions infrastructure. Ansible configures software on servers. Together they eliminate manual setup and ensure consistent environments across Dev, Staging, and Production.

🔰 Project 1: Manual Deployment — Feel the Pain

🎯 Objective: Deploy a Node.js application manually to EC2 via SSH — no automation. Experience every step of the pain: version confusion, downtime, and config errors. This is exactly what DevOps replaces.

⏱️ Time: 30–45 min

💰 Cost: EC2 t2.micro — free tier eligible

💰 Cost Note: A t2.micro costs ~$0.012/hour outside free tier. Terminate when done.

Part A: Launch EC2 and Deploy

  1. Go to EC2 → Launch Instance. Name it devops-manual-deploy. Choose Amazon Linux 2023, instance type t2.micro. Create or select a key pair and download it.

    Figure 11: 📸 EC2 Launch — name, AMI, and instance type filled in

  2. Under Network settings, add inbound rules for SSH (port 22) from My IP and HTTP (port 80) from anywhere. Click Launch Instance.

    Figure 12: 📸 Security Group — SSH from My IP, HTTP open for app traffic

  3. Once running, copy the Public IPv4 address from the EC2 console. SSH in:

    ssh -i /path/to/your-key.pem ec2-user@YOUR_PUBLIC_IP

    Figure 13: 📸 Instance Running — copy Public IPv4 for SSH

  4. Install Node.js and deploy your app on the server:

    sudo yum update -y
sudo yum install -y nodejs git
git clone https://github.com/YOUR_USERNAME/YOUR_REPO.git
cd YOUR_REPO
npm install
node app.js &

  5. Visit http://YOUR_PUBLIC_IP in a browser. Confirm the app is running before continuing.

    Figure 14: 📸 App Running — confirm in browser before making changes

Part B: Break It Intentionally

  1. Make a code change locally, push it, then SSH back in and redeploy manually. You must stop the process first — causing downtime:

    ps aux | grep node
kill -9 PID_NUMBER
git pull origin main
npm install
node app.js &

  2. While stopped (between kill and restart), visit the app URL — it returns a connection error. This is deployment downtime. Every manual deployment causes this.

  3. Introduce a config error: change the port in app.js from 80 to 8080 without updating the Security Group. The app starts but the browser cannot reach it — the environment mismatch problem, with no automated check to catch it.

✅ What You Learned: Manual deployments cause downtime and expose config errors that only appear in production. No automated check exists — only you. This pain is exactly what CI/CD pipelines eliminate.

Cleanup

  1. SSH in and stop Node: kill -9 $(pgrep node)

  2. EC2 console → select instance → Instance State → Terminate Instance.

⚙️ Project 2: Full AWS CI/CD Pipeline (GitHub → CodePipeline → EC2)

🎯 Objective: Replace manual deployment with a fully automated AWS CodePipeline. Every push to GitHub builds, tests, and deploys to EC2 automatically — zero SSH steps required.

⏱️ Time: 60–75 min

💰 Cost: EC2 t2.micro (free tier). CodePipeline: first pipeline free. CodeBuild: 100 build minutes/month free.

💰 Cost Note: Additional CodePipeline pipelines cost ~$1/month. CodeBuild beyond free tier is ~$0.005/build minute. Terminate all resources after the project.

Part A: Prepare Your Repository

  1. Create buildspec.yml in your repo root — CodeBuild reads this to know what to run:

    version: 0.2
phases:
  install:
    runtime-versions:
      nodejs: 18
  pre_build:
    commands:
      - npm install
  build:
    commands:
      - npm test
      - echo "Build successful"
artifacts:
  files:
    - '**/*'

  2. Create appspec.yml — CodeDeploy reads this to know how to deploy:

    version: 0.0
os: linux
files:
  - source: /
    destination: /home/ec2-user/app
hooks:
  AfterInstall:
    - location: scripts/start_server.sh
      timeout: 300
      runas: ec2-user

  3. Create scripts/start_server.sh:

    #!/bin/bash
cd /home/ec2-user/app
npm install
pkill node || true
node app.js > /tmp/app.log 2>&1 &

    Commit and push all three files to main.

Part B: Create IAM Roles

  1. Go to IAM → Roles → Create Role. Create CodeDeployEC2Role for the EC2 service. Attach AmazonS3ReadOnlyAccess and AmazonEC2RoleforAWSCodeDeploy.

    Figure 15: 📸 IAM Role — EC2 as trusted entity, role name entered

  2. Create a second role CodeDeployServiceRole. Trusted entity: CodeDeploy service. Attach AWSCodeDeployRole.

Part C: Launch EC2 with CodeDeploy Agent

  1. Launch a new t2.micro (Amazon Linux 2023). In Advanced details, paste this User Data to auto-install the CodeDeploy agent:

    #!/bin/bash
yum update -y
yum install -y ruby wget
cd /home/ec2-user
wget https://aws-codedeploy-us-east-1.s3.amazonaws.com/latest/install
chmod +x ./install
./install auto
service codedeploy-agent start

  2. Set IAM instance profile to CodeDeployEC2Role. Tag the instance: Key: Name, Value: MyDeployTarget.

    Figure 16: 📸 EC2 Advanced Details — IAM role and User Data script both set

Part D: Create the Pipeline

  1. Go to CodePipeline → Create Pipeline. Name: my-devops-pipeline. Let AWS create a new service role.

    Figure 17: 📸 Create Pipeline — name and new service role configured

  2. Source stage: GitHub (Version 2) → connect your account → select repo and main branch.

    Figure 18: 📸 Source Stage — GitHub Version 2 connected, repo and branch selected

  3. Build stage: AWS CodeBuild → Create Project. OS: Amazon Linux 2023, runtime Standard. Select Use a buildspec file.

    Figure 19: 📸 CodeBuild — managed image, buildspec file from repo

  4. Deploy stage: AWS CodeDeploy. Create application MyApp, deployment group MyDeployGroup. Service role: CodeDeployServiceRole. Type: In-place. Environment: Amazon EC2 instances, tag filter Name: MyDeployTarget.

    Figure 20: 📸 CodeDeploy Group — in-place, targeting EC2 by tag

  5. Finish and save. The pipeline triggers immediately. Watch all three stages progress in the console.

    Figure 21: 📸 Pipeline Running — Source succeeded, Build in progress, Deploy pending

Part E: Break It and Watch It Stop

  1. Add a syntax error in app.js (e.g., append const x = with no value). Commit and push. Watch Build fail in the pipeline.

    Figure 22: 📸 Pipeline Failed — Build blocked deployment automatically

  2. Fix the error, push again. Pipeline succeeds. App updates on EC2 — no SSH.

✅ What You Learned: A CI/CD pipeline removes all manual steps. Build failures block deployment automatically. The only human job is fixing the code.

Cleanup

  1. Delete CodePipeline, CodeBuild project, CodeDeploy application and group.
  2. Terminate the EC2 instance and delete both IAM roles.

🧠 Project 3: Multi-Environment Pipeline with Manual Approval

🎯 Objective: Deploy through Dev → Staging → Production, with a human approval gate before Prod. Code reaches users only when a person clicks Approve — Continuous Delivery in practice.

⏱️ Time: 60–90 min

💰 Cost: Three EC2 t2.micro instances (~$0.012/hour each outside free tier). SNS is free. Terminate all instances promptly.

💰 Cost Note: Three simultaneous EC2 instances will exceed free tier for most accounts. Terminate all three immediately after completing this project.

Part A: Launch Three Tagged EC2 Instances

  1. Launch three EC2 t2.micro instances (Amazon Linux 2023) with the CodeDeploy agent User Data and CodeDeployEC2Role from Project 2. Tag them with different Env values:

    • Instance 1 — Env: dev
    • Instance 2 — Env: staging
    • Instance 3 — Env: prod

    Figure 23: 📸 Three Instances — Dev, Staging, and Prod all running with Env tags

Part B: Create Three CodeDeploy Deployment Groups

  1. In CodeDeploy application MyApp, create three deployment groups — each targeting one environment tag:

    • DevDeployGroup — tag filter Env: dev

  1. Go to SNS → Topics → Create Topic. Type: Standard. Name: pipeline-approval. Add a subscription: protocol Email, endpoint your email. Confirm from your inbox.

Part D: Build the Six-Stage Pipeline

  1. Edit your pipeline (or create new). Add stages in order: Source → Build → DeployToDev → DeployToStaging → ManualApproval → DeployToProd.

  2. ManualApproval stage: action provider Manual approval, SNS topic ARN set to your pipeline-approval ARN.

    Figure 25: 📸 Six-Stage Pipeline — ManualApproval sits between Staging and Prod

  3. Push a commit. Watch the pipeline auto-deploy to Dev then Staging. When it hits ManualApproval it pauses and sends you an email.

🔥 Project 4: Intentional Failure and Automated Rollback

🎯 Objective: Deploy a broken version, watch CodeDeploy automatically catch the failure and restore the previous working version — without any human intervention. Experience production incident response firsthand.

⏱️ Time: 45–60 min

💰 Cost: One EC2 t2.micro (free tier eligible) plus CodePipeline and CodeDeploy as in Project 2.

Part A: Enable Automatic Rollback

  1. Open your CodeDeploy Deployment Group → Edit → scroll to Advanced — Rollback configuration. Check Roll back when a deployment fails. Save.

    Figure 28: 📸 Rollback Config — automatic rollback on failure enabled

Part B: Establish v1 (Known Good)

  1. Push a clean working version of your app. Confirm the pipeline succeeds and the app loads at your EC2 IP. This is v1 — your baseline.

Part C: Deploy a Broken Version

  1. Open scripts/start_server.sh and change the start command to reference a nonexistent file:

    node nonexistent_app.js > /tmp/app.log 2>&1 &

  2. Commit and push. Source and Build both succeed (valid syntax). Deploy fails because the app crashes at startup. CodeDeploy logs the failure.

    Figure 29: 📸 Deploy Failed — AfterInstall hook failed, deployment halted

  3. With automatic rollback enabled, CodeDeploy immediately triggers a rollback deployment of the previous successful revision. Open the CodeDeploy deployments list — a new rollback deployment appears and succeeds automatically.

    Figure 30: 📸 Rollback Triggered — v1 automatically restored without human action

  4. Visit your EC2 app URL. It is still serving v1 — the broken version never reached users.

Part D: Fix and Redeploy

  1. Revert start_server.sh to node app.js. Push the fix. Pipeline runs cleanly — no rollback this time.

✅ What You Learned: Automated rollback means a failed deploy restores the previous version in seconds. Without it, a production failure means your site is down while developers scramble — potentially for hours. Rollback is not optional in any production system.

Cleanup

  1. Delete the CodePipeline, CodeDeploy application and group, CodeBuild project. Terminate the EC2 instance.

🧩 Project 5: Quality Gate — Block Low-Coverage Code Automatically

🎯 Objective: Add a minimum test coverage threshold to the CI pipeline. If a developer pushes code that drops coverage below 70%, the pipeline stops and the code never reaches any environment — not Dev, not Staging, not Production.

⏱️ Time: 45–60 min

💰 Cost: CodeBuild usage only (free tier: 100 min/month). Uses the same EC2 from Project 2.

⚡ Why This Matters: Companies enforce minimum test coverage in CI pipelines as a hard quality gate. Code with low coverage hides critical bugs. The automated threshold is the first line of defense — no human needs to remember to check.

Part A: Add Coverage Enforcement to buildspec.yml

  1. Update buildspec.yml to run Jest with a coverage threshold. The build fails (exits non-zero) if line coverage falls below 70%:

    version: 0.2
phases:
  install:
    runtime-versions:
      nodejs: 18
  pre_build:
    commands:
      - npm install
  build:
    commands:
      - npm test -- --coverage --coverageThreshold='{"global":{"lines":70}}'
      - echo "Coverage check passed"
artifacts:
  files:
    - '**/*'

  2. Ensure package.json uses Jest as the test runner:

    "scripts": {
  "test": "jest"
}

    Commit and push. If your current coverage exceeds 70%, the pipeline passes and deploys normally.

    Figure 31: 📸 Coverage Pass — 85% lines, threshold met, pipeline proceeds to deploy

Part B: Trigger the Quality Gate Failure

  1. Delete a test file (or empty it) to drop coverage below 70%. Commit and push.

  2. In CodeBuild, open the failed build and view logs. You will see Jest output showing coverage below threshold with a non-zero exit code blocking the build.

    Figure 32: 📸 Coverage Fail — 45% lines, threshold not met, build fails

  3. Check CodePipeline — the Deploy stage is grayed out. It was never triggered. Your EC2 instance is still running the last good version.

    Figure 33: 📸 Pipeline Blocked — quality gate stopped everything before any environment was touched

Part C: Fix and Restore

  1. Restore the test file or add new tests to bring coverage above 70%. Push. Build passes, pipeline deploys successfully.

✅ What You Learned: A quality gate is the automated enforcement of "don't ship untested code." It fires at commit time — before code touches any server — and requires zero human memory or discipline. This is standard practice at every serious engineering team.

Cleanup

  1. Delete the CodePipeline, CodeBuild project, CodeDeploy application and group. Terminate the EC2 instance.
