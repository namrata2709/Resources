🌟 Introduction

Imagine your hard drive is almost full. You have two choices: swap it out for a bigger one (that's Scale Up), or plug in a second external hard drive and use it alongside the first (that's Scale Out). Today's session is all about the second approach — and how to take safe, incremental backups of your storage using AWS Snapshots.

Figure 1: EBS Scale Out — adding extra storage to an existing EC2 instance

⚡ What you'll learn: How to attach a new EBS volume to EC2, format and mount it, make the mount permanent using /etc/fstab, take EBS Snapshots (incremental backups), and restore snapshots to a new volume.

These are real skills used daily by cloud engineers and DevOps professionals. By the end of these notes, you'll be able to manage EC2 storage with confidence.

📦 Quick Recap: EBS Volume Types

Before we dive into Scale Out, let's make sure we're clear on what EBS volume types exist — because you'll be choosing one when you create a new volume.

Figure 2: EBS Volume Types — SSD vs HDD branches

SSD Types

EBS SSD volumes are split into two families: General Purpose (GP2, GP3) and Provisioned IOPS (io1, io2).

  • GP3 (recommended default): GP3 allows you to independently configure IOPS and throughput without increasing storage size — this is NOT possible with GP2. Cost-effective, great for most workloads.
  • GP2: Older generation. IOPS scales automatically with volume size (3 IOPS per GB). You cannot manually set IOPS or throughput.
  • io1 / io2: For databases and workloads requiring very high, consistent IOPS. More expensive. io2 offers higher durability (99.999%).

HDD Types

  • st1 (Throughput Optimized HDD): For big data, log processing, data warehouses. Cannot be a boot volume.
  • sc1 (Cold HDD): Cheapest option. For infrequently accessed data. Cannot be a boot volume.

💡 Exam tip: Only SSD volumes (GP2, GP3, io1, io2) can be used as EC2 boot volumes. HDD types (st1, sc1) cannot boot an OS.

✅ Best Practice: For most new workloads, choose GP3. It's cheaper than GP2 at higher storage sizes and gives you independent control over IOPS and throughput.

📐 Scale Up vs Scale Out — What's the Difference?

Think of your kitchen. If you need more counter space, you have two options: replace your small counter with a bigger one (scale up), or add a second table in the corner (scale out). Both give you more space — but the approach, the process, and the trade-offs are different.

Figure 3: Scale Up vs Scale Out — when to use each approach

AspectScale Up (Resize)Scale Out (Add Volume)
What it doesMakes existing volume biggerAdds a brand-new volume
Downtime required?No (modify in-place)No (hot-attach)
Data preserved?YesN/A (new empty disk)

💡 In Scale Out, each new EBS volume must be in the same Availability Zone as the EC2 instance it will attach to. EBS volumes cannot span AZs.

🔧 Scale Out: Step-by-Step (Attaching a New EBS Volume)

Let's walk through exactly what happens when you scale out — adding a fresh 12GB EBS volume to an EC2 instance that already has an 8GB root volume. Think of it like plugging a new external hard drive into your laptop. The laptop detects it, but it can't just start using it — you need to prepare it first.

Figure 4: Scale Out 5-step workflow — from creation to mounted storage

Step 1: Verify AZ and Check Current Storage

Before creating a new volume, confirm which Availability Zone your EC2 instance lives in. The new volume must be created in the exact same AZ.

# Check current attached storage lsblk # Check disk space usage (human-readable) df -h

The lsblk command lists all block devices (disks and partitions). The df -h command shows how much space is used vs. available on each mounted file system.

Step 2: Create and Attach the Volume in AWS Console

  1. Go to EC2 → Elastic Block Store → Volumes
  2. Click Create Volume
  3. Choose GP3, set size (e.g., 12 GB)
  4. Set the Availability Zone to match your EC2 instance's AZ exactly.
  5. Click Create Volume
  6. Once created, select the volume → Actions → Attach Volume
  7. Choose your EC2 instance → Click Attach

📸 Screenshot: Create Volume page — note the AZ must match your EC2 instance

📸 Screenshot: Attach Volume — select your running EC2 instance

Step 3: Verify the New Disk in Linux

After attaching, SSH into your EC2 and run lsblk again. You'll see the new volume appear — but it has no partition or file system yet.

lsblk

You'll see something like nvme1n1 (12G) listed, but it won't be mounted anywhere. The OS can see the disk, but it doesn't know how to use it yet.

💡 Why nvme1n1? Older EC2 instances named disks like sdb. Modern instances use NVMe (Non-Volatile Memory express) naming — nvme0n1, nvme1n1, etc. NVMe is a faster interface protocol for SSD storage.

Step 4: Format the Volume (Create a File System)

Think of formatting like putting shelves and labels inside a brand-new empty room. The room exists, but without shelves, you can't organize anything inside it. Formatting creates the file system structure the OS can understand.

# Format as XFS file system (recommended for Amazon Linux 2023) sudo mkfs -t xfs /dev/nvme1n1 # Alternative: Format as EXT4 (more compatible, handles dirty shutdowns better) sudo mkfs -t ext4 /dev/nvme1n1

mkfs stands for Make File System — it converts a raw disk into a structured file system the OS can read and write to.

❌ XFS vs EXT4 gotcha: XFS requires a clean shutdown before mounting a restored snapshot. If you take a snapshot of a running XFS volume and restore it, you may see UUID conflicts or dirty log errors. EXT4 handles this more gracefully. For production workloads that involve snapshot-based restores, consider EXT4.

Step 5: Create a Mount Point Directory

A mount point is just a folder — an address where the OS will "attach" the disk. Without an address, the OS doesn't know where to point users when they try to access the new storage.

# Create a directory to serve as the mount point sudo mkdir /data

You can name this folder anything — /data, /backup, /extra. It's just a location in the file system tree.

Step 6: Mount the Volume (Temporarily)

# Mount the new volume to the mount point sudo mount /dev/nvme1n1 /data # Verify it's mounted df -h

Now df -h will show both your original partition (8GB) and the new 12GB mounted at /data. The OS can now read and write to both.

⚡ This mounting is temporary — if you reboot the EC2 instance, the mount point is lost and the disk is no longer accessible at /data. The next section covers how to make it permanent.

🔒 Making the Mount Permanent: /etc/fstab

Here's a real-world problem: you've attached and mounted a 12GB volume. Everything works. But after a reboot, it's gone — Linux forgot about it. Why? Because the mount command only works for the current session. When the system reboots, it re-reads a special configuration file called /etc/fstab (file system table) to know which disks to mount automatically.

Figure 5: How /etc/fstab enables automatic mounting during boot

Think of /etc/fstab like a startup checklist for Linux. Every time Linux boots, it reads this list and automatically mounts every disk listed in it. If your new volume isn't in this list, Linux won't know to mount it — so after a reboot, it's as if the disk was never attached.

Step 1: Get the Block UUID

Instead of using the device name (/dev/nvme1n1), we use the disk's UUID (Universally Unique Identifier). Device names can change after reboots or when disks are reattached. UUIDs are permanent — they identify the specific disk regardless of what name the OS assigns it.

# Get the UUID of your new volume sudo blkid /dev/nvme1n1

You'll see output like:

/dev/nvme1n1: UUID="a1b2c3d4-e5f6-7890-abcd-ef1234567890" TYPE="xfs"

Copy the UUID value (just the part inside the quotes).

Step 2: Edit /etc/fstab

# Open the fstab file with nano editor sudo nano /etc/fstab

The file will have existing entries for your root partition. Add a new line at the bottom for your new volume, following this format:

UUID=a1b2c3d4-e5f6-7890-abcd-ef1234567890 /data xfs defaults,nofail 0 0

Figure 6: Anatomy of an /etc/fstab entry — each column explained

Understanding Each Column

ColumnValueMeaning
DeviceUUID=...Which disk to mount (use UUID, not device name)
Mount Point/dataWhere to attach the disk in the file system
File SystemxfsThe format used when formatting the disk
Optionsdefaults,nofailStandard options + don't fail boot if disk is missing
Dump0Backup frequency (0 = disabled)
Pass0fsck check order (0 = skip for non-root)

⚡ The nofail option is critical — it tells Linux to continue booting even if this disk is unavailable, preventing EC2 from getting stuck in a boot loop if the volume is ever detached.

Step 3: Test Your fstab Entry (Important!)

Always test your fstab entry before rebooting. A bad fstab can prevent the system from booting.

# Unmount the disk first sudo umount /data # Re-mount everything in fstab (tests your new entry) sudo mount -a # Verify the disk is mounted df -h

If mount -a works without errors and df -h shows your disk, the fstab entry is correct. Now the mount will survive reboots.

✅ Best Practice: Always run sudo mount -a after editing /etc/fstab to validate your changes before rebooting. A typo in fstab can make your instance unbootable.

📸 EBS Snapshots — Incremental Backups

Now that we know how to add storage, let's talk about protecting it. Imagine you have important project files on your EC2's EBS volume. What happens if someone accidentally deletes the volume? What if a ransomware attack encrypts your data? What if the instance itself is terminated? That's where EBS Snapshots come in.

Figure 7: EBS Snapshots — how backups flow from EBS volumes to S3

What is an EBS Snapshot?

An EBS Snapshot is a point-in-time backup of an EBS volume, stored automatically in Amazon S3. You don't manage the S3 storage yourself — AWS handles it completely in the background.

Incremental Backups — How They Work

Here's the most important thing to understand about EBS Snapshots, and a very common exam question: snapshots are incremental, not full backups. Let's break down what that means with a real analogy.

Figure 8: Incremental backup — each snapshot stores only changed blocks, not the full volume

Imagine Google Photos backing up your phone. Today you have 200 photos (2GB). Google backs them all up. Tomorrow you take 5 more photos. Does Google re-upload all 200 photos again? No — it only uploads the 5 new ones. That's exactly how EBS Snapshots work.

EBS Snapshots are incremental — only the blocks that have changed since the last snapshot are stored, not the entire volume.

💡 Key fact: Even though snapshots are incremental internally, each snapshot is self-sufficient for restoration. You don't need all previous snapshots to restore from any single snapshot. AWS reconstructs the full state automatically.

Where Are Snapshots Stored?

EBS Snapshots are stored in Amazon S3, but the S3 bucket is managed by AWS — you cannot directly access or see it in your S3 console. You interact with snapshots only through the EC2 console or CLI.

Snapshot Cost

You pay for the storage used by your snapshots. Since snapshots are incremental, costs stay low — you only pay for changed data, not the entire volume every time.

⚡ Exam tip: The size of a snapshot reflects the amount of data used on the volume, not the total volume size. If your 8GB volume only has 1.6GB of data, the first snapshot is approximately 1.6GB, not 8GB.

📷 How to Take EBS Snapshots

You can take a snapshot of a specific volume, or of an entire EC2 instance (which snapshots all its attached volumes at once). Let's walk through both.

Method 1: Snapshot a Single Volume

  1. Go to EC2 → Elastic Block Store → Volumes
  2. Select the volume you want to back up
  3. Click Actions → Create Snapshot
  4. Add a description (e.g., "root-vol-backup-nov-19")
  5. Optionally enable encryption
  6. Click Create Snapshot

📸 Screenshot: Create Snapshot from Volume — note the Volume ID field to confirm you're backing up the right volume

Method 2: Snapshot an Entire EC2 Instance

  1. Go to EC2 → Elastic Block Store → Snapshots
  2. Click Create Snapshot
  3. Under Resource type, select Instance (instead of Volume)
  4. Select your EC2 instance from the dropdown
  5. This creates snapshots of all volumes attached to that instance

💡 When to use Instance vs Volume snapshots: Use Instance snapshots when you need a consistent backup of your entire server (OS + all data volumes). Use Volume snapshots when you only need to back up a specific data disk.

Snapshot Status

After creating a snapshot, its status shows as pending and gradually becomes completed. You can use a snapshot for restore even while it's pending, but the data may not be complete yet.

📸 Screenshot: Snapshot list — status transitions from Pending to Completed

Snapshot Best Practices

  • For application-consistent snapshots, stop or pause writes to the volume before taking the snapshot, or use AWS Data Lifecycle Manager to automate scheduled snapshots.
  • Always add meaningful descriptions so you know what each snapshot contains months later.
  • Delete old snapshots you no longer need — they cost money.
  • Use Amazon Data Lifecycle Manager (DLM) to automate snapshot schedules and retention policies.

♻️ Restoring from Snapshots

Taking backups is only half the story. You also need to know how to use them. Restoring a snapshot means creating a new EBS volume from the snapshot data, then attaching it to an EC2 instance.

Figure 9: Snapshot restore workflow — snapshot → new volume → attach to EC2

Create a New Volume from a Snapshot

  1. Go to EC2 → Elastic Block Store → Snapshots
  2. Select your snapshot
  3. Click Actions → Create Volume from Snapshot
  4. Choose the same AZ as the EC2 instance you'll attach it to
  5. Choose volume type, size (minimum = snapshot's original size)
  6. Click Create Volume

📸 Screenshot: Creating a volume from snapshot — AZ must match your target EC2

XFS UUID Conflict When Restoring

Here's a real-world issue you may encounter: when you restore an XFS-formatted snapshot to a new EC2 instance, you may get a mount error like "wrong filesystem type" or a UUID conflict. Why?

Figure 10: XFS UUID Conflict — Linux rejects duplicate UUIDs to protect against corruption

When you create a volume from a snapshot, the new volume inherits the original's XFS UUID. When you try to mount it on a different EC2 instance, Linux sees a duplicate UUID and blocks the mount to prevent potential corruption. The solution is to bypass the UUID check:

# Mount while bypassing UUID conflict check sudo mount -o nouuid /dev/nvme1n1 /data

The -o nouuid option tells the XFS driver to ignore the UUID conflict and mount anyway. This is safe when you know you're mounting a restored snapshot on a different instance.

💡 EXT4 vs XFS for snapshots: EXT4 handles dirty logs and UUID conflicts more gracefully during snapshot restores. If your workload involves frequent snapshot-based restores, EXT4 may be more practical.

✅ Pro tip: When in doubt, always check the AWS EBS documentation. AWS updates it regularly and provides exact commands for handling snapshot restore edge cases. Documentation is the cloud engineer's most important tool.

🌍 Copying Snapshots Across Regions

EBS volumes exist in a single Availability Zone. Snapshots exist in a single region. But you can copy snapshots to other regions — which is essential for disaster recovery. If your entire Mumbai region went down, you'd want a backup in Singapore.

Figure 11: Cross-region snapshot copy — the foundation of a multi-region disaster recovery strategy

How to Copy a Snapshot

  1. Go to EC2 → Snapshots
  2. Select your snapshot
  3. Click Actions → Copy Snapshot
  4. Select the destination region
  5. Optionally enable encryption in the destination
  6. Click Copy Snapshot

Copied snapshots are independent copies — deleting the original snapshot does not affect the copy in another region.

⚡ Use case: Cross-region snapshot copies are a core component of a Disaster Recovery (DR) strategy. By replicating snapshots to a second region, you can launch EC2 instances in that region even if the primary region becomes unavailable.

🖼️ AMI from Snapshot — Creating a Custom Machine Image

A snapshot preserves your data. But what if you want to launch a brand-new EC2 instance that's a perfect copy of your existing server — same OS, same software, same configuration? That's where AMIs (Amazon Machine Images) come in.

Figure 12: Creating an AMI from an instance — the foundation of auto-scaling and cloning

You can create an AMI from a running EC2 instance (which automatically creates a snapshot first), or you can register an AMI from an existing snapshot. The AMI can then be used to launch identical EC2 instances.

💡 Snapshot vs AMI: A snapshot is just a data backup of a volume. An AMI (Amazon Machine Image) is a launchable template that includes a snapshot plus boot instructions (kernel, device mappings). Snapshots back up data; AMIs let you clone entire servers.

🎓 Exam Tips: EBS Scale Out & Snapshots

These are the most commonly tested EBS concepts in AWS certification exams. Know these cold.

  • EBS volumes are tied to a single Availability Zone — they cannot be attached to instances in a different AZ.
  • EBS Snapshots are region-scoped but can be copied across regions for disaster recovery.
  • EBS Snapshots use incremental backup — only changed blocks are stored after the first snapshot.
  • Snapshots are stored in Amazon S3 (AWS-managed, not visible in your S3 console).
  • You can create an EBS volume from a snapshot in any AZ within the same region.
  • Only SSD volume types (GP2, GP3, io1, io2) can be used as boot volumes — HDD types cannot.
  • GP3 allows independent customization of IOPS and throughput without changing volume size; GP2 does not.
  • The nofail option in fstab prevents EC2 boot failure if an attached volume is unavailable.
  • XFS and EXT4 are both supported file systems — EXT4 is more forgiving with snapshot restores.
  • Deleting a snapshot does not delete the volumes or AMIs created from it.

📝 Overall Summary

  • Scale Out vs Scale Up: Scale Out means adding a new EBS volume alongside the existing one; Scale Up means resizing the existing volume. Both are non-disruptive on AWS.
  • AZ Constraint: A new EBS volume must be created in the same Availability Zone as the EC2 instance it will attach to — this is a hard requirement.
  • 5-Step Scale Out Process: Create volume in same AZ → Attach to EC2 → Format with mkfs → Create mount point directory → Mount with mount command.
  • Temporary vs Permanent Mounts: The mount command is session-only and is lost on reboot. Permanent mounts require adding the volume's UUID and mount details to /etc/fstab.
  • fstab nofail option: Always include nofail in fstab entries for non-root volumes to prevent boot failures if the volume is unavailable.
  • EBS Snapshots: Point-in-time, incremental backups of EBS volumes automatically stored by AWS in S3. Only changed blocks are stored after the first snapshot.
  • Snapshot size: Reflects the amount of data used on the volume, not the total volume size.
  • Restore process: Create a new volume from the snapshot in the target AZ → Attach to EC2 → Mount (use -o nouuid for XFS if needed).
  • Cross-region copies: Snapshots can be copied to other regions for disaster recovery; copies are independent of the original.
  • AMI relationship: AMIs use snapshots under the hood — an AMI is a launchable template while a snapshot is purely a data backup.

Project 1: Scale Out — Attach and Permanently Mount a New EBS Volume

🎯 Objective: Attach a new 12GB EBS volume to a running EC2 instance, format it as XFS, create a mount point, and make the mount permanent using /etc/fstab.

⏱️ Time: 25–35 minutes

💰 Cost: ~$0.01/hour for the volume. Remember to delete when done!

  1. SSH into your EC2 instance and check the current storage layout.

    lsblk df -h

    📸 Screenshot: lsblk before adding new volume — only one disk visible

  2. In the AWS Console, navigate to EC2 → Volumes → Create Volume. Set type GP3, size 12GB, and the same AZ as your instance.

    📸 Screenshot: Create Volume — AZ must exactly match your EC2 instance

  3. Select the newly created volume → Actions → Attach Volume → choose your instance → Attach.

    📸 Screenshot: Attach Volume dialog — select the correct running instance

  4. Back in SSH, run lsblk again to confirm the new disk is visible.

    lsblk

    📸 Screenshot: df -h after reboot — /data still mounted, confirming fstab entry works

Project 3: Multi-Volume Setup — Mount Three EBS Volumes for Data, Backup, and Logs

🎯 Objective: Attach three separate EBS volumes to one EC2 instance and mount them at /data, /backup, and /logs — exactly how production servers are organized.

⏱️ Time: 35–45 minutes

💰 Cost: ~$0.03/hour for 3 volumes combined. Delete all when done.

💰 Cost Note: You are creating 3 extra EBS volumes. Each charges approximately $0.01/hour. Delete all three volumes after this project.

Real production servers separate storage by purpose — OS on one disk, application data on another, and logs on a third. If logs fill up, they cannot crash your app. If app data grows, it does not overflow the OS disk. This project builds that architecture hands-on.

  1. In the AWS Console, create 3 new EBS volumes (all GP3) in the same AZ as your EC2: Volume A: 10 GB (for /data), Volume B: 8 GB (for /backup), Volume C: 5 GB (for /logs).

    📸 Screenshot: Three volumes in Available state — all in the same AZ as EC2

  2. Attach all three to your EC2: select each volume → Actions → Attach Volume → select your instance.

    📸 Screenshot: EC2 Storage tab — 4 volumes total, 3 newly attached

  3. SSH into EC2 and verify all four disks are visible:

    lsblk

    📸 Screenshot: lsblk — four disks visible, three new disks unmounted

  4. Format all three new volumes as XFS:

    sudo mkfs -t xfs /dev/nvme1n1 sudo mkfs -t xfs /dev/nvme2n1 sudo mkfs -t xfs /dev/nvme3n1

  5. Create all three mount point directories:

    sudo mkdir /data /backup /logs

  6. Mount all three volumes and verify with df -h:

    sudo mount /dev/nvme1n1 /data sudo mount /dev/nvme2n1 /backup sudo mount /dev/nvme3n1 /logs df -h

    📸 Screenshot: df -h — all three volumes mounted at /data, /backup, /logs

  7. Get UUIDs for all three volumes:

    sudo blkid /dev/nvme1n1 sudo blkid /dev/nvme2n1 sudo blkid /dev/nvme3n1

    📸 Screenshot: blkid — three UUIDs visible, copy all before editing fstab

  8. Edit /etc/fstab and add all three entries (replace with your actual UUIDs):

    sudo nano /etc/fstab # Add at the bottom: UUID=<uuid-nvme1n1> /data xfs defaults,nofail 0 0 UUID=<uuid-nvme2n1> /backup xfs defaults,nofail 0 0 UUID=<uuid-nvme3n1> /logs xfs defaults,nofail 0 0

    📸 Screenshot: fstab — three new entries added, one per volume

  9. Test fstab then reboot to confirm all mounts persist:

    sudo umount /data /backup /logs sudo mount -a df -h sudo reboot

    📸 Screenshot: df -h after reboot — all three mounts survived

✅ What you built: A production-style multi-volume EC2 layout. This is exactly how real servers are structured — isolating data types prevents one volume growing and crashing another.

✅ Cleanup: Remove all three fstab entries first, reboot to confirm nothing breaks, then detach and delete all three volumes.

Project 4: Break fstab on Purpose — Then Recover the Instance

🎯 Objective: Deliberately create a broken /etc/fstab entry, observe the boot failure, and recover the EC2 instance — one of the most important real-world recovery skills.

⏱️ Time: 30–40 minutes

💰 Cost: Small — only a 5GB test volume (~$0.01/hour). Delete when done.

⚡ Why this matters: A bad fstab entry is one of the most common ways engineers brick an EC2 instance. Interviewers ask: "Have you ever recovered a broken EC2?" After this project, your answer is yes.

  1. Attach a 5GB EBS volume to your EC2, format it, mount at /test, and add the correct fstab entry with nofail. Test with sudo mount -a to confirm it works first.

  2. Now deliberately break fstab — corrupt the UUID AND remove nofail:

    sudo nano /etc/fstab # Change working entry: # UUID=a1b2c3d4-e5f6-7890 /test xfs defaults,nofail 0 0 # To broken version (wrong UUID, no nofail): # UUID=XXXBROKEN-0000-0000 /test xfs defaults 0 0

    💰 Warning: After the next reboot, SSH will fail. The instance boots into emergency mode. This is intentional — you will recover it in the following steps.

  3. Reboot the instance: sudo reboot. Try to SSH in — it will fail.

  4. In the AWS Console, go to EC2 → Instances → select instance → Actions → Monitor and troubleshoot → Get system log. You will see the fstab error.

    📸 Screenshot: System log — fstab mount failure causing emergency mode

  5. Recovery steps (detach and re-attach root volume method):

    1. Stop the broken EC2 instance.
    2. Detach its root EBS volume (nvme0n1).
    3. Attach the detached root volume to a healthy EC2 as a secondary volume.
    4. SSH into the healthy EC2. Mount the attached root volume: sudo mount /dev/nvme1n1p1 /mnt
    5. Edit the fstab file inside the mounted volume: sudo nano /mnt/etc/fstab
    6. Fix the broken entry — restore the correct UUID and add nofail.
    7. Unmount: sudo umount /mnt. Detach the fixed volume from the helper EC2.
    8. Reattach to the original EC2 as the root volume. Start it — it should boot cleanly.

    📸 Screenshot: Instance running with 2/2 checks passed — fully recovered

✅ What you learned: How a bad fstab destroys a boot, how to read the system log to diagnose it, and the root-volume-swap recovery technique. This is a real interview answer.

✅ Golden rule reinforced: Always use nofail. Always test with sudo mount -a before rebooting. Never skip these steps.

✅ Cleanup: Remove the /test fstab entry and delete the 5GB test volume.

Project 5: Simulate Accidental Data Loss — Recover from Snapshot

🎯 Objective: Write important files to a volume, take a snapshot, delete the files, and recover them — the complete real-world incident recovery workflow.

⏱️ Time: 30–40 minutes

💰 Cost: ~$0.01/hour for the extra volume + a few cents for snapshot storage. Delete both when done.

Every cloud engineer will face "someone deleted the wrong files." The question is: did you have backups, and can you restore? This project makes sure your answer is yes.

  1. Attach a 5GB EBS volume to EC2, format as XFS, mount at /important-data, and add to fstab.

  2. Create important-looking files:

    cd /important-data echo "Customer records - DO NOT DELETE" | sudo tee customers.txt echo "Q4 2025 Financial Report" | sudo tee report.txt sudo mkdir config echo "app_key=production_secret_123" | sudo tee config/app.conf ls -la /important-data/

    📸 Screenshot: Important files created — customers.txt, report.txt, config directory

  3. Take a snapshot of the volume NOW (before any deletion). Go to EC2 → Volumes → select the 5GB volume → Actions → Create Snapshot. Description: important-data-before-deletion.

    📸 Screenshot: Creating the backup snapshot before the deletion

  4. Wait for snapshot to show Completed in EC2 → Snapshots. Then simulate the accident:

    sudo rm -rf /important-data/* ls -la /important-data/ # Directory is now empty

    📸 Screenshot: Files deleted — directory completely empty

  5. Recover: In EC2 → Snapshots, select your snapshot → Actions → Create Volume from Snapshot (same AZ). Attach the new volume to your EC2.

  6. Mount the restored volume and verify files are present:

    sudo mkdir /recovered sudo mount -o nouuid /dev/nvme2n1 /recovered ls -la /recovered/

    📸 Screenshot: Files recovered — all three items visible in the restored volume

  7. Copy the recovered files back to the original volume:

    sudo cp -r /recovered/* /important-data/ ls -la /important-data/

✅ What you practiced: Write → Backup → Delete (accident) → Restore. This is exactly what cloud engineers do at 2am during production incidents.

✅ Cleanup: Delete the snapshot. Detach and delete both EBS volumes. Remove both fstab entries.

💡 Hint

Snapshots are incremental and capture used data, not the total volume size.

3. Your EC2 is in ap-south-1b (Mumbai, AZ b). Can you attach an EBS volume created in ap-south-1a (AZ a)? Why or why not?

💡 Hint

EBS volumes have an AZ constraint — they can only attach to instances in the same AZ.

4. When would you choose EXT4 over XFS as your file system for an EBS volume?

💡 Hint

Consider snapshot restore scenarios and how each file system handles UUID conflicts and dirty logs.

💡 Hint

Snapshots can be duplicated and sent to another AWS geographic area.
