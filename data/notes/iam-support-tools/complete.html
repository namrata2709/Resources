🌐 Introduction

Before you can build anything in AWS, you need to understand one fundamental question: who is allowed to do what? That is exactly what this session answers. We cover AWS Identity and Access Management (IAM) — the security backbone of every AWS account — and then round out the picture with the tools AWS provides to support you, monitor your account health, and keep your usage within limits.

Figure 1: IAM sits at the center of every AWS account, controlling who can access which resources

Think of AWS as a giant, multi-floor office building. Before anyone can enter and use the facilities, two things must happen: they need to prove who they are (authentication) and they need to be told where they can go (authorization). IAM is the security desk at the entrance that handles both.

⚡ What this session covers: Root user vs IAM users · IAM Groups · IAM Roles · IAM Policies · MFA · AWS Support Plans · Health Dashboard · Trusted Advisor · Service Quotas

🔐 What is IAM?

IAM stands for Identity and Access Management. It is a global AWS security service that lets you manage who can sign in to your AWS account and what they can do once they're in.

When you first create an AWS account, you log in with an email and password — this creates your root user. But in the real world, you are not alone. A whole team needs access. IAM is the service that makes this safely possible.

💡 Office Building Analogy: Imagine your AWS account is a 10-floor office tower. Each floor has different resources (servers, databases, file storage). IAM is the security system that: issues ID cards (authentication), decides which floors each person can enter (authorization), and logs every entry and exit.

Figure 2: Authentication proves who you are; Authorization determines what you can do

Authentication vs Authorization

These two terms are used constantly in IAM and in security interviews:

ConceptQuestion AnsweredExample
AuthenticationWho are you?Scanning your employee ID card at the office entrance
AuthorizationWhat can you do?Your card lets you into floors 1–3 but not the executive floor

IAM handles both: it provides authentication (identity) through usernames, passwords, and access keys, and authorization (permissions) through policies attached to users, groups, and roles.

According to AWS documentation, IAM is available at no additional charge. You pay only for the AWS resources your users access.

📚 Source: AWS IAM User Guide

👑 The Root User

When you create an AWS account using an email address and password, those credentials belong to the root user. This is the most powerful identity in the entire account.

Figure 3: Root user has unrestricted access to everything; IAM users only access what policies allow

The root user has unrestricted access to all AWS services and resources, including the ability to manage billing, close the account, and create or delete IAM users.

Root User Best Practices

Because the root user is so powerful, the industry treats it like a master key to a building — you keep it locked away and only use it when absolutely necessary.

✅ Best Practice 1: Enable Multi-Factor Authentication (MFA) on the root user immediately after account creation. This adds a second layer of security beyond just the password.

✅ Best Practice 2: Use the root user only for account-level tasks — never for day-to-day work.

❌ Common Mistake: Logging in as root every day for regular tasks. If you accidentally delete a security group or misconfigure a service while logged in as root, you have the power to do real damage — and there is no easy undo.

Tasks That Require Root User

There are a small set of actions that only the root user can perform — no IAM user, no matter how privileged, can do these:

  • Change the AWS account name or email address
  • Close (delete) the AWS account
  • Restore IAM user permissions (if all admin access is accidentally removed)
  • Enable IAM access to the Billing and Cost Management console
  • View certain tax invoices
  • Register as a seller in the Reserved Instance Marketplace
  • Configure an S3 bucket to enable MFA Delete

⚡ Exam Tip: If an exam question asks "which action can only be performed by the root user?" — closing the account and changing the root email are the most common answers.

👤 IAM Users

An IAM user is an identity you create inside your AWS account to represent a person or application that needs to interact with AWS. Each IAM user gets their own credentials — separate from the root user — so the root credentials are never shared.

Figure 4: Each team member gets their own IAM user with only the access their role requires

Going back to our office building analogy: instead of giving everyone a copy of the master key, you issue each employee their own ID card. The cards look different from the master key, are limited in what they unlock, and can be deactivated without affecting anyone else.

IAM User Credentials

IAM users can have two types of credentials depending on how they interact with AWS:

Credential TypeUsed ForExample
Username + PasswordAWS Management Console (browser login)A developer logging into the AWS console visually
Access Key ID + Secret Access KeyAWS CLI, SDKs, and programmatic accessA Python script calling the S3 API

💡 Important: Access keys are like a username and password for code. They must be kept secret and rotated regularly. Never embed access keys directly in source code — use IAM roles instead (covered below).

Principle of Least Privilege

This is one of the most important security principles in all of AWS — and it will appear in exams repeatedly.

The Principle of Least Privilege states that every IAM identity should be granted only the minimum permissions required to perform its specific job — nothing more.

❌ Real Example of Why This Matters: If a developer's IAM user has full admin access and their credentials get compromised (phishing, leaked code), the attacker can now do anything in your AWS account. But if that developer only had EC2 and S3 access, the damage is contained.

✅ Apply This By: Start with no permissions. Add only what the person absolutely needs to do their job. Review and reduce permissions quarterly.

👥 IAM Groups

Imagine you have 50 developers. You could attach permissions to each developer individually — but that would be a nightmare to manage. If you need to update what developers can do, you'd have to edit 50 users one by one. IAM Groups solve this problem.

An IAM Group is a collection of IAM users. Policies attached to a group automatically apply to all users in that group.

Figure 5: IAM Groups let you manage permissions for multiple users at once

Key Facts About IAM Groups

  • IAM Groups cannot be nested — a group cannot contain another group, only users.
  • A user can belong to multiple groups simultaneously.
  • Groups are a convenience feature — permissions still ultimately live on the policies, not the group itself.
  • There is a default limit of 300 groups per AWS account.

💡 Real-World Use: Create groups like Developers, DBAs, QA, Finance. When you hire a new developer, simply add them to the Developers group — they instantly get the right permissions. When they leave, remove them from the group.

💡 Try This: Create three groups (Dev, QA, Finance). Add one user to both Dev and QA. Attach different S3 policies to each group. Observe what happens to that user's effective permissions.

🧠 Think Like an Engineer: A new developer joins your team. Instead of attaching policies directly to their user, what is the one-step process that gives them everything they need automatically?

📋 IAM Policies

Permissions in IAM are defined using policies — JSON documents that specify exactly what actions are allowed or denied on which resources.

An IAM Policy is a JSON document that defines permissions. It specifies: Effect (Allow or Deny), Action (what AWS operations), and Resource (which AWS resources).

Figure 6: Anatomy of an IAM Policy — Effect, Action, and Resource are the three core fields

Types of IAM Policies

Policy TypeDescriptionUse When
AWS Managed PoliciesPre-built by AWS, maintained by AWSCommon use cases — fast to apply (e.g., AmazonS3ReadOnlyAccess)
Customer Managed PoliciesYou create and maintain themCustom business requirements not covered by AWS defaults
Inline PoliciesEmbedded directly into a single user/group/roleOne-off permissions that apply to only one identity

Policy Evaluation — Allow vs Deny

When AWS evaluates whether an action is allowed, it follows a specific order:

  1. By default, all requests are implicitly denied. If no policy allows an action, it is denied.
  2. If a policy explicitly Allows an action, access is granted.
  3. If any policy explicitly Denies an action, it always wins — even if another policy allows it. An explicit Deny overrides everything.

⚡ Exam Trap: "A user is in two groups. Group A allows S3 access. Group B denies S3 access. Does the user have S3 access?" — No. Explicit Deny always wins.

💡 Try This: Create a policy that allows s3:GetObject on only one specific bucket ARN. Try accessing a different bucket — observe the Access Denied error.

⚠️ Break This: Add an explicit Deny on s3:GetObject alongside an Allow for the same action. Try to access S3 — the Deny always wins, even with an Allow present.

🧠 Think Like an Engineer: How would you prevent accidental deletion of production S3 objects while still letting developers upload? Which Effect and Action combination achieves this?

🎭 IAM Roles

So far we've talked about users (humans logging in) and groups (collections of humans). But what about services? If an EC2 instance needs to read from S3, how does it authenticate? It can't use a username and password. This is where IAM Roles come in.

An IAM Role is an identity that can be assumed by an AWS service, an application, or a user from another account. Roles are not tied to a specific person — they are temporary, assumable identities.

Figure 7: IAM Roles are used by services, applications, and cross-account scenarios

Roles vs Users — Key Difference

IAM UserIAM Role
Tied to a person?Yes — permanent identityNo — temporary, assumable
Has long-term credentials?Yes — password, access keysNo — temporary credentials via STS
Used byHumans logging inAWS services, apps, cross-account users
Credentials expire?No (unless rotated manually)Yes — automatically expire

Common Role Use Cases

  • EC2 to S3: Attach an IAM Role to an EC2 instance so it can read/write S3 without hardcoding access keys in the application.
  • Lambda execution role: Lambda functions need a role to write CloudWatch logs, access DynamoDB, etc.
  • Cross-account access: A user in Account A can assume a role in Account B to perform tasks there.
  • Identity federation: Let users from your corporate Active Directory or Google login assume AWS roles.

✅ Best Practice: Always use IAM Roles for EC2 and Lambda instead of storing access keys on the instance or in environment variables. Roles automatically rotate credentials — you never have to manage them.

💡 Try This: Launch an EC2 instance without an IAM Role. SSH into it and run aws s3 ls. Observe the credentials error. Then attach an IAM Role with S3 read access and run the same command — it works.

⚠️ Break This: Deliberately remove the IAM Role from a running EC2 instance mid-task. Notice how access is revoked immediately without any key rotation needed.

🧠 Think Like an Engineer: A teammate stored AWS access keys in a GitHub repo by accident. What is the fastest way to fix this using IAM Roles — and why is it more secure than rotating the keys?

🔒 Multi-Factor Authentication (MFA)

A password alone is a single point of failure. If it leaks, your account is compromised. MFA adds a second factor — something you physically possess — making unauthorized access dramatically harder.

MFA (Multi-Factor Authentication) requires a user to provide two forms of verification: something they know (password) and something they have (a one-time code from a device).

Figure 8: AWS supports multiple MFA device types — Virtual MFA is the most common for everyday use

MFA Device Options in AWS

TypeExampleNotes
Virtual MFA DeviceGoogle Authenticator, Authy, DuoMost common — free app on your phone
Hardware TOTP TokenGemalto tokenPhysical device — used in high-security environments
FIDO Security KeyYubiKeyUSB/NFC key — phishing-resistant
Hardware OTP Token (Root)AWS-provided tokenSpecifically for root account protection

✅ Best Practice: Enable MFA on the root user as the very first thing you do after creating an AWS account. Then enable MFA for all IAM users who have console access.

✅ IAM Best Practices Summary

Figure 9: IAM Best Practices — follow all 8 to keep your AWS account secure

  • ✅ Enable MFA on root user immediately after account creation
  • ✅ Do not use the root user for day-to-day operations
  • ✅ Create individual IAM users — never share credentials
  • ✅ Organize users into IAM Groups and attach policies to groups
  • ✅ Follow the Principle of Least Privilege — grant only the minimum required permissions
  • ✅ Use IAM Roles for AWS services (EC2, Lambda) — never store access keys on instances
  • ✅ Rotate access keys regularly and delete unused credentials
  • ✅ Monitor IAM activity with AWS CloudTrail
  • ✅ Use IAM Access Analyzer to find resources shared with external entities

🆘 AWS Support Plans

AWS offers five support plans, ranging from free to enterprise-level. Understanding what each plan includes is a common exam topic — especially knowing which features are unique to Business and Enterprise plans.

Figure 10: AWS Support Plans — five tiers from Basic (free) to Enterprise

1. Basic Support

  • Free — included with every AWS account
  • Access to AWS documentation, whitepapers, and support forums
  • AWS Personal Health Dashboard access
  • Trusted Advisor provides only 7 core checks on the Basic plan
  • No technical support from AWS engineers
  • No SLA for response time

2. Developer Support

  • Starts at $29/month (or 3% of monthly AWS usage — whichever is greater)
  • One primary contact can open technical support cases
  • Response time: business hours only
  • General guidance: < 24 business hours
  • System impaired: < 12 business hours
  • Best for: developers experimenting or in early development

3. Business Support

  • Starts at $100/month (or 10% of monthly usage for the first $10K — tiered)
  • All IAM users can open technical support cases (not just one primary contact)
  • Response time: 24/7 phone, email, and chat
  • Production system impaired: < 4 hours
  • Production system down: < 1 hour
  • Full access to all Trusted Advisor checks (not just 7)
  • Access to AWS Health API
  • Infrastructure Event Management (for a fee)

4. Enterprise On-Ramp Support

  • Starts at $5,500/month
  • Critical system down: < 30 minutes
  • Access to a pool of Technical Account Managers (TAMs)
  • Concierge Support Team for billing and account questions
  • Best for: companies moving to AWS at scale

5. Enterprise Support

  • Starts at $15,000/month
  • Critical system down: < 15 minutes
  • Dedicated Technical Account Manager (TAM)
  • Concierge Support Team
  • Infrastructure Event Management included (no extra fee)
  • Training and gamedays
  • Best for: large enterprises with mission-critical workloads

Figure 11: Response time SLAs across support plans — key exam content

⚡ Exam Tip: The most tested difference is: Business = full Trusted Advisor + 1-hour production-down SLA. Enterprise = dedicated TAM + 15-minute critical SLA. Basic = 7 Trusted Advisor checks only.

❤️ AWS Health Dashboard

AWS operates hundreds of services across dozens of regions. Things occasionally go wrong — a region might have an outage, a service might degrade. The AWS Health Dashboard is how AWS communicates this to you.

The AWS Health Dashboard has two components: Service Health (global AWS status visible to everyone) and Personal Health Dashboard (personalized alerts for resources in your specific account).

Figure 12: Service Health is public; Personal Health Dashboard is account-specific

Service Health (Global View)

  • Publicly available at status.aws.amazon.com
  • Shows the health status of all AWS services across all regions
  • No AWS account required to view
  • Use this to check: "Is there a known AWS outage affecting my region?"

Personal Health Dashboard

  • Available inside your AWS account console
  • Shows events that specifically affect your resources — not just global AWS status
  • Provides proactive notifications (e.g., "Your EC2 instance is on hardware that will be retired")
  • Can be integrated with EventBridge to trigger Lambda, SNS, etc. for automated responses
  • Accessible via the AWS Health API (requires Business or Enterprise support for programmatic access)

💡 Real-World Example: If a power issue occurs in the us-east-1a availability zone and your EC2 instance is there, the Personal Health Dashboard will alert you. The Service Health page shows the global outage but doesn't know it affects your instance specifically — only the Personal Health Dashboard does.

🧠 AWS Trusted Advisor

Think of Trusted Advisor as a knowledgeable friend who has reviewed thousands of AWS accounts and knows exactly what mistakes people make. It looks at your account configuration and tells you: "Here's what you should fix."

AWS Trusted Advisor is an automated tool that analyzes your AWS account and provides real-time recommendations across five categories: Cost Optimization, Performance, Security, Fault Tolerance, and Service Limits.

Figure 13: Trusted Advisor's five recommendation categories cover the most important aspects of AWS well-being

The Five Categories

CategoryWhat It ChecksExample
💰 Cost OptimizationAre you wasting money?Idle EC2 instances, underused EBS volumes, Reserved Instance opportunities
⚡ PerformanceAre resources sized correctly?EC2 instances with high CPU — should you upsize?
🔒 SecurityAre there security gaps?S3 buckets open to public, root user with no MFA, unrestricted SSH ports
🏥 Fault ToleranceWill it survive failures?EC2 instances not in multiple AZs, no backup enabled
📊 Service LimitsAre you close to AWS limits?80%+ of EC2 instance limit used in a region

Trusted Advisor Access by Support Plan

The Basic and Developer support plans get access to only 7 core Trusted Advisor checks. The Business and Enterprise plans unlock all checks across all five categories.

💡 The 7 core checks available on Basic/Developer plans are mostly security-focused: S3 bucket permissions, security groups with unrestricted ports, IAM use, MFA on root account, EBS public snapshots, RDS public snapshots, and service limits.

✅ How to Use Trusted Advisor: Go to AWS Console → Trusted Advisor → Refresh all checks → Review recommendations by category → Prioritize red (action recommended) items first → Work through yellow (investigation recommended) items next.

📊 Service Quotas and Service Limits

Every AWS service has limits on how much you can use. These exist to prevent runaway costs, resource exhaustion, and abuse. Understanding the difference between the two types of limits is an important exam concept.

AWS service limits, also called Service Quotas, define the maximum number of resources you can create or use within an account or region.

Figure 14: Soft limits are adjustable via a request; hard limits are fixed and cannot be changed

Soft Limits (Adjustable Quotas)

Soft limits are the default limits set by AWS that can be increased by submitting a quota increase request.

  • Also called adjustable quotas
  • You submit a request via the Service Quotas console or AWS Support
  • AWS reviews the request and approves or adjusts based on your use case
  • Examples: EC2 instances per region (default: varies by instance type), number of S3 buckets per account (default: 100, can be raised to 1,000+), VPCs per region (default: 5)

Hard Limits (Non-Adjustable Quotas)

Hard limits are fixed limits set by AWS that cannot be increased regardless of request — they are architectural constraints.

  • Also called non-adjustable quotas
  • No amount of support tickets will change these — they are by design
  • Examples:
Hard LimitValue
Default VPCs per region1
Internet Gateways per VPC1
Maximum S3 buckets per account100 (soft up to 1,000 — but 1,000 is the hard ceiling)
Elastic IP addresses per region (default)5 (this is actually a soft limit — can be raised)

How to Request a Quota Increase

  1. Go to AWS Console → Service Quotas
  2. Search for the service (e.g., EC2)
  3. Find the specific quota you need increased
  4. Click Request account-level quota increase
  5. Enter the desired value and a business justification
  6. AWS will review and respond (typically within 24–48 hours)

⚡ Exam Tip: If an exam asks whether a limit can be increased — check if it is soft (adjustable) or hard (non-adjustable). The most commonly tested hard limits are: 1 default VPC per region, 1 internet gateway per VPC.

📝 Overall Summary

  • IAM (Identity and Access Management): A global, free AWS security service that controls authentication (who you are) and authorization (what you can do).
  • Root User: The most powerful identity in an AWS account — used only for account-level tasks, always protected with MFA, never used for daily work.
  • IAM Users: Individual identities created for team members or applications; each gets their own credentials and permissions.
  • IAM Groups: Collections of users — policies attached to a group apply to all members; groups cannot be nested.
  • IAM Policies: JSON documents defining Allow or Deny rules on specific actions and resources; explicit Deny always overrides Allow.
  • IAM Roles: Temporary, assumable identities used by AWS services, applications, and cross-account scenarios — no long-term credentials.
  • Principle of Least Privilege: Grant only the minimum permissions needed — the foundational security principle of IAM.
  • AWS Support Plans: Five tiers — Basic (free, 7 Trusted Advisor checks), Developer ($29/mo), Business ($100/mo, all TA checks, 1-hr SLA), Enterprise On-Ramp ($5,500/mo, 30-min SLA), Enterprise ($15,000/mo, 15-min SLA, dedicated TAM).
  • Health Dashboard: Two views — Service Health (public, global status) and Personal Health Dashboard (account-specific alerts about your resources).
  • Trusted Advisor: Automated account analyzer with five categories (Cost, Performance, Security, Fault Tolerance, Service Limits); full access requires Business or Enterprise support.
  • Service Quotas: Soft limits are adjustable via a request; hard limits are architectural constraints that cannot be changed regardless of support level.

🔰 Level 1 — Permission Playground: Users, Groups & Policies

🎯 Objective: Build intuition fast — create 5 users, 3 groups, and 2 policies. Map who can do what. Break things on purpose and see what happens.

⏱️ Time: 40–55 minutes

💰 Cost: Free — IAM has no charges

Part A — Enable MFA on Root & Create Your Admin User

  1. Sign in to the AWS Console as the root user. Click your account name (top-right) → Security credentials.

    📸 Screenshot: Account dropdown with Security credentials visible

  2. Scroll to Multi-factor authentication (MFA) → Assign MFA device → choose Authenticator app → scan the QR code in Google Authenticator or Authy → enter two consecutive codes to verify → Add MFA.

    📸 Screenshot: MFA setup page with QR code wizard open

  3. Go to IAM → Users → Create user. Username: admin-user. Enable console access. Set a custom password. On permissions: create group Administrators, attach AdministratorAccess. Finish and download credentials.

    📸 Screenshot: IAM user creation form filled in

Part B — Build the Permission Playground

  1. Create 4 more IAM users (no console access needed — CLI/SDK access only). Names: dev-alice, dev-bob, readonly-carol, noaccess-dave.

  2. Create three groups: Developers, ReadOnly, NoAccess.

    📸 Screenshot: IAM User groups list showing all 3 groups created

  3. Create a custom policy named S3FullAccess-Custom with this JSON — allows all S3 actions:

    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": "s3:*",
    "Resource": "*"
  }]
}

  4. Create a second policy named S3ReadOnly-Custom:

    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": [
      "s3:GetObject",
      "s3:ListBucket",
      "s3:ListAllMyBuckets"
    ],
    "Resource": "*"
  }]
}

  5. Attach S3FullAccess-Custom to the Developers group. Attach S3ReadOnly-Custom to the ReadOnly group. Leave NoAccess group with no policies attached.

  6. Add users to groups: dev-alice and dev-bob → Developers. readonly-carol → ReadOnly. noaccess-dave → NoAccess.

Part C — Test the Permission Matrix

  1. Generate access keys for each test user: IAM → Users → select user → Security credentials → Create access key → choose CLI.

    📸 Screenshot: Security credentials tab with Create access key button

  2. Using the AWS CLI (or AWS CloudShell — free, no setup needed), configure profiles for each user:

    aws configure --profile dev-alice
# Enter: Access Key ID, Secret Access Key, region (e.g. ap-southeast-1), output format: json

  3. Test permissions using this matrix — run each command and record the result:

    # Test: list S3 buckets (requires s3:ListAllMyBuckets)
aws s3 ls --profile dev-alice
aws s3 ls --profile readonly-carol
aws s3 ls --profile noaccess-dave

# Expected: dev-alice ✅ | readonly-carol ✅ | noaccess-dave ❌

    📸 Screenshot: Terminal showing Access Denied error for noaccess-dave

✅ Verification: You should see Developers can list/read/write S3, ReadOnly can list but not write, and NoAccess gets Access Denied on everything. This is least privilege in action.

⚠️ Cleanup: Delete access keys for all test users. Optionally delete the test users and groups when done.

⚙️ Level 2 — Company Structure: Multi-Team IAM Setup

🎯 Objective: Set up IAM for a small company — Developers, QA, and Finance teams. Each group gets scoped permissions. Add one user to two groups and observe overlapping permissions.

⏱️ Time: 35–50 minutes

💰 Cost: Free

  1. Create three groups: Dev-Team, QA-Team, Finance-Team.

  2. Attach the following AWS Managed Policies to each group:

    • Dev-Team → AmazonEC2FullAccess + AmazonS3FullAccess
    • QA-Team → ReadOnlyAccess (read-only on everything)
    • Finance-Team → AWSBillingReadOnlyAccess

    📸 Screenshot: Dev-Team group with both policies attached

  3. Create these users and assign them to groups:

    • dev-john → Dev-Team
    • qa-sarah → QA-Team
    • finance-mike → Finance-Team
    • lead-priya → both Dev-Team and QA-Team (she leads dev and reviews QA)

  4. View lead-priya's effective permissions: IAM → Users → lead-priya → Permissions tab → click Simulate or expand the policy summary.

    📸 Screenshot: lead-priya permissions showing inheritance from two groups

  5. Use IAM Policy Simulator (IAM → Policy Simulator in left nav) to test specific actions:

    # Questions to test in the simulator for lead-priya:
# Can she do: ec2:RunInstances? (Yes — from Dev-Team)
# Can she do: s3:PutObject? (Yes — from Dev-Team)
# Can she do: s3:GetObject? (Yes — from both groups!)
# Can she do: iam:CreateUser? (No — neither group has IAM permissions)

    📸 Screenshot: Policy Simulator showing allowed and denied actions for lead-priya

✅ Key Insight: When a user belongs to multiple groups, they get the union of all group permissions. There is no conflict between two Allows — both apply. The Deny-wins rule only matters when there is an explicit Deny.

⚠️ Cleanup: IAM → Users → delete test users. IAM → User groups → delete the three groups.

🧠 Level 3 — Secure S3 Access System: Policy Design Thinking

🎯 Objective: Stop clicking and start thinking. Write policies from scratch — restrict access to one specific S3 bucket. Test the explicit Deny override. One user uploads but cannot delete.

⏱️ Time: 45–60 minutes

💰 Cost: Free (S3 bucket creation is free, small storage within free tier)

  1. Create an S3 bucket named iam-lab-bucket-[yourname] (must be globally unique). Leave all default settings.

    📸 Screenshot: S3 bucket creation with bucket name filled and public access blocked

  2. Create a custom policy named BucketUploader-Policy. This allows listing the specific bucket and uploading objects — but not deleting:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowListBucket",
      "Effect": "Allow",
      "Action": "s3:ListBucket",
      "Resource": "arn:aws:s3:::iam-lab-bucket-[yourname]"
    },
    {
      "Sid": "AllowUploadOnly",
      "Effect": "Allow",
      "Action": [
        "s3:GetObject",
        "s3:PutObject"
      ],
      "Resource": "arn:aws:s3:::iam-lab-bucket-[yourname]/*"
    }
  ]
}

  3. Create a second policy named BucketReader-Policy — read-only on the same bucket:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::iam-lab-bucket-[yourname]",
        "arn:aws:s3:::iam-lab-bucket-[yourname]/*"
      ]
    }
  ]
}

  4. Create two users: bucket-uploader (attach BucketUploader-Policy) and bucket-reader (attach BucketReader-Policy). Generate access keys for both.

  5. Test the uploader — these should succeed:

    # Upload a test file
echo "hello IAM" > test.txt
aws s3 cp test.txt s3://iam-lab-bucket-[yourname]/ --profile bucket-uploader
# Expected: upload: ./test.txt to s3://...

# Download the file
aws s3 cp s3://iam-lab-bucket-[yourname]/test.txt ./downloaded.txt --profile bucket-uploader
# Expected: download: s3://... to ./downloaded.txt

  6. Now test what the uploader cannot do:

    # Try to delete the file — should FAIL
aws s3 rm s3://iam-lab-bucket-[yourname]/test.txt --profile bucket-uploader
# Expected: An error occurred (AccessDenied) when calling the DeleteObject operation

    📸 Screenshot: Access Denied error when uploader tries to delete — confirming least privilege policy works

  7. Now test the Explicit Deny override. Attach this additional inline policy directly to bucket-uploader:

    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Deny",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::iam-lab-bucket-[yourname]/*"
  }]
}

  8. Try to download again — even though BucketUploader-Policy allows s3:GetObject, the Deny wins:

    aws s3 cp s3://iam-lab-bucket-[yourname]/test.txt ./test2.txt --profile bucket-uploader
# Expected: AccessDenied — explicit Deny overrides the Allow!

    📸 Screenshot: Explicit Deny overrides the Allow — bucket-uploader can no longer download despite having Allow policy

✅ Key Insight: Resource-scoped policies prevent access to any other bucket. And explicit Deny is absolute — it overrides everything. Remove the inline Deny policy to restore download access and confirm it works again.

⚠️ Cleanup: Delete all objects in the bucket → Delete the bucket. Delete the two users, both custom policies, and the inline policy.

🔐 Level 4 — Zero Credential Architecture: EC2 + IAM Role

🎯 Objective: Launch an EC2 instance. First, try to access S3 without a role — it fails. Then attach an IAM Role with S3 access — it works. No access keys anywhere. This is how production systems are built.

⏱️ Time: 45–60 minutes

💰 Cost: EC2 t2.micro or t3.micro is free tier eligible. S3 is free tier. Remember to terminate the instance after.

💰 Cost Note: EC2 instances incur charges once your free tier hours are exhausted (~750 hrs/month). Terminate the instance immediately after completing this project.

  1. Launch an EC2 instance: EC2 → Launch Instance. Name: iam-role-test. AMI: Amazon Linux 2023. Instance type: t2.micro. Create or select a key pair. Leave all other defaults. Do NOT attach an IAM role yet. Click Launch instance.

    📸 Screenshot: EC2 launch with IAM instance profile field empty

  2. Connect to the instance using EC2 Instance Connect (no key pair needed in browser): EC2 → Instances → select instance → Connect → EC2 Instance Connect → Connect.

    📸 Screenshot: EC2 Instance Connect tab ready to connect

  3. Inside the EC2 terminal, try to list S3 buckets — this should fail because there are no credentials:

    aws s3 ls
# Expected: Unable to locate credentials. You can configure credentials by running "aws configure".

    📸 Screenshot: EC2 terminal showing Unable to locate credentials error

  4. Now create the IAM Role. Go to IAM → Roles → Create role. Trusted entity type: AWS service. Service: EC2. Click Next.

  5. Search for and attach the policy AmazonS3ReadOnlyAccess. Name the role EC2-S3-ReadOnly-Role. Click Create role.

    📸 Screenshot: IAM Role creation with EC2 trusted entity and S3ReadOnly policy selected

  6. Attach the role to the running EC2 instance: EC2 → Instances → select iam-role-test → Actions → Security → Modify IAM role → select EC2-S3-ReadOnly-Role → Update IAM role.

    📸 Screenshot: Modify IAM role page with the role selected and ready to attach

  7. Return to the EC2 Instance Connect terminal. Run the same command again:

    aws s3 ls
# Expected: Lists all S3 buckets in your account — no credentials entered anywhere!

    📸 Screenshot: aws s3 ls successfully lists buckets after role attachment — credentials provided by role automatically

  8. Confirm the credentials come from the role — not from any user:

    aws sts get-caller-identity
# Expected output shows: "Type": "AssumedRole" and the role ARN — confirming it's the role, not a user

✅ Key Insight: The EC2 instance obtained temporary credentials automatically from the IAM Role via the instance metadata service (IMDS). No access keys were stored anywhere. This is the production-standard pattern for all EC2 applications.

💰 Cleanup (Required): EC2 → Instances → select iam-role-test → Instance state → Terminate instance. IAM → Roles → delete EC2-S3-ReadOnly-Role.

🏢 Level 5 — Production-Ready IAM Architecture (Portfolio Project)

🎯 Objective: Build a complete, job-level IAM structure for a startup with 5 teams. This is what you explain in interviews. Least-privilege policies, roles for services, MFA enforcement, no root usage.

⏱️ Time: 60–90 minutes

💰 Cost: Free — IAM, S3 bucket creation, and basic EC2 t2.micro are all free tier

⚡ Scenario: You are the cloud engineer for a startup called NovaTech. The company has: a Dev team, a QA team, a Finance team, a DevOps team, and an External Auditor (third-party, different account). You need to design their IAM from scratch.

Step 1 — Create the Group Structure

  1. Create 4 IAM Groups with these policies:

    GroupPolicyReason
    NovaTech-DevAmazonEC2FullAccess + AmazonS3FullAccessDevelopers need to deploy and manage app infrastructure
    NovaTech-QAReadOnlyAccessQA reads resources to verify — never modifies
    NovaTech-FinanceAWSBillingReadOnlyAccessFinance views costs — no AWS resource access
    NovaTech-DevOpsAdministratorAccessDevOps manages the full platform

    📸 Screenshot: All 4 NovaTech groups created and visible in the groups list

Step 2 — Create Users and Assign to Groups

  1. Create one user per team. Enable console access. Require password change on first login. Add to the appropriate group.

    • dev-user1 → NovaTech-Dev
    • qa-user1 → NovaTech-QA
    • finance-user1 → NovaTech-Finance
    • devops-user1 → NovaTech-DevOps

Step 3 — Create an IAM Role for EC2

  1. Create a role named NovaTech-App-Role with trusted entity EC2 and attach AmazonS3ReadOnlyAccess. This role will be used by the application servers to read configuration from S3 — no hardcoded keys anywhere.

Step 4 — Enforce MFA via Policy

  1. Create a customer managed policy named RequireMFA-Policy with the following JSON. This policy denies all actions except MFA setup if MFA is not present:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyAllExceptMFASetup",
      "Effect": "Deny",
      "NotAction": [
        "iam:CreateVirtualMFADevice",
        "iam:EnableMFADevice",
        "iam:GetUser",
        "iam:ListMFADevices",
        "iam:ListVirtualMFADevices",
        "iam:ResyncMFADevice",
        "sts:GetSessionToken"
      ],
      "Resource": "*",
      "Condition": {
        "BoolIfExists": {
          "aws:MultiFactorAuthPresent": "false"
        }
      }
    }
  ]
}

  2. Attach RequireMFA-Policy to ALL four NovaTech groups. Now any user who logs in without MFA can only set up MFA — they cannot do anything else until they do.

    📸 Screenshot: RequireMFA-Policy attached to NovaTech-Dev group alongside existing permissions

Step 5 — Document Your Architecture

  1. Use the IAM Policy Simulator to verify the correct users have access to the right services. Screenshot the simulator results for your portfolio.

    📸 Screenshot: Policy Simulator results confirming dev-user1 can access EC2 and S3 but not IAM or RDS

  2. Review your setup against this production checklist:

    • ☑️ Root user has MFA and is not used for daily work
    • ☑️ All users have MFA enforcement (deny without MFA)
    • ☑️ No user has more permissions than their role requires
    • ☑️ EC2 applications use roles — no access keys on servers
    • ☑️ Each team is in a group — permissions managed centrally
    • ☑️ Finance can see bills but cannot touch any AWS resources

✅ This is your portfolio project. You can explain this in an interview as: "I designed the IAM architecture for a startup — created least-privilege groups per team, enforced MFA via policy, and ensured application servers use roles instead of access keys." That sentence alone demonstrates production-level thinking.

⚠️ Cleanup: IAM → Users → delete all NovaTech test users. IAM → User groups → delete all 4 groups. IAM → Roles → delete NovaTech-App-Role. IAM → Policies → delete RequireMFA-Policy.
