📚 Background / Theory

What is AWS CloudFormation?

AWS CloudFormation is an Infrastructure as Code (IaC) service that lets you model, provision, and manage AWS resources using template files written in JSON or YAML. You describe what you want — a VPC, an EC2 instance, a security group — and CloudFormation figures out the order to create them, handles dependencies, and builds everything as a single unit called a stack.

Think of a CloudFormation template like an IKEA instruction manual. The manual (template) describes every part and every step. You hand it to CloudFormation, which plays the role of the builder — assembling everything in exactly the right order, every time.

According to AWS documentation, CloudFormation is available at no additional charge — you only pay for the AWS resources created by your templates (EC2 hours, S3 storage, etc.).

Why Use CloudFormation?

Before IaC tools like CloudFormation, teams would manually click through the AWS Console to build environments. This was slow, error-prone, and impossible to reproduce exactly. If a developer built the staging environment one way and someone else built production slightly differently, you would get mysterious bugs that only appeared in production.

CloudFormation solves this with four superpowers:

  • Consistency: The same template deployed twice always produces identical infrastructure — no human error, no forgotten steps.
  • Repeatability: Deploy your staging, UAT, and production environments from the exact same template. Change one variable and get a different environment.
  • Version Control: Templates are just text files. Store them in Git. See who changed what and when. Roll back to a previous version if something breaks.
  • Automation: Run deployments on a schedule or as part of a CI/CD pipeline — no humans needed at 2 AM.

Key Concepts: Templates, Stacks, and Layers

There are three core concepts you need to understand before touching the console:

Template: A text file (JSON or YAML) that describes the AWS resources you want. Think of it as the blueprint or recipe. It is NOT the infrastructure itself — it is the instructions for building it.

Stack: A stack is a collection of AWS resources that CloudFormation creates, updates, and deletes as a single unit. When you deploy a template, you get a stack. Every resource in the stack — the VPC, the EC2 instance, the security group — is managed together. Delete the stack, and all its resources are deleted (unless you set deletion policies).

Figure 3: CloudFormation stack lifecycle — every stack moves through these states as you create, update, and delete it

Layered Architecture: In real-world deployments, you split your infrastructure into layers. A common pattern is:

  • Network Layer: VPC, subnets, internet gateways, route tables
  • Database Layer: RDS, DynamoDB tables, ElastiCache clusters
  • Application Layer: EC2 instances, Auto Scaling groups, load balancers, security groups

Separating infrastructure into layers allows different teams to manage their own stacks independently, and allows lower layers to be reused by multiple upper-layer stacks.

Figure 4: Layered CloudFormation architecture — each layer is a separate stack that can reference outputs from the layer below

⚡ A CloudFormation stack can export output values (like a VPC ID or Subnet ID) that other stacks can import using Fn::ImportValue. This is how layers talk to each other.

YAML vs JSON — Which to Use and Why

CloudFormation templates can be written in two formats. Todd's take from the session: "JSON feels more like it's written for a computer to read and parse easily. YAML is a little more user-friendly, so I prefer to use YAML when I can get away with it."

You will encounter both in practice: CloudWatch logs are JSON, AI training data is often JSON, and many AWS APIs return JSON. YAML is more common for human-written templates. Know both — prefer YAML for writing.

💡 The Infrastructure Composer console lets you switch between JSON and YAML views at the top of the editor panel — the same template, different format.

Template Anatomy: YAML vs JSON

CloudFormation templates can be written in two formats. YAML is the friendlier one — it uses indentation instead of curly braces and is easier for humans to read and edit. JSON is more machine-friendly but harder to write by hand.

Every CloudFormation template has the same skeleton:

AWSTemplateFormatVersion: 2010-09-09
Description: What this template does

Parameters:         # Optional: variables you can pass in at deploy time
  NetworkStackName:
    Type: String
    Default: lab-network

Resources:          # REQUIRED: the AWS resources to create
  MyEC2Instance:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: t2.micro
      ImageId: ami-12345678

Outputs:            # Optional: values to export or display after deployment
  InstanceId:
    Value: !Ref MyEC2Instance
    Export:
      Name: !Sub '${AWS::StackName}-InstanceID'

The key sections are:

  • Parameters: Like function arguments. Let you customize the template at deploy time without editing the file. Example: pass in a different AMI ID for each region.
  • Resources: The only mandatory section in a CloudFormation template. Every AWS resource you want created goes here.
  • Outputs: Values CloudFormation will display after the stack is created, and optionally export for other stacks to use.

In this lab, the lab-network.yaml template creates a VPC and subnet, then exports their IDs. The lab-application.yaml template then imports those IDs to place the EC2 instance in the right network — without you having to manually look up or copy any values.

Deletion Policies

When you delete a CloudFormation stack, by default all its resources are deleted. But sometimes you want to keep certain resources — like a database or a disk volume containing important data — even after the stack is gone.

A DeletionPolicy attribute on a resource tells CloudFormation what to do with that resource when the stack is deleted. The three options are Delete (default), Retain, and Snapshot.

  • Delete: Resource is permanently deleted (default behaviour)
  • Retain: Resource is kept in your account even after the stack is deleted
  • Snapshot: CloudFormation takes a final snapshot (backup) before deleting — available for EBS volumes, RDS databases, and ElastiCache clusters
DiskVolume:
  Type: AWS::EC2::Volume
  Properties:
    Size: 100
    AvailabilityZone: !GetAtt WebServerInstance.AvailabilityZone
  DeletionPolicy: Snapshot

In this lab, the 100 GB EBS volume attached to your web server has DeletionPolicy: Snapshot. When you delete the stack at the end, CloudFormation automatically takes a snapshot of that volume before destroying it — so no data is lost.

Intrinsic Functions: The Template Superpowers

CloudFormation templates can reference other resources, import values from other stacks, and build dynamic strings — using built-in functions called intrinsic functions. You will see these in every template you work with:

  • !Ref — Returns the value of a parameter or the ID of a resource. Example: !Ref WebServerSecurityGroup returns the security group ID.
  • !Sub — String substitution. Example: !Sub '${AWS::StackName}-VPCID' inserts the actual stack name into the string.
  • !GetAtt — Gets a specific attribute of a resource. Example: !GetAtt WebServerInstance.AvailabilityZone gets the AZ of the EC2 instance.
  • Fn::ImportValue — Imports an exported output value from another stack. This is how cross-stack references work in CloudFormation.
# Example from lab-application.yaml:
VpcId:
  Fn::ImportValue:
    !Sub ${NetworkStackName}-VPCID

This reads: "Import the export named [NetworkStackName]-VPCID from whatever stack name was passed as the NetworkStackName parameter." The result is the VPC ID created by the network stack — automatically wired in at deploy time.

📌 Important: Amazon Linux 2 End-of-Life

❌ This lab uses Amazon Linux 2 (AL2), which reached end-of-life. The AMI parameter in both lab-application.yaml and lab-application2.yaml points to the latest AL2 image:

AmazonLinuxAMIID:
  Type: AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>
  Default: /aws/service/ami-amazon-linux-latest/amzn2-ami-hvm-x86_64-gp2

To use Amazon Linux 2023 (the current supported version), replace the Default value with:

Default: /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64

⚠️ The update trap — why you cannot just update an existing stack with the new AMI: Changing the AMI ID is an immutable parameter change — it requires the EC2 instance to be replaced (Replacement = True), not modified in place. In the restricted Vocareum environment, this replacement fails and the stack rolls back. Todd demonstrated this live — the stack showed a rollback after he attempted the change. The solution: create a new stack entirely (lab-application3 in the session) rather than updating the existing one.

💡 Why CloudFormation "remembers" the old value: When you update a stack without explicitly overriding a parameter, CloudFormation uses the previously deployed value — not the template's current Default. So even after fixing the template file, updating an old stack may still use the old AL2 AMI because CloudFormation cached it from the first deployment. Create a new stack to get a fresh parameter resolution.

🔧 Task 1: Deploy the Networking Layer

In this task you deploy the foundation of your infrastructure — a VPC with a public subnet, internet gateway, and route table. This network stack will be referenced by the application stack in Task 2.

💡 Why start with the network? Everything in AWS lives inside a network (VPC). By deploying the network first as its own stack, you can reuse the same network across multiple application stacks — just like a landlord rents out the same building to different tenants.

⚡ Full lab-network.yaml — copy this exactly for personal account use:

AWSTemplateFormatVersion: 2010-09-09
Description: >-
  Network Template: Sample template that creates a VPC with DNS and public IPs enabled.

Resources:

  VPC:
    Type: AWS::EC2::VPC
    Properties:
      EnableDnsSupport: true
      EnableDnsHostnames: true
      CidrBlock: 10.0.0.0/16

  InternetGateway:
    Type: AWS::EC2::InternetGateway

  VPCGatewayAttachment:
    Type: AWS::EC2::VPCGatewayAttachment
    Properties:
      VpcId: !Ref VPC
      InternetGatewayId: !Ref InternetGateway

  PublicRouteTable:
    Type: AWS::EC2::RouteTable
    Properties:
      VpcId: !Ref VPC

  PublicRoute:
    Type: AWS::EC2::Route
    DependsOn: VPCGatewayAttachment
    Properties:
      RouteTableId: !Ref PublicRouteTable
      DestinationCidrBlock: 0.0.0.0/0
      GatewayId: !Ref InternetGateway

  PublicSubnet:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref VPC
      CidrBlock: 10.0.0.0/24
      AvailabilityZone: !Select
        - 0
        - !GetAZs
          Ref: AWS::Region

  PublicSubnetRouteTableAssociation:
    Type: AWS::EC2::SubnetRouteTableAssociation
    Properties:
      SubnetId: !Ref PublicSubnet
      RouteTableId: !Ref PublicRouteTable

  PublicSubnetNetworkAclAssociation:
    Type: AWS::EC2::SubnetNetworkAclAssociation
    Properties:
      SubnetId: !Ref PublicSubnet
      NetworkAclId: !GetAtt
        - VPC
        - DefaultNetworkAcl

Outputs:

  PublicSubnet:
    Description: The subnet ID to use for public web servers
    Value: !Ref PublicSubnet
    Export:
      Name: !Sub '${AWS::StackName}-SubnetID'

  VPC:
    Description: VPC ID
    Value: !Ref VPC
    Export:
      Name: !Sub '${AWS::StackName}-VPCID'

🖥️ Task 2: Deploy the Application Layer

Now you deploy the application on top of the network. This template creates an EC2 web server and its security group — and it automatically looks up the VPC ID and Subnet ID from the network stack's outputs. No copy-pasting needed.

⚡ Full lab-application.yaml — copy this for personal account use (change AMI default for AL2023):

AWSTemplateFormatVersion: 2010-09-09
Description: >-
  Application Template: Provisions an EC2 instance in a VPC Subnet from a different stack.

Parameters:

  NetworkStackName:
    Type: String
    MinLength: 1
    MaxLength: 255
    AllowedPattern: '^[a-zA-Z][-a-zA-Z0-9]*$'
    Default: lab-network

  AmazonLinuxAMIID:
    Type: AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>
    # Personal account: change to al2023-ami-kernel-default-x86_64
    Default: /aws/service/ami-amazon-linux-latest/amzn2-ami-hvm-x86_64-gp2

Resources:

  WebServerInstance:
    Type: AWS::EC2::Instance
    Metadata:
      'AWS::CloudFormation::Init':
        configSets:
          All:
            - ConfigureSampleApp
        ConfigureSampleApp:
          packages:
            yum:
              httpd: []
          files:
            /var/www/html/index.html:
              content: |
                <img src="https://s3.amazonaws.com/cloudformation-examples/cloudformation_graphic.png" alt="AWS CloudFormation Logo"/>
                <h1>Congratulations, you have successfully launched the AWS CloudFormation sample.</h1>
              mode: 000644
              owner: apache
              group: apache
          services:
            sysvinit:
              httpd:
                enabled: true
                ensureRunning: true
    Properties:
      InstanceType: t2.micro
      ImageId: !Ref AmazonLinuxAMIID
      NetworkInterfaces:
        - GroupSet:
            - !Ref WebServerSecurityGroup
          AssociatePublicIpAddress: true
          DeviceIndex: 0
          DeleteOnTermination: true
          SubnetId:
            Fn::ImportValue:
              !Sub ${NetworkStackName}-SubnetID
      Tags:
        - Key: Name
          Value: Web Server
      UserData:
        Fn::Base64: !Sub |
          #!/bin/bash -xe
          yum update -y aws-cfn-bootstrap
          /opt/aws/bin/cfn-init -v --stack ${AWS::StackName} --resource WebServerInstance --configsets All --region ${AWS::Region}
          /opt/aws/bin/cfn-signal -e $? --stack ${AWS::StackName} --resource WebServerInstance --region ${AWS::Region}
    CreationPolicy:
      ResourceSignal:
        Timeout: PT5M

  DiskVolume:
    Type: AWS::EC2::Volume
    Properties:
      Size: 100
      AvailabilityZone: !GetAtt WebServerInstance.AvailabilityZone
      Tags:
        - Key: Name
          Value: Web Data
    DeletionPolicy: Snapshot

  DiskMountPoint:
    Type: AWS::EC2::VolumeAttachment
    Properties:
      InstanceId: !Ref WebServerInstance
      VolumeId: !Ref DiskVolume
      Device: /dev/sdh

  WebServerSecurityGroup:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Enable HTTP ingress
      VpcId:
        Fn::ImportValue:
          !Sub ${NetworkStackName}-VPCID
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 80
          ToPort: 80
          CidrIp: 0.0.0.0/0
      Tags:
        - Key: Name
          Value: Web Server Security Group

Outputs:
  URL:
    Description: URL of the sample website
    Value: !Sub 'http://${WebServerInstance.PublicDnsName}'

Extended Task 4: Add Auto Scaling Group + Application Load Balancer

A single EC2 instance is a single point of failure. Real production environments replace it with an Auto Scaling Group (ASG) that manages multiple instances, and an Application Load Balancer (ALB) that distributes traffic across them. This is one of the biggest upgrades you can make to your template.

💰 Cost Warning: An Application Load Balancer costs approximately $16–22/month minimum (Load Balancer Capacity Units + hourly charge), regardless of traffic. This is the most expensive task in the extended lab. Run it, explore it, then delete the stack immediately to avoid ongoing charges. An ALB running for 1 hour costs roughly $0.02–0.03.

  1. Add a launch template resource (modern replacement for launch configurations):

    WebServerLaunchTemplate:
  Type: AWS::EC2::LaunchTemplate
  Properties:
    LaunchTemplateName: !Sub '${AWS::StackName}-launch-template'
    LaunchTemplateData:
      InstanceType: !Ref InstanceType
      ImageId: !Ref AmazonLinuxAMIID
      SecurityGroupIds:
        - !Ref WebServerSecurityGroup
      UserData:
        Fn::Base64: !Sub |
          #!/bin/bash
          yum update -y
          yum install -y httpd
          systemctl start httpd
          systemctl enable httpd
          echo "<h1>Hello from ${AWS::StackName}</h1>" > /var/www/html/index.html

  2. Add the Auto Scaling Group:

    WebServerASG:
  Type: AWS::AutoScaling::AutoScalingGroup
  Properties:
    MinSize: 1
    MaxSize: 3
    DesiredCapacity: 2
    LaunchTemplate:
      LaunchTemplateId: !Ref WebServerLaunchTemplate
      Version: !GetAtt WebServerLaunchTemplate.LatestVersionNumber
    VPCZoneIdentifier:
      - Fn::ImportValue: !Sub '${NetworkStackName}-SubnetID'
    TargetGroupARNs:
      - !Ref WebServerTargetGroup

  3. Add the target group and load balancer:

    WebServerTargetGroup:
  Type: AWS::ElasticLoadBalancingV2::TargetGroup
  Properties:
    Port: 80
    Protocol: HTTP
    VpcId:
      Fn::ImportValue: !Sub '${NetworkStackName}-VPCID'
    HealthCheckPath: /
    TargetType: instance

WebServerALB:
  Type: AWS::ElasticLoadBalancingV2::LoadBalancer
  Properties:
    Type: application
    Scheme: internet-facing
    Subnets:
      - Fn::ImportValue: !Sub '${NetworkStackName}-SubnetID'
    SecurityGroups:
      - !Ref WebServerSecurityGroup

ALBListener:
  Type: AWS::ElasticLoadBalancingV2::Listener
  Properties:
    LoadBalancerArn: !Ref WebServerALB
    Port: 80
    Protocol: HTTP
    DefaultActions:
      - Type: forward
        TargetGroupArn: !Ref WebServerTargetGroup

  4. Add an output for the ALB DNS name:

    Outputs:
  LoadBalancerURL:
    Description: URL of the Application Load Balancer
    Value: !Sub 'http://${WebServerALB.DNSName}'

  5. Deploy the stack and wait for CREATE_COMPLETE. Open the LoadBalancerURL from the Outputs tab and confirm you see the "Hello" page served through the load balancer.

Right now your EC2 instance boots but does nothing useful. UserData is a shell script that runs automatically on first boot — it self-configures the server. This is how CloudFormation makes instances arrive pre-installed and ready to serve traffic without any manual SSH session.

Extended Task 7: Add Region-Based AMI Mappings

The current template uses an SSM Parameter Store path to resolve the AMI ID, which handles region differences automatically. But many real-world templates use explicit Mappings — a lookup table baked into the template. This task shows you both approaches and when to use each.

💰 Cost: Free Tier eligible — same EC2 instance, just a cleaner AMI selection mechanism.

  1. Add a Mappings block at the top of your template (these are example AMI IDs — always verify current IDs from the EC2 console for your region):

    Mappings:
  RegionAMI:
    us-east-1:
      AL2023: ami-0230bd60aa4bbd038
    us-west-2:
      AL2023: ami-04e914639d0cca79a
    eu-west-1:
      AL2023: ami-09fd16644beea3565
    eu-central-1:
      AL2023: ami-0eddb4a4e7d846d6f
    ap-southeast-1:
      AL2023: ami-0df7a207adb9748c7

  2. Reference the mapping in your EC2 resource using Fn::FindInMap:

    WebServerInstance:

  4. Deploy in your primary region. Then try deploying the same template in a different region (switch region in the console top-right). CloudFormation will automatically pick the AMI for that region from the mapping.

Extended Task 10: Use Change Sets Properly

You got a quick preview of change sets in Task 3 of the original lab. Now go deeper — deliberately make three different types of changes and observe how CloudFormation classifies each. This builds intuition for safe deployments.

💰 Cost: Free Tier eligible. Change sets are free. You may incur brief EC2 charges if a replacement occurs (new instance launched before old is terminated). The window is typically under 5 minutes.

  1. Change 1 — In-place modification (no replacement): In your template, add a new tag to the EC2 instance. Create a change set and observe: Action=Modify, Replacement=False. Execute it. The instance is not restarted.

  2. Change 2 — Security group rule change (no replacement): Add an additional port (e.g., 8080) to your security group ingress rules. Create a change set. Observe Action=Modify, Replacement=False on the security group resource.

  3. Change 3 — Instance type change (requires replacement): Change InstanceType from t2.micro to t3.micro. Create a change set. You will see Action=Modify, Replacement=True on the EC2 instance. This means: the old instance is terminated and a new one is created. The public IP changes. Any data on the instance ephemeral storage is lost.

    📸 Replacement=True means the old instance is destroyed and a new one created — not an in-place update

  4. Try executing the replacement change set. Note the Outputs tab URL changes (new public DNS). Navigate to the new URL — nginx should still serve the page (because UserData runs on every new instance).

⚡ Properties that require replacement (like InstanceType, ImageId, KeyName) force CloudFormation to terminate the existing resource and provision a new one. Properties that do not require replacement (like Tags, SecurityGroupIds on supported resources) are modified in-place.

Extended Task 11: Convert to AWS CDK (TypeScript)

AWS CDK (Cloud Development Kit) lets you define infrastructure using a real programming language — TypeScript, Python, Java, or others — instead of YAML. The CDK code compiles down to a CloudFormation template automatically. Modern AWS teams prefer CDK for complex infrastructure because it gives you loops, conditionals, type checking, and reusable constructs that YAML simply cannot match.

⚡ Key mental model: CDK is not a replacement for CloudFormation — it is a higher-level abstraction that generates CloudFormation templates. When you run cdk deploy, CDK synthesizes a CloudFormation template and deploys it as a normal CloudFormation stack.

💰 Cost: CDK itself is free. The EC2 and VPC resources it deploys carry the usual Free Tier charges. Same as the original lab.

Why Use CDK Over Raw CloudFormation?

YAML is great for simple templates but gets painful at scale:

  • No loops — you copy-paste the same block 10 times for 10 resources
  • No type checking — a typo in a resource type name only fails at deploy time, not before
  • No abstraction — you cannot package a common pattern (e.g., "a VPC with 3 subnets") as a reusable component

CDK solves all of this. A CDK "Construct" is a reusable piece of infrastructure — like a class in object-oriented programming. AWS provides high-level constructs (called L2/L3) that include sensible defaults, so you write far less code.

  1. Install prerequisites. CDK requires Node.js 18+. Download from nodejs.org. Then install the CDK CLI:

    npm install -g aws-cdk

  2. Configure AWS credentials. The CDK CLI needs your AWS account credentials to deploy:

    aws configure
# Enter: Access Key ID, Secret Access Key, default region (e.g. eu-central-1), output format (json)

    You can find or create Access Keys in IAM → Users → your lab-admin user → Security credentials tab → Create access key.

  3. Bootstrap your account (one-time setup per account/region — creates an S3 bucket for CDK assets):

    cdk bootstrap aws://YOUR_ACCOUNT_ID/eu-central-1

Create a CDK App

  1. Create a new directory and initialize a CDK TypeScript app:

    mkdir cdk-cloudformation-lab
cd cdk-cloudformation-lab
cdk init app --language typescript

  2. Install the VPC and EC2 CDK libraries:

    npm install aws-cdk-lib constructs

  3. Open lib/cdk-cloudformation-lab-stack.ts and replace the content with:

    import * as cdk from 'aws-cdk-lib';
import * as ec2 from 'aws-cdk-lib/aws-ec2';
import { Construct } from 'constructs';

export class CdkCloudformationLabStack extends cdk.Stack {
  constructor(scope: Construct, id: string, props?: cdk.StackProps) {
    super(scope, id, props);

    // Create VPC with public subnet (CDK handles internet gateway, route table automatically)
    const vpc = new ec2.Vpc(this, 'LabVPC', {
      maxAzs: 1,
      natGateways: 0,
      subnetConfiguration: [
        {
          name: 'Public',
          subnetType: ec2.SubnetType.PUBLIC,
          cidrMask: 24,
        },
      ],
    });

    // Security group — HTTP and SSH
    const sg = new ec2.SecurityGroup(this, 'WebSG', {
      vpc,
      description: 'Allow HTTP and SSH',
    });
    sg.addIngressRule(ec2.Peer.anyIpv4(), ec2.Port.tcp(80), 'Allow HTTP');
    sg.addIngressRule(ec2.Peer.anyIpv4(), ec2.Port.tcp(22), 'Allow SSH');

    // EC2 instance using the latest Amazon Linux 2023 AMI
    const instance = new ec2.Instance(this, 'WebServer', {
      vpc,
      instanceType: ec2.InstanceType.of(
        ec2.InstanceClass.T2,
        ec2.InstanceSize.MICRO
      ),
      machineImage: ec2.MachineImage.latestAmazonLinux2023(),
      securityGroup: sg,
      vpcSubnets: { subnetType: ec2.SubnetType.PUBLIC },
    });

    // UserData bootstrap
    instance.addUserData(
      'yum update -y',
      'yum install -y nginx',
      'systemctl start nginx',
      'systemctl enable nginx',
      `echo "<h1>Deployed by CDK</h1>" > /usr/share/nginx/html/index.html`
    );

    // Output the public IP
    new cdk.CfnOutput(this, 'WebServerURL', {
      value: `http://${instance.instancePublicIp}`,
      description: 'URL of the web server',
    });
  }
}

  4. Preview what CloudFormation template CDK will generate (no deployment yet):

    cdk synth

    📸 CDK synthesizes your TypeScript into a CloudFormation JSON template automatically

  5. Deploy:

    cdk deploy

    CDK shows a security diff (what IAM/security changes will be made) and asks for confirmation. Enter y. Watch the CloudFormation stack deploy in the console.

Extended Task 12: Rebuild in Terraform and Compare

Terraform is an Infrastructure as Code tool from HashiCorp that works across multiple cloud providers — AWS, Azure, GCP, and others — using a single language called HCL (HashiCorp Configuration Language). While CloudFormation is AWS-native, Terraform is the most widely used IaC tool in multi-cloud organizations. Understanding both is a genuine industry differentiator.

⚡ Key mental model: CloudFormation stores its state inside AWS (the stack resource list). Terraform maintains its own state file (terraform.tfstate) — a snapshot of everything Terraform has deployed — which must be stored and shared carefully in team environments (usually in an S3 backend).

💰 Cost: Terraform itself is free (open source). The AWS resources it creates carry the same charges as CloudFormation. Same EC2 and VPC — Free Tier eligible.

    cat terraform.tfstate

Key Differences You Will Observe

  • Explicitness: CloudFormation handles internet gateway attachment automatically. In Terraform, you write every step explicitly — internet gateway, route table, route table association. More verbose but more transparent.
  • Plan vs Change Set: terraform plan runs against your state file every time — it always knows current state. CloudFormation change sets must be manually created before each update.
  • Rollback: If CloudFormation stack creation fails, it rolls back automatically. Terraform does not — it stops partway through and you must fix and re-run terraform apply.
  • Provider ecosystem: Terraform can manage your Route 53 domain, your GitHub repositories, your Datadog dashboards, and your AWS infrastructure — all in one tool. CloudFormation is AWS-only.

Extended Task 13: Deletion Protection Scenarios

You saw DeletionPolicy: Snapshot in the original lab. Now deliberately test all three deletion policy options and a fourth scenario — stack termination protection — to build real intuition about what survives and what disappears when infrastructure is torn down.

💰 Cost: EBS Snapshots cost ~$0.05/GB-month. A snapshot of a 100 GB volume = ~$5/month ongoing. Delete snapshots after the test. Retained resources (EBS volumes) also cost money — delete manually after the lab.

  1. Scenario A — DeletionPolicy: Delete (default): Deploy a stack with a 10 GB EBS volume and no DeletionPolicy. Delete the stack. The volume is permanently deleted. No recovery possible.

  2. Scenario B — DeletionPolicy: Retain: Add DeletionPolicy: Retain to the EBS volume. Delete the stack. Navigate to EC2 → Volumes. The volume still exists — it is now an orphaned resource, no longer managed by CloudFormation. You must delete it manually. Verify it shows no attachment.

  3. Scenario C — DeletionPolicy: Snapshot: Add DeletionPolicy: Snapshot. Delete the stack. Navigate to EC2 → Snapshots. A new snapshot was taken just before the volume was deleted. You can restore a volume from this snapshot at any time.

  4. Scenario D — Stack Termination Protection: Enable termination protection on a stack. In the CloudFormation console, select the stack → Stack actions → Edit termination protection → Enable. Try to delete the stack — CloudFormation blocks the deletion with an error. This is your last line of defence against accidental destruction of production stacks.

    # Also available via CLI:
aws cloudformation update-termination-protection   --stack-name lab-application   --enable-termination-protection

⚡ DeletionPolicy: Snapshot is only supported for EBS volumes, RDS database instances, and ElastiCache clusters — not for all resource types. For unsupported resource types, use Retain to preserve data.

🧹 Cleanup: Manually delete any retained EBS volumes in EC2 → Volumes. Manually delete any snapshots in EC2 → Snapshots. Disable termination protection before deleting the stack.

Extended Task 14: Create a CI/CD Pipeline for CloudFormation

The final evolution of IaC: templates stored in Git, automatically deployed on every push. This is how serious engineering teams work — no one manually uploads YAML to the console. A push to main triggers a pipeline that validates, reviews, and deploys the template automatically.

💰 Cost: GitHub Actions is free for public repositories and includes 2,000 free minutes/month for private repos. AWS CodePipeline charges ~$1/month per active pipeline. This task uses GitHub Actions (free option).

Option A: GitHub Actions (Recommended for Personal Accounts)

  1. Push your CloudFormation templates to a GitHub repository.

  2. Create an IAM user named github-deployer in your AWS account with only the permissions needed to deploy CloudFormation stacks. Attach this minimal policy:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "cloudformation:*",
        "ec2:*",
        "iam:PassRole",
        "s3:*"
      ],
      "Resource": "*"
    }
  ]
}

  3. In GitHub: go to your repository → Settings → Secrets and variables → Actions → New repository secret. Add two secrets: AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY from the github-deployer IAM user.

  4. Create the workflow file at .github/workflows/deploy-cfn.yml:

    name: Deploy CloudFormation Stack

on:
  push:
    branches:
      - main
    paths:
      - 'templates/**'

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Configure AWS credentials
        uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-access-key-id: ${{ secrets.AWS_ACCESS_KEY_ID }}
          aws-secret-access-key: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          aws-region: eu-central-1

      - name: Validate template
        run: |
          aws cloudformation validate-template             --template-body file://templates/lab-network.yaml

      - name: Deploy network stack
        run: |
          aws cloudformation deploy             --template-file templates/lab-network.yaml             --stack-name lab-network-cicd             --capabilities CAPABILITY_IAM             --no-fail-on-empty-changeset

      - name: Deploy application stack
        run: |
          aws cloudformation deploy             --template-file templates/lab-application2.yaml             --stack-name lab-application-cicd             --parameter-overrides NetworkStackName=lab-network-cicd             --capabilities CAPABILITY_IAM             --no-fail-on-empty-changeset

  5. Push a change to any file in the templates/ folder. Go to the Actions tab in GitHub and watch the pipeline run — validate, deploy network, deploy application — all automatically.

    📸 GitHub Actions running the full CloudFormation deployment pipeline on every push to main

Project 1: Static Website on S3 + CloudFront

🎯 Objective: Host a static HTML site on S3 and serve it globally through CloudFront CDN.
⏱️ Time: 30–45 min
💰 Cost: CloudFront has 1 TB free data transfer/month. S3 storage for a small site is pennies. Route 53 hosted zone is $0.50/month if used.

Figure: Static website architecture — browser → CloudFront CDN → S3 bucket

How to Perform

  1. Sign in to the AWS Console. In the top search bar, type S3 and open the S3 service.

  2. Click Create bucket. Enter a globally unique bucket name (e.g., your-name-cloudformation-lab-site). Choose your region. Leave all other settings as default.

    Figure: 📸 S3 Create bucket — enter a unique name and choose your region

  3. On the bucket page, go to the Permissions tab. Click Edit under Block public access. Uncheck Block all public access. Save changes and confirm the warning dialog.

  4. Stay on the Permissions tab. Scroll down to Bucket policy. Click Edit and paste the following policy (replace YOUR-BUCKET-NAME):

    {
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": "*",
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*"
  }]
}

  5. Go to the Properties tab. Scroll to Static website hosting and click Edit. Select Enable. Set Index document to index.html and Error document to error.html. Save changes.

    Figure: 📸 Static website hosting enabled — copy the endpoint URL shown at the bottom

  6. Go to the Objects tab. Click Upload. Upload an index.html and an error.html file. A minimal index.html example:

    <!DOCTYPE html>
<html><body><h1>My CloudFormation Lab Site</h1></body></html>

  7. In the Properties tab, copy the Bucket website endpoint URL. Open it in a browser — your site should load. This confirms S3 static hosting works.

  8. In the top search bar, type CloudFront and open the service. Click Create distribution.

  9. Under Origin domain, paste your S3 website endpoint URL (the one from the Properties tab — NOT the S3 bucket dropdown option, as that uses the REST endpoint which does not support redirect rules). Set Protocol to HTTP only.

  10. Scroll down to Default cache behavior. Leave Viewer protocol policy as Redirect HTTP to HTTPS. Under Cache key and origin requests, select CachingOptimized.

  11. Scroll to Settings. Set Default root object to index.html. Click Create distribution.

    Figure: 📸 CloudFront distribution created — wait for Status to change from Deploying to Enabled (~5 min)

  12. Wait until the distribution Status changes from Deploying to Enabled (about 5 minutes). Copy the Domain name (e.g., d1234abcd.cloudfront.net) and open it in a browser. Your site now loads via CDN.

✅ What you learn: S3 bucket policies and permissions, CDN behavior and caching, the difference between S3 REST endpoint and website endpoint, and how CloudFront integrates with S3.

Cleanup

  1. In CloudFront, select your distribution and click Disable. Wait for the status to change to Disabled — this takes about 15 minutes. Do NOT skip this — you cannot delete an enabled distribution.

  2. Once disabled, select the distribution and click Delete. Confirm.

  3. Go to S3. Open your bucket. Select all objects and click Delete. Confirm deletion.

  4. With the bucket now empty, go back to the S3 bucket list. Select your bucket and click Delete. Type the bucket name to confirm.

  5. Open AWS Cost Explorer or check Billing → Bills to confirm no ongoing CloudFront charges appear the next day.

Project 3: Build a Custom VPC from a CloudFormation Template

🎯 Objective: Write a CloudFormation template that creates a VPC, public subnet, internet gateway, and route table — the same network layer you deployed in Task 1, but this time you write the template yourself.
⏱️ Time: 45–60 min
💰 Cost: Free — VPCs, subnets, internet gateways, and route tables have no hourly charge.

Figure: Custom VPC architecture — the same network layer you deployed in Task 1

How to Perform

  1. On your local machine, create a new file called my-network.yaml. Open it in a text editor.

  2. Paste the following CloudFormation template and study each section before proceeding:

    AWSTemplateFormatVersion: 2010-09-09
Description: My custom VPC network layer

Resources:
  MyVPC:
    Type: AWS::EC2::VPC
    Properties:
      CidrBlock: 10.0.0.0/16
      EnableDnsSupport: true
      EnableDnsHostnames: true
      Tags:
        - Key: Name
          Value: my-custom-vpc

  MySubnet:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !Ref MyVPC
      CidrBlock: 10.0.1.0/24
      MapPublicIpOnLaunch: true
      AvailabilityZone: !Select [0, !GetAZs '']
      Tags:
        - Key: Name
          Value: my-public-subnet

  MyInternetGateway:
    Type: AWS::EC2::InternetGateway

  MyIGWAttachment:
    Type: AWS::EC2::VPCGatewayAttachment
    Properties:
      VpcId: !Ref MyVPC
      InternetGatewayId: !Ref MyInternetGateway

  MyRouteTable:
    Type: AWS::EC2::RouteTable
    Properties:
      VpcId: !Ref MyVPC

  MyRoute:
    Type: AWS::EC2::Route
    DependsOn: MyIGWAttachment
    Properties:
      RouteTableId: !Ref MyRouteTable
      DestinationCidrBlock: 0.0.0.0/0
      GatewayId: !Ref MyInternetGateway

  MySubnetRouteTableAssociation:
    Type: AWS::EC2::SubnetRouteTableAssociation
    Properties:
      SubnetId: !Ref MySubnet
      RouteTableId: !Ref MyRouteTable

Outputs:
  VPCID:
    Value: !Ref MyVPC
    Export:
      Name: !Sub '${AWS::StackName}-VPCID'
  SubnetID:
    Value: !Ref MySubnet
    Export:
      Name: !Sub '${AWS::StackName}-SubnetID'

  3. In the AWS Console, go to CloudFormation → Create stack → With new resources.

  4. Under Template source, select Upload a template file. Click Choose file and select your my-network.yaml. Click Next.

    Figure: 📸 Upload your template file to CloudFormation

  5. Name the stack my-network. Click Next through the remaining screens. On the final review screen, click Create stack.

  6. Watch the Events tab. Each resource should show CREATE_IN_PROGRESS then CREATE_COMPLETE. The overall stack should reach CREATE_COMPLETE within about 60 seconds.

    Figure: 📸 All resources created successfully — Events tab showing CREATE_COMPLETE

  7. Click the Outputs tab. You should see two exported values: my-network-VPCID and my-network-SubnetID. Go to the VPC console and verify the VPC, subnet, internet gateway, and route table were created with the correct CIDR blocks.

✅ What you learn: How to write a CloudFormation template from scratch, how !Ref and !GetAZs work, how outputs and exports are defined, and how to read the Events tab to verify successful creation.

Cleanup

  1. In CloudFormation, select the my-network stack.

  2. Click Delete, then Delete stack to confirm.

  3. Watch the Events tab. All resources should be deleted in reverse dependency order. The stack disappears from the list when complete.

  4. In the VPC console, confirm the VPC no longer exists. If deletion fails (a resource dependency still exists), check the Events tab for which resource caused the failure and resolve it manually.

💰 Cost: RDS db.t3.micro is Free Tier eligible (750 hours/month for 12 months). Stop the RDS instance when not in use to avoid charges.

Figure: Two-tier architecture — EC2 in public subnet, RDS in private subnet

How to Perform

  1. First, deploy the network stack from Project 3 (or use your existing my-network stack). This provides the VPC and subnet IDs for cross-stack referencing.

  2. Create a second template file my-database.yaml. Add a private subnet and an RDS DB subnet group:

    AWSTemplateFormatVersion: 2010-09-09
Parameters:
  NetworkStackName:
    Type: String
    Default: my-network

Resources:
  PrivateSubnet:
    Type: AWS::EC2::Subnet
    Properties:
      VpcId: !ImportValue
        Fn::Sub: '${NetworkStackName}-VPCID'
      CidrBlock: 10.0.2.0/24
      AvailabilityZone: !Select [1, !GetAZs '']

  DBSubnetGroup:
    Type: AWS::RDS::DBSubnetGroup
    Properties:
      DBSubnetGroupDescription: RDS subnet group
      SubnetIds:
        - !ImportValue
          Fn::Sub: '${NetworkStackName}-SubnetID'
        - !Ref PrivateSubnet

  DBSecurityGroup:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: RDS security group
      VpcId: !ImportValue
        Fn::Sub: '${NetworkStackName}-VPCID'
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 3306
          ToPort: 3306
          CidrIp: 10.0.0.0/16

  MyDatabase:
    Type: AWS::RDS::DBInstance
    DeletionPolicy: Snapshot
    Properties:
      DBInstanceClass: db.t3.micro
      Engine: mysql
      MasterUsername: admin
      MasterUserPassword: Password123!
      AllocatedStorage: 20
      DBSubnetGroupName: !Ref DBSubnetGroup
      VPCSecurityGroups:
        - !Ref DBSecurityGroup
      MultiAZ: false
      PubliclyAccessible: false

  3. Deploy this template as a new stack named my-database in CloudFormation. This may take 5–10 minutes as RDS provisioning is slow.

    Figure: 📸 RDS takes 5–10 minutes to provision — watch the Events tab while it creates

  4. Once the stack is CREATE_COMPLETE, go to RDS → Databases in the console. Confirm the instance is Available. Note the Endpoint URL — this is how your web server will connect to the database.

  5. Launch a t2.micro EC2 instance in the same VPC (using the public subnet). Connect via EC2 Instance Connect and test the database connection:

    sudo dnf install mysql -y
mysql -h YOUR-RDS-ENDPOINT -u admin -p

    Enter Password123! when prompted. You should get a MySQL prompt — confirming connectivity between the EC2 and RDS layers.

✅ What you learn: Multi-stack architecture, RDS provisioning, DB subnet groups, private subnet design, and cross-tier connectivity testing. This mirrors real production two-tier architectures.

Cleanup

  2. In CloudFormation, select the my-database stack and click Delete. Confirm. Because DeletionPolicy: Snapshot is set on the RDS instance, CloudFormation will create a final snapshot before deleting it. This takes 5–10 minutes.

  3. Once the database stack is deleted, go to RDS → Snapshots. You will see the automatic snapshot created by the deletion policy. Delete this snapshot manually to avoid ongoing storage charges (Actions → Delete snapshot).

Project 9: IaC with Nested Stacks and Parameters

🎯 Objective: Refactor the three-tier architecture from Project 8 into a parent stack with nested child stacks, using CloudFormation parameters to make everything configurable at deploy time.
⏱️ Time: 60–90 min
💰 Cost: Same as Project 8 — delete promptly.

How to Perform

  1. Create a parent.yaml template. Add parameters for environment name, instance type, and database password at the top of the template.

  2. Inside the parent template, use AWS::CloudFormation::Stack resources to reference each child template stored in S3. Upload your three child templates to an S3 bucket first:

    aws s3 cp network.yaml s3://your-templates-bucket/
aws s3 cp database.yaml s3://your-templates-bucket/
aws s3 cp application.yaml s3://your-templates-bucket/

  3. In parent.yaml, define nested stacks pointing to the S3 URLs:

    NetworkStack:
  Type: AWS::CloudFormation::Stack
  Properties:
    TemplateURL: https://your-templates-bucket.s3.amazonaws.com/network.yaml
    Parameters:
      EnvironmentName: !Ref EnvironmentName

DatabaseStack:
  Type: AWS::CloudFormation::Stack
  DependsOn: NetworkStack
  Properties:
    TemplateURL: https://your-templates-bucket.s3.amazonaws.com/database.yaml
    Parameters:
      VPCID: !GetAtt NetworkStack.Outputs.VPCID

  4. Deploy parent.yaml as a single stack. Watch how CloudFormation automatically creates the nested stacks in the correct order, passing outputs between them as parameters.

    Figure: 📸 Nested stack structure — parent stack with three child stacks deployed automatically

  5. Deploy a second environment from the same parent template with a different stack name and a different environment parameter value. You now have two complete, isolated environments from one set of templates.

✅ What you learn: Nested stacks, parameter passing between stacks, S3 as a template repository, and how to design truly reusable IaC templates for multiple environments.

  1. Delete the parent stack. CloudFormation deletes all nested child stacks automatically in the correct dependency order.

  2. Go to S3. Empty and delete the templates bucket (or just the template objects if you want to keep the bucket).

  3. Verify in CloudFormation that no child stacks remain — they should all be gone when the parent is deleted.

📝 Overall Summary

  • Infrastructure as Code: CloudFormation templates describe AWS infrastructure in YAML or JSON, enabling consistent, repeatable, and automated deployments.
  • Stacks: A stack is the collection of all AWS resources created from a single template — they are created, updated, and deleted together.
  • Layered Architecture: Deploying infrastructure in separate stacks (network, database, application) allows teams to manage their own layers independently and reuse lower layers across multiple applications.
  • Cross-Stack References: The Outputs section with Export and Fn::ImportValue enables one stack to reference resources created by another.
  • Stack Updates: Updating a stack with a new template only changes what is different — CloudFormation preserves unchanged resources and shows a change set preview before applying anything.
  • Change Set Preview: When Replacement = False, the resource is modified in-place. When Replacement = True, the old resource is replaced with a new one.
  • Deletion Policies: DeletionPolicy: Snapshot causes CloudFormation to take a final backup of an EBS volume or RDS database before deleting it when the stack is removed.
  • Infrastructure Composer (formerly Designer): A visual editor that renders a CloudFormation template as a diagram, making it easier to understand resource relationships.
  • Amazon Linux 2 EOL: The current lab templates use AL2, which is end-of-life. For new deployments, use the Amazon Linux 2023 AMI parameter path instead.
  • Security Group Creation Order: CloudFormation resolves dependencies and always creates security groups before the EC2 instances that reference them. Todd's analogy: "Build the castle walls before moving the king in."
  • Console Changes: CloudFormation Designer is now Infrastructure Composer. A new timeline view appeared for stack creation. The console changes constantly — focus on the concept, not the button location. "You never step into the same river twice."
  • "Nothing to perform": If you upload a template identical to the current deployed state, CloudFormation detects no delta and does nothing. Smart state management built in.
  • Werner Vogels principle: "Everything fails all the time." CloudFormation lets you define infrastructure as code so any failure can be recovered from by redeploying the same template — automatically.
  • IaC tool landscape: CDK generates CloudFormation templates (TypeScript/Python → JSON → CloudFormation stack). Terraform is cloud-agnostic with its own state file. Ansible is for configuration management. CloudFormation is the AWS-native foundation.
