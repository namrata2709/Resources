🌟 Introduction

Imagine you are setting up a new restaurant. You could wing it every time — buy tables, chairs, and kitchen equipment one piece at a time, hoping you remember everything. Or you could write a detailed blueprint: exactly which tables go where, which appliances are needed, and how the layout should look. Then hand that blueprint to a builder and have them set it up perfectly every single time — in any city, any branch.

That is exactly what AWS CloudFormation does for cloud infrastructure. Instead of clicking through the AWS Console to build servers, networks, and databases one by one, you write your entire infrastructure as code in a simple text file — and CloudFormation builds it all for you, automatically, consistently, and repeatably.

In this lab, you will experience this power first-hand. You will write (and use pre-written) templates to deploy a complete working web application — from the network layer all the way up to the web server — without ever manually clicking "Launch Instance" or "Create VPC." You will also update running infrastructure, explore a visual designer, and learn how to safely delete resources while preserving important data.

⚡ The big idea: CloudFormation lets you treat infrastructure like software — version it, review it, repeat it, and roll it back if something goes wrong.

📚 Background / Theory

What is AWS CloudFormation?

AWS CloudFormation is an Infrastructure as Code (IaC) service that lets you model, provision, and manage AWS resources using template files written in JSON or YAML. You describe what you want — a VPC, an EC2 instance, a security group — and CloudFormation figures out the order to create them, handles dependencies, and builds everything as a single unit called a stack.

Think of a CloudFormation template like an IKEA instruction manual. The manual (template) describes every part and every step. You hand it to CloudFormation, which plays the role of the builder — assembling everything in exactly the right order, every time.

According to AWS documentation, CloudFormation is available at no additional charge — you only pay for the AWS resources created by your templates (EC2 hours, S3 storage, etc.).

Why Use CloudFormation?

Before IaC tools like CloudFormation, teams would manually click through the AWS Console to build environments. This was slow, error-prone, and impossible to reproduce exactly. If a developer built the staging environment one way and someone else built production slightly differently, you would get mysterious bugs that only appeared in production.

CloudFormation solves this with four superpowers:

  • Consistency: The same template deployed twice always produces identical infrastructure — no human error, no forgotten steps.
  • Repeatability: Deploy your staging, UAT, and production environments from the exact same template. Change one variable and get a different environment.
  • Version Control: Templates are just text files. Store them in Git. See who changed what and when. Roll back to a previous version if something breaks.
  • Automation: Run deployments on a schedule or as part of a CI/CD pipeline — no humans needed at 2 AM.

✅ Real-world example from the session: The lab environment itself is built using CloudFormation. When you start the lab, CloudFormation runs a template in the background to set up all the permissions and baseline resources you need — in about 2 minutes, automatically.

Key Concepts: Templates, Stacks, and Layers

There are three core concepts you need to understand before touching the console:

Template: A text file (JSON or YAML) that describes the AWS resources you want. Think of it as the blueprint or recipe. It is NOT the infrastructure itself — it is the instructions for building it.

Stack: A stack is a collection of AWS resources that CloudFormation creates, updates, and deletes as a single unit. When you deploy a template, you get a stack. Every resource in the stack — the VPC, the EC2 instance, the security group — is managed together. Delete the stack, and all its resources are deleted (unless you set deletion policies).

Layered Architecture: In real-world deployments, you split your infrastructure into layers. A common pattern is:

  • Network Layer: VPC, subnets, internet gateways, route tables
  • Database Layer: RDS, DynamoDB tables, ElastiCache clusters
  • Application Layer: EC2 instances, Auto Scaling groups, load balancers, security groups

Separating infrastructure into layers allows different teams to manage their own stacks independently, and allows lower layers to be reused by multiple upper-layer stacks.

Figure 3: Layered CloudFormation architecture — each layer is a separate stack that can reference outputs from the layer below

⚡ A CloudFormation stack can export output values (like a VPC ID or Subnet ID) that other stacks can import using Fn::ImportValue. This is how layers talk to each other.

Template Anatomy: YAML vs JSON

CloudFormation templates can be written in two formats. YAML is the friendlier one — it uses indentation instead of curly braces and is easier for humans to read and edit. JSON is more machine-friendly but harder to write by hand.

Every CloudFormation template has the same skeleton:

AWSTemplateFormatVersion: 2010-09-09
Description: What this template does

Parameters:         # Optional: variables you can pass in at deploy time
  NetworkStackName:
    Type: String
    Default: lab-network

Resources:          # REQUIRED: the AWS resources to create
  MyEC2Instance:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: t2.micro
      ImageId: ami-12345678

Outputs:            # Optional: values to export or display after deployment
  InstanceId:
    Value: !Ref MyEC2Instance
    Export:
      Name: !Sub '${AWS::StackName}-InstanceID'

The key sections are:

  • Parameters: Like function arguments. Let you customize the template at deploy time without editing the file. Example: pass in a different AMI ID for each region.
  • Resources: The only mandatory section in a CloudFormation template. Every AWS resource you want created goes here.
  • Outputs: Values CloudFormation will display after the stack is created, and optionally export for other stacks to use.

In this lab, the lab-network.yaml template creates a VPC and subnet, then exports their IDs. The lab-application.yaml template then imports those IDs to place the EC2 instance in the right network — without you having to manually look up or copy any values.

Deletion Policies

When you delete a CloudFormation stack, by default all its resources are deleted. But sometimes you want to keep certain resources — like a database or a disk volume containing important data — even after the stack is gone.

A DeletionPolicy attribute on a resource tells CloudFormation what to do with that resource when the stack is deleted. The three options are Delete (default), Retain, and Snapshot.

  • Delete: Resource is permanently deleted (default behaviour)
  • Retain: Resource is kept in your account even after the stack is deleted
  • Snapshot: CloudFormation takes a final snapshot (backup) before deleting — available for EBS volumes, RDS databases, and ElastiCache clusters
DiskVolume:
  Type: AWS::EC2::Volume
  Properties:
    Size: 100
    AvailabilityZone: !GetAtt WebServerInstance.AvailabilityZone
  DeletionPolicy: Snapshot

In this lab, the 100 GB EBS volume attached to your web server has DeletionPolicy: Snapshot. When you delete the stack at the end, CloudFormation automatically takes a snapshot of that volume before destroying it — so no data is lost.

Intrinsic Functions: The Template Superpowers

CloudFormation templates can reference other resources, import values from other stacks, and build dynamic strings — using built-in functions called intrinsic functions. You will see these in every template you work with:

  • !Ref — Returns the value of a parameter or the ID of a resource. Example: !Ref WebServerSecurityGroup returns the security group ID.
  • !Sub — String substitution. Example: !Sub '${AWS::StackName}-VPCID' inserts the actual stack name into the string.
  • !GetAtt — Gets a specific attribute of a resource. Example: !GetAtt WebServerInstance.AvailabilityZone gets the AZ of the EC2 instance.
  • Fn::ImportValue — Imports an exported output value from another stack. This is how cross-stack references work in CloudFormation.
# Example from lab-application.yaml:
VpcId:
  Fn::ImportValue:
    !Sub ${NetworkStackName}-VPCID

This reads: "Import the export named [NetworkStackName]-VPCID from whatever stack name was passed as the NetworkStackName parameter." The result is the VPC ID created by the network stack — automatically wired in at deploy time.

📌 Important: Amazon Linux 2 End-of-Life

❌ This lab uses Amazon Linux 2 (AL2), which reached end-of-life. The AMI parameter in both lab-application.yaml and lab-application2.yaml points to the latest AL2 image:

AmazonLinuxAMIID:
  Type: AWS::SSM::Parameter::Value<AWS::EC2::Image::Id>
  Default: /aws/service/ami-amazon-linux-latest/amzn2-ami-hvm-x86_64-gp2

To use Amazon Linux 2023 (the current supported version), replace the Default value with:

Default: /aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64

⚠️ Note: CloudFormation caches parameter values from previous deployments. If you try to update an existing stack with the new AMI, CloudFormation may not apply the change (because it treats AMI changes as requiring instance replacement). To guarantee the new AMI is used, create a new stack rather than updating the existing one.

🔧 Task 1: Deploy the Networking Layer

In this task you deploy the foundation of your infrastructure — a VPC with a public subnet, internet gateway, and route table. This network stack will be referenced by the application stack in Task 2.

💡 Why start with the network? Everything in AWS lives inside a network (VPC). By deploying the network first as its own stack, you can reuse the same network across multiple application stacks — just like a landlord rents out the same building to different tenants.

  1. Download the network template file: lab-network.yaml (provided in your lab materials)

  2. In the AWS Management Console, search for and open CloudFormation.

    Figure 4: 📸 Navigate to CloudFormation from the AWS Console search bar

  3. Choose Stacks in the left navigation pane, then click Create stack → With new resources (standard).

  4. Step 1 — Specify template:

    • Template source: Upload a template file
    • Click Choose file and select lab-network.yaml
    • Click Next

    Figure 5: 📸 Upload the lab-network.yaml template file

  5. Step 2 — Stack details:

    • Stack name: lab-network
    • Click Next

  6. Step 3 — Configure stack options:

    • In the Tags section, add a tag: Key = application, Value = inventory
    • Click Next

    💡 Why add tags? Tags propagate to every resource created by the stack. In a large enterprise account with hundreds of resources, tags let you filter and identify which resources belong to which application — essential for cost allocation and troubleshooting.

  7. Step 4 — Review: Scroll to the bottom and click Create stack.

  8. Watch the stack creation progress. You will see a timeline view (or Events tab) showing each resource being created in sequence: VPC → Internet Gateway → Route Table → Subnet.

    Figure 6: 📸 CloudFormation's timeline view showing resources being created in real time

  9. Wait until the Stack Status shows CREATE_COMPLETE. Refresh every 15 seconds if needed.

  10. Once complete, explore these tabs:

    • Resources tab: Lists every AWS resource created by this template (VPC, subnet, gateway, route table, etc.)
    • Events tab: Full audit log of every action CloudFormation took, in chronological order
    • Outputs tab: Shows the exported values — the VPC ID and Subnet ID that your application stack will use
    • Template tab: Shows the exact YAML template that was used

    Figure 7: 📸 The Outputs tab shows the VPC ID and Subnet ID exported for other stacks to use

✅ What just happened? CloudFormation read your YAML template, resolved all the dependencies (e.g., the subnet needs the VPC to exist first), and created everything in the correct order — automatically. The entire network is now running and ready for an application to be deployed into it.

🖥️ Task 2: Deploy the Application Layer

Now you deploy the application on top of the network. This template creates an EC2 web server and its security group — and it automatically looks up the VPC ID and Subnet ID from the network stack's outputs. No copy-pasting needed.

  1. Download the application template file: lab-application.yaml

  2. In the CloudFormation console, click Create stack → With new resources (standard).

  3. Step 1 — Specify template:

    • Template source: Upload a template file
    • Click Choose file and select lab-application.yaml
    • Click Next

  4. Step 2 — Stack details:

    • Stack name: lab-application
    • NetworkStackName: lab-network (this tells the template which stack to import VPC/Subnet values from)
    • Click Next

    ⚡ The NetworkStackName parameter is the key link between your two stacks. The template uses it to construct the import name: !Sub ${NetworkStackName}-VPCID → lab-network-VPCID. CloudFormation then pulls the actual VPC ID from the network stack's Outputs.

  5. Step 3 — Configure stack options: Add the same tag: Key = application, Value = inventory. Click Next.

  6. Step 4 — Review: Click Create stack.

  7. Watch the Events and Resources tabs. Notice that the security group is created first — before the EC2 instance. This is intentional: you build the walls before moving in the assets.

    Figure 8: 📸 Security group is created before the EC2 instance — security first

  8. Wait for Status: CREATE_COMPLETE.

  9. Click the Outputs tab. You will see a URL output. Click it (or copy and paste into a new tab) to view your running web application.

    Figure 9: 📸 The application stack output shows the URL to access your deployed web application

  10. The web page should display the AWS CloudFormation logo and a congratulations message — confirming the web server is running correctly.

    Figure 10: 📸 The deployed web application is live and accessible from the internet

📌 How cross-stack references work in this lab: The security group in lab-application.yaml is placed inside the VPC using:

VpcId:
  Fn::ImportValue:
    !Sub ${NetworkStackName}-VPCID

And the EC2 instance is placed in the subnet using:

SubnetId:
  Fn::ImportValue:
    !Sub ${NetworkStackName}-SubnetID

These values are resolved at deploy time — CloudFormation automatically looks up the exported values from lab-network and injects them into the right places.

✏️ Task 3: Update a Stack

Running infrastructure is rarely static. You will need to change security rules, update AMIs, resize instances, and add new resources. CloudFormation makes these changes safe and predictable — it only modifies what has changed and leaves everything else untouched.

In this task you will add an SSH rule to the security group by uploading an updated template.

  1. First, verify the current state. In the AWS Console, go to EC2 → Security Groups. Find lab-application-WebServerSecurityGroup and view its Inbound rules. You should see only one rule: TCP port 80 (HTTP) from anywhere.

    Figure 11: 📸 Security group before update — only HTTP (port 80) is allowed

  2. Try to connect to the instance via SSH to see what failure looks like. In EC2 → Instances, select the web server instance and click Connect → EC2 Instance Connect. You should get an error because port 22 is not open.

  3. Download the updated template: lab-application2.yaml. If you open it, you will see a new entry in the security group's SecurityGroupIngress:

    - IpProtocol: tcp
  FromPort: 22
  ToPort: 22
  CidrIp: 0.0.0.0/0

  4. Return to CloudFormation → Stacks. Select lab-application, then click Update.

  5. Choose:

    • ✅ Replace current template
    • Template source: Upload a template file
    • Click Choose file and select lab-application2.yaml
    • Click Next

  6. Click Next through the parameters and stack options screens (no changes needed).

  7. On the final Review screen, scroll down to the Change set preview section. This is one of CloudFormation's most powerful features — it shows you exactly what will change before anything is modified.

    Figure 12: 📸 Change set preview shows the security group will be modified in-place (Replacement = False)

    ⚡ Replacement = False means the resource will be modified in-place. Replacement = True means CloudFormation must destroy the old resource and create a new one — which can cause downtime or change resource IDs.

  8. Click Update stack. The update takes about a minute.

  9. Once status returns to UPDATE_COMPLETE, return to EC2 → Security Groups and check the inbound rules again.

    Figure 13: 📸 Security group after update — SSH (port 22) rule has been added

  10. Now try connecting again: EC2 → Instances → select the web server → Connect → EC2 Instance Connect. This time it should succeed, and you will land in an SSH terminal session inside the web server.

    Figure 14: 📸 EC2 Instance Connect succeeds after the security group update allows port 22

    ⚠️ Security note: Allowing SSH from 0.0.0.0/0 (all IPs) is used here for convenience in a temporary lab environment. In production, always restrict SSH access to specific IP ranges (your office IP, a bastion host CIDR, or the EC2 Instance Connect IP range for your region).

🎨 Task 4: Explore CloudFormation Designer (Infrastructure Composer)

CloudFormation Designer (now called Infrastructure Composer in the console) is a visual editor for CloudFormation templates. It lets you see your infrastructure as a diagram and edit the underlying YAML/JSON at the same time.

📌 Console name change: The lab instructions refer to "CloudFormation Designer." The current console calls it Infrastructure Composer. This is common with AWS services — names change as features evolve. The functionality is the same.

  1. In the CloudFormation console, look for Infrastructure Composer in the left navigation pane (you may need to expand the menu).

  2. Click File → Open → Local file. Select lab-application2.yaml.

  3. Designer will render a graphical view of your template. You should see three resources with connecting lines:

    • WebServerSecurityGroup (lock icon) — connected to the EC2 instance
    • WebServerInstance (server icon) — the EC2 instance, connected to the security group
    • DiskVolume (disk icon) — the EBS volume, connected to the instance via the VolumeAttachment

    Figure 15: 📸 Infrastructure Composer shows the template as a visual diagram with YAML editor below

  4. Experiment with the designer:

    • Click on a resource in the diagram — the YAML editor below will jump to that resource's definition
    • Try dragging a new resource from the Resource types panel on the left onto the canvas
    • Notice the YAML is updated automatically when you add resources visually

  5. Also open lab-network.yaml to see the network resources visualized. You will see the VPC containing the subnet, internet gateway, and route table.

✅ Designer is especially useful for understanding templates you did not write yourself. When you inherit a complex template from a colleague or download one from the AWS samples library, Designer lets you immediately see the architecture at a glance.

🗑️ Task 5: Delete the Stack (with Deletion Policy)

When infrastructure is no longer needed, CloudFormation can tear it all down cleanly. In this task you delete the application stack and observe how the DeletionPolicy: Snapshot protects the EBS volume data before deletion.

💰 Cost Note: Always delete lab stacks after use. Running EC2 instances and EBS volumes incur hourly charges. Leaving them running after the lab wastes money. The snapshot created by the deletion policy is stored in EBS Snapshots and has a small cost — delete it after the lab if using your own account.

  1. Close the Designer and return to the CloudFormation Stacks list.

  2. Select lab-application and click Delete.

  3. Confirm by clicking Delete stack.

  4. Monitor deletion progress in the Events tab. Refresh occasionally. Watch for an event that says a snapshot is being created for the EBS volume.

    Figure 16: 📸 Events log during stack deletion showing EBS snapshot being created before the volume is deleted

  5. Once lab-application disappears from the stacks list, the deletion is complete. Note that lab-network is still there — the network stack was managed separately and was not affected.

  6. Verify the snapshot was created. Navigate to EC2 → Snapshots in the left panel. You should see a new snapshot with a recent Started time.

    Figure 17: 📸 EBS snapshot created automatically by the DeletionPolicy: Snapshot before the volume was deleted

✅ Key takeaway: The application stack was deleted but the network stack remained untouched. This is the power of layered architecture — the network team and the application team each own their own stack and can manage them independently.

📝 Overall Summary

  • Infrastructure as Code: CloudFormation templates describe AWS infrastructure in YAML or JSON, enabling consistent, repeatable, and automated deployments.
  • Stacks: A stack is the collection of all AWS resources created from a single template — they are created, updated, and deleted together.
  • Layered Architecture: Deploying infrastructure in separate stacks (network, database, application) allows teams to manage their own layers independently and reuse lower layers across multiple applications.
  • Cross-Stack References: The Outputs section with Export and Fn::ImportValue enables one stack to reference resources created by another.
  • Stack Updates: Updating a stack with a new template only changes what is different — CloudFormation preserves unchanged resources and shows a change set preview before applying anything.
  • Change Set Preview: When Replacement = False, the resource is modified in-place. When Replacement = True, the old resource is replaced with a new one.
  • Deletion Policies: DeletionPolicy: Snapshot causes CloudFormation to take a final backup of an EBS volume or RDS database before deleting it when the stack is removed.
  • Infrastructure Composer (formerly Designer): A visual editor that renders a CloudFormation template as a diagram, making it easier to understand resource relationships.
  • Amazon Linux 2 EOL: The current lab templates use AL2, which is end-of-life. For new deployments, use the Amazon Linux 2023 AMI parameter path instead.
  • Security Group Creation Order: CloudFormation creates security groups before EC2 instances — a best practice that ensures resources are protected before they come online.

💡 Hint
