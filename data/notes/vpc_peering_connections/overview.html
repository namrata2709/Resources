Version: 1.0

Introduction

A VPC peering connection is a one-to-one Layer-3 networking link between two VPCs that routes traffic privately within the AWS backbone. Peered VPCs communicate using private IPv4 or IPv6 addresses with no internet gateway, VPN, or NAT required. The connection is supported within the same account, across accounts, and across AWS Regions.

🏗️ Architecture & Constraints

VPC peering operates at the network layer. Key architectural constraints to know for both the exam and production deployments:

  • Non-overlapping CIDRs required: Peered VPCs must have completely non-overlapping IPv4 (and IPv6) CIDR blocks. Overlapping ranges prevent peering entirely.
  • Non-transitive routing: Peering is strictly point-to-point. If VPC-A peers with VPC-B and VPC-B peers with VPC-C, VPC-A cannot reach VPC-C via VPC-B. Direct peering or Transit Gateway is required for each pair.
  • No edge-to-edge routing: A peering connection cannot act as a conduit for traffic destined for an internet gateway, NAT device, VPN connection, Direct Connect connection, or VPC endpoint in the other VPC.
  • Single peering between any two VPCs: Only one peering connection can exist between any given pair of VPCs at a time.
  • Maximum connections per VPC: By default, 125 active peering connections per VPC (soft limit; can be increased).

🔧 Creating & Accepting a Peering Connection

Peering follows a request-accept model. The requester initiates; the accepter VPC owner must explicitly approve. This is enforced even within the same account.

Console Steps

  1. VPC → Peering Connections → Create Peering Connection
  2. Set Name tag, select Requester VPC and Accepter VPC (or specify different account/region).
  3. After creation, select the connection → Actions → Accept Request.
  4. Status transitions: Initiating-request → Pending-acceptance → Active

CLI Equivalent

# Create peering request
aws ec2 create-vpc-peering-connection \
  --vpc-id vpc-aaaa \
  --peer-vpc-id vpc-bbbb \
  --peer-region us-east-1

# Accept (run as accepter account/region)
aws ec2 accept-vpc-peering-connection \
  --vpc-peering-connection-id pcx-xxxx
💡 For cross-account peering, the accept command must be run with credentials of the accepter account. For cross-region, specify --peer-region and the accepter must accept in their region's console or CLI.

🗺️ Route Table Configuration

Route table updates are required on BOTH sides. A peering connection without route entries carries no traffic.

Lab VPC – Public Route Table

Destination Target Purpose
10.0.0.0/16 local Intra-VPC routing (automatic)
10.5.0.0/16 pcx-xxxx (Lab-Peer) Route to Shared VPC via peering
0.0.0.0/0 igw-xxxx Default route to internet

Shared VPC – Route Table

Destination Target Purpose
10.5.0.0/16 local Intra-VPC routing (automatic)
10.0.0.0/16 pcx-xxxx (Lab-Peer) Return route to Lab VPC via peering
❌ Common Mistake: Updating only one side's route table. Traffic will be one-directional — SYN packets may reach the destination, but ACK responses have no return path. The connection will time out.

🛡️ Security Considerations

Security Groups

Security Groups must explicitly permit traffic from the peered VPC's CIDR or specific SG. Peering does not bypass Security Group rules. Recommended: restrict database SG to accept MySQL (3306) from the app VPC's CIDR only (10.0.0.0/16), not from 0.0.0.0/0.

Network ACLs

NACLs are stateless. If NACLs are hardened (non-default), add both inbound and outbound rules for the peered VPC's CIDR. Default NACLs allow all traffic, so no changes required in default configurations.

ICMP for Diagnostics

ICMP (protocol 1) enables ping-based reachability testing. To allow pings from a peered VPC, add a Security Group inbound rule: Type = All ICMP – IPv4, Source = peered VPC CIDR. This was used in the lab to verify cross-VPC reachability before confirming database connectivity.

✅ VPC Flow Logs: Enable Flow Logs on both VPCs to capture traffic metadata for troubleshooting and compliance. Logs can be sent to CloudWatch Logs or S3.

🔍 Troubleshooting & Version Compatibility

Lab Issue: MySQL 8.4 vs Client Compatibility

The lab environment broke in early February 2026 when AWS's default MySQL version on RDS moved to 8.4.7. The CloudFormation template specified Engine: MySQL without pinning a version, so AWS provisioned the latest available engine. Two incompatibilities emerged:

  1. Authentication method: MySQL 8.4 defaults to caching_sha2_password. The EC2-hosted client software predates this method and cannot authenticate.
  2. Reverse DNS requirement: MySQL 8.4's default parameter group requires a successful reverse DNS lookup on the connecting client IP. RDS log shows: cannot be resolved.

CloudFormation Fix

Add version pinning to the RDS resource in the CloudFormation template:

Properties:
  Engine: mysql
  EngineVersion: "8.0"
  AutoMinorVersionUpgrade: true

This selects the latest MySQL 8.0.x release (currently 8.0.45), which retains backward compatibility with mysql_native_password authentication and older client libraries.

General Peering Troubleshooting Checklist

Symptom Likely Cause Resolution
Connection times out Missing route on one or both sides Verify route tables in both VPCs have entries for each other's CIDR
Connection refused Security Group blocking traffic Add inbound rule on destination SG allowing traffic from source VPC CIDR
Peering stuck Pending Accepter hasn't approved Go to Peering Connections, find pending request, accept
Cannot create peering Overlapping CIDRs Redesign VPC CIDR ranges to eliminate overlap
DB auth failure Engine/client version mismatch Pin engine version in IaC; update client libraries

⚖️ VPC Peering vs Transit Gateway
Criterion VPC Peering Transit Gateway
Topology Point-to-point (mesh) Hub-and-spoke
Transitivity Non-transitive Transitive (configurable)
Scalability Complex at 4+ VPCs (N*(N-1)/2 connections) Scales to thousands of VPCs
Cost Data transfer only (no hourly charge) Hourly attachment fee + data processing
Cross-account Yes Yes (via Resource Access Manager)
Cross-region Yes (inter-region peering) Yes (inter-region peering between TGWs)
Bandwidth No limit beyond VPC limits Up to 50 Gbps per attachment
Use case Small number of VPCs; cost-sensitive Large-scale multi-VPC architectures

📝 Overall Summary
  • VPC Peering: Private Layer-3 link between two VPCs; traffic stays on the AWS backbone.
  • Request-Accept model: Requester initiates; accepter must explicitly approve — even within the same account.
  • Bidirectional route updates: Both VPCs must have route table entries pointing to the peering connection ID for the other VPC's CIDR.
  • Non-transitive: A → B → C does not give A access to C. Direct peering or Transit Gateway required for each pair.
  • CIDR uniqueness: No IP range overlap permitted between peered VPCs.
  • Security Groups still enforce access: Peering enables routing; Security Groups control which traffic is permitted at the instance level.
  • Version pinning is critical: IaC templates (CloudFormation, Terraform) must specify engine versions to avoid unexpected upgrades breaking compatibility.
  • Transit Gateway preferred at scale: Use TGW when connecting more than 4-5 VPCs to avoid mesh complexity.
