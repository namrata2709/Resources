🌟 Introduction

Imagine you're cooking three dishes at once. You're watching one pot on the stove (that's a foreground process — your full attention is on it). Meanwhile, rice is slowly cooking in another pot without you watching it (that's a background process). Linux works exactly the same way.

In this session, we cover three powerful Linux concepts that every cloud engineer uses daily on AWS EC2:

  • Foreground vs Background Processes — running tasks without blocking your terminal
  • Package Managers (YUM, APT, DNF) — installing software safely from trusted repositories
  • File Transfer with FileZilla & SFTP — moving files between your local machine and EC2

Figure 1: The three key Linux concepts covered in this session

⚡ Why This Matters for AWS: Every time you deploy software on EC2 (install Docker, run a web server, transfer config files), these three skills are in play. Master them here, use them daily in real cloud work.

📦 Package Managers — Linux's App Store

On Windows, when you want to install software, you open a browser, search for it, download an installer, and click through wizards. Linux does not work like that. Instead, you type one command and the system fetches, verifies, and installs the software automatically. The engine behind this magic is called a Package Manager.

What is a Repository?

Before understanding the package manager, you need to understand where software comes from. When you run an install command on Linux, the system searches in a repository — think of it as Linux's Play Store. It is a trusted, verified online source from which Linux safely downloads packages.

Figure 2: How Linux fetches packages from a repository

💡 Analogy: Think of the repository like the Google Play Store. You don't download apps from random websites — you go to the Play Store because it is verified and safe. Linux repositories work the same way. Your package manager (YUM/APT) goes to the repository, finds the package, verifies it, and installs it.

Types of Software on Linux

Software on a Linux machine falls into three categories:

  • System Software: The OS itself — the kernel, drivers, core utilities that keep the machine running
  • Application Software: Tools used by end users — Git, Docker, Nginx, Apache
  • Utility Software: Day-to-day helper tools — curl, wget, vim, zip

All three types are managed through the same package manager — you install, update, or remove them using the same commands.

Package Manager Types by Linux Distro

Different Linux distributions use different package managers. The one you use depends on which Linux flavour is running on your EC2 instance:

Common Package Manager Commands

The commands are nearly identical across YUM and DNF. APT has slightly different syntax but the same concepts:

# Install a package (Amazon Linux / CentOS)
sudo yum install docker -y

# Install using DNF (Amazon Linux 2023)
sudo dnf install docker -y

# Install using APT (Ubuntu)
sudo apt install docker.io -y

# Update all packages
sudo yum update -y          # YUM
sudo apt update && sudo apt upgrade -y  # APT

# Remove a package
sudo yum remove docker -y
sudo apt remove docker.io -y

# Search for a package
yum search git
apt search git

# Check if a package is installed
yum list installed | grep docker
dpkg -l | grep docker   # APT/Ubuntu

⚡ The -y flag: When you install software, the system asks "Are you sure? (y/n)". Adding -y automatically answers YES to all prompts, allowing the installation to complete without manual interaction — essential for automation scripts.

Real Example: Installing Docker with Output Redirect

This is a real-world command combining everything — install Docker as a background process while redirecting all output to a log file:

sudo yum install docker -y > install.log &

Breaking this down:

  • sudo yum install docker -y — install Docker, auto-confirm
  • > install.log — redirect all standard output to a file called install.log (created automatically if it doesn't exist)
  • & — run the whole thing as a background process

💡 Why redirect output? When a process runs in the background (&), its output still prints to your terminal by default because Linux does not automatically detach standard output or standard error from the terminal. To truly silence it and keep your terminal clean, you must explicitly redirect the output to a file. This is what > install.log does.

⚙️ Foreground & Background Processes

Every command you run in a Linux terminal is a process. By default, when you run a command, it runs in the foreground — the terminal is occupied, you see all output live, and you cannot run anything else until it finishes. This is fine for fast commands like ls, but becomes a problem when a command takes a long time.

Figure 4: Foreground vs background process — terminal availability comparison

Foreground Processes

A foreground process occupies the terminal and blocks all other input until it completes. You see its output in real time, you can interact with it, but you cannot run any other command while it is running.

# This occupies the terminal for 10 seconds — you can do nothing else
sleep 10

# This runs ls and shows output immediately in the terminal
ls

To stop a foreground process at any time, press Ctrl + C. This sends a termination signal to the running process.

Background Processes — The Ampersand (&)

Adding & (ampersand) at the end of any command sends it to the background, freeing the terminal immediately.

# Run sleep in the background — terminal is immediately free
sleep 10 &

# Run ls in the background
ls &

When you run a command with &, Linux immediately shows you two numbers:

[1] 4823
  • [1] — the Job ID: a simple counter (1, 2, 3...) assigned by your current shell session to track background jobs
  • 4823 — the Process ID (PID): a system-wide unique number assigned by the OS kernel to identify this process across the entire system

💡 Job ID vs Process ID: Think of Job ID like a ticket number at a restaurant — it's just for your current session (your table). Process ID is like a national ID number — it's unique across the entire OS. Two different jobs can have the same Job ID in different terminal sessions, but no two processes ever share the same PID at the same time.

When to Use Background Processes

Use background processes when:

  • You are downloading or installing large software (takes minutes)
  • You are running a long data processing script
  • You want to start a server process and continue using the terminal
  • You are running multiple tasks simultaneously and don't want to wait for each one

Use foreground processes when:

  • You need to interact with the program (answer prompts, enter data)
  • You want to see the output immediately and act on it
  • The command is fast and you want the result right now

Managing Background Jobs

Once you have background jobs running, Linux provides commands to manage them:

# View all background jobs in current session
jobs

# Bring a background job to the foreground
# fg %1  → brings job #1 to foreground
fg %1

# Send a foreground job back to background
# First press Ctrl+Z to pause (suspend) it, then:
bg %1

Figure 5: Job control state transitions — moving processes between foreground, background, and suspended states

✅ Quick Reference:
jobs — list all background jobs
fg %N — bring job N to foreground
bg %N — send suspended job N to background
Ctrl + C — terminate foreground process
Ctrl + Z — suspend (pause) foreground process

🔍 Process Monitoring — ps and Process States

Background jobs and job IDs only work within your current terminal session. But processes are system-wide — they exist independent of your terminal. To see all processes running on your Linux system (not just your session), you use ps.

The ps Command

The ps (Process Status) command displays a snapshot of currently running processes. On its own, ps only shows processes in your current terminal session. The powerful version is:

# Show ALL processes for ALL users including daemon/background processes
ps aux

Breaking down the flags:

  • a — show processes for all users (not just you)
  • u — show user/owner information for each process
  • x — include daemon processes (background system processes not attached to any terminal)

Figure 6: Understanding ps aux output columns

💡 Why does ps aux show bash AND ps itself? When you run ps aux, Linux needs to execute the ps command. To execute any command, the shell (bash) must run first. So both bash (the shell interpreting your commands) and ps itself appear in the output — you are seeing the system work in real time.

Process STAT Codes — Understanding Process States

Every process in Linux has a STAT (status) field that describes its current state. This is critical for diagnosing performance issues and understanding what your system is doing.

⚡ Zombie Processes: A zombie process is NOT a running process consuming CPU. A zombie has already finished execution, but its entry remains in the process table because its parent process has not yet called wait() to collect the exit status. Too many zombies can exhaust the process table, but individually they consume no CPU or memory — just a PID slot.

Killing Processes

When a process is stuck, misbehaving, or consuming too many resources, you can terminate it:

# Graceful termination (asks process to stop)
kill PID
kill -15 PID

# Force kill (immediately terminates — no cleanup)
kill -9 PID

# Kill by name (kills all processes with that name)
killall nginx

# Find a process PID by name first
pgrep nginx
ps aux | grep nginx

❌ Use kill -9 with caution: Force-killing with signal 9 does not allow the process to clean up — open files may be left in a corrupted state, temporary files won't be deleted, and database transactions may be lost. Always try kill -15 (or just kill) first and only escalate to kill -9 if the process does not respond.

Managing Services with systemctl

Long-running background services (like web servers, databases, Docker) are called daemons. On modern Linux, they are managed by systemd using the systemctl command — not kill or &.

📸 From Session: systemctl command reference for managing Linux services

# Start a service
sudo systemctl start docker

# Stop a service
sudo systemctl stop nginx

# Restart a service (stop + start)
sudo systemctl restart nginx

# Reload config without stopping service
sudo systemctl reload nginx

# Enable auto-start at boot
sudo systemctl enable docker

# Disable auto-start at boot
sudo systemctl disable docker

# Check current status
sudo systemctl status docker

💡 Start vs Enable: These are two different things. start launches the service right now (this session only). enable tells Linux to start this service automatically every time the server boots. On AWS EC2, you almost always want to both start AND enable your services — otherwise after a reboot, your application is down.

📁 File Transfer — SFTP & FileZilla

In real cloud work, you constantly need to move files between your local machine and EC2 — deploying application code, uploading configuration files, downloading logs. There are several ways to do this.

What is SFTP?

SFTP (SSH File Transfer Protocol) is a secure file transfer protocol that runs over an SSH connection on port 22. It encrypts both commands and data, unlike the older FTP which transfers everything in plain text.

Setting Up FileZilla to Connect to EC2

FileZilla is a free, open-source FTP/SFTP client with a visual drag-and-drop interface. Here is how to connect it to your EC2 instance:

Step 1: Add your PEM key to FileZilla

  1. Open FileZilla
  2. Go to Edit → Settings
  3. Select SFTP from the left panel
  4. Click Add key file...
  5. Browse to your downloaded .pem key file and select it
  6. Click OK to save

Step 2: Create a new Site

  1. Go to File → Site Manager
  2. Click New Site — give it a recognizable name (e.g., my-ec2-server)
  3. Set Protocol to SFTP - SSH File Transfer Protocol
  4. Set Port to 22
  5. Set Host to your EC2 instance's Public IP address
  6. Set Logon Type to Interactive or Key file
  7. Set User to ec2-user (Amazon Linux) or ubuntu (Ubuntu)
  8. Click Connect

❌ Common Mistake — Key Conflicts: FileZilla stores previously used keys. If you add the same key file under two different names, or have duplicate keys, FileZilla may fail with "Server refused our key." Fix: go to Edit → Settings → SFTP, remove all duplicate key entries, and re-add only the correct .pem file.

Step 3: Transfer Files

  1. Once connected, the left panel shows your local machine files
  2. The right panel shows your EC2 files
  3. Drag files from left to right (upload) or right to left (download)

✅ Security Group Requirement: Before connecting with FileZilla (or any SSH/SFTP tool), make sure your EC2 Security Group has an inbound rule allowing SSH on port 22 from your IP address. Without this, all connection attempts will time out or be refused.

SCP Command (Terminal Alternative)

For scripting and automation, scp (Secure Copy Protocol) is faster than FileZilla:

# Upload a file from local to EC2
scp -i /path/to/key.pem /local/path/file.txt [email protected]:/home/ec2-user/

# Upload an entire folder (-r for recursive)
scp -i /path/to/key.pem -r /local/folder [email protected]:/home/ec2-user/

# Download a file from EC2 to local
scp -i /path/to/key.pem [email protected]:/home/ec2-user/file.txt /local/path/

# Download an entire folder
scp -i /path/to/key.pem -r [email protected]:/home/ec2-user/folder /local/path/

📝 Overall Summary

  • Repositories: Linux downloads packages from verified online repositories — like a Play Store for software. Package managers (YUM/DNF/APT) talk to these repositories on your behalf.
  • YUM vs DNF vs APT: Use yum on older Amazon Linux and CentOS; dnf on Amazon Linux 2023 and RHEL 8+; apt on Ubuntu and Debian. All do the same job, slightly different syntax.
  • Foreground Process: Occupies the terminal — you see output live but can't run other commands until it finishes. Use Ctrl+C to stop it.
  • Background Process (&): Adding & to any command runs it without blocking the terminal. Linux returns a Job ID and Process ID immediately.
  • Job ID vs PID: Job ID is local to your shell session (1, 2, 3...). Process ID is system-wide and assigned by the OS kernel.
  • jobs command: Lists all background jobs in your current terminal session.
  • fg %N: Brings background job N back to the foreground. bg %N sends a suspended job back to background.
  • ps aux: Shows all processes for all users including daemon processes. Essential for system monitoring.
  • STAT codes: R (Running), S (Sleeping), D (Uninterruptible Sleep), T (Stopped), Z (Zombie). Modifier symbols like + (foreground), s (session leader), l (multi-threaded) can appear after the main code.
  • Zombie Process: A completed process whose entry hasn't been cleaned up yet by its parent. Not dangerous individually, but too many can exhaust the process table.
  • systemctl: The right tool for managing long-running services (Docker, Nginx, etc.). Use start to run now and enable to auto-start at boot — you almost always need both.
  • SFTP / FileZilla: SFTP runs over SSH on port 22 and is the secure way to transfer files to/from EC2. FileZilla provides a GUI for drag-and-drop file transfers using your PEM key.
  • Output Redirection: Background processes still write to your terminal by default. Use > file.log to redirect output to a file and keep the terminal clean.

🟢 Project 1: Process Playground — Feel How Linux Behaves

🎯 Objective: Run real foreground and background processes by hand. Build muscle memory for &, Ctrl+C, Ctrl+Z, and jobs — before reading any more theory.

    Figure: 📸 SSH login to EC2 — confirm you see the ec2-user prompt

  2. Run sleep 30 as a foreground process. Notice the terminal is completely frozen. Press Ctrl+C to kill it.

  3. Run ping google.com as a foreground process. Watch the output stream continuously. Press Ctrl+C to stop it.

  4. Run sleep 60 &. Note the Job ID and PID that appear. Your terminal is immediately free.

🟡 Project 3: Background Execution + Real-Time Log Tracking

🎯 Objective: Run a long installation in the background, redirect output to a log file, and track progress in real time using tail -f. This is exactly how DevOps engineers handle long-running tasks.

⏱️ Time: 25–35 min | 💰 Cost: Free tier

  1. Run the nginx install as a background process with full output redirected to a log file:

    sudo yum install nginx -y > install.log 2>&1 &

    Figure: 📸 Install started in background — Job ID returned, terminal free

  2. While the install runs, open a second view of the log in real time:

    tail -f install.log

    You will see lines appear as the installation progresses. Press Ctrl+C to exit tail when done.

    Figure: 📸 tail -f watching the install log update in real time

  3. While the install is running in background AND tail is watching, open a third command in a new SSH session or after stopping tail — run ls -la, pwd, date. Confirm the terminal is fully usable.

  4. After installation completes, view the full log:

    cat install.log

  5. Count how many lines were logged:

    wc -l install.log

✅ You've achieved: You now understand async execution + logging — the foundation of all automation scripts in production.

🟡 Project 4: Process Tracking Dashboard (CLI)

🎯 Objective: Learn to observe running processes live using ps aux, grep, and watch. This is the skill you use when something is wrong on a server at 2am.

⏱️ Time: 20–30 min | 💰 Cost: Free tier

  1. Start nginx so there is a real service process to track:

    sudo systemctl start nginx

  2. Use ps aux to find the nginx process:

    ps aux | grep nginx

    Figure: 📸 ps aux | grep nginx — spot the master and worker processes

  3. Use watch to keep the process list updating every 2 seconds automatically:

    watch "ps aux | grep nginx"

    This refreshes the output every 2 seconds. Press Ctrl+C to exit.

    Figure: 📸 watch command — live auto-refreshing process monitor

  4. Now run a CPU-intensive background task to simulate load:

    yes > /dev/null &

    This sends the word "y" in an infinite loop to /dev/null (discards it). It will spike one CPU core.

  5. Watch the CPU climb using watch + ps:

    watch "ps aux --sort=-%cpu | head -10"

    Figure: 📸 yes > /dev/null causing CPU spike — visible in real-time process monitor

  6. Find the PID of the yes process and kill it:

    ps aux | grep "yes"
kill <PID>

    Watch the CPU drop back to normal in the watch window.

✅ You've achieved: You can observe systems live and identify CPU spikes — a critical on-call skill.

🔴 Project 9: Bash Automation Script — Stop Doing Things Manually

🎯 Objective: Write a bash script that sets up a complete nginx server on a fresh EC2 instance automatically. One script, zero manual steps — the foundation of all automation in DevOps.

⚫ Project 10: EC2 Auto Deploy System — Portfolio-Ready Project

🎯 Objective: Build a complete, production-style deployment system. One script launches a fresh EC2, installs nginx, deploys your HTML app, starts the service, enables auto-restart, and logs everything. This is what you show in interviews.

⏱️ Time: 60–90 min | 💰 Cost: Free tier (t3.micro)

💰 Cost Note: This project runs an EC2 instance. Stop it from the AWS Console after completing the project to avoid ongoing charges (~$0.01/hr for t3.micro).

  1. Create your HTML app locally (index.html) with any content you want to deploy.

  2. Create the full deployment script deploy.sh locally:

    #!/bin/bash

LOG="deploy.log"

echo "==============================" >> $LOG
echo "Deploy started: $(date)" >> $LOG
echo "==============================" >> $LOG

echo "[1/6] Updating system..." >> $LOG
sudo yum update -y >> $LOG 2>&1

echo "[2/6] Installing nginx..." >> $LOG
sudo yum install nginx -y >> $LOG 2>&1

echo "[3/6] Deploying app files..." >> $LOG
sudo cp ~/index.html /var/www/html/index.html >> $LOG 2>&1

echo "[4/6] Starting nginx..." >> $LOG
sudo systemctl start nginx >> $LOG 2>&1

echo "[5/6] Enabling auto-start at boot..." >> $LOG
sudo systemctl enable nginx >> $LOG 2>&1

echo "[6/6] Verifying deployment..." >> $LOG
sudo systemctl status nginx >> $LOG 2>&1

echo "==============================" >> $LOG
echo "Deploy complete: $(date)" >> $LOG
echo "==============================" >> $LOG

  3. Upload both files to EC2 via SCP:

    scp -i key.pem index.html deploy.sh ec2-user@<PUBLIC_IP>:~/

    Figure: 📸 Uploading app and deploy script to EC2 in one SCP command

  4. On EC2, make the script executable and run it in the background:

    chmod +x deploy.sh
./deploy.sh >> deploy.log 2>&1 &

  5. Watch deployment progress live:

    tail -f deploy.log

    Figure: 📸 Deployment log streaming — each numbered step confirming progress

  6. After completion, open your EC2 Public IP in a browser. Your app should be live.

    Figure: 📸 App live in browser — end-to-end automated deployment confirmed

  7. Add health check (bonus): Create a small health-check script that restarts nginx if it is not running:

    #!/bin/bash
if ! systemctl is-active --quiet nginx; then
  echo "$(date): nginx was down. Restarting..." >> health.log
  sudo systemctl start nginx
  echo "$(date): nginx restarted." >> health.log
else
  echo "$(date): nginx is healthy." >> health.log
fi

    Save as healthcheck.sh, make it executable (chmod +x healthcheck.sh), and run it manually to test both branches.
