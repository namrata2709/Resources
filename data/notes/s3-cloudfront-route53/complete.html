🌐 Introduction

Imagine you have built a beautiful website — product pages, a portfolio, a company landing page. It's all HTML, CSS, and JavaScript files — no backend server required. Where do you host it? You could spin up an EC2 server, but that means paying for compute 24/7, managing operating system patches, and scaling manually when traffic spikes. There's a much better way for static content.

Figure 1: Complete static website architecture — S3 + CloudFront + Route 53

In this session we cover the complete production-grade architecture for hosting a static website on AWS:

  • S3 (Simple Storage Service) — stores all website files as the origin
  • CloudFront — AWS's Content Delivery Network (CDN) that caches files at edge locations worldwide, solving the latency problem and keeping S3 private
  • Route 53 — AWS's DNS service that maps your friendly domain name to the CloudFront distribution
  • AWS SDK / Boto3 — programmatic control of AWS services (like launching EC2) directly from Python code, the developer's alternative to clicking through the console

⚡ The core problem this architecture solves: A single S3 bucket in Mumbai is slow for users in Australia, Canada, and New Zealand. Opening the bucket to the public is also a security concern. CloudFront solves both — caching globally and keeping the bucket private.

🪣 S3 Static Website Hosting

What Is S3 Static Website Hosting?

Amazon S3 is an object storage service. You upload files (objects) into containers called buckets. S3 has a built-in feature called Static Website Hosting that turns a bucket into a web server — meaning it will serve your HTML/CSS/JS files to browsers over HTTP.

Figure 2: S3 static website hosting — how a browser accesses content via the S3 endpoint

S3 static website hosting is suitable only for static content — HTML, CSS, JavaScript, images, and downloadable files. It cannot run server-side code like PHP, Node.js, or Python.

Enabling Static Website Hosting — Step by Step

Here is how you set up S3 static website hosting in the AWS Console:

  1. Go to the S3 Console and create a new bucket. S3 bucket names must be globally unique across all AWS accounts worldwide.

  2. Upload your website files (index.html, style.css, images, etc.) into the bucket.

  3. Go to Properties tab → scroll to Static website hosting → click Edit.

  4. Enable static website hosting and set the Index document to index.html. This is your root landing page — the first page users see.

  5. Save. You will now get a static website hosting endpoint URL — something like http://my-bucket.s3-website.ap-south-1.amazonaws.com.

  6. Go to the Permissions tab → Block Public Access → Edit → uncheck "Block all public access". By default S3 blocks public access — you must explicitly disable this for a public website.

  7. Add a Bucket Policy allowing public read access:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*"
    }
  ]
}

💡 s3:GetObject is a read-only action — visitors can read files but cannot upload, delete, or change anything. Even though the bucket is open to the internet, users only have the minimum permission needed to view the website.

The website is now accessible to anyone on the internet using that S3 endpoint URL. But there are two important problems with this setup:

  1. Latency problem: If your bucket is in Mumbai, users in Australia or Canada experience high latency — the data has to travel thousands of kilometres to reach them.
  2. Security concern: Your bucket and all its contents are open to the public internet. Your organisation may require that the storage layer remain private.

Both problems are solved by adding CloudFront in front of S3.

☁️ CloudFront — Content Delivery Network

What Is a CDN?

Think of a CDN like a chain of mini-warehouses spread across the globe. Instead of shipping every product from a single factory in Mumbai every time someone orders, you pre-stock the most popular products in local warehouses near your customers. When a customer in Sydney orders, it ships from the Sydney warehouse — not from Mumbai.

A Content Delivery Network (CDN) is a system of distributed servers (called edge locations) that cache content close to end users, dramatically reducing latency.

Figure 3: CloudFront edge locations worldwide — content cached close to every user

What Is Amazon CloudFront?

Amazon CloudFront is AWS's managed CDN service that delivers content from over 400+ edge locations and Regional Edge Caches globally.

When a user requests your website through CloudFront:

  1. CloudFront checks if it has a cached copy at the nearest edge location.
  2. If yes — it serves the file directly from the edge (called a cache hit). This is fast.
  3. If no — it fetches the file from the origin (your S3 bucket), caches it at the edge, and serves it to the user (called a cache miss). Only this first request is slow.

Figure 4: CloudFront cache hit vs cache miss flow

Three Things You Provide When Creating a Distribution

When you create a CloudFront distribution, you must provide three key things:

  1. Origin — Where is the source content? In our case, the S3 bucket.
  2. Root Object (Default Root Object) — Which file should be served when someone visits the root URL? This is index.html — your main landing page.
  3. Permissions (OAC — Origin Access Control) — A security configuration that tells CloudFront: only you are allowed to read from this S3 bucket. The bucket stays private. No one can access S3 directly.

What Is OAC (Origin Access Control)?

Origin Access Control (OAC) is a CloudFront feature that allows only a specific CloudFront distribution to access a private S3 bucket, preventing direct public access to S3.

Figure 5: OAC enforces that only CloudFront can talk to S3 — the bucket stays private

When you create a distribution with OAC, AWS generates a Distribution ID. You then update your S3 bucket policy to say: "Allow s3:GetObject only from this specific CloudFront distribution ID."

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowCloudFrontOAC",
      "Effect": "Allow",
      "Principal": {
        "Service": "cloudfront.amazonaws.com"
      },
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::YOUR-BUCKET-NAME/*",
      "Condition": {
        "StringEquals": {
          "AWS:SourceArn": "arn:aws:cloudfront::ACCOUNT-ID:distribution/DISTRIBUTION-ID"
        }
      }
    }
  ]
}

✅ With OAC in place: The S3 bucket blocks all public access. The S3 static website endpoint URL no longer works for end users. Customers must use the CloudFront distribution URL — ensuring all traffic goes through CloudFront's caching layer and security controls.

The CloudFront Distribution Endpoint

After creating the distribution, CloudFront gives you a distribution domain name — something like d1234abcd.cloudfront.net. This is what customers now use to access the website instead of the S3 URL.

💡 CloudFront distributions can take 5–20 minutes to deploy globally when first created or updated because settings must propagate to all edge locations worldwide.

CloudFront Pricing

CloudFront uses a pay-as-you-go model. There is a free tier of 1 TB of data transfer out and 10 million HTTP/HTTPS requests per month for the first 12 months. Beyond the free tier, pricing is based on:

  • Data Transfer Out — the volume of data delivered to end users from edge locations
  • HTTP/HTTPS Requests — number of requests CloudFront handles
  • Invalidation Requests — if you need to clear cached files before their TTL expires

Key Concepts to Know for Exams

  • The default TTL (Time To Live) for cached objects in CloudFront is 24 hours (86,400 seconds).
  • CloudFront supports both HTTP and HTTPS. You can enforce HTTPS-only delivery using an SSL/TLS certificate from AWS Certificate Manager (ACM).
  • CloudFront edge locations are separate from AWS Regions and Availability Zones — they are dedicated caching infrastructure points.
  • CloudFront is a global service — it does not belong to a specific region.

🗺️ Route 53 — Domain Name Service

Why Do We Need Route 53?

After setting up CloudFront, customers access the website using a CloudFront URL like d1234abcd.cloudfront.net. This URL is ugly, forgettable, and doesn't match your brand. Every real website uses a custom domain name like www.mycompany.com.

Route 53 is what bridges the gap: it maps your friendly custom domain name to the CloudFront distribution URL.

What Is Amazon Route 53?

Amazon Route 53 is AWS's highly available and scalable authoritative DNS (Domain Name System) service.

DNS is like a phone book for the internet. When you type www.amazon.com into your browser, DNS translates that human-readable name into an IP address your computer can connect to.

Figure 6: How Route 53 resolves a domain name to the CloudFront distribution

Route 53 Key Concepts

Hosted Zone: A hosted zone in Route 53 is a container for DNS records for a specific domain. When you create a hosted zone, Route 53 assigns it 4 name servers. You point your domain registrar to these name servers.

Name Servers: Route 53 gives you 4 name server addresses (e.g., ns-123.awsdns-45.com). You enter these into your domain registrar (GoDaddy, Namecheap, etc.) so that DNS queries for your domain are answered by Route 53.

DNS Records: Inside the hosted zone, you create records that map names to values. For CloudFront:

  • Create an A record (or ALIAS record) mapping your domain (e.g., www.mycompany.com) to the CloudFront distribution domain name (d1234abcd.cloudfront.net).

💡 ALIAS records vs CNAME records: For CloudFront integrations, AWS recommends using ALIAS records instead of CNAME records. ALIAS records are AWS-specific — they resolve at the DNS level and can point to AWS resources like CloudFront distributions. Unlike CNAMEs, ALIAS records work at the zone apex (e.g., example.com without www) and are free of charge when pointing to AWS resources.

The Complete Flow

Once Route 53 is configured, here is the complete journey for a user visiting your website:

  1. User types www.mycompany.com in their browser.
  2. Browser queries Route 53 (the authoritative name server for this domain).
  3. Route 53 returns the CloudFront distribution endpoint.
  4. Browser connects to the nearest CloudFront edge location.
  5. CloudFront either serves the file from cache (fast!) or fetches it from S3 (only on first request).
  6. User sees the website.

Route 53 Pricing

  • Hosted zone: $0.50 per hosted zone per month (first 25 zones)
  • DNS queries: $0.40 per million queries (first 1 billion queries/month)
  • Domain registration: Varies by TLD (e.g., .com is ~$13/year)

Routing Policies (Exam-Heavy)

Route 53 supports several routing policies — these are very commonly tested:

PolicyUse CaseKey Behaviour
SimpleSingle resourceReturns a single value
WeightedA/B testing, gradual deploymentsDistribute traffic by percentage weights
LatencyMulti-region deploymentsRoutes to region with lowest latency for user

GeoproximityFine-grained geographic controlRoutes based on location + bias factor

⚡ Route 53 is the only AWS service that can register domain names directly. All other AWS services require you to own the domain first.

Order of Setup

  1. Create S3 bucket → upload website files → enable Static Website Hosting
  2. Initially open bucket for testing (confirm website works via S3 endpoint)
  3. Create CloudFront distribution → specify S3 as origin → configure OAC → set index.html as Default Root Object
  4. CloudFront auto-generates a bucket policy update — apply it to make S3 private again
  5. Remove the public bucket policy from S3 (no longer needed — CloudFront handles access)

🐍 AWS SDK — Boto3 (Python)

What Is the AWS SDK?

Think of the AWS Console as a car with a steering wheel, dashboard, and buttons — great for humans. But what if you need 200 cars built the same way every night? You don't click 200 times — you write a script. That's what the AWS SDK is for.

An AWS SDK (Software Development Kit) is a set of programming libraries that lets developers interact with AWS services programmatically from their application code — without using the console or CLI.

Figure 8: Three ways to access AWS — Console, CLI, and SDK

Boto3 — The Python SDK for AWS

Boto3 is the official AWS SDK for Python. It is the most widely used SDK among AWS developers and DevOps engineers.

With Boto3, you can do anything you can do in the console — launch EC2 instances, upload files to S3, create databases, manage IAM users — all from Python code. This is how real-world automation is built.

Setting Up Boto3

Before Boto3 can talk to AWS, it needs credentials — your access key and secret access key. You configure these using the AWS CLI:

aws configure

This prompts you for:

  • AWS Access Key ID
  • AWS Secret Access Key
  • Default region name (e.g., ap-south-1 for Mumbai)
  • Default output format (e.g., json)

💡 Where do credentials come from? In the IAM Console → Users → your user → Security Credentials → Create Access Key. Access keys consist of an Access Key ID and a Secret Access Key. The secret access key is shown only once at creation — store it securely.

Installing Boto3

pip install boto3

Example: Launch an EC2 Instance with Boto3

Here is a real Python script that launches an EC2 instance — the same way the session demonstrated it:

import boto3

# Configuration
REGION = "ap-south-1"  # Mumbai
AMI_ID = "ami-0522ab6e1ddcc7055"  # Ubuntu Server in ap-south-1 (changes per region!)
INSTANCE_TYPE = "t3.micro"

def launch_ec2_instance():
    """Launch an EC2 instance and return its details."""
    try:
        # Create EC2 resource
        ec2 = boto3.resource('ec2', region_name=REGION)

        # Launch instance
        instances = ec2.create_instances(
            ImageId=AMI_ID,
            InstanceType=INSTANCE_TYPE,
            MinCount=1,
            MaxCount=1,
            TagSpecifications=[
                {
                    'ResourceType': 'instance',
                    'Tags': [{'Key': 'Name', 'Value': 'Boto3-Demo'}]
                }
            ]
        )

        instance = instances[0]
        print(f"Launching EC2 instance... Instance ID: {instance.id}")

        # Wait until instance is running
        print("Waiting for instance to enter running state...")
        instance.wait_until_running()

        # Reload to get updated attributes (public/private IP)
        instance.reload()

        print(f"✅ Instance launched successfully!")
        print(f"   Instance ID: {instance.id}")
        print(f"   Public IP:   {instance.public_ip_address}")
        print(f"   Private IP:  {instance.private_ip_address}")

    except Exception as e:
        print(f"❌ Error: {e}")

if __name__ == "__main__":
    print("Launching EC2 instance...")
    launch_ec2_instance()

⚡ Important: AMI IDs are region-specific — the same operating system has a different AMI ID in each AWS region. Always look up the correct AMI ID for your target region.

Boto3 Resource vs Client — What's the Difference?

Boto3 gives you two ways to work with AWS services:

TypeSyntaxStyleBest For
Resourceboto3.resource('ec2')Object-oriented (high-level)Common operations — easier to read/write
Clientboto3.client('ec2')Low-level API callsFull API access — every parameter available

Example: Upload a File to S3 with Boto3

import boto3

def upload_to_s3(file_path, bucket_name, object_key):
    """Upload a local file to an S3 bucket."""
    s3 = boto3.client('s3')
    try:
        s3.upload_file(file_path, bucket_name, object_key)
        print(f"✅ Uploaded {file_path} to s3://{bucket_name}/{object_key}")
    except Exception as e:
        print(f"❌ Upload failed: {e}")

# Example usage
upload_to_s3("index.html", "my-website-bucket", "index.html")

Why Developers and DevOps Engineers Use Boto3

  • Automation: Deploy infrastructure with one command instead of clicking through the console
  • Integration: Embed AWS operations directly in application code — e.g., a Flask app that saves uploaded photos to S3
  • Batch operations: Process thousands of resources (start/stop instances, move files) in a loop
  • CI/CD Pipelines: Deploy infrastructure as part of automated testing and deployment workflows

According to AWS documentation, Boto3 is built on top of a low-level library called botocore. Boto3 manages the session, credentials, retries, and serialisation automatically so developers focus on business logic.

📝 Overall Summary

  • S3 Static Website Hosting: Enables serving HTML/CSS/JS files from an S3 bucket as a website. Requires disabling Block Public Access and adding a GetObject bucket policy. Suitable for static content only.
  • The Two Problems with Public S3: High latency for global users, and the bucket must be open to the public internet — both solved by adding CloudFront.
  • CloudFront CDN: Caches content at 400+ global edge locations. Dramatically reduces latency by serving content from the nearest edge location instead of the origin region.
  • Three Things for a CloudFront Distribution: Origin (S3 bucket), Default Root Object (index.html), and OAC permission.
  • OAC (Origin Access Control): Keeps the S3 bucket private. Only the specific CloudFront distribution is allowed to read from S3. The old public S3 endpoint stops working.
  • CloudFront Cache Behaviour: Cache hit = fast (from edge); cache miss = slower (fetches from S3, then caches). Default TTL is 24 hours.
  • Route 53: AWS's authoritative DNS service. Creates a hosted zone for your domain and maps a custom domain name to the CloudFront distribution via an ALIAS record.
  • Hosted Zone → Name Servers → Records: Create a hosted zone → get 4 name servers → update registrar → create ALIAS A record pointing domain to CloudFront.
  • AWS SDK (Boto3): Python library for programmatic AWS access. Run aws configure first to set credentials. Use boto3.resource() for high-level OO access or boto3.client() for full low-level API.
  • AMI IDs are region-specific: The same OS image has a different AMI ID in each region. Always look up the correct ID for your target region.

Project 1: Host a Static Website on S3 with CloudFront

🎯 Objective: Deploy a static website to S3, accelerate it with CloudFront (OAC), and make the S3 bucket fully private.

⏱️ Time: 45–60 min

💰 Cost: Free tier eligible (S3 + CloudFront free tier)

  1. Create an S3 bucket. In S3 Console → Create bucket. Choose a globally unique name (e.g., my-website-20251201). Select your region (e.g., Mumbai). Leave Block Public Access ON for now — we'll configure CloudFront first.

    Figure: 📸 S3 bucket creation — unique name, region selected, block public access on

  2. Upload website files. Inside the bucket → Upload → drag and drop your index.html, CSS, JS, and image files. Click Upload.

    Figure: 📸 Files queued for upload in S3, including index.html as the root document

  3. Enable Static Website Hosting. Go to Properties tab → scroll to Static website hosting → Edit → Enable → set Index document to index.html → Save.

    Figure: 📸 Static website hosting enabled — note the S3 endpoint URL generated

  4. Create a CloudFront distribution. Go to CloudFront Console → Create distribution. Set Origin domain to your S3 bucket. Under Origin Access select Origin access control settings (recommended) → Create control setting. For Default root object, type index.html. Click Create distribution.

    Figure: 📸 CloudFront distribution creation — origin set to S3, OAC selected, root object set

  5. Copy the generated bucket policy. After creating the distribution, CloudFront shows a banner: "You need to update the S3 bucket policy." Click Copy policy.

  6. Apply the OAC bucket policy to S3. Go back to your S3 bucket → Permissions → Bucket Policy → Edit → paste the copied policy → Save changes. Keep Block Public Access enabled.

    Figure: 📸 S3 bucket policy updated with OAC policy — S3 remains private, only CloudFront has access

  7. Wait 5–20 minutes for CloudFront to deploy globally. Status changes from Deploying to Enabled.

  8. Test. Copy the Distribution domain name (e.g., dxxxxx.cloudfront.net) from the CloudFront console → paste into your browser. Your website should load.

    Figure: 📸 CloudFront distribution deployed successfully — status shows Enabled

Verification

  • ✅ Website loads at dxxxxx.cloudfront.net
  • ✅ Direct S3 website endpoint URL returns 403 Forbidden (bucket is private)

Cleanup

  1. Go to CloudFront → select your distribution → Disable → wait → then Delete
  2. Go to S3 → select all objects → Delete → then delete the bucket

Project 3: S3 Static Website — Break It and Fix It 🔧

🎯 Objective: Intentionally misconfigure an S3 static website to understand what each setting does — then fix it. You learn far more from diagnosing errors than from following steps that always succeed.

⏱️ Time: 30–45 min

💰 Cost: Free tier eligible

⚡ Why this matters in interviews: When an interviewer asks "what would cause a 403 on an S3 static website?" — you will know from experience, not guessing.

Part A — Set Up a Working Website First

  1. Create a new S3 bucket (e.g., break-fix-lab-yourname). Upload a simple index.html and an error.html file. The error page should contain: "Oops — page not found!"

  2. Go to Properties → Static website hosting → Enable. Set Index document: index.html. Set Error document: error.html. Save.

    Figure: 📸 Static website hosting enabled with both index and error document configured

  3. Go to Permissions → Disable Block Public Access → add a bucket policy allowing s3:GetObject for Principal: "*". Confirm the website loads via the S3 endpoint URL.

    Figure: 📸 Website loading successfully via S3 endpoint before any break scenario

Part B — Break Scenarios (run each, observe the error, then fix)

  1. Break 1 — Wrong index document name. Go to Static website hosting settings → change Index document from index.html to INDEX.HTML (uppercase). Visit the URL. Expected result: 403 Forbidden. Why: S3 object names are case-sensitive. Fix: revert to index.html.

    Figure: 📸 Break 1 result — 403 Forbidden caused by incorrect case in index document name

  2. Break 2 — Re-enable Block Public Access. Go to Permissions → Block Public Access → Edit → check Block all public access → Save. Visit the URL. Expected result: 403 Forbidden (even with bucket policy in place). Why: Block Public Access overrides bucket policies. Fix: uncheck all.

    Figure: 📸 Break 2 — Block Public Access overrides bucket policy, causing 403

  3. Break 3 — Delete the bucket policy. Go to Permissions → Bucket Policy → Delete policy → Save. Visit the URL. Expected result: 403 Forbidden. Why: No policy = default deny. Fix: re-add the GetObject policy.

  4. Break 4 — Request a missing file. In your browser, type the S3 endpoint URL + /missing-page.html. Expected result: Your custom error.html page should appear (not a generic AWS error). If you see the AWS XML error instead, your error document is not set correctly.

    Figure: 📸 Break 4 — Custom error page served for missing resources (correct behaviour)

Verification

  • ✅ You can reproduce a 403 by changing the index document case
  • ✅ You understand that Block Public Access overrides bucket policies
  • ✅ Custom error.html loads for missing paths

Cleanup

  1. Delete all objects in the bucket → delete the bucket

Project 4: Secure Architecture — Make S3 Private with OAC ✅

🎯 Objective: Take a public S3 website from Project 1 and convert it to a fully private architecture using CloudFront OAC. Verify that the S3 URL is completely blocked while the CloudFront URL works.

⏱️ Time: 45–60 min

💰 Cost: Free tier eligible

⚡ Interview note: "Most beginners fail here" — this is the most commonly asked CloudFront topic in AWS interviews. Know the before/after state of the bucket policy.

Part A — Start State: Public S3 Website

  1. Begin with a working S3 static website (from Project 1 or a fresh bucket). The bucket must have: Static website hosting enabled, Block Public Access off, a public GetObject bucket policy. Confirm the S3 website URL loads in your browser.

    Figure: 📸 Before state — S3 bucket is publicly accessible (Block Public Access: Off)

Part B — Add CloudFront with OAC

  1. Go to CloudFront Console → Create distribution.

    • Origin domain: your S3 bucket (use the bucket REST endpoint, NOT the static website endpoint — e.g., my-bucket.s3.ap-south-1.amazonaws.com)
    • Origin access: select Origin access control settings (recommended)
    • Click Create new OAC → accept defaults → Create
    • Default root object: index.html

    import boto3
 
REGION = "ap-south-1"
ec2 = boto3.client('ec2', region_name=REGION)
 
def list_running_instances():
    """List all running EC2 instances with their tags and IPs."""
    response = ec2.describe_instances(
        Filters=[{'Name': 'instance-state-name', 'Values': ['running']}]
    )
    instances = []
    for reservation in response['Reservations']:
        for instance in reservation['Instances']:
            # Get Name tag if it exists
            name = "No Name"
            for tag in instance.get('Tags', []):
                if tag['Key'] == 'Name':
                    name = tag['Value']
            instances.append({
                'id': instance['InstanceId'],
                'name': name,
                'type': instance['InstanceType'],
                'public_ip': instance.get('PublicIpAddress', 'N/A'),
                'private_ip': instance.get('PrivateIpAddress', 'N/A')
            })
    if instances:
        print(f"Found {len(instances)} running instance(s):")
        for i in instances:
            print(f"  [{i['id']}] {i['name']} | {i['type']} | Public: {i['public_ip']} | Private: {i['private_ip']}")
    else:
        print("No running instances found.")
    return instances

Project 8: Boto3 Automation — Deploy to S3 + Invalidate CloudFront 🚀

🎯 Objective: Write a single Python script that deploys your website to S3 AND automatically creates a CloudFront invalidation. This is the core of a CI/CD pipeline for static websites.

⏱️ Time: 40–50 min

💰 Cost: Free tier (first 1,000 invalidation paths free per month)

⚡ This script is exactly what GitHub Actions or Jenkins would run in a real deployment pipeline. Understanding this makes you immediately useful to a DevOps team.

The Complete Deployment Script

  1. Create a file called deploy.py with the following content. Replace the constants at the top with your actual values:

    import boto3
import os
import mimetypes
import time
 
# ─── CONFIG ────────────────────────────────────────────────
BUCKET_NAME        = "your-bucket-name"
DISTRIBUTION_ID    = "your-cloudfront-distribution-id"   # from CloudFront console
LOCAL_FOLDER       = "./site"     # folder containing your website files
REGION             = "ap-south-1"
# ────────────────────────────────────────────────────────────
 
s3 = boto3.client('s3', region_name=REGION)
cf = boto3.client('cloudfront')
 
def upload_folder_to_s3(local_folder, bucket_name):
    """Upload all files from a local folder to S3, preserving directory structure."""
    uploaded = []
    for root, dirs, files in os.walk(local_folder):
        for filename in files:
            local_path = os.path.join(root, filename)
            # Build S3 key (relative path)
            s3_key = os.path.relpath(local_path, local_folder).replace("\\", "/")
            # Detect content type
            content_type, _ = mimetypes.guess_type(local_path)
            content_type = content_type or 'application/octet-stream'
            extra_args = {'ContentType': content_type}
            # Set short TTL for HTML, long TTL for assets
            if filename.endswith('.html'):
                extra_args['CacheControl'] = 'max-age=300'
            else:
                extra_args['CacheControl'] = 'max-age=31536000'
            s3.upload_file(local_path, bucket_name, s3_key, ExtraArgs=extra_args)
            uploaded.append(s3_key)
            print(f"  ✅ Uploaded: {s3_key} ({content_type})")
    return uploaded
 
def invalidate_cloudfront(distribution_id, paths):
    """Create a CloudFront invalidation for the given paths."""
    invalidation_batch = {
        'Paths': {
            'Quantity': len(paths),
            'Items': [f'/{p}' for p in paths]
        },
        'CallerReference': str(int(time.time()))  # unique reference
    }
    response = cf.create_invalidation(
        DistributionId=distribution_id,
        InvalidationBatch=invalidation_batch
    )
    inv_id = response['Invalidation']['Id']
    status  = response['Invalidation']['Status']
    print(f"  ✅ Invalidation created: {inv_id} (Status: {status})")
    return inv_id
 
def deploy():
    print(f"🚀 Starting deployment to s3://{BUCKET_NAME}")
    uploaded_files = upload_folder_to_s3(LOCAL_FOLDER, BUCKET_NAME)
    print(f"\n📤 Uploaded {len(uploaded_files)} file(s).")
    print(f"\n🔄 Creating CloudFront invalidation for {len(uploaded_files)} path(s)...")
    invalidate_cloudfront(DISTRIBUTION_ID, uploaded_files)
    print(f"\n✅ Deployment complete! Changes will be live within 30–60 seconds.")
 
if __name__ == "__main__":
    deploy()

  2. Create a folder called site/ in the same directory as deploy.py. Place your index.html, CSS, and image files inside it.

  3. Run the script:

    python deploy.py

    Figure: 📸 deploy.py full output — files uploaded to S3 and CloudFront invalidation created automatically

  4. Verify in the CloudFront Console → your distribution → Invalidations tab. You should see a new invalidation with status In progress → Completed.

    Figure: 📸 CloudFront Invalidations tab confirming the deploy.py script created the invalidation successfully

  5. Update a file in your site/ folder and run python deploy.py again. Confirm the change appears on your CloudFront URL within 30–60 seconds.

Verification

  • ✅ All files from site/ folder appear in S3 with correct content types
  • ✅ HTML files have Cache-Control: max-age=300; other files have max-age=31536000
  • ✅ CloudFront Invalidations tab shows the new invalidation
  • ✅ Website reflects updated content within 60 seconds of running the script

Cleanup

  1. CloudFront → Disable → Delete distribution
  2. S3 → Delete all objects → Delete bucket
