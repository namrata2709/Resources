🌐 Introduction

Imagine you live in a gated apartment complex. Your apartment has a private address — it's not visible to the outside world. But you still want to access the internet: browse websites, download updates, stream videos. How do you do that without exposing your private address?

That's exactly the problem NAT Gateway solves inside AWS. Your private EC2 instances live in private subnets — no direct internet access. But sometimes they need to reach out (download patches, call external APIs). NAT Gateway lets them do that safely, without ever exposing their private IP to the world.

And what about connecting your entire office or data center to AWS? That's where VPN and Direct Connect come in — two very different ways to build a bridge between your on-premises network and your AWS VPC. One uses the existing internet (fast to set up, lower cost), the other uses a dedicated physical cable (premium, low-latency, ultra-reliable).

In this session, we cover all three: NAT, VPN, and Direct Connect — understanding when to use which, and how they work together in real AWS architectures.

🔒 The Problem NAT Solves

Private Subnets — Why They Sometimes Need the Internet

When you design a secure AWS architecture, you put most of your EC2 instances in private subnets. Private means no direct path to or from the internet — which is great for security. Your database servers, application servers, and backend workers live here, invisible to the outside world.

But here's the catch: these private instances still need to reach out to the internet occasionally. Think about:

  • Downloading software updates or patches from public repositories
  • Calling external APIs (payment gateways, weather services, SMS providers)
  • Downloading packages from npm, pip, apt, or yum
  • Sending logs or metrics to external monitoring services

If your private instance tries to go to the internet directly, it has a private IP (like 10.0.1.25). The internet doesn't know how to send a reply back to a private address — private IPs aren't routable on the public internet.

💡 The core problem: Private EC2 instances need outbound internet access but must never receive inbound connections from the internet. NAT is the solution — it translates private IPs to a public IP for outbound traffic only, and discards unsolicited inbound attempts.

Figure 2: Private IPs can't communicate directly with the internet — NAT bridges this gap

What is NAT?

NAT stands for Network Address Translation. It's a technique that replaces the source private IP address in outbound packets with a public IP address, forwards the request to the internet, receives the response, and then delivers it back to the original private instance.

NAT allows instances in a private subnet to connect to the internet while preventing the internet from initiating connections to those instances.

Think of NAT like a company receptionist. Employees (private instances) ask the receptionist (NAT) to make calls on their behalf. The outside world only sees the receptionist's number (public IP). When the call returns, the receptionist routes it to the right employee. The employee's direct line (private IP) is never exposed.

🚀 NAT Gateway

What is NAT Gateway?

NAT Gateway is a managed AWS service that provides Network Address Translation for instances in private subnets. You don't manage any servers — AWS runs, maintains, patches, and scales it for you. You just create it, attach it to a public subnet, and point your private subnet's route table at it.

Figure 3: NAT Gateway sits in a public subnet and handles all outbound internet traffic from private subnets

How NAT Gateway Works — Step by Step

  1. A private EC2 instance (e.g., IP 10.0.1.25) wants to reach api.example.com
  2. The instance sends the request to its subnet's route table
  3. The route table has an entry: 0.0.0.0/0 → NAT Gateway
  4. The NAT Gateway receives the packet, replaces the source IP with its own Elastic IP (public IP)
  5. The modified packet goes out through the Internet Gateway to the internet
  6. The response comes back to the NAT Gateway's public IP
  7. NAT Gateway translates it back and delivers it to the original EC2 instance

✅ Key architecture rule: NAT Gateway must always be placed in a public subnet, not a private one. It needs internet access itself to forward traffic. The private subnet's route table then points outbound traffic (0.0.0.0/0) to the NAT Gateway.

Key Features

  • Fully managed: No OS to patch, no instance to maintain, no configuration needed
  • NAT Gateway auto-scales up to 45 Gbps of bandwidth automatically.
  • Elastic IP required: You must assign one Elastic IP address to the NAT Gateway (this becomes its public IP)
  • NAT Gateway is highly available within a single AZ — to ensure HA across all AZs, create one NAT Gateway per AZ.
  • IPv4 only: Standard NAT Gateway supports IPv4 only (there is a separate NAT Gateway type for IPv6 called egress-only Internet Gateway)
  • Outbound only: The internet cannot initiate connections to your private instances through NAT Gateway

Pricing

NAT Gateway pricing includes a per-hour charge plus a per-GB data processing charge. This makes it more expensive than a NAT Instance for very high traffic workloads, but the operational simplicity usually makes it worth the cost for production environments.

💡 According to AWS documentation, you are charged for each hour that your NAT gateway is provisioned and available, and for each GB of data it processes. Partial hours are billed as full hours.
📚 Source:AWS VPC Pricing

When to Use NAT Gateway

  • Production workloads where high availability and zero maintenance are critical
  • Applications that require consistent, high-bandwidth outbound internet access
  • Teams that want simplicity and don't want to manage infrastructure
  • Any scenario where you have multiple private subnets across multiple AZs needing internet access

Figure 4: Best practice — one NAT Gateway per AZ for full high availability. If AZ-A's NAT Gateway fails, AZ-B's private instances still work.

🖥️ NAT Instance

What is a NAT Instance?

Before AWS introduced NAT Gateway, the only way to provide internet access to private subnets was to launch a regular EC2 instance configured to perform NAT. This EC2 instance would sit in a public subnet, and you'd configure it manually to forward traffic. This is called a NAT Instance.

A NAT Instance is a self-managed EC2 instance running special NAT AMI software, used to route traffic from private subnets to the internet.

❌ Important: NAT Instances are considered legacy. AWS recommends using NAT Gateway for all new workloads. However, NAT Instances still appear on AWS exams, so understanding them is important for certification.

How NAT Instance Works

To configure a NAT Instance, you must:

  1. Launch an EC2 instance in a public subnet using a special NAT AMI (provided by AWS)
  2. Disable Source/Destination Check — by default, EC2 drops packets not addressed to itself. NAT needs to forward packets for other instances, so this check must be disabled.
  3. Update the private subnet's route table: 0.0.0.0/0 → NAT Instance ID
  4. Configure Security Groups on the NAT Instance to allow the right traffic

💡 Source/Destination Check: Every EC2 instance checks that it is either the source or destination of any traffic it receives. NAT Instances must disable this check because they forward traffic on behalf of other instances — the packets belong to those instances, not the NAT Instance itself.

Key Characteristics

  • You manage everything: OS patching, availability, failover, performance tuning
  • NAT Instance bandwidth is limited by the EC2 instance type — you must manually resize to scale.
  • Can be used as a bastion host: Unlike NAT Gateway, a NAT Instance supports SSH access, so it can double as a jump server
  • Custom routing rules: You can install iptables rules for granular traffic control — something NAT Gateway doesn't support
  • Lower cost (potentially): You only pay for the EC2 instance, not the per-GB data processing fee
  • No built-in high availability: If the NAT Instance fails, all private subnet outbound traffic stops. You must set up failover scripts yourself.

🏢 Connecting Your Office to AWS

What is Hybrid Architecture?

Many companies don't live entirely in the cloud. They have existing on-premises servers — physical machines in their own data center or office building — that run critical applications, databases, and services. They also want to use AWS for new workloads, scaling, or disaster recovery.

This combination of on-premises + cloud is called a hybrid architecture. The challenge: how do these two worlds talk to each other securely?

Think of it like this: you have your home network (on-premises) and you want a private, secure channel to your office building (AWS VPC). You don't want to send sensitive data over the open internet unprotected. You need a private tunnel.

AWS provides two main options:

  • Site-to-Site VPN — an encrypted tunnel over the public internet
  • AWS Direct Connect — a dedicated private fiber cable bypassing the internet entirely

Figure 7: Two paths to connect your data center to AWS — VPN over internet (left) vs Direct Connect dedicated fiber (right)

🔐 Site-to-Site VPN

What is a VPN?

A VPN (Virtual Private Network) creates an encrypted, secure tunnel between two locations over the public internet. Think of it like a secret underground passageway between your house and a bank — even though the passageway runs under a public road, nobody above ground can see what's passing through it.

AWS Site-to-Site VPN creates an IPSec-encrypted tunnel between your on-premises network and your AWS VPC over the public internet.

The Connection Flow

The professor showed this flow in the session. Remember it — it appears frequently in architecture questions:

📸 From Session: VPN connection flow shown by the professor: On-prem Router ⇔ Internet ⇔ AWS VPN Gateway (VGW) ⇔ VPC

Figure 8: Full Site-to-Site VPN architecture — Customer Gateway on your side, Virtual Private Gateway on AWS side

Key Components

Setting up a Site-to-Site VPN requires two gateway components — one on each end of the tunnel:

1. Customer Gateway (CGW)

This is your side of the connection. It represents your on-premises router or firewall device. In the AWS console, you create a Customer Gateway resource and enter the public IP address of your on-premises device. This tells AWS where to connect to.

2. Virtual Private Gateway (VGW)

This is AWS's side of the connection. The Virtual Private Gateway (VGW) is attached to your VPC and acts as the AWS endpoint for the VPN tunnel. Once the VGW is attached to your VPC, your on-premises network can route traffic through the VPN into the VPC.

3. VPN Connection

Once both gateways are created, you create the VPN Connection in the console by selecting your VGW and CGW. AWS automatically creates two redundant IPSec tunnels (two endpoints for failover). Your on-premises router receives a configuration file with the tunnel parameters to configure your device.

✅ Setup order (important for exams and practicals):
1. Create Virtual Private Gateway → attach to VPC
2. Create Customer Gateway → enter on-prem device IP
3. Create Site-to-Site VPN Connection → link the two gateways
4. Download configuration → apply to your on-premises router

Tunnel Details

  • Each VPN connection provides two tunnels for redundancy — if one tunnel fails, traffic automatically moves to the second.
  • VPN bandwidth is limited to approximately 1.25 Gbps per tunnel.
  • Encryption uses IPSec (industry standard for network encryption)
  • Supports both static routing and BGP (dynamic routing)

When to Use VPN

  • Quick setup needed — VPN can be configured in hours
  • Budget is limited — VPN is relatively low cost
  • Small to medium workloads where bandwidth of ~1.25 Gbps is sufficient
  • Development, testing, or staging environments connecting to AWS
  • Disaster recovery — a backup path when Direct Connect is the primary
  • Startups or small businesses that don't need the premium of Direct Connect

VPN Limitations

  • Variable latency: Since traffic goes over the public internet, latency can fluctuate depending on internet conditions
  • Bandwidth ceiling: 1.25 Gbps per tunnel is not enough for large enterprise data transfers
  • Internet dependency: If your ISP has issues, your VPN connection is affected

⚡ AWS Direct Connect

What is Direct Connect?

Sometimes a VPN over the internet just isn't good enough. Banks transferring millions of transactions, hospitals transmitting huge medical imaging files, enterprises running latency-sensitive trading applications — these workloads can't afford variable latency or shared internet bandwidth.

That's where AWS Direct Connect comes in. AWS Direct Connect provides a dedicated private physical fiber connection from your on-premises data center directly to an AWS Direct Connect location, bypassing the public internet entirely.

Think of the difference between VPN and Direct Connect like this: VPN is like sending a letter through the regular postal service — it works, it's cheap, but delivery time varies and you share the system with everyone. Direct Connect is like hiring a private courier who drives directly from your office to the destination with nothing in between — faster, more reliable, but much more expensive.

Figure 9: Direct Connect — dedicated fiber from your data center to AWS, no internet in the path

How It Works

  1. You request a Direct Connect connection from AWS (through the console or a partner)
  2. AWS works with you to establish a physical connection at an AWS Direct Connect location (these are colocation facilities / data centers near major cities)
  3. A physical fiber cable runs from your data center (or connects via a colocation provider) to the AWS network
  4. You set up Virtual Interfaces (VIFs) to route traffic — private VIFs for VPC access, public VIFs for AWS public services
  5. Traffic flows directly between your premises and AWS over this dedicated circuit — no internet involved

Speeds Available

Direct Connect supports connection speeds of 1 Gbps, 10 Gbps, and higher (up to 100 Gbps via partners). This is a significant jump over VPN's 1.25 Gbps ceiling.

Key Characteristics

  • No internet: Traffic never touches the public internet — completely private
  • Consistent low latency: Predictable, stable performance because you're on a dedicated circuit
  • High bandwidth: Suitable for large-scale data transfers (backups, migrations, big data)
  • Direct Connect is not encrypted by default — you can combine it with a VPN on top for encryption if needed.
  • Takes weeks to provision: Physical infrastructure takes time — ordering, cabling, and testing a fiber connection isn't instant
  • High cost: Premium pricing for port charges plus facility fees

💡 Direct Connect + VPN (Best of Both Worlds): A common enterprise pattern is to use Direct Connect as the primary connection (for speed and reliability) and a VPN as a backup. If the fiber cable is ever cut or has an outage, the VPN kicks in automatically to maintain connectivity.

When to Use Direct Connect

  • Enterprise production workloads with strict latency and bandwidth requirements
  • Large-scale data migration (moving terabytes or petabytes to AWS)
  • Hybrid architectures where on-premises and cloud must communicate constantly at high speed
  • Regulated industries (finance, healthcare) that cannot send sensitive data over the public internet
  • Applications where network jitter (variable delay) would cause problems (voice/video systems, trading platforms)

🔀 Transit Gateway (Overview)

What is Transit Gateway?

As your AWS environment grows, you'll have multiple VPCs. Connecting every VPC to every other VPC directly (VPC peering) becomes a messy web. And connecting each VPC to your on-premises network via separate VPN connections multiplies cost and complexity.

Transit Gateway is AWS's solution to this scaling problem. It acts as a central hub that all your VPCs and on-premises networks connect to — instead of every network connecting to every other network individually.

AWS Transit Gateway is a network transit hub that enables customers to connect their VPCs and on-premises networks through a single gateway.

Figure 11: Transit Gateway hub-and-spoke model — one central hub replaces dozens of individual peering connections

Without Transit Gateway — The Mesh Problem

Imagine you have 5 VPCs and need them all to communicate with each other and with your on-premises network. Without Transit Gateway, you'd need:

  • 10 VPC peering connections (5 VPCs × 4 peers ÷ 2 = 10)
  • 5 separate VPN connections (one per VPC to on-premises)
  • 15 total connections to manage, monitor, and troubleshoot

With Transit Gateway: 5 VPC attachments + 1 VPN attachment = 6 connections total. Exponentially simpler.

💡 Note: Transit Gateway is a deeper topic we'll cover fully in a dedicated session. For now, understand that it's the enterprise-scale solution to connecting many VPCs and hybrid networks. It's often paired with Direct Connect and VPN in large architectures.

🎓 Exam Tips

NAT Gateway / NAT Instance Exam Tips

  • Managed vs self-managed: Any question mentioning "no maintenance" or "fully managed NAT" → NAT Gateway
  • Source/Destination Check: Only NAT Instances need this disabled — a classic exam question
  • Bastion host combo: Only NAT Instance can serve as both NAT and bastion (jump server)
  • For high availability, you need one NAT Gateway per AZ — not one per VPC.
  • Custom routing (iptables): NAT Gateway doesn't support iptables — only NAT Instance does

VPN Exam Tips

  • Two gateways: VGW on AWS side + CGW on customer side → always need both
  • Two tunnels: Each VPN connection has two tunnels for redundancy
  • IPSec only: AWS Site-to-Site VPN uses IPSec encryption
  • Bandwidth limit: ~1.25 Gbps per tunnel — not suitable for massive data transfers

Direct Connect Exam Tips

  • Direct Connect is not encrypted by default — this is the most common exam trap
  • Setup time: Weeks (physical cable) vs VPN's hours
  • Best for: Large bandwidth, consistent latency, compliance requirements
  • Failover pattern: Use VPN as backup when Direct Connect is primary
  • Virtual Interfaces: Private VIF for VPC access, Public VIF for AWS public services

⚡ Common exam scenario: "A company needs a fast, reliable connection to AWS with consistent low latency and their data is highly sensitive." Answer: Direct Connect. But if the question adds "with encryption," the answer is Direct Connect + VPN on top (or just VPN if budget is the concern).

📝 Overall Summary

  • NAT Gateway: Fully managed AWS service that enables private subnet instances to access the internet outbound-only; auto-scales to 45 Gbps; costs more but requires zero maintenance
  • NAT Instance: Legacy self-managed EC2 approach; requires disabling Source/Destination Check; more control (iptables) and lower cost but you own all maintenance and failover
  • For HA with NAT Gateway: Deploy one NAT Gateway per Availability Zone — not one per VPC
  • Site-to-Site VPN: Encrypted IPSec tunnel over public internet between on-premises and AWS; fast to set up (hours); limited to ~1.25 Gbps; variable latency
  • VPN Components: Virtual Private Gateway (VGW) on AWS side + Customer Gateway (CGW) on customer side + VPN Connection linking them
  • Direct Connect: Dedicated private physical fiber connection bypassing the internet; consistent low latency; 1–100 Gbps speeds; takes weeks to provision; high cost
  • Direct Connect is NOT encrypted by default — combine with VPN for encryption
  • Common pattern: Direct Connect as primary + VPN as failover backup
  • Transit Gateway: Central hub connecting multiple VPCs and on-premises networks; eliminates complex mesh peering at scale
  • Choose VPN when: speed of setup matters, budget is limited, small/medium workloads
  • Choose Direct Connect when: consistent latency required, high bandwidth needed, enterprise production, compliance requirements

💼 Hands-On Projects

📋 Prerequisites

  • ✅ AWS account (free tier eligible)
  • ✅ Existing VPC with public and private subnets (from earlier sessions)
  • ✅ At least one EC2 instance in a private subnet

Project 1: Create NAT Gateway and Enable Private Subnet Internet Access

🎯 Objective: Create a NAT Gateway in your public subnet and configure route tables so private subnet EC2 instances can access the internet outbound-only

⏱️ Time: 20–30 min

💰 Cost: ~$0.045/hour for NAT Gateway + $0.045/GB data processed — delete when done

  1. Navigate to VPC → Elastic IPs and allocate a new Elastic IP address (you will attach this to your NAT Gateway).

    📸 Screenshot: Elastic IP allocation — record the allocation ID shown

  2. Go to VPC → NAT Gateways → Create NAT Gateway. Select your public subnet, set Connectivity Type to Public, and attach the Elastic IP you just allocated.

    📸 Screenshot: NAT Gateway creation form — verify subnet is PUBLIC, not private

  3. Wait for the NAT Gateway status to show Available (takes 1–2 minutes). Copy the NAT Gateway ID.

    📸 Screenshot: NAT Gateway status showing "Available" — it is now ready to route traffic

  4. Navigate to VPC → Route Tables. Find the route table associated with your private subnet. Click Edit routes → Add route. Set Destination: 0.0.0.0/0, Target: your NAT Gateway ID. Save.

    📸 Screenshot: Private route table — 0.0.0.0/0 pointing to NAT Gateway, not Internet Gateway

  5. SSH into your private EC2 instance via the bastion host and verify outbound internet works: curl ifconfig.me (should return the NAT Gateway's Elastic IP, not your instance's private IP) and sudo apt update to confirm package downloads work.

  6. Cleanup: Delete the NAT Gateway → Release the Elastic IP → Remove the 0.0.0.0/0 route from the private route table. NAT Gateways charge hourly — always delete after practice.

Project 2: Break & Fix — Debug Networking Failures

🎯 Objective: Intentionally break networking at different layers and repair each failure — building the debug instinct that real interviews test

⏱️ Time: 30–40 min

💰 Cost: EC2 instance costs only (~$0.01/hour for t2.micro) — no NAT Gateway needed during break tests

⚡ Why this project matters: Most AWS interview troubleshooting questions are based on broken routing. Experiencing the failure firsthand — not just reading about it — is what builds real confidence.

  1. Start with a working setup: private EC2 with NAT Gateway configured and internet confirmed working (curl ifconfig.me returns the EIP).

  2. Break #1 — Remove the route: Go to the private subnet's route table → Edit routes → Delete the 0.0.0.0/0 → NAT Gateway route. SSH back into the private instance and run curl ifconfig.me. It should time out.

    📸 Screenshot: Route table with 0.0.0.0/0 removed — private instance now has no internet path

  3. Fix #1: Add the route back (0.0.0.0/0 → NAT Gateway). Verify internet works again. You just experienced and fixed a missing route — the #1 cause of private subnet connectivity failures.

  4. Break #2 — NAT Gateway in wrong subnet: Delete your NAT Gateway. Create a new NAT Gateway but put it in the private subnet (wrong placement). Keep the route table pointing to this new NAT Gateway. Test — internet still fails because NAT Gateway itself has no internet path.

    📸 Screenshot: NAT Gateway placed in private subnet — a common mistake. It must always be in a public subnet.

  5. Fix #2: Delete the misplaced NAT Gateway. Create a new one in the correct public subnet. Restore route table. Internet returns.

  6. Break #3 — Delete the Internet Gateway: Go to VPC → Internet Gateways. Detach and delete the IGW from your VPC. Now test from the private instance — internet fails even through NAT, because NAT has no path to the internet without IGW.

    📸 Screenshot: Internet Gateway detached — NAT Gateway itself now has no internet path, so all outbound traffic fails

  7. Fix #3: Create a new Internet Gateway → Attach to your VPC → Confirm the public subnet's route table has 0.0.0.0/0 → IGW. Test. Document each failure and fix in a notes file.

  8. Cleanup: Delete NAT Gateway → Release Elastic IP when done. Keep EC2 and VPC for the next project.

Project 3: NAT Gateway vs NAT Instance — Real Comparison

🎯 Objective: Set up both NAT options side by side and compare them on cost, control, and performance — turning theory into lived experience

⏱️ Time: 45–60 min

💰 Cost: NAT Gateway (~$0.045/hr) + NAT Instance EC2 t2.micro (~$0.013/hr) — delete both when done

  1. Create two private subnets in the same VPC: private-subnet-A (will use NAT Gateway) and private-subnet-B (will use NAT Instance). Launch one EC2 instance in each.

    📸 Screenshot: Two private subnets created — each will use a different NAT approach

  2. Path A — NAT Gateway: Create a NAT Gateway in your public subnet with an Elastic IP. Update private-subnet-A's route table: 0.0.0.0/0 → NAT Gateway.

  3. Path B — NAT Instance: Launch an EC2 instance using a NAT AMI (search amzn-ami-vpc-nat in Community AMIs) in the public subnet. Then select that instance → Actions → Networking → Change Source/Destination Check → Disable.

    📸 Screenshot: Disabling Source/Destination Check on the NAT Instance — this step is mandatory for forwarding to work

  4. Update private-subnet-B's route table: 0.0.0.0/0 → NAT Instance (its ENI or instance ID).

    📸 Screenshot: Route table for subnet-B pointing to NAT Instance — compare this with subnet-A's NAT Gateway route

  5. Test both paths: SSH into the EC2 in subnet-A and run curl ifconfig.me — it should return the NAT Gateway's EIP. SSH into the EC2 in subnet-B and run the same — it should return the NAT Instance's public IP.

  6. Compare: On the NAT Instance, run top while downloading a large file from subnet-B — you will see CPU usage. NAT Gateway has no equivalent CPU to monitor. Note the difference in operational visibility. Calculate cost for 1 month of each at your expected traffic volume.

  7. Cleanup: Delete NAT Gateway → Release EIP → Terminate NAT Instance → Remove custom routes.

Project 4: Multi-AZ NAT Gateway — High Availability Architecture

🎯 Objective: Implement a production-level multi-AZ NAT architecture and simulate an AZ failure to see HA in action

⏱️ Time: 40–50 min

💰 Cost: 2× NAT Gateways (~$0.09/hr combined) — delete when done

  1. Ensure your VPC has resources in two Availability Zones. Create: public-subnet-AZ1 and public-subnet-AZ2 (one per AZ), and private-subnet-AZ1 and private-subnet-AZ2.

    📸 Screenshot: Four subnets across two AZs — each AZ has one public and one private subnet

  2. Create NAT Gateway #1 in public-subnet-AZ1 with its own Elastic IP. Create NAT Gateway #2 in public-subnet-AZ2 with a second Elastic IP.

    📸 Screenshot: Two NAT Gateways — one per AZ. Each has its own Elastic IP.

  3. Set routes: private-subnet-AZ1 route table → 0.0.0.0/0 → NAT Gateway #1. private-subnet-AZ2 route table → 0.0.0.0/0 → NAT Gateway #2. This is the HA pattern — each AZ is self-contained.

    📸 Screenshot: Each AZ's private subnet routes to its own local NAT Gateway — no cross-AZ dependency

  4. Simulate AZ failure: Stop the EC2 instance in private-subnet-AZ1 (simulates AZ1 being unavailable). Check the EC2 in private-subnet-AZ2 — it should still have internet access through its own NAT Gateway #2 without any impact. This is HA working correctly.

  5. Anti-pattern test (optional): Change private-subnet-AZ2's route to also point to NAT Gateway #1 (cross-AZ). Then "fail" AZ1 by deleting NAT Gateway #1. Observe that AZ2's private instances lose internet access too — demonstrating why cross-AZ NAT routing is an anti-pattern.

  6. Cleanup: Delete both NAT Gateways → Release both Elastic IPs → Restore route tables.

Project 5: Site-to-Site VPN — Console Walkthrough

🎯 Objective: Create all VPN components in the console and analyze the downloaded configuration file to understand how real companies configure hybrid connectivity

⏱️ Time: 20–25 min

💰 Cost: VGW = free. VPN Connection = ~$0.05/hour — delete immediately after exploring

  1. Go to VPC → Virtual Private Gateways → Create Virtual Private Gateway. Leave ASN as Amazon default. After creation, select it → Actions → Attach to VPC → select your VPC.

    📸 Screenshot: Virtual Private Gateway created and attached to VPC — Status shows Attached

  2. Go to VPC → Customer Gateways → Create Customer Gateway. Enter a placeholder IP (e.g., 1.2.3.4). Routing: Static. In a real deployment, this would be your on-premises router's actual public IP.

    📸 Screenshot: Customer Gateway represents your on-premises router — in production, enter its real public IP

  3. Go to VPC → Site-to-Site VPN Connections → Create VPN Connection. Select your VGW and CGW. Note the two tunnel endpoints and routing options. Create the connection.

    📸 Screenshot: VPN Connection form linking VGW and CGW — both must exist before creating this

  4. Once created, select the VPN Connection → Download Configuration. Choose your router vendor (use Generic if unsure). Open the downloaded file — it contains the two tunnel IPs, pre-shared keys, and exact IKE/IPSec parameters your router needs. This file is what a network engineer applies to the physical router.

    📸 Screenshot: Download Configuration dialog — this file contains the IPSec settings for your on-premises router

  5. Cleanup: Delete VPN Connection first → Delete Customer Gateway → Detach and delete the Virtual Private Gateway.

Project 6: Transit Gateway — Connect Two VPCs

🎯 Objective: Build the hub-and-spoke Transit Gateway architecture — connect two isolated VPCs so their private EC2 instances can ping each other

⏱️ Time: 40–50 min

💰 Cost: TGW ~$0.05/hr per attachment (2 attachments = ~$0.10/hr) + data processing — delete when done

  1. Create two new VPCs with non-overlapping CIDRs: VPC-A (CIDR: 10.10.0.0/16) and VPC-B (CIDR: 10.20.0.0/16). Create one private subnet in each. Launch one EC2 in each subnet.

    📸 Screenshot: Two isolated VPCs — no peering yet. EC2s in each cannot reach each other.

  2. Go to VPC → Transit Gateways → Create Transit Gateway. Leave defaults. Wait for state to show Available.

    📸 Screenshot: Transit Gateway creation form — defaults are fine for this lab

  3. Go to VPC → Transit Gateway Attachments → Create Transit Gateway Attachment. Select your TGW, Attachment type: VPC, and select VPC-A. Repeat — create a second attachment for VPC-B.

    📸 Screenshot: Two Transit Gateway Attachments — one per VPC. Both must be Available before routing works.

  4. Update VPC-A's route table: add route 10.20.0.0/16 → Transit Gateway. Update VPC-B's route table: add route 10.10.0.0/16 → Transit Gateway. This tells each VPC to forward cross-VPC traffic through the TGW.

    📸 Screenshot: VPC-A route table — traffic for VPC-B's CIDR goes through Transit Gateway

  5. SSH into the EC2 in VPC-A and ping the private IP of the EC2 in VPC-B. It should succeed. You have just built a Transit Gateway hub-and-spoke network.

  6. Cleanup: Delete both TGW Attachments → Delete the Transit Gateway → Remove TGW routes from both VPCs' route tables → Terminate EC2s → Delete VPCs.

Project 7: Direct Connect — Design & Architecture Exercise

🎯 Objective: Design a production Direct Connect architecture with VPN failover — you cannot physically provision DX, but designing and explaining it is what interviews actually test

⏱️ Time: 30–40 min (design + documentation)

💰 Cost: Free — this is a design exercise with console exploration only

⚡ Why this counts: Direct Connect takes weeks and costs thousands to provision. Real engineers don't set it up from scratch — they design it, cost it, and explain the architecture. That is exactly what this project trains.

  1. Open the AWS Direct Connect console (search "Direct Connect" in the console). Browse to Connections → Create Connection. Do not create it — just explore the form. Note the location options, speed tiers (1 Gbps, 10 Gbps), and the colocation facilities listed near your region.

    📸 Screenshot: Direct Connect creation form — explore the location and speed options. Do not click Create.

  2. On paper or in a doc, sketch this architecture: On-Premises Data Center → [Direct Connect Location colocation] → AWS DX Location → Virtual Private Gateway → VPC. Add a VPN as the backup path running in parallel. Label: which path carries normal traffic, which activates on failure, and what BGP does to switch between them.

    📸 Screenshot: Your Direct Connect + VPN failover design — document this for your portfolio

  3. Answer these questions in writing (this is the real exercise): Why is Direct Connect not encrypted? What must you add for encryption? If the fiber is cut, how long before VPN takes over? What determines which path BGP prefers? What is a Private VIF vs Public VIF?

  4. Cost estimate: Look up the Direct Connect pricing page. Calculate the monthly cost for a 1 Gbps dedicated connection in your nearest region. Compare this to running a Site-to-Site VPN at the same data volume. Document the cost difference — this is the kind of thinking engineering managers test in system design interviews.
