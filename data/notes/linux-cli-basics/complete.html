🚀 Introduction

You've launched an EC2 instance — great. But now what? You open a terminal and you're staring at a blinking cursor. No buttons. No menus. Just a prompt waiting for you to type something. This is the Linux Command Line Interface, and it's the single most powerful tool you'll use as an AWS engineer.

Figure 1: Linux CLI — your direct line to the EC2 instance

Think of the CLI like a very obedient employee who does exactly what you tell them, instantly, without question. The GUI (graphical interface) is like ordering food at a restaurant with pictures — helpful for beginners. The CLI is like texting the chef directly — faster, more precise, and more powerful.

💡 Why Linux on AWS? Over 70% of EC2 instances run Linux. It's lightweight, free, highly customizable, and purpose-built for servers. Almost every DevOps, cloud, and backend engineering role requires Linux CLI skills.

In this session, we're going to cover the foundational Linux commands that every AWS engineer uses every single day — right on a real EC2 instance. By the end, you'll be able to navigate directories, create and delete files and folders, inspect your system, and understand exactly what's happening inside your EC2 terminal.

⚡ Session Context: This session was taught on a live EC2 instance (Amazon Linux 2, instance ID: i-0d9aa3a731ab9fdeb). The commands shown are the exact same ones you'll use in real AWS environments.

🐧 What is the Linux CLI?

The CLI (Command Line Interface) is a text-based interface where you interact with the operating system by typing commands. There's no mouse, no icons, no windows — just you, the keyboard, and the terminal.

Figure 2: GUI vs CLI — two ways to talk to your computer

Anatomy of a Command

Every Linux command follows this structure:

command [options] [arguments]

For example:

ls -l /home
  • ls — the command (list files)
  • -l — the option (long format)
  • /home — the argument (which directory to list)

💡 Options are also called flags. They modify how a command behaves. Most flags start with a hyphen (-). You can often combine them: ls -la is the same as ls -l -a.

The Terminal Prompt

When you SSH into an EC2 instance, you'll see a prompt like this:

[ec2-user@ip-172-31-15-240 ~]$

Let's decode it:

  • ec2-user — your username (default for Amazon Linux)
  • ip-172-31-15-240 — the hostname (your private IP in dashed format)
  • ~ — your current directory (tilde means home directory)
  • $ — indicates you're a regular user (not root). Root shows #

📸 From Session: EC2 terminal showing the history command — lists every command typed in this session

The $ symbol at the end of the prompt means you are logged in as a regular user. A # symbol means you are logged in as root.

📁 Navigation Commands

Before you can do anything useful in the terminal, you need to know where you are and how to get around. Think of the Linux filesystem like a building — you need to know which floor you're on before you can find the right room.

pwd — Print Working Directory

The very first command in the session was pwd. It answers the single most important question in the terminal: Where am I right now?

pwd

Output:

/home/ec2-user
pwd stands for Print Working Directory. It displays the absolute path of your current location in the filesystem.

💡 Absolute path means the full path from the root of the filesystem. It always starts with /. Example: /home/ec2-user — this tells you: start at root (/), go into home, then go into ec2-user.

cd — Change Directory

Once you know where you are, cd is how you move around. During the session, the instructor used cd .ssh to navigate into the SSH config folder.

cd .ssh

This takes you from /home/ec2-user into /home/ec2-user/.ssh. After running it, pwd would confirm:

/home/ec2-user/.ssh

Here are the most important cd shortcuts you need to know:

CommandWhat it does

cd ..Go up one level (parent directory)

📋 Listing Commands — ls and its Flags

After navigating to a directory, you need to see what's inside. The ls command (short for list) is the equivalent of opening a folder and looking at the contents. In the session, the instructor used four variations of ls. Let's go through each one.

Figure 4: ls command variations — each flag reveals more information

ls — Basic List

ls

Shows all visible files and folders in the current directory. Clean and simple. Hidden files (starting with .) are NOT shown.

ls -a — Show Hidden Files

ls -a

The -a flag means "all" — it shows everything, including hidden files. In Linux, any file or directory whose name starts with a dot (.) is considered a hidden file. Examples: .ssh, .bashrc, .bash_history.

You'll also see two special entries:

  • . — represents the current directory itself
  • .. — represents the parent directory

ls -l — Long Format

ls -l

This is where things get interesting. The long format gives you a detailed view of each file. Here's how to read it:

-rw-r--r-- 1 ec2-user ec2-user 1234 Oct 15 06:00 repo.txt
drwxr-xr-x 2 ec2-user ec2-user 4096 Oct 15 06:00 projects

Each column means:

ColumnMeaningExample
1st characterType: - = file, d = directoryd = directory
Permissions (9 chars)rwx for owner, group, othersrwxr-xr-x
LinksNumber of hard links2
OwnerWho owns the fileec2-user
GroupWhich group owns itec2-user
SizeFile size in bytes1234
ModifiedLast modification date/timeOct 15 06:00
NameFile or directory namerepo.txt
In ls -l output, a line starting with d is a directory, and a line starting with - is a regular file.

ls -la — Show All in Long Format

ls -la

This combines both flags — gives you the long format view of ALL files including hidden ones. This is the most complete picture of a directory's contents. You can also write it as ls -l -a. The result is identical.

✅ Best Practice: Use ls -la as your default when exploring an unfamiliar directory. It shows hidden config files, permissions, and sizes all at once — exactly what you need for security audits and debugging.

How to Tell a File from a Directory

In the session, the instructor pointed this out explicitly: the first character of ls -l output tells you the type.

  • A file like repo.txt appears as: -rw-r--r-- (starts with -)
  • A directory like projects appears as: drwxr-xr-x (starts with d)

The instructor also noted: a file with size 0 in ls -l output is an empty file — it exists but contains no data.

📂 Directory Management — mkdir and rmdir

Now that you can navigate and list, let's start creating structure. The mkdir command is how you create folders in Linux — it's short for "make directory."

mkdir — Create a Directory

mkdir foldername

This creates a single directory in your current location. Simple and immediate.

Example:

mkdir reports

Now ls will show a new directory called reports.

mkdir -p — Create Nested Directories

This was one of the key teaching moments in the session. The instructor demonstrated creating a deep folder structure in one single command using the -p flag.

mkdir -p projects/2025/January

Without -p, this would fail if projects doesn't exist yet. With -p, Linux creates every missing folder in the path automatically — parent first, then children.

Figure 5: mkdir -p creates the entire directory tree in one command

mkdir -p creates nested (parent) directories in a single command. If the parent directory already exists, it will not throw an error — it simply continues.

💡 The -p stands for "parents." Without it, mkdir projects/2025/January would fail with "No such file or directory" if projects or 2025 don't exist yet.

The instructor also showed that if you run the same mkdir -p command again on an existing path, it does nothing — no error, no duplication. It simply checks: does this exist? Yes → move on.

After running mkdir -p projects/2025/January, the session verified it worked:

cd projects
ls         # shows: 2025
cd 2025
ls         # shows: January

⚡ You can also navigate the full path directly without cd-ing one level at a time: cd projects/2025 takes you there in one command.

rmdir — Remove an Empty Directory

To delete an empty directory, use rmdir:

rmdir foldername

❌ Important: rmdir only works on empty directories. If the directory contains any files or subdirectories, the command will fail with: rmdir: failed to remove 'foldername': Directory not empty.

rmdir can only delete empty directories. To delete a directory that has contents, you need rm -r (recursive).

Example from the session:

rmdir 123

After this, ls confirmed the directory was gone.

💡 According to AWS documentation, when working in EC2 environments, always verify directory deletion with ls immediately after rmdir to confirm the operation succeeded. 📚 Source: AWS EC2 Linux Docs

📄 File Management — rm

Creating directories is one thing — managing files is another. The rm command is the primary tool for deleting files in Linux. During the session, the instructor demonstrated removing a file called repo.txt.

rm — Remove a File

rm filename

Example:

rm repo.txt

After this, ls confirmed the file was gone.

❌ Critical Warning: rm deletes files permanently. There is no Recycle Bin, no Trash, no Undo. Once deleted, the file is gone. Always double-check the filename before pressing Enter.

Figure 6: Choosing the right delete command

rm Variations You Must Know

CommandWhat it doesUse Case
rm filenameDelete a single fileDelete any file (empty or not)
rm -r foldernameDelete directory and all contents recursivelyDelete non-empty directories
rm -f filenameForce delete without promptingSkip confirmation (use carefully!)
rm -rf foldernameForce delete recursively — no promptsNuke a directory completely
rm *.txtDelete all .txt files in current directoryBulk delete by extension

❌ Never run: rm -rf / or rm -rf /*. This attempts to delete everything on the entire system. It is irreversible and catastrophic.

✅ Best Practice: Before running rm, always run ls first to confirm the filename. Better yet, for important deletions, use rm -i which prompts you for confirmation before deleting each file.

🛠️ Utility Commands — cat, clear, history

These three commands appeared in the EC2 session history and are everyday tools you'll use constantly.

cat — Concatenate and Display File Contents

cat filename

In the session, the instructor used cat authorized_keys inside the .ssh directory. This displayed the contents of the authorized SSH public keys file directly in the terminal.

cat is short for "concatenate." Its primary job is to print file contents to the screen — perfect for quickly reading small files without opening an editor.

cat authorized_keys     # read the SSH authorized keys file
cat /etc/os-release     # see which Linux distro you're running
cat repo.txt            # read any text file
The cat command displays the full contents of a file directly in the terminal. It does not open an editor — it just prints the output.

💡 cat for multiple files: cat file1 file2 prints both files one after the other. cat file1 file2 > combined.txt merges them into a new file. This is where "concatenate" actually comes in.

clear — Clear the Terminal Screen

clear

Clears all text from the visible terminal window. It doesn't delete your command history — it just gives you a clean workspace. The shortcut Ctrl + L does the same thing.

💡 clear only clears the screen — it doesn't remove anything from history. You can always scroll up to see previous output, or run history to see all past commands.

history — View Command History

history

This is exactly what was shown in the session screenshot. It lists all commands you've typed in this terminal session (and previous sessions), numbered in order.

📸 From Session: The history output showing all 13 commands from this EC2 session — exactly what the instructor ran during the Oct 15 class

Key things you can do with history:

CommandWhat it does
historyShow all commands
history 10Show last 10 commands only
!5Re-run command number 5
!!Re-run the last command
Ctrl + RSearch through history interactively
history -cClear the entire history
Linux command history is stored in a file called .bash_history in the home directory. It persists across terminal sessions.

🌳 Understanding the Linux Filesystem

To be effective at the CLI, you need a mental map of Linux's directory structure. Unlike Windows which has C:\, D:\ etc., Linux has one unified tree starting from / (called "root").

Figure 7: The Linux Filesystem Hierarchy — one tree, everything inside it

DirectoryWhat's in itAWS Relevance
/Root of everythingAll paths start here
/homeUser home directories/home/ec2-user is where you land on EC2
/etcConfig files for the system/etc/ssh/sshd_config — SSH server config
/varVariable data (logs, caches)/var/log/ — where application logs live
/tmpTemporary filesCleared on reboot — never store important data here
/usrUser programs and binariesMost installed software goes here
/binEssential system binariesls, pwd, cd all live here
The Linux filesystem starts at root (/). Every file and directory exists somewhere under this single root. There are no drive letters like Windows.

💡 Tilde (~) shortcut: In Linux, ~ is a shortcut for your home directory. So ~/projects is the same as /home/ec2-user/projects. It works in any command: cd ~/projects, ls ~/, etc.

Absolute vs Relative Paths

This is a concept that trips up many beginners, so let's make it crystal clear:

Path TypeDefinitionExample
AbsoluteFull path from root — always starts with //home/ec2-user/projects/2025
RelativePath from your current location — no leading /projects/2025 (if you're in /home/ec2-user)
An absolute path always starts with / and works from anywhere. A relative path is based on your current working directory.

🔐 Hidden Files and the .ssh Directory

During the session, the instructor navigated into .ssh and used cat authorized_keys. This is a critical AWS concept — understanding how SSH authentication actually works on EC2.

What is the .ssh Directory?

The .ssh directory lives in your home folder at /home/ec2-user/.ssh. It's hidden (starts with a dot) and contains everything related to SSH authentication.

FilePurpose
authorized_keysList of public keys allowed to log in as this user
id_rsaYour private key (if generated on this machine)
id_rsa.pubYour public key
known_hostsList of servers you've connected to before
configSSH client configuration

Figure 8: How SSH key authentication works — public key on EC2, private key on your machine

The Key Pair Question from Class

A student asked: "If I lose my private key, what happens?" The instructor's answer was clear and important:

❌ If you lose your private key, you cannot SSH into the EC2 instance. AWS does not store your private key — you are responsible for keeping it safe. The only recovery option is to create a new instance.

A student also had trouble connecting using PuTTY. The issue was file format:

⚡ PuTTY Key Format: AWS provides key pairs in .pem format. PuTTY requires keys in .ppk format. You must convert .pem to .ppk using PuTTYgen before connecting.

📝 Overall Summary

  • pwd: Always know where you are — pwd prints your current directory path.
  • ls and its flags: ls shows visible files, ls -a includes hidden, ls -l shows permissions and metadata, ls -la shows everything.
  • cd navigation: Use cd foldername to enter a directory, cd .. to go up one level, and cd ../../.. to go up multiple levels.
  • Hidden files: Any file or directory starting with a dot (.) is hidden in Linux. The .ssh folder holds SSH authentication keys.
  • mkdir: Creates a single directory. Use mkdir -p to create an entire nested directory tree in one command.
  • rmdir: Deletes empty directories only. If the directory has contents, it will fail.
  • rm: Permanently deletes files — no undo. Use rm -r for non-empty directories. Use with caution.
  • cat: Reads and displays file contents in the terminal. Does not open an editor.
  • clear: Clears the visible screen without deleting history.
  • history: Lists all commands run in this and previous sessions, stored in .bash_history.

Project 5: Log Inspector — Simulated Server Debugging

🎯 Objective: Simulate a real debugging scenario — create fake application logs using echo, grow them with >>, read them with cat, and use history to audit every action taken. This is what engineers do every day when something breaks on a server.

⏱️ Time: 25–35 min

💰 Cost: Free tier

On a real server, when something breaks, the first thing you do is check the logs. Here's how to simulate that entire workflow from the CLI.

  1. Create the log directory structure:

    mkdir -p server/logs

  2. Write the first log entry using echo and > — simulating server startup:

    echo "2025-10-15 06:00:00 INFO  Server started successfully" > server/logs/app.log

    The > operator creates the file and writes the output into it. If the file already exists, it overwrites it completely.

  3. Append more log entries over time using >>:

    echo "2025-10-15 06:01:15 INFO  User login: admin" >> server/logs/app.log
echo "2025-10-15 06:02:30 ERROR Database connection failed" >> server/logs/app.log
echo "2025-10-15 06:02:35 WARN  Retrying database connection..." >> server/logs/app.log
echo "2025-10-15 06:02:40 INFO  Database connection restored" >> server/logs/app.log
echo "2025-10-15 06:05:00 ERROR Disk space below 10%" >> server/logs/app.log

    The >> operator appends to the file. Existing content is never touched — the new line is added at the bottom. This is exactly how real application logs grow.

    📸 Screenshot: echo >> appending to app.log — each line adds to the file without overwriting

  4. Read the full log file to review all events:

    cat server/logs/app.log

    📸 Screenshot: cat app.log — all six log entries visible in chronological order

  5. Check the log file size with ls -l to confirm all entries were written:

    ls -l server/logs/

    A non-zero byte count confirms the file has content. A zero-byte size means the write failed — always check.

    📸 Screenshot: ls -l on the logs folder — non-zero size confirms all entries are inside

  6. Create a separate error-only log to simulate log separation:

    echo "2025-10-15 06:02:30 ERROR Database connection failed" > server/logs/error.log
echo "2025-10-15 06:05:00 ERROR Disk space below 10%" >> server/logs/error.log
cat server/logs/error.log

  7. Use history to review every command run during this debugging session — your audit trail:

    history

    📸 Screenshot: history — a complete audit trail of every action taken this session

  8. Clean up:

    rm -r server
ls

✅ What you practised: Creating files with echo >, appending with echo >>, reading with cat, verifying size with ls -l, and using history as an audit trail. These are core server debugging skills used daily in production.

⚡ Key rule to remember: > overwrites every time. >> adds to the end without touching existing content. For logs, always use >> — never >.

💡 Real-world context: On a production EC2 instance, application logs live in /var/log/. You would use cat on those files the exact same way. The commands are identical — only the path changes.

Project 6: Mistake Simulator — Learn by Breaking Things

🎯 Objective: Intentionally run wrong commands, read the error messages carefully, understand what went wrong, and fix it. The fastest way to stop fearing the CLI is to deliberately break things in a safe environment and see that they are recoverable.

⏱️ Time: 20–30 min

💰 Cost: Free tier

Most beginners fear error messages. Engineers read them. Every error message tells you exactly what went wrong — if you know how to read it. Let's practise that deliberately.

  1. Set up a safe sandbox:

    mkdir -p sandbox/test1/test2
echo "hello" > sandbox/test1/file.txt
ls -la sandbox/

    📸 Screenshot: sandbox created — a safe space to intentionally make mistakes

  2. Mistake 1 — Try to cd into a file:

    cd sandbox/test1/file.txt

    Error: bash: cd: sandbox/test1/file.txt: Not a directory

    What it means: file.txt is a file, not a directory. You can only cd into directories. Fix: use cd sandbox/test1 instead.

    📸 Screenshot: "Not a directory" — cd only works on directories, not files

  3. Mistake 2 — Try rmdir on a non-empty directory:

    rmdir sandbox

    Error: rmdir: failed to remove 'sandbox': Directory not empty

    What it means: sandbox contains files and subdirectories. rmdir refuses. Fix: use rm -r sandbox instead.

    📸 Screenshot: rmdir fails on non-empty directories — this is a safety feature, not a bug

  4. Mistake 3 — Try to cat a directory:

    cat sandbox/test1

    Error: cat: sandbox/test1: Is a directory

    What it means: cat reads files. test1 is a directory. To see what's inside a directory, use ls.

  5. Mistake 4 — Try mkdir without -p for a nested path that has no parents yet:

    mkdir newproject/src/components

    Error: mkdir: cannot create directory 'newproject/src/components': No such file or directory

    What it means: newproject doesn't exist yet. Without -p, mkdir won't create parents automatically. Fix: add -p.

    mkdir -p newproject/src/components
ls newproject/src/

    📸 Screenshot: Without -p it fails; with -p it works — the fix is one flag

  6. Mistake 5 — Try to delete a file that doesn't exist:

    rm sandbox/test1/ghost.txt

    Error: rm: cannot remove 'sandbox/test1/ghost.txt': No such file or directory

    What it means: The file doesn't exist. Check the real filename with ls sandbox/test1/ first before deleting.

  7. Clean up all experiment directories:

    rm -r sandbox
rm -r newproject
ls

    📸 Screenshot: Clean slate — both sandbox and newproject gone. ls confirms empty home.

✅ Error messages decoded: "Not a directory" → you used cd on a file. "Directory not empty" → use rm -r. "No such file or directory" → check the path with ls first. Read all three parts of every error — [command]: [what failed]: [reason] — and the fix becomes obvious.

⚡ Engineer mindset: Beginners panic at errors. Engineers treat errors as feedback. Every error message in Linux tells you exactly what went wrong. Your only job is to read it.
