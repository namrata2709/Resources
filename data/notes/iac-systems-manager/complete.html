🌟 Introduction

Imagine you're building a house. Every time you want a new house in a new city, you call contractors, buy materials, coordinate everything yourself — from scratch — every single time. That's exhausting, slow, and error-prone. Now imagine instead you write down exactly how your house should be built in a detailed blueprint. You hand that blueprint to any builder, anywhere, and they construct the exact same house — every time, without mistakes.

That's exactly what Infrastructure as Code (IaC) does for your cloud environment. Instead of manually clicking through the AWS Console to create servers, databases, and networks, you write a code file that describes everything you want. You hand that file to an IaC tool, and it builds your entire cloud infrastructure automatically — the same way, every time.

Figure 1: How IaC turns code into cloud infrastructure automatically

In this session, we cover two major topics. First, Infrastructure as Code — what it is, why it exists, and which tools AWS provides (CloudFormation, Terraform, Ansible). Second, AWS Systems Manager — a powerful service that lets you manage hundreds of servers from one place, connect to servers without SSH keys, store secrets securely, run commands at scale, and keep software up to date automatically.

⚡ Why this matters: In real-world cloud engineering, you almost never create resources manually. IaC and Systems Manager are the two pillars that let teams move fast, stay consistent, and recover from disasters in minutes instead of days.

🏗️ What is Infrastructure as Code (IaC)?

Before IaC existed, cloud engineers would log into the AWS Console, click through menus, and manually configure every resource — EC2 instances, VPCs, security groups, S3 buckets, databases — one by one. This worked for small setups, but it created serious problems at scale.

The Problem with Manual Setup

Think about cooking biryani from memory. You might forget an ingredient one day or add too much spice the next. The result is never quite the same. Manual infrastructure suffers the same problem — each engineer sets things up slightly differently, and your environments never match exactly. Now imagine you have a proper recipe. Anyone can follow it and produce the identical dish every time. That's the IaC philosophy.

Figure 2: Manual setup vs IaC — consistency wins every time

Infrastructure as Code (IaC) is the practice of defining and managing cloud infrastructure using code files instead of manual console actions. The code describes what resources you want, and an IaC tool reads that code and creates everything automatically in your AWS account.

Declarative vs Imperative

When you write your infrastructure as code, you can do it in one of two styles — and this is an important concept:

Figure 3: Declarative vs Imperative — two ways to describe what you want

Declarative means you describe your final desired state — what you want to exist — without specifying the exact steps to get there. It's like telling a builder: "I want a G+2 house with a penthouse." You state what you want; the tool figures out how to build it.

Imperative means you write the exact step-by-step instructions in order — first lay the foundation, then build the walls, then add the roof. You control every action.

💡 Key insight: AWS CloudFormation and Terraform are primarily declarative — you say what you want, and they handle how. Ansible can be both, but leans imperative when writing playbook tasks. Most modern IaC tools prefer declarative because it's simpler and less error-prone.

🔧 Problems IaC Solves

IaC isn't just a nicer way to work — it solves real, painful problems that every cloud team runs into. Here are the five core problems it addresses:

Figure 4: Five critical problems solved by IaC

Problem 1: Environment Inconsistency

You set up a development environment perfectly — it works. Your teammate tries to set up the same thing and gets different results. This happens all the time with manual setups because each person configures things slightly differently.

IaC solution: Everyone uses the same code file. The same code = the same output, every time, on any machine. IaC ensures environment consistency — dev, test, and production are built from identical code, eliminating the "it works on my machine" problem.

Problem 2: Disaster Recovery

Imagine you've spent weeks building a complex AWS setup — VPCs, EC2s, IAM roles, S3, Route 53, databases. Then your AWS account gets deleted or corrupted. Without IaC, you're rebuilding from memory, hoping you remember every configuration detail. With IaC, you run the code file again and your entire infrastructure is recreated automatically in minutes.

IaC enables fast disaster recovery — if infrastructure is lost, you simply re-run the code and everything is recreated identically.

Problem 3: Cross-Environment Differences

Your application works perfectly in development but breaks in production. Why? Because the two environments were configured differently by different people. IaC fixes this by using the same template for all environments — dev, test, and prod are built from the same blueprint, so they're always identical.

Problem 4: No Audit Trail

When you click through the console, there's no easy record of what changed, when, and why. With IaC, your code lives in a version control system like Git. Every change is tracked, who made it, and when — you get a full audit trail of your infrastructure history.

IaC integrates with version control systems like Git, providing a complete audit trail of all infrastructure changes.

Problem 5: Time-Consuming Manual Work

Setting up resources manually for the development team, then doing it again for the testing team, then again for production is never-ending repetitive work. IaC code is reusable — write it once, run it for every team, every environment, every region.

✅ Real-world practice: In production cloud environments, teams almost never create resources manually. Every resource — from a single EC2 instance to a full multi-region architecture — is defined in code and deployed via IaC tools.

🛠️ IaC Tools — Cloud-Specific vs Multi-Cloud

There are many IaC tools available, and they fall into two broad categories: tools that work with one cloud provider only, and tools that work across multiple clouds.

Figure 5: IaC tools — cloud-specific vs multi-cloud

Cloud-Specific IaC Tools

These tools are native to their respective cloud and only work within that cloud environment. Think of them as each cloud provider's native language:

  • AWS CloudFormation — Works only with AWS. The native IaC tool for AWS services. Code is written in YAML or JSON format.
  • Azure Resource Manager (ARM) — Works only with Microsoft Azure. Uses JSON-based ARM templates.
  • Google Cloud Deployment Manager — Works only with Google Cloud Platform (GCP). Uses YAML configuration files.

Multi-Cloud IaC Tools

These tools can provision resources across multiple cloud providers — AWS, Azure, GCP, and many others — using a single tool and workflow:

  • Terraform (by HashiCorp) — The most widely used multi-cloud IaC tool. Terraform uses HCL (HashiCorp Configuration Language) to define infrastructure, and supports AWS, Azure, GCP, and hundreds of other providers.

  • Pulumi — Similar to Terraform in multi-cloud support, but lets you write infrastructure code in familiar programming languages like Python, TypeScript, Go, and C# instead of a special configuration language.

💡 Which to use? If you're working exclusively in AWS, CloudFormation is a strong native choice — it's deeply integrated with AWS services. If your company uses multiple clouds or wants more flexibility, Terraform is the industry standard.

Configuration Management Tools (Ansible, Chef, Puppet)

There's a third category of tools that often get grouped with IaC but serve a different purpose: configuration management tools. While CloudFormation and Terraform create and manage infrastructure (the servers, networks, databases), configuration management tools manage what's running inside those servers — installing software, changing configuration files, keeping packages updated.

Figure 6: Ansible master-agent architecture — push-based configuration management

Ansible is the most popular configuration management tool. Here's how it works:

  1. You install Ansible on one server — your master (control node). Target servers need no special software installed.
  2. You create an inventory file listing the IP addresses of all servers you want to manage.
  3. You write playbooks — YAML files containing tasks (e.g., install nginx, update a config file, restart a service).
  4. Ansible pushes these tasks to all target servers over SSH, executes them, and reports results.

Ansible is agentless — target servers do not need any Ansible software installed; only the master/control node runs Ansible.

Ansible is a push-based tool — the master actively pushes commands to target servers.

In contrast, Chef and Puppet are pull-based — the target servers must periodically reach out to the Chef/Puppet server to pull and apply updates. This means agents must be installed on every target server.

⚡ The right tool for the right job: Use Terraform/CloudFormation to create your EC2 instances, VPCs, and databases. Then use Ansible to configure the software inside those EC2 instances — install packages, write config files, manage services. They complement each other perfectly.

☁️ AWS CloudFormation — Deep Dive

CloudFormation is AWS's native IaC tool. It lets you describe your entire AWS infrastructure in a text file (a template), and AWS builds everything for you automatically — EC2 instances, VPCs, S3 buckets, IAM roles, databases, and more — all from that single file.

Think of CloudFormation as giving AWS a blueprint. AWS reads the blueprint and constructs everything exactly as described.

Figure 7: How CloudFormation works — from template to stack

Key Concepts: Templates and Stacks

A template is the blueprint — a YAML or JSON file that describes the resources you want to create.

A stack is the actual collection of AWS resources created from a template. When you submit a template to CloudFormation, it creates a stack. All resources in that stack are managed together — create, update, or delete the stack and all its resources change together.

Template Structure

A CloudFormation template has several sections. Only Resources is mandatory — everything else is optional:

AWSTemplateFormatVersion: '2010-09-09' # Optional: template version
Description: My web application infrastructure # Optional: human-readable description

Parameters: # Optional: input values passed at creation time
  InstanceType:
    Type: String
    Default: t3.micro
    AllowedValues:
      - t3.micro
      - t3.small
      - t3.medium
    Description: EC2 instance type to use

Mappings: # Optional: lookup tables (e.g. AMI IDs per region)
  RegionMap:
    us-east-1:
      AMI: ami-0abcdef1234567890
    ap-south-1:
      AMI: ami-0fedcba9876543210

Resources: # MANDATORY: defines all resources to create
  MyWebServer:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: !FindInMap [RegionMap, !Ref AWS::Region, AMI]
      InstanceType: !Ref InstanceType
      Tags:
        - Key: Name
          Value: WebServer

  MyBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Sub '${AWS::StackName}-${AWS::AccountId}'

Outputs: # Optional: values to display after stack creation
  ServerPublicIP:
    Description: Public IP of the web server
    Value: !GetAtt MyWebServer.PublicIp

💡 According to AWS documentation, the Resources section is the only required section in a CloudFormation template. Every other section — Parameters, Mappings, Outputs, Metadata — is optional but extremely useful for building flexible, reusable templates.
📚 Source:AWS CloudFormation Template Anatomy Docs

Parameters — Making Templates Flexible

Hard-coding values directly into a template (like InstanceType: t3.micro) makes the template rigid — it can only ever create one instance type. Parameters solve this by letting you pass values in when you create the stack.

CloudFormation Parameters allow you to pass custom values into a template at stack creation time, making the same template reusable for different configurations.

Example: Instead of InstanceType: t3.micro, you use InstanceType: !Ref InstanceTypeParam. Now when you create the stack, you can specify t3.micro for dev, t3.medium for test, and t3.large for production — all using the same template.

Outputs — Exposing Stack Results

After a stack is created, you often need to know specific values — the public IP of an EC2 instance, the URL of a load balancer, the name of an S3 bucket. The Outputs section lets you declare these values, and they appear in the CloudFormation console under the stack's Outputs tab.

Mappings — Region-Aware Templates

AMI IDs are different in every AWS region. Mappings let you create lookup tables inside your template. For example, you can map each region to the correct AMI ID, and CloudFormation will automatically use the right one depending on where you deploy the stack.

Infrastructure Composer — Visual Template Builder

Don't know how to write YAML or JSON from scratch? CloudFormation includes a built-in visual builder called Infrastructure Composer. You drag and drop AWS service icons onto a canvas, connect them, and Infrastructure Composer automatically generates the correct YAML/JSON template for you.

✅ Best practice: Always validate your template before deploying. CloudFormation's built-in validator catches syntax errors and missing required fields before you waste time waiting for a failed stack creation. In the Infrastructure Composer, click "Validate" before creating the stack.

How to Create a Stack — Step by Step

  1. Go to AWS Console → CloudFormation → Create Stack → With new resources
  2. Provide your template: upload from your computer, reference an S3 URL, or build with Infrastructure Composer
  3. Give the stack a name (this becomes part of resource names if you use !Sub '${AWS::StackName}')
  4. Fill in any Parameter values if your template uses them
  5. Add optional tags, IAM permissions, and rollback settings
  6. Review and submit — CloudFormation creates all resources and shows real-time events

💡 Rollback on failure: By default, if any resource fails to create, CloudFormation automatically rolls back and deletes all resources it had already created. This prevents partial, broken states.


📚 Source:AWS CloudFormation Rollback Docs

CloudFormation Exam Tips

  • CloudFormation is a free service — you pay only for the AWS resources it creates, not for CloudFormation itself.
  • Templates are stored in S3 automatically when you upload them through the console
  • All resources in a stack are managed together — deleting a stack deletes all its resources.
  • CloudFormation uses change sets to preview what will change before you update a stack

🌍 Terraform — Multi-Cloud IaC

While CloudFormation is powerful for AWS-only environments, Terraform by HashiCorp has become the industry standard for multi-cloud infrastructure management. If your company uses AWS alongside Azure or GCP, or if you want a consistent IaC experience regardless of cloud provider, Terraform is the go-to tool.

Figure 8: Terraform works across AWS, Azure, GCP, and 1000+ other providers

Terraform uses HCL (HashiCorp Configuration Language) to define infrastructure, which is a human-readable, declarative configuration language specifically designed for infrastructure.

A basic Terraform configuration to create an EC2 instance looks like this:

provider "aws" {
  region = "us-east-1"
}

resource "aws_instance" "web_server" {
  ami           = "ami-0abcdef1234567890"
  instance_type = "t3.micro"

  tags = {
    Name = "WebServer"
  }
}

Terraform Core Workflow

  1. terraform init — Downloads required provider plugins (e.g. the AWS provider)
  2. terraform plan — Shows you exactly what will be created, changed, or destroyed — before doing anything
  3. terraform apply — Executes the plan and creates/updates resources
  4. terraform destroy — Destroys all resources defined in the configuration

Terraform maintains a state file (terraform.tfstate) that tracks the current state of your infrastructure, allowing it to detect what needs to change on subsequent runs.

🖥️ AWS Systems Manager (SSM)

Once you've used IaC to create your infrastructure — your EC2 instances, VPCs, databases — you need a way to manage everything that's now running. If you have 5 servers, managing them manually is annoying. If you have 50 or 500 servers, it's impossible.

That's where AWS Systems Manager (SSM) comes in.

AWS Systems Manager is a unified management platform that lets you view, control, and automate operations across your AWS infrastructure — and even on-premises servers — from a single interface.

Think of it like a central control room for a fleet of cars. Instead of physically checking each car one by one, you have a dashboard where you can see all cars, send commands to all of them at once, schedule maintenance automatically, and securely access any car without needing a physical key.

Figure 9: AWS Systems Manager and its five core sub-services

The SSM Agent — How SSM Talks to Your Servers

For Systems Manager to manage an EC2 instance, two things must be true:

  1. The EC2 instance must have the SSM Agent installed and running
  2. The EC2 instance must have an IAM role with the AmazonSSMManagedInstanceCore policy attached

The SSM Agent is software that must be installed on each EC2 instance (or on-premises server) for Systems Manager to manage it. It acts as a messenger between the instance and Systems Manager.

The SSM Agent is pre-installed by default on Amazon Linux 2, Amazon Linux 2023, Amazon ECS-optimized AMIs, and Windows Server AMIs provided by AWS.

To check if the SSM Agent is installed and running on a Linux instance:

sudo systemctl status amazon-ssm-agent

To install it manually on Amazon Linux 2:

sudo yum install -y amazon-ssm-agent
sudo systemctl enable amazon-ssm-agent
sudo systemctl start amazon-ssm-agent

💡 IAM Role required: The SSM Agent alone isn't enough. The EC2 instance needs permission to communicate with the Systems Manager service. Attach the AWS managed policy AmazonSSMManagedInstanceCore to an IAM role, then attach that role to your EC2 instance. Without this role, the instance won't appear in Systems Manager even if the agent is installed.

🔐 Session Manager — Secure Server Access Without SSH

Here's a common real-world scenario: your production EC2 instances are in a private subnet with no public IP address and no inbound security group rules. How do you connect to them for troubleshooting?

Traditionally, you'd need a bastion host (a jump server in the public subnet that you SSH into first, then hop to the private instance). But bastion hosts require maintenance, cost money, and create their own security risks. SSH keys also need to be managed and distributed securely.

Session Manager solves all of this.

Session Manager allows you to connect to EC2 instances through a browser-based shell or CLI without needing SSH keys, open inbound ports, or a bastion host.

Figure 10: Session Manager — connect to private instances without SSH keys or open ports

How Session Manager Works

  1. The EC2 instance has the SSM Agent installed and running
  2. An IAM role with AmazonSSMManagedInstanceCore is attached to the EC2 instance
  3. You go to AWS Console → Systems Manager → Session Manager → Start Session
  4. Select your instance — Systems Manager opens a browser-based terminal directly into the instance
  5. No SSH key, no port 22, no public IP required

Why This Matters in Real-World Teams

In professional cloud environments, sharing SSH keys among team members is a security risk. When a team member leaves, you need to revoke their key access across all servers — tedious and error-prone.

With Session Manager, instead of distributing SSH keys, you create each team member as an IAM user with EC2 and Systems Manager permissions. They log into the AWS Console with their own credentials and use Session Manager to connect. When someone leaves, you simply deactivate their IAM user — access to all servers is revoked instantly.

✅ Security best practices with Session Manager:
• No need to open port 22 (SSH) in security groups — keep it closed
• No SSH keys to distribute, rotate, or revoke
• Session logs can be automatically saved to S3 or CloudWatch for audit compliance
• Access is controlled through IAM, not server-level keys
• Works even for instances in completely private subnets with no internet access

Fleet Manager — See All Your Nodes

The Fleet Manager is a sub-service of Systems Manager that shows you all EC2 instances (and on-premises servers) that have the SSM Agent installed and are reporting in. From Fleet Manager, you can see inventory details, browse the file system, manage users, and check the status of all managed instances from one dashboard.

💡 According to AWS documentation, each managed instance that appears in Fleet Manager is called a managed node. An instance qualifies as a managed node when it has the SSM Agent running and the correct IAM permissions.
📚 Source:AWS Fleet Manager Docs

⚡ Run Command — Execute Commands on All Servers at Once

You have 50 EC2 instances and you need to create a directory, install a package, or update a configuration file on all of them. Without Systems Manager, you'd need to SSH into each server individually and run the command 50 times. With Run Command, you run it once and Systems Manager executes it on all 50 instances simultaneously.

Run Command allows you to execute shell commands, scripts, or predefined SSM Documents on one or many managed instances simultaneously, without SSH access.

Figure 11: Run Command — one command, many servers, instant results

How to Use Run Command

  1. Go to Systems Manager → Run Command → Run a Command
  2. Choose a Document — AWS provides pre-built documents for common tasks. For custom shell commands, choose AWS-RunShellScript
  3. Write your shell commands in the command input box
  4. Select your targets: manually pick instances, or use tags (e.g., all instances tagged Project: myapp)
  5. Optionally, save command output to an S3 bucket for auditing
  6. Click Run — Systems Manager executes on all targets and shows success/failure per instance

Smart Targeting with Tags

In real environments, you don't manually select 50 servers every time you run a command. Instead, you use tags. If all your web servers are tagged Role: webserver, you target by that tag and Run Command automatically finds and executes on all matching instances — even if you add more servers later.

⚡ Example use cases for Run Command:
• Install software packages across all instances in a fleet
• Create directories or update config files across multiple servers
• Restart services on all instances after a deployment
• Collect diagnostic information from all instances at once
• Run custom scripts for maintenance or cleanup tasks

🔄 Patch Manager — Automated Security Updates

Keeping servers patched and up to date is one of the most important and tedious tasks in cloud operations. Security vulnerabilities are discovered constantly, and unpatched servers are a major attack vector. Doing this manually on dozens of servers is unsustainable.

Patch Manager automates the process of patching managed nodes with both security-related and other types of updates on a defined schedule.

How Patch Manager Works

  1. Create a Patch Baseline — defines which patches to approve and install (e.g., critical security updates only, or all available patches)
  2. Create a Maintenance Window — a scheduled time window when patching occurs (e.g., every Sunday at 2 AM)
  3. Register target instances using tags or instance IDs
  4. Patch Manager connects to each instance via the SSM Agent and applies approved patches automatically
  5. Results are logged — you can see which patches were applied, which failed, and which instances are compliant

💡 Patch scan vs install: You can configure Patch Manager in two modes — Scan (only check and report what patches are missing, without applying them) or Scan and Install (check and automatically apply approved patches). Scan mode is useful for compliance reporting; Scan and Install is used for automated maintenance.


📚 Source:AWS Patch Manager Docs

✅ Best practice: Always test patches on a dev or test environment first before scheduling them on production. Use separate patch baselines for dev and production — with production having stricter approval gates.

📋 Inventory — Know What's on Every Server

Do you know what software is installed on all your EC2 instances right now? What version of Python, what packages, what configuration files exist? Without a tool, you'd need to SSH into each server and manually check. With Systems Manager Inventory, all that data comes to you automatically.

Systems Manager Inventory collects metadata about your managed instances — including installed applications, AWS components, network configurations, and running services — and displays it in a centralized dashboard.

What Inventory Collects

  • Installed applications and their versions
  • AWS components and agents
    • Network configuration (IP addresses, subnet, VPC)
  • Running services and processes
  • Custom inventory data you define (e.g., your own tags or metadata)
  • Windows Registry data (for Windows instances)

You can configure how often inventory data is collected (every 30 minutes, hourly, daily) and where to store it (Systems Manager console, S3, or queried via AWS Config and Athena).

🔑 Parameter Store — Secure Secret Storage

Here's a dangerous anti-pattern that developers sometimes fall into — hardcoding credentials directly in application code:

# ❌ DANGEROUS — Never do this
db_password = "MySecretPassword123"
api_key = "AKIAIOSFODNN7EXAMPLE"

If this code is committed to Git, those secrets are now public forever (even deleted commits can be found in history). Even in private repositories, anyone with code access can see your production database password.

Parameter Store solves this by providing a secure, centralized place to store all your secrets, passwords, and configuration values.

AWS Systems Manager Parameter Store provides secure, hierarchical storage for configuration data management and secrets management.

Figure 12: Parameter Store — secrets stay out of your code

Parameter Types

  • String — Plain text values (non-sensitive configuration data like an environment name or region)
  • StringList — Comma-separated list of values
  • SecureString — Values encrypted using AWS KMS. Use this for passwords, API keys, and any sensitive data.

How Applications Use Parameter Store

  1. Store the secret in Parameter Store: /myapp/prod/db-password as a SecureString
  2. Your application code calls the SSM API to retrieve the value at runtime
  3. The EC2 instance's IAM role grants permission to read that specific parameter
  4. The secret is never stored in code — it's fetched dynamically each time
# Application retrieves secret at runtime — never hardcoded
import boto3

ssm = boto3.client('ssm', region_name='us-east-1')
response = ssm.get_parameter(
    Name='/myapp/prod/db-password',
    WithDecryption=True
)
db_password = response['Parameter']['Value']

💡 Parameter Store vs Secrets Manager: Parameter Store is part of Systems Manager and is free for standard parameters. AWS Secrets Manager is a separate service that adds automatic secret rotation (e.g., auto-rotate database passwords every 30 days). For basic secret storage, Parameter Store is sufficient. For automatic rotation, use Secrets Manager.
📚 Source:AWS Parameter Store Docs

✅ Security best practice: Always use SecureString type for passwords, API keys, tokens, and any sensitive data. Use IAM policies to restrict which EC2 instances or users can access which parameters — follow the principle of least privilege.

📝 Overall Summary

  • IaC (Infrastructure as Code): Managing cloud infrastructure through code files instead of manual console clicking — making it repeatable, consistent, auditable, and recoverable.
  • Declarative vs Imperative: Declarative IaC describes the desired final state; imperative IaC describes every step. CloudFormation and Terraform are declarative; Ansible playbooks can be either.
  • CloudFormation: AWS-native IaC tool. Uses YAML or JSON templates. Resources are organized into Stacks. Only the Resources section is mandatory. Parameters, Mappings, and Outputs add flexibility.
  • Terraform: Multi-cloud IaC tool using HCL. Works across AWS, Azure, GCP, and 1000+ providers. Maintains a state file to track what's deployed.
  • Ansible: Agentless, push-based configuration management tool. Manages software inside servers (packages, config files, services) using SSH. Complements, not replaces, Terraform/CloudFormation.
  • Chef & Puppet: Pull-based configuration management tools — agents on servers periodically pull updates from the master server.
  • SSM Agent: Software pre-installed on Amazon Linux 2, Amazon Linux 2023, and AWS Windows AMIs. Required for Systems Manager to manage an instance. IAM role with AmazonSSMManagedInstanceCore also required.
  • Session Manager: Connects to EC2 instances via browser without SSH keys, open ports, or bastion hosts. Access is IAM-controlled and fully auditable.
  • Run Command: Execute shell commands or scripts on multiple instances simultaneously. Target by tag for dynamic fleet management.
  • Patch Manager: Automates security patching on a schedule. Supports scan-only or scan-and-install modes. Uses patch baselines and maintenance windows.
  • Inventory: Collects and centralizes metadata about all managed instances — installed software, network config, running services.
  • Parameter Store: Secure storage for secrets and configuration. Use SecureString type (KMS-encrypted) for sensitive data. Applications retrieve secrets at runtime via API — never hardcode credentials.

Project 1: Deploy a Complete Stack with CloudFormation

🎯 Objective: Write a CloudFormation template that creates an EC2 instance and an S3 bucket, deploy it as a stack, and verify the resources were created.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier (t3.micro EC2 + S3)

  1. Open the AWS Console and navigate to CloudFormation → Create Stack → With new resources (standard).

    Figure: 📸 CloudFormation Create Stack — choose template source

  2. Select Use Infrastructure Composer. In the composer, search for and drag an AWS::EC2::Instance and an AWS::S3::Bucket onto the canvas.

    Figure: 📸 Infrastructure Composer — EC2 and S3 resources on canvas

  3. Switch to the template view (YAML tab). Edit the EC2 instance properties to set a valid AMI ID for your region and set InstanceType: t3.micro. Verify the S3 bucket has BlockPublicAcls: true.

  4. Click Validate to check for syntax errors. You should see a green validation success message.

    Figure: 📸 Template validation success — no syntax errors

  5. Click Confirm and continue to CloudFormation. On the stack details page, enter a stack name such as invent-project-stack. Click Next through all optional pages and click Submit.

  6. Watch the Events tab as CloudFormation creates your resources. Wait until the stack status shows CREATE_COMPLETE.

    Figure: 📸 Stack creation complete — all resources created successfully

  7. Go to EC2 → Instances and confirm your new instance is running. Go to S3 and confirm a new bucket was created with your stack name in the bucket name.

✅ Verification

  • Stack status: CREATE_COMPLETE
  • EC2 instance exists in the correct region
  • S3 bucket exists with the stack name prefix

Project 4: Parameterized Template — One Template, Any Environment

🎯 Objective: Refactor the Project 1 template to use Parameters so the same file can deploy a dev, test, or production environment by just changing input values.

⏱️ Time: 25–35 minutes

💰 Cost: Free tier (t3.micro)

  1. Open a text editor and create a new file called parameterized.yaml. Add the following Parameters section at the top, above Resources:

    AWSTemplateFormatVersion: '2010-09-09'
Description: Parameterized template for any environment

Parameters:
  Environment:
    Type: String
    Default: dev
    AllowedValues:
      - dev
      - test
      - prod
    Description: Target environment name

  InstanceType:
    Type: String
    Default: t3.micro
    AllowedValues:
      - t3.micro
      - t3.small
      - t3.medium
    Description: EC2 instance type

Resources:
  MyServer:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: !Ref InstanceType
      ImageId: ami-0abcdef1234567890   # Replace with a valid AMI for your region
      Tags:
        - Key: Name
          Value: !Sub '${Environment}-web-server'
        - Key: Environment
          Value: !Ref Environment

  MyBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Sub 'my-app-${Environment}-${AWS::AccountId}'

Outputs:
  ServerName:
    Value: !Sub '${Environment}-web-server'
    Description: Name tag of the created server
  BucketName:
    Value: !Ref MyBucket
    Description: Name of the created S3 bucket

  2. Go to CloudFormation → Create Stack → With new resources. Choose Upload a template file and upload your parameterized.yaml.

    Figure: 📸 Uploading the parameterized template file

  3. On the Specify stack details page, name the stack dev-stack. You will see the Parameters section automatically — CloudFormation reads your Parameters block and renders input fields. Set Environment to dev and InstanceType to t3.micro.

    Figure: 📸 Parameters rendered as input fields — Environment and InstanceType dropdowns visible

  4. Click through to Submit. Wait for CREATE_COMPLETE. Go to the Outputs tab — you should see both ServerName and BucketName displayed.

    Figure: 📸 Stack Outputs tab — both values populated from parameter substitution

  5. Now create a second stack using the exact same template file. Name it prod-stack. This time set Environment to prod and InstanceType to t3.small. Submit and wait for CREATE_COMPLETE.

  6. Go to EC2 → Instances. You should see two instances — one tagged dev-web-server and one tagged prod-web-server. Go to S3 and confirm two separate buckets exist with dev and prod in their names — all from one template file.

    Figure: 📸 Two environments created from one template — different instance types, same blueprint

✅ Verification

  • Both stacks status: CREATE_COMPLETE
  • Each stack's Outputs tab shows the correct environment name
  • EC2 instance names and types differ between environments
  • Two S3 buckets exist, each prefixed with the environment name

🧹 Cleanup

  1. CloudFormation → delete dev-stack → wait for DELETE_COMPLETE
  2. CloudFormation → delete prod-stack → wait for DELETE_COMPLETE
  3. Verify both EC2 instances and both S3 buckets are gone

Project 5: Multi-Resource Stack with Dependencies — EC2 + Security Group + S3

🎯 Objective: Build a CloudFormation stack with three connected resources — a Security Group, an EC2 instance that depends on it, and an S3 bucket — understanding how CloudFormation handles resource dependencies automatically.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier

  1. Create a new file called multi-resource.yaml with the following content. Notice how the EC2 instance references the Security Group using !Ref — CloudFormation automatically creates the Security Group first because of this dependency:

    AWSTemplateFormatVersion: '2010-09-09'
Description: Multi-resource stack with dependency handling

Parameters:
  EnvironmentName:
    Type: String
    Default: demo

Resources:

  # Resource 1: Security Group
  WebServerSG:
    Type: AWS::EC2::SecurityGroup
    Properties:
      GroupDescription: Allow HTTP traffic to web server
      SecurityGroupIngress:
        - IpProtocol: tcp
          FromPort: 80
          ToPort: 80
          CidrIp: 0.0.0.0/0
      Tags:
        - Key: Name
          Value: !Sub '${EnvironmentName}-web-sg'

  # Resource 2: EC2 Instance — DEPENDS ON Security Group above
  WebServer:
    Type: AWS::EC2::Instance
    Properties:
      InstanceType: t3.micro
      ImageId: ami-0abcdef1234567890   # Replace with valid AMI for your region
      SecurityGroupIds:
        - !Ref WebServerSG            # This creates a dependency automatically
      Tags:
        - Key: Name
          Value: !Sub '${EnvironmentName}-web-server'

  # Resource 3: S3 Bucket
  AppBucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Sub '${EnvironmentName}-app-bucket-${AWS::AccountId}'

Outputs:
  WebServerSGId:
    Value: !Ref WebServerSG
    Description: Security Group ID
  WebServerInstanceId:
    Value: !Ref WebServer
    Description: EC2 Instance ID
  AppBucketName:
    Value: !Ref AppBucket
    Description: S3 Bucket Name

  2. Go to CloudFormation → Create Stack → Upload a template file. Upload multi-resource.yaml. Name the stack multi-resource-demo. Click through and submit.

  3. While the stack is creating, watch the Events tab closely. You will see CloudFormation creates the Security Group first, then the EC2 instance (because EC2 depends on the SG via !Ref WebServerSG), and the S3 bucket in parallel. CloudFormation resolves dependencies automatically.

    Figure: 📸 Events tab — Security Group created first, EC2 and S3 created after (dependency order respected)

  4. Wait for the stack to reach CREATE_COMPLETE. Go to the Resources tab — you will see all three resources listed with their Physical IDs (actual AWS resource IDs).

    Figure: 📸 Resources tab — three resources created, all showing CREATE_COMPLETE

  5. Go to EC2 → Instances. Click your instance, then go to Security tab. Confirm the security group demo-web-sg is attached and allows port 80. This proves the dependency reference worked correctly.

✅ Verification

  • Stack status: CREATE_COMPLETE
  • Events tab shows Security Group was created before EC2 instance
  • EC2 instance has the correct Security Group attached
  • Resources tab shows all three Physical IDs

🧹 Cleanup

  1. CloudFormation → select multi-resource-demo → Delete
  2. Wait for DELETE_COMPLETE — all three resources deleted automatically

Project 7: Secrets Without Hardcoding — Parameter Store + Python

🎯 Objective: Store a database password securely in Parameter Store as a SecureString, then write a Python script running on EC2 that retrieves it at runtime using the AWS SDK — with zero hardcoded credentials anywhere in code.

⏱️ Time: 30–40 minutes

💰 Cost: Free tier (1 t3.micro + Parameter Store standard tier is free)

  1. First, store the secret. Go to Systems Manager → Parameter Store → Create parameter. Fill in:

    • Name: /myapp/prod/db-password
    • Tier: Standard
    • Type: SecureString
    • KMS key source: My current account → use the default alias/aws/ssm key
    • Value: SuperSecret@123

    Figure: 📸 Creating a SecureString parameter with KMS encryption

  2. Click Create parameter. You should see the parameter listed. Notice the value is masked — it's stored encrypted. Click the parameter name, then click Show to decrypt and view the value (this uses your KMS key).

    Figure: 📸 Parameter stored — value is masked by default, Show button reveals it

  3. Now create an IAM policy that allows reading only this specific parameter. Go to IAM → Policies → Create policy → JSON and paste:

    {
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "ssm:GetParameter",
        "ssm:GetParameters"
      ],
      "Resource": "arn:aws:ssm:*:*:parameter/myapp/prod/*"
    },
    {
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "*"
    }
  ]
}

    Name the policy ReadProdParams and create it.

  4. Create a new IAM role: IAM → Roles → Create Role → EC2. Attach both AmazonSSMManagedInstanceCore and ReadProdParams. Name the role EC2-SSM-ParamRead-Role.

  5. Launch an EC2 instance: Amazon Linux 2023, t3.micro, no key pair, IAM profile: EC2-SSM-ParamRead-Role. No public IP, no inbound security group rules. Wait 2 minutes for Fleet Manager to show it Online.

  6. Connect via Session Manager. In the terminal, verify Python 3 and boto3 are available:

    python3 --version
pip3 install boto3 --quiet

  7. Create the Python script:

    cat << 'EOF' > /tmp/fetch_secret.py
import boto3

def get_secret(param_name):
    client = boto3.client('ssm', region_name='us-east-1')  # change region if needed
    response = client.get_parameter(
        Name=param_name,
        WithDecryption=True  # Decrypts SecureString using KMS
    )
    return response['Parameter']['Value']

# Fetch the secret at runtime — it is NEVER in this code
db_password = get_secret('/myapp/prod/db-password')

print("Database password retrieved successfully.")
print(f"Password length: {len(db_password)} characters")
print("Connection string: postgresql://admin:****@db.example.com:5432/myapp")
print("(Password used internally — never printed to logs in production)")
EOF
python3 /tmp/fetch_secret.py

    Figure: 📸 Python script output — secret retrieved from Parameter Store at runtime, never hardcoded

  8. Now test that the IAM permission is scoped correctly. Try to read a parameter that doesn't exist in the allowed path:

    python3 -c "
import boto3
client = boto3.client('ssm', region_name='us-east-1')
try:
    client.get_parameter(Name='/other/secret', WithDecryption=True)
    print('ERROR: Should not have access!')
except client.exceptions.ParameterNotFound:
    print('Parameter not found (expected)')
except Exception as e:
    print(f'Access denied (expected): {type(e).__name__}')
"

✅ Verification

  • Parameter visible in Parameter Store with type SecureString
  • Value is masked by default in the console
  • Python script retrieves the value successfully using instance IAM role — no hardcoded credentials
  • Access to out-of-scope parameter paths is denied

🧹 Cleanup

  1. Parameter Store → select /myapp/prod/db-password → Delete
  2. Terminate the EC2 instance
  3. Optionally delete ReadProdParams IAM policy and EC2-SSM-ParamRead-Role
