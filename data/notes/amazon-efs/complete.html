🌟 Introduction

Picture a shared office whiteboard. Anyone in the team can walk up, read what's there, and write something new — all at the same time. There is no "my whiteboard" and "your whiteboard" — it is one shared surface for the whole team.

Now imagine you have 10 EC2 instances all running a web application. Each instance needs to read and write to the same files — configuration, uploaded content, logs. With EBS volumes, you can't do that: an EBS volume is like a personal hard drive — it can only be attached to one EC2 instance at a time (in most cases). You would need to keep copying files around between instances, which is messy, slow, and error-prone.

Amazon EFS (Elastic File System) is a fully managed, scalable NFS (Network File System) that can be mounted by multiple EC2 instances simultaneously — all reading and writing the same files at the same time.

Figure 1: Amazon EFS — multiple EC2 instances sharing the same file system simultaneously

In today's class, after deleting the EFS file system we had created earlier, we looked at what EFS actually is, why it exists, and how to create and use one. EFS is described in the console as "managed file storage for EC2" — but it is much more than that.

🔍 What is Amazon EFS?

Definition

Amazon EFS is a fully managed, elastic, POSIX-compliant file system that uses the NFSv4 protocol and automatically scales from gigabytes to petabytes without any provisioning required.

Let's unpack those terms:

  • Fully managed: AWS handles all the infrastructure — hardware, patching, replication, durability. You just mount it and use it.
  • Elastic: Storage capacity grows and shrinks automatically as you add or delete files. You never pre-allocate a fixed size.
  • POSIX-compliant: Works with standard Linux file permissions — the same chmod, chown, and directory operations your applications already use.
  • NFSv4: The protocol used to mount and communicate with the file system over the network. Any Linux instance that supports NFS can use EFS.

💡 EBS vs EFS — The Core Difference:
EBS = personal hard drive (one instance, one volume, fixed size).
EFS = shared network drive (many instances, one file system, elastic size).

EFS in the AWS Console

EFS is found as its own top-level service: search for "EFS" or "Elastic File System" in the console. It is separate from EC2, though EC2 instances are the primary consumers. In today's class, we deleted our existing EFS file system from within the EFS console itself.

🏗️ EFS Architecture

Understanding how EFS is structured internally will help you configure it correctly and troubleshoot issues.

The EFS File System

When you create an EFS file system, AWS provisions a distributed file storage system that spans multiple Availability Zones in a region. Your data is automatically replicated across AZs for high availability and durability.

Mount Targets

To connect to an EFS file system, each EC2 instance communicates through a mount target — an NFS endpoint created in a specific subnet/AZ within your VPC.

Think of a mount target as the "door" to the EFS file system in a particular AZ. You create one mount target per AZ you want to use. EC2 instances connect to the mount target in their own AZ for best performance.

Figure 3: EFS mount target architecture — one mount target per AZ within your VPC

Mount targets have their own IP address and DNS name. When you mount EFS on an EC2 instance, you use the mount target's DNS name, which resolves to the closest AZ mount target automatically.

Security Groups for EFS

Both the EC2 instance and the mount target must allow NFS traffic. EFS uses port 2049 (NFS) for all file system communication. You must add an inbound rule for port 2049 on the mount target's security group, and an outbound rule for port 2049 on the EC2 instance's security group (or use the default outbound allow-all rule).

❌ Common mistake: Forgetting to allow port 2049 in security groups is the #1 reason EFS mounts fail. Always check this first when troubleshooting.

⚡ Performance Modes

EFS offers two performance modes you choose at file system creation time. You cannot change the performance mode after creation.

General Purpose Mode

General Purpose mode is the default and recommended for most workloads — it provides the lowest latency per file operation.

Best for: web servers, content management systems, home directories, development environments. This is what you should select for the vast majority of use cases.

Max I/O Mode

Max I/O mode is optimized for workloads requiring the highest aggregate throughput — at the cost of slightly higher per-operation latency.

Best for: big data analytics, media processing, genomics workloads — use cases where hundreds of EC2 instances access the file system simultaneously and raw throughput matters more than per-file latency.

📚 According to AWS documentation, with One Zone storage class, Max I/O performance mode is not available. Only General Purpose mode is supported for One Zone file systems.
📚 Source: Amazon EFS Performance Docs

📶 Throughput Modes

Separate from performance mode, EFS also lets you control how throughput is determined.

Elastic Throughput (Recommended)

Elastic Throughput automatically scales throughput up and down based on workload demand — you pay only for what you use and never set a limit. This is the default and recommended mode for most applications that have variable or unpredictable I/O patterns.

Provisioned Throughput

Provisioned Throughput allows you to specify a fixed throughput level (in MiB/s) independent of the amount of data stored — useful when your application consistently needs high throughput even on a small file system.

Example: A video editing application stores only 50GB of files but constantly reads and writes at high speed. With Elastic Throughput, the throughput would be low because the file system is small. Provisioned Throughput lets you request more throughput than the size-based allocation would normally provide.

Bursting Throughput

Bursting Throughput operates similarly to EC2 T-class instances — you earn burst credits when the file system is idle and spend them during periods of high activity.

The base burst rate is 50 MiB/s per TiB of storage. Burst credits accumulate at 50 MiB/s per TiB when throughput is below the baseline, allowing bursts up to 100 MiB/s per TiB.

🗄️ EFS Storage Classes

EFS offers multiple storage classes to balance cost and performance, similar to how S3 has storage tiers.

Figure 5: EFS storage classes — cost vs availability tradeoff

EFS Standard

EFS Standard stores data across multiple Availability Zones for high availability and durability — the default class for frequently accessed files.

EFS Standard-IA (Infrequent Access)

EFS Standard-IA stores data in a lower-cost tier across multiple AZs — designed for files not accessed every day, with a per-request retrieval fee.

Files in Standard-IA cost significantly less per GB to store, but each time a file is read, you pay a small retrieval charge. If a file is truly infrequent-access, the storage savings outweigh the retrieval cost.

EFS One Zone

EFS One Zone stores data in a single Availability Zone — lower cost than Standard, but data is lost if the AZ fails.

Best for dev/test environments, analytics workloads, or data that can be regenerated easily. Not suitable for production data requiring high availability.

EFS One Zone-IA

The lowest-cost EFS storage class — single AZ + infrequent access pricing. Maximum savings, maximum risk. Only for data that is rarely accessed AND can be recreated if lost.

Lifecycle Management (Intelligent Tiering)

EFS supports lifecycle management policies that automatically move files between Standard and Standard-IA (or One Zone and One Zone-IA) based on how recently they were accessed.

You configure a rule like "move files not accessed in 30 days to IA" — EFS does the rest. Files are automatically moved back to Standard when they are accessed again.

✅ Cost optimization tip: Enable lifecycle management on all EFS file systems. Files you haven't touched in 30 days are typically safe to move to IA, saving up to 92% on storage costs for those files.

🛠️ Creating and Mounting EFS

Here is the end-to-end process for creating an EFS file system and mounting it on an EC2 instance.

Step 1: Create the File System

  1. Open the EFS Console (search "EFS" in the AWS Console).
  2. Click Create file system.
  3. Give the file system a Name (optional but recommended).
  4. Select your VPC.
  5. Choose Customize if you need to change performance mode, throughput mode, or storage class. Otherwise, Create accepts all defaults.
  6. Under Network access, review the mount targets that AWS creates automatically — one per AZ in your VPC.

💡 AWS automatically creates mount targets in each AZ when you create the file system. You can customize which subnets and security groups they use.

Step 2: Configure Security Groups

  1. Ensure the security group attached to the mount target allows inbound NFS (port 2049) from the EC2 instances.
  2. The EC2 instance's security group should allow outbound port 2049 (or use default outbound allow-all).

Step 3: Mount on EC2

SSH into your EC2 instance (Amazon Linux 2 or Ubuntu). Run the following commands:

# Install the NFS client (Amazon Linux 2)
sudo yum install -y nfs-utils

# Create a mount directory
sudo mkdir /mnt/efs

# Mount the EFS file system
sudo mount -t nfs4 -o nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport \
    fs-xxxxxxxx.efs.ap-south-1.amazonaws.com:/ /mnt/efs

# Verify it is mounted
df -h | grep efs

⚡ AWS Recommended Mount Helper: AWS provides the amazon-efs-utils package, which simplifies mounting with the command:
sudo mount -t efs fs-xxxxxxxx:/ /mnt/efs
It handles TLS encryption, automatic retry, and CloudWatch integration automatically.

Step 4: Make the Mount Persistent

To ensure EFS is remounted after a reboot, add an entry to /etc/fstab:

fs-xxxxxxxx.efs.ap-south-1.amazonaws.com:/ /mnt/efs nfs4 nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport,_netdev 0 0

The _netdev option tells Linux to wait for network availability before mounting — critical for cloud environments where network comes up after filesystem initialization.

🔒 EFS Security

Encryption

EFS supports both encryption at rest (using AWS KMS) and encryption in transit (using TLS).

  • Encryption at rest: Enabled at file system creation time. Cannot be enabled after creation.
  • Encryption in transit: Enabled by using the amazon-efs-utils mount helper with TLS option (tls mount flag), or by using an EFS Access Point configured to require TLS.

IAM Policies

EFS supports IAM-based authorization for NFS clients. You can create IAM policies that control which IAM users, roles, or EC2 instances can connect to the file system.

EFS Access Points

EFS Access Points are application-specific entry points into an EFS file system that enforce a specific POSIX user identity and a root directory for all connections through that access point.

Imagine you have 3 applications sharing the same EFS file system. With access points, Application A can only see its own directory and always runs as a specific user — it cannot accidentally read or write Application B's data. This is powerful multi-tenant isolation without separate file systems.

💰 EFS Pricing

EFS pricing is based on per GB per month of data stored — you pay only for what you use, with no provisioning required.

🚀 Common Use Cases

Content Management Systems

WordPress, Drupal, and similar CMS platforms store uploaded media, themes, and plugins in a shared directory. Running multiple CMS servers behind a load balancer requires all servers to access the same files — this is a classic EFS use case.

Containerized Workloads (ECS and EKS)

ECS tasks and Kubernetes pods frequently need shared persistent storage. EFS is a native persistent volume option for both ECS (via EFS volume mounts) and EKS (via the EFS CSI driver).

User Home Directories

Organizations running Linux-based development environments or Jupyter notebooks on EC2 can mount a single EFS file system as the home directory — every user's files are accessible from any instance they connect to.

Lift-and-Shift of NFS Workloads

On-premises applications that use NFS file servers can migrate directly to AWS by replacing their NFS server with an EFS file system. Minimal application code changes required.

🎓 Exam Tips

  • EFS is Linux-only — for Windows shared storage, use Amazon FSx for Windows File Server.
  • EFS uses NFSv4 protocol on port 2049 — memorize this for security group troubleshooting questions.
  • EFS scales automatically — you never provision capacity. This distinguishes it from EBS (fixed size) and FSx (provisioned).
  • Performance mode cannot be changed after the file system is created — choose General Purpose for most workloads, Max I/O for massively parallel workloads.
  • Standard-IA and One Zone-IA have per-request retrieval fees — a scenario asking "how to reduce cost on infrequently accessed files" points to EFS lifecycle management to IA classes.
  • EFS is Regional — it spans all AZs in a region by default (Standard/Standard-IA). One Zone variants are single-AZ.
  • Mount targets = one per AZ. Connect through the mount target's DNS for optimal performance.

📝 Overall Summary

  • What is EFS: Fully managed, elastic, POSIX-compliant NFS file system — multiple EC2 instances can mount and use it simultaneously.
  • Key differentiator from EBS: EFS is shared (multi-instance), elastic (auto-sizing), and multi-AZ by default. EBS is dedicated (single-instance), fixed-size, and single-AZ.
  • Protocol: NFSv4 on port 2049.
  • Mount targets: Create one per AZ in your VPC — the entry point for EC2 instances in that AZ.
  • Performance modes: General Purpose (default, low latency) or Max I/O (high throughput, higher latency). Cannot be changed after creation.
  • Throughput modes: Elastic (auto-scale, recommended), Provisioned (fixed MiB/s), or Bursting (credit-based).
  • Storage classes: Standard, Standard-IA, One Zone, One Zone-IA. Use lifecycle management to auto-tier files to IA.
  • Linux-only: Does not support Windows. Use FSx for Windows File Server for Windows workloads.
  • Pricing: Pay per GB stored. No provisioning needed. Standard-IA and One Zone-IA have retrieval fees.
  • Security: Encryption at rest (KMS) and in transit (TLS). IAM authorization. EFS Access Points for per-app isolation.

Project 1: Shared Files Between Two EC2 Instances

🎯 Objective: Create an EFS file system, mount it on two EC2 instances, write a file on Instance 1, and read it from Instance 2 — proving shared concurrent access.

⏱️ Time: 30-40 min

💰 Cost: EFS Standard ~$0.36/GB-month. Delete immediately after. A near-empty test costs less than $0.01.

💰 Cost Note: EFS is not Free Tier eligible. Delete the file system immediately after completing this project.

  1. Open the EFS Console. Click Create file system. Name = my-shared-fs. Select your VPC. Click Create.

    📸 Screenshot: EFS Create file system dialog — name and VPC

  2. Click the file system ID → Network tab. Verify mount targets exist and show Available state. Note the mount target DNS.

    📸 Screenshot: EFS Network tab — mount targets Available in each AZ

  3. Update the mount target's security group: add inbound TCP port 2049 from the EC2 instances' security group.

  4. SSH into Instance 1. Install NFS client and mount:

    sudo yum install -y nfs-utils
sudo mkdir /mnt/efs
sudo mount -t nfs4 -o nfsvers=4.1   fs-xxxxxxxx.efs.YOUR-REGION.amazonaws.com:/ /mnt/efs
df -h

    📸 Screenshot: df -h on Instance 1 — EFS mounted at /mnt/efs

  5. On Instance 1, write a test file: echo "Hello from Instance 1 - $(date)" | sudo tee /mnt/efs/shared-test.txt

  6. SSH into Instance 2. Repeat mount steps. Then read the file: cat /mnt/efs/shared-test.txt

    📸 Screenshot: Instance 2 reads the file written by Instance 1 — shared storage confirmed

✅ What you proved: Both instances access identical files in real time. This is what makes EFS different from EBS — one file system, many readers and writers simultaneously.

🧹 Cleanup: sudo umount /mnt/efs on both instances. EFS Console → select file system → Delete → confirm.

Project 2: Auto-Mount EFS at Boot with /etc/fstab

🎯 Objective: Configure EFS to automatically remount after an EC2 instance reboot. Without this, every restart requires manual remounting — unacceptable in production. This proves you understand persistent storage configuration.

⏱️ Time: 20-30 min

💰 Cost: Same as Project 1 — minimal, delete after testing

  1. With EFS already mounted (from Project 1 or a fresh mount), verify it is mounted: df -h | grep efs. Note the EFS DNS name.

  2. Open /etc/fstab as root: sudo nano /etc/fstab. Add this line at the bottom (replace with your EFS DNS):

    fs-xxxxxxxx.efs.YOUR-REGION.amazonaws.com:/ /mnt/efs nfs4 nfsvers=4.1,rsize=1048576,wsize=1048576,hard,timeo=600,retrans=2,noresvport,_netdev 0 0

    📸 Screenshot: /etc/fstab with EFS mount entry added — note the _netdev option

  3. Test without rebooting: sudo umount /mnt/efs then sudo mount -a (mounts all fstab entries). Verify: df -h | grep efs.

    📸 Screenshot: sudo mount -a succeeds — fstab entry verified without rebooting

  4. Reboot the instance: AWS Console → EC2 → select instance → Instance state → Reboot instance. Wait ~2 minutes, reconnect via SSH.

  5. After reconnect, immediately check: df -h. EFS should appear already mounted — no manual action needed.

    📸 Screenshot: After reboot — EFS auto-mounted, no manual action taken

✅ What you proved: The _netdev option tells Linux to wait for the network before mounting — critical in cloud. Without it, the instance can fail to boot if EFS isn't reachable during startup. This is production-required knowledge.

🧹 Cleanup: Remove the fstab line (sudo nano /etc/fstab, delete the EFS line). Unmount: sudo umount /mnt/efs. Delete the EFS file system in the console.

Project 3: Shared Web Content with Nginx + EFS

🎯 Objective: Mount EFS at /var/www/html on two Nginx web servers. Upload one HTML file to EFS — both servers serve it instantly. This is the classic load-balanced web server problem that EFS solves.

⏱️ Time: 40-50 min

💰 Cost: EFS + EC2 t3.micro (Free Tier). Delete after testing.

  1. Create a fresh EFS file system (or reuse one). On both EC2 instances, install Nginx:

    sudo yum install -y nginx
sudo systemctl start nginx
sudo systemctl enable nginx

  2. On both instances, mount EFS at the Nginx document root:

    sudo umount /var/www/html 2>/dev/null; true
sudo mkdir -p /var/www/html
sudo mount -t nfs4 -o nfsvers=4.1   fs-xxxxxxxx.efs.YOUR-REGION.amazonaws.com:/ /var/www/html

    📸 Screenshot: EFS mounted at /var/www/html on Instance 1 — confirmed with df -h

  3. On Instance 1 only, create the web page:

    sudo bash -c 'cat > /var/www/html/index.html << EOF
<!DOCTYPE html>
<html><head><title>EFS Shared Site</title></head>
<body>
  <h1>This page lives on Amazon EFS</h1>
  <p>Written once on Instance 1. Served from both servers.</p>
  <p>Hostname: $(hostname)</p>
</body></html>
EOF'

  4. Open the public IP of Instance 1 in your browser and the public IP of Instance 2. Both should serve identical content — the page written only on Instance 1.

    📸 Screenshot: Both servers serving the same page — file written on Instance 1 only

  5. Now update the page on Instance 1 — edit /var/www/html/index.html and change the heading to "Updated content!" — then refresh both browsers. Both show the update instantly.

✅ What you proved: This is why EFS is the correct solution for load-balanced web servers. Any content update reaches all instances instantaneously — no sync scripts, no S3 sync, no manual copying. This is the real-world use case EFS was designed for.

🧹 Cleanup: Unmount EFS from both instances, delete the EFS file system, stop/terminate EC2 instances if created for this project.

Project 4: Isolate Apps with EFS Access Points

🎯 Objective: Create two EFS Access Points — one for App1, one for App2 — each enforcing its own root directory and POSIX user. App1 cannot read App2's data even though both use the same EFS file system. This is production-grade multi-tenant isolation.

⏱️ Time: 40-50 min

💰 Cost: Same EFS costs — minimal. No additional charge for access points.

  1. Create or reuse an EFS file system. In the EFS Console, click the file system ID → Access points tab → Create access point.

  2. Configure Access Point 1 for App1:
    Name = app1-access-point
    Root directory path = /app1
    Owner UID = 1001, Owner GID = 1001, Permissions = 755
    POSIX user: UID = 1001, GID = 1001

    📸 Screenshot: Access Point 1 — App1 configuration with root /app1 and UID 1001

  3. Create Access Point 2 for App2:
    Name = app2-access-point, Root = /app2, UID/GID = 1002, Permissions = 755.

    📸 Screenshot: EFS Access points list — app1 and app2 access points both Available

  4. On Instance 1, mount using the App1 access point (using amazon-efs-utils):

    sudo yum install -y amazon-efs-utils
sudo mkdir /mnt/app1
sudo mount -t efs -o tls,accesspoint=fsap-XXXXXXXX   fs-xxxxxxxx /mnt/app1
# Write a test file
echo "App1 secret data" | sudo tee /mnt/app1/secret.txt
# Check who owns it
ls -la /mnt/app1/

  5. On Instance 1, also mount using the App2 access point:

    sudo mkdir /mnt/app2
sudo mount -t efs -o tls,accesspoint=fsap-YYYYYYYY   fs-xxxxxxxx /mnt/app2
# Try to read App1's secret from App2 mount
cat /mnt/app2/secret.txt

    📸 Screenshot: App2 cannot read App1's file — access point isolation confirmed

✅ What you proved: Even on the same instance using the same EFS file system, Access Points enforce directory-level isolation. App2's mount sees only /app2 — it cannot reach /app1 regardless of Linux permissions. This is the security model used for multi-tenant applications sharing EFS.

🧹 Cleanup: sudo umount /mnt/app1 /mnt/app2. EFS Console → delete both access points → delete the file system.

Project 5: Lifecycle Management — Auto-Tier Files to IA

🎯 Objective: Enable EFS lifecycle management to automatically move inactive files to Standard-IA storage. Simulate access patterns to observe files being tiered. Understand cost savings without data loss.

⏱️ Time: 30-40 min (plus wait time for lifecycle to trigger)

💰 Cost: Minimal EFS storage. Standard-IA is ~93% cheaper per GB than Standard.

  1. Create a new EFS file system. Before clicking Create, expand Customize. Under Lifecycle management, set: Transition into IA = 7 days since last access (shortest available for testing). Click Create.

    📸 Screenshot: EFS lifecycle management — transition to IA after 7 days

  2. Mount the file system on an EC2 instance (same steps as Project 1).

  3. Upload test files of different ages (simulate by creating files you will not access):

    sudo mkdir -p /mnt/efs/active /mnt/efs/cold
echo "I get accessed regularly" | sudo tee /mnt/efs/active/hot-file.txt
echo "Nobody reads me after upload" | sudo tee /mnt/efs/cold/cold-file.txt
echo "Also ignored" | sudo tee /mnt/efs/cold/another-cold-file.txt

  4. Check the EFS Console → Storage tab to view storage breakdown by class. Initially all files are in Standard.

    📸 Screenshot: EFS Storage tab — all files in Standard before lifecycle triggers

  5. After the lifecycle window passes (7 days in production — for demo purposes you can check the console periodically or adjust the lifecycle policy to the minimum): access hot-file.txt regularly, leave cold-file.txt untouched. The Storage tab will show bytes migrating to Standard-IA.

    📸 Screenshot: EFS Storage tab — cold files moved to Standard-IA, hot files remain in Standard

✅ What you proved: EFS lifecycle management is truly automatic — no code, no manual sorting, no application changes. Files the system decides are cold move to IA at ~93% lower storage cost. This is one of the highest-impact cost optimizations available for EFS at zero operational effort.

⚡ Cost impact example: 1TB of data with 80% cold files: Standard cost = ~$360/month. With lifecycle IA: cold 800GB at $0.025 = $20 + hot 200GB at $0.36 = $72 = $92/month total. Savings: ~75%.

🧹 Cleanup: Unmount EFS. EFS Console → delete file system.
