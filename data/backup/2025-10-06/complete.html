🖥️ Understanding AMIs - Your Server Blueprint

What Exactly is an AMI?

Imagine you need to set up 10 identical computers for your office. Normally, you'd spend hours on each one:

  1. Install Windows from scratch
  2. Install Microsoft Office
  3. Install antivirus software
  4. Configure network settings
  5. Set up user accounts

Now imagine you could just press a button and have a fully configured computer ready in 2 minutes. An Amazon Machine Image (AMI) is a pre-configured template that contains everything needed to launch an EC2 instance.

Figure 1: How one AMI creates many identical servers

The Four Components of Every AMI

🎯 Think of AMI Components Like a House Blueprint:

Just as a house blueprint specifies the foundation (OS), installed features (applications), interior details (files), and system specs (configuration), an AMI specifies everything your server needs.

Component What It Contains Real-World Example
1. Operating System The base software that runs the server Like choosing Windows vs Mac for your computer
2. Applications Pre-installed programs Like having Office and Chrome already installed
3. Files Configuration files, scripts, data Like having your favorite settings and documents ready
4. Configuration Settings System parameters, environment variables Like having WiFi passwords and printer settings saved

Why AMIs Are Game-Changers

Problem: Your startup's website becomes viral overnight. You need to add 50 more web servers by tomorrow to handle traffic.

Without AMIs: Your team works all night, manually setting up each server. By the time you finish, your website has crashed from overload.

With AMIs: You created one perfect web server last month and saved it as an AMI. Now you click "Launch 50 instances from AMI" and AWS creates 50 identical servers in 5 minutes. Your website stays online.

✅ Key Benefits of AMIs:

  • Speed: Launch new servers in minutes instead of hours or days
  • Consistency: Every server is exactly the same, no configuration mistakes
  • Scalability: Create 1 server or 1,000 servers with the same effort
  • Disaster Recovery: If a server fails, launch a replacement instantly
  • Version Control: Save AMIs for each software version, roll back if needed

Real-World AMI Scenarios

Scenario 1: E-Commerce During Black Friday

An online store normally runs on 10 web servers. During Black Friday sales, traffic increases 50x. The company:

  1. Created an AMI of their perfect web server configuration
  2. During Black Friday, launches 500 instances from that AMI in 10 minutes
  3. After the sale, terminates the extra instances
  4. Saves thousands on infrastructure costs

Scenario 2: Software Testing

A development team needs to test new features across different environments:

  1. Create AMI for each environment (development, testing, staging)
  2. Developers launch instances from appropriate AMIs as needed
  3. Test features in isolated, identical environments
  4. Terminate instances after testing to save money

⚡ Exam Tip: AMIs are region-specific - if you create an AMI in us-east-1, it's only available in that region unless you copy it to other regions.

📦 Five Types of AMIs Explained

Not all AMIs are created equal. AWS provides different types of AMIs, each with different sources, trust levels, and use cases.

Figure 2: Five AMI types ranked by trust level and source

1. Official AMIs (The Safe Choice)

Official AMIs are created and maintained by AWS, providing the highest level of trust and regular security updates.

✅ Official AMIs Include:

  • Amazon Linux 2 and Amazon Linux 2023 - AWS's own Linux distributions
  • Ubuntu Server - Popular Linux for development
  • Red Hat Enterprise Linux (RHEL) - Enterprise-grade Linux
  • Windows Server - Microsoft Windows for cloud

Analogy: Think of Official AMIs like buying a computer directly from Apple or Dell. You know it's genuine, supported, and won't have any surprises.

Aspect Details
Who Creates Them Amazon Web Services
Security Updates Regular patches and updates from AWS
Cost Some free (Amazon Linux), others include licensing fees
Best For Production workloads requiring stability and support
Trust Level ⭐⭐⭐⭐⭐ Highest

2. AWS Marketplace AMIs (Pre-Built Solutions)

Marketplace AMIs come from verified software vendors who sell pre-configured solutions through AWS.

Analogy: Like buying pre-assembled furniture from IKEA instead of building it yourself. Costs more, but saves time and expertise.

💡 Common Marketplace AMIs:

  • Database servers: Pre-configured MongoDB, PostgreSQL, Oracle
  • Security appliances: Firewalls, intrusion detection systems
  • Development platforms: Pre-installed development environments
  • Enterprise software: SAP, Microsoft SQL Server, specialized applications
Aspect Details
Who Creates Them Verified software vendors (Cisco, MongoDB, Oracle, etc.)
Pricing EC2 charges + software licensing fees (hourly or annual)
Support Vendor provides support, not AWS
Best For When you need commercial software without installation hassle
Trust Level ⭐⭐⭐⭐ High (AWS verifies vendors)

3. Third-Party AMIs (External Vendors)

These come from software vendors who distribute outside AWS Marketplace.

Aspect Details
Distribution Vendor websites, partner programs
Verification Not verified by AWS
Support Vendor-provided only
Best For Specific vendor solutions with established relationships
Trust Level ⭐⭐⭐ Medium (depends on vendor reputation)

4. Community AMIs (Use With Caution)

Community AMIs are created by AWS users and shared publicly without any verification from AWS.

❌ Warning - Security Risk:

Community AMIs are completely unverified. They could contain:

  • Malware or viruses
  • Backdoors for unauthorized access
  • Misconfigured security settings
  • Cryptocurrency mining software
  • Outdated vulnerable software

Never use Community AMIs for production systems.

Analogy: Community AMIs are like downloading software from a random person on the internet. You have no idea what's really in there.

Aspect Details
Who Creates Them Anyone with an AWS account
Verification None - completely unvetted
Support No guaranteed support
Acceptable Use Personal learning, testing only (never production)
Trust Level ⭐ Very Low

5. Custom/Private AMIs (Your Personal Templates)

Custom AMIs are created by you from your own EC2 instances and remain private to your AWS account.

How to Create a Custom AMI:

  1. Start with a base: Launch an EC2 instance from an Official AMI
  2. Customize it: Install your applications, configure settings, add files
  3. Test thoroughly: Make sure everything works perfectly
  4. Create the AMI: Right-click instance → Image → Create Image
  5. Use it: Launch new instances from your custom AMI

✅ Why Create Custom AMIs:

  • Speed: New servers launch with everything pre-installed
  • Standardization: All your servers use the same configuration
  • Compliance: Bake security and compliance requirements into the AMI
  • Cost Savings: No time wasted on manual configuration

Real-World Example:

Your company's web application needs:

  • Ubuntu 22.04 OS
  • Node.js version 18
  • MongoDB client tools
  • Your company's monitoring agent
  • Security hardening configurations
  • Custom SSL certificates

Instead of installing these on every new server, you create one perfect server, save it as a custom AMI called "WebApp-Production-v1.0", and launch all new web servers from that AMI.

⚡ Pro Tip: Name your custom AMIs clearly with version numbers and dates. Examples: "WebServer-v2.3-20251006", "Database-Prod-v1.5-Oct2025". This makes managing multiple AMI versions much easier.

🔄 AMI vs EC2 Instance - What's the Difference?

This is one of the most confusing concepts for beginners. Let's clear it up with a simple analogy.

🏗️ The House Blueprint Analogy:

  • AMI = Blueprint: The architectural plan showing how to build a house
  • EC2 Instance = Actual House: The physical house built from that blueprint

You can build 1 house or 100 houses from the same blueprint. Each house is independent, but they all started from the same design.

Figure 4: The relationship between AMIs (templates) and EC2 instances (running servers)

Key Differences

Characteristic AMI (Template) EC2 Instance (Running Server)
What It Is Static template/blueprint Live, running virtual machine
State Unchanging, frozen in time Dynamic, constantly changing
Running Processes None (it's just a template) Operating system, applications, services
Costs Money Only storage costs (pennies per month) Per-hour or per-second billing while running
Can You Log In No (it's not running) Yes (via SSH or RDP)
Quantity Create once, use unlimited times Create as many as you need from AMI

The Lifecycle

Step 1: Start with AMI (template)
   ↓
Step 2: Launch EC2 Instance (running server)
   ↓
Step 3: Customize the instance (install software, configure)
   ↓
Step 4: Create new AMI from customized instance
   ↓
Step 5: Launch more instances from new AMI

Configuration Components

When you launch an instance, the AMI is just ONE of several configuration elements:

Component What You Choose Analogy
Instance Name Friendly identifier (optional) Like naming your computer "John's Laptop"
Tags Key-value labels for organization Like putting sticky notes: "Environment=Production, Owner=IT"
AMI Which template to use Which blueprint to build from
Instance Type Hardware specs (CPU, RAM) Like choosing laptop specs: i5 vs i7, 8GB vs 16GB RAM

✅ Remember This:

  • AMI = Software Configuration (what programs are installed)
  • Instance Type = Hardware Configuration (how powerful the server is)
  • Instance = AMI + Instance Type + Network + Storage

Practical Example

Let's say you need to create a web server:

Configuration Decisions:

  1. AMI: Choose "Amazon Linux 2023" (defines the operating system)
  2. Instance Name: "WebServer-Production-01" (for identification)
  3. Tags: Environment=Production, Application=Website, Team=DevOps
  4. Instance Type: t3.medium (2 vCPUs, 4 GB RAM)
  5. Key Pair: web-server-key.pem (for SSH access)
  6. Security Group: Allow HTTPS (443) from internet
  7. Storage: 30 GB SSD

The AMI (Amazon Linux 2023) determines what the server is. The instance type (t3.medium) determines how powerful it is.

🐧 Linux Basics - Why Linux Dominates the Cloud

If you look at any major tech company's cloud infrastructure, you'll find that approximately 70% of all EC2 instances run Linux rather than Windows. But why?

What is Linux?

Simple Definition: Linux is an open-source operating system based on Unix, created by Linus Torvalds in 1991.

Analogy: Think of an operating system like the manager of a restaurant. The manager (OS) coordinates the kitchen staff (CPU), ingredients (memory), storage rooms (disk), and waiters (network) to serve customers (applications).

Linux vs Windows - The Key Differences

Aspect Linux Windows
Cost Free and open-source Requires licensing fees
Code Access Source code is public, anyone can modify Proprietary, closed-source
Cloud Usage ~70% of cloud servers ~30% of cloud servers
Primary Interface Command-line (SSH) Graphical interface (RDP)
Resource Usage Lightweight, minimal overhead Heavier, more memory needed
Server Applications Apache, Nginx, Docker, Kubernetes IIS, .NET applications, Active Directory
Updates Flexible, can postpone indefinitely Regular mandatory updates
Security Model Permissions-based, very granular User-based access control

Why Cloud Loves Linux

✅ Linux Advantages in Cloud:

  • Zero Licensing Costs: Save thousands on Windows Server licenses when running hundreds of instances
  • Lower Resource Footprint: Linux needs less RAM and CPU, meaning smaller (cheaper) instance types
  • Automation-Friendly: Command-line tools make scripting and automation easier
  • Container Support: Docker and Kubernetes were built for Linux first
  • Customization: Modify anything in the OS to fit your needs
  • Stability: Linux servers often run for months or years without reboots

Popular Linux Distributions (Distros)

Linux comes in different "flavors" called distributions. All distributions use the same Linux kernel but package different tools, interfaces, and support models.

Figure 5: Popular Linux distributions and their typical uses

Distribution Best For Package Manager AWS Availability
Amazon Linux 2023 AWS-optimized workloads dnf/yum Official AMI (free)
Ubuntu Development, ease of use apt Official AMI (free)
Red Hat Enterprise Linux Enterprise, paid support yum/dnf Official AMI (licensing fees)
CentOS Free alternative to RHEL yum Community AMIs
Debian Stability, servers apt Official AMI (free)

💡 For Beginners: Start with Amazon Linux 2023 or Ubuntu. They're well-documented, have large communities, and work great in AWS.

When to Use Linux vs Windows in Cloud

Choose Linux When:

  • Running web servers (Apache, Nginx)
  • Hosting containerized applications (Docker)
  • Building microservices architectures
  • Cost optimization is priority
  • You need maximum control and customization

Choose Windows When:

  • Running .NET applications or ASP.NET websites
  • Need Microsoft SQL Server
  • Using Active Directory for authentication
  • Team is Windows-trained and prefers GUI
  • Running Windows-specific software

🏗️ Inside Linux - How the Layers Work

Linux isn't just one thing - it's a collection of layers working together, like floors in a building. Understanding these layers helps you troubleshoot problems and use Linux effectively.

Figure 6: The layered architecture of Linux - Each layer builds on the one below

Layer 1: Hardware (The Foundation)

At the bottom is the actual computer hardware - or in AWS's case, virtualized hardware.

Component What It Does In EC2
CPU Processes instructions Virtual CPUs allocated by AWS
RAM Temporary fast storage Instance memory (e.g., 4GB, 16GB)
Disk Permanent storage EBS volumes attached to instance
Network Connectivity Virtual network interfaces in VPC

💡 Cloud Magic: In EC2, you never touch physical hardware. AWS's hypervisor creates virtual hardware that looks and acts like real hardware to Linux. Your instance thinks it has dedicated CPU, RAM, and disk, but it's actually sharing with others securely.

Layer 2: Linux Kernel (The Brain)

The Linux kernel is the core of the operating system, managing all hardware resources and providing services to applications.

Kernel Responsibilities:

Function What It Does Real-World Example
Process Management Runs programs, allocates CPU time Like a teacher deciding which student gets to speak and for how long
Memory Management Allocates RAM to programs Like organizing your desk - which papers stay on top, which go in drawers
Device Drivers Communicates with hardware Like translators between you and someone who speaks another language
File System Organizes files and folders Like a filing cabinet system with labeled drawers and folders
Network Stack Handles network communication Like a post office routing letters to the right addresses

⚡ Important: Applications never talk directly to hardware. They always go through the kernel. This provides security (apps can't break hardware) and portability (same app works on different hardware).

Layer 3: System Libraries (The Toolbox)

System libraries are collections of pre-written code that programs can use for common tasks.

Analogy: Instead of building a chair from scratch, you use pre-made parts from IKEA. Instead of writing code to read files from scratch, programs use library functions like read() and write().

Common Libraries:

  • glibc: C library with basic functions (file operations, string manipulation)
  • OpenSSL: Encryption and secure communications
  • zlib: Data compression
  • libpthread: Multi-threading support

Layer 4: GNU Utilities (The Tools)

GNU utilities are command-line programs that perform specific tasks like file operations, text processing, and system administration.

🔧 Essential GNU Tools:

Tool What It Does Example
ls List files in directory ls /home shows files in /home
grep Search for text patterns grep "error" logfile.txt finds errors in logs
awk Process and analyze text awk '{print $1}' data.txt prints first column
sed Find and replace text sed 's/old/new/' file.txt replaces text
tar Create/extract archives tar -xzf archive.tar.gz extracts files

Layer 5: The Shell (Your Command Center)

The shell is your interface to Linux - it takes your typed commands and makes them happen.

How the Shell Works:

You type: ls -la
   ↓
Shell reads command
   ↓
Shell calls kernel system calls
   ↓
Kernel fetches directory data
   ↓
Shell formats and displays output

Popular Shells:

  • bash (Bourne Again Shell): Most common, default on most systems
  • sh (Bourne Shell): Original, simpler, still widely used in scripts
  • zsh (Z Shell): Advanced features, popular for power users

✅ Shell Superpowers:

  • Automation: Write scripts to automate repetitive tasks
  • Pipes: Chain commands together: ls | grep ".txt" | wc -l
  • Variables: Store values: NAME="John"; echo $NAME
  • Loops: Repeat operations: for file in *.txt; do echo $file; done

Layer 6: User Applications (What You Actually Use)

This is the software you install and run:

  • Web servers: Apache, Nginx
  • Databases: MySQL, PostgreSQL, MongoDB
  • Programming languages: Python, Node.js, Java
  • Your custom applications: Whatever you build

How Layers Communicate

Figure 7: How a file read request flows through Linux layers

Example: Reading a File

  1. Application (web server) wants to read index.html
  2. Application calls library function open("index.html")
  3. Library makes a kernel system call
  4. Kernel checks permissions, finds file on disk
  5. Kernel tells disk driver to read the data
  6. Hardware (disk) reads the physical bytes
  7. Data flows back up: Hardware → Kernel → Library → Application

💻 The Shell - Your Control Center

The shell is where the magic happens in Linux. While Windows users click buttons, Linux users type commands - and this is actually more powerful for cloud work.

GUI vs CLI - The Fundamental Difference

Aspect GUI (Graphical User Interface) CLI (Command-Line Interface)
What It Is Click buttons, drag icons Type text commands
Learning Curve Easier initially Steeper at first
Speed (After Learning) Slower for repetitive tasks Much faster once you know commands
Automation Difficult to automate clicking Easy to script commands
Remote Access Requires full screen sharing (slow) Text-only (very fast, low bandwidth)
Documentation Screenshots get outdated Commands stay the same for years

💡 Why CLI Dominates Cloud:

Imagine managing 100 servers. With GUI, you'd need to click through menus 100 times. With CLI, you write one script and run it on all 100 servers simultaneously. This is why most cloud automation and DevOps work relies heavily on command-line interfaces.

Basic Command Structure

Every Linux command follows a pattern:

command [options] [arguments]

Example:
ls -la /home/user

- ls = command (list files)
- -la = options (long format + show hidden)
- /home/user = argument (which directory)

Essential Commands for Cloud Work

pwd Print working directory Find out where you are in the file system

🎯 UNIX Philosophy and Modern Cloud

Linux inherited design principles from UNIX created in the 1970s. Surprisingly, these decades-old ideas are MORE relevant today in cloud computing than ever before.

Core UNIX Principles

✅ The UNIX Way:

  1. Do One Thing Well: Each program should do one task excellently
  2. Work Together: Programs should cooperate through standard interfaces
  3. Use Text Streams: Universal data format enabling program composition
  4. Choose Simplicity: Simple is better than complex

UNIX Principles in Modern Cloud

UNIX Principle 1970s Example 2025 Cloud Equivalent
Do One Thing Well grep only searches text
sort only sorts lines		 Microservices: Payment service only handles payments, not also user management
Work Together ls | grep ".txt" | wc -l
(List, filter, count)		 API-driven architecture: Services communicate via APIs
Event-driven systems
Text Streams Pipe output between programs JSON APIs, log aggregation, data pipelines
Modularity Small, swappable tools Docker containers, serverless functions

💡 Real-World Example:

Instead of one giant program that handles user registration, sends emails, processes payments, and generates reports...

UNIX/Microservices Way:

  • User service: handles registration
  • Email service: sends emails
  • Payment service: processes payments
  • Reporting service: generates reports

Each service is simple, focused, and can be developed, deployed, and scaled independently - just like UNIX commands.

Command-Line Interaction Benefits

Command-line interfaces enable automation, scripting, and reproducible infrastructure management in ways that graphical interfaces cannot match.

✅ Why CLI Matters in Cloud:

  • Infrastructure as Code: Write scripts to build entire environments
  • CI/CD Pipelines: Automated deployments run CLI commands
  • Configuration Management: Tools like Ansible execute CLI commands across hundreds of servers
  • Remote Management: SSH into servers from anywhere using just text
  • Logs and Monitoring: Parse, filter, analyze text logs efficiently

🧪 Software Testing in the Cloud

Cloud environments revolutionized software testing. Instead of maintaining expensive physical test labs, teams now spin up test environments on-demand and destroy them when done.

Software Documentation Standards

Document Full Name Purpose Who Uses It
SDD Software Design Document Technical architecture, component design, data models Developers, architects
SRRS Software Requirements Specification Functional requirements, acceptance criteria Product managers, QA, developers

Types of Software Testing

Figure 9: Software testing pyramid - More unit tests, fewer integration tests

1. Unit Testing

Unit testing validates individual code components in isolation to catch bugs early in development.

💡 Analogy: Like testing each ingredient before cooking. Check if the eggs are fresh, flour isn't expired, baking powder works - before baking the cake.

In Cloud: Developers run unit tests on their local machines or small EC2 instances. Tests run in seconds.

Example:

// Test a single function
function calculateTotal(price, tax) {
  return price + (price * tax);
}

// Unit test
assert(calculateTotal(100, 0.1) === 110); // Pass

2. Integration Testing

Integration testing verifies that different components work correctly together.

Analogy: Like testing if your car engine, transmission, and wheels work together - not just separately.

In Cloud: Launch multiple EC2 instances representing different services (web server, database, cache). Test if they communicate correctly.

Example Scenario:

  • Web server instance connects to database instance
  • User registration API calls email service
  • Payment service integrates with third-party payment gateway

3. Security Testing

Security testing identifies vulnerabilities, weak configurations, and potential attack vectors.

In Cloud: Create isolated VPC with test instances, run penetration testing tools, scan for vulnerabilities.

Common Tests:

  • Port scanning (are unnecessary ports open?)
  • SQL injection attempts
  • Authentication bypass attempts
  • Privilege escalation tests
  • Data encryption validation

⚠️ Security Testing Rules: Only test systems you own or have explicit permission to test. Never run security scans against AWS infrastructure itself or other customers' systems.

4. Performance Testing

Performance testing measures system behavior under load to identify bottlenecks and scalability limits.

In Cloud: Launch hundreds of instances to simulate thousands of users, measure response times, identify breaking points.

Test Types:

Test Type Purpose Cloud Example
Load Testing Test with expected normal load Simulate 1,000 concurrent users
Stress Testing Push beyond limits to find breaking point Increase to 10,000 users until system fails
Spike Testing Test sudden traffic increases Jump from 100 to 5,000 users instantly
Endurance Testing Test sustained load over time Run at 70% capacity for 48 hours

✅ Cloud Advantage for Testing:

  • On-Demand Environments: Create test infrastructure in minutes
  • Isolated Testing: Each test gets its own environment
  • Cost Efficiency: Pay only while tests run, then delete everything
  • Parallel Testing: Run multiple test suites simultaneously
  • Production-Like: Test environments can mirror production exactly

Software Maintenance Types

After deployment, software needs ongoing maintenance. Four maintenance types address different post-deployment needs: corrective, adaptive, perfective, and preventive.

Type Purpose Example Priority
Corrective Fix bugs and defects Patch security vulnerability, fix crashes Urgent
Adaptive Adapt to environment changes Update for new OS version, API changes Medium
Perfective Improve performance or features Optimize database queries, add new features Low-Medium
Preventive Prevent future problems Refactor code, improve monitoring Low

💡 Cloud Maintenance Example:

Scenario: Your web application runs on Amazon Linux 2.

  • Corrective: AWS announces a critical security patch - you update immediately
  • Adaptive: Amazon Linux 3 is released - you plan migration
  • Perfective: Users report slow page loads - you optimize code and add caching
  • Preventive: You implement monitoring and alerts before problems occur

☁️ EC2 Configuration Essentials

What is EC2?

EC2 (Elastic Compute Cloud) is AWS's Infrastructure as a Service (IaaS) offering that provides resizable virtual servers in the cloud.

The "Elastic" Part: You can scale up (bigger servers) or scale out (more servers) based on demand, then scale back down when demand decreases.

Figure 10: The six essential components for launching an EC2 instance

The Six Configuration Requirements

Launching an EC2 instance requires six essential decisions:

1. Server Configuration (Choose Your AMI)

This determines WHAT software runs on your server.

Decision Questions:

  • Linux or Windows?
  • Which distribution? (Amazon Linux, Ubuntu, Red Hat)
  • Do you need pre-installed software?
  • Using official AMI or your custom AMI?

2. Instance Type (Choose Your Hardware)

Instance types determine the hardware specifications including CPU cores, RAM, network bandwidth, and storage type.

Common Instance Type Families:

Family Purpose Example Types Use Case
t3 Burstable general purpose t3.micro, t3.small, t3.medium Web servers, development, small databases
m5 Balanced compute/memory m5.large, m5.xlarge Application servers, medium databases
c5 Compute optimized c5.large, c5.2xlarge CPU-intensive applications, batch processing
r5 Memory optimized r5.large, r5.xlarge Large databases, in-memory caches

✅ Instance Type Naming:

t3.medium breaks down as:

  • t = Family (burstable performance)
  • 3 = Generation (3rd generation)
  • medium = Size (2 vCPU, 4 GB RAM)

3. Key Pair (Your Login Credentials)

Key pairs use public-key cryptography for secure authentication - your private key proves you're authorized to access the instance.

How Key Pairs Work:

🔐 The Lock and Key Analogy:

  • Public Key: Like a padlock you put on your server (anyone can see it, but can't open it)
  • Private Key: Like the key in your pocket (only you have it, NEVER share it)

When you try to connect, your private key proves you have the matching key for the public lock.

❌ Critical Warning:

If you lose your private key file (.pem), you CANNOT access your instance. There's no password reset option. Always back up your key files securely.

4. Security Groups (Your Firewall)

Security Groups act as virtual firewalls controlling inbound and outbound traffic to your instances.

Common Security Group Rules:

Rule Type Protocol Port Source Use Case
Inbound SSH 22 Your IP address Remote administration (Linux)
Inbound RDP 3389 Your IP address Remote administration (Windows)
Inbound HTTP 80 0.0.0.0/0 (anywhere) Public website
Inbound HTTPS 443 0.0.0.0/0 (anywhere) Secure public website
Outbound All All 0.0.0.0/0 Instance can connect to internet

⚡ Important Security Concept: Security Groups are stateful, meaning if you allow inbound traffic, the response traffic is automatically allowed outbound.

5. Network Setup (VPC and Subnet)

Determines WHERE your instance lives in your virtual network.

  • VPC (Virtual Private Cloud): Your isolated network in AWS
  • Subnet: A segment within your VPC (like different floors in a building)
  • Public IP: Address accessible from internet
  • Private IP: Address only within your VPC

6. Storage (EBS Volumes)

EBS (Elastic Block Store) provides persistent block storage volumes that persist independently of instance lifecycle.

Common EBS Volume Types:

Type Performance Use Case Cost
gp3 General purpose SSD Most workloads, boot volumes Low
io2 High performance SSD Databases, latency-sensitive apps High
st1 Throughput-optimized HDD Big data, log processing Low

EC2 Instance Lifecycle and Billing

Understanding instance states is crucial for cost management:

Figure 11: EC2 instance states and what you pay for in each state

State What's Happening Billing Data Preserved
Pending AWS allocating resources ❌ No charges N/A
Running Instance fully operational ✅ Full charges Yes
Stopping Shutting down gracefully ✅ Still charged Yes
Stopped Instance powered off ⚠️ EBS storage only Yes (EBS only)
Terminated Instance deleted permanently ❌ No charges No (unless configured)

❌ Common Mistake:

Students forget to stop or terminate instances after practice sessions and receive unexpected bills. Always stop instances when not in use!

Cost Comparison:

  • Running t3.medium 24/7 for a month: ~$30
  • Running 8 hours/day (stop at night): ~$10
  • Running only during practice (4 hours/week): ~$1

Today we covered the essential foundations of EC2, AMIs, and Linux systems:

  • AMI Fundamentals: AMIs are templates containing OS, applications, files, and configurations that enable rapid, consistent EC2 instance deployment. They're the "blueprints" for creating identical servers.
  • Five AMI Types: Official (AWS-maintained, highest trust), Marketplace (vendor-verified commercial), Third-party (external vendors), Community (unverified public - avoid for production), and Custom (your own templates). Production should use Official or Custom AMIs.
  • AMI vs Instance Relationship: AMI is the static template, EC2 instance is the running server. One AMI can create unlimited instances. Instances can be saved as new AMIs for future use.
  • Linux Dominance: Approximately 70% of cloud instances run Linux due to zero licensing costs, lower resource requirements, and superior automation capabilities.
  • Linux Architecture: Six layers work together - Hardware → Kernel → System Libraries → GNU Utilities → Shell → Applications. Each layer builds on the one below, with the kernel managing all hardware resources.
  • Shell and CLI: Command-line interfaces enable automation, scripting, and infrastructure-as-code practices that are fundamental to modern DevOps.
  • UNIX Philosophy: "Do one thing well" and modularity principles from the 1970s directly influenced modern microservices architecture and containerization.
  • Software Testing: Four test types (unit, integration, security, performance) and four maintenance types (corrective, adaptive, perfective, preventive) address different software lifecycle needs. Cloud enables on-demand test environments.
  • EC2 Configuration: Six requirements to launch an instance - AMI (software), Instance Type (hardware), Key Pair (authentication), Security Groups (firewall), VPC (networking), and EBS (storage).
  • Instance Lifecycle: Running state incurs full charges, Stopped state charges only for EBS storage, Terminated state has no charges but data is lost. Stop instances when not in use to save 70-90% on costs.

Project 1: Exploring AMI Types in AWS Console

🎯 Objective: Navigate AWS Console to view and compare the five different AMI types, understanding their sources and use cases.

⏱️ Time: 20-25 minutes

💰 Cost: Free (viewing only, not launching)

What You'll Learn

How to find, filter, and evaluate AMIs for different use cases without launching any instances.

Step-by-Step Instructions

Step 1: Navigate to EC2 AMI Catalog

  1. Log into AWS Console
  2. Search for "EC2" in services search bar
  3. Click on EC2 service
  4. In left sidebar, click AMIs under "Images"

Step 2: Explore Official AWS AMIs

  1. In AMI search, change dropdown from "Owned by me" to "AWS Marketplace AMIs"
  2. Then change to "Quick Start AMIs"
  3. Observe the official options: Amazon Linux 2023, Ubuntu Server, Red Hat, Windows Server
  4. Click on Amazon Linux 2023 AMI
  5. Note the AMI ID format: ami-xxxxxxxxx
  6. Look at the description - notice "Amazon" as the owner

💡 What to Notice: Official AMIs show "Amazon" or "AWS" as the owner and have detailed descriptions with version numbers.

Step 3: Browse AWS Marketplace AMIs

  1. Change filter to "AWS Marketplace AMIs"
  2. In search box, type "MongoDB"
  3. Click on a MongoDB AMI result
  4. Notice:
    • Vendor name (e.g., "MongoDB Inc")
    • Pricing information (additional costs beyond EC2)
    • Pre-installed software stack
  5. Search for "PostgreSQL", "NGINX", or "WordPress" to see other examples

Step 4: View Community AMIs (Observation Only)

  1. Change filter to "Community AMIs"
  2. Search for "Ubuntu"
  3. Notice the HUGE number of results
  4. Observe:
    • No verification badges
    • Random owner account IDs
    • Varied naming conventions
    • No guaranteed support or updates

❌ Important: DO NOT launch any Community AMIs. These are unverified and potentially unsafe. This step is for observation only.

Step 5: Check Your Custom AMIs

  1. Change filter back to "Owned by me"
  2. Currently this should be empty (you haven't created any yet)
  3. Make a note: "In future project, we'll create our own custom AMI here"

Project 3: AMI Lifecycle Documentation Exercise

🎯 Objective: Document the complete lifecycle of creating a custom AMI from a running instance, understanding each step and its purpose.

⏱️ Time: 25-30 minutes

💰 Cost: Free (planning/documentation exercise, no instances launched)

What You'll Learn

The complete workflow for creating, managing, and deploying custom AMIs for infrastructure standardization.

Step-by-Step Instructions

Step 1: Document the AMI Creation Workflow

Create a flowchart or written workflow in your notes:

AMI Creation Workflow:

Phase 1: Preparation
1. Choose base AMI (e.g., Amazon Linux 2023)
2. Launch EC2 instance from base AMI
3. Connect to instance (SSH)

Phase 2: Customization
4. Update system packages
5. Install required applications
   - Web server (nginx/apache)
   - Database clients
   - Monitoring agents
   - Company-specific tools
6. Configure security settings
7. Add configuration files
8. Test everything works correctly

Phase 3: AMI Creation
9. Stop instance (optional but recommended)
10. Right-click instance → Image → Create Image
11. Provide AMI name and description
12. Wait for AMI creation (5-15 minutes)

Phase 4: Testing
13. Launch new instance from custom AMI
14. Verify all software is pre-installed
15. Confirm configurations are correct

Phase 5: Deployment
16. Use custom AMI for all future instances
17. Update AMI when new version needed
18. Maintain version history

Step 2: Create AMI Naming Convention

Document a standardized naming scheme:

AMI Naming Convention:

Format: [Application]-[Environment]-[Version]-[Date]

Examples:
- WebServer-Production-v1.0-20251006
- AppServer-Staging-v2.3-20251015
- Database-Development-v1.5-20251020

Why This Format:
- Application: Identifies purpose
- Environment: Prevents production/dev confusion
- Version: Tracks software versions
- Date: Helps identify newest AMI

Step 3: Document Version Control Strategy

Plan how you'll manage multiple AMI versions:

Scenario Action Example
Minor update (security patch) Increment minor version v1.2 → v1.3
Major update (new software version) Increment major version v1.9 → v2.0
Keep old versions Retain last 3 versions v1.8, v1.9, v2.0
Deregister old AMIs Delete AMIs older than 6 months Cleanup quarterly

Step 4: Document Use Case Scenarios

Write specific scenarios where custom AMIs provide value:

Scenario 1: Rapid Scaling

Your e-commerce site experiences Black Friday traffic spike:

  • Without AMI: Manually install software on each new server (30+ minutes per server)
  • With AMI: Launch 100 pre-configured servers in 5 minutes
  • Benefit: Handle traffic spike before customers leave

Scenario 2: Disaster Recovery

Critical web server crashes and data is corrupted:

  • Without AMI: Reinstall OS, reconfigure everything from memory/docs (2-4 hours)
  • With AMI: Launch replacement from last known good AMI (5 minutes)
  • Benefit: Minimize downtime, reduce data loss

Scenario 3: Environment Consistency

Bug appears in production but not in development:

  • Without AMI: Different configurations cause "works on my machine" problems
  • With AMI: Development, staging, and production all use same AMI
  • Benefit: Bugs caught earlier, easier debugging

  • You've created a clear naming convention
  • You understand version control for AMIs
  • You can explain real-world scenarios where custom AMIs solve problems

🤔 Reflection Questions

Test your understanding with these thought-provoking questions. Try to answer before viewing hints.

1. Why would a company choose to create custom AMIs instead of using official AWS AMIs for their production workloads?

💡 Hint

Think about deployment speed, consistency across environments, and organizational standards. What happens when you need to launch 50 servers quickly, all with identical configuration?

2. Explain the security risks of using Community AMIs to a non-technical manager.

💡 Hint

Use a real-world analogy like downloading software from strangers on the internet, or buying food from an unverified vendor. What could be hidden inside?

3. Why does Linux dominate cloud computing despite Windows being more popular on personal computers?

💡 Hint

Consider: licensing costs when running hundreds of servers, resource efficiency, automation capabilities, and the command-line interface advantages. How do these factors matter more in cloud than on personal computers?

4. How is the relationship between an AMI and EC2 instance similar to the relationship between a class and object in programming?

💡 Hint

In programming, a class is a blueprint/template, and objects are instances created from that class. How does this parallel the AMI/instance relationship? Can you create multiple objects from one class? Can you modify an object without changing the class?

5. Why would understanding the Linux kernel layer be important for a DevOps engineer troubleshooting performance issues?

💡 Hint

The kernel manages all resources - CPU scheduling, memory allocation, I/O operations. When applications are slow, the problem often lies in how the kernel is allocating these resources. What kernel-level metrics would you check?

6. How do the UNIX principles of "do one thing well" and "programs working together" apply to modern microservices architecture?

💡 Hint

Compare chaining Linux commands with pipes (ls | grep | wc) to microservices communicating via APIs. Each service/command does one thing, passes data to the next. What are the benefits of this approach?

7. Why would you stop an EC2 instance instead of terminating it, and what are the cost implications?

💡 Hint

Think about data persistence, configuration preservation, and restart speed. Compare the costs: running (full charges), stopped (storage only), terminated (no charges but data lost).

8. How would you design an AMI version control strategy for a growing startup that deploys multiple times per week?

💡 Hint

Consider: naming conventions with versions and dates, how many old versions to keep, when to create new AMIs (after each deployment? weekly?), how to test new AMIs before production use, and rollback strategy if new AMI has bugs.
