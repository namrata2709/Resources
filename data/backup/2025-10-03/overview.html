🔐 Multi-Factor Authentication (MFA)

MFA Architecture

AWS Multi-Factor Authentication implements a challenge-response authentication mechanism requiring possession of a physical or virtual device in addition to knowledge-based credentials.

Figure 1: AWS MFA Authentication Architecture

Authentication Flow

The MFA authentication process involves the following technical components:

  1. Initial Authentication: User credentials (email/password or access key) are validated against IAM identity store
  2. MFA Challenge: AWS Security Token Service (STS) issues MFA challenge if policy requires second factor
  3. Token Generation: Authenticator device generates time-based one-time password (TOTP) or receives challenge for hardware tokens
  4. Token Validation: AWS validates the TOTP against expected value calculated using shared secret and current time
  5. Session Token Issuance: Upon successful validation, STS issues temporary security credentials with session token

Supported MFA Mechanisms

MFA Type Protocol Token Format Use Case
Virtual MFA TOTP (RFC 6238) 6-digit numeric General purpose, cost-effective
Hardware Token TOTP or HOTP 6-8 digit numeric Air-gapped environments
U2F Security Key FIDO U2F Cryptographic signature Phishing-resistant authentication
FIDO2 Security Key WebAuthn/CTAP2 Cryptographic signature Passwordless, phishing-resistant

Authentication Protocols

TOTP (Time-based One-Time Password)

Virtual MFA devices implement RFC 6238 TOTP algorithm:

TOTP = HOTP(K, T)
where:
  K = shared secret key (established during device enrollment)
  T = (Current Unix Time - T0) / X
  T0 = Unix epoch (0)
  X = time step (typically 30 seconds)
  
HOTP(K, C) = Truncate(HMAC-SHA-1(K, C))
  C = counter value (T for TOTP)
  Output = 6-digit decimal number

Key Properties:

  • Time synchronization between client and server critical (typically ±1 time step tolerance)
  • Shared secret (K) established during QR code scan or manual entry
  • 30-second validity window balances security and usability
  • HMAC-SHA-1 provides cryptographic integrity

U2F/FIDO Protocol

Universal 2nd Factor (U2F) and FIDO2 provide phishing-resistant authentication through public-key cryptography:

  • Registration: Security key generates unique public/private key pair for each service
  • Authentication: Service sends challenge, key signs with private key, service verifies with stored public key
  • Phishing Resistance: Private key never leaves hardware, origin-binding prevents credential reuse on phishing sites

Implementation Strategies

IAM Policy Enforcement

Enforce MFA through IAM condition keys:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyAllExceptListedIfNoMFA",
      "Effect": "Deny",
      "NotAction": [
        "iam:CreateVirtualMFADevice",
        "iam:EnableMFADevice",
        "iam:GetUser",
        "iam:ListMFADevices",
        "iam:ListVirtualMFADevices",
        "iam:ResyncMFADevice",
        "sts:GetSessionToken"
      ],
      "Resource": "*",
      "Condition": {
        "BoolIfExists": {
          "aws:MultiFactorAuthPresent": "false"
        }
      }
    }
  ]
}

This policy denies all actions except MFA setup operations when MFA is not present in the request context.

Service Control Policies (SCP)

In AWS Organizations, enforce MFA at organizational level:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "BoolIfExists": {
          "aws:MultiFactorAuthPresent": "false"
        },
        "StringNotEquals": {
          "aws:PrincipalArn": [
            "arn:aws:iam::*:role/AllowedRoleWithoutMFA"
          ]
        }
      }
    }
  ]
}

Root Account Protection

Root user MFA is mandatory for compliance frameworks (PCI-DSS, SOC 2, ISO 27001). Implementation requirements:

  • Hardware MFA token or U2F security key recommended over virtual MFA
  • MFA device and backup codes stored in physically secured location (safe, HSM)
  • Root credentials used only for account and billing management tasks requiring root access
  • Alternative root user contacts configured for account recovery

Security Considerations

Threat Model

Attack Vector MFA Protection Mitigation
Phished Credentials ✓ Blocks (attacker lacks second factor) Use U2F/FIDO for phishing resistance
Credential Stuffing ✓ Blocks (valid password insufficient) Combined with password rotation policies
Man-in-the-Middle ⚠ Partial (depends on protocol) U2F/FIDO provides origin-binding protection
SIM Swapping (SMS MFA) ✗ Vulnerable AWS doesn't support SMS; use TOTP/U2F
Malware on Device ⚠ Reduced window (30-second TOTP) Hardware tokens provide air-gap protection
Social Engineering ⚠ User education critical Technical controls + security awareness training

Recovery and Continuity

MFA Device Loss Scenarios:

  • Virtual MFA: Recovery via backup codes, account recovery process through AWS Support (requires identity verification), or alternative authentication method if configured
  • Hardware Token: Backup device pre-enrolled, emergency access procedures documented, AWS Support recovery process
  • U2F Key: Multiple keys enrolled (primary + backup), stored in separate physical locations

Business Continuity Planning:

  • Document MFA device inventory and locations
  • Establish break-glass procedures for emergency access
  • Implement alternate root email addresses for account recovery
  • Regular testing of recovery procedures (quarterly recommended)

💰 AWS Budgets

Budget Service Architecture

AWS Budgets is a FinOps service within AWS Cost Management that provides proactive cost and usage tracking through customizable thresholds and automated alerting.

Figure 2: AWS Budgets Service Architecture

Data Pipeline

  1. Cost Data Collection: AWS services emit usage metrics to billing system
  2. Cost and Usage Report (CUR): Detailed billing data aggregated hourly
  3. Budget Evaluation: Budgets service compares actual/forecasted costs against defined thresholds every 6-8 hours
  4. Alert Triggering: When threshold exceeded, publish notification to SNS topic or email
  5. Forecasting Engine: Machine learning models predict end-of-period costs based on historical patterns

Budget Types and Use Cases

Cost Budgets

Track spending in dollar amounts across services, accounts, or tags.

Configuration Description Use Case
Fixed Budget Static dollar amount per period Predictable workloads, departmental allocations
Planned Budget Variable amounts by period (monthly schedule) Seasonal workloads, project-based spending
Auto-Adjusting Budget Adjusts based on prior period actual spend Growing workloads, percentage-based cost control

Example Configuration:

{
  "BudgetName": "Production-Monthly-Budget",
  "BudgetType": "COST",
  "TimeUnit": "MONTHLY",
  "BudgetLimit": {
    "Amount": "10000",
    "Unit": "USD"
  },
  "CostFilters": {
    "Service": ["Amazon EC2", "Amazon RDS"],
    "TagKeyValue": ["Environment$Production"]
  },
  "CostTypes": {
    "IncludeTax": true,
    "IncludeSubscription": true,
    "UseBlended": false
  }
}

Usage Budgets

Monitor service-specific usage metrics (hours, GB, requests) independent of cost.

Common Usage Metrics:

  • EC2: Instance-hours, data transfer GB, EBS volume GB-months
  • S3: Storage GB-months, PUT/GET requests, data transfer
  • Lambda: Invocations, GB-seconds (compute duration × memory)
  • RDS: Instance-hours, storage GB-months, IOPS

Use Case: Prevent runaway resource consumption before it impacts costs. Example: Alert when Lambda invocations exceed 1 million/day, indicating potential infinite loop or abuse.

Reservation and Savings Plans Budgets

Track utilization and coverage of Reserved Instances (RIs) and Savings Plans to ensure commitment optimization.

Metric Definition Target
RI Utilization Percentage of purchased RI hours actually used >80% (underutilization wastes money)
RI Coverage Percentage of usage covered by RIs vs On-Demand Varies by workload (50-90%)
Savings Plans Utilization Percentage of commitment used >90% (minimize waste)

Alert Mechanisms

Threshold Types

Threshold Basis Description Alert Timing
Actual Cost Current spend to date Real-time (6-8 hour delay)
Forecasted Cost Predicted end-of-period spend Early warning (days/weeks ahead)
RI/SP Utilization Percentage of commitment used Daily evaluation

Multi-Tier Alert Strategy

Enterprise-grade budget alerting employs graduated thresholds:

Tier 1: 50% threshold → Informational (cost tracking dashboards)
Tier 2: 75% threshold → Warning (email to cost owners)
Tier 3: 90% threshold → Critical (PagerDuty alert, team notification)
Tier 4: 100% threshold → Emergency (executive notification, spending review)
Tier 5: 110% threshold → Automated response (Lambda triggers resource tagging/quarantine)

Notification Targets

Email Notifications:

  • Up to 10 email addresses per alert
  • Subscription confirmation required (prevents spam)
  • HTML-formatted alert with budget details and AWS Console links

SNS Integration:

  • Publish to SNS topic for programmatic handling
  • Enable fan-out to multiple targets: Lambda, SQS, email, SMS, HTTP endpoints
  • Message payload includes budget metadata, threshold, actual/forecasted amounts

AWS Chatbot (Slack/Chime):

  • Real-time alerts in team communication channels
  • Interactive buttons for cost analysis and resource management
  • Reduces alert fatigue through contextual information

Integration and Automation

Event-Driven Cost Control

Implement automated responses to budget threshold breaches using EventBridge and Lambda:

Budget Alert → SNS → EventBridge → Lambda Function
                                           ↓
                                    Cost Mitigation Actions:
                                    • Tag resources for review
                                    • Stop non-production instances
                                    • Trigger approval workflow
                                    • Create ServiceNow incident
                                    • Update Cost allocation tags

Example Lambda Response Function:

import boto3

def lambda_handler(event, context):
    # Parse budget alert from SNS
    message = json.loads(event['Records'][0]['Sns']['Message'])
    budget_name = message['budgetName']
    threshold_type = message['thresholdType']
    
    if threshold_type == 'FORECASTED' and message['thresholdPercentage'] >= 90:
        # Critical threshold: Stop dev/test instances
        ec2 = boto3.client('ec2')
        instances = ec2.describe_instances(
            Filters=[{'Name': 'tag:Environment', 'Values': ['dev', 'test']}]
        )
        
        for reservation in instances['Reservations']:
            for instance in reservation['Instances']:
                if instance['State']['Name'] == 'running':
                    ec2.stop_instances(InstanceIds=[instance['InstanceId']])
                    # Log and notify
                    print(f"Stopped instance {instance['InstanceId']} due to budget threshold")
    
    return {'statusCode': 200, 'body': 'Budget response executed'}

Cost Anomaly Detection Integration

AWS Cost Anomaly Detection complements Budgets by using machine learning to identify unusual spending patterns:

  • Budgets: Alert on absolute thresholds (e.g., $10,000/month)
  • Anomaly Detection: Alert on deviations from expected patterns (e.g., 50% spike in EC2 costs)

Combined approach provides comprehensive cost governance:

Budget Alerts → Threshold-based control
Anomaly Detection → Pattern-based anomaly identification
Cost Explorer → Root cause analysis
Trusted Advisor → Optimization recommendations

🏢 Enterprise Implementation

Multi-Account Strategy with AWS Organizations

Consolidated Billing and Budgets

In Organizations, implement hierarchical budget structure:

Organization Root
├── Master Account Budget (Total spend across all accounts)
├── OU: Production
│   ├── OU Budget (Production workload aggregate)
│   ├── Account: prod-web (Service-specific budgets)
│   └── Account: prod-data (Service-specific budgets)
├── OU: Development
│   ├── OU Budget (Dev/test aggregate)
│   └── Zero-spend budget on sandbox accounts
└── OU: Shared Services
    └── Budgets for centralized services (networking, security)

MFA Enforcement via Service Control Policies

Prevent any API calls without MFA across the organization:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RequireMFAForAllActions",
      "Effect": "Deny",
      "Action": "*",
      "Resource": "*",
      "Condition": {
        "BoolIfExists": {"aws:MultiFactorAuthPresent": "false"},
        "StringNotLike": {
          "aws:PrincipalArn": [
            "arn:aws:iam::*:role/OrganizationAccountAccessRole",
            "arn:aws:iam::*:role/AWSServiceRole*"
          ]
        }
      }
    }
  ]
}

This SCP denies all actions when MFA is not present, with exceptions for cross-account roles and AWS service-linked roles.

Centralized Security Monitoring

MFA Compliance Monitoring

Use AWS Config to detect IAM users without MFA:

AWS Config Rule: iam-user-mfa-enabled
Trigger: Configuration changes to IAM users
Remediation: Lambda function sends notification + blocks API access

Parameters:
- MaximumExecutionFrequency: TwentyFour_Hours
- AutomationAssumeRole: arn:aws:iam::account:role/ConfigRemediation
- SNSTopic: arn:aws:sns:region:account:security-violations

Budget Alert Aggregation

Centralize budget alerts across accounts:

  • Create SNS topic in master account subscribed to by all member accounts
  • Lambda function aggregates alerts, deduplicates, and sends to centralized dashboard (QuickSight, Grafana)
  • CloudWatch metric streams for real-time cost tracking

📝 Overall Summary

Multi-Factor Authentication

  • MFA implements defense-in-depth by requiring possession factor in addition to knowledge factor
  • TOTP protocol (RFC 6238) generates time-based codes with 30-second validity windows
  • U2F/FIDO security keys provide phishing-resistant authentication through public-key cryptography
  • IAM policies and SCPs enforce MFA requirements at user, account, and organization levels
  • Root account MFA is mandatory for compliance and best practice
  • Recovery procedures critical for business continuity (backup codes, alternate devices)

AWS Budgets

  • Budgets provide proactive cost governance through threshold-based alerting
  • Four budget types: Cost, Usage, Reservation, Savings Plans
  • Forecasted alerts use ML to predict end-of-period spending for early warnings
  • SNS integration enables event-driven automation and multi-channel notifications
  • First two budgets free, $0.02/day per additional budget
  • Enterprise deployments use hierarchical budgets across AWS Organizations

Integration and Automation

  • Combine MFA enforcement (security) with budget controls (cost) for comprehensive governance
  • Event-driven architectures automate responses to security and cost events
  • Infrastructure as Code (CloudFormation, Terraform) ensures consistent deployment
  • Centralized monitoring aggregates security and cost metrics across multi-account environments
