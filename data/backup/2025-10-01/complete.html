⚖️ Understanding Scalability vs Elasticity

The Restaurant Analogy

Imagine you own a restaurant. Let's use this to understand scalability and elasticity:

🍽️ The Restaurant Story:

Scalability is like knowing your restaurant gets busier every holiday season, so you hire 5 more waiters in November because you expect December crowds. You planned ahead.

Elasticity is like having on-call staff who automatically show up when there's a sudden rush (maybe a tour bus stops by) and leave when things slow down. It happens automatically based on current crowd size.

What is Scalability?

Scalability is the ability of a system to handle increased load by adding resources through planned capacity expansion. It's about long-term growth and capacity planning.

Key characteristics:

  • Manual or planned: You decide when to add resources based on forecasts
  • Time horizon: Focuses on weeks, months, or years ahead
  • Goal: Ensure you can handle expected growth

Figure 1: Scalability (planned growth) vs Elasticity (automatic adjustment)

What is Elasticity?

Elasticity is the ability to automatically add or remove resources in real-time based on current demand. It's about right-sizing your infrastructure dynamically.

Key characteristics:

  • Always automatic: Triggered by metrics like CPU usage or request count
  • Real-time: Responds to spikes and drops as they happen
  • Goal: Optimize both performance and cost

💡 Key Difference: Scalability asks "Can we grow?", Elasticity asks "Can we grow AND shrink automatically?"

Real-World Examples

Scalability Example: Your e-commerce site has 2 servers handling 10,000 daily visitors. Analytics show traffic growing 20% monthly. You add 3 more servers next month to prepare for growth.

Elasticity Example: Your video streaming service runs on 5 servers normally. When a popular show releases, AWS Auto Scaling automatically launches 15 more servers. After 2 hours, viewership drops and Auto Scaling terminates 12 servers, keeping only 8 running.

Side-by-Side Comparison

Feature Scalability Elasticity
Definition Can grow to handle workload Automatically adjusts to current demand
Timing Planned/Manual Real-time/Automatic
Trigger Human decision Metric-based (CPU, memory, requests)
Direction Usually grows (scale up/out) Grows AND shrinks (bi-directional)
Goal Capacity management Cost + Performance optimization
Example Adding servers for holiday season Auto Scaling based on CPU usage

AWS Implementation

In AWS:

  • Scalability: You manually upgrade an EC2 instance from t3.medium to t3.large, or add more instances to your load balancer
  • Elasticity: You configure AWS Auto Scaling to launch instances when CPU exceeds 70% and terminate them when it drops below 30%

✅ Quick Memory Trick:

Scalability = "Can we handle MORE?" (planned growth)

Elasticity = "Can we handle MORE and LESS automatically?" (automatic adjustment)

📐 Types of Scaling: Vertical and Horizontal

The Building Analogy

🏢 Understanding Scaling with Buildings:

Vertical Scaling is like making your building taller - you add more floors to the SAME building. The building gets bigger, but it's still one building.

Horizontal Scaling is like building more buildings next to each other - instead of making one building taller, you construct multiple buildings of the same size.

Vertical Scaling (Scale-Up / Scale-Down)

Vertical scaling means increasing or decreasing the resources of a single server or instance. You're making one machine more powerful.

What you can scale vertically:

  • CPU: More processor cores for faster computation
  • RAM: More memory to handle larger datasets
  • Storage: Bigger hard drives for more data
  • Network: Higher bandwidth for faster transfers

Figure 2: Vertical Scaling - Upgrading a single server's resources

Real Example: Your database server has 16GB RAM but keeps running out of memory. You upgrade it to 32GB RAM. Same server, more powerful.

Advantages of Vertical Scaling

  • ✅ Easy to implement: Just change instance type in AWS
  • ✅ No application changes: Your software doesn't need modification
  • ✅ Simpler architecture: Everything runs on one machine
  • ✅ Better for databases: Transactions stay on one server

Disadvantages of Vertical Scaling

  • ❌ Physical limits: There's a maximum instance size you cannot exceed
  • ❌ Downtime: Usually requires stopping the instance to upgrade
  • ❌ Single point of failure: If that one server fails, everything stops
  • ❌ Expensive: Larger instances cost significantly more

Horizontal Scaling (Scale-Out / Scale-In)

Horizontal scaling means adding or removing multiple servers to distribute the workload. You're adding more machines instead of making one machine bigger.

Figure 3: Horizontal Scaling - Adding more identical servers

Real Example: Your web application runs on 2 servers. Traffic increases, so you add 3 more identical servers behind a load balancer. Now you have 5 servers sharing the work.

Advantages of Horizontal Scaling

  • ✅ Virtually unlimited: You can keep adding servers without hitting a ceiling
  • ✅ High availability: If one server fails, others continue working
  • ✅ No downtime: Add/remove servers while others handle traffic
  • ✅ Cost-effective: Use many small instances instead of one giant one
  • ✅ Perfect for web apps: Most modern applications scale horizontally

Disadvantages of Horizontal Scaling

  • ❌ Application complexity: Your app must support distributed architecture
  • ❌ State management: Need external session storage (can't store on single server)
  • ❌ Load balancer required: Must distribute traffic across servers
  • ❌ Data consistency: Coordinating between servers is complex

How AWS Implements Horizontal Scaling

AWS makes horizontal scaling easy with Auto Scaling Groups and Elastic Load Balancers:

Traffic Flow with Horizontal Scaling:

User Requests  →  Load Balancer  →  Distributes to:
                        |
          ┌─────────────┼─────────────┐
          ↓             ↓             ↓
      Server 1      Server 2      Server 3
      (EC2-1)       (EC2-2)       (EC2-3)
      
      Health: ✓     Health: ✓     Health: ✓
      
Auto Scaling monitors CPU:
- If CPU > 70% → Launch more servers
- If CPU < 30% → Terminate excess servers

When to Use Each Approach

✅ Use Vertical Scaling When:

  • Running a database that needs transactions on one server
  • You have a monolithic application (all code in one place)
  • Quick fix needed and you're hitting CPU/memory limits
  • Application can't be distributed across servers

🔄 Use Horizontal Scaling When:

  • Building web applications or APIs
  • Need high availability (no single point of failure)
  • Traffic varies significantly throughout the day
  • Want to optimize costs (pay for what you use)
  • Application is already stateless or can be made stateless

Combining Both Approaches

Modern architectures often use BOTH:

  • Database tier: Vertical scaling (one powerful database server)
  • Application tier: Horizontal scaling (many web servers behind load balancer)
  • Caching tier: Horizontal scaling (distributed cache nodes)

💡 Pro Tip: Start with horizontal scaling architecture from day one, even if you're running just 2 servers. It's much easier to scale later than to re-architect your entire application!

☁️ What is AWS?

Amazon Web Services Explained

Amazon Web Services (AWS) is a cloud computing platform that provides on-demand IT resources over the internet with pay-as-you-go pricing.

Think of AWS like a massive digital utility company. Just like you plug into electricity without building a power plant, you can use computing power without buying servers.

What AWS Provides

Instead of buying and managing physical hardware, you get access to:

  • Compute: Virtual servers (EC2) that run your applications
  • Storage: Cloud storage (S3) for files, images, videos, backups
  • Databases: Managed databases (RDS) without server maintenance
  • Networking: Virtual networks (VPC) for secure communication
  • And 200+ more services: Machine learning, analytics, IoT, security tools

Brief History

AWS launched in 2006 with two services: S3 (storage) and EC2 (virtual servers). Amazon built this infrastructure for their own e-commerce site and realized they could offer it to everyone.

Today, AWS is the leading cloud provider globally, operating in over 30 geographic regions worldwide.

The Pay-As-You-Go Model

💰 Traditional Way (Before Cloud):

Buy 10 servers for $50,000 → Pay electricity → Pay maintenance → Servers sit idle 70% of the time → Money wasted

💰 AWS Way (Cloud):

Use 10 servers when you need them → Pay only for hours used → Scale down to 2 servers when idle → Save 80% on costs

You pay for compute time by the second, storage by the GB, and data transfer by the GB. No upfront costs, no long-term commitments.

🌍 AWS Global Infrastructure Overview

What is Global Infrastructure?

AWS Global Infrastructure is the physical network of data centers, servers, and networking equipment distributed worldwide that powers all AWS services.

Imagine AWS as a global network of supermarkets. Instead of one giant store in Seattle, they've built stores in every major city worldwide so customers can shop close to home.

Why Global Infrastructure Matters

Having infrastructure spread globally enables:

  • Low Latency: Users connect to nearby data centers for faster response
  • High Availability: If one location fails, others keep running
  • Data Compliance: Keep customer data in specific countries (legal requirement)
  • Disaster Recovery: Backup your data across continents

Infrastructure Components Hierarchy

AWS infrastructure has four main layers:

🌐 Global Level
    │
    ├── 📍 Regions (30+ worldwide)
    │      │
    │      └── 🏢 Availability Zones (2-6 per Region)
    │             │
    │             └── 💾 Data Centers (multiple per AZ)
    │
    ├── 📡 Edge Locations (400+ worldwide)
    │
    ├── 🏙️ Local Zones (metro areas)
    │
    └── 📱 Wavelength Zones (5G networks)

Key Design Principles

AWS built this infrastructure following these principles:

  1. Isolation: Each Region operates independently - failures don't cascade across Regions
  2. Redundancy: Multiple copies of everything at every layer
  3. Performance: High-speed private network connections between components
  4. Security: Physical security, network isolation, and encryption throughout
  5. Compliance: Meet data sovereignty requirements for different countries

📍 AWS Regions Explained

What is an AWS Region?

A Region is a geographic area where AWS has multiple isolated data center clusters called Availability Zones. Each Region is completely independent from other Regions.

🌎 The Country Analogy:

Think of AWS Regions like different countries. Each country (Region) has its own government (infrastructure), laws (compliance rules), and economy (pricing). What happens in France doesn't affect Germany.

Similarly, us-east-1 (Virginia) and eu-west-1 (Ireland) are completely separate - an outage in Virginia won't affect Ireland.

Region Examples

Common AWS Regions:

  • us-east-1: US East (N. Virginia) - Oldest and largest
  • us-west-2: US West (Oregon)
  • eu-west-1: Europe (Ireland)
  • ap-south-1: Asia Pacific (Mumbai)
  • ap-southeast-1: Asia Pacific (Singapore)

Figure 5: AWS Region structure with multiple Availability Zones

Why Multiple Regions?

1. Data Residency Compliance

Many countries require customer data to remain within national borders for privacy and legal reasons. EU GDPR, for example, requires European citizen data to stay in Europe.

2. Latency Reduction

Users in India connecting to Mumbai Region get 20-50ms latency. Same users connecting to Virginia Region get 200-300ms latency. Closer = Faster.

3. Disaster Recovery

If an earthquake damages data centers in California, your backup in Tokyo keeps running. Regional isolation protects against regional disasters.

How to Choose a Region

✅ Region Selection Criteria:

  1. Proximity to users: Choose Region closest to your customers
  2. Service availability: Not all services available in all Regions
  3. Pricing: Virginia (us-east-1) is usually cheapest
  4. Compliance: Legal requirements may dictate Region

Important Region Characteristics

  • ✅ Fully isolated: Resources in one Region don't automatically replicate to other Regions
  • ✅ Independent pricing: Each Region has different prices
  • ✅ Separate accounts: You can create resources in multiple Regions with one AWS account
  • ✅ Data stays put: AWS never moves data between Regions unless you explicitly configure it

⚠️ Common Mistake: Students often think launching an EC2 instance makes it available globally. Wrong! When you launch in us-east-1, it only exists in us-east-1. To serve global users, you need multi-region deployment.

🏢 Availability Zones: Your High Availability Secret

What is an Availability Zone?

An Availability Zone (AZ) is one or more discrete data centers with redundant power, networking, and cooling within an AWS Region. Each Region has minimum 3 AZs.

🏦 The Bank Branch Analogy:

Imagine a city (Region) with 3 bank branches (AZs). Each branch:

  • Has its own building, vault, and staff (independent infrastructure)
  • Connected to other branches with secure communication lines (private network)
  • If one branch has a power outage, customers can still bank at the other two (high availability)

Similarly, if one AZ fails (power, network, disaster), your resources in other AZs keep running.

How Availability Zones Work

Each AZ has:

  • Independent power: Separate utility connections + backup generators + UPS systems
  • Independent cooling: Own HVAC systems to keep servers from overheating
  • Independent networking: Multiple internet service providers
  • Physical separation: Located miles apart (exact distance is secret for security)

Figure 6: Availability Zone architecture with independent infrastructure and redundant connections

AZ Naming Convention

AZs are named with Region code + letter:

  • us-east-1a = Availability Zone A in US East (Virginia)
  • us-east-1b = Availability Zone B in US East (Virginia)
  • us-east-1c = Availability Zone C in US East (Virginia)

🔐 Security Feature: AZ names are randomized per AWS account to prevent all customers from concentrating resources in the same physical data center. Your us-east-1a might be different physical location than another customer's us-east-1a.

The Magic of Multi-AZ Deployment

Here's where AZs become powerful for high availability:

Single-AZ Deployment (Bad):
┌─────────────────────────┐
│  us-east-1a (AZ 1)      │
│  ├── Web Server 1       │
│  ├── Web Server 2       │
│  └── Database           │
└─────────────────────────┘

❌ If AZ 1 fails → Everything goes down

Multi-AZ Deployment (Good):
┌─────────────────────┐  ┌─────────────────────┐  ┌─────────────────────┐
│  us-east-1a (AZ 1)  │  │  us-east-1b (AZ 2)  │  │  us-east-1c (AZ 3)  │
│  ├── Web Server 1   │  │  ├── Web Server 2   │  │  ├── Web Server 3   │
│  └── DB Primary     │  │  └── DB Standby     │  │  └── DB Standby     │
└─────────────────────┘  └─────────────────────┘  └─────────────────────┘
         ↓                         ↓                         ↓
              Load Balancer distributes traffic

✅ If AZ 1 fails → AZ 2 and AZ 3 continue serving users

Real-World Scenario

📖 E-Commerce Site Example:

You're running an online store. Here's your multi-AZ setup:

  • AZ 1: 3 web servers + primary database
  • AZ 2: 3 web servers + standby database
  • AZ 3: 3 web servers + standby database

What happens when AZ 1 loses power?

  1. Load balancer detects AZ 1 servers aren't responding
  2. Automatically routes ALL traffic to AZ 2 and AZ 3
  3. Database automatically promotes AZ 2 standby to primary
  4. Customers continue shopping - they notice nothing!

Result: Zero downtime, zero data loss, zero customer impact

AZ Connectivity

Availability Zones within a Region are connected by redundant, high-speed, low-latency private network links. This enables:

  • Fast data replication: Database changes sync to standby in milliseconds
  • Load balancing: Traffic distributes evenly across AZs
  • Free data transfer: No charges for traffic between AZs in same Region

Best Practices

✅ Multi-AZ Architecture Guidelines:

  1. Always use at least 2 AZs for production workloads
  2. Distribute resources evenly across AZs
  3. Use Elastic Load Balancer to route traffic across AZs
  4. Enable Multi-AZ for databases (RDS, DynamoDB)
  5. Test failover regularly by simulating AZ failure

📡 Edge Locations and Content Delivery

What Are Edge Locations?

Edge locations are data centers optimized for caching and delivering content to users with the lowest possible latency. Unlike Regions which run all AWS services, edge locations serve specific purposes.

📦 The Pizza Delivery Analogy:

Without Edge Locations: Everyone orders pizza from the main kitchen in Virginia. If you're in Tokyo, your pizza arrives cold after flying across the ocean.

With Edge Locations: The kitchen pre-delivers popular pizzas to local mini-kitchens (edge locations) in every city. Tokyo customers get hot pizza from Tokyo location in 10 minutes!

Edge locations cache (store copies of) your content close to users worldwide.

How Many Edge Locations?

AWS operates 400+ edge locations in over 90 cities across 48 countries. Far more than the 30+ Regions!

Why so many? Because content delivery needs proximity. A user in Mumbai shouldn't download files from Virginia when there's an edge location 5 miles away.

Figure 7: Edge locations (many, focused on population centers) vs Regions (fewer, full infrastructure)

Amazon CloudFront: The Primary Edge Service

Amazon CloudFront is AWS's Content Delivery Network (CDN) that uses edge locations to cache and serve content globally.

How CloudFront Works:

Step 1: You upload website files to S3 in Virginia
Step 2: You configure CloudFront to distribute those files
Step 3: CloudFront automatically copies files to edge locations worldwide

Benefits:

  • ✅ Reduced latency - content serves from nearby location
  • ✅ Lower origin load - edge serves cached copies
  • ✅ Improved performance - faster page loads globally
  • ✅ Cost savings - less data transfer from origin

What Content Gets Cached?

CloudFront excels at caching:

  • Static files: Images, videos, CSS, JavaScript, fonts
  • Software downloads: Installers, mobile apps, game clients
  • Streaming media: Live and on-demand video
  • API responses: Can cache GET requests (configurable)

Other Edge Location Services

AWS Global Accelerator

Uses edge locations as entry points for TCP/UDP traffic. Instead of public internet routing, traffic enters AWS network at nearest edge and travels on AWS's private backbone.

Result: Up to 60% performance improvement and consistent routing.

Lambda@Edge

Runs serverless functions at edge locations. You can:

  • Modify requests/responses before reaching origin
  • A/B test different content versions
  • Personalize content based on user location
  • Implement security headers

💡 Key Difference:

Regions = Full AWS infrastructure, run any service

Edge Locations = Lightweight, optimized for caching and content delivery only

🎯 Specialized Infrastructure: Local Zones, Wavelength, Outposts

AWS Local Zones

Local Zones extend AWS infrastructure to specific metropolitan areas, providing single-digit millisecond latency for users in those cities.

🏙️ The Local Office Analogy:

Your company headquarters is in Virginia (Region). You open satellite offices in Los Angeles, Miami, and Boston (Local Zones) so employees in those cities don't need to commute to Virginia for work.

Local Zones bring AWS compute closer to specific metros.

What's Available: Subset of services like EC2, EBS, VPC, ELB

Use Cases:

  • Gaming servers requiring sub-10ms latency
  • Live video streaming and production
  • Real-time trading applications
  • AR/VR applications

Example: us-west-2-lax-1 = Local Zone in Los Angeles, connected to us-west-2 (Oregon) Region

AWS Wavelength Zones

Wavelength Zones deploy AWS compute and storage inside telecommunications providers' 5G networks. This achieves ultra-low latency for mobile devices.

Figure 8: Wavelength Zone at 5G tower base for ultra-low latency mobile applications

Latency Achievement: Single-digit milliseconds (often <5ms)< /p>

Use Cases:

  • Mobile gaming with real-time multiplayer
  • Autonomous vehicles needing instant data processing
  • Industrial IoT and smart factories
  • Augmented reality on mobile devices

How It Works: AWS infrastructure literally sits at cellular network tower sites. Mobile data never leaves telecom network - it processes right there.

AWS Outposts

AWS Outposts brings AWS hardware and services to your on-premises data center. AWS delivers, installs, and manages the equipment - you just use it.

🏢 The Hybrid Solution:

You have:

  • Legacy systems that MUST stay on-premises (regulations, legacy integrations)
  • New cloud-native applications you want to run

Outposts lets you run AWS services on-premises with consistent AWS experience everywhere.

What You Get:

  • Physical rack of AWS hardware in your data center
  • Same AWS APIs, tools, and services
  • AWS manages hardware, updates, maintenance
  • Connects to AWS Region for extended services

Use Cases:

  • Financial services with data residency requirements
  • Healthcare protecting patient data on-premises
  • Manufacturing with low-latency factory floor needs
  • Government compliance requiring on-premises infrastructure

🔗 How Everything Connects

Within a Region: High-Speed Private Network

Availability Zones within the same Region connect via redundant, dedicated fiber optic links with bandwidth exceeding 100 Gbps.

This private network provides:

  • Low latency: Typically sub-millisecond between AZs
  • High bandwidth: Massive data transfer capacity
  • No cost: Data transfer between AZs in same Region is free
  • Security: Traffic never touches public internet

Figure 9: Intra-Region connectivity with redundant high-speed links

Why This Matters: You can replicate databases synchronously between AZs (zero data loss) because latency is so low.

Between Regions: Intentionally Isolated

AWS Regions are completely independent and isolated - there is no automatic connectivity or data replication between Regions.

⚠️ Important: Launching an EC2 instance in us-east-1 does NOT make it available in eu-west-1. Resources are Region-specific.

To Connect Regions, You Must Configure:

  • S3 Cross-Region Replication: Automatically copy objects between Regional buckets
  • VPC Peering: Private network connection between VPCs in different Regions
  • Transit Gateway: Hub-and-spoke connectivity across Regions
  • Application-level: Your code makes cross-region API calls

Inter-Region Considerations:

  • ❌ Higher latency: US-to-Europe = 80-100ms, US-to-Asia = 150-200ms
  • ❌ Data transfer costs: Charged per GB between Regions
  • ✅ Fault isolation: Region failure doesn't affect other Regions

Global Services Architecture

Some AWS services operate globally rather than regionally:

  • Route 53 (DNS): Global service resolving domains worldwide
  • CloudFront (CDN): Edge locations coordinate globally
  • IAM: Users and permissions sync across all Regions
  • AWS Organizations: Centralized multi-account management

💡 How to Know if Service is Regional or Global:

In AWS Console, look at the Region selector (top right):

  • If it shows a specific Region → Regional service
  • If it shows "Global" → Global service

The AWS Global Backbone

AWS operates a private global network backbone connecting all Regions and edge locations. This provides:

  • More reliable routing than public internet
  • Consistent performance
  • DDoS protection
  • Traffic encryption in transit

Services like Global Accelerator and CloudFront leverage this backbone for improved performance.

📝 Overall Summary

Here's everything we covered about scalability and AWS global infrastructure:

  • Scalability vs Elasticity: Scalability handles planned growth manually, elasticity adjusts automatically in real-time based on demand metrics. Both solve resource management but at different timescales.
  • Vertical Scaling: Upgrading single server resources (CPU, RAM) has physical limits and potential downtime, but works with any application architecture. Best for databases and monolithic apps.
  • Horizontal Scaling: Adding more servers provides unlimited capacity and high availability but requires distributed application design and load balancing. Best for web tiers and stateless services.
  • AWS Platform: Cloud computing platform launched in 2006, now offering 200+ services with pay-as-you-go pricing, eliminating capital expenditure on hardware.
  • AWS Regions: 30+ independent geographic areas worldwide, each containing multiple Availability Zones. Resources stay in chosen Region unless explicitly replicated elsewhere.
  • Availability Zones: Isolated data centers within Regions (minimum 3 per Region) with independent power, cooling, and networking. Deploy across multiple AZs for high availability.
  • Edge Locations: 400+ global points of presence for content caching and delivery through CloudFront CDN, dramatically reducing latency for end users.
  • Local Zones: Metro-area infrastructure extensions providing sub-10ms latency for specific cities, ideal for gaming, streaming, and real-time applications.
  • Wavelength Zones: AWS compute at 5G cellular network sites, enabling sub-5ms latency for mobile applications like AR/VR and autonomous vehicles.
  • AWS Outposts: AWS-managed hardware in your on-premises data center for hybrid cloud scenarios requiring local processing with cloud integration.
  • Regional Connectivity: AZs within Region connect via high-speed private links (sub-millisecond latency, free data transfer), enabling synchronous replication.
  • Inter-Region Isolation: Regions operate independently - cross-region connectivity and replication must be explicitly configured, incurs costs and higher latency.

  2. Go to EC2 Dashboard

  4. Now switch to "Asia Pacific (Mumbai)" - ap-south-1
  5. Check EC2 Dashboard again

💡 Key Learning: Notice resources in Virginia don't show in Mumbai? That's Regional isolation! Each Region is independent.

Step 3: View Availability Zones

  1. Stay in any Region (e.g., US East)
  2. In EC2 Console, click "Subnets" in left sidebar
  3. Look at the "Availability Zone" column
  4. Count different AZs (like us-east-1a, us-east-1b, us-east-1c)
  5. How many AZs does this Region have?

Step 4: Test Latency to Different Regions

  1. Open CloudPing.info (external site that pings AWS Regions)
  2. View latency from your location to different Regions
  3. Which Region has lowest latency for you?
  4. Which has highest?

✅ Success Indicators:

  • You can identify at least 5 different Regions
  • You understand each Region has different resources
  • You've seen 2-3 AZs within a Region
  • You know which Region is closest to you

Project 3: Simulate Multi-AZ High Availability

🎯 Objective: Design a multi-AZ architecture on paper

⏱️ Time: 30-40 minutes

💰 Cost: Free (planning exercise)

The Scenario

You're deploying an e-commerce website that must be highly available. The architecture includes:

  • 3 web servers
  • 1 database
  • 1 load balancer

Your job: Design how to deploy these across 3 Availability Zones.

Step 1: Single-AZ Design (Bad Practice)

Draw a diagram showing all resources in ONE Availability Zone:

┌─────────────────────────────┐
│  AZ 1: us-east-1a           │
│  ├── Load Balancer          │
│  ├── Web Server 1           │
│  ├── Web Server 2           │
│  ├── Web Server 3           │
│  └── Database               │
└─────────────────────────────┘

Problem: What if AZ 1 fails? ___________________

Step 2: Multi-AZ Design (Best Practice)

Redesign to spread across 3 AZs:

┌───────────┐  ┌───────────┐  ┌───────────┐
│  AZ 1     │  │  AZ 2     │  │  AZ 3     │
│ Web Srv 1 │  │ Web Srv 2 │  │ Web Srv 3 │
│ DB Primary│  │ DB Standby│  │           │
└───────────┘  └───────────┘  └───────────┘
      ↑              ↑              ↑
      └──────── Load Balancer ──────┘
           (Spans all AZs)

Step 3: Failure Scenario Analysis

Answer these questions about your multi-AZ design:

  1. AZ 1 fails: What happens?
    Answer: ________________________________
  2. Web Server 2 crashes: Impact?
    Answer: ________________________________
  3. Database primary fails: Recovery?
    Answer: ________________________________

✅ Correct Answers:

  1. AZ 2 and AZ 3 continue serving traffic, database promotes AZ 2 standby to primary
  2. Load balancer detects failure, routes traffic to Web Server 1 and 3
  3. Database automatically failsover to standby in AZ 2 within 60-120 seconds

Step 4: Cost Analysis

Calculate approximate costs (use AWS Pricing Calculator):

  • Single-AZ: 3 t3.micro instances + 1 db.t3.micro = $____/month
  • Multi-AZ: 3 t3.micro instances + 1 Multi-AZ database = $____/month
  • High Availability Premium: $____/month extra

💡 Trade-off: Multi-AZ costs ~50-100% more, but gives you near-zero downtime. Worth it for production!
