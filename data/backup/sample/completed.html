👤 Changing File Ownership

The Linux File Philosophy

One of the fundamental principles in Linux is that everything is treated as a file — programs, directories, devices, network connections, and configuration files are all represented as files in the filesystem.

Each file in Linux has two levels of ownership:

  1. User (Owner): The individual user who owns the file
  2. Group: A collection of users who share common access permissions

Figure 1: Three-level file access model in Linux

Ownership defines who controls the file, who can access it, and who can modify it. This is critical for security and proper system administration.

Understanding the chown Command

chown stands for "change owner" and is the primary command for changing file and directory ownership in Linux.

🔒 Security Note: Only the root user or users with sudo privileges can change file ownership. Regular users cannot change ownership of files they don't own.

Basic Syntax

# Change owner onlysudo chown newowner filename# Change owner and groupsudo chown newowner:newgroup filename# Change group onlysudo chown :newgroup filename# Change owner, keep existing groupsudo chown newowner: filename

Command Options

OptionPurposeExample
-RRecursive (apply to directory and all contents)sudo chown -R user:group /project
-vVerbose (display detailed output)sudo chown -v user file.txt
-cReport only when changes are madesudo chown -c user:group file.txt
--referenceUse ownership from reference filesudo chown --reference=ref.txt target.txt

Practical Examples

Example 1: Change File Owner

# Create a test fileecho "Hello" > file1.txt# Check current ownershipls -l file1.txt# Output: -rw-r--r-- 1 ec2-user ec2-user 6 Oct 31 10:00 file1.txt# Change owner to vikramsudo chown vikram file1.txt# Verify changels -l file1.txt# Output: -rw-r--r-- 1 vikram ec2-user 6 Oct 31 10:00 file1.txt

Example 2: Change Owner and Group

# Change both owner and group to vikramsudo chown vikram:vikram file1.txt# Verifyls -l file1.txt# Output: -rw-r--r-- 1 vikram vikram 6 Oct 31 10:00 file1.txt# Change back to ec2-usersudo chown ec2-user:ec2-user file1.txt

Example 3: Recursive Directory Ownership

# Create project directory with filesmkdir -p /home/ec2-user/projectstouch /home/ec2-user/projects/file1.txttouch /home/ec2-user/projects/file2.txt# Change ownership of entire directory recursivelysudo chown -R vikram:developers /home/ec2-user/projects# Verify all files changedls -lR /home/ec2-user/projects

✅ When to use -R: The recursive flag is essential when you have a directory structure. Without it, only the directory itself changes ownership, not its contents.

Real-World Use Case: Web Server File Ownership

This is one of the most common scenarios where you'll need to change file ownership in AWS environments.

The Problem

❌ Scenario: You upload web content to your EC2 instance as the ec2-user, but when you try to access your website, you get permission errors. Why?

Web servers like Nginx and Apache run as system users (nginx and apache respectively), not as ec2-user. These system users need ownership of the web files to read and serve them.

Figure 2: Web server ownership mismatch problem

The Solution

✅ Fix: Change ownership of web files to match the web server user.

# For Nginx web serversudo chown -R nginx:nginx /usr/share/nginx/html# For Apache web serversudo chown -R apache:apache /var/www/html# Verify ownership changedls -l /usr/share/nginx/html

Step-by-Step: Apache Web Server Setup

# Step 1: Install Apachesudo yum install httpd -y# Step 2: Create web content as ec2-userecho "Welcome to my website" | sudo tee /var/www/html/index.html# Step 3: Check ownership (will be root from sudo tee)ls -l /var/www/html/index.html# Output: -rw-r--r-- 1 root root 24 Oct 31 10:00 index.html# Step 4: Change ownership to apache usersudo chown apache:apache /var/www/html/index.html# Step 5: Start Apachesudo systemctl start httpd# Step 6: Test - Apache can now read the file!

System Users Explained

When you install services, they create system users — special user accounts that run background services. These are not login users; they exist solely to run specific processes.

💡 Common System Users:

  • nginx: Nginx web server
  • apache/httpd: Apache web server
  • mysql: MySQL database
  • docker: Docker container runtime
  • jenkins: Jenkins CI/CD server

These system users follow the principle of least privilege — they only have permissions necessary for their specific task, improving security.

Use Case: Team Collaboration

When multiple developers work on the same project, proper ownership and group permissions ensure everyone has appropriate access.

# Create a developers groupsudo groupadd developers# Add users to the groupsudo usermod -aG developers alicesudo usermod -aG developers bobsudo usermod -aG developers charlie# Create project directorysudo mkdir -p /opt/project# Change group ownershipsudo chown -R :developers /opt/project# Set group write permissionssudo chmod -R 775 /opt/project# Now all developers in the group can read, write, and execute

Figure 3: Group-based collaboration model

Troubleshooting with chown

When encountering permission errors, follow this systematic approach:

Troubleshooting Steps

  1. Identify the error: Check service logs for permission denied messages
  2. Check current ownership: Use ls -l to see who owns the file
  3. Identify the service user: Check service configuration or process list
  4. Change ownership: Use chown to match the service user
  5. Verify fix: Restart service and test functionality

Example: Nginx Troubleshooting

# Step 1: Nginx returns 403 Forbidden error# Check error logsudo tail /var/log/nginx/error.log# Output: [error] 1234#0: *1 open() "/usr/share/nginx/html/index.html" failed (13: Permission denied)# Step 2: Check file ownershipls -l /usr/share/nginx/html/index.html# Output: -rw-r--r-- 1 ec2-user ec2-user 100 Oct 31 10:00 index.html# Step 3: Identify Nginx userps aux | grep nginx# Output: nginx    1234  ... nginx: worker process# Step 4: Change ownership to nginxsudo chown nginx:nginx /usr/share/nginx/html/index.html# Step 5: Verify - reload page, now works!

Best Practices

  • Always use sudo when changing ownership
  • Use -R flag for directories to ensure all contents are updated
  • Match ownership to the service user (nginx for Nginx, apache for Apache)
  • Document ownership changes in deployment scripts
  • Use groups for team collaboration rather than individual user ownership
  • Test after changing ownership to ensure services still work
  • Be cautious with recursive changes on system directories

❌ Common Mistake: Running chown -R user:group / (entire filesystem). This breaks the system! Always specify the exact directory you need to change.

📜 Shell Scripting Fundamentals

What is a Shell Script?

A shell script is a file containing a series of commands written for the Linux shell. Instead of typing commands manually one by one, you write them in a file with a .sh extension, and the shell executes them automatically in sequence.

⚡ The Power of Automation: Shell scripts transform repetitive manual tasks into automated, consistent, error-free processes. They're the foundation of DevOps and infrastructure automation.

Why Shell Scripting Matters

Consider this scenario: You need to set up 10 web servers, each requiring:

  1. System updates
  2. Apache installation
  3. Apache start and enable
  4. Custom web page creation
  5. Firewall configuration

Manual approach: 50+ commands × 10 servers = 500 commands. Time: ~2 hours. Error rate: High.

Script approach: Write once, run 10 times. Time: 15 minutes. Error rate: Minimal.

Figure 4: Manual vs automated server configuration

Shell Script Structure

Anatomy of a Shell Script

#!/bin/bash# This is a comment explaining what the script does# Update system packagesecho "Updating system..."sudo yum update -y# Install Apache web serverecho "Installing Apache..."sudo yum install httpd -y# Start and enable Apacheecho "Starting Apache service..."sudo systemctl start httpdsudo systemctl enable httpd# Create welcome pageecho "Creating web page..."echo "Welcome to WinSys!" | sudo tee /var/www/html/index.htmlecho "Setup complete!"

The Shebang Line

The shebang (pronounced "hash-bang") is the #!/bin/bash at the beginning of a script. It consists of:

  • #! — Tells the operating system this is an interpreted script
  • /bin/bash — Path to the Bash shell interpreter

💡 Why it's called "shebang":# = "hash" or "sharp", ! = "bang". Together: "hash-bang" → "shebang".

Different Interpreters

#!/bin/bash        # Bash shell (most common for Linux)#!/bin/sh          # Bourne shell (portable across Unix systems)#!/usr/bin/python3 # Python 3 interpreter#!/usr/bin/node    # Node.js JavaScript interpreter#!/usr/bin/perl    # Perl interpreter

The shebang line tells the operating system which program should interpret and execute the script. Without it, the system doesn't know how to run your script.

Creating and Running Scripts

Method 1: Step-by-Step Creation

# Step 1: Create script file using nano editornano setup.sh# Step 2: Write your script (in nano)#!/bin/bashecho "Updating system..."sudo yum update -yecho "System updated successfully!"# Step 3: Save and exit (Ctrl+X, then Y, then Enter)# Step 4: Make script executablechmod u+x setup.sh# Step 5: Verify execute permission was addedls -l setup.sh# Output: -rwxr--r-- 1 ec2-user ec2-user 123 Oct 31 10:00 setup.sh#          ^^ Notice the 'x' showing execute permission# Step 6: Run the script./setup.sh

Method 2: Quick One-Liner Creation

# Create script with single commandcat > quick-script.sh << 'EOF'#!/bin/bashecho "Quick script created!"dateEOF# Make executable and runchmod u+x quick-script.sh && ./quick-script.sh

Script Execution Methods

There are two primary ways to execute shell scripts:

Method 1: Direct Execution (./script.sh)

./setup.sh

Requirements:

  • ✅ Script must have execute permission (chmod u+x)
  • ✅ Script must have shebang line
  • ✅ Script looks for shebang to determine interpreter

Method 2: Explicit Interpreter (bash script.sh)

bash setup.sh

Requirements:

  • ❌ Execute permission not required
  • ❌ Shebang line not required (overridden by bash command)
  • ✅ Directly uses bash interpreter

Common Permission Issues and Solutions

Problem 1: Redirect with Sudo

❌ This FAILS:

sudo echo "Welcome" > /var/www/html/index.html# Error: Permission denied

Why? Sudo only applies to echo, not to the redirect (>). The redirect runs as your user, who can't write to /var/www/html/.

✅ Solutions:

# Solution 1: Use tee commandecho "Welcome" | sudo tee /var/www/html/index.html# Solution 2: Use tee to appendecho "Welcome" | sudo tee -a /var/www/html/index.html# Solution 3: Hide tee outputecho "Welcome" | sudo tee /var/www/html/index.html > /dev/null

How tee Works

The tee command reads from standard input and writes to both standard output and files. When combined with sudo, it gives you root privileges for file writing.

Figure 6: How the tee command works with sudo

# What happens with: echo "text" | sudo tee file.txt# 1. echo outputs "text"# 2. Pipe (|) sends "text" to tee# 3. sudo tee runs with root privileges# 4. tee writes "text" to file.txt (as root)# 5. tee also outputs "text" to terminal

Script Best Practices

  1. Always include shebang:#!/bin/bash at the very first line
  2. Add comments: Explain what each section does
  3. Use descriptive names:setup-webserver.sh not script1.sh
  4. Show progress: Echo statements to indicate what's happening
  5. Test before deploying: Run on test systems first
  6. Make executable:chmod u+x script.sh before running
  7. Handle errors: Check if commands succeeded before continuing
  8. Use absolute paths:/usr/bin/python3 not python3

Advanced: Error Handling

#!/bin/bash# Exit immediately if a command failsset -e# Function to handle errorserror_exit() {echo "Error: $1" >&2exit 1}# Update system with error checkingecho "Updating system..."sudo yum update -y || error_exit "Failed to update system"# Install Apache with error checkingecho "Installing Apache..."sudo yum install httpd -y || error_exit "Failed to install Apache"echo "Setup completed successfully!"

💡 set -e explained: This makes your script exit immediately if any command returns a non-zero (error) status. It's like adding error checking to every line automatically.

☁️ EC2 User Data for Launch Automation

What is EC2 User Data?

EC2 User Data is a script or configuration that runs automatically when an EC2 instance launches for the first time. Think of it as a note you attach to your server saying "when you start, please do these tasks automatically."

⚡ The Automation Game-Changer: User Data eliminates the need to SSH into newly launched instances and manually configure them. Everything happens automatically during boot!

Why User Data Matters

Without User Data (Manual approach):

  1. Launch EC2 instance
  2. Wait for instance to boot (~2-3 minutes)
  3. SSH into instance
  4. Run update commands
  5. Install packages
  6. Configure services
  7. Create files
  8. Start services

Total time: 10-15 minutes per server. For 10 servers? 100-150 minutes!

With User Data (Automated approach):

  1. Launch EC2 instance with User Data script
  2. Instance boots and executes script automatically
  3. Server is ready by the time SSH access is available!

Total time: 3-5 minutes per server. For 10 servers? Still 3-5 minutes (parallel launches)!

Figure 7: User Data automation saves significant time

How User Data Works

When you launch an EC2 instance with User Data:

  1. Instance boots: AWS starts your EC2 instance
  2. Cloud-init starts: A service called cloud-init automatically runs
  3. User Data read: Cloud-init reads your User Data script
  4. Interpreter identified: Cloud-init checks the shebang line
  5. Script executes: Commands run automatically using the specified interpreter
  6. Logs created: All output is logged to /var/log/cloud-init-output.log

Figure 8: Complete EC2 User Data execution workflow

Cloud-Init: The Engine Behind User Data

Cloud-init is a Linux package that serves as the automation engine for User Data. It's a background service (daemon) that:

  • Runs automatically when EC2 instances boot for the first time
  • Reads and interprets User Data scripts
  • Executes commands using appropriate interpreters (bash, python, etc.)
  • Logs all execution details for troubleshooting
  • Configures network settings and SSH keys

💡 Think of cloud-init as: Your personal robot assistant that reads your to-do list (User Data) and completes all tasks while you're away. By the time you arrive (SSH in), everything is done!

Cloud-init is the background service that reads User Data and executes it automatically during the first boot. Without cloud-init, User Data wouldn't work.

Adding User Data to EC2

Step-by-Step: Launch with User Data

  1. Go to EC2 Console
  2. Click "Launch Instance"
  3. Configure:
    • Name and tags
    • AMI (Amazon Linux 2023)
    • Instance type (t2.micro)
    • Key pair
    • Security group (allow SSH port 22, HTTP port 80)
  4. Scroll down to "Advanced Details"
  5. Scroll to bottom → Find "User Data" text box
  6. Enter your script OR upload a file
  7. Launch instance

Important User Data Limitations

❌ Critical Limitations:

  • User Data only runs on first boot, not on restarts or reboots
  • Maximum size: 16 KB (after base64 encoding)
  • Cannot be modified after instance starts (for that specific launch)
  • No interactive prompts allowed (must be fully automated)
  • Requires internet access for package downloads

⏰ Crontab for Job Scheduling

What is Crontab?

Crontab is a Linux utility for scheduling tasks to run automatically at specific times. Think of it as an alarm clock for your Linux system that can trigger scripts, commands, or programs at scheduled intervals.

⚡ The Automation Principle: Repetitive + Manual + Time-based = Perfect candidate for crontab! Eliminate human error by automating scheduled tasks.

Real-World Analogy

Imagine you want to wake up at 6 AM every day:

Manual approach: Ask your mom to wake you at 6 AM daily

  • ✗ She might forget sometimes
  • ✗ She might wake you at 5:50 or 6:10 instead
  • ✗ Repetitive task prone to human error

Automated approach: Set an alarm clock to ring at 6 AM daily

  • ✓ Runs automatically without intervention
  • ✓ Precise timing every single day
  • ✓ No human error possible

Crontab is that alarm clock for your Linux system!

How Crontab Works

Installing and Starting Cron

On Amazon Linux 2023 and most modern Linux distributions, cron is pre-installed. However, you may need to install and start it:

💡 Daemon explained:A daemon is a background service that runs continuously, checking conditions and performing actions without user interaction. Cron daemon (crond) wakes up every minute to check if any jobs need to run.

🔗 Soft Links and Hard Links

Understanding Links in Linux

Links in Linux are shortcuts or alternate names that allow multiple names to point to the same data on disk. They're like having multiple keys to the same room or multiple shortcuts to the same program.

⚡ Why Use Links? Quick access to files in different locations without duplicating data. Essential for organizing complex directory structures and providing convenient access paths.

The Two Types of Links

Link TypeDescriptionReal-World Analogy
Hard LinkAnother name for the same file (shares same data and inode)Two doors to the same room
Soft Link (Symbolic)Shortcut that points to file's pathPost-it note with directions to the room

Hard Links Explained

What is a Hard Link?

A hard link is another name for the same file. Both the original filename and the hard link point to the exact same data on disk and share the same inode number.

💡 The Two Doors Analogy: Imagine a room with two doors. Both doors lead to the same room. If you lock one door, the room is still accessible through the other door. Similarly, if you delete one filename (hard link), the data remains accessible through other hard links.

Creating Hard Links

# Syntax: ln source_file hard_link_nameln original.txt hardlink.txt# Create file firstecho "Hello from WinSys" > original.txt# Create hard linkln original.txt hardlink.txt# View both filesls -l# Both files appear with same size# View with inode numbersls -li# Output:# 12345678 -rw-r--r-- 2 ec2-user ec2-user 18 Oct 31 10:00 original.txt# 12345678 -rw-r--r-- 2 ec2-user ec2-user 18 Oct 31 10:00 hardlink.txt#  ^^^^^^^ Same inode number!

Figure 13: Hard link structure - multiple names, same inode and data

Hard Link Characteristics

  • Share the same inode number (you can verify with ls -li)
  • Point to the same physical data on disk
  • Same file size, permissions, and timestamps
  • Data survives if original filename is deleted
  • Can only link files on the same filesystem/partition
  • Cannot link directories (only files)
  • Link count increases (shown in ls -l output)

Testing Hard Link Behavior

# Create file and hard linkecho "Test data" > original.txtln original.txt backup.txt# Read from bothcat original.txt# Output: Test datacat backup.txt# Output: Test data# Modify through hard linkecho "Updated" >> backup.txt# Check original - also updated!cat original.txt# Output:# Test data# Updated# Delete originalrm original.txt# Hard link still works!cat backup.txt# Output:# Test data# Updated

✅ Key Insight: Hard links preserve data even when the "original" is deleted because all hard links are equal - there's no concept of "original" vs "link" at the filesystem level. They all point to the same data.

Soft Links (Symbolic Links) Explained

What is a Soft Link?

A soft link (also called symbolic link or symlink) is a shortcut that points to another file's path. It's a separate small file that stores the path to the target file.

Creating Soft Links

# Syntax: ln -s target_path link_nameln -s /home/ec2-user/documents/report.pdf report-shortcut.pdf# Create file and soft link exampleecho "Original content" > /home/ec2-user/RMC/vig.txtln -s /home/ec2-user/RMC/vig.txt /root/short.txt# View with ls -l (note the arrow!)ls -l /root/short.txt# Output:# lrwxrwxrwx 1 root root 28 Oct 31 10:00 short.txt -> /home/ec2-user/RMC/vig.txt# ^ Starts with 'l' for link           ^^^ Arrow shows target

💡 Identifying Soft Links: In ls -l output, soft links are identified by three things: (1) Starts with 'l' in permissions, (2) Shows arrow (→) pointing to target, (3) Different color (typically cyan/blue) in colored terminals.

Soft Link Characteristics

  • Has its own separate inode number
  • Small file size (just stores the path string)
  • Points to file's path, not directly to data
  • Link breaks if target file is deleted
  • Can link across different filesystems/partitions
  • Can link to directories
  • Can create links to files that don't exist yet

Figure 14: Soft link structure - pointer to file path

Testing Soft Link Behavior

# Create file and soft linkmkdir -p /home/ec2-user/RMCecho "Hello World" > /home/ec2-user/RMC/vig.txtln -s /home/ec2-user/RMC/vig.txt /root/short.txt# Read through soft linquizat /root/short.txt# Output: Hello World# Check both existls -l /root/short.txt# lrwxrwxrwx ... short.txt -> /home/ec2-user/RMC/vig.txt# Delete original filerm /home/ec2-user/RMC/vig.txt# Try to read soft linquizat /root/short.txt# Error: No such file or directory# Soft link is now broken (shown in red)ls -l /root/short.txt# lrwxrwxrwx ... short.txt -> /home/ec2-user/RMC/vig.txt# (link file still exists but points to non-existent file)

❌ Broken Link: When the target file is deleted, the soft link becomes a "broken link" or "dangling symlink". The link file still exists but points nowhere. It displays in red in colored terminals.

Viewing Inode Numbers

An inode is a data structure that stores file metadata but not the filename. It's like an ID card for files containing permissions, owner, size, timestamps, and data location.

# View inode numbers with -i flagls -li# Example output:# 12345678 -rw-r--r-- 2 ec2-user ec2-user  100 Oct 31 10:00 original.txt# 12345678 -rw-r--r-- 2 ec2-user ec2-user  100 Oct 31 10:00 hardlink.txt# 87654321 lrwxrwxrwx 1 ec2-user ec2-user   12 Oct 31 10:00 softlink.txt -> original.txt## Notice: Hard links share inode 12345678#         Soft link has different inode 87654321

Practical Use Cases

Soft Link Use Cases

# 1. Quick access to deep directoryln -s /var/www/html/project/src/components /root/components# 2. Common Link Operations

# Create hard linkln source.txt hardlink.txt# Create soft linkln -s /full/path/to/source.txt softlink.txt# Overwrite existing link (force)ln -sf /new/target existing-link# Create link to directory (soft link only)ln -s /var/www/html www-shortcut# Remove link (doesn't affect target)rm link-name# Find all hard links to a file (by inode)find / -inum 12345678 2>/dev/null# Find all broken soft links in directoryfind /path -xtype l

Best Practices

  1. Use absolute paths for soft links: Prevents broken links when moving directories
  2. Use hard links for critical file backups: Data survives original deletion
  3. Use soft links for shortcuts: More flexible, easier to identify
  4. Check for broken links regularly:find -L . -type l
  5. Document link purposes: Add comments or use descriptive names
  6. Use -f flag carefully:ln -sf overwrites without confirmation
  7. Avoid circular links: Don't create link chains that loop back

❌ Common Mistake: Using relative paths in soft links. If you move the link to a different directory, relative paths break. Always use absolute paths: ln -s /full/path/to/target link

📝 Overall Summary

  • File Ownership with chown: Change file and directory ownership in Linux using chown user:group file. Only root or sudo users can change ownership. Critical for web servers (nginx, apache) which run as system users and need proper file ownership to access content. Use -R flag for recursive directory changes.
  • Shell Scripting Fundamentals: Automate repetitive tasks by writing commands in .sh files. Always start with shebang line (#!/bin/bash) to specify interpreter. Make scripts executable with chmod u+x script.sh. Execute with ./script.sh (needs permissions) or bash script.sh (doesn't need permissions). Use tee with sudo to write to protected files.
  • EC2 User Data Automation: Scripts that run automatically when EC2 launches for the first time. Maximum size 16 KB. Cloud-init is the background service that reads and executes User Data. Logs stored at /var/log/cloud-init-output.log. Only runs on first boot, not on restarts. Eliminates manual configuration after instance launch.
  • Crontab Job Scheduling: Automate time-based tasks using cron expressions with 5 fields (minute hour day month weekday). Edit with crontab -e, list with crontab -l. Cron daemon (crond) runs in background checking time every minute. Use asterisk (*) for "every" value. Use >> to append logs. Always use absolute paths in cron jobs.
  • Hard Links: Additional names for same file sharing same inode and data. Created with ln file hardlink. Data survives if any filename is deleted. Can't cross filesystems or link directories. Perfect for backups and point-in-time snapshots. Check inode with ls -li.
  • Soft Links (Symlinks): Shortcuts pointing to file paths. Created with ln -s target link. Have their own inode. Break if target is deleted. Can cross filesystems and link directories. Identified by 'l' in permissions and arrow in listings. Use for quick access and version management.
  • Key Concepts: Everything in Linux is a file. System users (nginx, apache) run services with minimal privileges following the principle of least privilege. Environment variables like EDITOR control program behavior. Automation reduces human error in repetitive tasks. Cloud-init bridges User Data to actual execution.
  • Troubleshooting Approach: Check logs first (/var/log/). Verify ownership with ls -l. Ensure services are running with systemctl status. Test scripts manually before automation. Use absolute paths to avoid environmental issues. Add comprehensive logging to all automated tasks.
  • Best Practices: Always use sudo for ownership changes. Test before deploying to production. Document your automation. Use descriptive file names. Add comments to explain complex logic. Keep scripts under version control. Backup crontab before changes. Monitor automated tasks for failures.
  • Real-World Applications: Automated server deployments with User Data. Daily database backups with cron. Web server configuration with proper ownership. Quick access to files with soft links. Disaster recovery with hard link snapshots. Self-healing infrastructure with monitoring cron jobs.
