🔷 Infrastructure as Code (IAC) Fundamentals

📖 Detailed Explanation

Infrastructure as Code (IAC) is a methodology where you manage and provision cloud infrastructure through machine-readable code files, rather than through manual processes using web consoles or physical hardware configuration.

The Traditional Manual Approach:

Without IAC, cloud engineers manually log into the AWS Console and click through various screens to create resources like EC2 instances, VPCs, S3 buckets, and databases. This process is time-consuming, error-prone, and difficult to replicate consistently across different environments.

The IAC Approach:

With IAC, you write code in a text file that describes all your infrastructure requirements. This code file is then submitted to an IAC tool (like CloudFormation or Terraform), which automatically creates all the specified resources in your AWS account. The code becomes the single source of truth for your infrastructure.

Key Benefits:

  • Consistency: Same code produces identical infrastructure every time
  • Version Control: Track changes to infrastructure over time using Git
  • Reusability: Use the same code across development, testing, and production
  • Documentation: Code serves as living documentation of your infrastructure
  • Speed: Deploy complex infrastructure in minutes instead of hours

🔑 Key Concepts

  • Declarative vs Imperative: Declarative describes desired end state; Imperative specifies exact steps to achieve it
  • Templates: Code files that define infrastructure configuration
  • Idempotency: Running the same code multiple times produces the same result
  • State Management: Tracking current infrastructure state vs desired state
  • Resource Dependencies: Defining relationships between infrastructure components

🔷 IAC Tools Overview

📖 Detailed Explanation

The IAC ecosystem includes various tools, each with specific purposes and capabilities. Understanding the different categories helps you choose the right tool for your needs.

Cloud-Specific IAC Tools:

These tools work exclusively with one cloud provider. They are deeply integrated with that provider's services and often provide the best support for native features. Examples include AWS CloudFormation (AWS only), Azure Resource Manager (Azure only), and Google Cloud Deployment Manager (GCP only).

Multi-Cloud IAC Tools:

These tools work across multiple cloud providers, allowing you to manage resources in AWS, Azure, GCP, and other platforms using a single toolset. Terraform and Pulumi are the most popular multi-cloud IAC tools.

Configuration Management Tools:

While IAC tools create infrastructure resources, configuration management tools handle software installation, updates, and configuration on servers after they're created. These include Ansible, Chef, and Puppet.

🔑 Key Concepts

  • Cloud-Specific Tools: Native tools provided by cloud vendors (CloudFormation, ARM, Deployment Manager)
  • Multi-Cloud Tools: Platform-agnostic tools that work across providers (Terraform, Pulumi)
  • Configuration Management: Tools for managing software on servers (Ansible, Chef, Puppet)
  • HCL (HashiCorp Configuration Language): Terraform's declarative language
  • YAML/JSON: Common formats for CloudFormation templates
  • Agentless vs Agent-Based: Some tools require agents on servers; others don't

🔷 AWS CloudFormation

📖 Detailed Explanation

AWS CloudFormation is AWS's native Infrastructure as Code service that allows you to model and provision AWS resources using templates. It's a fully managed service that handles the complexity of creating, updating, and deleting AWS resources in the correct order.

How CloudFormation Works:

You create a template file (in YAML or JSON format) that describes all the AWS resources you want to create. This template acts as a blueprint. You submit this template to CloudFormation, which reads it and automatically creates all specified resources in your AWS account. The collection of resources created from a template is called a "stack".

Key Features:

  • Declarative Templates: Describe what you want, not how to create it
  • Automatic Dependency Management: CloudFormation determines the correct order to create resources
  • Stack Management: Create, update, or delete entire collections of resources as a single unit
  • Rollback Protection: Automatically rolls back if creation fails
  • Change Sets: Preview changes before applying them
  • Drift Detection: Identifies manual changes made outside CloudFormation

When to Use CloudFormation:

  • Working exclusively within AWS ecosystem
  • Need deep integration with AWS services
  • Want zero cost (CloudFormation itself is free; you only pay for resources)
  • Prefer using AWS's native tooling
  • Need official AWS support for IAC implementation

🔑 Key Concepts

  • Template: YAML or JSON file describing infrastructure resources
  • Stack: Collection of AWS resources created and managed as a single unit
  • Resources: AWS services defined in your template (EC2, S3, VPC, etc.)
  • Parameters: Input values passed to templates for customization
  • Outputs: Values exported from stacks for reference by other stacks
  • Mappings: Key-value pairs for conditional resource creation
  • Change Set: Preview of proposed changes before execution
  • Drift Detection: Identifies resources modified outside CloudFormation

🔷 CloudFormation Templates

📖 Detailed Explanation

CloudFormation Templates are text files that describe your AWS infrastructure in either YAML or JSON format. Templates serve as blueprints that define what resources to create, how they should be configured, and how they relate to each other.

Template Structure:

A CloudFormation template consists of several sections:

  • AWSTemplateFormatVersion: (Optional) Specifies the template version
  • Description: (Optional) Text description of the template
  • Parameters: (Optional) Input values for customization
  • Mappings: (Optional) Key-value pairs for conditional logic
  • Resources: (Required) AWS resources to create
  • Outputs: (Optional) Values to return after stack creation

YAML vs JSON:

YAML is generally preferred for its readability and less verbose syntax. It doesn't require quotation marks or curly braces, making it cleaner. JSON is more verbose but may be preferred by teams familiar with JavaScript or when programmatically generating templates.

🔑 Key Concepts

  • Resources Section: The only required section; defines all AWS resources
  • Logical ID: Unique identifier for each resource within the template
  • Intrinsic Functions: Built-in functions like Ref, GetAtt, Join for dynamic values
  • Pseudo Parameters: AWS-provided parameters like AWS::Region, AWS::AccountId
  • Resource Properties: Configuration settings specific to each resource type
  • DependsOn: Explicitly defines resource creation order

📊 Template Example Structure

YAML Format Example:

AWSTemplateFormatVersion: '2010-09-09'
Description: 'Simple EC2 and S3 template'

Parameters:
  InstanceType:
    Type: String
    Default: t2.micro
    AllowedValues:
      - t2.micro
      - t2.small
      - t2.medium

Resources:
  MyEC2Instance:
    Type: AWS::EC2::Instance
    Properties:
      ImageId: ami-0c55b159cbfafe1f0
      InstanceType: !Ref InstanceType
      Tags:
        - Key: Name
          Value: MyServer

  MyS3Bucket:
    Type: AWS::S3::Bucket
    Properties:
      BucketName: !Sub '${AWS::StackName}-bucket-${AWS::AccountId}'
      BucketEncryption:
        ServerSideEncryptionConfiguration:
          - ServerSideEncryptionByDefault:
              SSEAlgorithm: 'aws:kms'

Outputs:
  InstanceId:
    Description: 'EC2 Instance ID'
    Value: !Ref MyEC2Instance
  BucketName:
    Description: 'S3 Bucket Name'
    Value: !Ref MyS3Bucket

🔷 CloudFormation Stacks

📖 Detailed Explanation

A CloudFormation Stack is a collection of AWS resources that you manage as a single unit. When you submit a template to CloudFormation, it creates a stack containing all the resources defined in that template.

Stack Lifecycle:

  • Create: CloudFormation provisions all resources defined in the template
  • Update: Modify existing resources by updating the template
  • Delete: Remove all resources in the stack with a single action

Stack Management Features:

CloudFormation provides comprehensive stack management capabilities. You can view stack events to track creation progress, examine resource details, monitor outputs, and review the original template. Stack operations are atomic - either all resources are created successfully, or CloudFormation rolls back to the previous state.

Stack Updates:

When updating a stack, CloudFormation determines which resources need to be modified, replaced, or left unchanged. Some updates can be performed without interruption, while others require resource replacement. Change sets allow you to preview the impact of updates before applying them.

🔑 Key Concepts

  • Stack Name: Unique identifier for your stack within a region
  • Stack Status: Indicates current state (CREATE_IN_PROGRESS, CREATE_COMPLETE, UPDATE_FAILED, etc.)
  • Stack Events: Chronological log of all stack operations
  • Stack Resources: List of all AWS resources managed by the stack
  • Stack Outputs: Values exported for use by other stacks or applications
  • Stack Policy: JSON document controlling update permissions
  • Rollback: Automatic reversion to previous state on failure

🔷 Drift Detection

📖 Detailed Explanation

Drift Detection is a CloudFormation feature that identifies when resources in a stack have been modified outside of CloudFormation. This happens when someone manually changes resource configurations through the AWS Console, CLI, or SDK instead of updating the CloudFormation template.

Why Drift Matters:

Drift creates a mismatch between your template (what you expect) and actual resource state (what exists). This can lead to confusion, failed updates, and unpredictable behavior. For example, if your template specifies that an S3 bucket should block public access, but someone manually disables this in the console, your infrastructure is "drifted" from its intended configuration.

How Drift Detection Works:

CloudFormation compares the current configuration of each resource in your stack against the expected configuration defined in your template. It generates a detailed report showing which resources have drifted, what properties changed, and the differences between expected and actual values.

Drift Status Values:

  • IN_SYNC: Resource matches template definition
  • MODIFIED: Resource properties differ from template
  • DELETED: Resource was deleted outside CloudFormation
  • NOT_CHECKED: CloudFormation hasn't checked this resource type yet

🔑 Key Concepts

  • Stack Drift: Overall drift status of the entire stack
  • Resource Drift: Drift status of individual resources
  • Expected Values: Configuration defined in CloudFormation template
  • Actual Values: Current configuration of live resources
  • Property Differences: Specific attributes that have changed
  • Drift Detection Time: When drift check was last performed

🔷 AWS Systems Manager

📖 Detailed Explanation

AWS Systems Manager is a unified interface for viewing and controlling your AWS infrastructure. It's not a single service, but rather a collection of capabilities that help you manage your EC2 instances, on-premises servers, and other AWS resources at scale.

Core Problem It Solves:

Imagine managing 100+ servers manually - logging into each one to install software, update configurations, apply patches, or troubleshoot issues. This is time-consuming, error-prone, and doesn't scale. Systems Manager centralizes these operations, allowing you to manage fleets of servers from a single dashboard.

Key Capabilities:

  • Operations Management: Run commands across multiple instances simultaneously
  • Configuration Management: Maintain consistent configurations across your fleet
  • Secrets Management: Securely store and retrieve sensitive data
  • Monitoring & Insights: View operational data and create inventories
  • Automation: Schedule and automate repetitive tasks

SSM Agent:

The Systems Manager Agent (SSM Agent) is software that must be installed on your instances to enable Systems Manager functionality. It runs in the background and communicates with Systems Manager to execute commands, collect inventory, and perform other operations. Most Amazon-provided AMIs have SSM Agent pre-installed.

🔑 Key Concepts

  • SSM Agent: Software that enables Systems Manager to manage instances
  • Managed Instances: Servers configured to work with Systems Manager
  • Run Command: Execute commands on multiple instances remotely
  • Session Manager: Secure shell access without SSH keys or bastion hosts
  • Parameter Store: Secure storage for configuration data and secrets
  • Patch Manager: Automate operating system patching
  • Fleet Manager: Unified view of all managed instances
  • Inventory: Collect metadata about instances and installed applications

🔷 Session Manager

📖 Detailed Explanation

Session Manager is a Systems Manager capability that provides secure and auditable instance management without the need to open inbound ports, maintain bastion hosts, or manage SSH keys.

Traditional SSH Challenges:

Traditional SSH access requires: opening port 22 in security groups (security risk), distributing and managing SSH key pairs, setting up bastion hosts for private instances, and tracking who accessed which instance. Session Manager eliminates all these requirements.

How Session Manager Works:

Session Manager establishes connections through the SSM Agent on your instance. The agent communicates outbound to Systems Manager endpoints over HTTPS (port 443). No inbound ports need to be opened. Authentication is handled through IAM, providing centralized access control and audit logging through CloudTrail.

Key Benefits:

  • No Inbound Ports: Eliminates port 22 exposure
  • No SSH Keys: No key distribution or rotation needed
  • No Bastion Hosts: Direct access to private instances
  • No Public IPs: Connect to instances without public IP addresses
  • IAM Integration: Leverage existing IAM users and policies
  • Session Logging: All sessions logged to S3 or CloudWatch
  • Session Recording: Optional video-like recording of sessions

🔑 Key Concepts

  • Session: Interactive shell connection to an instance
  • IAM Permissions: Control who can start sessions on which instances
  • Session Document: Defines session configuration and preferences
  • Port Forwarding: Tunnel traffic through sessions for applications
  • Session Preferences: Configure idle timeout, logging, encryption
  • Run As: Specify which OS user to execute commands as

🔷 Run Command

📖 Detailed Explanation

Run Command is a Systems Manager capability that allows you to remotely execute commands on multiple EC2 instances or on-premises servers simultaneously without logging into each one individually.

The Manual Problem:

Imagine needing to install a security patch on 50 servers. The manual approach requires: SSH into each server, run the update command, verify success, and repeat 49 more times. This takes hours and is prone to human error. Run Command executes the same operation across all 50 servers in parallel with a single action.

How Run Command Works:

You specify: (1) what command to run (shell script, PowerShell, or pre-built document), (2) which instances to target (by ID, tags, or resource groups), and (3) where to send output (optional S3 or CloudWatch). Systems Manager then executes the command on all targeted instances and reports results.

Common Use Cases:

  • Software Installation: Install packages across multiple servers
  • Configuration Changes: Update configuration files
  • Security Updates: Apply patches and updates
  • File Management: Create, modify, or delete files
  • Service Management: Start, stop, or restart services
  • Compliance Checks: Verify configurations meet standards

🔑 Key Concepts

  • Command Document: Pre-defined or custom script containing commands to execute
  • Target Selection: Methods to specify which instances receive commands
  • Command Status: Success, Failed, In Progress, Cancelled states
  • Rate Control: Limit concurrent execution and error thresholds
  • Command Output: Results from command execution
  • AWS-RunShellScript: Document for running shell commands on Linux
  • AWS-RunPowerShellScript: Document for running PowerShell on Windows

🔷 Fleet Manager

📖 Detailed Explanation

Fleet Manager provides a unified view of all your managed instances (called nodes) across your AWS infrastructure. It's a centralized console where you can view instance details, access file systems, manage users, and troubleshoot issues without logging into individual instances.

Key Capabilities:

Fleet Manager allows you to perform remote desktop-like operations directly from the AWS Console. You can browse the file system, view running processes, access Windows Registry, manage local users and groups, view event logs, and even access the instance terminal - all through a web browser.

Managed Instance (Node) Requirements:

For an instance to appear in Fleet Manager, it must have: (1) SSM Agent installed and running, (2) Proper IAM role attached, (3) Network connectivity to Systems Manager endpoints. When these conditions are met, the instance appears as an "online" node in Fleet Manager.

🔑 Key Concepts

  • Node: Any instance managed by Systems Manager (EC2 or on-premises)
  • Node Status: Online, Offline, or Connection Lost states
  • File System Browser: Navigate instance file systems through web interface
  • User Management: Create and manage local OS users
  • Process Viewer: See running processes and resource usage
  • Performance Monitoring: View CPU, memory, disk metrics

🔷 Parameter Store

📖 Detailed Explanation

Parameter Store is a secure, hierarchical storage for configuration data and secrets. It provides a centralized location to store values like database passwords, API keys, license codes, and configuration strings that your applications need.

Why Not Hardcode Secrets?

Hardcoding secrets directly in application code or CloudFormation templates is a severe security risk. If code is committed to Git or templates are shared, secrets are exposed. Parameter Store encrypts sensitive data and controls access through IAM, ensuring only authorized applications and users can retrieve secrets.

Parameter Types:

  • String: Plain text data (non-sensitive configuration)
  • StringList: Comma-separated values
  • SecureString: Encrypted using AWS KMS (for secrets)

Hierarchical Organization:

Parameters can be organized in hierarchies like file paths. For example: /prod/database/password, /prod/api/key, /dev/database/password. This structure makes it easy to manage parameters across different environments and retrieve groups of parameters using path-based queries.

🔑 Key Concepts

  • Parameter Name: Unique identifier following hierarchical path structure
  • Parameter Type: String, StringList, or SecureString
  • KMS Encryption: Used for SecureString parameters
  • Parameter Tiers: Standard (free, up to 4KB) and Advanced (paid, up to 8KB)
  • Versioning: Automatic versioning of parameter changes
  • Parameter Policies: TTL and notification policies for parameters

🔷 Patch Manager

📖 Detailed Explanation

Patch Manager automates the process of patching managed instances with security-related and other types of updates. Instead of manually logging into each server to apply updates, Patch Manager handles patching across your entire fleet on a defined schedule.

The Patching Challenge:

Keeping servers patched is critical for security but time-consuming at scale. Security vulnerabilities are discovered regularly, and unpatched systems are prime targets for attacks. Manually updating 100+ servers every week is unsustainable. Patch Manager automates this entire workflow.

How Patch Manager Works:

You define: (1) patch baseline (which patches to apply), (2) target instances (which servers to patch), and (3) maintenance window (when to patch). Patch Manager can scan instances to identify missing patches, or scan and install patches automatically. You can also set compliance rules to ensure all instances meet patching standards.

Patch Operations:

  • Scan: Check instances for missing patches without installing
  • Install: Apply approved patches to instances
  • Scan and Install: Check for and apply patches in one operation

🔑 Key Concepts

  • Patch Baseline: Rules defining which patches are approved for installation
  • Patch Group: Set of instances that share the same patch baseline
  • Maintenance Window: Scheduled time period for patching operations
  • Compliance Status: Whether instances meet patch baseline requirements
  • Patch Scanning: Identifying which patches are missing
  • Patch Installation: Actually applying patches to instances
  • Reboot Behavior: Control whether instances reboot after patching

📝 Overall Summary
  • Infrastructure as Code (IAC) enables you to manage cloud infrastructure through code files rather than manual console operations, ensuring consistency and repeatability
  • Declarative IAC focuses on describing the desired end state, while Imperative IAC specifies exact steps to achieve that state
  • AWS CloudFormation is AWS's native IAC service using YAML/JSON templates to define and provision AWS resources as stacks
  • CloudFormation Templates contain sections like Resources (required), Parameters, Outputs, and Mappings to define infrastructure blueprints
  • CloudFormation Stacks are collections of AWS resources managed as a single unit, supporting create, update, and delete operations atomically
  • Drift Detection identifies when resources have been manually modified outside CloudFormation, helping maintain infrastructure consistency
  • Terraform is a popular multi-cloud IAC tool using HCL (HashiCorp Configuration Language) that works across AWS, Azure, GCP, and other providers
  • Configuration Management Tools like Ansible, Chef, and Puppet handle software installation and configuration on servers after infrastructure is provisioned
  • AWS Systems Manager is a unified service collection for viewing, controlling, and automating operations across your AWS and on-premises infrastructure
  • Session Manager provides secure shell access to instances without SSH keys, bastion hosts, or open inbound ports, using IAM for authentication
  • Run Command executes commands remotely across multiple instances simultaneously, eliminating the need to SSH into each server individually
  • Fleet Manager offers a centralized dashboard to view and manage all SSM-enabled instances, including file system access and user management
  • Parameter Store securely stores configuration data and secrets with encryption, hierarchical organization, and IAM-based access control
  • Patch Manager automates security patching across instance fleets with scheduled maintenance windows and compliance tracking
  • SSM Agent is the software that must be installed on instances to enable Systems Manager functionality; it's pre-installed on most AWS AMIs
  • IAC tools solve critical problems: eliminates manual errors, ensures environment consistency, enables disaster recovery, and provides infrastructure documentation through code
