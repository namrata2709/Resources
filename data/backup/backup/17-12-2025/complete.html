🔍 VPC Flow Logs

🌍 Real-Life Analogy

Think of VPC Flow Logs like security cameras in a shopping mall...

Imagine a large shopping mall with security cameras everywhere. These cameras don't record every detail of what people are buying or saying - instead, they record metadata: who entered (person's appearance), when they entered (timestamp), which entrance they used (door number), where they went (store names), and whether security let them in or stopped them.

Similarly, VPC Flow Logs don't capture the actual data being sent (like the contents of your emails or files). Instead, they record: who sent the traffic (source IP), who received it (destination IP), what door they used (port number), what language they spoke (protocol), and whether it was allowed or blocked (action).

Example: Just like reviewing mall security footage helps you understand "Why did someone get stuck at the entrance?" - VPC Flow Logs help you understand "Why can't my EC2 instance connect to the database?"

📖 Detailed Explanation

VPC Flow Logs is a monitoring service that captures information about the network traffic flowing to and from your resources in AWS. Think of it as a detailed journal that records every conversation happening in your virtual network.

What is it? VPC Flow Logs captures metadata about IP traffic - not the actual content, but information about who's talking to whom, using which protocol, on which port, and whether the traffic was allowed or rejected.

Why does it matter? When your application suddenly stops working or a security breach occurs, Flow Logs are your detective tool. They help you answer critical questions: "Is traffic reaching my server?", "Is it being blocked by security rules?", "Which IP addresses are trying to access my resources?"

How does it work? Once enabled, Flow Logs continuously monitors network interfaces and records traffic information. This data is sent to either CloudWatch Logs (for real-time monitoring and alerts) or S3 (for long-term storage and cost-effective archiving). You can then query this data to troubleshoot issues, detect security threats, or analyze traffic patterns.

🔑 Key Concepts

  • Three Levels of Monitoring: VPC level (all resources), Subnet level (resources in specific subnet), or Network Interface level (specific EC2 or resource)
  • Traffic Types: Capture only accepted traffic, only rejected traffic, or all traffic - choose based on your needs
  • Aggregation Intervals: 1-minute intervals for real-time troubleshooting or 10-minute intervals for general monitoring
  • Storage Destinations: CloudWatch Logs for real-time analysis or S3 buckets for cost-effective long-term storage
  • Metadata Captured: Source/destination IPs, ports, protocol, packet count, byte count, action (accept/reject), and timestamps
  • Zero Performance Impact: Flow logs operate outside your traffic path - they don't slow down your applications
  • IAM Permissions Required: Flow logs need permissions to write to CloudWatch or S3

⚙️ Practical Implementation

Learn how to create VPC Flow Logs using both AWS CLI and AWS Management Console.

Method 1: Using AWS CLI

Prerequisites:

  • AWS CLI installed and configured (aws configure)
  • IAM permissions: ec2:CreateFlowLogs, logs:CreateLogGroup, iam:PassRole
  • VPC ID that you want to monitor

Step 1: Create CloudWatch Log Group

aws logs create-log-group \
  --log-group-name /aws/vpc/flowlogs/project-vpc \
  --region us-east-1

Explanation: Creates a log group in CloudWatch where flow log data will be stored. The log group name should be descriptive of which VPC it monitors.

Step 2: Create IAM Role for Flow Logs

# Create trust policy file
cat > flow-logs-trust-policy.json << EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Service": "vpc-flow-logs.amazonaws.com"
      },
      "Action": "sts:AssumeRole"
    }
  ]
}
EOF

# Create the role
aws iam create-role \
  --role-name VPC-Flow-Logs-Role \
  --assume-role-policy-document file://flow-logs-trust-policy.json

Explanation: Creates an IAM role that allows the VPC Flow Logs service to assume it and write logs to CloudWatch.

Step 3: Attach Policy to Role

# Create permissions policy
cat > flow-logs-permissions.json << EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "logs:CreateLogGroup",
        "logs:CreateLogStream",
        "logs:PutLogEvents",
        "logs:DescribeLogGroups",
        "logs:DescribeLogStreams"
      ],
      "Resource": "*"
    }
  ]
}
EOF

# Attach policy to role
aws iam put-role-policy \
  --role-name VPC-Flow-Logs-Role \
  --policy-name VPC-Flow-Logs-Policy \
  --policy-document file://flow-logs-permissions.json

Explanation: Grants the role permissions to create log streams and write log events to CloudWatch.

Step 4: Create VPC Flow Log

aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids vpc-0123456789abcdef0 \
  --traffic-type ALL \
  --log-destination-type cloud-watch-logs \
  --log-group-name /aws/vpc/flowlogs/project-vpc \
  --deliver-logs-permission-arn arn:aws:iam::123456789012:role/VPC-Flow-Logs-Role \
  --max-aggregation-interval 60 \
  --region us-east-1

Explanation: Creates the flow log for your VPC. Replace vpc-0123456789abcdef0 with your VPC ID and update the ARN with your account ID. This captures ALL traffic with 1-minute aggregation.

Step 5: Verify Flow Log Creation

aws ec2 describe-flow-logs \
  --filter "Name=resource-id,Values=vpc-0123456789abcdef0" \
  --region us-east-1

Expected output: JSON showing flow log status as "ACTIVE" with configuration details.

Method 2: Using AWS Management Console (GUI)

  1. Navigate: Go to AWS Management Console → VPC → Your VPCs
  2. Select VPC: Choose the VPC you want to monitor by clicking on its checkbox
  3. Create Flow Log:
    • Click the "Flow logs" tab at the bottom
    • Click "Create flow log" button (orange button)
  4. Configure Flow Log Settings:
    • Name: project-vpc-flow-logs
    • Filter: Select "All" to capture both accepted and rejected traffic
    • Maximum aggregation interval: Select "1 minute" for faster debugging
    • Destination: Select "Send to CloudWatch Logs"
  5. Configure CloudWatch Destination:
    • Destination log group: Enter /aws/vpc/flowlogs/project-vpc
    • If log group doesn't exist, you'll be prompted to create it
    • IAM role: Select "Create and use a new role" or choose existing role
    • If creating new: AWS will auto-create role with necessary permissions
  6. Review and Create:
    • Review all settings
    • Click "Create flow log"
    • Wait for status to change to "Active" (takes 1-2 minutes)
  7. View Flow Logs:
    • Go to CloudWatch → Log groups
    • Find your log group: /aws/vpc/flowlogs/project-vpc
    • Click on log group to see log streams
    • Click on any log stream to view actual flow log records
    • Wait 5-10 minutes for data to appear (initial setup takes time)

✅ Success Indicators:

  • Flow log status shows as "Active" in VPC console
  • Log group appears in CloudWatch Logs
  • Log streams start appearing (one per network interface)
  • Log records contain fields: srcaddr, dstaddr, srcport, dstport, protocol, action
  • Can see both ACCEPT and REJECT actions in logs

🔗 VPC Peering Connection

🌍 Real-Life Analogy

Think of VPC Peering like a private tunnel between two office buildings...

Imagine you work in Building A and your colleague works in Building B across the street. Normally, to visit them, you'd have to: (1) Exit your building to the public street, (2) Cross the street where anyone can see you, (3) Enter their building through the main entrance.

This is like using the public internet - everyone can see you're making the trip, it's slower (traffic lights, crosswalks), and less secure (someone might follow you or intercept you).

Now imagine the buildings decide to construct a private, enclosed tunnel connecting them. Now you can walk directly from Building A to Building B through this private passage. It's faster, more secure, climate-controlled, and no one on the street can see your movement.

That's exactly what VPC Peering does - it creates a private network connection between two VPCs so they can communicate directly through AWS's private network instead of going through the public internet.

📖 Detailed Explanation

VPC Peering is a networking connection between two Virtual Private Clouds (VPCs) that enables you to route traffic between them using private IPv4 or IPv6 addresses. Resources in either VPC can communicate as if they're in the same network, without ever touching the public internet.

What is it? VPC Peering creates a direct, private network link between two VPCs - whether they're in the same AWS account, different accounts, same region, or different regions. Once peered, EC2 instances in one VPC can talk to instances in the other VPC using their private IP addresses.

Why does it matter? Security and performance. Traffic between peered VPCs never leaves AWS's private network backbone, providing lower latency, higher bandwidth, and no exposure to internet-based attacks. It's also more cost-effective than VPN connections or Direct Connect for VPC-to-VPC communication.

How does it work? You create a peering connection request from one VPC (requester) to another (accepter). The accepter must approve the request. Then you manually update the route tables in both VPCs to direct traffic destined for the peer VPC through the peering connection. Security groups and NACLs still apply - peering doesn't bypass your security controls.

🔑 Key Concepts

  • Requester and Accepter Model: One VPC initiates the peering request, the other must accept it before traffic can flow
  • Non-Overlapping CIDR Blocks: Critical requirement - VPCs must have different IP address ranges (e.g., 10.0.0.0/16 and 10.1.0.0/16)
  • Manual Route Table Configuration: You must add routes in both VPCs pointing to each other through the peering connection
  • No Transitive Peering: If VPC-A peers with VPC-B, and VPC-B peers with VPC-C, VPC-A cannot reach VPC-C through VPC-B
  • Cross-Region and Cross-Account Support: Can peer VPCs across different regions and AWS accounts
  • Security Groups Still Apply: Must allow traffic in security groups and NACLs for communication to work
  • Private IP Communication: Resources communicate using private IPs, never public IPs

⚙️ Practical Implementation

Learn how to create VPC Peering connections using both AWS CLI and AWS Management Console.

Method 1: Using AWS CLI

Prerequisites:

  • AWS CLI installed and configured
  • IAM permissions: ec2:CreateVpcPeeringConnection, ec2:AcceptVpcPeeringConnection, ec2:CreateRoute
  • Two VPCs with non-overlapping CIDR blocks
  • VPC IDs for both requester and accepter VPCs

Step 1: Verify VPCs Have Non-Overlapping CIDRs

# Check VPC-A CIDR
aws ec2 describe-vpcs \
  --vpc-ids vpc-0123456789abcdef0 \
  --query 'Vpcs[0].CidrBlock' \
  --output text

# Check VPC-B CIDR
aws ec2 describe-vpcs \
  --vpc-ids vpc-abcdef0123456789 \
  --query 'Vpcs[0].CidrBlock' \
  --output text

Explanation: Verify that the CIDR blocks don't overlap. Example: 10.0.0.0/16 and 10.1.0.0/16 are fine. 10.0.0.0/16 and 10.0.0.0/16 will fail.

Step 2: Create VPC Peering Connection (Requester)

aws ec2 create-vpc-peering-connection \
  --vpc-id vpc-0123456789abcdef0 \
  --peer-vpc-id vpc-abcdef0123456789 \
  --peer-region us-east-1 \
  --tag-specifications 'ResourceType=vpc-peering-connection,Tags=[{Key=Name,Value=Project-Default-Peering}]' \
  --region us-east-1

Explanation: Creates peering request from VPC-A (requester) to VPC-B (accepter). Note the VpcPeeringConnectionId in the output - you'll need it for the next step.

Step 3: Accept VPC Peering Connection (Accepter)

aws ec2 accept-vpc-peering-connection \
  --vpc-peering-connection-id pcx-0123456789abcdef0 \
  --region us-east-1

Explanation: Accepter VPC accepts the peering request. If VPCs are in different accounts, run this command with credentials for the accepter account. Connection status changes from "pending-acceptance" to "active".

Step 4: Update Route Table in VPC-A (Requester)

# Get route table ID for VPC-A subnet
aws ec2 describe-route-tables \
  --filters "Name=vpc-id,Values=vpc-0123456789abcdef0" \
  --query 'RouteTables[0].RouteTableId' \
  --output text

# Add route to VPC-B CIDR through peering connection
aws ec2 create-route \
  --route-table-id rtb-0123456789abcdef0 \
  --destination-cidr-block 10.1.0.0/16 \
  --vpc-peering-connection-id pcx-0123456789abcdef0 \
  --region us-east-1

Explanation: Adds route in VPC-A's route table. Replace 10.1.0.0/16 with actual CIDR of VPC-B. This tells VPC-A "traffic destined for 10.1.0.0/16 should go through peering connection".

Step 5: Update Route Table in VPC-B (Accepter)

# Get route table ID for VPC-B subnet
aws ec2 describe-route-tables \
  --filters "Name=vpc-id,Values=vpc-abcdef0123456789" \
  --query 'RouteTables[0].RouteTableId' \
  --output text

# Add route to VPC-A CIDR through peering connection
aws ec2 create-route \
  --route-table-id rtb-abcdef0123456789 \
  --destination-cidr-block 10.0.0.0/16 \
  --vpc-peering-connection-id pcx-0123456789abcdef0 \
  --region us-east-1

Explanation: Adds route in VPC-B's route table pointing back to VPC-A. Replace 10.0.0.0/16 with actual CIDR of VPC-A. Now both VPCs can route to each other.

Step 6: Update Security Groups (Both VPCs)

# Allow traffic from VPC-B in VPC-A's security group
aws ec2 authorize-security-group-ingress \
  --group-id sg-0123456789abcdef0 \
  --protocol tcp \
  --port 22 \
  --cidr 10.1.0.0/16 \
  --region us-east-1

# Allow traffic from VPC-A in VPC-B's security group
aws ec2 authorize-security-group-ingress \
  --group-id sg-abcdef0123456789 \
  --protocol tcp \
  --port 22 \
  --cidr 10.0.0.0/16 \
  --region us-east-1

Explanation: Security groups act as firewalls. Update them to allow traffic from the peer VPC CIDR. Adjust port numbers based on your application needs.

Step 7: Test Connectivity

# From EC2 in VPC-A, ping EC2 in VPC-B using private IP
ping 10.1.1.50

# Or SSH to EC2 in VPC-B from VPC-A
ssh -i mykey.pem ec2-user@10.1.1.50

Expected output: Successful ping replies or SSH connection, proving private connectivity through peering works.

Method 2: Using AWS Management Console (GUI)

  1. Navigate: Go to AWS Management Console → VPC → Peering Connections
  2. Create Peering Connection:
    • Click "Create peering connection" button
    • Name: Project-Default-VPC-Peering
    • VPC (Requester): Select your first VPC (e.g., Project-VPC)
    • Note the CIDR displayed (e.g., 10.0.0.0/16)
  3. Select Accepter VPC:
    • Account: Select "My account" or "Another account" if cross-account
    • Region: Select "This region" or specific region if cross-region
    • VPC (Accepter): Select second VPC (e.g., Default-VPC)
    • Verify CIDR doesn't overlap with requester (e.g., 172.31.0.0/16)
    • Click "Create peering connection"
  4. Accept Peering Connection:
    • Status shows "Pending Acceptance"
    • Select the peering connection checkbox
    • Click "Actions" → "Accept request"
    • Confirm by clicking "Accept request" in dialog
    • Status changes to "Active"
  5. Update Route Table for VPC-A (Requester):

    • Click on the subnet you want to peer

    • Destination: Enter accepter VPC CIDR (e.g., 172.31.0.0/16)
    • Target: Select "Peering Connection" → Choose your peering connection
    • Click "Save changes"
  6. Update Route Table for VPC-B (Accepter):
    • Go to VPC → Your VPCs → Select Default-VPC
    • Follow same steps as above to access route table
    • Click "Edit routes" → "Add route"
    • Destination: Enter requester VPC CIDR (e.g., 10.0.0.0/16)
    • Target: Select "Peering Connection" → Choose your peering connection
    • Click "Save changes"
  7. Update Security Groups:
    • Go to EC2 → Security Groups
    • Select security group attached to your EC2 in VPC-A
    • Click "Inbound rules" tab → "Edit inbound rules"
    • Click "Add rule"
    • Type: Select protocol (e.g., SSH, HTTP, All traffic)
    • Source: Enter peer VPC CIDR (e.g., 172.31.0.0/16)
    • Click "Save rules"
    • Repeat for VPC-B security groups, allowing VPC-A CIDR
  8. Test Connectivity:
    • Connect to EC2 in VPC-A via Session Manager or SSH
    • Get private IP of EC2 in VPC-B (e.g., 172.31.1.50)
    • Run: ping 172.31.1.50
    • Should see successful ping replies
    • Try SSH: ssh -i key.pem ec2-user@172.31.1.50

  • Peering connection status shows "Active" in VPC console
  • Both route tables show routes to peer VPC through peering connection
  • Ping between EC2 instances in different VPCs succeeds using private IPs

🔌 VPC Endpoints

🌍 Real-Life Analogy

Think of VPC Endpoints like a private direct phone line to a company...

Imagine you need to regularly send documents to your bank. You have two options:

Option 1 (Without VPC Endpoint): You leave your office, walk to the post office (public place where anyone can see you), mail your documents through the public postal system, where they pass through multiple sorting centers, and eventually reach the bank. This is slower, less secure, and everyone at the post office can see you're sending something to the bank.

Option 2 (With VPC Endpoint): Your office has a private, dedicated courier tube (like those pneumatic tubes at drive-through banks) that connects directly to your bank's office. You drop documents in the tube, and they travel through a private, enclosed pathway directly to the bank. No one else can see what you're sending, it's faster, and more secure.

That's exactly what VPC Endpoints do - they create a private, direct connection from your VPC to AWS services (like S3, DynamoDB) without your traffic ever going through the public internet. It's faster, more secure, and often cheaper!

📖 Detailed Explanation

VPC Endpoints enable you to privately connect your VPC to supported AWS services without requiring an internet gateway, NAT device, VPN connection, or AWS Direct Connect. Traffic between your VPC and the AWS service does not leave the Amazon network, providing enhanced security and performance.

What is it? VPC Endpoints are virtual devices that allow private connectivity between your VPC and AWS services. There are two types: Gateway Endpoints (free, for S3 and DynamoDB) and Interface Endpoints (charged, for most other services). They eliminate the need for public IP addresses and internet gateways when accessing AWS services.

Why does it matter? Security and compliance. Many organizations have requirements that data should never traverse the public internet. VPC Endpoints ensure traffic stays on AWS's private network. Plus, you save money on NAT Gateway data transfer charges and reduce latency by taking a direct path to AWS services.

How does it work? For Gateway Endpoints, you create the endpoint and update your route table to direct traffic destined for S3 or DynamoDB through the endpoint. For Interface Endpoints, AWS creates an Elastic Network Interface (ENI) in your subnet with a private IP address. Your resources then use this private IP to access the AWS service instead of going through the internet.

🔑 Key Concepts

  • Gateway Endpoints (Free): Available only for S3 and DynamoDB; uses route table entries; no hourly charges
  • Interface Endpoints (Powered by AWS PrivateLink): For most AWS services; creates ENIs in your subnets; charged hourly plus data transfer
  • Private DNS: Interface endpoints support private DNS names, allowing existing code to work without changes
  • Endpoint Policies: IAM policies attached to endpoints to control which resources can be accessed
  • No Internet Gateway Required: Resources in private subnets can access AWS services without internet connectivity
  • Security Group Support: Interface endpoints support security groups for access control
  • Multi-AZ Deployment: Interface endpoints should be deployed in multiple AZs for high availability

Method 1: Using AWS CLI

Prerequisites:

  • AWS CLI installed and configured

  • VPC ID where endpoint will be created
  • EC2 instance in private subnet (for testing)

Step 1: Create S3 Gateway Endpoint

# Get route table IDs for your VPC
aws ec2 describe-route-tables \
  --filters "Name=vpc-id,Values=vpc-0123456789abcdef0" \
  --query 'RouteTables[*].RouteTableId' \
  --output text

# Create S3 Gateway Endpoint
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-0123456789abcdef0 \
  --service-name com.amazonaws.us-east-1.s3 \
  --route-table-ids rtb-0123456789abcdef0 rtb-abcdef0123456789 \
  --tag-specifications 'ResourceType=vpc-endpoint,Tags=[{Key=Name,Value=S3-Gateway-Endpoint}]' \
  --region us-east-1

Explanation: Creates a gateway endpoint for S3 and automatically updates specified route tables. Note the VpcEndpointId in output for future reference. This is FREE - no charges for gateway endpoints.

Step 2: (Optional) Create Endpoint Policy for Least Privilege

# Create policy file
cat > s3-endpoint-policy.json << EOF

Explanation: Creates interface endpoint with ENIs in multiple subnets for HA. Charges apply: ~$0.01/hour per AZ + data transfer. Enable private DNS so existing code works unchanged.

Question 1

What is VPC Flow Logs and what type of information does it capture?

Answer

VPC Flow Logs is a feature that captures metadata about IP traffic flowing to and from network interfaces in your VPC. It captures information like source/destination IP addresses, ports, protocol (TCP/UDP), number of packets and bytes, action (ACCEPT/REJECT), and timestamps. It does NOT capture actual packet contents, only metadata about the traffic.

Question 2

At what three levels can you create VPC Flow Logs?

Answer

VPC Flow Logs can be created at three levels: (1) VPC level - captures traffic for all resources in the VPC, (2) Subnet level - captures traffic for resources in a specific subnet, and (3) Network Interface level - captures traffic for a specific resource's ENI. This flexibility allows you to choose the appropriate scope for your monitoring needs.

Question 3

Where can VPC Flow Logs be stored and which destination is more cost-effective for long-term storage?

Answer

VPC Flow Logs can be stored in CloudWatch Logs or S3 buckets. S3 is significantly more cost-effective for long-term storage (approximately 10x cheaper than CloudWatch Logs). CloudWatch is better for real-time monitoring and alerting, while S3 is ideal for archive and compliance purposes with lifecycle policies to move old logs to Glacier.

Question 4

What is VPC Peering and what problem does it solve?

Answer

VPC Peering is a networking connection between two VPCs that enables private communication using private IP addresses. It solves the problem of having to route traffic between VPCs through the public internet. With peering, traffic stays on AWS's private network, providing better security, lower latency, and no data transfer charges through internet gateways or NAT gateways.

Question 5

What is the most critical requirement for VPC Peering to work, and what happens if this requirement isn't met?

Answer

The most critical requirement is non-overlapping CIDR blocks - the two VPCs must have different IP address ranges. If VPCs have overlapping CIDR blocks (e.g., both use 10.0.0.0/16), the peering connection creation will fail immediately. This cannot be fixed without recreating one VPC with a different CIDR range, which is why IP address planning is crucial from the beginning.

Question 6

After creating a VPC Peering connection, what additional configuration steps are required for traffic to flow between VPCs?

Answer

Three steps are required: (1) Update route tables in both VPCs to add routes pointing to the peer VPC CIDR through the peering connection, (2) Update security groups in both VPCs to allow traffic from the peer VPC CIDR, and (3) Update NACLs if they're being used. Simply creating the peering connection is not enough - these manual configuration steps are essential for traffic to flow.

Question 7

What is transitive peering and is it supported in AWS VPC Peering?

Answer

Transitive peering means if VPC-A peers with VPC-B, and VPC-B peers with VPC-C, then VPC-A could communicate with VPC-C through VPC-B. This is NOT supported in AWS VPC Peering. Each peering connection is a direct one-to-one relationship. If you need VPC-A to communicate with VPC-C, you must create a direct peering connection between them. For complex multi-VPC topologies, AWS Transit Gateway is a better solution.

Question 8

What are VPC Endpoints and what security benefit do they provide?

Answer

VPC Endpoints enable private connectivity between your VPC and AWS services without requiring an internet gateway, NAT device, or VPN connection. The key security benefit is that traffic never leaves the AWS private network and never traverses the public internet. This eliminates exposure to internet-based attacks, meets compliance requirements for data that cannot touch the internet, and reduces the attack surface of your infrastructure.

Question 9

What are the two types of VPC Endpoints, and which AWS services does each type support?

Answer

The two types are Gateway Endpoints and Interface Endpoints. Gateway Endpoints (free) are available ONLY for S3 and DynamoDB - they use route table entries. Interface Endpoints (charged) are powered by AWS PrivateLink and support most other AWS services like EC2, SNS, SQS, Lambda, etc. - they create ENIs in your subnets with private IP addresses.

Question 10

Why should you always create S3 and DynamoDB Gateway Endpoints in every VPC?

Answer

Because Gateway Endpoints for S3 and DynamoDB are completely FREE - there are no hourly charges or data transfer fees. They provide better security (traffic stays on AWS private network), lower latency (direct path), and save money by eliminating NAT Gateway data transfer charges. There's literally no reason not to create them - it's all benefits with zero cost. They should be created by default during VPC setup.

Question 11

How do resources in a private subnet access S3 when using a VPC Gateway Endpoint?

Answer

When you create a Gateway Endpoint, AWS automatically updates the specified route tables with routes to S3 prefix lists (pl-xxxxx) pointing to the endpoint. Resources in private subnets make normal S3 API calls, and the route table directs that traffic through the VPC endpoint instead of an internet gateway. No code changes are needed - the routing happens transparently at the network layer.

Question 12

What is API Gateway and what role does it play in serverless architectures?

Answer

API Gateway is a fully managed service that acts as a front door for applications to access backend services. In serverless architectures, it's the entry point that receives HTTP requests from clients and routes them to Lambda functions based on the URL path and HTTP method. It handles authentication, throttling, caching, and CORS, eliminating the need to build and manage your own web servers or load balancers.

Question 13

What are Resources and Methods in API Gateway?

Answer

Resources are URL paths that represent entities in your API (like /orders, /users, /payment). Methods are HTTP verbs that define what actions can be performed on those resources (GET to retrieve, POST to create, PUT to update, DELETE to remove). Together they form the complete API structure - for example, "GET /orders" retrieves orders, while "POST /orders" creates a new order.

Question 14

What is Lambda Proxy Integration and why should you use it?

Answer

Lambda Proxy Integration passes the entire HTTP request to your Lambda function as-is, and expects Lambda to return the complete HTTP response. This simplifies development because Lambda has full control over the response (headers, status codes, body) without needing complex API Gateway mapping templates. It's the recommended approach for most Lambda-based APIs as it reduces configuration complexity and gives developers more flexibility.

Question 15

What is CORS and why is it necessary when building browser-based applications?

Answer

CORS (Cross-Origin Resource Sharing) is a security feature that allows or restricts web applications running on one domain to make requests to a different domain. Without CORS enabled, browsers block API calls from websites to APIs on different domains as a security measure. You must enable CORS in API Gateway if your API will be called from web browsers, otherwise all requests will fail with CORS policy errors.

Question 16

What are Stages in API Gateway and why are they important?

Answer

Stages are deployment environments for your API (like dev, staging, production), each with a unique invoke URL. They're important because they allow you to test changes safely before deploying to production, maintain multiple versions of your API simultaneously, and quickly rollback if issues occur. Each stage can have different configurations like caching, throttling limits, and logging levels.

Question 17

How does enabling caching in API Gateway reduce costs?

Answer

Caching stores responses for identical requests and serves them directly without invoking Lambda. This can reduce Lambda invocations by 40-80% for read-heavy workloads. Since you pay per Lambda invocation, fewer invocations mean lower costs. Caching also improves response times significantly and reduces load on your backend services. It's most effective for GET requests where data doesn't change frequently.

Question 18

If VPC Flow Logs show ACTION=REJECT, what should you check to troubleshoot connectivity issues?

Answer

When flow logs show REJECT, you should check two main things: (1) Security Group rules - verify inbound rules allow traffic from the source IP on the required port, and (2) Network ACL (NACL) rules - check both inbound and outbound rules as NACLs are stateless. The REJECT action indicates traffic was blocked by one of these security layers before reaching the resource.

Question 19

Can you peer VPCs that are in different AWS regions or different AWS accounts?

Answer

Yes, VPC Peering supports both inter-region peering (VPCs in different AWS regions) and cross-account peering (VPCs in different AWS accounts). You can even combine both - peering VPCs that are in different regions AND different accounts. The process is the same, but for cross-account peering, the accepter must log into their account to accept the peering request. Data transfer charges apply for inter-region peering.

Question 20

What is the difference between Gateway Endpoints and Interface Endpoints in terms of implementation?

Answer

Gateway Endpoints use route table entries to direct traffic - you add the endpoint to route tables and AWS handles routing via prefix lists. Interface Endpoints create actual Elastic Network Interfaces (ENIs) with private IP addresses in your subnets - your resources connect to these private IPs. Gateway endpoints are simpler (just route table config), while interface endpoints are more flexible (support security groups and private DNS).

Question 21

What happens if you don't redeploy your API Gateway after making changes?

Answer

Changes you make in API Gateway (like adding methods, modifying integrations, updating CORS) are not live until you deploy them to a stage. If you don't redeploy, the invoke URL will continue serving the old version, and users won't see your changes. This is actually a safety feature - it allows you to make and test changes before they affect production users. Always remember to deploy after making changes.

Question 22

Why is it important to capture REJECTED traffic in VPC Flow Logs, not just ACCEPTED traffic?

Answer

Rejected traffic shows security events - attempted connections that were blocked by security groups or NACLs. This is crucial for security forensics (identifying attack attempts), troubleshooting (understanding why connections fail), and compliance (proving you blocked unauthorized access). If you only capture accepted traffic, you have no visibility into attacks, misconfigurations, or unauthorized access attempts. Always capture ALL traffic for complete visibility.

Question 23

When should you use AWS Transit Gateway instead of VPC Peering?

Answer

Use Transit Gateway when you need to connect 4 or more VPCs, or when you need transitive routing (hub-and-spoke model). With VPC Peering, connecting 5 VPCs requires 10 peering connections (mesh). With Transit Gateway, you need only 5 connections (each VPC to the gateway). Transit Gateway also supports on-premises connectivity, multicast, and centralized routing, making it better for complex enterprise network topologies. For 2-3 VPCs, peering is simpler and cheaper.

Question 24

What is an endpoint policy and when should you use one?

Answer

An endpoint policy is an IAM policy attached to a VPC endpoint that controls which AWS resources can be accessed through the endpoint. You should use endpoint policies to implement least-privilege access - for example, allowing access only to specific S3 buckets or DynamoDB tables. This adds defense-in-depth security by restricting endpoint usage even if security groups or IAM roles are misconfigured. It's a best practice for production environments.

Question 25

What is throttling in API Gateway and why is it important?

Answer

Throttling limits the number of requests per second that API Gateway will accept, returning 429 errors when exceeded. It's important for two reasons: (1) Protects your backend (Lambda, databases) from being overwhelmed by too many requests, and (2) Prevents cost surprises by limiting Lambda invocations during attacks or unexpected traffic spikes. You should set throttle limits proactively based on your backend capacity, not wait for problems.

Question 26

Do VPC Flow Logs impact network performance or add latency to your traffic?

Answer

No, VPC Flow Logs have zero impact on network performance or latency. They operate completely outside the path of your network traffic - AWS captures the metadata at the hypervisor level without touching your actual data packets. This means you can enable flow logs on high-traffic production systems without any performance concerns. It's a completely passive monitoring service.

Question 27

If you create an Interface Endpoint but don't enable Private DNS, how do resources access the service?

Answer

Without Private DNS, you must use the endpoint-specific DNS name (like vpce-123456-abcdef.ec2.us-east-1.vpce.amazonaws.com) instead of the standard service endpoint. This requires code changes in your applications. With Private DNS enabled, you can use standard AWS service endpoints (ec2.us-east-1.amazonaws.com) and they automatically resolve to the endpoint's private IP. Private DNS is recommended to avoid code changes.

Question 28

What AWS service limits should you be aware of before launching a high-traffic API Gateway application?

Answer

Key limits include: (1) API Gateway default throttle limit of 10,000 requests/second per account per region, (2) Lambda concurrent execution limit of 1,000 by default per account per region, and (3) API Gateway maximum timeout of 29 seconds. You should request limit increases from AWS Support BEFORE launch, do load testing to understand your needs, and set up CloudWatch alarms to monitor when you're approaching limits.
