🏗️ AWS Well-Architected Framework (WAF)

🌟 Real-Life Analogy: Building Your Dream House

Imagine you're building a house. You wouldn't just throw walls together randomly, right? You'd want:

  • 🏗️ Good operations - Smooth running water, electricity, heating that you can control
  • 🔒 Security - Strong locks, alarm system, fence around property
  • 💪 Reliability - Roof that doesn't leak, foundation that won't crack
  • ⚡ Performance - Fast internet, efficient appliances
  • 💰 Cost optimization - Energy-efficient lights, proper insulation to save on bills
  • 🌱 Sustainability - Solar panels, water recycling system

That's exactly what AWS Well-Architected Framework does - it helps you build your "cloud house" (application) properly using these same principles!

📖 What is Well-Architected Framework?

The AWS Well-Architected Framework is like a checklist given by expert architects to make sure your cloud application is built correctly. It answers three important questions:

  1. Is your application set up correctly on AWS?
  2. Are you following best practices?
  3. Are you getting the best value for your money?

⚠️ Important Note: Don't confuse "Well-Architected Framework" with "AWS WAF (Web Application Firewall)". They're different things:

  • Well-Architected Framework = Guidelines for building good applications (what we're learning)
  • AWS WAF = A security service like a firewall (a different AWS service)

1️⃣ Operational Excellence - "Running Things Smoothly"

Real-Life Story:

Think of a restaurant. A well-run restaurant has:

  • Standard recipes (procedures) that anyone can follow
  • Regular checks on food quality (monitoring)
  • Quick response when something goes wrong (like running out of ice)
  • Learning from mistakes (if customers complain about cold food, they get warming trays)

In AWS Terms:

  • Operations as code: Write your setup instructions so anyone can repeat them (like recipes)
  • Make small changes often: Don't change everything at once (like updating one menu item at a time)
  • Expect failures: Plan for what could go wrong (like having backup ingredients)
  • Learn from failures: Keep notes of what went wrong and how you fixed it
⚙️ How to Do This in Practice

Option 1: Using Command Line (CLI)

# Create a CloudWatch alarm to monitor your application
aws cloudwatch put-metric-alarm \
    --alarm-name HighCPUUsage \
    --alarm-description "Alert when CPU usage is high" \
    --metric-name CPUUtilization \
    --namespace AWS/EC2 \
    --statistic Average \
    --period 300 \
    --threshold 80 \
    --comparison-operator GreaterThanThreshold

# This command creates an alarm that watches your server
# If CPU usage goes above 80%, you get notified

What this command does: It sets up automatic monitoring - like having a temperature sensor in your restaurant kitchen that beeps when it gets too hot!

Option 2: Using AWS Website (Console)

  1. Go to AWS Console (the website)
  2. Search for "CloudWatch" (the monitoring service)
  3. Click "Alarms" on the left menu
  4. Click "Create alarm"
  5. Choose what to monitor (like CPU usage)
  6. Set the warning level (like 80%)
  7. Choose how to get notified (email, text message)
  8. Click "Create alarm"

2️⃣ Security - "Keeping Bad People Out"

Real-Life Story:

Your house security has layers:

  • Layer 1: Neighborhood gate (only residents allowed)
  • Layer 2: Your house fence (extra barrier)
  • Layer 3: Front door lock (main entry protection)
  • Layer 4: Bedroom door lock (protect valuable items)
  • Layer 5: Safe for jewelry (ultimate protection)
  • Bonus: Security cameras recording everything (monitoring)

If someone gets past one layer, there are more layers protecting you!

In AWS Terms - Defense in Depth:

  • Layer 1: IAM (Identity and Access Management) - Who's allowed in?
  • Layer 2: VPC & Security Groups - Network protection
  • Layer 3: AWS WAF - Website firewall
  • Layer 4: Encryption - Lock your data
  • Layer 5: GuardDuty - AI watching for threats

3️⃣ Reliability - "Stays Working Even When Things Break"

Real-Life Story:

Imagine a hospital:

  • Main power supply from grid
  • Backup generator if power fails
  • Battery backup if generator takes time to start
  • Medical equipment has its own batteries

Even if the city power goes out, the hospital keeps running because they planned for failures!

In AWS Terms:

  • Multi-AZ: Like having backup generators in different buildings (if one building floods, others still work)
  • Auto Scaling: Automatically add more servers when busy (like opening more checkout counters during rush hour)
  • Load Balancers: Distribute work evenly (like traffic police directing cars to avoid jams)
  • Backups: Regular snapshots of your data (like backing up your phone photos to cloud)

4️⃣ Performance Efficiency - "Fast and Responsive"

Real-Life Story:

Think of two pizza delivery shops:

Shop A (Inefficient):

  • One oven for all pizzas (bottleneck)
  • One delivery person for whole city
  • Keeps all ingredients ready even during slow hours (waste)
  • Result: 2-hour delivery time, high costs

Shop B (Efficient):

  • Multiple ovens working in parallel
  • More delivery people during busy hours, fewer during slow hours
  • Orders ingredients based on demand
  • Result: 30-minute delivery, lower costs, happy customers

In AWS Terms:

  • Right-sizing: Use correct server size (don't rent a mansion when you need a studio apartment)
  • Auto Scaling: Add resources when busy, remove when quiet (Shop B's delivery people)
  • Serverless: Pay only when code runs (like Uber - car comes only when you need it)
  • CDN (CloudFront): Store copies closer to users (like having pizza shops in every neighborhood)

Two families with same income:

Family A (Wasteful):

  • Leaves lights on 24/7
  • AC running even when out

In AWS Terms:

  • Auto Scaling: Turn off servers at night if not needed (Family B's smart thermostat)
  • S3 Lifecycle: Move old files to cheaper storage (like moving winter clothes to attic)

🚀 Cloud Adoption Framework (CAP)

🌟 Real-Life Analogy: Moving to a New City

Imagine your entire family is moving from a small town to a big city. You can't just pack bags and go! You need to plan:

  • 💼 Business reasons: Why are we moving? (Job opportunities, better schools)
  • 👨‍👩‍👧‍👦 People: Will everyone adjust? Do kids need new school registration? Do adults need job training?
  • 📋 Rules & Governance: What documents do we need? Voter registration? Bank account transfer?
  • 🏠 Infrastructure (Platform): Where will we live? What size house? Which neighborhood?
  • 🔒 Safety (Security): Is the neighborhood safe? Do we need alarm system? Health insurance?
  • 🚗 Daily Operations: How do we commute? Where to buy groceries? Where's the hospital?

If you plan all six things properly, the move is smooth. If you forget even one (like not enrolling kids in school), you have problems!

Cloud Adoption Framework is the same - it helps you plan your company's "move" from old servers to AWS cloud by thinking about all six areas.

📖 What is Cloud Adoption Framework?

CAF answers: "Is our organization ready to move to the cloud?"

It's NOT about technology alone. Moving to cloud changes your entire company - how people work, how you manage things, how you secure data. CAF makes sure you're ready for all these changes.

Figure 2: AWS Cloud Adoption Framework Journey - Envision → Align → Launch → Scale (Timeline: 2-4 weeks → 1-3 months → 3-6 months → 6-12 months)

⚠️ Important Difference:

  • CAF (Cloud Adoption Framework): Use BEFORE moving to cloud (planning phase)
  • WAF (Well-Architected Framework): Use AFTER moving to cloud (check if you built it right)

Key difference: CAP = "Are we READY?" | WAF = "Did we build it RIGHT?"

❌ What Happens Without Proper Planning?

Real Story - Company X's Failed Cloud Migration:

Company X decided to "go to cloud" without planning:

  • Moved their main application to AWS
  • Forgot to train IT team on AWS tools
  • Didn't plan for security compliance
  • No budget allocated for monthly cloud costs

Result:

  • Week 1: Application worked but team couldn't troubleshoot issues
  • Week 2: Security audit found major vulnerabilities
  • Month 1: AWS bill was 3x what they expected
  • Month 2: Had to move everything back to old servers, lost $200,000

Lesson: They failed NOT because AWS is bad, but because they didn't plan using CAF!

🔒 System & Network Hardening

🌟 Real-Life Analogy: Protecting Your Gold

Imagine you have a gold bar (your valuable data). How do you protect it?

Layer-by-Layer Protection (Defense in Depth):

  1. House Gate: Security guard checks IDs → Only neighbors allowed
    • In IT: Network Hardening - Who can even reach your server?
  2. House Door: Need house key
    • In IT: Firewall/Security Groups
  3. Bedroom Door: Another lock
    • In IT: System Hardening - What can you do inside server?
  4. Safe: Combination lock only you know
    • In IT: File Permissions - Who can read/write files?
  5. CCTV Cameras: Recording everything
    • In IT: Logging & Monitoring

Key Concept: Even if thief gets past one layer, there are more layers protecting you!

Figure 4: Defense in Depth - Concentric security layers protecting data (Center: Protected Data → File & Access Permissions → Application Security → System Hardening → Security Groups → Network Controls)

📖 The Core Truth About Security

⚠️ Security = Controlling Access at TWO Points:

  • BEFORE reaching the system = Network Hardening
  • AFTER reaching the system = System Hardening

Figure 6: Defense in Depth Strategy - Layer 1 (Network Hardening: BEFORE reaching system) + Layer 2 (System Hardening: AFTER reaching system) = Complete Security. Both layers required for complete protection!

🌐 Network Hardening - "Stop Bad Guys at the Gate"

Real-Life Story

Scenario: A bank branch

Network Hardening = Security BEFORE entering bank:

  • Metal detector at entrance (scan for weapons)
  • Security guard checks "Do you have appointment?"
  • CCTV records who enters
  • Only specific door is open (not back door, not window)

Result: Most troublemakers stopped BEFORE they get inside!

In IT - Network Hardening Asks:

  • WHO can connect? (Which IP addresses, which users)
  • FROM WHERE can they connect? (Office network? Home? Anywhere?)
  • ON WHICH PORT? (Port 22 for SSH, Port 80 for website, Port 3306 for database)

⚙️ How to Do This in Practice

Example: Setting up Security Group (Firewall)

Option 1: Using Command Line (CLI)

# Create security group (like hiring a security guard)
aws ec2 create-security-group \
    --group-name my-web-server-security \
    --description "Allows website traffic and admin access"

# Allow website visitors (Port 80 - HTTP from anywhere)
aws ec2 authorize-security-group-ingress \
    --group-id sg-12345 \
    --protocol tcp \
    --port 80 \
    --cidr 0.0.0.0/0

# Allow only YOU to login (Port 22 - SSH from your IP only)
aws ec2 authorize-security-group-ingress \
    --group-id sg-12345 \
    --protocol tcp \
    --port 22 \
    --cidr 203.0.113.25/32

# What this means:
# - Anyone can visit your website (port 80)
# - Only YOU can login as admin (port 22 from your IP)
# - Everything else is BLOCKED

Option 2: Using AWS Website (Console)

  1. Go to AWS Console, search for "EC2"
  2. On left menu, click "Security Groups"
  3. Click orange "Create security group" button
  4. Give it a name: "my-web-server-security"
  5. Under "Inbound rules" click "Add rule":
    • Type: HTTP | Source: Anywhere (0.0.0.0/0)
    • Type: SSH | Source: My IP
  6. Click "Create security group"
  7. Now attach this to your EC2 server

💻 System Hardening - "Control What They Can Do Inside"

Figure 8: System Hardening Security Layers - Center: Operating System (OS) → User Access Control (IAM) → Service Hardening → Application Security → Logging & Monitoring (outer layer). Each layer adds protection!

Real-Life Story

Scenario: Employee at a company office

You passed security, entered the building (network hardening worked). Now:

  • Can you enter CEO's office? NO (access control)
  • Can you read HR files? NO (file permissions)
  • Can you access finance system? NO (user permissions)
  • Can you use your own laptop on company WiFi? NO (service restrictions)
  • Is someone watching what you do? YES (logging/monitoring)

Even though you're INSIDE the building, you can only do specific things!

System Hardening = Control AFTER someone reaches your server

1️⃣ User Management - "Who Can Login?"

Best Practices:

  • Create separate accounts for each person (NOT shared passwords!)
  • Disable "root" login (root = master key to everything)
  • Use SSH keys instead of passwords (SSH key = unique fingerprint, can't be guessed)
  • Give MINIMUM permissions needed (janitor shouldn't access CEO files)
  • Enable MFA - Multi-Factor Authentication (password + phone code)

Example: Creating a User with Limited Access

# On Linux server - create new user
sudo adduser john

# Add John to "developers" group (NOT admin group!)
sudo usermod -aG developers john

# Disable root login via SSH (super important!)
sudo nano /etc/ssh/sshd_config
# Change this line: PermitRootLogin no
sudo systemctl restart sshd

# Now:
# - John can login but has limited permissions
# - Root user cannot login remotely (safer!)
# - All activities will be logged

2️⃣ Service Hardening - "Stop Unnecessary Programs"

Real-Life Analogy: Your house has electricity outlets in every room, but you don't plug devices in every outlet. Why? Wastes electricity and increases fire risk!

Same with servers: Linux comes with many services running by default. Stop what you don't need! 

# See what's running
sudo systemctl list-units --type=service --state=running

# Stop unnecessary service (like Bluetooth on a server - why would server need Bluetooth?)
sudo systemctl stop bluetooth.service

# Make sure it doesn't start again after reboot
sudo systemctl disable bluetooth.service

# Common services to disable on servers:
# - bluetooth (servers don't use Bluetooth)
# - cups (printing service - servers don't print)
# - avahi-daemon (network discovery - not needed)

3️⃣ File Permissions - "Who Can Read/Write/Execute?"

Real-Life Story:

In an office:

  • Public notice board: Everyone can READ, only manager can WRITE
  • HR files: Only HR can READ and WRITE
  • Fire alarm button: Everyone can EXECUTE (press it)

Linux File Permissions Work the Same Way:

Permission Number What It Means Example
Read (r) 4 Can view file contents Read a document
Write (w) 2 Can modify file Edit a document
Execute (x) 1 Can run file as program Run a script

Exercise: Create a Secure Web Server

🎯 Objective

Apply security hardening principles to create a secure EC2 web server that:

  • Allows public web traffic (HTTP/HTTPS)
  • Allows SSH only from your IP
  • Has proper user management
  • Has correct file permissions
  • Logs all activities

📋 Pre-requisites

  • AWS account (free tier is sufficient)
  • Basic understanding of Linux commands
  • Terminal/Command prompt access
  • Your public IP address (Google "what is my IP")

⚙️ Step-by-Step Procedure

Method 1: Using AWS CLI

Step 1: Create Security Group (Network Hardening) 

# Create security group
aws ec2 create-security-group \
    --group-name secure-web-server \
    --description "Secure web server with restricted SSH" \
    --vpc-id vpc-xxxxx

# Note the SecurityGroupId from output (e.g., sg-12345678)

# Allow HTTP from anywhere
aws ec2 authorize-security-group-ingress \
    --group-id sg-12345678 \
    --protocol tcp \
    --port 80 \
    --cidr 0.0.0.0/0

# Allow HTTPS from anywhere
aws ec2 authorize-security-group-ingress \
    --group-id sg-12345678 \
    --protocol tcp \
    --port 443 \
    --cidr 0.0.0.0/0

# Allow SSH only from YOUR IP (replace with your actual IP)
aws ec2 authorize-security-group-ingress \
    --group-id sg-12345678 \
    --protocol tcp \
    --port 22 \
    --cidr YOUR_IP_ADDRESS/32

# Verify security group rules
aws ec2 describe-security-groups --group-ids sg-12345678

Step 2: Launch EC2 Instance

# Create SSH key pair
aws ec2 create-key-pair \
    --key-name my-secure-key \
    --query 'KeyMaterial' \
    --output text > my-secure-key.pem

# Set correct permissions for private key
chmod 400 my-secure-key.pem

# Launch EC2 instance
aws ec2 run-instances \
    --image-id ami-0c55b159cbfafe1f0 \
    --instance-type t2.micro \
    --key-name my-secure-key \
    --security-group-ids sg-12345678 \
    --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=SecureWebServer}]'

# Note the InstanceId and PublicIpAddress from output

Step 3: Connect and Apply System Hardening

# Connect to instance
ssh -i my-secure-key.pem ec2-user@YOUR_INSTANCE_PUBLIC_IP

# Once connected, run these commands:

# 1. Update system (OS Hardening)
sudo yum update -y

# 2. Install web server
sudo yum install httpd -y

# 3. Create new user with limited permissions (User Management)
sudo adduser webadmin
sudo usermod -aG wheel webadmin  # Add to sudo group

# 4. Disable root SSH login (Security Best Practice)
sudo nano /etc/ssh/sshd_config
# Change: PermitRootLogin no
# Save and exit (Ctrl+X, Y, Enter)
sudo systemctl restart sshd

# 5. Set up web files with correct permissions (File Permissions)
sudo echo "
My Secure Web Server
" > /var/www/html/index.html
sudo chmod 644 /var/www/html/index.html  # Owner can edit, others can view
sudo chown apache:apache /var/www/html/index.html

# 6. Start web server
sudo systemctl start httpd
sudo systemctl enable httpd  # Auto-start on reboot

# 7. Stop unnecessary services (Service Hardening)
sudo systemctl stop postfix  # Mail service not needed
sudo systemctl disable postfix

# 8. Enable logging (Monitoring)
sudo tail -f /var/log/httpd/access_log  # View web server logs
Method 2: Using AWS Console (GUI)

Step 1: Create Security Group

  1. Go to AWS Console → EC2 → Security Groups
  2. Click "Create security group"
  3. Name: secure-web-server
  4. Description: Secure web server with restricted SSH
  5. Inbound rules:
    • Type: HTTP, Source: 0.0.0.0/0
    • Type: HTTPS, Source: 0.0.0.0/0
    • Type: SSH, Source: My IP
  6. Click "Create security group"

Step 2: Launch EC2 Instance

  1. Go to EC2 → Instances → Launch Instance
  2. Name: SecureWebServer
  3. AMI: Amazon Linux 2
  4. Instance type: t2.micro (free tier)
  5. Key pair: Create new or use existing
  6. Network settings: Select your security group
  7. Click "Launch instance"
  8. Wait for instance to be "Running"
  9. Note the Public IPv4 address

Step 3: Connect and Configure

  1. Click "Connect" button on instance
  2. Follow SSH instructions or use "EC2 Instance Connect"
  3. Run the same system hardening commands from Method 1 Step 3

  1. Visit http://YOUR_INSTANCE_IP in browser → See "My Secure Web Server"
  2. SSH from your computer → Success
  3. SSH from different computer/network → Denied (because security group allows only your IP)
  4. Check SSH config → Root login disabled
  5. Check services → Unnecessary services stopped
# Test from your computer

Exercise 2: Implement Multi-AZ RDS Database with Automated Backups

⏱️ Estimated Time: 25 minutes

🎯 Objective: Create a highly available database using Multi-AZ deployment with automated backups, demonstrating Reliability and Operational Excellence pillars

Prerequisites

  • AWS account with appropriate permissions
  • AWS CLI installed and configured (for CLI method)
  • Basic understanding of databases
  • VPC with at least 2 subnets in different Availability Zones

What You'll Learn

  • ✅ How to create Multi-AZ RDS database for high availability
  • ✅ Configure automated backups and retention policies
  • ✅ Implement security best practices for databases
  • ✅ Monitor database performance and health
  • ✅ Test failover scenarios

Method 1: Using AWS CLI

Step 1: Create DB Subnet Group (Required for Multi-AZ) 

# Create subnet group spanning multiple AZs
aws rds create-db-subnet-group \
    --db-subnet-group-name my-db-subnet-group \
    --db-subnet-group-description "Subnet group for Multi-AZ RDS" \
    --subnet-ids subnet-12345678 subnet-87654321 \
    --tags Key=Name,Value=MyDBSubnetGroup

# Verify subnet group created
aws rds describe-db-subnet-groups \
    --db-subnet-group-name my-db-subnet-group

Replace subnet-12345678 and subnet-87654321 with your actual subnet IDs from different AZs

Step 2: Create Security Group for Database

# Create security group for RDS
aws ec2 create-security-group \
    --group-name rds-security-group \
    --description "Security group for RDS database" \
    --vpc-id vpc-xxxxx

# Allow MySQL port 3306 only from application servers (NOT from internet!)
# Replace 10.0.1.0/24 with your application subnet CIDR
aws ec2 authorize-security-group-ingress \
    --group-id sg-xxxxx \
    --protocol tcp \
    --port 3306 \
    --cidr 10.0.1.0/24

# Verify security group
aws ec2 describe-security-groups --group-ids sg-xxxxx

Step 3: Create Multi-AZ RDS Instance

# Create MySQL database with Multi-AZ enabled
aws rds create-db-instance \
    --db-instance-identifier my-secure-database \
    --db-instance-class db.t3.micro \
    --engine mysql \
    --engine-version 8.0.35 \
    --master-username admin \
    --master-user-password 'YourStrongPassword123!' \
    --allocated-storage 20 \
    --storage-type gp3 \
    --storage-encrypted \
    --multi-az \
    --db-subnet-group-name my-db-subnet-group \
    --vpc-security-group-ids sg-xxxxx \
    --backup-retention-period 7 \
    --preferred-backup-window "03:00-04:00" \
    --preferred-maintenance-window "sun:04:00-sun:05:00" \
    --enable-cloudwatch-logs-exports '["error","general","slowquery"]' \
    --deletion-protection \
    --tags Key=Name,Value=MySecureDatabase Key=Environment,Value=Production

# Check instance status (takes 5-10 minutes to become available)
aws rds describe-db-instances \
    --db-instance-identifier my-secure-database \
    --query 'DBInstances[0].[DBInstanceStatus,MultiAZ,Endpoint.Address]'

What this command does:

  • --multi-az: Enables automatic failover to standby in different AZ
  • --storage-encrypted: Encrypts data at rest (Security pillar)
  • --backup-retention-period 7: Keeps daily backups for 7 days (Reliability)
  • --deletion-protection: Prevents accidental deletion
  • --enable-cloudwatch-logs-exports: Sends logs to CloudWatch (Operational Excellence)

Step 4: Enable Enhanced Monitoring

# Modify instance to enable enhanced monitoring
aws rds modify-db-instance \
    --db-instance-identifier my-secure-database \
    --monitoring-interval 60 \
    --monitoring-role-arn arn:aws:iam::ACCOUNT-ID:role/rds-monitoring-role \
    --apply-immediately

# View monitoring metrics
aws cloudwatch get-metric-statistics \
    --namespace AWS/RDS \
    --metric-name CPUUtilization \
    --dimensions Name=DBInstanceIdentifier,Value=my-secure-database \
    --start-time 2024-01-01T00:00:00Z \
    --end-time 2024-01-01T23:59:59Z \
    --period 3600 \
    --statistics Average

Step 5: Create Manual Snapshot (Additional Backup) 

# Create manual backup snapshot
aws rds create-db-snapshot \
    --db-instance-identifier my-secure-database \
    --db-snapshot-identifier my-database-snapshot-$(date +%Y%m%d)

# List all snapshots
aws rds describe-db-snapshots \
    --db-instance-identifier my-secure-database
