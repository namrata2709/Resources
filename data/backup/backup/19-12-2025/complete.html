🔄 CI/CD Workflow Overview

🌍 Real-Life Analogy

Think of CI/CD like a modern car assembly line:

Imagine a Toyota factory. When workers add a new part to the car, they don't wait until the entire car is built to test if it works. Instead, at every station, quality checks happen immediately. If a door doesn't fit properly, they catch it right away - not when the car reaches the showroom!

Similarly, in software development with CI/CD, every time a developer writes new code (adds a "part"), automated systems immediately test it (quality check). If something breaks, the developer knows within minutes, not weeks later when customers complain. This "continuous inspection" ensures the final product (software) works perfectly, just like how Toyota's assembly line produces reliable cars.

📖 Detailed Explanation

In modern software development using Agile methodologies with DevOps practices, developers work in short cycles called sprints. Within each sprint, continuous testing and integration happen throughout the day - not just at the end of a project.

What is it? CI/CD stands for Continuous Integration and Continuous Deployment/Delivery. It's an automated system that builds, tests, and deploys your code changes automatically whenever you make updates.

Why does it matter? Without CI/CD, testing happens manually, taking days or weeks. Bugs discovered late cost 10-100 times more to fix than bugs caught early. CI/CD catches problems within minutes, saving millions in development costs and preventing customer-facing failures.

How does it work? When a developer pushes code to GitHub, webhooks automatically trigger a pipeline. This pipeline checks out the code, compiles it, runs tests, analyzes quality, and packages it - all without human intervention. If any step fails, the developer gets immediate feedback.

🔑 Key Concepts

  • Version Control (Git): Like Google Docs' version history for code - tracks every change made
  • Local Repository (.git): Storage on your computer that remembers all code versions
  • Remote Repository (GitHub): Cloud storage where team shares code - like Dropbox for developers
  • Feature Branch: Separate workspace for new features - prevents breaking main code
  • Main Branch: The "production-ready" version - always should work perfectly
  • Pull Request (PR): Request to merge your code - requires approval from team lead
  • Webhooks: Automatic triggers - like motion sensors that start CI/CD pipeline
  • CI Pipeline: Automated assembly line for code - builds, tests, and validates

⚙️ Practical Implementation

Learn how to implement CI/CD using both AWS CLI and AWS Management Console.

Method 1: Using AWS CLI

Prerequisites:

  • AWS CLI installed and configured (aws configure)
  • IAM permissions: CodeBuild, CodePipeline, S3, CloudWatch
  • GitHub repository with application code
  • buildspec.yml file in repository root

Step 1: Create buildspec.yml File

# buildspec.yml - Instructions for CI pipeline
version: 0.2

phases:
  install:
    runtime-versions:
      nodejs: 18
  pre_build:
    commands:
      - echo Installing dependencies...
      - npm install
  build:
    commands:
      - echo Build started on `date`
      - npm run build
      - npm test
  post_build:
    commands:
      - echo Build completed on `date`

artifacts:
  files:
    - '**/*'

Explanation: This file tells AWS CodeBuild how to build and test your application automatically.

Step 2: Create CodeBuild Project

aws codebuild create-project \
  --name my-nodejs-project \
  --source type=GITHUB,location=https://github.com/username/repo.git \
  --artifacts type=S3,location=my-build-artifacts-bucket \
  --environment type=LINUX_CONTAINER,image=aws/codebuild/standard:7.0,computeType=BUILD_GENERAL1_SMALL \
  --service-role arn:aws:iam::123456789012:role/CodeBuildServiceRole \
  --region us-east-1

Expected output: JSON response with project details including ARN and creation timestamp.

Step 3: Start Build

aws codebuild start-build \
  --project-name my-nodejs-project \
  --region us-east-1

Explanation: Manually triggers build process. In production, webhook triggers this automatically on code push.

Step 4: Check Build Status

aws codebuild batch-get-builds \
  --ids my-nodejs-project:build-id-12345 \
  --region us-east-1

Method 2: Using AWS Management Console (GUI)

  1. Navigate: Go to AWS Management Console → Developer Tools → CodeBuild
  2. Create Build Project:
    • Click "Create build project" (orange button)
    • Project name: my-nodejs-project
    • Description: CI pipeline for Node.js application
  3. Configure Source:
    • Source provider: GitHub
    • Connect to GitHub using OAuth
    • Select repository from dropdown
    • Branch: main
  4. Configure Environment:
    • Environment image: Managed image
    • Operating system: Ubuntu
    • Runtime: Standard
    • Image: aws/codebuild/standard:7.0
    • Service role: Create new service role
  5. Configure Buildspec:
    • Build specifications: Use a buildspec file
    • Buildspec name: buildspec.yml (default)
  6. Configure Artifacts:
    • Type: Amazon S3
    • Bucket name: my-build-artifacts-bucket
    • Path: builds/
    • Artifacts packaging: Zip
  7. Configure Logs:
    • CloudWatch logs: Enabled
    • Group name: /aws/codebuild/my-nodejs-project
    • Stream name: build-logs
  8. Create Project: Click "Create build project"
  9. Start Build:
    • Click "Start build" button
    • Monitor progress in real-time
    • View logs in CloudWatch or directly in console

🖥️ Virtualization Technology

🌍 Real-Life Analogy

Think of virtualization like an apartment building:

Imagine you own a large piece of land (physical server). You could build one massive mansion and live alone, wasting 90% of the space. Or you could build an apartment building with 10 units, where each family has their own separate apartment (virtual machine).

Each apartment has its own kitchen, bathroom, and living space (operating system and allocated resources). If one apartment has a fire, only that unit is affected - others remain safe (isolation). The building manager (hypervisor) controls utilities, ensures fair distribution of electricity and water, and prevents one tenant from affecting others.

This is exactly what virtualization does - takes one expensive server and divides it into multiple independent virtual machines, each running its own operating system, completely isolated from others.

📖 Detailed Explanation

Virtualization is the technology that allows running multiple virtual computers (Virtual Machines) on a single physical server. Before virtualization, organizations had to purchase separate physical servers for different applications, leading to poor resource utilization (typically 10-15%) and high costs.

What is it? Virtualization creates software-based virtual computers that share the same physical hardware. Each virtual machine (VM) operates independently with its own operating system, allocated CPU, RAM, and storage.

Why does it matter? A company spending $100,000 on 20 physical servers with 15% utilization wastes $85,000. Virtualization increases utilization to 70-80%, effectively reducing hardware costs by 60-70% while improving flexibility and disaster recovery capabilities.

How does it work? A hypervisor (virtualization software) sits between physical hardware and virtual machines. It manages resource allocation, ensures isolation between VMs, and presents virtual hardware to each VM. Each VM sees its own CPU, RAM, and disk, but these are carved from the physical server's actual resources.

🔑 Key Concepts

  • Physical Server: Actual hardware machine with CPU, RAM, storage - the foundation
  • Virtual Machine (VM): Software-based computer running inside physical hardware
  • Hypervisor: Software creating and managing VMs (VMware, VirtualBox, Xen, Hyper-V)
  • Guest OS: Operating system running inside each virtual machine
  • Host OS: Operating system running on physical hardware (Type 2 only)
  • Resource Allocation: Pre-assigning specific CPU cores, RAM, disk to each VM
  • Isolation: VMs separated from each other for security and stability
  • Hardware Abstraction: VMs see virtualized hardware, not physical components

⚙️ Practical Implementation

Learn how to create virtual machines using both AWS CLI (EC2) and AWS Management Console.

Method 1: Using AWS CLI

Prerequisites:

  • AWS CLI installed and configured
  • IAM permissions: EC2FullAccess or EC2:RunInstances
  • VPC and subnet already created in target region
  • Key pair created for SSH access

Step 1: Create Security Group

aws ec2 create-security-group \
  --group-name web-server-sg \
  --description "Security group for web server VM" \
  --vpc-id vpc-0123456789abcdef0 \
  --region us-east-1

Explanation: Creates firewall rules for controlling network access to VM.

Step 2: Add Inbound Rules

# Allow SSH access
aws ec2 authorize-security-group-ingress \
  --group-id sg-0123456789abcdef0 \
  --protocol tcp \
  --port 22 \
  --cidr 0.0.0.0/0

# Allow HTTP access
aws ec2 authorize-security-group-ingress \
  --group-id sg-0123456789abcdef0 \
  --protocol tcp \
  --port 80 \
  --cidr 0.0.0.0/0

Step 3: Launch EC2 Instance (Virtual Machine)

aws ec2 run-instances \
  --image-id ami-0c55b159cbfafe1f0 \
  --instance-type t2.micro \
  --key-name my-key-pair \
  --security-group-ids sg-0123456789abcdef0 \
  --subnet-id subnet-0123456789abcdef0 \
  --count 1 \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Name,Value=WebServerVM}]' \
  --region us-east-1

Expected output: JSON response with instance ID, private IP, and current state (pending).

Step 4: Check Instance Status

aws ec2 describe-instances \
  --instance-ids i-0123456789abcdef0 \
  --query 'Reservations[0].Instances[0].[InstanceId,State.Name,PublicIpAddress]' \
  --output table

Method 2: Using AWS Management Console (GUI)

  1. Navigate: Go to AWS Management Console → EC2 → Instances
  2. Launch Instance:
    • Click "Launch Instance" (orange button)
    • Name: WebServerVM
  3. Choose AMI (Operating System):
    • Select "Amazon Linux 2023 AMI" (free tier eligible)
    • Or choose Ubuntu Server 22.04 LTS
    • Architecture: 64-bit (x86)
  4. Choose Instance Type:
    • Select t2.micro (1 vCPU, 1 GB RAM - free tier)
    • Or t2.small (1 vCPU, 2 GB RAM) for more resources
  5. Configure Key Pair:
    • Create new key pair or select existing
    • Key pair name: my-web-server-key
    • Key pair type: RSA
    • File format: .pem (for Linux/Mac) or .ppk (for Windows/PuTTY)
    • Download and save securely
  6. Network Settings:
    • VPC: Select your VPC (or use default)
    • Subnet: Select public subnet
    • Auto-assign public IP: Enable
    • Firewall (security groups): Create security group
    • Security group name: web-server-sg
    • Description: Allow SSH and HTTP
    • Inbound rules:
      • SSH (port 22) from My IP
      • HTTP (port 80) from Anywhere
  7. Configure Storage:
    • Root volume: 8 GB gp3 (default)
    • Volume type: General Purpose SSD (gp3)
    • Delete on termination: Yes
  8. Advanced Details (Optional):
    • User data: Enter startup script if needed
    • Example: Install web server on boot
  9. Review and Launch:
    • Review all settings
    • Click "Launch instance"
    • Wait 2-3 minutes for instance to start
  10. Connect to VM:
    • Select instance, click "Connect"
    • Choose SSH client tab
    • Follow connection instructions
    • Command: ssh -i my-key.pem ec2-user@public-ip

✅ Success Indicators:

  • Instance shows "Running" state with green dot
  • Status checks: 2/2 checks passed
  • Public IP address assigned and accessible
  • Can SSH into instance successfully
  • CPU utilization visible in monitoring tab

✅ Advantages of Virtualization

🌍 Real-Life Analogy

Think of virtualization advantages like a modern co-working space:

Before co-working spaces, small startups had to rent entire office buildings. A 10-person startup would rent a 50-desk office, using only 20% of the space while paying 100% of rent, electricity, and maintenance. What a waste!

Co-working spaces changed everything. Now multiple companies share one building efficiently. Each company has private offices (isolation), shared meeting rooms (resource sharing), and flexible desk allocation (scalability). If one company grows from 5 to 20 people, they simply rent more desks. If another company fails, it doesn't affect others.

This is exactly what virtualization does for servers - transforms wasteful single-use into efficient shared resources with isolation, flexibility, and dramatic cost savings.

📖 Detailed Explanation

Virtualization transformed IT infrastructure by solving critical resource utilization and management problems. Before virtualization, organizations faced poor hardware utilization (typically 10-15%), high costs for multiple physical servers, and complex management of distributed hardware.

What is it? The advantages of virtualization are the specific benefits organizations gain by implementing VM technology - primarily better resource utilization, application isolation, and simplified management.

Why does it matter? A company with 50 physical servers running at 15% utilization wastes 85% of their $250,000 hardware investment. Virtualization increases utilization to 75%, effectively saving $150,000 in hardware costs plus $30,000 annually in electricity.

How does it work? By sharing physical resources across multiple VMs, virtualization achieves 5x better utilization. The hypervisor's intelligent resource management prevents wastage while maintaining isolation, ensuring one VM's problems never affect others.

🔑 Key Advantages

  • Better Hardware Utilization: Increases from 10-15% to 70-80% usage
  • Cost Reduction: Reduces hardware spending by 50-70%, power by 60%
  • Application Isolation: Crashes in one VM don't affect others

  • Simplified Disaster Recovery: Snapshot entire VM state instantly
  • Hardware Independence: Migrate VMs between different physical servers
  • Rapid Provisioning: Deploy new VMs in minutes vs weeks for physical servers

❌ Disadvantages of Virtualization

🌍 Real-Life Analogy

📦 Containerization Fundamentals

🌍 Real-Life Analogy

Think of containers like standardized shipping containers:

Before shipping containers, cargo ships were nightmares. Each cargo needed custom handling - bananas packed differently than cars, fragile items needed special care, loading/unloading took weeks. Ports needed specialized equipment for every cargo type. Chaos!

Then came standardized shipping containers in 1956. Brilliant! Every container is same size (20 or 40 feet). Docker containers work exactly the same way. Instead of each application needing custom setup (like VMs with full OS), containers are standardized. Each container has application + minimal dependencies. The host OS handles ALL containers identically. Deploy anywhere. Fast. Efficient. Revolutionary!

📖 Detailed Explanation

Containerization is a lightweight alternative to full virtualization that runs applications in isolated environments without requiring a full operating system for each instance. Unlike VMs that include a complete OS, containers share the host operating system's kernel while maintaining application isolation.

What is it? Containerization packages applications with only their required libraries and dependencies - not a full OS. Containers share the host OS kernel, making them dramatically lighter and faster than VMs.

Why does it matter? A company running 100 microservices as VMs wastes 200-400 GB RAM on duplicate operating systems. With containers, that same 100 microservices might consume only 20-30 GB total. That's 10x better efficiency, enabling massive cost savings and instant scaling.

How does it work? Linux kernel features (cgroups and namespaces) provide resource isolation and management without needing a hypervisor or separate OS. When containers need CPU or RAM, cgroups dynamically allocate from the host. When done, resources return to the pool. No wasteful pre-allocation!

🔑 Key Concepts

  • Container: Lightweight isolated process running application with minimal dependencies
  • Host OS Kernel Sharing: All containers share same OS kernel from host machine
  • No OS Duplication: Containers don't include full operating system
  • CGroups (Control Groups): Linux feature for dynamic resource allocation and limits
  • Namespaces: Linux feature providing process isolation (PID, network, filesystem)
  • Lightweight: Container images are MBs instead of GBs (VM images)
  • Fast Startup: Containers start in seconds because no OS boot required
  • Portable: Run consistently across different environments (dev, test, production)

⚙️ How Containers Share Resources

CGroups (Control Groups) - Dynamic Resource Allocation:

  • Linux kernel feature managing resource allocation
  • Dynamically shares CPU, memory, disk among containers
  • When container needs resources, cgroups allocate from host
  • When container finishes work, resources released back to pool
  • No pre-allocation - prevents resource wastage
  • Can set limits to prevent one container monopolizing resources

Namespaces - Process Isolation:

  • PID Namespace: Each container sees its own process tree, process 1 is container's main process
  • Network Namespace: Each container has own network stack, IP address, ports
  • Mount Namespace: Each container has own filesystem view, can't see host files
  • UTS Namespace: Each container can have own hostname
  • IPC Namespace: Isolates inter-process communication between containers
  • User Namespace: Maps container root user to non-privileged host user

🐳 Docker Architecture

🌍 Real-Life Analogy

Think of Docker architecture like ordering food delivery:

You (Docker Client) open your phone app and order pizza. You don't cook it yourself - you just tell the app what you want. The app sends your order to the restaurant (Docker Daemon) which does all the actual work - making pizza, baking it, packaging it.

The restaurant has recipes (Docker Images) stored in their kitchen. When you order, they use the recipe to create your actual pizza (Container). If they don't have a recipe, they check the recipe book supplier (Docker Registry/Hub) to get it.

📖 Detailed Explanation

Docker is the most popular containerization platform, consisting of several components that work together to create, manage, and run containers. Understanding Docker's architecture is essential for working with containers effectively.

What is it? Docker uses a client-server architecture where the Docker CLI (client) communicates with the Docker daemon (server) that does the actual work of building, running, and managing containers.

Why does it matter? The separation between client and daemon allows remote management, better resource control, and security. One daemon can serve multiple clients. You can manage containers on remote servers from your laptop using Docker CLI.

How does it work? When you run docker build or docker run, the CLI sends requests via REST API to the daemon. The daemon executes operations - pulling images from registry, creating containers, managing networks. This separation keeps complexity hidden from users.

🔑 Key Components

  • Docker Client (CLI): Command-line interface where users issue commands (docker build, run, push)
  • Docker Daemon (dockerd): Background service managing Docker objects (images, containers, networks, volumes)
  • Docker Images: Read-only templates for creating containers (like blueprints)
  • Docker Containers: Running instances of Docker images (actual running applications)
  • Docker Registry: Repository for storing and distributing images (Docker Hub is public registry)
  • Dockerfile: Text file with instructions to build Docker images
  • Docker Volumes: Persistent storage mechanism for container data
  • Docker Networks: Virtual networks connecting containers for communication

Why Port Mapping?

  • Containers have isolated network by default
  • Cannot access container from outside without port mapping
  • Maps host machine port to container port
  • Allows external access to containerized applications

Question 1

What is the main difference between virtualization and containerization?

Answer

Virtualization runs full operating systems for each VM, while containerization shares the host OS kernel among containers. VMs include complete OS (2-4 GB per instance), whereas containers only include application code and minimal dependencies (MBs in size). This makes containers much lighter, faster to start (seconds vs minutes), and more efficient for resource utilization.

Question 2

Explain what a Dockerfile is and its purpose in the Docker workflow.

Answer

A Dockerfile is a plain text file containing step-by-step instructions to build a Docker image. It serves as a blueprint specifying the base image, dependencies to install, files to copy, and commands to run. Each instruction in the Dockerfile creates a new layer in the resulting image, enabling efficient caching and version control of the application environment.

Question 3

What are CGroups and Namespaces in the context of containerization?

Answer

CGroups (Control Groups) are Linux kernel features that manage and limit resource allocation (CPU, RAM, disk) to containers dynamically. Namespaces provide process isolation by creating separate views of system resources like process IDs, network interfaces, and filesystems. Together, they enable containers to run isolated from each other while efficiently sharing host resources.

Question 4

Why is it important to use volumes in Docker instead of storing data inside containers?

Answer

Containers are ephemeral by design - all data inside a container is lost when the container is deleted. Volumes provide persistent storage that exists independently of container lifecycle. This ensures critical data like databases, user uploads, or configuration files survive container updates, crashes, or deletions. Volumes also enable data sharing between containers and better I/O performance.

Question 5

Describe the role of Docker Hub in the Docker ecosystem.

Answer

Docker Hub is a cloud-based registry service for storing and distributing Docker images. It acts as a central repository where developers can push their custom images and pull official or community images. Docker Hub provides version control through image tagging, automated builds from GitHub repositories, and both public and private repository options for image storage and collaboration.

Question 6

What is the difference between a Docker image and a Docker container?

Answer

A Docker image is a read-only template containing application code, dependencies, and configuration - essentially a blueprint. A Docker container is a running instance of an image - the actual process executing the application. You can create multiple containers from a single image, and each container operates independently with its own writable layer on top of the shared image layers.

Question 7

How does port mapping work in Docker and why is it necessary?

Answer

Port mapping connects a port on the host machine to a port inside the container using the -p flag (e.g., -p 8080:80). Containers have isolated networks by default, so without port mapping, applications inside containers aren't accessible from outside. Port mapping acts like mail forwarding - external requests to host:8080 get routed to container:80, enabling external access to containerized applications.

Question 8

What are the main advantages of using containerization for microservices architecture?

Answer

Containerization provides lightweight isolation perfect for microservices - each service runs independently in its own container. Benefits include rapid scaling (seconds vs minutes for VMs), efficient resource usage (100+ containers per server), consistent environments across dev/prod, easy deployment and rollback, and independence between services. If one service crashes, others continue running unaffected.

Question 9

Explain what happens when you run the command "docker run -d -p 8080:80 nginx".

Answer

This command creates and starts an nginx container in detached mode (-d runs in background). Docker daemon pulls the nginx image from Docker Hub if not locally available, creates a new container instance, maps host port 8080 to container port 80 (-p 8080:80), and starts the nginx web server. You can access it at http://localhost:8080, which routes to nginx running on port 80 inside the container.

Question 10

What is the purpose of a CI/CD pipeline and how does it improve software development?

Answer

CI/CD pipeline automates code integration, testing, and deployment processes. When developers push code, the pipeline automatically builds, runs tests, performs security scans, and packages the application. This catches bugs within minutes instead of weeks, ensures consistent quality, reduces manual errors, and enables rapid deployment. It transforms software delivery from risky manual process to reliable automated workflow.

Question 11

How would you troubleshoot a container that starts but exits immediately?

Answer

First, check container logs with "docker logs container-id" to identify error messages. Common causes include: main process exiting immediately, misconfigured CMD/ENTRYPOINT, missing dependencies, or application crashes on startup. Verify the Dockerfile's CMD runs a foreground process (not background), check environment variables are set correctly, and use "docker exec -it container-id bash" on a running container to debug interactively.

Question 12

Why should you avoid using the "latest" tag for Docker images in production?

Answer

The "latest" tag is a moving target - it points to the most recently pushed image version. Using it in production means deployments aren't reproducible; you might deploy version 1.0 today and accidentally deploy 2.0 tomorrow with breaking changes. Always use specific version tags (e.g., myapp:1.2.3) to ensure predictable deployments, enable easy rollbacks, and maintain consistency across environments.

Question 13

Describe a scenario where you would choose VMs over containers.

Answer

Choose VMs when you need to run different operating systems (Windows app on Linux host), require maximum security isolation for multi-tenant environments, or have legacy applications needing full OS dependencies. VMs are also better for running stateful applications requiring dedicated resources or when regulatory compliance mandates hardware-level isolation. Containers and VMs often work together - databases on VMs, microservices in containers.

Question 14

What is multi-stage build in Docker and why is it beneficial?

Answer

Multi-stage builds use multiple FROM statements in one Dockerfile - one stage for building (with compilers, build tools) and another for production (only runtime dependencies). The final image contains only artifacts copied from the build stage, not build tools. This dramatically reduces image size (often 10x smaller), improves security by excluding unnecessary packages, and speeds up deployment while maintaining clean, maintainable Dockerfiles.

Question 15

How do you ensure your Docker containers run securely?

Answer

Security best practices include: never run containers as root (use USER directive), use official base images from trusted sources, scan images for vulnerabilities before deployment (Trivy, Snyk), implement resource limits to prevent DoS, keep images updated with security patches, use secrets management instead of hardcoding credentials, enable Docker Content Trust for image verification, and never expose Docker daemon without TLS encryption.

Question 16

Explain the concept of Docker image layers and why they matter.

Answer

Each instruction in a Dockerfile creates a new read-only layer in the image. Layers are cached and reused across builds and images, dramatically speeding up builds and reducing storage. When you update code but not dependencies, Docker rebuilds only affected layers. Multiple images can share base layers, saving disk space. Understanding layers is crucial for optimizing Dockerfile order - put frequently changing instructions (COPY code) last to maximize cache efficiency.

Question 17

What strategies would you use to optimize Docker build times?

Answer

Optimization strategies include: order instructions from least to most frequently changing (base image first, code last), use .dockerignore to exclude unnecessary files, leverage build cache by copying package files before application code, implement multi-stage builds to separate build and runtime, minimize layer count by combining RUN commands, use smaller base images (alpine variants), and enable BuildKit for parallel builds and better caching.

Question 18

How does Docker differ from virtual machines in terms of resource efficiency?

Answer

Docker containers share the host OS kernel, eliminating the 2-4 GB RAM overhead per instance required by VM operating systems. Containers use dynamic resource allocation via CGroups, releasing resources when idle, whereas VMs pre-allocate resources that sit idle 50-70% of the time. This enables running 100-1000 containers per server compared to 10-20 VMs, with container startup in seconds versus minutes for VMs.

Question 19

What are health checks in Docker and why are they important?

Answer

Health checks are automated tests defined in Dockerfile using HEALTHCHECK instruction that periodically verify container is functioning correctly. They run commands like HTTP requests to health endpoints or database connection tests. If health checks fail repeatedly, orchestration tools can automatically restart or replace unhealthy containers. This enables self-healing systems and prevents routing traffic to broken containers, essential for production reliability.

Question 20

Describe the Docker client-server architecture and how they communicate.

Answer

Docker uses client-server architecture where the Docker CLI (client) communicates with Docker daemon (server) via REST API. When you run commands like "docker build", the CLI sends requests to the daemon which performs actual work - building images, running containers, managing networks. This separation allows remote management, better security through controlled access, and enables one daemon to serve multiple clients across different machines.

Question 21

How would you implement a CI/CD pipeline for a Dockerized application?

Answer

Pipeline stages would include: (1) Code checkout from Git on push/PR, (2) Build Docker image from Dockerfile, (3) Run automated tests inside container, (4) Scan image for vulnerabilities with Trivy/Snyk, (5) Push tagged image to registry (Docker Hub/ECR), (6) Deploy to staging environment for integration tests, (7) After approval, deploy same image to production. Use tools like GitHub Actions, Jenkins, or AWS CodePipeline for orchestration.

Question 22

What considerations should you keep in mind when containerizing a stateful application like a database?

Answer

Critical considerations include: always use volumes for data persistence (never store in container), implement proper backup strategies for volume data, ensure adequate resource allocation (memory, IOPS), configure health checks for database connectivity, use StatefulSets in Kubernetes for ordered deployment, implement data replication across availability zones, plan for graceful shutdown procedures, and consider if managed database services (RDS) might be better than self-managed containers for production databases.

Question 23

Explain how you would handle secrets and sensitive data in Docker containers.

Answer

Never hardcode secrets in Dockerfiles or images. Instead: use Docker secrets (in Swarm) or Kubernetes secrets, pass via environment variables from secure sources at runtime, integrate with secrets managers (AWS Secrets Manager, HashiCorp Vault), mount secrets as files from external sources, use .dockerignore to prevent accidental inclusion, implement principle of least privilege for container access, rotate secrets regularly, and audit secret access patterns.

Question 24

What is the difference between CMD and ENTRYPOINT in a Dockerfile?

Answer

CMD specifies default command and arguments that can be overridden when running container. ENTRYPOINT defines the main executable that always runs, treating container as an executable. Best practice: use ENTRYPOINT for the main command (e.g., ["python"]) and CMD for default arguments (e.g., ["app.py"]). When both are used, CMD provides default arguments to ENTRYPOINT. Users can override CMD but ENTRYPOINT requires --entrypoint flag to change.

For deeper analysis: check container logs with "docker logs", inspect container details with "docker inspect", use cAdvisor for historical metrics, integrate with monitoring tools like Prometheus and Grafana, set resource limits to prevent exhaustion, monitor host system resources, and use "docker system df" to track disk usage. Implement alerting for resource threshold violations.

Method 1: Using Docker CLI

const express = require('express');
const mysql = require('mysql2/promise');
const app = express();

app.use(express.json());

let db;

async function initDB() {
  db = await mysql.createPool({
    host: process.env.DB_HOST || 'db',
    user: process.env.DB_USER || 'root',
    password: process.env.DB_PASSWORD || 'password',
    database: process.env.DB_NAME || 'appdb',
    waitForConnections: true,
    connectionLimit: 10
  });
}

app.get('/api/health', (req, res) => {
  res.json({ status: 'healthy', service: 'backend' });
});

app.get('/api/users', async (req, res) => {
  try {
    const [rows] = await db.query('SELECT * FROM users');
    res.json(rows);
  } catch (error) {
    res.status(500).json({ error: error.message });
  }
});

app.post('/api/users', async (req, res) => {
  try {
    const { name, email } = req.body;
    await db.query('INSERT INTO users (name, email) VALUES (?, ?)', [name, email]);
    res.json({ message: 'User created' });
  } catch (error) {
    res.status(500).json({ error: error.message });
  }
});

app.listen(5000, async () => {
  await initDB();
  console.log('Backend running on port 5000');
});
EOF
